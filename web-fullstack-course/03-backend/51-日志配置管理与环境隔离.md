# 51-日志配置管理与环境隔离

## 目标

当服务运行在自己的电脑上时，出了问题可以直接打断点；当服务部署到几十台服务器上、每天处理百万请求时，定位问题唯一的依据就是日志和配置。日志回答“刚才发生了什么、经过了哪些环节、是谁触发的”，配置回答“这个环境连哪个数据库、用什么密钥、以什么级别记录”。二者共同决定一个后端系统是否“可运维”。

本单元学习以 pino/winston 为核心的结构化日志体系，以及符合 12-factor 的配置管理与多环境隔离方法。

完成本知识单元后，学员应能够：

1. 区分 trace/debug/info/warn/error/fatal 各级别的语义，按“是否需要行动、行动紧急程度”选择级别。
2. 使用 pino 或 winston 输出结构化（JSON）日志，替代难以检索的字符串拼接式 `console.log`。
3. 在中间件生成请求 ID，并通过 AsyncLocalStorage 在整条调用链上透传，实现一次请求的日志聚合。
4. 对密码、令牌、身份证号、银行卡号等敏感字段做统一脱敏，保证日志可分享、可入库。
5. 按 12-factor 原则组织配置：环境变量注入、配置分层、单一配置模块、dev/test/prod 多环境隔离。
6. 保证密钥不进入版本库，使用启动配置校验（zod）在进程启动时 fail fast 地发现缺失或非法配置。

本单元的核心信念是：日志是写给“未来排查故障的你和机器”看的，配置是“同一份代码在不同环境安全运行”的唯一变量；二者都必须在系统上线之前设计好，而不是出事后补救。

## 技术栈

| 工具或库 | 当前稳定版本线 | 用途 | 学习要求 |

| pino | 9.x 稳定版 | 高性能结构化日志 | 掌握 logger 实例、子 logger、级别、redact |

约定：

- 主线示例使用 pino；winston 的等价写法在关键处对照给出。

## 详细的理论知识讲解和示例伪代码

### 1. 从 console.log 到可运维日志

#### 1.1 console.log 为什么不够用

`console.log` 适合临时打印，但在服务器上会暴露四个问题：

- 只有字符串，要排查“某个用户的某次下单”时只能肉眼搜索，无法按字段过滤；
- 没有级别区分，正常心跳和致命错误混在一起，无法只看 error；
- 多并发请求的日志交错出现，无法知道哪几行属于同一次请求；
- 不能按环境切换输出目标（开发打印终端、生产输出到采集系统）。

#### 1.2 可运维日志的四个标准

```text
1. 结构化：每条日志是一个带固定字段的 JSON 对象，可被检索系统按字段查询
2. 有级别：debug/info/warn/error 区分严重程度，可按环境过滤
3. 可关联：同一请求/任务的日志共享 requestId / jobId，可串成链路
4. 已脱敏：密码、令牌、卡号等在记录前被移除或打码
```

#### 1.3 一条合格日志长什么样

```json
{
  "level": "info",
  "time": "2026-09-10T03:12:44.812Z",
  "reqId": "req-7f3a91c2",
  "userId": "u-10086",
  "event": "order_created",
  "orderId": "ord-55201",
  "amount": 199,
  "message": "订单创建成功"
}
```

检索时可以直接表达：“找出 reqId 为 req-7f3a91c2 的全部日志”或“最近一小时所有 order_created 且 amount 大于 1000 的事件”，这是非结构化字符串做不到的。

#### 1.4 与后端系统的关系

生产环境没有调试器、没有断点，日志是事后还原现场的唯一证据链。日志质量直接决定平均故障恢复时间：字段完整、可关联的日志让定位以分钟计，字符串刷屏只能靠猜。

#### 1.5 常见误区

> 误区一：日志只给人看，随便拼字符串。

现代排障大量依赖机器检索与告警规则；结构化字段是自动化分析的前提。

> 误区二：把 `console.log` 留满整个项目再上线。

无法关闭、无法分级、无法脱敏；应统一走 logger 模块。

### 2. 日志级别

#### 2.1 六级模型与语义

| 级别 | 语义 | 例子 | 默认是否需要人行动 |
|---|---|---|---|
| trace | 最细粒度的执行轨迹 | 进入函数、SQL 参数 | 否 |
| debug | 调试用详细信息 | 分支判断结果、缓存命中 | 否 |
| info | 正常业务事件 | 用户注册、订单创建、服务启动 | 否 |
| warn | 异常但可恢复 | 重试一次成功、接近限流阈值 | 关注 |
| error | 操作失败、影响单次请求 | 支付失败、写库异常 | 是，尽快 |
| fatal | 进程不可用级故障 | 无法连数据库、启动失败 | 立即 |

#### 2.2 选择级别的判断问题

```text
问一：这条信息在生产正常运行时需要看到吗？
  不需要 → debug 或 trace
问二：系统自己恢复了吗？
  恢复了但值得留意 → warn
问三：这次操作失败了吗？影响范围多大？
  单次请求失败 → error
  整个进程无法继续 → fatal
```

#### 2.3 级别按环境过滤

```text
development：debug（本地排障看细节）
test：info 或 warn（保持测试输出干净）
production：info（量大时只留业务事件与异常）
```

生产记录 debug 会让日志量暴涨、成本上升并淹没真正的异常；需要临时打开某个模块的 debug 时，应支持按模块动态调整，而不是全局降级。

#### 2.4 error 日志应携带什么

只打一个 `"出错了"` 几乎无法定位。error 日志应包含：错误名与 message、堆栈、触发上下文（reqId、userId、关键业务 id）、错误码；但不得包含用户提交的完整敏感数据。

```text
合格：
logger.error({ reqId, orderId, err, event: 'charge_failed' }, '支付扣款失败')

不合格：
logger.error('error')                       // 无上下文
logger.error(JSON.stringify(user))          // 可能带出密码字段
```

#### 2.5 常见误区

> 误区一：把业务异常都打成 error。

“密码错误”“余额不足”是正常业务拒绝，用 info/warn 即可；否则错误率告警永远在响，真正的系统错误被淹没。

> 误区二：用 error 记录后请求仍返回成功且没有任何后续处理。

级别必须与处理动作一致；error 意味着有人要查、要修。

### 3. 结构化日志：pino 与 winston

#### 3.1 安装与创建 logger

```bash
pnpm add pino pino-http
```

```ts
// src/logger/logger.ts
import pino from 'pino';
import { env } from '../config/env';

export const logger = pino({
  level: env.logLevel,
  base: { service: 'knowledge-api', version: env.appVersion },
  timestamp: () => `,"time":"${new Date().toISOString()}"`,
  redact: {
    paths: [
      'password',
      'passwordHash',
      'token',
      'authorization',
      'req.headers.authorization',
      '*.password',
      '*.cardNumber',
      '*.idCardNumber',
    ],
    censor: '[REDACTED]',
  },
});
```

#### 3.2 结构化写法：字段在前，消息在后

```ts
// 正确：第一个参数是上下文字段对象，第二个参数是消息
logger.info({ userId: 'u-1', event: 'user_registered' }, '新用户注册');

try {
  await riskyCall();
} catch (err) {
  logger.error({ err, reqId, event: 'risky_call_failed' }, '调用失败');
}
```

pino 会自动序列化 `Error` 的 message、stack 与类型；不要手工 `err.toString()`，那样会丢掉堆栈。

#### 3.3 winston 对照

```bash
pnpm add winston
```

```ts
// src/logger/winston-logger.ts
import winston from 'winston';

export const winstonLogger = winston.createLogger({
  level: process.env.LOG_LEVEL ?? 'info',
  format: winston.format.combine(
    winston.format.timestamp(),
    winston.format.errors({ stack: true }),
    winston.format.json(),
  ),
  defaultMeta: { service: 'knowledge-api' },
  transports: [new winston.transports.Console()],
});

winstonLogger.info('新用户注册', { userId: 'u-1', event: 'user_registered' });
```

winston 的习惯是消息在前、上下文在后，pino 相反；接手项目时先确认库的惯例，不要混用。

#### 3.4 开发环境可读性

生产输出 JSON 给机器，开发可以用美化输出提升可读性：

```ts
// pino 开发环境通过 transport 美化
const isDev = env.nodeEnv === 'development';

export const logger = pino({
  level: env.logLevel,
  transport: isDev ? { target: 'pino-pretty' } : undefined,
});
```

```bash
pnpm add -D pino-pretty
```

注意美化 transport 只用于本地，生产保持原生 JSON 输出以降低开销。

#### 3.5 常见误区

> 误区一：先 `JSON.stringify` 再交给 logger。

变成被转义的字符串字段，失去结构化检索能力；直接传对象。

> 误区二：在循环里对每条记录创建新 logger 实例。

应创建一次实例并复用；需要附加固定字段时使用 child logger。

### 4. 请求 ID 与链路关联

#### 4.1 为什么需要请求 ID

一次请求会经过鉴权、查库、调外部服务、写队列，产生十几条日志。没有统一标识时，并发下这些日志完全无法归属。请求 ID（reqId）是同一次请求全部日志与下游调用共享的唯一标识。

#### 4.2 中间件生成或透传 reqId

```bash
pnpm add pino-http
```

```ts
// src/http/logging-middleware.ts
import { pinoHttp } from 'pino-http';
import { randomUUID } from 'node:crypto';
import type { Request, Response } from 'express';
import { logger } from '../logger/logger';

export const httpLogger = pinoHttp({
  logger,
  // 优先复用上游网关注入的请求 ID，没有再自己生成
  genReqId: (req: Request, res: Response) => {
    const incoming = req.headers['x-request-id'];
    const id = Array.isArray(incoming) ? incoming[0] : incoming;
    return id || randomUUID();
  },
  customLogLevel: (_req, res, err) => {
    if (err || res.statusCode >= 500) return 'error';
    if (res.statusCode >= 400) return 'warn';
    return 'info';
  },
  serializers: {
    req: (req) => ({
      method: req.method,
      url: req.url,
      requestId: req.id,
    }),
    res: (res) => ({ statusCode: res.statusCode }),
  },
});
```

响应时把 reqId 回写到响应头，方便前端与客服报障时提供：

```ts
app.use((req, res, next) => {
  res.setHeader('x-request-id', (req as Request & { id: string }).id);
  next();
});
```

#### 4.3 AsyncLocalStorage：在深层函数中拿到 reqId

业务函数往往在调用栈深处，不可能把 reqId 一层层传参。Node 内置的 AsyncLocalStorage 可以在整条异步链上隐式存取上下文：

```ts
// src/logger/request-context.ts
import { AsyncLocalStorage } from 'node:async_hooks';

export type RequestContext = {
  reqId: string;
  userId?: string;
};

const storage = new AsyncLocalStorage<RequestContext>();

export function runWithContext<T>(ctx: RequestContext, fn: () => Promise<T>) {
  return storage.run(ctx, fn);
}

export function currentContext(): RequestContext | undefined {
  return storage.getStore();
}
```

```ts
// 入口中间件包裹后续处理
app.use((req, res, next) => {
  const reqId = (req as Request & { id: string }).id;
  runWithContext({ reqId }, () => {
    res.on('finish', () => {
      // 响应结束时上下文自然失效
    });
    next();
  });
});
```

```ts
// 任意深层模块，无需传参即可取出 reqId
import { currentContext } from '../logger/request-context';

export function chargeUser(amount: number) {
  const ctx = currentContext();
  logger.info({ reqId: ctx?.reqId, amount, event: 'charge_started' }, '开始扣款');
}
```

#### 4.4 传播到下游服务与队列

```text
调用下游 HTTP：在请求头加 x-request-id: <reqId>
投递消息队列：把 reqId 放进 job 的 metadata
Worker 消费：从 metadata 取出 reqId，重新 runWithContext 后再处理
```

这样一次“用户点击 → API → 队列 → Worker → 下游服务”的完整链路能用同一个 id 全部串起。

#### 4.5 常见误区

> 误区一：把 reqId 放在全局变量里。

并发请求会互相覆盖；AsyncLocalStorage 的隔离单元正是一次异步调用链。

> 误区二：每次都生成新 id，忽略上游传入的 x-request-id。

跨系统链路在入口处断裂，无法端到端聚合；应优先透传。

### 5. 敏感字段脱敏

#### 5.1 日志是敏感信息泄露的高发渠道

数据库有访问控制，而日志常被多人查看、导出、同步到第三方平台。一次不经心的 `logger.info(user)` 就可能把密码哈希、手机号、身份证号写入日志。脱敏必须在日志框架层统一实现，而不是依赖每个开发者记得删字段。

#### 5.2 三类敏感字段与处理方式

| 类型 | 例子 | 处理方式 |
|---|---|---|
| 机密 | 密码、token、私钥、authorization | 整体移除，替换为固定占位符 |
| 个人标识 | 身份证号、护照号 | 保留前后少量字符，中间打码 |
| 联系方式 | 手机号、邮箱、银行卡号 | 部分掩码，保留定位能力 |

```text
手机号 13812345678 → 138****5678
邮箱   alice@example.com → a***@example.com
银行卡 6222021234567890123 → 6222 **** **** 0123
```

#### 5.3 pino redact 路径配置

```ts
// src/logger/logger.ts
export const logger = pino({
  redact: {
    paths: [
      'password',
      'passwordHash',
      'token',
      'accessToken',
      'refreshToken',
      'req.headers.authorization',
      'req.headers.cookie',
      '*.password',
      '*.secret',
      '*.cardNumber',
      '*.idCardNumber',
      'user.idCardNumber',
    ],
    censor: '[REDACTED]',
    remove: false,
  },
});
```

路径支持通配：`*.password` 覆盖任意嵌套层级对象上的 password 字段。对需要部分掩码（而非整段删除）的字段，应在数据进入日志前通过格式化函数处理。

#### 5.4 自定义掩码函数

```ts
// src/logger/mask.ts
export function maskPhone(phone: string): string {
  if (!/^\d{11}$/.test(phone)) return '[INVALID_PHONE]';
  return phone.slice(0, 3) + '****' + phone.slice(7);
}

export function maskEmail(email: string): string {
  const [name, domain] = email.split('@');
  if (!name || !domain) return '[INVALID_EMAIL]';
  return name[0] + '***@' + domain;
}

export function maskIdCard(idCard: string): string {
  if (idCard.length < 8) return '[REDACTED]';
  return idCard.slice(0, 4) + '**********' + idCard.slice(-4);
}
```

```ts
// 使用
logger.info(
  {
    event: 'kyc_submitted',
    phone: maskPhone(form.phone),
    idCard: maskIdCard(form.idCard),
  },
  '实名资料已提交',
);
```

#### 5.5 请求体与错误对象同样要管

```text
- 记录 req.body 前必须经过白名单字段过滤或 redact，登录接口的请求体天然含密码
- 第三方 SDK 的错误对象可能回显请求头（含 authorization），记录 err 时确认 serializer 已剥离
- 数据库行整行打印时使用列级映射，只取需要的列
```

#### 5.6 常见误区

> 误区一：先脱敏展示层，日志里仍打印原文。

界面打了星号但日志泄露，等于没做；脱敏在出口处统一处理。

> 误区二：自己写正则“匹配到就删”，遗漏嵌套字段。

应使用日志库的 redact 路径机制并建立字段清单评审，覆盖新增字段。

### 6. 配置分层与 12-factor

#### 6.1 12-factor 中与配置直接相关的原则

十二要素应用（The Twelve-Factor App）是 SaaS 应用的方法论，其中三条直接约束配置：

```text
III. 配置：在环境中存储配置
  代码与配置严格分离；同一份代码在各环境运行，差异只来自环境变量

IV. 后端服务：把数据库等当作附加资源
  数据库、缓存、队列都是可替换资源，其地址与凭据通过配置注入，不写死在代码里

IX. 易处理：快速启动、优雅终止
  配置在启动时一次读入并校验，缺失立即失败，不运行到一半才崩
```

#### 6.2 判断“什么该进环境变量”

```text
会随环境变化的值 → 环境变量
  数据库地址、Redis 地址、第三方密钥、日志级别、端口

不随环境变化的值 → 代码常量
  业务规则数字（如最大重试 3 次）、枚举定义

介于两者之间 → 配置文件按环境分目录，但文件中不含密钥
  功能开关矩阵、各环境的超时参数
```

简单判据：把代码公开到开源仓库，哪些值一旦泄露会造成损失？那些必须走环境变量与密钥管理。

#### 6.3 单一配置模块：全应用只从这里读配置

反模式是各处散落 `process.env.X`：字段拼错要运行到该行才暴露、类型全是字符串、无法集中校验。正确做法是启动时读取一次、校验一次、导出强类型对象。

```ts
// src/config/env.ts
import { z } from 'zod';

const schema = z.object({
  NODE_ENV: z.enum(['development', 'test', 'production']).default('development'),
  PORT: z.coerce.number().int().positive().default(3000),
  DATABASE_URL: z.string().url(),
  REDIS_URL: z.string().url(),
  LOG_LEVEL: z.enum(['trace', 'debug', 'info', 'warn', 'error', 'fatal']).default('info'),
  PAYMENT_API_KEY: z.string().min(1),
  JWT_SECRET: z.string().min(32),
  APP_VERSION: z.string().default('0.0.0'),
});

export type AppEnv = z.infer<typeof schema>;

let cached: AppEnv | undefined;

export function loadEnv(source: NodeJS.ProcessEnv = process.env): AppEnv {
  if (cached) return cached;

  const parsed = schema.safeParse(source);
  if (!parsed.success) {
    const issues = parsed.error.issues
      .map((issue) => `  - ${issue.path.join('.')}: ${issue.message}`)
      .join('\n');
    // 此时 logger 尚未初始化，使用 stderr 输出
    console.error(`启动配置校验失败：\n${issues}`);
    throw new Error('INVALID_ENVIRONMENT_CONFIG');
  }

  cached = parsed.data;
  return cached;
}

export const env = new Proxy({} as AppEnv, {
  get(_target, prop: string) {
    if (!cached) throw new Error('配置尚未初始化，请先调用 loadEnv()');
    return (cached as Record<string, unknown>)[prop];
  },
});
```

#### 6.4 配置分层的目录组织

```text
config/
├── env.ts          # 读取并校验环境变量，导出 env
├── defaults.ts     # 与环境无关的默认常量
├── features.ts     # 按环境区分的功能开关（无密钥）
└── timeouts.ts     # 各环境超时参数（无密钥）
```

业务代码只 import `env` 与这些模块，不直接读 `process.env`（测试代码与配置模块自身除外）。

#### 6.5 常见误区

> 误区一：把 NODE_ENV 以外的环境差异写进 if/else 硬编码。

代码里出现 `if (env === 'prod')` 的特殊分支，测试环境永远走不到生产逻辑；差异应数据化。

> 误区二：配置在请求处理中反复读取并做容错默认。

数据库地址缺失不应“用一个默认值凑合跑”，应在启动时就失败。

### 7. 多环境隔离与密钥不入库

#### 7.1 dev/test/prod 的差异矩阵

| 维度 | development | test | production |
|---|---|---|---|
| NODE_ENV | development | test | production |
| 数据库 | 本地开发库 | 独立测试库/容器 | 生产库（高可用） |
| 日志级别 | debug | info/warn | info |
| 日志输出 | 美化终端 | JSON/抑制 | JSON → 采集平台 |
| 密钥来源 | 本地 `.env`（gitignore） | CI 密钥变量 | 密钥管理服务/平台注入 |
| 外部服务 | 沙箱地址 | Stub/沙箱 | 真实地址 |

#### 7.2 dotenv 只服务本地

```bash
pnpm add -D dotenv
```

```ts
// src/config/load-local-env.ts
import { config } from 'dotenv';

// 仅在非生产、非 CI 的本地开发加载 .env
if (process.env.NODE_ENV !== 'production' && !process.env.CI) {
  config({ path: '.env' });
}
```

纯 CommonJS 项目可以在入口最顶部用一行 `require` 完成同样的加载；它必须出现在任何读取配置的代码之前：

```js
// src/config/load-local-env.js
if (process.env.NODE_ENV !== 'production' && !process.env.CI) {
  require('dotenv').config({ path: '.env' });
}
```

也可以不改源码，直接在启动命令上预加载：`node -r dotenv/config src/server.js`，此时 dotenv 默认读取工作目录下的 `.env`。

生产环境的环境变量应由部署平台或进程管理直接注入，不依赖 `.env` 文件——文件型密钥在镜像和机器上反而是泄露面。

#### 7.3 .env.example 入库，.env 不入库

```text
.env.example   # 提交：只含键名与占位，指导新成员需要哪些变量
.env           # 不提交：真实本地值
.env.local     # 不提交：个人覆盖
```

`.env.example`：

```bash

PORT=3000

REDIS_URL=redis://localhost:6379/0
LOG_LEVEL=debug
PAYMENT_API_KEY=replace-at-runtime
JWT_SECRET=replace-with-a-random-string-at-least-32-chars
APP_VERSION=0.0.0
```

`.gitignore` 必须包含：

```text

.env.*
!.env.example
*.pem
*.key
secrets/
```

#### 7.4 生产密钥的正规来源

```text
优先级从低到高：
1. 明文配置文件（禁止）
2. 部署平台环境变量（基础要求）
3. 专用密钥管理服务（KMS / Secret Manager），启动时拉取、内存持有、定期轮换
```

使用密钥管理服务时，访问凭据本身由平台身份（实例角色/服务账号）提供，代码中仍不出现长期密钥；轮换密钥不需要改代码、重新发版。

#### 7.5 启动顺序

```text
1. 加载本地 .env（仅开发）
2. loadEnv() 读取并校验全部配置
3. 用校验后的配置初始化 logger（此时日志中可记录“非敏感配置已加载”）
4. 初始化数据库、Redis 等连接
5. 启动 HTTP 服务
```

#### 7.6 常见误区

> 误区一：把 `.env.production` 打进镜像或提交到仓库“方便部署”。

任何能读到代码仓库或镜像的人都能拿到生产密钥；密钥必须在运行环境注入。

> 误区二：测试环境复用生产密钥“省得申请”。

测试系统的访问控制更弱，且测试日志可能泄露；各环境密钥必须独立。

### 8. 启动配置校验与故障快速暴露

#### 8.1 fail fast 的价值

配置错误（少一个变量、URL 拼错、密钥太短）最好的失败时机是“进程启动的那一秒”，此时没有真实流量、错误信息明确。最坏的失败时机是凌晨三点第一个请求打到那段代码时。启动校验把所有配置问题前置为确定性失败。

#### 8.2 zod schema 的完整校验策略

```ts
// src/config/schema.ts
import { z } from 'zod';

const nonEmptyString = z.string().min(1);

export const envSchema = z.object({
  NODE_ENV: z.enum(['development', 'test', 'production']),
  PORT: z.coerce.number().int().min(1024).max(65535),
  DATABASE_URL: z.string().regex(/^postgres(ql)?:\/\//, '必须是 PostgreSQL 连接串'),
  REDIS_URL: z.string().startsWith('redis'),
  PAYMENT_API_KEY: nonEmptyString,
  JWT_SECRET: z
    .string()
    .min(32, 'JWT 密钥至少 32 个字符')
    .regex(/[a-z]/)
    .regex(/[A-Z]/)
    .regex(/[0-9]/),
  LOG_LEVEL: z.enum(['trace', 'debug', 'info', 'warn', 'error', 'fatal']),
});

export function assertEnv(source: NodeJS.ProcessEnv) {
  const result = envSchema.safeParse(source);

  if (!result.success) {
    const report = result.error.issues.map((issue) => ({
      field: issue.path.join('.'),
      problem: issue.message,
    }));
    // 只输出字段名与问题，绝不回显环境变量的值
    console.error('环境配置不合法，进程终止：');
    for (const item of report) {
      console.error(`  [${item.field}] ${item.problem}`);
    }
    process.exit(1);
  }

  return result.data;
}
```

注意校验失败的输出只含字段名与原因，不打印变量值——值本身可能就是机密。

#### 8.3 连接级验证：启动时探活

静态格式正确不代表资源可用。启动时对数据库、Redis 做一次探活：

```ts
// src/bootstrap.ts
import { assertEnv } from './config/schema';
import { createLogger } from './logger/logger';
import { pingDatabase } from './db/ping';
import { pingRedis } from './redis/ping';

export async function bootstrap() {
  const env = assertEnv(process.env);
  const logger = createLogger(env);

  logger.info({ event: 'boot_start' }, '服务开始启动');

  try {
    await pingDatabase(env.DATABASE_URL);
    logger.info({ event: 'db_ready' }, '数据库连接正常');

    await pingRedis(env.REDIS_URL);
    logger.info({ event: 'redis_ready' }, 'Redis 连接正常');
  } catch (err) {
    logger.fatal({ err, event: 'dependency_unavailable' }, '关键依赖不可用，进程退出');
    process.exit(1);
  }

  logger.info({ event: 'boot_complete', port: env.PORT }, '启动完成');
  return env;
}
```

#### 8.4 优雅退出与配置收尾

收到 SIGTERM/SIGINT 时，停止接收请求、等待在途请求结束、关闭连接池后退出；退出本身记录一条 info 日志。退出码语义与第 13 单元一致：异常退出必须非零。

#### 8.5 常见误区

> 误区一：校验失败只 `throw`，外层却 catch 住继续启动。

fail fast 必须真正终止进程（非零退出码），否则流量会进入一个半残服务。

> 误区二：校验逻辑放在每个使用点。

校验重复、时机不一；集中在启动阶段一次完成。

## 实践练习题

### 练习 1：结构化日志与级别改造

#### 任务

把一个现有 Express 项目中的全部 `console.log` 替换为 pino 结构化日志，并为“注册、登录失败、下单异常、服务启动”四类事件选择正确级别。

#### 步骤约束

1. 创建 `src/logger/logger.ts`，服务名与版本从配置读取；生产 JSON、本地 pino-pretty。
2. 四类事件分别记录结构化上下文字段（event、userId/orderId 等），error 事件携带 `err` 对象保留堆栈。
3. 登录失败（密码错误）使用 warn/info 而非 error，并说明理由。
4. 日志级别由 `LOG_LEVEL` 控制，演示把级别调到 warn 后 info 日志不再输出。

#### 提交物

- logger 模块；
- 四类事件改造前后的代码对照；
- 不同级别过滤的运行记录。

#### 验收标准

- 项目中不再出现 console 调用（启动配置失败的 stderr 除外）；
- 日志为合法 JSON，字段可被按名检索；
- 级别与“是否需要行动”一致；
- 错误日志含堆栈与业务上下文。

### 练习 2：请求 ID 全链路透传

#### 任务

为“知识条目创建”链路加入请求 ID：中间件生成/透传、AsyncLocalStorage 存储、深层 Service 使用、响应头回写，并把 reqId 传播到模拟的下游调用。

#### 步骤约束

1. 优先使用入站 `x-request-id`，缺失时用 `randomUUID` 生成；响应头回写同一值。
2. 使用 AsyncLocalStorage 在入口包裹请求，深层模块通过 `currentContext()` 读取，禁止层层传参或全局变量。
3. 同一次请求的所有日志都带相同 reqId；用两个并发请求演示日志不串号。
4. 调用下游 Stub 时在请求头带上 reqId，并断言 Stub 收到该头。

#### 提交物

- request-context 与日志中间件；
- 含深层调用的 Service 代码；
- 并发请求日志按 reqId 聚合的证据。

#### 验收标准

- 并发下 reqId 互不污染；
- 入站 id 被透传而非重新生成；
- 深层模块无需参数即可拿到上下文；
- 下游调用与响应头中的 id 一致。

### 练习 3：配置模块、脱敏与启动校验

#### 任务

建立单一配置模块与多环境隔离：`.env.example` 入库、`.env` 忽略，zod 启动校验，redact 覆盖全部敏感字段，并演示三类配置错误在启动秒级失败。

#### 步骤约束

1. 编写 zod schema：端口范围、URL 格式、JWT 密钥长度与复杂度、枚举级别；失败时 `process.exit(1)`，输出只含字段名不含值。
2. 配置 redact 路径至少覆盖密码、token、authorization、cookie 与嵌套通配；提供手机/邮箱掩码函数并在业务日志中使用。
3. 启动流程按“加载 → 校验 → 初始化 logger → 探活数据库/Redis → 监听”顺序组织。
4. 演示三种失败：缺失必填变量、URL 格式错误、JWT 密钥过短，均在启动时终止且不监听端口。
5. 用扫描命令确认仓库内不含真实密钥、`.env` 未被跟踪。

#### 提交物

- config 模块与 schema；
- logger redact 与掩码函数；
- `.env.example`、`.gitignore` 片段；
- 三类启动失败的记录与 git 检查证据。

#### 验收标准

- 业务代码不直接读 process.env；
- 配置错误启动即失败、退出码非零；
- 敏感字段在所有日志路径中被移除或掩码；
- 仓库历史中不提交 `.env` 与真实凭据。

### 提交前自检

- [ ] 项目内不存在 console 日志输出（配置失败的 stderr 除外）。
- [ ] 每条日志为合法 JSON，含时间、级别、event 与必要业务 id。
- [ ] 同一请求全部日志可凭 reqId 聚合，并发不串号。
- [ ] 敏感字段在直接打印、请求体、错误对象三类路径下均已脱敏。
- [ ] 所有配置经由单一模块读取，业务代码不直接访问 process.env。
- [ ] 缺失或非法配置在启动时以非零退出码终止，端口未被监听。
- [ ] `.env` 未被跟踪，仓库中无真实密钥，各环境密钥相互独立。
