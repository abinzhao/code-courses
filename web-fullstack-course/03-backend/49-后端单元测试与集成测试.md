# 49-后端单元测试与集成测试

## 目标

后端代码掌管着真实的业务规则、资金计算、权限判断和数据写入，它的缺陷不会被浏览器界面挡住，而是直接变成脏数据、错误订单和资损。后端测试的目标不是“把代码跑一遍”，而是用自动化方式证明：每一个业务规则在独立状态下成立，多个模块组装后仍然成立，HTTP 接口对真实请求给出正确响应。

本单元从测试分层出发，完成从纯函数单元测试、Service 层测试、Mock 仓储到 supertest HTTP 集成测试的完整闭环。

完成本知识单元后，学员应能够：

1. 画出后端测试金字塔，说清单元测试、集成测试、契约测试与 E2E 测试各自的边界、成本与定位。
2. 在 Node.js + TypeScript 后端项目中配置 Jest 或 Vitest，区分两者的选择标准，并运行测试与覆盖率命令。
3. 为纯函数和领域逻辑编写独立、快速、不依赖 I/O 的单元测试，覆盖正常值、边界值与异常分支。
4. 使用依赖注入组织 Service 层，使用 Mock、Stub、Spy、Fake 等测试替身隔离仓储、时钟和外部服务。
5. 使用 supertest 对 Express/Fastify 应用发起真实 HTTP 请求做集成测试，断言状态码、Header 与 JSON 响应体。
6. 按 Arrange-Act-Assert 组织用例，使用行为导向命名，并能识别“过度 Mock”“测试实现细节”等可维护性陷阱。

本单元的核心信念是：低层测试多而快、高层测试少而真；Mock 只用于跨越边界，而不是用来把系统全部替换成“永远成功”的假世界。

## 详细的理论知识讲解和示例伪代码

### 1. 后端测试分层与测试金字塔

#### 1.1 后端为什么也要分层测试

一个后端请求会穿过路由、参数校验、业务 Service、仓储、数据库，还可能调用支付、短信等外部服务。如果只用一种“大测试”覆盖所有路径，会出现两个极端：

- 全部连真实数据库和外部服务：测试慢、不稳定、无法覆盖全部错误分支，外部服务宕机时全线瘫痪。
- 全部用假对象：测试飞快，但模块之间是否接得上、SQL 是否正确、JSON 结构是否匹配，完全没有保障。

分层测试的价值是让不同风险由不同成本的测试承担。

```text
        /  E2E \        少：真实部署、真实数据库、真实外部依赖
       / 契约测试 \     少：验证服务之间的接口约定
      /  集成测试   \   适量：多个模块组装，含真实数据库或 HTTP
     /   单元测试     \ 多：纯函数、Service、单个模块，毫秒级
    ------------------
       快、稳定、便宜            慢、脆弱、昂贵
```

#### 1.2 各层的边界

| 层级 | 被测对象 | 依赖处理 | 速度 | 典型数量 |
|---|---|---|---|---|
| 单元测试 | 函数、类、单个 Service | 全部协作对象可替身 | 毫秒级 | 最多 |
| 集成测试 | 路由 + Service + 仓储 + 数据库 | 数据库真实，外部服务可替身 | 秒级 | 适量 |
| 契约测试 | 两个服务之间的请求/响应结构 | 只验证约定，不验证业务 | 秒级 | 少量 |
| E2E 测试 | 完整部署的系统与关键业务路径 | 全部真实 | 十秒级以上 | 少而关键 |

判断一个用例属于哪层，只看一个问题：它允许多少边界保持真实。纯函数测试里数据库是假的；集成测试里数据库是真的；E2E 里连部署形态都是真的。

#### 1.3 与后端系统的关系

后端的 bug 往往不是“算错一个数”，而是“模块接不上”：Service 以为仓储返回数组，仓储实际返回 `null`；路由以为校验中间件一定执行，实际挂载顺序错了。单元测试守住每个零件，集成测试守住组装接缝，E2E 守住用户真正走的关键路径，三者缺一不可。

#### 1.4 常见误区

> 误区一：只写 E2E，认为“越真实越好”。

E2E 慢且定位困难，一次运行几分钟，失败时不知道坏在路由、Service 还是数据库，开发者会逐渐不敢频繁运行它。

> 误区二：只写单元测试，认为“覆盖率 100% 就安全”。

全部 Mock 之后，SQL 语法错误、事务边界错误、JSON 字段名不匹配都无法被发现。

### 2. Jest / Vitest 配置

#### 2.1 如何二选一

- Vitest：与 Vite/ESM/TypeScript 集成顺滑，启动快，watch 体验好，新项目优先选择。
- Jest：生态最成熟，存量 NestJS、Express 项目大量使用，接手老仓库时必须能读懂。

两者的断言 API 高度一致，`describe/it/expect` 与生命周期几乎可以无缝迁移，真正的差异集中在配置格式和 Mock 写法。

#### 2.2 Vitest 配置

```bash
pnpm add -D vitest @vitest/coverage-v8
```

```ts
// vitest.config.ts
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    globals: false,
    environment: 'node',
    include: ['src/**/*.test.ts', 'test/**/*.test.ts'],
    coverage: {
      provider: 'v8',
      reporter: ['text', 'html'],
      include: ['src/**/*.ts'],
      exclude: ['src/**/*.d.ts', 'src/server.ts'],
      statements: 80,
      branches: 75,
      functions: 80,
    },
  },

```

要点：后端测试使用 `environment: 'node'`，不需要 jsdom；`include` 同时收纳源码旁的单元测试和 `test/` 目录的集成测试，也可以拆成两个配置文件分别运行。

#### 2.5 与后端系统的关系

CI 和本地都通过退出码判断测试结果：断言失败时运行器以非零退出码结束，流水线因此中断。脚本必须区分“只跑快速单测”和“跑集成测试”，让开发者在提交前愿意频繁运行前者。

#### 2.6 常见误区

> 误区一：打开 `globals: true` 以少写导入。

隐式全局会让 IDE 类型推断和重构变差，还可能与其他全局命名冲突；显式导入更清晰。

> 误区二：把覆盖率门槛设成 100%。

团队会开始写无断言的空测试或到处 `/* c8 ignore */` 来回避门槛；门槛应守住底线而非追求满分。

### 3. 纯函数与领域逻辑单元测试

#### 3.1 纯函数是最值得先测的部分

纯函数满足“相同输入永远得到相同输出，且不产生外部副作用”。金额计算、折扣规则、积分换算、状态流转判断都属于领域逻辑，它们：

- 不依赖数据库、网络和时钟；
- 一个用例通常只需三行：输入、调用、断言；
- 是 bug 代价最高的区域（算错钱、发错权益）。

#### 3.2 示例：订单折扣计算

```ts
// src/domain/discount.ts
export type Coupon = {
  type: 'fixed' | 'percent';
  value: number;
  minAmount: number;
};

export function applyDiscount(originalAmount: number, coupon: Coupon): number {
  if (!Number.isFinite(originalAmount) || originalAmount < 0) {
    throw new Error('订单金额非法');
  }
  if (originalAmount < coupon.minAmount) {
    return originalAmount;
  }

  if (coupon.type === 'fixed') {
    return Math.max(0, roundMoney(originalAmount - coupon.value));
  }

  const next = (originalAmount * (100 - coupon.value)) / 100;
  return roundMoney(Math.max(0, next));
}

function roundMoney(value: number): number {
  return Math.round(value * 100) / 100;
}
```

```ts
// src/domain/discount.test.ts
import { describe, expect, it } from 'vitest';
import { applyDiscount } from './discount';

describe('applyDiscount', () => {
  it('未达到最低消费门槛时不打折', () => {
    const result = applyDiscount(90, {
      type: 'percent',
      value: 10,
      minAmount: 100,
    });

    expect(result).toBe(90);
  });

  it('百分比折扣按比例减免并保留两位小数', () => {
    const result = applyDiscount(100, {
      type: 'percent',
      value: 15,
      minAmount: 0,
    });

    expect(result).toBe(85);
  });

  it('固定减免大于金额时最低为 0，不出现负数', () => {
    const result = applyDiscount(30, {
      type: 'fixed',
      value: 50,
      minAmount: 0,
    });

    expect(result).toBe(0);
  });

  it('金额为负数时抛出业务错误', () => {
    expect(() =>
      applyDiscount(-1, { type: 'fixed', value: 10, minAmount: 0 }),
    ).toThrow('订单金额非法');
  });
});
```

#### 3.3 参数化覆盖边界值

边界值是缺陷最密集的位置：恰好等于门槛、金额为 0、折扣为 100%。可以用 `it.each` 把同类输入组织成表格，避免复制粘贴出十几个相似用例。

```ts
import { describe, expect, it } from 'vitest';

describe('applyDiscount 边界表', () => {
  it.each([
    { amount: 100, value: 0, expected: 100, case: '折扣为 0' },
    { amount: 100, value: 100, expected: 0, case: '折扣为 100%' },
    { amount: 0, value: 10, expected: 0, case: '金额为 0' },
    { amount: 99.99, value: 33.33, expected: 66.66, case: '无限小数四舍五入' },
  ])('$case：$amount 元打 $value% 折应得 $expected', ({ amount, value, expected }) => {
    const result = applyDiscount(amount, {
      type: 'percent',
      value,
      minAmount: 0,
    });

    expect(result).toBe(expected);
  });
});
```

#### 3.4 与后端系统的关系

这些规则直接决定扣多少钱、送多少积分，且会被多个 Service 复用。把它们从 Service 中抽成纯函数并单测，等于给资金安全加上第一道锁；测试运行只要几毫秒，可以在每次保存文件时自动运行。

#### 3.5 常见误区

> 误区一：用浮点直接比较，如 `expect(price).toBe(66.66000001)`。

金额应统一最小单位（分）或在出口做四舍五入；浮点误差是语言层面的客观事实，不是业务规则。

> 误区二：只测 happy path，忘记门槛边界和非法输入。

“恰好等于最低消费”“减免大于金额”这类边界才是事故高发点。

### 4. Service 层测试与依赖注入

#### 4.1 Service 层的定位

Service 承载一个完整用例的编排：校验参数 → 检查规则 → 调用仓储读写 → 调用外部服务 → 返回结果。它本身不应关心 SQL 怎么写、HTTP 怎么发，这些通过接口（仓储、网关）注入。这种结构天然可测：测试时传入假的仓储与网关，就能稳定制造“用户不存在”“支付失败”等分支。

#### 4.2 依赖注入的最小形式

不引入任何框架，构造函数注入就足够：

```ts
// src/services/order.service.ts
import type { OrderRepository } from '../repositories/order.repository';
import type { PaymentGateway } from '../gateways/payment.gateway';
import type { Clock } from '../lib/clock';

export type CreateOrderInput = {
  userId: string;
  amount: number;
};

export class OrderService {
  constructor(
    private readonly orders: OrderRepository,
    private readonly payment: PaymentGateway,
    private readonly clock: Clock,
  ) {}

  async create(input: CreateOrderInput) {
    if (input.amount <= 0) {
      throw new OrderError('订单金额必须大于 0');
    }

    const paid = await this.payment.charge(input.userId, input.amount);
    if (!paid.ok) {
      throw new OrderError('支付失败：' + paid.reason);
    }

    const order = await this.orders.insert({
      userId: input.userId,
      amount: input.amount,
      status: 'paid',
      createdAt: this.clock.now(),
    });

    return order;
  }
}

export class OrderError extends Error {}
```

#### 4.3 用手写假对象测试 Service

```ts
// src/services/order.service.test.ts
import { describe, expect, it, vi } from 'vitest';
import { OrderService } from './order.service';

function setup() {
  const orders = {
    insert: vi.fn(async (order) => ({ id: 'order-1', ...order })),
  };
  const payment = { charge: vi.fn() };
  const clock = { now: () => new Date('2026-09-01T08:00:00Z') };
  const service = new OrderService(orders as never, payment as never, clock);
  return { service, orders, payment };
}

describe('OrderService.create', () => {
  it('支付成功后写入状态为 paid 的订单', async () => {
    const { service, payment, orders } = setup();
    payment.charge.mockResolvedValue({ ok: true });

    const order = await service.create({ userId: 'u-1', amount: 100 });

    expect(payment.charge).toHaveBeenCalledWith('u-1', 100);
    expect(orders.insert).toHaveBeenCalledWith({
      userId: 'u-1',
      amount: 100,
      status: 'paid',
      createdAt: new Date('2026-09-01T08:00:00Z'),
    });
    expect(order.id).toBe('order-1');
  });

  it('支付失败时抛错且不写入订单', async () => {
    const { service, payment, orders } = setup();
    payment.charge.mockResolvedValue({ ok: false, reason: '余额不足' });

    await expect(service.create({ userId: 'u-1', amount: 100 })).rejects.toThrow(
      '支付失败：余额不足',
    );
    expect(orders.insert).not.toHaveBeenCalled();
  });

  it('金额为 0 时直接拒绝，不调用支付网关', async () => {
    const { service, payment } = setup();

    await expect(service.create({ userId: 'u-1', amount: 0 })).rejects.toThrow(
      '订单金额必须大于 0',
    );
    expect(payment.charge).not.toHaveBeenCalled();
  });
});
```

#### 4.4 与后端系统的关系

Service 是业务用例的核心，也是单元测试投入产出比最高的位置。注入时钟（而不是直接 `new Date()`）后，“月末结算”“超时取消”等时间相关规则才可测；注入网关后，第三方故障分支不用真的等对方宕机就能覆盖。

#### 4.5 常见误区

> 误区一：Service 内部直接 `new HttpClient()`、直接 `new Date()`。

所有协作者都被写死，测试无法替换，只能连真实外部服务，单测退化成不稳定的慢测试。

> 误区二：一个 Service 方法承担十几个职责。

无法为单个行为命名用例，Mock 列表越来越长；应按用例拆分。

### 5. Mock 依赖与仓储

#### 5.1 仓储模式让 Mock 有边界

仓储（Repository）用接口屏蔽数据库细节，Service 只依赖接口方法签名。测试替身只需实现接口，不必关心底层是 PostgreSQL 还是 MySQL。

```ts
// src/repositories/user.repository.ts
export type UserRecord = {
  id: string;
  email: string;
  status: 'active' | 'frozen';
};

export interface UserRepository {
  findById(id: string): Promise<UserRecord | null>;
  updateStatus(id: string, status: UserRecord['status']): Promise<void>;
}
```

#### 5.2 模块级 Mock：vi.mock / jest.mock

当依赖通过模块导入而不是构造函数注入时，使用模块 Mock。它的作用是“整个测试文件中，该模块被替换”。

```ts
// src/services/account.service.ts
import { sendWelcomeEmail } from '../mail/mailer';
import type { UserRepository } from '../repositories/user.repository';

export class AccountService {
  constructor(private readonly users: UserRepository) {}

  async activate(id: string) {
    const user = await this.users.findById(id);
    if (!user) return false;
    if (user.status === 'frozen') return false;

    await this.users.updateStatus(id, 'active');
    await sendWelcomeEmail(user.email);
    return true;
  }
}
```

```ts
// src/services/account.service.test.ts
import { beforeEach, describe, expect, it, vi } from 'vitest';

vi.mock('../mail/mailer', () => ({
  sendWelcomeEmail: vi.fn(),
}));

import { sendWelcomeEmail } from '../mail/mailer';
import { AccountService } from './account.service';

describe('AccountService.activate', () => {
  beforeEach(() => {
    vi.clearAllMocks();
  });

  it('激活成功后发送欢迎邮件', async () => {
    const users = {
      findById: vi.fn(async () => ({
        id: 'u-1',
        email: 'a@example.com',
        status: 'pending' as never,
      })),
      updateStatus: vi.fn(async () => undefined),
    };
    const service = new AccountService(users as never);

    const ok = await service.activate('u-1');

    expect(ok).toBe(true);
    expect(users.updateStatus).toHaveBeenCalledWith('u-1', 'active');
    expect(sendWelcomeEmail).toHaveBeenCalledWith('a@example.com');
  });
});
```

Jest 写法几乎一致，只需把 `vi` 换成 `jest`：`jest.mock('../mail/mailer', () => ({ sendWelcomeEmail: jest.fn() }))`。

#### 5.3 Mock 时间、随机数与外部请求

涉及“当前时间”“随机 ID”的逻辑同样要可控：

```ts
import { afterEach, describe, expect, it, vi } from 'vitest';

afterEach(() => {
  vi.useRealTimers();
});

it('票据在 15 分钟后过期', () => {
  vi.useFakeTimers();
  vi.setSystemTime(new Date('2026-09-01T08:00:00Z'));
  const ticket = createTicket('u-1');

  vi.advanceTimersByTime(15 * 60 * 1000);

  expect(isExpired(ticket)).toBe(true);
});
```

Jest 对应 API 为 `jest.useFakeTimers()`、`jest.setSystemTime()`、`jest.advanceTimersByTime()`。

#### 5.4 Mock 的断言纪律

Mock 不只是“让代码能跑”，更要验证交互：调用了谁、调用几次、参数是什么。

```text
应断言：
- 支付网关按 (userId, amount) 被精确调用一次
- 失败路径下仓储 insert 从未被调用
- 重试逻辑下外部请求共发生 3 次

不应断言：
- 被测对象内部的私有变量变化
- Mock 对象自身又调用了自己（无意义）
```

#### 5.5 常见误区

> 误区一：Mock 整个仓储层，却不校验调用参数。

Service 传错字段、漏传租户 id 都能通过，Mock 沦为“永远成功的挡板”。

> 误区二：Mock 被测模块自身的函数。

替换掉真正要验证的逻辑，测试一定通过但毫无保护。只 Mock 边界另一侧的协作者。

### 6. 测试替身的五种类型

#### 6.1 定义与区分

测试替身（Test Double）是“在测试中代替真实协作者的对象”的统称，按行为从简单到复杂分为五类：

| 类型 | 行为 | 典型用途 |
|---|---|---|
| Dummy | 被传入但从不使用，仅为凑齐参数 | 填充必填构造参数 |
| Stub | 返回预设答案，不响应其他调用 | 让仓储返回固定用户 |
| Spy | 包装真实对象并记录调用信息 | 验证邮件是否被发送 |
| Mock | 带预设期望的对象，未满足期望即失败 | 验证支付恰好调用一次 |
| Fake | 可用但简化的实现 | 内存版仓储替代数据库 |

#### 6.2 各类示例

```ts
import { describe, expect, it, vi } from 'vitest';

// Dummy：永远不会被读取
const dummyLogger = {} as never;

// Stub：固定返回
const stubUsers = {
  findById: vi.fn(async () => ({
    id: 'u-1',
    email: 'a@example.com',
    status: 'active',
  })),
};

// Spy：记录调用，不改变行为
const spyMailer = { send: vi.fn() };

// Mock：带期望（调用次数即契约）
expect(spyMailer.send).toHaveBeenCalledTimes(1);

// Fake：内存仓储，行为接近真实实现
class FakeUserRepository {
  private rows = new Map<string, { id: string; status: string }>();

  async insert(row: { id: string; status: string }) {
    this.rows.set(row.id, row);
  }

  async findById(id: string) {
    return this.rows.get(id) ?? null;
  }
}
```

#### 6.3 选择顺序

```text
优先使用 Fake（行为真实、可跨用例复用）
    ↓ 只需要固定返回值
使用 Stub
    ↓ 需要验证“是否调用、调用几次”
使用 Spy / Mock
    ↓ 参数列表需要占位但永不会被读
使用 Dummy
```

能不用 Mock 就不用：Mock 与实现细节耦合最深，重构时最容易批量红。

#### 6.4 与后端系统的关系

后端典型边界有四类：数据库、消息队列、第三方 HTTP、时间。每个边界都应预置一套替身（内存 Fake 仓储、假队列、可编排的 HTTP Stub、可拨动的时钟），形成团队共享的测试工具箱，而不是每个文件临时手写。

#### 6.5 常见误区

> 误区：术语混用，把所有替身都叫 “mock”。

沟通时无法区分对方想要“固定返回值的 Stub”还是“验证调用次数的 Mock”，用例会写偏。

### 7. supertest HTTP 集成测试

#### 7.1 集成测试要让 HTTP 层保持真实

路由匹配、中间件顺序、参数解析、错误处理和 JSON 序列化都属于框架组装行为，单元测试无法覆盖。supertest 在进程内直接对 Node HTTP 应用发起真实请求（不需要占用端口），让从请求进入到响应离开的整条链路保持真实。

#### 7.2 应用可导出但不自动监听

```ts
// src/app.ts
import express from 'express';
import { orderRouter } from './routes/order.router';
import { errorHandler } from './middleware/error-handler';

export function createApp(deps: { orderService: OrderService }) {
  const app = express();
  app.use(express.json());
  app.use('/api/orders', orderRouter(deps));
  app.use(errorHandler);
  return app;
}
```

```ts
// src/server.ts
import { createApp } from './app';
import { realDeps } from './deps';

const app = createApp(realDeps());
app.listen(3000, () => {
  console.log('listening on 3000');
});
```

关键分离：`app.ts` 只负责组装，`server.ts` 才监听端口。测试导入 `createApp`，生产启动走 `server.ts`，互不污染。

#### 7.3 supertest 示例

```bash
pnpm add -D supertest @types/supertest
```

```ts
// test/integration/order.api.test.ts
import request from 'supertest';
import { describe, expect, it, vi } from 'vitest';
import { createApp } from '../../src/app';

describe('POST /api/orders', () => {
  it('合法请求返回 201 和订单编号', async () => {
    const orderService = {
      create: vi.fn(async () => ({ id: 'order-9', status: 'paid' })),
    };
    const app = createApp({ orderService: orderService as never });

    const res = await request(app)
      .post('/api/orders')
      .send({ userId: 'u-1', amount: 100 })
      .expect('Content-Type', /json/);

    expect(res.status).toBe(201);
    expect(res.body).toMatchObject({ id: 'order-9', status: 'paid' });
    expect(orderService.create).toHaveBeenCalledWith({
      userId: 'u-1',
      amount: 100,
    });
  });

  it('缺少 amount 字段返回 400 和错误信息', async () => {
    const orderService = { create: vi.fn() };
    const app = createApp({ orderService: orderService as never });

    const res = await request(app)
      .post('/api/orders')
      .send({ userId: 'u-1' });

    expect(res.status).toBe(400);
    expect(res.body.message).toContain('amount');
    expect(orderService.create).not.toHaveBeenCalled();
  });

  it('业务错误被错误处理中间件转成 422', async () => {
    const orderService = {
      create: vi.fn(async () => {
        throw new Error('支付失败：余额不足');
      }),
    };
    const app = createApp({ orderService: orderService as never });

    const res = await request(app)
      .post('/api/orders')
      .send({ userId: 'u-1', amount: 100 });

    expect(res.status).toBe(422);
    expect(res.body.message).toBe('支付失败：余额不足');
  });
});
```

#### 7.4 数据库真实还是替身

集成测试内部也有粒度选择：

- 薄集成：Service 用替身，只验证“路由 → 中间件 → 控制器”的组装，速度快、定位准。
- 厚集成：Service 与仓储真实，只替换第三方支付，连真实测试数据库，能发现 SQL 和事务问题。

推荐比例：每个接口至少一条薄集成守组装；关键写接口再补厚集成守数据。厚集成所需的数据库隔离与种子策略在下一单元（38）系统讲解。

#### 7.5 与后端系统的关系

中间件顺序错误（如鉴权挂在路由之后）、忘记 `express.json()`、错误处理中间件漏注册，都是上线事故的常见来源，而且单元测试必然通过。supertest 用真实 HTTP 语义覆盖这些接缝，是投入产出比很高的一层。

#### 7.6 常见误区

> 误区一：测试中手动 `app.listen(3000)`。

端口可能冲突、用例结束后服务残留；supertest 可以直接接收 app 函数，无需监听。

> 误区二：只断言状态码，不读响应体。

接口返回 200 但 body 结构错、字段名拼错，前端照样崩；响应体必须有结构断言。

### 8. 命名、结构与可维护性

#### 8.1 Arrange-Act-Assert

每个用例清晰分三段：准备协作者与输入、执行一次被测行为、断言结果与交互。三段之间用空行分隔，阅读者十秒内能找到“测了什么、怎么触发的、期望什么”。

```text
Arrange：构造 Fake 仓储、创建 Service、准备输入
Act：const result = await service.create(input)
Assert：expect(result.id).toBeDefined()
        expect(repo.insert).toHaveBeenCalledTimes(1)
```

#### 8.2 行为导向命名

用例名描述“在什么条件下，应当发生什么行为”，推荐格式：

```text
describe('OrderService.create', () => {
  it('当支付网关返回失败时，不写入订单并抛出业务错误', () => {});
  it('当金额小于等于 0 时，不调用支付网关', () => {});
});
```

避免 `test1`、`handles stuff`、`works correctly` 这类名字：失败列表里看不出哪个业务坏了。

#### 8.3 独立、可重复、不共享可变状态

```text
- 用例之间不传递变量，公共搭建放 beforeEach 或 setup 工厂
- Mock 在用例间 clear/reset，避免“上一个用例的调用记录”污染计数
- 不依赖用例执行顺序，任何用例都能单独运行
- 不断言当前日期、随机值等不可控结果，先把它们注入并固定
```

#### 8.4 覆盖率的正确态度

覆盖率回答“哪些行/分支在测试中被执行过”，不回答“行为是否被验证”。没有断言的用例也能拉高数字。正确用法是：用报告发现从未被触达的模块和分支，优先补“含分支逻辑、曾出缺陷、涉及资金与权限”的位置，而不是为百分比写空测试。

#### 8.5 与后端系统的关系

测试套件是团队每天在 CI 上运行成百上千次的产品。一次偶发失败（flaky）会让大家习惯性点“重跑”，最终对红灯免疫。稳定、快速、命名清晰、失败即定位，是测试体系能长期守住质量的前提。

#### 8.6 常见误区

> 误区一：一个巨型用例走完“建单 → 支付 → 发货 → 退款”，失败无法定位。

按行为拆分，公共步骤沉淀为 setup 工厂或测试数据构造器（builder）。

> 误区二：为了让红灯变绿，删掉断言或 `skip` 用例。

红灯说明被测行为与预期不一致，正确动作是定位代码或修正过时预期，而不是关闭信号。

### 强制不通过条件

出现以下任一情况，本次验收不通过；修正后重新验收：

1. 测试直接连接真实第三方服务或访问真实外部网络。
2. 只覆盖成功路径，金额非法、支付失败、参数错误等失败分支没有用例。
3. Mock 不校验调用参数与次数，或 Mock 了被测模块自身的逻辑。
4. 集成测试中手动 `listen` 固定端口，或只断言状态码不读响应体。
5. 用例之间共享可变状态、不能单独运行，或连续运行三次出现偶发失败。
6. 通过删除断言、跳过用例等方式让红灯变绿。
7. 提交真实密码、令牌、私钥，或测试代码无法按 README 在评审环境运行。
