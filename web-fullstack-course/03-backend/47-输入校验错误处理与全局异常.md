# 47-输入校验、错误处理与全局异常

## 目标

完成本知识单元后，学员应能为后端建立“入口严格校验、内部类型可靠、出口统一响应、异常集中兜底”的防御性编程基线，让非法输入在到达业务逻辑之前就被拒绝。

学员应能够：

1. 解释“所有输入都不可信”的含义，识别请求体、查询参数、路径参数、请求头中的信任边界。
2. 使用 DTO 描述每类接口允许接收的数据形状，拒绝多余字段与非法类型。
3. 使用 Zod 完成声明式校验与 TypeScript 类型收窄，并了解 class-validator 的适用场景。
4. 设计统一错误模型与稳定错误码，让前端能按错误码编程而不是解析提示文案。
5. 实现全局异常中间件，统一处理已知业务错误、校验错误与未知异常。
6. 实现统一响应包装，正确使用 422 等状态码，并保证错误信息不泄露系统内部细节。

本单元处理“数据进来是否合法、出错如何返回”。认证授权相关的 401/403 语义见第 45、46 单元；安全头、限流等出口防护见第 48 单元。

## 详细的理论知识讲解和示例伪代码

### 1. 输入不可信原则与信任边界

#### 定义

输入不可信原则要求后端把一切来自系统外部的数据都视为可能被构造、篡改或畸形的数据，直到它通过显式校验。前端校验、表单控件限制、抓包工具修改都不能作为信任依据：攻击者可以绕过页面直接发送任意 HTTP 请求。

需要校验的入口至少包括：

| 输入来源 | 示例 | 风险 |
|---|---|---|
| 请求体 | `req.body.email` | 类型错误、超长、嵌套注入 |
| 查询参数 | `?page=-1&size=9999` | 负数、超大分页、枚举伪造 |
| 路径参数 | `/users/:id` | 非预期格式、路径穿越片段 |
| 请求头 | `Authorization`、`Referer` | 伪造来源、畸形令牌 |
| 文件与第三方响应 | 上传文件、外部 API 返回 | 内容伪装、下游数据异常 |

#### 与后端的关系

校验必须在业务逻辑入口完成：先校验、再使用。信任边界是“控制器/路由层”这一道闸门——闸门内的函数可以假设输入已经满足约定，闸门内不再需要处处防御，从而让内部代码简洁可靠。

#### 示例

```text
危险心智：前端表单限制了年龄只能输入 18-99，后端直接用 req.body.age
真实情况：攻击者用 curl 发送 {"age": -999}，后端未校验，库存或积分逻辑被绕过

安全心智：无论前端怎样，后端入口只接受符合 Schema 的数据
```

```js
// 每个路由入口先过校验中间件，处理函数拿到的就是干净数据
app.post('/api/users', validate(createUserSchema), (req, res) => {
  const data = req.body; // 此处类型与范围已经由 Schema 保证
  res.status(201).json({ data: createUser(data) });
});
```

#### 常见误区

> 加了 HTTPS，输入就可信了。

HTTPS 保护传输不被窃改，但发送方完全可以提交任意合法加密的恶意内容，与输入校验是两回事。

> 内部系统只给同事用，不用校验。

内部账号可能被冒用，且越权与误操作同样造成损失；任何系统入口都应校验。

### 2. DTO 与数据形状

#### 定义

DTO（Data Transfer Object，数据传输对象）用于显式描述一个接口“接受什么字段、每个字段什么类型和范围”。它同时承担两件事：作为校验依据，以及作为代码间关于输入数据的契约。DTO 应只包含业务真正需要的字段，对未知字段默认剥离或拒绝，避免“批量赋值”攻击（攻击者提交 `isAdmin: true`、`role: 'admin'` 等隐藏字段被原样写入数据库）。

#### 与后端的关系

每个写接口都应有明确 DTO：注册 DTO、登录 DTO、更新文章 DTO。更新类接口要区分“必填”与“可选”，避免缺字段被误写成清空数据。

#### 示例

```ts
// 创建用户 DTO 描述的“数据形状”
interface CreateUserDTO {
  email: string;            // 合法邮箱
  password: string;         // 8-64 位
  nickname: string;         // 2-20 位
  age?: number;             // 18-120，可选
}

// 注意：DTO 中没有 role、isAdmin、balance 等字段
// 即使客户端提交，也应在校验阶段被剥离，不能进入持久化
```

```text
允许进入系统的字段：email、password、nickname、age
被丢弃的字段（白名单之外）：role、isAdmin、id、createdAt、ownerId
白名单机制 = 明确列出允许项，其余一律不接收
```

#### 常见误区

> 用 TypeScript 的 interface 就算做了校验。

类型只在编译期存在，运行时对 JSON 数据没有任何约束；运行时校验需要 Schema 库。

> 客户端传什么字段就存什么字段，省得以后加字段改接口。

这正是批量赋值漏洞来源；多余字段必须显式拒绝或剥离。

### 3. Zod 校验与类型收窄

#### 定义

Zod 是一个以 TypeScript 优先的 Schema 声明与校验库：用链式 API 声明字段约束，调用 `parse` 时若不合法会抛出带路径信息的错误，合法时返回通过校验的值，并可用 `z.infer` 从 Schema 自动推导出静态类型，实现“一次声明、运行时校验与编译期类型同源”。

类型收窄指经过校验后，TypeScript 能把宽泛的 `unknown` 或可选字段收窄为确定类型，后续业务代码不再需要重复判空与转型。

#### 与后端的关系

Zod 应放在请求入口中间件：校验 `body`、`query`、`params` 三处；通过后用清洗过的值替换原始对象；失败转成统一的 422 响应。

#### 示例

```ts
import { z } from 'zod';

export const createUserSchema = z.object({
  email: z.string().trim().email().max(254),
  password: z
    .string()
    .min(8, '密码至少 8 位')
    .max(64)
    .regex(/[a-zA-Z]/, '需包含字母')
    .regex(/\d/, '需包含数字'),
  nickname: z.string().trim().min(2).max(20),
  age: z.coerce.number().int().min(18).max(120).optional(),
});

export type CreateUserInput = z.infer<typeof createUserSchema>;
// 推导结果：{ email: string; password: string; nickname: string; age?: number }
```

```ts
// 通用校验中间件工厂：对 req 的任意部位做 Schema 校验
import type { NextFunction, Request, Response } from 'express';
import { ZodError, type ZodType } from 'zod';

export function validate<T>(schema: ZodType<T>, target: 'body' | 'query' | 'params' = 'body') {
  return (req: Request, res: Response, next: NextFunction) => {
    try {
      const parsed = schema.parse(req[target]); // 不合法直接抛 ZodError
      // object Schema 默认会剥离未知键，防止批量赋值
      req[target] = parsed as Request[typeof target];
      next();
    } catch (err) {
      if (err instanceof ZodError) {
        return res.status(422).json({
          error: {
            code: 'VALIDATION_FAILED',
            message: '请求参数不合法',
            details: err.issues.map((issue) => ({
              path: issue.path.join('.'),
              message: issue.message,
            })),
          },
        });
      }
      next(err);
    }
  };
}
```

```text
输入：{ "email": "bad", "password": "123", "nickname": "x", "role": "admin" }
结果：422，details 指向 email/password/nickname 三条错误；role 被剥离
输入：全部合法 -> 处理函数拿到的类型即 CreateUserInput，无需再转型
```

#### 常见误区

> 只校验类型，不校验范围。

`age` 是 number 但可能是负数或超大数；`page` 要限定最小值和默认值；枚举要用 `z.enum`。

> 每个路由手写 try/catch 处理 ZodError。

错误转换应集中在中间件和全局异常处理中，路由只声明 Schema。

### 4. class-validator 对比认知

#### 定义

class-validator 是基于装饰器的校验库，配合 class-transformer 把普通对象转换为 DTO 类实例并按装饰器规则校验，常见于 NestJS 等依赖装饰器与 IoC 容器的框架。

与 Zod 的主要差异：

| 对比项 | Zod | class-validator |
|---|---|---|
| 声明方式 | 链式 Schema 对象 | 类属性 + 装饰器 |
| 类型来源 | `z.infer` 推导 | 手写 DTS class |
| 剥离多余字段 | object 默认剥离 | 需配合 `excludeExtraneousValues` |
| 生态场景 | 框架无关，函数式友好 | NestJS 深度集成 |

#### 与后端的关系

两种方案解决同一问题，选型跟随团队框架与风格，关键不是库名，而是“入口必须有运行时校验 + 白名单 + 错误集中转换”这三个效果。

#### 示例

```ts
import { Exclude, Expose } from 'class-transformer';
import { IsEmail, IsInt, IsOptional, IsString, Length, Matches, Max, Min } from 'class-validator';

@Exclude() // 默认不接收白名单之外的字段
export class CreateUserDTO {
  @Expose()
  @IsEmail()
  email!: string;

  @Expose()
  @IsString()
  @Length(8, 64)
  @Matches(/[a-zA-Z]/)
  password!: string;

  @Expose()
  @IsString()
  @Length(2, 20)
  nickname!: string;

  @Expose()
  @IsOptional()
  @IsInt()
  @Min(18)
  @Max(120)
  age?: number;
}
```

```js
// 转换 + 校验的概念流程（NestJS 中由 ValidationPipe 自动完成）
async function transformAndValidate(plain) {
  const dto = plainToInstance(CreateUserDTO, plain, { excludeExtraneousValues: true });
  const errors = await validate(dto);
  if (errors.length > 0) {
    throw new ValidationError(flattenValidationErrors(errors));
  }
  return dto;
}
```

#### 常见误区

> 用了 DTO class 就自动安全，不配置剥离选项。

不开启白名单/剥离时，提交的多余字段仍可能被保留，必须显式配置。

> 在普通 Express 函数式项目里强行引入装饰器体系。

没有框架支撑时装饰器方案样板更多；Zod 更轻，选型应匹配工程形态。

### 5. 统一错误模型与错误码

#### 定义

统一错误模型规定所有失败响应使用同一结构，错误码是机器可读的稳定标识，遵循“大写蛇形、语义稳定、一经发布不随意改含义”的约定；`message` 是给人看的提示，可以随语言与产品调整，客户端逻辑不得依赖提示文案。

推荐层次：

```text
error.code     稳定机器码，如 ARTICLE_NOT_FOUND
error.message  面向用户的简述
error.details  字段级错误（校验失败时）或排障编号
```

错误码与 HTTP 状态码各司其职：HTTP 状态码表达大类，错误码表达业务细分。例如同是 409，可能是 `EMAIL_TAKEN` 或 `SLUG_CONFLICT`。

#### 与后端的关系

业务代码通过抛出携带错误码的自定义错误来表达失败，而不是随手 `res.status(...).json(...)`，这样路由逻辑只描述业务，输出格式集中管理。

#### 示例

```ts
// 统一应用错误：业务中可预期的失败都用它
export class AppError extends Error {
  constructor(
    public readonly code: string,
    public readonly status: number,
    message: string,
    public readonly details?: unknown
  ) {
    super(message);
    this.name = 'AppError';
  }
}

// 语义化工厂，避免各处手写状态码
export const Errors = {
  notFound: (resource: string) =>
    new AppError(`${resource.toUpperCase()}_NOT_FOUND`, 404, '资源不存在'),
  conflict: (code: string, message: string) => new AppError(code, 409, message),
  unauthorized: () => new AppError('UNAUTHENTICATED', 401, '请先登录'),
  forbidden: () => new AppError('FORBIDDEN', 403, '没有执行该操作的权限'),
};
```

```js
// 业务使用：意图清晰，输出格式交给全局中间件
async function publishArticle(id, user) {
  const article = await findArticleById(id);
  if (!article) throw Errors.notFound('article');
  if (article.owner_id !== user.id && !user.permissions.has('article:publish:any')) {
    throw Errors.forbidden();
  }
  if (article.status === 'archived') {
    throw new AppError('ARTICLE_ARCHIVED', 409, '已归档文章不能发布');
  }
  return markPublished(article.id);
}
```

#### 常见误区

> 前端直接判断 `message.includes('密码')` 来处理分支。

提示文案会改、会做多语言，这样做必然脆弱；分支必须判断错误码。

> 每个接口自定义一套响应结构。

多套结构会让客户端和监控都无法统一处理；全系统应共用一个错误模型。

### 6. 全局异常中间件

#### 定义

全局异常中间件是 Express 中注册在所有路由之后、带有四个参数 `(err, req, res, next)` 的特殊中间件，是响应离开系统前的最后一道关卡。它负责：识别 AppError 并按其状态码与错误码返回；识别校验错误并转成 422；对未预期错误返回 500，同时记录完整服务端日志，但不把堆栈、SQL、内部路径暴露给客户端。

#### 与后端的关系

Express 4 不会自动捕获 async 函数中的 reject，需要在每个异步处理中把错误传给 `next(err)`，或用包装器统一转发；Express 5 会自动转发异步拒绝。无论哪种，业务代码都不应自己吞掉异常。

#### 示例

```js
// async 包装器（Express 4 必备思路）：把 reject 交给全局中间件
const asyncHandler = (fn) => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next);

app.get(
  '/api/articles/:id',
  asyncHandler(async (req, res) => {
    const article = await findArticleById(req.params.id);
    if (!article) throw Errors.notFound('article');
    res.json({ data: article });
  })
);
```

```js
// 全局异常中间件：必须是四个参数，且注册在路由之后
// eslint-disable-next-line no-unused-vars
app.use((err, req, res, next) => {
  // 1) 已知业务错误
  if (err instanceof AppError) {
    return res.status(err.status).json({
      error: { code: err.code, message: err.message, details: err.details },
    });
  }

  // 2) 校验库错误（例如 ZodError 漏网到这里）
  if (err.name === 'ZodError') {
    return res.status(422).json({ error: { code: 'VALIDATION_FAILED', message: '请求参数不合法' } });
  }

  // 3) 未预期错误：完整细节只进日志，对外给编号
  const incidentId = crypto.randomUUID();
  logger.error({ incidentId, err, path: req.path }, 'unhandled exception');
  res.status(500).json({
    error: { code: 'INTERNAL_ERROR', message: '服务暂时不可用，请稍后重试', incidentId },
  });
});
```

```text
异常分流：
AppError       -> 对应业务状态码与错误码（可预期）
ZodError       -> 422 VALIDATION_FAILED
Body parse 错误 -> 400 MALFORMED_REQUEST
其余未知异常    -> 500 INTERNAL_ERROR + incidentId，细节仅记录在服务端
```

#### 常见误区

> 在全局中间件里把 err.stack 原样返回，方便前端排错。

堆栈会暴露文件路径、依赖版本、SQL 片段，是攻击者的情报来源；对外只能给通用提示与编号。

> 业务代码 try/catch 后什么都不做。

吞异常会让请求挂起或让故障隐形；要么处理并转换，要么向上抛。

### 7. 统一响应包装与 422

#### 定义

统一响应包装规定成功与失败使用对称的外层结构，成功载荷放在 `data`，失败载荷放在 `error`。分页列表还应统一分页元信息。包装的价值在于客户端拦截器、类型定义和监控埋点可以只写一套。

关于状态码的选择：

| 状态码 | 使用时机 |
|---|---|
| 400 Bad Request | 报文本身畸形，如非法 JSON、内容类型错误 |
| 422 Unprocessable Entity | 报文可解析且类型正确，但不满足业务校验规则 |
| 401 / 403 | 认证 / 授权失败 |
| 404 / 409 | 资源不存在 / 状态冲突 |
| 500 | 服务端未预期错误 |

#### 与后端的关系

表单校验失败用 422 并在 `details` 中给字段级错误，前端据此回填到对应输入框；这与“请求没发好”的 400 是不同语义，应区分。

#### 示例

```js
// 成功包装助手
function ok(res, data, status = 200) {
  return res.status(status).json({ data });
}

function paginated(res, items, page, pageSize, total) {
  return res.json({
    data: items,
    meta: { page, pageSize, total, totalPages: Math.ceil(total / pageSize) },
  });
}

app.get('/api/articles', asyncHandler(async (req, res) => {
  const page = Math.max(1, Number(req.query.page) || 1);
  const pageSize = Math.min(50, Math.max(1, Number(req.query.size) || 10));
  const { items, total } = await listArticles({ page, pageSize });
  paginated(res, items, page, pageSize, total);
}));
```

```text
422 响应（表单回填场景）：
HTTP 422
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "请求参数不合法",
    "details": [
      { "path": "email", "message": "邮箱格式不正确" },
      { "path": "password", "message": "密码至少 8 位" }
    ]
  }
}
```

#### 常见误区

> 校验失败也返回 200，在 body 里放 `{ success: false }`。

这样客户端、网关、监控都无法按 HTTP 语义识别失败，重试与告警全部失效。

> 所有错误一律返回 500，省得区分。

会把“用户输入错误”伪装成“服务故障”，既误导监控也让用户无法纠正。

### 8. 错误信息不泄密与日志分级

#### 定义

错误信息不泄密要求对外响应只包含用户完成操作所必需的信息；技术细节（堆栈、SQL、文件系统路径、内部主机名、依赖版本）和业务敏感信息（“该手机号已在其他账号绑定”“某身份证号已存在”）都不应原样暴露。日志则相反：服务端日志应尽量完整，便于排障，但日志本身也要分级并脱敏，因为日志会被更多人员检索、可能被集中存储。

日志级别约定：

```text
error  未预期异常、需要人工介入（含 incidentId）
warn   可预期但异常的业务事件，如频繁登录失败
info   关键业务里程碑
debug  仅开发环境的详细上下文
```

#### 与后端的关系

同一次失败要生成两份视图：对外是安全、稳定、可展示的错误模型；对内是带上下文的结构化日志，用 incidentId 把两者关联，用户反馈编号即可定位。

#### 示例

```js
function logAndMaskError(incidentId, err, req) {
  logger.error({
    incidentId,
    name: err.name,
    message: err.message,
    stack: err.stack, // 仅服务端
    path: req.path,
    params: maskSensitive(req.params),
  });
}

function maskSensitive(obj) {
  const clone = { ...obj };
  for (const key of ['password', 'token', 'idCard', 'creditCard']) {
    if (key in clone) clone[key] = '***';
  }
  return clone;
}
```

```text
账号枚举防护：
错误做法：注册接口对“已存在邮箱”返回详细提示 -> 攻击者批量探测注册情况
安全做法：登录失败统一“邮箱或密码错误”；注册是否提示已占用按业务取舍并配合限流

敏感字段：密码、令牌、身份证、银行卡号永不出现在 URL、日志明文与错误详情中
```

#### 常见误区

> 为了显得透明，把数据库报错原文返回给用户。

错误原文常含表名、字段名、值片段，是注入探测的反馈通道；应只给通用提示。

> 日志记录完整请求体，排查最方便。

请求体可能含密码与证件号，必须在记录前脱敏并控制访问权限。

## 实践练习题

### 练习 1：Zod 校验中间件与用户注册

#### 任务

实现通用校验中间件，为注册接口编写 Zod Schema，完成非法输入的 422 返回与合法输入的类型收窄。

#### 步骤约束

1. 实现 `validate(schema, target)` 中间件，支持 body、query、params；失败返回统一错误模型的 422 与字段级 details。
2. 编写注册 Schema：邮箱、密码（8-64 位含字母数字）、昵称（2-20）、可选年龄（18-120）。
3. 验证未知字段（如 `role`、`isAdmin`）不会进入处理函数。
4. 合法请求返回 201；处理函数中直接使用推导类型，不做任何手动转型。
5. 为 Schema 编写至少 8 条用例：合法、空值、超长、类型错误、边界年龄、多余字段等。

#### 提交物

- Schema 与中间件代码；
- 测试用例与运行结果；
- 合法与 422 两类请求/响应记录；
- 100 字以上关于“类型收窄后内部代码为何可以简化”的说明。

#### 验收标准

- 422 响应 details 精确到字段路径；
- 多余字段被剥离，无法写入数据库；
- 处理函数中无手动类型断言；
- 边界值（18、120、8 位密码）行为正确；
- 不通过放宽正则或长度规则制造通过。

### 练习 2：统一错误模型与全局异常中间件

4. 对非法 JSON 请求体返回 400；对漏网校验错误返回 422。
5. 编写测试触发每一类错误，断言状态码与错误码稳定。

### 练习 3：分页、422 回填与脱敏综合改造

#### 任务

5. 编写端到端风格脚本，串联成功创建、422 回填、分页越界被纠偏、异常编号四个场景。

#### 提交物

#### 验收标准

- 更新操作不会因缺字段清空数据；
