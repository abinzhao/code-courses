# 04-环境变量权限与终端安全

## 目标

完成本知识单元后，学员应能把“配置”“身份”“权限”和“不可信输入”四件事放进同一个工程心智模型，而不是只会照抄教程里的启动命令。

学员应能够：

1. 用自己的语言解释环境变量是什么，并演示一个进程如何从父进程继承环境、为什么子进程改不动父 Shell 的变量。
2. 使用临时前缀和 `export` 两种方式设置环境变量，准确说出两者的作用域与生效时间；解释 Shell 如何借助 `PATH` 找到命令。
3. 在 Node.js 程序中通过 `process.env` 读取环境变量，把值按需要转换类型，并在启动时对必需变量做校验，缺失时输出可定位的信息并以非零退出码退出。
4. 使用 `.env`、`.env.example` 和 `.gitignore` 的组合管理本地配置，并用 Git 命令证明含密钥的文件不会被提交。
5. 读懂 `ls -l` 的权限输出，解释属主、组和其他三类身份以及 `rwx` 的含义，使用 `chmod`、`chown` 调整权限，按最小权限原则设置密钥文件、脚本和目录。
6. 识别命令注入、`eval`、`rm -rf` 误用和 `curl | sh` 四类常见终端风险，把“拼接用户输入到 shell”的代码改写为参数数组方式，并说明理由。

本单元只覆盖 Web 开发日常会直接遇到的环境变量、权限与终端安全基础。后端登录认证体系、依赖供应链安全和容器权限模型将在后续单元展开。

## 技术栈

本单元不使用前端框架、后端框架、数据库或第三方 npm 包；理解 `.env` 加载机制时以阅读思想为主，不要求安装 `dotenv`。

| 工具或环境 | 用途 | 学习要求 |
|---|---|---|
| Node.js 当前 LTS | 运行脚本、读取环境变量、安全调用子进程 | 能使用 `process.env`、`process.exit` 和参数数组式 API |
| macOS 或 Linux Terminal（zsh / bash） | 观察和设置环境、执行命令 | 能区分 Shell 内置命令与外部程序 |
| `printenv` / `env` | 查看当前环境变量 | 能查看全部变量与单个变量 |
| `export` / `unset` | 设置与删除 Shell 环境变量 | 能说出对当前会话和子进程的影响 |
| `which` | 查看命令的实际路径 | 能结合 `PATH` 解释查找结果 |
| `ls` / `chmod` / `chown` | 查看与修改文件权限和归属 | 能读懂权限串并按最小权限设置 |
| `git` | 验证忽略规则与提交内容 | 能用 `git status`、`git check-ignore` 取证 |
| `curl` | 仅用于安全的只读观察 | 能先查看地址与内容，不执行管道安装 |

课程命令以 macOS 和常见 Linux 环境为主：

- macOS 默认 Shell 通常是 zsh，Linux 上常见 bash；本单元的环境变量语法两者通用。
- Windows 学员建议在 WSL2 中完成本单元；PowerShell 的 `$env:NAME` 语法不作为主线。
- `<NAME>`、`<PID>` 表示需要替换的占位参数，不要原样输入尖括号。
- 所有示例中的密钥均为明显的占位值，例如 `REPLACE_ME_IN_LOCAL_ENV`，不是真实凭证。

开始前检查环境：

```bash
node -v
printenv | head -n 5
which node
git --version
```

预期观察：

- `node -v` 输出当前安装的 Node.js 版本号。
- `printenv | head -n 5` 输出当前 Shell 环境中的前 5 个变量，每行形如 `NAME=value`。
- `which node` 输出 `node` 可执行文件的完整路径，例如 `/usr/local/bin/node` 或用户目录下由版本管理器安装的路径。
- `git --version` 输出 Git 版本信息。

版本号不是考点。关键是确认这些工具存在，并能读懂后续命令的输出。

## 详细的理论知识讲解和示例伪代码

### 1. 环境变量：操作系统级的键值对配置

#### 1.1 通俗定义

环境变量是操作系统在进程启动时交给它的一组“键 = 值”字符串。可以把它理解为程序运行时随身带着的一张小卡片，上面写着配置信息：

```text
HOME=/Users/alice
USER=alice
SHELL=/bin/zsh
PORT=3000
```

程序不需要修改源代码，只要换一张卡片，就能改变行为。

#### 1.2 与 Web 开发的关系

Web 程序经常需要在不同条件下运行：

- 在开发者电脑上连接本地测试接口；
- 在公司测试环境中连接测试数据库；
- 在线上服务器上使用线上地址和端口；
- 在 CI 流水线中由平台注入地址和密钥。

这些差异不应该写死在代码里。常见做法是代码只负责读取变量，具体值由运行环境提供：

```text
服务启动
    ↓
读取环境变量 PORT，缺省时使用 3000
读取环境变量 API_BASE_URL，决定向哪个地址发起请求
    ↓
同一份代码在不同环境中表现不同
```

#### 1.3 查看环境变量

查看全部环境变量：

```bash
printenv
```

查看单个变量，变量名前加 `$`：

```bash
echo $HOME
```

预期：输出当前用户的主目录路径，例如 `/Users/alice`。

也可以使用 `printenv` 直接指定变量名：

```bash
printenv USER
```

预期：输出当前用户名。

#### 1.4 为什么不把配置写死在代码里

如果把配置写成这样：

```javascript
// 不推荐：配置与代码耦合
const port = 3000;
const apiBaseUrl = 'https://test.example.com';
const apiKey = 'REPLACE_ME_IN_LOCAL_ENV';
```

会带来三个问题：

1. 换环境必须改代码，改代码就可能引入新错误。
2. 密钥进入 Git 历史，即使后续删除也仍可能被翻出。
3. 多开发者共用一个仓库时，每个人的本地配置互相覆盖。

推荐思路是代码与配置分离：

```javascript
// 推荐：代码只描述“从哪里读”，不写死具体值
const port = process.env.PORT ?? '3000';
const apiBaseUrl = process.env.API_BASE_URL;
```

#### 1.5 常见误区

> 环境变量是一种编程语言或配置文件格式。

环境变量本质上是操作系统提供的一组字符串，不是文件格式，也不是语言。`.env` 只是一个用来方便地批量提供这些字符串的文本文件，它本身不会被系统自动加载。

> 环境变量可以保存数字、布尔值等多种类型。

操作系统传递的环境变量全部是字符串。`PORT=3000` 中的 `3000` 到了程序里也是字符串 `"3000"`，需要时由程序自己转换。

### 2. 作用域、进程继承与两种设置方式

#### 2.1 每个进程都有自己的环境

操作系统中每个进程启动时都持有一份属于自己的环境变量表。两份关键事实：

- 子进程默认从父进程继承一份环境副本。
- 子进程修改的是自己的副本，不会反向影响父进程。

#### 2.2 进程继承机制

在终端里启动程序时的继承过程：

```text
Shell 进程（例如 zsh）持有一份环境表
        ↓ 用户输入 node app.js
Shell 请求操作系统创建子进程
        ↓
操作系统把 Shell 的环境复制一份交给子进程
        ↓
Node.js 进程在自己独立的环境副本中运行
        ↓
Node.js 修改自己的环境变量
        ↓
父 Shell 的环境表不受任何影响
```

这解释了一个常见现象：在 Node.js 里 `process.env.X = '1'`，退出后回到终端 `echo $X`，什么也看不到。

#### 2.3 方式一：临时前缀

把变量写在命令前面，只对这一次启动的进程生效：

```bash
PORT=3001 node app.js
```

预期：这次启动的 Node.js 进程能读到 `PORT=3001`；命令结束后，当前 Shell 中并没有名为 `PORT` 的变量。

可以同时设置多个：

```bash
PORT=3001 NODE_ENV=development node app.js
```

#### 2.4 方式二：export

使用 `export` 把变量导出到当前 Shell 会话，之后从这个 Shell 启动的子进程都能继承：

```bash
export PORT=3001
node app.js
```

预期：第一条命令没有输出；之后在同一终端窗口里执行的命令都能读到 `PORT=3001`，直到手动修改或关闭终端。

验证作用域：

```bash
export DEMO_SCOPE=hello
echo $DEMO_SCOPE
```

预期：输出 `hello`。新开一个终端窗口再执行 `echo $DEMO_SCOPE`，预期输出为空，因为新窗口是新的 Shell 会话。

删除变量：

```bash
unset DEMO_SCOPE
echo $DEMO_SCOPE
```

预期：第二条命令输出为空。

#### 2.5 子 Shell 实验

下面的命令在一个子 Shell 中设置变量并立即打印：

```bash
( export INNER_ONLY=abc; echo "子Shell中: $INNER_ONLY" )
echo "父Shell中: $INNER_ONLY"
```

预期：第一行输出 `子Shell中: abc`，第二行输出 `父Shell中:`（冒号后为空），因为括号中的命令运行在子进程里。

#### 2.6 常见误区

> 在一个终端窗口 `export` 的变量，全局永久有效。

它只对当前 Shell 会话及其子进程有效。关闭窗口即失效。要长期生效需要写入 Shell 配置文件，这属于个性化配置，课程不建议把项目变量写进个人 Shell 配置。

> 临时前缀设置的变量会污染当前终端。

临时前缀只注入紧随其后的那一个进程，不改变 Shell 本身。这正是它适合“一次性实验”的原因。

### 3. PATH：Shell 如何找到命令

#### 3.1 通俗定义

`PATH` 是一个特殊的环境变量，内容是一组用冒号分隔的目录列表。当输入一个不是内置命令的名称时，Shell 会按顺序到这些目录里查找同名可执行文件。

```text
/usr/local/bin:/usr/bin:/bin:/Users/alice/.local/bin
```

#### 3.2 命令查找过程

以输入 `node app.js` 为例：

```text
1. node 是不是 Shell 内置命令？不是。
2. 是不是定义过的别名或函数？没有。
3. 按 PATH 中的目录从左到右逐个查找：
   /usr/local/bin 里有 node 吗？有 → 使用它，停止查找。
4. 若所有目录都找不到：输出 command not found。
```

查看当前 `PATH`：

```bash
echo $PATH
```

查看某个命令实际命中的路径：

```bash
which node
which git
```

预期：输出对应可执行文件的完整路径。若没有任何输出，通常表示该命令不在 `PATH` 的任何目录中。

#### 3.3 与 Web 开发的关系

这类问题在安装 Node 版本管理器后很常见：

```text
现象：终端里 node 能运行，IDE 的内置终端却提示 command not found
原因：两个 Shell 会话的 PATH 不一致，IDE 没有加载版本管理器初始化脚本
```

安装全局 CLI 后提示找不到命令，也往往是因为全局安装目录没有加入 `PATH`。理解查找机制后，排查方向就从“重装”变成“打印 PATH 并对比目录”。

#### 3.4 PATH 污染风险

- 把不可信目录放到 `PATH` 最前面，攻击者可以在其中放置与常用命令同名的恶意程序，实现“偷换命令”。
- 把当前目录 `.` 放进 `PATH`，进入恶意目录后执行 `ls` 可能运行目录内的同名陷阱程序。
- 空的目录项（连续两个冒号）在部分 Shell 中可能被当作当前目录，同样有风险。

#### 3.5 常见误区

> 安装了程序就一定能直接输入名称运行。

Shell 只认 `PATH` 里的目录。程序安装在非标准目录时，要么写完整路径，要么把其目录以合理顺序加入 `PATH`。

> `which node` 显示了路径，就说明所有终端都用这个 node。

`which` 只反映当前会话的查找结果。不同终端、不同用户、不同初始化脚本下，结果可能不同。

### 4. Web 开发常见环境变量与 Node.js 读取

#### 4.1 系统提供的常见变量

| 变量名 | 含义 | 示例值 |
|---|---|---|
| `HOME` | 当前用户主目录 | `/Users/alice` |
| `USER` | 当前用户名 | `alice` |
| `SHELL` | 默认 Shell 程序路径 | `/bin/zsh` |
| `PWD` | 当前工作目录 | `/Users/alice/project` |
| `PATH` | 命令查找目录列表 | 见上一节 |

#### 4.2 应用程序常见变量

| 变量名 | 常见用途 |
|---|---|
| `NODE_ENV` | 标识运行环境，常见值为 `development`、`test`、`production` |
| `PORT` | 服务监听端口 |
| `API_BASE_URL` | 自定义变量：后端或第三方接口基础地址 |
| `LOG_LEVEL` | 自定义变量：日志详细程度 |

`NODE_ENV` 是约定俗成的变量，不是 Node.js 强制保留字。程序和框架根据它选择不同行为，例如输出更详细的错误信息或启用不同优化策略。

#### 4.3 在 Node.js 中读取：process.env

Node.js 通过全局对象 `process` 的 `env` 属性暴露环境变量：

```javascript
// env-demo.js
console.log('HOME =', process.env.HOME);
console.log('USER =', process.env.USER);
console.log('PORT =', process.env.PORT);
console.log('类型 =', typeof process.env.PORT);
```

运行：

```bash
PORT=3000 node env-demo.js
```

预期：依次打印主目录、用户名和 `3000`，最后一行输出 `类型 = string`，说明读出来的是字符串。

需要数字时显式转换：

```javascript
const port = Number(process.env.PORT ?? '3000');

if (!Number.isInteger(port) || port < 1 || port > 65535) {
  console.error('PORT 必须是 1 到 65535 之间的整数');
  process.exit(1);
}
```

#### 4.4 缺省值与“服务端可见”边界

合理使用缺省值，让本地开发零配置可跑：

```javascript
const nodeEnv = process.env.NODE_ENV ?? 'development';
```

需要建立一条安全边界：

- 运行在 Node.js 服务端的代码可以读取服务端进程的环境变量，包括密钥。
- 浏览器端代码不应该、也无法直接读取服务器的环境变量。前端构建工具只会把明确允许暴露的变量编译进浏览器产物，具体前缀规则（例如 `VITE_`、`NEXT_PUBLIC_`）由工具决定。
- 因此，任何带 `VITE_` 等暴露前缀的变量都应视为“任何人都能在浏览器里看到”，不能放密钥。

#### 4.5 常见误区

> 不设置 `NODE_ENV`，Node.js 就无法运行。

`NODE_ENV` 未设置时程序照样运行，读到的是 `undefined`。很多框架只是默认按开发模式处理。

> 前端代码里也可以直接读服务器的密钥环境变量。

前端代码最终下载到用户浏览器执行，它没有服务器进程的环境。把密钥放进会暴露给浏览器的变量，等于公开密钥。

### 5. .env 文件、dotenv 思想与密钥保护

#### 5.1 .env 文件长什么样

`.env` 是一个约定俗成的文本文件，每行一个键值对，用于本地开发时集中提供环境变量：

```text
# .env（本地开发用，含模拟占位值）
NODE_ENV=development
PORT=3000
API_BASE_URL=http://127.0.0.1:8080
API_KEY=REPLACE_ME_IN_LOCAL_ENV
```

以 `#` 开头的行是注释。

#### 5.2 启动时加载的思想

`.env` 不会被操作系统自动读取。所谓 `dotenv`，思想是：程序启动时先读这个文本文件，把里面的键值对放进 `process.env`，然后再执行业务逻辑。下面是一个极简概念实现，用来理解原理：

```javascript
// load-env.js —— 仅用于理解加载思想的极简示例
import { readFileSync } from 'node:fs';

function loadEnv(filePath) {
  const text = readFileSync(filePath, 'utf8');

  for (const rawLine of text.split('\n')) {
    const line = rawLine.trim();

    // 跳过空行和注释
    if (!line || line.startsWith('#')) continue;

    const equalIndex = line.indexOf('=');
    if (equalIndex === -1) continue;

    const key = line.slice(0, equalIndex).trim();
    let value = line.slice(equalIndex + 1).trim();

    // 去掉成对的引号
    if (
      (value.startsWith('"') && value.endsWith('"')) ||
      (value.startsWith("'") && value.endsWith("'"))
    ) {
      value = value.slice(1, -1);
    }

    // 已存在的真实环境变量优先，不被文件覆盖
    if (process.env[key] === undefined) {
      process.env[key] = value;
    }
  }
}

loadEnv('.env');
console.log(process.env.API_BASE_URL);
```

运行 `node load-env.js`，预期输出 `.env` 中配置的 `http://127.0.0.1:8080`。

真实项目可以使用成熟的 `dotenv` 包完成同样工作，但入门阶段应先理解“读文件、解析键值、写入进程环境”这条主线。

#### 5.3 用 .gitignore 防止提交密钥

`.gitignore` 告诉 Git 哪些文件不纳入版本管理。项目中应明确忽略本地密钥文件：

```text
# .gitignore（节选）
node_modules/
.env
.env.local
*.local
```

验证忽略是否生效：

```bash
git status
git check-ignore -v .env
```

预期：

- `git status` 的未跟踪文件列表中不出现 `.env`。
- `git check-ignore -v .env` 输出命中的忽略规则及文件名，例如 `.gitignore:3:.env    .env`，证明该文件确实被忽略。

#### 5.4 用 .env.example 传递“需要哪些变量”

队友需要知道项目要求哪些变量，但又不能提交真实值。做法是提交一个不含密钥的模板文件：

```text
# .env.example（可以安全提交）
NODE_ENV=development
PORT=3000
API_BASE_URL=http://127.0.0.1:8080
API_KEY=请向团队申请本地开发密钥后替换本行
```

新人的操作路径是：复制模板为 `.env`，填入本地值；`.env` 被忽略，`.env.example` 被提交。

```bash
cp .env.example .env
```

预期：得到一个本地 `.env`，它不会出现在 `git status` 中。

#### 5.5 常见误区

> 仓库是私有的，所以可以提交 `.env`。

私有仓库仍有成员变动、日志、备份和授权第三方工具等多种泄露途径。更关键的是，密钥一旦进入 Git 历史，删除当前文件并不能消除历史记录。

> 把变量名改成复杂字符串就算加密。

混淆变量名不是加密。密钥管理的正确方向是不入库、由环境或平台注入，并在泄露后可轮换。

### 6. 文件权限模型：rwx、属主、组与其他

#### 6.1 为什么有权限模型

类 Unix 系统是多用户系统。操作系统用权限控制“谁能读、写、执行”每个文件，防止用户互相破坏或越权访问。Web 服务器、CI 运行账号也都是系统中的“身份”，同样受这套规则约束。

#### 6.2 读懂 ls -l 的输出

```bash
ls -l
```

典型输出：

```text
-rw-r--r--  1 alice  staff   412  10月  9 10:00 .env.example
-rwxr-xr-x  1 alice  staff  1803  10月  9 10:00 deploy.sh
drwxr-xr-x  2 alice  staff    64  10月  9 10:00 src
```

拆开看第一段 `-rwxr-xr-x`：

```text
-  rwx  r-x  r-x
│   │    │    └─ 其他用户（other）：读、不能写、可执行
│   │    └────── 同组用户（group）：读、不能写、可执行
│   └─────────── 文件属主（user/owner）：读、写、执行
└─────────────── 文件类型：- 为普通文件，d 为目录，l 为软链接
```

后续字段依次是硬链接数、属主名、组名、大小、修改时间和文件名。

#### 6.3 rwx 的准确含义

| 权限 | 对文件 | 对目录 |
|---|---|---|
| `r`（读，4） | 可查看内容 | 可列出目录内文件名 |
| `w`（写，2） | 可修改内容 | 可在目录中新建、删除、重命名文件 |
| `x`（执行，1） | 可作为程序运行 | 可进入该目录并访问其中文件 |

特别注意：对目录而言，删除文件看的是“所在目录”的写权限，而不是文件本身的写权限。

#### 6.4 数字权限

三组权限各用三位二进制表示，再压成一个八进制数字：

```text
属主 rwx = 4+2+1 = 7
组   r-x = 4+0+1 = 5
其他 r-- = 4+0+0 = 4
合起来：754
```

常见组合：

| 数字 | 权限串 | 典型用途 |
|---|---|---|
| `600` | `-rw-------` | 密钥、`.env`：仅属主可读写 |
| `644` | `-rw-r--r--` | 普通文档：属主可改，其他人只读 |
| `755` | `-rwxr-xr-x` | 脚本、程序：所有人可执行，仅属主可改 |
| `700` | `-rwx------` | 私有可执行脚本或敏感目录 |

#### 6.5 chmod 与 chown

修改权限用 `chmod`。给脚本增加属主执行权限：

```bash
chmod u+x deploy.sh
ls -l deploy.sh
```

预期：属主权限位出现 `x`，例如 `-rwxr-xr-x`。

直接按数字设置：

```bash
chmod 600 .env
ls -l .env
```

预期：权限串为 `-rw-------`，其他用户无法读取该文件。

修改属主和组用 `chown`（通常需要管理员权限）：

```bash
chown alice:staff report.txt
```

含义：把文件属主改为 `alice`、组改为 `staff`。入门阶段只要求理解它的作用，日常练习中应优先使用自己账号拥有的文件，不随意更改系统文件归属。

#### 6.6 最小权限原则

最小权限指只授予完成任务所必需的最小访问权。落到 Web 开发日常：

```text
.env、私钥文件        → 600，只有属主能读写
可执行脚本            → 755，不要默认对所有人开放写
普通源码和文档        → 644
项目目录              → 755（需要进入和读取）
```

额外收益：服务器进程若以低权限账号运行，即使被攻击，攻击者能读写的范围也被限制在该账号的权限内，不会直接获得整台机器的控制权。

#### 6.7 常见误区

> 权限给满（777）最省事，能解决所有访问问题。

`777` 意味着任何用户都能写和执行，等于放弃权限保护。访问被拒绝时正确做法是查清“哪个身份需要什么权限”，而不是放开全部权限。

> 文件不可执行，加上读权限就能运行。

读取内容和作为程序执行是两种权限。脚本必须具备 `x` 位才能以 `./script.sh` 方式直接运行；用 `bash script.sh` 运行则只需要读权限，因为真正执行的是 `bash`。

### 7. 终端安全：命令注入、eval 与危险命令

#### 7.1 命令注入：把用户输入拼进 shell

当程序把不可信输入直接拼接到命令字符串里，再交给 shell 执行时，攻击者可以通过特殊字符改变命令结构，这就是命令注入。

危险写法：

```javascript
// 危险：字符串拼接后交给 shell 解释
import { exec } from 'node:child_process';

function listDir(userInput) {
  exec(`ls -l ${userInput}`, (error, stdout) => {
    console.log(stdout);
  });
}
```

若用户输入是：

```text
; rm -rf $HOME
```

拼接后的命令变成：

```text
ls -l ; rm -rf $HOME
```

shell 会把分号解释为命令分隔符，先执行 `ls -l`，再执行删除。类似的危险字符还有 `&&`、反引号、`$()`、管道和重定向。

#### 7.2 安全写法：参数数组，不经过 shell

```javascript
// 安全：以参数数组调用，不启动 shell 解释
import { execFile } from 'node:child_process';

function listDir(userInput) {
  execFile('ls', ['-l', userInput], (error, stdout) => {
    console.log(stdout);
  });
}
```

此时用户输入只会成为 `ls` 的一个参数（一个文件名字符串），其中的分号不会被解释为命令分隔符。

还应在业务层做输入约束：

```text
接收用户输入
    ↓
按允许规则校验（只允许预期字符，或限定在指定目录内）
    ↓
使用参数数组调用外部程序
    ↓
拒绝任何不符合规则的输入，并记录可排查的信息
```

#### 7.3 eval 的风险

`eval` 会把字符串当作代码执行：

```javascript
// 危险：输入一旦可被影响，等于允许执行任意 JavaScript
const rawConfig = receiveUntrustedText();
const config = eval(`(${rawConfig})`);
```

解析 JSON 应使用专用方法：

```javascript
const config = JSON.parse(rawConfig);
```

`JSON.parse` 只接受数据文本，不执行函数、变量引用等代码结构，遇到非法格式直接报错。

#### 7.4 rm -rf 的风险

`rm -rf` 会递归、不提示地删除。它本身是合法工具，风险来自变量缺失和路径误判：

```bash
# 危险：若 TARGET_DIR 为空，可能展开成对根目录的删除
rm -rf "$TARGET_DIR"/*
```

更安全的写法是先校验变量：

```bash
if [ -z "$TARGET_DIR" ]; then
  echo "TARGET_DIR 未设置，拒绝执行"
  exit 1
fi

rm -rf -- "$TARGET_DIR"/*
```

要点：

1. 删除前用 `pwd` 和 `ls` 确认路径真实存在且符合预期。
2. 对变量做空值检查；`--` 表示之后不再解析选项，防止文件名以 `-` 开头被当作选项。
3. 自动化脚本优先提供 dry-run（先打印将要删除的内容）。
4. 不把自己不理解的删除命令复制进终端，尤其是带 `/`、`$HOME`、通配符的命令。

#### 7.5 curl | sh 的风险

```bash
# 高风险：下载后立即交给 shell 执行，没有检查机会
curl -fsSL https://example.com/install.sh | sh
```

风险在于：

- 脚本内容在执行前没有经过检查，其中可能包含破坏性命令。
- 远端内容可能随时间变化，今天正常不代表明天安全。
- 网络传输中若地址或证书异常，可能拿到非预期内容。

更稳妥的步骤：

```bash
curl -fsSL -O https://example.com/install.sh
less install.sh
# 确认脚本内容可信后，再决定是否执行
sh install.sh
```

即“先下载、阅读、再执行”。

#### 7.6 sudo 与最小权限

`sudo` 以管理员身份执行命令，权限放大后任何错误或恶意逻辑的破坏面也同步放大。

- 不为了“方便”给 `npm install -g`、脚本或编辑器默认加 `sudo`。
- 全局安装权限问题，优先通过版本管理器、用户级目录或正确的目录归属解决。
- 执行带 `sudo` 的命令前，应能说清楚它为什么必须提权、会改动哪些位置。

#### 7.7 常见误区

> 输入来自自己网站的表单，所以是可信的。

所有外部输入都应视为不可信，包括表单、URL 参数、请求头、文件内容和第三方接口返回。攻击者不需要登录后台，只要能影响被拼接的字符串。

> 用了参数数组就不需要任何业务校验。

参数数组解决的是“shell 解释特殊字符”的问题；业务上允许访问哪些路径、多大范围，仍需用白名单或目录约束控制，两道防线解决的是不同问题。
