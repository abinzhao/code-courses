# 07-HTTPS、Cookie、CORS 与 HTTP 缓存

## 目标

完成本知识单元后，学员应能说清“浏览器和服务器之间的消息是否可信、由谁识别身份、跨域规则在哪里生效、资源为什么可以不重新下载”，并能用工具拿出证据，而不是只记住几个安全名词。

学员应能够：

1. 用自己的语言解释明文 HTTP 的三类风险（被窃听、被篡改、无法验证身份），并说明 HTTPS 在 HTTP 与传输层之间增加了什么。
2. 区分对称加密、非对称加密和哈希的用途，说明 TLS 为什么要把三者组合使用，但不要求手写加密算法。
3. 讲清 CA、证书、公钥和证书链的关系，能根据浏览器或 `curl` 的证据判断一次 HTTPS 连接是否正常，读懂常见证书告警。
4. 根据 `Set-Cookie` 中的 `Domain`、`Path`、`Expires`、`Max-Age`、`HttpOnly`、`Secure`、`SameSite` 判断 Cookie 的发送范围和生命周期，并比较 Session 与 Token 两种登录态思路。
5. 判断两个 URL 是否同源，区分简单请求与预检请求，读懂 `Access-Control-*` 响应头，并说明为什么 CORS 不是前端在请求里加头就能单方面解决的问题。
6. 区分强缓存与协商缓存，读懂 `Cache-Control`、`Expires`、`ETag`、`Last-Modified` 和 `304`，并解释静态资源文件名加 hash 的部署策略。

本单元只建立机制层面的理解。登录接口、Session 存储和 JWT 的具体签发与校验将在后端课程中实现；本单元不要求编写 JWT。

## 技术栈

本单元不使用前端框架，不要求安装第三方 npm 包。重点是用浏览器自带工具和命令行观察真实流量。

| 工具或环境 | 用途 | 学习要求 |
|---|---|---|
| Chrome 或 Edge 当前稳定版 | 浏览页面、观察网络与安全信息 | 能使用 DevTools 的 Network、Security、Application 面板 |

协议基线：

- 现代浏览器与服务器默认使用 TLS 1.2 或 TLS 1.3；更旧的 TLS 版本正在被淘汰，课程不把它们作为学习目标。
- HTTPS 之下可以承载 HTTP/1.1、HTTP/2 或 HTTP/3，本单元关注的安全机制与具体 HTTP 版本无关。
- 域名、端口、状态码和请求方法等 HTTP 基础属于前置知识，本单元直接使用。

开始前检查环境：

```bash
curl --version
node -v

```

- `curl --version` 输出 `curl` 版本及其支持的协议列表，列表中应包含 `https`。
- `node -v` 输出当前安装的 Node.js 版本号。
- `openssl version` 输出 OpenSSL 版本；部分系统使用其他 TLS 实现，命令不存在时可跳过证书查看实验，不影响主线学习。

版本号不是考点。关键是确认工具存在，并能读懂后续输出。

## 详细的理论知识讲解和示例伪代码

### 1. HTTP 为什么不安全

#### 1.1 明文传输：路上的明信片

HTTP 消息在网络上以明文形式逐跳转发。客户端与服务器之间通常经过路由器、运营商设备、公共 Wi-Fi 接入点等多个中间节点，任何一个节点都可以直接读到请求和响应内容。

可以把 HTTP 想象成明信片：

- 内容写在外面，每个经手的人都能看；
- 经过的人还能在投递前改掉上面的字；
- 收件人无法仅凭明信片确认寄件人是谁。

在 Web 场景中，以下内容在明文 HTTP 下都可能被路过节点读到：

- 登录表单中的用户名和密码；
- URL 中的查询参数，例如 `?token=...`；
- Cookie 头中的会话标识；
- 接口返回的个人信息和业务数据。

常见误解：

> 我的页面没有敏感数据，用 HTTP 无所谓。

即使页面本身不敏感，页面中引用的脚本也可能被篡改（见 1.4），而且现代浏览器会对 HTTP 页面标注“不安全”，很多新 API（摄像头、地理位置、Service Worker 等）只在安全上下文中开放。

#### 1.2 中间人攻击

中间人攻击（Man-in-the-Middle，MITM）指攻击者处在通信双方之间，对客户端冒充服务器、对服务器冒充客户端，双方却以为自己在直接对话。

```text
没有攻击者时：

浏览器  <-------------------->  服务器

公共 Wi-Fi 中存在攻击者时：

浏览器  <------->  攻击者  <------->  服务器
                 转发、偷看、篡改
```

公共 Wi-Fi、被入侵的路由器、伪造的接入点都是中间人可能出现的位置。明文 HTTP 对这种攻击几乎没有识别能力。

#### 1.3 无法验证对方身份

HTTP 没有内置“你是谁”的验证机制。浏览器连上某个 IP 的 80 端口，并不能证明对面就是自己想访问的网站。

- DNS 解析可能被污染，返回错误的 IP；
- 接入点可能把流量导向伪造站点；
- 伪造站点可以返回和真站一模一样的页面。

仅凭 URL 栏里的域名，在 HTTP 下也无法保证对面持有该域名。

#### 1.4 内容可被篡改

因为没有完整性保护，中间节点不仅能看，还能改：

- 在网页中插入广告或恶意脚本；
- 把下载链接替换成带病毒的安装包；
- 偷加流量统计代码；
- 修改 API 返回的数据。

早期运营商网络中出现过的“网页被注入广告”，就是明文 HTTP 可被篡改的典型例子。

#### 1.5 HTTPS 不是一个新协议

HTTPS（HTTP Secure）并不是另一个应用协议，而是“HTTP 跑在 TLS 之上”：

```text
明文：
  HTTP  →  TCP  →  IP

加密：
  HTTP  →  TLS  →  TCP  →  IP
```

TLS（Transport Layer Security）在传输之前对 HTTP 消息加密，并完成身份验证和完整性保护。URL 中的 `https://` 和默认端口 `443` 表示使用这条链路。

HTTPS 要同时解决三件事：

1. 保密性：路上的人看不懂内容；
2. 完整性：内容被改过能被发现；
3. 身份认证：确认对面是证书上的那个域名。

只解决其中一件都不够，例如“自己加密但不验证服务器身份”，仍可能把密文发给假冒者。

### 2. 对称加密、非对称加密与哈希

#### 2.1 对称加密：一把共用的钥匙

对称加密指加密和解密使用同一把密钥。知道密钥的双方可以互相加解密，不知道密钥的人即使拿到密文也无法读懂。

```text
明文 "订单金额 100"
  + 密钥 K 加密 →  密文（看起来是随机字节）
  + 密钥 K 解密 →  明文 "订单金额 100"
```

特点：

- 速度快，适合大量数据，TLS 真正传输网页内容用的是对称加密；
- 难点是“怎么把这把共用密钥安全地交给对方”，在不可信网络上直接发送密钥等于把钥匙也交给了攻击者。

常见误解：

> 对称加密不安全，因为双方要共享密钥。

对称加密本身强度足够，问题出在密钥协商环节。TLS 的做法是用非对称手段安全地协商出对称密钥，再用对称密钥传输数据。

#### 2.2 非对称加密：成对的公钥与私钥

非对称加密使用一对数学上相关的密钥：

- 公钥：可以公开给任何人；
- 私钥：必须由持有者秘密保存，绝不外传。

两种基本用法：

```text
用法 A：公钥加密，只有私钥能解密
浏览器用服务器的公钥加密一段信息 → 只有持有对应私钥的服务器能解开

用法 B：私钥签名，任何人都能用公钥验证
服务器用私钥对摘要签名 → 浏览器用对应公钥验证，确认内容确实来自私钥持有者
```

特点：

- 解决了“如何在不安全信道上协商”和“如何证明身份”的问题；
- 计算成本高，不适合直接加密大量网页数据；
- 证书的核心内容之一，就是经过 CA 签名的服务器公钥（见第 3 节）。

常见误解：

> 公钥和私钥可以互相推算。

公钥可以公开发布正是因为从公钥在计算上无法推出私钥。私钥一旦泄露，整对密钥都必须作废更换。

#### 2.3 哈希：不可逆的指纹

哈希函数把任意长度的数据压缩成固定长度的摘要（指纹）。

```text
SHA-256("hello")  →  2cf24dba5fb0a30e...（固定 64 个十六进制字符）
SHA-256("hellp")  →  完全不同的结果，只改一个字母也天差地别
```

三个关键性质：

1. 同样输入永远得到同样输出；
2. 输入哪怕改动一个字节，摘要也明显不同；
3. 不能从摘要反推出原文。

在 Web 安全中的用途：

- 数字签名：对“消息的哈希”签名，而不是对整条消息签名；
- 证书与密码存储（密码应使用专门的慢哈希加盐存储，本单元只建立概念）；
- 完整性校验，例如核对下载文件的摘要。

常见误解：

> 哈希就是加密，解密就能得到原文。

哈希没有“解密”。它是单向的，无法还原原文；加密则是可逆的，持有密钥可以解密。

#### 2.4 数字签名的概念

数字签名把“哈希 + 非对称加密”组合起来：

```text
签名方：
  1. 对消息计算哈希
  2. 用自己的私钥加密这个哈希 → 得到签名

验证方：
  1. 用对方的公钥解密签名，得到原哈希
  2. 对收到的消息重新计算哈希
  3. 两个哈希一致 → 消息确实来自私钥持有者，且中途未被修改
```

证书本身就是 CA 对“网站公钥和身份信息”的签名，浏览器用 CA 的公钥来验证它。

#### 2.5 为什么 TLS 要把三种机制组合使用

| 机制 | 提供的能力 | 在 TLS 中的角色 |
|---|---|---|
| 对称加密 | 高速加解密大量数据 | 握手完成后传输 HTTP 内容 |
| 非对称加密 | 在不安全信道协商、证明身份 | 交换密钥材料、验证签名 |
| 哈希 | 指纹与完整性校验 | 签名、密钥派生、防篡改 |

三者各管一段，任何一个单独使用都无法同时实现保密、完整和身份认证。

### 3. TLS 握手与证书链

#### 3.1 连接开始时要解决的三个问题

浏览器在发送任何 HTTP 请求之前，先要通过 TLS 握手解决：

1. 协商：双方就使用哪套加密算法达成一致；
2. 认证：确认服务器真的持有目标域名；
3. 密钥交换：安全地产生只有双方知道的会话密钥。

#### 3.2 数字证书里有什么

数字证书是一张“公钥的身份证”，核心字段包括：

- 主体（Subject）：证书属于谁，例如域名 `example.com`；
- 公钥：服务器的公钥；
- 签发者（Issuer）：是哪家 CA 签的；
- 有效期（Not Before / Not After）；
- 签名：CA 对上述内容的数字签名；
- 扩展：例如这张证书还覆盖哪些域名。

证书不包含服务器私钥。服务器在握手时用私钥完成证明，但私钥永远不会发送给浏览器。

#### 3.3 CA 与证书链

CA（Certificate Authority，证书机构）是浏览器和操作系统预先信任的签发者。浏览器内置了一组受信任的根 CA 公钥，称为信任锚。

真实站点很少直接由根 CA 签发，通常是一条链：

```text
根 CA（自签名，预置在操作系统/浏览器中）
  ↓ 用根私钥签名
中间 CA
  ↓ 用中间 CA 私钥签名
example.com 的站点证书（包含 example.com 的公钥）
```

验证逻辑是逐级向上：

```text
用中间 CA 的公钥验证站点证书签名
用根 CA 的公钥验证中间 CA 签名
根 CA 在本地信任列表中 → 整条链可信
```

常见误解：

> 浏览器是实时联网去问 CA“这张证书真不真”。

证书链的主体验证依靠本地预置的根证书和证书上的签名在本地完成；在线检查（如证书吊销状态查询）是补充手段，不是信任的根基。

#### 3.4 TLS 握手宏观过程

下面是简化的概念流程，省略了具体密码学细节，重点是理解每一步解决什么问题：

```text
1. ClientHello
   浏览器 → 服务器：我支持的 TLS 版本和加密算法列表、随机数 A

2. ServerHello + Certificate
   服务器 → 浏览器：选定的算法、随机数 B、自己的证书链

3. 证书验证
   浏览器本地：验证证书链、有效期、域名是否匹配
   验证不通过 → 发出告警，停止连接（见 3.6）

4. 密钥交换
   双方利用证书公钥和交换的材料，各自算出同一个会话密钥 K
   攻击者看不到私钥，无法算出 K

5. 完成
   双方互发“后续通信改用会话密钥 K 加密”的确认
   握手结束，之后的 HTTP 消息全部用 K 对称加密
```

需要抓住的结论：

- 非对称运算只在握手阶段用于认证和协商；
- 真正的页面数据用协商出的对称密钥加密；
- 每次连接产生新的会话材料，长期使用的私钥泄露不等于历史流量自动可解（具备前向保密的密钥交换尤其如此）。

#### 3.5 HTTPS 验证：浏览器具体检查什么

浏览器对收到的证书至少检查四项：

1. 证书链能否追溯到本地受信任的根 CA；
2. 证书主体中的域名与当前访问的域名是否匹配（支持通配符，如 `*.example.com`）；
3. 当前时间是否在有效期之内；
4. 证书是否已被吊销（通过在线检查等机制）。

任何一项失败，浏览器都会显示整页告警，例如“您的连接不是私密连接”“NET::ERR_CERT_AUTHORITY_INVALID”。此时不应教用户盲目点击“继续访问”。

#### 3.6 常见告警的含义与误区

| 现象 | 常见原因 | 说明 |
|---|---|---|
| 证书颁发机构不受信任 | 使用自签名证书、公司代理拦截 | 公网正式站点不应出现 |
| 证书域名不匹配 | 证书签给了别的域名 | 可能是配置错误，也可能是假冒站点 |
| 证书已过期 | 运维未续期 | Let's Encrypt 一类证书有效期较短，需自动续期 |
| 混合内容被拦截 | HTTPS 页面引用了 HTTP 资源 | 浏览器会阻止或升级这类请求 |

常见误解：

> 页面上有把小锁就绝对安全。

锁只证明“到该域名的传输加密且证书验证通过”，不代表这个网站本身不骗人；钓鱼站同样可以申请到合法证书。

### 4. Cookie 属性与登录态

#### 4.1 Cookie 是什么

Cookie 是服务器通过 `Set-Cookie` 响应头让浏览器保存的小型键值数据，之后浏览器对同一服务器的请求会自动通过 `Cookie` 请求头带上。

```text
响应：Set-Cookie: sid=abc123; Path=/; HttpOnly
后续请求：Cookie: sid=abc123
```

典型用途：会话标识、登录态、简单的偏好设置。它的核心特点是“浏览器自动携带”，这既是方便之处，也是风险来源。

#### 4.2 Domain 与 Path：决定发送范围

- `Domain`：Cookie 对哪些域名生效。不写时默认是当前精确主机；设置为父域名后，子域名也会携带。
- `Path`：URL 路径前缀匹配，命中才发送。

```text
Set-Cookie: a=1; Domain=example.com
  → example.com、api.example.com、www.example.com 都会带上

Set-Cookie: b=2; Path=/admin
  → 只有 /admin 开头的请求带上
```

常见误解：

> 把 Cookie 的 Domain 设成另一个公司的域名，就能让浏览器把 Cookie 发给它。

浏览器不允许设置与当前站点无关的 Domain。Cookie 不能被用来向任意第三方域名写入数据。

#### 4.3 Expires 与 Max-Age：决定生命周期

- `Expires`：绝对到期时间（一个具体日期）；
- `Max-Age`：相对存活秒数，优先级高于 `Expires`。

```text
Set-Cookie: keep=1; Max-Age=3600        # 1 小时后过期
Set-Cookie: old=1; Expires=Wed, 21 Oct 2026 07:28:00 GMT
```

两者都不写时，Cookie 成为会话 Cookie：浏览器关闭后通常被清除。删除一个已有 Cookie 的标准做法，是用相同的 `Domain` 和 `Path` 重新设置一个已过期的同名 Cookie。

#### 4.4 HttpOnly 与 Secure

- `HttpOnly`：JavaScript 无法通过 `document.cookie` 读到该 Cookie，能降低 XSS 偷取会话标识的风险；
- `Secure`：只在 HTTPS 连接中发送，HTTP 下不会发送。

```text
Set-Cookie: sid=abc123; HttpOnly; Secure
```

常见误解：

> 设置了 HttpOnly，网站就不会遭受 XSS。

HttpOnly 只保护 Cookie 不被脚本读取，不阻止 XSS 本身。攻击者注入的脚本仍可以以用户身份发起请求。

> 在本地 http://localhost 开发时 Secure Cookie 行为正常。

现代浏览器对 `localhost` 有特殊对待，但在普通 HTTP 主机上 Secure Cookie 不会被保存，团队应统一本地开发约定。

#### 4.5 SameSite：控制跨站发送

`SameSite` 决定 Cookie 在跨站请求中是否被携带，用于缓解 CSRF（跨站请求伪造）：

| 取值 | 行为 |
|---|---|
| `Strict` | 跨站请求完全不携带；从外站链接点进来时首次也不带 |
| `Lax` | 默认值；同站携带，跨站的顶层 GET 导航携带，跨站接口请求不携带 |
| `None` | 允许跨站携带，但必须同时设置 `Secure` |

```text
Set-Cookie: sid=abc123; SameSite=Lax
Set-Cookie: cross=1; SameSite=None; Secure
```

注意“同站（same-site）”与“同源（same-origin）”是两个概念：同站看的是注册域名（含子域名），同源还要比较协议和端口。

#### 4.6 一个完整的 Set-Cookie 示例

```text
Set-Cookie: sid=abc123;
  Domain=example.com;
  Path=/;
  Max-Age=604800;
  HttpOnly;
  Secure;
  SameSite=Lax
```

读法：名为 `sid` 的会话标识，在 example.com 及其子域的所有路径上发送，7 天有效，脚本读不到，仅 HTTPS 发送，跨站接口请求不携带。

#### 4.7 Session 与 Token：两种登录态思路

Session 模式：

```text
1. 登录成功后，服务器生成随机会话标识 sid，并把用户数据保存在服务端（内存/数据库/缓存）
2. 浏览器只保存 sid（通常放在 Cookie 中）
3. 之后请求带上 sid，服务器查自己的会话存储确认身份
4. 登出 = 服务器删除这条会话
```

Token 模式：

```text
1. 登录成功后，服务器签发一个自包含的令牌（概念上：载荷 + 签名），交给客户端
2. 客户端保存令牌，请求时通过 Authorization 头带回
3. 服务器用密钥验证签名和有效期，无需在服务端保存会话
4. 令牌在到期前通常不能靠“删除服务端记录”立即作废
```

概念对比：

| 维度 | Session | Token |
|---|---|---|
| 状态保存位置 | 服务端 | 客户端携带，服务端只保存验签密钥 |
| 典型载体 | Cookie（自动携带） | `Authorization` 请求头（手动添加） |
| 跨子域/跨服务 | 依赖 Cookie 域与共享会话存储 | 各服务只要能验签即可 |
| 立即注销 | 删除服务端会话即可 | 需要黑名单等额外机制 |
| 对 CSRF 的关系 | Cookie 自动携带，需配合 SameSite/CSRF 防护 | 用请求头携带时天然不会被自动带上 |

常见误解：

> Token 一定比 Session 安全，JWT 一定比 Cookie 安全。

安全与否取决于存储位置、传输方式、有效期、泄露面等具体设计。两者都必须走 HTTPS。JWT 的签发、刷新和吊销实现属于后端课程，本单元不展开。

### 5. 同源策略与 CORS

#### 5.1 同源的定义

两个 URL 只有在协议、域名、端口三者完全相同时才算同源：

```text
http://www.example.com:80/page
        │       │            │
      协议     域名          端口
```

对比示例：

| URL A | URL B | 是否同源 | 原因 |
|---|---|---|---|
| `https://a.com` | `https://a.com/x` | 是 | 仅路径不同 |
| `https://a.com` | `http://a.com` | 否 | 协议不同 |
| `https://a.com` | `https://api.a.com` | 否 | 域名不同 |
| `https://a.com` | `https://a.com:8443` | 否 | 端口不同 |

#### 5.2 同源策略限制了什么

同源策略是浏览器实施的安全边界：默认情况下，脚本只能读取同源响应；跨源的图片、脚本等资源可以加载（标签能力），但脚本通常读不到其中内容。

需要特别记住：

- 这是浏览器的限制，不是互联网的通用规则；
- 服务器之间用 `curl` 或后端代码互相请求，不存在 CORS 拦截；
- 请求往往已经发出去了，被拦截的是“浏览器把响应交给脚本”这一步。

常见误解：

> CORS 报错说明请求没有到达服务器。

很多情况下请求已经到达服务器并被处理，只是响应缺少许可头，浏览器拒绝让 JavaScript 读取结果。因此预检之外的写请求可能已经产生副作用。

#### 5.3 简单请求

满足特定条件的请求被归为简单请求，浏览器直接发送，不做预检。常见条件包括：

- 方法是 `GET`、`HEAD` 或 `POST`；
- 只使用安全范围的请求头（如 `Accept`、`Content-Type` 等有限集合）；
- `Content-Type` 仅限 `text/plain`、`multipart/form-data`、`application/x-www-form-urlencoded`。

```text
浏览器实际发送：
POST /api/login HTTP/1.1
Origin: https://www.example.com
Content-Type: application/x-www-form-urlencoded
```

响应中需要带：

```text
Access-Control-Allow-Origin: https://www.example.com
```

浏览器比对响应头与当前源，匹配才把响应交给脚本。

#### 5.4 预检请求

不满足简单请求条件时，例如 `Content-Type: application/json` 的 `POST`、或带自定义头（如 `Authorization`），浏览器会先发一个 `OPTIONS` 请求询问服务器：

```text
预检：
OPTIONS /api/items HTTP/1.1
Origin: https://www.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type,authorization

服务器许可：
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://www.example.com
Access-Control-Allow-Methods: GET, POST, OPTIONS
Access-Control-Allow-Headers: content-type, authorization
Access-Control-Max-Age: 600

预检通过后，浏览器才发送真正的 POST。
```

`Access-Control-Max-Age` 表示预检结果可以缓存多少秒，缓存期内不必重复询问。

#### 5.5 Access-Control-* 响应头一览

| 响应头 | 作用 |
|---|---|
| `Access-Control-Allow-Origin` | 允许读取响应的源；`*` 表示任意源 |
| `Access-Control-Allow-Methods` | 允许的方法（预检回答） |
| `Access-Control-Allow-Headers` | 允许的请求头（预检回答） |
| `Access-Control-Allow-Credentials` | 是否允许携带凭证（Cookie） |
| `Access-Control-Expose-Headers` | 允许脚本读取的响应头白名单 |
| `Access-Control-Max-Age` | 预检结果缓存时间 |

#### 5.6 带凭证的跨域请求

跨域请求默认不携带 Cookie。要携带必须两边同时满足：

1. 前端请求显式要求凭证（如 `fetch(url, { credentials: 'include' })`）；
2. 服务器返回 `Access-Control-Allow-Credentials: true`；
3. 此时 `Access-Control-Allow-Origin` 不能是 `*`，必须回显具体源；
4. Cookie 自身的 `SameSite`、`Secure` 等属性仍要满足。

```text
请求：Origin: https://www.example.com
响应：
Access-Control-Allow-Origin: https://www.example.com
Access-Control-Allow-Credentials: true
```

#### 5.7 为什么前端不能单方面解决

CORS 的许可信息来自服务器响应头，浏览器只认这个。在前端请求里加 `Access-Control-Allow-Origin` 头不仅无效，还可能因新增非简单头而额外触发预检。

可行的解决路径只有：

- 正式方案：在服务器配置正确的 CORS 响应头，按需开放源、方法和凭证；
- 开发期方案：使用本地开发服务器的代理，让浏览器以为请求同源（代理服务器再转发），这只是开发手段，线上仍需正确配置；
- 同源部署：把前端和接口放在同一源下，由路径区分。

```text
开发代理的本质：

浏览器 → /api/...（同源，不触发 CORS）→ 本地开发服务器
本地开发服务器 → https://api.example.com（服务器之间转发，没有 CORS 概念）
```

### 6. HTTP 缓存

#### 6.1 为什么需要缓存

重复下载没变化的资源既慢又浪费带宽。缓存让浏览器或中间代理复用已获取的副本：

- 减少页面加载时间；
- 减轻服务器压力；
- 节省用户流量。

缓存主要分两条路径：强缓存（不问服务器直接用）和协商缓存（问过服务器再决定用不用）。

#### 6.2 强缓存：Cache-Control 与 Expires

命中强缓存时，浏览器不会向服务器发请求，Network 中显示 `200 (from disk cache)` 或 `200 (from memory cache)`。

现代控制方式是 `Cache-Control`：

```text
Cache-Control: max-age=31536000     # 1 年内视为新鲜，直接用本地副本
Cache-Control: no-cache             # 名字有迷惑性：不是不用，而是每次使用前必须向服务器验证
Cache-Control: no-store             # 真正的不缓存，连本地都不留
Cache-Control: public               # 浏览器和中间代理都可以缓存
Cache-Control: private              # 仅终端浏览器可缓存（含个人数据的响应常用）
```

旧方式 `Expires` 给出绝对过期时间：

```text
Expires: Wed, 21 Oct 2026 07:28:00 GMT
```

两者同时存在时 `Cache-Control` 优先。`Expires` 依赖客户端时钟，且是 HTTP/1.0 时代产物，新项目应以 `Cache-Control` 为准。

#### 6.3 协商缓存：ETag、Last-Modified 与 304

强缓存过期后，浏览器可以带着验证信息询问服务器“我的副本还能用吗”：

- `ETag`：资源内容的实体标识（类似内容指纹），对应请求头 `If-None-Match`；
- `Last-Modified`：资源最后修改时间，对应请求头 `If-Modified-Since`。

```text
首次响应：
HTTP/1.1 200 OK
ETag: "v-3f9a"
Last-Modified: Tue, 20 Oct 2026 10:00:00 GMT

再次请求（带上验证信息）：
GET /app.js HTTP/1.1
If-None-Match: "v-3f9a"
If-Modified-Since: Tue, 20 Oct 2026 10:00:00 GMT

内容没变 → 服务器不重发正文：
HTTP/1.1 304 Not Modified
（浏览器复用本地副本）

内容变了 → 正常返回：
HTTP/1.1 200 OK（带新的 ETag 和正文）
```

`304` 没有响应体，节省的是正文传输，但仍有一次往返。`ETag` 比 `Last-Modified` 更精确（秒级时间戳无法区分一秒内多次修改，也可能被误改时间）。

#### 6.4 缓存决策流程

```text
需要请求一个资源：

本地有副本吗？
├─ 没有 → 发请求，按响应缓存
└─ 有
   ├─ 在强缓存新鲜期内（如 max-age 未到）？
   │   ├─ 是 → 直接用副本，不发请求
   │   └─ 否 → 带上 ETag/Last-Modified 发验证请求
   │            ├─ 服务器返回 304 → 复用副本
   │            └─ 服务器返回 200 → 使用新正文并更新缓存
```

#### 6.5 静态资源 hash 策略

部署前端时面临一个矛盾：

- JS/CSS 希望长期强缓存以提速；
- 但代码更新后，用户必须立刻拿到新版本。

工程上的标准解法是“内容指纹 + HTML 不缓存（或短缓存）”：

```text
构建产物：
app.3f9a2c.js       ← 文件名包含内容 hash
app.7b1d0e.css
index.html          ← 引用带具体 hash 的文件名

部署新版（内容变化）：
app.e8c44f.js       ← hash 变了，等于一个新 URL
index.html         ← 改为引用新文件名
```

为什么有效：

1. 带 hash 的文件内容与文件名一一对应，可以放心 `max-age=31536000` 永久强缓存；
2. 内容一变，hash 就变，URL 变了，浏览器当成全新资源，绝不会拿到旧副本；
3. HTML 是入口，不长期缓存或必须协商验证，保证用户拿到的 HTML 指向最新 hash 文件。

常见误解：

> 用户看到旧页面，让用户清缓存就行。

清缓存是人工兜底，不是工程方案。正确的 hash 策略能让更新自动生效，无需用户操作。HTML 若被长期强缓存，才会出现“怎么发版都是旧页面”的事故。

#### 6.6 常见缓存误区汇总

| 误解 | 实际情况 |
|---|---|
| `no-cache` 表示不缓存 | 表示使用前必须向服务器验证 |
| 强缓存命中会有网络请求 | 不会，`200 from cache` 完全不发请求 |
| 304 会返回正文 | 不返回正文，只告知副本仍有效 |
| 所有响应都该长缓存 | 含个人信息的接口通常用 `private` 或 `no-store` |
| 接口数据天然不缓存 | 是否缓存取决于响应头与业务，需要显式决策 |

### 7. 用 DevTools 与 curl 观察

#### 7.1 用 curl 只看响应头

```bash
curl -sSI https://example.com
```

参数含义：`-s` 静默进度，`-S` 仍显示错误，`-S` 与 `-s` 组合，`-I` 只取 HEAD 响应头。

预期观察：

- 状态行如 `HTTP/2 200`；
- 能看到 `content-type`、`cache-control`、`expires`、`etag`、`last-modified` 等头；
- 若该站点设置了缓存相关头，可以直接读到具体策略。

#### 7.2 观察 TLS 握手细节

```bash
curl -svI https://example.com -o /dev/null
```

`-v` 输出连接过程的诊断信息（输出到 stderr），`-o /dev/null` 丢弃正文。

预期观察：

- 可以看到 `TLSv1.2` 或 `TLSv1.3` 字样及协商出的加密套件；
- 能看到证书校验成功的过程；
- 证书有问题时会在这里报 SSL 证书错误。

查看证书的主体、签发者和有效期：

```bash
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates
```

预期观察：输出三行，分别是 `subject=`（域名）、`issuer=`（签发 CA）、`notBefore=` 与 `notAfter=`（有效期）。对照第 3.5 节的四项检查逐一确认。

#### 7.3 DevTools Security 面板

打开 DevTools → Security：

- 正常 HTTPS 站点显示“Certificate valid”之类的有效提示；
- 可以查看证书查看器，读出证书链层级；
- 证书异常的站点会在此标红，说明失败原因。

#### 7.4 在 Application 面板观察 Cookie

DevTools → Application → Cookies：

- 逐列对照每个属性：Domain、Path、Expires/Max-Age、HttpOnly、Secure、SameSite；
- 勾选 HttpOnly 的 Cookie 在 Console 中用 `document.cookie` 读取时不会出现；
- 可以手动删除 Cookie 观察登出或重新登录的行为。

#### 7.5 在 Network 面板观察 CORS

1. 打开一个跨域页面或自己的实验页面；
2. 发起 `application/json` 的 POST，观察多出一条 `OPTIONS` 请求，状态码通常为 `204`；
3. 点开 OPTIONS 请求，在 Response Headers 中读出五项 `Access-Control-*`；
4. 故意让服务器不返回许可头，观察 Console 中的 CORS 报错，并确认真正的 POST 是否已发出。

#### 7.6 观察强缓存与协商缓存

1. 打开页面后在地址栏回车或在页面内跳转，观察静态资源是否变为 `200 (from disk/memory cache)`；
2. 勾选 Network 中的 `Disable cache`，再刷新，应看到全部请求重新发出；
3. 对返回 `ETag` 的资源直接刷新（不勾选 Disable cache），观察 `304`；
4. 对照请求头中的 `If-None-Match` 与上次响应的 `ETag`，验证两者一致。

#### 7.7 证据记录模板

观察任何一个结论时，建议按下表记录，避免“我记得是 304”这类无证据表述：

```text
资源 URL：
请求方法与状态（含 from cache 标注）：
关键请求头：
关键响应头：
现象与结论：
结论属于“已观察事实”还是“推测”：
```

### 练习 3：CORS 与缓存综合实验

#### 任务

启动两个不同端口的本地服务：页面服务（提供一个发起请求的 HTML 页面）与接口服务。先观察跨域被拦截，再在接口服务上正确放开 CORS，并叠加缓存策略观察。

#### 步骤约束

1. 页面分别发起一个简单 GET 和一个 `application/json` 的 POST。
2. 先不加任何 CORS 响应头，记录 Console 报错，并确认 OPTIONS 与 POST 的实际发送情况。
3. 在接口服务增加正确的 `Access-Control-Allow-Origin`、`Allow-Methods`、`Allow-Headers`，处理 OPTIONS 预检，再观察请求成功。
4. 增加 `credentials` 场景：前端使用 `credentials: 'include'`，服务端回显具体源并返回 `Allow-Credentials: true`，验证 `*` 在该场景下不可用。
5. 对一个静态文件分别设置 `max-age` 强缓存与 `ETag` 协商缓存，观察 `200 from cache` 与 `304`。
6. 将该文件复制为“文件名带内容 hash”的形式，修改内容后观察 URL 与缓存变化。

#### 提交物

- `page-server.js` 与 `api-server.js`；
- 报错与修复前后的 Network 证据；
- 预检请求的完整请求头与响应头记录；
- 强缓存、协商缓存与 hash 文件三组观察记录；
- 300 字以内结论，说明“开发代理”与“服务端 CORS 配置”的区别。

#### 验收标准

- 能复现并解释简单请求、预检与凭证请求三种情况；
- 明确指出请求已发出但响应被拦截的情形；
- 能观察并解释 `200 from cache`、`304` 与 hash 更新；
- 解决方式全部落在服务器侧或工程代理，不出现“在前端加 Allow-Origin”的错误做法；
- 实验结束后关闭所有本地服务，无残留端口。
