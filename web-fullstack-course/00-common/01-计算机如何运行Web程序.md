# 01-计算机如何运行 Web 程序

## 目标

完成本知识单元后，学员应能建立一套服务于 Web 开发的程序运行心智模型，而不是只记住几条系统命令。

学员应能够：

1. 画出源代码、Node.js 运行时、操作系统与硬件资源之间的关系图。
2. 用自己的语言解释程序从启动、运行、等待 I/O 到退出的基本过程。
3. 区分源代码、运行时、进程、PID、端口和退出码，避免混用这些概念。
4. 使用系统工具观察进程的 PID、父 PID、状态、CPU 占用和内存占用。
5. 使用端口监听信息判断一个服务是否正在运行，以及端口是否被其他进程占用。
6. 根据 CPU、内存、进程状态、端口和退出码等证据，提出合理的故障排查方向。
7. 区分浏览器中的前端 JavaScript 与 Node.js 中的服务端 JavaScript 的运行位置、能力和安全边界。
8. 比较 CPU 密集型任务与 I/O 密集型任务的外部表现，说明为什么两者需要不同的优化思路。

本单元只建立必要的基础模型。线程调度、JavaScript 事件循环、文件系统规则、网络协议和浏览器渲染流程将在后续知识单元中分别展开。

## 技术栈

本单元不使用前端框架、后端框架、数据库或第三方 npm 包。

| 工具或环境 | 用途 | 学习要求 |
|---|---|---|
| Node.js 当前 LTS | 运行 JavaScript 程序 | 能启动脚本、读取进程信息、观察退出 |
| macOS 或 Linux Terminal | 输入命令并读取系统证据 | 能识别命令、参数、输出和退出码 |
| `node` | 启动 Node.js 程序 | 理解一次启动通常对应一个 Node.js 进程 |
| `ps` | 查看进程快照 | 能读取 PID、PPID、状态、CPU 和内存 |
| `top` | 持续观察资源变化 | 能比较计算任务和等待任务 |
| `lsof` | 查看端口与进程关系 | 能定位占用指定端口的进程 |
| `kill` | 向进程发送终止信号 | 能优先使用可清理资源的正常终止方式 |
| 活动监视器或系统监视器 | 图形化观察进程 | 能将图形界面信息与命令行证据对应 |

课程命令以 macOS 和常见 Linux 环境为主：

- macOS 可使用 `top -pid <PID>` 聚焦指定进程。
- Linux 通常使用 `top -p <PID>` 聚焦指定进程。
- `ps`、`top` 输出列和状态字母可能因系统版本不同而略有差异。
- `<PID>` 和 `<PORT>` 表示需要替换的参数，不要原样输入尖括号。
- Windows 学员可以在 WSL 中完成本单元；原生 PowerShell 的对应命令不作为主线内容。

开始前检查环境：

```bash
node -v
ps --help
lsof -v
```

预期观察：

- `node -v` 输出当前安装的 Node.js 版本。
- `ps --help` 在部分 macOS 环境可能不支持；此时可使用 `man ps` 查看手册。
- `lsof -v` 输出工具版本信息。

版本号不是本单元考点。关键是确认命令存在，并能理解后续输出。

## 详细的理论知识讲解和示例伪代码

### 1. 计算机资源模型

#### 1.1 CPU：执行指令

CPU 是负责执行指令的计算资源。比较、计算、循环、解析和编码等操作都需要 CPU 时间。

在 Web 开发中的常见例子：

- 浏览器计算页面脚本；
- Node.js 解析 JSON；
- 对大量数据排序或聚合；
- 图片压缩和加密计算；
- 构建工具转换 TypeScript、打包模块。

CPU 占用高不一定表示程序出错，必须结合持续时间和业务目标判断：

- 短时间升高后恢复，可能是正常计算。
- 长时间接近一个核心的上限，可能存在大循环、低效算法或计算任务过重。
- CPU 很低但请求仍然很慢，瓶颈可能不在计算，而在网络、磁盘、数据库或外部服务。

常见误解：

> CPU 负责长期保存程序数据。

CPU 会使用寄存器和缓存辅助计算，但业务数据的主要运行时存放位置是内存，长期保存通常依赖磁盘或远程存储。

#### 1.2 内存：保存正在使用的数据

内存用于保存当前正在运行的程序代码和数据。Node.js 加载模块、创建对象、保存数组和处理请求时都会使用内存。

可以把内存理解为工作台：

- 工作台越大，同一时间可展开的材料越多。
- 材料不断堆积且不清理，工作台最终会放不下。
- 程序退出后，操作系统通常会回收该进程占用的内存。

在 Web 开发中的常见例子：

- 浏览器保存当前页面的 DOM、样式和 JavaScript 对象；
- Node.js 保存请求上下文、缓存和临时计算结果；
- 构建工具保存模块图和中间产物；
- 测试运行器保存测试环境与结果。

常见误解：

> 把数据放在内存变量中，就已经完成了持久化。

进程退出、崩溃或机器重启后，普通内存变量不会可靠保留。需要长期保存的数据应写入文件、数据库或其他持久化系统。

#### 1.3 磁盘：持久保存文件

磁盘用于保存源代码、依赖、配置、日志、构建产物和数据库文件。与内存相比，磁盘通常容量更大、能够持久保存，但访问速度更慢。

启动一个 Node.js 程序时通常会经历：

1. 从磁盘读取入口文件。
2. 继续读取程序依赖的模块。
3. 将执行所需内容加载到内存。
4. CPU 执行运行时解释或编译后的指令。

常见误解：

> 文件已经在磁盘上，所以程序运行时不会占用内存。

程序运行时仍需把代码和数据加载到内存。磁盘保存和内存使用是两个不同阶段。

#### 1.4 网络：连接其他计算机或服务

网络让程序与其他设备或服务交换数据。浏览器请求 API、Node.js 访问数据库、服务调用第三方接口，都属于网络 I/O。

网络请求通常包含两个不同阶段：

1. 程序发起请求，需要少量 CPU 组织数据和调用系统能力。
2. 程序等待远端响应，这段时间不代表 CPU 必须持续计算。

常见误解：

> 请求耗时 3 秒，就说明 CPU 连续计算了 3 秒。

请求可能大部分时间都在等待网络、远端服务器或数据库。判断瓶颈需要查看时间线和资源证据。

#### 1.5 一次 API 请求如何使用资源

下面的伪代码展示资源之间的协作关系：

```text
浏览器准备请求参数                 # 使用 CPU 和内存
浏览器通过网络发送请求             # 使用网络 I/O
服务器接收请求                     # 使用网络 I/O
Node.js 解析请求                    # 使用 CPU 和内存
服务器读取数据库                   # 等待网络或磁盘 I/O
Node.js 处理查询结果                # 使用 CPU 和内存
服务器发送响应                     # 使用网络 I/O
浏览器解析响应并更新页面            # 使用 CPU 和内存
```

这个过程说明：用户感受到的“慢”可能来自多个位置，不能只凭感觉认定是前端、后端或网络问题。

### 2. 从源代码到运行中的进程

#### 2.1 源代码是什么

源代码是开发者编写并保存在文件中的文本，例如：

```text
app.js
package.json
README.md
```

源代码描述“程序应该做什么”，但文件本身不会主动执行。必须由合适的运行环境读取和执行。

#### 2.2 Node.js 运行时是什么

Node.js 是 JavaScript 运行时。它提供：

- JavaScript 语言执行能力；
- 模块加载能力；
- 文件、网络、进程等服务端 API；
- 与操作系统交互的能力。

当执行下面的命令时：

```bash
node app.js
```

可以把它理解为：

```text
启动 Node.js 程序
把 app.js 作为入口文件交给 Node.js
由 Node.js 加载并执行其中的 JavaScript
```

Node.js 不是操作系统，也不是一个后端框架。Express 等框架运行在 Node.js 之上，Node.js 又依赖操作系统提供更底层的资源管理能力。

#### 2.3 进程是什么

进程是“正在运行的程序实例”。同一个源文件可以同时启动多次，每次启动通常都会形成独立进程。

例如连续执行两次：

```bash
node app.js
node app.js
```

如果两个程序都保持运行，系统中会出现两个 Node.js 进程。它们：

- 可以读取同一个源文件；
- 通常拥有不同的 PID；
- 拥有各自的内存空间；
- 可能竞争同一个端口或文件资源；
- 可以分别退出。

因此：

```text
源代码文件 ≠ Node.js 运行时 ≠ 进程
```

更完整的关系是：

```text
源代码
  ↓ 由运行时加载
Node.js 运行时
  ↓ 在操作系统管理下运行
进程
  ↓ 使用
CPU、内存、磁盘、网络等资源
```

#### 2.4 PID 与 PPID

PID 是 Process ID，即进程标识。操作系统使用 PID 区分当前正在运行的不同进程。

PPID 是 Parent Process ID，即父进程标识。终端启动 Node.js 时，Node.js 进程通常会把当前 Shell 进程作为父进程。

需要注意：

- PID 只在当前系统的当前运行周期内有意义。
- 进程退出后，它原来的 PID 可能在未来被其他进程重新使用。
- 不能把 PID 写死在长期脚本或文档中。
- PID 不是端口号，两者解决的问题不同。

#### 2.5 PID 与端口的区别

| 概念 | 解决的问题 | 示例 |
|---|---|---|
| PID | 在操作系统中标识进程 | `42810` |
| 端口 | 在网络通信中标识监听入口 | `3000` |

一个进程可以：

- 不监听任何端口，例如一次性文件处理脚本；
- 监听一个端口，例如简单 HTTP 服务；
- 监听多个端口；
- 与其他进程建立多个网络连接。

一个具体监听地址和端口在同一时刻通常不能被两个普通服务同时占用。若两个服务都尝试监听 `127.0.0.1:3000`，后启动者通常会收到“地址已被使用”的错误。

### 3. 进程的生命周期

#### 3.1 创建

用户输入 `node app.js` 后，Shell 请求操作系统启动 Node.js。操作系统会创建进程并分配基础资源。

概念伪代码：

```text
用户输入启动命令
Shell 解析命令和参数
Shell 请求操作系统创建进程
操作系统分配 PID 和基础内存
Node.js 加载入口模块
程序开始执行
```

#### 3.2 运行与等待

程序运行时并不一定一直占用 CPU。它可能在以下状态之间变化：

- 正在执行计算；
- 等待文件读取；
- 等待网络响应；
- 等待定时器到期；
- 等待系统资源；
- 暂停；
- 已结束但尚未被父进程读取状态。

`ps` 或 `top` 常见状态字母可能包括：

| 状态 | 常见含义 | 解读注意 |
|---|---|---|
| `R` | Running，可运行或正在运行 | 不表示一定持续占满 CPU |
| `S` | Sleeping，等待某个事件 | 服务等待请求时常见，不等于故障 |
| `T` | Stopped，已暂停 | 可能由调试或信号引起 |
| `Z` | Zombie，进程已结束但状态未被父进程回收 | 需要检查父进程处理 |

不同操作系统的状态字符和组合可能不同，应以本机手册为准。

#### 3.3 正常退出

程序完成工作后可以正常退出。按照常见约定：

- 退出码 `0` 表示程序按预期完成。
- 非 `0` 退出码表示程序未正常完成。

伪代码：

```text
读取输入
完成处理
输出结果
返回退出码 0
操作系统回收资源
```

退出码对自动化非常重要。Shell 脚本和 CI 不会像人一样阅读所有日志，它们通常首先使用退出码判断上一步是否成功。

#### 3.4 异常退出

程序可能因为以下原因异常结束：

- 未处理错误；
- 配置缺失；
- 文件不存在；
- 端口被占用；
- 权限不足；
- 内存不足；
- 收到终止信号。

伪代码：

```text
尝试启动服务

如果端口已被占用:
    输出可定位的错误信息
    返回非零退出码

如果启动成功:
    持续处理请求
```

“打印了一条错误日志”不等于已经正确向系统报告失败。如果程序出错后仍返回 `0`，CI 可能误判为成功。

#### 3.5 信号与终止

类 Unix 系统可以向进程发送信号。常见操作：

```bash
kill <PID>
```

默认通常发送 `SIGTERM`，表示请求进程终止。良好的服务会在退出前尝试：

- 停止接收新请求；
- 完成或中止正在处理的任务；
- 关闭数据库和网络连接；
- 刷新必要日志；
- 释放端口；
- 正常退出。

`Ctrl+C` 通常向前台进程发送 `SIGINT`。

不要把下面的命令作为常规终止方式：

```bash
kill -9 <PID>
```

`SIGKILL` 会让操作系统直接终止进程，程序没有机会执行清理逻辑。只有在进程无法响应正常终止请求且确认可以承担风险时，才把它作为最后手段。

#### 3.6 完整生命周期伪代码

```text
接收启动命令
请求操作系统创建进程
操作系统分配 PID、内存和其他基础资源
Node.js 运行时加载入口模块
执行当前可以立即执行的代码

如果任务需要文件、网络或定时器:
    发起 I/O 请求
    在等待期间让出执行机会
    I/O 完成后处理结果

如果发生未处理错误:
    记录错误
    返回非零退出码
否则:
    完成任务
    返回零退出码

操作系统回收进程资源
```

这段伪代码只描述宏观过程。Node.js 如何组织异步任务，将在事件循环知识单元中详细讲解。

### 4. 栈、堆与内存占用

#### 4.1 为什么需要内存模型

前端和后端程序都可能遇到：

- 页面越用越卡；
- 服务运行几小时后内存持续升高；
- 处理大文件时进程被系统终止；
- 递归过深导致调用栈溢出；
- 缓存没有上限导致内存耗尽。

解决这些问题前，需要先知道程序运行数据并不都以相同方式存在。

#### 4.2 栈的概念模型

栈可以用来理解函数调用关系。每次函数调用都会产生一层执行上下文；函数返回后，对应调用层结束。

伪代码：

```text
调用 main
    调用 parseInput
        调用 normalizeValue
        normalizeValue 返回
    parseInput 返回
main 返回
```

可以把它画成：

```text
顶部  normalizeValue
      parseInput
底部  main
```

如果递归没有合理终止条件，调用层不断增加，最终可能出现“Maximum call stack size exceeded”一类错误。

常见误解：

> JavaScript 中所有局部变量都能简单归类为“放在栈里”。

真实 JavaScript 引擎会做复杂优化。入门阶段应把栈当作理解调用顺序和调用深度的模型，不要用它推断所有变量的真实物理位置。

#### 4.3 堆的概念模型

堆用于理解动态创建、生命周期不完全跟随单次函数调用的数据，例如对象、数组和缓存。

伪代码：

```text
创建一个条目数组
循环读取数据
    创建条目对象
    把条目对象加入数组

只要数组仍被程序引用:
    其中的对象通常仍需要保留
```

如果程序不断向全局数组或缓存加入数据，却没有清理策略，内存可能持续增长。

#### 4.4 内存占用不只包含 JavaScript 堆

Node.js 进程的内存还可能包括：

- JavaScript 堆；
- 调用栈；
- Node.js 和 JavaScript 引擎自身数据；
- `Buffer` 等外部内存；
- 加载的本地模块；
- 线程和系统资源所需内存。

因此，系统工具显示的进程内存与某一个 JavaScript 堆指标不一定完全相同。

#### 4.5 如何判断内存增长是否异常

一次内存升高不等于内存泄漏。应观察趋势：

```text
启动后上升并稳定
    可能是正常加载和缓存

处理任务时上升，任务结束后明显下降
    可能是正常临时数据

相同任务重复执行后持续上升且不回落
    需要检查未释放引用、无上限缓存或资源未关闭
```

在本单元中，只要求能通过系统工具发现趋势并提出假设。精确定位内存问题将在浏览器和 Node.js 调试单元中展开。

### 5. CPU 密集型与 I/O 密集型任务

#### 5.1 CPU 密集型任务

CPU 密集型任务把大部分时间用于计算。

常见例子：

- 对大量数据排序；
- 复杂加密或压缩；
- 图像和视频处理；
- 大规模语法分析；
- 低效或无终止条件的循环。

示例伪代码：

```text
结果 = 0

从 1 循环到一个较大的有限数字:
    执行数学计算
    把结果累加

输出结果
退出
```

预期现象：

- 任务执行期间 CPU 占用明显升高；
- 任务规模越大，完成时间通常越长；
- 如果主执行路径被长计算占用，其他工作可能无法及时响应。

安全边界：

- 练习必须使用有限循环。
- 从较小规模开始，逐步增加。
- 发现机器明显卡顿时立即停止。
- 不为了观察 CPU 而故意编写无法终止的死循环。

#### 5.2 I/O 密集型任务

I/O 密集型任务的大部分时间用于等待外部资源。

常见例子：

- 读取文件；
- 请求远程 API；
- 查询数据库；
- 等待用户输入；
- 等待定时器。

示例伪代码：

```text
记录开始时间
发起一个需要等待的操作

等待操作完成

处理返回结果
记录结束时间
输出总耗时
```

预期现象：

- 程序总耗时可能较长；
- 等待期间 CPU 占用可能很低；
- 性能瓶颈可能来自外部服务、磁盘或网络，而不是本地计算。

#### 5.3 为什么必须区分

如果错误判断瓶颈，优化可能完全无效：

| 现象 | 可能方向 | 不应立即假设 |
|---|---|---|
| CPU 持续很高 | 算法、循环、序列化、计算规模 | 一定是网络慢 |
| CPU 很低但响应慢 | 网络、磁盘、数据库、锁、队列 | 一定要升级 CPU |
| 内存持续增长 | 缓存、引用、资源关闭、数据规模 | 一定是 CPU 不够 |
| 服务无法启动 | 配置、权限、端口、依赖 | 一定是代码语法错误 |

#### 5.4 Web 请求中的混合任务

真实业务通常既有计算也有 I/O：

```text
接收请求                       # 网络 I/O
校验参数                       # CPU
查询数据库                     # 网络或磁盘 I/O
整理查询结果                   # CPU
调用第三方服务                 # 网络 I/O
序列化响应                     # CPU
发送响应                       # 网络 I/O
```

排查性能时要分段测量，而不是只看总耗时。

### 6. 浏览器程序与 Node.js 程序

#### 6.1 相同点

浏览器和 Node.js 都可以执行 JavaScript，也都需要：

- CPU 执行指令；
- 内存保存运行数据；
- 运行时提供 API；
- 操作系统管理进程和资源。

JavaScript 语法相同，不代表运行环境提供的能力相同。

#### 6.2 浏览器中的前端程序

前端 JavaScript 通常运行在用户设备的浏览器环境中，主要负责：

- 响应用户交互；
- 操作页面；
- 调用后端 API；
- 管理页面状态；
- 使用浏览器提供的存储和媒体能力。

典型环境能力：

```text
window
document
DOM
fetch
localStorage
```

浏览器会限制网页直接访问本地文件和系统资源，避免普通网页任意控制用户设备。

#### 6.3 Node.js 中的服务端程序

Node.js 程序通常运行在开发者电脑、服务器、容器或云环境中，主要负责：

- 提供 API；
- 访问数据库；
- 读写服务器文件；
- 执行脚本和构建任务；
- 与其他内部或外部服务通信。

典型环境能力：

```text
process
文件系统 API
网络服务 API
环境变量
标准输入输出
```

Node.js 默认没有浏览器 DOM，因此下面的思路不能直接在普通 Node.js 程序中使用：

```text
查找页面中的按钮
修改 document
读取 window.location
```

#### 6.4 运行位置决定信任边界

前端代码会下载到用户设备，用户可以查看和修改其运行环境。因此：

- 不能把数据库密码、私钥或后端 Secret 放进前端代码。
- 前端隐藏按钮不能替代后端权限检查。
- 前端校验用于改善体验，后端仍需重新校验不可信输入。

后端代码不直接发送给普通用户，但也不能因此忽略安全：

- 环境变量和日志可能泄露敏感信息；
- 依赖和配置可能带来供应链风险；
- 进程权限过大可能扩大漏洞影响；
- 错误处理不当可能暴露系统细节。

#### 6.5 一次前后端协作的边界

```text
用户点击“保存”
    ↓
浏览器前端读取并校验表单
    ↓
浏览器通过网络发送请求
    ↓
Node.js 后端重新校验输入
    ↓
后端执行权限检查和业务逻辑
    ↓
后端返回结果
    ↓
浏览器根据结果更新页面
```

这条链路将在后续前端、后端和全栈联调阶段逐步实现。

### 7. 用系统证据观察程序

#### 7.1 为什么先收集证据

工程排查应从可观察事实开始：

```text
现象：页面打不开

需要先确认：
服务进程是否存在？
服务是否监听预期端口？
进程是否异常退出？
CPU 或内存是否异常？
日志记录了什么？
```

如果没有证据就直接修改代码，很容易把时间浪费在错误方向。

#### 7.2 在程序中输出 PID

Node.js 提供当前进程信息。概念示例：

```text
程序启动
输出当前进程 PID
输出父进程 PID
每隔一段时间输出心跳
收到终止请求后停止定时任务并退出
```

学员可以使用 `process.pid` 和 `process.ppid` 完成练习，但应理解这些值来自当前运行实例，不是源码的固定属性。

#### 7.3 使用 `ps` 查看进程快照

```bash
ps -p <PID> -o pid,ppid,state,%cpu,%mem,command
```

需要观察：

| 列 | 含义 |
|---|---|
| `PID` | 当前进程标识 |
| `PPID` | 父进程标识 |
| `STATE` | 当前进程状态 |
| `%CPU` | 采样时间内的 CPU 使用情况 |
| `%MEM` | 进程占系统内存的比例 |
| `COMMAND` | 启动命令 |

`ps` 提供的是某个时刻的快照。一次快照不能证明长期趋势，比较资源变化时应多次观察或使用 `top`。

#### 7.4 使用 `top` 观察变化

macOS：

```bash
top -pid <PID>
```

Linux：

```bash
top -p <PID>
```

重点观察：

- 计算开始前后的 CPU 变化；
- 任务结束后 CPU 是否恢复；
- 内存是否稳定、回落或持续增长；
- 进程是否仍存在。

退出 `top` 通常按 `q`。

#### 7.5 使用 `lsof` 查看端口

```bash
lsof -nP -iTCP:<PORT> -sTCP:LISTEN
```

例如检查本机 `3000` 端口：

```bash
lsof -nP -iTCP:3000 -sTCP:LISTEN
```

可能看到：

```text
COMMAND   PID  USER   FD   TYPE  DEVICE SIZE/OFF NODE NAME
node    42810  ...    ...  ...   ...    ...      ...  TCP 127.0.0.1:3000 (LISTEN)
```

需要解释：

- `COMMAND` 表示进程命令；
- `PID` 可用于继续查询进程；
- `NAME` 表示监听地址和端口；
- 没有输出通常表示当前未发现符合条件的监听进程，但仍应检查端口参数是否正确。

不要直接复制他人的 PID 执行 `kill`。必须先确认进程属于自己的练习任务。

#### 7.6 观察退出码

在前台运行程序，等待它结束后执行：

```bash
echo $?
```

预期：

- 正常完成通常为 `0`。
- 显式失败或未处理错误通常为非 `0`。
- 被信号终止时，Shell 可能使用与信号有关的非零值；具体表示以当前系统和 Shell 为准。

必须在目标命令结束后立即读取退出码。执行其他命令后，`$?` 会变成最近一条命令的退出码。

#### 7.7 标准排查顺序

遇到“服务无法访问”时，按以下顺序收集证据：

```text
1. 查看启动命令是否输出错误
2. 记录启动命令的退出码
3. 确认目标进程是否存在
4. 确认进程是否监听预期端口
5. 观察 CPU 和内存是否异常
6. 根据证据提出假设
7. 一次只验证一个假设
8. 修复后重复相同检查
```

示例：

```text
现象：访问 http://localhost:3000 失败

证据 A：启动命令立即结束，退出码为非零
证据 B：lsof 查不到 3000 端口
证据 C：日志显示地址已被使用

判断：当前服务没有成功监听 3000 端口
下一步：查找占用 3000 端口的进程，确认归属后再处理
```

证据支持的是下一步排查方向，不一定一次就能证明最终根因。

## 实践练习题

### 练习 1：观察一个持续运行的进程

#### 任务

创建 `heartbeat.js`。程序启动时输出当前 PID 和 PPID，此后每 2 秒输出一次包含当前时间的心跳。

概念伪代码：

```text
输出当前 PID
输出当前 PPID

每隔 2 秒:
    输出当前时间和 "heartbeat"

收到正常终止请求:
    停止定时任务
    输出 "shutting down"
    退出程序
```

#### 步骤约束

1. 使用 `node heartbeat.js` 启动程序。
2. 根据程序输出获得 PID，不把 PID 写死到脚本。
3. 使用 `ps` 查看 PID、PPID、状态、CPU、内存和命令。
4. 使用 `top` 连续观察至少 20 秒。
5. 使用 `Ctrl+C` 或默认的 `kill <PID>` 请求程序退出。
6. 再次使用 `ps` 确认进程已经不存在。

#### 提交物

- `heartbeat.js`；
- 启动命令；
- 一段经过脱敏的 `ps` 输出；
- CPU、内存和状态解释；
- 终止方式及终止后的验证结果。

#### 验收标准

- 能准确指出 PID 与 PPID；
- 能解释等待心跳时 CPU 较低的原因；
- 能证明终止前后进程状态发生变化；
- 没有使用固定 PID；
- 没有把 `kill -9` 作为默认终止方式。

### 练习 2：比较计算任务与等待任务

#### 任务

创建两个脚本：

- `cpu-task.js`：执行有限规模的重复计算。
- `io-task.js`：等待定时器后输出结果。

CPU 任务伪代码：

```text
读取一个有上限的任务规模
记录开始时间
结果 = 0

执行有限次数循环:
    完成一组数学计算
    累加结果

输出结果和耗时
退出
```

等待任务伪代码：

```text
记录开始时间
启动一个 5 秒定时器

定时器到期:
    输出总耗时
    退出
```

#### 步骤约束

1. 先使用较小任务规模验证 `cpu-task.js` 能在合理时间内结束。
2. 逐步调大规模，目标是获得数秒可观察时间，而不是让机器失去响应。
3. 分别运行两个脚本，并使用 `top` 观察 CPU。
4. 各执行至少三次，记录总耗时和 CPU 表现。
5. 不使用无终止条件的循环，不使用递归制造崩溃。

#### 提交物

- 两个脚本；
- 至少三轮观察记录；
- CPU 占用、总耗时和进程状态对比表；
- 100 至 200 字结论。

推荐记录表：

| 任务 | 第几次 | 总耗时 | CPU 表现 | 主要时间花在哪里 |
|---|---:|---:|---|---|
| 计算任务 | 1 |  |  |  |
| 等待任务 | 1 |  |  |  |

#### 验收标准

- 两个任务都能自动结束；
- 观察数据来自实际运行；
- 能说明“耗时长”与“CPU 高”不是同一个概念；
- 能提出计算任务和等待任务各自的优化方向；
- 实验不会长期占满系统资源。

### 练习 3：退出码与端口冲突

#### 任务

创建：

- `exit-code.js`：根据输入选择正常退出或非零退出。
- `server.js`：启动一个只用于实验的本地 HTTP 服务。

退出码伪代码：

```text
读取命令参数

如果参数是 success:
    输出成功信息
    返回退出码 0

如果参数是 failure:
    输出失败原因
    返回退出码 2

否则:
    输出参数使用方式
    返回退出码 1
```

服务伪代码：

```text
读取端口，默认使用 3000
尝试监听 127.0.0.1 和目标端口

如果监听成功:
    输出 PID 和端口

如果端口被占用:
    输出可识别的错误
    返回非零退出码
```

#### 步骤约束

1. 分别执行成功、失败和无效参数场景，每次立即使用 `echo $?` 记录退出码。
2. 启动第一个服务并确认端口正在监听。
3. 再启动第二个使用相同地址和端口的服务。
4. 记录第二个服务的错误和退出码。
5. 使用 `lsof` 确认端口由哪个 PID 监听。
6. 只终止自己启动的实验进程，并确认端口已释放。

#### 提交物

- 两个脚本；
- 三种参数场景及退出码记录；
- 端口冲突错误记录；
- `lsof` 证据；
- 清理进程和确认端口释放的记录。

#### 验收标准

- 成功与失败使用不同退出码；
- 能解释为什么端口冲突发生在第二个服务；
- 能从端口找到 PID，再从 PID 查询进程；
- 不终止与实验无关的进程；
- 实验结束后没有残留监听进程。

### 强制不通过条件

出现以下任一情况，本次验收不通过；修正后重新验收：

1. 无法区分源代码、Node.js 运行时和进程。
2. 把 PID 当作端口，或把端口当作进程标识。
3. 项目无法按照 README 在另一台满足环境要求的机器上复现。
4. 使用无终止条件的任务造成设备长时间失去响应。
5. 未确认进程归属就终止与实验无关的进程。
6. 提交真实密码、令牌、私钥或其他敏感信息。
7. 只提交截图，没有脚本、命令和文字解释。
