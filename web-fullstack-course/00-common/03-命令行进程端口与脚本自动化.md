# 03-命令行进程端口与脚本自动化

## 目标

完成本知识单元后，学员应能把命令行从“一条条手敲的指令”升级为“可以组合、可以保存、可以复现的自动化流水线”，并能独立处理开发中最常见的端口与进程问题。

学员应能够：

1. 区分标准输入、标准输出、标准错误三条通道，并使用重定向分别保存正常输出与错误输出。
2. 使用管道组合 `grep`、`head`、`tail`、`sort`、`uniq`、`wc`，完成对日志文件的筛选、统计与排序。
3. 使用 `ps`、`lsof`、`kill`、`jobs` 等命令观察进程、定位端口占用、以前台与后台方式运行任务。
4. 使用退出码以及 `&&`、`||`、`;`、命令替换组织多步命令，并预测每一步是否执行。
5. 编写包含 shebang、`set -e`、变量和条件判断的 shell 脚本，解释脚本在失败时为什么停止。
6. 在 `package.json` scripts 中组织跨平台命令，并用 Node.js `child_process` 的 `exec`、`spawn` 概念说明程序如何调用其他程序。

本单元聚焦“命令如何流动与组合”。环境变量的配置与作用域将在后续知识单元展开；进程与端口的底层心智模型请参考《01-计算机如何运行 Web 程序》。

## 技术栈

本单元不使用前端框架、后端框架或数据库。Node.js 示例只使用内置模块，shell 示例以 `bash` 语法为主，`zsh` 下同样适用。

| 工具或环境 | 用途 | 学习要求 |
|---|---|---|
| Shell（`bash` 或 `zsh` 当前稳定版） | 执行管道、重定向与脚本 | 能读懂一行组合命令的执行顺序 |
| Node.js 当前 LTS 版本 | 提供日志脚本与子进程 API | 能运行 `.mjs` 脚本并观察标准流 |
| npm（随 Node.js 当前 LTS 附带）或 pnpm 当前稳定版 | 执行 `package.json` scripts | 能说明 `npm run <脚本>` 实际调用了什么 |
| `grep`、`head`、`tail`、`sort`、`uniq`、`wc` | 基础文本处理 | 能按数据流向组合这些命令 |
| `ps`、`top`、`lsof`、`kill`、`jobs` | 进程与端口操作 | 能定位并安全处理占用端口的进程 |
| `node:child_process` | 在 Node 中启动其他程序 | 能区分 `exec` 与 `spawn` 的适用场景 |

课程命令以 macOS 和常见 Linux 环境为主：

- macOS 自带的文本处理工具多为 BSD 版本，个别选项输出格式与 Linux 的 GNU 版本略有差异，本课只使用两边通用的选项。
- Windows 学员请在 WSL2（Ubuntu 当前 LTS 版本）中完成命令行练习；同时需要理解 `package.json` scripts 在原生 Windows 下的跨平台注意事项。
- `<PID>`、`<端口>` 形式表示需要替换的占位参数，不要原样输入尖括号。

开始前检查环境：

```bash
node -v
npm -v
bash --version | head -n 1
lsof -v | head -n 1
```

预期观察：

- `node -v` 输出当前 Node.js 版本，例如以 `v20` 或 `v22` 开头。
- `npm -v` 输出随 Node 安装的 npm 版本号。
- `bash --version` 输出 bash 版本行；在 `zsh` 中执行此命令也能确认系统中存在 bash。
- `lsof -v` 输出版本与编译信息。

版本号不是考点，关键是确认工具存在、能读懂输出，并能把多个命令组合起来。

## 详细的理论知识讲解和示例伪代码

### 1. 三个标准流

#### 1.1 进程启动时自带三条通道

每个类 Unix 进程启动时，内核都会为它打开三条默认的数据通道，称为标准流：

| 名称 | 编号（文件描述符） | 默认连接 | 用途 |
|---|---|---|---|
| 标准输入 stdin | 0 | 键盘 | 接收输入 |
| 标准输出 stdout | 1 | 终端屏幕 | 输出正常结果 |
| 标准错误 stderr | 2 | 终端屏幕 | 输出错误与诊断信息 |

“默认连接”意味着可以被改变：管道和重定向的本质，就是把这三条通道重新接到别处。

#### 1.2 标准输入：数据进入程序的入口

默认情况下，程序从键盘读取 stdin。下面用 Node 写一个“回声”程序 `echo.mjs`：

```js
process.stdin.setEncoding('utf8');

process.stdin.on('data', (chunk) => {
  process.stdout.write(`你输入了: ${chunk}`);
});
```

运行后程序会停在原地等待键盘输入：

```bash
node echo.mjs
```

输入一行文字并回车，预期看到：

```text
你好
你输入了: 你好
```

按 `Ctrl+D` 表示输入结束（EOF），程序随之结束读取。

#### 1.3 标准输出：正常结果的出口

`console.log` 的内容进入 stdout。stdout 被设计成“干净的数据通道”，这样它既可以显示在屏幕上，也可以被管道送给下一个程序，而不夹带诊断文字。

#### 1.4 标准错误：为什么必须独立

错误信息单独走 stderr，是为了让“数据”和“抱怨”互不干扰：

- 用管道处理数据时，错误信息不会混进结果里。
- 在终端直接运行时，两条流都显示在屏幕上，所以人眼感觉不到区别。
- 重定向时可以分别保存，便于事后分析。

Node 中 `console.error` 写入 stderr：

```js
console.log('这是一条正常结果');   // stdout
console.error('这是一条错误诊断'); // stderr
```

与 Web 的关系：Web 服务器通常把访问日志写 stdout、把异常堆栈写 stderr，运维系统据此分别采集。在容器化部署中，“日志输出到标准流再由平台收集”是标准做法。

常见误解：

> `console.error` 打印的内容“不算输出”，管道和重定向都碰不到它。

错误信息仍然出现在终端，只是走了编号为 2 的独立通道。正因为它独立，才可以被单独重定向或与 stdout 合并。

### 2. 重定向：控制数据流向

#### 2.1 `>`：把标准输出写入文件（覆盖）

```bash
node report.mjs > out.log
```

执行后终端不再显示正常输出，内容被写入 `out.log`：

- 文件不存在时创建；
- 文件已存在时先清空再写入，原有内容无法找回。

因此 `>` 是“覆盖式”重定向，对已有文件使用前要确认不再需要旧内容。

#### 2.2 `>>`：追加

```bash
date >> run.log
node report.mjs >> run.log
```

`>>` 把输出写到文件末尾，不破坏原有内容。需要积累多次运行的日志时，应使用追加而不是覆盖。

#### 2.3 `2>` 与 `2>&1`：处理错误流

```bash
node app.mjs 2> error.log
```

只把 stderr 重定向到 `error.log`，正常输出仍显示在屏幕。

把正常输出和错误输出都收进同一个文件：

```bash
node app.mjs > all.log 2>&1
```

这条命令的阅读顺序至关重要：

```text
> all.log     先把 stdout(1) 指向 all.log
2>&1          再把 stderr(2) 指向“stdout 当前的去向”，即 all.log
```

顺序写反结果完全不同：

```bash
node app.mjs 2>&1 > out.log
```

此时先让 stderr 指向 stdout 当前的去向（屏幕），再把 stdout 改向文件，于是错误仍打到屏幕、只有正常输出进文件。

`bash` 还提供简写 `&> all.log`，能一次性把两条流都写入文件；为了清晰，入门阶段建议使用 `> all.log 2>&1` 的完整写法。

#### 2.4 丢弃输出：`/dev/null`

`/dev/null` 是一个特殊设备，写入其中的内容会被直接丢弃：

```bash
node noisy.mjs > /dev/null 2>&1
```

常用于“只关心程序是否成功、不关心输出”的自动化场景，例如在脚本里做一次前置检查。

#### 2.5 `<`：输入重定向

重定向也能作用于 stdin，把文件内容作为程序输入：

```bash
wc -l < access.log
```

预期输出 `access.log` 的行数。注意此时命令行中不显示文件名，因为 `wc` 只知道自己在读一条输入流。

#### 2.6 常见误解

> 重定向是命令程序自己实现的功能。

重定向由 Shell 在启动程序之前完成：Shell 先打开文件、接好通道，再启动程序。所以无论程序是否理解 `>`，重定向都生效。这也解释了为什么重定向符号写在命令前后位置不同，含义却都由 Shell 解释。

### 3. 管道：把命令接成流水线

#### 3.1 管道做了什么

竖线 `|` 创建一条管道：把左侧命令的 stdout 接到右侧命令的 stdin。

```text
产生数据的命令  |  消费数据的命令
   stdout   →     stdin
```

默认情况下，stderr 不进入管道，仍直接显示在终端，这保证错误信息不会污染数据。

#### 3.2 `grep`：按行筛选

`grep` 从输入或文件中找出包含指定文本的行：

```bash
grep "ERROR" app.log            # 输出包含 ERROR 的行
grep -n "ERROR" app.log         # 同时显示行号
grep -i "error" app.log         # 忽略大小写
grep -v "INFO" app.log          # 反向：输出不含 INFO 的行
grep -E "ERROR|FATAL" app.log   # 使用扩展正则，匹配两种关键词
```

#### 3.3 `head` 与 `tail`：取开头与结尾

```bash
head -n 5 app.log       # 前 5 行
tail -n 20 app.log      # 后 20 行
tail -f app.log         # 持续跟踪新写入的内容，实时刷出
```

`tail -f` 适合观察正在运行的服务日志：执行后停住不动，新日志一旦写入就立刻显示，按 `Ctrl+C` 退出。它与 `tail -n 20` 的区别在于：后者看完最后 20 行立即退出，前者会一直等待。

#### 3.4 `wc`：计数

```bash
wc -l access.log    # 行数
wc -w article.txt   # 单词数
wc -c file.bin      # 字节数
```

只给文件时，`wc` 会同时输出行数、单词数和字节数，并附带文件名。

#### 3.5 `sort` 与 `uniq`：排序与去重

```bash
sort names.txt              # 按行排序
sort -n numbers.txt         # 按数值而非文字排序
sort -r names.txt           # 逆序
uniq list.txt               # 合并相邻的重复行
uniq -c list.txt            # 同时统计每行连续出现的次数
```

关键点：`uniq` 只合并“相邻”的重复行，因此必须先排序，让相同行挨在一起：

```bash
sort names.txt | uniq -c
```

#### 3.6 组合实战：统计访问量最高的 IP

假设 `access.log` 每行开头是访问者 IP。一条流水线完成“提取 IP → 排序 → 计数 → 按次数排序 → 取前 5”：

```bash
grep -oE '([0-9]{1,3}\.){3}[0-9]{1,3}' access.log \
  | sort \
  | uniq -c \
  | sort -nr \
  | head -n 5
```

逐段解读数据如何变化：

```text
grep -oE ...   # 从每行中只抽出 IP，每行一个
sort           # 让相同 IP 相邻
uniq -c        # 合并并计数，输出“次数 + IP”
sort -nr       # 按数字(-n)逆序(-r)，次数最多的在最前
head -n 5      # 只保留前 5 名
```

预期输出形如：

```text
  42 192.168.1.10
  31 10.0.0.5
  17 10.0.0.8
   9 172.16.0.2
   4 10.0.0.9
```

这就是命令行“小工具组合”思想的典型体现：每个工具只做一件事，靠管道拼成复杂分析。

#### 3.7 管道与退出码

默认情况下，整条管道的退出码是最后一个命令的退出码，前面命令的失败可能被掩盖。在严谨脚本中可开启 `set -o pipefail`，让管道中任一命令失败都反映为整条管道失败（脚本小节会再讲）。

常见误解：

> `grep` 没有匹配到内容，说明命令坏了或文件有问题。

`grep` 找不到匹配时退出码为 `1`，这是它表达“没有符合条件的行”的正常语义；只有发生真正错误（例如文件不存在）才会返回 `2`。自动化脚本中区分这两种情况很重要。

### 4. 进程与端口的命令操作

#### 4.1 `ps`：与管道配合查找进程

在《01》中已学过 `ps` 的列含义，这里聚焦“如何在大量进程中筛出目标”：

```bash
ps aux | grep node
ps -ef | grep vite
```

预期输出包含命令行中带 `node` 或 `vite` 的进程，能读到 PID、CPU、内存和启动命令。

两个实用细节：

- 结果里往往多出一条 `grep node` 自身，因为它的命令行里也含 `node`；排除它可写 `ps aux | grep node | grep -v grep`。
- 只想要 PID 时可用 `pgrep -f "vite"`，输出更干净；该命令不是所有环境默认都有，主线仍使用 `ps`。

#### 4.2 `top`：快速看一眼资源

```bash
top
```

进入实时界面，重点读 CPU 总体占用、内存占用和进程列表，按 `q` 退出。需要聚焦单个进程时的写法在《01》中已给出，本单元不再重复。

#### 4.3 `kill`：从操作角度发送信号

```bash
kill <PID>          # 默认发送 TERM，请求进程自行退出
kill -TERM <PID>    # 与默认等价，写出来更明确
kill -9 <PID>       # KILL，强制结束，仅作最后手段
```

要避免使用 `killall node` 这类“按名字批量杀”的命令：它会结束系统里所有 Node 进程，可能误伤其他项目甚至他人任务。应先用 `ps` 确认具体 PID，再精确处理。

#### 4.4 `lsof`：定位端口对应的进程

```bash
lsof -nP -iTCP:5173 -sTCP:LISTEN
```

参数含义：

- `-nP`：不解析主机名与端口名，输出更快更直接；
- `-iTCP:5173`：只看与 TCP 5173 端口有关的连接；
- `-sTCP:LISTEN`：只看处于监听状态的套接字。

预期输出：

```text
COMMAND   PID    USER   FD   TYPE  ... NAME
node    51234 student   21u  IPv6  ... TCP *:5173 (LISTEN)
```

读到 PID `51234` 后，即可配合 `ps -p 51234` 确认归属，再决定是否终止。部分 Linux 环境还可用 `ss -ltnp` 查看所有监听端口。

#### 4.5 前台、后台与 `jobs`

默认启动的程序占据当前终端，称为前台进程，终端暂时无法输入新命令。在命令末尾加 `&` 可让程序在后台运行：

```bash
node server.mjs > server.log 2>&1 &
```

预期 Shell 立即返回一个作业编号和 PID，并重新给出提示符：

```text
[1] 51234
```

相关命令：

```bash
jobs        # 列出当前 Shell 的后台作业及状态
fg          # 把后台作业调回前台（%1 可指定作业号）
bg          # 让被 Ctrl+Z 暂停的作业在后台继续运行
```

操作节奏：前台运行时按 `Ctrl+Z` 可暂停当前程序回到 Shell，再用 `bg` 让它在后台继续；`fg` 调回前台后，按 `Ctrl+C` 发送中断。

后台程序的 stdout 与 stderr 仍默认打到终端，容易把界面刷乱，所以启动后台任务时通常配合重定向，如开头示例那样把输出写进日志文件。

#### 4.6 端口占用标准排查流程

```text
1. lsof -nP -iTCP:<端口> -sTCP:LISTEN   找到监听该端口的 PID
2. ps -p <PID> -o pid,ppid,command      确认这个进程确实是自己的服务
3. kill <PID>                            请求它正常退出
4. 再次执行第 1 步的 lsof                确认端口已经释放
5. 若进程无响应且确认风险，再考虑 kill -9
```

常见误解：

> 端口被占用最快的解决办法是重启电脑。

重启只是把所有进程清空，既慢又没有让你学会定位问题。标准流程只需两三条命令，且能确认“是谁占用、是否安全处理”。

### 5. 用退出码组合命令

#### 5.1 `$?`：读取上一条命令的退出码

```bash
node app.mjs
echo $?
```

成功通常输出 `0`，失败输出非 `0`。必须在目标命令结束后立即读取：一旦执行了其他命令，`$?` 就会被新命令的结果覆盖。

#### 5.2 `&&`：成功才继续

```bash
npm run build && echo "构建成功"
```

`&&` 具有“短路”特性：左侧成功（退出码 0）才执行右侧；左侧失败则右侧被跳过。

#### 5.3 `||`：失败才补救

```bash
mkdir -p logs || echo "创建目录失败"
```

左侧失败时才执行右侧，常用于兜底或给出更友好的提示。两者可以连用：

```bash
npm run build && echo "构建成功" || echo "构建失败"
```

#### 5.4 `;`：无条件顺序执行

```bash
echo "第一步"; echo "第二步"
```

分号只保证“从左到右依次执行”，不关心成败。需要在失败时立即停止就不能用 `;`，应使用 `&&` 或脚本中的 `set -e`。

#### 5.5 命令替换：`$(...)`

`$(命令)` 会执行其中的命令，并用其标准输出替换自身：

```bash
TODAY=$(date +%F)
mkdir "backup-$TODAY"
```

执行后得到形如 `backup-2026-10-09` 的目录名。`date +%F` 输出 `年-月-日` 格式的日期。

实用组合：自动找到并停止占用端口的进程

```bash
PID=$(lsof -tiTCP:5173 -sTCP:LISTEN) && kill "$PID"
```

逐段解释：

```text
lsof -t ...                 # -t 只输出 PID，便于直接使用
PID=$(...)                  # 把 PID 保存进变量
&& kill "$PID"              # 确实取到 PID 时才执行 kill
```

当端口没有任何进程监听时，`lsof -t` 无输出且退出码非 0，`&&` 自动短路，避免执行不带参数的 `kill`。

较旧的写法使用反引号 `` `命令` ``，含义与 `$(命令)` 相同；新代码统一使用 `$(...)`，可读性更好。

#### 5.6 常见误解

> 在两条命令之间插入一句 `echo $?` 不影响排查。

插入的任何命令都会重写 `$?`。想记录原始退出码，应在目标命令后立刻存入变量：`CODE=$?`，之后再慢慢使用 `$CODE`。

### 6. Shell 脚本基础

#### 6.1 为什么要把命令存成文件

当一组命令需要反复执行、需要交给队友或在 CI 中运行时，逐条手敲既低效又容易出错。把命令按顺序写进一个文本文件，就形成 shell 脚本：同样的步骤每次执行结果一致。

#### 6.2 shebang：声明用哪个解释器

脚本第一行通常是：

```bash
#!/usr/bin/env bash
```

- `#!` 称为 shebang，告诉系统用后面的程序解释这个文件；
- `/usr/bin/env bash` 表示在当前环境中查找 `bash`，比写死 `/bin/bash` 更易移植。

运行脚本有两种方式：

```bash
bash build.sh       # 显式交给 bash，不要求文件有可执行权限
./build.sh          # 直接执行，需要文件具备可执行权限
```

直接执行所需的权限位将在后续单元讲解，本单元统一使用 `bash 脚本名` 的方式。

#### 6.3 `set -e`：出错即停

默认情况下，脚本中某条命令失败后，脚本会继续执行下一条，这可能把小错误放大成更大破坏。开启严格模式：

```bash
set -e
```

任一步骤返回非 0，脚本立即停止并以该退出码退出。常见的严格模式组合是：

```bash
set -euo pipefail
```

- `-e`：命令失败立即退出；
- `-u`：使用未设置的变量时报错，防止空变量（例如删除命令）；
- `pipefail`：管道中任一命令失败都算失败。

某条命令“失败”其实是正常语义时（典型是 `grep` 没匹配到），可显式放行：

```bash
grep "warn" app.log || true
```

`|| true` 让这一步整体退出码为 0，脚本继续运行。

#### 6.4 变量

```bash
NAME="web-app"
echo "$NAME"
echo "${NAME}-dist"
```

语法注意：

- 等号两边不能有空格，`NAME = "x"` 会被当成命令执行而报错；
- 使用变量时建议加双引号，避免值中含空格被拆分；
- `${NAME}` 形式便于与后续文字明确分隔。

脚本还提供一组特殊变量：

| 变量 | 含义 |
|---|---|
| `$1`、`$2` | 第 1、第 2 个参数 |
| `$@` | 全部参数 |
| `$#` | 参数个数 |
| `$$` | 当前脚本进程 PID |

#### 6.5 条件判断基础

```bash
if [ -f package.json ]; then
  echo "找到 package.json"
else
  echo "当前目录不是项目根目录"
  exit 1
fi
```

- `[ ... ]` 中的 `[` 实际是一个命令，因此它周围和右括号前必须有空格；
- `if` 以 `fi` 结束，`then` 前需要分号或换行；
- 常用判断条件：`-f 文件`（是普通文件）、`-d 目录`、`-z 字符串`（为空）、`-n 字符串`（非空）。

#### 6.6 完整小脚本示例

```bash
#!/usr/bin/env bash
set -euo pipefail

# 用法: bash deploy.sh <环境名>
ENV_NAME="${1:-}"

if [ -z "$ENV_NAME" ]; then
  echo "错误: 必须提供环境名，例如 bash deploy.sh boe"
  exit 1
fi

if [ ! -d "node_modules" ]; then
  echo "未发现依赖，先执行安装"
  npm install
fi

npm run build
echo "面向 ${ENV_NAME} 的构建完成"
```

预期行为：

- 不带参数运行时输出用法提示，退出码为 1；
- 提供参数且无 `node_modules` 时先安装依赖再构建；
- 任一步骤失败，`set -e` 让脚本立即停止，不会带着错误继续。

常见误解：

> 写好的 `.sh` 文件在任何系统双击都能运行。

shell 脚本依赖类 Unix 环境，Windows 原生不识别；跨平台自动化的更稳妥选择是 Node 脚本配合 `package.json`，下一节展开。

### 7. package.json scripts 与跨平台调用

#### 7.1 scripts 字段

`package.json` 用 `scripts` 为项目约定统一的命令入口：

```json
{
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "start": "node server.mjs",
    "check": "node scripts/check.mjs",
    "logs": "tail -f server.log"
  }
}
```

#### 7.2 执行脚本时发生了什么

执行 `npm run build`（或 pnpm 的 `pnpm build`）时：

```text
1. npm 读取 package.json 中的 scripts
2. 把项目 node_modules/.bin 临时加到命令搜索路径最前面
3. 通过 Shell 执行对应命令字符串
4. 把该命令的退出码作为 npm run 自己的退出码
```

因此本地能直接调用 `vite`、`tsc`，即使没有全局安装。直接执行 `npm run` 不带脚本名，会列出全部可用脚本。

#### 7.3 跨平台陷阱

npm 在不同平台通过不同 Shell 执行脚本（Windows 上通常是 `cmd.exe`），下列写法会出问题：

```json
{
  "scripts": {
    "clean": "rm -rf dist",
    "serve": "PORT=3000 node server.mjs"
  }
}
```

- `rm`、`cp` 等类 Unix 命令在 `cmd.exe` 中不存在，Windows 队友执行失败；
- `PORT=3000 命令` 这种环境变量前置写法是 Shell 语法，Windows 同样不支持。

#### 7.4 跨平台方案

首选方案是把平台相关操作写成 Node 脚本，用内置 API 完成：

```js
// scripts/clean.mjs
import fs from 'node:fs/promises';

await fs.rm('dist', { recursive: true, force: true });
console.log('已清理 dist');
```

```json
{
  "scripts": {
    "clean": "node scripts/clean.mjs"
  }
}
```

`fs.rm` 的 `force: true` 表示目录不存在也不报错，行为与 `rm -rf` 接近，却在任何安装了 Node 的平台上一致运行。某些历史项目使用 `rimraf` 这类第三方包达到同样目的，了解即可；本课程主线优先使用 Node 内置能力。

此外 npm 还支持 `pre<script>`、`post<script>` 钩子，例如定义 `prebuild` 会在 `build` 前自动执行。钩子虽方便，但过多隐式步骤会让命令难以理解，入门阶段应谨慎使用。

常见误解：

> 命令在我的 macOS 终端能跑，写进 scripts 团队所有人就能跑。

scripts 的执行环境随平台变化。凡是需要团队共享的命令，都应假设“对面可能是 Windows”，优先选择 Node 脚本或明确声明只支持类 Unix 环境。

### 8. Node 中的子进程：exec 与 spawn

#### 8.1 从程序内部启动其他程序

《01》讲过进程由内核创建。在 Node 代码中完成这件事，使用内置模块 `node:child_process`。典型场景包括：调用 Git、执行构建工具、把耗时任务隔离到独立进程、复用系统已有命令。

#### 8.2 `exec`：通过 Shell 执行并一次取回结果

```js
import { exec } from 'node:child_process';

exec('ls -l', (error, stdout, stderr) => {
  if (error) {
    console.error('命令失败:', error.message);
    process.exitCode = 1;
    return;
  }
  console.log('标准输出:', stdout);
  if (stderr) {
    console.error('标准错误:', stderr);
  }
});
```

特点：

- 命令字符串交给 Shell 解析，因此可以使用管道、通配符；
- 输出先缓存在内存中，结束后一次性交给回调，适合输出较小的命令；
- 输出过大可能触及缓冲上限，不适合处理大文件或长日志。

#### 8.3 `execFile`：不经过 Shell

`execFile` 直接启动指定程序、参数以数组传递，不经过 Shell，避免了 Shell 解析带来的风险；在需要精确控制参数且不需要管道语法时比 `exec` 更安全。

#### 8.4 `spawn`：流式启动

```js
import { spawn } from 'node:child_process';

const child = spawn('node', ['server.mjs'], {
  stdio: 'inherit'
});

child.on('exit', (code, signal) => {
  console.log('子进程结束，退出码:', code, '信号:', signal);
});
```

- 命令与参数分离，参数以数组逐项传入，不经过 Shell 解析；
- 返回的对象带有 stdin、stdout、stderr 三条流，适合数据量大或需要实时处理的场景；
- `stdio: 'inherit'` 让子进程直接复用父进程的三条标准流，子进程的日志直接出现在当前终端。

#### 8.5 在代码中对接管道

`spawn` 的流可以用 `pipe` 接起来，效果等同于 Shell 中的 `|`：

```js
import { spawn } from 'node:child_process';

const ls = spawn('ls', ['-l']);
const grep = spawn('grep', ['js']);

ls.stdout.pipe(grep.stdin);

grep.stdout.on('data', (chunk) => {
  process.stdout.write(chunk);
});

ls.on('error', (err) => console.error('ls 启动失败:', err));
grep.on('error', (err) => console.error('grep 启动失败:', err));
```

预期只输出 `ls -l` 结果中包含 `js` 的行，与在终端执行 `ls -l | grep js` 一致。

#### 8.6 跨平台与安全注意

- Windows 上调用 `.cmd`、`.bat`（例如 npm 安装的部分工具）时，可能需要指定 `shell: true` 或给出完整文件名，否则无法直接启动。
- 永远不要把未经处理的用户输入拼进 `exec` 的命令字符串。恶意输入可能改变命令本身，例如注入额外指令：

```js
// 危险：fileName 来自外部输入，可被构造出额外命令
exec(`cat ${fileName}`);

// 安全：参数以数组传递，不经过 Shell 解析
import { execFile } from 'node:child_process';
execFile('cat', [fileName], (error, stdout) => {
  /* ... */
});
```

常见误解：

> 用 `exec` 执行包含用户输入的命令，只要界面做了校验就安全。

界面校验可以被绕过，真正的边界在执行处。默认选择 `spawn`/`execFile` 加参数数组，只在确有必要使用 Shell 语法时才使用 `exec`，并对输入做严格过滤。

### 练习 1：日志分拣台

#### 任务

编写一个 Node 脚本，同时向 stdout 和 stderr 输出内容，再使用重定向把两类输出分别保存，并合并出一份完整日志。

脚本概念伪代码：

```text
循环输出 3 条正常访问日志     # console.log，进入 stdout
输出 2 条错误日志             # console.error，进入 stderr
```

#### 步骤约束

1. 创建 `logger.mjs`，3 条正常日志形如 `[INFO] request /index`，2 条错误日志形如 `[ERROR] db timeout`。

3. 分别用 `cat out.log`、`cat err.log` 查看，确认两类信息各归其位。
4. 再执行一次 `node logger.mjs > all.log 2>&1`，确认 5 条记录全部进入 `all.log`。
5. 追加执行 `date >> all.log`，验证 `>>` 不覆盖原内容。

#### 提交物

- `logger.mjs`；
- 全部重定向命令及三个日志文件内容；
- 一段 150 字以内的说明，解释 stdout 与 stderr 在屏幕上“看起来一样”但为什么必须分流。

#### 验收标准

- `out.log` 只含 INFO、`err.log` 只含 ERROR；
- `all.log` 同时包含两类输出，追加的日期行位于末尾；
- 命令执行后的终端表现与说明一致；
- 日志中不包含任何真实密钥或个人信息。

### 练习 2：访问日志统计流水线

#### 任务

手工构造一个不少于 30 行的访问日志，然后只用管道组合回答三个统计问题：总请求数、404 响应数、访问次数最多的前 3 个 IP。

日志每行格式：

```text
<IP> - - [09/Oct/2026:10:00:00] "GET / HTTP/1.1" <状态码> 1024
```

#### 步骤约束

1. 使用编辑器或重定向生成 `access.log`，要求至少出现 5 个不同 IP，且至少 4 行状态码为 404，并人为制造若干重复 IP。
2. 总请求数使用 `wc -l`；404 数量使用 `grep " 404 " access.log | wc -l`。
3. IP 排行使用 `grep -oE '([0-9]{1,3}\.){3}[0-9]{1,3}' | sort | uniq -c | sort -nr | head -n 3`。
4. 对每条流水线逐段写出中间结果的含义，不允许整条命令写完却无法解释。
5. 自行改变日志内容再运行一次，确认统计结果随之变化，而不是写死答案。

#### 提交物

- `access.log`；
- 三条统计命令及真实输出；
- 逐段解释文档（含每个工具在流水线中的职责）；
- 修改日志前后的两次结果对比。

#### 验收标准

- 三个统计数字与日志内容人工核对一致；
- 命令均为单条流水线完成，无手工计数；
- 能讲清数据在每一段管道中的形态变化；
- 更换日志后命令无需修改即可重新统计。

### 练习 3：端口管家与启停脚本

#### 任务

启动一个实验 HTTP 服务并放入后台运行，编写 shell 脚本安全地停止它，再通过 `package.json` scripts 统一管理启动、停止和查看日志。

#### 步骤约束

1. 创建 `server.mjs`：监听 127.0.0.1 的 3210 端口，每收到一次请求输出一条访问日志；启动时打印 PID。
2. 用 `node server.mjs > server.log 2>&1 &` 放入后台，并用 `jobs`、`lsof -nP -iTCP:3210 -sTCP:LISTEN` 确认运行。
3. 编写 `stop.sh`：使用 `set -euo pipefail`；通过 `lsof -tiTCP:3210 -sTCP:LISTEN` 取 PID；用条件判断——取到 PID 才 `kill` 并等待复查，没取到则提示“服务未运行”。
4. 在 `package.json` 中定义 `start`、`stop`（`bash stop.sh`）、`logs`（`tail -f server.log`）三个脚本。
5. README 中写明：这些命令在类 Unix 与 WSL2 下可用；若团队有 Windows 原生环境，应如何用 Node 脚本重写停止逻辑。
6. 实验结束后确认端口释放、无残留进程。

#### 提交物

- `server.mjs`、`stop.sh`、`package.json`、`README.md`；
- 后台启动、作业状态、端口监听、停止复查的完整记录；
- 跨平台说明文字。

#### 验收标准

- 服务能以后台方式稳定运行，日志写入文件而非刷满终端；
- `stop.sh` 在“运行中”和“未运行”两种状态下表现都正确，不会执行无参数 `kill`；
- 三个 npm scripts 均能完成声明的职责；
- 停止后 `lsof` 查不到监听进程，端口确认释放。
