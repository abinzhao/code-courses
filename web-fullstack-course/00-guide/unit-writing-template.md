# 单元写作标准：把知识写成一次可完成的任务

本页供详细教程作者与自检读者使用。每个知识单元围绕一个可交付任务，包含下列 13 个板块，并保留任务卡、能力总结与单元导航。正文可以增加小节，但不能用篇幅替代深度，也不能让 13 个空标题冒充完整教学。

实际场景：准备写一篇“预约请求超时后怎样恢复”的教程时，先核对已教过的异步、HTTP 和领域契约，再把正常结果、超时、不确定状态、同键重试与安全停止都落到可运行文件和验收证据。不要临时加入尚未教授的真实支付或消息系统。

## 任务卡

用邻里集市中的具体人物和需求开场。写明本次成果、建议时间、一个可见成功结果和验收证据。开场只介绍当前困难，不预先堆叠后续技术。

例如商品发布者遇到保存后内容仍旧的问题，本课成果应是“证明页面来自哪份磁盘文件并恢复”，而不是“掌握编辑器全部功能”。学习者应能据任务卡判断做什么、留什么证据、完成后怎样结束。

## 1. 任务背景

说明谁遇到了什么问题、已有能力是什么、为什么现在增加这一层。把新技术绑定到产品行为，例如预约冲突、搜索结果或发布表单。

写清局部案例的边界：静态、内存教学服务、真实 API 或平台客户端不能混用。背景不承诺本课尚未实现的登录、持久化、交易或生产安全。

## 2. 学习目标

用可观察行为描述能力：解释机制、完成操作、预测输出、识别故障、说明取舍。目标应能在第 11 节逐条检查。

至少把“会用”和“能解释”分开。比如“请求成功时显示商品”与“超时不能证明服务端未写入”需要不同证据，不能统一写成“掌握 Fetch”。

## 3. 预备知识

列出前置教程的真实链接、必要工具和版本范围。区分必需能力与扩展阅读；不把后面才教授的语法作为隐藏前提。

复用文件时明确从哪篇哪个完整案例取得、放到个人项目哪里、是否覆盖旧文件。工具条件以[版本基线](version-baseline.md)和所在卷 README 为依据，不发明 SDK 补丁、平台权限或未运行过的兼容结论。

## 4. 核心理论

先展示结果，再解释输入、处理、状态和输出。短类比之后回到准确术语，配合表格或流程图。每个核心概念至少给一个观察方法。

理论要解释正常、边界与失败。例如取消浏览器等待、终止 HTTP 连接和撤销服务端业务不是同一个动作；需要用对应请求、状态或权威回读证明。

如果需要反例，明确标成错误案例，并与正确版本分开。主流程提供可以直接复制的完整版本，不让学习者连续修补多段代码才能运行；故障教程先运行明确的完整错误版，再给完整修复版和最小差异。

## 5. 标签、属性、API 或配置清单

表格使用四列：名称、作用、最小用法、边界。只列本课需要理解的项目；大型参考索引放在专门教程。

最小用法应真实存在于案例或能单独观察。边界说明什么没有保证：类型声明不实现运行时 API，`status` 干净不证明业务正确，权限声明不等于用户已授权。

## 6. 最小可运行案例

交代个人练习目录、文件位置、创建命令或明确编辑器操作、完整代码、运行命令、预期结果、证据位置、停止与清理方式，以及失败诊断。教材中的代码由学习者在个人工作区创建，教材仓库只保存 Markdown，不自动提供同名源码。

| 问题 | 必须给出的信息 |
|---|---|
| 放哪里？ | 相对个人项目的文件路径；独立实验与主线集成分开 |
| 怎样创建？ | 目录和空文件的可复现命令，或明确编辑器操作 |
| 在哪里运行？ | 当前目录、Shell、工具条件与必要环境输入 |
| 怎样成功？ | 页面文本、状态码、输出或测试结果 |
| 失败看哪里？ | 具体面板、日志、文件、输入或平台轨迹 |
| 证据放哪里？ | 学习记录、测试输出或脱敏截图的个人路径 |
| 怎样结束？ | 停止、恢复或清理动作及清理后的客观结果 |

完整代码不含“其余同上”“这里自行实现”或缺失函数。复用前篇完整文件可以，但必须给真实链接、准确文件清单、当前差异和可独立复核的启动条件。

命令区分 macOS/zsh 与 PowerShell；不能把 Unix 续行和变量语法冒充 Windows 命令。涉及进程只停止已确认归属的教学服务，清理仅针对本次产物。无后台进程的文档或静态案例，明确关闭文件或标签页即可。

## 7. 项目集成案例

说明该能力如何进入邻里集市、复用什么、改变哪个用户行为、哪些能力仍未实现。遵循[项目契约](project-contract.md)，不能把局部示例描述成完整生产系统。

集成应包含可运行的一条业务链，不只罗列未来架构。金额、时间、商品和预约状态按契约说明；进阶卷有显式扩展时标出差异，不让旧解析器静默接受新状态。

AI 工具建议不自动写业务；小程序离线草稿不等于预约成功；插件读到的网页文本不是可信后端数据。用各自证据验收，不把平台替身外推到真实运行时。

## 8. 常见错误与排查路径

按“现象 → 证据 → 原因 → 修复 → 复验”组织。至少覆盖一个可重复制造的故障，区分路径、版本、运行状态和业务逻辑问题。

错误记录必须保留修复前输入、观察和复现步骤；原因能解释这些证据，修复对应根因。用相同步骤复验，再检查相邻正常与错误路径。不得靠吞异常、写死结果、放宽断言或关闭安全检查制造通过。

连续两次修正失败时停止叠加猜测，重新核对文件、版本、运行对象和假设。

## 9. 课后题

包括理解、预测与取舍。参考答案可用 `details` 折叠，让学习者先尝试。答案解释依据，不只提供输出。

至少一个题目检验机制边界。例如“收到 404 是否说明服务没启动”“客户端取消是否证明事务回滚”“模型建议是否有权限写入”都应回答能观察什么、不能推出什么。

## 10. 实践练习

设置基础、提升和故障三类任务。每项说明文件或记录位置、运行方式、预期行为、失败观察点、恢复或清理动作与完成标准，给出可核对的答案要点。

基础复用当前能力，提升改变一个合理条件，故障验证理解边界。练习要求基于当前知识独立完成，不突然要求尚未教授的认证、数据库或部署。

例如路径课新增第二件商品、画不同路径基准、制造同名副本分别检验内容应用、路径解释和故障定位；不应三项都变成“继续阅读资料”。

## 11. 阶段验收

列出功能、解释和恢复证据，与第 2 节目标对应。提交材料包含源码路径、证据路径、创建与运行命令、正常结果、失败记录、修复动作、同路径复验、清理结果和已知边界。只读完教程不能替代验收。

自动测试报告必须写明实际执行命令、范围和结果；没有执行的平台标未验证。纯函数测试、HTTP/数据库集成、页面端到端、平台工具、真机和外部发布不能互相代替。

通过标准是别人能按材料重做并识别同一结果，错误实现也会被检查发现。安全、权限、数据一致性等关键项不能用其他评分补偿。

## 12. 常见问题

回答真实学习卡点：工具找不到、行为与预期不符、为什么这样组织、哪些能力下一阶段再做。提供读者可自行观察的步骤。

不要重复理论作为问答填充；“终端不返回提示符”应指导查前台进程与停止方式，“Network 空白”应指导开启记录后刷新，“构建成功但真机失败”应区分测试层次。

## 13. 扩展阅读

优先官方文档、标准和项目契约。每个链接说明带着什么问题阅读；涉及发布版本时记录核验日期与实际来源，未验证内容不写成确定结论。

内部链接从当前文件计算，锚点以真实标题为准。链接知识组时用分卷 README，开始实作时用现存详细教程，不引用已删除的章入口。正文不包含对话过程、修改流水账或编排说明。

## 我现在能做到什么

用两三句回顾新增能力，说明下一单元怎样复用它，并保留当前边界。总结来自能独立完成与解释，不使用“掌握全部知识”的口号。

## 单元导航

每篇详细教程结尾用真实链接给出上一课、下一课和分卷 README。阶段结束时可链接综合验收或后续卷第一课；不存在下一课时不猜文件名。

## 写作检查

维护操作：先核对目标、当前实现和前置，再按十三节写完整案例；在个人工作区从空目录复做，注入一次故障，按原步骤恢复，最后检查 Markdown 链接和锚点。临时审计脚本与提取源码放在教材外。

- [ ] 目标、理论、示例、题目和验收互相对应。
- [ ] 十三节、任务卡、能力总结与单元导航齐全且有实质内容。
- [ ] 主流程代码完整，错误版本单独标识。
- [ ] 文件、创建、cwd、Shell、工具、命令、结果与诊断明确。
- [ ] 证据位置、清理结果与同路径复验明确。
- [ ] 与邻里集市契约一致，局部或进阶扩展边界诚实。
- [ ] 基础、提升、故障练习可独立执行且有答案依据。
- [ ] 前置和导航指向真实教程或 README 锚点。
- [ ] 版本、官方资料和实际运行证据分开，不外推未验证平台。
- [ ] 正文无真实凭据、隐私、无解释的破坏性命令或对话过程。

全部通过后才将该单元标为已验收；未运行的命令与平台保留缺口，不用“结构齐全”代替教学和运行质量。
