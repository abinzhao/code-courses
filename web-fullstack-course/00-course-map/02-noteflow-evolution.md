# NoteFlow 演进地图

## 产品不是每周重做一次

NoteFlow 是课程的连续项目。每个阶段都在同一套产品上增加一种真实复杂度：

```text
公开页面
  -> 可访问内容
  -> 响应式视觉
  -> 浏览器交互
  -> React/Vue 管理端
  -> API 与数据库
  -> 认证、权限与组织隔离
  -> 缓存、队列、测试与部署
```

学习者每次只处理当前阶段需要的复杂度。这样可以看见一个决定如何影响后面的页面、接口、数据和验收，而不是把所有工程问题一次堆在面前。

## 三条产品线

### 公共内容侧

访客可以浏览已经发布的文章，按标签、分类和关键词搜索，查看作者、目录和相关文章。W1 只建立第一张静态草图；W2–W4 会把它变成语义化、可访问的内容页。

后续能力：

- 文章列表、详情和相关文章
- 响应式图片、音视频和字幕
- 搜索、评论和收藏
- SEO、Metadata、站点地图和 SSR
- 发布状态对公共可见性的约束

### 团队协作侧

工作区成员可以创建和编辑文档，Editor 负责内容审核，Admin 和 Owner 负责成员与组织设置。React 和 Vue 会实现同一组核心页面，用来比较两套响应式模型与组件设计。

后续能力：

- 登录和工作区首页
- 文档列表、编辑器和评论
- 成员列表、邀请和角色变更
- 审核队列和发布流
- 操作日志和高风险操作确认

### 平台工程侧

后端和交付阶段把“页面能显示”推进到“系统能在真实条件下稳定运行”：

- REST API 和统一错误响应
- PostgreSQL 关系模型、迁移、事务和索引
- Refresh Token 轮换、组织隔离和 RBAC
- Redis 缓存、BullMQ 队列和幂等任务
- 文件上传、测试数据库、E2E 和 CI
- Docker、健康检查、部署、回滚和可观测性

## 核心业务约束

课程中出现的实现都要逐步靠近这些约束：

1. 团队数据通过 `organizationId` 或工作区成员关系隔离。
2. 公开文章必须处于已发布状态。
3. 私有文档必须经过服务端成员关系和权限检查。
4. 删除、角色变更和所有权变更必须写入审计日志。
5. 文章发布和审核必须通过显式状态机推进。

文章状态机：

```text
DRAFT -> IN_REVIEW -> APPROVED -> PUBLISHED
  |          |             |
  +----------+-------------+
             REJECTED
```

W1 不实现状态机，但会在 NoteFlow 草图中使用“文章入口”和“团队内容”这些产品词，为后续的内容模型保留语境。

## W1 的第一块砖

第一周不追求“做出完整首页”，而是建立两个以后每周都会复用的习惯：

- 在浏览器中观察证据：页面、请求、状态码和资源。
- 在终端和 Git 中留下证据：命令、版本、差异和提交。

当学习者能说清楚“这个结果由谁负责、我在哪里看到了证据”，后面的框架和后端学习才不会变成盲目试错。
