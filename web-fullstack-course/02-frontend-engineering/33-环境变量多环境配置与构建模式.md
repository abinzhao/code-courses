# 33-环境变量多环境配置与构建模式

## 目标

完成本知识单元后，学员应能为前端应用设计一套安全、可复现、可排查的多环境配置体系，而不是只会在代码里写死几个地址。

学员应能够：

1. 解释前端环境变量“构建期注入”的本质，区分浏览器中的配置与 Node.js 服务端进程中的环境变量。
2. 说明 Vite 的 `VITE_` 前缀暴露规则，判断哪些值可以进入客户端产物，哪些值永远不能。
3. 使用 `.env` 文件族与模式（mode）组织 development、test、staging、production 的配置，并说清加载优先级。
4. 通过 `import.meta.env` 读取变量，并建立集中式配置层，避免环境判断散落在业务代码中。
5. 区分构建期配置与运行时配置，根据“是否需要重新构建才能变更”这一标准为不同配置项选型。
6. 为关键配置编写校验逻辑，让缺失或非法配置在启动、构建或部署阶段快速失败，并输出可定位的错误信息。

本单元聚焦“配置在工程链路中的位置”。密钥管理、CI 密钥注入和容器环境变量将在后续 CI/CD 与部署单元中进一步展开。

## 技术栈

| 工具或环境 | 用途 | 学习要求 |
|---|---|---|
| Vite 当前稳定版（6.x/7.x） | 开发服务器与生产构建、环境变量加载 | 理解 `.env` 加载规则、`--mode` 与 `import.meta.env` |
| Node.js 当前 LTS（24.x，或团队锁定的 LTS） | 运行构建脚本与配置校验脚本 | 能区分 `process.env` 与浏览器可见变量 |

- `import.meta.env` 是 ESM 与构建器协作的结果，只在被构建器处理的前端代码中可靠存在。

## 详细的理论知识讲解和示例伪代码

### 1. 前端环境变量的特殊性：构建期注入

#### 1.1 定义

环境变量在传统服务端程序中，是进程启动时由操作系统或启动脚本注入的键值对，程序运行期间通过 `process.env` 读取。改变环境变量后重启进程即可生效，源代码不需要变化。

前端程序则不同。浏览器中运行的代码是构建产物：构建器在 CI 或开发机上读取变量，把变量值“替换”进 JavaScript 产物，再把产物发送给浏览器。浏览器本身没有机会读取构建机器上的环境变量。

```text
服务端模式：
启动进程 → 进程从 process.env 读取变量 → 值只存在于服务器内存

前端模式：
构建器启动 → 读取环境变量 → 文本替换进 bundle → 产物发到浏览器 → 任何人可在产物中读到这些值
```

#### 1.2 工程化关系

这一差异决定了两条工程铁律：

1. 前端环境变量不是秘密。任何进入 `VITE_` 变量的值，都会出现在下载到用户设备的产物中，可以被 DevTools、查看源代码或抓包直接看到。
2. 修改前端环境变量通常意味着重新构建、重新发布。只改服务器上的环境变量而不重新构建，正在运行的前端产物不会发生任何变化。

示例：Vite 在构建时执行的是类似常量替换的动作。

```js
// 源码
const apiBase = import.meta.env.VITE_API_BASE_URL;

// 构建后的产物（示意，已被静态替换）
const apiBase = "https://api.example.com";
```

构建期只读、不带暴露前缀的变量则只存在于构建机器上：

```js
// vite.config.js 中可以读取无 VITE_ 前缀的变量
// 该值不会被注入到客户端代码
const secretToken = process.env.BUILD_MACHINE_TOKEN;
console.log(secretToken ? "构建机已授权" : "构建机未授权");
```

#### 1.3 常见误区

> 环境变量天然是安全的，把数据库密码放进前端环境变量不会泄露。

错。前端产物对用户完全可见，“环境变量”这个名字不提供任何保密性。前端环境变量只适合保存“可以公开、但因环境不同而不同”的值，例如 API 域名、功能开关、埋点 ID。

> 上线后在服务器上改一下环境变量，刷新页面就生效。

构建期注入的值在构建完成时已经固化。要让新值生效，必须用新变量重新构建并发布产物。需要“改完即生效”的配置，应使用运行时配置（见第 7 节）。

### 2. VITE_ 前缀与暴露边界

#### 2.1 定义

Vite 默认只把以 `VITE_` 开头的变量暴露给客户端代码，通过 `import.meta.env` 访问。不带前缀的变量不会出现在浏览器产物中，但可以在 `vite.config.js` 以及构建插件中通过 `process.env` 使用。

此外，Vite 内置了几个保留变量：

| 变量 | 含义 |
|---|---|
| `import.meta.env.MODE` | 当前模式，如 `development`、`production`、`staging` |
| `import.meta.env.DEV` | 是否为开发模式，布尔值 |
| `import.meta.env.PROD` | 是否为生产模式，布尔值 |
| `import.meta.env.SSR` | 是否在服务端渲染阶段，布尔值 |
| `import.meta.env.BASE_URL` | 应用的基础公共路径 |

#### 2.2 工程化关系

前缀规则是一道“防误操作”的工程护栏：即使构建机器上存在 `DB_PASSWORD` 之类的敏感变量，只要它不带 `VITE_` 前缀，就不会被意外打进前端产物。

可以通过 `envPrefix` 配置增加暴露前缀，但应极其谨慎：增加前缀等于扩大泄露面。

```js
// vite.config.js
import { defineConfig } from 'vite';

export default defineConfig({
  // 默认只暴露 VITE_ 开头的变量
  // 如需额外前缀，必须清楚知道这些变量都会进入客户端产物
  envPrefix: ['VITE_', 'PUBLIC_'],
});
```

可以在代码中显式检查，避免把敏感逻辑误判为“服务端可控”：

```ts
// src/config/index.ts
// 这里读到的一切都应当假设“用户可见”
export const apiBaseUrl = import.meta.env.VITE_API_BASE_URL;
export const analyticsId = import.meta.env.VITE_ANALYTICS_ID ?? '';
export const isDev = import.meta.env.DEV;
```

终端中可以直接观察“暴露”这一事实：

```bash
# 在项目根目录放一个非敏感的演示变量
printf 'VITE_DEMO_PUBLIC=visible-in-browser\n' > .env.local
printf 'DEMO_SERVER_ONLY=invisible-in-browser\n' >> .env.local
pnpm build
# 在 dist 目录中检索：能找到 visible-in-browser，找不到 invisible-in-browser
grep -R "visible-in-browser" dist | head -n 1
grep -R "invisible-in-browser" dist | head -n 1 || echo "未进入产物"
```

#### 2.3 常见误区

> 给变量起名叫 `VITE_API_SECRET` 就只有构建器能看到。

凡是带 `VITE_` 前缀的变量都会进入产物，与变量名里是否含 secret、key、password 无关。判断标准只有前缀，不是变量语义。

> 自定义一个 `APP_` 前缀，和 `VITE_` 一样安全。

前缀本身不提供安全性，只控制“是否暴露”。自定义前缀扩大了可暴露变量集合，团队必须同步建立命名规范和审查机制。

### 3. .env 文件族与加载优先级

#### 3.1 定义

Vite 使用 dotenv 从环境目录（默认是项目根目录，即包含 `index.html` 的目录或 `envDir` 指定目录）加载 `.env` 文件。文件族按模式和本地用途分层：

| 文件 | 用途 | 是否提交 Git |
|---|---|---|
| `.env` | 所有模式共享的默认值 | 提交 |
| `.env.local` | 所有模式共享的本地覆盖 | 不提交 |
| `.env.[mode]` | 指定模式的值，如 `.env.production` | 提交 |
| `.env.[mode].local` | 指定模式的本地覆盖 | 不提交 |

`.local` 文件应写入 `.gitignore`，用于个人机器上的临时覆盖，例如本机端口、个人测试 token（且该 token 本身必须是低权限的）。

#### 3.2 工程化关系

分层文件让“团队默认值”和“个人覆盖值”分离：共享配置随代码评审演进，个人实验不污染仓库。

示例文件内容：

```bash
# .env
VITE_APP_TITLE=订单控制台
VITE_API_BASE_URL=https://api-dev.example.com
VITE_FEATURE_NEW_REPORT=false
```

```bash
# .env.staging
VITE_API_BASE_URL=https://api-staging.example.com
VITE_FEATURE_NEW_REPORT=true
```

```bash
# .env.production
VITE_API_BASE_URL=https://api.example.com
VITE_FEATURE_NEW_REPORT=true
```

```bash
# .env.local（不提交，仅本机生效；值为占位演示）
VITE_API_BASE_URL=http://localhost:8080
```

加载优先级遵循“越具体越优先”。以 staging 模式为例：

```text
.env                    最低，提供兜底默认值
.env.local              覆盖通用默认值（测试模式除外）
.env.staging            覆盖模式值
.env.staging.local      最高，个人覆盖模式值
```

已经存在于真实 shell 环境中的变量一般不会被 `.env` 文件覆盖（dotenv 默认不覆盖已存在的 `process.env`），因此 CI 中注入的变量优先级最高，这正是期望行为。

`.gitignore` 中应包含：

```text
.env*.local
.env.local
```

#### 3.3 常见误区

> 把所有环境的值都写进一个 `.env`，代码里用 if 判断环境。

这会让环境差异藏在代码分支里，评审和排查都困难。环境差异应由文件层表达，代码只读取统一的键名。

> 把含真实 token 的 `.env.production.local` 提交到仓库“方便大家用”。

提交即泄露，即使之后删除也会留在 Git 历史中。共享密钥应通过 CI Secret 或团队密钥管理系统分发。

### 4. 模式（mode）：development、production、test

#### 4.1 定义

模式是一个字符串标识，决定加载哪一组 `.env` 文件，以及构建器采用哪种优化策略。`vite` 启动开发服务器时模式为 `development`，`vite build` 时默认为 `production`，可以通过 `--mode` 指定任意模式。

```bash
pnpm vite --mode staging          # 以 staging 模式启动开发服务器
pnpm vite build --mode staging    # 构建 staging 产物
pnpm vite build                   # 默认 production 构建
```

需要特别注意：模式与“是否压缩、是否开启开发工具”的构建行为有关联，但不是同一件事。例如以 staging 模式构建时，产物默认仍然按生产方式优化，因为 `vite build` 的命令属性决定了构建形态。

#### 4.2 工程化关系

模式让“一次构建流程”可以产出面向不同环境的产物，配合 package.json 脚本形成固定入口：

```json
{
  "scripts": {
    "dev": "vite",
    "build:test": "vite build --mode test",
    "build:staging": "vite build --mode staging",
    "build": "vite build --mode production",
    "preview:staging": "vite preview --mode staging"
  }
}
```

测试环境（Vitest）是另一个常见场景。Vitest 默认使用 `test` 模式加载 `.env.test`，用于固定测试用的 API 地址和开关，避免单元测试依赖开发者本机配置：

```bash
# .env.test
VITE_API_BASE_URL=http://localhost:3917
VITE_FEATURE_NEW_REPORT=false
```

```ts
// src/config/index.test.ts
import { describe, it, expect } from 'vitest';
import { apiBaseUrl } from './index';

describe('配置层', () => {
  it('在测试模式下读取测试环境地址', () => {
    expect(apiBaseUrl).toBe('http://localhost:3917');
  });
});
```

在页面上显式展示非生产环境标记，可以防止“在测试环境操作却以为是生产”的事故：

```tsx
// src/app/EnvBadge.tsx
export function EnvBadge() {
  if (import.meta.env.PROD) return null;
  return (
    <div className="env-badge">
      当前环境：{import.meta.env.MODE}
    </div>
  );
}
```

#### 4.3 常见误区

> `NODE_ENV` 和 Vite 的 mode 是同一个东西。

`NODE_ENV` 是 Node 生态约定，某些库据此切换开发/生产行为；Vite 的 mode 决定 `.env` 文件加载。两者默认值碰巧一致，但可以被独立设置。不要用其中一个推断另一个。

> 需要几个环境就复制几套源码或几个分支。

环境差异应通过模式和配置文件解决，长期维护“test 分支”“prod 分支”会让代码分叉、合并痛苦。

### 5. dev/test/staging/prod 多环境配置策略

#### 5.1 定义

一套常见的四环境职责划分如下：

| 环境 | 用途 | 数据 | 发布触发 |
|---|---|---|---|
| development（本地 dev） | 日常开发、联调 | mock 或本机服务 | 手动启动 |
| test（测试） | 自动化测试、提测后功能验证 | 测试数据 | PR 或合并后自动 |
| staging（预发） | 发布前在类生产环境验证 | 接近生产的脱敏数据 | 发布前手动/自动 |
| production（生产） | 对外服务 | 真实数据 | 审批后发布 |

#### 5.2 工程化关系

多环境策略的关键不是“文件多”，而是两个原则：

1. 键名在所有环境保持一致，值不同。业务代码只依赖键，不依赖环境。
2. 默认值放在 `.env`，环境特有的差异放在 `.env.[mode]`，禁止把环境判断写进业务代码。

推荐用一个配置矩阵明确每个变量在每个环境的取值与归属：

```text
变量                         dev                test               staging            prod
VITE_API_BASE_URL           localhost:8080      localhost:3917     api-staging        api
VITE_FEATURE_NEW_REPORT     false              false              true               true
VITE_ANALYTICS_ID           （空，关闭埋点）    （空）              G-STAGING-xxxx    G-PROD-xxxx
```

在 CI 中，变量由流水线注入而不依赖仓库中的文件。GitHub Actions 示例（概念级）：

```yaml
# .github/workflows/build.yml（节选）
jobs:
  build-staging:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm build:staging
        env:
          VITE_API_BASE_URL: ${{ secrets.STAGING_API_BASE_URL }}
          VITE_ANALYTICS_ID: ${{ secrets.STAGING_ANALYTICS_ID }}
```

本地联调对接后端时，推荐用 `.env.development.local` 覆盖，而不是修改已提交的文件：

```bash
# .env.development.local（不提交，占位演示）
VITE_API_BASE_URL=http://127.0.0.1:8080
```

#### 5.3 常见误区

> staging 和 production 用同一套地址，只在出问题时手动切换。

预发环境的价值就在于“接近生产但不触碰真实数据”。共用生产后端会让预发验证污染真实数据，也无法验证部署链路本身。

> 环境越多越好，每个分支配一个环境。

环境有维护成本（数据、权限、监控都要独立）。环境数量应服务发布流程，通常四环境足够，小团队甚至可以 dev/staging/prod 三环境。

### 6. import.meta.env 与集中配置层

#### 6.1 定义

`import.meta.env` 是读取暴露变量的唯一入口。直接在业务组件中散落读取，会造成三个问题：变量改名困难、不知道哪些变量被使用、无法统一设置默认值和校验。

集中配置层把所有环境读取收敛到一个模块（如 `src/config/`），业务代码只从该模块导入语义化常量。

#### 6.2 工程化关系

集中配置层让“配置契约”显式化：有哪些配置、类型是什么、缺省值是什么、哪些必填，一目了然。

```ts
// src/config/env.ts
const env = import.meta.env;

function required(value: string | undefined, key: string): string {
  if (!value || value.trim() === '') {
    throw new Error(`缺少必要的环境变量 ${key}，请检查 .env 文件或 CI 注入`);
  }
  return value;
}

export const config = {
  appTitle: env.VITE_APP_TITLE ?? '订单控制台',
  apiBaseUrl: required(env.VITE_API_BASE_URL, 'VITE_API_BASE_URL'),
  featureNewReport: env.VITE_FEATURE_NEW_REPORT === 'true',
  analytics: {
    enabled: Boolean(env.VITE_ANALYTICS_ID),
    id: env.VITE_ANALYTICS_ID ?? '',
  },
  mode: env.MODE,
  isDev: env.DEV,
  isProd: env.PROD,
} as const;

export type AppConfig = typeof config;
```

为了让 TypeScript 认识自定义变量，可以补充声明文件：

```ts
// src/vite-env.d.ts
/// <reference types="vite/client" />

interface ImportMetaEnv {
  readonly VITE_APP_TITLE: string;
  readonly VITE_API_BASE_URL: string;
  readonly VITE_FEATURE_NEW_REPORT?: 'true' | 'false';
  readonly VITE_ANALYTICS_ID?: string;
}

interface ImportMeta {
  readonly env: ImportMetaEnv;
}
```

业务代码只依赖语义化配置，不再直接接触原始变量：

```ts
// src/shared/api/client.ts
import { config } from '@/config/env';

export async function apiFetch(path: string, init?: RequestInit) {
  const response = await fetch(`${config.apiBaseUrl}${path}`, init);
  if (!response.ok) {
    throw new Error(`接口请求失败：${response.status}`);
  }
  return response.json();
}
```

```ts
// src/app/main.tsx
import { config } from '@/config/env';

if (config.analytics.enabled && config.isProd) {
  // 仅生产环境初始化埋点，避免开发数据污染统计
  console.log(`初始化分析 SDK：${config.analytics.id}`);
}
```

#### 6.3 常见误区

> 图省事，在几十个组件里直接写 `import.meta.env.VITE_xxx`。

变量重命名、改默认值、排查“这个变量在哪里用”都会变成全局搜索游戏。集中层的成本极低，收益持续整个项目生命周期。

> 布尔变量直接当布尔值用：`if (import.meta.env.VITE_FLAG)`。

`.env` 中所有值都是字符串，`"false"` 是非空字符串，直接判断永远为真。布尔配置必须显式与 `'true'` 比较。

### 7. 运行时配置与构建期配置

#### 7.1 定义

构建期配置在构建时固化，产物与环境一一对应；运行时配置在应用启动时（浏览器中）才获取，同一份产物部署到不同环境后，启动时拉取对应的配置。

常见运行时配置实现方式：

1. 在 `public/` 放置 `config.js`，由运维或部署步骤按环境生成，`index.html` 通过普通 `<script>` 引入，挂到 `window.__APP_CONFIG__`。
2. 应用启动时请求一个配置接口（如 `/config.json` 或 `/api/runtime-config`），拿到值后再渲染。

#### 7.2 工程化关系

选型标准是“变更这个值时，是否允许重新构建”：

| 配置类型 | 例子 | 适合方式 |
|---|---|---|
| 各环境固定、随版本发布 | API 基础域名、构建版本号 | 构建期 |
| 需要部署后动态调整、应急开关 | 紧急功能开关、灰度名单、非密钥化的运营参数 | 运行时 |
| 真正的密钥 | 数据库密码、服务端私钥 | 二者都不放，只能在服务端 |

运行时配置示例：

```js
// public/config.runtime.js（部署时由部署脚本按环境替换内容）
window.__APP_CONFIG__ = {
  apiBaseUrl: 'https://api.example.com',
  emergencyOfflineMode: false,
  rolloutPercentage: 100,
};
```

```html
<!-- index.html 中在应用脚本之前引入 -->
<script src="/config.runtime.js"></script>
```

```ts
// src/config/runtime.ts
type RuntimeConfig = {
  apiBaseUrl: string;
  emergencyOfflineMode: boolean;
  rolloutPercentage: number;
};

declare global {
  interface Window {
    __APP_CONFIG__?: RuntimeConfig;
  }
}

export function getRuntimeConfig(): RuntimeConfig {
  const raw = window.__APP_CONFIG__;
  if (!raw) {
    throw new Error('运行时配置缺失：未找到 window.__APP_CONFIG__');
  }
  return raw;
}
```

运行时配置同样不能存放密钥——它依然会下发到浏览器，只是获取时机从构建时移到了启动时。它解决的是“重新构建成本”和“应急变更速度”，不是保密问题。

两种方式可以混合使用：构建期配置承载稳定的环境骨架，运行时配置承载需要快速调整的少量开关。

#### 7.3 常见误区

> 用了运行时配置，就可以把 API 密钥放进去了。

不行。任何到达浏览器的值都是公开的。需要密钥的调用必须经由后端代理，或后端下发短期、受限、与用户会话绑定的凭证。

> 把全部配置都改成运行时拉取，首屏多一个请求“更灵活”。

配置接口会成为启动依赖：接口失败则应用白屏，也增加首屏时延。稳定配置应留在构建期，只有真正需要动态调整的少数项才走运行时。

### 8. 配置校验与快速失败

#### 8.1 定义

配置校验是在应用启动或构建开始时，检查所有必填变量是否存在、格式是否合法（如必须是 URL、必须属于枚举集合），不合法则立即终止并输出明确错误。目标是把“配置问题”从线上运行时的诡异现象，提前为本地或 CI 中的显式报错。

#### 8.2 工程化关系

校验应放在集中配置层，对所有入口生效。使用 schema 库的示例：

```ts
// src/config/schema.ts
import { z } from 'zod';

const envSchema = z.object({
  VITE_API_BASE_URL: z.string().url('VITE_API_BASE_URL 必须是合法 URL'),
  VITE_APP_TITLE: z.string().min(1).default('订单控制台'),
  VITE_FEATURE_NEW_REPORT: z
    .enum(['true', 'false'])
    .default('false'),
  VITE_ANALYTICS_ID: z.string().optional(),
});

const parsed = envSchema.safeParse({
  VITE_API_BASE_URL: import.meta.env.VITE_API_BASE_URL,
  VITE_APP_TITLE: import.meta.env.VITE_APP_TITLE,
  VITE_FEATURE_NEW_REPORT: import.meta.env.VITE_FEATURE_NEW_REPORT,
  VITE_ANALYTICS_ID: import.meta.env.VITE_ANALYTICS_ID,
});

if (!parsed.success) {
  const messages = parsed.error.issues
    .map((issue) => `  - ${issue.path.join('.')}：${issue.message}`)
    .join('\n');
  throw new Error(`环境变量校验失败：\n${messages}`);
}

export const env = parsed.data;
```

在构建机器侧（Node 环境，非浏览器代码），可以用独立脚本在构建前校验 CI 注入的变量，让失败发生在构建第一步：

```js
// scripts/check-build-env.mjs
const required = ['VITE_API_BASE_URL'];

const missing = required.filter((key) => !process.env[key]);

if (missing.length > 0) {
  console.error(`构建中止，缺少环境变量：${missing.join(', ')}`);
  console.error('请在 CI 配置或 .env 文件中提供上述变量。');
  process.exit(1);
}

const url = process.env.VITE_API_BASE_URL;
try {
  new URL(url);
} catch {
  console.error(`VITE_API_BASE_URL 不是合法 URL：${url}`);
  process.exit(1);
}

console.log('构建环境变量校验通过。');
```

将校验接入脚本，保证任何构建入口都先校验：

```json
{
  "scripts": {
    "prebuild": "node scripts/check-build-env.mjs",
    "build:staging": "pnpm prebuild && vite build --mode staging",
    "build": "pnpm prebuild && vite build --mode production"
  }
}
```

验证失败行为：

```bash
# 故意制造缺失
env -u VITE_API_BASE_URL pnpm build
# 预期：脚本输出“构建中止，缺少环境变量”，退出码为 1，vite build 不会执行
echo $?
```

#### 8.3 常见误区

> 变量缺失时让代码静默使用空字符串或线上地址兜底。

这会把配置问题伪装成“接口跨域”“页面空白”等运行时故障，排查成本极高。必填项缺失就应明确失败，默认值只适用于真正有合理缺省的可选项。

> 校验只在页面用到时才做。

延迟到用户操作时才报错，意味着问题可能在上线后才被发现。校验必须在启动或构建阶段集中执行一次。

### 练习 1：多模式配置骨架

#### 任务

- 一份 200 字以内的加载优先级说明。

#### 验收标准

- 四个模式均可正确构建，产物中的地址与对应文件一致；
- `.env.local` 的覆盖确实生效，且未被 Git 跟踪；
- 非生产环境页面可见模式标记，生产环境不可见；

#### 任务

#### 步骤约束

- 缺失与非法场景都在构建动作开始前被拦截，退出码为非零；
- 错误信息能让一名不了解项目的同学知道缺什么、怎么改；
- 成功场景退出码为 0；

### 练习 3：运行时应急开关

#### 任务

在不重新构建的前提下，为生产产物增加一个运行时应急开关：通过修改 `public/config.runtime.js`（模拟部署步骤替换）即可让页面进入“维护提示”状态，刷新即生效。

#### 步骤约束

1. 在 `index.html` 中以普通脚本方式引入运行时配置文件，挂载到 `window.__APP_CONFIG__`。

- 运行时配置文件、类型声明与读取模块；

- 构建期配置与运行时配置的选型说明（含边界与限制）；
- 演示用命令清单。

#### 验收标准

- 同一份产物在修改运行时配置后表现不同，期间没有重新构建；
- 运行时配置缺失时有可读错误；
- 文档明确写出保密边界，方案中不包含任何密钥；
- 构建期与运行时配置各司其职，没有把所有配置无差别迁移到运行时。
