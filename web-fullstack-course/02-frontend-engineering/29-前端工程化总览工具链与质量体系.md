# 29-前端工程化总览：工具链与质量体系

## 目标

完成本知识单元后，学员应能建立“前端工程化”的整体心智模型：既知道每一类工具解决什么问题，也能把它们串成一条从代码提交到线上发布的完整链路，而不是把 Vite、ESLint、CI 等名词当作彼此孤立的命令。

学员应能够：

1. 用自己的语言说明工程化要解决的四类问题：重复劳动、一致性、质量与协作，并各举出至少两个真实项目中的例子。
2. 画出前端工具链全景图，标出脚手架、开发服务、构建、Lint、测试、CI 与发布各环节的位置和数据流方向。
3. 解释模块化标准与“模块图”的概念，说明构建工具为什么要先建立模块图才能产出产物。
4. 使用 `create-vite` 创建项目，说清脚手架到底替我们做了什么、哪些决策仍需要团队自己负责。
5. 读懂并设计 `package.json` 脚本体系，理解脚本组合、退出码在自动化中的作用。
6. 描述质量体系的分层结构（开发时检查、提交门禁、CI 门禁、发布前检查），说明“质量左移”的含义与代价边界。

本单元是 02 阶段的总览，重在建立地图。Vite 深入、生产构建、规范门禁分别在 U30、U31、U32 展开；环境变量治理在 U33，CI 流水线在 U56 进一步落地。

## 技术栈

本单元不要求学员手写所有工具的配置，但需要实际跑通脚手架与脚本体系，获得第一手观察。

| 工具或环境 | 用途 | 学习要求 |
|---|---|---|
| Node.js 当前 LTS | 所有前端工具的运行时 | 能确认版本处于官方 LTS 窗口，理解工具运行在 Node 之上 |
| pnpm 当前稳定版 | 包管理与脚本执行 | 能安装依赖、执行 scripts、理解锁文件作用 |
| Vite 当前稳定主版本 | 开发服务器与生产构建 | 能创建项目、跑通 dev/build/preview，理解双模式 |
| Rollup（随 Vite） | 生产构建底层 | 知道 Vite 生产构建基于 Rollup，U31 深入 |
| Webpack 5 | 存量项目构建器认知 | 知道其核心概念与存量占比，新项目少用，U31 展开 |
| ESLint 9 flat config | 代码质量规则 | 知道其在工具链中的位置，U32 深入配置 |
| Prettier 当前稳定版 | 代码格式化 | 能区分格式化与质量规则的职责 |
| Git | 版本管理与提交钩子载体 | 理解提交门禁挂在 Git 生命周期上 |
| CI（GitHub Actions 或同类） | 自动化质量门禁 | 理解其在链路中的位置，本单元只做认知 |

开始前检查环境：

```bash
node -v
pnpm -v
git --version
```

预期观察：

- `node -v` 输出的主版本处于 Node.js 官方发布时间表的 LTS 窗口；本单元写作时 LTS 主线为 24.x，22.x 仍在维护窗口。
- `pnpm -v` 输出版本号；若未安装 pnpm，可先通过 Corepack 启用：`corepack enable pnpm`。
- 版本号本身不是考点，关键是确认后续命令有稳定、可复现的运行环境。

约定：

- 本课程统一使用 pnpm，不与 npm、yarn 混用；锁文件 `pnpm-lock.yaml` 必须提交。
- 命令中的 `<项目名>` 等尖括号内容表示需要替换的参数，不要原样输入。
- Windows 学员建议在 WSL 中完成命令行部分；PowerShell 不作为主线。

## 详细的理论知识讲解和示例伪代码

### 1. 工程化要解决的四类问题

#### 1.1 定义：工程化不是某个工具

前端工程化是指：把软件开发中可重复、可标准化、可自动检验的部分，固化为工具、规则与流程，使团队能够稳定、快速、可追溯地交付产品。

它不是某一个工具。Vite 不是工程化，ESLint 也不是；它们分别解决链路中某一段的具体问题。工程化是这些工具按正确方式组合后形成的体系。

一句话概括：

```text
工程化 = 把“在我机器上能跑”，变成“团队任何人随时都能可靠地交付”。
```

#### 1.2 问题一：重复劳动

没有工具时，开发者每天都在手动重复同样的动作：刷新浏览器、拼接文件、压缩图片、复制部署目录、给产物改文件名做缓存。

重复劳动的问题不只是“累”，更是：

- 每次手动操作都可能漏步骤或顺序出错；
- 不同人操作方式不同，产物就不同；
- 熟练者的经验无法沉淀给新人。

工程化把重复劳动收敛成一条命令：

```bash
pnpm dev       # 启动开发服务器，自动刷新交给 HMR
pnpm build     # 转换、打包、压缩、加 hash，一次完成
pnpm preview   # 本地预览生产产物
```

命令背后可能有几百个步骤，但执行者不需要记住它们，只需要相信并验证这条命令。

#### 1.3 问题二：一致性

团队协作中，一致性体现在多个层面：

| 层面 | 不一致的表现 | 工程化手段 |
|---|---|---|
| 代码格式 | 有人用单引号有人用双引号，缩进混用 | Prettier 统一格式 |
| 代码质量 | 有人写未使用变量，有人随手改全局 | ESLint 规则约束 |
| 依赖版本 | 每个人机器上装的 React 版本不同 | 锁文件固定版本 |
| 项目结构 | 每个新项目目录组织都不同 | 脚手架模板统一 |
| 环境配置 | 本机 Node 18，CI 上 Node 24 | `.nvmrc`、CI 镜像固定 |

一致性的价值在“读代码”和“换人维护”时才充分体现：当所有项目长得一样，开发者切换项目时几乎没有学习成本。

#### 1.4 问题三：质量

质量不是靠“发布前多看两眼”保证的。人脑不适合反复检查成百上千条机械规则，工具才适合。

工程化把质量拆成可自动判定的检查：

- 类型系统在编译期拦住类型错误；
- Lint 在提交前发现危险写法和坏味道；
- 单元测试在每次改动后验证逻辑；
- E2E 测试验证关键用户路径；
- 构建本身也会暴露语法与引用错误。

关键区别：

```text
“我觉得没问题”      —— 主观、不可重复、无法追溯
“所有自动检查都通过” —— 客观、可重复、日志可查
```

工程化并不消灭 bug，而是让缺陷在越早、成本越低的阶段被拦住。

一个能被类型系统在编码期拦住的问题示例：

```ts
interface TicketSummary {
  id: number;
  title: string;
}

function renderTitle(ticket: TicketSummary) {
  return ticket.titel.toUpperCase();
  //          ^^^^^^ 拼写错误立即被标红，而不是等用户点开页面才暴露
}
```

#### 1.5 问题四：协作

软件项目的大多数问题最终是协作问题：

- 多人同时改一个文件，如何不互相覆盖——版本控制；
- 改动如何让别人知道影响范围——代码评审与提交信息；
- 新人如何在半小时内把项目跑起来——README 与脚本体系；
- 谁在什么时间发布了什么——版本号、变更日志、发布记录；
- 不合规的代码如何不被合并——分支保护与 CI 门禁。

工程化让协作从“靠人提醒”变成“靠系统保证”。例如提交门禁会在代码进入仓库前自动运行检查，而不是依赖评审者逐行发现格式问题。

#### 1.6 工程化关系：四类问题如何映射到后续单元

```text
重复劳动  → 脚手架(U29)、Vite(U30)、构建(U31)
一致性    → 模板(U29)、ESLint/Prettier(U32)、锁文件
质量      → 类型检查、测试(U23/U24)、质量门禁(U32/U56)
协作      → 提交门禁(U32)、CI(U56)、版本与发布
```

常见误区：

> 工程化就是配置一堆工具，配置越复杂越专业。

工具数量不是指标。能用三条脚本和少量配置稳定交付的小项目，硬套十个插件和复杂流水线反而是负担。工程化的复杂度应与团队规模、项目寿命和风险水平匹配，并且每引入一个工具都要回答“它替我们省掉了什么、维护成本是什么”。

### 2. 前端工具链全景与一次提交的旅程

#### 2.1 定义：工具链

工具链是按开发顺序排列、彼此通过文件或协议衔接的一组工具。前一个工具的输出是后一个工具的输入：

```text
脚手架生成源码
   ↓
开发服务器在本地提供模块与 HMR
   ↓
（每次保存）格式化、Lint、类型检查即时反馈
   ↓
提交代码时触发提交门禁
   ↓
推送后 CI 执行完整检查
   ↓
通过后构建出生产产物
   ↓
产物分析与发布前检查
   ↓
发布到静态服务器 / CDN
```

#### 2.2 各环节职责一览

| 环节 | 代表工具 | 输入 | 输出 |
|---|---|---|---|
| 脚手架 | create-vite | 交互式选项 | 初始化好的项目目录 |
| 包管理 | pnpm | package.json、锁文件 | node_modules |
| 开发服务 | Vite dev server | 源码 | 本地 URL + HMR |
| 代码检查 | ESLint、tsc | 源码 | 问题报告、退出码 |
| 格式化 | Prettier | 源码 | 重排后的源码 |
| 测试 | Vitest、Playwright | 测试代码与源码 | 通过/失败报告 |
| 生产构建 | Vite（Rollup） | 全量源码 | dist 产物 |
| 产物分析 | visualizer 等 | 产物与统计数据 | 体积构成报告 |
| CI | GitHub Actions | 仓库代码 | 门禁结论、产物 |
| 发布 | 平台 CLI / CDN | dist 产物 | 线上可访问资源 |

注意“开发服务”和“生产构建”是两套机制：开发时追求响应快，生产时追求产物优。这是 U30 和 U31 的核心线索。

#### 2.3 跟着一次改动走完全程

假设开发者修改了 `src/features/tickets/list.tsx` 中一行文案：

```text
1. 保存文件
   - 编辑器调用 Prettier 格式化该文件
   - Vite 监听到文件变化，通过 HMR 只把该模块推给浏览器
   - 浏览器在不刷新页面的情况下更新界面

2. git commit
   - lint-staged 只对暂存文件运行 ESLint
   - 通过则提交成功；失败则提交被拒绝

3. git push 并发起合并请求
   - CI 全新环境执行：install → typecheck → lint → test → build
   - 任一步骤返回非零退出码，合并请求被标红、禁止合并

4. 合并后（或手动触发）发布
   - 构建产物、分析体积、上传 CDN、切换版本
```

这个例子说明：同一份质量问题（比如一个类型错误）可能在四个环节被拦住——编辑器、提交时、CI、构建时。越靠前成本越低，这就是“质量左移”。

#### 2.4 工程化关系：工具链不是直线而是闭环

```text
        ┌──────────────────────────────┐
        ↓                              │
  编写 → 本地反馈 → 提交门禁 → CI → 构建 → 发布
        ↑                              │
        └──────── 监控/错误追踪/复盘 ────┘
```

线上出现的问题通过监控回到开发环节，驱动规则与测试补充，工具链因此持续收紧。可观测性在 U58 展开。

常见误区：

> 本地 `pnpm build` 成功了，CI 一定也能成功。

本地成功依赖本机的 Node 版本、残留的 node_modules、未跟踪文件和全局缓存。CI 在干净环境、固定版本下运行，差异足以导致失败。判断 CI 必须以 CI 日志为准，这也是锁文件和版本固定的意义。

### 3. 模块化标准与模块图

#### 3.1 定义：模块

模块是拥有独立作用域、通过显式语法导入与导出的代码单元。现代 JavaScript 使用 ESM：

```js
// src/features/tickets/format.js
export function formatTicketTitle(raw) {
  return raw.trim().replace(/\s+/g, ' ');
}
```

```js
// src/features/tickets/list.js
import { formatTicketTitle } from './format.js';

const title = formatTicketTitle('  修复   登录问题 ');
console.log(title); // 修复 登录问题
```

ESM 的关键性质：

- 静态结构：`import`/`export` 在代码执行前就能被解析，依赖关系不靠运行时推断；
- 单例：同一模块在同一模块图中只执行一次，导出被各处共享；
- 严格模式：ESM 默认运行在严格模式下。

历史上还存在 CommonJS（`require`/`module.exports`）、AMD 等格式。Node 服务端与大量存量包使用 CommonJS，因此构建工具需要处理格式互操作，这正是 Vite 依赖预构建存在的原因之一。

#### 3.2 模块图是什么

构建工具从一个或多个入口出发，沿 import 边递归发现所有模块，形成有向图：

```text
index.html
  └─ src/main.tsx
       ├─ App.tsx
       │    ├─ features/tickets/list.tsx
       │    │    ├─ ./format.ts
       │    │    └─ shared/api/client.ts
       │    └─ shared/ui/Button.tsx
       └─ styles/global.css
```

图中的每个节点是一个模块，每条边是一个依赖。工具基于这张图完成：

- 判断哪些代码真正被用到（tree-shaking 的基础，U31）；
- 决定如何拆分成多个 chunk；
- 检测循环依赖；
- 在某个模块变化时，沿 HMR 边界判断失效范围（U30）。

概念伪代码：

```text
模块图 = 空图
待访问队列 = [入口模块]

当 待访问队列非空:
    模块 = 取出一个
    如果 模块已在图中: 继续
    解析模块的 import 语句，得到依赖列表
    把模块与依赖边加入图
    把新依赖放入待访问队列
```

#### 3.3 入口的特殊性

在 Vite 项目中，入口往往不是 JS 文件，而是 `index.html`：

```html
<!doctype html>
<html lang="zh-CN">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>工单系统</title>
  </head>
  <body>
    <div id="root"></div>
    <script type="module" src="/src/main.tsx"></script>
  </body>
</html>
```

构建工具解析 HTML 中的 `<script type="module">`，把它作为模块图的起点。CSS、图片等也通过 `import` 或 URL 引用成为图中的节点。

#### 3.4 工程化关系：模块边界即协作边界

模块划分不仅是技术问题，也是团队协作的接口：

- 模块通过导出声明“对外承诺什么”，内部实现可以自由调整；
- 稳定的模块边界让多人并行开发而不频繁冲突；
- 依赖方向应清晰（通用层不反向依赖业务层），否则图会退化成互相缠绕的结构。

TypeScript 能进一步在边界上检查类型，使接口承诺可被机器验证：

```ts
// shared/api/client.ts —— 边界上的类型承诺
export interface ApiClient {
  get<T>(path: string): Promise<T>;
}

export function createApiClient(baseUrl: string): ApiClient {
  return {
    async get<T>(path: string): Promise<T> {
      const res = await fetch(`${baseUrl}${path}`);
      if (!res.ok) throw new Error(`请求失败：${res.status}`);
      return (await res.json()) as T;
    },
  };
}
```

消费方一旦写错路径类型或返回结构，类型检查会在边界处报错，而不需要运行到那一步。

常见误区：

> 文件之间能 import 通，模块化就做好了。

“能跑通”只说明解析成功。循环依赖、跨层反向依赖、一个模块导出几百个符号、到处是深层相对路径（`../../../`），都是图结构腐化的信号。模块化的目标是降低耦合、让影响面可判断，而不只是让加载器找到文件。

### 4. 脚手架 create-vite 与项目模板

#### 4.1 定义：脚手架

脚手架是根据交互选项快速生成项目初始结构的工具。它替我们完成“每个新项目都要做一遍”的初始化工作。

使用 Vite 官方脚手架：

```bash
pnpm create vite@latest ticket-app
```

按提示选择框架与语言（例如 React + TypeScript），然后：

```bash
cd ticket-app
pnpm install
pnpm dev
```

非交互方式（适合脚本或演示）：

```bash
pnpm create vite@latest ticket-app -- --template react-ts
```

#### 4.2 脚手架到底生成了什么

一个典型模板包含：

```text
ticket-app/
├── index.html              # 构建入口 HTML
├── package.json            # 元数据与脚本
├── vite.config.ts          # Vite 配置
├── tsconfig.json           # TS 配置（可能还有分层配置）
├── public/                 # 原样拷贝的静态资源
└── src/
    ├── main.tsx            # 应用入口模块
    ├── App.tsx
    ├── App.css
    └── assets/             # 参与构建的静态资源
```

脚手架提供的是“可运行的最小起点”，它已经替我们：

- 约定了目录与入口；
- 配置好框架所需的最小插件；
- 给出了可用的脚本；
- 固定了一批经过验证的依赖版本。

#### 4.3 脚手架不负责什么

它不替团队做工程决策，以下内容仍需自己补齐：

- 代码规范与格式化（ESLint 9 flat config、Prettier，U32）；
- 提交门禁（Husky + lint-staged，U32）；
- 测试框架与用例（U23/U24）；
- 环境变量分层与安全策略（U33）；
- CI 工作流与分支保护（U56）；
- 业务目录结构与模块边界。

因此“脚手架生成的项目”不等于“企业级工程模板”。企业模板通常是在官方模板上沉淀团队规范后形成的内部版本。

#### 4.4 工程化关系：模板是规范的分发渠道

当团队把所有最佳实践固化进一个模板后，新项目就天然合规：

```text
新人入职 → 用内部模板创建项目 → 自动获得 Lint/门禁/测试/CI 骨架
```

模板也需要维护：依赖会过时、规则会演进。模板本身应当作为一个受版本管理的项目定期更新，而不是一次性产物。

常见误区：

> 脚手架选了什么模板，项目结构就一辈子不能动。

模板是起点不是牢笼。随着业务增长，目录应按业务边界演进。真正危险的是“从第一天起就过度设计五层架构”，或者“项目很大了仍然全部文件堆在一个目录”。这两种极端都应避免。

### 5. package.json 脚本体系

#### 5.1 定义：脚本体系

`package.json` 的 `scripts` 字段把工程任务命名化。团队成员记住的是语义化命令（dev、build、test），而不是每条命令的全部参数。

一个典型的脚本集合：

```json
{
  "name": "ticket-app",
  "version": "0.1.0",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "tsc --noEmit && vite build",
    "preview": "vite preview",
    "lint": "eslint .",
    "format": "prettier --write .",
    "test": "vitest run",
    "test:watch": "vitest",
    "typecheck": "tsc --noEmit",
    "prepare": "husky"
  }
}
```

执行方式：

```bash
pnpm dev
pnpm run build
pnpm test
```

`pnpm run <脚本名>` 会把 `node_modules/.bin` 加入 PATH，因此脚本里可以直接调用 `vite`、`eslint`，不需要全局安装，也不依赖个人机器的全局环境。

#### 5.2 脚本组合：串行、并行与失败传播

使用 `&&` 串行执行，前一步失败（非零退出码）则后续不再执行：

```bash
tsc --noEmit && vite build
```

含义：类型检查不过，就不允许产出构建结果。这是用退出码表达“门禁顺序”。

概念示例：

```text
pnpm build 执行过程:
  步骤 1: tsc --noEmit
    成功(退出码 0) → 继续
    失败(退出码 1) → 整条命令立即失败，vite build 不会执行
  步骤 2: vite build
    成功 → 产物写入 dist
```

生命周期脚本（如 `prepare`）会在特定时机被包管理器自动调用，常用于安装后初始化 Git 钩子。

#### 5.3 为什么脚本要“薄”

脚本应尽量薄：复杂逻辑放进独立脚本文件或工具配置，而不是塞进一行超长命令。

反例（难以阅读、跨平台脆弱）：

```bash
NODE_ENV=production TARGET=web tsc --noEmit && vite build && node scripts/report.js && cp -r dist /var/www/app
```

改进方向：

```json
{
  "scripts": {
    "build": "tsc --noEmit && vite build",
    "build:report": "node scripts/build-report.mjs",
    "deploy:local": "node scripts/deploy.mjs"
  }
}
```

把平台相关的操作收敛到 Node 脚本中，可以避免不同操作系统下命令不兼容的问题。

#### 5.4 工程化关系：脚本是所有自动化的入口

CI、提交门禁、新成员上手文档，最终都调用同一组脚本：

```text
开发者本地：pnpm lint
CI：        pnpm lint
README：    pnpm lint
```

三处使用同一命令，保证“本地检查什么，CI 就检查什么”，避免“我本地明明过了”的分歧。

常见误区：

> 命令执行报错但最后打印了“成功”，脚本就算成功。

自动化只认退出码。一条命令链只要其中某个工具返回非零，整体就是失败；反过来，如果脚本吞掉错误仍返回 0，CI 会误判通过。失败必须如实传播，不能用打印文案替代退出码。

### 6. 质量体系总览：质量左移与分层门禁

#### 6.1 定义：质量体系

质量体系是“检查手段 + 执行时机 + 阻断规则”的组合，它回答三个问题：检查什么、什么时候检查、不过怎么办。

分层结构：

| 层级 | 时机 | 典型检查 | 阻断方式 |
|---|---|---|---|
| 编辑器 | 编写/保存时 | 格式、类型提示、Lint 提示 | 不阻断，即时提示 |
| 提交门禁 | `git commit` | 暂存文件的 Lint/格式 | 拒绝提交 |
| CI 门禁 | 推送/合并请求 | 全量类型、Lint、测试、构建 | 禁止合并 |
| 发布检查 | 发布前 | 产物体积、敏感信息、冒烟测试 | 停止发布 |

#### 6.2 质量左移

缺陷发现得越早，修复成本越低：

```text
编码时发现   → 改几行，秒级
提交时发现   → 本地修复，分钟级
CI 发现      → 来回推送，十分钟级
线上发现     → 用户受损 + 回滚 + 复盘，小时甚至天级
```

“左移”就是把检查尽量往开发时间线的左侧推：编辑器即时反馈、保存自动格式化、提交前运行局部检查。

但左移有边界：

- 太重的本地检查会拖慢开发，应只对“变化的文件”做检查（lint-staged 的思路）；
- 全量测试、全量构建仍应放在 CI，因为需要干净环境与完整上下文；
- 左移不是取消 CI，而是让到达 CI 的代码大部分本来就合格。

#### 6.3 本地快检查与 CI 全检查的分工

```json
{
  "scripts": {
    "lint": "eslint .",
    "lint:staged": "eslint",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "test:related": "vitest related",
    "ci": "pnpm typecheck && pnpm lint && pnpm test && pnpm build"
  }
}
```

- 提交门禁只跑受影响文件：快，毫秒到秒级；
- CI 跑全量：慢但完整，是合并前的最终底线；
- 两者用同一套规则，只是范围不同，避免“本地标准”和“CI 标准”不一致。

#### 6.4 工程化关系：质量体系与测试金字塔

测试的分层（单元、组件、E2E）与门禁分层相互配合：底层检查数量多、速度快、执行频繁；顶层检查数量少、速度慢但最贴近真实用户路径。前端测试金字塔在 U23、U24 落地。

质量体系还包含“人的环节”：代码评审负责判断自动检查无法覆盖的设计与业务问题。自动化承担机械检查，评审才能把注意力放在真正需要人判断的地方。

常见误区：

> 门禁越严越好，最好每次提交跑全量测试和构建。

门禁的成本是每个开发者每天支付的。一次提交如果要等五分钟全量检查，开发节奏会被打断，团队最终会想办法绕过门禁。好的体系追求“频繁的检查足够轻、完整的检查不必每个人在本地等”，靠分层取得平衡。

### 7. 工程化成熟度与常见反模式

#### 7.1 定义：成熟度阶梯

可以粗略地把前端工程化能力分成四个台阶，用于评估现状而非追求一步到位：

```text
L0 手工：手动刷新、手动拷贝、靠口头约定
L1 可重复：脚手架 + 脚本体系，一条命令跑通
L2 有门禁：Lint/格式化 + 提交门禁 + CI 基础检查
L3 可度量：产物分析、测试覆盖、监控反馈驱动规则演进
```

新项目应至少从 L1 起步、很快达到 L2；L3 是随项目生命周期持续经营的结果，不是第一天配置出来的。

#### 7.2 常见反模式一：工具堆砌

症状：配置文件十几个、插件几十个，但没人能说清每个工具解决什么问题；升级一个依赖牵动一片。

判断方法：对每个工具追问：

```text
它拦住过什么问题？
删掉它会发生什么？
谁负责维护它的升级？
```

答不上来的工具，就是候选移除项。

#### 7.3 常见反模式二：门禁形同虚设

症状：规则一开就全员红灯，于是把关键规则关掉、CI 失败就重跑或跳过、提交用 `--no-verify` 绕过。

门禁失效比没有门禁更危险，因为团队以为自己受到保护。正确做法是：新规则先以警告模式灰度，再逐步收紧；历史问题用基线或分目录豁免，只要求新代码合规，而不是一次性放开或一次性关死。

#### 7.4 常见反模式三：文档与实际命令脱节

README 写着 `npm run serve`，实际脚本叫 `dev`；文档要求的环境变量根本没被读取。文档必须描述真实存在的脚本，并随脚本一起变更。验证方法很简单：让一名没接触过项目的同学严格按 README 操作一遍。

#### 7.5 工程化关系：成熟度服务于交付，而不是相反

所有工程化投入最终要回答一个问题：它是否让团队更稳定、更快、更可控地交付。工具是手段；当维护工具的成本超过它节省的成本时，应当简化而不是继续加码。

常见误区：

> 大厂的工程配置照抄过来，我们的工程化就先进了。

大厂配置服务于数千开发者、数万模块、多地域发布的场景，复杂度由其规模支撑。小团队照抄只会继承成本。理解每个配置背后的问题，再按自己的规模取舍，才是工程化思维。

- 全绿状态的终端记录。

#### 验收标准

- 脚本能被 pnpm 正确调用，无全局命令依赖；
- 失败会如实中断并返回非零退出码；
- 脚本文档与实际命令一致；
- `ci` 脚本可直接作为 CI 的唯一入口；
- 命名语义清晰，无超长难读的一行命令。
