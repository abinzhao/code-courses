# 59-全栈结业项目架构与实现

## 目标

完成本知识单元后，学员应能独立完成一个真实业务系统从需求到实现的全栈设计，讲清“为什么这样拆、边界在哪里、先做什么后做什么”，而不是拿到题目就开始写页面。

学员应能够：

1. 以“团队协作工单系统”为主线，完成需求拆解，编写带优先级与验收标准的用户故事。
2. 画出系统架构图，明确前端、后端、数据库、缓存与异步任务的模块边界与依赖方向。
3. 划分前后端职责，定义接口契约、错误规范与认证授权方式。
4. 设计数据模型、关系与索引，并说明关键查询与状态流转的落库方式。
5. 制定里程碑排期，把架构落到可执行、可验收的任务清单。
6. 完成认证授权、复杂状态、实时通知与异步任务等全栈实现要点，并用 DoD 收口质量。

本单元是第 59 单元。部署与可观测性分别见第 57、58 单元；上线验证、答辩与能力验收见第 60 单元。

## 详细的理论知识讲解和示例伪代码

### 1. 项目背景、需求拆解与用户故事

#### 1.1 项目背景

工单系统是团队协作的基础工具：成员提交问题、负责人分派与处理、相关人跟进讨论、管理者查看进展。它业务复杂度适中，天然覆盖全栈核心能力——权限、复杂表单、列表筛选、状态机、评论、通知、统计，是检验 30 周学习成果的理想主线。

角色设定：

```text
管理员 admin    管理成员、角色、工单全部操作、查看系统统计
处理人 agent    领取/分派/处理工单、填写处理结论、参与评论
报告人 reporter 创建工单、跟进自己提交的工单、评论与确认关闭
```

一个账号可以同时具备多个角色；最小实现允许每人一个角色，但模型要为多角色留有余地。

#### 1.2 从需求到用户故事

用户故事格式：作为〈角色〉，我希望〈能力〉，以便〈价值〉。每个故事必须附验收标准，否则不可进入开发。

```text
US-01（P0）作为报告人，我希望创建工单（标题、描述、优先级），
以便团队记录我反馈的问题。
验收标准：
 - 标题 1–120 字，描述必填，优先级枚举为 low/normal/high/urgent
 - 创建成功后跳转到工单详情，状态为 open，创建人自动加入关注人
 - 字段错误在字段旁明确提示，提交期间按钮防重复点击

US-02（P0）作为处理人，我希望按状态/优先级/指派人筛选并分页查看工单，
以便快速找到需要处理的任务。

US-03（P0）作为处理人，我希望变更工单状态并记录处理结论，
以便跟踪处理进度。

US-04（P0）作为相关人，我希望在工单详情中评论，
以便围绕同一问题协作。

US-05（P1）作为成员，我希望在工单被评论或状态变更时收到实时通知，
以便不用反复刷新页面。

US-06（P1）作为管理员，我希望查看工单量、平均处理时长等统计，
以便评估团队负载。
```

#### 1.3 MoSCoW 优先级与故事地图

```text
P0（必须有，缺了不能结业）：
 登录/登出、创建工单、工单列表（筛选+分页）、工单详情、
 状态流转、评论、权限校验、错误处理
P1（应该有）：
 实时通知、看板视图、关注/取关、统计仪表盘、@成员
P2（可以有）：
 富文本/附件、邮件摘要、SSO、批量操作、完整审计导出
```

需求拆解清单按“页面—功能—接口—数据—测试点”五列落表，每行可追溯到一个用户故事。

全栈关系：需求拆解是全栈工作的起点——用户故事决定前端页面与交互，也决定后端接口、数据字段与权限规则；本单元后续的架构图、接口契约与数据模型都是对这些故事的技术回应，每个故事编号将贯穿任务看板、提交记录与测试用例。

#### 1.4 常见误区

> 误区：把“想到的功能”都列进 P0，做到一半发现范围失控。

结业项目的核心是闭环与深度，不是功能数量。P0 必须少而完整，P1/P2 在 P0 收口后再按余量推进。

> 误区：用户故事只写“做什么”，不写验收标准。

没有验收标准，“做完”就没有客观判据，答辩时也无法证明功能真正成立。

### 2. 架构图与模块边界

#### 2.1 总体架构

```text
┌──────────────────────────────────────────────────────────┐
│ 浏览器：React SPA                                        │
│  页面层(route) → 特性模块(tickets/comments/auth)          │
│  → 数据访问层(TanStack Query / api client)              │
└───────────────┬──────────────────────────────────────────┘
                │ HTTPS（JSON / SSE）
┌───────────────▼──────────────────────────────────────────┐
│ Nginx：静态托管 + /api 反向代理 + TLS 终止               │
└───────────────┬──────────────────────────────────────────┘
                │ 127.0.0.1
┌───────────────▼──────────────────────────────────────────┐
│ Node.js API（Express，分层）                             │
│  routes → middlewares(auth/validate/error)               │
│  → services（业务逻辑/状态机）→ repositories(Prisma)     │
│  另有 SSE 通道与 worker（BullMQ 消费者）                 │
└───────┬───────────────────────────────┬──────────────────┘
        ▼                               ▼
 PostgreSQL（工单/用户/评论）      Redis（队列/缓存/会话可选）
```

#### 2.2 后端分层与依赖方向

```text
routes        只做参数接收与响应映射，不写业务规则
middlewares   认证、授权、输入校验、错误归一化
services      业务规则与事务边界，例如“状态流转 + 记录历史”
repositories  数据访问细节（Prisma 封装），可被替换与 mock
```

依赖只能从上到下：routes 依赖 services，services 依赖 repositories；反向依赖或跨层调用都会让改动不可控。事务边界放在 service 层，保证“状态更新、历史记录、通知入队”要么全部成功要么全部回退。

#### 2.3 前端模块边界

```text
src/
├── app/               路由与全局 Provider
├── features/
│   ├── auth/          登录、会话、权限钩子
│   ├── tickets/       列表、详情、表单、看板
│   ├── comments/      评论组件与接口
│   └── notifications/ 通知中心与 SSE 客户端
├── shared/
   ├── api/            fetch 封装、错误归一化
   ├── validation/     与后端共享的 Zod schema
   ├── components/     通用 UI
   └── lib/            工具函数
```

特性内聚：一个特性所需的组件、钩子、类型尽量放在自己的目录；只有被多个特性复用的代码才进入 `shared`，避免一开始就造“万能共享层”。

全栈关系：架构图把全栈各层一次性显形——前端特性模块、后端分层、数据库与队列各自承担什么、依赖朝哪个方向流动；它也是部署与监控设计的依据：哪些路径需要 Nginx 代理（第 57 单元）、哪些层需要埋点与探针（第 58 单元），都在这张图上确定。

#### 2.4 常见误区

> 误区：前端所有逻辑写在组件里，后端所有逻辑写在路由回调里。

业务规则散落各处会导致重复与不一致，例如状态流转规则在三个页面各写一遍。应下沉到 service 与共享 schema。

> 误区：画了漂亮架构图，代码里却没有对应目录。

架构图是代码结构的投影。模块边界必须能在仓库中逐目录指认，图与代码不一致等于没有架构。

### 3. 前后端职责与接口契约

#### 3.1 职责划分

```text
前端负责：交互与即时反馈、客户端校验、展示状态、路由组织、
          乐观更新与回退、可访问性
后端负责：认证授权、服务端最终校验、业务规则、事务一致性、
          数据持久化、通知与异步任务
双方共同：契约类型（共享 schema）、错误语义、字段命名约定
```

信任边界：前端代码运行在用户设备，可被改写。因此前端隐藏按钮只是体验，后端在每个写操作上必须重新鉴权与校验，二者缺一不可。

#### 3.2 接口契约示例

```text
GET  /api/tickets?status=open&priority=high&page=1&pageSize=20
 200 { items: Ticket[], total, page, pageSize }

POST /api/tickets
 请求 { title, description, priority, assigneeId? }
 201  Ticket
 400  { error: 'validation_error', details: [{ field, message }] }
 401  { error: 'unauthorized' }

GET    /api/tickets/:id
PATCH  /api/tickets/:id          { status?, priority?, assigneeId? }
POST   /api/tickets/:id/comments { content }
GET    /api/tickets/:id/comments?cursor=...
GET    /api/notifications/stream  （SSE）
```

统一错误响应规范：

```ts
type ApiError =
  | { error: 'validation_error'; details: Array<{ field: string; message: string }> }
  | { error: 'unauthorized' }
  | { error: 'forbidden' }
  | { error: 'not_found' }
  | { error: 'conflict'; message: string }
  | { error: 'internal_error' };
```

#### 3.3 前后端共享校验 schema

```ts
// shared/validation/ticket.ts
import { z } from 'zod';

export const ticketPriority = z.enum(['low', 'normal', 'high', 'urgent']);
export const ticketStatus = z.enum([
  'open', 'in_progress', 'pending', 'resolved', 'closed',
]);

export const createTicketSchema = z.object({
  title: z.string().trim().min(1).max(120),
  description: z.string().trim().min(1).max(5000),
  priority: ticketPriority.default('normal'),
  assigneeId: z.string().uuid().optional(),
});

export type CreateTicketInput = z.infer<typeof createTicketSchema>;
```

后端使用同一 schema：

```ts
import { createTicketSchema } from '@shared/validation/ticket';

app.post('/api/tickets', requireAuth, async (req, res, next) => {
  const parsed = createTicketSchema.safeParse(req.body);
  if (!parsed.success) {
    res.status(400).json({
      error: 'validation_error',
      details: parsed.error.issues.map((i) => ({
        field: i.path.join('.'),
        message: i.message,
      })),
    });
    return;
  }
  try {
    const ticket = await ticketService.create(req.user!.id, parsed.data);
    res.status(201).json(ticket);
  } catch (err) {
    next(err);
  }
});
```

前端 API 客户端与错误归一化：

```ts
export class ApiClientError extends Error {
  constructor(
    public readonly status: number,
    public readonly body: unknown,
  ) {
    super(`request failed with ${status}`);
  }
}

export async function api<T>(path: string, init?: RequestInit): Promise<T> {
  const res = await fetch(`/api${path}`, {
    credentials: 'include',
    headers: { 'Content-Type': 'application/json', ...init?.headers },
    ...init,
  });
  if (!res.ok) throw new ApiClientError(res.status, await res.json().catch(() => null));
  return res.json() as Promise<T>;
}
```

全栈关系：接口契约是前后端的协作接缝——前端据此组织 Query 与表单，后端据此实现路由与序列化，双方还共享同一份校验 schema；契约一旦确定，前端可用 mock 并行开发，部署时 Nginx 再把 `/api` 流量在同域下转发到后端。

#### 3.4 常见误区

> 误区：前端和后端各写一份校验，字段规则很快对不上。

应把 schema 作为单一真相源在两端共享；即便无法共享包，也要以文档形式锁定并在契约测试中校验。

> 误区：接口直接返回数据库实体，把内部字段、软删除标记都暴露出去。

应定义专门的响应序列化结构，只输出契约中声明的字段，避免数据结构变化直接波及前端。

### 4. 数据模型设计

#### 4.1 Prisma schema

```prisma
model User {
  id           String   @id @default(uuid())
  email        String   @unique
  name         String
  passwordHash String
  role         Role     @default(REPORTER)
  assigned     Ticket[] @relation("assignee")
  reported     Ticket[] @relation("reporter")
  comments     Comment[]
  watchers     Watch[]
  createdAt    DateTime @default(now())
}

enum Role {
  ADMIN
  AGENT
  REPORTER
}

model Ticket {
  id          String       @id @default(uuid())
  title       String
  description String
  status      TicketStatus @default(OPEN)
  priority    Priority     @default(NORMAL)
  reporterId  String
  reporter    User         @relation("reporter", fields: [reporterId], references: [id])
  assigneeId  String?
  assignee    User?        @relation("assignee", fields: [assigneeId], references: [id])
  comments    Comment[]
  history     TicketHistory[]
  watchers    Watch[]
  createdAt   DateTime     @default(now())
  updatedAt   DateTime     @updatedAt

  @@index([status, priority])
  @@index([assigneeId])
  @@index([createdAt])
}

enum TicketStatus {
  open
  in_progress
  pending
  resolved
  closed
}

enum Priority {
  low
  normal
  high
  urgent
}

model Comment {
  id        String   @id @default(uuid())
  ticketId  String
  ticket    Ticket   @relation(fields: [ticketId], references: [id], onDelete: Cascade)
  authorId  String
  author    User     @relation(fields: [authorId], references: [id])
  content   String
  createdAt DateTime @default(now())

  @@index([ticketId, createdAt])
}

model TicketHistory {
  id        String   @id @default(uuid())
  ticketId  String
  ticket    Ticket   @relation(fields: [ticketId], references: [id], onDelete: Cascade)
  actorId   String
  field     String
  fromValue String?
  toValue   String?
  createdAt DateTime @default(now())

  @@index([ticketId, createdAt])
}

model Watch {
  userId   String
  ticketId String
  user     User   @relation(fields: [userId], references: [id], onDelete: Cascade)
  ticket   Ticket @relation(fields: [ticketId], references: [id], onDelete: Cascade)

  @@id([userId, ticketId])
}
```

#### 4.2 索引与关系说明

```text
复合索引 (status, priority)：支撑列表最常用的筛选排序
assigneeId 索引：支撑“我的待办”查询
createdAt 索引：支撑按时间排序与统计报表
评论/历史 (ticketId, createdAt)：支撑详情页按时间游标分页
```

列表分页使用键集分页（cursor/keyset）比深页 OFFSET 更稳：

```ts
const items = await prisma.ticket.findMany({
  where: { status: 'open' },
  take: 21,
  orderBy: [{ createdAt: 'desc' }, { id: 'desc' }],
  ...(cursor ? { cursor: { id: cursor }, skip: 1 } : {}),
});
const nextCursor = items.length === 21 ? items[20].id : null;
```

#### 4.3 状态机

```text
        ┌────────────► in_progress ───────────┐
open ───┤                                   ├────► resolved ────► closed
        └────────────► pending ─────────────┘             ▲
                         │ 补充信息后回到 in_progress      │ 重新打开
                         └────────────────────────────────┘
```

合法流转以白名单描述，禁止直接信任前端传入的目标状态：

```ts
const transitions: Record<TicketStatus, TicketStatus[]> = {
  open: ['in_progress', 'pending', 'resolved', 'closed'],
  in_progress: ['pending', 'resolved', 'closed'],
  pending: ['in_progress', 'resolved', 'closed'],
  resolved: ['in_progress', 'closed'],
  closed: ['in_progress'],
};

export function canTransition(from: TicketStatus, to: TicketStatus): boolean {
  return transitions[from].includes(to);
}
```

全栈关系：数据模型是业务规则在存储层的投影——工单状态、角色关系、评论与历史都在这里落表；它向上决定接口能提供哪些字段、前端能展示什么，向下决定索引与查询性能，状态机白名单则保证跨前后端的状态语义一致。

#### 4.4 常见误区

> 误区：状态流转直接 PATCH 一个 status 字段，不校验合法性、不记历史。

非法跳转（如 open 直接 closed 又 reopen）会让数据失去业务含义，且无法追责。应在事务中校验白名单并写入 TicketHistory。

> 误区：给每个字段都建索引“以防万一”。

索引会拖慢写入、占用存储。应按实际查询路径设计，并通过查询计划验证索引被使用。

### 5. 里程碑排期与任务管理

#### 5.1 四周里程碑（以结业四周为例）

```text
M1 需求与架构（第 1 周）
 需求说明、用户故事与验收标准、架构图、数据模型、
 接口契约、脚手架与 CI 空骨架
 出口：契约评审通过，空应用可部署

M2 P0 核心闭环（第 2 周）
 登录登出、创建工单、列表筛选分页、详情、状态流转、评论
 出口：P0 路径手工可完整走通，含权限校验

M3 质量与 P1（第 3 周）
 单元/组件/接口/E2E 测试、SSE 通知、统计或看板其一、
 可观测性接入、性能初测
 出口：质量门禁全绿，关键路径有自动化保护

M4 打磨上线与答辩（第 3.5–4 周）
 安全检查、性能优化、可访问性、部署上线、文档与复盘
 出口：按 DoD 全部满足，完成第 60 单元答辩
```

#### 5.2 任务拆分示例

```text
工单创建（US-01）拆为：
 BE-1 schema 与错误映射（0.5d）
 BE-2 service + 事务 + 自动关注（0.5d）
 BE-3 路由鉴权与接口测试（0.5d）
 FE-1 表单与校验、提交态（0.5d）
 FE-2 成功跳转与 Query 失效（0.25d）
 FE-3 组件测试（0.25d）
```

每个任务必须满足：有唯一编号、关联故事、有验收标准、估时不超过 1 天，超过就继续拆。看板列使用“待办 / 进行中 / 待评审 / 已完成”，进行中的任务要受在制品数量限制。

#### 5.3 风险管理

```text
接口契约延迟 → 前端先按契约用 MSW mock 并行开发
范围蔓延   → 每周对照 MoSCoW，新增想法先进 P2 候选池
数据返工   → 早期就用迁移管理 schema，不手工改库
时间不足   → 保 P0 深度，砍 P1 数量，绝不留半成品
```

全栈关系：排期让全栈工作有序合龙——契约与模型先稳定，前端再并行开发，测试与部署在里程碑出口统一收口；每个出口都对应一个可演示、可验收的增量，风险（契约延迟、范围蔓延）也都有跨前后端的缓解方案。

#### 5.4 常见误区

> 误区：排期只写“第 2 周做工单模块”，没有任务级出口。

粗粒度计划无法早期发现偏差。应以可演示的小任务为单位，并为每个里程碑设置硬性出口条件。

### 6. 全栈实现要点

#### 6.1 认证与会话

采用服务端 Session：登录成功后生成随机会话标识，写入 HttpOnly、Secure、SameSite=Lax 的 Cookie，会话数据存服务端（Redis 或数据库）。这样前端无法读取令牌，XSS 无法直接窃取会话标识。

```ts
app.post('/api/auth/login', async (req, res) => {
  const { email, password } = loginSchema.parse(req.body);
  const user = await userService.findByEmail(email);
  if (!user || !(await verifyPassword(password, user.passwordHash))) {
    res.status(401).json({ error: 'unauthorized' });
    return;
  }
  const session = await sessionService.create(user.id);
  res.cookie('sid', session.id, {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'lax',
    maxAge: 60 * 60 * 24 * 7,
  });
  res.json({ user: userService.publicView(user) });
});
```

密码使用自适应哈希（如 Argon2id 或 bcrypt，合理成本因子），绝不存明文；登录失败响应保持一致，避免账号枚举。

#### 6.2 授权：RBAC 与资源级校验

```ts
const rolePermissions = {
  createTicket: ['ADMIN', 'AGENT', 'REPORTER'],
  assignTicket: ['ADMIN', 'AGENT'],
  closeAnyTicket: ['ADMIN'],
} as const;

export function requirePermission(action: keyof typeof rolePermissions) {
  return (req: Request, res: Response, next: NextFunction) => {
    const user = req.user;
    if (!user || !rolePermissions[action].includes(user.role)) {
      res.status(403).json({ error: 'forbidden' });
      return;
    }
    next();
  };
}
```

资源级规则不能只看角色：例如报告人只能评论自己相关的工单、只有管理员能关闭任意工单。service 层在操作前加载资源并校验归属，前端用同一权限规则控制按钮显隐作为体验补充。

#### 6.3 服务端状态获取与变更同步

```ts
export function useTickets(filters: TicketFilters) {
  return useQuery({
    queryKey: ['tickets', filters],
    queryFn: () => api<PagedTickets>(`/tickets?${toQuery(filters)}`),
    placeholderData: (prev) => prev,
  });
}

export function useCreateTicket() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (input: CreateTicketInput) => api('/tickets', {
      method: 'POST',
      body: JSON.stringify(input),
    }),
    onSuccess: () => qc.invalidateQueries({ queryKey: ['tickets'] }),
  });
}
```

状态归属原则：服务端数据交给 Query 缓存；可分享的筛选条件放 URL；纯 UI 状态放组件；只有真正跨页面共享的客户端状态才考虑上下文或 store。

#### 6.4 实时通知（SSE）

SSE 适用于“服务器单向推送到浏览器”的场景，比 WebSocket 简单且基于 HTTP，天然兼容 Nginx 代理与断线重连。

```ts
app.get('/api/notifications/stream', requireAuth, (req, res) => {
  res.writeHead(200, {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    Connection: 'keep-alive',
  });
  const unsubscribe = notificationBus.subscribe(req.user!.id, (payload) => {
    res.write(`event: notification\n`);
    res.write(`data: ${JSON.stringify(payload)}\n\n`);
  });
  req.on('close', unsubscribe);
});
```

Nginx 需要关闭缓冲并放宽读超时：

```nginx
location /api/notifications/stream {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Connection '';
    proxy_buffering off;
    proxy_read_timeout 3600s;
}
```

前端使用 EventSource：

```ts
const source = new EventSource('/api/notifications/stream', { withCredentials: true });
source.addEventListener('notification', (event) => {
  queryClient.invalidateQueries({ queryKey: ['notifications'] });
  console.log('new notification', JSON.parse(event.data));
});
```

#### 6.5 异步任务

状态变更后的通知与邮件不放在请求链路里同步执行：事务提交后把任务投递到 BullMQ，由 worker 异步消费，避免第三方接口拖慢用户操作。

```ts
await prisma.$transaction([
  prisma.ticket.update({ where: { id }, data: { status: next } }),
  prisma.ticketHistory.create({ data: historyData }),
]);
await notificationQueue.add('ticket-changed', {
  ticketId: id,
  actorId: user.id,
  type: 'status_changed',
});
```

worker 侧必须实现幂等消费与失败重试上限；重试无法解决的错误进入死信队列并告警。

全栈关系：本节要点正是全栈工程师的核心工作面——认证授权横跨 Cookie、前端路由守卫与服务端校验；服务端状态横跨 Query 缓存与数据库事务；SSE 与异步任务把“用户操作”和“系统副作用”解耦；每一处都需要前后端协同设计，而不是各写各的。

#### 6.6 常见误区

> 误区：JWT 存 localStorage，认为“前后端分离就必须这样”。

存储在 localStorage 的令牌可被 XSS 读取。优先使用 HttpOnly Cookie 的会话方案；若用 JWT，也应短时效并配合刷新令牌轮换。

> 误区：SSE 收不到消息，以为是前端问题，反复重连。

常见根因是 Nginx 默认开启 proxy_buffering 或读超时过短，需要在代理层显式配置。

### 7. 质量收口：测试、性能、安全与可访问性

#### 7.1 测试策略（测试金字塔）

```text
单元测试（多）：状态机 canTransition、权限规则、校验 schema、
               数据转换、service 业务逻辑（mock repository）
组件测试（中）：列表 loading/empty/error、表单校验、
               危险操作确认、无权限按钮状态
接口/集成测试：真实 Express + 测试数据库，覆盖鉴权与事务
E2E（少而关键）：登录→创建→筛选→处理→评论→关闭
```

状态机测试示例：

```ts
import { describe, expect, it } from 'vitest';
import { canTransition } from './ticket-state';

describe('canTransition', () => {

```

接口测试示例（Supertest + 测试库）：

```ts
const res = await request(app)
  .post('/api/tickets')
  .set('Cookie', await loginCookie('reporter'))
```

E2E 要求：断言用户可见结果，使用自动等待而非固定延时，保留失败截图与 trace；数据准备通过 API 或固定种子完成。

#### 7.2 性能收口

```text
前端：路由级代码分割、列表虚拟化或分页、图片优化、
     避免不必要重渲染；用 Lighthouse/Performance 记录 LCP、CLS、INP
后端：键集分页、N+1 查询检查（Prisma include 合理）、
     慢查询与 p95 延迟、异步化外部调用
证据：提交优化前后对比，所有结论带数字
```

检查 N+1 的概念示例——错误写法在循环内逐条查询，正确写法批量查询后在内存组装：

```ts
const tickets = await prisma.ticket.findMany({ where: filter, take: 20 });
const userIds = [...new Set(tickets.map((t) => t.assigneeId).filter(Boolean))];
const users = await prisma.user.findMany({ where: { id: { in: userIds } } });
const userMap = new Map(users.map((u) => [u.id, u.name]));
```

#### 7.3 安全收口

```text
XSS：React 默认转义；必须渲染 HTML 时先消毒；不拼接 innerHTML
CSRF：Cookie 使用 SameSite；敏感操作校验 CSRF 令牌或来源
越权：每个写操作服务端鉴权与资源归属校验
注入：参数化 ORM；不拼接 SQL；不拼接 shell 命令
依赖：锁定版本，定期审计，升级看来源与变更
信息：错误响应不暴露堆栈与系统细节，日志脱敏
上传：限制类型、大小，隔离存储域名（P1 时才开放）
```

安全响应头由 Nginx 或 Helmet 类中间件统一设置，例如 HSTS 需在 HTTPS 稳定运行后再启用并设置合理 max-age。

#### 7.4 可访问性收口

```text
语义化结构与标题层级；表单有可见 label；按钮可键盘操作；
焦点可见且弹窗有焦点陷阱与返回；图片有 alt；
错误提示通过 aria-describedby 关联，颜色不是唯一状态表达；
颜色对比度满足标准；详情页动态内容更新用 aria-live 告知读屏
```

全栈关系：质量收口必须在全栈两侧同时成立——前端有组件测试与性能、可访问性指标，后端有接口测试、慢查询与安全响应头，E2E 则跨越整个真实链路；任何一侧的短板都会成为用户可感知的风险，因此证据需要前后端对照。

#### 7.5 常见误区

> 误区：为覆盖率写无断言或只断言“不报错”的测试。

覆盖率只说明代码被执行，不说明被验证。关键测试必须断言具体行为；修 Bug 时先补能复现该 Bug 的回归测试。

> 误区：性能优化只有一句“做了懒加载”。

没有前后对比数字，无法证明优化有效，也无法判断是否引入回退。

### 8. 完成定义 DoD

#### 8.1 定义

完成定义（Definition of Done）是团队对“一个故事/整个项目真正做完”的统一、可检查的标准。没有 DoD，“开发完成”可能只意味着代码能跑，测试、文档、部署都还欠着。

#### 8.2 用户故事级 DoD

```text
[ ] 验收标准逐条满足并经演示确认
[ ] 服务端鉴权与校验完整，前端校验仅作体验
[ ] 新增逻辑有对应自动化测试，关键路径被覆盖
[ ] typecheck / lint / 相关测试通过
[ ] 接口契约与文档一致，响应不含多余内部字段
[ ] loading / empty / error 三态完整
[ ] 键盘可完成核心操作，无明显可访问性缺陷
[ ] 代码经过评审，意见已闭环
```

#### 8.3 项目级 DoD（结业标准）

```text
功能：全部 P0 闭环，P1 至少完成一项且可用
测试：单元、组件、接口、E2E 分层齐备，核心路径自动化
性能：关键指标有测量、有优化、有前后对比
安全：安全清单逐项检查，无真实密钥，越权被拒绝
部署：通过 HTTPS 公网可访问，可回滚（第 57 单元）
可观测：健康检查、指标、日志、错误追踪、告警可用（第 58 单元）
文档：需求、架构、接口、测试报告、复盘齐全
```

DoD 检查表必须在任务关闭时逐项勾选；任何一项不满足，状态只能是“未完成”，不得靠口头解释放行。

全栈关系：DoD 是全栈交付的统一裁判——故事级标准检查前后端协同的最小质量，项目级标准把测试、性能、安全、部署（第 57 单元）与可观测性（第 58 单元）全部纳入；它保证“完成”由客观证据定义，而不是由前端或后端任何一方单方面宣布。

#### 8.4 常见误区

> 误区：答辩前一晚把 DoD 全部打勾，实际并未验证。

DoD 的每项都应能现场出示证据（命令输出、面板、文档链接）。它是过程工具，不是答辩道具。

学员需在 25 分钟内完成：

1. 用架构图讲清模块边界、依赖方向与一次请求的完整时序。
2. 展示用户故事地图、P0 范围与验收标准，说明取舍理由。
3. 现场走通“登录 → 创建工单 → 筛选定位 → 处理与评论 → 关闭”全路径。
4. 展示数据模型、索引与状态机，解释一条历史记录如何产生。
5. 运行质量门禁与一条 E2E，展示分层测试结果。
6. 说明性能、安全与可访问性的证据与至少一项优化。
7. 对照 DoD 逐项说明满足情况。

### 强制不通过条件

出现以下任一情况，本次验收不通过：

1. P0 核心路径无法完整走通或存在阻断性缺陷。
2. 服务端缺少鉴权或资源级授权，越权请求成功。
3. 架构图、接口契约与实际代码三者明显不一致。
4. 状态流转无白名单校验或无历史记录，业务数据不可追溯。
5. 没有任何自动化测试，或关键 E2E 长期失败被忽略。
6. 提交真实数据库口令、密钥或用户隐私数据。
7. 存在无法闭环的“半成品”功能且未在范围中明确标注与说明。
