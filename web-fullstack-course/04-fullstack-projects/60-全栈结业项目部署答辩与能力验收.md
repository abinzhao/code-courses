# 60-全栈结业项目部署答辩与能力验收

## 目标

完成本知识单元后，学员应能把第 59 单元完成的工单系统真正“交付”出去：完成上线验证、组织演示与答辩、对照能力矩阵看清自己的水平，并以复盘驱动后续成长，而不是项目一上线就宣告结束。

学员应能够：

1. 执行发布前检查与上线后冒烟验证，基于证据做出“放行、回滚或观察”的发布决策。
2. 设计并完成一次结构清晰、风险可控的现场演示，使观众不依赖口头解释也能看懂系统。
3. 回答设计权衡、调试排查、安全、性能与工程协作五类答辩问题，用事实与取舍支撑观点。
4. 对照全栈工程师能力矩阵进行自评与他评，识别强项与短板，区分“知道”与“能独立做到”。
5. 提交完整的最终交付清单，保证他人可以接手运行与维护系统。
6. 完成项目复盘，输出可执行的个人成长计划，并理解综合评分的构成与通过条件。

本单元是 30 周课程的最后一个单元，前置内容为第 57 单元（部署与 HTTPS）、第 58 单元（可观测性）、第 59 单元（结业项目架构与实现）。

## 详细的理论知识讲解和示例伪代码

### 1. 上线验证与发布决策

#### 1.1 定义

上线验证是在发布动作完成后、正式宣告成功前，用一组事先定义的检查确认系统在真实环境中满足预期。它包含三层：部署验证（进程、端口、证书）、冒烟测试（最关键业务路径）、观察期（指标与错误追踪在一定时间窗内无异常）。

发布决策只有三类结论：

```text
放行      冒烟全部通过，观察期指标平稳
回滚      关键检查失败，切回上一版本（第 57 单元机制）
带风险观察 非关键问题，明确监控项、观察时长与负责人
```

全栈关系：上线验证把前三单元成果串成一条“可发布”证据链——部署来自 45，监测来自 46，被验证的系统来自 47。

#### 1.2 发布检查脚本与冒烟清单

```bash
#!/usr/bin/env bash
set -euo pipefail

BASE="https://app.example.com"

check() {
  local name="$1" url="$2" expect="$3"
  local code
  code="$(curl -s -o /dev/null -w '%{http_code}' "$url")"
  if [[ "$code" != "$expect" ]]; then
    echo "FAIL $name expected=$expect got=$code" >&2
    exit 1
  fi
  echo "PASS $name"
}

check "home" "$BASE/" 200
check "health" "$BASE/api/health/ready" 200
check "http_redirect" "http://app.example.com/" 301

curl -fsS "$BASE/api/metrics" | grep -q ticket_http_requests_total
echo "smoke finished"
```

人工冒烟清单（必须用演示账号走真实业务路径）：

```text
[ ] 登录 / 登出正常，未登录访问受保护页面被拦截
[ ] 创建工单成功，详情页数据与提交一致
[ ] 列表筛选、分页、刷新结果正确
[ ] 状态合法流转成功，历史记录新增
[ ] 评论发布后双方可见
[ ] 通知（SSE）至少收到一条
[ ] 权限：低权限账号看不到越权入口，直接调接口返回 403
```

观察期判定：

```text
观察时长：发布后至少 30 分钟（高峰发布适当延长）
检查项：5xx 比例、p95 延迟、进程重启次数、错误追踪新增 issue
对照基线：与发布前同时段指标比较，而非只看绝对值
```

#### 1.3 Nginx 侧的发布期保护

灰度或单机场景可用维护页与连接排空降低发布影响：

```nginx
location / {
    if (-f /opt/ticket-app/shared/MAINTENANCE) {
        return 503;
    }
    try_files $uri $uri/ /index.html;
}

error_page 503 @maintenance;
location @maintenance {
    root /opt/ticket-app/maintenance;
    rewrite ^(.*)$ /index.html break;
}
```

配合 systemd 优雅停机（应用收到 SIGTERM 后停止接新请求、处理完存量再退出），可避免发布瞬间用户看到连接被重置。

#### 1.4 常见误区

> 误区：发布后只点一下首页能打开就宣布成功。

首页正常不代表登录、创建、支付类写路径正常。冒烟必须覆盖最关键的业务动作，并且观察错误率而不仅是连通性。

> 误区：发现非关键小问题也立即回滚，或发现明显故障却“再等等看”。

决策应提前定义标准：关键路径失败立即回滚；非关键问题进入带风险观察并设定明确的观察期限与触发条件，不能凭临场情绪。

### 2. 演示流程设计

#### 2.1 定义

工程演示是在限定时间内，用真实运行的系统向观众证明价值与完成度。好演示遵循“一个主线故事、一条黄金路径、一次故障兜底”的结构，按观众能理解的业务顺序推进，而不是按代码目录念功能。

全栈关系：演示本身也是一次“生产级验证”——它要求系统稳定、数据可控、网络与回退方案齐备，倒逼工程质量。

#### 2.2 演示脚本示例

```text
总时长 10 分钟（答辩另计）
0:00–1:00 背景：一个团队如何用工单系统协作（一句话价值）
1:00–2:30 以报告人身份创建工单（展示表单校验与防重复提交）
2:30–4:30 切换处理人：筛选定位 → 认领 → 处理 → 评论
4:30–6:00 状态流转、通知实时到达、历史轨迹可追溯
6:00–7:30 管理员视角：统计/看板展示团队负载
7:30–9:00 质量证据：测试、监控面板、错误追踪（证明不是“玩具”）
9:00–10:00 总结取舍：做了什么、没做什么、下一步是什么
```

演示数据必须提前种好且可识别：标题统一前缀如“演示-”，保证观众跟得上；准备“重置演示数据”的脚本，答辩多场次间可快速恢复。

#### 2.3 演示的工程兜底

```bash
# 发布前确认现场可用
curl -fsS https://app.example.com/api/health/ready
# 准备录屏作为网络故障时的兜底播放
# 准备第二个浏览器窗口已登录，避免现场登录失败
# 手机热点作为网络备份
```

演示时操作要慢：每一步留出观众看清屏幕的时间，关键结果用鼠标指向再讲解；避免边操作边大幅跳转页面。

#### 2.4 常见误区

> 误区：演示全程念稿、堆砌全部功能，观众记不住任何重点。

演示要讲一条完整业务故事，P1/P2 功能一句带过或放在答疑；少即是多。

> 误区：只用“快乐路径”，对异常与边界绝口不提。

主动展示一个错误态或一次降级（如无权限提示、表单校验），反而更能证明工程成熟度。

### 3. 答辩问题库：设计权衡

#### 3.1 定义

设计权衡类问题考察的是“你为什么这样选，而不是那样选”，答案必须包含候选方案、取舍维度（复杂度、成本、团队规模、演进）和适用边界，而不是背定义。

全栈关系：每个全栈决策（认证方式、状态归属、实时方案、单体与拆分）都应能回溯到第 59 单元的架构与第 57、58 单元的工程约束。

#### 3.2 问题与答题框架

```text
Q1 为什么认证用 Session Cookie 而不是把 JWT 存 localStorage？
 框架：威胁模型（XSS/CSRF）→ 两种方案的风险 → 本项目形态
 （服务端渲染为主、同域 API）→ 选择 HttpOnly Cookie + SameSite
 → 边界：纯跨域/微服务多端场景会重新评估 JWT + 刷新令牌

Q2 哪些状态放组件、URL、Query 缓存、全局 store？
 框架：可分享性（URL）、持久化与来源（Query）、
 局部临时（组件）、跨页面客户端共享（store）四问

Q3 通知为什么选 SSE 而不是 WebSocket / 轮询？
 框架：方向性（服务器单向）→ 协议成本（HTTP、自动重连）
 → 代理兼容 → 边界：双向高频交互才需要 WebSocket

Q4 为什么单体起步，而不是一开始微服务化？
 框架：团队规模、部署与运维成本、领域是否稳定；
 先在单体中用清晰模块边界保留未来拆分可能
```

其余高频问题：为什么选 Prisma 而不是手写 SQL；为什么用 BullMQ 异步化；为什么前端做特性目录分层；为什么用键集分页；为什么共享 Zod schema。

一个“决策记录（ADR）”式答案模板：

```text
背景/约束：
考虑过的方案：
选择：
理由（对约束的响应）：
代价与风险：
什么条件下会重新评估：
```

#### 3.3 常见误区

> 误区：回答“因为业界都这么用 / 这个技术更先进”。

没有结合自身约束的选择不叫决策。必须讲代价，例如“选择 X 牺牲了 A，换来 B，在我们当前规模下值得”。

### 4. 答辩问题库：调试、安全、性能与工程协作

#### 4.1 定义

这四类问题考察实战：调试看证据链与假设验证，安全看威胁面与纵深防御，性能看测量与瓶颈定位，工程协作看流程、契约与沟通。评分关注“怎么做”而不是“知道什么名词”。

全栈关系：这四类问题正好对应前三个单元的实战产出——调试引用第 58 单元的指标、日志与请求 ID，安全引用第 59 单元的服务端鉴权与纵深防御，性能引用前后端两侧的测量数据，工程协作引用接口契约、CI 门禁与分支流程；回答时必须能出示项目中的真实证据，而不是泛泛而谈。

#### 4.2 调试类

```text
Q：你遇到最难定位的 Bug 是什么？
期望结构：现象 → 影响 → 复现条件 → 提出的假设与排除过程
 → 关键证据（日志/trace/最小复现）→ 根因 → 修复 → 回归测试
常见追问：怎么确定不是数据库的问题？如果无法复现怎么办？
```

现场可用的证据命令：

```bash
sudo journalctl -u ticket-api --since "1 hour ago" -p err --no-pager
curl -s https://app.example.com/api/metrics | grep -E 'restart|requests_total'
# 用请求 ID 串联：grep <requestId> 应用日志与 Nginx 日志
```

#### 4.3 安全类

```text
Q：报告人能不能把自己的工单改成任意状态 / 看到别人的工单？
期望：前端隐藏只是体验；后端在 service 层做角色 + 资源归属双重校验；
 给出越权请求返回 403 的实测证据
Q：如何防 XSS？Cookie 被盗怎么办？依赖出漏洞怎么办？
期望：默认转义 + 必要时消毒；HttpOnly/Secure/SameSite；
 依赖锁定 + 审计 + 及时升级；纵深防御，任何单层都不是全部
```

安全自检要点（TypeScript 侧的最小检查示例）：

```ts
function assertCanAccessTicket(user: SessionUser, ticket: Ticket) {
  const isOwner = ticket.reporterId === user.id;
  const isAssignee = ticket.assigneeId === user.id;
  if (user.role !== 'ADMIN' && !isOwner && !isAssignee) {
    throw new ForbiddenError('forbidden');
  }
}
```

#### 4.4 性能类

```text
Q：用户说慢，你怎么定位？
期望：先分清前端/网络/后端 → 前端看 LCP/INP/长任务，
 后端看分位数与 trace 落在哪一跳，数据库看慢查询与计划
Q：做过什么优化？前后数据？
期望：具体手段（分割/索引/异步化/批量查询）+ 前后数字 + 无回退证明
```

#### 4.5 工程协作类

```text
Q：后端接口没好，前端怎么办？
期望：按契约用 MSW 并行开发，契约变更走评审
Q：代码评审意见不一致怎么处理？
期望：对事不对人，用事实/数据/文档讨论，必要时记录 ADR
Q：如何保证多人开发不互相踩？
期望：分支策略、小步提交、CI 门禁、接口与目录约定
```

#### 4.6 常见误区

> 误区：调试问题答“我重启了一下就好了”。

没有根因与回归保护的恢复不算解决。答辩要讲方法与证据链。

> 误区：安全问题只答“用了 HTTPS”。

HTTPS 解决传输加密，不解决越权、XSS、注入；需展示分层防御。

### 5. 全栈工程师能力矩阵

#### 5.1 定义

能力矩阵把“全栈工程师应具备的能力”拆成若干维度，每个维度用可观察行为划分等级，用于自评、导师评与成长定位。关键是行为化描述：能讲清概念、能在指导下完成、能独立交付、能指导他人，是四个不同层级。

全栈关系：矩阵的每个维度对应课程的一组单元，可用于回看 30 周知识地图并定位缺口。

#### 5.2 矩阵示例

```text
维度                     L1 入门     L2 能独立      L3 熟练        L4 能带人
前端开发                能写静态页  组件化+状态   架构与性能优化  制定前端规范
后端开发                能写路由    分层 API+DB   复杂业务/事务   设计服务边界
数据建模与 SQL          会基础查询  建模+迁移     索引/查询优化   数据治理
测试与质量              会写用例    分层自动化    质量门禁/策略   建设质量体系
安全                    知道风险    落地基础防护  威胁建模/加固   安全评审
部署与运维              能按手册做  独立部署回滚  可观测/自动化   平台化设计
工程协作                用 Git 协作 评审/契约沟通 推动流程改进    跨团队协作
调试排障                会查日志    证据链定位    复杂系统排障    建立排障体系
```

自评需附证据，不允许只打等级：

```ts
type SkillLevel = 0 | 1 | 2 | 3 | 4;

interface SkillAssessment {
  dimension: string;
  level: SkillLevel;
  evidence: string[];          // 对应项目或单元中的具体产出
  nextAction: string;          // 提升一级所需的可执行动作
}

const example: SkillAssessment = {
  dimension: '部署与运维',
  level: 2,
  evidence: ['独立完成工单系统 HTTPS 上线', '部署脚本失败自动回滚演练通过'],
  nextAction: '为系统补齐 Prometheus 告警并完成一次故障演练复盘',
};
```

#### 5.3 常见误区

> 误区：每个维度都给自己 L3/L4。

脱离证据的自评没有可信度。L2 的标准是“独立交付过”，没有真实产出支撑不应越级。

> 误区：把“学过/看过”当成“会”。

能力看行为产出。看懂文档是 L0–L1，能在无指导下交付才到 L2。

### 6. 最终交付清单

#### 6.1 定义

最终交付清单是项目交接的最小完整集合，使一名不了解背景的工程师能够运行系统、理解设计、定位问题、继续迭代。它与 DoD 的区别：DoD 判断“是否做完”，交付清单回答“交什么东西”。

全栈关系：交付清单横跨全栈所有环节——既要包含前端运行与构建方式，也要包含后端服务、数据库迁移、环境变量、部署脚本与监控入口；它本质上是把第 45 至 47 单元的成果整理成“他人可独立接手”的形态，缺了任一层，系统都无法被真正维护。

#### 6.2 清单内容

```text
1. 代码：前端、后端、worker、共享包；README 含本地运行步骤
2. 数据：Prisma 迁移、种子脚本、ER 图
3. 文档：需求、架构、接口契约、测试报告、性能分析、复盘
4. 部署：Nginx 配置、systemd/pm2 配置、部署与回滚脚本
5. 可观测：指标清单、日志规范、告警规则、runbook
6. 环境：.env.example（仅键名与说明），环境准备步骤
7. 演示：演示脚本、演示账号说明、录屏
8. 质量证据：门禁命令输出、E2E 结果、安全与可访问性检查
```

仓库健康度快速检查：

```bash
git status
test -f README.md && grep -q "运行" README.md
test -f .env.example
! git ls-files | grep -qE '(^|/)\.env$'
npm run typecheck && npm run lint
npm run test -- --run
npm run build
```

#### 6.3 常见误区

> 误区：只交代码仓库，认为“代码即文档”。

接手者仍需要运行步骤、环境变量含义、部署方式与排障入口。代码之外的交付物决定可维护性。

> 误区：把 node_modules、dist、.env、演示数据库文件一起打包。

应通过 `.gitignore` 与交付脚本排除可重建产物和敏感文件；仓库克隆后应能凭命令恢复一切。

### 7. 复盘与成长计划

#### 7.1 定义

复盘是在项目结束后，对照最初目标，客观分析哪些做得好、哪些出了问题、为什么，并提炼可复用的经验。它关注流程与系统改进，而非追究个人。成长计划把复盘结论转成未来 1–3 个月可执行、可检验的行动。

全栈关系：复盘是把一次项目经验固化为长期能力的关键步骤，决定 30 周课程的学习能否迁移到后续工作。

#### 7.2 KPT 复盘示例

```text
Keep（保持）：
 - 契约先行 + MSW 让前后端几乎没有阻塞
 - 里程碑出口检查使第二周偏差被及时发现
Problem（问题）：
 - P1 范围一度膨胀，靠砍项才保住 P0
 - SSE 问题在 Nginx 层排查耗时过长
Try（尝试）：
 - 下个项目开列“候选池”，新增想法一律先进池
 - 提前写部署架构的排障清单
```

#### 7.3 成长计划模板

```text
目标（SMART）：
 三个月内能独立设计并交付含异步任务与可观测能力的后端服务
差距（对照能力矩阵）：
 查询优化与告警策略处于 L1
行动：
 每周完成一次慢查询分析练习（4 周）
 为个人项目补一套指标+告警并做一次演练（6 周）
 精读一本数据库/系统设计材料并输出笔记（持续）
检验方式：
 能在限时排障演练中独立定位、能在面试中讲清取舍
```

用 TypeScript 表达目标追踪的最小结构：

```ts
interface GrowthGoal {
  title: string;
  deadline: string;
  actions: Array<{ item: string; done: boolean }>;
  verify: string;
}

const goal: GrowthGoal = {
  title: '后端复杂交付能力达到 L3',
  deadline: '三个月内',
  actions: [
    { item: '完成四次慢查询分析', done: false },
    { item: '个人项目告警演练', done: false },
  ],
  verify: '限时排障演练通过',
};
```

#### 7.4 常见误区

> 误区：复盘写成“时间不够，下次努力”。

不分析机制就无法改进。要落到具体流程动作，例如“增加范围评审”而不是“提高效率”。

> 误区：成长计划列了十几项，没有期限和检验方式。

计划要少而可执行，带截止时间与可验证的产出，否则只是愿望清单。

### 8. 综合评分标准

#### 8.1 定义

综合评分是对结业项目全过程的最终评价，覆盖功能、架构、工程质量、上线交付与答辩表达，强调证据与独立完成。它把前三单元的验收结果汇总，并补上交付与答辩维度。

全栈关系：评分不是目的，而是能力信号；每个评分维度都映射到课程目标与能力矩阵。

#### 8.2 评分构成

```text
综合总分 100 分，70 分通过；另设强制不通过条件（一票否决）
 业务完整度        15  P0 闭环、关键流程可用
 架构与设计        15  模块边界、取舍合理、图码一致
 前端实现          12  组件/状态/路由/可访问性
 后端与数据        13  分层、数据模型、事务与权限
 测试质量          12  金字塔分层、核心路径保护
 性能与安全        10  有证据的优化、无高危风险
 部署与可观测性    10  HTTPS 上线、可回滚、监控告警
 答辩与表达        8   讲得清设计、调试与协作
 文档与交付完整度  5   接手友好、清单齐全
```

等级参考：

```text
90–100 优秀：P0 闭环且 P1 有亮点，能讲清代价，工程证据完整
75–89  良好：P0 扎实，少量非关键短板
70–74  通过：P0 完整可用，短板有明确改进计划
70 以下 不通过：P0 未闭环或触发强制条件
```

#### 8.3 与各单元验收的关系

```text
第 57 单元验收（部署）      → 支撑“部署与可观测性”中的部署部分
第 58 单元验收（可观测）    → 支撑监控告警部分
第 59 单元验收（设计实现）  → 支撑业务、架构、前后端、测试、性能安全
本单元（48）               → 负责上线验证、演示答辩、交付完整度
```

答辩现场记录表示例：

```text
学员：              评委：
演示完成度（黄金路径是否走通）：
答辩问题（记录问题编号与回答质量）：
亮点：
风险/追问暴露的问题：
各维度得分：
综合结论：
```

#### 8.4 常见误区

> 误区：只凭演示效果给分，忽略代码与工程证据。

演示可能掩盖结构问题。评分须结合代码、测试、部署与文档证据，现场可要求学员出示任意一项。

> 误区：认为“功能越多分越高”。

范围失控的半成品不加分；闭环深度、工程质量与清晰取舍才是评分核心。

## 课后题

1. 发布决策有哪三类？分别对应什么判定标准？请说明“带风险观察”必须明确哪些要素。
2. 场景分析：工单系统发布后首页正常，但创建工单接口 5xx 比例升至 6%。你会如何决策并执行？
3. 为什么演示要围绕一条业务主线，而不是按功能清单逐个展示？请为工单系统写一份 10 分钟演示脚本大纲。
4. 场景分析：演示现场网络中断或登录失败。说明至少三种兜底方案，以及为什么这些兜底本身就是工程能力。
5. 用 ADR 框架回答：为什么本项目认证选择 HttpOnly Cookie 的 Session 方案？什么条件下你会改用 JWT？
6. 场景分析：答辩时评委问“报告人能否直接调接口关闭任意工单”，你如何用设计与实测证据回答？
7. 能力矩阵中 L1 到 L2、L2 到 L3 的本质跨越是什么？为什么“学过”不能直接评为 L2？
8. 最终交付清单与 DoD 有何区别？只交代码仓库为什么不足以让他人接手？
9. 场景分析：复盘发现项目后期靠连续加班才上线。请用机制化思路分析问题，并给出下次可执行的预防动作。
10. 综合评分中为什么“功能数量”不占主导？请结合范围管理与闭环深度解释。

## 实践练习题

### 练习 1：发布检查与冒烟自动化

#### 任务

为结业项目建立可重复执行的发布检查脚本与冒烟清单，并完成一次真实发布决策记录。

#### 步骤约束

1. 编写脚本覆盖跳转、首页、健康检查与指标端点，失败返回非零退出码。
2. 制定业务冒烟清单，至少 7 项，使用演示账号走真实路径。
3. 发布后设置不少于 30 分钟观察期，记录错误率、p95 与重启次数。
4. 输出一份发布决策记录（放行/回滚/观察及理由）。
5. 演练一次关键检查失败时的回滚动作。
6. 所有记录使用脱敏后的真实输出。

#### 提交物

- 发布检查脚本；
- 冒烟清单与执行记录；
- 观察期指标截图或数据；
- 发布决策记录与一次回滚演练记录。

#### 验收标准

- 脚本能正确区分通过与失败；
- 冒烟覆盖写路径与权限场景；
- 发布结论有证据支撑；
- 回滚在 10 分钟内完成并验证恢复。

### 练习 2：现场演示与答辩准备

#### 任务

完成一次 10 分钟正式演示彩排，并针对五类答辩问题建立带证据的问答卡。

#### 步骤约束

1. 编写演示脚本，明确每段时间、操作与讲解重点。
2. 准备演示数据与一键重置脚本，完成至少两次完整彩排。
3. 配齐网络、登录、录屏三类兜底。
4. 每类答辩问题至少准备 3 张问答卡，按“结论—理由—证据—边界”组织。
5. 组织同伴模拟答辩，记录被问住的问题并补强。
6. 主动设计一个展示错误态或降级处理的环节。

#### 提交物

- 演示脚本；
- 彩排记录与演示录屏；
- 五类问答卡；
- 模拟答辩问题与改进清单。

#### 验收标准

- 演示在 10 分钟内完成且主线清晰；
- 兜底方案经过实测可用；
- 问答卡均有项目证据支撑；
- 模拟答辩中暴露的问题已闭环。

### 练习 3：能力自评、复盘与成长计划

#### 任务

对照能力矩阵完成带证据的自评，输出项目复盘与三个月成长计划，并整理最终交付包。

#### 步骤约束

1. 八个维度逐项评级，每项附至少两条证据与一条提升动作。
2. 使用 KPT 法完成复盘，机制化分析至少两个问题。
3. 制定不超过 5 项的成长行动，带期限与检验方式。
4. 按最终交付清单逐项核对，排除 `.env`、依赖目录等不可交付内容。
5. 邀请导师或同伴对自评进行他评，记录差异与理由。
6. 在 README 中补充接手入口与排障指引。

#### 提交物

- 能力自评表（含证据与他评对照）；
- KPT 复盘文档；
- 三个月成长计划；
- 完整最终交付包。

#### 验收标准

- 评级与证据匹配，自评与他评差异有讨论；
- 复盘结论可执行、非口号；
- 成长计划可检验；
- 交付包可由他人按文档独立运行。

## 阶段验收作业

### 作业名称

全栈结业项目上线答辩与综合能力验收

### 作业场景

这是 30 周课程的最终关口。你的工单系统已通过第 59 单元的设计与代码验收，现在需要公网上线、现场演示、回答评委追问，并证明你具备“独立交付一个真实全栈系统”的综合能力。评委会结合线上系统、代码、证据材料与现场表现给出最终成绩。

### 提交物

```text
final-delivery/
├── 系统访问信息说明（地址、演示账号，不含真实口令）
├── 发布检查与冒烟记录
├── 演示脚本与录屏
├── 答辩问答卡
├── 能力矩阵自评与他评表
├── 项目复盘与成长计划
├── 完整代码仓库访问方式
└── 最终交付清单核对表
```

### 演示步骤

答辩总时长 35 分钟：

1. 系统上线确认（3 分钟）：出示 HTTPS、证书、健康检查与观察期指标。
2. 正式演示（10 分钟）：按业务主线走通黄金路径，含一个错误态展示。
3. 质量证据（5 分钟）：测试、监控、错误追踪、性能与安全证据。
4. 评委提问（12 分钟）：从五类问题库中随机抽取并允许追问。
5. 复盘陈述（5 分钟）：讲清取舍、最大教训与成长计划。

评委可临时要求：现场制造一个小故障让学员处理、要求展示任意评分项证据、或更改演示路径，以验证真实性。

### 评分标准（100 分）

| 维度 | 分值 | 满分要求 |
|---|---:|---|
| 业务完整度 | 15 | P0 全路径闭环，验收标准逐条满足 |
| 架构与设计 | 15 | 边界清晰、取舍有据、图码一致 |
| 前端实现 | 12 | 组件与状态合理，三态完整，可访问性达标 |
| 后端与数据 | 13 | 分层、模型、事务、资源级授权正确 |
| 测试质量 | 12 | 金字塔分层，核心风险自动化覆盖且稳定 |
| 性能与安全 | 10 | 有证据的优化，无越权/注入/泄密高危问题 |
| 部署与可观测性 | 10 | HTTPS 上线、可回滚，监控告警真正生效 |
| 答辩与表达 | 8 | 讲得清设计权衡与调试过程，承认边界 |
| 文档与交付 | 5 | 接手友好，交付清单完整 |

等级线：90+ 优秀，75–89 良好，70–74 通过，低于 70 不通过。

### 强制不通过条件

出现以下任一情况，综合验收不通过：

1. P0 核心路径在现场或线上无法走通。
2. 系统未通过 HTTPS 上线，或发布失败后无法回滚恢复。
3. 存在可直接利用的越权访问，且现场实测成功。
4. 项目无法由他人按文档运行，或代码、设计、契约三者严重不符。
5. 核心工作非本人完成且无法解释关键实现。
6. 提交真实口令、私钥、生产令牌或用户隐私数据。
7. 答辩中对自己系统的核心机制无法给出合理解释。
