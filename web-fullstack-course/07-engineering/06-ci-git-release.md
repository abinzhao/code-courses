# 06 CI、Git 与发布：让证据跟随同一提交

## 本章任务

把本地验证过的邻里集市变更组织成可审查提交，为同一提交设计可复现 CI，并明确制品、部署、发布与回滚各自能证明什么。本章不操作教材仓库的远端，也不执行生产发布。

## 必要前置

- 已完成[单元、集成与端到端测试](05-unit-integration-e2e.md)。
- 能在个人练习项目中执行 `pnpm verify`。
- 理解锁文件、生产构建与浏览器测试的边界。
- Git 写操作只在读者拥有的一次性练习仓库中执行。

## 学习顺序

1. [Git 范围、审查与可回退提交](06-ci-git-release/01-git-scope-reviewable-commits.md)：区分工作树、暂存区、提交、分支、worktree 与外部资源。
2. [可复现 CI 质量流水线](06-ci-git-release/02-ci-reproducible-quality-pipeline.md)：把版本探针、冻结安装和 `pnpm verify` 映射到最小权限工作流。
3. [制品、发布、缓存与回滚边界](06-ci-git-release/03-artifacts-release-cache-rollback.md)：让制品绑定提交，并设计静态资源发布顺序和恢复证据。

建议连续投入 4 至 5 小时。先完成第一课的本地范围证据，再阅读工作流；否则容易把 YAML 语法误当成变更正确性。

## 依赖关系

```text
精确选择本地变更
  -> 同一提交的冻结安装与质量门
  -> 提交绑定制品
  -> 发布顺序、观察与回滚决策
```

分支和 worktree 只隔离文件状态，不隔离数据库、云账号、域名或缓存。CI 绿灯只覆盖实际执行的步骤；上传制品不等于部署，前端回滚也不能撤销数据库写入。

## 邻里集市综合任务

在读者拥有的 `market-engineering-capstone` 一次性副本中：

1. 只暂存本次金额与搜索竞态修复涉及的源码和测试。
2. 用 staged diff 证明提交不含构建目录、环境文件和无关格式变化。
3. 静态审查 GitHub Actions 教学工作流，核对 Node `24.21.0`、pnpm `12.10.1`、冻结安装、双编译器探针、匹配 Chromium 和 `pnpm verify`。
4. 证明构建制品名称包含提交 SHA，缺失产物会使上传步骤失败。
5. 写出“先上传带 hash 资源、后切换 HTML、保留旧资源”的发布顺序，并列出前端回滚无法恢复的数据状态。

## 章级验收证据

| 证据 | 判定标准 |
| --- | --- |
| 变更范围 | `git status --short`、未暂存 diff 与 staged diff 均被阅读，提交路径可逐项解释 |
| 本地等价门 | 冻结安装、版本探针和 `pnpm verify` 的命令、退出码、提交标识被记录 |
| 工作流静态审查 | 最小权限、超时、并发、未受信 PR、生命周期脚本与 Action 引用边界均有结论 |
| 制品故障注入 | 错误产物路径触发失败，恢复真实路径后重新检查 |
| 外部操作边界 | 推送、托管 CI、registry、CDN、TLS、生产部署、数据库恢复均未冒充已验证 |

本章不要求对远端执行任何写操作。只有读者在已授权仓库真实运行工作流后，才能把“工作流文本已审查”升级为“托管 CI 已通过”。
