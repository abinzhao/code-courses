# 24-E2E 测试与前端质量门禁

## 目标

端到端（End-to-End，E2E）测试启动真实浏览器，像真实用户一样访问页面、点击、输入并观察结果，覆盖从前端路由、请求到后端响应的完整链路。组件测试回答“组件行为是否正确”，E2E 回答“整个系统是否真的可用”。质量门禁则把类型检查、规范、单元测试、构建和 E2E 组织成自动化流水线，使缺陷在合并前被拦截。

完成本知识单元后，学员应能够：

1. 安装并配置 Playwright，理解 baseURL、webServer、projects、retries 与报告产物的作用。
2. 使用 `getByRole`、`getByLabel`、`getByText` 等定位器和 Web-first 断言，利用自动等待机制写出稳定用例。
3. 使用网络拦截构造成功、失败与延迟场景，并通过 `waitForResponse` 等方式校验请求与响应。
4. 启用 trace、截图和视频等失败产物，使用 Trace Viewer 对失败进行复盘。
5. 实现用例隔离与数据准备：独立账号、API 级初始化、storageState 复用登录态，避免用例相互污染。
6. 覆盖登录与增删改查关键业务流，并组织 typecheck/lint/unit/build/e2e 质量门禁脚本，配置本地 pre-commit 与 CI 执行。

本单元强调：E2E 贵而关键，数量要少而准；门禁的价值在于“不可绕过的自动化纪律”，而不是让开发者本地多敲几条命令。

## 技术栈

| 工具或库 | 当前稳定版本线 | 用途 | 学习要求 |
|---|---|---|---|
| Playwright | 当前稳定版（1.x） | E2E 测试框架与浏览器自动化 | 掌握 config、定位器、断言、网络拦截、trace、storageState |
| `@playwright/test` | 随 Playwright 发布 | 测试 API | 掌握 `test`、`expect`、fixtures 与钩子 |
| React | 19.x | 被测前端 | E2E 覆盖第 21 至 23 单元构建的页面 |
| Vite | 当前稳定版 | 本地开发服务器 | 由 webServer 配置自动拉起 |
| TypeScript | 5.x 稳定版 | 类型检查 | `tsc --noEmit` 作为门禁第一步 |
| Vitest | 3.x 稳定版 | 单元/组件测试 | 门禁中以非交互模式运行 |
| ESLint | 9.x flat config | 代码规范 | 门禁与 lint-staged 共用配置 |
| Husky + lint-staged | 当前稳定版 | Git 钩子提交校验 | 掌握 pre-commit 的安装与配置 |
| GitHub Actions（或 GitLab CI） | 当前版本 | 持续集成 | 能编写合并前执行全部门禁的工作流 |
| pnpm | 当前稳定版 | 包管理与脚本串联 | 统一所有命令入口 |

约定：

- E2E 环境地址使用 `http://localhost:5173` 与测试环境占位域名 `https://staging.example.com`，不写真实生产地址。
- 测试账号一律使用“按用例动态生成”的账号，不在代码中保存固定密码、令牌或真实用户数据。
- 不在任何配置文件中提交凭据；如需密钥，由 CI 的密钥机制注入。

## 详细的理论知识讲解和示例伪代码

### 1. Playwright 安装、配置与第一个用例

#### 1.1 安装

```bash
pnpm create playwright
pnpm exec playwright install
```

安装过程会生成 `playwright.config.ts`、`e2e/` 目录和示例用例；`playwright install` 下载 Chromium、Firefox、WebKit 浏览器二进制。

#### 1.2 配置文件

```ts
// playwright.config.ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './e2e',
  fullyParallel: true,
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 1 : undefined,
  reporter: [['list'], ['html', { open: 'never' }]],
  use: {
    baseURL: 'http://localhost:5173',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
  },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'webkit', use: { ...devices['Desktop Safari'] } },
  ],
  webServer: {
    command: 'pnpm dev',
    url: 'http://localhost:5173',
    reuseExistingServer: !process.env.CI,
    timeout: 120_000,
  },
});
```

关键配置说明：

| 配置 | 作用 |
|---|---|
| `baseURL` | 相对路径 `page.goto('/login')` 的前缀 |
| `webServer` | 运行测试前自动启动开发服务器，就绪后再执行用例 |
| `fullyParallel` | 允许用例在并行 worker 中执行 |
| `retries` | CI 中失败自动重试，用于甄别偶发失败；重试全红才算真失败 |
| `workers` | 并行进程数；CI 资源有限时常收敛为 1 |
| `forbidOnly` | CI 中禁止 `test.only` 导致只跑单个用例 |
| `trace/screenshot/video` | 失败诊断产物，按策略保留以节省空间 |

#### 1.3 第一个用例

```ts
// e2e/home.spec.ts
import { expect, test } from '@playwright/test';

test('首页展示应用标题', async ({ page }) => {
  await page.goto('/');

  await expect(
    page.getByRole('heading', { name: '知行引擎' }),
  ).toBeVisible();
});
```

运行命令：

```bash
pnpm exec playwright test
pnpm exec playwright test e2e/home.spec.ts --headed
pnpm exec playwright show-report
```

#### 1.4 与 Web 的关系

Playwright 驱动的是真实浏览器：真实 DNS（在不拦截时）、真实 HTTP、真实布局和渲染管线。组件测试中 jsdom 无法验证的焦点跳转、导航、滚动、跨浏览器差异，E2E 都能覆盖。代价是速度与维护成本——一条 E2E 通常以秒计，因此它位于测试金字塔顶端，只覆盖关键路径。

#### 1.5 常见误区

> 误区一：把每个组件测试改写成 E2E，追求“全面 E2E”。

执行慢、调试难、数据准备重；E2E 应少而关键，常规行为交给组件测试。

> 误区二：本地能跑就认为配置完整。

CI 没有图形界面、端口与并发策略不同，必须显式配置 webServer、workers 与重试。

### 2. 定位器、自动等待与 Web-first 断言

#### 2.1 定位器优先级

与 Testing Library 的理念一致，Playwright 也推荐语义定位：

```ts
page.getByRole('button', { name: '保存' });
page.getByRole('textbox', { name: '标题' });
page.getByLabel('邮箱');
page.getByPlaceholder('输入关键字');
page.getByText('提交成功');
page.getByTestId('custom-chart'); // 最后手段，可在 config 中改 testIdAttribute
```

链式缩小范围与筛选：

```ts
const table = page.getByRole('table', { name: '条目列表' });
await table.getByRole('row', { name: /第一篇/ }).getByRole('button', { name: '删除' }).click();

const rows = page.getByRole('listitem');
await expect(rows.filter({ hasText: '小林' })).toHaveCount(1);
```

#### 2.2 自动等待

Playwright 的操作内置“可操作性检查”：执行 `click()` 前自动等待元素出现、可见、稳定（无动画位移）、接收事件、启用。因此绝大多数场景不需要手写“先等 500ms”。这消除了 E2E 最主要的偶发失败来源。

```ts
// 不需要 sleep：点击前框架自动等待按钮可操作
await page.getByRole('button', { name: '发布' }).click();

// 需要等待导航完成时使用显式断言或 waitForURL
await expect(page).toHaveURL(/\/items\/\d+/);
```

#### 2.3 Web-first 断言

`expect(locator).toBeVisible()` 等断言会自动重试直到超时，适合异步页面：

```ts
await expect(page.getByRole('status')).toHaveText('保存成功');
await expect(page.getByRole('button', { name: '保存' })).toBeDisabled();
await expect(page).toHaveTitle(/知识条目/);
await expect(page.getByRole('listitem')).toHaveCount(3);
```

需要对非定位器值轮询时使用 `expect.poll`；不希望一个失败中断后续检查时使用软断言：

```ts
await expect.poll(async () => page.title(), { timeout: 3000 }).toContain('列表');

await expect.soft(page.getByText('页脚')).toBeVisible();
await expect.soft(page.getByRole('link', { name: '首页' })).toBeVisible();
```

#### 2.4 与 Web 的关系

网络与渲染的耗时天然不确定，硬编码等待在快环境浪费、在慢环境不足。自动等待把“等待固定时间”改成“等待条件成立”，与第 23 单元的 findBy/waitFor 一脉相承。语义定位器还迫使应用保持可访问的 DOM：没有 label 的输入、没有角色的图标按钮，自动化同样“看不见”。

#### 2.5 常见误区

> 误区一：大量使用 `page.locator('.btn-primary')` 与 `nth(0)`。

样式类与顺序是最不稳定的定位方式，重构 UI 即批量失败；优先 role 与 name。

> 误区二：用 `page.waitForTimeout(1000)` 等待。

它不检查任何条件，只制造时间，是偶发失败的主要来源。

### 3. 网络拦截与请求校验

#### 3.1 使用 page.route 拦截

```ts
await page.route('**/api/v1/items', async (route) => {
  if (route.request().method() === 'GET') {
    await route.fulfill({
      status: 200,
      contentType: 'application/json',
      body: JSON.stringify({
        items: [{ id: '1', title: '拦截出的条目' }],
      }),
    });
    return;
  }
  await route.continue();
});

await page.goto('/items');
await expect(page.getByText('拦截出的条目')).toBeVisible();
```

构造难以在真实环境复现的异常场景：

```ts
await page.route('**/api/v1/items', (route) =>
  route.fulfill({ status: 500, body: JSON.stringify({ message: 'error' }) }),
);

await page.goto('/items');
await expect(page.getByRole('alert')).toContainText('加载失败');
```

模拟慢网络以验证加载态（也可用 browser context 的 `route` 加延时）：

```ts
await page.route('**/api/v1/items', async (route) => {
  await new Promise((resolve) => setTimeout(resolve, 1500));
  await route.continue();
});
```

#### 3.2 校验真实请求

不拦截、只观察，验证前端确实发出了正确请求：

```ts
const responsePromise = page.waitForResponse(
  (response) =>
    response.url().includes('/api/v1/items') &&
    response.request().method() === 'POST',
);

await page.getByRole('button', { name: '发布' }).click();

const response = await responsePromise;
expect(response.status()).toBe(201);

const requestPromise = page.waitForRequest((request) =>
  request.url().includes('/api/v1/items'),
);
const request = await requestPromise;
expect(request.method()).toBe('POST');
const body = request.postDataJSON();
expect(body).toMatchObject({ title: '我的标题', visibility: 'private' });
```

#### 3.3 真实后端与拦截的取舍

```text
关键业务流（登录、下单、增删改查）
    优先连接隔离的测试环境，真实链路最可信，配合独立测试数据
难以构造的场景（500、超时、慢网络、第三方支付回调）
    使用网络拦截稳定复现
纯前端演示环境（后端不可用）
    大范围拦截，使 E2E 可在无后端时运行
```

拦截只影响浏览器上下文内的请求，不会改动后端数据，因此适合异常演练；但它也意味着“后端没有被验证”，不能用拦截版本替代真实链路版本。

#### 3.4 与 Web 的关系

`page.route` 的拦截点位于浏览器内部、请求离开网卡之前，因此前端代码经历的 URL 拼接、方法、请求头、Cookie 携带和响应解析全部是真实的 HTTP 语义，只是网络往返被替换。被 `fulfill` 的响应同样携带状态码、content-type 与 body，浏览器会像处理真实响应一样更新缓存、触发 fetch 回调。这让拦截既保持了 Web 请求链路的完整覆盖，又获得了对异常与延迟的完全控制力；选择 `continue` 时请求则照常发往真实服务器。

#### 3.5 常见误区

> 误区：所有用例全部拦截网络，E2E 退化为“带浏览器的组件测试”。

真实部署后的集成问题（鉴权、CORS、数据形状漂移）将完全漏网。

### 4. Trace、截图、视频与失败复盘

#### 4.1 产物配置与查看

在配置中设置策略后：

```bash
pnpm exec playwright test --trace on
pnpm exec playwright show-trace trace.zip
pnpm exec playwright show-report
```

Trace Viewer 包含时间线、每一步的 DOM 快照、网络请求、控制台与源码定位，可以像录像一样回放失败过程。截图与视频按 `only-on-failure`/`retain-on-failure` 保留，兼顾可诊断性与磁盘占用。CI 中应把 HTML 报告和 trace 作为构件上传（见第 8 节）。

#### 4.2 失败复盘流程

```text
1. 看断言信息：期望与实际的可见结果是什么
2. 打开 trace：失败前最后一次用户操作停在哪里
3. 检查网络：请求是否发出、状态码、响应体
4. 检查控制台：是否有渲染错误或未捕获 Promise
5. 判断归因：产品缺陷 / 用例问题 / 环境数据问题 / 偶发失败
6. 修复后本地复跑三次，再推 CI
```

#### 4.3 与 Web 的关系

E2E 失败往往涉及完整链路而非单点，trace 把浏览器视角的全部证据（DOM、网络、控制台）固化为可分享文件，使“失败可重放、可协作分析”。这与生产环境用户录屏、服务端链路日志的思路一致：先取证，再判断。

#### 4.4 常见误区

> 误区一：失败后只看一行报错就重跑“碰运气”。

偶发失败也要看 trace 找根因；反复重跑会掩盖竞态类真问题。

> 误区二：trace 设置为全局 `on` 且从不清理。

每个用例都产生大量数据，磁盘迅速膨胀；按需用 on-first-retry。

### 5. 用例隔离与数据准备

#### 5.1 隔离原则

每个用例必须自包含、可任意顺序、可并行执行：

- Playwright 为每个用例提供独立的 BrowserContext（独立 Cookie 与存储），默认已隔离会话。
- 数据互不重叠：每条用例生成唯一标识（时间戳、随机串）创建自己的资源。
- 用例结束后通过 API 清理自己创建的数据，或使用一次性账号随账号回收数据。

```ts
// e2e/utils/fixtures.ts
import { test as base } from '@playwright/test';

function uniqueEmail() {
  return `e2e_${Date.now()}_${Math.random().toString(36).slice(2, 8)}@example.com`;
}

type UserAccount = { email: string; password: string };

export const test = base.extend<{ account: UserAccount }>({
  account: async ({}, use) => {
    const account: UserAccount = {
      email: uniqueEmail(),
      password: 'Practice#2026',
    };
    // 通过注册 API 直接准备账号，不走 UI
    await fetch('https://staging.example.com/api/v1/auth/register', {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify(account),
    });
    await use(account);
    // 清理账号（接口按团队约定提供）
    await fetch('https://staging.example.com/api/v1/test/users', {
      method: 'DELETE',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({ email: account.email }),
    });
  },
});

export { expect } from '@playwright/test';
```

#### 5.2 API 登录与 storageState

除一条“界面登录”用例外，其他用例都通过 API 获取登录态并注入，避免每条用例重复登录表单：

```ts
// e2e/utils/auth.ts
import { request } from '@playwright/test';

async function createLoggedInState(email: string, password: string, path: string) {
  const context = await request.newContext({ baseURL: 'https://staging.example.com' });
  await context.post('/api/v1/auth/login', {
    data: { email, password },
  });
  await context.storageState({ path });
  await context.dispose();
}

export { createLoggedInState };
```

```ts
// 在用例或全局 setup 中保存状态，config 加入 storageState
test('登录后创建条目', async ({ browser, account }) => {
  const stateFile = `./.auth/${account.email}.json`;
  await createLoggedInState(account.email, account.password, stateFile);

  const context = await browser.newContext({ storageState: stateFile });
  const page = await context.newPage();

  await page.goto('/items');
  await expect(page.getByRole('button', { name: '新建' })).toBeVisible();

  await context.close();
});
```

#### 5.3 与 Web 的关系

E2E 数据问题本质上是“多个真实客户端操作同一个真实后端”：用例并行、历史残留、他人测试都会制造干扰。唯一标识与账号级隔离让每个用例只断言自己创建的数据，把不确定性降到最低；API 级准备比界面点击快一个数量级，也不会因为登录页改版导致全部用例瘫痪。

#### 5.4 常见误区

> 误区一：用例之间共享同一个“固定测试账号”。

并行执行时互相删除、互相修改列表，断言随机失败。

> 误区二：每条用例都走 UI 登录。

登录页成为所有用例的前置瓶颈；UI 登录本身保留一条专属用例即可。

### 6. 登录与增删改查关键流

#### 6.1 界面登录用例

```ts
// e2e/login.spec.ts
import { expect, test } from './utils/fixtures';

test('使用正确账号登录后进入列表页', async ({ page, account }) => {
  await page.goto('/login');

  await page.getByLabel('邮箱').fill(account.email);
  await page.getByLabel('密码').fill(account.password);
  await page.getByRole('button', { name: '登录' }).click();

  await expect(page).toHaveURL(/\/items/);
  await expect(page.getByRole('heading', { name: '条目列表' })).toBeVisible();
});

test('密码错误时显示错误提示且停留在登录页', async ({ page }) => {
  await page.goto('/login');

  await page.getByLabel('邮箱').fill('someone@example.com');
  await page.getByLabel('密码').fill('WrongPassword#1');
  await page.getByRole('button', { name: '登录' }).click();

  await expect(page.getByRole('alert')).toContainText('邮箱或密码不正确');
  await expect(page).toHaveURL(/\/login/);
});
```

#### 6.2 增删改查完整链路

```ts
// e2e/items-crud.spec.ts
import { expect, test } from './utils/fixtures';

test('条目可以被创建、查看、编辑和删除', async ({ browser, account }) => {
  const stateFile = `./.auth/${account.email}.json`;
  await createLoggedInState(account.email, account.password, stateFile);
  const context = await browser.newContext({ storageState: stateFile });
  const page = await context.newPage();

  const unique = Date.now().toString(36);
  const createTitle = `E2E 条目 ${unique}`;
  const editTitle = `E2E 条目 ${unique} 已编辑`;

  // Create
  await page.goto('/items');
  await page.getByRole('button', { name: '新建' }).click();
  await page.getByRole('textbox', { name: '标题' }).fill(createTitle);
  await page.getByRole('textbox', { name: '正文' }).fill('这是一段超过二十个字的合法正文内容。');
  await page.getByRole('button', { name: '发布' }).click();

  // Read：列表与详情都能看到
  await expect(page.getByRole('row', { name: new RegExp(createTitle) })).toBeVisible();
  await page.getByRole('row', { name: new RegExp(createTitle) }).getByRole('link', { name: '查看' }).click();
  await expect(page.getByRole('heading', { name: createTitle })).toBeVisible();

  // Update
  await page.getByRole('button', { name: '编辑' }).click();
  await page.getByRole('textbox', { name: '标题' }).fill(editTitle);
  await page.getByRole('button', { name: '保存' }).click();
  await expect(page.getByRole('heading', { name: editTitle })).toBeVisible();

  // Delete
  await page.goto('/items');
  const row = page.getByRole('row', { name: new RegExp(editTitle) });
  await row.getByRole('button', { name: '删除' }).click();
  await page.getByRole('button', { name: '确认删除' }).click();
  await expect(page.getByRole('row', { name: new RegExp(editTitle) })).toHaveCount(0);

  await context.close();
});
```

#### 6.3 与 Web 的关系

增删改查是绝大多数业务系统的核心闭环：它串联了路由、表单校验、请求、缓存刷新、导航和二次确认。一条这样的用例可以在每次发布前回答“系统主链路是否可用”。断言全部落在用户可见结果（行存在、标题变化、URL），而不是数据库或内部状态，因此即使实现重构，用例依然有效。

#### 6.4 常见误区

> 误区一：删除操作不点确认直接断言消失，或断言依赖具体条数。

条数会被其他用例影响；断言“目标行不存在”而非“只剩 N 行”，并完整走确认交互。

> 误区二：用例失败后残留数据，越积越多影响后续运行。

清理逻辑与创建逻辑成对出现；一次性账号策略让数据随账号生命周期回收。

### 7. 质量门禁脚本：typecheck / lint / unit / build / e2e

#### 7.1 脚本组织

```json
{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "lint": "eslint .",
    "format": "prettier --write .",
    "test": "vitest run",
    "test:watch": "vitest",
    "build": "vite build",
    "preview": "vite preview",
    "e2e": "playwright test",
    "e2e:report": "playwright show-report",
    "gate": "pnpm typecheck && pnpm lint && pnpm test && pnpm build"
  }
}
```

`gate` 串联四项秒级到分钟级的检查，任一步失败立即终止并返回非零退出码，适合本地合并前自检；E2E 需要拉起服务，单独通过 `e2e` 执行，也可以在 shell 脚本中合并：

```bash
# scripts/full-check.sh
#!/usr/bin/env bash
set -euo pipefail

pnpm typecheck
pnpm lint
pnpm test
pnpm build
pnpm e2e
```

#### 7.2 各项门禁拦截的问题

| 门禁 | 拦截的问题 | 不应替代 |
|---|---|---|
| typecheck | 类型不匹配、空值未处理、接口字段漂移 | 运行时校验 |
| lint | Hooks 规则、未用变量、常见逻辑与风格问题 | 代码评审 |
| unit | 纯函数、组件行为回归 | E2E |
| build | 打包错误、产物生成失败、导入不可解析 | 预览验证 |
| e2e | 关键业务链路在真实浏览器中断 | 低层测试 |

门禁的失败纪律：任何一项红了就先修复，不允许跳过该步、不允许放宽断言或关闭规则来制造通过；确属规则不合理时，先走团队评审修改规则，再重新运行。

#### 7.3 与 Web 的关系

这些门禁对应了缺陷进入生产前的不同过滤层：类型与规范问题成本最低，本地即可拦截；构建问题在部署前暴露；E2E 在真实浏览器守住关键业务。分层组合使整体反馈“早而快”，又在最后有“重而准”的保障。

#### 7.4 常见误区

> 误区：认为五条命令“开发者记住就好”，不写统一入口。

没有统一脚本时，每个人跑的子集不同，漏检成为常态；自动化必须由脚本和 CI 强制执行。

### 8. 本地 pre-commit 与 CI 执行

#### 8.1 Husky + lint-staged

```bash
pnpm add -D husky lint-staged
pnpm exec husky init
```

```sh
# .husky/pre-commit
pnpm lint-staged
```

`package.json` 中增加配置：

```json
{
  "lint-staged": {
    "*.{ts,tsx}": ["eslint --fix", "prettier --write"],
    "*.{json,md,css}": ["prettier --write"]
  }
}
```

pre-commit 只检查暂存区文件，秒级反馈；不要在提交钩子里跑完整构建和 E2E——那会让提交慢到被开发者绕过。重型检查属于 CI。

#### 8.2 GitHub Actions 工作流

```yaml
# .github/workflows/quality.yml
name: quality-gate

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 9

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Type check
        run: pnpm typecheck

      - name: Lint
        run: pnpm lint

      - name: Unit and component tests
        run: pnpm test

      - name: Build
        run: pnpm build

      - name: Install Playwright browsers
        run: pnpm exec playwright install --with-deps

      - name: E2E tests
        run: pnpm e2e

      - name: Upload Playwright report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: playwright-report
          path: playwright-report
          retention-days: 14
```

#### 8.3 CI 失败处理与 GitLab 变体

```text
1. 本地复现：检出同一提交，运行失败的那一步
2. 读日志与 trace 构件，按第 4 节流程归因
3. 修复并推新提交；不关闭检查、不用重跑“掩盖”偶发失败
4. 连续偶发失败视为真问题，先隔离再修竞态
```

使用 GitLab CI 的学员可用等价的 `.gitlab-ci.yml`：阶段拆为 `check`（typecheck/lint）、`test`（unit/build）、`e2e`，镜像中预装 Playwright 依赖或执行 `playwright install --with-deps`，报告用 `artifacts:when: always` 上传。

#### 8.4 与 Web 的关系

CI 是团队共享、不可跳过的质量基线：它在干净环境中按锁定版本的依赖（`--frozen-lockfile`）执行，任何“我机器上能跑”的差异都会暴露。门禁全绿才允许合并，使主干始终保持可部署状态——这是持续交付的前提。

#### 8.5 常见误区

> 误区一：CI 只跑 build，测试靠开发者自觉。

构建通过不代表行为正确；五层门禁缺一不可，顺序上先快后慢。

> 误区二：pre-commit 钩子不随仓库共享，或开发者用 `--no-verify` 跳过而无人约束。

钩子配置入库共享；跳过钩子的提交仍会被 CI 拦截，这是第二道防线。

## 实践练习题

### 练习 1：登录与异常场景 E2E

#### 任务

为登录页编写 E2E：成功登录进入列表页；错误凭据显示提示且不跳转；服务端返回 500 时展示服务不可用提示。

#### 步骤约束

1. 成功路径使用动态生成的测试账号（API 注册）。
2. 错误路径使用明显非法的固定占位凭据；500 路径通过 `page.route` 拦截登录接口构造。
3. 定位使用 `getByLabel` 与 `getByRole`，断言使用 URL 与 `role="alert"` 文本。
4. 不出现固定 `waitForTimeout`；登录后用 `expect(page).toHaveURL(...)` 等待。
5. 本地故意运行一次错误版本（改错断言文案），确认失败产物正常生成。

#### 提交物

- `e2e/login.spec.ts`；
- 三类场景的用例代码与拦截写法；
- 一次失败的截图或 trace 记录及归因说明。

#### 验收标准

- 三条路径都能稳定复现；
- 不依赖样式类与固定等待；
- 失败产物可以完整复盘；
- 不包含真实账号密码。

### 练习 2：增删改查闭环与数据隔离

#### 任务

编写条目增删改查的完整 E2E，实现 API 数据准备、storageState 登录复用和用例后清理。

#### 步骤约束

1. 使用自定义 fixture 生成唯一账号与唯一标题；清理逻辑成对出现。
2. 除登录用例外，本练习通过 API 登录并保存 storageState，再创建浏览器上下文。
3. 覆盖新建（含二次确认删除）、列表可见、详情可见、编辑后标题变化、删除后目标行消失。
4. 删除断言针对“目标行 count 为 0”，不写死总行数。
5. 用 `waitForResponse` 校验创建请求返回 201；连续运行三遍均通过。

#### 提交物

- fixture、auth 工具与 CRUD 用例；
- 请求校验与清理代码；
- 三遍运行记录。

#### 验收标准

- 用例可并行、可任意排序执行；
- 运行后无残留账号与条目；
- 全程用户视角断言；
- 无固定等待、无共享固定账号。

### 练习 3：门禁脚本、pre-commit 与 CI 工作流

#### 任务

为项目建立完整质量门禁：统一脚本、Husky + lint-staged 提交检查、CI 工作流，并演示“缺陷被拦截 → 修复 → 重新通过”。

#### 步骤约束

1. `package.json` 提供 typecheck/lint/test/build/e2e 与 gate 入口；另提供合并五步的 shell 脚本。
2. 配置 pre-commit 执行 lint-staged（仅暂存文件），不允许放入 E2E。
3. 编写 GitHub Actions 或 GitLab CI 工作流：锁文件安装 → typecheck → lint → test → build → Playwright（含浏览器安装）→ 报告作为构件上传。
4. 故意制造一个类型错误推送分支，展示 CI 变红和日志定位；修复后重新变绿。
5. 再制造一次 E2E 失败（改错按钮文案），展示报告/trace 构件可下载查看。

#### 提交物

- 脚本与配置文件（package.json、钩子、工作流、shell 脚本）；
- 两次红 → 绿的 CI 记录链接或截图；
- 一份门禁设计说明（每层拦什么、为什么这样排序）。

#### 验收标准

- 在干净克隆上按脚本可完整执行；
- 跳过本地钩子的提交仍会被 CI 拦截；
- 不通过关闭检查或放宽断言制造绿色；
- 报告构件在失败时确实保留。
