## 详细的理论知识讲解和示例伪代码

### 1. v-model 进阶：表单控件与提交状态

#### 1.1 定义

`v-model` 在表单控件上创建双向绑定，本质是“绑定值属性并监听输入事件”的语法糖。不同控件对应的值属性与事件不同，Vue 在内部统一处理；组件上的 `v-model` 则按第 26 单元的 `modelValue` 与 `update:modelValue` 约定工作。

常用内置修饰符：

```text
.trim   自动去除输入首尾空白
.number 把输入转换为数字
.lazy   把 input 事件触发改为 change 事件触发
```

#### 1.2 与 Web 的关系

工单新建与编辑是典型表单：文本框、多行描述、数字优先级、单选状态、多选标签与下拉处理人。表单草稿是客户端状态，提交中与成功跳转、失败回填共同构成完整交互。

使用 reactive 组织整组表单字段：

```vue
<!-- src/pages/TicketEditPage.vue -->
<script setup lang="ts">
import { reactive, ref } from 'vue';
import { useRouter } from 'vue-router';

type TicketForm = {
  title: string;
  description: string;
  priority: number;
  status: 'open' | 'closed';
  tags: string[];
  assignee: string;
};

const router = useRouter();
const submitting = ref(false);

const form = reactive<TicketForm>({
  title: '',
  description: '',
  priority: 2,
  status: 'open',
  tags: [],
  assignee: '',
});

async function handleSubmit() {
  submitting.value = true;
  try {
    const created = await createTicket({ ...form });
    router.push({ name: 'ticket-detail', params: { id: created.id } });
  } finally {
    submitting.value = false;
  }
}

async function createTicket(payload: TicketForm) {
  return { id: 1, ...payload };
}
</script>

<template>
  <form @submit.prevent="handleSubmit" class="ticket-form">
    <label>
      标题
      <input v-model.trim="form.title" type="text" required />
    </label>

    <label>
      描述
      <textarea v-model="form.description" rows="5" />
    </label>

    <label>
      优先级
      <input v-model.number="form.priority" type="number" min="1" max="5" />
    </label>

    <fieldset>
      <legend>状态</legend>
      <label>
        <input v-model="form.status" type="radio" value="open" />
        待处理
      </label>
      <label>
        <input v-model="form.status" type="radio" value="closed" />
        已关闭
      </label>
    </fieldset>

    <fieldset>
      <legend>标签</legend>
      <label>
        <input v-model="form.tags" type="checkbox" value="urgent" />
        紧急
      </label>
      <label>
        <input v-model="form.tags" type="checkbox" value="frontend" />
        前端
      </label>
    </fieldset>

    <label>
      处理人
      <select v-model="form.assignee">
        <option disabled value="">请选择</option>
        <option value="alice">Alice</option>
        <option value="bob">Bob</option>
      </select>
    </label>

    <button type="submit" :disabled="submitting">
      {{ submitting ? '提交中…' : '保存工单' }}
    </button>
  </form>
</template>
```

`.number` 的结果在无法解析时仍可能返回原始字符串，需要时应再用 `Number.isFinite` 校验。复选框绑定数组时，勾选值进入数组；绑定单个布尔值时，直接得到布尔状态。

重置表单：优先使用原生 `type="reset"` 配合初始值，或把字段重新赋为初始快照：

```ts
const initial: TicketForm = {
  title: '',
  description: '',
  priority: 2,
  status: 'open',
  tags: [],
  assignee: '',
};

function resetForm() {
  Object.assign(form, initial);
}
```

#### 1.3 常见误区

> 提交中只把按钮文字改成“提交中…”就够了。

还应禁用提交按钮防止重复提交，并在必要时锁住关键字段；网络失败要恢复可提交状态。

> v-model 绑定子组件就可以让子组件随意修改表单。

表单状态归属页面或表单容器，子组件仍通过事件回传变化；v-model 是契约，不是放权。

> 多选框一定返回布尔值。

绑定到数组时收集的是 value 列表，单个勾选框才是布尔值，使用前应明确数据形态。

### 2. 表单校验：手写规则与 VeeValidate 加 Zod

#### 2.1 定义

表单校验确认字段是否满足业务规则：必填、长度、范围、格式与字段间一致性。校验可在提交时统一执行，也可在字段失焦或变化后渐进提示。一个完整方案还包括服务端错误回填与错误信息的可访问性关联。

手写校验的最小结构：规则函数返回错误文案，聚合得到错误表：

```ts
// src/validation/ticket.ts
import type { TicketForm } from '../pages/TicketEditPage.vue';

export type TicketErrors = Partial<Record<keyof TicketForm, string>>;

export function validateTicket(form: TicketForm): TicketErrors {
  const errors: TicketErrors = {};

  const title = form.title.trim();
  if (!title) {
    errors.title = '标题不能为空';
  } else if (title.length < 4) {
    errors.title = '标题至少 4 个字符';
  } else if (title.length > 80) {
    errors.title = '标题不能超过 80 个字符';
  }

  if (!form.assignee) {
    errors.assignee = '请选择处理人';
  }

  if (!Number.isFinite(form.priority) || form.priority < 1 || form.priority > 5) {
    errors.priority = '优先级必须是 1 到 5 的数字';
  }

  return errors;
}
```

在页面中提交时校验，并支持失焦后渐进提示：

```vue
<script setup lang="ts">
import { reactive, ref } from 'vue';
import { validateTicket, type TicketErrors } from '../validation/ticket';

const form = reactive({
  title: '',
  description: '',
  priority: 2,
  status: 'open' as 'open' | 'closed',
  tags: [] as string[],
  assignee: '',
});

const errors = ref<TicketErrors>({});
const touched = ref<Record<string, boolean>>({});

function markTouched(field: keyof typeof form) {
  touched.value[field] = true;
  errors.value = validateTicket(form);
}

async function handleSubmit() {
  errors.value = validateTicket(form);
  if (Object.keys(errors.value).length > 0) {
    return;
  }
  // 校验通过后再发起请求
}
</script>

<template>
  <form novalidate @submit.prevent="handleSubmit">
    <label>
      标题
      <input
        v-model.trim="form.title"
        type="text"
        aria-invalid="touched.title && Boolean(errors.title)"
        aria-describedby="title-error"
        @blur="markTouched('title')"
      />
    </label>
    <p id="title-error" v-if="touched.title && errors.title" class="field-error">
      {{ errors.title }}
    </p>
  </form>
</template>
```

#### 2.2 与 Web 的关系：VeeValidate 加 Zod 的声明式思路

复杂表单中，手写 touched、错误表与提交流程会逐渐膨胀。VeeValidate 负责表单与字段状态管理，Zod 负责描述规则与推导类型。

```ts
// src/validation/ticketSchema.ts
import { z } from 'zod';

export const ticketSchema = z.object({
  title: z.string().trim().min(4, '标题至少 4 个字符').max(80, '标题不能超过 80 个字符'),
  description: z.string().max(500, '描述不能超过 500 字'),
  priority: z.coerce.number().int().min(1).max(5),
  status: z.enum(['open', 'closed']),
  tags: z.array(z.string()),
  assignee: z.string().min(1, '请选择处理人'),
});

export type TicketSchema = z.infer<typeof ticketSchema>;
```

在组件中通过 toTypedSchema 接入（组件式 API 形态，理解思路即可）：

```vue
<script setup lang="ts">
import { useForm } from 'vee-validate';
import { toTypedSchema } from '@vee-validate/zod';
import { ticketSchema } from '../validation/ticketSchema';

const { handleSubmit, errors, isSubmitting } = useForm({
  validationSchema: toTypedSchema(ticketSchema),
  initialValues: {
    title: '',
    description: '',
    priority: 2,
    status: 'open',
    tags: [],
    assignee: '',
  },
});

const onSubmit = handleSubmit(async (values) => {
  await createTicket(values);
});

async function createTicket(_values: unknown) {
  return { id: 1 };
}
</script>

<template>
  <form novalidate @submit="onSubmit">
    <label>
      标题
      <input name="title" type="text" />
    </label>
    <p v-if="errors.title" class="field-error">{{ errors.title }}</p>
    <button type="submit" :disabled="isSubmitting">保存</button>
  </form>
</template>
```

使用 VeeValidate 的字段组件或 `useField` 可以进一步接管绑定与 aria 属性；无论哪种写法，错误文案都应通过 `aria-describedby` 关联、输入框带 `aria-invalid`。

#### 2.3 服务端错误回填

服务端可能在提交后返回字段级错误，例如处理人已离职、标题与已有工单冲突。前端校验通过不代表业务一定成功：

```ts
type ServerFieldErrors = Record<string, string>;

function applyServerErrors(remoteErrors: ServerFieldErrors) {
  for (const [field, message] of Object.entries(remoteErrors)) {
    errors.value[field as keyof TicketErrors] = message;
  }
}
```

提交后应区分三类结果：字段错误（回填对应字段）、全局错误（页面顶部提示）、成功（跳转或提示）。前端校验改善体验，后端仍必须重新校验不可信输入，这一信任边界与 React 单元一致。

#### 2.4 常见误区

> 用户还没提交就在每个字段显示红色错误，显得严格。

过早报错会打扰输入。推荐首次提交前只在失焦后提示，提交后再全量提示。

> 有了前端校验，后端可以直接信任数据。

前端代码与请求都可被篡改，后端必须独立校验与鉴权。

> Zod 只用于表单，不能描述接口响应。

Zod 同样适合在网络边界校验响应结构，避免把异常数据直接渲染。

### 3. 数据请求封装：fetch 与 axios

#### 3.1 定义

请求客户端是应用与后端 HTTP 接口之间的统一入口，负责拼接 Base URL、组装请求头、序列化与解析、处理凭证以及把各种失败归一化为可识别的错误类型。集中封装可以避免相同样板散落在每个组件中。

#### 3.2 与 Web 的关系

工单列表、详情与表单提交都依赖网络请求。把 Base URL 与凭证策略写死在组件里，既不安全也难以在多环境切换。Base URL 应通过环境变量注入，敏感凭证不能出现在前端代码中。

基于 fetch 的封装：

```ts
// src/api/client.ts
export class ApiError extends Error {
  constructor(
    message: string,
    readonly status: number,
    readonly payload?: unknown,
  ) {
    super(message);
    this.name = 'ApiError';
  }
}

type RequestOptions = {
  method?: 'GET' | 'POST' | 'PUT' | 'DELETE';
  body?: unknown;
  signal?: AbortSignal;
};

const BASE_URL = import.meta.env.VITE_API_BASE_URL ?? '/api';

export async function request<T>(path: string, options: RequestOptions = {}): Promise<T> {
  const response = await fetch(`${BASE_URL}${path}`, {
    method: options.method ?? 'GET',
    headers: {
      'Content-Type': 'application/json',
      Accept: 'application/json',
    },
    body: options.body === undefined ? undefined : JSON.stringify(options.body),
    signal: options.signal,
    credentials: 'include',
  });

  if (response.status === 204) {
    return undefined as T;
  }

  const payload = await response.json().catch(() => undefined);

  if (!response.ok) {
    const message = typeof payload === 'object' && payload && 'message' in payload
      ? String((payload as { message: unknown }).message)
      : `请求失败（${response.status}）`;
    throw new ApiError(message, response.status, payload);
  }

  return payload as T;
}
```

领域 API 建立在统一客户端之上：

```ts
// src/api/tickets.ts
import { request } from './client';

type Ticket = {
  id: number;
  title: string;
  description: string;
  status: 'open' | 'closed';
  assignee: string;
};

export function fetchTickets(signal?: AbortSignal) {
  return request<Ticket[]>('/tickets', { signal });
}

export function createTicket(input: Omit<Ticket, 'id'>) {
  return request<Ticket>('/tickets', { method: 'POST', body: input });
}

export function closeTicket(id: number) {
  return request<Ticket>(`/tickets/${id}`, { method: 'PUT', body: { status: 'closed' } });
}
```

axios 的等价封装，重点是实例与拦截器：

```ts
// src/api/axios-client.ts
import axios, { AxiosError } from 'axios';

export const httpClient = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL ?? '/api',
  timeout: 10000,
  withCredentials: true,
});

httpClient.interceptors.request.use((config) => {
  // 可在此统一附加会话信息；不要在此写入硬编码密钥
  return config;
});

httpClient.interceptors.response.use(
  (response) => response,
  (error: AxiosError<{ message?: string }>) => {
    const status = error.response?.status ?? 0;
    const message = error.response?.data?.message ?? error.message;
    return Promise.reject(new ApiError(message, status, error.response?.data));
  },
);
```

#### 3.3 常见误区

> 把后端地址写死成 `https://某真实主机` 方便联调。

应使用环境变量，并提供 `.env.example` 说明需要哪些变量；真实主机与令牌不进入提交。

> 每个组件直接 fetch，错误时统一弹“网络异常”。

应区分 HTTP 错误、断网、超时与业务错误，给出可操作的提示与重试，而不是掩盖原因。

### 4. loading、error、empty 三态与竞态取消

#### 4.1 定义

每一次远程数据展示至少要考虑四种界面：初始加载（loading）、失败（error）、成功有数据（content）、成功但为空（empty）。竞态是指先后发出的两个请求，较早的请求更晚返回，过期数据覆盖新数据；请求取消通过 `AbortController` 主动中止不再需要的请求。

#### 4.2 与 Web 的关系

工单列表在关键词快速变化、筛选频繁切换时最容易出现竞态。三态完整能避免白屏与“看起来成功却没有内容”；取消旧请求既减少浪费，也从根本上防止过期响应覆盖。

```vue
<!-- src/pages/TicketListPage.vue -->
<script setup lang="ts">
import { onBeforeUnmount, onMounted, ref } from 'vue';
import { fetchTickets } from '../api/tickets';
import { ApiError } from '../api/client';

type Ticket = { id: number; title: string; status: 'open' | 'closed' };

const tickets = ref<Ticket[]>([]);
const loading = ref(false);
const errorMessage = ref('');

let controller: AbortController | null = null;

async function load() {
  controller?.abort();
  controller = new AbortController();

  loading.value = true;
  errorMessage.value = '';

  try {
    tickets.value = await fetchTickets(controller.signal);
  } catch (cause) {
    if (cause instanceof DOMException && cause.name === 'AbortError') {
      return;
    }
    errorMessage.value = cause instanceof ApiError ? cause.message : '加载失败，请稍后重试';
  } finally {
    loading.value = false;
  }
}

onMounted(load);
onBeforeUnmount(() => controller?.abort());
</script>

<template>
  <section>
    <h1>工单列表</h1>

    <p v-if="loading" aria-live="polite">正在加载…</p>

    <template v-else>
      <div v-if="errorMessage" role="alert" class="error-panel">
        <p>{{ errorMessage }}</p>
        <button type="button" @click="load">重试</button>
      </div>

      <p v-else-if="tickets.length === 0" class="empty">
        当前没有工单，可以点击“新建工单”开始。
      </p>

      <ul v-else>
        <li v-for="ticket in tickets" :key="ticket.id">
          {{ ticket.title }}（{{ ticket.status === 'open' ? '待处理' : '已关闭' }}）
        </li>
      </ul>
    </template>
  </section>
</template>
```

请求顺序的概念说明：

```text
发起请求 A（关键词 a）
用户快速输入，发起请求 B（关键词 ab），取消 A
A 即使稍后返回，也因 abort 被忽略
B 的结果成为唯一被采纳的数据
```

表单提交的防重复提交与列表请求略有不同：提交动作一般应禁用按钮、保留在途请求，而不是每次点击都 abort；具体策略取决于业务是否允许覆盖。

#### 4.3 常见误区

> loading 在请求失败后忘记关闭，按钮一直转圈。

应在 finally 中关闭 loading，并为失败提供重试入口。

> 用“先请求到的结果为准”就能避免竞态。

网络返回顺序不保证与发起顺序一致，必须靠取消、序列号或服务端状态库处理。

### 5. Vue Query：服务端状态的正式方案

#### 5.1 定义

Vue Query 是 TanStack Query 的 Vue 适配，提供缓存、自动重新验证、重试、去重、失效与乐观更新等能力。它与 React 版共享同一核心，只是消费方式变为组合式 API。

```text
useQuery：声明查询，返回 data、isPending、isError、error 等
useMutation：声明变更动作，成功后让相关查询失效并重新获取
QueryClient：缓存与配置中心，通过 VueQueryPlugin 安装
```

#### 5.2 与 Web 的关系

当应用存在多个列表、详情与筛选页面时，手写缓存与竞态逻辑会重复且容易出错。Vue Query 把服务端状态从 Pinia 与组件中分离，开发者声明 queryKey 与查询函数即可。

安装与配置：

```ts
// src/main.ts
import { VueQueryPlugin, QueryClient } from '@tanstack/vue-query';

const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 30_000,
      retry: 1,
    },
  },
});

app.use(VueQueryPlugin, { queryClient });
```

组件中使用：

```vue
<script setup lang="ts">
import { computed } from 'vue';
import { useQuery } from '@tanstack/vue-query';
import { fetchTickets } from '../api/tickets';

const { data, isPending, isError, error, refetch } = useQuery({
  queryKey: ['tickets'],
  queryFn: ({ signal }) => fetchTickets(signal),
});

const tickets = computed(() => data.value ?? []);
</script>

<template>
  <section>
    <p v-if="isPending">正在加载…</p>
    <div v-else-if="isError" role="alert">
      {{ error?.message }}
      <button type="button" @click="refetch">重试</button>
    </div>
    <p v-else-if="tickets.length === 0" class="empty">暂无工单</p>
    <ul v-else>
      <li v-for="ticket in tickets" :key="ticket.id">{{ ticket.title }}</li>
    </ul>
  </section>
</template>
```

变更后失效相关查询：

```ts
import { useMutation, useQueryClient } from '@tanstack/vue-query';
import { closeTicket } from '../api/tickets';

const queryClient = useQueryClient();

const mutation = useMutation({
  mutationFn: (id: number) => closeTicket(id),
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: ['tickets'] });
  },
});
```

与 React 版完全对应：queryKey 设计、staleTime、gcTime、invalidate、乐观更新等概念一致；差别只在 `data.value` 这类组合式解包。

#### 5.3 与 Pinia 的边界

```text
Vue Query：来自服务器、需要缓存与重新验证的数据
Pinia：登录会话、权限、主题密度等客户端状态
URL：筛选、分页、详情 id
组件：弹窗开合等局部临时状态
computed：从已有数据直接派生的值
```

简单页面可以只用第 3、4 节的手写请求；一旦出现跨页面缓存、共享列表、自动刷新与复杂失效，应采用 Vue Query，而不是把远程快照塞进 Pinia 手工维护。

#### 5.4 常见误区

> Vue Query 会替代所有状态管理。

它只管服务端状态；主题、会话与 UI 偏好仍由 Pinia 或组件承担。

> 使用 Query 后不需要 loading/error/empty。

这些状态由库提供标志位，但界面仍必须完整表达三种结果，不能因为有缓存就忽略空态与错误。

### 6. 组件测试：Vue Test Utils 加 Vitest

#### 6.1 定义

组件测试验证一个组件在浏览器般的环境中，面对输入与用户操作时是否表现出正确行为。Vue Test Utils 负责把 SFC 挂载到 jsdom 并提供查询、触发事件与 setValue 等工具；Vitest 提供运行器、断言与 Mock。

```text
mount：完整挂载，含子组件
shallowMount：把后代组件存根，隔离当前组件
wrapper：测试包裹器，可查询 DOM、读取 emitted、触发事件
```

#### 6.2 与 Web 的关系

组件测试位于纯函数单元测试与 E2E 之间：比单元测试贴近用户，比 E2E 快速稳定。测试应面向行为（渲染了什么、用户能做什么、抛出了什么事件），而不是断言内部某个 ref 的实现细节。

配置：

```ts
// vitest.config.ts
import { defineConfig } from 'vitest/config';
import vue from '@vitejs/plugin-vue';

export default defineConfig({
  plugins: [vue()],
  test: {
    environment: 'jsdom',
    globals: false,
    include: ['src/**/*.test.ts'],
  },
});
```

一个 props 渲染测试：

```ts

    expect(wrapper.text()).toContain('待处理');

```

#### 6.3 可维护性原则

- 查询优先使用可访问的角色、标签与文本；data-test 用于语义不足时兜底。
- 不快照大段 HTML；快照对内部改动过敏，难以表达行为意图。
- 网络依赖用 vi.mock 或 MSW 拦截，不访问真实网络。
- 每个测试可独立运行，不依赖前一个测试留下的状态。

#### 6.4 常见误区

> 通过修改组件内部 ref 来“造数据”更快。

测试内部状态会让重构时测试大面积失效。应通过 props、用户操作与 Mock 接口构造场景。

> 异步测试加固定 setTimeout 等待。

应使用 flushPromises、findBy 类查询或等待可观察结果，固定延时既慢又不稳定。

### 7. 端到端测试：Playwright 关键用户流

#### 7.1 定义

端到端测试在真实浏览器中启动完整应用，按用户路径操作并验证结果，覆盖组件测试无法保证的集成链路：路由、请求、构建产物与浏览器行为。Playwright 的测试代码不关心框架实现，Vue 与 React 应用使用同一套 API 与配置。

#### 7.2 与 Web 的关系

工单模块至少有一条关键流必须被 E2E 保护：登录、新建工单、列表出现新工单、打开详情。E2E 数量应少而关键，把细节校验留给组件测试。

配置：

```ts

```

#### 7.3 选择器与可访问性

```text
优先 getByRole，配合可访问名称
其次 getByLabel（表单）、getByText
getByTestId 仅在没有更好语义时使用
避免依赖易变的 CSS 结构与 nth 序号
```

这套查询同时倒逼界面具备正确的角色、label 与键盘可用性，与 React 单元的 E2E 经验完全互通。

#### 7.4 常见误区

> 为每个组件写 E2E，覆盖率最高。

E2E 慢且定位成本高，应覆盖跨页面关键流与高风险回归，细枝末节交给组件测试。

> E2E 直接依赖真实后端数据。

应通过独立测试环境、固定种子数据或接口拦截保证可重复，避免测试因数据变化而随机失败。

### 8. 生态集成、可访问性与演进方向

#### 8.1 定义

生态集成是指在 Vue 核心之外，按统一约定接入第三方库、可访问性要求与编译演进能力，并让它们与组件树、响应式系统及构建工具协同。它不是“多装几个包”，而是回答每一类数据与副作用分别应该放在哪一层。

Vue 模块四个单元建立了一套完整的状态决策体系：

```text
局部临时状态：ref/reactive，放在使用组件
派生状态：computed
可分享的查询与分页：路由查询参数
跨页面客户端状态：Pinia
服务端状态：手写请求加三态，或 Vue Query
有状态逻辑复用：Composable，必要时用 VueUse
```

#### 8.2 与 Web 的关系：第三方库与可访问性集成

周边生态按需接入：图表、地图、富文本等优先选择支持 Vue 3 组合式 API、维护活跃的库；接入第三方命令式库时使用模板引用与生命周期，并在卸载时调用其销毁方法。

```ts
// 概念示例：把一个命令式第三方库纳入 Vue 生命周期
import { onBeforeUnmount, onMounted, ref } from 'vue';

type ThirdPartyWidget = { destroy: () => void };

function createThirdPartyWidget(_container: HTMLElement): ThirdPartyWidget {
  // 真实项目在此调用第三方库的构造函数
  return {
    destroy() {
      console.log('释放第三方库资源');
    },
  };
}

const containerRef = ref<HTMLElement | null>(null);
let widget: ThirdPartyWidget | null = null;

onMounted(() => {
  if (containerRef.value) {
    widget = createThirdPartyWidget(containerRef.value);
  }
});

onBeforeUnmount(() => {
  widget?.destroy();
  widget = null;
});
```

可访问性要求同样要落到模板中，一个带错误关联的可复用字段如下：

```vue
<script setup lang="ts">
defineProps<{
  label: string;
  error?: string;
  modelValue: string;
}>();

const emit = defineEmits<{
  'update:modelValue': [value: string];
}>();
</script>

<template>
  <div class="form-field">
    <label>
      {{ label }}
      <input
        :value="modelValue"
        :aria-invalid="Boolean(error)"
        :aria-describedby="error ? `${label}-error` : undefined"
        @input="emit('update:modelValue', ($event.target as HTMLInputElement).value)"
      />
    </label>
    <p v-if="error" :id="`${label}-error`" class="field-error">{{ error }}</p>
  </div>
</template>
```

可访问性不是单独一章的点缀，应贯穿表单与测试：

- 每个输入有可见 label 或 `aria-label`，错误通过 `aria-describedby` 关联。
- 关键操作可通过键盘完成，焦点在弹窗打开与关闭时有明确移动与归还。
- 动态加载与错误信息使用 `aria-live`，让辅助技术能够播报。
- E2E 以角色与名称查询，天然检查语义是否完整。

#### 8.3 Vapor 编译模式与演进方向

Vue 生态持续演进。Vapor Mode（无虚拟 DOM 的编译策略方向）是官方讨论与逐步推进的编译模式：目标是在合适场景下，让模板在编译阶段生成更直接的 DOM 操作代码，减少运行时虚拟节点开销。其启用方式、支持范围与稳定性应以官方最新口径与当前版本发布说明为准，不要依据非官方传闻提前改造项目。

学习这一信息的正确姿态：

```text
理解编译时优化是趋势：把更多工作从运行时移到构建阶段
新项目仍以当前稳定版的标准响应式与虚拟 DOM 为主线
关注官方发布说明与迁移指南，特性稳定且业务受益时再评估引入
```

类似地，服务端渲染（SSR）、静态站点生成（SSG）与 Nuxt 等上层方案会在后续工程化模块展开，本单元不提前展开其配置。

#### 8.4 常见误区

> 听到新编译模式，就应立刻在项目中开启。

演进特性在未稳定、未与业务需求匹配前贸然引入，会增加维护风险。应以官方口径、真实收益与团队成本共同决策。

> 使用了流行 UI 组件库，可访问性与表单错误就不用再管。

组件库提供基础能力，字段关联、焦点管理与错误回填仍需按业务实现并验证。

4. Playwright 覆盖：进入新建页、填写表单、提交后看到详情、返回列表看到新工单；再覆盖一条校验失败流。
5. E2E 选择器优先使用角色与标签，不依赖易变 CSS 结构。
6. 测试与应用代码一起通过构建，README 写明运行方式。
