## 目标

## 详细的理论知识讲解和示例伪代码

### 1. 浏览器的多进程架构

#### 定义

进程是操作系统分配资源的最小单位，线程是进程内部执行指令的单位，同一进程内的线程共享内存。现代浏览器采用多进程架构，把不同职责放进不同进程：

- 浏览器进程（Browser Process）：浏览器的"主控"，负责地址栏、书签、前进后退、窗口管理，以及协调其他进程。
- 渲染进程（Renderer Process）：负责把 HTML、CSS、JavaScript 变成用户看到的页面，运行排版引擎与 JavaScript 引擎。
- GPU 进程：负责统一处理 GPU 指令，支撑硬件加速的合成与绘制。
- 网络进程（Network Service / Utility Process）：负责发起网络请求、管理连接与资源缓存。
- 此外还有插件进程、音频进程、存储进程等工具进程，按需创建。

#### 与 Web 的关系

多进程架构最直接的价值是稳定性与安全性：一个标签页的渲染进程崩溃（通常是页面脚本或复杂图形导致），通常只影响该标签页，不会拖垮整个浏览器；GPU 进程异常时页面可能黑屏，但浏览器外壳仍可操作。打开任务管理器可以看到：浏览器只有一个主进程，但每个标签页通常对应一个独立渲染进程。

在任务管理器中可以观察到的现象：

```text
任务管理器（示意，数值仅为说明格式）
任务                         内存占用      CPU    进程 ID
浏览器                        180 MB        0.2    1024
网络服务                       45 MB        0.1    2048
GPU 进程                      120 MB        1.0    2051
标签页：周刊首页               260 MB        3.5    3100
标签页：数据后台               310 MB        8.2    3120
子框架：https://example-pay…   90 MB        0.4    3188
```

各进程协作完成一次页面访问的过程：

```text
用户在地址栏输入网址并回车
  → 浏览器进程处理输入，通知网络进程发起请求
  → 网络进程建立连接、接收响应头与响应体
  → 浏览器进程判断响应是 HTML，准备一个渲染进程
  → 渲染进程解析 HTML/CSS、执行 JS、生成页面
  → 绘制指令交给 GPU 进程合成后显示到屏幕
```

渲染进程内部又是多线程的：

```text
渲染进程
├── 主线程        运行 JS、解析 HTML/CSS、布局、绘制记录（绝大多数前端关注点都在这里）
├── 合成线程      分块、处理图层、配合 GPU 合成
├── 光栅线程池    把图层块转成位图
└── 工作线程      由 Web Worker 等 API 创建，可执行 JS 但不能直接操作 DOM
```

```text
关键结论：
  普通 JavaScript 跑在渲染进程的主线程上
  主线程同时还要负责布局、绘制记录等工作
  所以一段长时间运行的 JS 会让整个页面"卡住"
```

#### 常见误区

> 开一个标签页就只有一个进程为它服务。

标签页的渲染进程是独立的，但网络、GPU、浏览器主进程由所有标签页共享；某些情况下同一站点的多个标签页还会复用渲染进程。

> JavaScript 是多线程语言，所以页面能一边跑脚本一边响应点击。

普通脚本始终在主线程单线程执行。能"同时"响应，是因为任务之间有间隙、事件循环在调度；真正的并行需要 Web Worker，而 Worker 不能直接操作 DOM。

### 2. 站点隔离与安全边界

#### 定义

站点隔离（Site Isolation）是浏览器的一项安全架构：把不同站点（site，由协议、注册域名等决定，比 origin 的粒度略宽）的页面放进彼此独立的渲染进程，跨站 iframe 也运行在单独的进程中。它基于操作系统的进程内存隔离，配合同源策略，形成更强的防线。

#### 与 Web 的关系

同源策略限制 JavaScript 跨源读取数据，但历史上恶意页面仍可能利用 CPU 的推测执行漏洞（如熔断、幽灵类漏洞）读取同进程内其他站点的内存。站点隔离让银行页面和可疑广告页面根本不在同一进程，从内存层面无法互访。代价是内存占用上升、进程数增多，跨站 iframe 间的通信也需要走进程间消息。

用一个包含跨站 iframe 的页面观察进程：

```html
<!doctype html>
<html lang="zh-CN">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>站点隔离观察</title>
  </head>
  <body>
    <h1>主页面：weekly.example</h1>
    <!-- 跨站内容：与主页面不同注册域名，会被放进独立渲染进程 -->
    <iframe
      src="https://payment.example.net/checkout"
      title="支付窗口"
      width="100%"
      height="320"
    ></iframe>
  </body>
</html>
```

在任务管理器中应能看到：

```text
标签页：weekly.example 的页面        进程 ID 3100
子框架：https://payment.example…    进程 ID 3188   ← 独立进程
```

区分同源、跨源、跨站：

```text
页面 A：https://www.weekly.example:443/articles
页面 B：https://api.weekly.example/v1          → 同站（注册域名相同），但跨源（子域不同）
页面 C：https://payment.example.net/checkout   → 跨站（注册域名不同）
规则：
  同源检查：协议 + 主机名 + 端口三者完全一致
  站点检查：协议 + 注册域名（eTLD+1），子域不影响站点归属
```

站点隔离对开发的实际影响：

```text
1. 跨站 iframe 崩溃不会带走主页面。
2. 跨站 iframe 与主页面的交互必须通过 postMessage 等显式消息机制。
3. 内存敏感的页面嵌入大量跨站 iframe 时，进程数和内存会明显上升。
4. 某些浏览器的隔离策略还会区分同一站点内是否需要隔离，具体以浏览器版本为准。
```

#### 常见误区

> 同源策略已经足够，站点隔离只是重复防护。

同源策略是 JavaScript 层面的访问规则；站点隔离是操作系统进程层面的内存隔离，防御的是能绕过脚本层检查的 CPU 与内存漏洞，两者层次不同。

> 只要域名里出现同一个词就是同站。

站点由注册域名（如 `example.com` 这种公共后缀加一段）决定。`weekly-example.com` 与 `weekly.example.com` 注册域名不同，属于跨站，不能凭字符串相似判断。

### 3. 导航与文档提交

#### 定义

导航（navigation）是浏览器从"当前文档"切换到"新文档"的过程。文档提交（commit）是导航中的关键瞬间：浏览器确认响应来自可靠服务器、内容类型为 HTML 后，把渲染进程与本次导航正式绑定，开始用新响应数据替换旧文档。提交之前，页面仍显示旧内容；提交之后，地址栏更新、旧文档卸载、新页面开始解析。

#### 与 Web 的关系

理解导航链路能解释很多现象：为什么点击链接后有一小段时间地址栏还没变；为什么服务器返回下载文件时页面不跳转（响应不是 HTML，不发生文档提交）；为什么重定向会让 Network 里出现多条请求。它也是理解 TTFB、首字节、白屏时间的基础。

一次导航的完整阶段：

```text
1. 用户输入 URL 或点击链接
2. 浏览器进程进行输入处理：检查是否为搜索词、是否命中缓存、是否已有连接
3. 发起 DNS 查询、建立连接（网络进程）
4. 发送请求，等待服务器返回响应
5. 收到响应行与响应头：检查状态码（是否重定向）、Content-Type（是否 HTML）
6. 文档提交：渲染进程绑定本次导航
7. 地址栏更新、旧页面 beforeunload/unload、提交导航历史条目
8. 渲染进程接收响应体，开始解析与渲染
9. 资源继续加载，触发 DOMContentLoaded、load 等事件
```

用实验页面观察各事件时间点：

```html
<!doctype html>
<html lang="zh-CN">
  <head>
    <meta charset="UTF-8" />
    <title>导航事件观察</title>
    <script>
      document.addEventListener('readystatechange', () => {
        console.log('readyState =', document.readyState, '时间 =', performance.now());
      });
    </script>
  </head>
  <body>
    <h1>观察文档加载各阶段</h1>
    <img src="./large-image.jpg" alt="用于推迟 load 事件的大图" />
    <script>
      document.addEventListener('DOMContentLoaded', () => {
        console.log('DOMContentLoaded：DOM 解析完成，时间 =', performance.now());
      });
      window.addEventListener('load', () => {
        console.log('load：所有资源加载完成，时间 =', performance.now());
      });
    </script>
  </body>
</html>
```

控制台预期输出顺序：

```text
readyState = loading        解析开始
readyState = interactive    DOM 解析完成
DOMContentLoaded：…          与 interactive 阶段相邻
readyState = complete       图片等子资源也完成
load：所有资源加载完成…
```

不同响应类型对导航的影响：

```text
Content-Type: text/html                 → 提交文档，渲染新页面
Content-Type: application/octet-stream  → 触发下载，当前页面保留，不提交
状态码 301/302 + Location               → 浏览器跟随重定向，产生新的导航请求
状态码 204 No Content                   → 无响应体，页面保持不变
```

#### 常见误区

> 请求一发出去，页面就会立刻切换。

从发请求到文档提交之间要先收到响应头并确认是 HTML。这个等待期间旧页面仍然显示，弱网下尤其明显。

> `DOMContentLoaded` 和 `load` 是同一时刻。

`DOMContentLoaded` 在 HTML 解析完成时触发，无需等待图片、样式表等子资源；`load` 要等所有资源都加载完。页面含大图时两者可能相差数秒。

### 4. DOM、CSSOM 与渲染树

#### 定义

DOM（文档对象模型）是 HTML 解析后在内存中形成的树形结构，每个标签、文本、注释都是一个节点。CSSOM（CSS 对象模型）是 CSS 解析后形成的样式规则结构，记录选择器与声明的层级关系。渲染树（Render Tree）是 DOM 与 CSSOM 合并后的结果，只包含"需要显示"的可见节点，并为每个节点带上计算后的样式。

#### 与 Web 的关系

渲染树是渲染流水线承上启下的产物：没有它，浏览器不知道页面上有什么、各长什么样。注意渲染树与 DOM 不是一一对应：`<head>` 里的元信息不进渲染树；设置了 `display: none` 的元素在 DOM 中存在，但不进入渲染树（而 `visibility: hidden` 仍占位，会进入渲染树）。

观察解析产物之间的关系：

```html
<!doctype html>
<html lang="zh-CN">
  <head>
    <meta charset="UTF-8" />
    <title>渲染树观察</title>
    <style>
      body { font-family: sans-serif; margin: 0; }
      .visible-block { padding: 16px; background: #e0f2fe; }
      .hidden-none { display: none; }
      .invisible-keep { visibility: hidden; height: 40px; }
    </style>
  </head>
  <body>
    <div class="visible-block">我在渲染树里并占据空间</div>
    <div class="hidden-none">display:none：不在渲染树中</div>
    <div class="invisible-keep">visibility:hidden：在渲染树中，占位但不可见</div>
  </body>
</html>
```

三种可见性状态在渲染树中的区别：

```text
写法                  DOM 中   渲染树中   是否占位   可见
普通元素               是       是         是         是
display: none         是       否         否         否
visibility: hidden    是       是         是         否
opacity: 0            是       是         是         否（但仍可交互）
```

渲染树的构建过程：

```text
HTML 字节流
  → 按编码分词（开始标签、结束标签、属性、文本）
  → 生成节点，挂到 DOM 树上
  ↓
CSS（外部样式表、style 标签、行内样式）
  → 解析为 CSSOM，按选择器匹配、按层叠与继承计算
  ↓
从 DOM 根节点遍历可见节点
  → 对每个可见节点查找匹配的计算样式
  → 生成带样式的渲染对象，组成渲染树
```

CSS 为什么会阻塞渲染：

```text
浏览器在 CSSOM 没准备好之前不会渲染页面：
  如果先用无样式的 DOM 画一版，等 CSS 到达再重画，
  用户会看到"闪一下无样式内容"（FOUC）。
所以渲染要等 CSS；这也是"CSS 是阻塞渲染的资源"的原因。
不过 CSS 下载不会阻塞 HTML 解析，两者可以并行进行。
```

#### 常见误区

> DOM 树就是渲染树，两者一一对应。

`display: none` 元素、`<head>` 元信息在 DOM 中但不进渲染树；伪元素（`::before`）不是 DOM 节点却会进入渲染树。

> CSS 既阻塞 HTML 解析，又阻塞渲染。

CSS 阻塞渲染，但不阻塞 HTML 解析（解析器会继续建 DOM）。真正会暂停 HTML 解析的是同步 `<script>`，因为脚本可能读取或修改尚未解析的结构。

### 5. 布局、绘制与合成

#### 定义

渲染流水线后半段分三步：

- 布局（Layout，Chromium 新版术语也称 Layout，旧版称 Reflow 的结果阶段）：根据渲染树计算每个节点在屏幕上的精确位置与尺寸（几何信息），即"谁在哪、多大"。
- 绘制（Paint）：按绘制顺序把元素的填充、边框、文字、阴影等拆成一条条绘制记录，即"往哪些区域填什么像素效果"。
- 合成（Composite）：把页面拆成多个图层，分别光栅化为位图，再由合成线程按正确层级叠加到屏幕。

#### 与 Web 的关系

理解三步分工能解释为什么"改样式的代价不一样"：只改不影响几何的属性（如颜色、透明度）可能跳过布局；能交给合成线程处理的属性（如 `transform`、`opacity`）开销最小，是动画首选。这正是现代动画性能建议的底层依据。

制造不同阶段的可观察变化：

```html
<button type="button" id="change-geometry">改宽度（触发布局）</button>
<button type="button" id="change-color">改颜色（只触发重绘）</button>
<button type="button" id="move-layer">位移（交给合成）</button>
<div id="box" style="width: 100px; height: 100px; background: #2563eb;"></div>

<script>
  const box = document.querySelector('#box');

  document.querySelector('#change-geometry').addEventListener('click', () => {
    box.style.width = '200px';          // 几何变化 → 布局 → 绘制 → 合成
  });

  document.querySelector('#change-color').addEventListener('click', () => {
    box.style.background = '#dc2626';   // 外观变化 → 绘制 → 合成，跳过布局
  });

  document.querySelector('#move-layer').addEventListener('click', () => {
    box.style.transform = 'translateX(100px)'; // 合成属性 → 主要在合成阶段完成
  });
</script>
```

不同改动触发的流水线范围：

```text
改动内容                         布局    绘制    合成
width / height / top / left      需要    需要    需要
color / background / box-shadow  不需要  需要    需要
transform / opacity              不需要  不需要  主要由合成完成
```

光栅化与图层的工作方式：

```text
主线程把布局结果与绘制记录交给合成线程
合成线程把页面切成图层，并按视口分块（tile）
光栅线程池只优先光栅化可见区域的块
滚动时，已光栅化的块直接移动，新块按需光栅化
  → 这就是滚动可以非常流畅的原因
```

用 CSS 提示浏览器把元素提升为独立图层：

```css
.animated-card {
  will-change: transform;          /* 提前告知该元素将变化，便于浏览器准备图层 */
}

.animated-card.promoted {
  transform: translateZ(0);        /* 传统写法：触发独立图层，现代项目优先 will-change */
}
```

```text
注意：
  图层不是越多越好。每个图层占内存，移动端尤其昂贵。
  只在确实需要频繁合成动画的少数元素上使用 will-change。
```

#### 常见误区

> 修改任何 CSS 属性都要走一遍完整流水线。

布局、绘制、合成的触发范围取决于改动内容。动画用 `transform` 与 `opacity`，可以绕开主线程的布局与绘制，显著更流畅。

> 加了 `translateZ(0)` 页面就一定变快。

盲目提升图层会增加内存占用与合成开销，图层过多反而更慢。提升图层要基于性能证据，而不是全局滥用。

### 6. 重排、重绘与布局抖动

#### 定义

重排（reflow，也称回流）：当 DOM 结构、几何样式或窗口尺寸变化时，浏览器重新计算元素几何信息的过程，对应流水线中的布局阶段。重绘（repaint）：元素外观变化但几何不变时，重新生成绘制记录的过程。重排必定引发后续重绘，重绘不一定经过重排。

强制同步布局（forced synchronous layout）：JavaScript 先修改了样式，紧接着读取 `offsetWidth` 等布局属性，浏览器为了给出最新值，不得不立即、同步地执行一次布局，而不是等到本帧末尾批量处理。在循环里反复"修改—读取"会造成布局抖动（layout thrashing）。

#### 与 Web 的关系

重排的代价与影响范围有关：改一个子元素的宽度，可能只重排局部；改顶层字体或窗口尺寸，可能导致整个文档重排。动画循环里发生强制同步布局，是长列表滚动、拖拽卡顿最常见的根因之一。

演示布局抖动的典型反模式：

```html
<div id="list"></div>
<script>
  const list = document.querySelector('#list');

  // 先造一批元素
  for (let i = 0; i < 100; i += 1) {
    const item = document.createElement('div');
    item.className = 'item';
    item.textContent = `条目 ${i}`;
    list.appendChild(item);
  }

  // 反模式：循环内"先写样式，再读布局"，每轮都强制同步布局
  const items = document.querySelectorAll('.item');
  for (let i = 0; i < items.length; i += 1) {
    items[i].style.width = `${100 + i}px`;   // 写：标记布局失效
    const measured = items[i].offsetHeight;  // 读：逼浏览器立刻重排
    items[i].dataset.height = measured;
  }
</script>
```

重构为先读后写、批量操作：

```js
const items = document.querySelectorAll('.item');

// 第一步：先批量读取所有布局值（此时布局只需计算一次）
const heights = Array.from(items).map((item) => item.offsetHeight);

// 第二步：再批量写入，浏览器在帧末统一重排一次
items.forEach((item, i) => {
  item.style.width = `${100 + i}px`;
  item.dataset.height = heights[i];
});
```

用临时离线处理避免多次重排：

```js
// 对一个元素做大量改动时，先隐藏、改完再显示，只触发两次布局
box.style.display = 'none';
box.classList.add('complex-layout');
box.style.padding = '24px';
box.style.border = '1px solid #ccc';
box.style.display = '';
```

```text
常见会触发布局读取的属性（节选）：
  offsetWidth / offsetHeight / offsetTop / offsetLeft
  clientWidth / clientHeight
  getBoundingClientRect()
  scrollTop / scrollHeight
原则：连续读取它们之前，不要穿插样式写入。
```

减少重排影响范围的其他手段：

```text
1. 用 className 或 CSS 文本批量改样式，而不是逐条改 style。
2. 对需要频繁变化的元素，让它脱离普通文档流（如定位、独立图层），缩小重排范围。
3. 动画尽量使用 transform，而不是改 top/left/width。
4. 表格布局重排成本高，避免用大表格承载动画区域。
```

#### 常见误区

> 重排和重绘只是名字不同，开销差不多。

重排要重新计算几何并级联影响子树，通常远比重绘昂贵；重绘只更新像素外观。能用重绘解决的不要触发重排，能合成解决的不要触发重绘。

> 读取 `offsetWidth` 是只读操作，不会有性能代价。

如果此前有未应用的样式改动，读取会强制浏览器立即布局。代价不在"读"本身，而在它迫使布局提前、同步发生。

### 7. JavaScript 阻塞与 async/defer

#### 定义

HTML 解析器遇到没有特殊标记的 `<script>` 时，会暂停解析，下载（若为外部脚本）并立即执行脚本，执行完才继续解析后面的 HTML。这是因为脚本可能调用 `document.write`、读取或修改 DOM，浏览器无法跳过它继续。

两个属性改变外部脚本的行为：

- `defer`：脚本并行下载，不阻塞解析；等 HTML 全部解析完成后、`DOMContentLoaded` 之前，按文档顺序执行。
- `async`：脚本并行下载，下载完成后立即执行，执行时仍会阻塞解析；多个 async 脚本执行顺序不确定。
- 模块脚本（`type="module"`）默认具备 defer 的时序特性。

#### 与 Web 的关系

首屏放置大体积同步脚本，会让用户长时间面对白屏或半成品页面。合理的脚本加载策略是关键渲染路径优化的核心一环：不影响首屏的脚本延后，依赖 DOM 的脚本用 defer，完全独立的第三方统计脚本可用 async。

对比四种脚本写法的时序：

```html
<!-- 1. 普通脚本：遇到即阻塞，下载 + 执行期间 HTML 停止解析 -->
<script src="./heavy.js"></script>

<!-- 2. defer：后台下载，DOM 解析完后按顺序执行 -->
<script src="./app.js" defer></script>

<!-- 3. async：下载完立刻执行，顺序不保证，执行时仍阻塞解析 -->
<script src="./analytics.js" async></script>

<!-- 4. 模块脚本：默认 defer 时序，延迟到解析完成后 -->
<script type="module" src="./main.js"></script>
```

时序示意（横轴为时间）：

```text
普通脚本：
  解析HTML ──┤下载+执行 heavy├──┤继续解析HTML ──┤DOMContentLoaded

defer：
  解析HTML ──────────────────────────┤执行 app│DOMContentLoaded
            └─下载 app（并行）────────┘

async：
  解析HTML ──────┤执行 analytics├──┤继续解析…
            └下载 analytics（并行）┘
```

选择策略的决策表：

```text
脚本类型                         推荐方式
依赖完整 DOM、脚本间有依赖顺序    defer（或放在 body 末尾）
独立的第三方统计、监控            async
首屏必需且极小的内联配置          普通内联脚本，保持精简
现代模块化业务代码                type="module"
```

用一个实验页面验证阻塞：

```html
<!doctype html>
<html lang="zh-CN">
  <head>
    <meta charset="UTF-8" />
    <title>脚本阻塞观察</title>
    <!-- 该脚本执行约 2 秒；普通写法下，下面的 h1 会延迟出现 -->
    <script src="./slow-sync.js"></script>
  </head>
  <body>
    <h1>如果脚本是同步的，我会晚两秒出现</h1>
  </body>
</html>
```

```js
// slow-sync.js：用有限循环模拟约两秒的同步计算
const deadline = Date.now() + 2000;
while (Date.now() < deadline) {
  // 空转，仅用于实验；生产代码中绝不应这样阻塞主线程
}
console.log('同步脚本执行完毕');
```

把它改成 `<script src="./slow-sync.js" defer></script>` 后，标题立即可见，脚本在解析完成后才执行。

#### 常见误区

> `async` 和 `defer` 都让脚本不阻塞，效果一样。

`defer` 保证在 DOM 就绪后按顺序执行；`async` 下载完就插队执行，顺序随机且执行时仍阻塞解析。有依赖关系的业务脚本用 async 会出现时序错误。

> 把脚本放在 `<head>` 里一定会阻塞首屏。

加了 `defer` 或使用模块脚本后，放在 head 中也不会阻塞解析。关键不在位置，而在加载与执行时序。

### 8. 关键渲染路径与优化

#### 定义

关键渲染路径（Critical Rendering Path）是浏览器完成首屏渲染所必须经历的最小步骤集合：请求 HTML → 构建 DOM → 请求并构建 CSSOM → 合成渲染树 → 布局 → 绘制 → 合成。路径上阻塞渲染的资源（CSS、同步 JS）越少、体积越小，首屏出现得越早。

#### 与 Web 的关系

首屏速度直接影响用户留存，企业项目中大量优化工作都围绕关键渲染路径展开：精简与压缩关键资源、推迟非关键资源、内联极小的关键样式、预连接关键域名、让脚本不再阻塞。优化原则是"让浏览器尽早拿到渲染首屏所需的最小集合，其余的延后"。

优化前后的页面对比：

```html
<!-- 反例：head 中两个大体积同步脚本 + 未优化的整站样式表 -->
<head>
  <script src="./vendor-large.js"></script>
  <script src="./app-large.js"></script>
  <link rel="stylesheet" href="./all-pages.css" />
</head>
```

```html
<!-- 优化：关键 CSS 内联或精简，样式表拆分，脚本全部延迟，提前建立关键连接 -->
<head>
  <meta name="viewport" content="width=device-width, initial-scale=1" />
  <!-- 提前与关键域名建立连接，减少后续请求的握手等待 -->
  <link rel="preconnect" href="https://cdn.weekly.example" />
  <!-- 首屏必需的极小关键样式内联 -->
  <style>
    body { margin: 0; font-family: system-ui, sans-serif; }
    .hero { min-height: 60dvh; display: grid; place-items: center; }
  </style>
  <!-- 非首屏样式通过媒体条件延迟应用；其余业务脚本全部 defer/module -->
  <link rel="stylesheet" href="./critical.css" />
  <link rel="stylesheet" href="./rest.css" media="print" onload="this.media='all'" />
  <script type="module" src="./main.js"></script>
</head>
```

资源提示类标签的作用：

```text
<link rel="preconnect" href="…">   提前完成 DNS、连接、TLS 握手
<link rel="dns-prefetch" href="…"> 仅提前做 DNS 查询，成本更低
<link rel="preload" href="…" as="style"> 提前高优先级加载关键资源
<link rel="prefetch" href="…">     预取下一页可能用到的资源，优先级低
```

关键渲染路径优化清单：

```text
HTML：
  1. 精简结构，压缩传输（gzip / brotli）。
  2. 首屏 HTML 由服务端尽快返回，避免在服务器上长时间拼装。

CSS：
  3. 只加载首屏需要的关键 CSS，其余延迟或按路由拆分。
  4. 避免用 @import 串行加载样式表（@import 中的资源要等解析到才请求）。
  5. 字体文件合理设置来源与显示策略，减少文字不可见时间。

JavaScript：
  6. 同步脚本改为 defer/module，第三方独立脚本用 async。
  7. 代码分割，首屏不加载与首屏无关的大脚本。
  8. 把长任务拆小，避免主线程被长时间占用（细节在性能单元展开）。
```

衡量优化是否生效的观测点：

```text
在 Network 与 Performance 中确认：
  首条 HTML 请求的首字节是否更早（TTFB）
  首次出现内容的时间是否提前（FCP）
  渲染阻塞资源的数量与体积是否下降
  主线程长任务是否减少
指标采集与判读将在第 16 单元系统学习。
```

#### 常见误区

> 把所有 CSS、JS 都合并成一个文件，请求数最少就最快。

单个大文件可能包含大量首屏用不到的代码，反而推迟首屏；它还会拖累缓存命中率。现代实践倾向按首屏需要做代码分割与资源提示，而不是一味追求单文件。

> 优化就是把脚本一律加上 `async`。

有依赖顺序的业务脚本 async 后会乱序执行。优化必须结合脚本依赖关系选择 defer、async 或 module，并在性能工具中验证效果，而不是机械套用。

线上一个内容页面被投诉"手机上打开先白很久，滚动还一卡一卡"。团队要求你不仅要优化，还要用浏览器机制解释清楚：为什么白、为什么卡、每一项改动动了渲染流水线的哪一段。你需要交付一套可复现的实验项目，包含"问题版本"与"优化版本"，并用进程、导航、流水线、脚本时序四类证据支撑结论。

### 演示步骤

学员需在 15 分钟内完成以下现场演示：

1. 打开任务管理器，指认为本项目服务的浏览器、渲染、GPU、网络进程，并展示跨站 iframe 的独立进程。
2. 在导航页面中结合控制台时间戳，讲清文档提交、`DOMContentLoaded`、`load` 三个节点。
3. 对着自己绘制的流水线图，用自己的语言串讲 DOM、CSSOM、渲染树、布局、绘制、合成。
4. 现场触发抖动版列表并展示 Performance 录制中的密集布局；再触发优化版，对比布局次数与耗时。
5. 依次切换普通、defer、async、module 四种脚本，让导师观察标题出现时间与执行顺序。
6. 展示优化前后的 Network，对比渲染阻塞资源数与首次内容时间。
7. 用一句话总结每条优化措施动了流水线的哪个阶段。

导师可以临时调整脚本时长、断点宽度或元素数量，验证学员是否真正理解机制。

### 强制不通过条件

出现以下任一情况，本次验收不通过；修正后重新验收：

1. 无法区分浏览器进程、渲染进程与线程，或认为普通 JavaScript 是多线程并行执行。
2. 把 `DOMContentLoaded` 与 `load` 混为一谈，或无法解释文档提交的含义。
3. 认为 DOM 树与渲染树完全一一对应，对三种可见性状态的区别判断错误。
4. 布局抖动练习只改了代码却拿不出优化前后的 Performance 证据，或反例中没有真正的"写后读"。
5. 认为 `async` 与 `defer` 效果相同，或在有依赖顺序的脚本上错误使用 async 导致执行乱序。
6. 使用无终止条件的死循环模拟阻塞，造成设备长时间失去响应。
7. 只提交截图或结论，缺少可运行页面、录制记录与过程说明。
