# 请求、HTTP 与缓存：从地址到可解释的响应

本章把一次网页请求拆成三层证据：先确认 URL、名称、连接与 TLS，再按 HTTP 方法、状态和表示处理响应，最后验证缓存与跨源读取。目标不是背瀑布图，而是能判断失败发生在哪一层。

## 本章任务

你将为邻里集市建立一组本地网络实验：

1. 分解商品 URL，观察本机解析、连接和协议字段。
2. 运行支持状态、语言协商与 gzip 的 Node HTTP 服务。
3. 复现条件请求的200/304以及 CORS 允许、拒绝和预检。
4. 用同一份诊断格式记录现象、证据、原因、修复和复验。

章级产出是“商品公告请求诊断包”：三组完整源码、Network 记录、curl 条件请求记录、缓存决策表和一份故障复验表。

| 顺序 | 教程 | 核心问题 | 建议投入 | 关键证据 |

## 邻里集市综合任务

在个人目录完成“商品公告请求诊断包”：

```text
network-evidence/
  url-connection.md
  http-status.md
  cache-cors.md
  decision-table.md
```

`decision-table.md` 至少回答：

| 决策 | 必须说明 |
| --- | --- |
| 入口 HTML 缓存 | 如何发现新版本 |
| 内容哈希 JS/CSS | 为什么可长期缓存 |
| 公开商品列表 | 新鲜期、验证器和查询键 |
| `/auth/me` | 隐私与共享缓存边界 |
| 跨源 API | 精确允许源、预检、凭据 |
| 商品编辑 | CORS、CSRF、认证、对象授权各自职责 |

价格继续使用整数分，时间继续使用 UTC ISO 8601。实验数据必须标记为本地内存数据；本章不实现真实登录、持久化或生产 HTTPS。

## 综合验收

- [ ] 三篇教程的 Node/HTML/JS 完整文件均能按说明启动。
- [ ] 能用 URL API 证明片段没有进入服务端请求目标。
- [ ] 能区分名称解析、连接、TLS、HTTP 状态和业务错误。
- [ ] 200、204、404、405、406 均有实际证据，204 不解析 JSON。
- [ ] 条件请求形成200、304、版本变化后200的记录。
- [ ] 能解释浏览器脚本状态与 Network 304 的不同视角。
- [ ] CORS 允许、拒绝读取和预检各有证据。
- [ ] 能证明跨源脚本不可读不等于写请求没有到达服务。
- [ ] 缓存决策覆盖入口、哈希资源、公开列表和个人接口。
- [ ] 每个故障均有“现象、证据、原因、修复、复验”。
- [ ] 明确记录未验证的真实 CDN、代理、Firefox、Safari、移动网络与生产证书。

验收时随机改变一个端口、一个状态路径和一个 ETag，学习者应能在不改无关代码的情况下定位并恢复。
