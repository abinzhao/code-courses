# 09-HTML 文档结构与语义化

## 目标

完成本知识单元后，学员应能够把一个网页视为“有结构的文档”，而不是一堆等待 CSS 摆放的方框。学员应能够：

1. 根据页面草图独立写出符合 HTML5 规范的完整文档骨架，正确放置 `doctype`、`html`、`head`、`body`，并配置字符编码与视口元信息。
2. 面对一段真实内容，依据其含义选择 `header`、`nav`、`main`、`section`、`article`、`aside`、`footer`、`figure`、`time` 等语义标签，并口头说明每个选择的理由与可替代方案。
3. 为一篇多章节文章设计不跳级、不重复的标题层级，并能口述由标题与分区共同形成的文档大纲。
4. 使用 `ul`、`ol`、`dl` 和完整的 `table` 系列标签组织列表与表格数据，解释每个子标签在语义上的职责。
5. 为页面配置 `title`、`description` 与 Open Graph 元数据，并使用 W3C 校验工具定位、分类和修复标记错误。
6. 在确无合适语义标签时才使用 `div` 与 `span`，并能向他人解释语义化对搜索引擎、读屏器和团队维护的具体价值。

## 详细的理论知识讲解和示例伪代码

### 1. HTML 文档的整体骨架

#### 1.1 定义

HTML（HyperText Markup Language）是用标记描述网页结构和内容含义的语言。一个最基本的 HTML5 文档由四部分组成：

1. `<!doctype html>`：文档类型声明，位于文件第一行，告知浏览器按 HTML5 的标准模式（standards mode）解析文档。
2. `<html>`：根元素，包裹页面全部内容，`lang` 属性声明文档主语言。
3. `<head>`：文档元数据区，存放不直接显示在页面正文里的信息，如字符编码、标题、样式与脚本引用。
4. `<body>`：文档主体区，用户在页面中看到的内容都在这里。

#### 1.2 与 Web 的关系

浏览器收到服务器返回的 HTML 字节流后，先依据 `doctype` 决定解析模式，再把标记解析成 DOM 树。搜索引擎爬虫、阅读模式、读屏器都以这棵树和标签语义为工作基础。

如果缺少 `doctype` 或把它写错，浏览器可能进入怪异模式（quirks mode），按十年前的旧规则渲染盒模型，导致同一套 CSS 在不同页面表现不一致。

完整骨架示例：

```html
<!doctype html>
<html lang="zh-CN">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>页面标题</title>
  </head>
  <body>
    <main>
      <h1>页面主标题</h1>
      <p>第一段正文。</p>
    </main>
  </body>
</html>
```

#### 1.3 各部分的职责边界

| 部分 | 是否显示在正文 | 典型内容 | 常见错误 |
|---|---|---|---|
| `doctype` | 否 | 仅此一条声明 | 写成旧版的长串 DTD，或漏写 |
| `html` | 否（作为容器） | `lang`、`dir` 属性 | 在文档中出现第二个根元素 |
| `head` | 否 | `meta`、`title`、`link`、`script` | 把正文内容误放进 `head` |
| `body` | 是 | 所有可见结构 | 同一页面出现多个 `body` |

#### 1.4 常见误区

> `<!doctype html>` 是一个需要闭合的 HTML 标签。

它是文档类型声明，不是元素，没有结束标签，也不区分大小写，但约定写成小写形式。

> `lang="zh-CN"` 只是给搜索引擎看的，写不写无所谓。

`lang` 会影响读屏器选用的发音语音、浏览器的翻译建议和 hyphenation（断字）规则。混合语言页面还可以在局部元素上用 `lang="en"` 标注一段英文引述。

### 2. head 中的元信息与资源引用

#### 2.1 定义

元数据（metadata）是“关于文档的数据”。`head` 中最常用的元信息包括：

- `<meta charset="UTF-8" />`：声明字符编码，保证中文不乱码。
- `<meta name="viewport" ... />`：声明视口规则，使页面在手机上按设备宽度布局。
- `<title>`：文档标题，显示在浏览器标签页、收藏夹和搜索结果中。
- `<meta name="description" ... />`：页面内容摘要。
- `<link>`：引用外部资源，最常见的是样式表与图标。
- `<script>`：引用或内嵌脚本，可放在 `head` 或 `body` 中。

#### 2.2 与 Web 的关系

字符编码必须在解析早期确定。规范要求 `charset` 声明尽量出现在文档前 1024 个字节内，否则浏览器可能已经按错误编码猜测并解析了部分内容，出现“中文变乱码”。

`viewport` 是移动端布局的前提。没有它，手机浏览器会按约 980px 的虚拟视口渲染再缩放，用户看到的字会很小；加上视口声明后，CSS 中的布局宽度才与设备实际宽度对应。

#### 2.3 示例

```html
<!doctype html>
<html lang="zh-CN">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>城市书店 - 首页</title>
    <meta name="description" content="城市书店是一家社区独立书店，提供新书推荐、作者沙龙与深夜阅读空间。" />
    <link rel="stylesheet" href="./styles.css" />
    <link rel="icon" href="/favicon.ico" />
  </head>
  <body>
    <main>
      <h1>城市书店</h1>
    </main>
    <script src="./main.js" defer></script>
  </body>
</html>
```

资源引用路径说明：

```text
./styles.css     当前目录下的文件，推荐使用
/styles.css      站点根目录下的文件
../styles.css    上一级目录中的文件
https://...      绝对 URL，指向其他站点资源
```

#### 2.4 script 位置与 defer

- 把普通 `<script src="..."></script>` 放在 `head` 中且不加 `defer`，浏览器下载并执行脚本时会暂停解析后续 HTML，可能短暂阻塞渲染。
- 加 `defer` 的脚本会在文档解析完成后、`DOMContentLoaded` 之前按顺序执行。
- 放在 `body` 末尾也是经典做法，脚本执行时 DOM 已存在。
- `script` 元素永远需要结束标签：`<script src="x.js"></script>`，自闭合写法在 HTML 中无效。

#### 2.5 常见误区

> 只要文件保存成 UTF-8，就不需要 `<meta charset>`。

文件编码和浏览器推测编码不是一回事。跨服务器、跨浏览器传输时，没有显式声明仍可能被错误猜测，必须显式声明。

> `initial-scale=1.0` 可以防止用户手动放大页面。

它只是设置初始缩放比例。禁止缩放要用到 `maximum-scale` 与 `user-scalable=no`，这会损害低视力用户的访问能力，生产页面不应这样做。

### 3. 语义化与标题层级

#### 3.1 定义

语义化（semantics）是指标记名和属性名能够表达“这是什么内容、承担什么职责”，而不仅仅是“它长什么样”。

标题元素 `h1` 至 `h6` 表示六级章节标题，数字越小级别越高。它们共同构成文档的标题大纲（outline）：

- `h1`：页面或最高层级内容的主标题，一个页面通常只应有一个。
- `h2`：主要章节标题。
- `h3` 至 `h6`：逐级嵌套的子章节标题。

#### 3.2 与 Web 的关系

读屏器用户可以通过快捷键在标题之间跳转，快速建立对页面结构的认识；搜索引擎用标题判断内容的主次；浏览器的阅读模式也依赖标题与分区提取正文。

标题层级应当通过嵌套关系表达，不允许为了“字小一点”而跳级。

```html
<body>
  <h1>前端培养课程</h1>

  <section>
    <h2>HTML 基础</h2>
    <section>
      <h3>文档结构</h3>
      <p>本节讨论文档骨架。</p>
    </section>
    <section>
      <h3>语义化标签</h3>
      <p>本节讨论标签含义。</p>
    </section>
  </section>

  <section>
    <h2>CSS 基础</h2>
  </section>
</body>
```

上述结构形成的大纲是：

```text
前端培养课程
  HTML 基础
    文档结构
    语义化标签
  CSS 基础
```

#### 3.3 标题层级检查规则

| 规则 | 正确做法 | 错误做法 |
|---|---|---|
| 起点 | 主内容从 `h1` 开始 | 用 `div` 加粗大号字充当主标题 |
| 递进 | `h2` 下面用 `h3` | `h2` 之后直接跳到 `h4` |
| 外观 | 用 CSS 调整字号 | 因为想要小字而选用 `h5` |
| 数量 | 一个 `h1` 表示一个页面主题 | 为每个板块各放一个 `h1` |

#### 3.4 常见误区

> 页面里多个卡片都有自己的标题，所以都应该用 `h1`。

卡片标题应根据它们在整页大纲中的位置选择层级，通常是 `h2` 或 `h3`。层级由嵌套关系决定，不由视觉大小决定。

> 用了语义分区标签后，标题层级就可以随意。

分区标签与标题层级是两套互补机制。即使全部用 `section` 包裹，跳级的标题仍然会让大纲出现断层。

### 4. 地标与内容分区语义

#### 4.1 定义

HTML5 提供一组分区标签描述页面的典型区域，它们也被称为地标（landmark）角色：

| 标签 | 含义 | 典型内容 |
|---|---|---|
| `header` | 引言或导航帮助区 | 站点标志、站名、主导航、搜索框 |
| `nav` | 主要导航链接区 | 顶部菜单、面包屑、目录 |
| `main` | 页面主体内容，每页唯一 | 文章、列表、核心功能区 |
| `section` | 按主题划分的章节，通常带标题 | 文章的一章、首页的一个板块 |
| `article` | 可独立分发或复用的完整内容 | 一篇博文、一条评论、一张卡片 |
| `aside` | 与主内容相关但可分离的补充内容 | 侧边栏、相关推荐、广告 |
| `footer` | 所属区域的结尾信息 | 版权、备案号、联系链接 |

#### 4.2 与 Web 的关系

读屏器可以列出页面的所有地标并直接跳转，例如“跳到主内容”“跳到导航”。这与跳过重复的站点头部、快速获取信息密切相关。搜索引擎也借此判断正文与导航、补充内容的边界。

#### 4.3 页面级分区示例

```html
<!doctype html>
<html lang="zh-CN">
  <head>
    <meta charset="UTF-8" />
    <title>科技周刊 - 第 12 期</title>
  </head>
  <body>
    <header>
      <p>科技周刊</p>
      <nav aria-label="主导航">
        <ul>
          <li><a href="/">首页</a></li>
          <li><a href="/archive">往期</a></li>
          <li><a href="/about">关于</a></li>
        </ul>
      </nav>
    </header>

    <main>
      <article>
        <h1>第 12 期：浏览器的一年</h1>
        <p>本周刊回顾过去一年浏览器平台的重要变化。</p>

        <section>
          <h2>平台新能力</h2>
          <p>多个新接口在当前稳定版浏览器中可用。</p>
        </section>

        <section>
          <h2>开发者工具</h2>
          <p>调试体验持续改善。</p>
        </section>
      </article>

      <aside>
        <h2>订阅周刊</h2>
        <p>留下邮箱，每周收到一期。</p>
      </aside>
    </main>

    <footer>
      <p>© 2026 科技周刊</p>
    </footer>
  </body>
</html>
```

#### 4.4 section 与 article 的选择

判断顺序：

```text
这段内容是否可以脱离当前页面独立成立（单独分享、订阅、复用）？
  是 → article
  否 → 它是否按主题构成一个章节，并且通常带有标题？
        是 → section
        否 → 考虑普通容器或其他语义标签
```

一篇博文是 `article`；博文中的“评论区”“正文小结”是 `section`；评论区里的每一条评论又是一个 `article`，因为每条评论都可独立存在。允许嵌套：`article` 里可以有 `section`，`section` 里也可以有多个 `article`。

`header` 与 `footer` 不限于页面顶层。放在 `article` 内部时，它们表示这篇文章的头部（标题、发布时间）与尾部（标签、作者链接）。

#### 4.5 常见误区

> 只要内容在页面侧边，就必须用 `aside`。

`aside` 表达的是“与主内容相关但可分离”的含义，与视觉位置无关。侧边的聊天入口若与正文无关，不应使用 `aside`；正文中的补充说明即使不放在侧边也可以是 `aside`。

> 导航一定要包在 `nav` 里，所以页脚的链接列表也要加。

`nav` 用于主要导航区域。页脚那组法律条款、备案链接通常不属于主要导航，不必加 `nav`；一页中也不宜让每个链接列表都成为 `nav`，否则地标导航失去意义。

### 5. figure、time 与其他内容语义

#### 5.1 定义

- `figure`：带有可选标题 `figcaption` 的独立内容单元，如图表、插图、代码片段、引述。其内容即使被移到附录也不影响正文理解。
- `figcaption`：对 `figure` 内容的说明，放在 `figure` 内的开头或结尾。
- `time`：表示日期或时间，`datetime` 属性提供机器可读格式。
- `address`：提供最近的 `article` 或整个文档的联系信息，不是任意邮政地址的容器。
- `blockquote` 与 `q`：成段引述与短引述，`cite` 属性指向来源。
- `mark`：在当前语境中需要高亮的内容，如搜索结果中的命中词。

#### 5.2 与 Web 的关系

`datetime="2026-10-09"` 让浏览器、日历软件和搜索引擎获得无歧义的日期，页面上则可以自由显示为“2026 年 10 月 9 日”或“10 月 9 日”。`figure` 的说明与图片在结构上绑定，读屏器读到图片时能一并朗读图注。

#### 5.3 示例

```html
<article>
  <header>
    <h1>城市交通报告</h1>
    <p>发布于 <time datetime="2026-10-09">2026 年 10 月 9 日</time></p>
  </header>

  <p>报告开头给出结论：</p>
  <blockquote cite="https://example.com/report/2026">
    <p>公交专用道使高峰时段平均通行时间缩短百分之十二。</p>
  </blockquote>

  <figure>
    <img src="./chart.png" alt="高峰时段通行时间对比柱状图，专用道启用后下降百分之十二" width="640" height="360" />
    <figcaption>图 1：专用道启用前后高峰时段平均通行时间对比</figcaption>
  </figure>

  <p>在检索“<mark>公交专用道</mark>”时，命中词会被高亮显示。</p>

  <footer>
    <address>
      联系作者：<a href="mailto:editor@example.com">editor@example.com</a>
    </address>
  </footer>
</article>
```

`time` 的 `datetime` 常用格式：

```text
2026-10-09                日期
2026-10-09T14:30          日期与本地时间
2026-10-09T14:30Z         UTC 时间
14:30                     一天中的时间
P3D                       持续三天的时长
```

#### 5.4 常见误区

> 所有图片都应该包在 `figure` 里。

内容性图片用普通 `img` 即可。`figure` 用于“带说明、可从正文流中移出而不影响理解”的独立单元；纯装饰图片应通过 CSS 背景处理或使用空的 `alt=""`。

> `address` 可以用来排版任意地址文本。

它只表示联系信息。用户的收货地址、历史地点都不应使用 `address`，普通段落即可。

### 6. 列表与表格的语义结构

#### 6.1 三种列表

- `ul`：无序列表，项目顺序不重要，如功能点、标签。
- `ol`：有序列表，顺序有意义，如操作步骤、排行榜，可用 `reversed`、`start` 控制编号。
- `dl`：描述列表，由 `dt`（术语）与 `dd`（描述）组成，适合术语表、键值信息。

列表项内部可以放段落、链接甚至嵌套列表。导航菜单几乎总是用 `ul` 或 `ol` 实现，因为它本质是一组可跳转的链接。

```html
<h2>注册流程</h2>
<ol>
  <li>填写邮箱并验证。</li>
  <li>设置登录密码。</li>
  <li>补充个人资料。</li>
</ol>

<h2>常见术语</h2>
<dl>
  <dt>DOM</dt>
  <dd>文档对象模型，把 HTML 文档表示为可被脚本操作的节点树。</dd>
  <dt>语义化</dt>
  <dd>用标签表达内容含义，而不是只表达外观。</dd>
</dl>
```

#### 6.2 表格的完整结构

表格用于呈现“行列关系明确的表格数据”，不应用于页面布局。完整的表格元素包括：

| 元素 | 职责 |
|---|---|
| `table` | 表格容器 |
| `caption` | 表格标题，帮助读者快速了解表格内容 |
| `thead` | 表头行分组 |
| `tbody` | 表体行分组 |
| `tfoot` | 表尾行分组（如合计） |
| `tr` | 一行 |
| `th` | 表头单元格，`scope` 声明它对应列还是行 |
| `td` | 普通数据单元格 |

```html
<table>
  <caption>2026 年第三季度各门店销售额（万元）</caption>
  <thead>
    <tr>
      <th scope="col">门店</th>
      <th scope="col">七月</th>
      <th scope="col">八月</th>
      <th scope="col">九月</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <th scope="row">中心店</th>
      <td>42</td>
      <td>38</td>
      <td>51</td>
    </tr>
    <tr>
      <th scope="row">滨江店</th>
      <td>30</td>
      <td>33</td>
      <td>29</td>
    </tr>
  </tbody>
  <tfoot>
    <tr>
      <th scope="row">合计</th>
      <td>72</td>
      <td>71</td>
      <td>80</td>
    </tr>
  </tfoot>
</table>
```

`scope` 让读屏器在逐单元格浏览时能朗读“七月，中心店，42”，把数据与其行列标题关联起来。跨列跨行的 `colspan`、`rowspan` 应谨慎使用，合并后要保证标题关系仍然清晰。

#### 6.3 与 Web 的关系

列表与表格是“关系型内容”在网页上的标准表达：导航是链接的列表，步骤是有序的列表，术语与定义是一一对应的描述列表；财务、日程、对照数据则天然落在行列网格中。浏览器、搜索引擎和读屏器都能识别这些关系——读屏器会播报“列表，共几项”“第 2 项”，并在表格中把当前单元格与其行标题、列标题一起读出。若改用无语义方框加 CSS 模仿外观，这些关系信息就全部丢失，用户只能“看到排列”，无法“理解关系”。

#### 6.4 常见误区

> 想要一排横向排列的方框，用表格最省事。

那是视觉布局需求，应由 Flexbox 或 Grid 完成。表格语义表示数据关系，布局表格会让读屏器按“行、列、单元格”播报，体验混乱。

> 表格太简单，`caption` 和 `th` 能省则省。

没有标题和表头，单看“42、38”这样的数字无法知道含义。只要数据存在行列关系，就应提供 `caption` 与带 `scope` 的 `th`。

### 7. div、span 的无语义角色

#### 7.1 定义

- `div`：块级通用容器，本身不表达任何含义，用于把若干元素组合起来，以便施加样式或脚本行为。
- `span`：行内通用容器，同样无语义，用于标记一段行内文本。

它们是“没有合适语义标签时”的兜底选择，而不是页面的基本建材。

#### 7.2 与 Web 的关系

通用容器不会出现在地标导航中，也不向读屏器和搜索引擎传达内容角色。合理使用可以满足样式分组（如为一张卡片内部再分“媒体区”和“正文区”）；滥用则会产生层层嵌套的“div 汤”（div soup），让文档难以阅读和维护。

#### 7.3 对比示例

无语义写法：

```html
<div class="page">
  <div class="top">
    <div class="logo">城市书店</div>
    <div class="menu"><a href="/">首页</a></div>
  </div>
  <div class="content">
    <div class="title">新书到店</div>
    <div class="text">本周有十二本新书上架。</div>
  </div>
</div>
```

语义写法：

```html
<header>
  <p>城市书店</p>
  <nav aria-label="主导航">
    <a href="/">首页</a>
  </nav>
</header>
<main>
  <h1>新书到店</h1>
  <p>本周有十二本新书上架。</p>
</main>
```

需要组合样式时，`div` 与 `span` 仍然是正确工具：

```html
<article class="book-card">
  <div class="book-card__media">
    <img src="./cover.jpg" alt="《晚风与海》图书封面" />
  </div>
  <h2 class="book-card__title">晚风与海</h2>
  <p>
    会员价
    <span class="book-card__price">¥32</span>
    起
  </p>
</article>
```

#### 7.4 选择顺序

```text
1. 是否存在表达该含义的 HTML 标签（文章、导航、日期、图注……）？
   有 → 使用语义标签
2. 是否需要为样式或脚本把若干元素组合成一组？
   是 → 使用 div（块级）或 span（行内）
3. 组合后是否需要向辅助技术传达角色、状态？
   是 → 在后续单元学习的 ARIA 属性上补充，而不是自创标签名
```

#### 7.5 常见误区

> 用了语义标签就不能再写 `div`。

语义标签选择含义，`div` 解决分组。卡片内部为了布局加一层无语义容器是常见且合理的，关键是不要用 `div` 替代本应存在的语义。

> 给 `div` 加上 `class="nav"` 就等于有了导航语义。

类名只服务于 CSS 和脚本选择，不改变元素的语义角色。读屏器不会因为类名叫 nav 就提供导航地标。

### 8. SEO、社交分享元数据与 HTML 校验

#### 8.1 title、description 与 Open Graph

- `title`：搜索结果中可点击的标题，也是标签页标题，应准确概括本页主题并包含必要的站点信息。
- `description`：搜索结果可能展示的摘要，应写清页面提供什么，每页不同。
- Open Graph（OG）：以 `property="og:..."` 声明的一组元数据，社交平台分享链接时据此生成卡片，包括标题、类型、图片与地址。

```html
<head>
  <meta charset="UTF-8" />
  <title>晚风与海 - 城市书店</title>
  <meta
    name="description"
    content="《晚风与海》是一部长篇小说，现由城市书店独家发售，支持到店自取与邮寄。"
  />
  <meta property="og:type" content="book" />
  <meta property="og:title" content="晚风与海" />
  <meta property="og:description" content="一部关于海边小镇与归乡者的长篇小说。" />
  <meta property="og:url" content="https://example.com/books/evening-wind" />
  <meta property="og:image" content="https://example.com/images/evening-wind-cover.jpg" />
  <meta name="twitter:card" content="summary_large_image" />
</head>
```

SEO 的基础是可访问的 HTML：能被抓取的语义内容、唯一标题、清晰大纲、可解析的链接地址。元数据是锦上添花，堆砌关键词或隐藏文本不会提升排名，反而可能被判定为作弊。

与 Web 的关系：搜索引擎爬虫本质上是“不渲染样式、不执行复杂交互”的特殊读者，它依靠 `title`、标题层级、语义分区和链接文本理解页面；社交平台则在无人访问页面之前，只读取 OG 元数据生成卡片预览。元数据因此决定了页面在“被点击之前”的样子。

#### 8.2 HTML 校验

W3C Nu Html Checker 会按规范检查标签嵌套、属性合法性、重复 ID、缺少替代文本等问题。使用方式：

1. 打开 validator.w3.org。
2. 选择 Validate by Direct Input（粘贴代码）、Validate by URI（线上地址）或 Validate by File Upload（本地文件）。
3. 阅读结果：Error 表示违反规范必须修复；Warning 表示需要人工确认，如可疑的空标题。
4. 修复后重新校验，直到没有错误。

常见校验结果与处理：

| 报告信息示例 | 含义 | 处理方式 |
|---|---|---|
| Element “div” not allowed as child of element “ul” | 列表中直接放了 `div` | 列表直接子元素只能是 `li`（或允许的脚本支持元素） |
| Duplicate ID “main-title” | 同一文档 ID 重复 | ID 必须全文档唯一，改用不同 ID 或类 |
| An “img” element must have an “alt” attribute | 图片缺少替代文本 | 补充 `alt`，纯装饰图用 `alt=""` |
| Start tag seen but an element of the same type was already open | 标签未正确闭合就开了下一个 | 按报告行号检查嵌套与闭合 |

#### 8.3 常见误区

> 页面在浏览器里显示正常，说明 HTML 没有问题。

浏览器对错误标记有很强的容错与自动补全能力，但自动修正结果可能与作者意图不同，读屏器和爬虫未必按同样方式理解。能显示不等于结构正确，应以校验结果为准。

> 加了 Open Graph 标签后，分享一定立刻显示新卡片。

平台会缓存分享卡片，且要求图片可公开访问、尺寸与格式符合其规范。调试时应使用各平台提供的卡片调试工具重新抓取，而不是反复修改后猜测。

### 验收演示流程

学员需要在 15 分钟内完成以下演示：

1. 用自己的语言口述页面的文档大纲，并指出唯一的 `h1` 与各章节层级（3 分钟）。
2. 在浏览器中打开页面，用开发者工具指出 `head` 元信息与资源引用位置（2 分钟）。
3. 展示一个表格，说明 `caption` 与 `scope` 如何帮助读屏器关联数据（3 分钟）。
4. 现场把一处语义标签改为 `div`，说明这一改动会让地标与大纲发生什么变化，再改回（3 分钟）。
5. 展示校验结果与标签决策文档，回答导师针对任一标签的追问（4 分钟）。

导师可以临时指定一个新增板块（如“读者来信”），要求学员口述应选标签、标题层级与嵌套位置，以检验迁移能力。

### 评分标准

总分 100 分，70 分及以上通过。

| 维度 | 分值 | 满分要求 |
|---|---:|---|
| 文档骨架与元数据 | 20 | 骨架四部分与必要 meta 齐全，title/description/OG 规范且与内容匹配 |
| 语义标签选择 | 25 | 地标、分区、内容语义标签全部选对，能解释理由与备选方案 |
| 标题大纲 | 15 | 单一 h1、层级不跳级，手写大纲与实际结构一致 |
| 列表与表格 | 15 | 三种列表按需使用，表格结构完整、数据自洽、scope 正确 |
| 校验与工程规范 | 15 | 校验无 Error，无重复 ID，路径与编码规范，提交物齐全 |
| 表达与决策说明 | 10 | 决策文档清晰，能区分事实、理由与备选方案 |

细分评分规则：

#### 文档骨架与元数据：20 分

- `doctype`、`html lang`、`head`、`body` 正确：6 分；
- `charset` 与 `viewport` 正确：5 分；
- `title` 与 `description` 唯一且贴合内容：4 分；
- Open Graph 至少四个字段且用途正确：5 分。

#### 语义标签选择：25 分

- 页面级地标完整：8 分；
- `article`、`section`、`aside` 选择正确：8 分；
- `figure`、`time` 等内容语义至少两处：5 分；
- 决策文档能解释五个选择及备选方案：4 分。

#### 标题大纲：15 分

- 唯一 `h1`：4 分；
- 全文不跳级：6 分；
- 手写大纲与 DOM 结构一致：5 分。

#### 列表与表格：15 分

- 有序或描述列表使用正确：4 分；
- 表格完整结构：7 分；
- 数据自洽、合计正确：4 分。

#### 校验与工程规范：15 分

- W3C 校验无 Error：7 分；
- 无重复 ID、无未闭合标签：4 分；
- 目录结构与提交物齐全：4 分。

#### 表达与决策说明：10 分

- 决策文档条理清晰：5 分；
- 现场问答能用自己的语言解释：5 分。

### 强制不通过条件

出现以下任一情况，本次验收不通过；修正后重新验收：

1. 缺少 `doctype`、`charset`、`viewport` 中任意一项，或页面出现多个 `main`、多个 `body`。
2. 标题出现跳级，或用 `div` 加粗放大充当标题且未提供真实标题。
3. 用表格进行页面布局。
4. 提交代码无法通过 W3C 校验且存在 Error，或拒绝运行校验。
5. 标签选择与含义明显冲突（如把整页内容放进 `aside`、导航全部无语义容器）且不能解释。
6. 提交真实密码、令牌、私钥或其他敏感信息。
7. 只提交截图，没有 HTML 源文件与证据文档。

### 学习目标与验收映射

| 学习目标 | 验收证据 |
|---|---|
| 写出完整 HTML5 文档骨架 | `index.html` 头部结构与现场指认 |
| 根据内容含义选择语义标签 | 页面结构与 `tag-decisions.md` |
| 设计不跳级的标题大纲 | `outline.md` 与现场口述大纲 |
| 正确组织列表与表格数据 | 页面表格、列表及数据自洽性检查 |
| 配置 SEO 与社交分享元数据 | `head` 中 title、description、OG 字段 |
| 使用校验工具保证标记质量 | `validation.txt` 与现场复校 |
| 理解 div/span 的兜底边界 | 决策文档与现场改标签演示 |

### 提交前自检

- [ ] 文件第一行是 `<!doctype html>`，根元素带有正确的 `lang`。
- [ ] `charset`、`viewport`、`title`、`description` 齐全且位于 `head`。
- [ ] 页面恰好一个 `h1`、一个 `main`，所有标题逐级递进。
- [ ] 地标与分区标签都能说出含义依据，不存在“因为教程这么写”的标签。
- [ ] 表格含 `caption` 与 `scope`，合计与明细一致。
- [ ] 所有 `img` 都有合适的 `alt`，装饰图使用空 alt。
- [ ] W3C 校验没有 Error，文档中没有重复 ID。
- [ ] Open Graph 字段完整，图片地址可公开访问。
- [ ] 提交物中不含个人敏感信息、密钥与本机绝对路径。
- [ ] 同学按 README 在自己的电脑上可以直接打开并复现全部检查。
