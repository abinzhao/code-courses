# 22-错误边界、并发特性与性能优化

## 目标

React 应用进入中等复杂度后，开发者必须回答三个问题：局部功能崩溃时，如何避免整页白屏；用户高频交互时，如何保持界面响应；页面变慢时，如何用证据而不是直觉定位瓶颈。这三个问题分别对应错误隔离、并发渲染与性能优化。

完成本知识单元后，学员应能够：

1. 说明 Error Boundary 在 React 19 中的实现现状，区分布局路由级、页面级和组件级边界的适用位置。
2. 列出 Error Boundary 不能捕获的错误类型（事件处理、异步回调、 Promise 拒绝、SSR），并为每类错误选择正确的处理方式。
3. 使用 Suspense 组织加载状态，理解边界嵌套与回退（fallback）的展示规则。
4. 使用 `useTransition` 和 `useDeferredValue` 标记非紧急更新，保证输入等高优先级交互不被阻塞。
5. 判断 `memo`、`useMemo`、`useCallback` 的真实收益与成本，避免“默认全包”的反模式。
6. 正确处理列表 key 与超大列表（虚拟列表），使用 `React.lazy` 做代码分割，并用 Profiler 先测量、再优化、最后复测。

本单元反复强调一条工程纪律：性能优化以测量证据开始，以测量对比结束。没有数据的“优化”只是猜测。

## 详细的理论知识讲解和示例伪代码

### 1. Error Boundary：定义与 React 19 现状

#### 1.1 定义

Error Boundary（错误边界）是一种特殊组件：当它的子组件在渲染期间抛出 JavaScript 错误时，边界能捕获错误、记录上报，并渲染备用 UI，而不是让整个 React 树卸载成白屏。

成为错误边界必须实现（或之一）两个生命周期：

- `static getDerivedStateFromError(error)`：根据错误更新 state，决定渲染什么备用 UI。
- `componentDidCatch(error, info)`：执行副作用，如日志上报；`info.componentStack` 给出组件栈。

```tsx
import { Component, ErrorInfo, ReactNode } from 'react';

type ErrorBoundaryProps = {
  children: ReactNode;
  fallback: (error: Error, reset: () => void) => ReactNode;
};

type ErrorBoundaryState = {
  error: Error | null;
};

export class ErrorBoundary extends Component<ErrorBoundaryProps, ErrorBoundaryState> {
  state: ErrorBoundaryState = { error: null };

  static getDerivedStateFromError(error: Error): ErrorBoundaryState {
    // 渲染阶段调用：只更新 state，不做上报等副作用
    return { error };
  }

  componentDidCatch(error: Error, info: ErrorInfo): void {
    // 提交阶段调用：适合上报；这里只打印结构，不接真实上报服务
    console.error('captured by boundary', error.message);
    console.error('component stack', info.componentStack);
  }

  reset = () => {
    this.setState({ error: null });
  };

  render() {
    if (this.state.error !== null) {
      return this.props.fallback(this.state.error, this.reset);
    }
    return this.props.children;
  }
}
```

使用方式：

```tsx
import { ErrorBoundary } from './ErrorBoundary';

function ProblemPanel() {
  // 模拟渲染期抛错
  throw new Error('PANEL_BROKEN');
}

export function DashboardPage() {
  return (
    <main>
      <h1>控制台</h1>
      <ErrorBoundary
        fallback={(error, reset) => (
          <div role="alert">
            <p>面板加载失败：{error.message}</p>
            <button type="button" onClick={reset}>
              重试
            </button>
          </div>
        )}
      >
        <ProblemPanel />
      </ErrorBoundary>
    </main>
  );
}
```

#### 1.2 与 Web 的关系

Web 页面传统上没有“局部崩溃”概念：脚本未捕获错误往往中断整页脚本执行。错误边界把服务端开发中常见的“异常隔离”带到前端：一个卡片组件的数据源异常，不应让导航和其他卡片全部消失。边界放置粒度的经验：

```text
应用根边界         兜住一切未预期错误，提供“刷新页面”
路由级边界         单个页面崩溃，导航与布局仍可用
关键区域边界       侧边栏、图表、评论区互不影响
可重置的小部件边界  重试成本低，提供 reset
```

#### 1.3 使用 react-error-boundary

手写 class 之外，可以使用声明式库，它额外提供重置语义和 `resetKeys`（依赖变化时自动解除错误）：

```tsx
import { ErrorBoundary } from 'react-error-boundary';

type FallbackProps = {
  error: Error;
  resetErrorBoundary: () => void;
};

function ChartFallback(props: FallbackProps) {
  return (
    <div role="alert">
      <p>图表暂时不可用</p>
      <button type="button" onClick={props.resetErrorBoundary}>
        重新加载图表
      </button>
    </div>
  );
}

export function SalesSection({ chartId }: { chartId: string }) {
  return (
    <ErrorBoundary
      FallbackComponent={ChartFallback}
      resetKeys={[chartId]}
      onError={(error, info) => {
        console.error(error.message, info.componentStack);
      }}
      onReset={() => {
        // 重置时清理本区域的外部状态
      }}
    >
      <SalesChart chartId={chartId} />
    </ErrorBoundary>
  );
}

function SalesChart(props: { chartId: string }) {
  return <div>图表 {props.chartId}</div>;
}
```

#### 1.4 常见误区

> 误区一：认为 React 19 提供了函数式错误边界 Hook。

截至 React 19，错误边界仍必须是 class。社区库内部同样以 class 实现。

> 误区二：只在应用根部包一个边界。

粒度过粗等于没有隔离：一个图表抛错，整页内容都被替换成兜底。应按路由和关键区域分层布置。

### 2. Error Boundary 不能捕获的错误

#### 2.1 定义与边界对照表

错误边界只捕获“React 渲染流程中”的错误。以下场景不在捕获范围：

| 错误来源 | 边界是否捕获 | 正确处理方式 |
|---|---|---|
| 渲染函数 / 生命周期 / 构造器中抛错 | 是 | 边界兜底 |
| 事件处理函数（onClick 等） | 否 | 事件内 `try/catch`，错误写入 state |
| `setTimeout`、Promise 回调 | 否 | `await` + `try/catch` 或 `.catch` |
| 未处理的 Promise 拒绝 | 否 | `unhandledrejection` 全局监听 + 局部 catch |
| SSR 期间错误 | 否（边界在客户端水合后生效） | 服务端框架的错误处理机制 |
| 边界自身抛出的错误 | 否 | 兜底组件必须简单可靠 |

#### 2.2 事件处理错误的处理

把事件错误转成渲染期状态，才能让 UI 响应错误：

```tsx
import { useState, useTransition } from 'react';

type SubmitState = { status: 'idle' } | { status: 'error'; message: string };

async function postComment(content: string): Promise<void> {
  if (content.trim() === '') {
    throw new Error('评论内容不能为空');
  }
}

export function CommentBox() {
  const [content, setContent] = useState('');
  const [state, setState] = useState<SubmitState>({ status: 'idle' });
  const [isPending, startTransition] = useTransition();

  const handleSubmit = () => {
    startTransition(async () => {
      try {
        await postComment(content);
        setContent('');
        setState({ status: 'idle' });
      } catch (error) {
        setState({
          status: 'error',
          message: error instanceof Error ? error.message : '提交失败',
        });
      }
    });
  };

  return (
    <div>
      <label>
        评论
        <textarea value={content} onChange={(e) => setContent(e.target.value)} />
      </label>
      <button type="button" onClick={handleSubmit} disabled={isPending}>
        {isPending ? '发送中…' : '发送'}
      </button>
      {state.status === 'error' ? (
        <p role="alert">{state.message}</p>
      ) : null}
    </div>
  );
}
```

#### 2.3 全局兜底监听

局部 catch 之外，可以在应用入口注册全局监听，捕获漏网错误用于告警，但不应用它替代局部处理：

```tsx
export function registerGlobalGuards() {
  const onError = (event: ErrorEvent) => {
    console.error('window error', event.message);
  };

  const onRejection = (event: PromiseRejectionEvent) => {
    console.error('unhandled rejection', String(event.reason));
  };

  window.addEventListener('error', onError);
  window.addEventListener('unhandledrejection', onRejection);

  return () => {
    window.removeEventListener('error', onError);
    window.removeEventListener('unhandledrejection', onRejection);
  };
}
```

#### 2.4 与 Web 的关系

事件处理运行在 React 渲染周期之外：用户点击时，浏览器事件循环直接调用回调，此时没有“正在进行的渲染提交”可以被中断或回退，因此边界无法介入。理解这一点，就不会在 onClick 里故意 `throw` 期望边界接住。异步代码同理——它在未来的微任务/宏任务中执行，与渲染栈已经脱离。

#### 2.5 常见误区

> 误区一：在事件回调里抛错，然后疑惑为什么兜底 UI 不出现。

事件错误必须就地捕获，或通过路由层（如路由的 errorElement）与状态机制展示。

> 误区二：兜底组件里再写复杂异步逻辑。

兜底组件自身抛错没有更外层边界时会向上冒泡；保持 fallback 简单、确定、可一键重试。

### 3. Suspense 与加载状态

#### 3.1 定义

Suspense 是一种“声明等待”机制：子树表示自己“尚未准备好”（抛出 promise），React 沿树向上找到最近的 `<Suspense>`，在等待期间展示其 `fallback`，数据就绪后自动恢复渲染真实内容。

```tsx
import { Suspense } from 'react';

function Skeleton() {
  return <div aria-busy="true">内容加载中…</div>;
}

export function ArticlePageLayout() {
  return (
    <div>
      <Suspense fallback={<Skeleton />}>
        <ArticleBody />
      </Suspense>

      <Suspense fallback={<span>评论加载中…</span>}>
        <CommentList />
      </Suspense>
    </div>
  );
}

function ArticleBody() {
  return <article>正文</article>;
}

function CommentList() {
  return <ul><li>评论</li></ul>;
}
```

#### 3.2 边界嵌套与 React 19 的 use

内层边界优先处理本区域等待；可以把稳定内容放在边界外，避免它们被一起替换成加载骨架。React 19 中可以在渲染中用 `use` 读取一个正在进行的 Promise（示例使用本地模拟）：

```tsx
import { Suspense, use } from 'react';

type Profile = { name: string };

function fetchProfile(id: string): Promise<Profile> {
  return new Promise((resolve) => {
    setTimeout(() => resolve({ name: `用户 ${id}` }), 300);
  });
}

const profilePromise = fetchProfile('42');

function ProfileName() {
  const profile = use(profilePromise);
  return <span>{profile.name}</span>;
}

export function ProfilePanel() {
  return (
    <Suspense fallback={<span>用户信息加载中…</span>}>
      <ProfileName />
    </Suspense>
  );
}
```

#### 3.3 与 Web 的关系

传统加载态是命令式的：`setLoading(true)` → 请求 → `setLoading(false)`，多个并发请求时还要写计数器或竞态判断。Suspense 把“等待”从组件状态提升为渲染机制：加载 UI 的位置由 Suspense 边界在树中的位置决定，多个子组件共享同一份数据请求时，边界只显示一次回退，不需要手工协调。骨架屏应与真实内容布局一致，减少加载完成后的布局位移（与 CLS 相关）。

#### 3.4 常见误区

> 误区一：在整个应用外包一个巨大 Suspense，任何区域等待都导致全屏骨架。

应按内容稳定性和视觉分区设置多个边界。

> 误区二：把 Suspense 当作数据请求库。

Suspense 只规定“如何等待”，不负责缓存、重试、去重；数据能力由集成 Suspense 的请求库或框架提供。

### 4. useTransition 与 useDeferredValue

#### 4.1 useTransition：标记非紧急更新

`useTransition` 返回 `[isPending, startTransition]`。在 transition 中触发的更新是可中断的：用户新的紧急输入到来时，React 可以暂停旧的渲染，先保证输入响应。

```tsx
import { useState, useTransition } from 'react';

type Row = { id: number; label: string };

function buildRows(keyword: string): Row[] {
  // 故意构造较重的同步过滤，放大渲染压力
  const rows: Row[] = [];
  for (let i = 0; i < 20000; i += 1) {
    if (keyword === '' || String(i).includes(keyword)) {
      rows.push({ id: i, label: `结果 ${i}` });
    }
  }
  return rows;
}

export function HeavySearch() {
  const [keyword, setKeyword] = useState('');
  const [rows, setRows] = useState<Row[]>(() => buildRows(''));
  const [isPending, startTransition] = useTransition();

  const handleChange = (value: string) => {
    // 输入框立即更新：紧急更新
    setKeyword(value);
    // 大列表计算标记为非紧急，可被新输入打断
    startTransition(() => {
      setRows(buildRows(value));
    });
  };

  return (
    <div>
      <label>
        搜索
        <input value={keyword} onChange={(e) => handleChange(e.target.value)} />
      </label>
      {isPending ? <span>结果更新中…</span> : null}
      <ul aria-label="搜索结果">
        {rows.slice(0, 500).map((row) => (
          <li key={row.id}>{row.label}</li>
        ))}
      </ul>
    </div>
  );
}
```

#### 4.2 useDeferredValue：延迟消费某个值

当你无法控制更新的发起方（例如值来自 props），用 `useDeferredValue` 得到一个“滞后副本”，用滞后副本驱动昂贵渲染，紧急部分仍使用最新值。

```tsx
import { useDeferredValue, useMemo, useState } from 'react';

export function FilteredDirectory({ items }: { items: Row[] }) {
  const [keyword, setKeyword] = useState('');
  const deferredKeyword = useDeferredValue(keyword);

  const visibleRows = useMemo(
    () =>
      items.filter((row) =>
        row.label.toLowerCase().includes(deferredKeyword.toLowerCase()),
      ),
    [items, deferredKeyword],
  );

  const isStale = keyword !== deferredKeyword;

  return (
    <div>
      <input value={keyword} onChange={(e) => setKeyword(e.target.value)} />
      <ul style={{ opacity: isStale ? 0.6 : 1 }}>
        {visibleRows.map((row) => (
          <li key={row.id}>{row.label}</li>
        ))}
      </ul>
    </div>
  );
}
```

#### 4.3 与 Web 的关系

浏览器主线程同时负责执行 JavaScript 和响应用户输入。一次耗时渲染若不可中断，用户键入的字符会延迟上屏，表现为“输入卡顿”。并发特性不是多线程（JavaScript 仍在单主线程执行），而是让 React 把渲染拆成可中断、可让位的片段，把“用户正在等的反馈”排在“重算大片列表”之前。这直接影响 INP（交互到下一次绘制）指标。

#### 4.4 常见误区

> 误区一：把网络请求放进 startTransition 就以为它会被中断。

transition 只影响渲染优先级，不会取消 fetch；取消请求需要请求库的取消能力。

> 误区二：在 transition 里更新输入框本身。

受控输入必须保持紧急更新，否则字符上屏反而滞后。

### 5. memo、useMemo 与 useCallback 的正确使用

#### 5.1 各自的作用

- `React.memo(Component)`：props 浅比较，相同则跳过重渲染。
- `useMemo`：缓存计算结果，依赖不变时复用。
- `useCallback`：缓存函数引用，本质是 `useMemo(() => fn, deps)`。

```tsx
import { memo, useCallback, useMemo, useState } from 'react';

type MetricCardProps = {
  label: string;
  value: number;
  onSelect: (label: string) => void;
};

const MetricCard = memo(function MetricCard(props: MetricCardProps) {
  return (
    <button type="button" onClick={() => props.onSelect(props.label)}>
      {props.label}：{props.value}
    </button>
  );
});

export function MetricsBoard() {
  const [count, setCount] = useState(0);
  const [selected, setSelected] = useState('');

  const values = useMemo(() => [count, count * 2, count * 3], [count]);

  const handleSelect = useCallback((label: string) => {
    setSelected(label);
  }, []);

  return (
    <div>
      <p>已选：{selected}</p>
      <button type="button" onClick={() => setCount((c) => c + 1)}>
        刷新数值
      </button>
      {['今日', '本周', '本月'].map((label, index) => (
        <MetricCard
          key={label}
          label={label}
          value={values[index]}
          onSelect={handleSelect}
        />
      ))}
    </div>
  );
}
```

#### 5.2 什么时候真的有收益

`memo` 只有在“父组件频繁因无关状态重渲染，而该组件 props 不变”时才有意义。若 props 每次都是新对象/新函数，memo 白白增加比较成本。三个 API 本身都有成本（缓存内存、依赖比较、记忆化读取），因此默认策略是：先写普通代码，出现可测量的浪费时再针对性添加。

```tsx
// 反模式：内联对象与内联函数让 memo 永远失效
export function BadUsage() {
  return <MetricCard label="x" value={1} onSelect={(label) => console.log(label)} />;
}

// 每次渲染 onSelect 都是新引用，memo 的浅比较必不相等
```

#### 5.3 与 Web 的关系

React 的默认行为是“父组件重渲染，所有子组件函数重新执行”，这在大多数页面上完全足够，因为 DOM diff 后真正提交的变更很少。性能问题通常出现在“渲染函数本身很贵”（大列表、复杂计算）而不是“提交了很多 DOM 变更”。优化工具减少的是重复执行渲染与重复计算，对真实 DOM 操作没有直接加速作用。

#### 5.4 常见误区

> 误区一：项目规定“所有组件必须 memo，所有函数必须 useCallback”。

这会让代码充斥缓存噪音，且多数没有收益，还可能因依赖写错产生陈旧值。

> 误区二：把对象直接放进依赖数组，却每次新建对象。

依赖按引用比较；应缓存对象本身，或拆解为稳定的原始值依赖。

### 6. 列表 key 与虚拟列表

#### 6.1 key 的作用

key 帮助 React 在前后两次渲染中识别“哪个元素是同一个”，从而复用 DOM 与组件状态。key 必须在同级列表中稳定且唯一。

```tsx
type Article = { id: string; title: string };

export function ArticleList({ articles }: { articles: Article[] }) {
  return (
    <ul>
      {articles.map((article) => (
        <li key={article.id}>
          <label>
            <input type="checkbox" />
            {article.title}
          </label>
        </li>
      ))}
    </ul>
  );
}
```

使用稳定 id 的原因：当列表头部插入一项时，React 按 key 复用已有 DOM，原有各项的勾选状态得以保留。使用数组下标作 key 时，下标对应的内容整体错位，React 误以为“还是同一个元素”，可能用旧数据更新输入、保留错误的勾选状态。

```text
插入前列表（index 作 key）：
key=0 -> A    key=1 -> B

头部插入 C：
key=0 -> C（复用了 A 的 DOM 与内部状态）
key=1 -> A（复用了 B 的 DOM 与内部状态）
key=2 -> B

组件内部状态（勾选、输入草稿）随 key 错位，引发难以排查的 bug。
```

仅当列表“静态、不重排、没有内部状态”时，下标 key 才可接受；可增删、过滤、排序的列表一律使用稳定标识。

#### 6.2 虚拟列表（窗口化渲染）

虚拟列表只渲染可视区附近的少量行，用容器总高撑开滚动条，滚动时根据 scrollTop 计算窗口。即使数据有十万条，DOM 中也只有几十个节点。

```tsx
import { useRef, useState } from 'react';

type VirtualListProps = {
  items: string[];
  rowHeight: number;
  containerHeight: number;
  overscan?: number;
};

export function SimpleVirtualList(props: VirtualListProps) {
  const { items, rowHeight, containerHeight, overscan = 4 } = props;
  const [scrollTop, setScrollTop] = useState(0);
  const containerRef = useRef<HTMLDivElement>(null);

  const startIndex = Math.max(0, Math.floor(scrollTop / rowHeight) - overscan);
  const visibleCount = Math.ceil(containerHeight / rowHeight);
  const endIndex = Math.min(
    items.length,
    Math.floor(scrollTop / rowHeight) + visibleCount + overscan,
  );

  const visibleItems = items.slice(startIndex, endIndex);
  const totalHeight = items.length * rowHeight;
  const offsetY = startIndex * rowHeight;

  return (
    <div
      ref={containerRef}
      style={{ height: containerHeight, overflowY: 'auto' }}
      onScroll={(event) => setScrollTop(event.currentTarget.scrollTop)}
      role="list"
    >
      <div style={{ height: totalHeight, position: 'relative' }}>
        <div style={{ transform: `translateY(${offsetY}px)` }}>
          {visibleItems.map((item, i) => {
            const index = startIndex + i;
            return (
              <div
                key={index}
                role="listitem"
                style={{ height: rowHeight }}
              >
                {item}
              </div>
            );
          })}
        </div>
      </div>
    </div>
  );
}
```

生产项目可使用成熟虚拟列表库，它们支持动态行高、横向滚动、栅格布局和滚动 API；行高不固定时，自研方案需要额外测量，优先使用库。

#### 6.3 与 Web 的关系

DOM 节点数量直接影响浏览器的样式计算、布局、绘制和内存。十万个节点的列表即使内容简单，首次渲染和每次更新都很慢；虚拟列表把 DOM 规模从“数据量”降为“屏幕可容纳量”，是数据密集型页面最有效的性能手段之一。它不改变数据处理方式，因此功能不会被删减。

#### 6.4 常见误区

> 误区一：先用下标 key，等出现 bug 再改。

key 错位引起的状态污染通常在联调晚期才暴露，修复要遍历所有列表，应在编写时就使用 id。

> 误区二：数据只有几百条就引入虚拟列表。

虚拟列表牺牲了可搜索性（页面内查找找不到未渲染内容）、可访问性和实现复杂度；应在 Profiler 证明节点数量确实是瓶颈时再使用。

### 7. React.lazy 与代码分割

#### 7.1 定义

`React.lazy` 允许把某个组件的代码推迟到首次渲染时才加载，配合 Suspense 显示加载态；打包器据此把该组件拆成独立 chunk。

```tsx
import { lazy, Suspense } from 'react';

const ReportsPage = lazy(() => import('./ReportsPage'));

function PageLoading() {
  return <div>页面加载中…</div>;
}

export function ReportsRoute() {
  return (
    <Suspense fallback={<PageLoading />}>
      <ReportsPage />
    </Suspense>
  );
}
```

#### 7.2 路由级分割与预取

最常见的分割粒度是路由：用户进入哪个页面才下载哪个页面的代码，首包显著变小。分割不是越多越好——每个 chunk 都有请求开销，过细的拆分会造成“加载瀑布”。实践策略：

```text
首屏需要的代码         保留在主包
非首屏路由             路由级 lazy
体积大且按需出现的内容   富文本编辑器、图表、大型弹窗单独成块
点击前可预测的需求       在链接悬停或按钮聚焦时预取 chunk
```

概念性预取写法（利用动态导入的静态可分析形式）：

```tsx
const reportsModule = import('./ReportsPage');

export function prefetchReports() {
  // 触发浏览器提前下载与解析，真正渲染时 React.lazy 复用同一模块
  void reportsModule;
}
```

#### 7.3 与 Web 的关系

代码分割直接对应 HTTP 层的按需加载与缓存：主包小，首屏可更早执行（影响 LCP）；带内容哈希的 chunk 在内容不变时可以长期缓存，发布后只有变化的块需要重新下载。构建产物分析应关注“首屏需要多少 JS、最大块是什么、是否存在重复打包的依赖”，而不是只看总大小。

#### 7.4 常见误区

> 误区一：把首屏立即可见的组件也 lazy，首屏反而多一次往返。

分割目标是首屏不立即需要的代码。

> 误区二：lazy 组件外层没有 Suspense，或 fallback 离得太远导致整页闪烁。

边界应紧邻懒加载内容，并让稳定布局留在边界外。

### 8. Profiler：先测量再优化

#### 8.1 React DevTools Profiler

Profiler 记录每次提交：哪些组件渲染、耗时多少、为什么重渲染（props、state、context、hooks 变化）。火焰图中横向宽的条代表耗时长的提交，灰色表示未重渲染。标准工作流：

```text
1. 明确场景与操作路径（例如“在搜索框快速输入 10 个字符”）
2. 开始录制，执行操作，停止录制
3. 找出耗时最长的若干次提交，阅读重渲染原因
4. 针对证据选择手段（拆分边界、transition、memo、虚拟列表、分割）
5. 同样路径再次录制，对比耗时与重渲染范围
6. 记录优化前后数据，确认没有引入交互回退
```

#### 8.2 用 Profiler 组件编程采集

除了浏览器扩展，React 提供 `<Profiler>` 组件，可在测试或局部场景编程收集提交耗时：

```tsx
import { Profiler, ProfilerOnRenderCallback } from 'react';

const handleRender: ProfilerOnRenderCallback = (
  id,
  phase,
  actualDuration,
  baseDuration,
  startTime,
  commitTime,
) => {
  console.log(
    `${id} ${phase} 实际耗时 ${actualDuration.toFixed(1)}ms` +
      ` 基线 ${baseDuration.toFixed(1)}ms`,
  );
};

export function MeasuredBoard() {
  return (
    <Profiler id="metrics-board" onRender={handleRender}>
      <div>在此放置被测组件树</div>
    </Profiler>
  );
}
```

字段含义：`phase` 为 mount 或 update；`actualDuration` 是本次提交实际渲染耗时；`baseDuration` 是不做 memo 时的估算成本，用于判断记忆化的潜在空间。生产环境采集需要带 profiling 构建的 React，日常优化用 DevTools 即可。

#### 8.3 与 Web 的关系

浏览器提供 Performance 面板度量长任务与渲染管线，React Profiler 则度量“React 层面的渲染提交”，两者回答不同问题：主线程长任务可能来自脚本、样式或布局；只有确认耗时花在 React 提交中，memo、transition 这些 React 手段才对症。结合 Web 指标（LCP、INP、CLS），可以把微观的提交耗时与用户真实感受关联起来。

#### 8.4 常见误区

> 误区一：看一次渲染耗时就下结论。

单次数据可能受系统负载影响；应重复操作、关注稳定的高耗时模式，并固定测试条件。

> 误区二：优化后没有复测，或为了数字牺牲交互正确性。

没有前后对比的优化不成立；任何提速如果改变了功能、错误处理或可访问性，都不算完成。

### 练习 1：分层错误隔离

#### 任务

搭建一个含顶部导航、两个信息面板（“销售图表”“动态列表”）的控制台页面，分别为两个面板和页面根部设置错误边界，使任一面板抛错时导航与另一面板仍可用。

- 页面与边界组件（手写 class 或 `react-error-boundary`）；

- 单面板崩溃与双面板正常的演示记录。

- 局部崩溃不影响导航与另一区域；
- 重试确实能恢复渲染；
- 能现场说明哪些错误边界接不住；
- 兜底组件自身不包含可能再次抛错的复杂逻辑。

### 练习 2：并发搜索与列表体验

#### 任务

实现一个大数据目录页：搜索框 + 两万条数据的过滤列表，使用并发特性保证输入流畅，并给出明确的“更新中”反馈。

#### 步骤约束

1. 输入框为紧急更新，过滤计算通过 `useTransition` 标记为非紧急；或使用 `useDeferredValue`，二选一并说明理由。
2. 结果更新期间展示“结果更新中…”，旧结果可保留并降低透明度，避免列表闪烁消失。
3. 渲染前用 Profiler 录制“快速输入 10 个字符”，记录最长一次提交耗时。
4. 正确使用稳定 key；列表项包含可勾选的复选框，验证过滤前后状态不发生错位。
5. 若数据规模继续增大导致节点过多，改为虚拟列表实现并保留全部功能。

#### 提交物

- 目录页组件与（如使用）虚拟列表组件；
- Profiler 优化前后的录制截图或文字数据；
- 选择 transition 或 deferredValue 的理由说明。

#### 验收标准

- 输入过程中字符上屏不延迟；
- 重渲染可被新输入打断，反馈状态清晰；
- key 稳定、勾选状态不错位；
- 优化前后有同口径数据对比。

### 练习 3：路由级代码分割与性能复盘

#### 任务

为多页应用（首页、报表、设置三个路由）实施代码分割，并用 Profiler 与构建产物完成一次完整性能复盘。

#### 步骤约束

1. 报表页使用 `React.lazy` + Suspense，首页关键代码保留主包。

4. 为报表页内的一个昂贵子树加上 `<Profiler>` 采集，或用 DevTools 录制并记录。
5. 复盘文档包含：问题、证据、采取的手段、前后数据、未解决项与后续计划。

#### 提交物

- 路由与懒加载代码、预取逻辑；
- 构建产物体积记录；
- 不少于 400 字的性能复盘文档。

#### 验收标准

- 首包体积下降且首屏功能完整；
- chunk 拆分合理，无加载瀑布；
- 复盘结论与数据一一对应；
- 不以删除功能或降低正确性换取数字。
