# 05-网络基础TCP-IP-DNS与请求链路

## 目标

完成本知识单元后，学员应能在脑中“看见”浏览器输入网址后数据如何穿过网络到达服务器，再带着页面内容返回，而不是把上网当作一个无法解释的黑盒。

学员应能够：

1. 画出网络分层心智模型，说出应用层、传输层、网络层和链路层各自解决什么问题，并用一次 Web 请求举例。
2. 区分 IP 地址与端口，区分 IPv4 与 IPv6、公网地址、内网地址和 loopback 地址，并用本机命令找到证据。
3. 解释 TCP 面向连接的含义、三次握手在概念上完成了什么、TCP 如何提供可靠传输；说明 UDP 与 TCP 的关键差异及各自适用场景。
4. 拆解一个 URL，准确说出 scheme、host、port、path、query 和 fragment 的职责。
5. 描述 DNS 从域名查到 IP 的过程及各级缓存的作用，解释 hosts 文件的本地覆盖能力，使用 `dig`、`nslookup` 和 `ping` 观察网络证据。
6. 完整描述一次请求链路（DNS 解析 → TCP 连接 → TLS 握手 → 发送请求 → 接收响应 → 浏览器渲染），并能用 `curl -v` 的输出逐段对应。

本单元聚焦“链路与机制”。HTTP 报文内部结构在下一单元（06）展开，TLS 的加密与证书细节在后续安全单元展开，本单元只做必要的点名。

## 技术栈

本单元不使用前端框架、后端框架、数据库或第三方 npm 包。

| 工具或环境 | 用途 | 学习要求 |
|---|---|---|
| Node.js 当前 LTS | 理解网络程序与简单套接字实验 | 知道一次监听对应 IP 加端口 |
| macOS 或 Linux Terminal | 执行网络观察命令 | 能读懂命令输出的关键字段 |
| `curl`（`-v` 参数） | 观察一次请求的完整连接过程 | 能把输出分段对应到链路各阶段 |
| `dig` / `nslookup` | 查询 DNS 记录 | 能读出域名对应的 IP 与记录类型 |
| `ping` | 观察网络可达性与往返时间 | 能解释它使用 ICMP，不等于 HTTP 可用 |
| `ifconfig` / `ip addr` | 查看本机网络地址 | 能找到本机 IP 与 loopback |
| Node.js 内置 `net` 模块 | 概念性 TCP 客户端与服务端实验 | 理解连接、端口与数据收发 |
| hosts 文件 | 观察本地域名覆盖 | 知道其位置与作用，不随意修改系统条目 |

课程命令以 macOS 和常见 Linux 环境为主：

- macOS 自带 `ping`、`nslookup`；`dig` 可能需要额外安装，缺失时可用 `nslookup` 替代。
- Linux 上查看本机地址通常用 `ip addr`；macOS 常用 `ifconfig`。
- 部分公司网络会限制 `ping` 使用的 ICMP 协议，此时“ping 不通”不代表网站无法访问。
- `<域名>`、`<端口>` 表示需要替换的占位参数，不要原样输入尖括号。

开始前检查环境：

```bash
node -v
curl --version | head -n 1
which dig || echo "dig 不可用，将使用 nslookup"
ping -c 1 127.0.0.1
```

预期观察：

- `node -v` 输出当前 Node.js 版本号。
- `curl --version` 第一行输出 curl 版本与支持的协议列表。
- 若 `dig` 不可用，会打印提示信息，不影响后续学习。
- `ping -c 1 127.0.0.1` 向本机发送一次探测，输出 `1 packets transmitted, 1 packets received` 一类统计，`0.0% packet loss` 表示收到回应。

## 详细的理论知识讲解和示例伪代码

### 1. 网络与客户端-服务器模型

#### 1.1 通俗定义

网络是把多台计算机连接起来，让它们按事先约定的规则（协议）交换数据的设施。一次通信至少有两个角色：

- 客户端：主动发起请求的一方，例如浏览器、curl、Node.js 里调用接口的代码。
- 服务器：长期监听、等待请求并返回响应的一方，例如提供网页和 API 的机器。

#### 1.2 请求与响应的基本回合

```text
客户端：我要这份资源（发起请求）
服务器：收到，处理中……
服务器：结果在这里（返回响应）
客户端：解析并展示结果
```

这一回合是所有 Web 通信的基本形状。无论页面多复杂，都是由许多这样的回合组成。

#### 1.3 与 Web 开发的关系

- 浏览器是最常见的客户端，负责向服务器要页面、样式、脚本和数据。
- Node.js 程序既可以做服务器（对外提供 API），也可以做客户端（去请求数据库、缓存或第三方接口）。
- “访问慢”可能发生在客户端、网络途中或服务器，理解角色划分是定位问题的前提。

#### 1.4 常见误区

> 一个网站就是一台叫这个域名的电脑。

一个网站背后可能是多台服务器、负载均衡和多层缓存。域名只是一个名字，它可以指向不同机器，也可以随时间变化。

> 两台电脑联网就等于有一条独占的直线相连。

数据通常被拆成小块，经过多台中间设备逐站转发，走的是共享网络而不是一条专线。

### 2. 网络分层心智模型

#### 2.1 为什么要分层

网络通信要解决的问题很多：在线缆上传信号、在众多机器间找到目标、保证数据完整送达、让具体应用读懂内容。把这些问题分成若干层，每层只负责一类事，并向上面一层提供服务，可以让复杂系统变得可设计、可替换、可排查。

#### 2.2 四层模型与职责

| 层 | 主要职责 | Web 中的例子 |
|---|---|---|
| 应用层 | 定义应用之间交换什么内容 | HTTP 请求与响应 |
| 传输层 | 区分同一台机器上的不同程序，控制传输方式 | TCP、端口 |
| 网络层 | 在多个网络之间寻址和转发 | IP 地址、路由 |
| 链路层 | 在相邻设备之间传递数据帧 | 网卡、Wi-Fi、以太网 |

一个记忆线索：从上到下，问题从“说什么”逐步变成“信号怎么走”。

#### 2.3 数据封装：每层加上自己的头

发送数据时，数据从上往下逐层“套信封”：

```text
应用层数据        HTTP 内容
  ↓ 加传输层头
传输层段          TCP 头 + HTTP 内容
  ↓ 加网络层头
网络层包          IP 头 + TCP 头 + HTTP 内容
  ↓ 加链路层头尾
链路层帧          帧头 + IP 头 + TCP 头 + HTTP 内容 + 帧尾
```

接收端则从下往上逐层拆封。每一层只关心自己的头，就像套娃。

#### 2.4 分层如何帮助排查故障

```text
域名解析不出结果       → 重点看 DNS（应用层）与网络可达性
连不上目标 IP 和端口   → 重点看 IP 路由与 TCP（网络层、传输层）
连接成功但返回异常     → 重点看 HTTP（应用层）
网页拿到了但显示异常   → 重点看浏览器解析与渲染
```

分层不是考试摆设，它直接决定排查从哪一层开始。

#### 2.5 常见误区

> 分层模型是一套真实存在的软件文件。

它是帮助理解和设计的心智模型。真实系统里各层由操作系统、网卡驱动和应用程序协作实现，并不是四个看得见的文件夹。

> 写应用层代码必须完全掌握下层所有细节。

入门阶段的目标是知道每层在做什么、出问题时看哪里。日常 Web 开发主要在应用层工作，但要能借助工具读懂下层证据。

### 3. IP 地址与端口

#### 3.1 IP 地址：网络层的“门牌号”

IP 地址用于在网络中标识一台设备的网络接口，使数据能被路由到正确目标。

- IPv4：32 位，通常写成四段点分十进制，例如 `93.184.216.34`，每段 0 到 255。
- IPv6：128 位，用冒号分隔的十六进制表示，例如 `2606:2800:220:1:248:1893:25c8:1946`，用于解决地址数量不足等问题。

#### 3.2 公网地址、内网地址与 loopback

| 类别 | 作用 | 例子 |
|---|---|---|
| 公网地址 | 可在全球互联网中被路由 | `93.184.216.34` |
| 内网地址 | 仅在局域网内部使用，通过网关访问外网 | `10.0.0.2`、`192.168.1.10` |
| loopback | 指向本机的回环地址 | `127.0.0.1`、`::1` |

常见的内网地址范围：

```text
10.0.0.0    ～ 10.255.255.255
172.16.0.0  ～ 172.31.255.255
192.168.0.0 ～ 192.168.255.255
```

内网地址在不同家庭和公司里可以重复使用，因为它们不直接出现在公网上，由网关设备做地址转换。

特殊地址 `0.0.0.0` 在服务监听时通常表示“监听本机所有网卡地址”，意味着既接受 loopback 访问，也接受其他网卡上的访问；它不是一个用于访问别人的目标地址。

#### 3.3 端口：同一台机器上的“窗口号”

一台机器同时运行很多网络程序，仅靠 IP 无法区分数据该给谁。端口是一个 0 到 65535 的整数，用于在传输层区分具体程序。

IP 与端口合在一起称为套接字（socket），例如：

```text
127.0.0.1:3000
```

它表示“本机上监听 3000 端口的那个程序”。

常见端口的约定：

| 端口 | 常见用途 |
|---|---|
| 80 | HTTP 默认端口 |
| 443 | HTTPS 默认端口 |
| 3000 | 常见本地后端端口 |
| 5173 | 常见前端开发服务器端口 |
| 3306 | MySQL 默认端口（认知即可） |

URL 中使用默认端口时可以省略，例如 `http://example.com` 等价于访问其 80 端口。

#### 3.4 用命令观察本机地址

Linux：

```bash
ip addr
```

macOS：

```bash
ifconfig
```

预期：输出多个网络接口，其中 `lo0`（macOS）或 `lo`（Linux）包含 `127.0.0.1`；其他接口中能找到本机当前使用的内网地址，例如 `192.168.x.x`。

观察哪个程序在监听端口：

```bash
lsof -nP -iTCP:3000 -sTCP:LISTEN
```

若有服务在监听，会输出进程名、PID 和 `TCP 127.0.0.1:3000 (LISTEN)` 一类信息；没有输出通常表示该端口当前没有监听者。

#### 3.5 常见误区

> 服务监听在 `127.0.0.1:3000`，同局域网的同事也能访问。

loopback 只接受来自本机的访问。要让局域网内其他机器访问，服务需要监听对应网卡地址或 `0.0.0.0`，并确认防火墙策略允许。

> IP 和端口是同一种编号。

IP 标识机器，端口标识机器上的程序；一个是网络层概念，一个是传输层概念。

> 知道服务器内网 IP，就能从家里直接连过去。

内网地址不在公网路由，通常只能在对应局域网内部访问。

### 4. TCP 与 UDP：传输层的两种方式

#### 4.1 TCP：面向连接、可靠、有序

TCP（传输控制协议）在传数据前先在双方之间建立连接，并在传输过程中保证：

- 数据可靠到达：丢失会重传；
- 顺序正确：乱序到达会重新排好；
- 数据无重复、无差错：通过序号和校验机制处理；
- 双方可以根据接收能力调整发送速度（流量控制的基本思想）。

代价是额外的控制开销和连接建立延迟。

#### 4.2 三次握手在概念上完成了什么

建立 TCP 连接时，双方交换三次消息，俗称三次握手：

```text
客户端 → 服务器：SYN            （我想连接，我的初始序号是 x）
服务器 → 客户端：SYN + ACK      （我同意，我的初始序号是 y，确认了你的 x）
客户端 → 服务器：ACK            （我确认了你的 y，连接建立）
```

可以用对话理解：

```text
甲：你能听到我吗？
乙：能。你能听到我吗？
甲：能，我们开始吧。
```

三次交互让双方都确认了两件事：自己发得出去、对方收得到，且自己收得到、对方发得出来。握手本身不是加密过程，它只是为建立可靠连接做准备。

#### 4.3 可靠传输的工作循环

```text
发送端发出一段数据，带上序号
接收端收到后回复确认 ACK
发送端在约定时间内没收到确认
        ↓
认为该段丢失，重新发送
接收端按序号整理，交给上层应用
```

“可靠”是靠机制换来的，不是物理线路保证不丢。重传会增加延迟，因此网络拥塞时基于 TCP 的请求可能明显变慢。

#### 4.4 UDP：轻量、无连接、不保证可靠

UDP（用户数据报协议）不建立连接、不确认、不重传、不保证顺序，结构简单、额外开销小、发送快。

| 对比项 | TCP | UDP |
|---|---|---|
| 连接 | 先建立连接 | 无连接，直接发 |
| 可靠性 | 保证到达与顺序 | 不保证 |
| 开销 | 较大 | 小 |
| 典型场景 | 网页、API、文件传输 | DNS 查询、语音、视频、在线游戏 |

实时音视频中，偶尔丢一帧画面不值得为它重传（重传来时画面早过去了），更适合 UDP 的“尽量送达”思路。

#### 4.5 与 Web 的关系

- HTTP/1.1 和 HTTP/2 通常运行在 TCP 之上，所以打开一个网站前往往先有 TCP 连接建立过程。
- HTTP/3 运行在名为 QUIC 的传输机制之上，而 QUIC 基于 UDP 实现，这属于扩展认知，入门阶段只需知道“并非所有 HTTP 都走 TCP”。
- 选择 TCP 还是 UDP 由应用需求决定，Web API 开发默认面对的是 TCP。

#### 4.6 概念性 TCP 实验（Node.js net 模块）

服务端：

```javascript
// tcp-server.js
import { createServer } from 'node:net';

const server = createServer((socket) => {
  console.log('客户端已接入:', socket.remoteAddress, socket.remotePort);

  socket.write('你好，这是服务器返回的消息\n');

  socket.on('data', (data) => {
    console.log('收到:', data.toString().trim());
  });

  socket.on('end', () => {
    console.log('客户端断开连接');
  });
});

server.listen(4000, '127.0.0.1', () => {
  console.log('TCP 服务监听在 127.0.0.1:4000');
});
```

客户端：

```javascript
// tcp-client.js
import { connect } from 'node:net';

const socket = connect(4000, '127.0.0.1', () => {
  console.log('已连接到服务器');
  socket.write('hello from client');
});

socket.on('data', (data) => {
  console.log('服务器说:', data.toString().trim());
  socket.end();
});
```

运行顺序：先在一个终端执行 `node tcp-server.js`，再在另一个终端执行 `node tcp-client.js`。

预期：客户端打印连接成功和服务器问候；服务端打印客户端接入地址与收到的消息；随后双方看到连接结束。这个实验直观展示了“端口监听”与“连接建立”。

#### 4.7 常见误区

> 三次握手是为了给通信加密。

握手只负责建立可靠连接，不含加密。加密由 TLS 完成，TLS 在连接建立之后再进行。

> 用了 TCP，数据就绝对不会延迟或丢失。

TCP 在逻辑上保证最终按序交付，但靠重传实现；网络差时延迟会上升。它提供的是“可靠机制”，不是“即时保证”。

### 5. URL 结构

#### 5.1 通俗定义

URL（统一资源定位符）是资源在网络上的地址，告诉客户端用什么协议、找哪台机器、访问哪个资源。

#### 5.2 拆解一个 URL

```text
https://shop.example.com:8443/products/list?category=book&page=2#reviews
└─┬─┘  └──────┬───────┘ └┬┘ └─────┬─────┘ └────────┬────────┘ └──┬───┘
scheme       host       port     path              query        fragment
```

| 部分 | 作用 | 本例 |
|---|---|---|
| scheme | 用什么协议访问 | `https` |
| host | 服务器域名或 IP | `shop.example.com` |
| port | 端口，省略时用协议默认端口 | `8443` |
| path | 服务器上的资源路径 | `/products/list` |
| query | 附加参数，键值对用 `&` 连接 | `category=book&page=2` |
| fragment | 页面内定位标识 | `reviews` |

#### 5.3 与 Web 开发的关系

- path 常用于服务器或前端路由选择页面与接口。
- query 常用于传递筛选、分页、搜索关键词等参数。
- fragment（`#` 后部分）由浏览器处理，通常不会发送到服务器，常用于页面内锚点或前端路由状态。
- 非 ASCII 字符和特殊符号在 URL 中需要编码，例如空格可编码为 `%20`，中文也会被编码成 `%` 加十六进制形式。

#### 5.4 常见误区

> query 和 fragment 都会发给服务器。

query 是 URL 路径之后、`#` 之前的内容，会发送给服务器；fragment 在 `#` 之后，主要由浏览器本地使用。

> URL 只能是 http 或 https。

scheme 还可以是其他协议，例如 `ftp`、`mailto` 等，浏览器和系统会按 scheme 决定如何处理。

### 6. DNS：把域名翻译成 IP

#### 6.1 通俗定义

DNS（域名系统）是一套分布式的“目录服务”，负责把人类好记的域名翻译成机器通信需要的 IP 地址。人们记 `example.com`，机器通信需要 `93.184.216.34`，DNS 负责这层翻译。

#### 6.2 一次解析的大致过程

```text
浏览器要访问 www.example.com
        ↓
1. 查浏览器自身缓存
        ↓ 没有
2. 查操作系统缓存
        ↓ 没有
3. 查 hosts 文件中是否有本地映射
        ↓ 没有
4. 向配置的递归解析器（通常是运营商或公共 DNS）查询
        ↓
5. 递归解析器依次询问：根服务器 → 顶级域服务器(.com) → 权威服务器(example.com)
        ↓
6. 拿到 IP，沿途缓存结果，返回给浏览器
```

各级缓存由 TTL（生存时间）控制保留多久。TTL 没到期时直接使用缓存结果，不必每次都从头查询。

#### 6.3 常见记录类型

| 类型 | 含义 |
|---|---|
| A | 域名对应的 IPv4 地址 |
| AAAA | 域名对应的 IPv6 地址 |
| CNAME | 把一个域名别名指向另一个域名 |

入门阶段只需能在工具输出中认出这几类记录。

#### 6.4 hosts 文件：本地最高优先级的覆盖

hosts 是操作系统本地的一个文本文件，在 DNS 查询之前被检查，可直接把某个域名映射到指定 IP。

- macOS 与 Linux 通常位于 `/etc/hosts`。
- Windows 通常位于 `C:\Windows\System32\drivers\etc\hosts`。

它常用于本地开发，把某个域名指向 `127.0.0.1`，使本地服务可以用域名访问。由于它会影响系统对域名的解析，只应添加自己理解的条目，不修改或删除原有系统条目。

#### 6.5 用命令观察 DNS

使用 `dig`：

```bash
dig example.com
```

预期：输出中包含 `QUESTION SECTION`（查询的域名与类型）和 `ANSWER SECTION`，后者形如 `example.com. 数字 IN A 93.184.216.34`，其中 `A` 后就是 IPv4 地址。

只看简短答案：

```bash
dig +short example.com
```

预期：直接输出一个或多个 IP 地址。

使用 `nslookup`：

```bash
nslookup example.com
```

预期：输出当前使用的 DNS 服务器地址，以及 `Name:` 和 `Address:` 行给出的域名与 IP。

#### 6.6 用 ping 观察可达性与往返时间

```bash
ping -c 4 example.com
```

预期：先把域名解析成 IP，然后逐行显示回应，包含 `time=xx ms` 的往返时间；结尾汇总发送、接收和丢包率。

关键理解：

- ping 使用 ICMP 协议，不是 HTTP。ping 通只能说明网络层可达，不代表目标的 80 或 443 端口在正常提供网页服务。
- 很多服务器禁止响应 ICMP，因此 ping 不通而网页能正常打开是常见现象。
- `time` 值越大，通常表示网络延迟越高。

#### 6.7 常见误区

> DNS 解析成功，网站一定能访问。

DNS 只解决“域名对应哪个 IP”。目标服务器是否开机、端口是否开放、服务是否正常，DNS 都不负责。

> 修改 hosts 或 DNS 后所有程序都会立刻生效。

程序和系统可能持有缓存。修改后可能需要等待缓存过期，或重开应用，具体行为以系统为准。

> 每次访问域名都会完整地从根服务器查一遍。

由于浏览器、系统和递归解析器都有缓存，绝大多数访问只用到缓存结果。

### 7. 一次请求的完整链路

#### 7.1 把前面的机制串起来

在浏览器地址栏输入 `https://example.com/index.html` 并回车，宏观链路如下：

```text
1. 解析 URL
   识别 scheme=https、host=example.com、path=/index.html

2. DNS 解析
   查缓存与 hosts，必要时通过 DNS 得到目标 IP

3. 建立 TCP 连接
   客户端与服务器完成三次握手，形成可靠连接

4. TLS 握手（仅知道它在这里发生）
   在 TCP 之上协商加密，建立保密通道；细节在后续安全单元展开

5. 发送 HTTP 请求
   通过加密通道把请求报文发给服务器

6. 服务器处理并返回响应
   服务器读取资源或调用后端逻辑，回送响应报文

7. 浏览器接收并解析
   解析 HTML，继续请求其中引用的 CSS、JS、图片

8. 渲染页面并执行脚本
   构建页面结构、应用样式、运行 JavaScript，脚本可能再发起 API 请求
```

首屏之后往往还有许多子请求：一个现代页面可能包含几十个资源与接口请求，每个请求大体重复 3 到 6 步。

#### 7.2 链路各阶段的故障映射

| 阶段 | 典型现象 | 排查方向 |
|---|---|---|
| URL 解析 | 地址格式错误 | 检查域名、路径与编码 |
| DNS | 提示找不到域名、名称无法解析 | 换 DNS、查域名拼写、查 hosts |
| TCP | 连接超时、连接被拒绝 | 服务器是否开机、端口是否开放、防火墙 |
| TLS | 证书告警、握手失败（后续单元展开） | 证书与系统时间 |
| HTTP 请求与响应 | 返回错误状态码 | 看状态码与响应内容（06 单元） |
| 渲染 | 白屏、样式错乱、脚本报错 | 浏览器 DevTools |

#### 7.3 用 curl -v 观察链路

`-v` 表示详细输出，会把连接过程打印出来：

```bash
curl -v http://example.com
```

预期输出中包含三类行，前缀不同含义不同：

```text
*    以星号开头：连接过程信息
>    以大于号开头：发出去的请求内容
<    以小于号开头：收到的响应内容
```

典型片段及对应阶段：

```text
*   Trying 93.184.216.34:80 ...        ← DNS 已得到 IP，正在发起 TCP 连接
* Connected to example.com (93.184.216.34) port 80   ← TCP 连接建立成功
> GET / HTTP/1.1                        ← 开始发送 HTTP 请求
> Host: example.com
>
< HTTP/1.1 200 OK                       ← 收到响应状态行
< Content-Type: text/html
<
<!doctype html> ...                     ← 响应正文（HTML）
```

对照阅读就能把“抽象链路”与“真实输出”一一对上。HTTP 行内细节在下一单元讲解，本单元只需识别它们属于哪一阶段。

观察 HTTPS 时（只做阶段识别）：

```bash
curl -v https://example.com 2>&1 | head -n 20
```

预期：在 `Connected` 之后、发送请求之前，多出若干以 `*` 开头的 TLS 协商行，例如 `TLSv1.3`，说明加密握手确实发生在 TCP 连接之后、HTTP 请求之前。

#### 7.4 常见误区

> curl 能拿到内容，就说明浏览器页面一定能正常显示。

curl 只验证网络与 HTTP 这一层。页面渲染还依赖 HTML/CSS/JS 正确性、浏览器能力和前端状态，属于另一阶段。

> 首屏只发一次请求。

HTML 之后还会触发大量静态资源和接口请求。理解这点才能在 Network 面板中看懂请求瀑布。

### 练习 1：本机网络身份与端口观察

#### 任务

使用系统命令找出本机的 loopback 地址与内网地址，并配合一个 TCP 监听实验，理解 IP 与端口如何共同确定通信入口。

#### 步骤约束

1. 用 `ifconfig`（macOS）或 `ip addr`（Linux）找到 `127.0.0.1` 和一个当前网卡上的内网地址。
2. 用本单元的 Node.js `tcp-server.js` 监听 `127.0.0.1:4000`。
3. 用 `lsof -nP -iTCP:4000 -sTCP:LISTEN` 确认监听者。
4. 用 `tcp-client.js` 从本机连接，记录双方输出。
5. 把服务改为监听 `0.0.0.0:4000`，再次用 `lsof` 观察监听地址变化，结束后恢复或停止服务。

#### 提交物

- 本机网络接口观察记录（标注 loopback 与内网地址）；
- 两种监听地址下的 `lsof` 输出；
- 客户端与服务端完整对话记录；
- 一张“IP 与端口分工”说明表。

#### 验收标准

- 能从接口输出中准确指出 loopback 与内网地址；
- 能解释监听 `127.0.0.1` 与 `0.0.0.0` 的区别；
- 能用端口查到对应监听进程；
- 实验结束后没有残留监听进程。
