# 44-数据库迁移、关系映射与查询优化

## 目标

完成本知识单元后，学员应能把“schema 改了之后如何安全上线”和“接口为什么慢、如何优化”两件事工程化地完成，形成可复现、可回滚、有证据的数据层工作流。

学员应能够：

1. 使用 Prisma Migrate 的开发与部署工作流，理解迁移历史、迁移文件与数据库状态的关系。
2. 在关系上配置外键级联策略，区分级联删除、限制、置空等行为的业务含义。
3. 识别 N+1 查询并使用关系加载或批量查询解决，使用交互式事务组织多步读写。
4. 实现 offset 分页与 cursor 分页，并说明深分页的性能与稳定性差异。
5. 在 schema 中声明索引并与查询协同，用执行计划验证命中，编写可重复执行的幂等种子。
6. 综合运用字段裁剪、批量写入、日志测量与原生 SQL 边界，完成查询优化闭环。

本单元以 Prisma 当前稳定大版本与 PostgreSQL 当前稳定大版本为准。迁移命令与事务 API 长期稳定；关系加载策略等特性可能随版本演进，应以当前版本文档为准，课程不锁定小版本。

## 详细的理论知识讲解和示例伪代码

### 1. Prisma Migrate 工作流

#### 1.1 定义

**数据库迁移（migration）**是对结构变更的版本化记录。Prisma Migrate 的工作方式：

1. 修改 `schema.prisma`。
2. 执行开发命令，CLI 对比 schema 与迁移历史，生成一个带时间戳的迁移目录，内含 `migration.sql`。
3. CLI 应用该迁移并重新生成客户端。
4. 迁移目录提交版本库，团队成员和生产环境据此获得相同结构。

常用命令与场景：

| 命令 | 场景 | 关键行为 |
|---|---|---|
| `prisma migrate dev` | 本地开发 | 生成并应用迁移、生成客户端，必要时提示重置开发库 |
| `prisma migrate deploy` | 测试 / 生产发布 | 非交互应用全部待执行迁移，不生成新迁移 |
| `prisma migrate status` | 检查状态 | 列出已应用与待执行迁移 |
| `prisma migrate resolve` | 处理特殊情况 | 标记某个迁移为已应用或已回滚 |
| `prisma db push` | 原型阶段 | 直接同步 schema，不维护迁移历史 |

#### 1.2 与后端的关系

部署流程中“发布代码”和“变更数据库”必须协同：新版本代码依赖新列时，迁移应在应用切流前应用。迁移历史保证所有环境结构一致，回滚代码时也能根据迁移文件判断结构是否兼容。把结构变更写成可审查的 SQL，是团队协作的底线。

#### 1.3 示例

```bash
# 修改 schema，例如为 Post 增加 viewCount 字段后
npx prisma migrate dev --name add_post_view_count

# 查看迁移目录与状态
npx prisma migrate status
```

生成的目录结构：

```text
prisma/
├── migrations/
│   ├── migration_lock.toml
│   └── <时间戳>_add_post_view_count/
│       └── migration.sql
└── schema.prisma
```

`migration.sql` 示意：

```sql
ALTER TABLE "posts" ADD COLUMN "view_count" INTEGER NOT NULL DEFAULT 0;
```

发布到其他环境的流程伪代码：

```text
CI / CD：
  1. 拉取包含迁移目录的代码
  2. 执行非交互部署命令应用待执行迁移
  3. 检查状态，确认无遗漏
  4. 再启动新版本应用
```

#### 1.4 常见误区

> 在生产库执行 migrate dev 顺便发布。

开发命令是交互式的，并可能在检测到漂移时重置开发库数据。生产环境只能使用专门的部署命令。

> 生成的迁移目录是临时文件，可以不提交。

迁移文件是结构变更的唯一共享记录。不提交会导致同事和生产环境无法重建相同结构，历史链断裂。

### 2. 外键与级联策略

#### 2.1 定义

删除或更新被引用行时如何处理引用它的行，由外键的**引用行为（referential action）**决定。Prisma 在 `@relation` 上通过 `onDelete`、`onUpdate` 配置：

| 行为 | 含义 |
|---|---|
| `Cascade` | 删除父行时连带删除子行；更新主键时同步外键 |
| `Restrict` / `NoAction` | 只要存在子行就阻止删除父行 |
| `SetNull` | 父行删除后把外键置空（外键必须可空） |
| `SetDefault` | 外键回落到默认值（默认值必须能引用到合法行） |

默认语义与字段是否可空有关：必填关系通常默认阻止删除，可选关系可能默认置空。不要依赖“默认值应该是这样”，关键关系应显式写出策略。

#### 2.2 与后端的关系

- 用户删除账号，其文章应如何处理？连同删除（Cascade）、保留为匿名内容（SetNull 到可空作者列）还是阻止注销（Restrict）——这是产品决策，不是纯技术细节。
- 级联会沿关系链传播：删一个父行可能静默删除成千上万的后代行，且难以恢复。
- 实践中大量内容平台选择软删除（状态标记）配合显式归档，而不是物理级联。

#### 2.3 示例

```prisma
model User {
  id      Int      @id @default(autoincrement())
  email   String   @unique
  posts   Post[]
  profile Profile?
}

model Post {
  id       Int    @id @default(autoincrement())
  authorId Int
  author   User   @relation(
    fields: [authorId],
    references: [id],
    onDelete: Cascade,
    onUpdate: Cascade,
  )
}

model Comment {
  id       Int   @id @default(autoincrement())
  authorId Int?
  author   User? @relation(
    fields: [authorId],
    references: [id],
    onDelete: SetNull,
  )
}

model Profile {
  id     Int  @id @default(autoincrement())
  userId Int  @unique
  user   User @relation(
    fields: [userId],
    references: [id],
    onDelete: Restrict,
  )
}
```

删除行为的概念伪代码：

```text
DELETE 用户 7

posts（Cascade）  → 该用户全部文章被删除
comments（SetNull）→ 评论保留，authorId 变 NULL
profile（Restrict）→ 只要资料存在，删除被直接拒绝
```

#### 2.4 常见误区

> SetNull 可以配在必填外键上。

置空要求外键列可空。必填关系上配置置空会在 schema 校验阶段失败。

> 配了 Cascade 就不用管数据量。

级联删除可能放大锁范围、产生大量 WAL 并拖垮实例。上线前应评估后代行数，必要时改为分批归档。

### 3. N+1 查询：识别与解决

#### 3.1 定义

**N+1 问题**指为了加载一个列表及其关系，先执行 1 次查询取列表，再对每行各执行 1 次查询取关系，总共 N+1 次数据库往返。它的主要成本往往不是单次查询变慢，而是网络往返与重复解析的累积。

识别方法：

- 代码里出现循环内 `await` 查询。
- 开启客户端查询日志后，一次接口动作打印出大量结构相同、参数不同的语句。
- 接口耗时随列表长度近似线性增长。

解决思路：

- 使用关系加载（`include` / 嵌套 `select`），由客户端批量装配关系，显著减少往返。
- 手工批量方案：先取列表，收集 id，再用一次 `findMany({ where: { id: { in: ids } } })` 取关联数据，在内存中按外键归并。
- 当前版本支持配置关系加载策略，可选择以批量独立查询或 JOIN 形式装配，具体以版本文档为准。

#### 3.2 与后端的关系

首页信息流、评论楼层、后台订单列表都是 N+1 重灾区。数据量小时没人察觉，上线后随列表增长 P95 延迟恶化。数据访问代码评审应把“循环内查询”列为重点检查项。

#### 3.3 示例

```ts
// 错误：循环内逐条查询作者
async function listPostsBad() {
  const posts = await prisma.post.findMany({ take: 50 });

  for (const post of posts) {
    post.author = await prisma.user.findUnique({
      where: { id: post.authorId },
    });
  }

  return posts;
}

// 正确：一次关系加载完成装配
async function listPostsWithInclude() {
  return prisma.post.findMany({
    take: 50,
    include: { author: { select: { id: true, name: true } } },
  });
}

// 手工批量方案：两次查询，内存归并
async function listPostsBatched() {
  const posts = await prisma.post.findMany({ take: 50 });
  const authorIds = [...new Set(posts.map((post) => post.authorId))];

  const authors = await prisma.user.findMany({
    where: { id: { in: authorIds } },
    select: { id: true, name: true },
  });

  const authorMap = new Map(authors.map((author) => [author.id, author]));

  return posts.map((post) => ({
    ...post,
    author: authorMap.get(post.authorId) ?? null,
  }));
}
```

用查询日志量化的配置：

```ts
const prisma = new PrismaClient({
  log: [{ level: 'query', emit: 'event' }],
});

prisma.$on('query', (event) => {
  if (event.duration > 50) {
    console.warn('慢查询', event.duration, event.query);
  }
});
```

#### 3.4 常见误区

> 用了 include 就绝对不会有 N+1。

include 解决的是声明处的关系装配；如果在循环里再次手工查询、或嵌套结构里继续循环查询，仍会产生 N+1。

> 只要 SQL 语句总数少，查询就一定快。

一条大 JOIN 也可能因为返回大量重复宽行而变慢。批量装配与 JOIN 之间要结合数据形状选择，并以测量为准。

### 4. $transaction：交互式事务

#### 4.1 定义

Prisma 提供两种事务形式：

- **顺序事务（数组形式）**：`prisma.$transaction([op1, op2])`，按顺序执行一批已构造好的操作，全部成功才提交；适合步骤之间不依赖返回值的场景。
- **交互式事务（回调形式）**：`prisma.$transaction(async (tx) => { ... })`，在回调里使用事务客户端 `tx` 逐步执行并根据中间结果决策，抛错即回滚。

可配置项包括最大等待时间、执行超时和隔离级别。事务回调内的所有读写必须使用 `tx`，使用外部客户端实例不会加入该事务。

#### 4.2 与后端的关系

下单扣库存、转账、跨表状态流转必须用交互式事务：先锁定并校验，再更新，再写明细。事务应尽量短，避免在事务内发起外部 HTTP 调用；否则会长时间持锁并可能超时。

#### 4.3 示例

```ts
// 顺序事务：两个更新同生共死
await prisma.$transaction([
  prisma.account.update({
    where: { id: 1 },
    data: { balance: { decrement: 100 } },
  }),
  prisma.account.update({
    where: { id: 2 },
    data: { balance: { increment: 100 } },
  }),
]);

// 交互式事务：带校验的转账
async function transfer(fromId: number, toId: number, amount: Decimal) {
  return prisma.$transaction(
    async (tx) => {
      const from = await tx.account.findUnique({
        where: { id: fromId },
      });

      if (from === null || from.balance.lessThan(amount)) {
        throw new Error('余额不足或账户不存在');
      }

      await tx.account.update({
        where: { id: fromId },
        data: { balance: { decrement: amount } },
      });

      const to = await tx.account.update({
        where: { id: toId },
        data: { balance: { increment: amount } },
      });

      return { fromId, toId, remaining: to.balance };
    },
    {
      isolationLevel: 'Serializable',
      timeout: 10000,
      maxWait: 5000,
    },
  );
}
```

事务边界概念伪代码：

```text
BEGIN（获取事务客户端 tx）
  用 tx 读 → 用 tx 判断 → 用 tx 写
  任何一步抛错 → ROLLBACK
  正常返回     → COMMIT
```

#### 4.4 常见误区

> 在回调里混用全局 prisma 与 tx 也能一起提交。

全局客户端使用的是事务外的独立连接，那些语句不受回滚保护。事务中只能使用回调提供的客户端。

> 事务里可以放心调用第三方支付接口。

外部调用耗时不可控，会拉长事务、持锁过久。正确做法是事务内只处理数据库状态，外部调用放在事务外并配合状态机与对账。

### 5. offset 分页与 cursor 分页

#### 5.1 定义

- **offset 分页**：用 `skip` 与 `take` 实现“第 N 页”。优点是可直接跳到任意页；缺点是深分页时数据库仍需计算并跳过前面的大量行，且数据变动时会出现重复或遗漏。
- **cursor 分页**：以上一页最后一条记录的唯一有序值作为游标，查询“小于（或大于）该游标的前 n 条”。跳过游标自身使用 `skip: 1`。优点是深分页成本稳定、适合无限滚动；缺点是只能顺序翻页，不能直接跳到第 N 页。

cursor 必须选择唯一且稳定的排序列；单列时间可能重复，实践中常组合“排序键 + 唯一 id”的比较条件。

#### 5.2 与后端的关系

后台管理表格需要页码跳转，适合 offset；移动端信息流、评论加载更多适合 cursor。响应中应返回下一页游标（或下一页标识），由前端在下次请求带回。

#### 5.3 示例

```ts
// offset 分页
async function listPostsByPage(page: number, pageSize = 20) {
  const safePage = Math.max(page, 1);

  const [items, total] = await Promise.all([
    prisma.post.findMany({
      where: { published: true },
      orderBy: { createdAt: 'desc' },
      skip: (safePage - 1) * pageSize,
      take: pageSize,
    }),
    prisma.post.count({ where: { published: true } }),
  ]);

  return { items, total, page: safePage, pageSize };
}

// cursor 分页
async function listPostsByCursor(cursorId: number | null, pageSize = 20) {
  const items = await prisma.post.findMany({
    where: { published: true },
    orderBy: [{ id: 'desc' }],
    take: pageSize,
    skip: cursorId === null ? 0 : 1,
    ...(cursorId === null ? {} : { cursor: { id: cursorId } }),
  });

  const nextCursor = items.length === pageSize ? items[items.length - 1].id : null;

  return { items, nextCursor };
}
```

游标响应与请求契约：

```ts
type CursorPage = {
  items: { id: number; title: string }[];
  nextCursor: number | null;
};

// GET /posts?cursor=123 → 下次请求继续带回 nextCursor
```

#### 5.4 常见误区

> offset 深分页和第一页一样快。

`skip` 的行仍需被计算和排序。十万行之后的翻页会明显变慢，热门流量入口应改用 cursor。

> 用不唯一的时间列做游标也能严格不重不漏。

时间相同的行会导致边界处重复或丢失。游标必须包含唯一列，或使用组合比较条件。

### 6. 索引协同：在 schema 中声明并验证

#### 6.1 定义

索引应随模型一起声明，使结构与查询形状保持一致：

- 单列：`@@index([field])`。
- 复合索引：`@@index([fieldA, fieldB, fieldC])`，顺序遵循最左前缀。
- 唯一索引：`@@unique([...])`。
- 对经常排序的收尾列，可在索引中配合排序方向声明。

声明后通过迁移落到数据库，再用执行计划验证。验证不通过的“索引”等于没有索引。

#### 6.2 与后端的关系

列表接口的典型形状是“租户/作者等值过滤 + 状态等值 + 时间倒序 + take”，对应复合索引 `(tenant_id, status, created_at)`。先有查询形状，再设计索引，而不是凭感觉给每列加索引。修改查询后应重新验证计划。

#### 6.3 示例

```prisma
model Order {
  id        Int      @id @default(autoincrement())
  tenantId  Int      @map("tenant_id")
  userId    Int      @map("user_id")
  status    String
  amount    Decimal  @db.Decimal(12, 2)
  createdAt DateTime @default(now()) @map("created_at") @db.Timestamptz()

  @@index([tenantId, status, createdAt(sort: Desc)])
  @@index([userId, createdAt(sort: Desc)])
  @@map("orders")
}
```

用原生 SQL 通道验证计划（只读，安全）：

```ts
const plan = await prisma.$queryRaw`
  EXPLAIN (ANALYZE, BUFFERS)
  SELECT id, amount
  FROM orders
  WHERE tenant_id = 1
    AND status = 'paid'
  ORDER BY created_at DESC
  LIMIT 20
`;

console.dir(plan, { depth: null });
```

索引设计概念伪代码：

```text
从查询中提取：
  等值列（租户、状态）→ 放前面
  排序列（时间）      → 放收尾
  是否需要唯一性保证  → 用唯一索引
然后：迁移 → EXPLAIN 验证 → 未命中则重新调整列顺序
```

#### 6.4 常见误区

> 索引建得越多，写入慢点可以接受。

写入放大在高并发系统中非常显著，且优化器选择空间变大。应以实际查询清单驱动索引数量，并定期清理从未命中的索引。

> ORM 生成的查询“应该”走索引，不需要验证。

参数形状、列顺序和类型匹配都可能影响命中。必须用执行计划确认，而不是猜测。

### 7. 数据库种子：可重复的幂等初始化

#### 7.1 定义

**种子（seed）**是把数据库初始化到可用状态的脚本，用于新成员上手、测试环境重建和演示准备。好的种子脚本应：

- 通过 CLI 的 seed 机制统一执行；
- **幂等**：重复执行不产生重复数据，常用 `upsert` 或带跳过选项的批量插入；
- 遵守外键依赖顺序（先父表后子表）；
- 区分“基础字典数据”与“演示业务数据”。

#### 7.2 与后端的关系

CI 每次重建数据库后都依赖种子提供测试底数；演示前一键灌数避免手工操作。脚本必须在空库和已有基础数据的库上都能正确运行，否则自动化流水线会不稳定。

#### 7.3 示例

`package.json` 中的 seed 配置：

```json
{
  "prisma": {
    "seed": "tsx prisma/seed.ts"
  }
}
```

种子脚本：

```ts
import { PrismaClient, Prisma } from '@prisma/client';

const prisma = new PrismaClient();

async function main() {
  const admin = await prisma.user.upsert({
    where: { email: 'admin@example.com' },
    create: {
      email: 'admin@example.com',
      name: '管理员',
      role: 'ADMIN',
    },
    update: { role: 'ADMIN' },
  });

  await prisma.post.createMany({
    data: [
      { title: '入门指南', authorId: admin.id, published: true },
      { title: '部署清单', authorId: admin.id, published: false },
    ],
    skipDuplicates: true,
  });

  console.log('种子完成');
}

main()
  .catch((error: unknown) => {
    console.error('种子失败', error);
    process.exitCode = 1;
  })
  .finally(async () => {
    await prisma.$disconnect();
  });
```

执行与重建流程：

```bash
npx prisma migrate reset
# 重置开发库、重新应用全部迁移并自动执行种子

npx prisma db seed
# 仅对当前库单独执行种子
```

#### 7.4 常见误区

> 种子只需要在空库跑通一次。

自动化环境会反复重建与重跑；非幂等脚本会制造重复数据或主键冲突，导致流水线偶发失败。

> 重置命令可以在任何环境使用。

重置会清空开发库数据，严禁对包含真实数据的环境使用；它是本地与练习环境工具。

### 8. 查询优化综合：测量、裁剪、批量与原生 SQL 边界

#### 8.1 定义

把前七节串成一个优化方法轮：

1. **测量**：开启查询日志与慢查询记录，用 `EXPLAIN ANALYZE` 定位节点。
2. **裁剪**：用 `select` 只取必要字段，减少传输与序列化。
3. **批量**：写入用 `createMany`、更新用原子操作符，减少往返。
4. **装配**：用关系加载或手工批量消除 N+1。
5. **索引**：按查询形状补索引并验证命中。
6. **边界**：ORM 无法表达时使用参数化原生 SQL，并清楚其绕过了部分类型便利。

#### 8.2 与后端的关系

优化不是一次性动作：建立“测量 → 假设 → 改动 → 复测”的习惯，和调试代码完全一致。任何“优化”如果没有前后对比证据，都只是猜测。

#### 8.3 示例

```ts
// 批量写入替代循环 create
async function importUsers(rows: { email: string; name: string }[]) {
  const chunks = [];

  for (let i = 0; i < rows.length; i += 500) {
    chunks.push(rows.slice(i, i + 500));
  }

  for (const chunk of chunks) {
    await prisma.user.createMany({
      data: chunk,
      skipDuplicates: true,
    });
  }
}

// 原子更新，避免先读后写的竞态
await prisma.post.update({
  where: { id: 1 },
  data: { viewCount: { increment: 1 } },
});

// 参数化原生 SQL：标签模板方式仍然是参数化的
const hotPosts = await prisma.$queryRaw<{ id: number; title: string }[]>`
  SELECT id, title
  FROM posts
  WHERE published = TRUE
  ORDER BY view_count DESC
  LIMIT 10
`;
```

优化闭环伪代码：

```text
改之前：记录 P95、查询次数、EXPLAIN
提出假设：N+1 / 缺索引 / 深分页 / 字段过宽
实施改动：一次只改一个变量
复测：  相同数据规模下重新记录
结论：  数字对比 + 剩余风险
```

#### 8.4 常见误区

> 原生 SQL 字符串拼接外部输入更灵活。

拼接即注入。必须使用参数化标签模板；带“unsafe”字样的接口只用于受控的可信输入场景。

> 一次把能想到的优化全加上，再统一看效果。

多变量同时修改无法归因，且可能互相抵消。逐项验证才能沉淀可复用经验。

10. 场景分析：有人为了灵活用字符串拼接方式执行原生 SQL 并把前端排序字段直接拼进 `ORDER BY`。存在哪些风险？应如何安全处理？
