# 58-可观测性监控日志与错误追踪

## 目标

完成本知识单元后，学员应能为已上线的全栈应用建立一套“出问题时能发现、能定位、能告警”的可观测性体系，而不是等用户投诉后才登录服务器翻日志。

学员应能够：

1. 解释可观测性三支柱指标（metrics）、日志（logs）、追踪（traces）各自回答什么问题，以及三者如何配合。
2. 区分存活探针（liveness）与就绪探针（readiness），实现应用健康检查端点并避免误判。
3. 采集应用指标（请求量、延迟、错误率）与进程指标（CPU、内存、事件循环延迟、重启次数）。
4. 编写结构化日志，理解日志聚合与集中查询的基本概念，知道日志中应脱敏哪些字段。
5. 接入错误追踪系统（Sentry 类工具），上报异常、版本与用户上下文，并完成发布回归监测。
6. 配置基础告警与可用性监测，描述从告警触发到根因定位的完整闭环。

本单元是第 58 单元。部署与 HTTPS 基础见第 57 单元；这些可观测性能力将直接用于第 59、60 单元的结业项目交付与答辩。

## 详细的理论知识讲解和示例伪代码

### 1. 可观测性与三支柱

#### 1.1 定义

可观测性是指：当系统出现意料之外的问题时，仅凭系统对外暴露的数据，就能够回答“哪里坏了、为什么坏、影响多大”，而不需要为每个新问题临时登录机器加日志。

三支柱的分工：

| 支柱 | 回答的问题 | 数据特征 | 典型用途 |
|---|---|---|---|
| 指标 metrics | 出问题了吗？范围多大？ | 数值 + 标签，可聚合、成本低 | 看趋势、定阈值、做告警 |
| 日志 logs | 当时具体发生了什么？ | 带时间戳的事件记录，信息最全 | 查个案、复盘细节 |
| 追踪 traces | 一次请求慢在哪一跳？ | 跨服务的 span 与耗时 | 定位链路瓶颈与依赖故障 |

全栈关系：

```text
用户报告“工单提交偶尔失败”
   │
   ├─ 指标先证实：错误率从 0.1% 升到 8%，集中在 /api/tickets
   ├─ 日志再定位：某段时间数据库连接超时，报 ECONNREFUSED
   └─ 追踪补全链路：时间花在数据库连接等待，而非应用代码
```

没有指标，不知道有问题；没有日志，不知道细节；没有追踪，不知道跨环节耗时。三者不是互相替代，而是从宏观到微观逐层下钻。

指标中最常用的“黄金信号”：

```text
流量 rate      每秒请求数
延迟 latency   请求耗时分布（关注 p95、p99，而不只是平均值）
错误 errors    5xx、异常、失败任务的比例
饱和度 sat     CPU、内存、连接池等资源的饱和程度
```

#### 1.2 一个最小的指标埋点示例（text）

```text
对每次 HTTP 请求记录：
  http_requests_total{method="POST", route="/api/tickets", status="201"} +1
  http_request_duration_seconds 按桶（0.05, 0.1, 0.3, 1, 3）记录耗时
每隔 10 秒记录一次进程指标：
  process_resident_memory_bytes
  process_cpu_seconds_total
  nodejs_eventloop_lag_seconds
```

#### 1.3 常见误区

> 误区：监控就是“装个监控软件”，装好就完事。

工具只是采集与展示，真正的核心是明确关心哪些信号、阈值如何定、告警后谁来处理、怎么闭环。没有处置流程的监控等于没有监控。

> 误区：只看平均延迟。

平均值会掩盖长尾。若 5% 的用户要等 3 秒，平均可能只有 300 毫秒。需要看 p95、p99 分位数。

### 2. 健康检查与就绪探针

#### 2.1 定义

健康检查是一个轻量 HTTP 端点，供监控系统、负载均衡和部署脚本判断服务状态。两个概念必须区分：

- 存活探针（liveness）：进程是否还“活着”。失败意味着应重启该进程。
- 就绪探针（readiness）：是否“准备好接收流量”。失败意味着应暂时把它从流量中摘除，而不是重启。

例如应用启动时需要先建立数据库连接、加载缓存：在此期间它是“活着但没就绪”。若把依赖检查塞进存活探针，数据库一次短暂抖动就会导致进程被反复杀死，制造“重启风暴”。

全栈关系：第 57 单元部署脚本里的发布后检查、Nginx/负载均衡是否转发流量、Uptime 外部探测，底层都依赖健康检查端点的语义清晰。

#### 2.2 TypeScript 实现示例

```ts
import express from 'express';

const app = express();
let ready = false;
let shuttingDown = false;

async function checkDatabase(): Promise<boolean> {
  // 例如执行一次 SELECT 1，并设置 1 秒超时
  return Promise.resolve(true);
}

app.get('/health/live', (_req, res) => {
  if (shuttingDown) {
    res.status(503).json({ status: 'shutting_down' });
    return;
  }
  res.status(200).json({ status: 'alive', pid: process.pid });
});

app.get('/health/ready', async (_req, res) => {
  if (shuttingDown) {
    res.status(503).json({ status: 'shutting_down' });
    return;
  }
  const dbOk = await checkDatabase();
  if (!dbOk) {
    res.status(503).json({ status: 'not_ready', checks: { database: false } });
    return;
  }
  res.status(200).json({ status: 'ready', checks: { database: true } });
});

async function bootstrap() {
  // 初始化数据库连接与缓存，完成后再置为就绪
  ready = true;
  app.listen(3000, '127.0.0.1', () => console.log('api started'));
}

bootstrap();
```

用 Bash 同时验证状态码与响应体：

```bash
curl -fsS http://127.0.0.1:3000/health/live
curl -fsS http://127.0.0.1:3000/health/ready || echo "not ready yet"
```

#### 2.3 常见误区

> 误区：健康检查端点里串联所有外部依赖，任何一个抖动都返回失败并重启进程。

存活检查应尽量只反映进程自身；依赖检查放就绪检查，失败时摘流不杀进程。同时外部调用必须带超时，避免健康检查自身被慢依赖拖死。

> 误区：健康检查永远返回 200，只是为了让监控面板“好看”。

这会让探针失去意义，真正崩溃时系统无法自动发现和摘除。

### 3. 应用指标与进程指标

#### 3.1 定义

应用指标描述业务与协议层表现：请求量、延迟分布、状态码、登录失败次数、队列积压。进程指标描述运行时与系统层表现：常驻内存、CPU 时间、事件循环延迟、文件描述符数量、重启次数。

Prometheus 的基本数据模型是“指标名 + 标签 + 数值 + 时间戳”。常见指标类型：

```text
Counter   只增不减，如请求总数、错误总数
Gauge     可增可减，如当前连接数、内存占用
Histogram 按桶统计分布，可计算分位数，如请求延迟
Summary   客户端直接计算分位数
```

全栈关系：前端还可以补充“真实用户指标”（页面加载、接口在用户网络下的耗时与失败率），与服务端指标互相对照，区分“服务端慢”和“用户网络慢”。

#### 3.2 使用 prom-client 埋点

```ts
import client from 'prom-client';
import express from 'express';

const app = express();

client.collectDefaultMetrics({ prefix: 'ticket_' });

const httpRequests = new client.Counter({
  name: 'ticket_http_requests_total',
  help: 'Total HTTP requests',
  labelNames: ['method', 'route', 'status'] as const,
});

const httpDuration = new client.Histogram({
  name: 'ticket_http_request_duration_seconds',
  help: 'HTTP request duration in seconds',
  labelNames: ['method', 'route'] as const,
  buckets: [0.05, 0.1, 0.3, 0.5, 1, 3],
});

app.use((req, res, next) => {
  const end = httpDuration.startTimer({ method: req.method, route: req.path });
  res.on('finish', () => {
    httpRequests.inc({
      method: req.method,
      route: req.route?.path ?? req.path,
      status: String(res.statusCode),
    });
    end();
  });
  next();
});

app.get('/metrics', async (_req, res) => {
  res.set('Content-Type', client.register.contentType);
  res.end(await client.register.metrics());
});
```


#### 3.4 常见误区

> 误区：标签里放用户 ID、工单号等高基数字段。

每个不同标签值都会产生一条独立时间序列。把工单号或会话 ID 放进标签，会让时间序列数量爆炸，拖垮监控系统。这类标识应放到日志或追踪中。

> 误区：只在出问题后才开始加指标。

指标依赖历史数据才能对比。可观测性建设要先于故障，关键链路在上线时就应埋点。

### 4. 结构化日志与日志聚合

#### 4.1 定义

结构化日志是把一条日志编码为字段明确的 JSON 对象（时间、级别、消息、请求 ID、路由、用户标识等），而不是一段需要人脑解析的自由文本。机器可以直接按字段过滤、聚合和告警。

日志聚合是把分散在多台主机、多个进程的日志集中采集到统一存储，提供跨主机检索、保留期限与访问控制。常见技术路线包括 Loki（与 Prometheus 标签模型一致）与 ELK（Elasticsearch 全文检索）。对学习项目，先做到本地结构化 JSON 输出与按请求 ID 串联，再理解聚合系统的分层即可。

日志级别约定：

```text
error   当前请求失败，需要人介入
warn    异常但被降级处理，值得关注
info    正常的关键业务事件
debug   诊断细节，生产默认关闭
```

全栈关系：请求 ID（trace ID）把“前端一次点击 → Nginx → API → 数据库”相关的日志串成一条线，是全栈排障的关键纽带。

#### 4.2 结构化日志示例

使用 pino：

```ts
import pino from 'pino';

export const logger = pino({
  level: process.env.LOG_LEVEL ?? 'info',
  base: { service: 'ticket-api', version: process.env.APP_VERSION ?? 'dev' },
  redact: {
    paths: ['req.headers.authorization', 'password', 'email', '*.token'],
    censor: '[redacted]',
  },
});

logger.info({ ticketId: 'T-1024', action: 'created' }, 'ticket created');
logger.error({ err, ticketId: 'T-1024' }, 'failed to assign ticket');
```

输出形如：

```text
{"level":30,"time":1760000000000,"service":"ticket-api","ticketId":"T-1024","action":"created","msg":"ticket created"}
```

为每个请求生成并透传请求 ID 的中间件：

```ts
import { randomUUID } from 'node:crypto';
import type { Request, Response, NextFunction } from 'express';

app.use((req: Request, res: Response, next: NextFunction) => {
  const requestId = req.header('x-request-id') ?? randomUUID();
  req.headers['x-request-id'] = requestId;
  res.setHeader('x-request-id', requestId);
  (req as Request & { log?: unknown }).log = logger.child({ requestId });
  next();
});
```

Nginx 在日志中加入请求 ID，便于与应用日志对齐：

```nginx
log_format with_request_id '$remote_addr - $request_id "$request" $status '
                           'rt=$request_time uct="$upstream_connect_time" '
                           'urt="$upstream_response_time"';

access_log /var/log/nginx/access.log with_request_id;
```

本地查询 JSON 日志：

```bash
grep 'T-1024' /var/log/ticket-api/app.log
jq 'select(.level>=50) | {time,msg,requestId}' /var/log/ticket-api/app.log
```

#### 4.3 日志聚合概念分层

```text
应用输出 JSON 到 stdout/文件
   ▼
采集代理（如 Promtail / Filebeat / journald 导出）
   ▼
带标签的集中存储（Loki / Elasticsearch）
   ▼
统一查询界面（Grafana / Kibana）：按 requestId、service、level 检索
```

保留策略要平衡成本与合规：热数据保留数天到数周用于快速排障，更早的日志降冷或按法规要求定期删除。

#### 4.4 常见误区

> 误区：把完整请求体、Cookie、Authorization 头都打进日志以便排障。

日志可能被多人查看、长期保存，这会造成口令、令牌与个人信息泄露。应显式配置脱敏字段，敏感信息用掩码替代。

> 误区：到处 console.log，出错时再肉眼搜索。

非结构化文本无法聚合统计，级别缺失也无法告警。生产日志应通过统一日志库输出，字段与级别有规范。

### 5. 错误上报与 Sentry 类工具

#### 5.1 定义

错误追踪系统专门收集应用运行时异常，并完成去重、分组、堆栈还原、影响面统计与回归监测。它和日志的区别是：日志记录“所有事件”，错误追踪聚焦“需要修复的缺陷”，并自动把同类错误归并为一个 issue，附带首次/最近出现时间、影响用户数、发布版本和环境信息。

Sentry 是这类工具的事实标准之一，也可使用兼容协议的自托管服务。前端与后端都应接入：前端能捕获未处理 Promise 拒绝、资源加载失败；后端能捕获请求处理中的异常与崩溃。

发布（release）监测的价值：给每次发布打版本号，若新版本错误率突增，可立即定位“从哪个版本开始”，与第 57 单元的回滚策略联动。

全栈关系：错误追踪横跨前后端——前端上报交互与资源错误，后端上报请求异常，两侧通过同一个 release 版本号与用户标识对齐；它与指标、日志共同构成下钻路径：指标发现异常率升高，再按版本与用户进入错误追踪查看堆栈，最后用请求 ID 回到日志取细节。

#### 5.2 后端接入示例

```ts
import * as Sentry from '@sentry/node';

Sentry.init({
  dsn: process.env.SENTRY_DSN,
  environment: process.env.NODE_ENV ?? 'development',
  release: process.env.APP_VERSION ?? 'dev',
  tracesSampleRate: 0.1,
  beforeSend(event) {
    if (event.request?.headers?.authorization) {
      event.request.headers.authorization = '[redacted]';
    }
    return event;
  },
});

app.use(Sentry.Handlers.requestHandler());

app.get('/api/tickets/:id', async (req, res) => {
  try {
    // 查询与处理
    res.json({ id: req.params.id });
  } catch (err) {
    Sentry.captureException(err, {
      tags: { route: '/api/tickets/:id' },
      user: { id: req.user?.id },
      extra: { ticketId: req.params.id },
    });
    res.status(500).json({ error: 'internal_error' });
  }
});

app.use(Sentry.Handlers.errorHandler());
```

部署后通知新版本，建立“发布—错误”关联：

```bash
export SENTRY_AUTH_TOKEN=请通过CI密钥注入
sentry-cli releases new "$APP_VERSION"
sentry-cli releases set-commits "$APP_VERSION" --auto
sentry-cli releases finalize "$APP_VERSION"
```

#### 5.3 前端接入与告警噪音控制

```ts
import * as Sentry from '@sentry/react';

Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,
  environment: import.meta.env.MODE,
  release: import.meta.env.VITE_APP_VERSION,
  ignoreErrors: [
    // 合并已知第三方浏览器扩展产生的噪音
    'ResizeObserver loop limit exceeded',
  ],
  beforeSend(event) {
    return event;
  },
});
```

控制噪音的工程做法：同一错误靠指纹自动去重；第三方脚本噪音加入忽略列表；用环境过滤开发机异常；告警只针对“新增 issue”或“影响用户数超阈值”的问题，而不是每条错误都通知。

#### 5.4 常见误区

> 误区：把 DSN 当成机密，不敢放在前端。

前端 DSN 本身设计为公开，它只用于上报、不能读取数据；真正需要保密的是服务端 `SENTRY_AUTH_TOKEN`。同时仍要防止把敏感数据放进上报内容。

> 误区：接入后从不处理 issue，错误列表越积越多。

错误追踪的价值在闭环：分配负责人、在修复版本中关闭、用回归状态验证。长期不处理的 issue 会淹没真正重要的新问题。

### 6. 分布式追踪概念入门

#### 6.1 定义

一次请求在复杂系统中会穿过多个服务与组件。追踪把这一过程表示为一棵 span 树：每个 span 是一个带开始时间、耗时和属性的操作（如“HTTP 入口”“数据库查询”“调用外部 API”），同一条链路共享一个 trace ID。

OpenTelemetry（OTel）是厂商中立的埋点标准，统一了指标、日志与追踪的数据规范。学习阶段不要求自建完整 OTel 后端，但应能读懂 trace 视图、理解 span 之间的父子关系。

全栈关系：在“前端 → Nginx → API → 数据库/队列”的结业项目中，追踪能回答“用户觉得慢，究竟慢在数据库查询、排队任务还是外部接口”。

#### 6.2 概念示例

```text
trace_id=4b8f...（整条请求唯一）
  span A  POST /api/tickets                320ms
    span B  validate payload               4ms
    span C  prisma ticket.create          210ms
      span D  SELECT ... FOR UPDATE       180ms
    span E  enqueue notification job      18ms
    span F  send to search index          80ms（超时重试 1 次）
```

最小手动埋点概念（OpenTelemetry API 风格）：

```ts
import { trace } from '@opentelemetry/api';

const tracer = trace.getTracer('ticket-api');

app.post('/api/tickets', async (_req, res) => {
  await tracer.startActiveSpan('create_ticket', async (span) => {
    span.setAttribute('app.route', '/api/tickets');
    try {
      // 业务逻辑；数据库与 HTTP 客户端库通常会自动生成子 span
      res.status(201).json({ ok: true });
    } catch (err) {
      span.recordException(err as Error);
      span.setStatus({ code: 2 });
      throw err;
    } finally {
      span.end();
    }
  });
});
```

#### 6.3 常见误区

> 误区：给每个函数都建 span，采样率拉满。

追踪是有成本的，过细的 span 会淹没关键路径。应覆盖重要边界（入站请求、数据库、外部调用、队列处理），配合基于头部采样的策略。

> 误区：trace ID 在服务间没有透传，每跳都是新链路。

必须通过 HTTP 头（如 W3C `traceparent`）在调用间传播上下文，否则 span 无法串联成一棵树。

### 7. 基础告警与可用性监测

#### 7.1 定义

可用性监测从系统外部、以用户视角周期性访问站点（首页、健康检查、登录页），确认“别人到底能不能打开”。它不依赖主机是否在线——即使主机彻底失联，外部探测也能发现。

告警是把“指标越过阈值或探测失败”这一事件通知给负责人。好的告警应满足：可执行（收到后知道做什么）、基于用户影响、有去重与恢复通知。频繁误报会让人对告警麻木。

全栈关系：告警是闭环入口。它应直接链接到对应的指标面板、相关日志查询和错误追踪 issue，减少切换成本。

#### 7.2 Uptime 探测配置概念

```text
探测名称      工单系统首页
URL           https://app.example.com/
方法          GET，期望状态码 200
关键字检查    页面中包含“工单”
间隔          60 秒
失败重试      连续 3 次失败才通知
通知渠道      即时消息群 + 邮件
另建探测      https://app.example.com/health/ready
```

Prometheus 告警规则示例：

```text
groups:
  - name: ticket-api
    rules:
      - alert: HighErrorRate
        expr: sum(rate(ticket_http_requests_total{status=~"5.."}[5m]))
              / sum(rate(ticket_http_requests_total[5m])) > 0.05
        for: 3m
        labels:
          severity: page
        annotations:
          summary: "接口 5xx 比例超过 5%"
          runbook: "https://docs.example.internal/runbooks/error-rate"

      - alert: APIProcessRestarting
        expr: increase(ticket_app_restart_total[15m]) >= 3
        for: 1m
        labels:
          severity: page
        annotations:
          summary: "应用 15 分钟内重启超过 3 次"
```

告警分级建议：

```text
page（立即处理）  站点不可用、错误率持续升高、频繁崩溃
ticket（工作时间处理）  磁盘将满、单依赖抖动但已降级
info（仅记录）    短时尖峰后自动恢复
```

#### 7.3 常见误区

> 误区：阈值凭感觉定，指标抖动一秒就告警。

应使用 `for:` 持续时间窗口过滤瞬时尖峰，并结合历史基线调整阈值；告警要有恢复通知，避免问题已解决却无人知晓。

> 误区：监控系统和被监控服务部署在同一台主机、同一网络。

主机宕机或网络分区时，监控自身也失联，永远不会告警。外部可用性探测应独立于被监控环境。

### 8. 从告警到根因的排障闭环

#### 8.1 定义

排障闭环是一条标准化流程：收到告警 → 确认影响面 → 用指标缩小范围 → 用日志和追踪定位根因 → 缓解（回滚、摘流、扩容）→ 修复 → 验证 → 复盘并改进监控。

全栈关系：它把本单元所有概念串成实战动作，也是第 60 单元答辩中“调试类问题”的标准答案结构。

#### 8.2 流程示例

```text
告警：HighErrorRate，/api/tickets 5xx 比例 12%
 1. 影响面：看请求量与用户分布，确认全局性还是局部
 2. 时间相关性：错误率起点与最近一次发布时间是否吻合
    吻合 → 优先按第 57 单元流程回滚到上一版本，先止血
 3. 下钻日志：按 level=error 过滤，读取错误类型与堆栈
 4. 查看追踪：p95 高的 span 落在哪个依赖
 5. 对照进程指标：内存持续升高？事件循环延迟？重启次数？
 6. 缓解后验证：错误率回落、Uptime 恢复、错误追踪新增停止
 7. 根因修复：补回归测试，更新 runbook，必要时补埋点与告警
```

一次事故记录模板：

```text
事故标题：
发生与恢复时间：
影响范围（用户比例、失败请求数）：
时间线（告警、发现、缓解、恢复各节点）：
根因：
采取的措施：
后续行动（责任人、期限、如何防止复发）：
```

用 Bash 快速收集排障证据：

```bash
sudo journalctl -u ticket-api --since "20 minutes ago" -p err --no-pager
systemctl status ticket-api --no-pager -l
curl -fsS http://127.0.0.1:3000/metrics | grep ticket_http_requests_total
```

#### 8.3 常见误区

> 误区：服务恢复后就结束，不做复盘。

没有根因修复与防复发措施，同类事故会再次发生。复盘关注流程与系统，而不是追究个人。

> 误区：排查时一次改多个变量。

无法确定是哪一项生效。应一次验证一个假设，并在每一步保留证据。

5. 场景分析：监控显示 `/api/tickets` 错误率在发布后从 0.2% 升到 9%。你会如何按时间线止血并定位？

7. 什么是结构化日志？请求 ID 在全栈排障中起什么作用？它需要在哪些组件之间透传？

10. 场景分析：用户反馈“偶发很慢”，服务端平均延迟正常。结合追踪、真实用户指标和分位数，你会如何找到这部分用户？

## 实践练习题

### 练习 1：健康检查与结构化日志

#### 任务

为已有 Node 服务实现分级健康检查与结构化 JSON 日志，并能用请求 ID 串联一次完整请求。

#### 步骤约束

1. 实现 `/health/live` 与 `/health/ready`，就绪检查包含带超时的数据库探测。
2. 应用启动完成前就绪探针返回 503，启动完成后返回 200。
3. 使用日志库输出 JSON 日志，包含 service、version、requestId、level、msg。
4. 为每个请求生成或继承请求 ID，并在响应头返回。
5. 配置脱敏：口令、授权头、邮箱、令牌不得出现在日志中。
6. 记录启动、就绪、一次成功请求和一次模拟错误。

#### 提交物

- 健康检查与日志中间件代码；
- 四类事件的 JSON 日志样本；
- 请求 ID 在响应头与日志中对应的证据；
- 200 字以内的探针语义说明。

#### 验收标准

- 存活与就绪语义正确，依赖故障时只摘流不乱杀进程；
- 日志为合法 JSON，字段齐全且敏感字段被掩码；
- 同一次请求的日志可通过 requestId 串联；
- 用 curl 能复现状态码变化。

### 练习 2：指标埋点与错误上报

#### 任务

为应用接入 Prometheus 指标与错误追踪，建立“请求量、延迟、错误率”的可查询指标，以及异常自动上报与发布关联。

#### 步骤约束

1. 暴露 `/metrics`，采集默认进程指标与 HTTP 请求 Counter、延迟 Histogram。
2. 本地运行 Prometheus 抓取，用 PromQL 写出 p95 延迟与 5xx 占比查询。
3. 接入错误追踪（DSN 用环境变量占位注入），上报一次手工触发的异常。
4. 在错误上报中附带版本、环境与用户标识，并脱敏授权信息。
5. 用版本号创建一次 release，记录命令与结果。
6. 制造一次 5xx，验证它同时出现在指标与错误追踪中。

#### 提交物

- 指标与错误上报代码；
- Prometheus 配置与两条 PromQL 查询结果；
- 错误追踪 issue 的脱敏截图或描述；
- release 命令记录。

#### 验收标准

- `/metrics` 输出包含应用与进程指标；
- p95 与错误率查询可执行且数值合理；
- 异常可在错误追踪中按版本检索；
- 提交物不含真实 DSN 令牌与用户敏感信息。

### 练习 3：外部可用性监测与告警闭环

#### 任务

部署独立的 Uptime 监测并配置至少两条告警规则，完成一次从告警到复盘的完整演练。

#### 步骤约束

1. 在与应用不同的环境（或本机外的网络位置）部署可用性探测，间隔不超过 60 秒。
2. 配置首页与就绪端点两个探测，关键字校验页面内容。
3. 在 Prometheus 中配置高错误率与频繁重启两条告警，使用持续时间窗口。
4. 演练一次故障（停服务或注入错误），记录告警触发、通知与恢复全过程。
5. 先通过回滚或重启缓解，再定位根因并验证恢复。
6. 按事故模板输出一份复盘，包含时间线、根因与防复发行动。

#### 提交物

- 探测与告警配置；
- 告警触发与恢复通知记录；
- 排障过程的指标、日志证据；
- 一份完整事故复盘。

#### 验收标准

- 探测独立于被监控主机，故障时确能收到通知；
- 告警有去重、持续窗口与恢复通知；
- 排障遵循先止血后定位的顺序，证据链完整；
- 复盘包含可执行的防复发措施与负责人。
