# 32-上线运营结业答辩与跨端拓展

## 目标

这是课程的收官单元。「逛吃指南」已经完成功能、交易、性能与测试，最后一公里是让它真正被用户搜索和扫码使用，并在结业答辩中证明你具备独立交付小程序工程师的完整能力；同时把视野从微信单一平台扩展到支付宝、抖音与跨端框架。完成本单元后，学员应能够：

1. 说清开发版、体验版、正式版三者的关系与访问权限，独立完成上传、提交审核、发布、分阶段放量与回退的完整操作闭环。
2. 识别审核高频拒因：功能不完整、测试账号缺失或失效、类目与资质不符、用户隐私保护指引缺失、诱导分享/关注、iOS 端虚拟支付违规等，并能在送审前逐项自查。
3. 读懂审核驳回意见，按“定位条款 → 最小整改 → 附说明复审”的方法论完成整改，理解加急、定时发布等机制的使用边界。
4. 理解小程序类目体系与资质要求：知道本地生活、餐饮、平台信息类业务分别需要什么证照，以及资质与小程序实际功能必须一致。
5. 建立数据运营的指标语言：访问（打开、PV/UV、来源场景）、留存（次日/7 日/30 日）、转化（自定义漏斗）各自衡量什么、如何驱动迭代。
6. 使用小程序管理后台与自定义分析：注册自定义事件、用 `wx.reportEvent` 埋点、配置漏斗与留存分析，并产出一份基于真实数据的运营分析。
7. 概览微信、支付宝、抖音三大小程序平台在模板语法、API 命名、登录支付、审核规则与流量生态上的差异，建立“能力对照”而非“语法背诵”的认知。
8. 掌握 Taro（React 系）与 uni-app（Vue 系）的入门开发方式与编译/运行时原理，能把「逛吃指南」首页改造成一个跨端 demo 并在至少两个平台编译运行。
9. 结合已有的原生功底完成跨端选型：说清什么场景留在原生、什么场景引入跨端框架，以及跨端不等于免维护平台差异。
10. 按流程完成结业答辩：组织九维能力矩阵的全部证据，提交最终交付清单，现场演示已上线小程序的交易闭环并回答架构、合规与权衡类问题。

## 详细的理论知识讲解和示例伪代码

### 1. 三个版本：开发版、体验版、正式版

小程序的版本不是 Git 分支概念，而是公众平台上的三类发布物：

| 维度 | 开发版 | 体验版 | 正式版 |
|---|---|---|---|
| 产生方式 | 开发者工具「上传」，每次上传生成一个开发版 | 在开发版列表中「选为体验版」，同时只有一个 | 审核通过后「发布」 |
| 谁能访问 | 项目成员（开发者、协作者） | 后台添加的体验成员，扫码进入 | 所有微信用户，可搜索、可扫码 |
| 是否需要审核 | 否 | 否 | 是 |
| 典型用途 | 日常联调、提审的来源版本 | 给产品/测试/客户验收、真机回归 | 对外服务 |
| 有效期 | 保留数量与期限受平台限制 | 随被选为体验版的版本更新 | 长期在线，直至新版本替换 |

关键关系：**提审的入口挂在某个开发版上；审核通过后发布出去，才成为正式版；体验版是从开发版里“标记”出来给体验成员用的，不经过审核。** 所以一个标准节奏是：

```text
开发完成 → 上传得到开发版 → 选为体验版做真机回归
        → 用同一个开发版提交审核 → 审核通过 → 发布（可分阶段）
```

误区：以为“上传了就是上线了”。上传只产生开发版，用户完全无感知；只有审核通过并发布后，正式版才会变更。

### 2. 上传与提审全流程

上传（开发者工具或 CI 中的 miniprogram-ci，U30 已讲）时需要填写版本号与备注。建议版本号语义化（如 `1.2.0`），备注写清本次变更点，它会出现在开发版列表里，也是提审材料的一部分。

提审在公众平台「管理 → 版本管理」中操作，需要准备：

1. **服务类目**：选择与实际功能一致的类目，部分类目需上传资质（见第 6 节）。
2. **功能页面（首页/测试路径）**：告诉审核员从哪个页面进入主流程。
3. **测试账号**：如果小程序需要登录才能使用核心功能，必须提供账号密码或免登方式，并保证审核期间有效。
4. **功能与页面说明**：多页面、多角色、特殊流程（支付、退款、商家端）要给出操作指引。
5. **权限与隐私声明**：位置、相机、相册、手机号等权限的用途，与已配置的用户隐私保护指引一致。

```text
提审检查单：
  □ 服务类目与功能一致，资质在有效期内
  □ 体验版真机回归通过（含支付、登录、各异常分支）
  □ 测试账号可登录、数据完整、审核期间不过期
  □ 隐私指引已配置，弹窗与代码行为一致
  □ 无占位页面、无死按钮、无 console 调试输出
  □ U31 的自动化测试与门禁为绿色
```

审核时长通常为数小时到一两个工作日，存在节假日波动；加急审核每年次数有限，只用于真正紧急的修复，不应作为常规手段。

### 3. 发布：立即发布、定时发布与分阶段发布

审核通过后并不自动上线，可以选择发布方式：

- **全量发布**：正式版立即对全部用户更新。用户冷启动时拉取新版本，已经在线的用户受小程序更新策略影响（可结合 `wx.getUpdateManager` 提示更新，U04 已讲）。
- **定时发布**：指定时间自动发布，适合配合运营活动、统一上线时点。
- **分阶段发布（灰度）**：按比例让一部分用户先用上新版，例如先放量较小比例，观察一段时间无异常再继续扩大，直至全量。

灰度的工程意义在于：U31 的自动化测试只能验证“想到的场景”，而真实用户的机型、网络、数据组合无法穷举。分阶段发布把“未知问题”的爆炸半径限制住。放量期间应同步观察：

```text
放量  →  观察崩溃率/异常率、关键接口成功率与耗时
       观察支付漏斗每一步转化是否与旧版一致
       无异常 → 继续放量；异常 → 暂停或回退
```

误区：灰度开了就不管，到点直接全量。灰度不是“延迟发布”，价值全在观察窗口与决策动作。

### 4. 回退机制与发布事故处置

平台支持在分阶段发布期间取消发布，并允许在一定条件下将正式版回退到上一历史版本（有时间与次数限制，以后台实际提供为准）。因此发布前必须有预案，而不是出事后临时找按钮：

```text
发布预案（上线前写好）：
  1. 回退责任人与联系方式
  2. 监控指标与阈值：崩溃率、支付成功率、核心接口错误率
  3. 分级处置：
     - 轻微问题：暂停放量，修复后走快速通道
     - 核心功能受损：立即回退到上一版本
     - 资损风险（支付/订单）：回退 + 数据核对 + 受影响用户通告
  4. 回退验证清单：回退后确认旧版服务正常、数据兼容
  5. 复盘要求：时间线、根因、为何测试未拦截、改进项
```

一个必须正视的事实：回退只能回退小程序代码，**已经写入的数据库数据、已经发生的订单不会自动回滚**。所以涉及数据结构变更时（集合字段调整、状态机变更），要保持新旧版本双写兼容或提供数据修复脚本——发布设计的边界远大于“点一下回退”。

### 5. 审核拒因一：功能完整度与测试账号

“功能不完整/功能无法体验”是最常见的驳回类型，典型情形：

- 页面是占位状态：空白页、“敬请期待”“建设中”、大量 Lorem 式假数据；
- 按钮点击无反应、跳转 404、列表永远 loading；
- 核心链路走不通：下单后无反馈、支付后无结果页；
- 仅适配了特定机型，审核机上布局错乱；
- 保留了调试代码：vConsole、测试入口、mock 数据开关。

第二类高频问题是**测试账号**：

- 需要登录却没提供账号；
- 提供的账号已失效、被锁定、密码错误；
- 账号权限不完整（比如审核员看不到付费流程）；
- 测试数据是空的（登录后没有任何店铺/商品可点）。

整改方法不是碰运气重提，而是：用全新设备、全新网络、用审核员视角按提审路径完整走一遍；账号在审核期内保持有效并准备好预置数据。这也是体验版回归的意义——体验成员扫码进入的体验，就近似审核员的体验。

### 6. 审核拒因二：类目资质与 iOS 虚拟支付

**类目与资质**必须与实际功能匹配。小程序后台有完整的类目树，常见方向：

- 餐饮（点餐、外卖、餐饮服务平台）：涉及食品经营的，需要营业执照及《食品经营许可证》等相应资质；
- 本地生活/信息平台：以平台模式聚合商家信息时，可能涉及增值电信业务等资质要求，具体以类目说明为准；
- 特殊行业：医疗、金融、保险、新闻、政务、教育、直播等有专门资质或许可，个人主体通常不可选；
- 地图与位置：底层地图需由有资质的服务商提供（课程使用腾讯位置服务）。

原则是“**功能跑到哪，类目资质覆盖到哪**”。一个餐饮点评小程序若开放在线点餐，就不再只是“信息查询”类目；新增业务线前先查类目要求，不要等审核驳回。

**iOS 端虚拟支付**是另一条高压线：在 iOS 端，小程序内销售虚拟商品（会员、课程、虚拟币、数字内容、解锁功能）不得使用微信支付等第三方支付方式——这是平台与苹果规则的共同约束。实体商品（外卖、到店消费、实物电商）正常使用微信支付不受影响。常见踩雷：用“支付 1 元解锁高级筛选”测试课程功能。课程中如需演示虚拟权益，应在 Android 或开发环境演示，并在 iOS 端隐藏入口。

### 7. 审核拒因三：隐私保护指引与诱导分享

隐私合规的核心配置：

1. 在公众平台配置《小程序用户隐私保护指引》，逐项声明收集的信息类型（手机号、位置、相册、相机、微信账号信息等）与用途。
2. 代码侧开启隐私检查（`app.json` 中 `__usePrivacyCheck__: true`），在收集敏感信息前向用户展示指引并取得同意。
3. 敏感接口在配置中声明，用途说明必须与实际使用一致：

```json
// app.json（节选）
{
  "usePrivacyCheck": true,
  "permission": {
    "scope.userLocation": {
      "desc": "用于按距离为你排序附近的逛吃店铺"
    }
  },
  "requiredPrivateInfos": [
    "getLocation",
    "chooseLocation"
  ]
}
```

驳回高发点：调用了定位/相册/手机号却没有对应指引；用途说明空泛（“用于优化服务”）；拒绝授权后页面白屏或功能锁死（必须提供不授权时的可用路径）。

**诱导分享/诱导关注**同样是红线：

- “分享到群后才能解锁功能/领取优惠”——强制分享；
- 分享文案利诱、承诺分享可得现金、诱导分享朋友圈集赞；
- 诱导关注公众号（“关注公众号后继续使用”）；
- 利益诱导添加个人微信、下载 App。

U25 的分享裂变要与诱导分享划清界限：正常的“自愿分享 + 分享后自然的服务信息（如拼团状态）”允许；以阻断核心功能为筹码的强制分享不允许。判别标准是“用户不分享，还能不能正常使用”。

### 8. 整改方法论与复审节奏

收到驳回通知时先读两样东西：**驳回条款**（对应运营规范的具体条目）与**审核员描述/截图**。整改流程：

```text
第一步 定位：在规范中找到对应条款，确认违规的确切页面与行为
第二步 复现：按描述在本机/真机复现，复现不了时用截图反推
第三步 最小整改：只改违规点，不顺手重构，避免引入新问题
第四步 自测：按提审路径完整回归，更新测试账号与说明
第五步 重提：在提审备注中逐条说明“问题—改法—验证方式”
```

提审备注的写法示例：

```text
本次针对上次驳回整改：
1. “功能不完整”：已补全订单详情页退款入口，新增退款申请→商家审核流程，
   入口：我的→全部订单→任意已支付订单→申请退款；
2. “测试账号失效”：已更换账号 138****0000（密码见测试信息），账号内有
   3 家店铺与可下单数据，审核期间持续有效；
3. 已按隐私指引补充相册用途说明（用于上传评价图片）。
```

两个经验：整改说明让审核员低成本确认每一条，过审更快；反复同类违规会影响审核信誉，第一次驳回就应根治。

### 9. 数据运营指标：访问、留存、转化

上线只是开始，数据回答“做得怎么样、下一步改什么”。三类核心指标：

**访问类（用户从哪来、来了多少）**

| 指标 | 含义 |
|---|---|
| 打开次数 | 小程序被启动的次数（含冷启动、热启动的统计口径） |
| 访问次数 / 访问人数（PV/UV） | 页面浏览量 / 去重用户数 |
| 新用户数 | 首次访问的用户 |
| 人均停留时长 / 人均页面数 | 访问深度 |
| 来源与场景值 | 扫码、搜索、分享、公众号、附近、直播间等入口（scene） |

**留存类（用户还回不回来）**

- 次日留存、7 日留存、30 日留存：某日新增用户在第 N 天再次访问的比例。
- 对「逛吃指南」这类本地生活应用，留存反映“是否真的进入用户的消费决策循环”；只看访问量容易被一次分享带来的瞬时流量误导。

**转化类（用户有没有完成目标动作）**

为逛吃指南定义的核心漏斗：

```text
店铺列表曝光 → 进入店铺详情 → 加菜/领券 → 提交订单 → 支付成功
   100%          45%            22%         15%         12%
```

每一步的转化率都指向具体改进：列表→详情低是封面/名称/排序问题；详情→加菜低是菜单与价格问题；提交→支付低要查支付失败率、运费/配送费展示、收银台体验。脱离漏斗谈“优化体验”是没有靶子的。

### 10. 小程序后台、自定义分析与埋点

管理后台的「统计」提供开箱即用的访问、用户画像、留存看板；「自定义分析」支持自定义事件、漏斗与留存。自定义事件需要先在后台注册（事件名与参数），再在代码中上报：

```ts
// miniprogram/utils/report.ts
export function reportAddCart(payload: {
  shopId: string
  dishId: string
  price: number
}) {
  wx.reportEvent('add_cart', {
    shop_id: payload.shopId,
    dish_id: payload.dishId,
    price: payload.price
  })
}

export function reportPayResult(
  orderId: string,
  amount: number,
  result: 'success' | 'cancel' | 'fail'
) {
  wx.reportEvent('pay_result', {
    order_id: orderId,
    amount,
    result
  })
}
```

```ts
// 支付回调处（U23 的成果）
success: () => {
  reportPayResult(orderId, amount, 'success')
  wx.redirectTo({ url: '/pages/pay-result/pay-result?status=success' })
},
fail: (err) => {
  const result = /cancel/.test(err.errMsg) ? 'cancel' : 'fail'
  reportPayResult(orderId, amount, result)
}
```

埋点纪律：

- 事件名与参数先在后台注册再上报，命名稳定、含义单一，避免一个事件塞十种语义；
- 参数用可枚举的有限取值（如 result: success/cancel/fail），不要上报自由文本；
- 只上报分析必需的字段，不上报姓名、手机号等敏感信息；
- 关键业务指标（支付成功率等）也可用 `wx.reportMonitor` 做数值监控与告警。

产出物是一份运营分析：选定时间窗口，给出访问/留存概览与一个自定义漏斗，指出最低转化的环节并提出一个可执行的改进假设——数据工作的价值在决策，不在截图。

### 11. 微信 / 支付宝 / 抖音小程序差异概览

三大平台同属“小程序”技术形态，宿主模型高度相似（逻辑/视图分离、类小程序 API），但在细节上各成体系：

| 维度 | 微信 | 支付宝 | 抖音 |
|---|---|---|---|
| 模板/样式 | WXML / WXSS | AXML / ACSS | TTML / TTSS |
| 指令前缀 | `wx:if`、`wx:for` | `a:if`、`a:for` | `tt:if`、`tt:for` |
| API 命名空间 | `wx.*` | `my.*` | `tt.*` |
| 登录 | `wx.login` → code 换 openid | `my.getAuthCode` → 换 userId | `tt.login` → 换 openid/anonymous |
| 支付 | 微信支付 JSAPI | 支付宝小程序支付 | 抖音支付（担保交易等） |
| 消息触达 | 订阅消息 | 订阅消息/生活号链路 | 订阅消息 |
| 生态流量 | 社交分享、搜一搜、附近、公众号 | 生活号、芝麻信用、政务民生 | 短视频挂载、直播间、内容推荐 |
| 开发者工具 | 微信开发者工具 | 支付宝小程序开发者工具（小程序开发者工具） | 抖音开发者工具 |
| 云能力 | 微信云开发 CloudBase | 支付宝小程序云 | 抖音云 |

需要特别注意的差异类型：

1. **组件/API 覆盖不一致**：同一个能力（如地图组件、蓝牙、复杂动画、订阅消息的一次/长期模型）在三端的字段和行为有差异，`canIUse` 式判断在各端都要做。
2. **授权模型不同**：权限弹窗、拒绝后引导设置页的路径、可获取的用户信息字段各不相同；2022 年后微信头像昵称已改为合规填写，支付宝/抖音也有各自的用户信息规则。
3. **审核与运营规则不同**：三端类目资质、虚拟支付、诱导分享的尺度各异，上线要分别按各端规范走。
4. **网络与域名**：request 合法域名、ICP 备案要求在各端后台分别配置。

结论：平台差异主要不在“语法长什么样”（机械差异），而在登录体系、支付、生态触达与审核规则（生态差异）。跨端框架能抹掉机械差异，抹不掉生态差异。

Taro 是 React 技术栈的跨端框架（当前主线 Taro 4，配合 React 18）。用同一套 React 代码编译到微信/支付宝/抖音等小程序及 H5、RN。

```ts

  id: string
  name: string
  score: number
  cover: string
}

export async function fetchShops(params: { city: string }): Promise<Shop[]> {

    data: params
```

样式方面，Taro 以设计稿宽度（默认 750）为基准，构建时把 `px` 换算为各端的 `rpx` 单位，也可直接使用 `rpx`。

**原理**要讲清两代机制：Taro 早期版本以“编译时转换”为主，把 JSX 直接编译成各端模板；Taro 3/4 转向“**运行时适配**”——内置一个小程序版的 React reconciler，React 的更新不再一一翻译成静态模板，而是通过一套通用渲染模板配合运行时把组件树数据 `setData` 到视图层。好处是 React 写法更纯粹、动态性更强；代价是运行时开销与包体积增加，极端复杂列表仍需关注性能。

平台差异用环境变量做条件处理：

```ts
if (process.env.TARO_ENV === 'weapp') {
  // 仅微信逻辑
} else if (process.env.TARO_ENV === 'alipay') {
  // 仅支付宝逻辑
}
```

构建命令按平台区分：`taro build --type weapp`、`--type alipay`、`--type tt`，产物分别用各端开发者工具打开。

### 14. 跨端选型：带着原生功底做判断

选型不是“Taro 和 uni-app 谁更好”，而是“我的团队、目标平台与维护成本是什么”：

| 考量 | 倾向原生 | 倾向 Taro | 倾向 uni-app |
|---|---|---|---|
| 只做微信、追求最细颗粒控制 | ✔ |  |  |
| 团队是 React 技术栈 |  | ✔ |  |
| 团队是 Vue 技术栈 |  |  | ✔ |
| 同时覆盖小程序 + H5 |  | ✔ | ✔（H5 成熟） |
| 需要大量平台特有能力、频繁踩平台边界 | ✔ | 条件编译补足 | 条件编译补足 |
| 复用 Web 生态（状态管理、组件库、工程链） |  | React 生态 | Vue 生态 |

三条必须建立的判断：

1. **跨端框架不消除平台差异**。登录、支付、订阅消息、审核规则仍按各端分别处理；框架解决的是“少写几套 UI 代码”，不是“一次开发什么都不管”。
2. **原生功底在跨端时代更值钱，而不是作废**。你在课程里学到的双线程模型、`setData` 成本、宿主能力边界，正是跨端框架底层发生的事——理解这些才能解释跨端页面为什么慢、某些 DOM 库为什么不能用、条件编译为什么绕不开。
3. **真实工程里混合很常见**：主 App 用原生保稳定与性能，营销活动页用跨端快速铺多端；先用原生把一个平台做深，再用跨端扩平台，是比“一开始就全平台”稳妥得多的路径。

### 练习 2：埋点方案与转化漏斗运营报告

#### 任务

为「逛吃指南」设计并实现核心漏斗埋点（列表曝光、进详情、加菜、下单、支付结果），在自定义分析中注册事件并配置漏斗，运行一段时间后产出一份运营报告，指出最薄弱环节并给出改进假设。

参考代码：

```ts
// miniprogram/utils/report.ts
export function reportFunnel(
  step: 'list_view' | 'detail_view' | 'add_cart' | 'submit_order' | 'pay_result',
  extra?: Record<string, string | number>
) {
  wx.reportEvent(step, {
    shop_id: extra?.shop_id ?? '',
    amount: extra?.amount ?? 0,
    result: extra?.result ?? ''
  })
}
```

#### 步骤约束

1. 事件与参数先在后台注册，命名全小写下划线风格，参数取值可枚举。
2. 支付结果必须覆盖 success、cancel、fail 三种取值。
3. 报告必须包含：时间窗口、访问概览、漏斗各步绝对值与转化率、一个改进假设（如“详情→加菜转化仅 35%，假设首屏无招牌菜图导致，建议加置顶位 A/B”）。
4. 数据必须来自真实上报，可用自己多次操作+同学互助产生，但禁止编造。

#### 提交物

- 埋点代码与后台事件注册截图；
- 自定义漏斗配置截图；
- 一页运营报告。

#### 验收标准

- 五个事件均可在后台查到真实数据，漏斗与埋点一一对应；
- 报告的结论能由数据推出、改进建议可执行；
- 上报参数不含敏感信息。

### 练习 3：跨端 demo——Taro 或 uni-app 版逛吃指南首页

#### 任务

使用 Taro（React）或 uni-app（Vue）把「逛吃指南」首页迁移为跨端 demo：包含店铺列表、加载态、点击进详情（详情页可只保留标题与店铺名）、分享入口；至少编译到微信 + 支付宝/抖音两个平台并成功运行。

参考代码（Taro 条件处理）：

```tsx
import Taro from '@tarojs/taro'
import { View, Text } from '@tarojs/components'

export default function PlatformTag() {
  const platform =
    process.env.TARO_ENV === 'weapp'
      ? '微信'
      : process.env.TARO_ENV === 'alipay'
        ? '支付宝'
        : '其他平台'

  return (
    <View>
      <Text>当前运行平台：{platform}</Text>
    </View>
  )
}
```

uni-app 可使用 `<!-- #ifdef MP-WEIXIN -->` 条件编译达到同样效果。

#### 步骤约束

1. 数据通过 `Taro.request`/`uni.request` 请求课程提供的接口（或本地 fixture），两端使用各自开发者工具分别打开验证。
2. 平台特有元素（如微信 open-type=share）必须用条件编译/环境变量隔离，保证另一个平台编译不报错。
3. 样式使用响应式单位，列表在两台不同尺寸设备上不错位。
4. 代码结构保持组件化：列表项抽为独立组件，不允许全部堆在一个文件。

#### 提交物

- 跨端项目仓库（含 README：安装、编译、各端运行命令）；
- 两个平台的编译成功截图与真机/模拟器运行截图；
- 200 字选型说明：为什么选 Taro/uni-app、踩了哪些平台差异。

#### 验收标准

- 两个平台均编译通过、核心链路（列表→详情）可操作；
- 平台特有能力已隔离，无平台报错；
- demo 基于真实业务字段，不是模板计数器。

## 阶段验收作业

本作业是 W16 结业里程碑、也是整个课程的总验收：「逛吃指南」正式上线（或采用课程指定替代方案）、跨端 demo 可运行、九维能力证据齐备并通过结业答辩。

### 任务描述

1. 完成上线闭环：准备提审材料 → 提交审核 → 处理驳回（如有）→ 发布 → 分阶段放量并观察 → 确认全量；保留全过程记录。
2. 建立发布预案与数据基线：写明回退责任人、监控阈值与处置分级；上线后给出真实的访问、留存与支付漏斗数据，提出一个改进假设。
3. 完成跨端 demo：用 Taro 或 uni-app 迁移首页，至少在两个平台编译运行，并说明选型理由与遇到的平台差异。
4. 整理九维证据：对照能力矩阵逐项准备材料，补齐缺失维度；完成最终交付清单的全部 10 项。
5. 参加结业答辩：真机演示正式版交易闭环，讲解架构、合规与权衡，现场回答提问。

### 完成标准

- 「逛吃指南」为已发布正式版，可通过扫码或搜索访问，交易闭环（下单→支付→订单状态，退款入口可演示）真实可走；采用替代方案者，提审记录完整、阻断原因客观可核、体验版全流程可演示。
- 审核整改记录真实可查，隐私指引、类目资质、分享与支付合规无遗留问题。
- 后台有真实数据，漏斗分析与改进假设成立；跨端 demo 两个平台均实际运行通过。
- 最终交付清单 10 项齐全，九维矩阵每维有对应证据，无空白维度。
- 答辩现场演示成功，问答中能解释架构取舍、安全设计与平台边界。

### 强制不通过条件

- 小程序未上线且不属于课程认可的替代情形，或替代材料缺失（无提审记录、阻断说明不成立）；
- 演示的交易闭环是伪造的（前端假支付、无真实订单状态、跳过验签），或仅播放录屏而无任何真实环境演示；
- 存在明知未整改的合规问题：诱导分享、iOS 虚拟支付违规、隐私指引缺失、类目资质造假；
- 跨端 demo 只有一个平台跑通、套模板与课程业务无关，或无法说明框架基本原理；
- 九维矩阵中有任一维度无证据（以课程总纲为准），或交付清单缺项超过 2 项；
- 运营数据全部编造、后台无任何真实上报记录；
- 答辩中无法解释核心架构决策（登录鉴权、支付安全、数据权限、性能取舍）中的任意基本问题。

完成本作业即达成课程培养目标：你已独立走完“需求 → 开发 → 云与后端 → 交易 → 性能 → 测试 → 上线 → 运营 → 跨端”的完整闭环，并能以工程师的方式表达这一切。小程序生态仍在演进（新渲染引擎、新平台能力、新合规要求），带着本课程建立的机制级认知与证据化习惯继续迭代，从「逛吃指南」出发，去交付下一个真正有人用的产品。
