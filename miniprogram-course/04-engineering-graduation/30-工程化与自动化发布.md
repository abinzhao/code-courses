# 30-工程化与自动化发布

## 目标

完成本知识单元后，学员应能把「逛吃指南」的交付方式从“开发者在本机打开微信开发者工具、手动点上传”升级为“代码合入即触发流水线：装依赖、类型检查、Lint、构建 npm、生成预览二维码、按版本自动上传”的工程化体系，并保证任何一个新同学在一台干净机器上都能复现同样的构建结果。

学员应能够：

1. 说清小程序使用 npm 的完整链路：`package.json` 声明依赖、安装到 `node_modules`、开发者工具“构建 npm”把可被小程序识别的产物拷贝到 `miniprogram_npm`，以及为什么小程序运行时不能直接读 `node_modules`。
2. 正确配置 `project.config.json` 中的 `packNpmManually`、`packNpmRelationList` 与 `miniprogramRoot`，讲清“构建 npm”到底构建了什么、哪些包无法被构建。
3. 在小程序工程中启用 TypeScript 严格模式，写出面向小程序运行时的 `tsconfig.json`，理解 `strict`、`noUncheckedIndexedAccess`、类型声明与编译产物位置。
4. 使用 ESLint 对 TS/JS 做静态检查，配置小程序环境与规则集，区分“会导致 bug 的问题”与“风格问题”；用 Prettier 统一格式，并解决二者的规则冲突。
5. 配置 Git 提交规范与本地钩子（husky + lint-staged），让格式、Lint 在提交前自动执行，理解“本地快检查 + CI 全量检查”的分工。
6. 接入 Vant Weapp 或 TDesign Miniprogram 组件库，掌握“安装 → 构建 npm → 全局/页面 usingComponents 引用 → 按需使用”的完整步骤，说清小程序组件库与 npm 普通库的差异。
7. 说清小程序插件（plugin）与 npm 组件库、自定义组件的区别，完成插件在 `app.json` 的声明、申请与使用。
8. 理解 miniprogram-ci 的定位：不依赖开发者工具图形界面即可在命令行完成预览与上传；完成准备工作（小程序代码上传密钥、IP 白名单），区分“小程序代码上传私钥”与业务密钥。
9. 使用 miniprogram-ci 的 `preview` 与 `upload` 方法，在 Node 脚本中生成预览二维码（自定义编译条件）与上传开发版本，理解机器人号与上传版本号语义。
10. 在 CI 中通过 Secrets 注入上传私钥，做到密钥绝不入库；编写 GitHub Actions 流水线串起 install / typecheck / lint / build npm / preview / upload，制定版本号与描述规范，并能通过锁文件、缓存与干净环境验证保证构建可复现。

## 技术栈

本单元在微信原生 + TypeScript 工程上引入 npm、静态检查与持续集成，发布动作由 miniprogram-ci 在 GitHub Actions 中完成。

| 工具或环境 | 用途 | 学习要求 |
|---|---|---|
| `package.json` / package-lock.json | 依赖声明与锁定 | 理解 dependencies/devDependencies |
| `node_modules` / `miniprogram_npm` | npm 安装产物 / 小程序可用产物 | 说清“构建 npm”的拷贝与裁剪 |
| 微信开发者工具“构建 npm” | 生成 miniprogram_npm | 会触发构建并读懂报错 |
| `project.config.json` npm 相关字段 | 声明 npm 构建关系 | 会配 packNpmManually 等 |
| TypeScript 5 + `tsconfig.json` | 类型检查 | 会开 strict 并处理类型错误 |
| ESLint 8（含 typescript-eslint） | 静态检查 | 会写配置并区分错误等级 |
| Prettier 3 | 代码格式化 | 会与 ESLint 协作不冲突 |
| husky + lint-staged | 提交前钩子 | 只对暂存文件快速检查 |
| Vant Weapp / TDesign Miniprogram | 开源组件库 | 完成安装、构建、引用全流程 |
| 小程序插件（plugin） | 平台级能力扩展 | 会声明、申请、调用 |
| miniprogram-ci | 命令行预览/上传 | 会写 preview/upload 脚本 |
| 小程序代码上传密钥（私钥） | CI 身份凭证 | 只走 CI Secrets，不入库 |
| GitHub Actions | CI/CD 平台 | 会写 workflow、job、step 与缓存 |
| 语义化版本号 + 版本描述 | 发布规范 | 会按规范命名与生成描述 |
| 干净环境（新机器/全新 runner） | 可复现验证 | 会验证无隐式依赖 |

工程约定：

- 上传私钥、任何业务密钥只通过 CI Secrets / 本地环境变量注入，仓库与日志中不得出现私钥内容。
- 主分支保护：必须通过 CI 的 typecheck/lint 才能合并；禁止在本机“手动上传正式包”绕过流水线。
- 依赖必须锁定（提交 lock 文件），CI 使用 `npm ci` 按锁文件安装，保证可复现。
- 各工具版本、基础库版本、miniprogram-ci 参数以官方当前文档为准。

## 详细的理论知识讲解和示例伪代码

### 1. 为什么需要工程化

在课程前半段，发布一个版本意味着：开发者在本机打开微信开发者工具 → 点“预览”生成二维码自己测 → 点“上传”，手动填版本号和描述 → 到公众平台设为体验版/提交审核。这个流程在团队规模小、发版少时可以接受，但存在结构性问题：

- **不可复现**：构建结果依赖“某台电脑上的工具状态”，别人无法重建同样的包。
- **不可审查**：代码是否通过类型检查、有没有低级错误，全靠个人自觉。
- **密钥与权限失控**：谁都能用自己的微信账号上传，无法审计；手动操作容易把测试代码传上去。
- **效率低**：每次改动都要人工点一遍，无法做到“每次提交都出一个可扫码预览的包”。

工程化的目标是把这些重复、易错的环节固化为**机器自动执行、对所有人一致**的流水线。

```text
改造后的交付链路：
  git push / Pull Request
        │
        ▼
 GitHub Actions：npm ci → typecheck → lint → 构建 npm
        │
        ├─ 非发布分支：miniprogram-ci preview → 产出预览二维码（贴到 PR）
        └─ 发布标签：miniprogram-ci upload  → 开发版本，带规范版本号与描述
```

误区：认为“工程化就是配一堆工具”。工具只是手段，真正的产出是“质量门禁 + 一致环境 + 自动化发布”这套可依赖的流程。

### 2. 小程序“构建 npm”原理：node_modules 与 miniprogram_npm

普通 Node/Web 项目可以直接 `import` 位于 `node_modules` 里的包；小程序不行。小程序运行时只认识打包进小程序工程目录、路径明确的文件，且对包体积、文件组织有约束。为此微信提供了“构建 npm”机制：

```text
1. package.json 声明依赖并执行 npm install
        │  产物在 node_modules（体积大、含开发文件、含 Node 内置依赖）
        ▼
2. 开发者工具执行“构建 npm”（工具菜单或 CI 中对应能力）
        │  读取依赖入口、裁剪、按小程序可识别结构组织
        ▼
3. 生成 miniprogram_npm/（真正会被打进小程序包的产物）
        │  页面/组件通过 require/import 从 'miniprogram_npm/包名' 引用
        ▼
4. 上传时只打包 miniprogram_npm，不会上传 node_modules
```

需要在 `project.config.json` 中告诉工具 npm 工程的位置。最简配置：

```json
{
  "miniprogramRoot": "./",
  "setting": {
    "packNpmManually": false,
    "packNpmRelationList": []
  }
}
```

当 `package.json` 与小程序代码不在同一目录（如 monorepo、或小程序在子目录）时，需要手动声明构建关系：

```json
{
  "setting": {
    "packNpmManually": true,
    "packNpmRelationList": [
      {
        "packageJsonPath": "./package.json",
        "miniprogramNpmDistDir": "./miniprogram_npm/"
      }
    ]
  }
}
```

关键事实：

- `miniprogram_npm` 是**构建产物**，应加入 `.gitignore`，由工具/CI 生成，而不是手工维护。
- 修改依赖或升级包后，必须重新“构建 npm”，否则运行的还是旧产物。
- “构建 npm”针对的是**可在小程序环境运行的包**，并不是任意 npm 包都能成功（见下一节）。

### 3. 哪些 npm 包能被小程序使用

小程序逻辑层没有 Node.js 运行时：没有 `fs`、`path`、`http` 等内置模块，没有原生 addon，也没有 DOM。因此：

- 纯逻辑、零依赖或只依赖小程序可运行模块的包（如部分工具函数库）通常可用；
- 依赖 Node 内置模块、调用 `window/document`、包含原生二进制的包无法构建或运行报错；
- 小程序 UI 组件库（Vant Weapp、TDesign）以“自定义组件”形态发布，构建后在 `usingComponents` 引用；
- 包体积受小程序整体包大小限制，重型库要评估是否值得引入。

引入新依赖前的检查习惯：

```text
  ① 是否真的需要（能否用少量自有代码替代）
  ② 是否依赖 Node 内置模块 / DOM / 原生能力
  ③ 构建后体积增量（装进主包还是分包）
  ④ 维护活跃度与许可证
  ⑤ 安装后重新构建 npm 并真机验证
```

误区：看到 npm 上有包就装，构建时才发现依赖 `Buffer`/`stream`；为了一个小函数引入几百 KB 的通用库；忘记重新构建，线上仍跑旧版本。

### 4. TypeScript 严格模式与 tsconfig

课程全程使用 TypeScript，工程化阶段要把严格检查真正打开，让类型系统在 CI 中兜底，而不是“写了 TS 但处处 any”。

```json
// tsconfig.json
{
  "compilerOptions": {
    "strict": true,
    "target": "ES2020",
    "module": "CommonJS",
    "moduleResolution": "Node",
    "lib": ["ES2020"],
    "outDir": "dist",
    "rootDir": ".",
    "sourceMap": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "noImplicitReturns": true,
    "noFallthroughCasesInSwitch": true,
    "noUncheckedIndexedAccess": true,
    "forceConsistentCasingInFileNames": true,
    "skipLibCheck": true,
    "esModuleInterop": true,
    "resolveJsonModule": true,
    "types": ["miniprogram-api-typings"]
  },
  "include": ["**/*.ts"],
  "exclude": ["node_modules", "miniprogram_npm", "dist"]
}
```

要点解释：

- `strict: true` 是一组严格选项的总开关：包含 `noImplicitAny`、`strictNullChecks`、`strictFunctionTypes` 等。
- `strictNullChecks` 强制处理 `undefined/null`，大量“取不到数据导致白屏”的 bug 在编译期暴露。
- `noUncheckedIndexedAccess` 让 `arr[0]`、`obj[key]` 的结果自动包含 `undefined`，防止越界/缺键误判。
- `types: ["miniprogram-api-typings"]` 引入微信 API 的类型声明，让 `wx.request` 等带类型与智能提示。
- 小程序运行只认 JS，TS 由工具/编译流程转成 JS；类型信息在运行时不存在，不能用“interface”做运行时校验（表单校验仍需手写或用库）。

误区：为了让报错消失随手 `as any`，等于关掉类型保护；`strict` 只在本地开、CI 没跑 typecheck；混淆“类型断言”与“运行时转换”。

### 5. ESLint 静态检查

ESLint 负责发现**潜在缺陷与不规范写法**：未定义变量、未处理 Promise、重复声明、不可达代码、不当的比较等。使用 typescript-eslint 解析 TS。

```javascript
// .eslintrc.cjs
module.exports = {
  root: true,
  env: {
    es2020: true,
    node: true
  },
  parser: '@typescript-eslint/parser',
  parserOptions: {
    ecmaVersion: 2020,
    sourceType: 'module'
  },
  plugins: ['@typescript-eslint'],
  extends: [
    'eslint:recommended',
    'plugin:@typescript-eslint/recommended'
  ],
  globals: {
    wx: 'readonly',
    App: 'readonly',
    Page: 'readonly',
    Component: 'readonly',
    getApp: 'readonly',
    getCurrentPages: 'readonly',
    __wxConfig: 'readonly'
  },
  rules: {
    'no-console': ['warn', { allow: ['warn', 'error'] }],
    'prefer-const': 'error',
    'no-var': 'error',
    eqeqeq: ['error', 'always'],
    '@typescript-eslint/no-explicit-any': 'warn',
    '@typescript-eslint/no-unused-vars': ['error', { argsIgnorePattern: '^_' }]
  },
  ignorePatterns: ['node_modules/', 'miniprogram_npm/', 'dist/']
}
```

工程要点：

- 把 `wx`、`App`、`Page`、`Component` 等小程序全局声明为 `globals`，否则 ESLint 报“未定义”。
- 规则分级：`error` 会让 CI 失败（真正的问题），`warn` 只提示（风格或待改进项）。
- 不要把 ESLint 当“类型检查器”：它不做完整类型推断，类型问题交给 `tsc`。
- 可加入 `no-debugger`、`no-undef`、`no-unsafe-*` 等规则防止调试代码上线。

误区：规则全开但团队不维护，满屏报错只能 `--no-verify` 绕过；把格式化问题也写成 ESLint error，与 Prettier 职责重叠。

### 6. Prettier 与 ESLint 协作

Prettier 只关心**代码长什么样**：缩进、引号、分号、换行、行宽，不关心逻辑对错。二者分工应清晰：Prettier 管格式，ESLint 管质量。

```json
// .prettierrc.json
{
  "printWidth": 100,
  "singleQuote": true,
  "semi": false,
  "trailingComma": "none",
  "tabWidth": 2,
  "endOfLine": "lf",
  "arrowParens": "always"
}
```

二者都能影响引号、分号等格式时会“打架”。标准解法是让 ESLint 关闭与 Prettier 冲突的格式规则（较新版本通过关闭风格规则 + 单独跑 prettier，或使用 `eslint-config-prettier` 禁用冲突项）：

```javascript
// .eslintrc.cjs 的 extends 末尾追加，确保放最后以覆盖前面的风格规则
module.exports = {
  extends: [
    'eslint:recommended',
    'plugin:@typescript-eslint/recommended',
    'prettier'
  ]
}
```

常用脚本：

```json
{
  "scripts": {
    "format": "prettier --write .",
    "format:check": "prettier --check .",
    "lint": "eslint . --ext .ts,.js",
    "typecheck": "tsc --noEmit"
  }
}
```

误区：把 Prettier 规则写进 ESLint 导致两边互相修正、无限 diff；CI 只 lint 不检查格式，合入后格式化工具一改就是一整片无关 diff。

### 7. 提交规范与 pre-commit 钩子

即使有 CI，也应在**提交时**做快速反馈：只格式化和检查本次改动的文件，避免把问题推到 CI 才发现、再往返修改。使用 husky 管理 Git 钩子，lint-staged 只处理暂存区文件。

初始化（一次性）：

```bash
npm install -D husky lint-staged
npx husky install
npx husky add .husky/pre-commit "npx lint-staged"
```

```json
// package.json
{
  "scripts": {
    "prepare": "husky install"
  },
  "lint-staged": {
    "*.{ts,js}": ["prettier --write", "eslint --fix"],
    "*.{json,wxss,wxml,md}": ["prettier --write"]
  }
}
```

提交信息可约定 Conventional Commits，便于自动生成版本描述与变更日志：

```text
<type>(<scope>): <subject>

type 例如：feat 新功能 / fix 修复 / perf 性能 / refactor 重构
           docs 文档 / ci 流水线 / chore 杂项 / style 格式
示例：feat(shops): 店铺列表支持按距离排序
```

要点：钩子只做“快检查”，几秒内完成；CI 仍做全量 typecheck/lint，因为钩子可被 `--no-verify` 跳过、且 PR 可能来自没有钩子的环境。误区：在钩子里跑全量测试导致提交卡顿，大家改用 `--no-verify`；把强制门禁只放在本地钩子上。

### 8. 接入 Vant Weapp / TDesign Miniprogram 组件库

成熟的小程序组件库以“微信自定义组件集合”的形式发布到 npm，接入流程比普通 JS 库多“构建 npm + usingComponents 引用”两步。以 Vant Weapp 为例（TDesign 流程类似）：

```bash
npm install @vant/weapp --save
```

随后在开发者工具执行“构建 npm”，生成 `miniprogram_npm/@vant/weapp`。在页面或全局 JSON 中声明使用：

```json
// app.json（全局可用）或某页面 .json
{
  "usingComponents": {
    "van-button": "@vant/weapp/button/index",
    "van-cell": "@vant/weapp/cell/index",
    "van-card": "@vant/weapp/card/index"
  }
}
```

WXML 中直接使用，事件与属性按组件文档：

```xml
<van-card
  title="{{ shop.name }}"
  desc="{{ shop.address }}"
  thumb="{{ shop.coverUrl }}"
>
  <view slot="footer">
    <van-button size="small" type="primary" bind:click="onViewDetail">查看</van-button>
  </view>
</van-card>
```

工程注意：

- 组件库属于运行时依赖，放在 `dependencies`；升级后必须重新构建 npm。
- 只引用需要的组件路径即可，配合 U26 的包体积治理，避免全量引入撑大主包。
- 组件样式、主题定制遵循库的规范（如样式变量、外部样式类），不要强改 `miniprogram_npm` 内文件——下次构建会被覆盖。
- 选型关注对 Skyline 的兼容、维护活跃度与设计规范一致性。

误区：装完包不构建 npm 直接用，页面报组件未找到；直接修改 miniprogram_npm 里的源码；一个项目混用多套风格不一的组件库。

### 9. 接入小程序插件（plugin）

小程序**插件**是微信平台提供的一种能力分发形态：由第三方开发、经平台审核，宿主小程序声明后可直接使用其页面、组件与接口。它与 npm 组件库有本质区别：

| 对比项 | npm 组件库 | 小程序插件 |
|---|---|---|
| 分发方式 | npm 包，经构建 npm 进入工程 | 平台插件，按 AppID 引用 |
| 是否随包打包 | 是，占本小程序体积 | 否，由平台托管 |
| 使用前置 | 安装 + 构建 | app.json 声明 + 部分需向插件方申请授权 |
| 典型内容 | 基础 UI 组件 | 较完整服务（如地图服务、行业能力、直播等） |

在 `app.json` 声明插件：

```json
{
  "plugins": {
    "myPlugin": {
      "version": "1.2.0",
      "provider": "wxXXXXXXXXXXXXXX"
    }
  }
}
```

使用插件提供的组件（在页面 JSON 的 usingComponents 中以 `plugin://` 协议引用）：

```json
{
  "usingComponents": {
    "hello-comp": "plugin://myPlugin/hello-component"
  }
}
```

调用插件接口：

```typescript
// 具体命名空间与方法以插件文档为准
const plugin = requirePlugin('myPlugin')
plugin.doSomething({ foo: 1 })
```

误区：把插件当 npm 包去 `npm install`；忽略“部分插件需申请、需等待审核通过”的前置；插件版本不固定，升级未回归导致行为变化。

### 10. miniprogram-ci 原理与准备：上传密钥

miniprogram-ci 是微信官方提供的**命令行/Node SDK**，能在没有开发者工具图形界面的环境（如 CI runner）里完成代码预览与上传。它解决的正是“自动化”最后一公里：CI 是无头环境，不可能手动打开工具点按钮。

准备工作：

1. 在微信公众平台 → 开发管理 → 开发设置中，生成并下载**小程序代码上传密钥**（一个私钥文件）。
2. 按需配置 IP 白名单（若开启，只有白名单内 IP 能使用该密钥上传；CI 出口 IP 不固定时通常关闭白名单，改用“私钥保密 + 最小权限”）。
3. 记录小程序 AppID。
4. 在 CI 平台把私钥内容存入 Secrets（如 GitHub Actions 的 secret），由流水线在运行时写入临时文件。

关键安全事实：

- 上传私钥等同于“可以替该小程序上传代码”的凭证，**必须视为机密**：不提交进仓库、不打印到日志、不放在构建产物里；任务结束即删除临时文件。
- 它不是小程序业务里的 JWT，也不是 `AppSecret`；三者用途完全不同，不要混用。
- 私钥泄露应立即在公众平台重置（旧密钥作废）。

安装：

```bash
npm install -D miniprogram-ci
```

误区：把 `private.wx.key` 直接提交到项目根目录；把私钥内容 echo 到 CI 日志；用个人微信扫码上传“凑合作废”，导致版本归属无法追溯。

### 11. miniprogram-ci 的 preview 与 upload

`preview` 生成一个预览包与二维码，用于真机扫码验证当前代码；`upload` 上传一个“开发版本”到微信后台，可设为体验版或用于提交审核。

封装一个发布脚本，参数化动作、版本号与描述：

```typescript
// scripts/ci-miniprogram.ts
import ci from 'miniprogram-ci'
import { readFileSync, existsSync } from 'fs'

async function main() {
  const action = process.env.MP_ACTION // 'preview' | 'upload'
  const appid = process.env.WX_APPID!
  const keyPath = process.env.MP_PRIVATE_KEY_PATH!
  const version = process.env.MP_VERSION || '0.0.0'
  const desc = process.env.MP_DESC || 'CI build'

  if (!existsSync(keyPath)) {
    throw new Error('missing upload private key')
  }

  const project = new ci.Project({
    appid,
    type: 'miniProgram',
    projectPath: process.cwd(),
    privateKeyPath: keyPath,
    ignores: ['node_modules/**/*', 'scripts/**/*', '**/*.md']
  })

  if (action === 'preview') {
    const result = await ci.preview({
      project,
      desc,
      setting: {
        es6: true,
        minify: true,
        autoPrefixWXSS: true
      },
      qrcodeFormat: 'image',
      qrcodeOutputDest: 'preview-qrcode.png',
      // 自定义编译条件，可指定进入页面与启动参数
      customCompile: {
        pathName: 'pages/index/index',
        query: 'from=ci'
      },
      robot: 1,
      threads: 4
    })
    console.log('preview done', result.subPackageInfo)
  } else if (action === 'upload') {
    const result = await ci.upload({
      project,
      version,
      desc,
      setting: {
        es6: true,
        minify: true,
        autoPrefixWXSS: true
      },
      robot: 1
    })
    console.log('upload done', result.subPackageInfo)
  } else {
    throw new Error(`unknown action: ${action}`)
  }
}

main().catch((err) => {
  console.error(err)
  process.exit(1)
})
```

要点：

- `robot` 为机器人编号，CI 用固定机器人上传，便于在后台区分“人工包”与“流水线包”。
- `setting` 与开发者工具上传选项对应（ES6 转 ES5、压缩等）；要保证 CI 与本地工具设置一致，避免“两个地方编出不同结果”。
- `ign`ores 控制不参与上传的文件；`projectPath` 指向小程序工程目录。
- 上传版本号需符合微信规则；同名同版本重复上传会被拒绝或覆盖语义需注意。

误区：在 CI 里没有先“构建 npm”就上传，导致 miniprogram_npm 缺失；CI 的压缩/ES6 设置与工具不一致；预览二维码生成了但没有作为产物保存，过期后无法追溯。

### 12. CI Secrets：私钥注入与“绝不入库”

在 GitHub Actions 中，机密统一存放在仓库 Settings → Secrets and variables → Actions。流水线通过环境变量引用，GitHub 自动在日志中掩码。

常见需要的 Secrets：

| Secret 名称 | 内容 | 用途 |
|---|---|---|
| `WX_APPID` | 小程序 AppID（也可公开，但统一走变量） | 初始化 Project |
| `MP_PRIVATE_KEY` | 代码上传私钥文本 | 运行时写入临时文件 |
| `WX_API_SECRET` 等 | U29 服务端密钥（如后端流水线需要） | 服务端部署，不进小程序 |

在 workflow 中把私钥文本落到临时文件再调用脚本：

```yaml
- name: Restore upload key
  env:
    MP_PRIVATE_KEY: ${{ secrets.MP_PRIVATE_KEY }}
  run: |
    printf '%s' "$MP_PRIVATE_KEY" > "$RUNNER_TEMP/mp.key"
    chmod 600 "$RUNNER_TEMP/mp.key"
    echo "MP_PRIVATE_KEY_PATH=$RUNNER_TEMP/mp.key" >> "$GITHUB_ENV"
```

安全要点：

- 使用 `printf '%s'` 而非 `echo`，避免私钥尾部换行被改动；文件权限收紧为 600。
- 绝不把私钥内容 `cat` 出来、不放进可被外部访问的构建产物；预览二维码是“小程序包二维码”，不是私钥，可以作为产物上传。
- Fork PR 默认拿不到 Secrets，这是保护机制；预览通常只对受信任分支/PR 开启。
- `.gitignore` 中加入 `*.key`、`private.*`、`.env`，从源头防误提交。

误区：把私钥 base64 后“以为安全”仍提交入库（base64 不是加密）；在日志里调试打印环境变量；长期密钥不轮换。

### 13. GitHub Actions 流水线

下面是一条完整 workflow：在 push/PR 时安装依赖、类型检查、Lint、格式检查、构建 npm 产物并生成预览；在发布标签（如 `v1.3.0`）时执行 upload。

```yaml
# .github/workflows/miniprogram.yml
name: miniprogram-ci

on:
  push:
    branches: [main]
    tags: ['v*']
  pull_request:
    branches: [main]

jobs:
  verify:
    name: typecheck / lint / build
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Type check
        run: npm run typecheck

      - name: Lint
        run: npm run lint

      - name: Format check
        run: npm run format:check

      - name: Build npm for miniprogram
        run: npm run build:npm

      - name: Upload build artifact
        uses: actions/upload-artifact@v4
        with:
          name: miniprogram-npm
          path: miniprogram_npm
          retention-days: 7

  preview:
    name: preview qrcode
    needs: verify
    if: github.event_name == 'pull_request' || github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run build:npm
      - name: Restore upload key
        env:
          MP_PRIVATE_KEY: ${{ secrets.MP_PRIVATE_KEY }}
        run: |
          printf '%s' "$MP_PRIVATE_KEY" > "$RUNNER_TEMP/mp.key"
          chmod 600 "$RUNNER_TEMP/mp.key"
          echo "MP_PRIVATE_KEY_PATH=$RUNNER_TEMP/mp.key" >> "$GITHUB_ENV"
      - name: Generate preview
        env:
          WX_APPID: ${{ secrets.WX_APPID }}
          MP_ACTION: preview
          MP_DESC: "preview ${{ github.event.pull_request.head.sha || github.sha }}"
        run: npm run ci:mp
      - name: Upload qrcode
        uses: actions/upload-artifact@v4
        with:
          name: preview-qrcode
          path: preview-qrcode.png
          retention-days: 7

  release:
    name: upload release
    needs: verify
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run build:npm
      - name: Restore upload key
        env:
          MP_PRIVATE_KEY: ${{ secrets.MP_PRIVATE_KEY }}
        run: |
          printf '%s' "$MP_PRIVATE_KEY" > "$RUNNER_TEMP/mp.key"
          chmod 600 "$RUNNER_TEMP/mp.key"
          echo "MP_PRIVATE_KEY_PATH=$RUNNER_TEMP/mp.key" >> "$GITHUB_ENV"
      - name: Upload to WeChat
        env:
          WX_APPID: ${{ secrets.WX_APPID }}
          MP_ACTION: upload
          MP_VERSION: ${{ github.ref_name }}
          MP_DESC: "release ${{ github.ref_name }}"
        run: npm run ci:mp
```

设计要点：

- 质量门禁（verify）先行，preview/release 都 `needs: verify`，检查不过不产出包。
- 用 `npm ci` 而非 `npm install`：严格按 lock 文件安装，干净、快速、可复现。
- 预览只在受信分支/PR 跑（Fork PR 没有 Secrets，天然受限）。
- 发布由打标签触发，把“版本号”交给 Git Tag，避免人工填错。

### 14. 版本号与描述规范

采用语义化版本（SemVer）：`主版本.次版本.修订号`，即 `MAJOR.MINOR.PATCH`。

- `PATCH`（1.2.1）：向后兼容的缺陷修复；
- `MINOR`（1.3.0）：向后兼容的新功能；
- `MAJOR`（2.0.0）：不兼容的重大变更。

小程序微信后台的版本与 Git Tag 应一一对应。版本描述用于让测试、审核与运营看懂这次发了什么，建议结合提交记录自动生成：

```text
版本：v1.4.0
描述：
  feat(shops)：新增按距离排序
  fix(review)：修复评价图片偶现不显示
  perf(index)：首页进入耗时降低约 20%
构建信息：commit 9f3c2a1 / 分支 main / 机器人 CI-1
```

package.json 中同步维护 `version`，便于脚本读取与产物对照：

```json
{
  "name": "guangchi-miniprogram",
  "version": "1.4.0",
  "private": true
}
```

注意微信小程序版本号格式规则与“开发版本/体验版/审核版/线上版”的概念区分：`upload` 得到的是开发版本，需在后台再设为体验版或提交审核，CI 通常只负责上传，审核与发布动作受平台流程约束。误区：版本号随意写（如 `latest`）；描述只写“更新了一些东西”，无法追溯；Git Tag、package.json、上传版本三处不一致。

### 15. 干净环境可复现：锁文件、缓存与排错

“在我电脑上是好的”是工程化要消灭的核心问题。可复现性靠以下机制保证：

- **锁文件**：提交 `package-lock.json`，CI 用 `npm ci` 安装完全一致的依赖树；本地 Node 版本用 `.nvmrc` 或 `engines` 约定。
- **不提交产物与密钥**：`miniprogram_npm`、`dist`、`*.key`、`.env` 均加入 `.gitignore`，全部由流程生成。
- **显式步骤**：流水线从零开始，先 checkout 空仓库再逐步构建，任何“依赖本机已安装的全局工具”的步骤都会暴露。
- **合理缓存**：缓存 npm 全局缓存目录以提速，但缓存只影响速度、不影响结果；缓存损坏时应能回退到全新安装。
- **矩阵验证（可选）**：在多个 Node 版本或操作系统上跑检查，提前发现跨平台问题（换行符、路径大小写）。

```text
# .gitignore 节选
node_modules/
miniprogram_npm/
dist/
*.key
.env
preview-qrcode.png
```

```bash
# 本地模拟“干净环境”自检
rm -rf node_modules miniprogram_npm
npm ci
npm run typecheck && npm run lint && npm run build:npm
```

常见 CI 故障与定位：CI 通过但工具报错（多为本地没重新构建 npm / Node 版本不一致）；`npm ci` 失败（lock 与 package.json 不同步，需本地更新并提交 lock）；大小写问题在 Linux runner 暴露（macOS/Windows 文件系统默认大小写不敏感）；Secrets 在 Fork PR 缺失导致预览步骤被跳过（预期行为）。

### 任务描述

1. 建立工程基座：`package.json` + lock 文件、严格 `tsconfig.json`、ESLint、Prettier、husky/lint-staged，质量脚本齐全且可在干净环境执行。
2. 接入至少一个 npm 组件库（Vant/TDesign）与一个小程序插件，至少一个页面真实使用，并完成“构建 npm”在 CI 中的自动化。
3. 配置 miniprogram-ci：在公众平台生成代码上传密钥，把 AppID 与私钥存入 GitHub Secrets；编写支持 preview/upload 的脚本。
4. 编写 GitHub Actions workflow，至少包含：`npm ci` → typecheck → lint → format check → 构建 npm；在 PR/main 上产出预览二维码并作为构件保存；在 `v*` 标签上执行 upload。
5. 制定并落地版本号与描述规范（SemVer + 规范化描述 + commit 信息），完成一次从提交到预览（以及一次标签上传或完整 dry-run）的端到端演示。
6. 提交一份可复现性与安全说明：如何在新机器复现、缓存策略、Secrets 清单（只列名称）、私钥轮换与泄露应急流程。

### 完成标准

- 质量门禁真实生效：故意引入类型/lint 错误时 CI 变红、不产生预览包，修复后变绿；
- 预览二维码由流水线自动生成并可下载扫码，上传包带规范版本号、描述与固定机器人号；
- 全新 runner / 新机器按文档步骤可无差别复现构建，不依赖任何本机隐式状态；
- 仓库、历史提交、CI 日志、构建产物中均无私钥或业务密钥；
- 完成一次端到端录屏（提交 → 检查 → 预览 → 标签上传或 dry-run）。

### 强制不通过条件

- 代码上传私钥、`AppSecret` 或任何业务密钥出现在仓库、提交历史、CI 日志或构建产物中；
- 没有真实质量门禁（CI 永远绿灯或允许 `--no-verify` 绕过），或故意引入错误时 CI 不能变红；
- 流水线缺少 typecheck/lint/构建 npm 的关键环节，或在未构建 npm 的情况下执行 preview/upload；
- 预览二维码/上传无法在干净环境复现，强依赖某台机器的手工状态或全局工具；
- 版本号不符合 SemVer、描述无法追溯，或 Git Tag / package.json / 上传版本三处不一致；
- Fork/分支权限与 Secrets 使用存在明显泄露风险且未处理；
- 无法现场解释“构建 npm”原理、miniprogram-ci 鉴权方式或流水线各阶段的作用。
