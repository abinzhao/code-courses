# 08-事件系统与交互反馈

## 目标

完成本知识单元后，学员应能让已经还原好的界面“点得动、有回应、不出错”：理解双线程下事件从渲染层到逻辑层的完整旅程，正确处理冒泡、捕获与传参，并为每一个关键操作提供符合微信规范的交互反馈，而不是只写一个裸 `bindtap` 然后对异常沉默。

学员应能够：

1. 描述一次触摸操作的完整链路：渲染层采集 → 事件消息跨线程到逻辑层 → 执行处理函数 → `setData` 异步回流，理解逻辑层没有 DOM 事件监听器。
2. 使用 `bind` 绑定事件、`catch` 阻断冒泡、`mut-bind` 处理互斥绑定，说清三者的区别与适用场景。
3. 说清事件冒泡的路径与实际影响，用 `capture-bind / capture-catch` 处理捕获阶段需求。
4. 读懂事件对象：`type / timeStamp / detail / target / currentTarget / mark / touches / changedTouches`，准确区分 `target` 与 `currentTarget`。
5. 使用 `data-*` dataset 在 WXML 上挂载参数并在处理函数中取用，能识别“取到的都是字符串”等类型陷阱。
6. 使用 `mark` 在冒泡路径上携带结构化参数，区分 mark 与 dataset 的合并规则。
7. 正确使用触摸事件（touchstart/move/end/cancel）与高频业务事件（tap/longpress/input/confirm/scroll）。
8. 用 `wx.showToast / showLoading / showModal / showActionSheet` 为操作结果、异步过程、危险操作、多分支选择提供规范反馈，并正确配对 `hideLoading`。
9. 用 `wx.vibrateShort / vibrateLong` 提供触觉反馈，用 button 的 `loading / disabled / hover-class` 表达按钮状态。
10. 实现防重复点击与下拉刷新（`onPullDownRefresh + wx.stopPullDownRefresh`），为「逛吃指南」的发布、领券、列表项、二次确认等真实交互建立完整反馈闭环。

本单元只覆盖视图层事件与交互反馈；自定义组件的事件（triggerEvent）在 U09，手势与 Worklet 动画在 Skyline 单元 U28。

## 技术栈

使用微信原生框架 + TypeScript，不引入第三方组件库。

| 技术或 API | 用途 | 学习要求 |
|---|---|---|
| `bind:tap` / `catch:tap` | 事件绑定与阻断 | 能选择正确的绑定方式 |
| `capture-bind` / `capture-catch` | 捕获阶段绑定 | 理解与冒泡阶段的顺序 |
| `mut-bind` | 互斥绑定 | 知道其“只执行一个”的语义 |
| 事件对象 `event` | 事件上下文 | 会取 target/currentTarget/detail/dataset/mark |
| `data-*` | dataset 传参 | 会写会取，知道类型转换 |
| `mark:*` | 标记数据 | 会沿冒泡路径取合并值 |
| 触摸事件 | 触点跟踪 | 会读 touches/changedTouches |
| `wx.showToast` | 轻提示 | 能选 icon、控制时长与遮罩 |
| `wx.showLoading/hideLoading` | 加载反馈 | 必须成对调用，异常分支也要关闭 |
| `wx.showModal` | 模态确认 | 会处理 confirm/cancel、editable |
| `wx.showActionSheet` | 多选择菜单 | 会取 tapIndex、处理取消 |
| `wx.vibrateShort/Long` | 触觉反馈 | 会选择震动强度 |
| button 状态属性 | 按钮三态 | 会用 loading/disabled/hover-class |
| `onPullDownRefresh` | 下拉刷新 | 会配 JSON、会 stop、异常分支兜底 |

约定：

- 事件处理函数统一命名为 `onXxx`（如 `onPublish`、`onNoteTap`），与生命周期函数区分。
- 所有异步操作都必须给出反馈；失败分支不得静默。
- 逻辑层不存在 `window/document`，事件是小程序响应用户操作的唯一正道，不要出现 `addEventListener` 之类写法。

## 详细的理论知识讲解和示例伪代码

### 1. 事件是什么：双线程下的一次点击旅程

事件是“渲染层上发生的事情”被通知给逻辑层的机制。回顾 U02 的双线程模型：用户手指在渲染层的节点上触摸、抬起，渲染层把“发生了什么、在哪个节点、附带什么数据”序列化成消息，经 Native 桥接送到逻辑层，逻辑层找到对应的处理函数执行；若处理函数调用了 `setData`，数据再异步回流渲染层更新界面。

```text
手指点击“发布笔记”按钮
  → 渲染层识别 tap、计算节点路径与 dataset
  → 事件消息跨线程（序列化）
  → 逻辑层执行 onPublish
  → wx.showLoading / 请求云函数或后端
  → setData / wx.hideLoading / wx.showToast（异步回流渲染层）
```

两个必须建立的认知：

- 绑定写在 WXML 上，函数写在 `Page`（或 `Component`）里。节点上没有浏览器式的 DOM 事件系统，逻辑层拿不到“事件对象之外”的任何节点状态。
- `setData` 是跨线程异步的：调用后界面不会“立刻”改变，不要在 `setData` 下一行假设渲染已完成。

最小示例：

```xml
<view class="entry" bindtap="onEntryTap">
  <text>点击进入探店笔记</text>
</view>
```

```typescript
Page({
  onEntryTap() {
    wx.navigateTo({ url: '/pages/detail/detail?id=1001' })
  }
})
```

`bindtap` 与 `bind:tap` 两种写法等价，课程统一使用带冒号的 `bind:tap`。

**常见误区**：

- 在 TS 里写 `element.addEventListener('click', ...)`：逻辑层没有 DOM，也没有元素可拿。
- 以为事件回调里 `setData` 后马上读到新界面尺寸——跨线程通信需要时间。
- 把点击反馈只做在 `hover-class` 上：手指抬起后没有结果提示，用户不知道操作是否成功。

### 2. bind、catch 与 mut-bind

三种基础绑定方式：

| 写法 | 语义 | 典型场景 |
|---|---|---|
| `bind:tap="onXxx"` | 绑定，事件继续向上冒泡 | 绝大多数点击 |
| `catch:tap="onXxx"` | 绑定并**阻止继续冒泡** | 内层卡片点击不希望触发外层 |
| `mut-bind:tap="onXxx"` | 互斥绑定：同一事件若存在多个 mut-bind，只执行其中一个 | 组件/mixin 都可能绑同一事件时避免重复执行 |

一个卡片里有两个可点区域，内层按钮不希望触发整卡跳转：

```xml
<view class="note-card" bind:tap="onCardTap" data-id="{{item.id}}">
  <image class="note-card__img" src="{{item.cover}}" mode="aspectFill" />
  <view class="note-card__body">
    <text class="note-card__title">{{item.title}}</text>
    <view class="note-card__actions">
      <view class="action" catch:tap="onLikeTap" data-id="{{item.id}}">
        <text>{{item.liked ? '已赞' : '点赞'}}</text>
      </view>
      <view class="action" catch:tap="onCollectTap" data-id="{{item.id}}">
        <text>收藏</text>
      </view>
    </view>
  </view>
</view>
```

```typescript
Page({
  onCardTap(event) {
    const id = event.currentTarget.dataset.id
    wx.navigateTo({ url: `/pages/detail/detail?id=${id}` })
  },
  onLikeTap(event) {
    const id = Number(event.currentTarget.dataset.id)
    // catch 已阻断冒泡：这里执行后不会再触发 onCardTap
    console.log('点赞：', id)
  },
  onCollectTap(event) {
    console.log('收藏：', Number(event.currentTarget.dataset.id))
  }
})
```

`mut-bind` 的语义细节：若同一节点（或同一调度路径）上用 `mut-bind` 绑了多个处理函数，框架保证只调用其中一个，常用于“基础组件和业务扩展都可能绑 tap，但绝不能重复跳转/重复提交”的场景。普通业务代码用得少，但读第三方组件源码时要能看懂。

**常见误区**：

- 所有点击都用 `catch`，导致外层永远收不到事件，嵌套层级稍复杂就难以排查。
- 以为 `catch` 能阻止兄弟节点或其他类型事件：它只阻断当前事件继续传播。
- 在同一个节点上既 `bind:tap` 又 `catch:tap`，语义混乱；一个节点同一事件只需一种绑定。

### 3. 事件冒泡

冒泡指事件从**触发节点开始，沿节点树向上层祖先依次传递**，途经节点上绑定的同类事件处理函数会依次执行，直到根节点或被 `catch` 截断。

```xml
<view class="page" bind:tap="onPageTap">
  <view class="section" bind:tap="onSectionTap">
    <view class="box" bind:tap="onBoxTap">
      <text>点我</text>
    </view>
  </view>
</view>
```

点击“点我”时，执行顺序为：

```text
onBoxTap → onSectionTap → onPageTap
```

若把中间层改为 `catch:tap="onSectionTap"`，则 `onPageTap` 不再执行。

冒泡是“事件委托”的基础：长列表不必给每个节点分别绑定，可利用父节点统一处理（小程序中更常见的还是 wx:for 内直接绑，dataset 携带 id；事件委托在极大列表时可减少绑定描述）。

在「逛吃指南」里，冒泡最典型的用途与陷阱都在卡片：整卡可点进详情，卡内点赞/收藏按钮必须用 `catch`，否则“点赞一次还跳转了页面”。

**常见误区**：

- 内层用 `bind` 绑按钮又抱怨“一点赞就跳详情”——应改用 `catch`。
- 误以为列表项之间会互相冒泡：兄弟节点不在同一条祖先链上，不传播。
- 在祖先的处理函数里不判断来源就执行逻辑，被子节点冒泡“误触发”。

### 4. 捕获阶段：capture-bind 与 capture-catch

一次完整的事件传播分为两个阶段：

```text
捕获阶段：从页面根节点向下，直到目标节点
冒泡阶段：从目标节点向上，回到页面根节点
```

默认 `bind/catch` 监听的是冒泡阶段。需要在事件到达目标**之前**拦截时，用捕获绑定：

| 写法 | 语义 |
|---|---|
| `capture-bind:tap="onXxx"` | 捕获阶段执行，事件继续向下 |
| `capture-catch:tap="onXxx"` | 捕获阶段执行并**中断传播**，后续捕获与冒泡都不再进行 |

```xml
<view class="page" capture-bind:tap="onPageCapture" bind:tap="onPageBubble">
  <view class="box" capture-bind:tap="onBoxCapture" bind:tap="onBoxBubble">
    <text>点我</text>
  </view>
</view>
```

点击文字后的执行顺序：

```text
onPageCapture → onBoxCapture → onBoxBubble → onPageBubble
```

外层若改成 `capture-catch:tap`，则在最外层捕获处即被截断，连目标节点的点击都不会执行。

业务中捕获阶段用得不多，典型场景：做埋务/手势面板时希望“在外层优先感知、必要时拦截子节点操作”，例如一个可滑动面板想在特定区域吞掉点击。

**常见误区**：

- 认为 `bind` 监听捕获、`catch` 监听冒泡：二者默认都是冒泡阶段，捕获必须显式写 `capture-` 前缀。
- 在捕获处理函数里误以为能“修改事件结果”：捕获只能提前响应或中断，不能改变 target。
- 无拦截需求却使用 `capture-catch`，导致子节点按钮全部失灵且很难定位。

### 5. 事件对象与 target、currentTarget

处理函数收到的事件对象按事件类型分为三类：基础事件（`BaseEvent`）、自定义事件（`CustomEvent`，多一个 `detail`）、触摸事件（`TouchEvent`，多 `touches` 等）。

常用字段：

| 字段 | 含义 |
|---|---|
| `type` | 事件名，如 `tap`、`input` |
| `timeStamp` | 事件生成时距页面打开的毫秒数 |
| `target` | **最初触发**事件的节点（id、dataset） |
| `currentTarget` | **当前绑定处理函数**的节点（id、dataset） |
| `detail` | 组件自定义数据，如 input 的 value、scroll 的位置 |
| `mark` | 冒泡路径上合并的 mark 数据（第 6 节） |
| `touches` | 当前停留在屏幕上的触点数组 |
| `changedTouches` | 引发本次事件的触点数组 |

`target` 与 `currentTarget` 的区别在“点到子节点、函数绑在父节点”时立刻显现：

```xml
<view id="card" class="card" bind:tap="onTap" data-id="1001">
  <text id="title" class="title">巷子里的面馆</text>
</view>
```

```typescript
Page({
  onTap(event) {
    console.log(event.target.id)          // 点到文字时：'title'
    console.log(event.currentTarget.id)   // 始终：'card'
    console.log(event.currentTarget.dataset.id) // 始终：'1001'
  }
})
```

实践结论：**取绑定时就确定的参数，用 `currentTarget.dataset`**；只有需要知道“具体点中了内部哪个子元素”时才看 `target`。

组件事件的 `detail` 各组件不同，例如：

- `input`：`detail.value`（输入值）、`detail.cursor`（光标位置）。
- `scroll-view` 的 `scroll`：`detail.scrollTop / scrollLeft`。
- `swiper` 的 `change`：`detail.current / detail.source`。

**常见误区**：

- 在父节点处理函数里用 `target.dataset` 取 id，点到内部没有 data-id 的子节点时取到 `undefined`。
- 想当然地给事件对象加字段跨处理函数传值：事件对象是一次性的，数据应放 `data`。
- 忽略 TypeScript 类型：可用 `WechatMiniprogram.TouchEvent` 等内置类型标注参数，避免读错字段。

### 6. dataset 与 mark 传参

#### 6.1 dataset：WXML 到逻辑层的常规挂载点

在节点上写 `data-*`，处理函数通过 `currentTarget.dataset` 读取。命名规则：连字符写法会转成小驼峰。

```xml
<view
  class="note"
  bind:tap="onNoteTap"
  data-note-id="{{item.id}}"
  data-shop-name="{{item.shopName}}"
  data-is-hot="{{item.isHot}}"
>
  <text>{{item.shopName}}</text>
</view>
```

```typescript
Page({
  onNoteTap(event) {
    const { noteId, shopName, isHot } = event.currentTarget.dataset
    // data-note-id → noteId；data-shop-name → shopName
    console.log(noteId, shopName, isHot)
    wx.navigateTo({
      url: `/pages/detail/detail?id=${noteId}&name=${encodeURIComponent(shopName)}`
    })
  }
})
```

类型陷阱：写死在属性里的值（`data-id="1001"`）到达逻辑层是**字符串**，做数值比较前要 `Number()`；用 Mustache 绑定（`data-id="{{item.id}}"`）则保留原始数据类型。

列表中推荐的标准写法：

```xml
<view
  wx:for="{{notes}}"
  wx:key="id"
  class="note-item"
  bind:tap="onNoteTap"
  data-id="{{item.id}}"
>
  <text>{{item.shopName}}</text>
</view>
```

#### 6.2 mark：沿冒泡路径合并的结构化数据

`mark` 用 `mark:变量名="{{值}}"` 声明。事件触发时，**从触发节点到根节点路径上所有 mark 会被合并**进 `event.mark`，同名时以更靠近触发节点的为准。mark 支持绑定任意类型数据。

```xml
<view mark:page="noteList">
  <view
    wx:for="{{notes}}"
    wx:key="id"
    mark:noteid="{{item.id}}"
    bind:tap="onNoteTap"
  >
    <text mark:action="title">{{item.shopName}}</text>
  </view>
</view>
```

```typescript
Page({
  onNoteTap(event) {
    console.log(event.mark) // { page: 'noteList', noteid: 1001, action: 'title' }
  }
})
```

dataset 只携带 `target` 或 `currentTarget` 单个节点的属性；mark 天然带上整条路径的上下文，做埋点（来源页 + 模块 + 内容 id）时尤其方便。

**常见误区**：

- 把对象直接塞进 `data-extra="{{obj}}"` 后又期待它是字符串：绑定保留类型，但拼接 URL 前仍需自行序列化。
- 中文/特殊字符直接拼到 URL，不做 `encodeURIComponent`，目标页解析错乱。
- mark 变量名大小写写错：mark 键名**原样保留**（不做连字符转换），与 dataset 规则不同。

### 7. 触摸事件：touchstart、touchmove、touchend、touchcancel

需要跟踪手指滑动（下拉、抽屉、手势菜单）时使用四个触摸事件：

| 事件 | 触发时机 |
|---|---|
| `touchstart` | 手指接触屏幕 |
| `touchmove` | 手指在屏幕上移动（持续触发） |
| `touchend` | 手指抬起 |
| `touchcancel` | 触摸被系统打断（来电、手势被微信接管等） |

事件对象中的两组触点：

- `touches`：当前**仍在屏幕上**的触点（touchend 时为空数组）。
- `changedTouches`：引发**本次事件**的触点（touchend 时抬起的手指在这里）。

每个触点常用字段：`identifier`（多点触控时区分手指）、`clientX/clientY`（相对可视区）、`pageX/pageY`（相对页面，含滚动距离）。

一个“跟手横向滑动”的最小示例：

```xml
<view
  class="track"
  bind:touchstart="onTouchStart"
  bind:touchmove="onTouchMove"
  bind:touchend="onTouchEnd"
  bind:touchcancel="onTouchEnd"
>
  <view class="track__content" style="transform: translateX({{dx}}px);">
    <text>左右滑动查看门店相册</text>
  </view>
</view>
```

```typescript
Page({
  data: {
    startX: 0,
    dx: 0
  },
  onTouchStart(event) {
    this.setData({ startX: event.touches[0].clientX })
  },
  onTouchMove(event) {
    const currentX = event.touches[0].clientX
    this.setData({ dx: currentX - this.data.startX })
  },
  onTouchEnd() {
    // 抬手回弹，正式项目中复杂手势建议 Skyline Worklet（U28）
    this.setData({ dx: 0 })
  }
})
```

注意高频 `touchmove` 中频繁 `setData` 跨线程通信会掉帧；本课程主线只用它做简单联动，复杂手势后续在 Skyline 单元解决。

**常见误区**：

- 只监听 `touchend` 却从 `touches` 取坐标：手指已抬起，`touches` 为空，应读 `changedTouches[0]`。
- 不处理 `touchcancel`：来电中断后抽屉停在半截状态。
- 在 touchmove 里做重计算/大对象 setData，导致明显卡顿。

### 8. 高频业务事件

除了 tap 与触摸事件，日常开发最常用的一组：

| 事件 | 常用组件 | 关键数据 |
|---|---|---|
| `longpress` | view、list 项 | 长按约 350ms 触发；触发后不再触发 tap |
| `input` | input、textarea | `detail.value` |
| `confirm` | input | 键盘“完成/搜索”按下 |
| `focus / blur` | input | 聚焦/失焦 |
| `scroll` | scroll-view | `detail.scrollTop` |
| `scrolltolower / scrolltoupper` | scroll-view | 触底/触顶 |
| `change` | switch、swiper、picker | 各组件 detail 不同 |

列表项长按删除（替代容易误触的悬浮删除键）：

```xml
<view
  class="note-item"
  bind:tap="onNoteTap"
  bind:longpress="onLongPress"
  data-id="{{item.id}}"
>
  <text>{{item.shopName}}</text>
</view>
```

```typescript
Page({
  onLongPress(event) {
    const id = Number(event.currentTarget.dataset.id)
    wx.vibrateShort({ type: 'medium' })
    wx.showActionSheet({
      itemList: ['不感兴趣', '删除笔记'],
      success: (res) => {
        if (res.tapIndex === 1) {
          this.confirmDelete(id)
        }
      }
    })
  }
})
```

搜索框输入 + 键盘确认：

```xml
<input
  class="search-input"
  value="{{keyword}}"
  bind:input="onInput"
  bind:confirm="onSearch"
  confirm-type="search"
  placeholder="搜索门店、菜品"
/>
```

```typescript
Page({
  data: { keyword: '' },
  onInput(event) {
    this.setData({ keyword: event.detail.value })
  },
  onSearch() {
    this.fetchNotes(this.data.keyword)
  }
})
```

**常见误区**：

- 使用已废弃的 `longtap`：应使用 `longpress`（longpress 触发后自动抑制 tap，语义更干净）。
- 在 `bindinput` 里不回写 `value` 受控，处理极端输入（如表情、IME 组词）时光标容易跳。
- scroll-view 的触底距离忘记通过 `lower-threshold` 配置，分页加载时机不符预期。

### 9. wx.showToast：轻提示

`wx.showToast` 用于“短、轻、不需要用户做选择”的结果反馈：领取成功、已复制、网络异常等。

```typescript
wx.showToast({
  title: '已领取',
  icon: 'success', // success / error / loading / none
  duration: 1500,
  mask: false
})

wx.showToast({
  title: '网络异常，请稍后重试',
  icon: 'none' // 长文案/无语义图标时用 none
})
```

要点：

- `success` 图标自带“对勾”语义，只用于成功；失败用 `error` 或 `none`。
- 标题文案不宜长，建议 7 个汉字以内，超长会被截断；复杂解释改用 modal。
- 连续调用多个 toast 会互相顶掉（同一提示层），不要用 toast 排队播报多条信息。
- 需要自定义图标可用 `image` 指定图片，但优先考虑语义化内置 icon。

**常见误区**：

- 用 `icon: 'success'` 提示“请先登录”这类非成功信息，语义错误。
- 失败完全静默，只在控制台打印；用户视角就是“按钮点了没反应”。
- 用 toast 提示需要用户决策的内容（如“是否删除”）——应使用 modal。

### 10. wx.showLoading 与 wx.hideLoading

耗时操作（网络请求、云函数调用、上传图片）期间用 loading 阻止用户误以为“没反应”：

```typescript
async onClaim(couponId: number) {
  wx.showLoading({
    title: '领取中',
    mask: true // mask 阻止穿透点击，避免在 loading 下继续操作
  })
  try {
    await this.claimCoupon(couponId)
    wx.hideLoading()
    wx.showToast({ title: '领取成功', icon: 'success' })
  } catch (err) {
    wx.hideLoading()
    wx.showToast({ title: '领取失败，请重试', icon: 'none' })
  }
}
```

硬性规则：

- `showLoading` 与 `hideLoading` 必须成对；**失败/异常分支也要 hide**，统一放 `try/finally` 最稳妥。
- loading 与 toast 共用一个提示层：`hideLoading` 之后再 showToast，避免后者被立刻冲掉。
- loading 只适合秒级到十几秒的等待；超长任务应配合进度条（如上传用 `wx.uploadFile` 的进度回调）。

```typescript
async onClaim(couponId: number) {
  wx.showLoading({ title: '领取中', mask: true })
  try {
    await this.claimCoupon(couponId)
    wx.showToast({ title: '领取成功', icon: 'success' })
  } finally {
    wx.hideLoading()
  }
}
```

**常见误区**：

- 只在成功分支 hideLoading，请求抛错后 loading 永久转圈，只能杀小程序。
- loading 不加 mask，用户在等待期间连续点击，发出多笔相同请求。
- 把 loading 当 toast 用，结束后不提供成功/失败结果提示。

### 11. wx.showModal：模态确认

需要用户明确决策、尤其是**破坏性或不可逆操作**（删除笔记、放弃编辑、退出发布）时，用 modal 二次确认：

```typescript
confirmDelete(noteId: number) {
  wx.showModal({
    title: '删除笔记',
    content: '删除后不可恢复，确定删除这篇探店笔记吗？',
    confirmText: '删除',
    confirmColor: '#e54d42',
    cancelText: '再想想',
    success: (res) => {
      if (res.confirm) {
        this.deleteNote(noteId)
      }
      // res.cancel 时什么都不做，这正是二次确认的意义
    }
  })
}
```

`editable: true` 时弹窗带输入框，用户输入经 `res.content` 返回，可用于“输入活动口令”等轻量录入：

```typescript
wx.showModal({
  title: '加入探店团',
  editable: true,
  placeholderText: '请输入团长提供的口令',
  success: (res) => {
    if (res.confirm && res.content) {
      this.joinGroup(res.content.trim())
    }
  }
})
```

要点：确认按钮文案应表达动作（“删除/退出”），而不是笼统的“确定”；危险操作用红色 `confirmColor`。

**常见误区**：

- 删除、解绑等操作不做确认，误触后无法挽回。
- 任何小操作都弹 modal，用户被频繁打断；低风险反馈用 toast。
- 在 `success` 外直接读取 `res.confirm`：回调外拿不到用户选择。

### 12. wx.showActionSheet：多分支操作菜单

当一个入口有多个并列操作（分享到朋友圈/好友、保存图片、举报），用底部操作菜单：

```typescript
onMoreTap() {
  wx.showActionSheet({
    itemList: ['分享给好友', '保存海报', '不感兴趣', '举报'],
    itemColor: '#1f2329',
    success: (res) => {
      switch (res.tapIndex) {
        case 0:
          this.shareNote()
          break
        case 1:
          this.savePoster()
          break
        case 2:
          this.markDislike()
          break
        case 3:
          this.report()
          break
      }
    },
    fail: (err) => {
      if (err.errMsg.includes('cancel')) return // 用户取消属正常路径
      console.warn('操作菜单异常', err)
    }
  })
}
```

规则与细节：

- `itemList` 最多 6 项，超出请重新设计信息架构。
- 用户选择后通过 `res.tapIndex` 区分；取消会走 `fail`，取消不是错误，应静默处理。
- 菜单适合“同一对象的多个操作”；是/否类二元决策仍用 modal。

**常见误区**：

- 把“取消”当异常上报，产生无意义错误日志。
- 在 actionSheet 里放“删除”却不做二次确认：菜单项是一次性选择，破坏性动作应再弹 modal。
- 操作项过多依赖系统“更多”，不如按使用频率收敛。

### 13. 震动反馈与 button 三态

#### 13.1 触觉反馈

`wx.vibrateShort`（短促，15~ms 级）配合点赞、长按、操作成功等轻反馈；`wx.vibrateLong`（约 400ms）用于强烈提醒。

```typescript
wx.vibrateShort({ type: 'light' }) // heavy / medium / light / rigid / soft
wx.vibrateLong()
```

震动无需授权，不支持的设备/开发者工具上会静默失败；应作为“增强”而非“唯一”反馈——必须与视觉反馈一起出现。

#### 13.2 button 的 loading、disabled、hover-class

```xml
<button
  class="publish-btn {{formValid ? '' : 'publish-btn--disabled'}}"
  loading="{{submitting}}"
  disabled="{{!formValid || submitting}}"
  hover-class="publish-btn--hover"
  hover-stay-time="80"
  bind:tap="onPublish"
>
 发布笔记
</button>
```

```css
.publish-btn {
  background: #ff5a3c;
  color: #fff;
  border-radius: 44rpx;
  font-size: 30rpx;
}
.publish-btn--hover {
  background: #e84e31;
}
.publish-btn--disabled {
  background: #ffc2b5;
  color: #fff;
}
```

三个状态各自承担不同信息：

- `loading`：提交进行中，按钮内转圈。
- `disabled`：条件不满足（表单没填完）时不可点，且应有视觉变浅。
- `hover-class`：按下瞬间的反馈；设为 `none` 可取消默认按压态。

**常见误区**：

- 表单未填完时按钮看起来完全正常，点击后才 toast 报错；应直接 disabled 并做视觉区分。
- 震动当主要反馈，静音的设备/不支持时用户毫无感知。
- loading 只做在按钮上，请求却从别处也可能触发，状态不同步；提交锁应是唯一数据源（第 14 节）。

### 14. 防重复点击

弱网下用户对“没反应”的本能反应是再点一次，于是两笔订单、两篇重复笔记。防重分两层：

第一层，按钮状态：请求期间 `disabled + loading`（第 13 节）。

第二层，逻辑锁：处理函数入口先判断，处理结束（无论成败）再释放。锁比按钮更可靠，因为入口可能来自手势、键盘 confirm 等非按钮路径。

```typescript
Page({
  data: {
    submitting: false
  },

  async onPublish() {
    if (this.data.submitting) return // 互斥：进行中的请求未结束
    if (!this.validateForm()) {
      wx.showToast({ title: '请完善门店和图片', icon: 'none' })
      return
    }

    this.setData({ submitting: true })
    wx.showLoading({ title: '发布中', mask: true })
    try {
      const noteId = await this.publishNote()
      wx.showToast({ title: '发布成功', icon: 'success' })
      setTimeout(() => {
        wx.redirectTo({ url: `/pages/detail/detail?id=${noteId}` })
      }, 800)
    } catch (err) {
      wx.showToast({ title: '发布失败，请重试', icon: 'none' })
    } finally {
      wx.hideLoading()
      this.setData({ submitting: false })
    }
  }
})
```

非异步的快速点击（如疯狂点点赞、连续切换 Tab）可用时间节流：

```typescript
function throttle<T extends (...args: any[]) => void>(fn: T, wait = 500) {
  let last = 0
  return function (this: unknown, ...args: Parameters<T>) {
    const now = Date.now()
    if (now - last < wait) return
    last = now
    fn.apply(this, args)
  }
}
```

支付场景补充安全红线：`wx.requestPayment` 所需的预支付参数必须由**云函数或自有服务器**生成，签名密钥只能保存在服务端，**密钥不放前端**；前端只负责发起支付与反馈结果。

**常见误区**：

- 只禁用按钮不加逻辑锁，键盘 confirm/代码复用路径仍能重复触发。
- 请求失败后忘记释放锁，按钮永久转圈不可再点。
- 用全局变量 `window.xxx` 做锁：逻辑层没有 `window`，锁应放 `data` 或页面实例字段。

### 15. 下拉刷新与反馈规范

#### 15.1 下拉刷新

页面 JSON（或 `app.json` 的 window）开启：

```json
{
  "enablePullDownRefresh": true,
  "backgroundTextStyle": "dark",
  "backgroundColor": "#f6f7f9"
}
```

逻辑层实现 `onPullDownRefresh`，数据回来后必须调用 `wx.stopPullDownRefresh` 收起刷新动画，失败分支同样要收起：

```typescript
Page({
  async onPullDownRefresh() {
    try {
      await this.refreshNotes()
      wx.showToast({ title: '已更新', icon: 'success' })
    } catch (err) {
      wx.showToast({ title: '刷新失败', icon: 'none' })
    } finally {
      wx.stopPullDownRefresh()
    }
  },

  async refreshNotes() {
    const notes = await fetchLatestNotes()
    this.setData({ notes })
  }
})
```

也可用 `wx.startPullDownRefresh()` 代码触发同样的动画（如进入页面自动刷新）。注意 scroll-view 内部滚动的页面，系统下拉与容器滚动可能冲突，那种结构用 scroll-view 的 `refresher-enabled` 自定义下拉，后续组件单元再讲。

#### 15.2 交互反馈选择规范

```text
操作成功且无需决策        → showToast(success)
操作失败/弱提示           → showToast(none/error)
正在等待（请求、上传）      → showLoading(mask) + 按钮 loading
破坏性/不可逆操作          → showModal 二次确认
同一对象多个并列操作       → showActionSheet
点赞/长按等需要增强确认     → vibrateShort（叠加视觉反馈）
列表数据更新              → 下拉刷新或局部 setData + toast
```

通用原则：

- 任何异步操作都有“进行中 / 成功 / 失败”三态，失败绝不沉默。
- 反馈文案说结果与下一步，不说技术黑话（避免“code: -1 / errno 40001”直接给用户）。
- 反馈层级克制：同屏同时只应有一个遮罩类反馈，避免 loading 上叠 modal 上又 toast。
- 触觉反馈只在关键节点使用，避免每个点击都震动造成骚扰。

**常见误区**：

- 刷新成功但忘记 `stopPullDownRefresh`，刷新动画一直转。
- 用 toast 表示“进行中”：toast 会自动消失，长请求中途用户失去等待提示，应用 loading。
- 所有错误统一“网络异常”文案，实际是权限/参数问题，用户无法自救。

为「逛吃指南」补齐核心交互闭环：

1. 首页笔记列表：点卡片进详情；卡内点赞、收藏独立响应且不触发跳转；下拉可刷新列表。
2. 发布页：带校验、按钮三态、防重复点击的发布流程，成功后离开表单页，失败可重试。
3. “我的笔记”：长按操作菜单（含删除），删除前二次确认，删除结果有明确反馈。
4. 所有异步操作具备“加载 / 成功 / 失败”三态反馈；关键节点提供适度触觉反馈。

### 完成标准

- 能现场画出任意一次点击的事件传播路径，并解释 bind/catch、捕获/冒泡的选择理由；
- dataset/mark 取参正确，弱网连点不会产生重复数据；
- 破坏性操作必须二次确认，任何失败分支对用户可见；
- 下拉刷新动画正常收起，列表状态前后一致；
- 代码中无 `window/document/addEventListener` 等不存在的 DOM 调用，无前端密钥。

### 评分要点（100 分）

| 维度 | 分值 | 要点 |
|---|---:|---|
| 事件机制理解 | 20 | 绑定方式、冒泡/捕获、target 区分准确 |
| 参数传递 | 15 | dataset 类型处理正确、mark 使用合理 |
| 反馈完整性 | 25 | 加载/成功/失败三态齐全，API 选择规范 |
| 防重复与安全 | 20 | 逻辑锁可靠、成功后路由正确、无前端密钥 |
| 下拉刷新 | 10 | 配置正确、异常分支也能收起 |
| 代码质量 | 10 | 命名规范、无静默失败、无遮罩叠加 |

### 强制不通过条件

- 弱网连点能产生重复发布/重复领券，或失败后按钮永久不可用；
- 删除等破坏性操作无二次确认，或任一失败分支静默无反馈；
- 下拉刷新动画无法收起、列表状态错乱；
- 代码中出现 `window/document` 等 DOM/BOM 调用，或在前端写入任何密钥；
- 无法说清卡片上“点赞不跳转”的事件传播原理。
