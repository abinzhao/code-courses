# 14-云函数与后端逻辑

## 目标

完成本知识单元后，学员应能把“后端逻辑跑在哪、用户身份从哪来、为什么云函数里的数据库操作是管理员身份”讲清楚，并把 U13 中前端直写的发布笔记、点赞等写操作全部收敛到云函数，用真实的越权测试证明系统安全闭环，而不是以为“前端校验过了就等于安全”。

学员应能够：

1. 说清云函数的运行模型：运行在云端 Node.js 环境、无状态、按需拉起与回收，存在冷启动，因此业务状态必须落数据库而不能放内存。
2. 在项目中创建云函数（`cloudfunctions` 目录、入口文件、`package.json`），完成本地调试、上传部署与版本更新。
3. 使用 `wx.cloud.callFunction` 在小程序端调用云函数，处理 `result` 与 `fail`，并为调用建立统一的返回结构。
4. 说清 `event` 与 `context` 的含义与常用字段，知道函数超时、剩余执行时间等运行时信息的来源。
5. 使用 `cloud.getWXContext()` 在云函数中获取可信的 `OPENID`（以及 APPID、UNIONID），明确“openid 只能从平台上下文取，禁止由前端传入”。
6. 理解云函数中的 `cloud.database()` 以**管理员身份**操作数据库，可绕过安全规则执行批量操作，并据此收紧集合权限。
7. 把“发布笔记”收敛为云函数：字段白名单、参数校验、服务端时间、跨集合更新用户计数，必要时使用事务保证一致。
8. 把“点赞/取消点赞”收敛为云函数：用确定性记录与事务实现幂等、防重复点赞与计数准确。
9. 掌握云函数间调用（`cloud.callFunction`）、依赖安装（`wx-server-sdk` 与第三方包）、定时触发器（`config.json` 中的 cron）、云端日志与错误处理。
10. 完成开发/生产环境区分与密钥治理：密钥与管理员操作只存在于云函数，小程序端零密钥；并交付越权被拒的验证证据。

本单元是 U13 的安全闭环：数据库负责存储与“门卫”规则，云函数负责“裁判”业务逻辑。

## 详细的理论知识讲解和示例伪代码

### 1. 云函数是什么：Node 运行时、无状态与冷启动

云函数是一段运行在云端、由平台托管的 Node.js 代码。小程序端不需要知道服务器地址，只要按“函数名”调用，平台负责拉起执行环境、运行代码、返回结果。

三个关键性质：

1. **无状态**：每次调用不应假设上一次调用留在内存里的变量还在。平台可能在任意时刻回收实例；计数、标志位等必须写进数据库。
2. **按需运行**：没有请求时不占服务器；请求到来时才执行，按调用次数与运行资源计费。
3. **冷启动**：长时间没有调用或首次发布后，平台需要新建实例、加载代码与依赖，首次调用会稍慢；热实例复用时则较快。因此云函数要轻量，依赖要精简。

典型调用链：

```text
小程序逻辑层
  └─ wx.cloud.callFunction({ name, data })
        └─ 微信云平台：鉴权 → 拉起/复用实例 → 注入用户上下文
              └─ exports.main(event, context) 执行
                    └─ 返回 result 给小程序
```

「逛吃指南」里应放进云函数的动作：发布/删除笔记、点赞、评论、每日热门榜单、任何需要密钥或开放接口的操作。

常见误区：

- 在云函数全局变量里存“当前调用计数”并期待它累加——实例回收后归零，且并发实例之间不共享。
- 认为云函数“一直运行”——它只在被调用或被触发器触发时运行，不能常驻内存。

### 2. 创建第一个云函数：目录结构与入口

#### 2.1 项目配置

在 `project.config.json` 中确认云函数根目录（使用云开发模板时通常已配置）：

```json
{
  "cloudfunctionRoot": "cloudfunctions/"
}
```

开发者工具中该目录会出现特殊图标。每个云函数是其中的一个子目录，例如：

```text
cloudfunctions/
  └─ sum/
      ├─ index.js
      └─ package.json
```

#### 2.2 最小函数（JavaScript）

```javascript
// cloudfunctions/sum/index.js
const cloud = require('wx-server-sdk')

cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })

exports.main = async (event, context) => {
  const { a, b } = event
  if (typeof a !== 'number' || typeof b !== 'number') {
    return { code: 1001, msg: '参数必须是数字' }
  }
  return {
    code: 0,
    data: { sum: a + b },
    msg: 'ok',
    requestId: context.requestId,
  }
}
```

```json
{
  "name": "sum",
  "version": "1.0.0",
  "main": "index.js",
  "dependencies": {
    "wx-server-sdk": "~3.0.0"
  }
}
```

#### 2.3 TypeScript 版本（课程主线）

使用支持 TS 的云函数模板时，目录中会包含 `index.ts` 与 `tsconfig.json`，部署前由工具链编译：

```typescript
// cloudfunctions/sum/index.ts
import * as cloud from 'wx-server-sdk'

cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })

interface SumEvent {
  a: number
  b: number
}

interface SumResult {
  code: number
  data?: { sum: number }
  msg: string
}

export const main = async (event: SumEvent): Promise<SumResult> => {
  if (typeof event.a !== 'number' || typeof event.b !== 'number') {
    return { code: 1001, msg: '参数必须是数字' }
  }
  return { code: 0, data: { sum: event.a + event.b }, msg: 'ok' }
}
```

注意：`exports.main` 是平台约定入口，名字不能随意改；函数返回的对象会作为小程序端拿到的 `result`。

### 3. 部署、版本与本地调试

#### 3.1 部署方式

在开发者工具中右键云函数目录：

- **上传并部署：云端安装依赖**（推荐）：只传源码，`npm install` 在云端执行，避免本地上传大量 `node_modules` 且与云端环境更兼容。
- **上传并部署：所有文件**：连同本地 `node_modules` 一起上传，仅在云端安装失败等特殊情况使用。
- **上传触发器**：只更新 `config.json` 等配置而不改代码。

每次修改云函数代码后必须重新上传部署，调用的才是新版本；本地调试与云端版本是两套，排错时先确认“线上到底跑的是哪版”。

#### 3.2 本地调试

- 右键函数选择“本地调试”，工具会在本机拉起模拟器，可在面板中直接构造 event 调用、打断点、看返回。
- 本地调试同样能取到模拟用户上下文，可在调试面板中切换 openid 做身份测试。

#### 3.3 函数配置

在控制台可以配置超时时间、内存规格、环境变量等。耗时任务（如批量处理）要适当调大超时，但根本上应让函数短小快速；具体可配范围以控制台为准。

常见误区：改完代码没重新部署就抱怨“怎么不生效”；把几百 MB 的 `node_modules` 全量上传导致部署极慢。

### 4. 小程序端调用：wx.cloud.callFunction

```typescript
async function callSum(a: number, b: number) {
  try {
    const res = await wx.cloud.callFunction({
      name: 'sum',          // 云函数名（目录名）
      data: { a, b },       // 作为 event 传入
    })
    const result = res.result as { code: number; data?: { sum: number }; msg: string }
    if (result.code === 0) {
      console.log('结果：', result.data!.sum)
    } else {
      wx.showToast({ title: result.msg, icon: 'none' })
    }
  } catch (err) {
    // 网络失败、函数不存在、函数执行超时/抛错未捕获等
    console.error('调用云函数失败', err)
    wx.showToast({ title: '网络异常，请重试', icon: 'none' })
  }
}
```

调用要点：

- `data` 里的字段会被展开进云函数的 `event`；不要传函数、DOM 对象等不可序列化内容。
- 云函数 `return` 的内容就是 `res.result`。
- 云函数内部未捕获的异常会让调用进入 catch/fail；因此函数应自己兜住业务异常，返回统一结构。

建议建立统一的调用封装与返回类型：

```typescript
// services/cloud.ts
interface CloudResult<T> {
  code: number
  data?: T
  msg: string
}

export async function call<T>(name: string, data = {}): Promise<T> {
  const res = await wx.cloud.callFunction({ name, data })
  const result = res.result as CloudResult<T>
  if (result.code !== 0 || result.data === undefined) {
    throw new Error(result.msg || '云函数返回异常')
  }
  return result.data
}
```

### 5. event 与 context：输入和运行时上下文

- **event**：本次调用的输入。小程序端传的 `data` 字段、触发器携带的信息都在这里。
- **context**：本次调用的运行时信息，如 `requestId`（用于在日志中定位单次请求）、函数名/版本、剩余可执行时间等。

```javascript
exports.main = async (event, context) => {
  console.log('入参 event：', event)
  console.log('请求 id：', context.requestId)
  console.log('剩余毫秒：', typeof context.getRemainingTimeInMillis === 'function'
    ? context.getRemainingTimeInMillis()
    : 'n/a')
  return { code: 0, event, msg: 'ok' }
}
```

定时触发器调用时，`event` 中会带有触发器名称等字段（如 `TriggerName`），可据此区分“这次是被定时任务唤醒的”还是被小程序直接调用的。

工程建议：把 `requestId` 带进关键日志，出现问题时能在云端日志里完整还原一次请求。

常见误区：把整个 `context` 存数据库或返回给前端（没必要且可能含内部信息）；不校验 event 直接使用导致 `undefined` 报错。

### 6. 在云函数中获取可信 openid：getWXContext

用户身份不能由前端“自报”，必须由平台在调用时注入：

```typescript
import * as cloud from 'wx-server-sdk'

cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })

export const main = async (event: any) => {
  const wxContext = cloud.getWXContext()
  return {
    code: 0,
    data: {
      openid: wxContext.OPENID,   // 当前用户在本小程序下的唯一标识
      appid: wxContext.APPID,
      unionid: wxContext.UNIONID, // 绑定开放平台时才有
    },
    msg: 'ok',
  }
}
```

铁律：

- **openid 只能从 `getWXContext()` 取**。如果允许前端在 data 里传 openid / userId，任何人都能传别人的 id 冒充身份。
- 数据归属判断一律以云端取到的 OPENID 为准，例如更新/删除时检查文档的 `_openid === OPENID`。
- UNIONID 只在小程序绑定了微信开放平台账号、用户满足条件时才存在，不要假设它一定有值。

对比 U13：小程序端 `add` 时系统自动写入 `_openid`；云函数 `add` 不会自动写，需要显式 `data: { _openid: OPENID, ... }`。

常见误区：在小程序端拿本地缓存的 openid 传给云函数做鉴权；用昵称/头像当用户唯一标识（可重复、可更改）。

### 7. 管理员身份操作数据库：cloud.database

在云函数中获取的数据库连接默认拥有**管理员权限**：

```typescript
const db = cloud.database()

// 可以更新/删除任意文档，不受小程序端安全规则限制
await db.collection('notes').doc(noteId).update({
  data: { likeCount: db.command.inc(1) },
})

// 管理员端批量删除：删除某笔记的全部评论
await db.collection('comments').where({ noteId }).remove()
```

两端身份对比：

| 操作端 | 身份 | 受安全规则约束 | 单次条数上限 |
|---|---|---|---|
| 小程序端 | 普通用户 | 是 | 较低（如 get 默认 20） |
| 云函数端 | 管理员 | 否（规则不拦截） | 更高 |

正因为云函数“权力很大”，必须做到：

1. **入口先鉴权**：每个操作都确认调用者身份（OPENID）与操作对象归属。
2. **字段白名单**：只取允许的字段写入，忽略前端多传的任何字段（如 `likeCount`、`status`）。
3. **收紧集合权限**：写操作既然都走云函数，集合的小程序写权限就可以设为 false，形成“即使有人绕过前端直写也写不进”的纵深防御。

常见误区：以为“云函数是自己写的，不用再校验归属”——云函数的调用者仍然是任意用户，鉴权不能省。

### 8. 综合实战（上）：发布笔记收敛到云函数

#### 8.1 云函数 publishNote

```typescript
// cloudfunctions/publishNote/index.ts
import * as cloud from 'wx-server-sdk'

cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })

const db = cloud.database()
const _ = db.command

interface PublishEvent {
  title: string
  content: string
  images: string[]
  category: string
  tags: string[]
  shopName: string
  location?: { type: 'Point'; coordinates: [number, number] }
}

const ALLOWED_CATEGORIES = ['coffee', 'dessert', 'hotpot', 'fastfood', 'local']

export const main = async (event: PublishEvent) => {
  const { OPENID } = cloud.getWXContext()

  // 1. 参数校验
  const title = (event.title || '').trim()
  if (!title || title.length > 30) {
    return { code: 1001, msg: '标题需为 1-30 字' }
  }
  if (!event.content || event.content.length > 2000) {
    return { code: 1001, msg: '正文需为 1-2000 字' }
  }
  if (!Array.isArray(event.images) || event.images.length === 0 || event.images.length > 9) {
    return { code: 1001, msg: '图片需为 1-9 张' }
  }
  if (!ALLOWED_CATEGORIES.includes(event.category)) {
    return { code: 1001, msg: '分类不合法' }
  }

  // 2. 字段白名单：绝不能把 event 整体展开写入（防止刷 likeCount/status）
  const now = db.serverDate()
  const noteData = {
    _openid: OPENID,
    title,
    content: event.content,
    images: event.images,
    category: event.category,
    tags: Array.isArray(event.tags) ? event.tags.slice(0, 10) : [],
    shopName: (event.shopName || '').slice(0, 50),
    location: event.location,
    likeCount: 0,
    commentCount: 0,
    status: 'published',
    deleted: false,
    createdAt: now,
    updatedAt: now,
  }

  // 3. 跨集合一致性：写笔记 + 用户笔记数 +1，用事务
  try {
    const result = await db.runTransaction(async (transaction) => {
      const addRes = await transaction.collection('notes').add({ data: noteData })
      const noteId = addRes._id

      const userRef = transaction.collection('users').doc(OPENID)
      const userSnap = await userRef.get().catch(() => null)
      if (userSnap && userSnap.data) {
        await userRef.update({ data: { noteCount: _.inc(1) } })
      } else {
        // 用户资料不存在则建档（资料由登录流程补全）
        await transaction.collection('users').add({
          data: { _id: OPENID, _openid: OPENID, noteCount: 1, createdAt: now },
        })
      }
      return noteId
    })

    return { code: 0, data: { id: result }, msg: '发布成功' }
  } catch (err) {
    console.error('发布事务失败', OPENID, err)
    return { code: 1500, msg: '发布失败，请稍后重试' }
  }
}
```

#### 8.2 小程序端改为调用云函数

```typescript
// services/noteService.ts
import { call } from './cloud'

export function publishNote(input: PublishInput) {
  return call<{ id: string }>('publishNote', input)

```

页面调用：

```typescript
async function onPublish() {
  wx.showLoading({ title: '发布中' })
  try {
    const { id } = await publishNote(this.data.form)
    wx.showToast({ title: '发布成功' })
    wx.redirectTo({ url: `/pages/note-detail/index?id=${id}` })
  } catch (err) {
    wx.showToast({ title: (err as Error).message, icon: 'none' })
  } finally {
    wx.hideLoading()
  }
}
```

同步收紧权限：notes 集合的小程序端 `write` 设为 `false`（写全部走云函数），`read` 维持“已发布可读”。此时再从客户端直写，会被安全规则拒绝。

常见误区：用 `{ ...event }` 整体入库，让攻击者可注入 `status`、`likeCount`；笔记计数用两次独立写而不加事务，中途失败导致数据不一致。

### 9. 综合实战（中）：点赞收敛、幂等与防重复

点赞的难点：同一用户重复点、网络重试、并发计数。设计独立的 `note_likes` 集合，记录“谁赞了什么”，用**确定性 _id** 保证幂等。

实现策略分三步，再给出完整代码：

1. 用 `openid + noteId` 拼出确定性 `_id`，同一用户对同一笔记的点赞记录全局唯一。
2. 先查点赞记录是否存在：请求状态与现状一致时直接返回当前状态，天然幂等，连点和重试都不会重复计数。
3. 状态确实需要变化时，在事务中同时写 `note_likes` 记录与 `notes.likeCount` 计数，两者要么都成功要么都回滚。

```typescript
// cloudfunctions/toggleNoteLike/index.ts
import * as cloud from 'wx-server-sdk'

cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })

const db = cloud.database()
const _ = db.command

interface LikeEvent {
  noteId: string
  like: boolean // true 点赞，false 取消
}
```

完整入口函数：

```typescript
export const main = async (event: LikeEvent) => {
  const { OPENID } = cloud.getWXContext()
  const { noteId, like } = event
  if (typeof noteId !== 'string' || typeof like !== 'boolean') {
    return { code: 1001, msg: '参数不合法' }
  }

  const likeId = `${OPENID}_${noteId}`
  const likeRef = db.collection('note_likes').doc(likeId)

  try {
    const existing = await likeRef.get().catch(() => null)
    const hasLiked = !!(existing && existing.data)

    if (like === hasLiked) {
      return { code: 0, data: { liked: hasLiked, changed: false }, msg: 'ok' } // 幂等：重复操作直接返回当前状态
    }

    await db.runTransaction(async (transaction) => {
      const noteRef = transaction.collection('notes').doc(noteId)
      if (like) {
        await transaction.collection('note_likes').add({
          data: { _id: likeId, _openid: OPENID, noteId, createdAt: db.serverDate() },
        })
        await noteRef.update({ data: { likeCount: _.inc(1) } })
      } else {
        await transaction.collection('note_likes').doc(likeId).delete()
        await noteRef.update({ data: { likeCount: _.inc(-1) } })
      }
    })

    return { code: 0, data: { liked: like, changed: true }, msg: 'ok' }
  } catch (err) {
    console.error('点赞失败', OPENID, noteId, err)
    return { code: 1500, msg: '操作失败，请重试' }
  }
}
```

要点：

- 确定性 `_id` 让“重复点赞”要么已存在被幂等忽略，要么在事务中触发重复键错误，计数永远不会多加。
- 计数与点赞记录在同一事务里更新，避免“记录加了计数没加”。
- `note_likes` 集合权限设为“仅管理端可读写”；notes 的 `likeCount` 不再允许前端直改。
- 前端连点、超时重试都只会得到一致结果；可在云函数中再加简单频限（如同用户短时间内调用次数）防刷。

### 10. 云函数间调用：cloud.callFunction

在一个云函数中调用另一个云函数，用于复用逻辑或编排：

```typescript
const res = await cloud.callFunction({
  name: 'getUserRank',
  data: { openid: cloud.getWXContext().OPENID },
})
const result = res.result as { code: number; data: any }
```

适用场景：

- 多个函数共用“计算用户等级”“生成短链”等逻辑，抽成独立函数复用。
- 一个编排函数顺序调用多个子函数（如发布后触发内容检测、发通知）。

代价与边界：

- 函数间调用计入调用次数并增加链路耗时，超时风险叠加，不要无意义地层层嵌套。
- 被调用函数同样要做鉴权/参数校验；内部调用也不应信任传入参数。
- 只抽一段纯计算逻辑时，直接抽成普通模块文件 `require('./lib/rank')` 更省资源，不必为了复用而多一次函数调用。

### 11. 依赖管理：wx-server-sdk 与第三方包

- 每个云函数有独立的 `package.json` 与依赖，函数 A 装了包，函数 B 不能直接用。
- `wx-server-sdk` 是官方云端 SDK，提供 `database`、`getWXContext`、`callFunction`、`openapi` 等能力。
- 需要其他库（如时间处理、加解密、HTTP 请求）时，先 `npm install 包名 --save` 写入依赖，再部署时云端安装。

示例 `package.json`：

```json
{
  "name": "publishNote",
  "version": "1.0.0",
  "main": "index.js",
  "dependencies": {
    "wx-server-sdk": "~3.0.0",
    "dayjs": "^1.11.10"
  }
}
```

注意：

- 依赖越多、体积越大，冷启动越慢；只装真正需要的包，优先用 Node 内置能力。
- 需要联网调用第三方 HTTP 接口时确认云函数网络策略允许；涉及鉴权的密钥必须放在云端（环境变量/配置），不能写进能被下发的小程序代码。
- 锁定合理版本范围，避免云端安装到不兼容的大版本。

### 12. 定时触发器：config.json 与 cron

在云函数目录新增 `config.json` 声明触发器：

```json
{
  "permissions": {
    "openapi": []
  },
  "triggers": [
    {
      "name": "dailyHotRank",
      "type": "timer",
      "config": "0 0 2 * * * *"
    }
  ]
}
```

云开发定时触发器的 cron 为 **7 段**：`秒 分 时 日 月 星期 年`。

| 表达式 | 含义 |
|---|---|
| `0 0 2 * * * *` | 每天 02:00 |
| `0 */30 * * * * *` | 每 30 分钟 |
| `0 0 9 * * 1 *` | 每周一 09:00 |
| `0 0 0 1 * * 2026` | 2026 年每月 1 日 00:00 |

函数中识别触发来源：

```typescript
export const main = async (event: any) => {
  console.log('触发来源：', event.TriggerName)
  if (event.TriggerName === 'dailyHotRank') {
    await refreshHotRank()
  }
  return { code: 0, msg: 'done' }
}

async function refreshHotRank() {
  // 取近期高赞笔记，写入 rank 集合供首页读取（rank 集合前端只读）
}
```

部署触发器用“上传触发器”或重新部署函数；删除触发器要同步改配置重新上传，仅删本地文件不会让云端定时任务停止。

常见误区：按 Linux 5 段 cron 书写导致不生效；以为删除本地 `config.json` 云端就自动停止。

### 13. 日志与错误处理

#### 13.1 统一返回结构

约定全课程云函数统一返回：

```typescript
interface ApiResponse<T> {
  code: number      // 0 成功；1xxx 参数错误；1403 越权；1500 服务端错误
  data?: T
  msg: string
}
```

#### 13.2 函数内捕获并记录

```typescript
try {
  // 业务逻辑
} catch (err) {
  // 云端日志面板可检索；带上 openid 与关键业务 id 便于定位
  console.error('publishNote failed', { openid: cloud.getWXContext().OPENID, err })
  return { code: 1500, msg: '系统繁忙，请稍后再试' }
}
```

不要把内部错误堆栈直接返回给前端：给用户看友好提示，详细信息只进日志。

#### 13.3 调用端处理与重试

- 小程序端对网络抖动可以做有限次重试，但**重试只适用于幂等操作**；发布类重试要配合服务端幂等设计（如前端生成 requestId 或确定性业务键），否则可能产生重复数据。
- 在云端日志面板按 `requestId`、时间、函数名过滤，先确认请求是否到达、event 是什么、走到了哪一步，再谈修复。

常见误区：函数里不 catch，异常直接让调用进入 fail 且无日志上下文；对非幂等接口无脑自动重试造成重复发布。

### 14. 环境区分与密钥治理

#### 14.1 使用动态环境

```typescript
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
```

`DYNAMIC_CURRENT_ENV` 表示“函数部署在哪个环境，就用哪个环境的资源”，避免代码里写死环境 ID、dev 的函数误连 prod 数据库。需要跨环境访问时才显式指定 env。

#### 14.2 多环境流程

- dev 环境函数与数据仅供开发联调；prod 环境承载线上流量。
- 小程序端通过构建时配置（如不同分支/配置文件）切换调用的环境，发布前确认指向 prod。
- 集合结构变更先在 dev 验证，再同步 prod，避免直接动线上数据。

#### 14.3 密钥只存在于云端

- 第三方 API 的 key、证书、token 等只放在云函数的环境变量/云端配置中，需要时在函数内读取。
- 小程序代码包会被分发到用户设备，**写在前端的任何密钥都等于公开**；U13/U14 的原则就是“密钥与管理员操作收敛云函数”。
- 配置最小权限的 key（如只读、限 IP/限服务），并定期轮换。

### 15. 综合实战（下）：收紧规则、越权验证与上线检查

#### 15.1 权限收口后的目标配置

| 集合 | 小程序读 | 小程序写 | 云函数 |
|---|---|---|---|
| notes | 已发布可读 | false（仅云函数） | 读写、计数 |
| users | 本人可读 | false（仅云函数） | 读写 |
| comments | 所有人可读 | false（仅云函数） | 读写 |
| note_likes | 不开放 | false | 读写（幂等键） |
| rank | 所有人可读 | false | 定时刷新 |

#### 15.2 必做的越权测试清单

1. **直写被拒**：在小程序代码/调试器中直接 `db.collection('notes').add(...)`，应被安全规则拒绝。
2. **伪造身份无效**：调用 publishNote 时在 data 中塞入 `_openid: '别人的'`，入库记录的归属仍为真实调用者。
3. **注入字段被忽略**：发布时多传 `likeCount: 99999`、`status: 'published'`，结果中这些字段不被前端输入控制。
4. **改他人笔记被拒**：云函数中做更新/删除时校验 `doc._openid === OPENID`，传入他人笔记 id 返回越权错误码（如 1403）。
5. **重复点赞不多计数**：连点 10 次或重试，`likeCount` 最多 +1，`note_likes` 只有一条。
6. **取消他人点赞无意义但安全**：对没有点赞记录的取消操作保持幂等，计数不会变负。

参考的归属校验片段：

```typescript
async function assertOwner(noteId: string, openid: string) {
  const snap = await db.collection('notes').doc(noteId).get().catch(() => null)
  if (!snap || !snap.data) return { ok: false, code: 1004, msg: '笔记不存在' }
  if (snap.data._openid !== openid) return { ok: false, code: 1403, msg: '无权操作' }
  return { ok: true }
}
```

#### 15.3 上线前检查

- 全部写操作确为云函数，客户端零密钥；prod 环境的配额告警已设置。
- 关键函数有日志、有统一返回、有参数校验；超时与内存配置合理。
- 定时触发器时间正确（注意时区按平台规则，一般为北京时间），任务可重复执行不出错。
- 删除类操作优先软删除或带事务，防止误删。
