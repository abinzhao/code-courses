# 13-云开发与云数据库

## 目标

完成本知识单元后，学员应能把“数据存在云端的哪里、怎么查、谁能写、为什么不能让前端随便写”讲清楚，并为「逛吃指南」建立 notes / users / comments 三个集合，跑通真实的增删改查，而不是只会在控制台手动加数据、在页面里写死数组。

学员应能够：

1. 说清微信云开发（CloudBase）的能力地图：云数据库、云函数、云存储、云调用各自解决什么问题，以及与自建服务器方案的取舍。
2. 独立开通云环境，记住并使用环境 ID 在 `wx.cloud.init` 中完成初始化，理解开发环境与生产环境分离的意义。
3. 建立配额与计费意识：免费额度、套餐、按量计费分别覆盖哪些资源维度（存储容量、读写次数、云函数用量、CDN 流量等），知道具体数字以控制台与官方文档为准。
4. 说清文档型数据模型：集合（collection）、文档（document）、字段（field）与关系型表的对应关系，理解 `_id`、`_openid` 两个内置字段的含义。
5. 使用 `db.collection` 完成增（`add`）、查（`get`）、改（`update`）、删（`remove`），并能在 TypeScript 中为文档定义接口。
6. 掌握查询指令 `db.command`：`where`、`eq`、`in`、`gt` 等比较与逻辑指令，以及 `db.RegExp` 正则查询。
7. 使用 `db.Geo.Point` 与 `geoNear` 实现“附近的店”地理查询，说清为什么必须建地理位置索引。
8. 使用 `orderBy`、`skip`、`limit`、`field`、`count` 完成排序、分页与字段投影，理解深分页的代价。
9. 配置数据库权限：仅创建者可读写、所有人可读仅创建者可写、仅管理端、自定义安全规则，并写出最小权限的 JSON 规则。
10. 说清小程序端直写数据库的风险，确立“读可客户端直读、写操作（尤其涉及计数、跨集合、密钥与管理员操作）收敛到云函数”的原则，为 U14 做好设计铺垫。

本单元承接 U12 的本地数据层：本地存储负责离线与加速，云数据库成为业务真值的最终存放地；本单元的写操作会在 U14 全部收敛到云函数。

## 技术栈

本单元使用微信原生云开发能力与 TypeScript，不引入自建服务器。

| 工具或环境 | 用途 | 学习要求 |
|---|---|---|
| 微信开发者工具云开发面板 | 开通环境、建集合、配权限、建索引、看数据 | 能独立完成环境创建与配置 |
| wx.cloud.init | 初始化云能力 | 会传 env、traceUser，知道只初始化一次 |
| wx.cloud.database | 获取数据库实例 | 会在 app 与服务模块中使用 |
| db.collection().add/get/update/remove | 文档增删改查 | 掌握返回值与失败处理 |
| db.command（_ 指令） | 条件、逻辑与更新指令 | 会用 eq/in/gt/and/or/inc/push |
| db.RegExp | 正则检索 | 会写 options，知道全表扫描代价 |
| db.Geo / geoNear | 地理点与附近查询 | 知道经纬度顺序与索引要求 |
| orderBy/skip/limit/field/count | 排序分页与投影 | 会实现分页列表与计数 |
| 自定义安全规则 JSON | 集合级读写权限 | 会写最小权限表达式 |
| TypeScript | 文档类型与服务层 | 通过 tsc，不用 any 掩盖结构 |

学习约定：

- 配额、条数上限等具体数字以云开发控制台与官方文档当前说明为准；本单元只要求记牢“有上限、超限会失败”这一事实并做防御。
- 小程序端 `get` 单次默认最多返回 20 条记录，云函数（管理员端）默认上限更高；因此全量统计、批量操作本单元只做认知，实现在 U14。
- 逻辑层没有 DOM，所有数据要显示到界面，仍然通过 `setData` 跨线程传递，不要写 `document.querySelector`。

## 详细的理论知识讲解和示例伪代码

### 1. 云开发是什么：能力地图与适用边界

微信云开发是微信团队联合腾讯云提供的 **Serverless 一体化后端**。你不用购买、运维服务器，就能在小程序里直接使用数据库、文件存储和运行在云端的函数。它由以下几块组成：

| 能力 | 是什么 | 「逛吃指南」中的用途 |
|---|---|---|
| 云数据库 | 文档型数据库（类 MongoDB） | 笔记、用户、评论、门店、活动 |
| 云函数 | Node.js 云端函数 | 发布笔记、点赞、定时统计、敏感操作 |
| 云存储 | 文件存储与 CDN 分发 | 笔记图片、头像（U15 详讲） |
| 云调用 | 在云函数中免鉴权调用开放接口 | 订阅消息、内容安全检测 |
| 静态网站托管 | 托管 H5 等静态资源 | 活动落地页（后续课程） |

与传统自建后端对比：

| 维度 | 自建服务器 | 云开发 |
|---|---|---|
| 服务器运维 | 自己购买、部署、扩容 | 无需运维，按量弹性 |
| 登录鉴权 | 自己实现登录态 | 平台天然注入 openid |
| 数据库 | MySQL 等关系型，需自建 | 文档型，开箱即用 |
| 适合场景 | 复杂业务、已有技术栈 | 中小团队快速上线、小程序优先 |

要注意：Serverless 不是“没有后端”，而是“后端不用自己养服务器”。**业务规则、安全校验、数据一致性仍然是你要设计的后端逻辑**，只是这些逻辑写在云函数里（U14）。

常见误区：

- “用了云开发就不用学后端了”——错误。权限设计、幂等、原子更新、错误处理一样不少。
- “云数据库就是个云端的 Storage”——错误。它有查询指令、索引、权限模型，是真正的数据库。

### 2. 开通云环境：环境 ID、初始化与配额计费

#### 2.1 开通与创建环境

1. 在微信开发者工具顶部点击「云开发」按钮，按提示开通（需已登录并绑定小程序 AppId，测试号能力受限）。
2. 创建一个环境，得到唯一的**环境 ID**（形如 `gc-prod-6gxxxxxx`），注意环境 ID 与环境名称是两回事，代码里用的是 ID。
3. 一个小程序可以创建多个环境，建议至少建立：
   - `gc-dev-xxxx`：开发联调环境；
   - `gc-prod-xxxx`：正式环境。

#### 2.2 在代码中初始化

在 `app.ts` 的 `onLaunch` 中调用一次 `wx.cloud.init`：

```typescript
// app.ts
App({
  onLaunch() {
    if (!wx.cloud) {
      console.error('当前基础库不支持云开发，请升级基础库')
      return
    }
    wx.cloud.init({
      env: 'gc-dev-6g1234abcdef', // 环境 ID
      traceUser: true,             // 记录访问用户到控制台，便于运营观察
    })
  },
  globalData: {},
})
```

也可以给不同能力分别指定环境：

```typescript
wx.cloud.init({
  env: {
    database: 'gc-dev-6g1234abcdef',
    storage: 'gc-dev-6g1234abcdef',
    functions: 'gc-prod-6g999999', // 云函数指向另一环境
    default: 'gc-dev-6g1234abcdef',
  },
})
```

#### 2.3 配额与计费概念

云开发的成本由若干资源维度累加，学习阶段必须建立“每个动作都消耗资源”的意识：

- **数据库**：存储容量、读写次数、并发连接。
- **云函数**：调用次数、运行时长 × 内存（GB·s）、出网流量。
- **云存储/CDN**：存储空间、下载次数、CDN 回源流量。
- **云调用**：部分开放接口有次数限制。

计费与额度的三层结构（以官方当前说明为准）：

1. **免费额度/基础版**：新环境通常带一定免费额度，适合学习和低流量应用，但不是永久无限。
2. **套餐版**：按月付费，包含固定配额，适合稳定运营的小程序。
3. **按量付费**：超出套餐或未购套餐时按实际用量结算。

工程建议：

- 开发期统一使用 dev 环境，避免调试产生脏数据污染生产。
- 在控制台设置**用量告警与预算提醒**，避免被异常调用刷爆额度。
- 上线前评估：图片是否压缩、查询是否分页、轮询能否改为触发。

常见误区：

- “把环境名称填进 env”——错误，必须填环境 ID。
- “免费额度等于无限用”——错误，被刷或流量上涨后会产生费用或被限流。
- “每个页面都 init 一次更保险”——错误，应用启动时初始化一次即可。

### 3. 文档型数据模型：集合、文档与字段

云数据库是**文档型数据库**，数据组织三层结构：

- **集合 collection**：类似关系型数据库的“表”，如 `notes`。
- **文档 document**：集合中的一条记录，类似“一行”，是一个 JSON 对象。
- **字段 field**：文档中的键值对，类似“列”，但同一集合里不同文档可以有不同字段。

```json
{
  "_id": "note-001",
  "_openid": "oXXXXXXXXXXXXXXXX",
  "title": "巷子里的宝藏面馆",
  "tags": ["面食", "人均20", "老字号"],
  "shop": { "name": "老王面馆", "address": "xx路12号" },
  "likeCount": 128,
  "createdAt": "2026-10-01T10:00:00.000Z"
}
```

与关系型数据库对照：

| 关系型 | 文档型 |
|---|---|
| database | 环境（env） |
| table | collection |
| row | document |
| column | field（弱约束，可动态变化） |
| join | 嵌套对象/数组，或应用层多次查询 |

两个内置字段必须记牢：

- `_id`：文档唯一标识。新增时不传则系统自动生成；也可自己指定（如用业务编号）。
- `_openid`：**小程序端新增**时服务端自动注入当前用户的 openid，用于标识“这条数据是谁创建的”。注意：云函数中 `add` 不会自动注入，需手动写入（U14）。

支持的常见数据类型：字符串、数字、布尔、对象、数组、null、时间（建议 `db.serverDate()`）、地理位置点（`db.Geo.Point`）。

「逛吃指南」的数据关系（没有外键约束，靠字段关联）：

```text
users（用户）
  └─ notes（笔记：_openid 关联用户，location 关联门店位置）
        └─ comments（评论：noteId 关联笔记，_openid 关联评论者）
shops（门店：name/address/location 地理点）
activities（活动：shopId、startTime、endTime）
```

常见误区：

- 把所有内容塞进一个无限深嵌套大对象，导致每次更新都要重写整段，且无法按子项查询。
- 用一个无限增长的数组存“所有点赞用户”，导致文档膨胀；正确做法是用独立的 `likes` 集合（U14）。
- 期待数据库帮你做跨集合 join 和外键级联删除——文档库没有，需要在云函数里编排。

### 4. 获取数据库实例与读取一条数据

在逻辑层获取数据库实例：

```typescript
const db = wx.cloud.database() // 使用 init 时的默认环境
// 或指定环境：
const dbProd = wx.cloud.database({ env: 'gc-prod-6g999999' })
```

按 `_id` 读取单条文档：

```typescript
async function getNoteById(id: string): Promise<Note | null> {
  try {
    const res = await db.collection('notes').doc(id).get()
    return res.data as Note
  } catch (err) {
    // 文档不存在或无权限时会 reject
    console.warn('读取笔记失败', err)
    return null
  }
}
```

为文档定义 TypeScript 接口，让整个服务层有类型约束：

```typescript
// types/note.ts
interface Note {
  _id: string
  _openid: string
  title: string
  content: string
  images: string[]
  category: string
  tags: string[]
  shopName: string
  likeCount: number
  commentCount: number
  status: 'draft' | 'published'
  location?: DB.GeoPoint
  createdAt: Date
  updatedAt: Date
}
```

页面使用时仍然要经 `setData` 到渲染层：

```typescript
onLoad(query: Record<string, string>) {
  getNoteById(query.id).then((note) => {
    if (note) this.setData({ note })
  })
}
```

注意：`doc().get()` 在记录不存在时不是返回空对象，而是抛错/走 fail，必须用 try/catch 或 fail 回调处理。

### 5. 新增 add 与服务端时间

```typescript
interface CreateNoteInput {
  title: string
  content: string
  images: string[]
  category: string
  tags: string[]
  shopName: string
  location?: DB.GeoPoint
}

async function createNote(input: CreateNoteInput): Promise<string> {
  const res = await db.collection('notes').add({
    data: {
      ...input,
      likeCount: 0,
      commentCount: 0,
      status: 'published',
      createdAt: db.serverDate(), // 服务端时间，避免客户端时钟不准
      updatedAt: db.serverDate(),
    },
  })
  return res._id // 新文档 _id
}
```

要点：

- 成功返回 `{ _id }`，失败走 Promise reject。
- 小程序端新增时，服务端自动补 `_openid`；你不需要也不应该自己传 openid（前端传的 openid 不可信）。
- `db.serverDate()` 写入的是云端服务器时间，比 `new Date()` 更可靠。

在调用前做基本的前端校验（注意这只是体验层校验，不能替代服务端校验）：

```typescript
if (!input.title.trim()) {
  wx.showToast({ title: '标题不能为空', icon: 'none' })
  return
}
if (input.images.length === 0) {
  wx.showToast({ title: '至少上传一张图片', icon: 'none' })
  return
}
```

常见误区：

- 用客户端 `new Date()` 作为创建时间，用户改手机时间即可伪造。
- 以为在云函数里 `add` 也会自动带 `_openid`——云函数以管理员身份写入，需手动取 openid 写入（U14）。
- 在一个 `add` 里传函数或 `undefined`——文档只能存可序列化的 JSON 数据。

### 6. 条件查询 where 与查询指令 db.command

最简单的等值条件：

```typescript
const res = await db.collection('notes').where({
  category: 'coffee',
  status: 'published',
}).get()
console.log(res.data) // 小程序端单次最多 20 条
```

复杂条件要用查询指令，先拿到 `db.command`：

```typescript
const _ = db.command

// 分类在给定列表内，且点赞数大于 100
db.collection('notes').where({
  category: _.in(['coffee', 'dessert', 'hotpot']),
  likeCount: _.gt(100),
  status: _.eq('published'),
}).get()

// 逻辑或：标题含“面”或者分类为“快餐”
db.collection('notes').where(_.or([
  { title: db.RegExp({ regexp: '面' }) },
  { category: 'fastfood' },
])).get()

// 逻辑与：点赞 10~500 且必须有封面
db.collection('notes').where({
  likeCount: _.and(_.gte(10), _.lte(500)),
  images: _.exists(true),
}).get()
```

常用指令速查：

| 指令 | 含义 |
|---|---|
| `_.eq / _.neq` | 等于 / 不等于 |
| `_.gt / _.gte` | 大于 / 大于等于 |
| `_.lt / _.lte` | 小于 / 小于等于 |
| `_.in / _.nin` | 在列表中 / 不在列表中 |
| `_.and / _.or` | 逻辑与 / 逻辑或 |
| `_.exists(true)` | 字段是否存在 |

查询结果统一是 `{ data: 文档数组 }`，小程序端一次最多 20 条，需要更多数据要用 `skip` 分页或在云函数中取。

常见误区：

- 先 `get` 全量再用数组 `filter` 筛选——浪费流量与配额，应在 `where` 里筛。
- 在 `where` 里写 JavaScript 函数——条件必须用查询指令表达。
- 以为 `get` 会一次返回全部匹配记录——小程序端有单次条数上限。

### 7. 更新 update 与更新指令

按 `_id` 局部更新（只传需要改的字段）：

```typescript
async function updateNoteTitle(id: string, title: string) {
  const res = await db.collection('notes').doc(id).update({
    data: {
      title,
      updatedAt: db.serverDate(),
    },
  })
  console.log(res.stats.updated) // 受影响条数，通常为 0 或 1
}
```

更新指令提供原子操作：

```typescript
const _ = db.command

// 点赞数 +1（原子自增，不是读出再加回）
await db.collection('notes').doc(id).update({
  data: { likeCount: _.inc(1) },
})

// 标签数组追加 / 移除
await db.collection('notes').doc(id).update({
  data: { tags: _.push('深夜食堂') },
})
await db.collection('notes').doc(id).update({
  data: { tags: _.pull('深夜食堂') },
})

// 整体替换某个对象字段（不用 set 时是按 key 合并）
await db.collection('notes').doc(id).update({
  data: { shop: _.set({ name: '新店名', address: '新地址' }) },
})
```

要点：

- `update` 是“局部更新”：未传的字段保持不变；嵌套对象默认按键合并，想整体替换用 `_.set`。
- 是否能更新成功受**权限规则**约束：小程序端默认只能更新自己创建的文档。
- `where(...).update()` 同样只能命中当前用户有权限的文档；跨用户的批量更新必须走云函数。

常见误区：

- 把整个修改后的对象丢进 `update`，以为会“整体替换”——实际是合并语义，可能留下旧字段。
- 信任前端做 `_.inc(-1)` 这种计数更新——是否允许减、能否为负，应由云函数判定（U14）。

### 8. 删除 remove 与“只能删自己的”边界

```typescript
async function deleteMyNote(id: string) {
  const res = await db.collection('notes').doc(id).remove()
  console.log(res.stats.removed) // 0 或 1
}
```

小程序端的硬约束：

- 只能删除 `_openid` 等于当前用户的文档（在权限规则允许的前提下）。
- `where(...).remove()` 也只能删除当前用户创建的文档；**批量删除任意文档只能在云函数以管理员身份执行**。

工程上更推荐**软删除**：

```typescript
await db.collection('notes').doc(id).update({
  data: { deleted: true, deletedAt: db.serverDate() },
})
```

列表查询默认过滤 `deleted: _.neq(true)`，这样误删可恢复，评论等关联数据也不会成为孤儿。删除他人笔记、清理论文等管理操作一律进云函数。

常见误区：

- 以为前端调 `remove` 想删哪条删哪条——权限与 openid 双重限制。
- 物理删除笔记后，关联评论与点赞记录悬空无法追溯。

### 9. 正则查询 db.RegExp

`db.RegExp` 用于字符串模糊匹配：

```typescript
// 标题中包含“咖啡”，忽略大小写
db.collection('notes').where({
  title: db.RegExp({ regexp: '咖啡', options: 'i' }),
}).get()

// 门店名以“老王”开头（前缀匹配，更可能命中索引）
db.collection('notes').where({
  shopName: db.RegExp({ regexp: '^老王', options: 'i' }),
}).get()

// 多个关键词之一
db.collection('notes').where({
  content: db.RegExp({ regexp: 'coffee|咖啡|拿铁', options: 'i' }),
}).get()
```

`options` 常用值：`i` 忽略大小写，`m` 多行模式，`s` 让 `.` 匹配换行符。

使用注意：

- 搜索用户输入前，应对正则特殊字符做转义，避免用户输入 `(`、`*` 改变语义或造成报错。
- 不带 `^` 的包含型正则通常无法有效利用索引，数据量大时是全表扫描，应配合其他等值条件缩小范围。
- 超长文本、全文搜索需求应考虑专门的搜索方案，不要把正则当搜索引擎。

常见误区：把任意用户输入直接拼进正则；对十万级集合跑无边界的 `.*关键词.*`。

### 10. 地理查询：db.Geo.Point 与 geoNear

探店类应用的核心查询是“附近有什么”。云数据库用 GeoJSON 风格存点：

```typescript
// 经度 longitude 在前，纬度 latitude 在后！
const point = db.Geo.Point(116.404, 39.915)
```

查询距离某坐标 1 公里内的门店：

```typescript
const _ = db.command

async function findNearbyShops(longitude: number, latitude: number) {
  const res = await db.collection('shops').where({
    location: _.geoNear({
      geometry: db.Geo.Point(longitude, latitude),
      maxDistance: 1000, // 单位：米
      minDistance: 0,
    }),
  }).get()
  return res.data
}
```

配合 `wx.chooseLocation` 获取用户选择的位置：

```typescript
wx.chooseLocation({
  success: (res) => {
    findNearbyShops(res.longitude, res.latitude).then((shops) => {
      this.setData({ shops })
    })
  },
})
```

还可以用 `_.geoWithin` 判断点是否在一个多边形范围内（如商圈范围）。

硬性要求与误区：

- **坐标顺序是“经度, 纬度”**，写反会得到完全错误的结果。
- 必须在控制台对该字段建立**地理位置索引**，否则 `geoNear` 报错或退化为全表扫描。
- 位置必须存为 `db.Geo.Point` 类型，存成 `"116.404,39.915"` 字符串无法做地理查询。

### 11. 排序、分页与字段投影

#### 11.1 排序 orderBy

```typescript
// 按发布时间倒序
db.collection('notes')
  .where({ status: 'published' })
  .orderBy('createdAt', 'desc')
  .get()

// 多重排序：先按分类，再按点赞数
db.collection('notes')
  .orderBy('category', 'asc')
  .orderBy('likeCount', 'desc')
  .get()
```

#### 11.2 分页 skip / limit

```typescript
async function listNotes(page: number, pageSize = 10) {
  const res = await db.collection('notes')
    .where({ status: 'published' })
    .orderBy('createdAt', 'desc')
    .skip((page - 1) * pageSize)
    .limit(pageSize)
    .get()
  return res.data
}
```

页面下拉触发 `page + 1`，把新结果追加进数组即可实现“上拉加载更多”。

#### 11.3 字段投影 field 与计数 count

```typescript
// 列表页只取必要字段，减少传输量
db.collection('notes')
  .field({ title: true, cover: true, shopName: true, likeCount: true })
  .limit(10)
  .get()

// 统计我的笔记数量
const countRes = await db.collection('notes')
  .where({ _openid: '{openid}' }) // 实际由系统结合权限处理
  .count()
```

注意小程序端 `count` 受权限和结果集规模约束，大集合的精确总数应在云函数/聚合中统计，前端分页通常用“是否取满一页”判断是否还有更多，而不是依赖总数。

深分页问题：`skip(10000)` 意味着数据库仍要扫描并跳过前一万条，代价很高；高频场景可用“上一页最后一条的 createdAt 做条件”的游标式分页替代大 skip。

常见误区：

- 不 `orderBy` 却期待结果顺序稳定——无排序时返回顺序不应被业务依赖。
- 用客户端时间字段排序、用字符串存数字再排序（`"9" > "10"` 的字典序陷阱）。

### 12. 数据库权限与自定义安全规则

权限是集合级别的“门卫”，决定小程序端能不能读、能不能写。内置预设四种：

| 预设 | 读 | 写 | 适用 |
|---|---|---|---|
| 仅创建者可读写 | 自己的 | 自己的 | 私有草稿、私密收藏 |
| 所有人可读，仅创建者可写 | 所有人 | 自己的 | 公开笔记、用户主页信息 |
| 所有人可读写 | 所有人 | 所有人 | 谨慎使用，基本只用于只读演示 |
| 仅管理端（云函数）可读写 | 前端不可 | 前端不可 | 计数表、配置表、敏感数据 |

当预设不够用时，使用**自定义安全规则**（JSON），分别写 `read` 与 `write` 的布尔表达式。可用变量：

- `doc`：当前文档，如 `doc._openid`；
- `auth`：当前用户，如 `auth.openid`；
- `true` / `false`：直接放行或拒绝；
- `now`：当前时间，可做有效期判断。

「逛吃指南」推荐配置：

users 集合（每人只能读写自己的资料）：

```json
{
  "read": "doc._openid == auth.openid",
  "write": "doc._openid == auth.openid"
}
```

notes 集合（已发布的所有人可读，未发布的仅作者可读；写仅作者）：

```json
{
  "read": "doc.status == 'published' || doc._openid == auth.openid",
  "write": "doc._openid == auth.openid"
}
```

comments 集合（所有人可读，仅作者可写自己的评论）：

```json
{
  "read": true,
  "write": "doc._openid == auth.openid"
}
```

likeCount 等计数字段如果也放在 notes 里，会导致前端规则无法区分“改标题”和“刷点赞数”，这正是要把点赞收敛到云函数、甚至把计数表设为“仅管理端可读写”的原因。

核心原则：

- **最小权限**：能 false 就不 true，能仅创建者就不给所有人。
- 安全规则只能表达“谁能对哪类文档读写”，**不能表达字数限制、库存扣减、跨集合事务**——这些归云函数。
- 前端“隐藏按钮”不是鉴权，任何人都能直接构造请求；门卫必须在数据库/云函数这一层。

常见误区：为了图省事把所有集合设成所有人可读写；以为安全规则能做业务校验。

### 13. 索引：让查询从“翻全书”变成“查目录”

没有索引时，数据库只能逐条扫描集合；索引是预先排好的快速查找结构。

- **单字段索引**：针对常用查询字段，如 `status`、`category`、`_openid`。
- **组合索引**：针对多字段条件，如 `status + createdAt`。
- **地理位置索引**：`geoNear` 的必需条件。
- 唯一索引等高级能力以控制台当前支持为准。

建组合索引时字段顺序有讲究，通常遵循“等值条件字段在前，排序/范围字段在后”。例如列表查询 `where status=published orderBy createdAt desc`，适合建 `{ status: 1, createdAt: -1 }` 这样的组合索引。

代价：索引提升读性能，但会占用存储、拖慢写入（每次写入要同步维护索引），因此按实际高频查询建，而不是给每个字段都建。

排查路径：控制台有慢查询/索引建议时，先看实际查询语句，再决定加什么索引；不要凭感觉堆索引。

### 14. 小程序端直写数据库的风险与“写操作收敛云函数”原则

#### 14.1 为什么前端不可信

- 小程序代码包可以被反编译，`wx.cloud.database` 的调用参数在调试环境中可被构造和篡改。
- 前端能传任意字段：你收的是 `title`，他可以多塞一个 `likeCount: 99999`。
- 前端的校验、隐藏按钮、登录判断都运行在用户设备上，绕过它们不需要黑客技术。

#### 14.2 直写写不了的业务规则

- 字段白名单与字数、内容合法性（敏感词）；
- 跨集合一致性：发笔记同时要给用户 `noteCount +1`；
- 计数准确与防重复点赞；
- 限频、限额、风控；
- 任何需要**密钥**调用第三方接口的操作。

#### 14.3 读写决策表

| 操作 | 建议方式 |
|---|---|
| 读公开笔记/门店/评论 | 小程序端直读 + 安全规则 |
| 读自己的私有数据 | 小程序端直读 + 仅创建者规则 |
| 修改本人昵称头像等简单资料 | 可直写，但 U14 起建议统一走云函数 |
| 发布笔记、点赞、评论、计数 | 一律走云函数 |
| 删除他人内容、批量操作、定时任务 | 只能云函数（管理员身份） |
| 用到密钥或开放接口 | 只能云函数（密钥不下前端） |

一句话原则：

> **读：能用安全规则保护的，客户端直读以换取速度；写：凡是涉及信任、计数、跨集合、密钥与管理员操作的，全部收敛到云函数。**

这也与 U12 形成分工：本地 Storage 做草稿、缓存与离线兜底；云数据库是唯一真值；写动作的“裁判”在云函数。

#### 15.2 类型与服务层

```typescript
// types/index.ts
interface UserRecord {
  _id: string
  _openid: string
  nickName: string
  avatarUrl: string
  noteCount: number
  createdAt: Date

interface CommentRecord {
  _id: string
  _openid: string

```

```typescript
// services/noteService.ts
const db = wx.cloud.database()
const _ = db.command

export const noteService = {
  // 分页列表
  async listPublished(page: number, pageSize = 10): Promise<Note[]> {
    const res = await db.collection('notes')
      .where({ status: 'published' })
      .orderBy('createdAt', 'desc')
      .field({ title: true, images: true, shopName: true, likeCount: true, commentCount: true })
      .skip((page - 1) * pageSize)
      .limit(pageSize)
      .get()
    return res.data as Note[]
  },

  // 详情
  async detail(id: string): Promise<Note | null> {
    try {
      const res = await db.collection('notes').doc(id).get()
      return res.data as Note
    } catch {
      return null
    }
  },

  // 我的笔记
  async listMine(page: number, pageSize = 10): Promise<Note[]> {
    const res = await db.collection('notes')
      .orderBy('createdAt', 'desc')
      .skip((page - 1) * pageSize)
      .limit(pageSize)
      .get()
    return res.data as Note[]
  },

  // 关键词搜索（标题或门店名）
  async search(keyword: string): Promise<Note[]> {
    const safe = keyword.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')
    const res = await db.collection('notes').where({
      status: 'published',
      ..._.or([
        { title: db.RegExp({ regexp: safe, options: 'i' }) },
        { shopName: db.RegExp({ regexp: safe, options: 'i' }) },
      ]),
    }).limit(20).get()
    return res.data as Note[]
  },

  // 附近门店
  async nearbyShops(longitude: number, latitude: number, radiusMeters = 1000) {
    const res = await db.collection('shops').where({
      location: _.geoNear({
        geometry: db.Geo.Point(longitude, latitude),
        maxDistance: radiusMeters,
      }),
    }).get()
    return res.data
  },
}
```

说明：本单元为了讲清数据库 API，列表与搜索都走客户端直读；**新增/更新/删除/点赞在 U14 会改为 `wx.cloud.callFunction`**，届时 notes 的写权限会收紧为“仅管理端可写”或“写操作仅限云函数规则”，形成纵深防御。

#### 15.3 页面联调示例

```typescript
// pages/note-list/index.ts
Page({
  data: { notes: [] as Note[], page: 1, hasMore: true, loading: false },

  onShow() {
    this.refresh()
  },

  async refresh() {
    const list = await noteService.listPublished(1)
    this.setData({ notes: list, page: 1, hasMore: list.length === 10 })
  },

  async onReachBottom() {
    if (!this.data.hasMore || this.data.loading) return
    this.setData({ loading: true })
    const nextPage = this.data.page + 1
    const list = await noteService.listPublished(nextPage)
    this.setData({
      notes: this.data.notes.concat(list),
      page: nextPage,
      hasMore: list.length === 10,
      loading: false,
    })
  },
})
```
