# 16-登录鉴权与用户体系

## 目标

完成本知识单元后，学员应能把「我是谁、由谁证明、登录态怎么维持、用户资料怎么合规收集」讲清楚，并为「逛吃指南」实现首次进入静默登录、用户资料落库与头像昵称/手机号的合规收集，而不是让前端随便传一个 openid 或继续使用已废弃的 `wx.getUserInfo` 弹窗拿真实信息。

学员应能够：

1. 说清鉴权的基本原则：用户身份由微信平台签发、由服务端/云函数验证，**前端无法伪造**；小程序端拿到的 code、token 都不是身份本身。
2. 使用 `wx.login` 获取一次性临时登录凭证 code，说清 code 的性质：临时、短时有效、只能被服务端用 AppID + AppSecret 换取一次。
3. 掌握 `code2session` 的服务端流程：用 code 换取 openid、session_key，以及在满足条件时返回的 unionid，并能处理常见错误码与频率限制。
4. 区分 openid 与 unionid：openid 是「用户在单个小程序」下的身份，unionid 是「用户在同一微信开放平台账号下多个应用」的统一身份，用于多端/多应用账号打通。
5. 说清 session_key 的用途（解密加密数据、校验用户信息签名）与保密要求，并使用 `wx.checkSession` 判断登录态是否过期、过期后重新静默登录。
6. 在云函数中通过 `cloud.getWXContext()` 获取调用者的 OPENID/UNIONID，理解云开发调用天然带平台鉴权，不依赖前端自报身份。
7. 实现云函数签发并维护自定义登录态：服务端生成 token（会话号或签名令牌），客户端缓存并在后续请求中携带，服务端校验有效期并支持刷新/失效。
8. 设计并落地 `users` 用户集合：首次登录自动建档（openid/unionid/创建时间），资料字段按需补全，登录与资料收集解耦。
9. 按当前合规要求收集头像昵称：`button open-type="chooseAvatar"` 选择头像（临时路径需上传云存储得 fileID）、`input type="nickname"` 填写昵称并用 `nickname-review` 审核结果把关。
10. 实现手机号快速验证：`button open-type="getPhoneNumber"` 取动态令牌，在云函数中换取真实手机号；说清已废弃 API（getUserInfo/getUserProfile）的演进、降级与未认证账号的兜底方案。

本单元是阶段二里程碑的收口：完成后，「逛吃指南」的笔记、文件都能归属到真实、不可伪造的用户，W8 即可交付登录、数据库、云函数、云存储全部闭环的云开发版本。

## 技术栈

本单元基于微信原生小程序 + TypeScript，使用云函数与云开发服务端 SDK（`wx-server-sdk`），不引入第三方账号体系。

| 工具或 API | 用途 | 学习要求 |
|---|---|---|
| `wx.login` | 获取临时登录凭证 code | 理解 code 的一次性与有效期 |
| `code2session` | 服务端换 openid/session_key/unionid | 掌握请求参数与错误处理 |
| `wx.checkSession` | 判断登录态是否过期 | 会据此触发重新登录 |
| `cloud.getWXContext()` | 云函数取调用者身份 | 会取 OPENID/APPID/UNIONID |
| 自定义 token 登录态 | 维持服务端会话 | 会签发、缓存、校验、刷新、失效 |
| `wx.cloud.callFunction` | 小程序调用登录云函数 | 会携带 code 并处理返回 |
| `users` 集合 | 用户资料落库 | 会设计字段与 upsert 建档 |
| `button open-type="chooseAvatar"` | 合规选择头像 | 会处理 chooseavatar 临时路径 |
| `input type="nickname"` | 合规填写昵称 | 会用 form 收集、nickname-review 把关 |
| `button open-type="getPhoneNumber"` | 手机号快速验证 | 云函数用动态令牌换取手机号 |
| TypeScript | 类型化登录服务与资料表单 | 类型完整，不用 any 掩盖结构 |

实验约定：

- AppID、AppSecret 等机密只存在微信服务端/云函数环境中，**绝不写入小程序代码或仓库**；云函数中优先用 `getWXContext`，无需自行持有 Secret。
- 登录（拿 openid）静默完成；头像、昵称、手机号属于用户资料，必须由用户在明确场景下主动填写或授权，二者不混为一谈。
- 各能力的基础库版本、账号认证要求（手机号能力需非个人主体并完成认证）、审核规则以微信官方文档为准，并必须提供降级方案。

## 详细的理论知识讲解和示例伪代码

### 1. 身份与鉴权的基本问题：为什么身份不能由前端声明

#### 1.1 是什么

鉴权（Authentication）要回答的第一个问题是「**你是谁**」。在小程序里，这个「谁」最终对应一个由微信平台签发的身份标识——openid。安全模型的核心前提是：**身份凭证只能由微信平台和你自己的服务端产生与验证，客户端代码是运行在用户设备上、可被分析和篡改的，因此客户端自报的身份一律不可信**。

#### 1.2 为什么前端传 openid 不可信

假设「逛吃指南」的发布接口接受前端传来的 `openid` 参数作为作者身份，攻击者只需：

1. 抓包或阅读代码知道参数名；
2. 在请求里把 openid 改成任意值；
3. 就能把笔记写到别人名下、或读取/删除他人数据。

前端没有任何「不可篡改的边界」——小程序包可以被解包，请求可以被工具重放。所以正确做法是：客户端只传递微信颁发的临时凭证，由**服务端/云函数向微信验证后，从可信上下文中取出 openid**。

#### 1.3 三条安全结论

1. 身份由平台签发：`wx.login` 的 code → 服务端换 openid，或云函数 `getWXContext` 直接取；
2. 密钥只在服务端：AppSecret、签名密钥、token 签发密钥绝不下发到客户端；
3. 登录态由服务端维护：客户端持有的 token 只是「票据」，服务端可随时作废，真正的会话真值在服务端。

误区提醒：

- 「代码做了混淆/小程序是封闭环境，前端传身份没问题」——混淆不等于安全，封闭是错觉，凭证必须服务端验证。
- 「加了登录按钮、点过授权就是登录了」——按钮与授权弹窗是产品交互，登录成立的唯一标准是服务端确认了 openid 并建立了会话。

### 2. wx.login：获取一次性临时凭证 code

#### 2.1 是什么

`wx.login` 让当前用户在当前小程序下获得一个临时登录凭证 **code**。它是整个登录流程的起点：code 本身不含用户身份信息（拿不到 openid），它只是一张「去服务端换取身份的取号小票」。

#### 2.2 code 的性质

- **临时**：有效期很短（约 5 分钟，以官方文档为准）；
- **一次性**：一个 code 只能被 `code2session` 成功换取一次，重复使用报错；
- **不携带敏感信息**：即使被截获，攻击者没有 AppSecret 也换不到 openid；
- 用户无感知：`wx.login` 不弹任何授权框，属于**静默登录**。

#### 2.3 可运行示例

```typescript
/** 静默获取登录 code */
export function getLoginCode(): Promise<string> {
  return new Promise((resolve, reject) => {
    wx.login({
      timeout: 5000,
      success(res) {
        if (res.code) {
          resolve(res.code)
        } else {
          reject(new Error('wx.login 未返回 code'))
        }
      },
      fail(err) {
        reject(new Error(err.errMsg))
      },
    })
  })
}
```

误区提醒：

- 「把 code 当 openid 存起来」——code 几分钟就失效，且只是换取凭证，不是身份。
- 「为了省事先缓存 code，过期再说」——code 一次性、短时，缓存没有意义；需要缓存的是换取成功后由服务端签发的登录态。

### 3. code2session：服务端用 code 换 openid / session_key / unionid

#### 3.1 是什么

`code2session` 是微信服务端接口。你的服务端（或云函数背后的可信环境）拿着 AppID、AppSecret 和 code 调用它，微信验证通过后返回：

- `openid`：用户在本小程序的唯一标识；
- `session_key`：会话密钥，用于解密微信下发的加密数据（不应下发给客户端长期保存）；
- `unionid`：当小程序已绑定微信开放平台账号时返回；
- 出错时返回 `errcode` / `errmsg`。

#### 3.2 接口形态

```text
GET https://api.weixin.qq.com/sns/jscode2session
    ?appid=APPID
    &secret=APPSECRET
    &js_code=CODE
    &grant_type=authorization_code
```

成功响应示例：

```json
{
  "openid": "o1b2c3d4e5f6...",
  "session_key": "tA3xxxx==",
  "unionid": "uXYZ..."
}
```

#### 3.3 自建服务器示例（Node.js，仅用于理解流程）

```typescript
// 注意：本文件属于【服务端】，AppSecret 来自服务端环境变量，绝不在小程序端
import https from 'https'

interface SessionResult {
  openid: string
  session_key: string
  unionid?: string
}

export function code2Session(appid: string, secret: string, code: string): Promise<SessionResult> {
  const url = `https://api.weixin.qq.com/sns/jscode2session?appid=${appid}&secret=${secret}&js_code=${code}&grant_type=authorization_code`
  return new Promise((resolve, reject) => {
    https.get(url, (resp) => {
      let raw = ''
      resp.on('data', (chunk) => (raw += chunk))
      resp.on('end', () => {
        const data = JSON.parse(raw) as SessionResult & { errcode?: number; errmsg?: string }
        if (data.errcode) {
          reject(new Error(`code2session 失败：${data.errcode} ${data.errmsg}`))
          return
        }
        resolve({ openid: data.openid, session_key: data.session_key, unionid: data.unionid })
      })
    }).on('error', reject)
  })
}
```

#### 3.4 常见错误码（以官方文档为准）

| errcode | 含义 | 处理方式 |
|---|---|---|
| 40029 | code 无效 / 已被使用 | 重新 wx.login 获取新 code |
| 45011 | API 频率限制 | 降低频率、退避重试 |
| 40013 | AppID 不合法 | 检查服务端配置 |
| 40125 | AppSecret 不正确 | 检查密钥配置，定期轮换 |

误区提醒：

- 「在小程序端直接请求 code2session」——这会暴露 AppSecret，任何人解包即可冒充你的应用；该请求必须在服务端发起。
- 「session_key 返回给前端保存方便解密」——session_key 是服务端机密，泄露后加密数据失去保护；解密动作在服务端完成。

### 4. openid 与 unionid：单应用身份与多端打通

#### 4.1 是什么

- **openid**：一个微信用户在「某一个小程序（AppID）」下的唯一 ID。同一个用户，在不同小程序里的 openid 不同；在同一小程序里永远不变。
- **unionid**：当多个小程序、公众号、移动应用绑定到**同一个微信开放平台账号**下时，同一个微信用户在这些应用中拿到相同的 unionid。它是跨应用打通账号体系的钥匙。

#### 4.2 关系图

```text
微信用户 U
 ├── 小程序 A（AppID-A） → openid_A，unionid_X
 ├── 小程序 B（AppID-B） → openid_B，unionid_X
 └── 公众号 C             → openid_C，unionid_X
        openid 各不相同；只要都绑在同一开放平台账号，unionid 相同
```

#### 4.3 对「逛吃指南」的意义

如果未来「逛吃指南」要出 App 版或再做一个「逛吃商家版」小程序，希望用户头像、收藏、笔记在多端共享，就应以 **unionid 作为账号主键之一**；单个小程序内，用 openid 即可定位用户。设计 `users` 表时建议两个字段都保留。

注意：unionid 不是默认就有——需要在微信开放平台绑定小程序、主体一致并通过审核；未绑定时 `code2session`/`getWXContext` 不返回 unionid，业务要允许其为空并在以后回填。

误区提醒：

- 「openid 可以在两个小程序间通用」——不行，跨应用必须用 unionid。
- 「同一公司主体的小程序天然共享 unionid」——必须显式绑定到同一个开放平台账号，主体相同不等于自动打通。

### 5. session_key：用途、保密与 wx.checkSession

#### 5.1 session_key 能做什么

session_key 是微信与服务端之间的会话密钥，主要用于：

1. 解密小程序通过 `encryptedData` 上送的加密内容（如旧版手机号、用户信息）；
2. 校验敏感数据的签名，防止被篡改；
3. 作为「微信侧登录态是否仍有效」的依据。

它**不是**业务登录态，业务登录态应由服务端自行签发（第 7 节）。

#### 5.2 wx.checkSession

`wx.checkSession` 用来检查微信侧的会话（session_key）是否仍然有效：

- success：会话仍有效，短期内不必重复登录；
- fail：会话已过期（用户长时间未使用、或微信侧主动失效），需要重新 `wx.login`。

```typescript
/** 以布尔形式返回微信会话是否有效 */
export function isWxSessionValid(): Promise<boolean> {
  return new Promise((resolve) => {
    wx.checkSession({
      success: () => resolve(true),
      fail: () => resolve(false),
    })
  })
}
```

#### 5.3 使用建议

checkSession 只是「优化项」，用来避免频繁 `wx.login`；即使它返回有效，服务端的自定义登录态仍可能已过期。**是否真正登录成功，最终以服务端校验为准**，过期则静默重登并刷新 token。

误区提醒：

- 「checkSession 有效就等于业务已登录」——两回事，微信会话有效但你的服务端会话可能已被注销。
- 「频繁 wx.login 没成本」——存在频率限制，且会让 session_key 轮换；应先用 checkSession 判断。

### 6. 云函数获取调用者身份：cloud.getWXContext

#### 6.1 是什么

在云开发中，小程序通过 `wx.cloud.callFunction` 调用云函数时，平台会在调用上下文中自动注入调用者的可信身份。云函数里调用 `cloud.getWXContext()` 即可拿到 `OPENID`、`APPID`、`UNIONID`（如已绑定开放平台）。

这意味着：**在云开发体系内，你甚至不需要自己调 code2session**——平台已经完成了「这次调用来自哪个用户」的鉴权，且该字段不可被前端伪造。

#### 6.2 可运行示例

```typescript
// cloudfunctions/whoami/index.ts
import cloud from 'wx-server-sdk'

cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })

exports.main = async () => {
  const ctx = cloud.getWXContext()
  return {
    openid: ctx.OPENID,
    appid: ctx.APPID,
    unionid: ctx.UNIONID ?? '',
  }
}
```

小程序端：

```typescript
const res = await wx.cloud.callFunction({ name: 'whoami' })
console.log(res.result) // { openid: '...', appid: '...', unionid: '...' }
```

#### 6.3 与 code2session 的选型

| 方式 | 适用架构 | 是否需要持有 Secret |
|---|---|---|
| `getWXContext` | 纯云开发（云函数 + 云数据库） | 不需要，平台托管 |
| `code2session` | 自建后端 / 混合架构 / 需要 session_key 解密 | 需要，Secret 存服务端 |

误区提醒：

- 「前端把 openid 传给云函数，云函数直接用更方便」——多此一举且制造伪造入口；云函数应只信 `getWXContext`。
- 「getWXContext 在云函数本地随便构造调用也能拿到用户」——由平台在真实调用链路注入，不可由调用参数指定。

### 7. 自定义登录态：云函数签发 token 与服务端会话

#### 7.1 云开发里为什么还要讲 token

云函数之间的调用已自带 openid，但仍有场景需要**自定义登录态**：

1. 小程序要访问**自建服务器**（Express 等），自建服务器不在云调用链路里；
2. 多端统一账号（App/Web），需要一套与端无关的会话；
3. 需要做「踢人下线、单点登录、会话过期管理」等服务端可控策略。

因此标准做法是：云函数确认 openid 后签发一个 token，客户端缓存并在后续请求中携带，服务端凭 token 反查/验签得到 openid。

#### 7.2 两种 token 实现思路

- **不透明会话号（Opaque Token）**：服务端生成随机串，在库中保存 `token → openid、过期时间`；校验时查库，优点是可即时作废，缺点是每次要查存储。
- **签名令牌（如 JWT 风格）**：服务端用密钥对 `{ openid, unionid, exp }` 做 HMAC 签名；校验时验签、看过期时间，无需查库，但作废较麻烦（需配黑名单/短有效期）。

教学示例采用不透明会话号（更易理解与维护）。

#### 7.3 云函数签发示例

```typescript
// cloudfunctions/login/index.ts
import cloud from 'wx-server-sdk'
import crypto from 'crypto'

cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const db = cloud.database()
const TOKEN_TTL_MS = 7 * 24 * 60 * 60 * 1000 // 7 天

interface UserRecord {
  _id: string
  openid: string
  unionid: string
  profileCompleted: boolean
}

exports.main = async () => {
  const { OPENID, UNIONID } = cloud.getWXContext()

  // 1. 查找或创建用户（upsert 语义）
  const user = await findOrCreateUser(OPENID, UNIONID ?? '')

  // 2. 签发会话号：足够随机，不可猜测
  const token = crypto.randomBytes(32).toString('hex')
  const now = Date.now()

  await db.collection('login_sessions').add({
    data: {
      token,
      openid: OPENID,
      unionid: UNIONID ?? '',
      createdAt: new Date(now),
      expiresAt: new Date(now + TOKEN_TTL_MS),
      revoked: false,
    },
  })

  // 3. 返回 token 与用户资料（session_key 绝不下发）
  return {
    token,
    expiresIn: TOKEN_TTL_MS,
    profile: {
      id: user._id,
      profileCompleted: user.profileCompleted,
    },
  }
}

async function findOrCreateUser(openid: string, unionid: string): Promise<UserRecord> {
  const users = db.collection('users')
  const found = await users.where({ openid }).get()
  if (found.data.length > 0) return found.data[0] as UserRecord
  const created = await users.add({
    data: {
      openid,
      unionid,
      nickname: '',
      avatarFileID: '',
      phone: '',
      phoneVerified: false,
      profileCompleted: false,
      createdAt: new Date(),
      updatedAt: new Date(),
    },
  })
  return { _id: created._id, openid, unionid, profileCompleted: false }
}
```

#### 7.4 自建服务器端的签名令牌（概念示例）

```typescript
// 服务端：HMAC 签名，密钥 SESSION_SECRET 只存在服务端环境变量
import crypto from 'crypto'

function sign(payload: object, secret: string): string {
  const body = Buffer.from(JSON.stringify(payload)).toString('base64url')
  const sig = crypto.createHmac('sha256', secret).update(body).digest('base64url')
  return `${body}.${sig}`
}

function verify(token: string, secret: string): { openid: string; exp: number } | null {
  const [body, sig] = token.split('.')
  const expect = crypto.createHmac('sha256', secret).update(body).digest('base64url')
  if (sig !== expect) return null
  const data = JSON.parse(Buffer.from(body, 'base64url').toString()) as { openid: string; exp: number }
  if (Date.now() > data.exp) return null
  return data
}
```

误区提醒：

- 「token 里直接写明 openid 不签名也能用」——可被任意篡改；不透明 token 必须服务端可查，自描述 token 必须签名。
- 「token 用时间戳/短随机数凑合」——可被猜测枚举；应使用密码学安全随机源（`crypto.randomBytes`）。
- 「登录态永不过期最省事」——丢失后风险无限放大；必须有有效期与服务端作废能力。

### 8. 登录态的缓存、过期、刷新与续期

#### 8.1 客户端把 token 放哪

token 属于「敏感但需要跨启动使用」的票据，建议：

1. 用 `wx.setStorage` 持久化，保证重启后仍可用；
2. 同时在内存（模块变量/globalData）保留一份，方便同步读取；
3. 不把 token 拼到 URL 里（容易被日志/分享泄露），放请求头或云函数参数；
4. 收到 401/会话失效时清除本地 token 并重新静默登录。

#### 8.2 双端过期协同

```text
客户端：存 token + expiresAt，临近过期可主动刷新
服务端：会话记录有 expiresAt，校验时判过期；支持刷新接口换发新 token、旧 token 作废
微信侧：session_key 可能先过期，靠 wx.checkSession / 接口 401 兜底重登
```

#### 8.3 可运行示例：客户端会话存取

```typescript
interface AuthSession {
  token: string
  expiresAt: number
  profileCompleted: boolean
}

const KEY = 'gc_auth_session'

export function saveSession(s: AuthSession): void {
  wx.setStorageSync(KEY, s)
}

export function readSession(): AuthSession | null {
  const s = wx.getStorageSync(KEY) as AuthSession | ''
  if (!s || !s.token) return null
  if (Date.now() > s.expiresAt) {
    wx.removeStorageSync(KEY)
    return null
  }
  return s
}

export function clearSession(): void {
  wx.removeStorageSync(KEY)
}
```

误区提醒：

- 只信客户端过期时间、服务端不校验——改本地时间即可绕期；服务端必须独立判过期。
- 刷新 token 时旧 token 不失效——形成多个有效会话，丢设备后无法收敛；刷新应轮换并可作废旧会话。

### 9. 静默登录完整流程与登录承诺复用

#### 9.1 完整时序

```text
启动 App
  → 读本地会话：未过期可先用
  → wx.checkSession：微信会话是否有效
  → 无效/无本地会话：wx.login 得 code
  → callFunction('login', {}) 由 getWXContext 取 openid 并签发 token
  → 缓存 token，返回用户资料
  → 后续请求携带 token；401 则清除并重登
```

#### 9.2 登录承诺复用（避免并发重复登录）

启动时多个页面/组件可能同时需要登录。若各自调用 wx.login，会产生重复登录与竞态。标准做法是把「进行中的登录 Promise」缓存，所有调用方共享同一个承诺。

```typescript
// services/auth.ts
import { readSession, saveSession, clearSession, type AuthSession } from './session'

let inFlight: Promise<AuthSession> | null = null

/** 确保已登录，返回有效会话；可被任意页面并发调用 */
export function ensureLogin(): Promise<AuthSession> {
  const cached = readSession()
  if (cached) return Promise.resolve(cached)
  if (inFlight) return inFlight

  inFlight = doLogin().finally(() => {
    inFlight = null
  })
  return inFlight
}

async function doLogin(): Promise<AuthSession> {
  // 微信侧会话过期也没关系，云函数靠 getWXContext，仍可静默完成
  await wx.login()
  const res = await wx.cloud.callFunction({ name: 'login' })
  const result = res.result as { token: string; expiresIn: number; profile: { profileCompleted: boolean } }
  const session: AuthSession = {
    token: result.token,
    expiresAt: Date.now() + result.expiresIn,
    profileCompleted: result.profile.profileCompleted,
  }
  saveSession(session)
  return session
}

/** 服务端报会话失效时调用 */
export async function handleUnauthorized(): Promise<AuthSession> {
  clearSession()
  return ensureLogin()
}
```

#### 9.3 在需要身份的操作前使用

```typescript
async function onTapPublish(this: WechatMiniprogram.Page.Instance<{ needProfile: boolean }, Record<string, never>>) {
  const session = await ensureLogin()
  if (!session.profileCompleted) {
    wx.navigateTo({ url: '/pages/profile-edit/profile-edit?from=publish' })
    return
  }
  wx.navigateTo({ url: '/pages/publish/publish' })
}
```

误区提醒：

- 在 `App.onLaunch` 里 await 登录、阻塞所有页面首屏——登录失败会拖垮启动；应让首屏尽快渲染，需要身份的操作再 `ensureLogin`，或设置超时兜底。
- 登录失败只弹一次错就放弃——静默登录应有限自动重试/可手动重试，并区分网络错误与服务端拒绝。

### 10. 用户资料落库：users 集合设计与首次建档

#### 10.1 集合字段设计

```text
users
  _id              文档主键
  openid           本小程序身份（唯一）
  unionid          开放平台统一身份（可空）
  nickname         用户填写的昵称
  avatarFileID     头像在云存储的 fileID
  phone            已验证手机号（可空）
  phoneVerified    手机号是否已验证
  profileCompleted 资料是否完整
  createdAt        首次登录时间
  updatedAt        最近更新时间
```

设计原则：**登录与资料分离**。首次登录只写身份字段即可建档，昵称/头像/手机号留空，引导用户在「个人资料」页按需补全；笔记表通过 openid 关联作者。

#### 10.2 更新资料的云函数（服务端收敛写操作）

```typescript
// cloudfunctions/updateProfile/index.ts
import cloud from 'wx-server-sdk'

cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const db = cloud.database()

interface ProfileInput {
  nickname?: string
  avatarFileID?: string
}

exports.main = async (event: ProfileInput) => {
  const { OPENID } = cloud.getWXContext()

  const patch: Record<string, unknown> = { updatedAt: new Date() }
  if (typeof event.nickname === 'string') patch.nickname = event.nickname.slice(0, 20)
  if (typeof event.avatarFileID === 'string' && event.avatarFileID.startsWith('cloud://')) {
    patch.avatarFileID = event.avatarFileID
  }

  // 以 openid 定位本人资料，前端无法指定改谁
  const found = await db.collection('users').where({ openid: OPENID }).get()
  if (found.data.length === 0) return { ok: false, code: 'NO_USER' }

  const profile = found.data[0] as { nickname: string; avatarFileID: string }
  const completed = Boolean(patch.nickname ?? profile.nickname) && Boolean(patch.avatarFileID ?? profile.avatarFileID)
  patch.profileCompleted = completed

  await db.collection('users').doc(found.data[0]._id).update({ data: patch })
  return { ok: true, profileCompleted: completed }
}
```

误区提醒：

- 「更新资料接口让前端传 userId/openid」——又是伪造入口；一律由 getWXContext 定位。
- 「把 session_key、token 也存进 users 表」——会话数据独立集合管理，便于过期与作废，不和档案混放。

### 11. 头像昵称合规收集：chooseAvatar + type=nickname

#### 11.1 合规演进的结论

根据《小程序用户头像昵称获取规则调整公告》及现行规则：小程序**不能再通过 wx.getUserInfo / wx.getUserProfile 静默或弹窗获取用户真实微信头像与昵称**，调用这些接口只会得到灰色默认头像和「微信用户」。现行方案是**头像昵称填写能力**：由用户主动选头像、主动填昵称。

需要在小程序管理后台配置「用户隐私保护指引」，说明收集用途，这是能力可用的前提。

#### 11.2 WXML：头像按钮 + 昵称输入框

```xml
<!-- pages/profile-edit/profile-edit.wxml -->
<view class="form">
  <view class="row">

    </button>
  </view>

  <form bindsubmit="onSubmit">
    <view class="row">
      <text class="label">昵称</text>
      <input
        class="nick-input"
        type="nickname"
        name="nickname"
        value="{{form.nickname}}"
        placeholder="请输入昵称"
        bind:nickname-review="onNicknameReview"
      />
    </view>
    <button class="save" form-type="submit" disabled="{{saving}}">保存</button>

</view>
```

#### 11.3 页面逻辑：接收头像临时路径

```typescript
const defaultAvatar = '/images/default-avatar.png'

Page({
  data: {
    defaultAvatar,
    saving: false,
    nicknamePassed: true,
    form: { avatarUrl: '', avatarFileID: '', nickname: '' },
  },

  onLoad() {
    // 预填已有资料（从「我的」页传入或查询）
  },

  onChooseAvatar(e: WechatMiniprogram.CustomEvent<{ avatarUrl: string }>) {
    // e.detail.avatarUrl 为本地临时路径，需上传云存储换 fileID
```

要点：`chooseAvatar` 仅在用户选定后触发；自基础库 2.24.4 起，未通过安全检测的图片不会触发该事件，因此不触发本身就是一种拦截信号。

误区提醒：

- 「把 chooseAvatar 的临时路径直接存库」——临时路径只在本机有效，必须上传云存储得 fileID（衔接 U15）。
- 「在 bindinput 里立刻保存昵称」——安全检测在失焦后异步进行，可能存下违规昵称；应通过 form 提交并结合 nickname-review 结果。

### 12. 昵称安全审核 nickname-review 与头像上传得 fileID

#### 12.1 nickname-review 事件

自基础库 2.29.1 起，昵称输入框提供 `nickname-review` 回调（WXML 中用 `bind:nickname-review` 或 `bindnicknamereview` 绑定），安全检测完成后回调：

```text
event.detail = { pass: boolean, timeout: boolean }
```

- `pass`：昵称是否通过安全检测；
- `timeout`：检测是否超时（超时不等于一定违规，但提交需谨慎，可让用户稍后重试）。

正确提交策略：**只有拿到 pass 为 true 才允许保存**；未通过时清空昵称并提示重填。

#### 12.2 保存：先传头像、再提交资料

```typescript
import { ensureLogin } from '../../services/auth'
import { buildCloudPath } from '../../utils/cloudPath'

async function onSubmit(this: WechatMiniprogram.Page.Instance<AnyObject, AnyObject>, e: WechatMiniprogram.CustomEvent) {
  const nickname = (e.detail.value.nickname as string) ?? ''

  if (!this.data.nicknamePassed) {
    wx.showToast({ title: '昵称未通过审核', icon: 'none' })
    return
  }
  if (nickname.trim() === '') {
    wx.showToast({ title: '请填写昵称', icon: 'none' })
    return
  }

  this.setData({ saving: true })
  try {
    await ensureLogin()

    // 1. 头像：本地临时路径 -> 云存储 fileID
    let avatarFileID = this.data.form.avatarFileID as string
    const localAvatar = this.data.form.avatarUrl as string
    if (localAvatar && !avatarFileID) {
      const up = await wx.cloud.uploadFile({
        cloudPath: buildCloudPath('avatars', 'jpg'),
        filePath: localAvatar,
      })
      avatarFileID = up.fileID
    }

    // 2. 昵称 + 头像 fileID 经云函数落库（身份由云函数取）
    const res = await wx.cloud.callFunction({
      name: 'updateProfile',
      data: { nickname: nickname.trim(), avatarFileID },
    })
    if ((res.result as { ok: boolean }).ok) {
      wx.showToast({ title: '已保存', icon: 'success' })
      wx.navigateBack()
    } else {
      wx.showToast({ title: '保存失败', icon: 'none' })
    }
  } catch (err) {
    wx.showToast({ title: '保存失败，请重试', icon: 'none' })
  } finally {
    this.setData({ saving: false })
  }
}
```

#### 12.3 更换头像时的旧文件处理

用户反复更换头像会让旧头像 fileID 指向的文件失去引用。可在 `updateProfile` 成功替换后，由云函数把旧 `avatarFileID` 放入清理表（复用 U15 的 `file_cleanup_tasks`），避免存储浪费。

误区提醒：

- 「review 超时就当作通过先提交」——违规内容可能因此入库；超时应阻断或走服务端二次内容检测。
- 「昵称、头像先存本地就算完善了资料」——资料真值要落云库，否则换设备即丢失。

### 13. 手机号快速验证：getPhoneNumber 与云函数取号

#### 13.1 使用前提

手机号属于高度敏感的个人信息，能力门槛与合规要求更严：

1. 小程序需为**非个人主体并完成微信认证**，个人主体小程序无法使用；
2. 需在隐私指引中声明用途，按真实业务最小化收集；
3. 必须通过用户点击 `open-type="getPhoneNumber"` 的按钮主动授权，不能静默获取。

#### 13.2 新版本：动态令牌 code（推荐）

WXML：

```xml
<button
  class="bind-phone"
  open-type="getPhoneNumber"
  bind:getphonenumber="onGetPhoneNumber"
>绑定手机号</button>
```

页面逻辑：

```typescript
async onGetPhoneNumber(
  this: WechatMiniprogram.Page.Instance<Record<string, never>, Record<string, never>>,
  e: WechatMiniprogram.CustomEvent<{ code: string; errMsg: string }>,
) {
  if (e.detail.errMsg !== 'getPhoneNumber:ok') {
    // 用户拒绝授权：不强制，走降级（手动输入 + 短信验证）
    return
  }
  try {
    const res = await wx.cloud.callFunction({
      name: 'bindPhone',
      data: { code: e.detail.code },
    })
    const result = res.result as { ok: boolean }
    wx.showToast({ title: result.ok ? '绑定成功' : '绑定失败', icon: 'none' })
  } catch (err) {
    wx.showToast({ title: '绑定失败', icon: 'none' })
  }
}
```

云函数取号（需在云函数 `config.json` 声明 openapi 权限）：

```json
{
  "permissions": {
    "openapi": ["phonenumber.getPhoneNumber"]
  }
}
```

```typescript
// cloudfunctions/bindPhone/index.ts
import cloud from 'wx-server-sdk'

cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const db = cloud.database()

exports.main = async (event: { code: string }) => {
  const { OPENID } = cloud.getWXContext()

  // 用动态令牌向微信换取手机号
  const phoneResult = await cloud.openapi.phonenumber.getPhoneNumber({ code: event.code })
  const info = phoneResult.phoneInfo

  await db.collection('users').where({ openid: OPENID }).update({
    data: {
      phone: info.purePhoneNumber,
      phoneVerified: true,
      countryCode: info.countryCode,
      updatedAt: new Date(),
    },
  })

  return { ok: true }
}
```

返回字段中：`purePhoneNumber` 是不带国家码的纯手机号，`phoneNumber` 可能带国家码前缀，`countryCode` 为区号，`watermark` 含时间戳与 appid。

#### 13.3 旧版本：encryptedData + iv 解密（了解与兼容）

早期方案中按钮回调返回 `encryptedData` 与 `iv`，服务端用 session_key 做 AES-128-CBC 解密，明文 JSON 内含 `phoneNumber`、`purePhoneNumber`、`countryCode` 与 `watermark`。服务端解密后**必须校验 `watermark.appid` 是自己的小程序**，防止拿其他应用的数据重放。该方案已被动态令牌取代，新项目不主动使用，但在维护老代码时要认识它。

误区提醒：

- 「把 code 发给前端、让前端直接调微信接口拿手机号」——取号需要 access_token（由 AppSecret 换取），只能服务端完成。
- 「用户拒一次就一直弹」——应尊重拒绝，提供手动绑定/稍后再绑的降级路径，不得反复骚扰。
- 「拿到手机号全量下发给页面展示」——按最小必要原则，前端通常只展示脱敏号（如 138****8000）。

### 14. 废弃 API 说明、合规演进与降级策略

#### 14.1 API 演进时间线（要点）

| 时期 | 能力 | 现状 |
|---|---|---|
| 早期 | `wx.getUserInfo`、`wx.authorize({scope:'userInfo'})` 弹窗授权 | 弹窗能力早已回收，现只返回匿名信息 |
| 过渡期 | `button open-type="getUserInfo"` + `bindgetuserinfo` | 同上，旧版本历史产物 |
| 2021 | `wx.getUserProfile` 每次使用需确认 | 已停止返回真实头像昵称，现返回「微信用户」+ 默认头像 |
| 现行 | 头像昵称填写能力 chooseAvatar + nickname | 推荐，用户主动填写，平台做安全检测 |

结论：**新项目不要再写 getUserInfo / getUserProfile 去获取真实头像昵称**；登录身份（openid）始终通过 wx.login 在服务端静默获取，与展示资料是两条独立链路。

#### 14.2 必须配套降级

| 能力 | 低版本基础库 / 不满足条件时 | 降级方案 |
|---|---|---|
| chooseAvatar | 基础库低于 2.21.2 | 用普通「相册选图 + 上传」引导用户自定义头像 |
| nickname 输入与 review | 不支持 type=nickname / review | 普通 input + 服务端内容安全检测（msgSecCheck） |
| getPhoneNumber | 个人主体/未认证/用户拒绝 | 手动输入手机号 + 短信验证码验证 |
| 云开发不可用 | 环境异常/欠费 | 明确提示服务异常，保留本地草稿，恢复后重试 |

#### 14.3 兼容判断写法

```typescript
if (wx.canIUse('button.open-type.chooseAvatar')) {
  // 使用头像昵称填写能力
} else {
  // 降级：自定义上传头像 + 普通昵称输入
}
```

误区提醒：

- 「开发者工具里 getUserProfile 能返回信息，就继续用」——工具表现与真机/线上规则可能不同，以现行公告与真机为准。
- 「旧公告生效期前的版本不受影响，所以永远不改」——存量版本是过渡豁免，新发布版本必须合规，越拖迁移成本越高。

### 15. 首次进入自动登录时序、常见误区与安全清单

#### 15.1 推荐的启动时序

```text
App onLaunch
  ├── 初始化云开发 wx.cloud.init
  ├── 非阻塞地触发 ensureLogin()（带异常捕获与超时）
  └── 首屏尽快渲染（首页浏览不强依赖登录结果）
页面需要身份时
  ├── ensureLogin() 拿会话（共享同一登录承诺）
  ├── 资料不完整 → 引导 profile-edit
  └── 接口返回 401 → handleUnauthorized 重登后重试一次
```

这样「逛吃指南」既能在用户无感时完成自动登录，又不会因为登录服务抖动而白屏。

#### 15.2 功能正确性误区汇总

1. 用前端传的 openid/userId 确定身份；
2. 把 code 当身份、把临时头像路径当永久地址；
3. getUserInfo/getUserProfile 仍幻想能拿真实资料；
4. 多个页面各自登录，产生竞态与重复会话；
5. 登录态只在内存、或只靠客户端过期时间；
6. 用户拒绝手机号/资料就无法继续使用本可公开浏览的功能。

#### 15.3 安全红线（再次强调）

- **身份不可前端伪造**：openid 由 code2session/getWXContext 从平台取得；
- **密钥不下发**：AppSecret、session_key、token 签名密钥只在服务端/云函数；
- **登录态可管控**：服务端设有效期、可刷新、可作废，401 即重登；
- **敏感资料最小化**：手机号/头像/昵称由用户主动授权或填写，用途写入隐私指引，展示注意脱敏；
- **越权全在云端拦**：隐藏按钮只是体验，安全规则与云函数归属校验才是防线。

## 实践练习题

### 练习 1：静默登录与登录承诺复用

#### 任务

实现 `services/session.ts`（会话缓存读写）与 `services/auth.ts`（`ensureLogin`/`handleUnauthorized`），在 App 启动时非阻塞触发登录，两个页面同时调用 `ensureLogin` 时只发生一次登录；登录成功后能拿到 token 与资料完整度。

参考代码：

```typescript
let inFlight: Promise<AuthSession> | null = null

export function ensureLogin(): Promise<AuthSession> {
  const cached = readSession()
  if (cached) return Promise.resolve(cached)
  if (inFlight) return inFlight
  inFlight = doLogin().finally(() => { inFlight = null })
  return inFlight
}
```

#### 步骤约束

1. `login` 云函数用 `getWXContext` 取 openid 并 upsert 用户，禁止前端传 openid。
2. token 用 `crypto.randomBytes(32)` 生成，会话记录含过期时间，TTL 设 7 天。
3. 必须验证「并发调用共享同一登录承诺」（在两个 onLoad 中同时调用并打日志）。
4. 模拟一次 401（可手动让服务端判 token 失效），验证清除会话并重新登录。

#### 提交物

- `services/session.ts`、`services/auth.ts`、`login` 云函数源码；
- 首次静默登录与并发只登录一次的日志截图；
- 401 后自动重登的录屏。

#### 验收标准

- 首次进入无弹窗即建立会话，重进后会话仍有效；
- 并发调用时 `wx.login`/云函数只执行一次；
- 会话过期/失效后可自动恢复，无未处理异常；
- 前端代码与缓存中不出现 AppSecret/session_key。

## 阶段验收作业

本作业是阶段二里程碑「登录鉴权与用户体系」的综合证据点，重点证明**你能让用户无感知地获得由平台背书、不可伪造的身份，可靠维护登录态，并在当前合规框架下完成头像、昵称、手机号的收集与降级**。

### 任务描述

在「逛吃指南」中交付完整的登录与用户体系：

1. 交付登录层：`services/session.ts` + `services/auth.ts`，实现首次进入静默登录、登录承诺复用、会话缓存与 401 自动重登；`login` 云函数用 `getWXContext` 取身份、upsert 用户并签发 token。

5. 编写不超过 300 字说明：静默登录与自定义登录态如何配合、密钥与身份的信任边界、合规收集与降级策略。

### 完成标准

- 真机上首次进入自动静默登录，全程无多余授权弹窗；杀掉重进后登录态有效，过期可自动恢复；
- 用户身份全部来自 `getWXContext`/平台验证，任何前端传入的身份字段都不被采信；
- users 集合建档与资料更新正确，头像为 fileID、昵称过审核、手机号已验证且脱敏展示；
