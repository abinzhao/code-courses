# 12-本地存储与全局状态

## 目标

完成本知识单元后，学员应能把「数据存在哪、活多久、怎么在页面之间同步」讲清楚，并为「逛吃指南」实现收藏、浏览历史、发布草稿的本地持久化，而不是把所有数据都堆在 `globalData` 或每次进页面都重新请求。

学员应能够：

1. 说清小程序本地存储的定位：由微信客户端持久化、按小程序与用户隔离、重启不丢，但可能被用户或系统清理。
2. 区分异步 `wx.setStorage` / `wx.getStorage` 与同步 `setStorageSync` / `getStorageSync`，能根据调用时机（启动期、事件回调、生命周期）选择正确版本并处理失败。
3. 使用 `wx.getStorageInfo` / `getStorageInfoSync` 获取 `keys`、`currentSize`、`limitSize`，记住单个 key 与总容量上限，并在写满时做异常处理与降级。
4. 封装一个带命名空间与过期时间（TTL）的缓存工具，支持安全读取、默认值与 JSON 结构存储。
5. 说清常见读写策略：读缓存/回源的 cache-aside、写穿 write-through、只接受可序列化数据，以及容量治理（上限、裁剪、清理）。
6. 使用 `App` 的 `globalData` 存放应用级状态，理解它“活在内存、重启即失”，与本地存储互补而非互相替代。
7. 实现一个事件总线（订阅/发布），完成跨页面、跨组件的解耦通信，并在页面卸载时取消订阅避免泄漏。
8. 使用 `EventChannel` 在 `navigateTo` 的两个页面之间建立双向通道，并与 URL query、页面栈 `getCurrentNodes`/`getCurrentPages` 传参做对比选型。
9. 掌握跨页数据同步与刷新时机：`onShow`、事件回调、EventChannel 返回、发布订阅，分别适合什么场景。
10. 在「逛吃指南」中落地收藏、浏览历史、发布草稿三类本地持久化功能，保证多入口数据一致、容量可控、异常可降级。

本单元承接 U11 的组件化升级，为 U13 之后的网络层与云开发提供“离线优先”的数据底座。

## 技术栈

本单元不依赖后端，使用微信基础库内置存储 API 与 TypeScript 实现。

| 工具或环境 | 用途 | 学习要求 |
|---|---|---|
| wx.setStorage / getStorage 系列 | 异步读写本地缓存 | 掌握 success/fail/complete 与 Promise 化 |
| wx.setStorageSync 等同步 API | 启动期/关键路径同步读写 | 会 try/catch，知道阻塞特性 |
| wx.getStorageInfo(Sync) | 查询容量与 key 列表 | 理解 currentSize/limitSize |
| App({ globalData }) | 应用级内存状态 | 会用 getApp 读取与更新 |
| EventChannel | navigateTo 双向通信 | 会 emit/on 与 getOpenerEventChannel |
| getCurrentPages | 页面栈访问与回传 | 会取上一页实例调用方法 |
| TypeScript | 编写类型化工具与模块 | 通过 tsc，不用 any 掩盖结构 |

容量与持久化约定：

- 单个 key 数据上限约 1 MB，所有小程序本地存储总量上限约 10 MB；超出时写入会失败并进入 fail/抛异常。
- 存储按“小程序 + 微信账号”隔离，不同小程序互不可见；卸载微信、清理缓存、存储回收都可能导致数据丢失。
- 本单元所有容量数字以官方文档为准；编码时必须对“写失败/读不到”做防御。

## 详细的理论知识讲解和示例伪代码

### 1. 本地存储是什么：定位、存放位置与隔离性

小程序的**本地存储**是微信客户端提供的、在逻辑层通过 `wx.*Storage*` API 使用的持久化能力。可以把它类比成浏览器的 `localStorage`，但实现与边界由微信客户端掌控，逻辑层拿不到文件路径，也不能直接读写磁盘文件。

四条基本性质：

1. **持久化**：数据写入后，关闭页面、退出小程序甚至重启微信仍然存在，下次启动可读。
2. **隔离性**：数据按“小程序 AppId + 当前微信账号”隔离，A 小程序读不到 B 小程序的数据；同一手机切换微信账号后数据视图不同。
3. **可被清理**：用户在微信中清理缓存、卸载微信、系统存储紧张时的回收，都可能使数据消失；因此本地缓存是“可重建的副本”，不是唯一真值。
4. **有容量上限**：不是无限硬盘，写满会报错。

它与三类相邻概念的区别：

| 概念 | 存放位置 | 生命周期 | 典型用途 |
|---|---|---|---|
| 页面 data | 逻辑层内存 | 页面实例期间 | 驱动渲染 |
| globalData | 逻辑层内存（App 实例） | 本次小程序运行期间 | 运行期共享状态 |
| 本地 Storage | 微信客户端持久化 | 跨启动，可能被清理 | 收藏、历史、草稿、配置 |

核心结论：

> 内存里的东西（data/globalData）重启就没；Storage 能跨重启，但不保证永久。重要数据要“本地一份 + 服务端一份”，本地只做加速与离线兜底。

误区提醒：

- “Storage 等于数据库”——错误。它没有查询、事务、多表关联，且会被清理，不能承载唯一业务真值。
- “Storage 里的数据逻辑层和渲染层共享”——错误。Storage 在逻辑层被读写，渲染层要用其中的数据，仍然要经 `setData` 跨线程传递。

### 2. 异步读写：wx.setStorage / getStorage

异步接口不会阻塞当前 JS 执行，结果通过回调（success/fail/complete）或 Promise 返回。

**写入：**

```typescript
wx.setStorage({
  key: 'gc_launch_count',
  data: 3,
  success() {
    console.log('写入成功')
  },
  fail(err) {
    console.error('写入失败', err.errMsg)
  },
})
```

**读取：**

```typescript
wx.getStorage({
  key: 'gc_launch_count',
  success(res) {
    console.log('读到：', res.data)
  },
  fail(err) {
    // key 不存在等情况会走 fail
    console.warn('读取失败', err.errMsg)
  },
})
```

现代基础库支持 Promise 化调用（不传 success/fail 时返回 Promise）：

```typescript
async function readLaunchCount(): Promise<number> {
  try {
    const res = await wx.getStorage({ key: 'gc_launch_count' })
    return (res.data as number) ?? 0
  } catch {
    return 0
  }
}

async function writeLaunchCount(n: number): Promise<void> {
  try {
    await wx.setStorage({ key: 'gc_launch_count', data: n })
  } catch (err) {
    console.warn('写入失败，降级为内存计数', err)
  }
}
```

异步 API 适合的场景：

- 数据较大，不想阻塞逻辑；
- 页面运行期响应用户操作时的读写；
- 需要并发发起多个独立存储操作（配合 `Promise.all`）。

但要注意时序：`setStorage` 的 success 表示“客户端已完成落盘”，而 `setData` 的 callback 表示“渲染层已更新”，二者是不同通道，不要混淆。

误区提醒：

- 异步写入后立刻用同步/异步读取，在极端时序下并非你想要的“同一段顺序代码”语义；关键链路要在 success/await 之后再进行下一步。
- 不要忽略 fail：key 不存在、容量超限都会触发它。

### 3. 同步版本：setStorageSync 等与异常处理

同步 API 命名以 `Sync` 结尾，调用后立即返回结果；但出错时会**抛异常**，必须用 `try/catch` 包裹。

```typescript
// 写入
try {
  wx.setStorageSync('gc_draft', { title: '老字号探店', content: '...' })
} catch (err) {
  console.error('草稿保存失败', err)
  wx.showToast({ title: '草稿保存失败', icon: 'none' })
}

// 读取（key 不存在时 getStorageSync 返回 ''）
function readDraft(): Draft | null {
  try {
    const value = wx.getStorageSync('gc_draft')
    return value ? (value as Draft) : null
  } catch (err) {
    console.warn('草稿读取失败', err)
    return null
  }
}

interface Draft {
  title: string
  content: string
  updatedAt: number
}
```

同步系列完整清单：

| 同步 API | 作用 | key 不存在时 |
|---|---|---|
| `wx.setStorageSync(key, data)` | 写入（覆盖） | —— |
| `wx.getStorageSync(key)` | 读取 | 返回空字符串 `''` |
| `wx.removeStorageSync(key)` | 删除单个 key | 不报错 |
| `wx.clearStorageSync()` | 清空全部 | —— |
| `wx.getStorageInfoSync()` | 获取容量信息 | —— |

什么时候用同步：

1. **应用启动早期**（`onLaunch` / `onLoad`）：需要先拿到配置再决定渲染，代码顺序直观。
2. **短小、高频、必须立刻生效**的数据：如收藏 id、开关项。
3. **不适合用同步的场景**：大数据块（序列化/落盘会占用 JS 执行时间）、可延迟处理的非关键写入——这些应交给异步 API。

误区提醒：

- 同步不是“更快”，而是“阻塞当前逻辑直到完成”。在大对象上滥用 Sync 会让交互卡顿。
- `getStorageSync` 读不到返回 `''`，直接当对象用会出错，读取后要判空再转换类型。

### 4. 删除、清空与 StorageInfo：容量上限

**删除单个 key：**

```typescript
wx.removeStorage({
  key: 'gc_draft',
  success() {
    console.log('已删除草稿')
  },
})
// 或同步
wx.removeStorageSync('gc_draft')
```

**清空全部（谨慎）：**

```typescript
wx.clearStorageSync() // 会清掉本小程序所有 key，包括非本模块的数据
```

工程上几乎不应该无脑 `clearStorage`——它会波及其他模块。更安全的做法是“按命名空间删除本模块的 key”（第 6 节）。

**查询容量信息：**

```typescript
const info: wx.getStorageInfo.SuccessCallbackResult = wx.getStorageInfoSync()
console.log('所有 key：', info.keys)
console.log('当前占用（KB）：', info.currentSize)
console.log('上限（KB）：', info.limitSize)
```

容量事实：

- 单个 key 数据大小上限约 1 MB；
- 总容量上限约 10 MB（`limitSize` 通常为 10240 KB）；
- 超限时写入失败，异步走 fail、同步抛异常。

写满时的降级处理：

```typescript
function safeSet(key: string, data: unknown): boolean {
  try {
    wx.setStorageSync(key, data)
    return true
  } catch (err) {
    // 先清理可重建的缓存（浏览历史等），再重试一次
    console.warn('写入失败，尝试清理后重试', err)
    try {
      trimHistory(20) // 裁剪历史，见第 14 节
      wx.setStorageSync(key, data)
      return true
    } catch (e2) {
      console.error('重试仍失败', e2)
      return false
    }
  }
}
```

误区提醒：

- `currentSize` 是估算占用，精确字节感受序列化方式影响，不要拿它当严格账本。
- 发现超限不要立刻 `clearStorageSync()`，应清理“可再生”数据（历史、临时缓存），保留用户资产（收藏、草稿）。

### 5. 数据类型、序列化与常见限制

Storage 只接受可以序列化的数据：字符串、数字、布尔值、普通对象、数组；较新版本也支持 `ArrayBuffer`。**函数、`undefined`、包含循环引用的对象、DOM 节点等不能存储。**

```typescript
// 合法
wx.setStorageSync('k1', '文本')
wx.setStorageSync('k2', 123)
wx.setStorageSync('k3', { a: 1, b: [true, false] })

// 非法/无意义
// wx.setStorageSync('k4', function () {})        // 函数不会被保存
// wx.setStorageSync('k5', { node: document.xx }) // 小程序逻辑层本就没有 document/DOM
```

因为逻辑层没有 DOM，也不存在“把节点对象存起来”的用法；所有要持久化的内容都应是纯数据。

实践建议：

- 统一存“带版本号的对象信封”，便于将来结构升级：

```typescript
interface StorageEnvelope<T> {
  v: number // 数据结构版本
  t: number // 写入时间戳
  d: T // 真实数据
}
```

- 读取时做结构校验，防止历史脏数据导致页面白屏；
- 时间统一用时间戳（number），不要存 `Date` 对象实例。

误区提醒：

- 存入对象后，再修改内存中的对象不会自动更新 Storage，必须重新调用写入。
- 不要假设“写进去什么类型，读出来一定还是什么类型”，被清理、旧版本数据都可能让读取结果异常。

### 6. 封装缓存工具（上）：命名空间

直接到处写字符串 key 有三个问题：容易撞名、难以批量清理、无法统一加过期逻辑。第一步是引入**命名空间**：所有业务 key 自动加统一前缀，并集中管理。

```typescript
// utils/storage.ts

const NAMESPACE = 'gc' // 逛吃指南 GuangChi

function buildKey(key: string): string {
  return `${NAMESPACE}_${key}`
}

export function set<T>(key: string, data: T): boolean {
  try {
    wx.setStorageSync(buildKey(key), data)
    return true
  } catch (err) {
    console.warn(`[storage] set 失败: ${key}`, err)
    return false
  }
}

export function get<T>(key: string, fallback: T): T {
  try {
    const value = wx.getStorageSync(buildKey(key))
    if (value === '' || value === null || value === undefined) return fallback
    return value as T
  } catch (err) {
    console.warn(`[storage] get 失败: ${key}`, err)
    return fallback
  }
}

export function remove(key: string): void {
  try {
    wx.removeStorageSync(buildKey(key))
  } catch (err) {
    console.warn(`[storage] remove 失败: ${key}`, err)
  }
}

/** 只清理本命名空间下的 key，避免误伤其他模块 */
export function clearNamespace(): void {
  try {
    const info = wx.getStorageInfoSync()
    info.keys.forEach((k) => {
      if (k.startsWith(`${NAMESPACE}_`)) wx.removeStorageSync(k)
    })
  } catch (err) {
    console.warn('[storage] clearNamespace 失败', err)
  }
}
```

使用时不再散落裸字符串：

```typescript
import { set, get } from '../../utils/storage'

set('fav_ids', ['shop_1', 'shop_2'])
const ids = get<string[]>('fav_ids', [])
```

要点：

1. 命名空间让“清空本模块数据”变成精确操作，不需要 `clearStorage` 横扫一切。
2. `get` 强制传 `fallback`，从 API 层面消灭“读到空字符串当数组用”的错误。
3. 所有异常在工具内统一收敛，业务层拿到的是布尔成功标志与带类型的数据。

### 7. 封装缓存工具（下）：过期时间与安全读

第二步，在命名空间基础上加 **TTL（过期时间）** 与信封结构。适合存“短时效数据”：接口响应快照、临时令牌副本（注意真正的密钥不能放前端）、活动配置等。

```typescript
// utils/cache.ts
import { set as rawSet, get as rawGet } from './storage'

interface Envelope<T> {
  v: number
  t: number // 写入时间（ms）
  expire: number // 过期时长（ms），0 表示永不过期
  d: T
}

/** 写入带过期时间的缓存；expireMs 不传或为 0 表示永久 */
export function setCache<T>(key: string, data: T, expireMs = 0): boolean {
  const envelope: Envelope<T> = {
    v: 1,
    t: Date.now(),
    expire: expireMs,
    d: data,
  }
  return rawSet(`cache_${key}`, envelope)
}

/** 读取；已过期则删除并返回 fallback */
export function getCache<T>(key: string, fallback: T): T {
  const envelope = rawGet<Envelope<T> | null>(`cache_${key}`, null)
  if (!envelope) return fallback

  const expired = envelope.expire > 0 && Date.now() - envelope.t > envelope.expire
  if (expired) {
    wx.removeStorageSync(`gc_cache_${key}`)
    return fallback
  }
  return envelope.d
}

/** 异步刷新缓存：先给旧数据，再回源更新（stale-while-revalidate 思路） */
export async function withCache<T>(
  key: string,
  expireMs: number,
  loader: () => Promise<T>,
): Promise<{ data: T; fromCache: boolean }> {
  const cached = getCache<T | null>(key, null)
  if (cached !== null) {
    // 后台刷新，不阻塞当前使用
    loader()
      .then((fresh) => setCache(key, fresh, expireMs))
      .catch((err) => console.warn('后台刷新失败', err))
    return { data: cached, fromCache: true }
  }

  const fresh = await loader()
  setCache(key, fresh, expireMs)
  return { data: fresh, fromCache: false }
}
```

过期策略要与数据性质匹配：

- 用户资产（收藏、草稿）：**不设过期**，只能由用户或明确操作删除；
- 接口快照（店铺列表、详情）：设置几分钟到几小时的过期，作为离线/加速兜底；
- 临时态（一次性引导标记）：可短 TTL，或用完即删。

误区提醒：

- 时间判断依赖本机时钟，用户改系统时间可能影响 TTL；对强时效数据应以后端时间为准。
- 过期删除依赖“下一次读取”触发，长期不读的过期数据仍占空间，容量治理时要主动扫描清理。

### 8. 读写策略：cache-aside、写穿与容量治理

把存储 API 升级为“数据层”时，有几种经典策略。

**Cache-Aside（旁路缓存，读多写少最常见）**：

```text
读取：
  先查本地缓存
  命中 -> 直接返回
  未命中 -> 请求服务端 -> 成功后写入缓存 -> 返回
写入：
  先改服务端 -> 成功后更新/失效本地缓存
```

```typescript
async function getShopDetail(id: string): Promise<Shop> {
  const cached = getCache<Shop | null>(`shop_${id}`, null)
  if (cached) return cached

  const shop = await fetchShopFromServer(id) // U13/U29 的网络层
  setCache(`shop_${id}`, shop, 30 * 60 * 1000) // 30 分钟
  return shop
}
```

**Write-Through（写穿，关键状态保证本地与来源一致）**：

```typescript
function toggleFavorite(shopId: string, next: boolean): void {
  // 本地立即更新，保证界面即时响应（乐观更新）
  const ids = get<string[]>('fav_ids', [])
  const nextIds = next
    ? Array.from(new Set([...ids, shopId]))
    : ids.filter((id) => id !== shopId)
  const ok = set('fav_ids', nextIds)

  if (!ok) {
    wx.showToast({ title: '本地写入失败', icon: 'none' })
    return
  }

  // 再同步到服务端；失败时要有回滚/重试（U29 展开）
  syncFavoriteToServer(shopId, next).catch((err) => {
    console.warn('服务端同步失败，待重试', err)
  })
}
```

**容量治理三板斧**：

1. **限量**：数组类数据（历史、草稿箱）维护最大条数，超出裁剪最旧项。
2. **分层**：可再生数据（快照、历史）与用户资产（收藏、草稿）分开存储，超容量时只牺牲前者。
3. **巡检**：在合适时机（如启动、进入“我的”页）读取 `getStorageInfo`，超阈值时清理过期与旧数据。

误区提醒：

- 不要把本地缓存当作“写了就一定在”的真值来设计业务流程。
- 乐观更新必须配套失败回滚，否则断网时界面与服务端长期不一致。

### 9. globalData：应用级全局状态

`globalData` 挂在 `App` 实例上，是**本次运行期间**所有页面共享的内存状态。

```typescript
// app.ts
interface IGlobalData {
  systemInfo: wx.WindowInfo | null
  city: string
  loggedIn: boolean
  unreadCount: number
}

App<{
  globalData: IGlobalData
  onLaunch: () => void
}>({
```

globalData 与 Storage 的分工：

| 需求 | 选择 |
|---|---|
| 当前定位城市、登录态（本次运行） | globalData |
| 窗口尺寸等启动即得、反复读取 | globalData |
| 收藏、历史、草稿（重启仍要在） | Storage |
| 用户上次选择的城市（跨启动恢复） | Storage，启动时读出灌入 globalData |

常见组合拳：**启动时从 Storage 恢复偏好到 globalData，运行期读写 globalData，关键变更再落盘 Storage。**

误区提醒：

- globalData 不是响应式的，直接改它不会自动刷新任何界面；页面要刷新仍需 `setData`。
- 不要把大列表、缓存副本全塞 globalData，它只放“高频共享、体积可控”的运行期状态。

### 10. 事件总线：订阅/发布做跨页通信

当多个页面/组件需要互通、又不想彼此持有引用时，可以实现一个极简**事件总线（Event Bus）**。

```typescript
// utils/event-bus.ts
type Handler<T = unknown> = (payload: T) => void

class EventBus {
  private channels = new Map<string, Set<Handler>>()

  /** 订阅事件，返回取消订阅函数 */
  on<T>(event: string, handler: Handler<T>): () => void {
    if (!this.channels.has(event)) this.channels.set(event, new Set())
    this.channels.get(event)!.add(handler as Handler)
    return () => this.off(event, handler)
  }

  /** 订阅一次 */
  once<T>(event: string, handler: Handler<T>): () => void {
    const wrap: Handler<T> = (payload) => {
      this.off(event, wrap)
      handler(payload)
    }
    return this.on(event, wrap)
  }

  /** 发布事件 */
  emit<T>(event: string, payload: T): void {
    this.channels.get(event)?.forEach((handler) => {
      try {
        handler(payload)
      } catch (err) {
        console.error(`[event-bus] ${event} 处理器异常`, err)
      }
    })
  }

  off<T>(event: string, handler: Handler<T>): void {
    this.channels.get(event)?.delete(handler as Handler)
  }
}

export const bus = new EventBus()

// 统一事件名，避免散落字符串
export const EVENTS = {
  FAVORITE_CHANGED: 'favorite:changed',
  DRAFT_SAVED: 'draft:saved',
  CITY_CHANGED: 'city:changed',
} as const
```

发布方（详情页改变收藏）：

```typescript
import { bus, EVENTS } from '../../utils/event-bus'

bus.emit(EVENTS.FAVORITE_CHANGED, { shopId: 'shop_1', liked: true })
```

订阅方（列表页，页面卸载必须取消订阅）：

```typescript
import { bus, EVENTS } from '../../utils/event-bus'

let unsubscribe: (() => void) | null = null

Page({
  onLoad() {
    unsubscribe = bus.on<{ shopId: string; liked: boolean }>(
      EVENTS.FAVORITE_CHANGED,
      ({ shopId, liked }) => {
        // 只更新受影响的卡片，避免整列表重渲染
        const index = this.data.shops.findIndex((s) => s.id === shopId)
        if (index >= 0) {
          this.setData({ [`shops[${index}].liked`]: liked })
        }
      },
    )
  },
  onUnload() {
    unsubscribe?.()
    unsubscribe = null
  },
})
```

要点：订阅发布是**内存通信**，只在当前运行期有效；它解决“谁也不认识谁也能通信”，不负责持久化。忘记取消订阅是最常见的内存泄漏来源——页面销毁后回调仍持有 `this`。

### 11. EventChannel：页面级双向通道

`wx.navigateTo` 支持 **EventChannel**，在打开页与被打开页之间建立一条双向通道，适合“打开一个选择器/编辑器，把结果实时或返回时带回来”的场景。

发起页 A：

```typescript
wx.navigateTo({
  url: '/pages/picker/picker',
  events: {
    // 监听被打开页 emit 过来的事件
    picked(payload: { shopId: string; name: string }) {
      console.log('已选择', payload)
    },
  },
  success(res) {
    // 页面打开成功后，可主动向被打开页发数据
    res.eventChannel.emit('init', { city: '广州' })
  },
})
```

被打开页 B：

```typescript
Page({
  onLoad() {
    const channel = this.getOpenerEventChannel()

    channel.on('init', (payload: { city: string }) => {
      console.log('发起页给的初始值', payload.city)
    })

    // 用户选择后，向发起页发事件；不需要关闭页面也能实时通信
    // channel.emit('picked', { shopId: 'shop_9', name: '阿婆牛杂' })
  },
  onConfirm() {
    const channel = this.getOpenerEventChannel()
    channel.emit('picked', { shopId: 'shop_9', name: '阿婆牛杂' })
    wx.navigateBack()
  },
})
```

EventChannel 的特点：

1. 通道是**页面级、一次性**的，绑定在这次 navigateTo 关系上，返回后关系结束。
2. 双向：两侧都能 `emit` / `on`，比 URL query 只能“带过去”更强。
3. 数据可携带较大对象，不拼在 URL 里，也不经过持久化。

它适合“编辑/选择结果回传”，但不适合长期广播——长期、多对多用事件总线，跨启动用 Storage。

### 12. URL query、EventChannel、页面栈与事件总线：四种方式对比

小程序页面间传参有四种常用手段，选型要看“方向、时机、数据大小、耦合度”。

| 方式 | 方向 | 时机 | 数据量 | 耦合度 | 典型场景 |
|---|---|---|---|---|---|
| URL query | 上一页 → 下一页 | navigateTo 时 | 小，受 URL 长度限制 | 低 | 传 id、类型 |
| EventChannel | 双向 | 打开期间/返回 | 可较大 | 中 | 选择器结果、编辑回传 |
| 页面栈 getCurrentPages | 下一页 → 上一页 | 返回前直接调用 | 任意 | 高 | 返回时刷新上一页 |
| 事件总线 | 多对多 | 运行期任意时机 | 任意 | 低（匿名） | 收藏变更广播 |

**URL query：**

```typescript
wx.navigateTo({ url: `/pages/detail/detail?id=${shopId}&from=list` })

// detail 页
Page({
  onLoad(query) {
    console.log(query.id, query.from)
  },
})
```

参数要做编码：`encodeURIComponent`，避免特殊字符破坏 URL。

**页面栈直接回传（返回前刷新上一页）：**

```typescript
// detail 页返回前
Page({
  onTapBack() {
    const pages = getCurrentPages()
    const prev = pages[pages.length - 2] as
      | { refreshFavorite?: (shopId: string, liked: boolean) => void }
      | undefined

    prev?.refreshFavorite?.('shop_1', true)
    wx.navigateBack()
  },
})
```

页面栈方式要克制：

- 依赖页面栈深度与具体页面方法，耦合最强；
- tab 切换、重定向场景下上一页未必是你预期的实例；
- 能用 EventChannel/事件总线表达的，优先用它们。

误区提醒：

- 不要试图通过全局变量给“任意页面”传参并指望对方自动刷新——内存传参必须配合显式调用或事件订阅。
- URL 上不要放敏感信息（它出现在路由记录里）；密钥、令牌不放前端，更不能拼 URL。

### 13. 跨页数据同步与刷新时机

“数据改了，别的页面什么时候刷新”是本单元的核心工程问题。几个关键时机：

1. **`onShow`：页面每次显示时刷新（最通用兜底）。**

```typescript
Page({
  onShow() {
    // 从下级页返回、从后台切回都会触发；重算收藏态/草稿数
    this.refreshFromStorage()
  },
})
```

优点是不依赖具体通信手段、最可靠；缺点是每次显示都执行，要控制成本（只读必要字段、做差异判断）。

2. **事件回调：变更发生时精准更新（最省成本）。**

   收藏变更通过事件总线广播，列表只更新对应项（路径 setData），而不是整列表刷新。

3. **EventChannel / 页面栈：返回动作绑定的一次性回传。**

   选择器选完立即通知发起页，语义最直接。

4. **启动恢复：`onLaunch`/`onLoad` 从 Storage 灌入内存。**

推荐的组合是“**事件精准刷新 + onShow 兜底**”：正常路径走事件，只更新变化项；任何漏掉的时序由 `onShow` 统一校正。

数据一致性还要注意：

- 所有写入收敛到统一模块（如 `services/favorite.ts`），不要在多个页面各自拼 key 直接写；
- 写入采用“先本地、后服务端 + 失败补偿”，保证离线可用、上线可同步；
- 刷新时以 Storage/服务端为准，避免用页面内存旧值覆盖新状态。

#### 14.1 收藏模块

```typescript
// services/favorite.ts
import { get, set } from '../utils/storage'
import { bus, EVENTS } from '../utils/event-bus'

const KEY = 'fav_ids'

export function isFavorite(shopId: string): boolean {
  return get<string[]>(KEY, []).includes(shopId)
}

export function listFavoriteIds(): string[] {
  return get<string[]>(KEY, [])
}

export function setFavorite(shopId: string, liked: boolean): void {
  const ids = listFavoriteIds()
  const nextIds = liked
    ? Array.from(new Set([...ids, shopId]))
    : ids.filter((id) => id !== shopId)

  if (!set(KEY, nextIds)) {
    wx.showToast({ title: '操作失败，请重试', icon: 'none' })
    return
  }

  bus.emit(EVENTS.FAVORITE_CHANGED, { shopId, liked })

  // 服务端同步失败的补偿逻辑在 U29 展开
  // syncToServer(shopId, liked).catch(...)
}

export function toggleFavorite(shopId: string): boolean {
  const next = !isFavorite(shopId)
  setFavorite(shopId, next)
  return next
}
```

#### 14.2 浏览历史模块（限量 + 去重 + 置顶）

```typescript
// services/history.ts
import { get, set } from '../utils/storage'

const KEY = 'history'
const MAX_HISTORY = 50

export interface HistoryItem {
  id: string
  name: string
  cover: string
  visitedAt: number
}

export function listHistory(): HistoryItem[] {
  return get<HistoryItem[]>(KEY, [])
}

export function addHistory(shop: Omit<HistoryItem, 'visitedAt'>): void {
  const list = listHistory().filter((item) => item.id !== shop.id)
  const next = [{ ...shop, visitedAt: Date.now() }, ...list].slice(0, MAX_HISTORY)

  if (!set(KEY, next)) {
    // 容量不足时退化为只保留更少条数再试
    set(KEY, next.slice(0, 20))
  }
}

export function clearHistory(): void {
  set(KEY, [])
}

export function removeHistory(id: string): void {
  set(KEY, listHistory().filter((item) => item.id !== id))
}
```

#### 14.3 发布草稿模块（单篇/草稿箱两种形态）

```typescript
// services/draft.ts
import { get, set } from '../utils/storage'

const SINGLE_KEY = 'draft_current'
const BOX_KEY = 'draft_box'
const MAX_BOX = 10

export interface Draft {
  id: string
  title: string
  content: string
  images: string[]
  updatedAt: number
}

/** 自动保存当前正在编辑的草稿（防抖应由编辑页配合） */
export function saveCurrentDraft(draft: Omit<Draft, 'updatedAt'>): boolean {
  const full: Draft = { ...draft, updatedAt: Date.now() }
  const ok = set(SINGLE_KEY, full)
  if (ok) wx.showToast({ title: '草稿已保存', icon: 'success' })
  return ok
}

export function loadCurrentDraft(): Draft | null {
  return get<Draft | null>(SINGLE_KEY, null)
}

export function clearCurrentDraft(): void {
  set(SINGLE_KEY, null)
}

/** 存入草稿箱（用户主动“存草稿并退出”） */
export function addToBox(draft: Omit<Draft, 'updatedAt'>): boolean {
  const box = get<Draft[]>(BOX_KEY, [])
  const full: Draft = { ...draft, updatedAt: Date.now() }
  const next = [full, ...box.filter((d) => d.id !== draft.id)].slice(0, MAX_BOX)
  return set(BOX_KEY, next)
}

export function listBox(): Draft[] {
  return get<Draft[]>(BOX_KEY, [])
}
```

### 15. 常见误区、安全与容量清单

**功能误区：**

1. 把 Storage 当唯一真值，不做服务端备份；
2. 直接修改已缓存对象，期望 Storage 自动更新；
3. 用 `clearStorage` 清理本模块，误伤其他数据；
4. 把短时效状态永久化，或把用户资产设成过期；
5. 在大对象上滥用 Sync 阻塞交互；
6. 订阅事件后不在 `onUnload` 取消，造成泄漏；
7. 改 globalData 后期待界面自动更新（它非响应式）；
8. 通过页面栈深度硬编码上一页，忽略 tab/重定向场景。

**安全底线：**

- **密钥（AppSecret、私钥、第三方密钥）绝不放前端**：小程序代码包可被提取，写进 Storage、globalData 或源码都等于公开。需要签名的操作应由服务端完成。
- Storage 不加密，用户态信息（手机号、身份证等）尽量不本地留存；确需缓存要最小化并能被用户清除。
- URL query 与页面记录不适合放敏感参数。

**上线前容量自查清单：**

1. 是否所有数组类数据都有最大条数；
2. 是否对写入失败、读取为空都有降级；
3. 是否存在“可再生数据与用户资产混存”；
4. 是否能在不 `clearStorage` 的情况下精确清理本模块；
5. 是否在启动/“我的”页做过容量巡检与过期清理。
