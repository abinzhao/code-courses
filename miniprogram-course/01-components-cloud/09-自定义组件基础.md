# 09-自定义组件基础

## 目标

完成本知识单元后，学员应能把页面中重复出现、职责内聚的界面块抽成**自定义组件**，并用「properties 向下、triggerEvent 向上」的标准方式与页面通信，而不是把所有 WXML 和逻辑都堆在一个页面里。

学员应能够：

1. 说清为什么要组件化：复用、职责分离、可维护性与协作边界，以及「逛吃指南」中哪些界面块适合抽组件。
2. 掌握自定义组件的**四件套**：`.wxml`、`.wxss`、`.ts`、`.json`，并在 json 中声明 `"component": true`。
3. 熟练使用 `Component({})` 构造器，组织 `properties`、`data`、`methods`、`lifetimes`、`pageLifetimes` 等字段。
4. 正确定义 `properties`：`type`、`value` 默认值、`observer` 观察者，以及用 `optionalTypes` 接受多种类型。
5. 区分 `properties` 与 `data` 的职责，理解两者最终都会挂载到 `this.data` 上，但来源和修改方式不同。
6. 在 `methods` 中编写事件处理函数，通过 `this.setData` 更新组件自身状态，并理解其跨线程异步语义。
7. 说清组件生命周期 `created / attached / ready / moved / detached` 的触发时机、可执行操作与典型用途。
8. 使用 `pageLifetimes` 让组件感知所在页面的 `show / hide / resize`，例如页面隐藏时暂停组件内计时。
9. 完成父子组件通信：**properties 单向向下**传入数据，**this.triggerEvent 向上**抛出事件，由页面 `bind:事件名` 接收。
10. 在页面 json 或 `app.json` 中用 `usingComponents` 注册组件，区分组件与页面的差异，并把主线项目的**笔记卡片**与**搜索栏**抽成可复用组件。

本单元承接 U04 页面生命周期与 U08 事件系统；U10 将进一步学习 behaviors、observers、relations 与样式隔离等进阶能力。

## 技术栈

本单元不引入后端与第三方依赖，在已有的 TypeScript 原生小程序项目中新增 `components/` 目录即可。

| 工具或 API | 用途 | 学习要求 |
|---|---|---|
| `Component({})` 构造器 | 定义自定义组件 | 能组织 properties/data/methods/lifetimes |
| 组件 `.json`（`component: true`） | 声明组件文件 | 理解组件 json 与页面 json 的区别 |
| `properties` | 接收外部传入数据 | 会写 type/value/observer/optionalTypes |
| `data` + `this.setData` | 组件内部状态 | 理解跨线程异步、不可直接赋值 |
| `methods` | 组件方法与事件处理 | 会绑定 WXML 事件并处理 |
| `lifetimes` | 组件生命周期 | 掌握 created/attached/ready/moved/detached |
| `pageLifetimes` | 页面状态感知 | 会用 show/hide/resize |
| `this.triggerEvent` | 子 → 父 通信 | 会携带 detail 与事件选项 |
| `usingComponents` | 注册组件 | 会在页面 json / app.json 注册 |
| `this.selectComponent` | 获取子组件实例 | 能在确有必要时调用子组件方法 |
| 微信开发者工具 | 调试组件 | 会看 AppData、组件树与事件日志 |

实验约定：

- 组件统一放在项目根目录 `components/` 下，每个组件一个目录、四件套同名。
- 先在独立演示页跑通最小组件，再回首页/探索页替换原有重复代码，不在原页面里「边抽边改到一半」。
- 生命周期一律先打日志观察真实顺序，结论以实际运行为准；字段细节以官方文档为准。

## 详细的理论知识讲解和示例伪代码

### 1. 为什么需要自定义组件

#### 1.1 是什么

自定义组件是开发者用 `Component` 构造器自己定义的、可在多个页面中重复使用的独立单元，由结构（WXML）、样式（WXSS）、逻辑（JS/TS）和配置（JSON）四部分组成。它和 `view`、`text` 这些内置组件用法一致：先注册，再以标签形式写进 WXML。

#### 1.2 与小程序开发的关系

随着页面增多，「逛吃指南」首页、探索页、详情页甚至搜索结果页都会出现**同一款探店笔记卡片**；搜索栏也会出现在首页、探索页。如果每个页面都复制一份卡片代码：

- 改一次评分样式，要在四五个文件里同步修改，极易漏改；
- 单页面 WXML 越来越长，结构难以阅读；
- 点赞、跳转等逻辑被复制多份，行为不一致的风险高。

把内聚的界面块抽成组件后，组件内部只关心「如何展示一次笔记」，页面只关心「有哪些笔记、点了之后干什么」，职责清晰、一处修改处处生效。

#### 1.3 一个可运行的最小示例

目录结构：

```text
components/
  hello-box/
    hello-box.wxml
    hello-box.wxss
    hello-box.ts
    hello-box.json
```

hello-box.json：

```json
{
  "component": true,
  "usingComponents": {}
}
```

hello-box.wxml：

```xml
<view class="hello-box">你好，{{name}}！</view>
```

hello-box.ts：

```typescript
Component({
  properties: {
    name: {
      type: String,
      value: '吃货'
    }
  }
})
```

页面 json 注册后即可使用（注册方式见第 11 节）：

```xml
<hello-box name="阿团" />
```

#### 1.4 常见误区

- 把只使用一次的巨型结构也硬拆成一堆组件，导致层级过深、props 透传繁琐。组件化的前提是**复用或职责内聚**，不是拆得越碎越好。
- 抽组件时只搬 WXML 不搬样式与逻辑，留下大量依赖父级 class 和全局变量的「半残组件」，换个页面就跑不起来。

### 2. 组件四件套与目录规范

#### 2.1 是什么

一个自定义组件由四个同名文件组成：

| 文件 | 职责 |
|---|---|
| `.wxml` | 组件结构模板，支持数据绑定、列表渲染、插槽（U10） |
| `.wxss` | 组件样式，默认只作用于当前组件（样式隔离 U10 详解） |
| `.ts` / `.js` | 用 `Component({})` 定义组件逻辑 |
| `.json` | 必须有 `"component": true`，声明这是组件而非页面 |

#### 2.2 与小程序开发的关系

组件的 json 与页面 json 职责不同：组件 json 不写 `navigationBarTitleText` 这类页面配置，只声明组件自身选项（如 `component`、`styleIsolation`、`multipleSlots`、`usingComponents`）。组件内部还可以继续引用其他组件，形成组件树。

推荐目录组织：

```text
miniprogram/
  components/
    note-card/
      note-card.wxml
      note-card.wxss
      note-card.ts
      note-card.json
    search-bar/
    empty-state/
  pages/
    index/
    explore/
```

#### 2.3 可运行示例：组件内再引用组件

note-card.json 中声明自己依赖一个评分组件：

```json
{
  "component": true,
  "usingComponents": {
    "rater": "/components/rater/rater"
  }
}
```

note-card.wxml 中可以直接使用：

```xml
<rater score="{{note.rating}}" />
```

#### 2.4 常见误区

- 忘记 `"component": true`，框架把它当普通文件处理，组件标签不生效。
- 四个文件不同名或大小写写错（如 `NoteCard` 与 `note-card` 混用），在真机上路径匹配失败。
- 把组件文件放进 `pages/` 目录并注册到 `app.json` 的 `pages` 中——组件不是页面，不能作为路由目标。

### 3. Component 构造器总览

#### 3.1 是什么

`Component(options)` 是注册组件的全局构造器，常用字段：

| 字段 | 作用 |
|---|---|
| `properties` | 组件的对外属性，由外部传入 |
| `data` | 组件内部状态 |
| `methods` | 组件方法，含事件处理函数 |
| `lifetimes` | 组件自身生命周期 |
| `pageLifetimes` | 组件所在页面的生命周期 |
| `options` | 样式隔离、多插槽等选项（U10） |
| `behaviors` | 混入复用（U10） |
| `observers` / `relations` | 字段监听与关联组件（U10） |

#### 3.2 与小程序开发的关系

`Component` 与 `Page` 是两套构造器：页面用 `Page`，可复用单元用 `Component`。一个组件实例由框架创建并管理，其内部更新同样走 `setData` 跨线程通信链路，因此 U02 的性能结论在组件中完全适用。

#### 3.3 可运行示例：完整骨架

```typescript
// components/note-card/note-card.ts
type Note = {
  id: string
  title: string
  shop: string
  cover: string
  rating: number
  tags: string[]
  liked: boolean
}

Component({
  properties: {
    note: {
      type: Object,
      value: {} as Note
    }
  },
  data: {
    animating: false
  },
  lifetimes: {
    attached() {
      console.log('[note-card] attached', this.data.note.id)
    }
  },
  pageLifetimes: {
    hide() {
      console.log('[note-card] 所在页面被隐藏')
    }
  },
  methods: {
    onLike() {
      this.setData({ animating: true })
    }
  }
})
```

#### 3.4 常见误区

- 把事件处理函数写在组件顶层而不是 `methods` 里——组件的 WXML 事件只会在 `methods` 中查找。
- 用 `Page({})` 的写法定义组件（如写 `onLoad`），组件不识别页面生命周期。

### 4. properties：对外属性

#### 4.1 是什么

`properties` 是组件对外暴露的输入接口。外部通过标签属性传入，组件内部通过 `this.data.xxx` 读取。每个属性可声明：

- `type`：类型构造器，常用 `String / Number / Boolean / Object / Array / null`；
- `value`：默认值，当外部未传时使用；
- `observer(newVal, oldVal)`：属性变化时的回调；
- `optionalTypes`：允许的其他类型（此时 `type` 写 `null`）。

#### 4.2 与小程序开发的关系

properties 实现了**父 → 子的单向数据传入**：页面决定卡片显示哪条笔记、搜索栏显示什么占位文案，组件只负责按传入值渲染。这种单向约定让数据流可追踪——看到一个属性值，就知道它来自外部，而不是组件内部凭空产生。

#### 4.3 可运行示例：搜索栏的属性定义

```typescript
// components/search-bar/search-bar.ts
Component({
  properties: {
    placeholder: {
      type: String,
      value: '搜索小店、菜品、商圈'
    },
    keyword: {
      type: String,
      value: '',
      observer(newVal, oldVal) {
        // 外部传入的关键词变化时响应
        console.log(`[search-bar] keyword: ${oldVal} -> ${newVal}`)
      }
    },
    disabled: {
      type: Boolean,
      value: false
    },
    maxLength: {
      type: null,
      optionalTypes: [Number, String],
      value: 20
    }
  }
})
```

对应的使用方式：

```xml
<search-bar
  placeholder="搜索附近的火锅店"
  keyword="{{query}}"
  disabled="{{false}}"
  max-length="{{20}}"
/>
```

注意 WXML 属性名使用连字符写法（`max-length`），组件内定义用驼峰（`maxLength`）。

Object / Array 类型属性的默认值应在组件内部初始化，不要引用可能被多处共享修改的外部对象：

```typescript
properties: {
  note: {
    type: Object,
    value: {
      id: '',
      title: '',
      tags: [] as string[]
    }
  }
}
```

#### 4.4 常见误区

- 在组件内部直接 `this.setData({ keyword: '...' })` 去修改一个由父级控制的属性，导致「组件显示值」与「父级状态」脱节。需要改变时应 `triggerEvent` 通知父级，由父级更新传入（受控模式）。
- Boolean 属性只写属性名不传值：`<search-bar disabled />` 等价于传 `true`，要显式传 false 需写 `disabled="{{false}}"`。
- 在 `observer` 里再 `setData` 同一个属性，造成循环触发。
- 以为 `observer` 会在首次赋值时触发——它响应的是「变化」，初始化用默认值时不会执行。

### 5. data：组件内部状态

#### 5.1 是什么

`data` 是组件**私有**的状态数据，由组件自己创建、自己修改，外部无法直接传入或控制。

#### 5.2 与小程序开发的关系

判断一个字段放 `properties` 还是 `data`，看「谁说了算」：

- 文案、数据条目、开关初始值来自外部 → `properties`；
- 只服务于组件内部展示的临时状态（如「点赞按钮是否正在播放动画」「本地输入草稿」）→ `data`。

properties 与 data 最终会被合并，组件内部统一通过 `this.data.xxx` 读取，但修改私有状态用 `this.setData`，修改外部数据要走事件。

#### 5.3 可运行示例

```typescript
Component({
  properties: {
    note: { type: Object, value: {} as { id: string; liked: boolean } }
  },
  data: {
    animating: false,
    localDraft: ''
  },
  methods: {
    onLike() {
      if (this.data.animating) return
      this.setData({ animating: true })
      // 动画结束后复位（真实项目可用 animationfinish 事件）
      setTimeout(() => {
        this.setData({ animating: false })
      }, 300)
      // 数据变更仍需通知页面
      this.triggerEvent('like', { id: this.data.note.id })
    }
  }
})
```

#### 5.4 常见误区

- 把本该由外部决定的数据塞进 `data`，然后在组件内发请求自己取数，结果多个页面复用同一组件时行为各异、数据来源混乱。基础展示型组件应「给什么显示什么」。
- 沿用 U02 的反模式 `this.data.animating = true` 不调 `setData`，界面不更新。

### 6. methods：事件处理与组件方法

#### 6.1 是什么

`methods` 中定义组件的所有函数：既包括被 WXML 事件绑定的处理函数，也包括供内部复用的工具函数（U10 还可通过 relations 被关联组件调用）。

#### 6.2 与小程序开发的关系

组件内的交互闭环是：用户在渲染层点击 → 事件消息跨线程到逻辑层 → `methods` 中对应函数执行 → `setData` 或 `triggerEvent` → 界面更新或通知页面。组件把「怎么交互」封装在自己内部，页面只订阅组件抛出的业务事件。

#### 6.3 可运行示例：笔记卡片的完整交互

note-card.wxml：

```xml
<view class="note-card" bindtap="onCardTap">
  <image class="cover" src="{{note.cover}}" mode="aspectFill" />
  <view class="body">
    <view class="title">{{note.title}}</view>
    <view class="shop">{{note.shop}}</view>
    <view class="tags">
      <text wx:for="{{note.tags}}" wx:key="*this" class="tag">{{item}}</text>
    </view>
    <view class="footer">
      <text class="rating">★ {{note.rating}}</text>
      <view
        class="like {{note.liked ? 'liked' : ''}} {{animating ? 'pop' : ''}}"
        catchtap="onLike"
      >
        {{note.liked ? '已赞' : '点赞'}}
      </view>
    </view>
  </view>
</view>
```

note-card.ts：

```typescript
Component({
  properties: {
    note: {
      type: Object,
      value: {} as {
        id: string
        title: string
        shop: string
        cover: string
        rating: number
        tags: string[]
        liked: boolean
      }
    }
  },
  data: {
    animating: false
  },
  methods: {
    onCardTap() {
      // 点击整张卡片：通知页面跳详情
      this.triggerEvent('tapcard', { id: this.data.note.id })
    },
    onLike() {
      // catchtap 阻止冒泡，避免触发卡片点击
      this.setData({ animating: true })
      setTimeout(() => this.setData({ animating: false }), 300)
      this.triggerEvent('like', {
        id: this.data.note.id,
        liked: !this.data.note.liked
      })
    }
  }
})
```

#### 6.4 常见误区

- 组件内部用 `bindtap` 绑了未在 `methods` 中定义的函数，点击无反应也无报错提示。
- 子组件按钮事件冒泡到整卡，点点赞同时触发跳转——需要阻止冒泡时用 `catchtap`。
- 在回调里丢失 `this`：`methods` 中的函数由框架绑定了组件实例，但若把方法解构出来单独调用（如 `const { onLike } = this`），`this` 会丢失，建议始终以 `this.fn()` 形式调用或用箭头函数包裹。

### 7. 组件生命周期 lifetimes

#### 7.1 是什么

组件自身的生命周期描述组件实例从创建到销毁的过程：

| 回调 | 触发时机 | 可做什么 |
|---|---|---|
| `created` | 实例刚被创建，尚未进入页面节点树 | 读取初始 data；**不能调用 setData**；适合给实例挂工具字段 |
| `attached` | 组件进入页面节点树 | properties 已就绪，可 setData、发请求、建立监听 |
| `ready` | 组件视图层布局完成 | 依赖节点位置/尺寸的操作 |
| `moved` | 组件在节点树中被移动（位置变化但未销毁） | 同步与位置相关的状态 |
| `detached` | 组件从节点树移除、实例销毁 | 清理定时器、监听、取消请求 |

生命周期推荐写在 `lifetimes` 字段中；直接写在构造器顶层的旧式写法仍然兼容，但两者同时存在时以 `lifetimes` 为准。

#### 7.2 与小程序开发的关系

理解时序能避免在错误的阶段做不可做的事：`created` 中 `setData` 是常见报错来源；首屏请求应放 `attached`；组件内的定时器、订阅必须在 `detached` 清理，否则切走页面后仍在后台执行，造成内存与性能问题。

#### 7.3 可运行示例：用日志验证时序

```typescript
Component({
  data: { counter: 0 },
  lifetimes: {
    created() {
      console.log('[note-card] created —— 不能 setData')
      // 可在此挂载非响应式字段
      this.timer = null as null | ReturnType<typeof setInterval>
    },
    attached() {
      console.log('[note-card] attached —— 可以发请求')
      console.log('拿到 property id:', this.data.note?.id)
    },
    ready() {
      console.log('[note-card] ready —— 布局完成')
    },
    moved() {
      console.log('[note-card] moved')
    },
    detached() {
      console.log('[note-card] detached —— 清理资源')
      if (this.timer) clearInterval(this.timer)
    }
  }
})
```

用 `wx:if` 切换组件的挂载/卸载，可以在开发者工具 Console 中清楚看到 `created → attached → ready` 与 `detached` 的完整序列。

#### 7.4 常见误区

- 在 `created` 中 `this.setData`：此时组件尚未完成挂载，调用无效并可能告警。
- 把首屏请求放进 `ready`：`ready` 要等渲染层布局完成，比 `attached` 晚，白白推迟数据获取。
- 在 `detached` 后异步回调仍到达并 `setData`：发请求时要考虑组件可能已卸载，必要时用标志位拦截。

### 8. pageLifetimes：感知所在页面

#### 8.1 是什么

组件除了自身生命周期，还可以通过 `pageLifetimes` 监听**它所在页面**的状态变化：`show`（页面显示，包括 onLoad 后与从其他页返回）、`hide`（页面被跳转覆盖或切走）、`resize`（页面尺寸变化）。

#### 8.2 与小程序开发的关系

组件被 `navigateTo` 的新页面盖住时，自身不会销毁（不触发 `detached`），但页面已经 `onHide`。如果组件里有轮播计时、定位上报、音视频播放，就应在 `pageLifetimes.hide` 中暂停，在 `show` 中恢复——这比页面自己去操作每个子组件更内聚。

#### 8.3 可运行示例：页面隐藏时暂停计时

```typescript
Component({
  data: { seconds: 0 },
  lifetimes: {
    created() {
      this.timer = null as null | ReturnType<typeof setInterval>
    },
    attached() {
      this.start()
    },
    detached() {
      this.stop()
    }
  },
  pageLifetimes: {
    show() {
      // 从详情页返回时恢复
      this.start()
    },
    hide() {
      // 进入详情页或切 Tab 时暂停
      this.stop()
    }
  },
  methods: {
    start() {
      if (this.timer) return
      this.timer = setInterval(() => {
        this.setData({ seconds: this.data.seconds + 1 })
      }, 1000)
    },
    stop() {
      if (this.timer) {
        clearInterval(this.timer)
        this.timer = null
      }
    }
  }
})
```

#### 8.4 常见误区

- 混淆组件生命周期与 `pageLifetimes`：切到其他页面再返回，组件没有重新创建，不会重新 `attached`，只有页面 `show/hide` 在触发。
- 在 `pageLifetimes.show` 中无脑重发首屏请求，导致每次返回都全量刷新。应按需判断「数据是否过期」。

### 9. 父子通信总览：单向数据流

#### 9.1 是什么

小程序组件的标准通信模型只有两个方向：

```text
页面（父） ──properties 单向传入──▶ 组件（子）
页面（父） ◀── triggerEvent 事件── 组件（子）
```

- 向下：页面在标签上写属性，数据经 properties 进入组件；
- 向上：组件调用 `this.triggerEvent('事件名', detail)`，页面用 `bind:事件名` 监听，从 `event.detail` 取数据。

#### 9.2 与小程序开发的关系

这一模型与 U02 的双线程结构一致：没有「子组件直接改父组件数据」的通道，所有状态变更都显式发生在逻辑层的页面或组件自身，数据流可预测、可调试。排查问题时只要问两个问题：这个值由谁传入？这个变化由哪个事件触发？

#### 9.3 可运行示例：页面使用笔记卡片

pages/index/index.json：

```json
{
  "usingComponents": {
    "note-card": "/components/note-card/note-card"
  }
}
```

pages/index/index.wxml：

```xml
<note-card
  wx:for="{{notes}}"
  wx:key="id"
  id="card-{{item.id}}"
  note="{{item}}"
  bind:like="onNoteLike"
  bind:tapcard="onOpenDetail"
/>
```

pages/index/index.ts：

```typescript
type Note = {
  id: string
  title: string
  shop: string
  cover: string
  rating: number
  tags: string[]
  liked: boolean
}

Page({
  data: {
    notes: [] as Note[]
  },
  onNoteLike(e: WechatMiniprogram.CustomEvent<{ id: string; liked: boolean }>) {
    const { id, liked } = e.detail
    const list = this.data.notes.map((note) =>
      note.id === id ? { ...note, liked } : note
    )
    this.setData({ notes: list })
  },
  onOpenDetail(e: WechatMiniprogram.CustomEvent<{ id: string }>) {
    wx.navigateTo({ url: `/pages/detail/detail?id=${e.detail.id}` })
  }
})
```

#### 9.4 常见误区

- 子组件直接修改 `this.data.note.liked` 期望页面同步：组件内这样改既违背单向约定，也不会反向更新页面数据。
- 事件名大小写不一致：`triggerEvent('likeTap')` 而页面写 `bind:liketap`，事件名是大小写敏感的字符串，团队应统一命名风格（推荐全小写或 kebab-case）。

### 10. triggerEvent 详解

#### 10.1 是什么

`this.triggerEvent(name, detail, options)` 在组件上派发一个自定义事件：

- `name`：事件名，页面以 `bind:name` / `catch:name` 监听；
- `detail`：随事件携带的数据，页面通过 `event.detail` 读取；
- `options`：`bubbles`（是否冒泡）、`composed`（是否跨越组件边界）、`capturePhase`（是否有捕获阶段）。

#### 10.2 与小程序开发的关系

绝大多数业务事件只需 `this.triggerEvent('like', data)` 默认配置。当组件嵌套较深、希望事件沿组件树向上冒泡时，才需要 `bubbles: true`；配合 `composed: true` 才能让事件穿出组件边界。一般优先让直接父级处理事件，保持链路简单。

#### 10.3 可运行示例：搜索栏向上抛出三种事件

```typescript
// components/search-bar/search-bar.ts
Component({
  properties: {
    placeholder: { type: String, value: '搜索小店、菜品' },
    keyword: { type: String, value: '' }
  },
  data: {
    innerValue: ''
  },
  methods: {
    onInput(e: WechatMiniprogram.Input) {
      const value = e.detail.value
      this.setData({ innerValue: value })
      // 每次输入都通知页面，页面可实时联想
      this.triggerEvent('input', { value })
    },
    onConfirm(e: WechatMiniprogram.Input) {
      // 按下键盘“搜索”
      this.triggerEvent('search', { value: e.detail.value })
    },
    onClear() {
      this.setData({ innerValue: '' })
      this.triggerEvent('clear')
      this.triggerEvent('input', { value: '' })
    }
  }
})
```

search-bar.wxml：

```xml
<view class="search-bar">
  <text class="icon">🔍</text>
  <input
    class="input"
    value="{{innerValue}}"
    placeholder="{{placeholder}}"
    confirm-type="search"
    bindinput="onInput"
    bindconfirm="onConfirm"
  />
  <view wx:if="{{innerValue}}" class="clear" bindtap="onClear">×</view>
</view>
```

页面监听：

```xml
<search-bar
  bind:input="onSearchInput"
  bind:search="onSearchSubmit"
  bind:clear="onSearchClear"
/>
```

```typescript
Page({
  onSearchInput(e: WechatMiniprogram.CustomEvent<{ value: string }>) {
    console.log('实时输入：', e.detail.value)
    // 在此做本地过滤或防抖请求
  },
  onSearchSubmit(e: WechatMiniprogram.CustomEvent<{ value: string }>) {
    console.log('发起搜索：', e.detail.value)
  },
  onSearchClear() {
    console.log('已清空，恢复完整列表')
  }
})
```

#### 10.4 常见误区

- 把业务数据放在 `event.currentTarget.dataset` 里「假冒」事件数据。dataset 适合静态标记，动态数据应放 `detail`。
- 在 `triggerEvent` 之后立刻假设父级已经完成 setData：父级监听函数是同步执行的，但父级 setData 仍是跨线程异步，组件内读不到「更新后的 prop」。
- 滥用 `bubbles + composed` 让事件穿透多层组件，导致谁在处理事件难以追踪。

### 11. usingComponents：注册组件

#### 11.1 是什么

使用组件前必须在 json 的 `usingComponents` 中登记：键是标签名，值是组件路径。可以在两个层级注册：

- **页面 json**：仅当前页面可用，按需注册、利于控制包体积；
- **app.json**：全局可用，适合几乎每个页面都会用的基础组件。

路径以 `/` 开头表示从小程序根目录开始的绝对路径；也可用相对当前文件的 `../` 路径。

#### 11.2 与小程序开发的关系

注册机制让框架在编译期就建立组件树依赖，组件标签才能被识别。它也是一种依赖声明：看页面 json 就知道本页依赖哪些组件，Code Review 与后续分包优化（U26）都依赖这份清单。

#### 11.3 可运行示例

页面级注册：

```json
{
  "usingComponents": {
    "note-card": "/components/note-card/note-card",
    "search-bar": "/components/search-bar/search-bar"
  }
}
```

全局注册（app.json）：

```json
{
  "pages": ["pages/index/index", "pages/explore/explore"],
  "usingComponents": {
    "empty-state": "/components/empty-state/empty-state"
  }
}
```

注册后，标签名即自定义元素：

```xml
<view class="page">
  <search-bar />
  <empty-state wx:if="{{notes.length === 0}}" text="还没有笔记，换个关键词试试" />
  <note-card wx:for="{{notes}}" wx:key="id" note="{{item}}" />
</view>
```

确有必要时，页面可用 `selectComponent` 拿到子组件实例调用其方法：

```typescript
const card = this.selectComponent('#card-n1001')
console.log(card)
```

但这会增加父子耦合，优先用 properties + 事件；需要导出精简接口时可配合 U10 的 `wx://component-export`。

#### 11.4 常见误区

- 路径漏写开头 `/` 或相对路径层级算错，模拟器因缓存看似正常、真机白屏。
- 在每个页面 json 重复注册同一重型组件却以为全局注册——作用域以 json 所在层级为准。
- 标签名与注册键不一致（注册 `noteCard` 却写 `<note-card>`），框架按字符串精确匹配。

### 12. 组件与页面的区别

| 对比项 | 页面 Page | 自定义组件 Component |
|---|---|---|
| 构造器 | `Page({})`（也可用 Component 构造器写页面） | `Component({})` |
| 注册方式 | `app.json` 的 `pages` 列表 | json `usingComponents` |
| json 声明 | 页面配置 | 必须 `"component": true` |
| 路由能力 | 可被路由 API 打开、有 URL query | 不是路由目标 |
| 生命周期 | onLoad/onShow/onReady/onHide/onUnload | created/attached/ready/moved/detached |
| 感知页面 | 自身即页面 | 通过 `pageLifetimes` 感知 |
| 数据来源 | 路由参数、请求、全局状态 | properties 传入 + 私有 data |
| 复用 | 一般不跨页面复用 | 设计目的就是跨页面复用 |

补充：微信支持「用 Component 构造器构造页面」，此时页面可使用 `methods` 等组件字段，并通过 `onLoad` 等页面生命周期字段工作；本课程仍统一用 `Page` 写页面、`Component` 写组件，降低心智负担。

### 13. 实战：把笔记卡片抽成组件

#### 13.1 重构步骤

1. 新建 `components/note-card/` 四件套，json 声明 `component: true`。
2. 把首页 WXML 中单个卡片的结构原样搬进 note-card.wxml，把 wx:for 留在**页面**（组件只渲染一条）。
3. 把原本依赖的列表项变量改为 property `note`；卡片内联样式搬进 note-card.wxss，最外层 class 加组件前缀避免冲突。
4. 卡片内「点赞」「点击整卡」分别 `triggerEvent('like')`、`triggerEvent('tapcard')`。
5. 首页注册组件、用 `<note-card>` 替换原结构，页面保留列表数据与跳转、点赞合并逻辑。

#### 13.2 重构前后对照

重构前，首页承担全部细节：

```xml
<view wx:for="{{notes}}" wx:key="id" class="note-card" data-id="{{item.id}}" bindtap="goDetail">
  <image src="{{item.cover}}" class="cover" />
  <view class="title">{{item.title}}</view>
  <view class="like" catchtap="doLike" data-id="{{item.id}}">点赞</view>
</view>
```

重构后，首页只剩「数据 + 编排」：

```xml
<note-card
  wx:for="{{notes}}"
  wx:key="id"
  note="{{item}}"
  bind:like="onNoteLike"
  bind:tapcard="onOpenDetail"
/>
```

#### 13.3 常见误区

- 把 `wx:for` 写进组件内部却把整个数组通过 property 传入——组件变成了「列表组件」，失去单条卡片的复用性。列表渲染应留在使用方，除非你确实在设计列表组件（U10 relations 场景）。
- 抽完后页面与组件各保留一份点赞逻辑，状态来源不清。原则：**业务数据归页面，展示状态归组件**。

### 14. 实战：把搜索栏抽成组件

搜索栏的组件边界：

- 组件负责：输入框 UI、清除按钮、键盘确认；抛出 `input / search / clear` 事件。
- 页面负责：维护关键词、过滤列表、发起请求。

页面 WXML：

```xml
<search-bar
  placeholder="搜索探店笔记"
  bind:input="onSearchInput"
  bind:search="onSearchSubmit"
  bind:clear="onSearchClear"
/>
<view wx:if="{{loading}}">搜索中...</view>
<empty-state wx:elif="{{filteredNotes.length === 0}}" text="没有找到相关笔记" />
<note-card
  wx:else
  wx:for="{{filteredNotes}}"
  wx:key="id"
  note="{{item}}"
  bind:tapcard="onOpenDetail"
/>
```

页面逻辑（本地过滤版，网络搜索在 U18 工程化）：

```typescript
let inputTimer: ReturnType<typeof setTimeout> | null = null

Page({
  data: {
    allNotes: [] as Array<{ id: string; title: string; shop: string }>,
    filteredNotes: [] as Array<{ id: string; title: string; shop: string }>,
    loading: false
  },
  onSearchInput(e: WechatMiniprogram.CustomEvent<{ value: string }>) {
    const keyword = e.detail.value.trim()
    // 简单防抖：停止输入 200ms 后再过滤
    if (inputTimer) clearTimeout(inputTimer)
    inputTimer = setTimeout(() => {
      const result = keyword
        ? this.data.allNotes.filter(
            (n) => n.title.includes(keyword) || n.shop.includes(keyword)
          )
        : this.data.allNotes
      this.setData({ filteredNotes: result })
    }, 200)
  },
  onSearchSubmit(e: WechatMiniprogram.CustomEvent<{ value: string }>) {
    console.log('确认搜索：', e.detail.value)
  },
  onSearchClear() {
    this.setData({ filteredNotes: this.data.allNotes })
  },
  onOpenDetail(e: WechatMiniprogram.CustomEvent<{ id: string }>) {
    wx.navigateTo({ url: `/pages/detail/detail?id=${e.detail.id}` })
  }
})
```

常见误区：把过滤逻辑写进搜索栏组件，组件就无法在「搜笔记」「搜门店」「搜用户」之间复用。输入组件只管输入，搜什么、怎么搜由使用方决定。

### 15. 组件设计常见误区清单

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| created 中 setData | 无效/告警 | 延后到 attached |
| 子组件直接改 property | 状态脱节、难排查 | triggerEvent 由父级更新 |
| 事件处理写在构造器顶层 | 点击无反应 | 放进 methods |
| 事件名/标签名拼写不一致 | 事件丢失 | 统一命名并自测 |
| 组件内自行发请求取展示数据 | 复用即失控 | 数据由页面经 properties 传入 |
| detached 不清理定时器 | 泄漏、后台耗电 | detached/pageLifetimes.hide 清理 |
| 一个组件承担多种职责 | 难以维护 | 单一职责，组合使用 |
| 组件根节点依赖父级 class | 换页面就坏 | 样式自包含（U10 再讲隔离） |

一条贯穿始终的设计原则：**properties 是组件的「输入」，triggerEvent 是组件的「输出」，data 是组件的「内务」**。守住这条边界，组件就可复用、可测试、可替换。

### 练习 1：创建 note-card 组件并在首页复用

#### 任务

新建 `components/note-card/` 组件，接收单条笔记数据并展示，替换首页原有重复的卡片结构；点赞与点击整卡通过事件交给页面处理。

#### 参考代码

组件 ts 核心部分：

```typescript
Component({
  properties: {
    note: {
      type: Object,
      value: {} as {
        id: string
        title: string
        shop: string
        cover: string
        rating: number
        tags: string[]
        liked: boolean
      }
```

- 点赞只更新对应卡片，点击整卡正确跳转详情；

### 练习 2：抽离 search-bar 组件并驱动列表过滤

```typescript
Component({
```

### 练习 3：生命周期观察与页面级暂停恢复

#### 任务

在组件内实现一个秒级计时器，通过打日志观察组件生命周期，并使用 `pageLifetimes` 在页面隐藏时暂停、页面重新显示时恢复、组件销毁时清理。

#### 伪代码

```text
created:   初始化 timer 字段（禁止 setData）
attached:  start()，打印生命周期日志
ready:     打印日志
page.show: start()
page.hide: stop()
detached:  stop()，打印销毁日志
start/stop: 维护 setInterval，每秒 setData({ seconds: +1 })
```

#### 步骤约束

1. 五个组件生命周期与两个 pageLifetimes 都要打印带前缀的日志。
2. 用 `wx:if` 控制组件挂载/卸载各一次，观察 created 到 detached 的完整序列。
3. 从计时器页面 navigateTo 到详情页再返回，验证暂停与恢复，且返回后计数不偷偷增加。
4. 切 Tab / 切后台至少验证一次暂停行为。
5. 卸载后不得再出现任何 setData。

#### 提交物

- 计时器组件四件套与演示页代码；
- 生命周期日志截图（含挂载、覆盖返回、卸载三类操作）；
- 200 字以内时序结论。

#### 验收标准

- 日志顺序与实际操作对应正确；
- 页面隐藏期间计数不增长，返回后继续；
- 组件销毁后无残留定时器与告警。

## 阶段验收作业

本作业是阶段二组件化的第一块基石，重点证明**组件边界清晰、通信方向正确、生命周期使用规范**。

### 任务描述

将「逛吃指南」首页与探索页的重复界面块组件化：

1. 新建 `note-card` 组件：完整展示一条探店笔记（封面、标题、门店、标签、评分、点赞），通过 `note` property 接收数据，通过 `like`、`tapcard` 事件向外通信。
2. 新建 `search-bar` 组件：输入、确认、清除完整可用，抛出 `input / search / clear` 事件，页面侧实现防抖过滤与空状态。
3. 至少在首页、探索页两个页面注册并复用上述组件；两个页面的过滤字段允许不同，但组件代码不得修改。
4. 在组件中用日志体现对 `created / attached / ready / detached` 与 `pageLifetimes.show / hide` 的正确处理，定时器等资源在销毁与隐藏时被正确清理。

### 完成标准

- 能现场画出「properties 向下、triggerEvent 向上」的数据流图，并解释单向数据流的意义；
- 两个页面复用同一套组件，点赞、跳转、搜索过滤、空状态四条链路均可演示；
- 组件内不直接修改外部数据，页面不替组件实现内部展示状态；
- 生命周期时序回答正确，无 created 中 setData、无定时器泄漏。

### 评分要点（100 分）

| 父子通信 | 25 | properties 单向传入、triggerEvent 向上、detail 规范 |

### 强制不通过条件

- 组件直接修改 property 并以此作为状态同步手段，或通信方向整体用反；
- 组件未在 usingComponents 注册、json 缺少 `"component": true`，导致核心链路不可运行；
- 在 `created` 中调用 setData，或 `detached`/页面隐藏后定时器仍在运行；
- 为了通过验收在两个页面各复制一份组件代码，而非真正复用同一组件；
- 无法说清任一组件生命周期或父子通信的基本机制。
