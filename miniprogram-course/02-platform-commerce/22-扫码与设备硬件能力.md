# 22-扫码与设备硬件能力

## 目标

完成本知识单元后，学员应能把“调用设备硬件能力”从“看到 API 就调一下”升级为“先判能力、再走权限、失败有兜底、结果由服务端裁决”的工程实践。学员要为「逛吃指南」交付用户扫码领券、店员扫码核销的完整闭环，并合理使用震动、网络状态、屏幕、电量与各类传感器，同时对蓝牙、NFC、Wi-Fi 等重硬件能力的门槛与边界有清醒认识。

学员应能够：

1. 熟练使用 `wx.scanCode`，掌握 `scanType`（barCode/qrCode/datamatrix/pdf417）、`onlyFromCamera` 等参数与 `result/scanType/charSet/rawData` 返回结构，并处理用户取消等失败分支。
2. 使用 camera 组件的 `scanCode` 模式实现自定义扫码界面（扫码框、闪光灯、提示文案），理解自定义扫码与通用扫码的取舍。
3. 设计扫码券的领取链路：二维码内容与券活动绑定、领取状态机、服务端幂等领取，避免重复领券与伪造券码。
4. 实现扫码核销的状态校验：券是否存在、是否属于当前门店、是否已领取/已核销/已过期，并在服务端以原子操作完成核销，从根本上防止同一券重复使用。
5. 熟练使用 `wx.setClipboardData` / `getClipboardData`，知道系统默认提示与隐私限制，不静默读取剪贴板。
6. 使用 `vibrateShort` / `vibrateLong` 做操作反馈，了解 iOS/Android 在震动类型上的差异与系统开关影响。
7. 通过 `wx.getNetworkType` 与 `wx.onNetworkStatusChange` 感知网络，在断网/弱网与恢复时调整 UI 与请求策略。
8. 使用屏幕亮度与常亮（setScreenBrightness/setKeepScreenOn）、电量（getBatteryInfo）等系统信息能力，理解用完恢复、低电降级等工程约束。
9. 使用加速度计、罗盘等传感器实现摇一摇、方向指示等功能，理解高频回调下不要每次 setData 的跨线程性能约束。
10. 说清蓝牙 BLE、NFC、Wi-Fi 三类重硬件能力的完整流程、权限门槛与平台限制，知道什么场景值得用、什么场景应放弃，并在所有设备能力调用前用 `canIUse` 做能力检测与降级。

本单元承接 U21 的位置能力（核销时可以结合“到店”上下文），也是“平台能力”阶段的收官单元。

## 技术栈

本单元使用微信原生设备与扫码能力 + TypeScript，券状态由自建服务端/云函数裁决，本地存储沿用 U12，网络请求层沿用 U17。

约定：

- 设备能力必须真机验证：开发者工具可以模拟扫码与多数回调，但蓝牙、NFC、传感器、网络切换等行为只有真机可靠。
- 一切“是否领取、是否核销”的最终结论由服务端数据决定，前端展示只是缓存；扫码得到的任何字符串都不可被直接信任。
- 硬件权限属于强打扰能力，按需申请、用完即放（如蓝牙适配器、传感器监听），不在无关页面长期占用。

## 详细的理论知识讲解和示例伪代码

### 1. 设备能力全景：分层、权限与能力检测

小程序能调用的设备能力可以按“重硬件程度”分成四档：

1. **轻系统能力**：剪贴板、震动、屏幕亮度、常亮、电量、系统信息——基本无需额外授权，调用门槛低；
2. **传感器能力**：加速度计、罗盘、陀螺仪（部分平台）——需启动监听，无显式授权弹窗，但高频耗电；
3. **相机扫码能力**：`wx.scanCode`（直接跳微信扫码页）与 camera 自定义扫码——前者零 UI 成本，后者可定制；
4. **重硬件能力**：蓝牙 BLE、NFC、Wi-Fi——涉及系统蓝牙/定位/附近设备权限，平台差异大，调用链长。

贯穿所有能力的两条工程纪律：

- **先检测再调用**：用 `wx.canIUse('API')` 或判断 API 是否存在，低版本基础库直接走降级；
- **区分三种失败**：用户取消/拒绝授权、能力不支持（canIUse 为假）、运行时失败（如设备没开），提示与兜底各不相同。

```typescript
// utils/capability.ts
export function canUse(api: string): boolean {
  return typeof wx.canIUse === 'function' && wx.canIUse(api)
}

/** 安全调用封装：能力缺失或运行失败时走 fallback，绝不抛白屏 */
export async function withCapability<T>(
  api: string,
  invoke: () => Promise<T>,
  fallback: T,
): Promise<T> {
  if (!canUse(api)) return fallback
  try {
    return await invoke()
  } catch (err) {
    return fallback
  }
}
```

「逛吃指南」的硬件能力使用非常克制：领券/核销用扫码，配合震动反馈与网络感知；蓝牙、NFC、Wi-Fi 只在“门店打印小票、连接硬件设备”等可选场景出现，不做主流程。

误区提醒：

- 以为“基础库够新就一定能用”：蓝牙/NFC 还依赖机型硬件、系统开关与系统权限，canIUse 通过不代表调用一定成功。

### 2. wx.scanCode：通用扫码的参数、返回值与错误处理

```typescript
wx.scanCode({
  onlyFromCamera: false, // true 时只能实时拍摄，不允许从相册选图
  scanType: ['qrCode', 'barCode'], // 可指定码制：barCode/qrCode/datamatrix/pdf417
  success: (res) => {
    res.result // 码的原始文本内容，如 https://xxx/coupon?c=abc123
    res.scanType // 实际识别到的码制：QR_CODE / EAN_13 / CODE_128 ...
    res.charSet // 字符集，如 UTF-8
    res.rawData // 原始 base64 数据（一般用不到）
  },
  fail: (err) => {
    // 用户点取消：errMsg 包含 "scanCode:fail cancel"
  },
})
```

码制选择建议：

- 优惠券、核销码、跳转链接用 **二维码（qrCode）**：容量大、容错强、可被远距离识别；
- 商品条码（EAN-13/UPC/Code128）用 **barCode**：用于“扫商品条码查同款”；
- `datamatrix`、`pdf417` 多见于工业票据/证件，按需开启。

把扫码结果交给服务端前先做最小解析，用户取消单独处理：

```typescript
// services/scan.ts
export interface ParsedScan {
  kind: 'coupon' | 'redeem' | 'unknown'
  payload: string
}

export function parseScanResult(result: string): ParsedScan {
  // 例：码内容约定为 https://m.example.com/c/coupon?code=XXX
  const matched = result.match(/[?&]code=([\w-]+)/)
  if (matched) {
    const isRedeem = result.includes('/redeem')
    return { kind: isRedeem ? 'redeem' : 'coupon', payload: matched[1] }
  }
  return { kind: 'unknown', payload: result }
}

export function scanOnce(scanType: string[] = ['qrCode']): Promise<ParsedScan | null> {
  return new Promise((resolve) => {
    wx.scanCode({
      scanType,
      success: (res) => resolve(parseScanResult(res.result)),
      fail: (err) => {
        if (err.errMsg.includes('cancel')) resolve(null) // 用户取消，静默返回
        else {
          wx.showToast({ title: '扫码失败，请重试', icon: 'none' })
          resolve(null)
        }
      },
    })
  })
}
```

`onlyFromCamera` 的安全语义：核销场景建议设 `true`，防止店员从相册选一张二维码图片“假装扫到”，强制现场实时拍摄。

误区提醒：

- 直接把 `res.result` 当成券码提交：码可能是任意网址甚至恶意文本，必须先按约定格式解析，服务端再校验。
- 把用户取消当成错误弹 toast：取消是正常行为，应静默返回上一步。

### 3. 自定义扫码：camera 组件的 scanCode 模式

通用扫码页无法定制样式。需要“门店主题扫码框、活动文案、闪光灯按钮”时，用 camera 组件：

```xml
<!-- pages/scan/scan.wxml -->
<view class="scan-page">
  <camera
    mode="scanCode"
    device-position="back"
    flash="{{flashOn ? 'torch' : 'off'}}"
    frame-size="large"
    bindscancode="onScanCode"
    binderror="onCameraError"
    class="camera"
  >
    <cover-view class="overlay">
      <cover-view class="scan-box {{scanning ? '' : 'is-paused'}}"></cover-view>
      <cover-view class="tip">将券二维码对准框内，自动识别</cover-view>
      <cover-view class="flash-btn" bindtap="toggleFlash">
        {{flashOn ? '关闭闪光灯' : '打开闪光灯'}}
      </cover-view>
    </cover-view>
  </camera>
</view>
```

```typescript
// pages/scan/scan.ts
const DEBOUNCE_MS = 2000

Page({
  data: { flashOn: false, scanning: true, lastScanAt: 0 },

  onScanCode(e: WechatMiniprogram.CameraOnScanCode) {
    const now = Date.now()
    // 自定义扫码会连续识别同一码，必须加锁 + 时间窗去重
    if (!this.data.scanning || now - this.data.lastScanAt < DEBOUNCE_MS) return
    this.setData({ scanning: false, lastScanAt: now })

    const parsed = parseScanResult(e.detail.result)
    this.dispatch(parsed)
  },

  toggleFlash() {
    this.setData({ flashOn: !this.data.flashOn })
  },

  onCameraError() {
    wx.showModal({
      title: '无法使用相机',
      content: '请检查是否已授权相机权限，或改用系统扫码',
      confirmText: '去设置',
      success: (r) => r.confirm && wx.openSetting(),
    })
  },

  resetScan() {
    this.setData({ scanning: true })
  },
})
```

注意几个原生组件细节：

- camera 是原生组件，蒙层只能用 `cover-view` / `cover-image`；
- `bindscancode` 可能在一次对准内连续触发，必须像上面一样用 `scanning` 锁 + 时间窗，否则一次扫码会发起多次请求；
- `frame-size` 控制识别帧开销，低端机用小帧可降低卡顿；
- CameraContext（`wx.createCameraContext`）可做手动变焦（setZoom）、拍照等，扫码模式下最常用的是闪光灯与重置识别。

取舍：没有定制 UI 的硬需求时，优先 `wx.scanCode`——稳定、兼容好、零页面成本；自定义扫码的成本是要自己处理连续识别、权限、闪光灯与各种机型差异。

误区提醒：

- 忘记“同一码连续触发”的去重，用户扫一次，服务端收到一串请求。
- 把普通 view 浮层盖在 camera 上，真机上会被原生画面穿透遮挡。

### 4. 扫码券领取：码设计、状态机与服务端幂等

先定券的数据模型与状态机：

```typescript
// 券在服务端的状态
type CouponStatus = 'claimed' | 'used' | 'expired' | 'revoked'

interface Coupon {
  id: string
  activityId: string
  code: string // 券码
  userId: string
  shopId?: string // 限某店使用时
  status: CouponStatus
  claimedAt: number
  expireAt: number
  usedAt?: number
}
```

二维码内容不要直接放敏感信息，只放一个可校验的领取凭证，例如：

```text
https://m.guangchi.example.com/c/coupon?code=8F3KQ9
```

- `code` 是服务端生成的随机短码，本身不含面额/门槛等任何业务数据；面额、有效期全部由服务端按 code 查库得到，改码字符串毫无意义；
- 更严格时可以对载荷做服务端签名（HMAC），签名密钥只在服务端，前端不参与。

领取链路与幂等：

```typescript
// services/coupon.ts
export async function claimCoupon(code: string): Promise<Coupon> {
  return new Promise((resolve, reject) => {
    wx.request({
      url: 'https://api.example.com/coupons/claim',
      method: 'POST',
      data: {
        code,
        idempotencyKey: getIdempotencyKey(), // U20 的幂等键机制
      },
      header: { Authorization: getToken() },
      success: (res) => {
        const body = res.data as ApiResponse<Coupon>
        if (body.code === 0) {
          wx.vibrateShort({ type: 'light' })
          resolve(body.data)
        } else {
          reject(new Error(body.message))
        }
      },
      fail: () => reject(new Error('NETWORK_ERROR')),
    })
  })
}
```

服务端领取逻辑（云函数示意）：

```typescript
// 1) 校验 code 属于进行中的活动且未被领取
// 2) 幂等：同一 (idempotencyKey) 直接返回首次结果
// 3) 落库：对 (code) 建唯一约束，INSERT ... 失败即“已被领取”
async function claim(code: string, userId: string, idemKey: string) {
  const cached = await idemStore.get(idemKey)
  if (cached) return cached // 重试复用首次结果

  const coupon = await db.coupon.findUnclaimed(code)
  if (!coupon) throw new BusinessError('优惠券无效或已被领完')
  if (coupon.activityEndAt < Date.now()) throw new BusinessError('活动已结束')

  const claimed = await db.coupon.claimIfFree(code, userId) // 原子抢占
  if (!claimed) throw new BusinessError('手慢了，该券已被领取')

  await idemStore.set(idemKey, claimed)
  return claimed
}
```

错误语义要区分：码无效、活动未开始/已结束、已被他人领走、用户自己已领过（可直接回显已有券），不能一律“领取失败”。

误区提醒：

- 用“先查询再插入”两步实现领取：高并发下两人同时查到“未领取”会重复发券；必须靠唯一约束或原子条件更新。
- 把面额写进二维码明文，前端读到什么显示什么——用户可以自行伪造券内容。

### 5. 扫码核销：状态校验、原子操作与防重复使用

核销是店员动作，安全要求最高。要依次校验：

1. 操作者是**已登录且有权限的店员**，且券的适用门店包含当前门店；
2. 券真实存在且属于某个用户；
3. 状态必须是 `claimed`（已领取、未使用、未过期、未作废）；
4. 核销是服务端的**原子条件更新**，以影响行数决定成败。

```typescript
// services/coupon-redeem.ts
type RedeemResult =
  | { ok: true; coupon: Coupon }
  | { ok: false; reason: 'not-found' | 'used' | 'expired' | 'wrong-shop' | 'revoked' }

export async function redeemByScan(scanResult: string, shopId: string): Promise<RedeemResult> {
  const parsed = parseScanResult(scanResult)
  if (parsed.kind !== 'redeem' && parsed.kind !== 'coupon') {
    return { ok: false, reason: 'not-found' }
  }
  return new Promise((resolve) => {
    wx.request({
      url: 'https://api.example.com/coupons/redeem',
      method: 'POST',
      data: {
        code: parsed.payload,
        shopId,
        idempotencyKey: getIdempotencyKey(),
      },
      header: { Authorization: getStaffToken() },
      success: (res) => resolve((res.data as ApiResponse<RedeemResult>).data),
      fail: () => wx.showToast({ title: '网络异常，请重试', icon: 'none' }),
    })
  })
}
```

服务端核销（核心是带条件的原子更新）：

```sql
-- 只在状态仍是 claimed 且未过期时更新成功
UPDATE coupon
SET status = 'used', used_at = ?, used_by_shop = ?
WHERE code = ? AND status = 'claimed' AND expire_at > ?;
-- affectedRows = 1 -> 核销成功；affectedRows = 0 -> 状态已变化，回查原因
```

```typescript
async function redeem(code: string, shopId: string, staffId: string, idemKey: string) {
  const cached = await idemStore.get(idemKey)
  if (cached) return cached // 弱网重试，不重复核销

  const coupon = await db.coupon.findByCode(code)
  if (!coupon) return { ok: false, reason: 'not-found' }
  if (coupon.status === 'used') return { ok: false, reason: 'used' }
  if (coupon.status === 'expired' || coupon.expireAt < Date.now()) {
    return { ok: false, reason: 'expired' }
  }
  if (coupon.status === 'revoked') return { ok: false, reason: 'revoked' }
  if (coupon.shopId && coupon.shopId !== shopId) {
    return { ok: false, reason: 'wrong-shop' }
  }

  const affected = await db.coupon.redeemIfClaimed(code, shopId, staffId)
  const result: RedeemResult = affected
    ? { ok: true, coupon: { ...coupon, status: 'used' } }
    : { ok: false, reason: 'used' } // 并发下被别人抢先核销

  await idemStore.set(idemKey, result)
  return result
}
```

前端交互上，扫码后应**先展示券信息让店员确认，再点“确认核销”**，而不是扫到即核销；核销成功给强反馈（成功提示 + 震动），失败原因明确（“该券已于 10:02 在本店核销”）。对同一码的重复扫描，服务端返回 `used` 并显示已有核销记录，而不是再执行一次。

误区提醒：

- 只在前端判断“这张券没用过”：前端状态可被篡改、可被并发绕过，真正的防重只靠服务端条件更新。
- 用“查到 used 就报错”处理重复核销：重试/重复扫码是高频正常行为，应幂等地返回首次核销结果（含时间、门店），体验上明确告知“已核销”。

### 6. 剪贴板：setClipboardData 与隐私边界

```typescript
// 写入后系统默认弹出“内容已复制”提示，无法静默取消
wx.setClipboardData({
  data: couponCode,
  success: () => {
    // 不建议再自己 showToast，会与系统提示叠加
  },
})

wx.getClipboardData({
  success: (res) => {
    res.data // 剪贴板文本
  },
})
```

典型用法：领券成功后提供“复制券码”，方便用户在不能自动跳转的场景粘贴使用。

隐私边界非常重要：

- 现代 iOS/Android 对“读取剪贴板”有明显的系统提示（顶部“已粘贴/来自某 App”横幅），**绝不要在 onShow 里静默读剪贴板**去“自动识别口令”，这会让用户每次进入都看到读取提示，审核也会关注；
- 只有在用户明确点击“粘贴/从剪贴板导入”时才读一次；
- 剪贴板内容不可信，读取后要按业务格式校验，不能直接当券码使用。

误区提醒：

- 在页面 `onShow` 自动 `getClipboardData`：属于高打扰、易被判定为超范围收集。
- 复制后又自己弹 toast，与系统“内容已复制”叠加出现两条提示。

### 7. 震动反馈：vibrateShort / vibrateLong 与平台差异

```typescript
// 短震：扫码识别、按钮点击的轻反馈
wx.vibrateShort({
  type: 'medium', // heavy | medium | light | rigid | soft
})

// 长震：核销失败等需要强提醒的场景
wx.vibrateLong()
```

差异要点：

- `type` 的精细区分主要在 iOS 生效；Android 上多数机型震动手感相同（部分新机型支持区分），不要把交互正确性建立在 type 差异上；
- 用户在系统设置里关闭震动后，调用仍成功但没有震感，因此震动只能是**增强反馈**，必须同时有视觉反馈（成功页/对勾动画）；
- 连续高频震动会让用户不适，一次操作只反馈一次。

在「逛吃指南」里推荐的反馈组合：

```typescript
export function feedbackSuccess() {
  wx.vibrateShort({ type: 'light' })
  wx.showToast({ title: '领取成功', icon: 'success' })
}

export function feedbackError() {
  wx.vibrateLong()
  wx.showToast({ title: '核销失败', icon: 'none' })
}
```

误区提醒：

- 只给震动不给视觉反馈：静音/关闭震动的用户完全感知不到结果。

### 8. 网络状态：getNetworkType 与 onNetworkStatusChange

```typescript
// 主动查询
wx.getNetworkType({
  success: (res) => {
    res.networkType // wifi | 2g | 3g | 4g | 5g | none | unknown
  },
})

// 持续监听
wx.onNetworkStatusChange((res) => {
  res.isConnected // 是否有网络连接
  res.networkType
})
```

在 App 或核销页注册监听，断网时给出明确状态、恢复时自动重试：

```typescript
// pages/redeem/redeem.ts
Page({
  data: { offline: false },

  onShow() {
    wx.onNetworkStatusChange(this.handleNetworkChange)
  },

  onHide() {
    wx.offNetworkStatusChange(this.handleNetworkChange) // 解绑，避免重复监听
  },

  handleNetworkChange(res: WechatMiniprogram.OnNetworkStatusChangeResult) {
    this.setData({ offline: !res.isConnected })
    if (res.isConnected && this.data.pendingRedeem) {
      this.doRedeem() // 网络恢复后自动补发（配合服务端幂等键）
    }
  },

  async doRedeem() {
    if (this.data.offline) {
      wx.showToast({ title: '当前无网络，请联网后重试', icon: 'none' })
      this.setData({ pendingRedeem: true })
      return
    }
    // 正常核销，幂等键不变
  },
})
```

网络类型还可以驱动降级：`2g/3g` 等弱网下减少图片加载、用更小图（呼应 U19），避免核销页在弱网下长时间无响应。

误区提醒：

- `onNetworkStatusChange` 注册后不解绑，页面多次进出会叠加多个监听器，一次网络变化触发多轮逻辑。
- 监听到恢复就无条件重发请求：必须配合固定的幂等键，否则可能重复核销（虽然服务端有条件更新兜底，但仍应规范）。

### 9. 屏幕亮度与保持常亮：扫码页与核销页的体验增强

```typescript
// 读亮度
wx.getScreenBrightness({
  success: (res) => res.value, // 0 ~ 1
})

// 设置亮度：扫码页临时提亮，暗处更好识别
wx.setScreenBrightness({ value: 1.0 })

// 保持屏幕常亮：核销操作进行中不自动锁屏
wx.setKeepScreenOn({ keepScreenOn: true })
```

工程要点是**用完恢复**：进入扫码页记录原始亮度并提亮，离开时恢复用户原设置，不要永久改掉系统亮度。

```typescript
// pages/scan/scan.ts
let originalBrightness = 1

Page({
  onShow() {
    wx.getScreenBrightness({
      success: (res) => {
        originalBrightness = res.value
        wx.setScreenBrightness({ value: 1 })
        wx.setKeepScreenOn({ keepScreenOn: true })
      },
    })
  },

  onHide() {
    wx.setScreenBrightness({ value: originalBrightness })
    wx.setKeepScreenOn({ keepScreenOn: false })
  },

  onUnload() {
    wx.setScreenBrightness({ value: originalBrightness })
    wx.setKeepScreenOn({ keepScreenOn: false })
  },
})
```

适用边界：亮度与常亮只应在扫码、核销等短时强交互页面使用；普通浏览页提亮既打扰又耗电。

误区提醒：

- 提亮后不在 onHide/onUnload 恢复，等于替用户改了系统设置。
- 全局 onShow 里设置常亮，导致整个小程序都不锁屏，严重耗电。

### 10. 电量信息：getBatteryInfo 与低电降级

```typescript
// 异步
wx.getBatteryInfo({
  success: (res) => {
    res.level // 0 ~ 100
    res.isCharging // 是否充电中
  },
})

// 同步版本（谨慎使用）
const info = wx.getBatteryInfoSync()
```

用途是“按需降级”而不是打扰用户：例如检测到低电量（< 20%）且未充电时，降低传感器采样频率、关闭非必要动画、缩短高精度定位超时。

```typescript
export function shouldDegrade(): boolean {
  if (!canUse('getBatteryInfo')) return false
  const info = wx.getBatteryInfoSync()
  return info.level <= 20 && !info.isCharging
}

function startSensors() {
  wx.startAccelerometer({ interval: shouldDegrade() ? 'normal' : 'game' })
}
```

误区提醒：

- 根据电量去限制核心功能（如不让核销）——电量只能用于非关键体验降级，不能影响业务正确性。
- 频繁调用 getBatteryInfoSync：电量变化很慢，进入页面取一次即可。

### 11. 加速度计：摇一摇与高频回调陷阱

```typescript
wx.startAccelerometer({
  interval: 'game', // game(20ms) | ui(60ms) | normal(200ms)
})

wx.onAccelerometerChange((res) => {
  res.x // 左右，-1 ~ 1
  res.y // 上下
  res.z // 垂直方向（静止平放约为 -1 或 1）
})
```

摇一摇的正确姿势：检测瞬时合加速度突变，加冷却时间，触发后立刻反馈。

```typescript
// pages/shake/shake.ts
const SHAKE_THRESHOLD = 22 // 合加速度突变阈值，真机标定
const COOLDOWN_MS = 1500
let lastShakeAt = 0

Page({
  onShow() {
    wx.startAccelerometer({ interval: 'ui' })
    wx.onAccelerometerChange(this.onAccel)
  },

  onHide() {
    wx.stopAccelerometer()
    wx.offAccelerometerChange(this.onAccel)
  },

  onAccel(res: WechatMiniprogram.OnAccelerometerChangeCallbackResult) {
    // 高频回调：这里只做逻辑判断，绝不能每次 setData（跨线程开销大）
    const magnitude = Math.abs(res.x) + Math.abs(res.y) + Math.abs(res.z)
    const now = Date.now()
    if (magnitude > SHAKE_THRESHOLD && now - lastShakeAt > COOLDOWN_MS) {
      lastShakeAt = now
      wx.vibrateShort({ type: 'medium' })
      this.drawCoupon() // 触发抽奖/领券
    }
  },
})
```

阈值必须真机标定：不同机型静止基准不同，建议用“相对静止基线的变化量”而非固定绝对值；页面退出要 stop + off 成对清理。

误区提醒：

- 在 onAccelerometerChange 里 setData 展示实时 x/y/z：每秒触发十几次到几十次跨线程通信，页面迅速卡顿；需要可视化时先节流到 10 次/秒以内。
- 不做冷却，摇一次触发一连串抽奖。

### 12. 罗盘：方向感知与校准提示

```typescript
wx.startCompass()
wx.onCompassChange((res) => {
  res.direction // 面对方向相对正北的角度 0 ~ 360
  res.accuracy // 精度，异常时表示需要校准
})
```

典型用途：详情页“门店在你的西北方向 300 米”这类方位指示。计算目标方位需要经纬度差：

```typescript
// utils/bearing.ts
export function bearingTo(from: LatLng, to: LatLng): number {
  const toRad = (d: number) => (d * Math.PI) / 180
  const toDeg = (r: number) => (r * 180) / Math.PI
  const φ1 = toRad(from.latitude)
  const φ2 = toRad(to.latitude)
  const Δλ = toRad(to.longitude - from.longitude)
  const y = Math.sin(Δλ) * Math.cos(φ2)
  const x =
    Math.cos(φ1) * Math.sin(φ2) - Math.sin(φ1) * Math.cos(φ2) * Math.cos(Δλ)
  return (toDeg(Math.atan2(y, x)) + 360) % 360
}

export function bearingLabel(deg: number): string {
  const dirs = ['北', '东北', '东', '东南', '南', '西南', '西', '西北']
  return dirs[Math.round(deg / 45) % 8]
}
```

当 `accuracy` 异常（磁场干扰），系统会提示用户做“8 字校准”；小程序可提示“请远离强磁场并转动手机校准指南针”。同样，罗盘回调要节流，离开页面 `stopCompass` / `offCompassChange`。

误区提醒：

- 室内磁场环境（电梯、音响附近）方向乱跳时仍把方位当可信信息展示；方位应标注为参考，导航以 openLocation 为准。

### 13. 蓝牙 BLE：完整流程、权限门槛与资源释放

蓝牙是本单元链路最长的能力。典型场景是「逛吃指南」核销成功后连接门店便携打印机出票，或连接蓝牙秤读取重量。标准 BLE 流程：

```text
openBluetoothAdapter（打开适配器、触发授权）
  └─ startBluetoothDevicesDiscovery + onBluetoothDeviceFound（扫描发现）
       └─ stopBluetoothDevicesDiscovery（找到后停止扫描，省电）
            └─ createBLEConnection（建立连接）
                 └─ getBLEDeviceServices（取服务）
                      └─ getBLEDeviceCharacteristics（取特征）
                           ├─ notifyBLECharacteristicValueChange + onBLECharacteristicValueChange（订阅数据）
                           ├─ writeBLECharacteristicValue（下发指令，如打印内容）
                           └─ closeBLEConnection → closeBluetoothAdapter（收尾）
```

参考实现：

```typescript
// services/ble.ts
export function openAdapter(): Promise<void> {
  return new Promise((resolve, reject) => {
    wx.openBluetoothAdapter({ success: () => resolve(), fail: reject })
  })
}

export function findDevice(namePrefix: string, timeoutMs = 10000): Promise<WechatMiniprogram.BluetoothDeviceInfo> {
  return new Promise((resolve, reject) => {
    let done = false
    const finish = (err: Error | null, device?: WechatMiniprogram.BluetoothDeviceInfo) => {
      if (done) return
      done = true
      wx.offBluetoothDeviceFound(handler)
      wx.stopBluetoothDevicesDiscovery()
      err ? reject(err) : resolve(device!)
    }

    const handler = (res: WechatMiniprogram.OnBluetoothDeviceFoundResult) => {
      const device = res.devices.find((d) => (d.name || d.localName || '').startsWith(namePrefix))
      if (device) finish(null, device)
    }

    wx.onBluetoothDeviceFound(handler)
    wx.startBluetoothDevicesDiscovery({ allowDuplicatesKey: false })
    setTimeout(() => finish(new Error('BLE_TIMEOUT')), timeoutMs)
  })
}

export async function connectAndPrint(deviceId: string, payload: string): Promise<void> {
  await wx.createBLEConnection({ deviceId })
  const { services } = await wx.getBLEDeviceServices({ deviceId })
  const serviceId = services[0].uuid // 实际应按设备协议指定目标服务
  const { characteristics } = await wx.getBLEDeviceCharacteristics({ deviceId, serviceId })
  const writable = characteristics.find((c) => c.properties.write)
  if (!writable) throw new Error('NO_WRITABLE_CHARACTERISTIC')

  // 单包长度有限（通常 20 字节），长数据需分片
  const buffer = encodePrintPayload(payload)
  for (const chunk of splitIntoChunks(buffer, 20)) {
    await wx.writeBLECharacteristicValue({
      deviceId,
      serviceId,
      characteristicId: writable.uuid,
      value: chunk.buffer as ArrayBuffer,
    })
  }
}

export function teardown(deviceId: string) {
  wx.closeBLEConnection({ deviceId }).catch(() => {})
  wx.closeBluetoothAdapter().catch(() => {})
}
```

门槛与边界：

- 需要用户打开手机蓝牙，并可能经过微信的蓝牙授权；Android 还涉及附近设备/位置类系统权限（扫描 BLE 在部分安卓版本上要求定位开启）；
- iOS 对蓝牙权限、后台连接有严格限制，离开小程序后连接会被系统挂起；
- 写特征值有单包长度限制（MTU），长内容必须分片；订阅 notify 后数据经 `onBLECharacteristicValueChange` 返回；
- 连接、扫描都是耗电操作，必须在成功/失败/超时所有分支里关闭发现、断开连接、关闭适配器。

决策建议：蓝牙只用于“确定存在专用硬件”的门店侧功能；面向普通消费者的主流程不要依赖蓝牙，否则适配与投诉成本极高。

误区提醒：

- 忘记 stopBluetoothDevicesDiscovery：持续扫描让手机发热耗电，即使已经连上设备。
- 异常分支不释放适配器，用户后续再用蓝牙时状态错乱。
- 一次写入超过 MTU 的数据导致失败，却不知道要分片。

### 14. NFC 与 Wi-Fi：能力边界比用法更重要

这两类能力在普通小程序里使用面很窄，重点是知道它们“能做什么、不能做什么”。

**NFC（近场通信）：**

- 小程序提供的主要是 **HCE 卡模拟** 系列接口：`wx.startHCE`（启动卡模拟）、`wx.onHCEMessage`（接收读卡器发来的指令）、`wx.sendHCEMessage`（返回 APDU 响应）、`wx.stopHCE`、`wx.getHCEState`；
- 典型模式：把手机模拟成一张“卡”，由外部 NFC 读卡器（如门禁、闸机）来读，小程序按协议应答，可用于门店门禁、会员贴卡；
- **仅 Android 支持，iOS 不支持这些接口**，且需要系统 NFC 开启；调用前必须 canIUse 并准备 iOS 降级路径；
- 小程序不能把自己当成通用 NFC 读卡器随意读取任意标签，不要承诺“扫一下 NFC 标签就领券”这类能力。

```typescript
if (wx.canIUse('startHCE')) {
  wx.startHCE({
    aid_list: ['F00102030405060708'],
    success: () => {
      wx.onHCEMessage((message) => {
        // message.data 为读卡器指令，按协议用 sendHCEMessage 应答
        wx.sendHCEMessage({ data: buildApduResponse(message.data) })
      })
    },
  })
}
```

**Wi-Fi：**

- 相关接口包括 `wx.startWifi`、`wx.connectWifi`（按 SSID/密码连接）、`wx.getConnectedWifi`（获取当前连接）、`wx.getWifiList` / `wx.onGetWifiList`（扫描列表）等；
- 典型场景是“线下硬件配网”：门店售卖的智能设备让用户在小程序里输入 Wi-Fi 密码完成配网，或“一键连店内免费 Wi-Fi”；
- 平台限制显著：扫描 Wi-Fi 列表在 Android 上通常要求系统定位服务开启（系统出于隐私对 SSID 的限制），iOS 上 `getWifiList` 基本不可用、`connectWifi` 受系统热点配置能力约束并需要用户确认；
- 不同安卓版本对“静默连接指定 Wi-Fi”权限收紧，多数情况下需要用户确认，无法做到完全无感知。

结论：NFC 与 Wi-Fi 都属于“有明确线下硬件配套才投入”的能力，设计前必须先用目标机型实测，不能只看文档就承诺功能；对逛吃指南主线，使用二维码完成领券/核销是成本与兼容性最优的选择。

误区提醒：

- 认为 iOS/Android 都支持 NFC HCE 或 Wi-Fi 扫描；不做 canIUse 与平台分支直接上线。
- 把 Wi-Fi 列表/连接当成无权限门槛能力，真机上因系统定位/热点权限全面失败。

### 15. 综合落地、权限兜底与上线自查

把本单元能力收敛为「逛吃指南」到店闭环：

```typescript
// pages/coupon-scan/coupon-scan.ts
Page({
  // 用户端：扫码领券
  async onClaim() {
    const scan = await scanOnce(['qrCode'])
    if (!scan) return
    if (scan.kind !== 'coupon') {
      wx.showToast({ title: '不是有效的活动二维码', icon: 'none' })
      return
    }
    try {
      const coupon = await claimCoupon(scan.payload)
      feedbackSuccess()
      this.goCouponDetail(coupon.id)
    } catch (err) {
      feedbackError()
      wx.showToast({ title: (err as Error).message, icon: 'none' })
    }
  },
})

// pages/staff-redeem/staff-redeem.ts
Page({
  // 店员端：扫码 -> 展示券 -> 确认核销
  async onScan() {
    const scan = await scanOnce(['qrCode'])
    if (!scan) return
    const preview = await previewCoupon(scan.payload, this.data.shopId)
    if (!preview.ok) {
      feedbackError()
      return this.showRedeemError(preview.reason)
    }
    this.setData({ coupon: preview.coupon, waitingConfirm: true })
  },

  async onConfirmRedeem() {
    const result = await redeemByScan(this.data.rawScan, this.data.shopId)
    if (result.ok) {
      feedbackSuccess()
      this.setData({ waitingConfirm: false, lastRedeem: result.coupon })
    } else {
      feedbackError()
      this.showRedeemError(result.reason)
    }
  },

  showRedeemError(reason: RedeemResult extends { reason: infer R } ? R : never) {
    const text: Record<string, string> = {
      'not-found': '券码无效',
      used: '该券已核销，请勿重复使用',
      expired: '该券已过期',
      'wrong-shop': '该券不可在本门店使用',
      revoked: '该券已作废',
    }
    wx.showModal({ title: '无法核销', content: text[reason], showCancel: false })
  },
})
```

上线前自查清单：

1. 所有硬件 API 调用前是否做了 canIUse / typeof 判断，并有降级路径；
2. 用户取消扫码、拒绝相机/蓝牙授权、设备未开启三类失败是否分别处理，无白屏；
3. 自定义扫码是否做了连续识别去重，蒙层是否使用 cover-view；
4. 领券/核销是否由服务端裁决，是否有唯一约束与原子条件更新；
5. 核销幂等键在重试中是否保持不变，重复扫码是否返回“已核销”而非再次执行；
6. 网络监听、传感器、蓝牙等是否在页面 onHide/onUnload 成对解绑与释放；
7. 屏幕亮度/常亮是否在离开页面恢复，剪贴板是否只在用户主动操作时读取；
8. 管理后台隐私保护指引是否勾选相机、蓝牙（如使用）等对应项并通过审核；
9. 蓝牙/NFC/Wi-Fi 是否在目标机型实测，iOS 不支持的能力是否已降级。

## 阶段验收作业

本作业是阶段三“平台能力”的收官证据点，重点证明**你能为「逛吃指南」交付“用户扫码领券—店员扫码核销”的到店交易闭环，且把状态裁决、防重复、权限兜底与硬件能力边界处理到位**。

### 任务描述

实现「逛吃指南」扫码券完整链路：

1. 券与码设计：服务端生成随机券码与二维码；二维码只含可校验凭证，面额/有效期等全部服务端查询；券状态含 claimed/used/expired/revoked。
2. 用户领券：扫码（或自定义扫码页）识别、解析、领取；固定幂等键，连点/重试一人一活动只领一张；成功有视觉 + 震动反馈，可在“我的券”查看。
3. 店员核销：店员登录并绑定门店；扫码后先预览券再确认核销；服务端按 claimed + 未过期 + 门店匹配做原子条件更新；五类失败原因明确，重复扫描幂等返回“已核销”信息；核销来源强制实时拍摄。
4. 系统与传感器配合：核销/扫码页按需使用震动、网络状态监听（断网提示、恢复补发）、亮度与常亮（用完恢复）；可选用加速度计实现“摇一摇抽券”。
5. 重硬件边界：对蓝牙/NFC/Wi-Fi 至少完成一次真机能力调研记录（是否支持、所需权限、典型用途），不把它们放入主流程强依赖。
6. 提交不超过 300 字说明：券状态机与防重原理、幂等设计、权限与隐私保护做法、硬件能力边界结论。

### 完成标准

- 真机完整走通“发码 → 用户扫码领取 → 店员扫码核销 → 我的券状态更新”，数据在服务端正确流转；
- 连点、重试、并发双扫、相册截图四种攻击/异常路径下，券都不会被重复领取或重复核销（以服务端记录为准）；
- 已用/过期/非本店/作废/无效五类核销结果提示清晰，重复扫码可查首次核销信息；
- 断网提示与恢复补发正确，监听/传感器/亮度等资源用完即释放恢复；
- TS 类型检查通过，前端无签名密钥，用户隐私保护指引覆盖所用能力。
