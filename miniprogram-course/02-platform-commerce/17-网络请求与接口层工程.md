# 17-网络请求与接口层工程

## 目标

完成本知识单元后，学员应能把「一个请求是怎么从页面发出去、又怎么带着错误与数据回来的」讲清楚，并为「逛吃指南」建立一套可复用的接口层：页面只描述“要什么数据”，鉴权、错误、超时、重试、取消、域名与环境全部在接口层统一解决，而不是在每个页面里复制粘贴 `wx.request`。

学员应能够：

1. 说清 `wx.request` 在小程序双线程模型中的位置：由逻辑层发起、微信原生客户端完成实际网络收发、回调回到逻辑层，渲染层要用响应数据仍需经 `setData` 跨线程传递。
2. 掌握 `wx.request` 全参数：`url`、`data`、`header`、`method`、`timeout`、`dataType`、`responseType` 及 `enableHttp2` 等开关，知道 GET/POST 时 `data` 分别如何被序列化。
3. 用 TypeScript 将回调风格的 `wx.request` Promise 化，写出带泛型的 `request<T>`，并保留 `RequestTask` 以便取消。
4. 设计并落地统一响应结构（如 `code` / `message` / `data` / `traceId`），区分“HTTP 成功”与“业务成功”，用类型而不是 `any` 表达接口契约。
5. 实现请求/响应拦截器：注入鉴权 token 与公共参数、解包响应体、统一处理业务错误码，做到错误统一收敛。
6. 处理 401 与登录态失效：只触发一次重新登录，期间其他请求排队，登录恢复后自动重放，并防止重复弹窗。
7. 实现统一 loading 计数与 toast 策略，避免 loading 不闭合、toast 刷屏；页面可以按需静默。
8. 实现超时与重试：仅对幂等请求、可重试错误做有限次指数退避重试，绝不盲目重试写操作。
9. 使用 `RequestTask.abort()` 取消请求，并实现并发控制（并发上限、信号量队列、重复请求合并），讲清微信对并发请求数量的限制。
10. 说清合法域名规则（管理后台配置、HTTPS、ICP 备案）与开发期“不校验合法域名”的边界，实现开发/测试/生产环境 baseUrl 切换，最终封装 request 模块对接第三方与自建接口。

本单元承接云开发阶段的全栈经验，把“数据从哪来”从云函数调用升级为工程化的接口层，为 U18 的列表搜索与分页提供数据通道。

## 技术栈

本单元使用微信原生能力与 TypeScript 实现接口层，后端可以是自建 Node 服务或任意第三方 HTTPS 接口。

| 工具或环境 | 用途 | 学习要求 |
|---|---|---|
| wx.request | 发起 HTTPS 请求 | 全参数、success/fail/complete 时序 |
| RequestTask | 请求任务对象 | abort、onHeadersReceived、onChunkReceived |
| Promise + TypeScript 泛型 | 异步封装与接口契约 | request&lt;T&gt;、ApiResponse&lt;T&gt;，禁用无意义 any |
| 请求/响应拦截器 | 鉴权、公共参数、错误收敛 | 会设计拦截链并保持顺序 |
| wx.setStorage(Sync) | 保存自定义登录态 token | 知道 token 可本地缓存、密钥绝不放前端 |
| config/env.ts | 多环境 baseUrl 切换 | 配合 __wxConfig.envVersion 自动识别 |
| 微信公众平台 · 服务器域名 | 配置 request 合法域名 | HTTPS、ICP 备案、四类域名分开配置 |
| 自建 Node 接口 / 第三方接口 | 提供业务数据 | 会适配不同响应结构，第三方签名走服务端代理 |
| 微信开发者工具 Network 面板 | 观察请求、重放、限流调试 | 会看 status、header、耗时与失败原因 |

工程约定：

- 所有网络调用必须收敛到 `utils/request` 与 `services/*`，页面与组件不得直接出现裸 `wx.request`。
- 所有错误都要被翻译成统一的 `ApiError`，要么由接口层提示，要么显式抛给业务层，禁止吞掉异常。
- 所有域名数字、超时上限、并发上限以官方文档与管理后台实际规则为准。

## 详细的理论知识讲解和示例伪代码

### 1. 接口层是什么：wx.request 在双线程模型中的位置

小程序运行在双线程模型中：渲染层是一个或多个 WebView，逻辑层是独立的 JavaScript 线程（JsCore）。`wx.request` 由**逻辑层**调用，但真正的 DNS 解析、TLS 握手、HTTP 收发并不在 JsCore 里完成，而是交给**微信原生客户端**的网络模块。响应回来后，回调被投递回逻辑层执行。

```text
页面事件（逻辑层）
   │  调用 wx.request
   ▼
微信原生客户端网络模块（真正发 HTTP）
   │  HTTPS 请求 → 服务器
   │  响应返回
   ▼
success/fail 回调（逻辑层）
   │  this.setData(...)
   ▼
跨线程通信（逻辑层 → 渲染层，序列化）
   ▼
WXML/WXSS 渲染（WebView）
```

这解释了两个高频困惑：

1. **为什么请求回调里直接改 `this.data.xxx` 界面不更新？** 因为数据改在逻辑层，渲染层不知道；必须经 `setData` 跨线程把数据序列化后传过去。
2. **为什么网络请求不会卡住 WebView 动画？** 因为实际收发在原生模块，逻辑层回调只是短时间占用 JsCore；但回调里做重计算仍会让逻辑层卡顿、事件响应变慢。

云开发阶段我们用 `wx.cloud.callFunction` 取数据，平台帮我们处理了鉴权与传输；转向自建/第三方接口后，这些责任落到自己的接口层。接口层的价值是：**把“发请求”这件横切所有页面的事，统一在一个地方做对一次。**

误区提醒：

- “`wx.request` 是在 WebView 里用 XHR/fetch 发的”——错误，逻辑层没有 XHR/fetch，网络由微信原生模块托管。
- “请求成功后界面自动更新”——错误，仍需 `setData` 跨线程，且应只传渲染所需字段。

### 2. wx.request 全参数逐项拆解

一个最朴素的请求：

```typescript
wx.request({
  url: 'https://api.guangchi.example/v1/shops',
  method: 'GET',
  data: { city: '广州', page: 1 },
  header: { 'content-type': 'application/json' },
  timeout: 10000,
  success(res) {
    console.log(res.statusCode, res.data)
  },
  fail(err) {
    console.error(err.errMsg)
  },
  complete() {
    console.log('无论成败都执行')
  },
})
```

关键参数说明：

| 参数 | 类型 | 含义与注意点 |
|---|---|---|
| `url` | string | 必须是完整 URL；正式环境域名须在管理后台 request 合法域名列表中 |
| `data` | string/object/ArrayBuffer | GET/HEAD 时拼为 query string；POST 默认按 JSON 放入 body |
| `header` | object | 请求头；`Referer` 等头不可设置；`content-type` 决定 data 序列化方式 |
| `method` | string | GET/POST/PUT/DELETE/PATCH/HEAD/OPTIONS 等，默认 GET |
| `timeout` | number | 超时毫秒数；默认值 60000，设置上限以官方文档为准 |
| `dataType` | string | `json`（默认）时对响应体做 JSON.parse；其他值原样返回字符串 |
| `responseType` | string | `text`（默认）或 `arraybuffer`，下载二进制时用后者 |
| `enableHttp2` | boolean | 是否尝试 HTTP/2，需服务端支持 |
| `enableQuic` | boolean | 是否尝试 QUIC，需服务端与网络支持 |
| `enableCache` | boolean | 是否开启 HTTP 缓存语义 |
| `success` / `fail` / `complete` | function | 回调三件套，complete 一定执行 |

`data` 的序列化规则要记牢：

- GET 请求不能带 body，`data` 会被编码成 `?city=%E5%B9%BF%E5%B7%9E&page=1`；
- POST 请求若 `header['content-type']` 为 `application/json`（默认），`data` 以 JSON 字符串发送；
- POST 请求若显式设为 `application/x-www-form-urlencoded`，`data` 会被编码成表单键值对。

`success` 回调结果结构：

```typescript
interface RequestResult {
  data: string | object | ArrayBuffer // 由 dataType / responseType 决定
  statusCode: number // HTTP 状态码
  header: object // 响应头
  cookies: string[] // 响应中的 Set-Cookie（基础库支持时）
  profile?: object // 各阶段耗时，用于性能分析
  totalDataSize?: number
}
```

**重要：只要服务器有 HTTP 响应回来（哪怕是 404、500），都走 `success`；只有网络层失败（超时、断网、abort、域名不合法）才走 `fail`。** 因此不能用 success/fail 判断业务成败。

误区提醒：

- “statusCode 200 就是成功”——不完整，还要看响应体里的业务码 `code`。
- “401/500 会走 fail”——错误，它们是有效 HTTP 响应，走 success，要自行检查 `statusCode`。
- 忘记 `dataType` 默认是 json：服务端返回非 JSON 时解析结果可能为字符串或异常。

### 3. Promise 化封装：从回调到 request&lt;T&gt;

回调风格在连续异步、错误处理上很痛苦。`wx.request` 的返回值是 `RequestTask`（用于 abort），本身不是 Promise，因此标准做法是手写封装，同时暴露 Promise 与 task：

```typescript
// utils/request/core.ts

export type HttpMethod =
  | 'GET'
  | 'POST'
  | 'PUT'
  | 'DELETE'
  | 'PATCH'
  | 'HEAD'
  | 'OPTIONS'

export interface RequestConfig {
  url: string
  method?: HttpMethod
  data?: Record<string, unknown> | string | ArrayBuffer
  header?: Record<string, string>
  timeout?: number
  /** 是否静默（不弹 toast、不显示全局 loading） */
  silent?: boolean
  /** 失败时是否自动重试 */
  retry?: number
}

export interface RequestOutput<T> {
  task: wx.RequestTask
  promise: Promise<T>
}

export function dispatch<T = unknown>(config: RequestConfig): RequestOutput<T> {
  const task = wx.request({
    url: config.url,
    method: config.method ?? 'GET',
    data: config.data as Record<string, unknown>,
    header: config.header,
    timeout: config.timeout,
    success() {},
    fail() {},
  })

  const promise = new Promise<T>((resolve, reject) => {
    task.onHeadersReceived(() => {})
    // wx.request 只允许一个 success/fail，需要在回调里改写逻辑，
    // 因此实际工程中把 resolve/reject 提到外层闭包：
    const raw = wx.request({
      url: config.url,
      method: config.method ?? 'GET',
      data: config.data as Record<string, unknown>,
      header: config.header,
      timeout: config.timeout,
      success: (res) => resolve(normalize<T>(res, config)),
      fail: (err) => reject(toError(err, config)),
    })
    // 用第二次调用的 task 覆盖，保证 abort 命中真实请求
    output.task = raw
  })

  const output: RequestOutput<T> = { task, promise }
  return output
}

function normalize<T>(
  res: WechatMiniprogram.RequestSuccessCallbackResult,
  config: RequestConfig,
): T {
  // 占位：第 6 节实现完整的响应解包
  return res.data as T
}

function toError(
  err: WechatMiniprogram.RequestFailCallbackResult,
  config: RequestConfig,
): ApiError {
  return new ApiError(err.errMsg, 'NETWORK_ERROR')
}
```

上面为了同时拿到 task 与 Promise 用了两次调用，仅用于说明结构。**真实实现不要发两次请求**，规范写法是把 `resolve/reject` 提前声明：

```typescript
export function dispatch<T = unknown>(config: RequestConfig): RequestOutput<T> {
  let resolveFn!: (value: T) => void
  let rejectFn!: (reason: ApiError) => void

  const promise = new Promise<T>((resolve, reject) => {
    resolveFn = resolve
    rejectFn = reject
  })

  const task = wx.request({
    url: config.url,
    method: config.method ?? 'GET',
    data: config.data as Record<string, unknown>,
    header: config.header,
    timeout: config.timeout,
    success: (res) => {
      try {
        resolveFn(normalize<T>(res, config))
      } catch (err) {
        rejectFn(err as ApiError)
      }
    },
    fail: (err) => rejectFn(toError(err, config)),
  })

  return { task, promise }
}
```

要点：

1. Promise 化后可以 `async/await`，错误用 `try/catch` 或 `.catch` 统一处理。
2. 泛型 `T` 让调用方拿到精确类型：`const list = await get<ShopCard[]>(...)`。
3. 必须同时保留 `RequestTask`，否则无法 abort，也就无法解决 U18 的搜索竞态。

### 4. 统一响应结构与类型契约

和后端约定一个统一信封，是错误统一收敛的前提。「逛吃指南」自建接口采用：

```typescript
// types/api.ts

/** 成功的统一响应体 */
export interface ApiEnvelope<T> {
  code: number // 0 表示业务成功，非 0 为业务错误码
  message: string // 面向开发者或可直接展示的文案
  data: T // 真正的业务数据
  traceId?: string // 服务端链路追踪 id，排障必备
}

/** 分页数据的统一结构（U18 大量使用） */
export interface PageResult<T> {
  list: T[]
  page: number
  pageSize: number
  total: number
  hasMore: boolean
}
```

一次成功响应示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "list": [{ "id": "shop_1", "name": "阿婆牛杂" }],
    "page": 1,
    "pageSize": 20,
    "total": 56,
    "hasMore": true
  },
  "traceId": "a1b2c3d4"
}
```

统一错误类型：

```typescript
// utils/request/error.ts

export type ApiErrorCode =
  | 'HTTP_ERROR' // 有 HTTP 响应但状态码非 2xx
  | 'BIZ_ERROR' // HTTP 2xx 但业务码非 0
  | 'TIMEOUT' // 超时
  | 'ABORTED' // 被主动取消
  | 'NETWORK_ERROR' // 断网、DNS、域名不合法等
  | 'UNAUTHORIZED' // 401 未登录/登录失效

export class ApiError extends Error {
  readonly kind: ApiErrorCode
  readonly bizCode?: number
  readonly statusCode?: number
  readonly traceId?: string
  /** 是否已经被接口层提示过（避免页面重复 toast） */
  handled: boolean = false

  constructor(
    message: string,
    kind: ApiErrorCode,
    extra?: {
      bizCode?: number
      statusCode?: number
      traceId?: string
    },
  ) {
    super(message)
    this.name = 'ApiError'
    this.kind = kind
    this.bizCode = extra?.bizCode
    this.statusCode = extra?.statusCode
    this.traceId = extra?.traceId
  }
}
```

三层成败必须分清：

1. **网络层**：断网/超时/abort → `fail`；
2. **HTTP 层**：有响应但 `statusCode` 不是 2xx（401、403、404、500）；
3. **业务层**：HTTP 2xx，但信封里 `code !== 0`（如“店铺已下架”“余额不足”）。

误区提醒：

- 只判 HTTP 不判业务码，会把“查询成功但业务被拒绝”当成功渲染。
- 直接把 `message` 当稳定分支条件——文案会改，分支判断必须用 `code`。

请求拦截器负责在发送前改写配置：拼接 baseUrl、注入 token、加公共参数与标识头。

```typescript
// utils/request/interceptors/request.ts
import { ENV } from '../../../config/env'
import { getToken } from '../../auth'
import type { RequestConfig } from '../core'

type RequestInterceptor = (
  config: RequestConfig,
) => RequestConfig | Promise<RequestConfig>

/** 拼接完整 URL，并带上公共参数 */
const withBaseUrl: RequestInterceptor = (config) => {
  const url = config.url.startsWith('http')
    ? config.url
    : `${ENV.baseUrl}${config.url}`
  return { ...config, url }
}

/** 注入鉴权 token 与基础请求头 */
const withAuth: RequestInterceptor = (config) => {
  const token = getToken()
  const header: Record<string, string> = {
    'content-type': 'application/json',
    'x-client': 'wechat-miniprogram',
    ...config.header,
  }
  if (token) header.Authorization = `Bearer ${token}`
  return { ...config, header }
}

export const requestInterceptors: RequestInterceptor[] = [
  withBaseUrl,
  withAuth,
]
```

token 的读取与保存（U12 的存储工具）：

```typescript
// utils/auth.ts
import { get, set, remove } from './storage'

const TOKEN_KEY = 'access_token'

export function getToken(): string {
  return get<string>(TOKEN_KEY, '')
}

export function setToken(token: string): void {
  set(TOKEN_KEY, token)
}

export function clearToken(): void {
  remove(TOKEN_KEY)
}
```

安全边界再次强调：**前端可以保存“后端颁发给当前用户的登录令牌（token）”，但绝不能放 AppSecret、私钥、第三方地图/支付密钥。** 小程序代码包可被解包提取，写在源码、Storage、globalData 里的密钥等于公开。需要用密钥签名的请求，应由自建后端签名后转发（见第 15 节）。

### 6. 请求模块（二）：响应拦截器与错误统一收敛

响应拦截器负责“解包信封 + 翻译错误”，业务层只拿到 `data`。

```typescript
// utils/request/interceptors/response.ts
import { ApiError } from '../error'
import type { ApiEnvelope } from '../../../types/api'
import type { RequestConfig } from '../core'

export function parseResponse<T>(
  res: WechatMiniprogram.RequestSuccessCallbackResult,
  config: RequestConfig,
): T {
  const { statusCode, data: raw } = res

  // 第一层：HTTP 状态码
  if (statusCode < 200 || statusCode >= 300) {
    throw new ApiError(`请求失败（${statusCode}）`, 'HTTP_ERROR', {
      statusCode,
    })
  }

  const envelope = raw as ApiEnvelope<T>

  // 防御：服务端未按约定返回信封
  if (
    envelope === null ||
    typeof envelope !== 'object' ||
    typeof (envelope as ApiEnvelope<T>).code === 'undefined'
  ) {
    // 某些第三方接口直接返回裸数据，可在 adapter 中处理（第 15 节）
    return raw as T
  }

  // 第二层：业务码
  if (envelope.code !== 0) {
    throw new ApiError(envelope.message || '业务异常', 'BIZ_ERROR', {
      bizCode: envelope.code,
      traceId: envelope.traceId,
    })
  }

  return envelope.data
}
```

统一错误提示（收敛在一个地方，页面可 `silent`）：

```typescript
// utils/request/handler.ts
import { ApiError } from './error'
import { clearToken } from '../auth'

export function handleError(error: unknown, silent: boolean): ApiError {
  const apiError =
    error instanceof ApiError ? error : new ApiError('未知错误', 'NETWORK_ERROR')

  if (silent || apiError.handled) return apiError

  let title = apiError.message
  switch (apiError.kind) {
    case 'TIMEOUT':
      title = '请求超时，请稍后再试'
      break
    case 'NETWORK_ERROR':
      title = '网络连接失败，请检查网络'
      break
    case 'ABORTED':
      // 主动取消通常不应打扰用户
      return apiError
    case 'UNAUTHORIZED':
      title = '登录已失效，请重新登录'
      clearToken()
      break
    default:
      title = apiError.message || '服务开小差了'
  }

  wx.showToast({ title, icon: 'none', duration: 2000 })
  apiError.handled = true
  return apiError
}
```

工程含义：页面里不会再出现十几个不同的错误分支，所有失败都以同一个 `ApiError` 形态出现，提示策略统一；页面确有特殊处理（如“余额不足”引导充值）时，判断 `apiError.bizCode`。

误区提醒：

- 在拦截器里 `console.error` 后不 rethrow，等于吞异常，页面会一直转圈。
- 对每个请求都弹 toast，弱网下连续失败会刷屏——silent 与节流要配套。

### 7. 401：单次重新登录、排队与请求重放

登录态失效是最需要全局协作的错误。错误做法是每个 401 都弹一次登录；正确做法是引入“刷新中”状态与等待队列：

```typescript
// utils/auth/session.ts
import { getToken, setToken, clearToken } from '../auth'
import { http } from '../request'

let isRefreshing = false
let waitQueue: Array<{
  resolve: () => void
  reject: (err: unknown) => void
}> = []

/** 走 wx.login 静默换发新 token（后端校验 code，见鉴权单元） */
async function refreshLogin(): Promise<void> {
  const { code } = await wx.login()
  const res = await http.post<{ token: string }>('/auth/login', { code }, {
    silent: true,
  })
  setToken(res.token)
}

/** 保证同一时刻只有一次登录流程，返回后队列全部重放 */
export async function ensureLogin(): Promise<void> {
  if (getToken()) return

  if (!isRefreshing) {
    isRefreshing = true
    try {
      await refreshLogin()
      isRefreshing = false
      flushQueue()
    } catch (err) {
      isRefreshing = false
      rejectQueue(err)
      clearToken()
      throw err
    }
    return
  }

  // 已有登录在进行：排队等待
  return new Promise<void>((resolve, reject) => {
    waitQueue.push({ resolve, reject })
  })
}

function flushQueue(): void {
  waitQueue.forEach((item) => item.resolve())
  waitQueue = []
}

function rejectQueue(err: unknown): void {
  waitQueue.forEach((item) => item.reject(err))
  waitQueue = []
}
```

在响应处理中拦截 401（改造第 6 节的 HTTP 分支）：

```typescript
if (statusCode === 401) {
  const authError = new ApiError('登录已失效', 'UNAUTHORIZED', { statusCode })
  try {
    await ensureLogin()
    // 登录恢复后由调用方决定是否重放；常见做法是在 request 外壳里自动重试一次
  } catch {
    throw authError
  }
}
```

更完整的外壳策略：401 且本次未重试过 → `ensureLogin()` → 用原配置重发一次；仍 401 → 抛错。注意给 `RequestConfig` 加内部字段 `_retried401?: boolean`，防止无限重放。

要点：

1. 无论多少接口同时 401，只触发一次登录，其余排队，恢复后一起重放。
2. `wx.login` 的 `code` 只能由后端配合 AppSecret 换 session，**AppSecret 在服务端**，前端永远接触不到。
3. 静默登录失败再考虑引导用户操作（手机号/重新进入），不要在首页连环弹窗。

### 8. 统一 loading：请求计数与闭合

全局 loading 最大的坑是“多个请求并发，先回来的把 loading 关了，其他请求还在飞”。用计数器解决：

```typescript
// utils/request/loading.ts

let activeCount = 0

export function beginLoading(): void {
  if (activeCount === 0) {
    wx.showLoading({ title: '加载中', mask: true })
  }
  activeCount += 1
}

export function endLoading(): void {
  activeCount = Math.max(0, activeCount - 1)
  if (activeCount === 0) wx.hideLoading()
}
```

在请求外壳里成对调用（complete 语义）：

```typescript
async function withLoading<T>(
  config: RequestConfig,
  run: () => Promise<T>,
): Promise<T> {
  if (!config.silent) beginLoading()
  try {
    return await run()
  } finally {
    if (!config.silent) endLoading()
  }
}
```

实践策略：

- 首屏数据、提交类操作走全局 loading（mask 防重复点击）；
- 分页加载更多用列表底部的小 loading，不用全局遮罩（U18）；
- 后台静默刷新（如预取）设 `silent: true`；
- 提交按钮还应配合按钮自身 loading/disabled，双保险防重复提交。

误区提醒：

- 只在 success 里 `hideLoading`，失败时 loading 永久转圈——必须放 finally。
- 混用 `wx.showToast` 与 `wx.hideLoading`：二者在部分版本互斥，注意调用顺序。

### 9. 超时与重试：幂等、退避与抖动

重试必须满足两个前提：**请求幂等**（同样参数执行多次结果一致）且**错误可安全重试**。

| 错误类型 | 是否重试 | 理由 |
|---|---|---|
| 超时 | 可重试 | 请求可能没到服务端，也可能已执行，需接口幂等 |
| 网络连接失败 | 可重试 | 通常未到达服务端 |
| 502/503/504 | 谨慎重试 | 服务端可能已处理，GET 相对安全 |
| 400/401/403/404 | 不重试 | 参数或权限问题，重试无意义（401 走登录流程） |
| POST 下单/支付 | 绝不自动重试 | 可能重复创建、重复扣款，必须靠幂等键由业务控制 |

退避实现：

```typescript
// utils/request/retry.ts

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms))

/** 指数退避 + 随机抖动，避免大量客户端同时重试压垮服务端 */
function backoffDelay(attempt: number, base = 500): number {
  const exp = base * 2 ** attempt // 500ms、1s、2s...
  const jitter = Math.random() * base
  return Math.min(exp + jitter, 5000)
}

export function isRetryable(error: unknown, method: string): boolean {
  if (method !== 'GET' && method !== 'HEAD') return false
  if (!(error instanceof ApiError)) return false
  return (
    error.kind === 'TIMEOUT' ||
    error.kind === 'NETWORK_ERROR' ||
    error.statusCode === 502 ||
    error.statusCode === 503 ||
    error.statusCode === 504
  )
}

export async function withRetry<T>(
  config: RequestConfig,
  run: () => Promise<T>,
): Promise<T> {
  const maxRetry = config.retry ?? 0
  let lastError: unknown

  for (let attempt = 0; attempt <= maxRetry; attempt += 1) {
    try {
      return await run()
    } catch (err) {
      lastError = err
      if (attempt >= maxRetry || !isRetryable(err, config.method ?? 'GET')) {
        throw err
      }
      await sleep(backoffDelay(attempt))
    }
  }
  throw lastError
}
```

超时还要分层：接口层默认超时要短于微信默认值，让用户更快得到反馈；`wx.request` 的 timeout 到点会触发 fail（errMsg 含 timeout），可被识别为 `TIMEOUT`。

### 10. RequestTask.abort：取消请求

`wx.request` 返回的 `RequestTask` 支持 `abort()`，调用后请求中断，fail 回调触发，`err.errMsg` 为 `request:fail abort`。典型场景：离开页面、搜索关键词变化、切换筛选条件时废弃旧请求。

```typescript
// utils/request/cancel.ts

export class CancelRegistry {
  private tasks = new Map<string, wx.RequestTask>()

  add(key: string, task: wx.RequestTask): void {
    this.tasks.get(key)?.abort()
    this.tasks.set(key, task)
  }

  cancel(key: string): void {
    const task = this.tasks.get(key)
    if (task) {
      task.abort()
      this.tasks.delete(key)
    }
  }

  cancelAll(): void {
    this.tasks.forEach((task) => task.abort())
    this.tasks.clear()
  }
}

export function isAbortError(err: unknown): boolean {
  return err instanceof ApiError && err.kind === 'ABORTED'
}
```

把 abort 错误识别出来（改写第 3 节 `toError`）：

```typescript
function toError(
  err: WechatMiniprogram.RequestFailCallbackResult,
): ApiError {
  if (/abort/.test(err.errMsg)) {
    return new ApiError('请求已取消', 'ABORTED')
  }
  if (/timeout/.test(err.errMsg)) {
    return new ApiError('请求超时', 'TIMEOUT')
  }
  return new ApiError(err.errMsg, 'NETWORK_ERROR')
}
```

页面中的用法（U18 会系统化展开）：

```typescript
const cancelRegistry = new CancelRegistry()

Page({
  onSearch(keyword: string) {
    const { task, promise } = http.get('/shops', { keyword })
    cancelRegistry.add('search', task)
    promise.then((data) => this.setData({ shops: data.list })).catch(() => {})
  },
  onUnload() {
    cancelRegistry.cancelAll() // 离开页面，全部废弃，避免回调操作已销毁页面
  },
})
```

要点：abort 后的错误通常要**静默**，它不是“失败”，而是“这个响应我们不要了”。回调里仍可能有收尾逻辑，因此页面卸载时配合标志位判断更稳。

### 11. 并发控制：数量上限、信号量与请求合并

微信对同时进行的网络请求有**并发数量上限**（`wx.request`、上传、下载共享微信侧限制，常见上限为 10 个，以官方文档为准）。首屏一次性发出十几个请求时，超出部分会排队甚至超时失败，因此我们在接口层自己做信号量：

```typescript
// utils/request/semaphore.ts

class Semaphore {
  private running = 0
  private waiters: Array<() => void> = []

  constructor(private readonly max: number) {}

  async acquire(): Promise<void> {
    if (this.running < this.max) {
      this.running += 1
      return
    }
    await new Promise<void>((resolve) => {
      this.waiters.push(resolve)
    })
    this.running += 1
  }

  release(): void {
    this.running -= 1
    const next = this.waiters.shift()
    if (next) next()
  }
}

export const networkSemaphore = new Semaphore(8) // 预留 2 个给上传/下载等
```

在请求外壳包裹：

```typescript
await networkSemaphore.acquire()
try {
  result = await rawRequest(config)
} finally {
  networkSemaphore.release()
}
```

**重复请求合并**也很实用：同一个 GET 短时间内被多处调用（如多个组件都要城市配置），只发一次，共享 Promise：

```typescript
// utils/request/dedup.ts

const inflight = new Map<string, Promise<unknown>>()

export async function withDedup<T>(
  key: string,
  run: () => Promise<T>,
): Promise<T> {
  const existing = inflight.get(key)
  if (existing) return existing as Promise<T>

  const promise = run().finally(() => inflight.delete(key))
  inflight.set(key, promise)
  return promise
}
```

要点：

1. 信号量让“瞬间几十个请求”变成“最多 N 个在飞”，保护弱网与服务端；
2. 合并的 key 要包含 URL + 关键参数，POST 默认不合并；
3. 请求结束（成功或失败）都必须释放/删 key，否则槽位泄漏，后续全部卡死。

误区提醒：

- “超限的请求微信会自动完美排队”——不要依赖黑盒行为，接口层自控才可控、可测。
- 忘记在失败分支 release，信号量会被慢慢耗尽。

### 12. 合法域名：HTTPS、ICP 备案与管理后台配置

小程序出于安全考虑，**正式环境只允许与预先登记的域名通信**。配置入口：微信公众平台（mp.weixin.qq.com）→「开发」→「开发管理/开发设置」→「服务器域名」。

四类域名分别配置：

| 类别 | 对应 API |
|---|---|
| request 合法域名 | wx.request |
| socket 合法域名 | wx.connectSocket |
| uploadFile 合法域名 | wx.uploadFile |
| downloadFile 合法域名 | wx.downloadFile |

硬性规则：

1. 必须 **HTTPS**（TLS），不允许 HTTP；TLS 版本需满足平台最低要求；
2. 域名必须完成 **ICP 备案**，且备案主体等信息需符合平台要求；
3. 只支持域名，**不支持 IP 地址与 localhost**；一般走标准 443，不支持自定义端口（以文档为准）；
4. 配置到域名级别，不包含路径；可配置多个，数量有上限；
5. 域名列表**每月可修改次数有限**，上线前应规划好域名，不要临时更换；
6. 开发、测试、生产环境要用的域名都要登记（例如 `dev-api`、`boe-api`、`api` 三个子域）。

配置后若仍报 `url not in domain list`：重新编译/重启小程序确认配置已下发，并检查是否误配到其他类别（如把 request 域名配到了 uploadFile）。

误区提醒：

- “先上线再补域名”——正式版请求会直接失败，域名是上线前置条件。
- 把测试 IP、内网域名当成可以长期使用的正式域名。

### 13. 开发期“不校验合法域名”的边界

微信开发者工具提供本地开关：「详情 → 本地设置 → 不校验合法域名、web-view（业务域名）、TLS 版本以及 HTTPS 证书」。开启后，开发工具里可以请求任意域名、自签名证书、HTTP 接口，便于本地联调。

必须清楚它的边界：

1. **仅对开发者工具生效**；真机预览、真机调试、体验版、正式版都不生效，一律按服务器域名白名单校验；
2. 不能把它当成解决方案，更不能在代码、文档里写“勾选这个就能用”交付给用户；
3. 常见正确用途：本地后端（如 `http://localhost:3000`）联调、临时验证第三方接口、证书未就绪时的早期开发；
4. 用它调通第三方域名后，正式方案仍然是：让后端配置代理 + 登记自己的 HTTPS 域名，或直接登记第三方域名（需对方支持且符合合规）。

一个团队协作细节：这个开关是**每个人本机的设置**，不会随项目同步。新人拉代码后接口全挂，多半是没勾这个开关或没配本地环境；应在项目说明里写清“仅开发期使用，正式环境不依赖”。

误区提醒：

- “我在工具里能请求，上线肯定没问题”——两回事，真机立即打回原形。
- 长期靠这个开关对接未备案域名，掩盖合规问题直到上线暴雷。

### 14. 多环境 baseUrl 切换

第 5 节用 `__wxConfig.envVersion` 自动识别环境：开发版为 `develop`、体验版为 `trial`、正式版为 `release`。这样同一份代码在不同版本自动指向不同后端，避免把测试地址带到线上。

工程上还要注意：

```typescript
// 调试期临时强制环境（仅在特殊排障时使用，禁止提交到主分支）
// const FORCE_ENV: keyof typeof ENV_MAP = 'develop'
```

1. **默认零配置**：开发者工具自动走 develop，体验版走 trial，正式版走 release，不靠人工切换；
2. **不向用户暴露环境切换入口**，测试环境切换只通过开发者工具的“编译模式/自定义条件”；
3. 环境配置集中在一个文件，baseUrl、超时、是否打印日志都从这里出；
4. 第三方 key、第三方 baseUrl 同样按环境区分，但**key 本身（密钥）不在前端**，前端只访问自建后端的代理路径。

判断“当前到底打到了哪个环境”最直接的方法：看 Network 面板里请求的域名，或在开发期日志中打印 `ENV.name`。

```typescript
// utils/request/index.ts
import { dispatch } from './core'
import { networkSemaphore } from './semaphore'
import { withRetry } from './retry'
import { handleError } from './handler'
import { beginLoading, endLoading } from './loading'
import type { RequestConfig } from './core'

async function request<T>(config: RequestConfig): Promise<T> {
  if (!config.silent) beginLoading()
  try {
    await networkSemaphore.acquire()
    return await withRetry(config, () => dispatch<T>(config).promise)
  } catch (err) {
    throw handleError(err, config.silent ?? false)
  } finally {
    networkSemaphore.release()
    if (!config.silent) endLoading()
  }
}

export const http = {
  get<T>(url: string, data?: Record<string, unknown>, extra?: Partial<RequestConfig>) {
    return request<T>({ url, method: 'GET', data, ...extra })
  },
  post<T>(url: string, data?: Record<string, unknown>, extra?: Partial<RequestConfig>) {
    return request<T>({ url, method: 'POST', data, ...extra })
  },
  put<T>(url: string, data?: Record<string, unknown>, extra?: Partial<RequestConfig>) {
    return request<T>({ url, method: 'PUT', data, ...extra })
  },
  delete<T>(url: string, data?: Record<string, unknown>, extra?: Partial<RequestConfig>) {
    return request<T>({ url, method: 'DELETE', data, ...extra })
  },
}
```

第三方接口适配：第三方响应结构往往不是我们的信封（例如地图 POI 搜索返回 `status` / `message` / `data`）。**不要在前端适配密钥**，而是请求自建后端的代理路径，由后端完成签名，再可以选择在后端统一转成我们的信封，或前端做一层 adapter：

```typescript
// services/poi.ts
import { http } from '../utils/request'

interface ThirdPoiResult {
  status: number // 0 为成功
  message: string
  data: Array<{ id: string; title: string; address: string; location: { lat: number; lng: number } }>
}

export async function searchNearbyPoi(keyword: string, lat: number, lng: number) {
  // 密钥与签名由后端 /proxy/tencent-map 完成，前端无密钥
  const res = await http.get<ThirdPoiResult>(
    '/proxy/tencent-map/place/v1/search',
    { keyword, boundary: `nearby(${lat},${lng},1000)` },
    { silent: true },
  )
  if (res.status !== 0) throw new Error(res.message)
  return res.data
}
```

**接口层上线前自查清单：**

1. 页面/组件中是否已无裸 `wx.request`，全部经 `services` → `http`；
2. 三层成败（网络/HTTP/业务）是否都有处理，无吞异常；
3. 401 是否只登录一次、可重放；loading 是否在 finally 闭合；
4. 重试是否仅限幂等请求；abort 错误是否静默；
5. 信号量/合并缓存是否在失败时也释放；
6. 正式域名是否已在管理后台登记并 HTTPS、ICP 备案；
7. 源码、Storage、截图中是否确认无任何密钥。

## 实践练习题

### 练习 1：封装 Promise 化的 request 基础模块

#### 任务

实现 `utils/request` 基础模块：`wx.request` Promise 化、泛型 `http.get/post`、统一 `ApiEnvelope<T>` 解包、`ApiError` 与基础 toast，页面通过 `services/shop.ts` 调用，不出现裸 `wx.request`。

参考代码：

```typescript
// services/shop.ts
export function listShops(page: number, pageSize: number) {
  return http.get<PageResult<ShopCard>>('/v1/shops', { page, pageSize })
}

// 页面中
const res = await listShops(1, 20)
this.setData({ shops: res.list })
```

#### 步骤约束

1. `dispatch` 只允许发起一次真实请求，resolve/reject 用外层闭包持有。
2. 必须依次处理 HTTP 状态码与业务码，非 0 业务码抛出含 `bizCode` 的 `ApiError`。
3. 提供 `silent` 选项；abort、timeout、普通网络错误要能被区分。
4. 服务端返回非约定结构时要有防御，不得直接白屏。

#### 提交物

- `utils/request/*`、`types/api.ts`、`services/shop.ts`；
- 成功、业务错误、网络错误三种场景的 Network 截图与页面表现截图；
- 200 字以内的模块说明。

#### 验收标准

- 页面中无裸 `wx.request`；
- 业务码非 0 时能拿到带 bizCode 的错误并给出提示；
- 成功路径返回类型精确，无滥用 any；
- 三种错误在界面上表现可区分、不崩溃。

### 练习 2：401 单次登录重放 + loading 计数

#### 任务

在练习 1 基础上实现登录态治理：并发制造多个需要鉴权的请求，服务端先返回 401；要求只触发一次登录恢复，所有请求在恢复后自动成功重放；loading 在整个过程中只出现一次且正确闭合。

参考伪代码：

```text
请求 A、B、C 同时发出 → 全部 401
A 触发 ensureLogin（isRefreshing=true）
B、C 进入 waitQueue
登录成功 → flushQueue → A/B/C 用原参数重放
```

#### 步骤约束

1. 用标志位保证同一时刻只有一个登录流程，禁止重复登录或重复弹窗。
2. 每个 401 请求最多自动重放一次，需有防重放字段。
3. loading 用计数器在 finally 闭合，模拟“一个先失败、其余成功”也不能残留遮罩。
4. 登录恢复失败时队列要被 reject，不得永久挂起。

#### 提交物

- `session.ts`、拦截器改造代码；
- 并发 401 → 单次登录 → 全部重放的录屏；
- 说明 AppSecret 为什么必须在服务端。

#### 验收标准

- 多个 401 只产生一次登录请求；
- 队列请求重放后业务数据正确；
- 任何失败路径下 loading 都能闭合、队列不泄漏；
- 代码中无 AppSecret 等机密。

### 练习 3：超时重试、请求取消与并发队列

#### 任务

为 request 模块增加三项韧性能力：幂等 GET 的有限次指数退避重试；`RequestTask.abort()` 取消（页面卸载/手动触发）；信号量把在飞请求控制在 8 个以内，并对同一 GET 做 in-flight 合并。

参考代码：

```typescript
http.get('/v1/config', undefined, { retry: 2 }) // 最多再试 2 次
cancelRegistry.cancel('search')                // 取消指定请求
await networkSemaphore.acquire()               // 并发槽
```

#### 步骤约束

1. 重试只对 GET/HEAD 且错误为超时/网络错误/502/503/504 生效，POST 不重试。
2. 退避需带抖动并设置上限；通过可切换的模拟接口制造超时验证。
3. abort 触发的错误标记为 ABORTED 并默认静默，不弹 toast。
4. 信号量在成功与失败路径都必须 release；合并缓存用 finally 清理。

#### 提交物

- `retry.ts`、`cancel.ts`、`semaphore.ts`、`dedup.ts`；
- 重试时序日志、取消录屏、并发计数日志（证明峰值不超过 8）；
- 弱网（开发者工具网络限速）下的验证结果。

#### 验收标准

- 重试次数与退避时序符合配置，错误不可重试时立即抛出；
- 取消后无回调写入已销毁页面；
- 瞬时批量请求时峰值在飞数不超过 8，相同 GET 实际只发一次；
- 无槽位泄漏与缓存悬挂。
