## 学习目标

- 能把唯一性、引用关系和业务状态落实为数据库约束。
- 能复现并发冲突，解释隔离级别并选择重试策略。
- 能用查询计划证明索引收益和代价。

## 内容讲解

### 1. 先确定实体和不变量

文章、作者、标签和关联表是独立实体。用外键保持关联，用唯一约束保证业务 ID，用 CHECK 限制局部状态：

```sql
CREATE TABLE article_lab (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner_id bigint NOT NULL,
  title text NOT NULL CHECK (length(title) BETWEEN 1 AND 100),
  status text NOT NULL CHECK (status IN ('draft', 'published')),
  revision integer NOT NULL DEFAULT 1 CHECK (revision > 0),
  created_at timestamptz NOT NULL DEFAULT now()
);
```

仅用于本地空练习库。实际 owner_id 还需关联用户外键，多租户必须设计 tenant_id 及每次查询过滤。数据库约束能覆盖多个调用方，前端表单校验不能替代它。

### 2. 乐观并发

```sql
UPDATE article_lab
SET title = $1, revision = revision + 1
WHERE id = $2 AND revision = $3
RETURNING revision;
```

返回 0 行表示不存在或版本冲突，服务端按授权与资源状态分类，不能无条件重试覆盖。用两个会话读 revision=1，第一个更新后，第二个携带 revision=1 应更新不到。

### 3. 隔离级别

PostgreSQL Read Committed 每个语句读取其开始时的已提交快照；同一事务的连续查询可看见不同结果。Repeatable Read 保持事务快照，但仍可能出现不能串行化的业务异常。Serializable 以检测冲突等机制实现串行语义，可能要求重试整个事务。

PostgreSQL 将 Read Uncommitted 按 Read Committed 处理，不能照搬其他数据库脏读实验。

锁定同一资源可用 `SELECT ... FOR UPDATE`，多个资源按固定顺序取锁减少死锁。遇到 serialization/deadlock 类错误，用有界重试重新执行整个事务，外部支付/消息不能在可重试事务里重复产生副作用。

### 4. 查询计划

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title
FROM article_lab
WHERE owner_id = 1
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

ANALYZE 会真实执行语句；对 UPDATE/DELETE 不能当只读分析使用。只在本地种子库运行写入类实验。

比较估算行数与实际行数、扫描类型、过滤丢弃行、排序、缓存命中和读取。小表 Seq Scan 可能正确，不能为了“看到 Index Scan”强行关闭优化器。

增加 `(owner_id, created_at DESC, id DESC)` 索引后，以相同数据与条件比较。索引占空间并增加写入成本，字段顺序由真实查询决定。

### 5. 连接池与迁移

进程数 × 每进程最大连接不能超过数据库整体预算。事务内等待用户或远端请求会占用连接与锁，应缩短事务。

破坏性迁移采用 expand → migrate → contract：先兼容新旧字段、迁移并核对数据，再移除旧字段。备份不等于恢复完成，隔离恢复后校验行数、约束和关键旅程。

## 常见问题

**ORM 能自动选对事务吗？** 不能，业务不变量、锁和重试边界由设计决定。

**有缓存是不是不需要索引？** 未命中和失效时仍依赖数据库，缓存不能掩盖错误数据模型。

## 实操作业

基础创建约束并拒绝空标题；进阶双会话复现 revision 冲突；挑战建立查询计划对比与连接预算。

### 参考答案与验收

两个旧 revision 更新最多一个成功；约束失败不能部分写入；计划报告包含实际行数、buffer、数据规模和写入成本。未运行数据库时只能标注文档审阅。
