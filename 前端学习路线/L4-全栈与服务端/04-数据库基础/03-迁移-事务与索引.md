## 内容讲解

### 第一部分：数据库迁移

#### 一、为什么需要迁移？

你在开发博客系统，今天给 `posts` 表加了一个 `excerpt` 字段。你的代码能工作了——但你同事的本地数据库呢？测试环境呢？生产环境呢？

**迁移**就是数据库结构的"版本管理"——像 Git 管理代码一样，迁移文件管理数据库 Schema 的每一次变更。

没有迁移的世界：
- 同事：`ERROR: column "excerpt" does not exist` → 你："哦，你手动跑一下这个 SQL"
- 生产环境：谁改的？改了什么？有没有备份？出了事能回滚吗？——全答不上来

有迁移的世界：
```bash
git pull                    # 拉到新的迁移文件
npx prisma migrate dev      # 自动应用所有未应用的迁移
# 数据库结构和同事保持一致了
```

每一份迁移文件都是一个不可变的 SQL 脚本，按时间顺序排列：

```
prisma/migrations/
├── 20250101000000_init/
│   └── migration.sql          # 初始建表
├── 20250102000000_add_excerpt/
│   └── migration.sql          # 给 posts 加 excerpt 列
├── 20250103000000_add_tags/
│   └── migration.sql          # 创建 tags 和 post_tags 表
└── migration_lock.toml        # 锁文件，记录 Prisma 版本
```

---

#### 二、Prisma Migrate 的三种环境与命令

| 环境 | 命令 | 行为 |
|------|------|------|
| **本地开发** | `npx prisma migrate dev --name <描述>` | 对比 Schema → 生成 SQL → 应用 → generate |
| **CI / 测试** | `npx prisma migrate deploy` | 只应用尚未应用的迁移（不对比 Schema） |
| **仅生成 SQL** | `npx prisma migrate diff` | 生成差异 SQL 但不应用（用于审查） |

#### 2.1 开发工作流

```bash
# 1. 修改 prisma/schema.prisma，比如给 Post 加 excerpt 字段
# model Post {
#   excerpt  String?  @db.Text    ← 新增这行
#   ...
# }

# 2. 生成并应用迁移
npx prisma migrate dev --name add_post_excerpt

# 输出：
# Applying migration `20250102000000_add_post_excerpt`
# The following migration(s) have been created and applied from new schema changes:
# migrations/
#   └─ 20250102000000_add_post_excerpt/
#     └─ migration.sql

# 3. 检查生成的 SQL（应该养成这个习惯！）
cat prisma/migrations/20250102000000_add_post_excerpt/migration.sql
```

自动生成的迁移 SQL：

```sql
-- 这是 Prisma 自动生成的，你可以读但不要手动改
ALTER TABLE "Post" ADD COLUMN "excerpt" TEXT;

-- 如果字段是 NOT NULL，Prisma 还会处理已有数据的默认值
-- ALTER TABLE "Post" ADD COLUMN "excerpt" TEXT NOT NULL DEFAULT '';
```

> **避坑提示**：`prisma migrate dev` 会触发一次 reset 如果它检测到迁移历史被手动修改了。**不要手动修改或删除已有的迁移文件**——如果需要修正迁移，创建一个新的迁移来修复。

#### 2.2 CI/CD 工作流

```yaml
# .github/workflows/deploy.yml 中的典型步骤
- name: Run database migrations
  run: npx prisma migrate deploy
  env:
    DATABASE_URL: ${{ secrets.DATABASE_URL }}
```

`prisma migrate deploy` 的特点：
- **只执行未应用的迁移**，不会对比 Schema 生成新迁移
- **失败时回滚**当前迁移（PostgreSQL 支持 DDL 事务）
- ⚠️ 不会因为有 Schema 差异而失败——它只关心迁移记录表

#### 2.3 团队协作流程

```
你（修改了 Schema）：
  git checkout -b feat/add-tags
  修改 prisma/schema.prisma
  npx prisma migrate dev --name add_tags
  git add prisma/migrations/
  git commit -m "feat: add tags table"
  git push
  → 提 MR

同事（拉取你的分支）：
  git pull origin feat/add-tags
  npx prisma migrate dev    # 自动应用你创建的迁移
  # 或 npx prisma generate  # 如果数据库已经是最新
```

合并冲突处理：

如果两个分支都新增了迁移，保留两边各自的迁移目录。`migration_lock.toml` 只记录数据库 provider；若它发生文本冲突，应确认两边使用同一种 provider 并保留正确值：
```bash
# 合并代码后，在开发数据库验证完整迁移历史
npx prisma migrate dev
npx prisma migrate status
```

> **避坑提示**：不要把 `migration_lock.toml` 当作可删除的临时文件。它应与整个 `prisma/migrations` 目录一起提交，用于检测数据库 provider 是否被更换。已经应用过的迁移文件也不要直接修改或删除；应修复历史不一致的根因。

#### 2.4 回滚和重置

```bash
# 开发环境：回滚到指定迁移
npx prisma migrate diff \
  --from-schema-datamodel prisma/schema.prisma \
  --to-schema-datasource prisma/schema.prisma \
  --script > rollback.sql

# 更粗暴的方式：完全重置（⚠️ 丢失所有数据）
npx prisma migrate reset

# 生产环境不支持回滚！只能前滚：
# 创建一个新的迁移来撤销之前的更改
```

Prisma 不原生支持回滚的原因是：回滚可能丢失数据（如 DROP COLUMN），而"前滚修复"更安全可控。

### 第二部分：事务（Transaction）

#### 三、事务的 ACID 特性

事务是数据库最核心的保障机制。四个字母代表了四个保证：

| 特性 | 含义 | 类比 |
|------|------|------|
| **A**tomicity 原子性 | 要么全做，要么全不做 | 银行转账：A 扣 100 元 + B 加 100 元必须同时成功或同时失败 |
| **C**onsistency 一致性 | 事务前后，数据都满足约束 | 转账后总金额不变；外键始终指向存在的行 |
| **I**solation 隔离性 | 并发事务互不干扰 | 你和同事同时下单，库存扣减不会互相覆盖 |
| **D**urability 持久性 | 提交后数据不会丢失 | 转账成功后，即使服务器宕机，钱不会"回去" |

用代码说话：

```typescript
// 没有事务：灾难场景
async function transfer(fromId: number, toId: number, amount: number) {
  // 步骤 1：扣款
  await prisma.account.update({
    where: { id: fromId },
    data: { balance: { decrement: amount } },
  });
  // 💥 假设这里服务器宕机了！
  // 步骤 2 永远不会执行——钱扣了，但没有加出去
  await prisma.account.update({
    where: { id: toId },
    data: { balance: { increment: amount } },
  });
}

// 有事务：安全
async function transfer(fromId: number, toId: number, amount: number) {
  await prisma.$transaction(async (tx) => {
    await tx.account.update({
      where: { id: fromId },
      data: { balance: { decrement: amount } },
    });
    // 即使这里宕机，整个事务回滚——钱没扣
    await tx.account.update({
      where: { id: toId },
      data: { balance: { increment: amount } },
    });
  });
}
```

#### 四、事务的常见业务场景

##### 4.1 下单扣库存

```typescript
async function placeOrder(userId: number, productId: number, quantity: number) {
  // 使用隔离级别更强的 raw SQL
  return prisma.$transaction(async (tx) => {
    // 1. 锁定库存行并检查库存（SELECT ... FOR UPDATE 防止并发超卖）
    const [product] = await tx.$queryRaw<[{stock: number}]>`
      SELECT stock FROM "Product" WHERE id = ${productId} FOR UPDATE
    `;
    if (!product || product.stock < quantity) {
      throw new Error('库存不足');
    }

    // 2. 扣减库存
    await tx.product.update({
      where: { id: productId },
      data: { stock: { decrement: quantity } },
    });

    // 3. 创建订单
    const order = await tx.order.create({
      data: { userId, productId, quantity, totalAmount: productPrice * quantity },
    });

    return order;
  });
}
```

关键点：`SELECT ... FOR UPDATE` 锁定要修改的行，防止两个并发请求同时读到"还有 1 件库存"然后都下单成功——这就是**超卖**的产生原因。

##### 4.2 用户注册（多表写入）

```typescript
async function register(data: {
  name: string; email: string; password: string; inviteCode?: string;
}) {
  return prisma.$transaction(async (tx) => {
    // 1. 创建用户
    const user = await tx.user.create({
      data: { name: data.name, email: data.email, passwordHash: hash(data.password) },
    });

    // 2. 创建默认配置
    await tx.userProfile.create({
      data: { userId: user.id, theme: 'light', language: 'zh-CN' },
    });

    // 3. 如果有邀请码，处理邀请奖励
    if (data.inviteCode) {
      const inviter = await tx.user.findUnique({ where: { inviteCode: data.inviteCode } });
      if (inviter) {
        await tx.inviteRecord.create({
          data: { inviterId: inviter.id, inviteeId: user.id },
        });
        await tx.user.update({
          where: { id: inviter.id },
          data: { inviteCount: { increment: 1 } },
        });
      }
    }

    return user;
  });
}
```

##### 4.3 发布文章（状态变更 + 关联更新）

```typescript
async function publishPost(postId: number) {
  return prisma.$transaction(async (tx) => {
    const post = await tx.post.findUnique({ where: { id: postId } });
    if (!post) throw new Error('文章不存在');
    if (post.status !== 'draft') throw new Error('只有草稿可以发布');

    const published = await tx.post.update({
      where: { id: postId },
      data: {
        status: 'published',
        publishedAt: new Date(),
      },
      include: { author: { select: { id: true, name: true } } },
    });

    // 如果作者开启了发布通知，创建通知记录
    const author = await tx.user.findUnique({ where: { id: post.userId } });
    if (author?.notifyOnPublish) {
      await tx.notification.create({
        data: {
          userId: author.id,
          type: 'post_published',
          title: `文章「${post.title}」已发布`,
          link: `/posts/${post.slug}`,
        },
      });
    }

    return published;
  });
}
```

#### 五、Prisma 的两种事务 API

```typescript
// 方式一：批量事务 $transaction([...])
// 适用：多个独立的 Prisma 操作，彼此不依赖
const [user, postCount] = await prisma.$transaction([
  prisma.user.create({ data: { name: '张三', email: 'z3@ex.com' } }),
  prisma.post.count({ where: { status: 'published' } }),
]);

// 方式二：交互式事务 $transaction(async (tx) => { ... })
// 适用：操作之间存在依赖关系，需要在事务中做条件判断
const result = await prisma.$transaction(async (tx) => {
  const user = await tx.user.findUnique({ where: { email: 'z3@ex.com' } });
  if (user) {
    throw new Error('邮箱已注册');  // 抛出异常 → 事务回滚
  }
  const created = await tx.user.create({
    data: { name: '张三', email: 'z3@ex.com' },
  });
  return created;
});
```

> **避坑提示**：
> 1. 批量事务中如果某个操作依赖前一个操作的结果，用交互式事务，不要用批量事务——批量事务内部的执行顺序不确定。
> 2. 事务中的代码要尽可能快——事务持有锁，长时间运行的事务会阻塞其他请求。
> 3. 不要在事务中发 HTTP 请求、读文件、做复杂计算——这些不应该占用数据库锁。

#### 六、隔离级别的实际影响

PostgreSQL 默认隔离级别是 **Read Committed**，它足够应对大部分场景。但你至少需要知道三个常见的并发问题：

| 问题 | 现象 | 解决方式 |
|------|------|---------|
| **脏读** | 读到别的事务未提交的数据 | PostgreSQL 所有级别都防止了 |
| **不可重复读** | 同一事务中两次读同一行，值不同 | `REPEATABLE READ` |
| **幻读** | 同一事务中两次查同一条件，行数不同 | `SERIALIZABLE` 或 `FOR UPDATE` 锁定 |

```typescript
// 设置事务隔离级别（不常用，按需使用）
await prisma.$transaction(
  async (tx) => {
    await tx.$executeRaw`SET TRANSACTION ISOLATION LEVEL SERIALIZABLE`;
    // ... 业务操作
  },
  { isolationLevel: 'Serializable' }  // Prisma 也支持参数方式
);
```

对于前端工程师，记住一句话就够：**遇到"同时修改同一行"的场景（如库存扣减），用 `FOR UPDATE` 加锁或乐观锁，而不是调隔离级别。**

### 第三部分：索引（Index）

#### 七、索引的原理

没有索引时，数据库做全表扫描（Sequential Scan）：

```
SELECT * FROM posts WHERE slug = 'hello-world';

顺序扫描:
┌────┬──────────────┬──────────────────────┐
│ id │ title        │ slug                 │ ← 一行一行看
├────┼──────────────┼──────────────────────┤
│ 1  │ Hello World  │ hello-world   ✓ 找到了！但还要继续扫...
│ 2  │ Another Post │ another-post
│ 3  │ ...          │ ...
│ ...│ ...          │ ...
│ 10M│ Last Post    │ last-post            │ ← 扫了 1000 万行
└────┴──────────────┴──────────────────────┘
```

有 B-Tree 索引时，数据库做索引扫描（Index Scan）：

```
          索引树 (B-Tree)
              [hello]
             /       \
      [another]     [world]
      /    \        /    \
  [a...] [b...]  [h...] [z...]

查找 "hello-world":
  根节点 "hello" → 右子树 "world" → 叶子节点 → 直接定位到行
  时间复杂度: O(log n)，1000 万行只需约 24 次比较
```

B-Tree 是 PostgreSQL 默认的索引类型，适用于：
- `=`、`>`、`>=`、`<`、`<=` 比较
- `BETWEEN`、`IN` 范围查询
- `IS NULL`、`ORDER BY`

---

#### 八、索引类型速查

| 索引类型 | 适用场景 | 创建语句 |
|---------|---------|---------|
| **B-Tree**（默认） | 等值、范围、排序 | `CREATE INDEX idx_xxx ON table(column)` |
| **UNIQUE** | 唯一约束 + 快速查找 | `CREATE UNIQUE INDEX idx_xxx ON table(column)` |
| **复合索引** | 多列联合查询 | `CREATE INDEX idx_xxx ON table(a, b, c)` |
| **部分索引** | 条件筛选（如只索引活跃用户） | `CREATE INDEX idx_xxx ON table(a) WHERE active = true` |
| **GIN** | 全文搜索、数组、JSONB | `CREATE INDEX idx_xxx ON table USING GIN(column)` |
| **覆盖索引** | 查询只需索引中的列，不回表 | `CREATE INDEX idx_xxx ON table(a) INCLUDE(b, c)` |

---

#### 九、什么时候创建索引？

**不是每列都要索引**——索引有代价。遵循以下原则：

✅ **应该索引**：
1. **WHERE 条件中频繁出现的列**（如 `status`、`user_id`）
2. **JOIN 关联的外键列**（如 `posts.user_id`）
3. **ORDER BY 排序的列**（如 `created_at DESC`）
4. **UNIQUE 约束列**（数据库自动创建唯一索引）
5. **高选择性的列**（不同值很多，如 `email`、`slug`）

❌ **不应该索引**：
1. **低选择性的列**（不同值很少，如 `gender` 只有男/女）
2. **频繁更新的列**（索引维护开销大）
3. **小表**（几千行以下，全表扫描更快）
4. **几乎不参与查询的列**

> **避坑提示**：给 `status` 这种低基数列建索引时，组合其他列或使用部分索引。比如只索引 `status = 'draft'` 的行（草稿通常是少数），而不是全表索引 status。

---

#### 十、索引的代价

索引不是免费的午餐：

| 代价 | 说明 |
|------|------|
| **写入性能下降** | 每次 INSERT/UPDATE/DELETE，所有相关索引都要更新 |
| **存储空间增加** | 每个索引都占用额外的磁盘空间（通常比表本身多 10-30%） |
| **查询规划开销** | 索引太多会让查询优化器选择困难，有时会选择次优方案 |

判断标准：**一个索引带来的查询性能提升，是否超过了它造成的写入性能下降和存储开销？**——读取远远多于写入的表，可以多建索引；写入密集的表，要谨慎。

#### 十一、EXPLAIN ANALYZE：分析查询性能

看查询慢不慢，不能凭感觉，要用数据说话：

```sql
-- EXPLAIN：显示执行计划（不实际执行）
EXPLAIN SELECT * FROM posts WHERE slug = 'hello-world';

-- EXPLAIN ANALYZE：实际执行并显示真实耗时
EXPLAIN ANALYZE SELECT * FROM posts WHERE slug = 'hello-world';
```

看懂 EXPLAIN 输出的关键：

```
-- 无索引时的全表扫描（慢）
Seq Scan on posts  (cost=0.00..458.00 rows=1 width=500)
                   (actual time=0.012..4.523 rows=1 loops=1)
  Filter: (slug = 'hello-world'::text)
  Rows Removed by Filter: 9999
Planning Time: 0.102 ms
Execution Time: 4.541 ms
-- ↑ 扫了 10000 行，过滤掉了 9999 行

-- 有索引时的索引扫描（快）
Index Scan using "Post_slug_key" on posts  (cost=0.29..8.30 rows=1 width=500)
                                           (actual time=0.015..0.016 rows=1 loops=1)
  Index Cond: (slug = 'hello-world'::text)
Planning Time: 0.089 ms
Execution Time: 0.028 ms
-- ↑ 直接定位到 1 行，快了 160 倍
```

关键指标：
- **Seq Scan** = 全表扫描（通常要优化）
- **Index Scan** = 索引扫描（好的）
- **Index Only Scan** = 只读索引不回表（最好）
- **cost** = 估算成本（越低越好）
- **actual time** = 实际耗时（唯一真实数据）
- **Rows Removed by Filter** = 扫描了多少无用行（越少越好）

#### 十二、常见性能反模式

##### 12.1 N+1 查询

```typescript
// ❌ N+1 问题：先查所有文章（1 次），再逐篇查作者（N 次）
const posts = await prisma.post.findMany();
for (const post of posts) {
  const author = await prisma.user.findUnique({ where: { id: post.userId } });
  console.log(post.title, author.name);
}
// 10 篇文章 = 11 次数据库查询

// ✅ 用 include 一次查完
const posts = await prisma.post.findMany({
  include: { author: true },
});
// 10 篇文章 = 1 次数据库查询（JOIN）
```

N+1 是 ORM 中最常见的性能杀手。症状：页面加载慢、数据库连接数飙升。**始终用 `include` 或 `select` 一次性加载关联数据。**

##### 12.2 全表扫描

```sql
-- ❌ 函数包裹列名 → 无法使用索引
SELECT * FROM posts WHERE LOWER(title) = 'hello world';

-- ✅ 建表达式索引
CREATE INDEX idx_posts_title_lower ON posts (LOWER(title));

-- ❌ 模糊前缀 % → 无法使用索引
SELECT * FROM posts WHERE title LIKE '%PostgreSQL%';

-- ✅ 用全文搜索或 pg_trgm 扩展
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_posts_title_trgm ON posts USING GIN (title gin_trgm_ops);
-- 然后 LIKE '%PostgreSQL%' 就可以使用索引了
```

##### 12.3 隐式类型转换

```sql
-- ❌ userId 是 INTEGER 列，但 WHERE 中用字符串比较 → 跳过索引
SELECT * FROM posts WHERE user_id = '123';
-- ✅ 使用正确的类型
SELECT * FROM posts WHERE user_id = 123;
```

##### 12.4 过度使用 SELECT *

```sql
-- ❌ 返回所有列，包括不需要的 TEXT 大字段
SELECT * FROM posts;

-- ✅ 只选择需要的列，配合覆盖索引效果更好
SELECT id, title, slug, created_at FROM posts WHERE status = 'published';
```

```typescript
async function seed() {

    }
```

```sql

SELECT * FROM "Post" WHERE slug = 'hello-world';

-- 预期输出：
-- Gather  (actual time=200.000..250.000 ...) ← 很慢
--   Parallel Seq Scan on "Post"              ← 全表扫描
--     Filter: (slug = 'hello-world'::text)

-- 测试 2：按状态和用户 ID 分页查询（无复合索引）

SELECT id, title, created_at
FROM "Post"
WHERE status = 'published' AND "userId" = 1
ORDER BY created_at DESC
LIMIT 10;
```

##### 步骤 3：创建索引

```sql
-- 1. 文章 slug 唯一索引（Prisma 中 @unique 已自动创建）
--    如果之前没建，手动创建：
CREATE UNIQUE INDEX "Post_slug_key" ON "Post"(slug);

-- 2. 按状态 + 用户 ID 的复合索引（分页查询热点）
CREATE INDEX idx_posts_status_userid_created
ON "Post"(status, "userId", created_at DESC);

-- 3. 用户的所有文章（外键列，JOIN 热点）
CREATE INDEX idx_posts_user_id ON "Post"("userId");

-- 4. 部分索引：只索引草稿（草稿是少数，查询频率高）
CREATE INDEX idx_posts_drafts
ON "Post"("userId", created_at DESC) WHERE status = 'draft';

-- 5. 覆盖索引：列表页只需要 id + title + created_at
CREATE INDEX idx_posts_list
ON "Post"(status, created_at DESC) INCLUDE (id, title, slug);
```

```sql

-- 预期输出：
-- Index Scan using "Post_slug_key" on "Post"  ← 索引扫描！
--   (actual time=0.020..0.021 ...)             ← 快了 10000 倍

-- 按状态 + 用户 ID 查询
EXPLAIN ANALYZE
```

```prisma
// 在 prisma/schema.prisma 中定义索引（Prisma Migrate 会自动生成）

model Post {
  id        Int      @id @default(autoincrement())
  title     String   @db.VarChar(200)
  slug      String   @unique                    // ← 自动创建唯一索引
  content   String   @db.Text
  status    String   @default("draft") @db.VarChar(20)
  userId    Int
  // ... 其他字段、关系

  @@index([userId])                              // ← 单列索引
  @@index([status, userId, createdAt(sort: Desc)]) // ← 复合索引（带排序）
  @@index([userId, createdAt(sort: Desc)])        // ← 部分索引需要通过 migration 手动创建
}
```

## 常见问题

**Q1: 迁移文件应该提交到 Git 吗？**

**必须提交**。整个 `prisma/migrations` 目录（包括 `migration_lock.toml`）是数据库变更历史的可信来源；只提交 `schema.prisma` 不足以复现定制 SQL。`.env` 不要提交（含数据库密码），`node_modules/.prisma` 不要提交。

**Q2: `prisma migrate dev` 和 `prisma db push` 有什么区别？**

`migrate dev` 在开发环境生成并应用版本化迁移；`db push` 直接同步数据库结构但不生成迁移文件，适合可丢弃的原型数据库。测试和生产环境应由 CI/CD 使用 `prisma migrate deploy` 应用已提交的迁移，不能运行会生成迁移或提示重置数据库的 `migrate dev`。

**Q3: 事务中的代码越短越好，但业务逻辑就是很复杂怎么办？**

把事务外的工作移到事务外：先做数据校验、权限检查、外部 API 调用，只在事务中做纯粹的数据库写操作。

**Q4: 给所有外键都加索引是必要的吗？**

不一定。PostgreSQL 不会自动为引用方的外键列创建索引；频繁按外键连接、筛选，或父表经常 `DELETE`/更新被引用键时，索引通常很有价值。但小表、低写入频率或几乎不按该列查询的场景可能不值得承担写入和存储成本。用真实查询与 `EXPLAIN (ANALYZE, BUFFERS)` 决定，而不是机械地给所有外键加索引。

**Q5: 复合索引的列顺序重要吗？**

非常重要。索引 `(A, B, C)` 支持查询 `WHERE A = ?` 和 `WHERE A = ? AND B = ?` 和 `WHERE A = ? AND B = ? AND C = ?`，但**不支持** `WHERE B = ?` 或 `WHERE B = ? AND C = ?`。把选择性最高的列放在前面通常更好。

**Q6: 索引会让查询变慢吗？**

极少情况下会。当索引选择性太低（如全表只有 3 个不同值），查询优化器可能错误地选择索引扫描而不是全表扫描，反而更慢。用 `EXPLAIN ANALYZE` 验证。

**Q7: 怎么排查 N+1 查询？**

Prisma 开发模式下可以开启日志：
```typescript
const prisma = new PrismaClient({
  log: ['query'],
});
```
然后看控制台输出——如果同一个查询模式重复出现很多次，就是 N+1。生产环境用 APM 工具（如 DataDog、Sentry Performance）监控查询次数。

**Q8: 我的查询用了索引但还是慢，怎么办？**

检查 EXPLAIN ANALYZE 的 `actual time` 和 `rows`。可能原因：索引碎片化（`REINDEX`）、统计信息过期（`ANALYZE`）、数据量确实太大（考虑分区表）、或者慢的是网络/应用层而不是数据库。

## 本节小结

- **迁移**是数据库 Schema 的版本控制，迁移文件必须提交到 Git
- `prisma migrate dev`（开发） vs `prisma migrate deploy`（生产）职责不同，不要混用
- **事务 ACID**：原子性（全做或全不做）、一致性（约束完好）、隔离性（并发互不干扰）、持久性（提交即永久）
- **库存扣减**类并发场景用 `FOR UPDATE` 行锁，不要只依赖事务隔离级别
- **索引**是 B-Tree 结构，用空间换时间：查询快了但写入慢了，需要权衡
- **创建索引的黄金法则**：频繁出现在 WHERE / JOIN / ORDER BY 中的列，且选择性高
- **EXPLAIN ANALYZE** 是性能分析的起点——不要凭感觉优化，用数据说话
- **N+1 是最常见的 ORM 性能杀手**——始终用 `include`/`select` 一次性加载关联数据
