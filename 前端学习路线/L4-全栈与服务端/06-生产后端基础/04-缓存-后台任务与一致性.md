## 学习目标

- 能建立包含失效、降级和权限边界的缓存策略。
- 能设计可重试任务、去重、死信与事务 outbox。

## 内容讲解

### 1. 缓存不是数据真相

Cache-aside：先读缓存，未命中查数据库并写缓存；写数据库成功后失效相关缓存。这个顺序仍存在并发读写竞态，业务必须接受短暂陈旧或采用版本键/一致性方案。

键至少包含资源、租户和实际响应维度；用户私有结果不能用公共 key。TTL 提供陈旧上限但不是精确失效承诺；给 TTL 加抖动可减轻同时过期。

缓存击穿可用请求合并或短时互斥，但锁获取失败、锁过期和持有者崩溃都需要恢复。不能只 `SETNX` 后忘记释放。

### 2. 降级与监控

| 故障 | 处理 |
|---|---|
| 缓存不可用 | 有界回源，保护数据库并发 |
| 热 key 过期 | 请求合并，允许受控陈旧 |
| 权限变化 | 失效敏感缓存，服务端重新授权 |
| 缓存数据损坏 | schema 校验后丢弃并重建 |

命中率高不代表正确，需要跟踪陈旧、错误、回源量和延迟。缓存中不要保存无必要的秘密和真实个人信息。

### 3. 任务状态机

```text
pending → running(lease) → succeeded
             ↓
           retrying → running
             ↓
           dead-letter → 人工处理/修复后重放
```

任务包含 jobId、业务幂等键、输入 schemaVersion、尝试次数和租约。worker 崩溃后租约到期可重试，业务写入按幂等键去重。队列“取出一次”不等于业务“执行一次”。

退避带抖动且有限次数；确定性非法输入不应一直重试。重放死信前确认原副作用和当前权限，保留审计。

### 4. 事务 outbox

数据库写文章与“需要索引”的 outbox 记录放在同一事务：

```sql
BEGIN;
UPDATE articles SET title = $1, revision = revision + 1 WHERE id = $2;
INSERT INTO outbox (event_id, type, resource_id, payload)
VALUES ($3, 'article.updated', $2, $4);
COMMIT;
```

SQL 假设 tables 已由项目迁移建立，事件 ID 有唯一约束。独立 dispatcher 读取未发送 outbox 并投递，成功后标记。发送后标记前崩溃会重复投递，消费者仍须去重。

`FOR UPDATE SKIP LOCKED` 可用于多 worker 获取不同任务，但租约、重试和饥饿问题仍要设计。不能把“数据库和消息队列各写一次”称为原子提交。

### 5. 可观察性与关闭

指标包括队列长度、最老任务年龄、成功率、重试率与 dead-letter 数；仅看长度可能漏掉一个长期卡住的关键任务。

worker 收到关闭信号后停止领取新任务，完成或安全放回当前任务，并有退出预算。部署后验证新旧 schema 的任务都能处理。

## 常见问题

**Redis 锁是否等于可靠业务事务？** 不等于，租约、故障和下游副作用都需要正确性模型。

**后台任务是不是不需要鉴权？** 发起时与执行时的权限、资源归属和撤销策略必须明确。

## 实操作业

基础设计文章缓存键与失效；进阶在任务执行后确认前杀掉 worker，验证重复无副作用；挑战实现 outbox 与 dead-letter 恢复。

### 参考答案与验收

跨租户缓存不能混用；缓存故障不造成无界回源；重复索引不会生成重复业务记录；dispatcher 重启能继续；dead-letter 有可定位原因。
