## 内容讲解

### 一、限流先定义主体和资源

“每分钟 100 次”缺少关键信息：

- 对谁：IP、用户、租户、API key？
- 限什么：登录、搜索、发布、导出？
- 在哪里：单进程、单区域、全局？
- 超限后：拒绝、排队、降级？
- 允许多大突发？

示例策略：

| 接口 | key | 策略 |
|---|---|---|
| 登录 | 账号 + 可信客户端维度 | 低速率、失败退避 |
| 搜索 | 用户或匿名会话 | 令牌桶，允许小突发 |
| 发布文章 | 用户 | 低并发 + 幂等 |
| 批量导出 | 租户 | 并发限制 + 队列 |

### 二、常见算法

#### 固定窗口

```text
10:00:00 - 10:00:59 最多 100 次
```

实现简单，但窗口边界前后可能瞬间通过两倍流量。

#### 滑动窗口

统计当前时刻之前一段时间的请求，边界更平滑，存储成本更高。

#### 令牌桶

按速率补充令牌，请求消耗令牌：

```text
补充速率：10 token/s
桶容量：30
```

允许短暂突发，又能控制长期平均速率。

#### 并发限制

对数据库连接、导出任务和第三方 API，限制“同时进行多少个”往往比每分钟请求数更有效。

### 三、生产限流需要共享状态

进程内 Map 只看到当前进程：

```text
实例 A：用户已请求 20 次
实例 B：用户已请求 0 次
```

负载均衡后限流被绕过，重启后状态丢失。生产环境使用 Redis、API Gateway、CDN 限流、Durable Object 等共享或平台级能力。

IP 也不是天然可信身份。只有在已知反向代理会清洗转发头时，才能读取可信客户端 IP。

### 四、429 响应

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
Content-Type: application/problem+json
```

```json
{
  "type": "https://atlas.example.com/problems/rate-limit",
  "title": "请求过于频繁",
  "status": 429,
  "retryAfterSeconds": 30
}
```

客户端应遵守 Retry-After，并使用带抖动的退避，不能立即无限重试。

### 五、幂等处理重复请求

幂等表示同一业务操作重复执行，最终效果与执行一次相同。

天然幂等：

```http
PUT /articles/a-1
DELETE /articles/a-1
```

语义上非幂等：

```http
POST /payments
POST /articles
```

可使用幂等键：

```http
POST /articles
Idempotency-Key: 6ad8...
```

服务端保存：

```text
租户 + 用户 + 接口 + 幂等键
状态：processing / succeeded / failed
请求摘要
响应状态与响应体
过期时间
```

流程：

```text
首次请求 → 原子占用 key → 执行业务 → 保存响应
重复请求 → 请求摘要一致 → 重放原响应
重复请求 → 摘要不同 → 409 Conflict
```

幂等记录和业务写入需要在可靠事务边界中协调，否则可能出现“业务成功但幂等记录失败”。

### 六、并发更新与版本号

两个用户同时编辑文章：

```sql
UPDATE articles
SET title = $1, version = version + 1
WHERE id = $2 AND version = $3;
```

受影响行数为 0 表示版本已变化，返回 409，让用户比较并合并，而不是静默覆盖。

### 七、优雅关闭

服务收到 SIGTERM 后不能立刻退出：

```text
收到终止信号
→ 标记 not ready，停止接收新流量
→ 停止创建新后台任务
→ 等待进行中请求
→ 关闭数据库、队列和日志出口
→ 超时后强制退出
```

Node.js 示例：

```js
let shuttingDown = false;

server.on('request', (request, response) => {
  if (shuttingDown) {
    response.writeHead(503, { connection: 'close' });
    response.end('Server is shutting down');
  }
});

async function shutdown(signal) {
  if (shuttingDown) return;
  shuttingDown = true;
  console.log({ signal, message: 'shutdown started' });

  const forceExit = setTimeout(() => {
    process.exit(1);
  }, 30_000);
  forceExit.unref();

  server.close(async error => {
    try {
      if (error) throw error;
      await database.close();
      await telemetry.flush();
      clearTimeout(forceExit);
      process.exit(0);
    } catch (cause) {
      console.error(cause);
      process.exit(1);
    }
  });
}

process.on('SIGTERM', () => void shutdown('SIGTERM'));
process.on('SIGINT', () => void shutdown('SIGINT'));
```

生产中应避免在普通库代码随意调用 `process.exit()`，由应用入口统一管理生命周期。

### 八、过载时优先降级

可选动作：

- 拒绝低优先级写入
- 返回缓存读结果
- 限制分页大小
- 暂停批量导出
- 关闭非核心推荐模块
- 对队列设置最大长度

无限排队只会把快速失败变成高延迟雪崩。

## 常见问题

### Q1：限流能防 DDoS 吗？

应用限流只能保护部分资源。大规模攻击需要 CDN、WAF、网络清洗和平台容量策略。

### Q2：只按 IP 限流可以吗？

共享出口会误伤大量用户，攻击者也可分散 IP。登录等场景应组合账号、设备、IP 和风险信号。

### Q3：前端禁用按钮还需要幂等吗？

需要。网络重试、多标签页、脚本调用和代理重放都能绕过按钮状态。

### Q4：所有 POST 都要幂等键吗？

不是。对支付、创建订单、发布等重复后果严重的操作优先实施；低风险操作可按业务成本决定。

### Q5：服务关闭时最长等多久？

由编排平台终止宽限期、请求超时和业务任务时长共同决定。必须小于平台强杀时间并保留余量。

### Q6：失败的幂等请求是否缓存？

参数校验等确定性失败可短时重放；临时依赖故障是否允许重试要明确区分。

## 实操作业

### 基础：限流设计

为 Atlas 搜索、登录、发布和导出分别定义 key、算法、窗口、突发、超限响应与存储。

### 进阶：幂等发布

实现文章发布接口：

- 接收 Idempotency-Key
- 校验请求摘要
- 原子占用
- 重放成功响应
- 不同请求复用 key 返回 409
- 并发测试只能产生一篇文章

### 挑战：关闭与过载演练

1. 发起持续 10 秒请求。
2. 请求中发送 SIGTERM。
3. 验证新请求收到 503，旧请求在宽限期完成。
4. 验证数据库和遥测正常关闭。
5. 注入超时，验证强制退出和告警。

## 本节小结

- 限流必须定义主体、资源、范围和突发策略
- 多实例系统不能依赖进程内 Map 保存生产限流状态
- 幂等键要绑定请求摘要，并和业务事务协调
- 并发更新可以用版本号避免静默覆盖
- 优雅关闭包含停止接流量、排空、释放资源和超时兜底
