## 学习目标

- 能设计可查询、可脱敏的结构化日志
- 理解 request ID、trace ID、span ID 的作用
- 能把浏览器请求、服务端处理和数据库调用串联起来
- 能区分存活、就绪和启动检查
- 能定义 RPO、RTO、备份保留和恢复演练
- 能为 Atlas 建立最小生产运维闭环

## 内容讲解

### 一、日志是事件数据，不是字符串作文

不推荐：

```js
console.log('用户 ' + userId + ' 发布文章失败: ' + error.message);
```

结构化事件：

```js
logger.error({
  event: 'article.publish.failed',
  requestId,
  traceId,
  userId,
  articleId,
  errorType: error.name,
  errorMessage: error.message,
  durationMs,
});
```

统一字段：

```text
timestamp
level
service
environment
release
event
requestId
traceId
durationMs
result
```

日志级别：

| 级别 | 用途 |
|---|---|
| debug | 本地或短期开启的诊断细节 |
| info | 关键生命周期和业务结果 |
| warn | 可恢复但需要关注 |
| error | 当前操作失败 |
| fatal | 进程无法继续 |

不要把所有异常记为 error，也不要把正常业务拒绝制造成告警风暴。

### 二、日志必须脱敏

禁止记录：

- 密码
- Session、JWT、API key
- 完整 Cookie/Authorization Header
- 银行卡与身份证完整值
- 未经授权的用户正文

允许记录最小必要标识，例如内部用户 ID、脱敏邮箱、字段名称和错误类型。

日志系统本身也需要访问控制、保留期限和删除策略。

### 三、请求关联

入口读取可信 request ID，缺失时生成：

```js
const incoming = request.headers.get('x-request-id');
const requestId = isValidRequestId(incoming)
  ? incoming
  : crypto.randomUUID();
```

响应返回：

```http
X-Request-ID: 7a63...
```

用户错误页可显示 request ID，支持客服与研发定位，但不能暴露内部堆栈。

### 四、分布式追踪

```text
Trace：一次端到端用户请求
Span ：其中一个操作
```

```text
Browser fetch
└── Next.js Route Handler
    ├── auth.verify
    ├── article.query
    │   └── PostgreSQL SELECT
    └── response.serialize
```

每个 Span 应包含：

- 名称
- 开始与结束时间
- 状态
- 父子关系
- 少量稳定属性

不要把 user ID、完整 URL 查询、文章内容作为高基数 Metric label。高基数信息更适合受控日志或 Trace 属性。

OpenTelemetry 提供统一 API/SDK/协议，但采集器、采样和后端仍需设计。

### 五、采样

常见策略：

- 全量错误 Trace
- 慢请求提高采样率
- 普通成功请求低比例采样
- 特定租户或发布短期提高采样

Head sampling 在请求开始决定，成本可控但可能错过后续错误；Tail sampling 在结果产生后决定，需要 Collector 缓冲。

### 六、健康检查不是一个 `/health`

#### Liveness

进程是否还活着。失败会触发重启，不应依赖短暂外部服务。

```http
GET /health/live
200 {"status":"alive"}
```

#### Readiness

是否能接收流量。可以检查关键依赖、迁移状态和关闭标记：

```http
GET /health/ready
503 {"status":"not_ready","reason":"database_unavailable"}
```

#### Startup

启动较慢时防止平台过早判定失败。

检查必须设置严格超时，不能因健康检查本身耗尽连接池。

### 七、指标与日志、Trace 的分工

| 信号 | 回答 |
|---|---|
| Metric | 系统是否异常、影响多大 |
| Log | 某个离散事件发生了什么 |
| Trace | 一次请求慢或失败在哪里 |

三者通过 release、service、environment、request/trace ID 关联。

### 八、备份先定义目标

```text
RPO：最多可以丢失多少时间的数据
RTO：故障后多久必须恢复服务
```

示例：

```text
RPO = 15 分钟
RTO = 2 小时
```

备份策略：

- 定期基础备份
- WAL / 增量日志
- 跨故障域副本
- 加密与密钥管理
- 保留和删除策略
- 恢复权限最小化

高可用副本不等于备份。误删除可能同步到所有副本，勒索或权限错误也可能同时影响线上和副本。

### 九、恢复演练

有效备份必须能够恢复：

```text
创建隔离恢复环境
→ 获取指定时间点备份
→ 恢复数据库
→ 执行 schema 与数据校验
→ 启动应用
→ 跑关键业务测试
→ 记录实际 RPO/RTO
→ 安全销毁恢复环境
```

只看“备份任务成功”不能证明恢复有效。

### 十、Runbook

Runbook 至少包含：

- 告警含义
- 影响判断
- 第一批查询与链接
- 止损动作
- 回滚与恢复步骤
- 升级联系人
- 禁止动作
- 事后补录

命令必须经过演练，不能在事故时第一次执行。

## 常见问题

### Q1：记录更多日志是不是更好？

不是。无边界日志增加成本、噪声和泄漏风险。记录能支持决策和排查的最小字段。

### Q2：request ID 和 trace ID 一样吗？

可以关联但语义不同。request ID 常用于单次入口请求，trace ID 可跨多个服务与异步调用。

### Q3：readiness 是否应该查所有依赖？

只检查当前实例接流量所必需的依赖，并设置超时。非关键依赖失败可降级而不是摘除整个实例。

### Q4：数据库有云厂商自动备份，还要演练吗？

要。配置错误、权限、密钥、恢复时长和应用兼容问题只有恢复演练才能暴露。

### Q5：前端错误如何进入同一 Trace？

通过 W3C Trace Context 传播 `traceparent`，并在 CORS、安全与采样策略允许时关联浏览器、服务端和后端 Span。

### Q6：备份能放在同一账号吗？

同账号权限被破坏时备份也可能被删。重要系统应评估跨账号、不可变存储和独立恢复权限。

## 实操作业

### 基础：日志契约

为登录、搜索、发布、审核定义事件名、级别、字段、脱敏和保留期限。

### 进阶：请求追踪与健康检查

实现：

- request ID 生成与回传
- Trace Context 传播
- `/health/live`
- `/health/ready`
- 关闭过程中 readiness 变为失败

### 挑战：恢复演练

1. 创建 Atlas 测试数据库和种子数据。
2. 做基础备份并继续写入。
3. 恢复到隔离环境的指定时间点。
4. 运行迁移和关键 E2E。
5. 记录实际 RPO、RTO、失败点和改进项。

## 本节小结

- 结构化日志需要稳定字段、级别和脱敏策略
- request ID 与 Trace 把跨层操作关联起来
- Metric、Log、Trace 分别回答规模、事件和路径问题
- liveness、readiness、startup 具有不同控制含义
- 备份目标由 RPO/RTO 决定，恢复演练才证明备份有效
