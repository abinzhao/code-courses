## 学习目标

- 能用证据区分 CPU 阻塞、I/O 等待、内存增长与连接池饱和。
- 能测量事件循环延迟和内存，并选择正确的优化位置。

## 内容讲解

### 1. 不先猜“Node 太慢”

请求变慢可能发生在客户端、代理、应用、数据库或下游。先关联 requestId/Trace 与分段耗时；CPU 使用率低不代表系统健康，可能在等待连接池或数据库锁。

```js
import { monitorEventLoopDelay, performance } from 'node:perf_hooks';

const delay = monitorEventLoopDelay({ resolution: 20 });
delay.enable();
let previous = performance.eventLoopUtilization();
const timer = setInterval(() => {
  const current = performance.eventLoopUtilization();
  const interval = performance.eventLoopUtilization(current, previous);
  previous = current;
  console.log({
    p99DelayMs: delay.percentile(99) / 1e6,
    utilization: interval.utilization,
    memory: process.memoryUsage(),
  });
  delay.reset();
}, 1000);

setTimeout(() => {
  const start = performance.now();
  while (performance.now() - start < 250) {
    // 只在本地诊断实验注入一个有界 CPU 阻塞。
  }
}, 1500);
setTimeout(() => {
  clearInterval(timer);
  delay.disable();
}, 4000);
```

运行此脚本，记录注入前后延迟。采样值不保证在每次运行都完全相同，关注相同条件下的变化。事件循环利用率不是 CPU 利用率，两者需结合判断。

### 2. 内存模型

`heapUsed` 是 JS 堆使用，`rss` 包含更多进程内存，Buffer 常计入 external/arrayBuffers。不能只看 heapUsed 就判断整个进程没泄漏。

内存随负载上涨再回落可能正常；停止新增请求并释放业务对象后仍持续增长才需要调查。常见引用来源有无界 Map、事件监听未移除、timer 闭包、大数组和未释放外部资源。

堆快照可能暂停进程、消耗额外内存并含敏感数据。只在隔离环境用种子数据采集，不公开真实用户内容。

### 3. 诊断命令

```bash
node --cpu-prof diagnostic.mjs
node --inspect=127.0.0.1:9229 diagnostic.mjs
```

Inspector 只绑定本机；不要向公网暴露。CPU profile 用调用栈定位热点，不能仅由函数名字推断原因。任务需先最小化，再比较优化前后同一输入和并发。

### 4. 对症处理

| 已确认瓶颈 | 优先措施 | 验证 |
|---|---|---|
| 大 JSON/同步文件阻塞 | 输入限额、异步或分块处理 | 延迟、吞吐和内存 |
| CPU 密集任务 | Worker 池或后台任务 | 序列化成本与主线程延迟 |
| 数据库锁/慢查询 | 事务缩短、索引、查询优化 | 执行计划与等待事件 |
| 连接池饱和 | 并发预算、超时与背压 | 等待队列与连接使用 |
| 无界缓存 | 上限、TTL 与淘汰 | 压力停止后的内存恢复 |

Worker 适合 CPU 工作，不自动加速异步网络 I/O。cluster、多进程会放大内存和数据库连接数，需要整体预算。

## 常见问题

**await 是否释放了 CPU？** 只在等待 Promise 时让出当前执行；async 函数中的同步循环仍阻塞 agent。

**调用 GC 能修复泄漏吗？** 不能回收仍被强引用的对象，先找引用链。

## 实操作业

基础运行有界阻塞实验；进阶建立有上限和无上限缓存对比；挑战定位一个慢请求，给出分段耗时与最小修复。

### 参考答案与验收

报告必须有输入规模、并发、采样周期、运行时和前后指标；请求加速但内存无界增长不算通过。区分采样证据与推断，不把单次峰值当普遍结论。
