## 内容讲解

### 一、数据校验的底层逻辑：为什么需要双层校验？

很多初学者认为"前端已经校验过了，后端没必要再校验"。这是危险的幻觉：

```
┌──────────────────────────────────────────────────┐
│                  浏览器                           │
│  ┌──────────────┐                                │
│  │ 前端校验      │  ← 做给用户看的（体验层）       │
│  │（可选，可绕过）│    JS 可以被禁用、被修改、被跳过  │
│  └──────┬───────┘                                │
│         │ HTTP 请求（任何人都能构造）               │
├─────────┼────────────────────────────────────────┤
│         ▼          服 务 器                       │
│  ┌──────────────┐                                │
│  │ 后端校验      │  ← 做给安全看的（底线层）       │
│  │（必须，不可绕过）│   服务端代码攻击者无法修改       │
│  └──────────────┘                                │
└──────────────────────────────────────────────────┘
```

**前端校验为什么可以被绕过？**

```javascript
// 方法 1：用浏览器 DevTools 直接执行 JS
fetch('/api/posts', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ title: '', content: '<script>alert("XSS")</script>' }),
});

// 方法 2：用 curl 直接发请求（绕过所有前端逻辑）
// curl -X POST https://你的网站.com/api/posts \
//   -H "Content-Type: application/json" \
//   -d '{"title":"","content":"恶意内容"}'

// 方法 3：用 Postman / Insomnia 等 API 工具，随便构造参数
```

**三层防线模型**：

| 防线 | 位置 | 目的 | 可绕过？ |
|------|------|------|----------|
| 前端校验 | 浏览器 | 即时反馈、减少无效请求 | ✅ 随便绕过 |
| Schema 校验 | 服务端入口 | 拒绝非法数据进入业务逻辑 | ❌ 不可绕过 |
| 数据库约束 | 数据库 | 最后防线（非空、唯一、外键） | ❌ 不可绕过 |

> **核心原则**：前端校验提升用户体验（不需要等服务器返回才知道错误），后端校验保障数据安全（不信任任何来自客户端的数据）。两者互补，不能相互替代。

### 二、Zod 深度使用

Zod 是 TypeScript 生态中最流行的 Schema 声明与校验库。它的核心设计理念是：**一个 Schema 定义，同时提供运行时校验和编译时类型推导**。

#### 2.1 基础 Schema 定义

```typescript
import { z } from 'zod';

// ========== 基础类型 ==========
const StringSchema = z.string();               // string
const NumberSchema = z.number();               // number
const BooleanSchema = z.boolean();             // boolean
const DateSchema = z.date();                   // Date 对象
const BigIntSchema = z.bigint();               // bigint

// ========== 带约束的基础类型 ==========
const NameSchema = z.string()
  .min(1, '名称不能为空')                         // 最小长度 + 自定义错误信息
  .max(100, '名称最多 100 个字符')
  .trim();                                       // 自动去除首尾空格

const AgeSchema = z.number()
  .int('年龄必须是整数')                          // 必须是整数
  .min(0, '年龄不能为负')
  .max(150, '请输入合理的年龄');

const EmailSchema = z.string()
  .email('邮箱格式不正确')                        // 内置 email 校验
  .toLowerCase()                                 // 自动转小写
  .transform((email) => email.trim());           // 自定义转换

const UrlSchema = z.string()
  .url('请输入有效的 URL')
  .startsWith('https://', '只允许 HTTPS 链接');   // 自定义前缀约束

// ========== 字面量 ==========
const RoleSchema = z.enum(['admin', 'editor', 'viewer']);  // 枚举类型
const StatusSchema = z.literal('active');                   // 只能是 'active'

// ========== 数组 ==========
const TagsSchema = z.array(z.string().min(1).max(20))  // 字符串数组，每个 1-20 字符
  .min(1, '至少需要 1 个标签')                           // 数组本身至少有 1 个元素
  .max(5, '最多 5 个标签');

// ========== 对象 ==========
const UserSchema = z.object({
  username: z.string().min(3).max(30),
  email: z.string().email(),
  age: z.number().min(0).max(150).optional(),  // optional = 可以不传
  role: z.enum(['admin', 'user']).default('user'), // default = 不传时用默认值
});
```

#### 2.2 Schema 组合与复用

```typescript
// ========== extend：扩展已有 Schema ==========
const BasePostSchema = z.object({
  title: z.string().min(1).max(200),
  content: z.string().min(10),
});

// 创建帖子时的 Schema（继承基础字段，新增必填字段）
const CreatePostSchema = BasePostSchema.extend({
  tags: z.array(z.string()).max(5).default([]),
  status: z.enum(['draft', 'published']).default('draft'),
});

// 更新帖子时的 Schema（所有字段都变为可选）
const UpdatePostSchema = BasePostSchema.partial().extend({
  tags: z.array(z.string()).max(5).optional(),
  status: z.enum(['draft', 'published', 'archived']).optional(),
});

// ========== pick / omit：选择/排除字段 ==========
const PostSummarySchema = BasePostSchema.pick({ title: true });
// → { title: string }

const PostWithoutContentSchema = BasePostSchema.omit({ content: true });
// → { title: string }

// ========== merge：合并两个 Schema ==========
const TimestampSchema = z.object({
  createdAt: z.date(),
  updatedAt: z.date(),
});

const PostWithTimestamps = BasePostSchema.merge(TimestampSchema);
// → { title, content, createdAt, updatedAt }

// ========== discriminatedUnion：根据字段区分类型 ==========
// 多态数据：根据 type 字面量来推断具体 Shape
const EventSchema = z.discriminatedUnion('type', [
  z.object({ type: z.literal('click'), x: z.number(), y: z.number() }),
  z.object({ type: z.literal('keypress'), key: z.string() }),
  z.object({ type: z.literal('scroll'), deltaY: z.number() }),
]);

type Event = z.infer<typeof EventSchema>;
// 当你判断 event.type === 'click' 时，TypeScript 自动知道它有 x 和 y
```

#### 2.3 核心杀招：refinement 和 transform

```typescript
// ========== refine：自定义校验逻辑 ==========
// 单一真相源往往需要跨字段校验，这是 refine 的主场

const RegisterSchema = z.object({
  password: z.string().min(8, '密码至少 8 位'),
  confirmPassword: z.string(),
}).refine(
  // 校验函数：返回 true 表示通过
  (data) => data.password === data.confirmPassword,
  {
    message: '两次输入的密码不一致',
    path: ['confirmPassword'],   // 将错误绑定到 confirmPassword 字段
  }
);

// ========== superRefine：更灵活的多条件校验 ==========
const OrderSchema = z.object({
  items: z.array(z.object({ name: z.string(), price: z.number() })),
  discountCode: z.string().optional(),
  totalAmount: z.number(),
}).superRefine((data, ctx) => {
  // 可以做多个校验，每个用 ctx.addIssue 报告
  if (data.items.length === 0) {
    ctx.addIssue({
      code: z.ZodIssueCode.custom,
      message: '订单不能为空',
      path: ['items'],
    });
  }

  // 跨字段校验：折扣码必须存在且有效
  if (data.discountCode && !isValidDiscountCode(data.discountCode)) {
    ctx.addIssue({
      code: z.ZodIssueCode.custom,
      message: '无效的折扣码',
      path: ['discountCode'],
    });
  }

  // 计算校验：总金额必须与商品价格之和一致
  const computedTotal = data.items.reduce((sum, item) => sum + item.price, 0);
  if (data.totalAmount !== computedTotal) {
    ctx.addIssue({
      code: z.ZodIssueCode.custom,
      message: '总金额与商品价格之和不匹配',
      path: ['totalAmount'],
    });
  }
});

// ========== transform：输入值类型转换 ==========
const PriceSchema = z.union([z.string(), z.number()])
  .transform((val) => {
    // 将字符串 "99.99" 转为数字 99.99
    const num = typeof val === 'string' ? parseFloat(val) : val;
    return Math.round(num * 100) / 100; // 保留两位小数
  })
  .pipe(z.number().min(0.01, '价格必须大于 0'));
  // ↑ pipe：先执行前面的 transform，再把结果传给后面的 schema 校验

// 使用示例
PriceSchema.parse('99.99');  // → 99.99（数字，不是字符串）
PriceSchema.parse(100);      // → 100
PriceSchema.parse('abc');    // → 抛出 ZodError
```

#### 2.4 Zod + TypeScript：单一真相源

```typescript
// ══════════════════════════════════════════
// 传统方式：类型和校验分离（三个"真相"）
// ══════════════════════════════════════════

// 真相 1：TypeScript 类型定义（编译时）
interface CreateUserInput {
  name: string;
  email: string;
  age?: number;
}

// 真相 2：校验逻辑（运行时）
function validateCreateUserInput(body: unknown): CreateUserInput {
  if (typeof body !== 'object' || body === null) throw new Error('...');
  // ... 大量手动校验代码
  return body as CreateUserInput;
}

// 真相 3：JSDoc / 接口文档（如果还存在）
// 三者在修改时很容易不同步！

// ══════════════════════════════════════════
// Zod 方式：一个 Schema = 类型 + 校验（唯一的真相）
// ══════════════════════════════════════════

const CreateUserSchema = z.object({
  name: z.string().min(1),
  email: z.string().email(),
  age: z.number().optional(),
});

// 自动推导 TypeScript 类型（和 Schema 永远同步）
type CreateUserInput = z.infer<typeof CreateUserSchema>;

// 运行时校验（和类型定义永远同步）
function handleCreateUser(body: unknown) {
  const input = CreateUserSchema.parse(body);
  // input 的类型是 CreateUserInput，直接使用
  return db.users.create({ data: input });
}
```

### 三、错误处理的层次

错误处理最容易被写成"一刀切"——所有错误都用 `try/catch` 包起来，返回一个"出错了"就算完。实际上有严格的分层：

```
未知错误（unexpected）
  └── 系统错误（system）
        └── 业务错误（expected）
```

| 层次 | 定义 | 示例 | 处理方式 |
|------|------|------|----------|
| **业务错误** | 可预期的、用户操作导致的 | "邮箱已被注册"、"余额不足" | 返回业务错误码，前端展示提示 |
| **系统错误** | 依赖的外部服务异常 | 数据库连接超时、Redis 不可用 | 返回 503，记录日志，触发告警 |
| **未知错误** | 代码 Bug、逻辑缺陷 | 调用 `.toUpperCase()` 但值是 `null` | 返回 500，记录完整堆栈，触发告警 |

```typescript
// ========== 错误层次的设计实现 ==========

// 1. 业务错误：可预期、可恢复
class BusinessError extends Error {
  constructor(
    message: string,
    public code: string,           // 业务错误码，如 "EMAIL_ALREADY_EXISTS"
    public httpStatus: number = 422
  ) {
    super(message);
    this.name = 'BusinessError';
  }
}

// 2. 系统错误：外部依赖异常
class SystemError extends Error {
  constructor(
    message: string,
    public service: string,        // 哪个服务异常，如 "Database", "Redis"
    public httpStatus: number = 503
  ) {
    super(message);
    this.name = 'SystemError';
  }
}

// 3. 未知错误：代码 Bug（通常是 TypeError、ReferenceError 等）
// 不需要自定义类，直接捕获原生 Error

// ========== 在 API 中使用 ==========
async function registerUser(body: unknown) {
  // 第 1 层：Schema 校验（Zod 抛出，自动成为业务错误）
  const input = RegisterSchema.parse(body);

  // 第 2 层：业务逻辑中的预期错误
  const existing = await db.users.findUnique({ where: { email: input.email } });
  if (existing) {
    throw new BusinessError('该邮箱已被注册', 'EMAIL_ALREADY_EXISTS', 409);
  }

  // 第 3 层：依赖调用（可能抛出 SystemError）
  try {
    return await db.users.create({ data: input });
  } catch (error) {
    if (error instanceof Prisma.PrismaClientKnownRequestError) {
      throw new SystemError('数据库操作失败', 'Database');
    }
    throw error; // 未知错误向上传播
  }
}
```

### 四、统一错误响应格式

无论哪种错误，前端都应该收到格式一致的响应，这样只需写一套错误处理逻辑：

```typescript
// ========== 统一响应格式 ==========
interface ApiResponse<T = unknown> {
  success: boolean;             // 请求是否成功
  data?: T;                     // 成功时的数据
  error?: {                     // 失败时的错误信息
    code: string;               // 机器可读的错误码（前端用来做逻辑判断）
    message: string;            // 用户可读的错误提示（前端直接展示）
    details?: unknown;          // 详情（开发环境才有，生产环境隐藏）
  };
  requestId: string;            // 请求追踪 ID（用于查日志）
}

// ========== Next.js Route Handler 中的统一错误处理 ==========
import { NextResponse } from 'next/server';
import { ZodError } from 'zod';

export async function POST(req: Request) {
  const requestId = crypto.randomUUID(); // 每个请求一个唯一 ID

  try {
    const body = await req.json();

    // Zod 校验 —— 失败时 ZodError 包含详细的字段级错误
    const input = RegisterSchema.parse(body);

    // 业务逻辑
    const user = await registerUser(input);

    return NextResponse.json({
      success: true,
      data: user,
      requestId,
    }, { status: 201 });

  } catch (error) {
    // ────────── 错误分类处理 ──────────

    // 1. Zod 校验失败 → 422
    if (error instanceof ZodError) {
      return NextResponse.json({
        success: false,
        error: {
          code: 'VALIDATION_ERROR',
          message: '输入数据格式不正确',
          // 字段级别的错误详情，帮助前端定位到具体输入框
          details: error.errors.map((e) => ({
            field: e.path.join('.'),
            message: e.message,
          })),
        },
        requestId,
      }, { status: 422 });
    }

    // 2. 业务错误 → 对应的 HTTP 状态码
    if (error instanceof BusinessError) {
      return NextResponse.json({
        success: false,
        error: {
          code: error.code,
          message: error.message,
        },
        requestId,
      }, { status: error.httpStatus });
    }

    // 3. 系统错误 → 503
    if (error instanceof SystemError) {
      console.error(`[${requestId}] 系统错误 (${error.service}):`, error.message);
      return NextResponse.json({
        success: false,
        error: {
          code: 'SERVICE_UNAVAILABLE',
          message: '服务暂时不可用，请稍后再试',
        },
        requestId,
      }, { status: 503 });
    }

    // 4. 未知错误 → 500（记录完整堆栈，但不暴露给客户端）
    console.error(`[${requestId}] 未预期的错误:`, error);
    return NextResponse.json({
      success: false,
      error: {
        code: 'INTERNAL_ERROR',
        message: '服务器内部错误',
        // 生产环境不暴露 details，开发环境暴露堆栈
        ...(process.env.NODE_ENV === 'development' && {
          details: error instanceof Error ? error.stack : String(error),
        }),
      },
      requestId,
    }, { status: 500 });
  }
}
```

### 五、Next.js 中的错误处理模式

#### 5.1 error.tsx —— 错误边界

`error.tsx` 捕获**渲染阶段**的错误，是 React Error Boundary 的 Next.js 封装：

```tsx
"use client";
// app/posts/error.tsx

export default function PostsError({
  error,
  reset,       // 重试函数：重新渲染出错的路由段
}: {
  error: Error & { digest?: string };  // digest 是 Next.js 生成的错误哈希
  reset: () => void;
}) {
  return (
    <div className="flex flex-col items-center justify-center min-h-[400px]">
      <h2 className="text-xl font-semibold text-red-600">加载失败</h2>
      <p className="text-gray-500 mt-2">
        {error.message || '发生了未知错误'}
      </p>
      <button
        onClick={reset}
        className="mt-4 px-6 py-2 bg-blue-600 text-white rounded-lg hover:bg-blue-700 transition"
      >
        重试
      </button>
    </div>
  );
}
```

**error.tsx 的隔离规则**（很重要）：

- `error.tsx` 只捕获**同级和子级 `page.tsx`** 的渲染错误
- `layout.tsx` 的错误**不会**被同级的 `error.tsx` 捕获（需要父级来处理）
- `error.tsx` 必须是客户端组件（因为需要交互式的重试按钮）

#### 5.2 notFound() —— 主动触发 404

```tsx
// app/posts/[id]/page.tsx
import { notFound } from 'next/navigation';

export default async function PostPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const post = await db.posts.findUnique({ where: { id: Number(id) } });

  if (!post) {
    // 主动触发 404，Next.js 会渲染最近的 not-found.tsx
    notFound();
  }

  return <article>{post.content}</article>;
}
```

#### 5.3 Server Actions 中的错误处理

Server Actions 用特殊的方式返回错误（通过 `useActionState` 或直接 `try/catch`）：

```tsx
// ========== 方式 A：用 try/catch（简单直接） ==========
"use client";

import { createPost } from './actions';
import { useState } from 'react';

export function CreatePostForm() {
  const [error, setError] = useState<string | null>(null);

  async function handleSubmit(formData: FormData) {
    setError(null);
    try {
      await createPost(formData);
      // 成功：跳转或显示成功提示
    } catch (err) {
      setError(err instanceof Error ? err.message : '创建失败');
    }
  }

  return (
    <form action={handleSubmit}>
      {error && <p className="text-red-600 text-sm">{error}</p>}
      {/* 表单字段... */}
    </form>
  );
}
```

```tsx
// ========== 方式 B：用 useActionState（React 19 推荐） ==========
"use client";

import { useActionState } from 'react';
import { createPost } from './actions';

interface FormState {
  error?: string;
  fieldErrors?: Record<string, string>; // 字段级别的错误
}

const initialState: FormState = {};

export function CreatePostForm() {
  const [state, formAction, isPending] = useActionState(createPost, initialState);

  return (
    <form action={formAction}>
      {state.error && (
        <div className="bg-red-50 text-red-600 p-3 rounded-md text-sm">
          {state.error}
        </div>
      )}

      <div>
        <input name="title" className="border rounded p-2 w-full" />
        {state.fieldErrors?.title && (
          <p className="text-red-600 text-xs mt-1">{state.fieldErrors.title}</p>
        )}
      </div>

      <button type="submit" disabled={isPending} className="...">
        {isPending ? '创建中...' : '创建帖子'}
      </button>
    </form>
  );
}
```

```typescript
// ========== Server Action 定义 ==========
"use server";
// app/posts/actions.ts

import { z } from 'zod';

const CreatePostSchema = z.object({
  title: z.string().min(1, '标题不能为空').max(200, '标题最多 200 字'),
  content: z.string().min(10, '内容至少 10 字'),
});

interface FormState {
  error?: string;
  fieldErrors?: Record<string, string>;
}

export async function createPost(
  prevState: FormState,
  formData: FormData
): Promise<FormState> {
  // 从 FormData 提取数据
  const rawData = {
    title: formData.get('title') as string,
    content: formData.get('content') as string,
  };

  // Zod 校验
  const result = CreatePostSchema.safeParse(rawData);
  if (!result.success) {
    // 将 Zod 错误转换为友好的字段错误格式
    const fieldErrors: Record<string, string> = {};
    for (const issue of result.error.issues) {
      const field = issue.path[0] as string;
      if (!fieldErrors[field]) {
        fieldErrors[field] = issue.message;
      }
    }
    return { fieldErrors };
  }

  try {
    await db.posts.create({ data: result.data });
    // 成功：可以 trigger revalidatePath 刷新缓存
    return {}; // 空对象表示成功
  } catch (error) {
    return { error: '创建失败，请稍后重试' };
  }
}
```

### 六、Node.js 全局错误处理

未捕获的异常会导致 Node.js 进程崩溃。应该设置全局兜底：

```typescript
// ========== server.js 或 instrumentation.ts 中 ==========

// 1. 未捕获的同步异常（程序 Bug，应该记录后优雅退出）
process.on('uncaughtException', (error) => {
  console.error('💥 未捕获的异常，进程即将退出:', error);
  // 记录到日志系统、发送告警
  // logger.fatal('uncaughtException', { error: error.stack });
  // 给进程一点时间记录日志，然后退出
  setTimeout(() => process.exit(1), 1000);
});

// 2. 未处理的 Promise 拒绝（不一定会导致进程退出，但应该修复）
process.on('unhandledRejection', (reason, promise) => {
  console.error('⚠️ 未处理的 Promise 拒绝:', reason);
  // 记录到日志系统，发送告警
  // logger.error('unhandledRejection', { reason });
});

// ========== 开发环境用 Zod 的 safeParse 代替 parse ==========
// parse() 失败直接抛异常，safeParse() 返回 { success, data, error }

// ❌ 抛异常方式（适合全局中间件统一 catch）
const input = Schema.parse(body);

// ✅ 不抛异常方式（适合需要精细控制错误流程的场景）
const result = Schema.safeParse(body);
if (!result.success) {
  return { errors: result.error.flatten().fieldErrors };
}
const input = result.data;  // 类型安全
```

### 七、用户友好 vs 开发者友好

这是错误处理中最重要的**分离关注点**：

```typescript
// ═══════════════════════════════════════
//  面向用户的错误（User-Facing）
//  特点：模糊、友好、不暴露技术细节
// ═══════════════════════════════════════

const USER_FACING_MESSAGES: Record<string, string> = {
  VALIDATION_ERROR: '输入信息有误，请检查后重试',
  EMAIL_ALREADY_EXISTS: '该邮箱已被注册',
  INVALID_CREDENTIALS: '邮箱或密码不正确',
  RATE_LIMIT_EXCEEDED: '操作过于频繁，请 1 分钟后再试',
  SERVICE_UNAVAILABLE: '服务暂时不可用，请稍后再试',
  INTERNAL_ERROR: '服务器内部错误，我们正在处理',
  // 永远不会出现："Connection refused to PostgreSQL at 10.0.1.5:5432"
  //               "TypeError: Cannot read properties of null"
};

// ═══════════════════════════════════════
//  面向开发者的错误（Developer-Facing）
//  特点：精确、详细、便于定位
// ═══════════════════════════════════════

function logError(requestId: string, error: unknown) {
  if (error instanceof BusinessError) {
    console.warn(`[${requestId}] [业务错误] ${error.code}: ${error.message}`);
    return;
  }

  if (error instanceof SystemError) {
    console.error(`[${requestId}] [系统错误] ${error.service} 不可用:`, {
      message: error.message,
      stack: error.stack,
    });
    return;
  }

  // 未知错误：记录完整堆栈
  console.error(`[${requestId}] [未知错误]`, {
    message: error instanceof Error ? error.message : String(error),
    stack: error instanceof Error ? error.stack : undefined,
    timestamp: new Date().toISOString(),
  });
}
```

### 八、实战：表单系统的完整校验 + 错误处理链路

以下是一个"注册表单"的完整前端到后端链路，演示如何把校验和错误处理贯穿全程。

```typescript
// ============================================================
// 文件 1: schemas/auth.ts —— 共享的 Zod Schema（前后端同源）
// ============================================================
import { z } from 'zod';

export const RegisterSchema = z.object({
  username: z
    .string()
    .min(3, '用户名至少 3 个字符')
    .max(30, '用户名最多 30 个字符')
    .regex(/^[a-zA-Z0-9_]+$/, '用户名只能包含字母、数字和下划线'),
  email: z.string().email('请输入有效的邮箱地址'),
  password: z
    .string()
    .min(8, '密码至少 8 位')
    .regex(/[a-z]/, '密码需要包含小写字母')
    .regex(/[A-Z]/, '密码需要包含大写字母')
    .regex(/[0-9]/, '密码需要包含数字'),
  confirmPassword: z.string(),
}).refine((data) => data.password === data.confirmPassword, {
  message: '两次输入的密码不一致',
  path: ['confirmPassword'],
});

// 自动推导类型 —— 前后端共用
export type RegisterInput = z.infer<typeof RegisterSchema>;

// Zod Schema 的错误信息扁平化（用于表单字段绑定）
export function flattenZodErrors(error: z.ZodError): Record<string, string> {
  const fieldErrors: Record<string, string> = {};
  for (const issue of error.issues) {
    const key = issue.path.join('.');
    if (!fieldErrors[key]) {
      fieldErrors[key] = issue.message; // 每个字段只保留第一个错误
    }
  }
  return fieldErrors;
}
```

```typescript
// ============================================================
// 文件 2: app/auth/register/actions.ts —— Server Action
// ============================================================
"use server";

import { RegisterSchema, flattenZodErrors } from '@/schemas/auth';
import { db } from '@/lib/db';
import { hashPassword } from '@/lib/auth';
import { logError } from '@/lib/logger';

interface RegisterState {
  success?: boolean;
  error?: string;
  fieldErrors?: Record<string, string>;
}

export async function register(
  prevState: RegisterState,
  formData: FormData
): Promise<RegisterState> {
  // 步骤 1：提取表单数据
  const rawData = {
    username: formData.get('username')?.toString().trim() || '',
    email: formData.get('email')?.toString().trim() || '',
    password: formData.get('password')?.toString() || '',
    confirmPassword: formData.get('confirmPassword')?.toString() || '',
  };

  // 步骤 2：后端 Zod 校验（安全底线，前端校验不能代替）
  const result = RegisterSchema.safeParse(rawData);
  if (!result.success) {
    return { fieldErrors: flattenZodErrors(result.error) };
  }

  const { username, email, password } = result.data;

  try {
    // 步骤 3：检查邮箱是否已被注册（业务校验）
    const existing = await db.users.findUnique({ where: { email } });
    if (existing) {
      return { error: '该邮箱已被注册，请直接登录或使用其他邮箱' };
    }

    // 步骤 4：创建用户
    await db.users.create({
      data: {
        username,
        email,
        passwordHash: await hashPassword(password),
      },
    });

    return { success: true };

  } catch (error) {
    // 步骤 5：系统错误 / 未知错误的兜底
    logError('register', error);
    return { error: '注册失败，请稍后重试。如继续遇到此问题，请联系技术支持。' };
  }
}
```

## 常见问题

### Q1：前端校验和后端校验的规则应该保持一致吗？怎么保持？

应该在**共享的 Zod Schema** 中定义规则，前后端引用同一个 Schema 文件。这样规则只有一处定义，不会出现前端允许 3 个字符、后端要求 5 个字符的 Bug。上面实战中的 `schemas/auth.ts` 就是这个模式。

### Q2：`ZodError` 的 `flatten()` 和 `format()` 有什么区别？

- `flatten()`：返回 `{ formErrors: string[], fieldErrors: Record<string, string[]> }`，适合绑定到表单字段
- `format()`：返回嵌套的错误树，保持原始 Schema 的结构

99% 的前端场景用 `flatten()`。

### Q3：什么时候用 `parse()`，什么时候用 `safeParse()`？

- `parse()`：失败抛异常。适合全局中间件、需要统一 try/catch 的地方
- `safeParse()`：返回 `{ success, data, error }`。适合需要精细控制错误流程的地方（如 Server Actions 中逐字段反馈）

### Q4：Server Actions 中抛出的错误能被 error.tsx 捕获吗？

不会。error.tsx 只捕获**渲染阶段**的错误。Server Action 中的错误必须由调用方（客户端组件）的 `try/catch` 或 `useActionState` 的 `state` 来处理。

### Q5：`uncaughtException` 和 `unhandledRejection` 的区别是什么？

- `uncaughtException`：同步代码中未被 try/catch 捕获的异常。Node.js 默认会让进程崩溃退出
- `unhandledRejection`：Promise 被 reject 但没有 `.catch()` 处理。Node.js 不会退出但会打印警告

两者都应该监听，并上报到日志/告警系统。

### Q6：Zod 的 `refine` 和 `superRefine` 什么时候用哪个？

- `refine`：简单的跨字段校验（一个条件），返回 true/false
- `superRefine`：复杂的多条件校验，需要给不同字段加不同的错误信息

如果 `refine` 的 `message` 和 `path` 参数足够，直接用 `refine`；需要多个 `ctx.addIssue` 时用 `superRefine`。

### Q7：如何避免在错误信息中泄露数据库结构或技术细节？

在错误响应中**永远只用映射后的消息**，不要直接返回 `error.message`。参考第七节的分层设计：面向用户的永远是 `USER_FACING_MESSAGES` 中的模糊描述，面向开发者的精确信息只记录在日志中。

### Q8：生产环境中应该把堆栈信息返回给前端吗？

**绝对不要**。堆栈信息（stack trace）暴露了服务端的文件路径、框架版本、代码逻辑，是安全风险。开发环境可以返回（方便调试），生产环境只返回 `requestId`，通过它去日志系统中检索详细信息。

## 本节小结

数据校验和错误处理是区分"能跑起来"和"能放心上生产"的关键：

1. **双层校验**：前端校验是体验（即时反馈），后端校验是安全（不信任客户端）
2. **Zod = 单一真相源**：一个 Schema 定义，自动得到 TypeScript 类型和运行时校验逻辑
3. **错误分层**：业务错误（可预期、可恢复）→ 系统错误（外部依赖）→ 未知错误（代码 Bug），每层独立处理
4. **统一响应格式**：无论哪种错误，前端收到的结构一致（`{ success, error: { code, message }, requestId }`）
5. **用户 vs 开发者**：用户看到模糊友好的提示，开发者通过 `requestId` 查日志看到精确堆栈
6. **全局兜底**：`uncaughtException` 和 `unhandledRejection` 是最后的防线

一个经验法则：**如果你看到一个 `try/catch` 里只有一个 `console.error` 然后返回 500，这个错误处理是不合格的。**好的错误处理会区分错误类型、选择合适的 HTTP 状态码、给用户有意义的信息、给开发者可追踪的日志。

至此，L4「API 设计与数据层」的三个子主题全部完成。你已经掌握了 RESTful API 设计规范、tRPC 端到端类型安全、以及从 Zod 校验到全局错误处理的完整链路——这些是构建生产级全栈应用的地基。
