## 学习目标

- 能识别资产、参与者、信任边界和数据流
- 能使用 STRIDE 等框架系统枚举威胁
- 能把威胁转成设计控制、测试和监控
- 理解安全验证包含预防、检测、响应和恢复
- 能评估前端、Server Function、API、数据库和供应链边界
- 能为 Atlas 输出可复查的威胁模型

## 内容讲解

### 一、威胁建模不是漏洞清单

它回答：

```text
我们在保护什么？
谁可能攻击或误用？
数据经过哪些边界？
可能发生什么？
已有控制是否足够？
如何验证和发现失效？
```

先画数据流，再讨论安全产品。

### 二、Atlas 资产

示例资产：

- 用户会话
- 未发布草稿
- 文章发布权限
- 审计日志
- 数据库备份
- 部署凭证
- 第三方 OAuth 身份映射

不同资产影响不同：草稿泄漏是保密性问题，文章被篡改是完整性问题，发布服务不可用是可用性问题。

### 三、信任边界

```text
浏览器
  │ 不可信输入
  ▼
CDN / Proxy
  │
  ▼
Next.js Server Functions / Route Handlers
  │ 授权边界
  ▼
数据访问层
  │
  ▼
PostgreSQL / 对象存储 / 队列
```

边界变化点包括：

- 数据从 URL、表单、Header 进入
- 客户端调用 Server Function
- 服务端调用第三方 API
- CI 获取部署凭证
- 备份离开生产账号

### 四、STRIDE

| 类别 | 问题 | Atlas 示例 |
|---|---|---|
| Spoofing | 冒充身份 | 窃取会话后冒充作者 |
| Tampering | 篡改数据 | 修改他人草稿 |
| Repudiation | 否认操作 | 发布后缺少审计证据 |
| Information Disclosure | 信息泄漏 | 错误返回数据库堆栈 |
| Denial of Service | 拒绝服务 | 导出接口耗尽内存 |
| Elevation of Privilege | 权限提升 | 普通用户调用审核接口 |

STRIDE 是检查框架，不替代领域威胁、隐私评估和业务滥用分析。

### 五、风险排序

不要用“高/中/低”替代依据。至少记录：

- 前置条件
- 可利用性
- 影响范围
- 数据敏感度
- 可检测性
- 已有控制
- 剩余风险

风险矩阵只能辅助排序，关键安全边界即使概率低也可能需要强制控制。

### 六、控制要覆盖生命周期

#### 预防

- 服务端输入校验
- 参数化查询
- 认证和资源级授权
- CSP 与输出编码
- 最小权限
- 依赖锁定与构建来源

#### 检测

- 异常登录
- 权限拒绝突增
- CSP 报告
- 依赖漏洞与完整性变化
- 审计日志缺口

#### 响应

- 会话撤销
- 密钥轮换
- 功能开关
- 隔离账号或租户
- 安全事故沟通

#### 恢复

- 数据恢复
- 权限与配置重建
- 清理持久化后门
- 重新验证受影响资产

### 七、安全需求要可测试

模糊：

```text
系统应当安全地处理权限。
```

可验证：

```text
普通作者对其他作者草稿执行 PATCH /articles/:id 时，
服务端返回 404，数据库无写入，审计日志记录 denied，
响应不包含目标文章标题。
```

### 八、自动化安全测试

层次：

- 单元测试：策略函数允许/拒绝矩阵
- 集成测试：API 输入、认证、授权、事务
- E2E：浏览器会话与 CSRF
- 静态扫描：依赖、Secret、危险 API
- 动态测试：预发布环境安全扫描
- 手工测试：业务逻辑、滥用路径

不要让扫描通过替代威胁建模。工具只能发现其规则覆盖的模式。

### 九、CSP 验证

先 Report-Only：

```http
Content-Security-Policy-Report-Only:
  default-src 'self';
  script-src 'self' 'nonce-...';
  object-src 'none';
  base-uri 'none';
  report-to csp-endpoint
```

流程：

1. 收集真实违规。
2. 区分业务依赖与攻击信号。
3. 修复内联脚本和第三方来源。
4. 设置采样、保留与告警。
5. 切换强制模式。

CSP 报告可能包含 URL，进入日志前需要隐私处理。

### 十、供应链边界

审查：

- 谁能发布包
- CI 是否固定 Action commit
- 安装脚本是否必要
- lockfile 是否被审阅
- 构建产物是否可追溯
- Source Map 和签名如何保护
- Secret 是否只在需要的 Job 可见

依赖数量不是唯一风险，维护者权限和发布链路同样重要。

## 常见问题

### Q1：小项目需要威胁模型吗？

需要，但规模可以小。登录、付款、隐私、上传和管理后台即使代码少也有高风险边界。

### Q2：只做 OWASP Top 10 可以吗？

它是通用检查入口，不能覆盖具体业务滥用、权限模型和供应链流程。

### Q3：前端是否属于安全边界？

前端可提供 CSP、可信类型、输入提示和减少暴露，但用户可控制客户端，权威校验必须在服务端。

### Q4：安全扫描零告警是否代表安全？

不代表。规则覆盖、配置、业务逻辑和运行环境仍可能存在缺口。

### Q5：威胁模型多久更新一次？

信任边界、认证、数据类型、第三方依赖或部署拓扑发生变化时更新；至少在重大 RFC 审阅时核对。

### Q6：是否需要保存攻击 payload？

只保存排查所需的最小、安全编码和受控样本，避免日志二次注入和敏感信息扩散。

## 实操作业

### 基础：数据流图

画出 Atlas 登录、草稿保存、文章发布和备份的数据流，标记所有信任边界与资产。

### 进阶：STRIDE 过账

对每条数据流至少评估六类威胁，记录已有控制、验证方式、剩余风险和负责人。

### 挑战：安全回归门禁

建立：

- 权限矩阵自动测试
- Secret 扫描
- 依赖高风险阻断
- CSP Report-Only 验证
- 上传文件类型与内容测试
- 预发布 DAST

故意注入一个权限回归，确认门禁可以失败并提供可定位证据。

<!-- exercise-guidance:start -->
### 作业参考与验收

- **基础**：标浏览器、API、DB、队列与备份边界，数据流含认证/敏感字段。不能只画组件框；登录和草稿分别列主体、资产与被信任输入。
- **进阶**：每条流按 STRIDE 评估，可不适用但需理由；威胁映射控制/证据/残余风险。身份认证不能代替资源授权，日志也有篡改和泄露风险。
- **挑战**：权限、secret、依赖、CSP、上传与 DAST 门禁各有失败夹具；扫描结果人工分类。故意取消授权控制后测试失败，恢复后正常与拒绝路径都通过。

## 本节小结

- 威胁建模从资产、参与者、数据流和信任边界开始
- STRIDE 用于系统枚举，不替代业务和隐私分析
- 控制需要覆盖预防、检测、响应和恢复
- 安全需求必须转成明确输入、结果和副作用
- 自动扫描是验证手段之一，不是安全结论
