## 内容讲解

### 一、技术选型为什么重要

你写过很多代码，修过无数 Bug，但有一种债比代码债更难还——**选错的技术债**。

代码债可以通过重构慢慢消化：一个函数写得烂，重写它；一个模块耦合度高，拆开它。但技术选型的代价是系统性的：

```
选错框架 → 3 年后生态萎缩 → 招不到人 → 迁移成本 = 重写整个系统
选错工具 → 构建时间 20 分钟 → CI 排队 2 小时 → 每天浪费整个团队的时间
选错范式 → REST 强套实时场景 → WebSocket 补丁越打越多 → 架构腐化
```

**选型不是在选"最好"的技术，而是在选"最适合当前上下文"的技术。** 这句话值得反复咀嚼。Facebook 用 React 不是因为 React 最优雅，而是因为 React 解决了他们当时的核心痛点——广告系统需要高性能 DOM 更新。Netflix 用 GraphQL 不是因为 REST 不够好，而是因为他们的多端（TV、手机、网页）需要灵活的查询粒度。

> **选型的第一原则：明确你要解决的问题。** 不解决问题的选型，最终会成为问题本身。

### 二、选型的七个维度

当你面对两个技术方案时，不要只比"谁的功能多"或"谁的 GitHub Star 多"。从以下七个维度系统评估：

| 维度 | 核心问题 | 反面案例 |
|------|----------|----------|
| **功能性** | 能解决核心问题吗？边界 case 覆盖如何？ | 用 MongoDB 的事务做支付，MongoDB 事务是后来加的，不如传统关系型可靠 |
| **性能** | 在预期规模下表现如何？高并发/大数据量时的表现？ | 单体应用选微服务，网络开销反而拖慢性能 |
| **生态** | 插件/库/工具链丰富吗？API 设计是否稳定？ | Svelte 很优秀但生态远不如 React，大型项目没有现成的 UI 库、状态管理方案 |
| **团队能力** | 团队有相关经验吗？学习曲线多陡？ | 选择 Rust 重写前端工具链，但团队全是 JS 开发者，学习成本远超预期增益 |
| **维护成本** | 升级路径是否平滑？Breaking Change 频繁吗？ | Angular 1→2 的重写式升级，社区分裂 |
| **社区活跃度** | Issue 响应速度？核心维护者几个？企业赞助情况？ | 个人开源项目，维护者离职后项目停更 |
| **许可证合规** | 许可证类型？是否有专利条款？ | GPL 协议的库在商业闭源项目中使用，法律风险 |

**实战套路**：做一个评分表。给每个维度加权，然后打分。这不是为了"算出一个正确答案"，而是**强迫自己把直觉拆解为可讨论的维度**。

```
选型评估表示例（React vs Vue 的团队内评估）：

维度（权重）           React      Vue
功能性    (×2)         9          8
性能      (×1.5)       8          9
生态      (×2)         10         7
团队能力  (×1.5)       8          6
维护成本  (×1)         7          9
社区      (×1.5)       10         8
许可证    (×1)         10         10
─────────────────────────────────────
加权总分               90.5       78.5
```

注意：权重反映你的上下文。一个 3 人创业团队和一个 200 人企业级团队，"团队能力"和"维护成本"的权重会完全不同。

### 三、ADR：让决策留痕

ADR（Architecture Decision Records）是记录重大架构决策的轻量级文档。它解决一个核心痛问题：**6 个月后，新同事问你"为什么当初选了 GraphQL 而不是 REST"，你既想不起来，也没法证明这个决策在当时是合理的。**

#### ADR 的完整模板

```markdown
# ADR-{序号}：{标题}

## 状态

<!-- 可选值：提议中 / 已接受 / 已废弃 / 已替代 -->

已接受

## 日期

2026-01-15

## 背景

<!-- 描述问题场景和驱动因素。这不是罗列方案的优缺点，而是说清楚：
     1. 我们现在面临什么问题？
     2. 为什么"保持现状"不可取？
     3. 这个决策的约束条件是什么？（时间、团队、技术栈） -->

我们的电商平台前端目前使用 Zustand 管理状态。随着项目规模扩展到 5 个子应用、
15 个共享模块，Zustand 的零配置理念反而成了负担：
- 每个模块独立创建 Store，跨模块通信靠手动传递，已有 3 处循环依赖 Bug
- 后端 BFF 层提供了丰富的缓存策略，前端重复请求同一数据的问题无法根治
- 新人 onboarding 需要理解每个模块自创的状态管理模式，文档零散

约束条件：(1) 已有 200+ 组件依赖 Zustand，不能一次性重写；(2) 团队 8 人，
其中 3 人对 React Query 有经验；(3) 必须在 2 个迭代内完成核心模块迁移。

## 决策

<!-- 清晰描述：选择了什么方案，拒绝了什么方案，核心理由是什么 -->

采用 **TanStack Query（原 React Query）** 作为服务端状态管理方案，
Zustand 保留用于客户端状态（UI 状态、表单草稿等）。

核心理由：
1. 90% 的状态问题来自服务端数据缓存，TanStack Query 原生解决缓存失效、
   请求去重、乐观更新等问题，不需要手写
2. 与现有 Zustand 不冲突——服务端状态由 TanStack Query 管理，
   客户端状态由 Zustand 管理，职责清晰
3. 渐进式迁移路径：逐个模块将 API 调用从 Store 迁移到 useQuery/useMutation，
   无需一次全部切换

拒绝的方案：
- **Redux Toolkit**：生态最强但引入概念过多（Slice、Thunk、Entity），
  对当前团队的学习成本不划算，且服务端缓存仍需要 RTK Query，本质上是同样的问题
- **纯 Zustand**：已证明在跨模块场景下力不从心，继续在 Zustand 上打补丁
  不如引入专业工具

## 后果

<!-- 诚实地写清楚：这个决策带来了什么正面影响和负面影响。
     这是 ADR 最有价值的部分——没有人能预知所有后果，但记录下你的预判，
     未来复盘时才知道哪些判断对了、哪些错了。 -->

### 正面影响
- 减少约 40% 的手写数据获取逻辑（loading / error / refetch 样板代码）
- 服务端数据天然具备缓存隔离、乐观更新、后台重取等能力
- 培训成本可控：TanStack Query 概念简单（Query / Mutation / Invalidation）

### 负面影响
- 引入新依赖，Bundle 增加约 12KB（gzip 后）
- Zustand 和 TanStack Query 共存时期，新人需要理解两套状态范式的边界
- 如果未来需要离线优先（Offline-First），TanStack Query 的原生支持有限，
  可能需要额外引入 Persist Query Client 插件或迁移方案

### 迁移风险
- 现有 Zustand Store 中的服务端状态逻辑需要在迁移过程中手动清理，
  迁移期间存在"同一数据存在于两处"的过渡态
```

### 四、典型选型场景深度分析

#### 场景一：React vs Vue

这个问题被问得最多，但它的答案从来不是"哪个更好"，而是"哪个更匹配你的上下文"。

| 维度 | 选 React 的典型场景 | 选 Vue 的典型场景 |
|------|---------------------|-------------------|
| **团队** | 已有 React 经验 / TypeScript 重度用户 / 需要跨 React Native | 团队来自传统模板引擎背景 / 偏好渐进式学习 |
| **项目** | 大型 SPA / 微前端 / 需要 SSR（Next.js 生态） | 中小型项目 / 快速原型 / 存量 jQuery 项目逐步改造 |
| **生态** | 需要丰富的第三方库 / 复杂的表单 / 可视化图表 | 需要开箱即用的全家桶 / 不想在 Router/Store/Build 上做选择 |
| **组织** | 公司技术栈已锁定 React / 需要跨项目复用组件 | 新团队自建技术栈 / 追求开发体验和文档友好度 |

**2026 年的新变量**：Server Components（React）和 Vapor Mode（Vue）都在向"服务端 + 客户端混合渲染"演进。两个框架的设计哲学在趋同——React 的 `use` hook 让数据获取更简单，Vue 的 Composition API 让逻辑复用更灵活。**选择的天平越来越倾向于团队能力和生态，而非框架本身的优劣。**

#### 场景二：REST vs GraphQL vs tRPC

```
REST：资源导向，稳定
├── 适合：对外开放的 API、cache-heavy 的读写分离场景
├── 痛点：over-fetching / under-fetching，多端适配需维护多个 endpoint
└── 生态：OpenAPI / Swagger 生成文档和 SDK

GraphQL：查询导向，灵活
├── 适合：多端（Web/iOS/Android/小程序）需要不同数据字段、复杂关联查询
├── 痛点：N+1 问题、复杂查询的 DB 压力、缓存困难、文件上传别扭
└── 生态：Relay / Apollo / GraphQL Code Generator

tRPC：类型导向，端到端类型安全
├── 适合：全栈 TypeScript 项目、前后端同仓库（Monorepo）
├── 痛点：仅限 TypeScript 生态、非 TS 客户端无法调用、不适合对外 API
└── 生态：tRPC + Zod（输入校验）+ Prisma（DB 层）= 全链路类型安全
```

**决策框架**：

```
你的项目是内部工具、前后端都是 TypeScript？
  ├── 是 → tRPC（类型安全零成本，开发效率最高）
  └── 否 → 需要支持多端（移动端/H5/第三方）吗？
            ├── 是 → GraphQL（灵活查询，避免为每个端维护一套 endpoint）
            └── 否 → REST + OpenAPI（最成熟、最好招人、CDN 缓存最友好）
```

#### 场景三：Vite vs Webpack vs Rspack

2026 年的构建工具格局已经清晰：

```
开发体验
  Vite（ESBuild + Rollup）       ← 开发极快，生产用 Rollup 打包
  Rspack（Rust 实现，兼容 Webpack） ← 比 Webpack 快 10 倍，生态兼容 Webpack Loader
  Turbopack（Rust 实现，Next.js 专属）← Next.js 生态，非通用方案

构建生态
  Webpack                       ← 生态最全，但已经是"旧时代的王者"
  Rspack                        ← Webpack 的最平滑替代
  Vite                          ← Webpack 的不兼容替代（但值得）
```

**选择建议**：
- 新项目：Vite（除非有强依赖 Webpack Loader 的库）
- 存量 Webpack 项目想提速：Rspack（兼容 Webpack 配置，迁移成本最低）
- Next.js 项目：不用选，直接用内置方案

#### 场景四：SQL vs NoSQL（前端视角）

前端开发者通常不决定数据库选型，但你经常要设计 BFF 层的数据模型：

```
PostgreSQL（关系型）          MongoDB（文档型）
├── 适合：结构化数据           ├── 适合：灵活 Schema、嵌套文档
├── 举例：订单、用户、支付      ├── 举例：日志、商品属性（不同品类字段不同）
├── 关联查询（JOIN）           ├── 聚合管道（Aggregation Pipeline）
└── 事务强                     └── 最终一致性

不要做的事：
❌ 因为"JSON 方便"就把订单系统用 MongoDB 存——退款场景的事务会让你崩溃
❌ 因为"SQL 规范"就把日志数据建表——字段每天都在变，Schema Migration 累死
```

#### 场景五：Monorepo vs Polyrepo

这是影响团队协作模式的基础设施决策：

```
Monorepo（Turborepo / Nx / pnpm workspace）
├── 优势：跨项目重构一条命令、共享配置/类型/组件零成本、原子化 CI
├── 劣势：仓库体积大、权限控制粗、CI 需要额外做增量构建
└── 适合：10+ 人的全职前端团队，多个相互依赖的子应用/库

Polyrepo（独立仓库）
├── 优势：权限隔离、独立部署、仓库小
├── 劣势：跨仓库变更需要多个 PR、版本对齐困难、公共代码复制粘贴化
└── 适合：不同团队独立维护、弱依赖、或组织要求代码隔离
```

**不要盲目上 Monorepo**——如果你只有 2 个子项目，Monorepo 的配置成本大于收益。

### 五、选型中的常见陷阱

**陷阱一：追新综合征**

现象：React 19 刚发布就用上 Server Components，Next.js 15 第二天就升级。

```
正确姿势：
├── 主版本升级：等 .1 或 .2 补丁后，先在非核心项目验证
├── 新范式（如 RSC）：先在内部工具中试用 1-2 个月，总结踩坑经验
└── 原则：别人踩过的坑不要重复踩。让激进团队帮你探路。
```

**陷阱二：过度工程化**

现象：3 人团队的内部管理后台，用了微前端 + GraphQL + K8s。

```
自检清单：
□ 这个方案解决的痛点在"我们的规模"下真的存在吗？
□ 如果不引入这个技术，最坏的结果是什么？能接受吗？
□ 2 年后如果有人接手，他会觉得这方案是"明智的"还是"疯狂的"？
```

**陷阱三：框架锁定（Vendor Lock-in）**

Next.js 的 `next/image`、`next/link`、`next/font` Vercel 特有能力便捷但绑定性强。Remix 的 `loader` / `action` 范式也同理。

```
防御策略：
├── 业务逻辑和框架尽量解耦：核心逻辑放在纯 TS/JS 模块中，不依赖框架 API
├── 抽象层：对框架 API 做薄封装（如 useRouter → 自己的 useNavigation）
└── 评估替换成本：做一个"最坏情况推演"——如果 2 年后需要换掉这个框架，要改多少代码？
```

### 六、渐进式迁移 vs 大爆炸重写

这是选型正确之后，第二重要的决策——**怎么把选型落地**。

```
大爆炸重写（Big Bang Rewrite）：
    旧系统 ────────────────→ 并行开发 6 个月 ───→ 新系统（一次性切换）
                                                   ↑
                                              切换日：万一失败，无路可退

渐进式迁移（Strangler Fig Pattern）：
    旧系统 ──→ 模块 A 迁移 ──→ 模块 B 迁移 ──→ ... ──→ 旧系统最终退役
               ↓ 验证 OK       ↓ 验证 OK              ↓ 验证 OK
              可以随时回滚     可以随时回滚           可以随时回滚
```

**渐进式迁移的常用策略**：

| 策略 | 适用场景 | 实现方式 |
|------|----------|----------|
| **路由层切换** | 单页应用 → 新框架 SPA | Nginx / CDN 按路径分发请求到不同应用 |
| **组件级跨越** | 同一框架内的技术升级 | 逐个组件替换（如 Class → Hooks） |
| **微前端** | 巨石应用到多个独立子应用 | Module Federation，每个子应用独立框架/部署 |
| **BFF 层过渡** | 后端 API 升级 | BFF 层同时聚合新旧 API，前端无感切换 |

> **迁移切片应有明确且较短的完成周期。** 可以把 1-2 周作为常见起点，再根据团队发布节奏、验证成本和风险调整。每个切片都应能独立上线、验证和回滚；如果预计跨越多个迭代，应继续拆分，或明确中间状态如何长期共存。

### 七、实战：为电商项目撰写 3 篇 ADR

假设场景：你是一个电商项目的 Tech Lead，项目处于启动阶段。你需要为以下三个决策撰写 ADR。

#### ADR 1：前端框架选择

```markdown
# ADR-0001：选择 React 作为前端框架

## 状态

已接受

## 日期

2026-01-10

## 背景

电商平台包含：PC 端主站、移动端 H5、商家后台、运营后台，预计 4 个子应用。
团队当前 6 名前端开发者，计划扩到 10 人。

核心需求：
- 多子应用间复用 UI 组件（商品卡片、价格展示、购物车逻辑等）
- 需要 SSR/SSG 以支持 SEO 和首屏性能
- 未来可能扩展到 React Native 实现 App 端

约束条件：
- 团队中有 4 人有 React 经验，1 人有 Vue 经验，1 人为应届生
- 有 2 个现有的 Vue 后台管理系统（商家后台的一部分），但核心逻辑可以重写
- 启动时间紧张，1 月内需要完成 MVP

## 决策

采用 **React + Next.js（App Router）** 作为前端框架。

核心理由：
1. Next.js 是 React 生态中 SSR/SSG 最成熟的方案，SEO 和首屏性能有保障
2. 团队已有 2/3 的 React 经验者，培训成本最低
3. React Native 的扩展路径清晰，电商天然需要 App 端
4. React 生态中的 UI 库（Radix UI / shadcn/ui）、状态管理（TanStack Query）
   已有成熟的最佳实践，能加速 MVP 交付

拒绝的方案：
- **Vue + Nuxt**：生态同样优秀，但在"可招聘性"和"现有团队能力"上不占优
- **Svelte + SvelteKit**：简洁优雅但社区生态和人才储备不够，大型电商项目风险过高
- **纯 React（不用 Next.js）**：需要自己搭建路由、SSR、图片优化等，
  重复造轮子，不符合快速交付的约束

## 后果

### 正面影响
- SSR 保障首屏性能和 SEO，对电商转化率有直接帮助
- App Router 的 Server Components 减少客户端 JS 体积，对移动端 H5 友好
- 社区资源丰富，遇到问题能找到现成的解决方案

### 负面影响
- Next.js 的"Vercel 锁定"风险：部分特性（ISR 的细粒度控制、Analytics）
  强依赖 Vercel 平台
- App Router 的缓存策略复杂（四种缓存类型），需要文档化团队规范
- 两个现有 Vue 后台需要重写，短期投入增加

### 缓解措施
- 核心组件（商品卡片等）用纯 TS 封装，不依赖 Next.js 专有 API
- 建立团队 Next.js 使用规范文档，覆盖缓存策略、数据获取模式、错误处理
- Vue 后台迁移作为第二批迭代，MVP 阶段暂时保留
```

#### ADR 2：状态管理方案选择

```markdown
# ADR-0002：选择 TanStack Query + Zustand 作为状态管理方案

## 状态

已接受

## 日期

2026-01-12

## 背景

电商平台的状态需求分析：
- **服务端状态（占 80%）**：商品列表、详情、购物车同步、订单状态、
  用户信息——这些数据来自后端，需要在客户端缓存、去重、失效
- **客户端状态（占 15%）**：UI 状态（弹窗、loading）、表单草稿、
  筛选条件暂存
- **跨组件通信（占 5%）**：全局通知、主题切换

团队评估：Redux 经验者 3 人，但不希望在 2026 年继续用 Redux 的
"Action → Reducer → Store → Selector"链条处理数据获取。

## 决策

采用 **TanStack Query（服务端状态）+ Zustand（客户端状态）** 的组合。

责任边界：
- TanStack Query 负责：所有 API 请求的缓存、去重、乐观更新、
  后台重取、分页/无限滚动
- Zustand 负责：UI 状态（模态框开关、表单步骤）、全局偏好（主题、语言）

核心理由：
1. 职责分离——服务端状态和客户端状态的失效策略完全不同，
   不应放在同一套机制中处理
2. 减少样板代码——相比 Redux Toolkit，数据获取的 loading / error /
   success 状态由 useQuery 自动管理
3. Zustand 的 API 极简，5 分钟上手，适合零散的 UI 状态

拒绝的方案：
- **Redux Toolkit + RTK Query**：概念多（Slice、Entity、Thunk），
  新人上手需要 1-2 周。RTK Query 本身也很好，但在概念体系上增加了学习成本。
  选 TanStack Query 是因为它更聚焦——只做服务端状态这一件事
- **Jotai / Recoil**：原子化状态管理更灵活，但电商场景不需要那么细粒度的
  状态拆分。Zustand 的单一 Store 模型已经足够

## 后果

### 正面影响
- 每个数据获取 Hook 自动附带 loading / error / data 三态，无需手写
- 乐观更新（如购物车加减）由 useMutation 的 onMutate + onError
  rollback 天然支持
- 后台重取（staleTime / refetchOnWindowFocus）保障数据新鲜度，
  用户切换 Tab 回来后购物车自动更新

### 负面影响
- Bundle Size 增加约 13KB（gzip），移动端 H5 需要关注
- 两种状态范式的共存需要团队规范文档（什么放 Zustand、什么放 Query）
- 对离线场景（如弱网环境操作购物车）支持有限，需要额外搭配
  Persist Query Client 或自定义离线队列
```

#### ADR 3：构建工具选择

```markdown
# ADR-0003：选择 Vite 作为构建工具

## 状态

已接受

## 日期

2026-01-14

## 背景

电商平台的构建需求：
- 4 个子应用 + 1 个共享组件库（Package）
- 开发时热更新（HMR）速度直接影响开发体验
- 需要支持 TypeScript、CSS Modules、SVG 组件化、环境变量按环境注入

当前没有 Webpack 历史包袱，可以自由选择。

## 决策

采用 **Vite** 作为构建工具，共享组件库也用 Vite Library Mode 打包。

核心理由：
1. **开发体验**：HMR 毫秒级，Webpack 冷启动 30 秒的项目 Vite 只需 2 秒
2. **配置简洁**：TypeScript / CSS Modules / 环境变量开箱即用，
   不需要 webpack.config.js 的 200 行配置
3. **生产构建**：底层用 Rollup，Tree Shaking 和代码分割效果优于
   多数团队手写的 Webpack 配置

拒绝的方案：
- **Webpack**：配置复杂度高，HMR 慢，2026 年新项目不推荐
- **Rspack**：性能优秀、兼容 Webpack Loader，但我们没有 Webpack Loader
  依赖，用 Rspack 的额外优势不存在
- **Turbopack**：Next.js 专属（我们的管理后台也用 Vite 生态），不够通用

## 后果

### 正面影响
- 开发服务器冷启动 < 3 秒，HMR < 100ms，开发效率提升显著
- 配置文件总量约 50 行（vs Webpack 的 200+ 行）
- Rollup 产出物 Tree Shaking 质量好

### 负面影响
- Vite 插件生态不如 Webpack 丰富（但主流需求都已覆盖）
- 开发环境和生产环境使用不同打包器（ESBuild vs Rollup），
  极少数场景下行为可能不一致（如动态 import 的边界 case）
- CommonJS 依赖的处理需要额外配置（ssr.noExternal / optimizeDeps）

### 缓解措施
- CI 中增加生产构建验证步骤，确保构建结果符合预期
- 遇到 CJS 依赖时，使用 vite-plugin-commonjs 或在 optimizeDeps 中
  使用 esbuild 预构建
```

## 常见问题

**Q1：ADR 需要写得多正式？小决策也要写吗？**

ADR 只需要覆盖"如果做错了，3 个月后你会后悔"的决策。具体标准：(1) 影响架构结构（框架、状态管理、构建工具），(2) 影响多个子应用/模块，(3) 一旦做了很难回头（迁移成本高）。至于"用 lodash 还是 lodash-es"，不需要 ADR——一个 Tech Design Doc 里的备注就够。

**Q2：如果团队中有人强烈反对决策，ADR 怎么处理？**

这是好事——说明有人在认真思考。在 ADR 的状态中加一个"评论期"（Review），所有人的反对意见记录在 `## 反对意见` 章节中。决策人（通常是 Tech Lead 或架构师）最终拍板，但需要逐条回应反对意见，写清楚"为什么没有采纳"。

**Q3：ADR 写成后发现有错误怎么办？**

不修改原始 ADR，而是创建新的 ADR 替代它。例如：ADR-0002 决定用 Zustand 管理所有状态，后来发现服务端状态需要专业工具，就写 ADR-0005 "采用 TanStack Query，替代 ADR-0002 中的服务端状态部分"。旧 ADR 状态改为"已替代"，在索引中注明被哪个 ADR 替代。**保留决策的历史痕迹，比保留永远正确的记录更有价值。**

**Q4：小团队（3 人以下）也需要 ADR 吗？**

团队越小，ADR 越重要——因为小团队没有"决策者口口相传"的奢侈，任何一个人离开都意味着知识断层。但小团队的 ADR 可以更轻量：省略日期、简化背景，保留核心的"决策"和"后果"部分。

**Q5：技术选型中最容易被忽略的维度是什么？**

**许可证合规**。很多团队用了 GPL / AGPL 协议的库不自知。特别是公司被收购或上市时，法务团队会做技术尽职调查——曾经有因为一个 GPL 组件导致几百万估值的案例。养成习惯：添加任何依赖前，看一眼 License。

**Q6：GraphQL 和 tRPC 能共存吗？**

可以，但不推荐两者在所有场景混用。如果你同时有对外 API（需要灵活查询）和内部 BFF（需要类型安全），可以：外部 API → GraphQL，内部 BFF → tRPC。但如果你只是内部项目，不要因为"GraphQL 好酷"硬上——tRPC 的类型安全和简单性在你的上下文中更有价值。

**Q7："渐进式迁移"说到底有多慢？**

Strangler Fig Pattern 没有固定速度。一个常见的节奏是：每 2 周迁移一个独立模块（如"用户中心 → 新版本"），迁移后灰度 5%→20%→100%，稳定一周后再推进下一个模块。这样 3 个月能迁移 6 个模块，且每个模块都有安全回滚窗口。比"6 个月重写一切"安全得多。

**Q8：Monorepo 的 CI 时间怎么控制？**

关键是用增量构建工具（Turborepo / Nx），只构建和测试变更影响的包。Turborepo 通过 `turbo.json` 中的 `dependsOn` 和 `cache` 配置实现构建缓存。CI 中一个典型配置：`turbo run build test lint --filter=[HEAD^1]`，只处理变更文件关联的包。

## 实操作业

### 基础练习：为你的项目写一篇 ADR

1. 从你参与的项目中找一个"值得记录的架构决策"（框架选择、状态管理、构建工具、部署方案均可）
2. 按照本文的 ADR 模板，撰写一篇完整的 ADR
3. 重点写好"背景"和"后果"两部分——背景说清楚"为什么这个决策是必要的"，后果说清楚"这个决策带来了什么得失"
4. 在项目 `docs/adr/` 目录中保存，并创建 `README.md` 索引文件

### 进阶练习：完成选型对比分析

1. 选择一个你熟悉的选型场景（例如：CSS 方案选型——CSS Modules vs Tailwind vs styled-components vs Vanilla Extract）
2. 建立一个七维度评分表，给每个方案打分并加权
3. 基于评分表和上下文，撰写一篇精选方案的 ADR
4. 在 ADR 的"后果"部分，采访一位使用该方案超过 6 个月的同事，加入真实的实践反馈

### 挑战练习：制定团队的技术选型规范

1. 为你的团队制定一份"技术选型手册"，包含：
   - 选型流程（谁发起、谁评审、谁批准）
   - 七维度评估模板（含团队自定义的权重）
   - ADR 编写规范和存储位置
   - "黑名单"技术（团队明确不采用的技术及理由）
   - 技术选型的时间窗（例如：框架可选在项目启动时，启动后 3 个月内可以改，超过 3 个月只做增量式改进）
2. 找一位 Tech Lead 或架构师 review 你的手册
3. 根据反馈修改后，在团队技术分享会上介绍

### 作业参考与验收

- **基础**：ADR 写约束、选择、真实备选和收益/代价，保存不可变编号与索引。读者能追溯为何当时合理；已取代决策加链接，不重写历史假装从未选错。
- **进阶**：权重先依据项目约束确定，再用实测/官方支持/成本证据评分。敏感性分析看权重改变是否换赢家；真实反馈不可伪造，无访谈标待验证。
- **挑战**：流程按影响范围与可逆性分级，评审时限有责任人。禁用项给上下文理由与复审条件，不能用统一三个月窗口替代风险/回滚成本判断。

## 本节小结

技术选型是 L5 架构能力的第一课——它让你从"这个技术怎么写"升级到"这个技术该不该用"。回顾本节的三个核心收获：

1. **决策有框架**：不再凭直觉选技术，而是用七维度评估表 + ADR 让决策过程可审视、可回溯
2. **决策会留痕**：ADR 不是官僚文书，而是你作为架构师对未来的自己、对未来的同事留下的"决策说明书"
3. **决策知道止损**：理解渐进式迁移和大爆炸重写的边界，知道"慢就是稳，稳就是快"

从写代码到做决策，你的价值不再是你写了多少行代码，而是你帮团队避免了哪些错误决策。**好的技术决策，是最便宜的代码。**

下一节，我们将面对选型正确后的另一面——技术债。毕竟，每个决策都在创造未来的债，关键在于你知道哪些债"值得欠"。
