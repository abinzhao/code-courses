# 02-技术债识别与治理

## 学习目标

- 区分技术债的四种类型，建立"不是所有债都是坏事"的认知
- 掌握技术债的量化方法：代码异味清单、圈复杂度指标、测试覆盖率趋势
- 理解技术债治理的策略和优先级公式，能制定可落地的治理路线图
- 学会说服管理层分配治理时间的方法——用业务语言讲述技术债的危害
- 掌握重构 vs 重写的决策框架和微前端作为渐进升级的手段

---

## 内容讲解

### 一、承认一件事：你永远在欠债

先打掉一个幻觉：**没有技术债的项目是不存在的。** 就像国家有国债、公司有贷款、你有信用卡账单一样，技术债是软件工程的常态。

但关键区别在于——有些债是你主动欠的，你知道利息是多少、什么时候还；有些债是你不知不觉欠的，利息已经滚到你还不起。

```
刻意债 → 我选了一个简单方案快速上线，技术方案文档里写了"6个月后需要重构为XX"
疏忽债 → 我没有写测试，因为"太忙了"，3个月后没人敢改这段代码
设计债 → 我们用了一个插件架构，但插件之间共享全局状态，改一个崩溃三个
过程债 → Code Review 形同虚设，合并按钮一按，线上半夜告警
```

作为架构师，你的工作不是消灭所有技术债——那不可能。你的工作是：**让债可见、可量化、可控。**

---

### 二、技术债的四种类型

这个分类来自 Martin Fowler 的技术债象限，每一类需要不同的治理策略：

```
                        鲁莽的（Reckless）
                              │
          刻意 ───────────────┼───────────── 疏忽
                              │
                         谨慎的（Prudent）
```

| 类型 | 定义 | 真实例子 | 治理策略 |
|------|------|----------|----------|
| **刻意债 / 谨慎的** | 明知有更优方案，但为抢时间选择了更简单的。文档记录了为什么这么做、什么时候还 | "产品下个月就要上线大促，我们用硬编码的促销规则顶一下，大促结束后用规则引擎替换" | ✅ 这是好的债。记入技术债 Backlog，设定偿还时间窗口 |
| **刻意债 / 鲁莽的** | 明知有更好的做法，但不关心后果。没有文档、没有计划 | "管他呢，先上线再说。后期有问题后期再补" | ❌ 这不是债，是埋雷。Code Review 阶段就应该拦截 |
| **疏忽债 / 谨慎的** | 写完代码后才发现有更好的方案。团队缺乏经验而非缺乏责任心 | "我们当时不知道 React 18 的 Concurrent Features 能解决这个竞态条件问题，现在知道了" | 通过技术分享、代码走查、外部咨询来提升团队认知 |
| **疏忽债 / 鲁莽的** | 团队根本不关心代码质量。测试覆盖率长期为零，CI 是装饰品 | "Code Review？那是浪费时间" | ❌ 文化/管理问题，技术手段无法解决。需要团队共识和流程强制 |

**第一条铁律**：治理技术债之前，先分类。你把"刻意谨慎债"和"鲁莽疏忽债"放在同一个治理流程里，是对前者的侮辱。

### 三、技术债的信号——你的项目中招了几个？

不需要跑工具，用以下自检清单就能初步判断项目的债有多重：

**信号一：Bug 回归频率高**

修复一个 Bug → 引入两个新 Bug。这不是你的团队水平差，而是代码的耦合度过高——一个修改影响多处，而你根本不知道影响了哪里。

```
"修了购物车按钮的样式，首页的导航栏塌了"
→ 根因：全局 CSS 选择器污染，没有作用域隔离
→ 债的类型：设计债（缺乏 CSS 模块化 / CSS-in-JS / Tailwind 等隔离方案）
```

**信号二：onboarding 时间过长**

新同事需要 2 个月才能独立写第一个 Feature？不是他能力不够，是你的代码没有"新手友好"设计。

```
"新人花了 3 天时间才搞清楚用户登录后 token 存在哪里"
→ 根因：auth 逻辑分散在 5 个文件中，有的用 Cookie，有的用 localStorage，有的用内存
→ 债的类型：设计债（缺乏统一的状态管理 / 认证层抽象）
```

**信号三：同样的需求要做两次**

前端和 App 端各自实现了一套商品详情页逻辑。产品改一个字段，两个端各改一遍，还经常对不齐。

```
→ 债的类型：过程债（缺乏共享层 / BFF / 跨端协作规范）
```

**信号四：没人敢碰某些模块**

"那个模块是张三 2 年前写的，他离职后没人动过。" 这在团队中有一个专业术语——"巴士因子（Bus Factor）"。如果张三被巴士撞了（＝离职），这个模块就成黑盒了。

```
→ 债的类型：疏忽债（缺乏文档 + 测试 + 知识传承）
```

### 四、技术债的量化——从"感觉"到"数据"

管理层不会因为"代码看着不爽"给你治理时间。你需要把技术债翻译成管理层能理解的语言：**数据。**

#### 4.1 代码异味清单（Code Smell Checklist）

代码异味不是 Bug，但它是"这个代码在未来会变成 Bug"的预警信号。以下是前端项目最高频的 10 种异味：

```
1. 单文件超过 500 行                    → 职责过多，强耦合
2. 函数超过 50 行，或参数超过 5 个        → 难以测试，违反单一职责
3. 重复代码块（3 处以上相同逻辑）         → 修改一处漏 2 处，Bug 温床
4. 神秘命名（data, info, list, handler） → 读代码 = 解谜
5. 过多条件分支（10+ if-else / switch）  → 需要策略模式 or 查表法
6. 循环依赖（A 引 B，B 引 A）            → 打包失败 or 运行时 undefined
7. 死代码（注释掉的代码、未使用的变量）    → 占位置、混淆视线
8. 过深的嵌套（4 层以上的回调/组件嵌套）   → 难以理解，难以调试
9. 全局状态滥用（一切放 Redux/Store）     → 状态污染，不知谁改了谁
10. 硬编码（魔法数字、硬编码 URL）        → 改环境/改逻辑需要改代码
```

```bash
# 用工具而非肉眼扫描
# ESLint 配置：自动检测部分代码异味
# .eslintrc.js
module.exports = {
  extends: ['plugin:sonarjs/recommended'], // SonarJS 规则集
  rules: {
    'max-lines': ['warn', { max: 500 }],        // 文件行数限制
    'max-params': ['error', 4],                   // 函数参数数量限制
    'complexity': ['warn', 20],                    // 圈复杂度上限
    'no-console': ['warn', { allow: ['warn', 'error'] }], // console 限制
  },
};
```

#### 4.2 圈复杂度（Cyclomatic Complexity）

圈复杂度衡量一个函数有多少条独立的执行路径。简单来说：**if/else/switch/for/while 越多，圈复杂度越高**。

```
function calculatePrice(item) {     // 圈复杂度 = 1（基线）
  if (item.type === 'digital') {    // +1
    if (item.country === 'EU') {    // +1
      return item.price * 1.2;      // 含 VAT
    } else {
      return item.price;
    }
  } else if (item.type === 'physical') {  // +1
    return item.price + 10;         // 运费固定
  } else {
    return item.price;              // 圈复杂度 = 4 ✅ 可接受
  }
}

// ❌ 圈复杂度 = 30+ 的函数：
// - 很难理解所有分支
// - 几乎不可能完整测试（需要 30+ 个测试用例覆盖所有路径）
// - 每次修改都在赌博
```

**实践标准**：
- 圈复杂度 ≤ 10：健康
- 10 < 圈复杂度 ≤ 20：需要关注，建议重构
- 圈复杂度 > 20：高风险，应考虑重写并拆分为多个小函数

**工具**：

```bash
# 检查项目圈复杂度（需要安装 eslint-plugin-complexity 或其他工具）
npx eslint --rule 'complexity: ["warn", 10]' src/

# 或者用更专业的工具如 Plato、CodeClimate CLI
npx codeclimate analyze
```

#### 4.3 测试覆盖率趋势

覆盖率不是目的，但**覆盖率的下降趋势**是重要的预警信号。

```
测试覆盖率趋势图（每周记录一次）：

Week 1:  78%  ██████████████████████████████████████████████
Week 4:  72%  ████████████████████████████████████████████
Week 8:  65%  █████████████████████████████████████████
Week 12: 58%  ██████████████████████████████████████
──────────── ↓ 趋势不对！────────────────────────────────────

原因诊断：
- 新增 Feature 只写了代码，没写测试 → 在 PR 模板中增加测试 checklist
- 重构时删了测试，没补 → 重构 PR 必须维持或提升覆盖率
```

**覆盖率解读的陷阱**：
- 80% 覆盖率可能是"80% 的代码只测了 happy path"
- 关键路径（支付、登录）即使只有 5% 的代码，也必须有 100% 覆盖率
- 覆盖率上升但测试质量下降（Mock 了一切，测了个寂寞）比低覆盖率更危险

### 五、技术债治理策略

#### 策略一：破窗理论——不要让第一扇破窗存在

犯罪学中的破窗理论：一栋建筑如果有一扇窗户破了没人修，很快所有窗户都会被打破。在代码中：**如果有一个 hack 被允许合并，很快整个模块都会变成 hack 的集合。**

```
操作指南：
├── PR Review Checklist 中增加"代码异味"检查项
├── 发现异味时，给两种选择：(1) 修复 (2) 在技术债 Backlog 中登记，标注偿还日期
└── 超过偿还日期的债，自动转为 P1 Bug（让债进入 Sprint 排期，而不是一直躺在 Backlog 里）
```

#### 策略二：童子军规则（Boy Scout Rule）

"离开营地时，让它比你来的时候更干净。" 在编码中：**每次修改一个文件，顺手清理一个不相关的小问题。**

```
实战场景：
你在修一个购物车的 Bug，顺便发现购物车组件里有一个 200 行的 render 方法。
你不需要全部重构（那会拖慢 Bug 修复），但你可以做其中一小步：
- 把 render 中的 50 行 JSX 提取为一个子组件
- 给这个组件加一个 Prop Type 校验
这额外花了 15 分钟，但代码质量提升了一点。

积少成多：如果团队 8 个人每人每天做 1 个小改进，40 天大改进 = 320 个改进点。
```

#### 策略三：20% 治理时间

Google 著名的"20% 时间"起源于工程团队，很多团队也拿 20% 的时间治理技术债。

```
一个 2 周的 Sprint = 10 个工作日
20% = 2 天 / 人 / Sprint

这 2 天的使用方式：
├── 方式 A（推荐）：每人从技术债 Backlog 中认领一项，独立完成
├── 方式 B：团队集中治理——这 2 天全团队一起攻克一个高风险模块
└── 方式 C：技术债黑客松——周五下午，全队比赛谁消灭的债最多，奖励一杯咖啡
```

**关键**：这 20% 必须被保护。如果每次 Sprint 都把治理时间让给"紧急需求"，那治理永远排不上号。技术债治理是"重要但不紧急"的典型象限——你需要像保护核心需求排期一样保护它。

### 六、技术债的偿还优先级

治理技术债的最大陷阱是：**试图一次性还清所有债**。正确的做法是排优先级。

#### 偿还优先级公式

```
偿还优先级 = 影响面 × 修改频率 × 风险等级
```

**影响面**：这个债影响了多少用户 / 模块 / 开发者？
- 一个影响支付流程的债 >> 一个只影响管理后台某页面的债

**修改频率**：这段代码多久被改动一次？
- 一个月改 10 次的商品列表模块 >> 一年不改一次的工具函数

**风险等级**：这段代码出问题的后果有多严重？
- 数据丢失/金钱损失 >> 样式错乱 >> 控制台报了个 warning

```
优先级矩阵：

                    修改频率高              修改频率低
     ┌─────────────────────────┬────────────────────────┐
     │  ⭐ P0：立即治理        │  P1：Sprint 内处理      │
     │  例如：购物车状态管理，  │  例如：注册流程校验逻辑  │
影响力大│  每天被人改，错了就赔钱  │  不常改但错了用户无法注册│
     ├─────────────────────────┼────────────────────────┤
     │  P1：Sprint 内处理      │  P3：记录下来，等机会    │
影响力小│  例如：频繁改动的工具函数 │  例如：2 年前写的废弃页面 │
     └─────────────────────────┴────────────────────────┘
```

#### 实操：建立技术债 Backlog

用飞书多维表格或 Jira 建立技术债 Backlog，每条债包含：

```
| 字段 | 示例 |
|------|------|
| 标题 | 购物车状态管理耦合度过高，修改按钮样式影响价格计算 |
| 位置 | src/modules/cart/CartProvider.tsx |
| 类型 | 设计债 |
| 影响面 | 5 个模块（购物车、商品详情、订单确认、支付、售后） |
| 修改频率 | 每周 3-4 次 |
| 风险等级 | 高（涉及金额计算） |
| 优先级 | P0 = 9 × 4 × 5 = 180 |
| 预计修复时间 | 2 天 |
| 登记日期 | 2026-03-01 |
| 偿还截止日期 | 2026-03-15 |
```

### 七、说服管理层分配治理时间的方法

你把技术债分析得再好，管理层不给时间，一切免谈。以下是经过验证的说服策略：

**错误说法**：
> "我们的代码太烂了，需要花 2 周时间重构。"

管理层的听到的是："开发抱怨代码不好写，想要 2 周假。"

**正确说法**：
> "上个季度我们有 4 次线上故障是因为购物车模块的代码耦合导致的。每次平均影响 30 分钟、波及约 2000 名用户。如果我们投入 3 天做解耦重构，预计 Q2 的同类故障可以减少 80%。"

管理层听到的是："投入 3 天，避免 4 次故障，保护 8000 名用户体验。"

**翻译技巧**：把技术债翻译为业务影响

| 技术语言 | 业务语言 |
|----------|----------|
| 圈复杂度太高 | 每次改这个模块都可能引入新 Bug，线上故障概率高 |
| 测试覆盖率低 | 改代码不知道有没有改坏，全靠手工回归测试，上线周期长 |
| 代码重复 | 同样需求在不同端各做一遍，排期翻倍 |
| 缺乏文档 | 只有张三懂这个模块，他休假期间出问题没人能修 |
| 依赖版本过旧 | 安全漏洞无法修复，有合规风险（这个特别管用） |

**数据驱动的提案模板**：

```
治理提案：商品模块解耦重构

当前状态：
- 过去 6 个月，该模块产生 12 个 Bug（占全项目 Bug 的 35%）
- 每次修改该模块的平均排期为 3 人天（是其他模块的 2 倍）
- 新同事熟悉该模块需要 5 天（其他模块平均 2 天）

治理方案：
- 投入：2 人 × 3 天 = 6 人天
- 产出：解耦后预计 Bug 率下降 60%，修改排期缩短至 1.5 人天

ROI：
- 6 人天的投入，预计 3 个月内回收（按 Bug 修复时间节省计算）
- 1 次线上故障的赔偿 + 修复成本 ≈ 5 人天，避免 1 次故障就回本
```

### 八、重构 vs 重写的决策框架

这是技术债治理中最关键的岔路口——选错了，代价极大。

```
                    ┌──→ 重构（Refactor）
                    │    改善内部结构，不改变外部行为
技术债 ──→ 怎么还？ ──┤
                    │  ┌─→ 大爆炸重写（Big Bang Rewrite）
                    └──→ 重写（Rewrite）
                       └─→ 渐进式重写（Strangler Fig）
```

**应该重构的信号**：
- 核心业务逻辑是正确且经过验证的，只是代码结构混乱
- 有测试覆盖（哪怕只有集成测试），可验证重构后行为不变
- 团队理解当前系统的业务规则

**应该重写的信号**：
- 基础框架/语言已经过时（如 jQuery SPA → React/Vue）
- 原始架构假设已不成立（如"用户量 < 1000"但现在是百万用户）
- 代码质量差到修改成本 > 重写成本
- 团队完全不理解当前系统（原团队已离开）

**重写的致命陷阱**：Netscape 花了 3 年重写浏览器，结果 IE 已经占领市场。重写期间，现有系统还在跑，新功能还要加——你在同时维护两套系统。**对大多数团队而言，重写不如渐进式重构。**

```
重构与重写的决策公式：

修改成本 = 影响范围 × 每次修改平均工时
重写成本 = 完整开发 + 测试 + 部署 + 回滚方案 + 用户迁移 + 旧系统维护

如果 重写成本 < 未来 2 年修改成本 → 考虑重写
如果 重写成本 > 未来 2 年修改成本 → 渐进式重构

警告：大爆炸重写的实际成本通常是预估的 2-3 倍。
因为你估算时只算了"写代码"的时间，没算"理解旧系统的隐含逻辑"的时间。
```

### 九、微前端：渐进式架构升级的利器

当你的使命不是重构一个模块、不是重写一个系统，而是**升级整个架构**——微前端（Module Federation）是你最有力的工具。

#### Module Federation 的核心思想

```
传统单体前端：
┌─────────────────────────────────────┐
│         单一 SPA 应用                │
│  购物车 │ 商品 │ 订单 │ 用户 │ 支付   │
│  都共享同一个运行时、同一套依赖      │
└─────────────────────────────────────┘
→ 升级一个模块 = 全量构建 + 回归测试所有模块

Module Federation 微前端：
┌──────────┐ ┌──────────┐ ┌──────────┐
│ Shell 应用│ │ 购物车子应用│ │ 商品子应用 │  ← 独立构建、独立部署
│（路由调度）│ │ React 17  │ │ React 18  │  ← 可以不同版本！
└──────────┘ └──────────┘ └──────────┘
→ 升级一个模块 = 只构建这个子应用，其他无感
```

**Module Federation 解决的核心问题**：让你把一个巨石应用拆成独立部署的子应用，每个子应用可以独立选择技术栈版本、独立发布、独立回滚。

#### 适用场景

```
你的项目适合微前端的信号：
✅ 5+ 个团队在同一个仓库上开发，经常互相踩踏
✅ 不同模块的发布节奏完全不同（商品页每周发版，支付页每季度发一次）
✅ 某个模块需要技术升级但不可能停下来全面重写
✅ 构建时间超过 10 分钟，影响 CI/CD 效率

你的项目不适合微前端的信号：
❌ 3 人团队的小项目——微前端的架构成本远超收益
❌ 子应用之间需要频繁通信和共享状态——不如用 Monorepo
❌ 没有独立的部署能力（所有子应用必须一起发版）
```

#### 治理即升级：用微前端还技术债

```
阶段 1：当前状态
┌─────────────────────────────┐
│    单体 App（React 16 + Webpack 4）│
│  遗留模块 A │ 遗留模块 B │ 新模块 C  │
└─────────────────────────────┘

阶段 2：搭建 Shell + 迁移第一个模块
┌──────────────┐
│  Shell（新）  │  ← 应用壳，只负责路由和布局
└──────────────┘
       │ 加载
┌──────┴──────┐ ┌──────────────┐
│ 遗留模块 B   │ │ 新模块 C     │  ← 第一个迁移的模块，用新框架
│ React 16    │ │ React 18     │
└──────────────┘ └──────────────┘

阶段 3：逐步替换
┌──────────────┐
│     Shell     │
└──────────────┘
       │ 加载
┌──────┴──────┐ ┌──────┴──────┐ ┌──────┴──────┐
│ 模块 A (新)  │ │ 模块 B (新)  │ │ 模块 C (新)  │  ← 全部迁移完成
└──────────────┘ └──────────────┘ └──────────────┘

阶段 4：退役 Shell（如果子应用都独立后不再需要路由编排）
```

```
├── 购物车结算解耦（每次改动提心吊胆）

```

## 常见问题

**Q1：技术债是不是"写得不好"的同义词？**

不是。刻意债是一种工程策略——你用今天的简单换取明天的复杂，前提是你能精确评估利息。贷款买房子是债务，但不是错误；借高利贷去赌场才是。关键在于你有没有还款计划。

**Q2：什么情况下"欠刻意债"是错的？**

当你欠的债影响的是系统安全或数据一致性时。支付、退款、用户隐私相关的代码，不应该用"先上线再说"的心态处理。这些领域一旦出问题，利息不是额外的开发时间，而是赔偿金和法律风险。

**Q3：重构和重写到底什么时候选哪个？**

一个简单的判断标准：如果你能在**不改变系统对外行为**的前提下改善内部结构，就是重构。如果你必须改变系统对外行为（比如 API 契约、数据模型、交互流程），就是重写。重构比重写安全得多，因为你有现成的测试（和用户）帮你验证正确性。

**Q4：微前端会不会是过度工程化？**

如果你的团队 5 人以下，几乎一定是过度工程化。微前端的核心价值是**独立部署**和**技术栈隔离**——如果你不需要独立部署（同一时间发版没问题），不需要技术栈隔离（全团队用同一套技术栈），那你就是在用一个复杂的方案解决一个不存在的问题。

**Q5：每次 Sprint 的 20% 治理时间被抢占怎么办？**

记录被抢占的次数和原因。3 个 Sprint 后带着数据去找你的 Manager："这个季度我们规划了 6 天治理时间，实际只用了 1.5 天，被 4 次紧急需求打断。这 4 次紧急需求中有 2 次正是因为我们要治理的技术债导致的线上故障。这是一个恶性循环，我们需要你的帮助打破它。" 用数据说话，而不是抱怨。

**Q6：ESLint 规则越严格越好吗？**

不是。太严格的规则会让人绕过它或关闭它，反而失去信任。分层引入：第一层（error，必须修）：no-unused-vars、no-console（部分允许）、禁止 eval。第二层（warn，建议修）：complexity、max-lines。第三层（off，团队投票决定开不开）：prefer-destructuring、sort-imports（格式化问题交给 Prettier）。

**Q7：循环依赖如何发现和解决？**

`npx madge --circular src/` 可以检测循环依赖。解决方案：(1) 提取公共依赖到第三方模块，(2) 使用依赖反转——高层定义接口，低层实现，(3) 在 Monorepo 中将相互依赖的代码提取为共享 Package。最直接的办法：画一张依赖拓扑图，箭头只能单向——有反向箭头的地方就是问题。

**Q8：如果我是一个人做项目，还需要技术债管理吗？**

更需要。因为你没有 Code Review、没有 Pair Programming、没有人提醒你"这里可能有问题"。一个人的项目，技术债的唯一受害者就是未来的你自己。给自己一个简单的规则：每次写完一个 Feature，花 15 分钟回头看一眼——有没有可以顺手清理的？有没有该写注释但没写的？有没有该加测试但跳过的？这 15 分钟是给你 3 个月后的自己买的保险。

## 实操作业

### 基础练习：对当前项目做技术债扫描

1. 在你参与的项目中运行以下工具：
   - ESLint + SonarJS 规则集
   - `npx depcheck`（检测未使用依赖）
   - `npx madge --circular src/`（检测循环依赖）
2. 整理出一份技术债清单，按"影响面 × 修改频率 × 风险等级"排序
3. 标注每条债的类型（刻意 / 疏忽 / 设计 / 过程）
4. 在团队技术债 Backlog 中登记

### 进阶练习：制定并执行一个治理 Sprint

1. 从你的技术债清单中选出优先级最高的 2-3 项
2. 评估每项的修复所需工时
3. 在下一个 Sprint 中规划 20% 时间专门治理这 2-3 项债
4. Sprint 结束后写一份简要的治理报告：
   - 修复了什么、怎么修复的
   - 修复前后的代码质量指标对比
   - 遇到了什么意外困难
   - 下次类似治理有什么可以改进

### 挑战练习：推动组织级别的技术债治理文化

1. 在团队中建立技术债看板（推荐飞书多维表格 / Jira）
2. 定义技术债的分类标准和优先级计算公式
3. 在团队周会中增加"技术债趋势"固定议题（5 分钟，只看趋势数字）
4. 编写并宣讲一份《团队技术债治理手册》，包含：
   - 什么是技术债，四种类型的区分
   - 如何识别和登记技术债
   - 治理优先级怎么算
   - PR Review 中的技术债检查清单
   - 季度回顾节奏
5. 3 个月后，对比关键指标的趋势变化，写出总结报告

## 本节小结

技术债治理不是一场"把代码写完美"的道德运动，而是一项需要系统工程思维的资产管理。作为架构师，你的角色不是债的消灭者，而是债的精算师：

1. **认清债**：刻意债是策略，疏忽债是问题，设计债是隐患，过程债是文化
2. **量化债**：用圈复杂度、测试覆盖率、代码异味清单把"感觉"变成"数据"
3. **排列债**：影响面 × 修改频率 × 风险等级——先还最贵的
4. **说服人**：用业务语言讲技术债的故事，用 ROI 数据争取治理时间
5. **有工具**：重构 vs 重写的决策框架 + 微前端作为渐进升级手段

从修复 Bug 到识别债务模式，你的视角已经从"这一行代码"提升到了"这一类问题"。**优秀架构师不是不欠债，而是知道什么时候还、怎么还、还多少。**

下一节，我们进入架构治理的最后一课——RFC 方案编写。当技术选型和技术债治理都需要团队共识时，RFC 就是你最好的沟通工具。
