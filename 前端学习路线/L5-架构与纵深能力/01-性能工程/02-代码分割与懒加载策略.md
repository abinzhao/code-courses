# 02-代码分割与懒加载策略

## 学习目标

- 掌握代码分割的三种方式及其在架构层面的决策逻辑
- 能制定不同规模项目的 vendor chunk 策略
- 理解各种预加载指令的语义差异和优先级机制
- 掌握虚拟列表的实现原理和性能边界
- 能独立完成一个项目的 bundle 分析并落地优化方案

## 内容讲解

### 一、代码分割的架构视角

L3 阶段你已经学过代码分割的基础配置。站在 L5 架构视角，代码分割的本质是回答三个问题：

1. **什么代码必须首屏加载？** → 决定入口 bundle 的大小
2. **什么代码可以延迟加载？** → 决定懒加载的切分点和预加载策略
3. **什么代码几乎不变？** → 决定 vendor chunk 的粒度，追求最大化缓存命中率

这三个问题的答案构成了你的**代码分割策略**，它应该是一份文档化的决策，而不是散落在 webpack 配置中的随意参数。

#### 三种分割方式的决策树

```
你有一个模块需要拆分
  │
  ├── 它是独立页面/路由吗？
  │     └── 是 → 动态 import() + React.lazy → 路由级懒加载
  │
  ├── 它被多个页面使用吗？
  │     └── 是 → splitChunks 提取为 common chunk
  │
  ├── 它是第三方库吗？
  │     ├── React 全家桶 → 单独 vendor chunk（更新频率极低）
  │     ├── UI 组件库 → 单独 vendor chunk（偶尔更新）
  │     └── 其他工具库 → 合并 vendor chunk
  │
  └── 它是大型非首屏组件吗（图表、编辑器、视频播放器）？
        └── 是 → 动态 import() + 交互触发时的懒加载
```

### 二、动态导入：从路由级到组件级

#### 路由级懒加载（每个 SPA 的基础）

```tsx
// router.tsx —— 路由级懒加载的标准写法
import { lazy, Suspense } from 'react';
import { createBrowserRouter } from 'react-router-dom';

// ✅ 每个页面都是独立的 chunk，首屏只加载当前路由的代码
const HomePage = lazy(() => import(
  /* webpackChunkName: "page-home" */
  /* webpackPrefetch: true */
  './pages/HomePage'
));

const DashboardPage = lazy(() => import(
  /* webpackChunkName: "page-dashboard" */
  './pages/DashboardPage'
));

// ❌ 错误：不要在 lazy 外面包任何东西
// const Page = lazy(async () => {
//   const mod = await import('./Page');
//   return { default: mod.Page };  // 这样不行，lazy 要求返回 { default: Component }
// });

const router = createBrowserRouter([
  {
    path: '/',
    element: (
      // Suspense 是懒加载的"加载态入口"
      <Suspense fallback={<PageSkeleton />}>
        <HomePage />
      </Suspense>
    ),
  },
  {
    path: '/dashboard',
    element: (
      <Suspense fallback={<PageSkeleton />}>
        <DashboardPage />
      </Suspense>
    ),
  },
]);

// ✅ 骨架屏：比 spinner 更好的加载体验
function PageSkeleton() {
  return (
    <div className="page-skeleton" aria-busy="true" aria-label="页面加载中">
      <div className="skeleton-header" />
      <div className="skeleton-content">
        <div className="skeleton-line" style={{ width: '80%' }} />
        <div className="skeleton-line" style={{ width: '60%' }} />
        <div className="skeleton-line" style={{ width: '90%' }} />
      </div>
      <style>{`
        .skeleton-header { height: 200px; background: linear-gradient(90deg, #f0f0f0 25%, #e0e0e0 50%, #f0f0f0 75%); margin-bottom: 24px; border-radius: 8px; }
        .skeleton-line { height: 16px; background: #f0f0f0; margin-bottom: 12px; border-radius: 4px; }
      `}</style>
    </div>
  );
}
```

#### 组件级懒加载：不只有路由才需要懒加载

```tsx
// ✅ 图表组件懒加载 —— 图表库通常很大（ECharts ~1MB，Chart.js ~200KB）
// 用户不滚动到图表区域时永远不需要加载
import { lazy, Suspense, useState } from 'react';

const SalesChart = lazy(() => import(
  /* webpackChunkName: "chart-sales" */
  './charts/SalesChart'
));

function Dashboard() {
  const [showChart, setShowChart] = useState(false);

  return (
    <div>
      <h2>销售数据总览</h2>
      <p>本月销售额：¥128,000</p>

      {/* 用户点击"查看趋势图"时才加载图表组件 */}
      <button onClick={() => setShowChart(true)}>查看趋势图</button>

      {showChart && (
        <Suspense fallback={<div style={{ height: 400, background: '#f5f5f5', display: 'flex', alignItems: 'center', justifyContent: 'center' }}>图表加载中...</div>}>
          <SalesChart />
        </Suspense>
      )}
    </div>
  );
}

// ✅ 富文本编辑器懒加载 —— 几十万字的编辑器库只有编辑时才需要
const RichEditor = lazy(() => import(
  /* webpackChunkName: "editor" */
  './components/RichEditor'
));
```

#### 懒加载时机决策表

| 场景 | 策略 | 预加载建议 |
|------|------|-----------|
| 路由页面 | 必定懒加载 | 高频页面加 `prefetch` |
| 图表/可视化 | 滚动到可见区域时懒加载 | Intersection Observer 触发 |
| 富文本编辑器 | 点击"编辑"时懒加载 | 鼠标 hover 时 prefetch |
| 视频播放器 | 首帧可见时懒加载 | 不预加载（体积大、用户可能不播放） |
| 模态框/弹窗 | 首次打开时懒加载 | 按钮 hover 时 prefetch |
| 设置/管理页面 | 必定懒加载 | 不需要预加载（低频） |

### 三、Vendor Chunk 策略：缓存命中率最大化

缓存命中率是性能预算中最重要的长期指标之一。**一个合理的 vendor 分割策略可以让 80% 的页面访问命中缓存。**

#### 三级 Vendor 策略（推荐，适合大中型项目）

```javascript
// vite.config.ts —— 三级 vendor 分层
import { defineConfig } from 'vite';

export default defineConfig({
  build: {
    rollupOptions: {
      output: {
        manualChunks(id) {
          // 第一级：框架核心（更新频率：季度级）
          // 这些包极少更新，单独打包以最大化缓存命中率
          if (id.includes('node_modules/react') ||
              id.includes('node_modules/react-dom') ||
              id.includes('node_modules/react-router') ||
              id.includes('node_modules/react-router-dom')) {
            return 'vendor-framework';
          }

          // 第二级：UI 组件库（更新频率：月度级）
          // antd 的迭代比 React 频繁，但比业务代码少得多
          if (id.includes('node_modules/antd') ||
              id.includes('node_modules/@ant-design')) {
            return 'vendor-ui';
          }

          // 第三级：通用工具与数据层（更新频率：月度~季度级）
          if (id.includes('node_modules/axios') ||
              id.includes('node_modules/dayjs') ||
              id.includes('node_modules/lodash-es') ||
              id.includes('node_modules/@tanstack/react-query') ||
              id.includes('node_modules/zustand')) {
            return 'vendor-common';
          }

          // 注意：echarts、monaco-editor 等超大库不要放这里
          // 它们应该随懒加载的组件一起打包（只在用到时才加载）
        },
      },
    },
  },
});
```

**为什么不用一个大的 vendor chunk？**

```
假设你的 vendor.js = 800KB（React + AntD + ECharts + axios + ...）

某天你给 axios 升了一个小版本：
  vendor.js 的哈希变了 → 用户缓存失效 → 重新下载整个 800KB

三级分层后：
  vendor-framework.js  = 160KB（React，极少更新）→ 缓存命中率 95%+
  vendor-ui.js         = 400KB（AntD，偶尔更新）  → 缓存命中率 80%+
  vendor-common.js     = 80KB（工具库）             → 缓存命中率 70%+
  axios 升级 → 只有 vendor-common.js 缓存失效 → 只下载 80KB
```

#### Webpack 等价配置

```javascript
// webpack.config.js —— 三级 vendor 策略
module.exports = {
  optimization: {
    splitChunks: {
      cacheGroups: {
        framework: {
          test: /[\\/]node_modules[\\/](react|react-dom|react-router|react-router-dom)[\\/]/,
          name: 'vendor-framework',
          priority: 30,  // 最高优先级，确保不被其他规则捕获
          chunks: 'all',
        },
        ui: {
          test: /[\\/]node_modules[\\/](antd|@ant-design)[\\/]/,
          name: 'vendor-ui',
          priority: 20,
          chunks: 'all',
        },
        commonVendor: {
          test: /[\\/]node_modules[\\/](axios|dayjs|lodash-es|@tanstack|zustand)[\\/]/,
          name: 'vendor-common',
          priority: 10,
          chunks: 'all',
        },
      },
    },
  },
};
```

### 四、预加载策略：精确控制资源加载时机

这里有五种预加载指令，每种有不同的语义和优先级：

| 指令 | 时机 | 优先级 | 适用场景 |
|------|------|--------|---------|
| `preload` | 当前页面立即需要 | 高 | LCP 图片、关键 CSS、关键字体 |
| `prefetch` | 未来导航可能需要 | 低（空闲时） | 下一个页面的 JS bundle |
| `preconnect` | 建立早期连接（DNS+TCP+TLS） | — | 关键第三方域名 |
| `dns-prefetch` | 只做 DNS 解析 | — | 非关键第三方域名 |
| `modulepreload` | 类似 preload，但用于 ES Module | 高 | 现代构建工具产出的 ESM chunk |

```html
<head>
  <!-- 预连接到图片 CDN：省去 DNS + TCP + TLS 的 100-300ms -->
  <link rel="preconnect" href="https://images.cdn.example.com" />

  <!-- 只需要 DNS 解析：分析域名不需要提前建立连接 -->
  <link rel="dns-prefetch" href="https://analytics.example.com" />

  <!-- 预加载 LCP 图片：high priority，立即开始下载 -->
  <link rel="preload" as="image" href="/hero-banner.webp" fetchpriority="high" />

  <!-- 预取下一个页面的 JS：low priority，浏览器空闲时才下载 -->
  <link rel="prefetch" as="script" href="/assets/page-dashboard.js" />

  <!-- 字体预加载：crossorigin 必须加，否则浏览器会忽略 -->
  <link rel="preload" as="font" href="/fonts/custom.woff2"
        type="font/woff2" crossorigin="anonymous" />

  <!-- ESM 预加载：Vite/Rspack 产出 ESM 时使用 -->
  <link rel="modulepreload" href="/assets/vendor-framework.js" />
</head>
```

#### React Router 的预加载实践

```tsx
// 在链接 hover 时触发预加载，用户点击时 chunk 已经下载好了
import { Link } from 'react-router-dom';

function NavLink({ to, children, prefetchChunk }) {
  const handleMouseEnter = () => {
    // 在鼠标悬浮时预加载目标页面的 chunk
    // Webpack 的 /* webpackPrefetch: true */ 是编译时行为
    // 这里演示运行时动态 prefetch 的方式
    const link = document.createElement('link');
    link.rel = 'prefetch';
    link.as = 'script';
    link.href = prefetchChunk;
    document.head.appendChild(link);
  };

  return (
    <Link to={to} onMouseEnter={handleMouseEnter}>
      {children}
    </Link>
  );
}
```

#### Priority Hints：给浏览器更精确的优先级信号

```html
<!-- fetchpriority 让浏览器知道哪些资源比其他的更重要 -->
<!-- 值：high / low / auto（默认） -->

<!-- LCP 图片最高优先级加载 -->
<img src="/hero.webp" fetchpriority="high" />

<!-- 首屏不需要的大图降低优先级 -->
<img src="/footer-bg.jpg" fetchpriority="low" loading="lazy" />

<!-- 关键脚本最高优先级 -->
<script src="/app-critical.js" fetchpriority="high"></script>
```

**Priority Hints 的实际效果**：在没有 Priority Hints 时，浏览器对所有 `<img>` 一视同仁。如果你首屏有 10 张图，浏览器可能同时下载它们，导致 LCP 图片和 footer logo 竞争带宽。`fetchpriority="high"` 告诉浏览器"先把这个下载完再说别的"。

### 五、图片懒加载：两种方案对比

#### 原生 `loading="lazy"`

```html
<!-- ✅ 最简单的懒加载：一个字都不需要写 JS -->
<img src="/product-1.webp" loading="lazy" alt="" width="400" height="300" />

<!-- ⚠️ 注意：loading="lazy" 的加载阈值由浏览器决定（约视口下方 1250px 处开始加载） -->
<!-- 如果你需要更精确的控制（如只在元素进入视口时才加载），用 Intersection Observer -->

<!-- ❌ 不要对 LCP 图片用 loading="lazy"，反而会延迟加载 -->
<img src="/hero-banner.webp" fetchpriority="high" />
<!-- ↑ 不加 loading="lazy"：LCP 图片应该尽快加载 -->
```

#### Intersection Observer（精确控制）

```javascript
// ✅ 当图片距离视口 200px 时开始加载（比 loading="lazy" 更激进）
const imageObserver = new IntersectionObserver(
  (entries) => {
    entries.forEach(entry => {
      if (entry.isIntersecting) {
        const img = entry.target;
        // 把 data-src 的值赋给 src，触发浏览器加载图片
        img.src = img.dataset.src;

        // 图片加载完成后移除模糊占位效果
        img.onload = () => img.classList.add('loaded');

        // 已经加载的图片不需要再观察
        imageObserver.unobserve(img);
      }
    });
  },
  {
    rootMargin: '200px',  // 提前 200px 开始加载，用户滑到图片时已经加载好了
    threshold: 0,          // 元素只要露出 1px 就触发
  }
);

// 观察所有带 data-src 的图片
document.querySelectorAll('img[data-src]').forEach(img => {
  imageObserver.observe(img);
});
```

```css
/* 配合模糊占位效果，图片加载后平滑过渡 */
img[data-src] {
  filter: blur(10px);
  transform: scale(1.05);
  transition: filter 0.4s, transform 0.4s;
}
img[data-src].loaded {
  filter: blur(0);
  transform: scale(1);
}
```

**选择决策**：一般的图片用 `loading="lazy"`（零成本）；需要在图片靠近视口前就开始加载的用 Intersection Observer；需要模糊占位效果的用 Intersection Observer + data-src 模式。

### 六、虚拟列表（Virtual Scrolling）的实现原理

虚拟列表是解决"1 万条数据渲染到 DOM 会卡死"的标准方案。核心思想：**只渲染可视区域内的元素**。

```
┌─────────────────────────────────────┐
│  scrollTop = 0                      │ ← 容器顶部
├─────────────────────────────────────┤
│  元素 1-3（不可见，不渲染）          │
│  ...                                │
├─────────────────────────────────────┤
│  元素 4 ┐                           │ ← startIndex = 4
│  元素 5 │ 可视区域（实际渲染）        │    visibleCount = 3
│  元素 6 ┘                           │ ← endIndex = 6
├─────────────────────────────────────┤
│  元素 7-10000（不可见，不渲染）       │
│  ...                                │
├─────────────────────────────────────┤
│  scrollTop = max                    │ ← 容器底部
└─────────────────────────────────────┘

关键技巧：用一个高度撑开的"幽灵 div"来保持滚动条的正确比例
滚动条的总高度 = 每项高度 × 总项数（而不是实际 DOM 数）
```

```tsx
// VirtualList.tsx —— 虚拟列表的核心实现
import { useState, useRef, useCallback, useEffect } from 'react';

interface VirtualListProps<T> {
  items: T[];                          // 所有数据
  itemHeight: number;                  // 每项固定高度
  containerHeight: number;             // 可视容器高度
  renderItem: (item: T, index: number) => React.ReactNode;
  overscan?: number;                   // 预渲染数量（默认 3，避免快速滚动时白屏）
}

export function VirtualList<T>({
  items,
  itemHeight,
  containerHeight,
  renderItem,
  overscan = 3,
}: VirtualListProps<T>) {
  // 当前滚动位置
  const [scrollTop, setScrollTop] = useState(0);
  const containerRef = useRef<HTMLDivElement>(null);

  // 计算可见范围
  const startIndex = Math.max(0, Math.floor(scrollTop / itemHeight) - overscan);
  const visibleCount = Math.ceil(containerHeight / itemHeight) + overscan * 2;
  const endIndex = Math.min(items.length, startIndex + visibleCount);

  // 可见数据切片
  const visibleItems = items.slice(startIndex, endIndex);

  // 占位元素的总高度（保持滚动条真实比例）
  const totalHeight = items.length * itemHeight;

  // 可见区域的偏移量（用 translateY 把可见元素放到正确位置）
  const offsetY = startIndex * itemHeight;

  const handleScroll = useCallback((e: React.UIEvent<HTMLDivElement>) => {
    // 用 requestAnimationFrame 节流，避免 scroll 事件过于频繁触发重渲染
    requestAnimationFrame(() => {
      setScrollTop(e.currentTarget.scrollTop);
    });
  }, []);

  return (
    <div
      ref={containerRef}
      onScroll={handleScroll}
      style={{
        height: containerHeight,
        overflow: 'auto',
        position: 'relative',
        // 在 iOS 上使用 momentum 滚动效果
        WebkitOverflowScrolling: 'touch',
      }}
      role="list"
    >
      {/* 幽灵占位元素：撑开滚动条 */}
      <div style={{ height: totalHeight, pointerEvents: 'none' }} />

      {/* 实际渲染的元素区域：绝对定位 + translateY 偏移 */}
      <div
        style={{
          position: 'absolute',
          top: 0,
          left: 0,
          right: 0,
          transform: `translateY(${offsetY}px)`,
        }}
      >
        {visibleItems.map((item, i) => (
          <div
            key={startIndex + i}
            style={{ height: itemHeight }}
            role="listitem"
          >
            {renderItem(item, startIndex + i)}
          </div>
        ))}
      </div>
    </div>
  );
}
```

**虚拟列表的性能边界**：
- 固定高度项：O(1) 查找 → 性能天花板很高（百万条数据也无压力）
- 动态高度项：需要先测量再计算，复杂度 O(log N)，推荐用 `react-window` 的 `VariableSizeList`
- 不推荐自己实现动态高度虚拟列表，`react-window` 或 `@tanstack/virtual` 已经做得很好

### 七、实战：分析一个项目的 Bundle

#### 第一步：生成分析报告


```typescript
    }),
```

#### 第二步：解读分析报告（以典型项目为例）

```
量级最大的 Top 5 chunk（gzip 后）：

1. vendor-ui.js         380 KB   ← Ant Design（按需导入可瘦身到 200KB）
2. vendor-framework.js  160 KB   ← React / ReactDOM（正常）
3. page-dashboard.js    240 KB   ← 仪表盘页面（包含 ECharts，应拆分）
4. vendor-common.js     120 KB   ← lodash-es + moment + axios（moment 可换成 dayjs）
5. main.js              95 KB    ← 入口 bundle（正常）

发现问题：
- ECharts（~180KB gzip）被打包到了 page-dashboard.js 中
  → 应将其懒加载，只有用户打开仪表盘时才下载
- lodash-es 全局被 import，很多函数没用到
  → 检查是否做了 Tree Shaking，或者改为按需导入
- moment.js 占约 60KB
  → 换成 dayjs（~7KB）或 date-fns（tree-shakable）
- Ant Design 的 icons 全量导入了 icon set（~150KB）
  → 改为按需导入 @ant-design/icons 的单个图标
```

#### 第三步：实施优化

```typescript
// 优化 1：ECharts 懒加载
// ❌ 之前：顶部 import，打包到页面 chunk 中
// import * as echarts from 'echarts';  // 即使这个页面可能不显示图表

// ✅ 优化后：动态导入，只有真正需要时才加载

  const echarts = await import('echarts');
```

## 常见问题

**Q1：`React.lazy` 只能用默认导出吗？**

A：是的，`React.lazy` 要求被加载的模块必须有 `default` 导出 React 组件。如果你的模块是命名导出，需要包装一层：

```tsx
// ❌ 直接对命名导出用 lazy 会报错
// const Page = lazy(() => import('./Page')); // Page 使用 export const Page

// ✅ 包装一层转为默认导出
const Page = lazy(() => import('./Page').then(mod => ({ default: mod.Page })));
```

**Q2：SSR 能用 `React.lazy` 吗？**

A：不能直接在服务端用 `React.lazy`。Next.js 中路由天然支持代码分割（`page.tsx` 自动分割），不需要 `React.lazy`。但对于非路由级组件，Next.js 推荐用 `next/dynamic`，它支持 SSR + 懒加载：

```tsx
import dynamic from 'next/dynamic';
const Chart = dynamic(() => import('./Chart'), {
  ssr: false,  // 图表组件不需要 SSR
  loading: () => <div>图表加载中...</div>,
});
```

**Q3：`preload` 和 `prefetch` 到底怎么选？**

A：`preload` = "这个资源本页马上用到，现在就下载，高优先级"。`prefetch` = "这个资源下个页面可能用到，浏览器你闲着的时候下载，低优先级"。简单记忆：preload = 立即需要，prefetch = 稍后可能需要。错误的用法是把 `preload` 当 `prefetch` 用——同时 preload 十几个资源，高优先级的互相抢带宽，反而拖慢真正的关键资源。

**Q4：虚拟列表的 `overscan` 设多少合适？**

A：`overscan = 2~5` 是常见范围。太小则快速滚动时会出现白屏；太大则 DOM 节点增多，抵消了虚拟列表的性能优势。经验值：桌面端 `overscan=5`，移动端 `overscan=3`（移动端 GPU 渲染能力更弱，减少 DOM 更重要）。

**Q5：`splitChunks` 的最小体积（`minSize`）应该设多少？**

A：默认 20000（20KB）。太小会产生大量小 chunk（增加 HTTP 请求数，抵消分割收益）；太大则分割不彻底。对于 HTTP/2 的项目，可以设到 10KB（多路复用消除了请求数瓶颈）。对于 HTTP/1.1 的项目，建议至少 30KB。一句话：HTTP/2 允许更激进的分割策略。

**Q6：为什么我的 bundle 分析报告里，某个库的体积比 npm 页面显示的大很多？**

A：npm 页面通常显示的是源代码大小（不含依赖），而你实际打包进 bundle 的是该库及其依赖的 tree-shaken 后的体积。此外，构建工具可能会注入 polyfill、运行时帮助代码等。用 `gzipSize: true` 对比压缩后的大小才公平。

**Q7：图片懒加载和虚拟列表能一起用吗？**

A：可以而且应该。图片懒加载控制"何时下载图片字节"，虚拟列表控制"何时创建 DOM 节点"。两者正交：虚拟列表保证可视区外没有 DOM 节点（当然也不会有 `<img>` 请求），图片懒加载保证可视区内的图片也不一定要立即下载（滚动到足够近才下载）。组合使用是列表密集型页面的最佳实践。

**Q8：`loading="lazy"` 对所有图片都适用吗？**

A：不。对于视口内的图片（尤其是 LCP 元素），`loading="lazy"` 反而会让浏览器延迟加载，增加 LCP。策略：首屏图片不加 `loading="lazy"`，首屏以下的所有图片都加。这也意味着你需要清楚地知道哪些图片在首屏——另一个需要性能预算和架构意识的例子。

## 本节小结

代码分割和懒加载不是"配置一下 splitChunks 就好了"的一次性操作。架构层面需要持续关注三个问题：

1. **你的 chunk 结构是否让缓存命中率最大化？** —— 稳定的库单独打包，易变的代码按路由分割
2. **你的首屏 bundle 里是否有首屏不需要的代码？** —— 凡是用户不滚动、不点击就看不到的组件，都应该懒加载
3. **你的预加载策略是否与用户行为模式匹配？** —— 在用户操作之前就把下一段旅程需要的资源准备好

好的代码分割策略 = 首屏轻量 + 缓存收益高 + 导航零等待。这不是一次性配置，而是在每次 PR 中都应审视的持续关注点。
