### 一、渲染流水线回顾与深化

L0 阶段你学过重排、重绘、合成的基本概念。这里我们从**性能代价的角度**重新审视每个阶段：

```
                        触发条件              性能代价
                          
  JavaScript 执行  ←  状态变更 / 事件处理      取决于代码量

        ↓

  Style 计算       ←  修改了样式属性           中（需重新计算选择器匹配和继承）

        ↓

  Layout（布局）    ←  修改了几何属性            高 ⚠️（树状计算，可能波及大量节点）
        |              width / height / top / left
        |              padding / margin / border
        |              display / position
        |              读取 offsetWidth 等（强制同步布局）

        ↓

  Paint（绘制）     ←  修改了视觉属性            中（向量转位图，复杂样式更慢）
        |              color / background / box-shadow
        |              border-color / outline

        ↓

  Composite（合成） ←  修改了图层属性            低 ✅（GPU 完成，主线程不参与）
                       transform / opacity
```

**核心认知**：你的目标不是消灭 Layout 和 Paint（它们有时不可避免），而是：

1. 把 Layout 和 Paint 的工作量降到最低（减小影响范围）
2. 在动画场景中完全避开 Layout 和 Paint（只走 Composite）
3. 把不可避免的计算分散到多帧中（拆分长任务）

### 二、仅触发 Composite 的属性

以下两个 CSS 属性在元素有独立图层时，修改它们**只触发 Composite**，是最廉价的视觉更新：

| 属性 | 效果 | GPU 操作 |
|------|------|---------|
| `transform` | 位移、缩放、旋转、倾斜 | 矩阵变换 |
| `opacity` | 透明度 | Alpha 混合 |

```css
/* ✅ 最佳：动画只触发 Composite */
.slide-in {
  /* transform: translateX() 代替 left 做水平移动 */
  transform: translateX(-100%);
  transition: transform 0.3s ease-out;
}
.slide-in.visible {
  transform: translateX(0);
}

/* ❌ 避免：用 left 做动画 → 触发 Layout → Paint → Composite */
.slide-in-bad {
  position: relative;
  left: -100%;
  transition: left 0.3s ease-out;
}

/* ✅ opacity 做淡入淡出（Composite only） */
.fade-in {
  opacity: 0;
  transition: opacity 0.3s;
}
.fade-in.visible {
  opacity: 1;
}

/* ✅ 组合使用 transform + opacity */
.scale-on-hover:hover {
  transform: scale(1.05);
  opacity: 0.9;
  transition: transform 0.2s, opacity 0.2s;
}
```

**如何判断一个 CSS 属性触发哪些渲染阶段？**

打开 DevTools Performance 面板，录制操作过程，查看火焰图：
- 出现 **Layout**（紫色块）= 触发了 Layout
- 只有 **Paint**（绿色块）没有 Layout = 只触发了 Paint
- 既没有 Layout 也没有 Paint = 只触发了 Composite

也可以在 [csstriggers.com](https://csstriggers.com) 上查阅每个 CSS 属性触发的渲染阶段。

### 三、`will-change`：正确用法和常见误用

`will-change` 告诉浏览器"这个元素即将会变"，浏览器会提前为它创建独立图层。

```css
/* ✅ 正确用法：仅在动画即将开始前设置，动画结束后移除 */
.animate-once {
  will-change: transform, opacity;
}
```

```javascript
// ✅ 更好的方式：用 JS 在动画前后动态设置和移除 will-change
const element = document.querySelector('.animated-card');

// 动画开始前：提前创建图层
element.addEventListener('mouseenter', () => {
  element.style.willChange = 'transform';
});

// 动画结束后：释放图层资源
element.addEventListener('animationend', () => {
  element.style.willChange = 'auto';
});

// 或者：动画结束后延迟移除（给 transition 留出时间）
element.addEventListener('transitionend', () => {
  requestAnimationFrame(() => {
    element.style.willChange = 'auto';
  });
});
```

**`will-change` 的三大误用**：

```css
/* ❌ 误用 1：给所有元素都加 will-change */
* {
  will-change: transform, opacity;
}
/* 后果：页面中每个元素都被提升为独立图层，GPU 显存瞬间爆满，
   移动端会出现严重掉帧甚至白屏 */

/* ❌ 误用 2：给永远不会动画的元素加 will-change */
.static-text {
  will-change: transform;
}
/* 后果：白占 GPU 内存，没有任何收益。will-change 是"预支"，不是"魔法" */

/* ❌ 误用 3：will-change 常驻不释放 */
.sidebar {
  will-change: transform;
}
/* 这个 sidebar 每次展开只动画 300ms，但 will-change 一直占据图层，
   即使 sidebar 关闭后也不释放 */
```

**规则总结**：`will-change` 就像预支未来的钱——只在需要时预支，用完立刻还，不要为所有未来可能发生的事预支。对于一个页面上同时存在的独立图层，合理上限是 30-50 个。

### 四、`requestAnimationFrame`：正确使用模式

```javascript
// ✅ 模式 1：用 rAF 节流高频事件（scroll、resize、mousemove）
// 问题：scroll 事件可能每帧触发多次（60Hz 下最高 60 次/秒）
//      但渲染只需要每帧一次，多余的调用是浪费
let ticking = false;

window.addEventListener('scroll', () => {
  if (!ticking) {
    requestAnimationFrame(() => {
      // 所有视觉更新集中在这里，每帧只执行一次
      updateParallax();
      updateStickyHeader();
      ticking = false;
    });
    ticking = true;
  }
});

// ✅ 模式 2：动画循环（标准写法）
function animate(timestamp) {
  // timestamp 是 DOMHighResTimeStamp，精确到微秒
  // 用它计算 delta time，而不是依赖固定的 16ms
  const delta = timestamp - lastTimestamp;
  lastTimestamp = timestamp;

  // 基于 delta 做更新，保证动画在不同帧率设备上都流畅
  element.style.transform = `translateX(${position}px)`;
  position += speed * (delta / 16.67); // 归一化到 60fps 的速度

  requestAnimationFrame(animate);
}

let lastTimestamp = performance.now();
requestAnimationFrame(animate);

// ✅ 模式 3：在 rAF 中批量读取和批量写入
// 避免在循环中读写混用导致的强制同步布局
requestAnimationFrame(() => {
  // 第一阶段：批量读取（触发一次 Layout）
  const heights = elements.map(el => el.getBoundingClientRect().height);

  // 第二阶段：批量写入（浏览器在帧末尾统一 Layout）
  elements.forEach((el, i) => {
    el.style.height = `${heights[i] * 2}px`;
  });
});
```

### 五、CSS 动画 vs JS 动画：深度对比

#### 执行位置差异

```
CSS 动画（transform/opacity）：
  合成器线程 → GPU → 屏幕
  （主线程完全空闲！即使主线程被 JS 阻塞，动画依然流畅）

JS 动画（requestAnimationFrame）：
  主线程 → 计算 → 提交到合成器 → GPU → 屏幕
  （主线程忙时动画会卡顿）
```

**这解释了为什么 CSS 动画在低端设备和主线程繁忙时更流畅。** 你可以做一个实验：在页面上运行一个 5 秒的长任务（如大量计算），同时播放一段动画。CSS 动画继续丝滑运行，JS 动画完全卡住——这就是合成器线程独立于主线程的威力。

#### 何时必须用 JS 动画

| 场景 | 推荐 | 原因 |
|------|------|------|
| 简单过渡（hover、展开/收起） | CSS Transition | 声明式、零 JS 开销 |
| 复杂关键帧动画 | CSS Animation (`@keyframes`) | 维护成本低、性能好 |
| 基于物理的动画（弹簧、阻尼） | JS + rAF | 只有 JS 能动态计算 |
| 基于滚动的动画（视差、进度条） | JS + rAF | 需要访问 scroll 值 |
| 响应交互的动画（拖拽、手势） | JS + rAF | 需要实时的交互坐标 |
| SVG 路径动画 | JS（如 GSAP/Anime.js） | CSS 的 SVG 支持有限 |

**实际情况是两者混合使用**：基础过渡用 CSS，复杂交互动画用 JS（GSAP / Framer Motion / Motion One 等库对性能有深度优化）。

### 六、FLIP 动画技术

FLIP 是解决"从旧位置到新位置的过渡动画"的标准方案。传统方式需要知道起始和结束坐标，不仅逻辑复杂，而且容易触发 Layout。FLIP 的思路是反过来：

```
F - First：  记录元素的起始位置
L - Last：   修改 DOM（插入、删除、移动），记录元素的新位置
I - Invert： 计算位置差，用 transform 把元素"移回"旧位置
P - Play：   去掉 transform，让元素自然过渡到新位置
```

```javascript
// FLIP 动画的核心实现
function flipAnimate(container, elements, mutateDOM) {
  // F - First：记录起始位置
  const firstRects = elements.map(el => el.getBoundingClientRect());

  // L - Last：执行 DOM 变更，记录新位置
  mutateDOM();
  const lastRects = elements.map(el => el.getBoundingClientRect());

  // I - Invert：计算差值，用 transform 把元素移回原位置
  elements.forEach((el, i) => {
    const deltaX = firstRects[i].left - lastRects[i].left;
    const deltaY = firstRects[i].top - lastRects[i].top;

    if (deltaX !== 0 || deltaY !== 0) {
      // 关键：用 transform 做位移，不触发 Layout！
      el.style.transform = `translate(${deltaX}px, ${deltaY}px)`;
      el.style.transition = 'none'; // 先禁用 transition，让 transform 立刻生效

      // P - Play：在下一帧去掉 transform，触发过渡动画
      requestAnimationFrame(() => {
        el.style.transition = 'transform 0.3s ease-out';
        el.style.transform = 'translate(0, 0)';
      });
    }
  });
}

// ============================================
// 使用示例：列表重排序
// ============================================
const list = document.querySelector('.sortable-list');

document.getElementById('shuffle-btn').addEventListener('click', () => {
  const items = [...list.children];

  flipAnimate(list, items, () => {
    // 打乱顺序
    const shuffled = items.sort(() => Math.random() - 0.5);
    shuffled.forEach(item => list.appendChild(item));
  });
});
```

**FLIP 的精髓**：它把"元素从 A 移到 B"变成了"元素已经在 B，但我用 transform 把它伪装成在 A，然后去掉伪装让它自然滑到 B"。全程只用 transform（Composite only），零 Layout 开销。

**生产推荐**：FLIP 的实现细节已经封装得很好，直接使用 GreenSock 的 Flip 插件或 Framer Motion 的 `layout` prop（AnimateSharedLayout）即可。但理解 FLIP 的原理能帮你判断什么场景适合用它。

### 七、长列表渲染优化策略对比

长列表有三大优化策略，按"改动成本 → 效果"排序：

```
策略 1：分页加载
  改造成本：低 | 效果：解决首屏渲染压力，但翻页时仍有大量 DOM 操作
  适用：数据量中（< 500 条）、业务要求精确分页（如搜索结果）

策略 2：虚拟列表
  改造成本：中 | 效果：DOM 节点数恒定（= 可见数 + overscan），与数据总量无关
  适用：数据量大（> 500 条）、需要滚动浏览（如消息列表、Feed 流）

策略 3：DOM 回收（Recycling）
  改造成本：高 | 效果：DOM 节点复用，零创建/销毁开销
  适用：超大数据量（> 10000 条）、极致性能要求（如金融行情）
```

#### 虚拟列表（最常见的生产方案）

上一节已经给出了完整实现，这里补充一个重要的架构视角：

**虚拟列表不是全能的。** 以下场景虚拟列表会失效或体验变差：

1. **列表项高度不固定** — 需要动态测量，增加计算量，且需要额外的缓存层来记录已测高度
2. **列表项内有富文本/嵌入式内容**（如微博的展开全文、直播卡片）— 内容展开后高度变化，需要重新测量
3. **列表项需要键盘导航和焦点管理**（如文件管理器）— 未渲染的元素无法接收焦点，需要额外处理
4. **列表项需要打印** — 可视区外元素不存在，打印结果只有当前视口的内容

**生产推荐**：用 `react-window`（固定高度）或 `@tanstack/virtual`（动态高度）。它们处理了所有边界情况，不要自己从零实现。

### 八、防抖与节流：性能优化的瑞士军刀

```javascript
// ============================================
// 防抖（Debounce）：连续触发只执行最后一次
// 适用：搜索框输入、窗口 resize、表单校验
// ============================================
function debounce(fn, delay = 300) {
  let timer = null;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

// 使用：用户停止输入 300ms 后才发送搜索请求
searchInput.addEventListener('input', debounce((e) => {
  fetchSearchResults(e.target.value);
}, 300));

// ============================================
// 节流（Throttle）：固定频率执行
// 适用：滚动事件、mousemove、动画帧
// ============================================
function throttle(fn, limit = 100) {
  let inThrottle = false;
  return function (...args) {
    if (!inThrottle) {
      fn.apply(this, args);
      inThrottle = true;
      setTimeout(() => { inThrottle = false; }, limit);
    }
  };
}

// 使用：每 100ms 最多更新一次滚动进度
window.addEventListener('scroll', throttle(() => {
  updateScrollProgress();
}, 100));
```

**防抖和节流的本质区别：**

```
用户持续输入 "hello"
  防抖：h → e → l → l → o → (等 300ms)
        每次新输入都重置计时器，最终只执行一次
        适合"等用户完成操作后再响应"
        
  节流：h ↓ e ↓ l ↓ l ↓ o ↓ o ↓ o
        →执   →不执  →执   →不执   →执
        每 100ms 最多执行一次
        适合"限制执行频率，但过程中也需要响应"
```

### 九、React 中的渲染性能优化

#### React.memo：阻止不必要的重渲染

```tsx
// ❌ 父组件每次 state 变化，ExpensiveList 都会重渲染
function Parent() {
  const [count, setCount] = useState(0);
  const items = useMemo(() => generateItems(1000), []); // 稳定的大数据

  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>计数: {count}</button>
      <ExpensiveList items={items} /> {/* 即使 items 不变也会重渲染 */}
    </div>
  );
}

// ✅ React.memo：props 没变就不重渲染
const ExpensiveList = React.memo(function ExpensiveList({ items }: { items: Item[] }) {
  console.log('ExpensiveList 渲染'); // 只在 items 变化时打印
  return (
    <ul>
      {items.map(item => (
        <li key={item.id}>{item.name}</li>
      ))}
    </ul>
  );
});
```

**`React.memo` 的适用判断**：
- 组件渲染成本高（大数据列表、复杂计算、图表组件）→ 值得加
- 组件 props 很少变化（纯展示组件）→ 值得加
- 组件 props 每次都变（如包含 `children` 或内联对象）→ 加了也没用
- 组件渲染成本很低（简单的文本/图标）→ 不值得加（memo 本身的比较也有开销）

#### useMemo / useCallback：稳定引用 vs 缓存计算

```tsx
function SearchResults({ query }: { query: string }) {
  // ✅ useMemo：缓存计算结果
  // 只有 query 变化时才重新过滤，避免每次渲染都遍历整个列表
  const filtered = useMemo(() => {
    return allProducts.filter(p =>
      p.name.toLowerCase().includes(query.toLowerCase())
    );
  }, [query]);

  // ✅ useCallback：稳定函数引用
  // 没有 useCallback 的话，每次渲染都会创建新函数
  // → 传给 React.memo 的子组件时，子组件会认为 props 变了 → 重渲染
  const handleSelect = useCallback((id: string) => {
    setSelectedId(id);
    trackEvent('product_select', { id });
  }, []); // 依赖为空：这个函数不依赖任何会变的值

  return <ProductList items={filtered} onSelect={handleSelect} />;
}

// 如果 ProductList 用了 React.memo，handleSelect 的引用稳定性
// 决定了 ProductList 是否重渲染
const ProductList = React.memo(function ProductList({
  items, onSelect
}: {
  items: Product[];
  onSelect: (id: string) => void;
}) {
  // ...
});
```

**useMemo / useCallback 的两个不要**：
1. 不要为了"优化"而无脑包裹所有值和函数 —— 它们本身也有内存和比较开销，只对真正需要的场景用
2. 不要用 useMemo 来避免子组件重渲染 —— 那应该用 React.memo。useMemo 的职责是缓存计算结果

#### useTransition：把非紧急更新标记为低优先级

```tsx
function ProductSearch() {
  const [query, setQuery] = useState('');
  const [isPending, startTransition] = useTransition();

  function handleInput(e: React.ChangeEvent<HTMLInputElement>) {
    // 紧急更新：输入框的值必须立刻响应
    setQuery(e.target.value);

    // 非紧急更新：搜索结果可以延迟显示
    // 用户输入时不会因为搜索过滤计算而感觉卡顿
    startTransition(() => {
      setFilteredProducts(
        allProducts.filter(p =>
          p.name.toLowerCase().includes(e.target.value.toLowerCase())
        )
      );
    });
  }

  return (
    <div>
      <input
        value={query}
        onChange={handleInput}
        placeholder="搜索产品..."
      />
      {isPending && <small>搜索结果更新中...</small>}
      <ProductList products={filteredProducts} />
    </div>
  );
}
```

**`useTransition` 的适用场景**：
- 搜索过滤（输入框 + 大列表）— 经典场景
- Tab 切换（切换后渲染复杂内容）— 保持 Tab 点击的即时响应
- 路由导航（页面跳转时渲染目标页）— 保持导航的即时反馈

### 十、实战：优化一个存在性能问题的复杂互动页面

以典型的"数据可视化仪表盘"为例：

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8">
  <title>实时仪表盘 — 性能优化实战</title>
  <style>
    .dashboard {
      display: grid;
      grid-template-columns: repeat(auto-fit, minmax(300px, 1fr));
      gap: 16px;
      padding: 24px;
      max-width: 1400px;
      margin: 0 auto;
    }
    .card {
      background: #fff;
      border-radius: 12px;
      padding: 20px;
      box-shadow: 0 2px 8px rgba(0,0,0,0.08);
      /* ✅ 动画属性使用 transform/opacity，只触发 Composite */
      transition: transform 0.2s, box-shadow 0.2s;
      will-change: transform; /* 卡片 hover 需要缩放，提前创建图层 */
    }
    .card:hover {
      transform: translateY(-4px);
      box-shadow: 0 8px 24px rgba(0,0,0,0.12);
    }
    .chart-container {
      position: relative;
      /* ✅ 图表容器固定高度，避免加载前后 CLS */
      min-height: 300px;
      background: #fafafa;
      border-radius: 8px;
      display: flex;
      align-items: center;
      justify-content: center;
      color: #999;
      font-size: 14px;
    }
    .chart-container canvas {
      max-width: 100%;
    }
    /* ✅ 数据更新的闪烁动画：只用 opacity（Composite only） */
    .data-updating {
      animation: pulse 0.6s ease-in-out;
    }
    @keyframes pulse {
      0%, 100% { opacity: 1; }
      50% { opacity: 0.5; }
    }
    .scroll-container {
      /* ✅ 滚动容器加 will-change: transform 提升为独立图层 */
      will-change: transform;
    }
  </style>
</head>
<body>
  <div class="dashboard" id="dashboard"></div>

  <script type="module">
    // ============================================
    // 渲染优化 1：批量更新 DOM
    // 问题：每 100ms 收到一批数据，如果直接逐个更新 DOM，会触发大量 Layout
    // 解决：收集一批数据后，在 rAF 中统一更新
    // ============================================
    const dashboard = document.getElementById('dashboard');
    const cardCache = new Map();
    let pendingUpdates = [];

    // 初始化骨架卡片（避免后续动态插入导致 CLS）
    const cardConfigs = [
      { id: 'cpu', title: 'CPU 使用率' },
      { id: 'memory', title: '内存占用' },
      { id: 'network', title: '网络流量' },
      { id: 'disk', title: '磁盘 IO' },
    ];

    cardConfigs.forEach(({ id, title }) => {
      const card = document.createElement('div');
      card.className = 'card';
      card.id = `card-${id}`;
      card.innerHTML = `
        <h3 style="margin:0 0 12px; font-size:16px">${title}</h3>
        <div class="chart-container" id="chart-${id}">加载中...</div>
        <div style="margin-top:12px; font-size:24px; font-weight:700" id="value-${id}">--</div>
      `;
      dashboard.appendChild(card);
      cardCache.set(id, card);
    });

    // ============================================
    // 渲染优化 2：用 rAF 批量更新，避免 Layout 抖动
    // ============================================
    function scheduleUpdate(update) {
      pendingUpdates.push(update);
      if (pendingUpdates.length === 1) {
        // 第一个更新进入时，调度一个 rAF 批次
        requestAnimationFrame(flushUpdates);
      }
    }

    function flushUpdates() {
      const updates = pendingUpdates;
      pendingUpdates = [];

      // 第一阶段：批量读取（触发一次 Layout）
      const rects = updates.map(u => ({
        el: cardCache.get(u.id),
        rect: cardCache.get(u.id).getBoundingClientRect(),
      }));

      // 第二阶段：批量写入（浏览器在帧末尾统一 Layout）
      const fragment = document.createDocumentFragment();
      updates.forEach(({ id, value, unit }) => {
        const valueEl = document.getElementById(`value-${id}`);
        if (valueEl && valueEl.textContent !== `${value}${unit}`) {
          valueEl.textContent = `${value}${unit}`;
          // 添加短暂的闪烁动画表示数据更新
          valueEl.classList.add('data-updating');
          valueEl.addEventListener('animationend', () => {
            valueEl.classList.remove('data-updating');
          }, { once: true });
        }
      });
    }

    // ============================================
    // 渲染优化 3：模拟实时数据推送 + 节流
    // 问题：如果数据更新频率高于屏幕刷新率，会产生无效渲染
    // 解决：用 rAF 天然限制为一帧最多一次更新
    // ============================================
    function startDataStream() {
      setInterval(() => {
        cardConfigs.forEach(({ id }) => {
          const value = (Math.random() * 100).toFixed(1);
          scheduleUpdate({
            id,
            value: parseFloat(value),
            unit: '%',
            timestamp: performance.now(),
          });
        });
      }, 200); // 每 200ms 推送一批，但实际渲染帧率由 rAF 控制
    }

    // ============================================
    // 渲染优化 4：滚动性能优化
    // ============================================
    window.addEventListener('scroll', () => {
      // 只在 rAF 中更新视觉属性，不在 scroll 回调中直接操作 DOM
      requestAnimationFrame(updateScrollBasedUI);
    }, { passive: true }); // passive: true 告诉浏览器不会调用 preventDefault()

    function updateScrollBasedUI() {
      // 根据滚动位置更新某些 UI（如返回顶部按钮的显示/隐藏）
      // 只修改 transform/opacity，不触发 Layout
      const backToTop = document.getElementById('back-to-top');
      if (backToTop) {
        const shouldShow = window.scrollY > 500;
        backToTop.style.opacity = shouldShow ? '1' : '0';
        backToTop.style.transform = shouldShow ? 'translateY(0)' : 'translateY(20px)';
      }
    }

    // 启动数据流
    startDataStream();
  </script>

  <button id="back-to-top"
    style="position:fixed;bottom:24px;right:24px;width:48px;height:48px;
           border-radius:50%;background:#2563eb;color:#fff;border:none;
           cursor:pointer;opacity:0;transform:translateY(20px);
           transition:opacity 0.3s,transform 0.3s;
           will-change:transform,opacity;z-index:100;"
    onclick="window.scrollTo({top:0,behavior:'smooth'})">
    ↑
  </button>
</body>
</html>
```

**本实战涵盖的优化手段汇总：**

| 序号 | 优化手段 | 解决的问题 | 所属阶段 |
|------|---------|-----------|---------|
| 1 | CSS `transition` 只用 `transform/opacity` | 动画触发 Layout | Composite |
| 2 | `will-change: transform` | 动画前创建图层，避免首次动时卡顿 | Composite |
| 3 | rAF 批量读写分离 | 强制同步布局 | Layout |
| 4 | `passive: true` + rAF 处理 scroll | 滚动卡顿 | Event → Layout |
| 5 | `animationend` 清理动画 class | 避免累积大量动画绑定 | JS |
| 6 | CSS `@keyframes` 做闪烁动画（只用 opacity） | 低代价的视觉反馈 | Composite |

## 常见问题

**Q1：`will-change` 设置后多久生效？**

A：立即生效——浏览器在下次渲染帧时会为该元素创建独立图层。但创建图层本身有开销（分配 GPU 内存、上传纹理），所以最佳实践是在动画开始前至少一帧设置 `will-change`（通常用 `mouseenter` 或组件 `onFocus` 事件），而不是在动画正在发生的帧设置。

**Q2：怎么看一个元素有没有独立图层？**

A：DevTools → 更多工具（三个点） → Layers（图层）面板。或者：Rendering 标签（需要在 DevTools 设置中开启） → 勾选"Layer borders"，页面上橙色边框的元素就是独立图层。如果满屏都是橙色，说明图层过多，说明有代码滥用了 `will-change`。

**Q3：`React.memo` 和 `useMemo` 都会增加内存，什么时候不值得用？**

A：简单来说：如果组件渲染只需要 < 1ms，加了 `React.memo` 后每次 props 比较需要 0.05ms，而 props 有一半的概率会变（比较 0.05ms + 渲染 1ms = 1.05ms vs 不加时直接渲染 1ms），那 memo 反而增加了开销。经验法则：组件渲染时间 > 2ms 或包含 useEffect 副作用（这些重复执行代价大）才值得加 memo。

**Q4：FLIP 动画用 transform，但 transform 只能做矩阵变换，如果动画需要改变颜色怎么办？**

A：FLIP 的核心价值是处理**位置变化**的动画（列表重排序、布局切换）。颜色过渡可以直接用 CSS Transition（`transition: color 0.3s`）。两者互不冲突：FLIP 用 transform 处理位移，CSS Transition 处理颜色或其他属性。

**Q5：虚拟列表 + `position: sticky` 能一起用吗？**

A：可以，但需要小心。`position: sticky` 依赖父容器的 overflow 设置。如果虚拟列表的容器是 `overflow: auto`，则 sticky 元素应该放在容器内部（而不是虚拟列表的滚动容器内）。常见的做法是 sticky 的表头放在虚拟列表外部，虚拟列表自身滚动。

**Q6：为什么我的 `requestAnimationFrame` 在移动端不流畅？**

A：检查三个点：(1) 低电量模式下，iOS 会降低 rAF 频率到 30fps；(2) 移动端 GPU 更弱，如果图层过多或 transform 导致大量像素重绘，帧率会下降；(3) `touchmove` 事件处理中如果调用了 `event.preventDefault()` 且没有加 `passive: true`，浏览器会等待 JS 执行完毕才滚动，造成延迟。

**Q7：`debounce` 和 `throttle` 的延迟设多少合适？**

A：没有通用值，取决于场景：(1) 搜索建议：debounce 300-500ms（等用户停止输入）；(2) 窗口 resize：debounce 200ms；**(3) scroll 事件：不要用 debounce/throttle，用 rAF**——因为 scroll 频率与渲染帧率一致，rAF 天然对齐帧率，是最优解；(4) 按钮防重复提交：throttle 1000ms。

**Q8：Framer Motion 和纯 CSS 动画在性能上有多大差距？**

A：Framer Motion 的动画核心也是使用 `transform` 和 `opacity`，底层通过 rAF 驱动。对于简单动画，纯 CSS 性能更好（合成器线程独立运作）；对于复杂编排（序列、交错、手势响应），Framer Motion 的 JS 驱动提供了 CSS 无法实现的灵活性。实际差距通常在 1-3ms 的 JS 开销范围内，对于 60fps（16.7ms 预算），通常可以接受。

## 本节小结

渲染性能和动画优化的核心是**理解浏览器的渲染流水线，然后把动画的负担从主线程转移到合成器线程**。

三大原则：

1. **位移、缩放和淡入淡出优先考虑 `transform` 与 `opacity`**：它们通常能避开布局，元素具备合适图层时还可避开重绘；但图层创建、纹理上传和合成本身仍有成本，是否真正走合成路径要用 DevTools 验证。

2. **批量读写，减少 Layout 抖动**：对高频或批量更新，用 rAF 做帧级调度，并尽量先读取尺寸、再集中写入样式，避免在循环中反复触发同步布局。

3. **按证据提升图层**：`will-change` 是工具而非银弹。只在性能分析表明图层提升有收益时，于动画前设置并在结束后移除。图层没有通用数量上限，应结合目标设备的内存和 Performance/Layers 数据判断。

这些优化不是炫技，而是直接影响真实用户的体验。在 60Hz 屏幕上，每帧总预算约为 16.7 毫秒，页面脚本只能使用其中一部分；更高刷新率的预算更短。最终以目标设备上的帧时间、长任务和 INP 数据为准。
