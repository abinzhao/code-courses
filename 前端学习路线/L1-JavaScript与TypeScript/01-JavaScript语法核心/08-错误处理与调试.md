## 学习目标

- 能区分编程错误、运行环境错误、外部输入错误和业务拒绝
- 能正确使用 throw、try/catch/finally 和 Error.cause
- 能处理同步异常、Promise rejection 和事件回调错误
- 能设计面向用户与面向开发者的不同错误信息
- 能使用断点、调用栈、条件断点和网络证据定位根因
- 能写出可复现、可回归的缺陷记录

## 内容讲解

### 一、先分类，再决定处理方式

| 类型 | 示例 | 处理原则 |
|---|---|---|
| 编程错误 | 访问不存在的属性 | 尽早失败，修复代码 |
| 外部输入错误 | 表单字段非法 | 返回字段级反馈 |
| 依赖错误 | API 超时、存储配额满 | 重试、降级或明确失败 |
| 业务拒绝 | 无权限、库存不足 | 呈现可操作结果 |
| 用户取消 | 取消搜索、关闭弹窗 | 通常不显示为系统故障 |

不要用同一个 `catch` 把所有问题变成“操作失败”：

```js
try {
  await publishArticle(input);
} catch (error) {
  console.error(error);
  alert('操作失败');
}
```

这会丢失可恢复性与排查信息。

### 二、只在能处理的边界 catch

```js
class ValidationError extends Error {
  constructor(message, field) {
    super(message);
    this.name = 'ValidationError';
    this.field = field;
  }
}

function normalizeTitle(value) {
  const title = value.trim();
  if (title.length < 3) {
    throw new ValidationError('标题至少 3 个字符', 'title');
  }
  return title;
}
```

调用方根据错误类型处理：

```js
try {
  const title = normalizeTitle(input.value);
  await saveArticle({ title });
} catch (error) {
  if (error instanceof ValidationError) {
    showFieldError(error.field, error.message);
    return;
  }
  throw error;
}
```

无法处理的错误继续抛出，让上层错误边界、全局监控或进程策略接管。

### 三、保留错误原因链

```js
async function loadArticle(id) {
  try {
    return await articleRepository.findById(id);
  } catch (cause) {
    throw new Error(`读取文章 ${id} 失败`, { cause });
  }
}
```

`cause` 保留底层错误，不需要把数据库地址、SQL 或文件路径拼进用户消息。

```js
function serializeError(error) {
  if (!(error instanceof Error)) {
    return { name: 'UnknownError', message: String(error) };
  }

  return {
    name: error.name,
    message: error.message,
    stack: error.stack,
    cause: error.cause instanceof Error
      ? serializeError(error.cause)
      : error.cause,
  };
}
```

生产日志还需要脱敏，不能直接上传用户输入、令牌或完整请求体。

### 四、finally 负责资源清理

```js
const controller = new AbortController();
const timeoutId = setTimeout(() => controller.abort('timeout'), 5000);

try {
  return await fetch('/api/articles', {
    signal: controller.signal,
  });
} finally {
  clearTimeout(timeoutId);
}
```

`finally` 无论成功或失败都会执行。不要在 `finally` 中 `return`，否则可能覆盖原始返回值或异常。

### 五、Promise 错误必须沿链返回

```js
function loadData() {
  return fetch('/api/articles')
    .then(response => {
      if (!response.ok) throw new Error(`HTTP ${response.status}`);
      return response.json();
    });
}

loadData()
  .then(renderArticles)
  .catch(showError);
```

常见丢链：

```js
function loadData() {
  fetch('/api/articles'); // 没有 return，调用方无法等待和捕获
}
```

`async` 函数同样需要被 await 或返回：

```js
button.addEventListener('click', () => {
  void saveDraft().catch(showError);
});
```

`void` 表示明确不等待返回值，但 rejection 仍被处理。

### 六、全局错误监听是兜底，不是业务流程

```js
window.addEventListener('error', event => {
  reportUnexpectedError(event.error);
});

window.addEventListener('unhandledrejection', event => {
  reportUnexpectedError(event.reason);
});
```

用途：

- 捕获遗漏
- 关联页面、版本与用户操作
- 发现未知故障

不适合：

- 替代表单错误处理
- 吞掉异常继续执行未知状态
- 向所有用户显示同一弹窗

### 七、断点比猜测更快

#### 普通断点

在可疑行暂停，检查：

- Scope
- Call Stack
- Watch
- 当前 DOM 与网络状态

#### 条件断点

只在特定数据触发：

```text
article.id === "a-17" && article.status === "draft"
```

#### 日志断点

不修改源码即可记录表达式，适合高频路径。

#### XHR/fetch 断点

按 URL 片段暂停发请求的 JavaScript，定位请求来源。

### 八、最小复现

高质量最小复现满足：

1. 只保留触发问题的最少文件。
2. 固定输入、版本和运行命令。
3. 能稳定区分正常与异常。
4. 不依赖私有数据和偶然时序。
5. 修复后可转成自动化回归测试。

诊断循环：

```text
稳定复现
→ 缩小输入和模块
→ 提出单一可证伪假设
→ 增加观测点
→ 实施最小修复
→ 增加回归测试
```

### 九、用户消息与开发信息分离

```js
const USER_MESSAGES = {
  NETWORK_UNAVAILABLE: '网络暂时不可用，请稍后重试',
  PERMISSION_DENIED: '你没有执行此操作的权限',
};
```

用户需要：

- 发生了什么
- 是否可重试
- 下一步是什么

开发者需要：

- error type
- stack
- cause
- request ID
- release
- 环境与输入摘要

不能把数据库异常和堆栈直接返回给用户。

## 常见问题

### Q1：什么时候抛异常，什么时候返回结果对象？

违反函数正常契约、无法继续时适合异常；可预期业务分支可使用带类型的结果。团队应保持一致，避免调用方猜测。

### Q2：catch 后可以什么都不做吗？

用户主动取消等已理解情况可以静默结束；其他错误至少要恢复状态、记录或继续抛出。

### Q3：为什么 `try/catch` 捕获不到 setTimeout 里的错误？

计时器回调在后续任务中执行，已经离开原同步调用栈。应在回调内处理，或把异步操作包装成 Promise 并 await。

### Q4：错误一定是 Error 实例吗？

JavaScript 允许抛任意值。边界代码要先判断：

```js
const message = error instanceof Error ? error.message : String(error);
```

### Q5：断点会改变异步时序吗？

会。暂停主线程可能让网络、Worker 或服务端继续推进。涉及竞态时还要使用 Performance、网络节流和结构化日志。

### Q6：Source Map 会泄漏源码吗？

公开部署 Source Map 可能暴露源码。可上传到受控监控平台但不公开托管，并验证发布流程。

## 实操作业

### 基础：错误分类

为以下情况设计类型和用户提示：

- 标题为空
- API 401
- API 500
- JSON 解析失败
- 用户取消请求
- localStorage 配额不足

### 进阶：统一请求错误

实现：

```js
requestJson(url, options);
toUserMessage(error);
serializeError(error);
```

要求保留 `cause`、请求 ID 和 HTTP 状态，同时不暴露敏感响应体。

### 挑战：复现并修复竞态

为 Atlas 搜索制造旧请求覆盖新请求的问题：

1. 用不同延迟稳定复现。
2. 使用断点和时间线证明顺序。
3. 使用 AbortController 或请求序号修复。
4. 添加自动化测试，确保旧结果不能覆盖新结果。
5. 提交缺陷报告和修复前后证据。

## 本节小结

- 错误处理从分类开始，不是统一 catch
- 只在能恢复或转换语义的边界捕获异常
- Error.cause 用于保留根因链，用户消息与开发日志必须分离
- Promise 必须被返回、await 或显式处理 rejection
- 全局错误监听用于兜底观测，不替代业务错误流程
- 最小复现和回归测试是调试闭环的一部分
