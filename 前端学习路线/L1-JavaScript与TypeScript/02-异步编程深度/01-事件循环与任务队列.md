## 学习目标

- 理解 JS 单线程的本质，以及浏览器如何通过多线程配合实现异步
- 能画出事件循环（Event Loop）的完整流程图
- 掌握调用栈（Call Stack）的工作机制，能解释"栈溢出"的成因
- 能准确区分宏任务（macrotask）和微任务（microtask），说出各自的典型 API
- 能分析任意 setTimeout + Promise 组合的执行顺序
- 理解微任务与渲染时机的关键关系

## 内容讲解

### 1. JS 为什么是单线程？

同一个 JavaScript agent 在任一时刻只执行一个任务中的 JavaScript。DOM 与脚本共享这一执行上下文，使页面状态变化具有可推理的顺序；这不代表 JavaScript 语言或浏览器只能使用一个操作系统线程。

浏览器会用其他线程、进程或系统服务处理网络、计时、光栅化等工作。下面是便于理解的职责划分，不是规范要求浏览器必须创建这些同名线程：

| 线程 | 职责 |
|------|------|
| **JS 引擎线程** | 执行 JS 代码（这就是"单线程"所指的线程） |
| **GUI 渲染线程** | 绘制页面、处理回流/重绘 |
| **事件循环与任务源** | 按任务源组织计时器、用户交互、网络结果等任务 |
| **网络服务** | 处理 fetch/XHR 的连接与数据传输 |

**关键认知**：JS 引擎线程和 GUI 渲染线程是**互斥**的——同一时间只有一个在工作。所以 JS 执行太久会"卡页面"。

```
你的代码调用 setTimeout(fn, 1000)

不是"JS 等着，满 1 秒后执行 fn"
而是"宿主环境记录定时器，达到阈值后排入计时器任务"
JS 线程继续往下跑，不等待
```

---

### 2. 调用栈（Call Stack）

调用栈是一个 **LIFO（后进先出）** 的数据结构，记录当前正在执行的函数调用链。

```javascript
function c() { console.log('c'); }
function b() { c(); console.log('b'); }
function a() { b(); console.log('a'); }
a();
```

调用栈变化过程：

```
步骤1: 执行 a()        → 栈: [a]
步骤2: a 内部调用 b()  → 栈: [a, b]
步骤3: b 内部调用 c()  → 栈: [a, b, c]
步骤4: c 执行完 return  → 栈: [a, b]
步骤5: b 执行完 return  → 栈: [a]
步骤6: a 执行完 return  → 栈: []  ← 栈空，事件循环可以取下一个任务
```

**栈溢出**就是调用深度超过当前引擎和运行环境允许的上限。这个上限不是 Web 标准常量，不应依赖固定层数：

```javascript
function overflow() { overflow(); }
overflow(); // Uncaught RangeError: Maximum call stack size exceeded
```

---

### 3. 事件循环（Event Loop）

事件循环负责协调任务、微任务、渲染机会和其他宿主工作。用于页面脚本推理时，可以采用下面的简化模型：

```
while (true) {
  1. 从宏任务队列取一个任务执行（执行完调用栈会清空）
  2. 执行当前调用栈中的所有同步代码
  3. 清空微任务队列（一个不剩，产生新的微任务也立即执行完）
  4. 如果时机合适，执行渲染（GUI 线程工作）
  5. 回到步骤 1
}
```

翻译成人话：事件循环通常选择一个可运行任务，任务结束后执行微任务检查点，然后浏览器根据帧时机、页面可见性和自身策略决定是否更新渲染。规范使用的是“task”，而“宏任务”是社区常用称呼。

---
**时间线图示：**

```
│<------------- 一次事件循环 tick ------------->│<------- 下一个 tick ------>│
│                                                │                            │
│ [一个任务] → [同步代码] → [微任务检查点] → [可能渲染] │ [下一个任务] → ...      │
│   ↑                           ↑            ↑    │                            │
│   │                           │            │    │                            │
│  setTimeout              Promise.then    DOM   │                            │
│  事件回调                queueMicrotask  更新   │                            │
│  MessageChannel          MutationObserver       │                            │
│                                                │                            │
```

---

### 4. 宏任务 vs 微任务

这是分析异步时序的重要模型，但要记住它是简化表达：

> - **任务**：事件循环从某个任务源中选择一个可运行任务，不存在开发者可见的单一“总宏任务队列”
> - **微任务**：到达微任务检查点时会持续执行，直到队列为空；微任务不断追加会造成饥饿

| 类型 | 常见 API | 队列特点 |
|------|----------|----------|
| **浏览器任务** | `setTimeout`、用户交互、网络回调、`MessageChannel`、`postMessage` | 来自不同任务源，由事件循环选择 |
| **浏览器微任务** | `Promise.then/catch/finally`、`queueMicrotask()`、`MutationObserver` | 微任务检查点持续执行到队列为空 |
| **Node.js 特有队列** | `process.nextTick()`、`setImmediate()` | 不要直接套用浏览器分类与顺序 |

### 5. 经典面试题：执行顺序分析

这是每一场 JS 面试都绕不开的题：

```javascript
console.log('1');

setTimeout(() => {
  console.log('2');
  Promise.resolve().then(() => console.log('3'));
}, 0);

Promise.resolve().then(() => {
  console.log('4');
  setTimeout(() => console.log('5'), 0);
});

console.log('6');
```

**执行分析——跟着时间线走：**

```
同步代码：
  console.log('1')           → 输出: 1
  setTimeout(2+3, 0)         → 宏任务队列: [任务A: log2 + then(log3)]
  Promise.then(log4+set5)    → 微任务队列: [任务B: log4 + setTimeout(log5)]
  console.log('6')           → 输出: 6

同步代码结束，开始清空微任务队列：
  执行任务B:
    console.log('4')         → 输出: 4
    setTimeout(log5, 0)      → 宏任务队列: [任务A, 任务C: log5]
  微任务队列已空

宏任务队列取第一个（任务A）：
  console.log('2')           → 输出: 2
  Promise.then(log3)         → 微任务队列: [任务D: log3]
  宏任务执行完，清空微任务：
    执行任务D → 输出: 3

宏任务队列取下一个（任务C）：
  console.log('5')           → 输出: 5

最终输出: 1 → 6 → 4 → 2 → 3 → 5
```

**为什么要理解这个？** 不仅是面试题，更关系到：
- 你的 `loading = false` 为什么在数据更新之前就触发了
- 为什么把长任务拆开后浏览器才可能获得渲染机会
- 为什么框架调度不能只用“宏任务优先级”解释

---

### 6. 微任务与渲染时机

**关键规则**：任务结束并完成微任务检查点后，浏览器才可能获得一次渲染机会；是否立即渲染由帧预算、页面可见性和实现策略决定。

```javascript
// ❌ 错误认知：以为这段代码会让页面先显示"加载中"
document.body.textContent = '加载中...';
heavyComputation(); // 耗时 3 秒，页面直接卡住
document.body.textContent = '加载完成';

// ⚠️ setTimeout 只能把计算放到后续任务，不能保证中间一定完成绘制
document.body.textContent = '加载中...';
setTimeout(() => {
  heavyComputation();
  document.body.textContent = '加载完成';
}, 0);
```

**原理**：`setTimeout(fn, 0)` 让计算进入后续计时器任务，使浏览器“有机会”在两个任务之间渲染。如果业务要求确认至少跨过一次绘制，应使用与帧同步的调度策略，例如先 `requestAnimationFrame` 更新 UI，再在后续任务中开始重计算；长计算仍应切片或移入 Worker。

## 常见问题

**Q1：为什么 `setTimeout(fn, 0)` 不是 0 毫秒后立即执行？**

`0` 表示最早可调度阈值，不表示立即执行。浏览器需要等当前任务与微任务结束；定时器连续嵌套达到规范阈值后还会应用至少 4ms 的限制。未嵌套定时器的实际延迟由浏览器、系统调度、后台节流和主线程工作决定，不能固定成“通常 1ms”。

---

**Q2：`Promise` 的 `executor` 函数是同步还是异步？**

同步执行。`new Promise((resolve) => { console.log(1); resolve(); })` 中的 `console.log(1)` 是立即打印的。只有 `.then()` 的回调才是异步（微任务）。

---

**Q3：`async` 函数里的 `await` 后面代码是微任务吗？**

从时序上看，`await` 暂停当前 async 函数，恢复执行会通过 Promise Job 进入微任务队列。它与手写 `.then()` 有相近的调度结果，但不是简单的源码替换，两者在错误栈、控制流和规范算法上仍有差异。

---

**Q4：为什么我的 `for` 循环里用 `await` 是串行的？**

因为 `await` 会暂停当前函数的执行。`for` 循环每次迭代都会等到 `await` 完成才继续。如果想并行，用 `Promise.all`。

---

**Q5：宏任务和微任务哪个优先级高？**

在浏览器到达微任务检查点时，微任务会在下一个任务前执行。递归追加微任务会造成任务和渲染饥饿，因此它不是可滥用的“更高优先级线程”。

---

**Q6：`requestAnimationFrame` 属于宏任务还是微任务？**

都不是。`requestAnimationFrame` 的回调在**渲染之前**执行，处于微任务清空之后、实际绘制之前。它是独立于事件循环任务分类的"帧回调队列"。

---

**Q7：如何直观验证自己的事件循环理解？**

在浏览器 DevTools 的 Performance 面板录制一段代码，可以看到任务、微任务、渲染的精确时序。或者直接在 Console 运行本文第 5 节的面试题代码。

---

**Q8：Node.js 的事件循环和浏览器一样吗？**

两者都依赖事件循环，但 Node.js 使用 libuv 阶段，并有 `process.nextTick`、`setImmediate` 等专有机制；Node.js 20 起定时器阶段行为也发生过变化。本文只讨论浏览器，Node.js 顺序应在对应运行时章节单独分析。

## 实操作业

### 基础：分析执行顺序

写出下面代码的输出顺序，然后在浏览器 Console 中验证：

```javascript
console.log('A');

setTimeout(() => console.log('B'), 0);

Promise.resolve()
  .then(() => console.log('C'))
  .then(() => console.log('D'));

console.log('E');

queueMicrotask(() => console.log('F'));

setTimeout(() => {
  console.log('G');
  queueMicrotask(() => console.log('H'));
}, 0);
```

### 进阶：实现一个微任务调度器

用 `queueMicrotask` 实现一个函数 `defer(fn)`，让 `fn` 在当前同步代码全部执行完后、下一个宏任务之前执行。然后用它来批量收集日志并一次性输出：

```javascript
// 预期：所有 log 调用收集完成后，一次性打印 ["step1", "step2", "step3"]
const logs = [];
function log(msg) {
  // 在这里实现：收集 msg，用微任务一次性输出
}
log('step1');
log('step2');
log('step3');
console.log('同步代码结束');
```

## 本节小结

- JS 是单线程的，但浏览器通过多线程协作实现异步——定时器线程计时、网络线程收发数据，JS 线程只管执行回调
- 事件循环的节奏：**一个宏任务 → 清空微任务 → 可能渲染 → 下一个宏任务**
- 微任务（Promise.then、queueMicrotask）会在当前宏任务结束后立刻全部执行，是一个"插队"机制
- 理解宏任务/微任务的执行顺序，是所有异步代码推理的基础——不掌握它，你写的 Promise 和 async/await 行为就无法预测

官方参考：[HTML Standard - Event loops](https://html.spec.whatwg.org/multipage/webappapis.html#event-loops) · [HTML Standard - Timers](https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html#timers)
- 面试题中的 setTimeout + Promise 组合看似刁钻，实则考验的是你对事件循环 tick 边界的理解
