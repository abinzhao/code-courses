## 内容讲解

### 一、JS 的内存生命周期

JavaScript 在你不知不觉中完成了三件事：

```
分配（Allocate）→ 使用（Use）→ 释放（Release）
```

```javascript
let user = { name: '小明' }; // ① 分配：在堆上创建对象，栈上存引用
console.log(user.name);       // ② 使用：通过引用访问值
user = null;                  // ③ 释放：断开引用，对象变成垃圾等待回收
```

前两步是你在写代码时主动控制的，第三步由**垃圾回收器（Garbage Collector, GC）**自动完成。JS 是**自动内存管理**的语言，开发者不需要手动 `free()` 或 `delete` 内存——但这不代表你可以完全不管内存。

### 二、栈内存 vs 堆内存

JS 的内存空间分成两大区域：

| | 栈（Stack） | 堆（Heap） |
|---|---|---|
| 存储内容 | 基本类型值（number, string, boolean, null, undefined, symbol, bigint）和**引用地址** | 对象、数组、函数等**引用类型** |
| 大小 | 小，固定（通常几 MB） | 大，动态分配 |
| 分配速度 | 极快（移动指针即可） | 相对慢（需查找空闲块） |
| 回收方式 | 函数执行完自动弹出 | 垃圾回收器回收 |
| 访问速度 | 快 | 慢（多一次间接寻址） |

```javascript
function demo() {
  // 栈内存：原始值直接存在栈中
  let age = 25;               // 栈帧中存 25
  let name = 'hello';         // 栈帧中存 'hello'

  // 堆内存：对象存在堆中，栈中只存引用地址
  let obj = { x: 10 };       // 堆中: { x: 10 }，栈中: obj → 堆地址0xA1
  let arr = [1, 2, 3];       // 堆中: [1, 2, 3]，栈中: arr → 堆地址0xA2
}
// 函数执行完毕，栈帧弹出，obj/arr 的引用消失
// 如果堆上的对象没有被其他变量引用，就会被 GC 回收
```

> **关键结论**：你常说的「引用赋值」——`let b = a`（a 是对象）——复制的是栈上的引用地址，不是堆上的对象本身。

### 三、垃圾回收算法

#### 3.1 引用计数（Reference Counting）

**算法**：每个对象维护一个「被引用次数」计数器。引用加 1，取消引用减 1。为 0 时立即回收。

```javascript
let a = { name: 'obj' };  // obj 引用计数 = 1
let b = a;                 // obj 引用计数 = 2
a = null;                  // obj 引用计数 = 1（b 还在引用）
b = null;                  // obj 引用计数 = 0 → 立即回收
```

**优点**：即时回收，不会突然暂停。
**致命缺陷**：无法处理**循环引用**。

```javascript
function createCycle() {
  let objA = {};
  let objB = {};
  objA.ref = objB;    // objB 引用计数 +1
  objB.ref = objA;    // objA 引用计数 +1
  // 函数结束，objA、objB 局部变量消失
  // 但 objA.ref 和 objB.ref 还是互相引用，计数永远 ≥1
  // → 内存泄漏！
}
```

由于这个缺陷，现代 JS 引擎不再单独使用引用计数，而是用标记-清除作为主要算法。

#### 3.2 标记-清除（Mark-and-Sweep）

**算法分两阶段**：

1. **标记（Mark）**：从根对象（Root，全局对象、当前执行栈上的变量）出发，深度遍历所有可到达的对象并打上标记
2. **清除（Sweep）**：遍历整个堆，回收**没有标记**的对象

```
根对象（全局 window / global、调用栈）
   │
   ├→ objA（标记 ✓）
   │    └→ objA.child（标记 ✓）
   │
   └→ objB（标记 ✓）

objC（无标记 ✗，不可达 → 回收！）
```

循环引用在标记-清除下不是问题：两个互相引用的对象如果都无法从根到达，就不会被标记，最终会被清除。

**缺点**：标记和清除期间需要暂停 JS 执行（Stop-The-World），如果堆很大，暂停时间会卡到你。

#### 3.3 V8 的分代垃圾回收

V8 引擎观察到一个事实：**大多数对象死得很快，活下来的对象会活很久**。基于这个假设，它将堆分为两代：

```
┌──────────────────────────────────────┐
│  新生代（Young Generation）            │
│  大小：1-8 MB                         │
│  算法：Scavenge（半空间复制）          │
│  特点：频繁、快速、回收短期对象        │
│  存活条件：经历过一次 GC 还活着         │
└──────────────┬───────────────────────┘
               │ 晋升（Promotion）
┌──────────────▼───────────────────────┐
│  老生代（Old Generation）              │
│  大小：动态增长                        │
│  算法：Mark-Sweep-Compact             │
│  特点：低频、回收长期对象              │
└──────────────────────────────────────┘
```

**新生代 Scavenge 算法**：将内存空间一分为二（From 空间和 To 空间），对象分配在 From 空间中。GC 时，把 From 中的存活对象复制到 To 空间，然后清空整个 From 空间。最后 From 和 To 角色互换。这种半空间复制的优势是**速度快**（只需处理存活对象），代价是**空间利用率只有 50%**。

**老生代 Mark-Sweep-Compact**：先用标记-清除回收垃圾，然后对存活对象进行**整理（Compact）**——把它们向一端移动，消除碎片化空间，方便后续分配大对象。

### 四、常见内存泄漏场景

#### 4.1 意外的全局变量

```javascript
function leak() {
  name = '一个全局变量';  // 忘记加 const/let → 泄漏到 window.name
  this.data = '数据';     // 非严格模式下 this = window → window.data
}
leak();
// name 和 data 永远不会被回收，直到页面关闭
```

**修复**：始终使用 `const`/`let` 声明变量，开启严格模式 `'use strict'`。

#### 4.2 未清除的定时器

```javascript
function startTimer() {
  const bigData = new Array(1000000).fill('🐘'); // 大对象
  setInterval(() => {
    console.log(bigData.length); // 定时器持续引用 bigData
  }, 1000);
}
startTimer();
// 即使 startTimer 执行完毕，bigData 也不会被回收
// 因为定时器的回调仍在引用它
```

**修复**：用 `clearInterval`/`clearTimeout` 清除不再需要的定时器。

#### 4.3 闭包中的意外引用

```javascript
function createHandler() {
  const bigData = new Array(1000000);
  return function handler() {
    // 只用了 bigData 的一小部分
    console.log(bigData[0]);
  };
}
const handler = createHandler();
// 整个 bigData 都无法回收，因为 handler 闭包持有整个作用域
```

**修复**：将不需要长期持有的数据设为 `null`，或缩小闭包范围。

#### 4.4 游离的 DOM 引用

```javascript
const elements = {
  button: document.getElementById('myButton'),
};
document.body.removeChild(elements.button);
// DOM 从页面上消失了，但 JS 中的 elements.button 还在引用它
// → DOM 节点无法被 GC 回收
```

**修复**：移除 DOM 后，同时清除 JS 中的引用：`elements.button = null`。

#### 4.5 未移除的事件监听器

```javascript
class Component {
  mount() {
    window.addEventListener('resize', this.onResize);
  }
  onResize() { console.log('resize'); }
  // 忘记实现 unmount() 中 removeEventListener
}
// 组件销毁后，即使 window 上没有任何可见组件，
// 事件监听器仍持有 Component 实例的引用 → 内存泄漏
```

**修复**：在组件销毁时用 `removeEventListener` 清除监听。

### 五、WeakMap 和 WeakSet：弱引用机制

`WeakMap` 和 `WeakSet` 的「Weak」指的是**键的引用是弱引用**——弱引用不计入引用计数，不阻止垃圾回收。

```javascript
// 普通 Map：强引用，阻止 GC
const map = new Map();
let obj = { data: 'important' };
map.set(obj, 'metadata');
obj = null;           // map 仍然持有对原对象的引用 → 不会回收！

// WeakMap：弱引用，不阻止 GC
const weakMap = new WeakMap();
let obj2 = { data: 'important' };
weakMap.set(obj2, 'metadata');
obj2 = null;          // 没有其他强引用 → obj2 会被回收
                      // weakMap 中的对应键值也会自动消失
```

**WeakMap/WeakSet 的限制**：
- 键必须是对象（不能是基本类型）
- 不可迭代（没有 `keys()`、`values()`、`entries()`、`forEach()`、`size`）
- 只有 `get()`、`set()`、`has()`、`delete()` 四个方法

**典型应用场景**：缓存、关联数据（DOM 节点的额外数据）、依赖追踪（Vue 3 的 `targetMap` 用的就是 `WeakMap`）。

```javascript
// 场景：给 DOM 元素关联一些额外数据
const nodeMeta = new WeakMap();

const div = document.createElement('div');
nodeMeta.set(div, { clickCount: 0, lastUpdated: Date.now() });

// 当 div 从 DOM 中移除且没有其他引用时，nodeMeta 中的记录会自动清理
// 不需要手动 delete
```

### 六、实战：用 Chrome Memory 面板排查内存泄漏

**步骤演示（你要跟着做）**：

1. 打开 Chrome DevTools → **Memory** 面板
2. 选择 **Heap snapshot** 模式
3. 点击 **Take snapshot** 拍一张堆快照（基线）
4. 执行你怀疑泄漏的操作（如反复创建/销毁组件）
5. 再次 **Take snapshot**
6. 在第二张快照中，将视图切换为 **Comparison**，对比第一张快照
7. 按 **Delta**（差值）排序，查看哪些对象数量/大小异常增长

```
快照对比表（示例）：
┌──────────────────────┬──────────┬──────────┬──────────┐
│ Constructor           │ # New    │ # Deleted│ Delta    │
├──────────────────────┼──────────┼──────────┼──────────┤
│ HTMLElement           │ +50      │ -0       │ +50 ⚠️   │
│ (closure)             │ +30      │ -0       │ +30 ⚠️   │
│ Array                 │ +5       │ -5       │ 0  ✓     │
└──────────────────────┴──────────┴──────────┴──────────┘
```

HTMLElement 和闭包只增不减 → 确认内存泄漏。

**进一步定位**：点击有问题的构造器，下方会列出具体对象。选中一个对象，底部的 **Retainers** 面板会展示「是什么在持有这个对象的引用」——这就是泄漏的根源。

## 常见问题

**Q1：JS 是自动管理内存的，为什么还要学垃圾回收？**

知道 GC 怎么工作，你才能写出不泄漏的代码。内存泄漏不会立即报错，但会在运行一段时间后让页面卡死甚至崩溃。线上定位这类问题往往非常痛苦，不如预防。

**Q2：`null` 赋值和 `delete` 操作能手动控制内存吗？**

`obj = null` 只是断开引用，让对象变成可回收状态，并不立即释放内存——GC 会在它认为合适的时机回收。`delete obj.prop` 删除属性，同样只是断开引用。两者都不是 `free()`，不要把它们当手动内存管理用。

**Q3：V8 新生代为什么那么小？**

小空间意味着 Scavenge 复制操作非常快（通常 <1ms），适合频繁回收短命对象。如果把新生代搞大了，每次 GC 的停顿就不可接受。

**Q4：闭包一定会导致内存泄漏吗？**

不。闭包只是捕获了作用域中的变量。只有当闭包函数被长期持有（如绑定到全局事件、存入全局数组），且闭包捕获了不再需要的大对象时，才构成内存泄漏。正常使用闭包完全没问题。

**Q5：WeakRef 是什么？和弱引用有什么关系？**

`WeakRef` 是 ES2021 引入的 API，让你显式创建一个弱引用：`const ref = new WeakRef(obj)`。通过 `ref.deref()` 获取原对象，如果已回收则返回 `undefined`。但不推荐在生产代码中使用——GC 时机不确定，`deref()` 的返回值不可预测，应优先用 `WeakMap`。

**Q6：JSON.parse 大字符串时内存怎么分配的？**

JSON 字符串本身是基本类型，可能很长但仍存在栈或专用字符串空间中（V8 对大字符串有特殊处理）。`JSON.parse()` 会创建对应的 JS 对象（放在堆上），所以解析大的 JSON 时堆内存会显著增长。

**Q7：移动端浏览器的 GC 策略和桌面端一样吗？**

基本算法相同，但移动端对内存更敏感。在低内存设备上，V8 会更激进地触发 GC，且老生代堆的上限更低。如果页面内存占用过高，移动端可能直接被系统杀掉。

**Q8：能用代码显式触发垃圾回收吗？**

理论上 `window.gc` 存在，但仅在 Chrome 启动时传了 `--js-flags="--expose-gc"` 参数的 DevTools 中可用。生产代码不应该也不建议手动触发 GC。

## 实操作业

### 基础练习：手动制造并修复内存泄漏

写一段代码，每 1 秒创建一个 10,000 个元素的数组，保存到不会被回收的地方（如全局数组）。运行 10 秒后停止创建，但不清除引用。

1. 使用 Chrome Memory 面板的快照对比功能确认内存持续增长
2. 修改代码，给泄漏加一个清理机制（如每 5 秒清理旧数据），验证内存恢复稳定

### 进阶练习：实现一个基于 FinalizationRegistry 的资源追踪器

`FinalizationRegistry` 允许你在对象被 GC 回收时执行回调。用它实现一个简单的内存监控工具：

```javascript
// 目标：追踪哪些对象已经被 GC 回收
const tracker = createTracker();
tracker.track(myObj, 'myObj');
// ... 当 myObj 被 GC 回收时，自动打印 "[GC] myObj 已回收"
```

### 挑战练习：用 WeakMap 实现一个带过期时间的缓存

实现一个 `ExpirableCache` 类：
- 用 `WeakMap` 存储数据值，键为对象引用
- 每个缓存项有自己的过期时间（TTL）
- 读取过期数据时自动清理并返回 `undefined`
- 利用 `WeakMap` 的弱引用特性，当缓存键对象被释放时，对应缓存自动消失

```javascript
const user1 = { id: 1 };
const cache = new ExpirableCache();
cache.set(user1, { data: 'user data' }, 5000); // 5 秒过期
setTimeout(() => {
  console.log(cache.get(user1)); // undefined（已过期）
}, 6000);
```

### 作业参考与验收

- **基础**：有界创建 10 秒后停 timer；快照查看全局数组的 retained path。清引用后允许 GC 再比较，单次 heap 下降或未下降都不足以证明完整修复。
- **进阶**：注册 heldValue 不得反向强引用被追踪对象；unregister 用 token。FinalizationRegistry 回调时机不保证，不能作为关闭文件、释放连接或必需日志的唯一机制。
- **挑战**：WeakMap 记录 {value,expiresAt}，get 时检查并删除过期项；用可注入时钟测试边界。WeakMap 不可枚举，不能提供真实全量 size 或定时扫描所有键。

## 本节小结

- JS 内存自动管理但并非免费：了解 GC 原理是写出不泄漏代码的前提
- 栈存基本类型和引用，堆存对象；函数执行完栈自动释放，堆由 GC 回收
- 标记-清除是主流 GC 算法：从根可达则存活，不可达则回收；循环引用不再致命
- V8 分代回收：新生代对象用 Scavenge（快但空间小），老生代用 Mark-Sweep-Compact（稳定但可能 STW）
- 常见泄漏：意外的全局变量、未清除的定时器/事件监听器、游离 DOM 引用、闭包持有大对象
- `WeakMap`/`WeakSet` 的弱引用不计入 GC 决策，适合缓存和元数据关联场景
- Chrome Memory 面板的快照对比是排查泄漏的核心工具
