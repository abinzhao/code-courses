# 03 — 移动优先与适配策略

## 学习目标

- 理解"移动优先"的真正含义——不是"只做手机"，而是一种思维方式和编码策略
- 掌握视口（viewport）meta 标签的每一个属性及其作用
- 能根据场景选择合适的 CSS 单位（rem / em / px / vw / vh / dvh）
- 理解并解决移动端常见适配问题（1px 边框、安全区域、点击区域）
- 学会使用响应式图片技术（`<picture>`、`srcset`、`sizes`）
- 能编写从 320px 到 1920px 无缝适配的完整页面

---

## 内容讲解

### 1. "移动优先"的真正含义

很多人误以为"移动优先"就是"先做手机端再做桌面端"。这只是表面。真正的含义是：

**"先从最受限的环境开始设计，然后逐步增强。"**

| 维度 | 移动优先思维 | 桌面优先思维 |
|------|-------------|-------------|
| 出发点 | 内容为核心，只放最重要的 | 空间充足，什么都放上去 |
| 布局 | 单列 → 多列 | 多列 → 藏着掖着 |
| 性能 | 从一开始就考虑加载速度 | 后来才优化 |
| 交互 | 触摸 + 键盘 | 鼠标优先 |
| 编码 | 基础样式 = 手机，`min-width` 往上加 | 基础样式 = 桌面，`max-width` 往下减 |

**实操口诀**：先写一个能在 320px 屏幕上流畅使用的版本，然后用 `min-width` 媒体查询逐步为更大屏幕**增强**（不是修补、不是补救）体验。

---

### 2. Viewport Meta 标签详解

这是每个 HTML 页面的第一行"必修课"：

```html
<meta name="viewport" content="width=device-width, initial-scale=1.0">
```

这行代码告诉移动浏览器："请用设备的实际宽度来渲染页面，不要假装自己是 980px 宽的桌面浏览器。"

#### 2.1 属性说明

| 属性 | 取值 | 含义 |
|------|------|------|
| `width` | `device-width` 或具体值 | 视口宽度。`device-width` = 设备屏幕宽度（CSS 像素） |
| `initial-scale` | 数字，如 `1.0` | 初始缩放比例。1.0 = 不缩放 |
| `minimum-scale` | 数字 | 最小缩放比例（通常不建议设为 1.0，会阻止用户缩放） |
| `maximum-scale` | 数字 | 最大缩放比例 |
| `user-scalable` | `yes` / `no` | 是否允许用户缩放。**不建议设为 no**，这会破坏可访问性 |
| `viewport-fit` | `auto` / `cover` | 是否延伸到刘海屏区域（配合 safe-area-inset 使用） |
| `interactive-widget` | `resizes-visual` / `resizes-content` / `overlays-content` | 虚拟键盘弹出时视口的行为 |

#### 2.2 推荐配置

```html
<!-- 标准页面：允许缩放，保证可访问性 -->
<meta name="viewport" content="width=device-width, initial-scale=1.0">

<!-- 需要全屏沉浸的页面（如游戏、全景图）—— 但保留最小缩放 -->
<meta name="viewport" content="width=device-width, initial-scale=1.0, viewport-fit=cover">
```

#### 2.3 不写 viewport 会怎样？

移动浏览器会默认将页面渲染在一个 980px（或 1024px）的虚拟视口中，然后缩小以适配屏幕。结果就是所有文字小到看不清，用户必须手动放大。

### 3. CSS 单位全景对比

#### 3.1 核心单位速查

| 单位 | 相对什么 | 典型场景 |
|------|---------|---------|
| `px` | 设备像素（考虑 DPR） | 边框、精确尺寸、`box-shadow` 偏移 |
| `rem` | 根元素（`<html>`）的 `font-size` | 字号、间距、布局尺寸（全局一致性） |
| `em` | **当前元素**的 `font-size` | 组件内部的比例关系、图标大小 |
| `vw` | 视口宽度的 1% | 全宽区段、流体排版 |
| `vh` | 视口高度的 1% | 全高区段、弹窗高度 |
| `dvh` | 动态视口高度（含/不含地址栏） | 移动端全屏体验（现代替代 vh） |
| `svh` | 最小视口高度（地址栏展开时） | 保守型全高 |
| `lvh` | 最大视口高度（地址栏收起时） | 激进型全高 |
| `%` | 父元素的对应属性 | 相对父级的比例尺寸 |
| `ch` | "0" 字符的宽度 | 限制文字行宽（可读性） |

#### 3.2 rem vs em 的经典案例

```css
html { font-size: 16px; }  /* 根字号 = 16px */

.article {
  font-size: 1.125rem;      /* = 18px（相对 html） */
  padding: 2rem;             /* = 32px（相对 html） */
}

.article .title {
  font-size: 2em;            /* = 36px（相对 .article 的 18px × 2） */
  margin-bottom: 0.5em;      /* = 18px（相对自身 font-size 36px × 0.5） */
}
```

**选择口诀**：
- 全局一致的尺寸 → `rem`
- 组件内部和文字大小成比例的间距 → `em`
- 需要精确像素控制的 → `px`
- 需要随视口变化的 → `vw` / `vh` / `dvh`

#### 3.3 vh 的陷阱与 dvh 的解决方案

```css
/* ❌ 移动端常见问题：100vh 会让底部被地址栏遮挡 */
.hero {
  height: 100vh; /* Safari 中地址栏展开/收起时高度会跳动 */
}

/* ✅ 现代方案：dvh 会动态适应地址栏 */
.hero {
  height: 100dvh; /* 地址栏收起时 = lvh，展开时 = svh，平滑过渡 */
}

/* 渐进增强：不支持 dvh 的浏览器回退到 vh */
.hero {
  height: 100vh;
  height: 100dvh;
}
```

#### 3.4 流体排版（clamp）

```css
/* clamp(最小值, 理想值, 最大值) */
h1 {
  /* 最小 32px，理想 5vw，最大 64px */
  font-size: clamp(2rem, 5vw, 4rem);
}

.container {
  /* 最小 320px，理想 90%，最大 1200px */
  width: min(100% - 32px, 1200px);
  /* 等价于 width: 100%; max-width: 1200px; padding: 0 16px; —— 但更简洁 */
}
```

`clamp()` 让你**不需要媒体查询也能实现流畅响应式**。字号、间距、宽度都可以用 `clamp()` 做无缝缩放。

### 4. 移动端 1px 边框问题

#### 4.1 问题根源

在 DPR（设备像素比）为 2 或 3 的屏幕上，CSS 的 `1px` 实际渲染为 2 或 3 个物理像素，导致边框看起来粗了一倍。

#### 4.2 解决方案

```css
/* 方案 1：伪元素 + transform（兼容性好，推荐） */
.hairline-border {
  position: relative;
}

.hairline-border::after {
  content: "";
  position: absolute;
  left: 0;
  bottom: 0;
  width: 100%;
  height: 1px;
  background: #e0e0e0;
  /* 只在 DPR ≥ 2 的设备上缩小 */
}

@media (-webkit-min-device-pixel-ratio: 2) {
  .hairline-border::after {
    transform: scaleY(0.5);
    transform-origin: 0 0;
  }
}

@media (-webkit-min-device-pixel-ratio: 3) {
  .hairline-border::after {
    transform: scaleY(0.3333);
  }
}

/* 方案 2：viewport 方案（需要 JS 配合） */
/* 但涉及动态写入 viewport，不是纯 CSS 方案 */
```

### 5. 安全区域适配（safe-area-inset）

iPhone X 之后，所有全面屏手机都有"刘海"或"挖孔"，以及底部的 Home Indicator。`safe-area-inset-*` 是 CSS 环境变量，告诉你内容的安全渲染区域：

```css
/* 完整的 safe-area 适配 */
.header {
  /* 顶部避开刘海 */
  padding-top: env(safe-area-inset-top);
}

.footer {
  /* 底部避开 Home Indicator */
  padding-bottom: env(safe-area-inset-bottom);
}

.sidebar {
  padding-left: env(safe-area-inset-left);
  padding-right: env(safe-area-inset-right);
}

/* ✅ 推荐的通用写法：叠加 padding */
.page {
  /* 基础间距 + 安全区域 */
  padding:
    calc(16px + env(safe-area-inset-top))
    calc(16px + env(safe-area-inset-right))
    calc(16px + env(safe-area-inset-bottom))
    calc(16px + env(safe-area-inset-left));
}

/* 前提：viewport meta 标签中包含 viewport-fit=cover */
/* <meta name="viewport" content="width=device-width, initial-scale=1.0, viewport-fit=cover"> */
```

### 6. 响应式图片

#### 6.1 为什么需要响应式图片？

在手机上加载一张 1920px 宽的桌面版图片，浪费带宽、拖慢加载。响应式图片让浏览器根据屏幕尺寸和像素密度选择最合适的图片资源。

#### 6.2 分辨率切换：srcset + sizes

```html
<!-- 语法：srcset="图片URL 宽度描述符w" sizes="媒体条件 槽位宽度" -->
<img
  src="photo-800.jpg"
  srcset="
    photo-400.jpg   400w,
    photo-800.jpg   800w,
    photo-1200.jpg 1200w,
    photo-1600.jpg 1600w
  "
  sizes="
    (max-width: 600px) 100vw,
    (max-width: 1200px) 50vw,
    33vw
  "
  alt="响应式示例图片"
>
```

**`sizes` 的阅读方式**：

- `(max-width: 600px) 100vw` → 屏幕 ≤ 600px 时，图片占满屏宽
- `(max-width: 1200px) 50vw` → 屏幕 601-1200px 时，图片占屏宽一半
- `33vw` → 其他情况（> 1200px），图片占屏宽 1/3

浏览器会根据当前视口宽度和 DPR 自动选择 `srcset` 中最合适的图片下载。

#### 6.3 艺术方向：`<picture>` 元素

```html
<!-- 不同屏幕尺寸显示不同裁剪/构图的图片 -->
<picture>
  <!-- 窄屏 → 竖版裁剪（聚焦主体） -->
  <source
    media="(max-width: 600px)"
    srcset="hero-mobile.jpg"
  >

  <!-- 中等屏幕 → 方形裁剪 -->
  <source
    media="(max-width: 1200px)"
    srcset="hero-tablet.jpg"
  >

  <!-- 宽屏 → 横版大图 -->
  <img
    src="hero-desktop.jpg"
    alt="网站主视觉"
  >
</picture>
```

**`srcset` vs `<picture>` 的决策**：

- 同一张图、不同分辨率 → `srcset` + `sizes`
- 不同构图、不同比例 → `<picture>` + `media`
- 不同格式（WebP vs JPEG）→ `<picture>` + `type`

```html
<!-- 格式回退：现代浏览器用 WebP，老浏览器回退 JPEG -->
<picture>
  <source srcset="photo.webp" type="image/webp">
  <img src="photo.jpg" alt="图片">
</picture>
```

### 7. 触屏交互最佳实践

#### 7.1 点击区域最小 44px

Apple 和 Google 的 HIG 都建议：可点击元素的最小尺寸为 **44×44 CSS 像素**。这不是"建议"，而是在触屏设备上避免用户挫败感的底线。

```css
.nav-link {
  display: inline-flex;
  align-items: center;
  justify-content: center;
  min-width: 44px;
  min-height: 44px;
  padding: 8px 12px; /* 视觉间距和点击区域解耦 */
}

/* 图标按钮：即使图标只有 24px，点击区域也应该是 44px */
.icon-btn {
  width: 44px;
  height: 44px;
  display: flex;
  align-items: center;
  justify-content: center;
}

.icon-btn svg {
  width: 24px;
  height: 24px;
}
```

#### 7.2 hover 的替代方案

触屏设备没有 hover 状态。为 `:hover` 写的交互逻辑在手机上永远不会触发：

```css
/* ❌ 只在 hover 时显示的信息，手机端完全无法查看 */
.button .tooltip {
  display: none;
}
.button:hover .tooltip {
  display: block;
}

/* ✅ 使用媒体查询区分触屏和鼠标设备 */
.button .tooltip {
  display: none;
}

/* 鼠标设备：hover 显示 */
@media (hover: hover) {
  .button:hover .tooltip {
    display: block;
  }
}

/* 触屏设备：active/focus 显示 + 移除 hover 样式 */
@media (hover: none) {
  .button:active .tooltip,
  .button:focus-within .tooltip {
    display: block;
  }
}
```

#### 7.3 其他触屏注意事项

```css
/* 1. 禁用移动端长按菜单（谨慎使用） */
.no-callout {
  -webkit-touch-callout: none;
}

/* 2. 让滚动更顺滑 */
.scroll-container {
  -webkit-overflow-scrolling: touch;
  overflow-y: auto;
}

/* 3. 防止 iOS 输入框自动缩放（字号 ≥ 16px 时不触发） */
input, textarea {
  font-size: 16px; /* iOS 不会对 ≥ 16px 的输入框自动缩放 */
}

/* 4. 触屏优化：给 :active 添加视觉反馈 */
.tap-target:active {
  transform: scale(0.97);
  transition: transform 0.1s;
}
```

2. **拖宽到 768px**：导航链接出现，汉堡消失，卡片变两列
3. **拖宽到 1024px**：卡片变三列，内容区居中
4. **整个过程**：字体用 `clamp()` 平滑缩放，间距用 `clamp()` 自适应
5. **切换到系统暗色模式**：颜色自动跟随

## 常见问题

**Q1：移动优先和桌面优先到底选哪个？**

移动优先。原因：移动端流量占比持续上升；先写简单再写复杂永远比反过来容易；Google 的移动优先索引（Mobile-First Indexing）让移动端体验直接影响搜索排名。

**Q2：rem 的根字号应该设为多少？设计稿和 rem 怎么换算？**

推荐保持 `html { font-size: 16px; }`（浏览器默认值），然后按 `设计稿px值 ÷ 16` 计算 rem。例如设计稿上间距 24px → `1.5rem`。不推荐改根字号为 10px 或 62.5%（虽然计算方便），因为这会覆盖用户的浏览器默认字号偏好。

**Q3：什么时候用 vw/vh，什么时候用 rem？**

`vw` 用于需要跟随视口响应式变化的尺寸（如全屏 Hero 高度、流体排版）。`rem` 用于需要保持一致性的尺寸（如文章内边距、全局字号）。一个简单的测试：如果调整浏览器窗口大小时这个值应该跟着变 → `vw`；如果只应该跟着根字号变 → `rem`。

**Q4：Safari 的 100vh 问题怎么彻底解决？**

在 Safari 中，`100vh` 不包含地址栏高度，导致地址栏展开/收起时页面跳动。解决方案：用 `100dvh`（动态视口高度），并回退 `100vh` 给不支持的浏览器。如果需要兼容老版 Safari，可以用 JS 动态设置 `--vh` 变量作为兜底方案。

**Q5：`<picture>` 和 `srcset` 需要为不同屏幕准备很多图片吗？**

不是必需的。两到三个尺寸通常就够用了：移动端（~400px 宽）、平板/小桌面（~800px 宽）、大桌面（~1200px 宽）。现代构建工具（如 Next.js Image、Vite 的图片插件）可以自动为你生成这些尺寸。

**Q6：`clamp()` 和媒体查询比，哪个更好？**

不是"哪个更好"的问题——它们是互补的。`clamp()` 用于需要**无缝缩放**的属性（字号、间距），媒体查询用于需要**突变**的属性（布局切换、显示/隐藏元素）。典型的页面会同时使用两者。

**Q7：移动端点击事件有 300ms 延迟是怎么回事？怎么解决？**

这是历史问题了。浏览器在移动端用 300ms 等待判断用户是否要做双击缩放。解决方案：在 `<head>` 中正确设置 `viewport` meta 标签并设置 `width=device-width`，现代移动浏览器就不会添加这个延迟。如果还需要更快的响应，可以使用 `touch-action: manipulation` CSS 属性来彻底消除。

## 实操作业

### 练习 1（基础）：移动优先导航栏

动手写一个导航栏，要求：
- 320px 时显示 Logo + 汉堡图标（☰），导航链接隐藏
- 768px 时隐藏汉堡，显示横向导航链接
- 所有可点击区域 ≥ 44px
- 使用 `min-width` 做移动优先

### 练习 2（进阶）：图片画廊的响应式

为一个图片画廊页面（6 张图）实现：
- 手机（< 640px）：单列，图片占满宽度
- 平板（640-1024px）：两列
- 桌面（> 1024px）：三列
- 使用 `<picture>` 为每张图提供移动版和桌面版（可以用占位图服务，如 `https://placehold.co/{width}x{height}`）
- 用 `clamp()` 设置标题字号和卡片间距

### 练习 3（挑战）：完全响应式着陆页

从零写一个完整的产品着陆页，覆盖 320px → 1920px：
- 导航栏、主横幅、特性区（至少 4 个卡片）、CTA 按钮、页脚
- 全程使用 CSS 变量管理颜色、间距、字号
- 支持系统深色/浅色模式自动切换
- 适配安全区域（`safe-area-inset`）
- `prefers-reduced-motion` 时禁用所有动效
- 触屏设备上 hover 替换为 active 反馈

## 本节小结

- "移动优先"是一种**思维方式**，不是先后顺序——从最受限的环境开始，逐步增强
- `viewport` meta 标签是移动端适配的第一道门，不写它一切免谈
- 单位选择有章可循：全局尺寸用 `rem`，精确尺寸用 `px`，流体尺寸用 `vw`/`clamp()`，组件内部比例用 `em`
- `dvh` 解决了 `vh` 在移动端地址栏场景下的历史痛
- 1px 边框问题用伪元素 + `transform: scale()` 解决
- 安全区域用 `env(safe-area-inset-*)` 适配刘海屏和底部指示条
- 响应式图片不是"一张图缩放"，而是**按需选择最合适的图片资源**
- 触屏交互的核心底线：44px 点击区域 + hover 的替代方案 + 输入框字号 ≥ 16px
- 从 320px 到 1920px 的密码是：`clamp()` 做无缝缩放 + 媒体查询做布局突变
