# 01-浏览器架构与多进程模型

## 学习目标

- 理解浏览器多进程架构的组成及各进程职责
- 能用 Chrome 任务管理器观察浏览器内部进程
- 理解进程与线程的概念区别
- 明白浏览器为什么要设计成多进程，以及它解决了什么问题

---

## 内容讲解

### 1. 概念前置：进程 vs 线程

在你开始理解浏览器架构之前，必须先搞清楚两个被反复提及的概念。

**进程（Process）**：操作系统分配资源的最小单位。每个进程拥有独立的内存空间，进程之间不能直接访问彼此的数据。你可以把进程理解为「一个正在运行的程序实例」。

**线程（Thread）**：CPU 调度的最小单位。一个进程内可以包含多个线程，同一进程内的线程共享该进程的内存空间。

类比：一栋写字楼就是一个**进程**，楼里的每个工位和正在干活的人就是**线程**。同一栋楼里的人共用洗手间、茶水间（共享内存），但两栋不同写字楼里的人不能随意串门（进程隔离）。

> **关键结论**：进程之间天然隔离，一个进程挂了不会影响另一个；但同一进程内的线程共享内存，一个线程崩溃可能导致整个进程挂掉。

### 2. Chrome 多进程架构全景

打开 Chrome，你就启动了多个操作系统进程。Chrome 主要包含以下进程类型：

| 进程 | 职责 | 数量 |
|------|------|------|
| **浏览器主进程（Browser Process）** | 管理 Chrome 的 UI（地址栏、书签、前进后退按钮）、协调其他进程、处理网络请求和文件访问 | 1 个 |
| **渲染进程（Renderer Process）** | 负责解析 HTML、CSS、JS，将网页渲染出来。运行在**沙箱**中，权限受限 | 每个标签页 1 个（site isolation 下可能更多） |
| **GPU 进程** | 处理 GPU 相关任务（CSS 3D 变换、视频解码、Canvas 2D 加速） | 1 个 |
| **网络进程（Network Process）** | 专门处理网络请求（曾经由浏览器主进程负责，现在独立出来） | 1 个 |
| **插件进程（Plugin Process）** | 运行 Flash 等第三方插件（现在已随插件淘汰而淡出） | 每种插件 1 个 |

**动手验证**：打开 Chrome，按 `Shift + Esc` 打开 Chrome 任务管理器，你就能直观看到每个标签页对应一个独立的渲染进程。试试关闭某个标签页，对应的进程也会随之消失。

> **避坑提示**：你在 Chrome 地址栏输入的 URL、点击的按钮，最终由**浏览器主进程**发起调度——它通知网络进程下载资源，再把数据交给渲染进程去显示。不要以为「浏览器 = 渲染进程」。

### 3. 为什么必须是多进程？

假设浏览器只有一个进程，会发生什么灾难？

**场景 1：单页崩溃 → 整浏览器崩溃**
一个标签页里的 JS 死循环或内存泄漏，会拖垮整个浏览器。你打开 10 个标签页，其中一个挂了，全部陪葬。

**场景 2：安全噩梦**
同一个进程内的 JS 脚本可以访问任意内存。恶意网站通过缓冲区溢出等手段，能窃取你在其他标签页输入的信息（密码、银行卡号等）。

**多进程架构如何解决这些问题？**

```
┌──────────────────────────────────────────────────┐
│                  浏览器主进程                      │
│         (UI线程、存储线程、文件线程)                 │
└──────────┬──────────┬──────────┬─────────────────┘
           │          │          │
    ┌──────▼──┐  ┌────▼───┐  ┌──▼─────────┐
    │渲染进程1 │  │渲染进程2│  │   GPU进程   │
    │(tab A)  │  │(tab B) │  │             │
    └─────────┘  └────────┘  └─────────────┘
```

**隔离性**：每个标签页独立一个渲染进程，一个页面崩溃，只关掉对应进程，其他标签页不受影响。

**安全性**：渲染进程运行在**沙箱（Sandbox）**中，无法直接访问操作系统资源（文件系统、网络等），所有敏感操作必须通过浏览器主进程中转。即使恶意网站发现了 JS 引擎漏洞，由于沙箱限制，它也无法触及系统层面。

**释放内存快**：关闭标签页时，对应渲染进程被操作系统直接回收，不存在内存碎片长期驻留的问题。

### 4. Site Isolation（站点隔离）

Chrome 在 67 版本以后引入了站点隔离机制。即使两个 iframe 嵌入在同一个标签页中，如果它们来自不同域名，Chrome 也会为它们分配独立的渲染进程。

```
tab A (a.com)
  ├── 主文档 a.com        → 渲染进程 1
  ├── iframe b.com        → 渲染进程 2  (独立！)
  └── iframe c.com        → 渲染进程 3  (独立！)
```

**意义**：Spectre/Meltdown 这类 CPU 级漏洞让同一进程内的内存隔离形同虚设。Site Isolation 以进程为单位彻底隔离不同站点，从根本上堵死了这类跨站数据泄露的缝隙。

> **避坑提示**：Site Isolation 会显著增加内存占用。如果开发时发现 Chrome 吃内存特别多，不是 Chrome 的 bug，是它为安全性付出的代价。

### 5. 渲染进程内部的多线程

渲染进程本身也不是铁板一块，内部由多个线程协同工作：

| 线程 | 职责 |
|------|------|
| **主线程（Main Thread）** | 解析 HTML、构建 DOM、执行 JS、计算样式和布局。**JS 的单线程特性指的就是这个主线程** |
| **合成线程（Compositor Thread）** | 负责将图层合成为最终画面，可以在不阻塞主线程的情况下响应滚动和动画 |
| **光栅化线程（Raster Thread）** | 将矢量图形转换为位图像素 |
| **Worker 线程** | 处理 Web Worker 和 Service Worker 的任务，不阻塞主线程 |

**你熟悉的「JS 是单线程的」说的只是渲染进程中的主线程**，不是整个浏览器只有一个线程。

## 常见问题

**Q1：为什么 JS 设计成单线程的？**

A：JS 最初就是为了操作 DOM 而生的。如果多个线程同时修改同一个 DOM 节点（一个删、一个改样式），浏览器不知道该听谁的。单线程避免了并发操作的复杂性。但现代 Web Worker 允许你在后台线程中做纯计算，只是不能直接操作 DOM。

**Q2：多进程是不是浪费内存？**

A：确实更占内存，但换来的是稳定性和安全性。Chrome 团队也在不断优化：空闲标签页的渲染进程会被「冻结」，减少内存占用。对于设备内存有限的情况，Chrome 会合并部分渲染进程。

**Q3：iframe 中的页面和主页面是同一个进程吗？**

A：不一定。如果 iframe 和主页面同源（同协议、同域名、同端口），可能共享一个渲染进程。如果不同源且开启了 Site Isolation，iframe 会有自己的独立进程。

**Q4：插件进程现在还有吗？**

A：Chrome 早已停止支持 NPAPI 插件（2023 年全面移除），现在插件进程基本退出历史舞台。PDF 查看器等功能已内嵌到渲染进程中。

**Q5：进程之间怎么通信？**

A：通过 **IPC（Inter-Process Communication，进程间通信）** 机制。Chrome 主要使用 **Mojo** 框架。比如你在地址栏输入 URL，浏览器主进程通过 IPC 把请求发给网络进程，网络进程下载完数据后再通过 IPC 交还给渲染进程。

**Q6：「JS 单线程」和「Event Loop」是什么关系？**

A：JS 主线程上所有同步代码按顺序执行；异步任务（setTimeout、fetch、事件监听）由浏览器其他线程或进程处理，完成后将回调放入**任务队列**。主线程空闲时通过 Event Loop 机制从队列中取出回调执行。这就是「看似能并行，实则交替执行」的本质。

**Q7：为什么不把所有事情都放进 GPU 进程加速？**

A：GPU 擅长的是并行计算和图形渲染，但不擅长处理 DOM 结构的计算、JS 逻辑判断等顺序性任务。GPU 和 CPU 各有所长，互相配合。

## 实操作业

### 基础作业：观察进程

1. 打开 Chrome，按 `Shift + Esc` 打开任务管理器
2. 观察当前打开了哪些进程，每个进程占用多少内存和 CPU
3. 新开 3 个不同网站的标签页（如 bilibili.com、github.com、zhihu.com），观察进程数量变化
4. 关闭一个标签页，查看对应进程是否释放
5. 打开一个包含 iframe 跨域广告的页面，右键点击任务管理器中的网页标题，选择「按站点分组」，观察 Site Isolation 效果

### 进阶作业：理解隔离

1. 在 Chrome 地址栏输入 `chrome://process-internals/`，查看当前所有进程的详细信息，包括进程 ID、所属站点、沙箱状态
2. 写一个死循环的页面：新建 `loop.html`，内容为 `<script>while(true){}</script>`，用浏览器打开它
3. 在另一个标签页打开任意网站，验证是否仍然正常访问
4. 思考：如果你的 VSCode 插件导致编辑器卡死，它和浏览器的多进程架构有什么关系？

### 挑战作业：复现进程崩溃

1. 在 Chrome 地址栏输入 `chrome://crash` 让当前标签页崩溃
2. 观察其他标签页是否受影响
3. 打开 Chrome DevTools → 在 Console 中输入 `await fetch('chrome://crash')`，观察会发生什么
4. 阅读 Chrome 官方文档 [Process Model and Site Isolation](https://www.chromium.org/developers/design-documents/process-models/)（英文），总结 3 点收获

## 本节小结

- 浏览器采用多进程架构，核心包括浏览器主进程、渲染进程、GPU 进程和网络进程
- 每个标签页至少对应一个渲染进程，进程间通过沙箱隔离，一个标签页崩溃不影响其他
- Site Isolation 将不同站点的 iframe 也放入独立进程，防止 Spectre 类攻击
- JS 的单线程指的是渲染进程的主线程，渲染进程内部还有其他线程（合成线程、光栅化线程等）
- 多进程架构是浏览器在现代 Web 安全与稳定性需求下的必然选择
