## 内容讲解

### 1. 概念前置：进程 vs 线程

在你开始理解浏览器架构之前，必须先搞清楚两个被反复提及的概念。

**进程（Process）**：操作系统分配资源的最小单位。每个进程拥有独立的内存空间，进程之间不能直接访问彼此的数据。你可以把进程理解为「一个正在运行的程序实例」。

**线程（Thread）**：CPU 调度的最小单位。一个进程内可以包含多个线程，同一进程内的线程共享该进程的内存空间。

类比：一栋写字楼就是一个**进程**，楼里的每个工位和正在干活的人就是**线程**。同一栋楼里的人共用洗手间、茶水间（共享内存），但两栋不同写字楼里的人不能随意串门（进程隔离）。

> **关键结论**：进程通常拥有独立虚拟地址空间，也可显式使用共享内存；崩溃影响仍取决于资源和依赖关系。同一进程内线程共享地址空间，严重故障可能导致整个进程退出。

### 2. Chrome 多进程架构全景

打开 Chrome，你就启动了多个操作系统进程。Chrome 主要包含以下进程类型：

| 进程 | 职责 | 数量 |
|------|------|------|
| **浏览器主进程（Browser Process）** | 管理 Chrome 的 UI（地址栏、书签、前进后退按钮）、协调其他进程、处理网络请求和文件访问 | 1 个 |
| **渲染进程（Renderer Process）** | 负责解析 HTML、CSS、JS，将网页渲染出来。运行在**沙箱**中，权限受限 | 按站点实例和进程策略分配，可被多个标签页共享，也可让一个标签页使用多个 |
| **GPU 进程** | 处理 GPU 相关任务（CSS 3D 变换、视频解码、Canvas 2D 加速） | 1 个 |
| **网络进程（Network Process）** | 专门处理网络请求（曾经由浏览器主进程负责，现在独立出来） | 1 个 |
| **工具进程（Utility Process）** | 承载音频、存储、解码等需要隔离的服务，具体拆分随平台和版本变化 | 0 个或多个 |

**动手验证**：打开 Chrome，按 `Shift + Esc` 打开任务管理器，比较标签页、子框架与进程的关系。不要期待“一标签一进程”严格成立：同源页面可能共享进程，跨站 iframe 可能占用额外渲染进程，进程数量还会受设备资源和浏览器策略影响。

> **避坑提示**：你在 Chrome 地址栏输入的 URL、点击的按钮，最终由**浏览器主进程**发起调度——它通知网络进程下载资源，再把数据交给渲染进程去显示。不要以为「浏览器 = 渲染进程」。

### 3. 为什么必须是多进程？

假设浏览器只有一个进程，会发生什么灾难？

**场景 1：单页崩溃 → 整浏览器崩溃**
一个标签页里的 JS 死循环或内存泄漏，会拖垮整个浏览器。你打开 10 个标签页，其中一个挂了，全部陪葬。

**场景 2：安全噩梦**
正常 JavaScript 不能直接读取任意内存；但引擎内存安全漏洞或侧信道可能削弱同一进程内的隔离。不同站点共享地址空间时，潜在暴露范围更大。

**多进程架构如何解决这些问题？**

```
┌──────────────────────────────────────────────────┐
│                  浏览器主进程                      │
│         (UI线程、存储线程、文件线程)                 │
└──────────┬──────────┬──────────┬─────────────────┘
           │          │          │
    ┌──────▼──┐  ┌────▼───┐  ┌──▼─────────┐
    │渲染进程1 │  │渲染进程2│  │   GPU进程   │
    │(tab A)  │  │(tab B) │  │             │
    └─────────┘  └────────┘  └─────────────┘
```

**隔离性**：不同站点通常被分配到不同渲染进程。渲染进程崩溃时，受该进程承载的页面或子框架会失败，而其他进程中的页面通常仍能工作；共享同一进程的页面可能一起受影响。

**安全性**：渲染进程运行在**沙箱（Sandbox）**中，对文件系统、网络服务等敏感能力的访问受到限制，需要通过浏览器进程或受控服务中转。沙箱用于降低单个渲染器漏洞的影响，但不能保证攻击“绝不触及系统”；现实攻击可能组合渲染器漏洞与沙箱逃逸漏洞。

**内存管理更可控**：当某个渲染进程不再承载页面时，操作系统可以整体回收它的地址空间。但标签页关闭后进程也可能被复用或缓存，不能据此断言内存会立即全部释放。

### 4. Site Isolation（站点隔离）

Chrome 67 起默认启用更严格的 Site Isolation。跨站 iframe 通常通过 OOPIF（Out-of-Process iframe）进入不同渲染进程；这里按“站点”而不是简单的“域名字符串”划分，实际分配仍受浏览器进程模型影响。

```
tab A (a.com)
  ├── 主文档 a.com        → 渲染进程 1
  ├── iframe b.com        → 渲染进程 2  (独立！)
  └── iframe c.com        → 渲染进程 3  (独立！)
```

**意义**：Spectre 类侧信道攻击削弱了同一地址空间内的数据边界。Site Isolation 把不同站点放入不同进程和地址空间，显著减少跨站数据暴露面，但它是纵深防御的一层，不是对所有跨站攻击的绝对保证。

> **避坑提示**：Site Isolation 会增加进程与内存成本，但内存增长也可能来自页面泄漏、缓存或扩展。先测量分布，不能仅凭架构排除故障。

### 5. 渲染进程内部的多线程

渲染进程本身也不是铁板一块，内部由多个线程协同工作：

| 线程 | 职责 |
|------|------|
| **主线程（Main Thread）** | 解析 HTML、构建 DOM、执行 JS、计算样式和布局。**JS 的单线程特性指的就是这个主线程** |
| **合成线程（Compositor Thread）** | 负责将图层合成为最终画面，可以在不阻塞主线程的情况下响应滚动和动画 |
| **光栅化线程（Raster Thread）** | 将矢量图形转换为位图像素 |
| **Worker 线程** | 处理 Web Worker 和 Service Worker 的任务，不阻塞主线程 |

“JS 单线程”通常指同一个 JavaScript agent 内的代码按单一执行线程运行，不等于整个浏览器只有一个线程。Worker 拥有独立 agent，可以与页面主线程并行执行 JavaScript。

## 常见问题

**Q1：为什么 JS 设计成单线程的？**

A：JS 最初就是为了操作 DOM 而生的。如果多个线程同时修改同一个 DOM 节点（一个删、一个改样式），浏览器不知道该听谁的。单线程避免了并发操作的复杂性。但现代 Web Worker 允许你在后台线程中做纯计算，只是不能直接操作 DOM。

**Q2：多进程是不是浪费内存？**

A：多进程有资源成本，也带来隔离。冻结页面主要减少执行，丢弃页面才可能回收更多资源；具体复用和回收策略取决于平台、版本和资源约束。

**Q3：iframe 中的页面和主页面是同一个进程吗？**

A：不一定。同源页面可能共享进程，跨站 iframe 通常可使用 OOPIF。同站不同源不等于一定分配独立进程，需按站点与隔离策略判断。

**Q4：为什么这里不再把插件进程列为核心进程？**

A：NPAPI 和 Flash 插件已经退出现代 Chrome。当前 Chromium 更常把音频、存储、解码等能力放入沙箱化 Utility Process；PDF、扩展和媒体能力的具体进程归属会随版本和平台变化，不应沿用旧版“每种插件一个进程”的模型。

**Q5：进程之间怎么通信？**

A：通过 **IPC（Inter-Process Communication，进程间通信）** 机制。Chrome 主要使用 **Mojo** 框架。比如你在地址栏输入 URL，浏览器主进程通过 IPC 把请求发给网络进程，网络进程下载完数据后再通过 IPC 交还给渲染进程。

**Q6：「JS 单线程」和「Event Loop」是什么关系？**

A：JS 主线程上所有同步代码按顺序执行；异步任务（setTimeout、fetch、事件监听）由浏览器其他线程或进程处理，完成后将回调放入**任务队列**。主线程空闲时通过 Event Loop 机制从队列中取出回调执行。这就是「看似能并行，实则交替执行」的本质。

**Q7：为什么不把所有事情都放进 GPU 进程加速？**

A：GPU 擅长的是并行计算和图形渲染，但不擅长处理 DOM 结构的计算、JS 逻辑判断等顺序性任务。GPU 和 CPU 各有所长，互相配合。

## 实操作业

### 基础作业：观察进程

1. 打开 Chrome，按 `Shift + Esc` 打开任务管理器
2. 观察当前打开了哪些进程，每个进程占用多少内存和 CPU
3. 新开 3 个不同网站的标签页（如 bilibili.com、github.com、zhihu.com），观察进程数量变化
4. 关闭一个标签页，查看对应进程是否释放
5. 打开一个包含 iframe 跨域广告的页面，右键点击任务管理器中的网页标题，选择「按站点分组」，观察 Site Isolation 效果

### 进阶作业：理解隔离

1. 在 Chrome 地址栏输入 `chrome://process-internals/`，查看当前所有进程的详细信息，包括进程 ID、所属站点、沙箱状态
2. 在独立测试资料创建有界阻塞页面：执行约 500ms 的循环，观察主线程阻塞后恢复
3. 在另一个标签页打开任意网站，验证是否仍然正常访问
4. 思考：如果你的 VSCode 插件导致编辑器卡死，它和浏览器的多进程架构有什么关系？

### 挑战作业：复现进程崩溃

1. 在独立测试浏览器中用任务管理器停止一个仅承载虚构练习页的渲染任务
2. 观察哪些页面或子框架受影响，并对照其进程归属
3. 恢复页面，记录共享进程、独立进程与恢复行为
4. 阅读 Chrome 官方文档 [Process Model and Site Isolation](https://www.chromium.org/developers/design-documents/process-models/)（英文），总结 3 点收获

### 作业参考与验收

- **基础**：记录标签、frame、PID 和进程类型，而不是把标签数当进程数。关闭标签后可能仍有共享进程；依据 PID 与站点归属解释观察值。
- **进阶**：500ms 有界阻塞后页面应恢复；比较另一页的响应并记录是否共享进程。扩展宿主、UI 与渲染进程的隔离粒度不同，不能据此保证编辑器绝不卡死。
- **挑战**：只停止独立测试资料内的练习渲染任务；列出受影响页面与共同 PID。重新加载恢复，结合站点隔离解释结果，不终止日常浏览器进程。

## 本节小结

- 浏览器采用多进程架构，核心包括浏览器主进程、渲染进程、GPU 进程和网络进程
- 标签页与进程不是一一对应；崩溃影响按实际共享进程和依赖判断
- Site Isolation 减少跨站共享地址空间，是对 Spectre 等风险的纵深控制
- JS 单线程通常指一个 agent 的执行，Worker 有独立 agent；浏览器整体包含多个线程与进程
- 多进程架构是浏览器在现代 Web 安全与稳定性需求下的必然选择

官方参考：[Chromium Multi-process Architecture](https://www.chromium.org/developers/design-documents/multi-process-architecture/) · [Site Isolation](https://www.chromium.org/developers/design-documents/site-isolation/)
