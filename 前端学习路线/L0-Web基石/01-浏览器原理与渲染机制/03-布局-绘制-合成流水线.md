## 学习目标

- 理解浏览器渲染管线的三个核心阶段：Layout → Paint → Composite
- 掌握盒模型、文档流在布局阶段的计算逻辑
- 理解图层合成的概念和 GPU 加速的原理
- 知道 `will-change` 和 `transform` 为什么能实现高性能动画

---

## 内容讲解

### 1. 渲染管线的全景图

一旦渲染树（Render Tree）构建完成，浏览器进入「画出来」的阶段。这个阶段由三个步骤组成：

```
渲染树 ──► Layout（布局）──► Paint（绘制）──► Composite（合成）──► 屏幕像素
              │                  │                  │
         计算元素位置大小      生成绘制指令        将图层合并输出
              │                  │                  │
         也叫「Reflow」      也叫「Rasterize」    GPU 负责
```

这三个步骤不一定是线性的——后续章节会讲，某一步可以跳过，也可以局部重做。下面逐一展开。

### 2. Layout（布局 / 回流）阶段

布局阶段的核心任务：**给渲染树中每个节点计算它在屏幕上的精确位置和尺寸。**

#### 2.1 盒模型计算

每个可见的 DOM 元素在布局阶段被建模为一个**矩形盒子（CSS Box Model）**：

```
    ┌──────── margin-top ────────┐
    │  ┌──── border-top ──────┐  │
    │  │ ┌── padding-top ──┐  │  │
    │  │ │                 │  │  │
    │  │ │    content      │  │  │
    │  │ │    (width×height)   │  │  │
    │  │ │                 │  │  │
    │  │ └── padding-bottom┘  │  │
    │  └──── border-bottom ────┘  │
    └──────── margin-bottom ──────┘
```

布局阶段对每个盒子的计算包括：
- 内容区尺寸（`width` / `height`）
- 内边距（`padding`）
- 边框（`border`）
- 外边距（`margin`）
- 相对父元素的位置（x, y 坐标）

**`box-sizing` 的影响**：`content-box`（默认）下，`width` 只指内容区；`border-box` 下，`width` 包含 content + padding + border。这个选择直接改变布局阶段的尺寸计算方式。

```css
/* content-box：元素实际占用宽度 = 200 + 20*2 + 5*2 = 250px */
.box-content {
  box-sizing: content-box;
  width: 200px;
  padding: 20px;
  border: 5px solid #333;
}

/* border-box：元素实际占用宽度 = 200px（内容区自动缩小为 150px） */
.box-border {
  box-sizing: border-box;
  width: 200px;
  padding: 20px;
  border: 5px solid #333;
}
```

> **避坑提示**：很多 CSS 框架（如 Tailwind）默认使用 `border-box`，因为直觉上「我设置 width: 200px，它就应该是 200px 宽」。如果你在某个项目中混用两种盒模型，调试布局问题会非常痛苦。

#### 2.2 文档流（Normal Flow）

布局阶段按照**文档流**规则将盒子排列到页面上：

**块级元素（Block）**：独占一行，从上到下堆叠。`<div>`、`<p>`、`<h1>` 等默认是块级。

**行内元素（Inline）**：在一行内从左到右排列，放不下时换行。`<span>`、`<a>`、`<strong>` 等默认是行内。

**脱离文档流**：`position: absolute`、`position: fixed`、`float` 的元素不参与正常的块级/行内排列。它们被提升到更高的渲染层级（这也是它们可能触发新图层的原因）。

```
正常文档流：
┌──────────────────┐
│  <div> (块级)     │  ← 占满整行
├──────────────────┤
│  <div> (块级)     │  ← 下一行
├──────────────────┤
│ <span> <span> <span>  │  ← 行内，左右排列
└──────────────────┘
```

#### 2.3 布局是一个递归过程

浏览器从渲染树的根节点开始，递归遍历每个节点：

1. 父元素先确定自己的尺寸和位置
2. 再根据子元素的样式（`width`、`height`、`margin`、`padding`、`position` 等）计算每个子元素的尺寸和位置
3. 父元素的最终高度通常由子元素「撑开」

**这就带来一个重要推论**：修改一个元素的几何属性（宽、高、边距、定位），可能导致父元素和后续兄弟元素都需要重新布局——这正是「重排代价高」的根本原因。

### 3. Paint（绘制）阶段

布局完成，每个元素的位置和大小都确定了。绘制阶段做一件事：**生成绘制指令（Paint Records）**。

绘制指令类似于一份「绘画说明书」：先在 (100, 200) 位置画一个红色矩形，再在 (110, 210) 位置写一段 14px 的黑色文字……

**绘制顺序**：浏览器按照**层叠上下文（Stacking Context）**的规则决定绘制顺序，大致是：

1. 背景色（background-color）
2. 背景图（background-image）
3. 边框（border）
4. 子元素（按文档流 + z-index 决定前后）
5. 轮廓（outline）——在边框之外，不占布局空间

> **关键认知**：绘制阶段不产生位图像素，只产生**指令**。真正的「光栅化」（将指令转为像素）发生在后续的合成阶段。

### 4. Composite（合成）阶段

这是渲染管线中最容易被忽视但性能影响最大的阶段。

#### 4.1 图层（Layer）的概念

浏览器不一定把所有内容画在一张「画布」上。它会根据特定条件将页面内容划分到不同的**图层（Layer）**中：

**独立的图层可以分别光栅化，最后由合成线程合并输出到屏幕**——这整个过程称为「合成」。

默认每个渲染进程有一个包含一切的根图层。满足以下条件的元素会被提升为独立图层：

- 根元素（`<html>`）
- `position: fixed` 或 `position: sticky`
- 带有 3D transform 的元素（`transform: translateZ(0)`）
- 带有 `will-change: transform` 的元素
- `<video>`、`<canvas>`、`<iframe>` 元素
- 对 opacity/transform 做过 CSS 动画或过渡的元素
- `overflow: scroll` 的元素（部分浏览器）

**如何查看图层**：Chrome DevTools → 右上角三个点 → More tools → Layers，可以看到当前页面的图层分解图。

#### 4.2 GPU 加速的本质

当图层独立后：

1. 图层的内容在**光栅化线程**中被转为位图纹理（texture）
2. 位图纹理上传到 **GPU 显存**
3. **合成线程**直接操作 GPU 对图层做位移（translate）、缩放（scale）、旋转（rotate）、透明度（opacity）变换
4. **整个过程不经过主线程，不触发 Layout 和 Paint！**

```
主线程                        合成线程 + GPU
───────                      ───────────────
Layout → Paint → 生成位图 → 上传纹理 → 变换 → 合成输出
                                    ↑
                              transform / opacity
                              在这里操作，纯 GPU
```

**类比**：你可以把每个图层想象成一张独立的透明胶片。合成线程拿着这些胶片在 GPU 里挪来挪去、调透明度、缩放旋转，然后把它们摞在一起拍张照。挪动胶片本身不需要重新画图——这就是 `transform` 动画为什么能做到 60fps 丝滑。

#### 4.3 will-change 的正确用法

`will-change` 告诉浏览器：「这个元素即将发生某种变化，请提前优化」。

```css
/* ✅ 正确：动画开始前设置，动画结束后移除 */
.animate-box {
  will-change: transform;
}
.animate-box.animating {
  /* 实际动画在此触发 */
  transition: transform 0.3s;
}
```

```css
/* ❌ 错误：永远不用的 will-change 是纯浪费 */
.everything {
  will-change: transform, opacity, left, top;
  /* 每个元素都被提升为独立图层，GPU 显存爆炸 */
}
```

**will-change 的本质代价**：每个独立图层都需要 GPU 显存来存储纹理。图层太多 → 显存不足 → 性能反而下降。

> **避坑提示**：不要从 `/` 选择器开始加 `will-change`。只在确定会发生动画的元素上使用，且动画结束后通过 JS 移除该属性。如果你的页面出现了「整个页面模糊」「元素边缘有锯齿」的问题，大概率是 GPU 纹理内存超限，图层被降级软件渲染了。

### 5. 渲染管线的三种更新路径

并非每次样式变化都要走完整的三阶段。根据修改的属性不同，触发的路径也不同：

| 修改的属性 | 触发阶段 | 性能代价 |
|-----------|---------|---------|
| `width`、`height`、`padding`、`margin`、`left`、`top`、`font-size` | Layout → Paint → Composite | 最高 |
| `color`、`background`、`box-shadow`、`border-color` | Paint → Composite（跳过 Layout） | 中等 |
| `transform`、`opacity`、`cursor` | Composite（跳过 Layout 和 Paint） | 最低 |

```
修改 width               修改 color              修改 transform
──────────              ──────────              ─────────────
Layout ────┐            Layout (跳过)           Layout (跳过)
    │      │                │                       │
   ╳       │               ╳                       ╳
    │      │                │                       │
Paint ────┤            Paint ────┐              Paint (跳过)
    │      │                │      │                 │
   ╳       │               ╳      │                ╳
    │      │                │      │                 │
Composite ┘            Composite ─┘              Composite ──► 屏幕
```

理解这三条路径，你在做动画和交互优化时就知道该用哪些 CSS 属性了。核心原则：**尽量走 Composite-only 路径**。

## 常见问题

**Q1：Layout 和 Reflow 是一回事吗？**

A：是一回事。Layout 是首次渲染时的布局计算，Reflow（回流/重排）是指页面已经显示后，由于属性变化导致需要**重新**布局。本质上执行的代码路径相同。

**Q2：为什么 `z-index` 不是越大越靠前？**

A：`z-index` 只在同一个**层叠上下文**（Stacking Context）内有效。一个 `z-index: 1` 的元素如果位于更高层级的层叠上下文中，可能覆盖 `z-index: 9999` 的元素。层叠上下文的层级由多种因素决定（`position`、`opacity < 1`、`transform` 非 none 等）。

**Q3：`transform: translateX(100px)` 和 `left: 100px` 在动画性能上有什么区别？**

A：定位元素的 `left` 变化通常需要重新布局并可能重绘；`transform` 不改变文档布局，已有合成图层时常可只更新合成属性。但浏览器是否提升图层、是否需要重新光栅化以及最终帧率取决于元素内容和设备，不能由属性名保证。用 Performance 和 Layers 面板比较目标页面。

**Q4：图层越多越好吗？**

A：不是。每个图层都可能增加纹理内存、光栅化和合成成本，浏览器还会根据设备资源与内部策略调整图层。不存在适用于所有页面的固定数量上限；只在性能证据表明有收益时提升图层，并观察内存、帧时间和图层边界。

**Q5：`opacity: 0` 的元素还在渲染树里吗？**

A：它仍在布局树中，也可能继续参与命中测试和可访问性语义；浏览器可以跳过不可见像素的实际绘制。把 `opacity` 从 0 动画到 1 通常比切换 `display` 更容易优化，但是否只发生合成仍取决于图层状态，且隐藏交互元素时还要处理焦点和点击。

**Q6：`will-change: transform` 什么时候应该被移除？**

A：动画结束后立即移除。如果元素持续存在动画（如无限旋转的 loading 图标），可以保留。移除后，Chrome 会将图层回收，释放显存。

**Q7：`requestAnimationFrame` 运行在管线中的哪个位置？**

A：在 Layout 之前。浏览器每帧的节奏大致是：`rAF 回调 → 样式计算 → Layout → Paint → Composite`。在 rAF 中批量修改样式，能让浏览器在同一个渲染帧内完成所有变更，避免多次重排。

## 实操作业

### 基础作业：观察图层

1. 打开一个复杂页面（如 B 站首页），Chrome DevTools → Layers 面板
2. 找到至少 3 个独立图层，记录每个图层被提升的原因（面板会显示「Compositing Reasons」）
3. 在页面中找一个使用了 `position: fixed` 的导航栏，确认它是否独立图层
4. 禁用/启用 Layers 面板中的「Paints」复选框，观察不同图层的绘制区域（红色高亮）

### 进阶作业：对比动画性能

```html
<!-- 创建两个动画对比页面 -->
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8">
  <style>
    .box { width: 100px; height: 100px; margin: 10px; }
    /* 用 left 做动画 —— 触发 Layout */
    .bad {
      background: red;
      position: absolute;
      animation: move-left 2s infinite;
    }
    /* 用 transform 做动画 —— 只触发 Composite */
    .good {
      background: blue;
      position: absolute; top: 150px;
      animation: move-transform 2s infinite;
    }
    @keyframes move-left {
      0%, 100% { left: 0; }
      50% { left: 300px; }
    }
    @keyframes move-transform {
      0%, 100% { transform: translateX(0); }
      50% { transform: translateX(300px); }
    }
  </style>
</head>
<body>
  <div class="box bad"></div>
  <div class="box good"></div>
</body>
</html>
```

用 Performance 面板分别录制红色和蓝色方块动画，对比：
- 每帧的耗时
- 是否触发了 Layout/Paint
- 帧率（FPS）差异

### 挑战作业：手动构建合成动画

1. 创建一个包含 50 个绝对定位元素（模拟粒子效果）的页面
2. 第一版使用 `left` + `top` 做位移动画
3. 第二版改为 `transform: translate()` + `will-change`
4. 用 Performance 面板对比两版的 FPS 和 Layout 耗时
5. 在移动端模式（Device Toolbar → 切换为低配手机）下再次对比
6. 写一段 200 字的优化总结，说明为什么 `transform` 是最推荐的动画属性

### 作业参考与验收

- **基础**：记录 Layers 中实际合成原因、大小与绘制情况；fixed 不保证总被提升。合成层与 CSS 层叠上下文不是同一个概念，不能用其中一个代替另一个的证据。
- **进阶**：相同元素数和动画时长分别测 left 与 transform；预期前者更易触发布局。以 trace 的 Layout/Paint/Composite 为准，首次栅格化仍可能绘制。
- **挑战**：从少量粒子开始加到 50 个；对比 frame、布局耗时和图层内存。will-change 只在需要时启用，设备模拟不等于真机性能；不预设 transform 版必然最优。

## 本节小结

- 渲染管线分为 Layout（位置尺寸计算）→ Paint（生成绘制指令）→ Composite（图层合并输出）三个阶段
- Layout 阶段递归计算每个元素的盒模型（content + padding + border + margin）和文档流位置
- 独立图层允许合成线程直接在 GPU 中操作，跳过主线程的 Layout 和 Paint，实现高性能动画
- `transform` 和 `opacity` 的修改只触发 Composite，是动画性能最优解；`left`、`width` 等属性触发全流程，代价高昂
- `will-change` 是性能优化利器，但滥用会导致 GPU 显存溢出，反而降低性能
