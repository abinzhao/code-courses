# 04-重排重绘与性能影响

## 学习目标

- 掌握重排（Reflow）和重绘（Repaint）的触发条件与性能代价
- 能区分哪些操作只触发合成、哪些会触发 Layout
- 学会批量 DOM 修改的最佳实践（requestAnimationFrame、DocumentFragment）
- 能使用 Chrome Performance 面板分析页面性能问题

---

## 内容讲解

### 1. 什么是重排（Reflow）？

重排 = 浏览器重新计算元素的几何属性（位置和尺寸），并更新渲染树中受影响的部分。

**触发条件**：任何导致元素几何属性变化的操作都可能引发重排。常见的有：

**DOM 操作**：
- 添加、删除、移动 DOM 节点
- 修改元素的 `width`、`height`、`padding`、`margin`、`border`
- 修改 `position`、`top`、`left`、`right`、`bottom`
- 修改 `display`（none ↔ block 等切换）

**内容变化**：
- 修改文本内容（可能改变元素高度）
- 修改 `font-size`、`font-family`、`line-height`
- 图片加载完成（尺寸确定可能撑开容器）

**窗口变化**：
- 浏览器窗口 resize
- 移动设备横竖屏切换

**读取特定属性（强制同步布局）**：
- `offsetTop`、`offsetLeft`、`offsetWidth`、`offsetHeight`
- `scrollTop`、`scrollLeft`、`scrollWidth`、`scrollHeight`
- `clientTop`、`clientLeft`、`clientWidth`、`clientHeight`
- `getComputedStyle()`
- `getBoundingClientRect()`

> **为什么读取这些属性也会触发重排？** 因为浏览器采用**惰性计算**：修改样式后，Layout 不会立即执行，而是排队等待下一帧。但当你读取这些属性时，浏览器必须立刻给你一个**准确的、最新的**值，所以被迫同步执行 Layout——这称为**强制同步布局（Forced Synchronous Layout）**。

### 2. 什么是重绘（Repaint）？

重绘 = 元素的几何属性没变，但视觉外观变了，浏览器重画这个元素。

**触发条件**：
- 修改 `color`、`background-color`
- 修改 `box-shadow`、`text-shadow`
- 修改 `border-color`、`outline-color`
- 修改 `visibility`（hidden ↔ visible）

**重排一定伴随重绘，重绘不一定伴随重排。** 因为重排要重新计算布局，布局变了自然要重新画；但只改颜色时，位置没变，只需要重画。

### 3. 复合（Composite）——零代价的更新

修改 `transform` 和 `opacity` 时，如果目标元素在独立图层上，浏览器只需要合成线程操作 GPU 即可，**主线程完全不参与**。

```
                     主线程          合成线程(CPU)      GPU
修改 width     →   Layout → Paint → 光栅化 → 上传纹理 → 合成 → 屏幕
修改 color     →   (跳过L)→ Paint → 光栅化 → 上传纹理 → 合成 → 屏幕
修改 transform →   (全跳过) → 跳过 → (已有纹理) → 直接变换 → 屏幕
```

**永远优先使用 `transform` 和 `opacity` 做动画和过渡**，这是现代前端性能优化的第一原则。

### 4. 批量 DOM 修改的最佳实践

初学者写 JS 时很容易写出这种代码：

```javascript
// ❌ 糟糕的写法：每次循环都触发重排
for (let i = 0; i < 1000; i++) {
  const div = document.createElement('div');
  div.textContent = `第 ${i} 个元素`;
  document.body.appendChild(div);  // 每次 append 都可能导致重排
}
```

优化思路很简单：**把多次写操作合并，让浏览器在一帧内完成**。

#### 方案 1：DocumentFragment（推荐）

```javascript
// ✅ 使用 DocumentFragment 批量插入
// DocumentFragment 是轻量级的「虚拟容器」，它存在于内存中，不属于 DOM 树
// 对它做任何操作都不会触发重排！只在最后 append 到 body 时才触发一次
const fragment = document.createDocumentFragment();

for (let i = 0; i < 1000; i++) {
  const div = document.createElement('div');
  div.textContent = `第 ${i} 个元素`;
  div.style.padding = '8px';
  div.style.borderBottom = '1px solid #eee';
  fragment.appendChild(div);  // 不会触发重排，fragment 不在 DOM 中
}

document.body.appendChild(fragment);  // 一次性插入，只触发 1 次重排
```

#### 方案 2：先隐藏，再操作，再显示

```javascript
// ✅ 操作前将元素脱离渲染树，操作完再放回去
const container = document.getElementById('list');

container.style.display = 'none';  // 脱离渲染树，后续操作不触发重排

// 大量 DOM 操作（不会触发重排，因为 container 不在渲染树里）
for (let i = 0; i < 1000; i++) {
  const item = document.createElement('li');
  item.textContent = `Item ${i}`;
  container.appendChild(item);
}

container.style.display = 'block';  // 回到渲染树，只触发 1 次重排
```

#### 方案 3：cloneNode（适合复杂模板）

```javascript
// ✅ 克隆模版 → 修改 → 替换，只在替换时触发一次重排
const template = document.getElementById('template');
const clone = template.content.cloneNode(true);
// clone 不在 DOM 中，修改它不触发重排
clone.querySelector('.title').textContent = '新标题';
clone.querySelector('.desc').textContent = '新描述';
document.body.appendChild(clone);  // 触发布局
```

#### 方案 4：读写分离（避免强制同步布局）

```javascript
// ❌ 糟糕：写入 → 读取 → 再写入，触发强制同步布局
divs.forEach((div, i) => {
  div.style.width = `${i * 10}px`;      // 写（排队）
  const width = div.offsetWidth;         // 读（强制同步布局！）
  div.style.height = `${width}px`;       // 又写
});

// ✅ 好：先全部读完，再全部写
// 第一步：批量读（触发一次 Layout，拿到所有初始值）
const widths = divs.map(div => div.offsetWidth);

// 第二步：批量写（浏览器在下一帧统一 Layout）
divs.forEach((div, i) => {
  div.style.width = `${i * 10}px`;
  div.style.height = `${widths[i]}px`;   // 用读阶段保存的值，不触发强制同步布局
});
```

> **避坑提示**：在循环中混用读写是最常见的性能杀手之一。如果你在 Chrome Performance 面板中看到大量紫色标记（Layout），大概率是强制同步布局在作祟。

### 5. requestAnimationFrame（rAF）

`requestAnimationFrame` 是浏览器专门为动画和视觉更新提供的高精度回调机制。

```javascript
// ❌ 使用 setInterval 做动画 —— 不可靠
// 问题 1：setInterval 不关心屏幕刷新率（60Hz → 16.6ms 一帧）
// 问题 2：如果回调在帧中间执行，触发的变更可能不会在这一帧渲染，造成掉帧
setInterval(() => {
  box.style.left = position + 'px';
  position += 1;
}, 16);  // 人为指定的 16ms，不准

// ✅ 使用 requestAnimationFrame —— 浏览器自动对齐刷新率
function animate() {
  box.style.transform = `translateX(${position}px)`;
  position += 1;
  requestAnimationFrame(animate);  // 每帧执行一次
}
requestAnimationFrame(animate);
```

**rAF 的三大优势**：
1. **对齐刷新率**：浏览器保证在每帧绘制前执行 rAF 回调，你正好拿到了 16.6ms 的预算来更新画面
2. **自动节流**：标签页在后台时，rAF 自动暂停，不浪费 CPU
3. **合并更新**：一帧内的多次 rAF 回调中的样式修改，浏览器会合并为一次 Layout 和 Paint

**rAF 的最佳搭配**：在 rAF 中集中做样式修改，让浏览器在一个渲染帧内消化所有变更。

```javascript
// ✅ 批量 DOM 更新的标准模式
function batchUpdate(updates) {
  requestAnimationFrame(() => {
    // 在同一个 rAF 回调中集中修改
    updates.forEach(({ el, prop, value }) => {
      el.style[prop] = value;
    });
    // 浏览器在 rAF 之后统一 Layout → Paint，只触发一次重排
  });
}
```

### 6. Performance 面板分析实战

Chrome DevTools 的 Performance 面板是诊断渲染性能的利器。下面是一个标准分析流程：

**第一步：打开面板**

`F12` 打开 DevTools → 切换到 `Performance` 标签 → 左上角点击录制按钮（●）

**第二步：录制**

在页面上触发表现卡顿的操作（如滚动列表、拖拽元素、播放动画），然后点击 Stop。

**第三步：解读火焰图**

录制结果的关键区域：

```
FPS  ━━━━ 绿色=60帧  (绿色越高越好)
CPU  ━━━━ 各种颜色=不同类型工作
NET  ━━━━ 蓝色=网络请求
────────────────────────────────────────
         Main (主线程火焰图)
  ┌─────────────────────────────────┐
  │ 紫色 = 样式计算+布局              │  ← 越多越卡
  │ 绿色 = 绘制                      │  ← 多也不好
  │ 黄色 = JS 执行                   │
  │ 灰色 = 其他（GC、空闲等）         │
  └─────────────────────────────────┘
```

**重点关注**：
- **大量紫色块**：强制同步布局（Forced Reflow）。展开后通常能看到 `Layout` 字样，点击可跳转到触发代码
- **FPS 红色区域**：帧率低于 60，可能是长任务阻塞
- **右上角红色三角**：浏览器标记的性能问题，点击查看详情

**第四步：实战排查示例**

```html
<!-- 创建一个明显有性能问题的页面用于练习 -->
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8">
  <style>
    .box {
      width: 20px; height: 20px;
      background: #3498db;
      position: absolute;
      border-radius: 50%;
    }
  </style>
</head>
<body>
  <button id="btnBad">糟糕的动画（left+强制同步布局）</button>
  <button id="btnGood">好的动画（transform）</button>
  <div id="container"></div>
  
  <script>
    // 创建 100 个元素
    for (let i = 0; i < 100; i++) {
      const div = document.createElement('div');
      div.className = 'box';
      div.style.top = `${Math.random() * 500}px`;
      div.style.left = `${Math.random() * 500}px`;
      document.getElementById('container').appendChild(div);
    }
    
    const boxes = document.querySelectorAll('.box');
    
    // ❌ 糟糕的动画：left + 强制同步布局
    document.getElementById('btnBad').onclick = function () {
      function animateBad() {
        boxes.forEach(box => {
          const currentLeft = parseFloat(box.style.left); // 读（强制同步布局）
          box.style.left = `${currentLeft + 1}px`;          // 写（触发重排）
        });
        requestAnimationFrame(animateBad);
      }
      requestAnimationFrame(animateBad);
    };
    
    // ✅ 好的动画：transform，只触发 Composite
    document.getElementById('btnGood').onclick = function () {
      let x = 0;
      function animateGood() {
        x += 1;
        boxes.forEach(box => {
          box.style.transform = `translateX(${x}px)`;
        });
        requestAnimationFrame(animateGood);
      }
      requestAnimationFrame(animateGood);
    };
  </script>
</body>
</html>
```

用 Performance 面板分别录制按钮「糟糕的动画」和「好的动画」的 3 秒运行情况，你会看到：

- 「糟糕的动画」：主线程火焰图中大量紫色 Layout 块，帧率可能跌到 20fps 以下
- 「好的动画」：主线程几乎空闲，帧率稳定在 60fps

**这就是理解渲染原理在实战中的直接价值。**

### 7. 实战性能检查清单

在日常开发中，如果你遇到页面卡顿，按以下顺序排查：

1. **动画是否用了 `left` / `top` / `width`？** → 换成 `transform`
2. **是否有读写混用？** → 搜索 `.offset`、`.getBoundingClientRect()` 附近是否有样式修改
3. **是否有大量 DOM 插入？** → 改用 DocumentFragment
4. **是否有频繁的 `getComputedStyle()` 调用？** → 缓存结果
5. **是否有第三方脚本在轮询布局属性？** → Performance 面板中定位来源
6. **是否有未销毁的 setInterval/动画？** → 检查组件卸载时是否清理

## 常见问题

**Q1：`display: none` 和 `visibility: hidden` 在性能上有什么区别？**

A：修改 `display: none` 触发重排（元素离开渲染树，周围元素需要重新排列）。修改 `visibility: hidden` 可能只触发重绘（元素位置不变，只是透明）。如果元素需要频繁切换显示/隐藏，用 `visibility` 或 `opacity` 性能更好。

**Q2：`requestAnimationFrame` 和 `setTimeout(fn, 0)` 哪个先执行？**

A：`requestAnimationFrame` 在渲染帧开始前执行；`setTimeout(fn, 0)` 的时机取决于任务队列，可能在任意时刻。前者稳定在每个 ~16.6ms 的帧边界执行，后者不保证。做视觉更新必须用 rAF。

**Q3：CSS Transition 和 JS 动画（rAF）选哪个？**

A：对于简单的过渡效果（hover、点击后的状态切换），CSS Transition 更好——声明式、不需要 JS、浏览器内部优化。对于复杂动画（基于物理的动画、路径动画、响应滚动），用 rAF + JS 更灵活。实际上它们可以共存。

**Q4：为什么修改 `innerHTML` 比重建整个节点树更高效？**

A：用 `innerHTML +=` 追加内容会触发整个容器内的全部节点重建（销毁旧 DOM → 解析 HTML 字符串 → 构建新 DOM），代价极高。正确做法是用 `insertAdjacentHTML('beforeend', html)` 或 `appendChild` 只追加新节点。

**Q5：第三方库（如 jQuery）会导致重排问题吗？**

A：会。jQuery 的 `$(el).width()` 内部可能触发强制同步布局。现代框架（React、Vue）普遍使用虚拟 DOM + 批量更新策略来减少重排，比手动 jQuery 操纵 DOM 聪明得多。但框架也不能完全杜绝重排——如果 `useEffect` 中同时读写 DOM 属性，同样会产生强制同步布局。

**Q6：CSS `will-change` 用多了会有什么实际表现？**

A：页面渲染模糊、部分元素出现锯齿、移动端掉帧严重。表现和 GPU 显存不足的症状一致。可以在 `chrome://gpu` 中查看 GPU 状态，在 Layers 面板中数一下独立图层数量（超过约 30-50 个就要警惕）。

**Q7：浏览器的「渲染帧」和「Event Loop」是什么关系？**

A：Event Loop 的每一轮（tick）可能包含多次任务执行。渲染帧是其中的一个特殊阶段：`执行 rAF 回调 → 样式计算 → Layout → Paint → Composite`。如果当前帧的 JS 任务执行时间过长（超过 16.6ms），渲染阶段就会被推迟或跳过——这就是「长任务导致掉帧」的原因。

**Q8：移动端 Web 页面卡顿，和桌面端的排查方法一样吗？**

A：大方向一致，但移动端有两个额外关注点：(1) 移动端 GPU 显存更小，创建图层时要更克制；(2) 移动端滚动性能更敏感，避免在 `scroll` 事件中做 Layout 操作，要用 `passive: true` 的事件监听器并配合 requestAnimationFrame 做限流。

## 本节小结

- 重排（Reflow）由几何属性变化触发，代价最高；重绘（Repaint）只涉及视觉属性变化，代价中等；合成只涉及图层变换，代价最低
- 强制同步布局（Forced Synchronous Layout）是读写混用导致的最常见性能杀手
- DocumentFragment、display:none 中转、读写分离是批量 DOM 修改的三大优化手段
- requestAnimationFrame 对齐浏览器刷新率，是做视觉更新和动画的唯一正确选择
- Chrome Performance 面板是前端性能诊断的核心工具，学会解读火焰图是每个前端开发者的必备技能
