# 03 — DNS、TCP、TLS 握手过程

## 学习目标

- 理解 DNS 解析的完整流程，以及每一层 DNS 缓存的作用

- 知道 TLS 1.3 相比 1.2 简化了什么
- 能把一次完整的 HTTPS 请求旅程串起来：DNS → TCP → TLS → HTTP → 渲染
- 理解 `dns-prefetch` 和 `preconnect` 的实际作用
- 能用 Chrome Network Timing 面板分析请求各阶段耗时

## 内容讲解

### 一、DNS 解析：把域名翻译成 IP 地址

你在浏览器输入 `www.example.com`，计算机不认识这个名字——它只认识 IP 地址（如 `93.184.216.34`）。DNS（Domain Name System，域名系统）就是负责做这个"翻译"工作的。

> **类比**：DNS 就像手机通讯录。你要打给"张三"，手机帮你把"张三"翻译成 `138xxxx1234`。你不会去记每个人的号码，DNS 让你不用记每个网站的 IP。

#### 1.1 域名层级结构

```
www.example.com.
│   │       │  │
│   │       │  └── 根域（最后有一个隐式的点，通常省略）
│   │       └───── 顶级域（Top-Level Domain，如 .com、.cn）
│   └───────────── 二级域（example）
└───────────────── 三级域 / 子域（www）
```

DNS 查询是**从右向左**逐级进行的：先问根域 → 再问 `.com` → 再问 `example.com` → 最后得到 `www.example.com` 的 IP。

#### 1.2 DNS 解析的两种查询方式

**递归查询**：你把问题交给 DNS 解析器，它替你一层层问到底，最后把结果告诉你。

```
你的电脑                        DNS 递归解析器
   │  "www.example.com 的 IP？"      │
   │ ──────────────────────────────→ │
   │                                 │ ──→ 问根 DNS 服务器
   │                                 │ ←── ".com 找它"
   │                                 │ ──→ 问 .com 顶级 DNS
   │                                 │ ←── "example.com 找它"
   │                                 │ ──→ 问 example.com 权威 DNS
   │                                 │ ←── "IP 是 93.184.216.34"
   │  "93.184.216.34"               │
   │ ←────────────────────────────── │
```

**迭代查询**：DNS 服务器不替你查，而是告诉你"我不知道，但你可以去问 XXX"，你（或你的解析器）自己去挨个问。

> 实际网络中：你的电脑对运营商 DNS 发起**递归查询**；运营商 DNS 对根域 / 顶级域 / 权威 DNS 发起**迭代查询**。

#### 1.3 DNS 缓存链

DNS 解析如果每次都走完整流程，一个请求可能要多花几十甚至上百毫秒。所以每一层都有缓存：

```
浏览器 DNS 缓存（Chrome 默认缓存 1 分钟）
        ↓ 未命中
操作系统 DNS 缓存（hosts 文件 + 系统缓存）
        ↓ 未命中
路由器 DNS 缓存
        ↓ 未命中
运营商（ISP）DNS 缓存
        ↓ 未命中
递归查询（完整走一遍）
```

> **hosts 文件**：你可以手动在 `/etc/hosts`（Mac/Linux）或 `C:\Windows\System32\drivers\etc\hosts` 里写域名和 IP 的映射，浏览器会优先读取。前端开发中经常用这种方式做本地域名转发（如 `127.0.0.1 www.my-project.local`）。

#### 1.4 在浏览器层面加速 DNS

你可以在 HTML 中预解析将来会用到的域名：

```html
<!-- DNS 预解析：提前把域名翻译成 IP -->
<link rel="dns-prefetch" href="//api.example.com">
<link rel="dns-prefetch" href="//cdn.example.com">

<!-- 预连接：DNS + TCP + TLS 一把梭，连连接都建好 -->
<link rel="preconnect" href="//api.example.com">
```

`dns-prefetch` 只做 DNS 解析，成本极低。`preconnect` 把 DNS + TCP + TLS 全做了，成本稍高，但后续请求几乎零延迟。

### 二、TCP 三次握手：建立可靠连接

HTTP 是基于 TCP 的（HTTP/3 除外）。在发送 HTTP 数据之前，必须先建立 TCP 连接。这个过程叫**三次握手**。

> **类比**：你给朋友打电话：
> 1. 你："喂，能听到吗？"（SYN）
> 2. 朋友："能听到，你能听到我吗？"（SYN-ACK）
> 3. 你："能听到，咱们开始聊吧。"（ACK）
>
> 三次确认后，对话正式开始。任何一方没确认，通话就无法建立。

#### 2.1 三次握手流程图

```
客户端（浏览器）                        服务器
       │                                  │
       │ ──── SYN (seq=x) ────────────→  │  第 1 次：客户端说"我想连你"
       │    SYN 标志位=1, 序列号=x        │
       │                                  │
       │ ←── SYN-ACK (seq=y, ack=x+1) ── │  第 2 次：服务器说"收到，我也想连你"
       │    SYN=1, ACK=1, 序列号=y        │
       │    确认号=x+1                    │
       │                                  │
       │ ──── ACK (seq=x+1, ack=y+1) ──→ │  第 3 次：客户端说"好，连上了"
       │    ACK=1, 确认号=y+1             │
       │                                  │
       │  ═══ TCP 连接建立，开始传数据 ═══  │
```

#### 2.2 为什么是三次，而不是两次或四次？

**为什么不是两次？** 这是核心问题。

假设只有两次握手（客户端发 SYN → 服务器回 SYN-ACK 就认为连接建立）。考虑这个场景：

1. 客户端发了一个 SYN，但网络延迟很高，超时了
2. 客户端以为丢了，重新发了一个 SYN
3. 第二次握手成功，传完数据，关闭连接
4. **此时**，第一个"迷路"的 SYN 终于到达服务器
5. 服务器回 SYN-ACK，以为连接建立，分配资源等待数据
6. 但客户端早就忘了这件事，不会发送数据
7. 服务器资源被白白占用

第三次握手（客户端回 ACK）让服务器确认：客户端确实还想要这个连接，不是旧的迷路消息。

**为什么不是四次？** 三次已经够用了——客户端发 SYN（我要连） + 服务器回 SYN-ACK（收到，我也要连） + 客户端回 ACK（确认）。双方收发能力都验证完毕，四次是浪费。

### 三、TCP 四次挥手：优雅关闭连接

关闭 TCP 连接比建立连接多一步，因为 TCP 是全双工的——双方都可以独立发送和接收数据。

> **类比**：你和朋友打电话结束时：
> 1. 你："我说完了，先挂了"（FIN）
> 2. 朋友："好，我知道你说完了"（ACK）——但**朋友可能还有话要说**
> 3. 朋友："我也说完了，拜拜"（FIN）
> 4. 你："拜拜"（ACK）
>
> 因为两边可能不是同时说完的，所以关闭需要四步。

#### 3.1 四次挥手流程图

```
客户端（主动关闭方）                    服务器（被动关闭方）
       │                                       │
       │ ──── FIN (seq=u) ──────────────────→ │  第 1 次：客户端说"我没数据了"
       │                                       │
       │ ←── ACK (ack=u+1) ────────────────── │  第 2 次：服务器说"收到"
       │                                        （服务器可能还在发数据）
       │                                       │
       │ ←── FIN (seq=v, ack=u+1) ─────────── │  第 3 次：服务器说"我也发完了"
       │                                       │
       │ ──── ACK (ack=v+1) ─────────────────→ │  第 4 次：客户端说"收到，拜拜"
       │                                       │
       │  等待 2MSL（最长报文寿命 × 2）            │
       │  确保最后的 ACK 到达，然后关闭             │
```

#### 3.2 为什么是四次？

TCP 是全双工的，两端都能独立收发。当一端说"我没数据了"（FIN），另一端可能还有数据没发完。所以：

- 第一次 FIN + 第二次 ACK：关闭客户端 → 服务器的方向
- 第三次 FIN + 第四次 ACK：关闭服务器 → 客户端的方向

如果服务器在收到 FIN 时刚好也没数据要发了，可以把第二次的 ACK 和第三次的 FIN 合并成一条消息，这时候就是"三次挥手"。但通常情况下是四次。

#### 3.3 TIME_WAIT 状态

主动关闭方在发送最后一个 ACK 后，不会立即关闭连接，而是进入 **TIME_WAIT** 状态并等待 **2MSL**（Maximum Segment Lifetime，约 1-4 分钟）。

两个目的：
1. 确保最后一个 ACK 能到达对方（如果丢了，对方会重发 FIN，你还有机会再回 ACK）
2. 让旧连接的所有"迷路"数据包在网络中自然消亡，不会污染到后续的新连接

### 四、TLS 握手：加密通信的建立

TCP 连接建立后，如果是 HTTPS，还需要进行 TLS 握手来协商加密密钥。

> **类比**：TCP 三次握手是"打通电话"，TLS 握手是"确认对方身份 + 约定暗号"。打通电话只是能说话了，但你要确认接电话的人确实是你要找的人（身份验证），并且约好用什么暗号加密聊天内容（密钥协商）。

#### 4.1 TLS 1.2 握手（老版本，需要 2-RTT）

```
客户端                                  服务器
  │                                        │
  │ ──── ClientHello ────────────────────→ │  客户端：我支持这些加密方式
  │    （支持的密码套件、随机数1）             │
  │                                        │
  │ ←── ServerHello ────────────────────── │
  │     Certificate（服务器证书）            │  服务器：选一个加密方式，给你看证书
  │     ServerKeyExchange                  │
  │     ServerHelloDone                    │
  │                                        │
  │ ──── ClientKeyExchange ──────────────→ │  客户端：用证书公钥加密，传预主密钥
  │     ChangeCipherSpec（开始加密）         │
  │     Finished                            │
  │                                        │
  │ ←── ChangeCipherSpec ──────────────── │  服务器：我也切换加密，完成
  │     Finished                            │
  │                                        │
  │  ═══ 加密通信开始 ═══                    │
```

TLS 1.2 需要 **2 个往返（2-RTT）** 才能开始传输数据。

#### 4.2 TLS 1.3 握手（现代版本，只需 1-RTT）

TLS 1.3 做了大刀阔斧的简化：

```
客户端                                  服务器
  │                                        │
  │ ──── ClientHello ────────────────────→ │
  │    （支持的密码套件、密钥协商参数）        │  客户端：我要这些加密方式 + 我的密钥参数
  │                                        │
  │ ←── ServerHello ────────────────────── │
  │     {Certificate}（加密的证书）          │
  │     {CertificateVerify}                │  服务器：就这个方式 + 证书 + 确认
  │     {Finished}                          │  （证书部分已经被加密了！）
  │                                        │
  │ ──── {Finished} ──────────────────────→ │  客户端：收到，开始加密通信
  │                                        │
  │  ═══ 加密通信开始 ═══                    │
```

TLS 1.3 只需 **1-RTT**，比 1.2 少了一半的时间。而且如果客户端之前连接过这个服务器（PSK，预共享密钥），甚至可以实现 **0-RTT**——在第一条消息里就开始发送加密数据。

**TLS 1.3 的主要改进**：
1. 握手从 2-RTT 降到 1-RTT（0-RTT 恢复）
2. 删除了所有不安全的加密算法（RSA 密钥交换、CBC 模式、SHA-1 等）
3. 证书在握手阶段就被加密，防窃听
4. 只支持前向安全（Forward Secrecy）的密钥交换

### 五、一次完整的 HTTPS 请求旅程

现在把所有环节串起来，看看你在浏览器敲下回车后发生了什么：

```
时间轴 →

0ms   DNS 解析
      ├── 浏览器 DNS 缓存 → 系统缓存 → 路由器 → ISP → 递归查询
      └── 得到服务器 IP：93.184.216.34
      耗时：10-100ms（缓存命中时接近 0ms）

      TCP 三次握手
      ├── 客户端 → 服务器：SYN
      ├── 服务器 → 客户端：SYN-ACK
      └── 客户端 → 服务器：ACK
      耗时：1 个 RTT（往返时间，约 10-50ms）

      TLS 握手（TLS 1.3）
      ├── 客户端 → 服务器：ClientHello（密钥协商）
      └── 服务器 → 客户端：ServerHello（证书 + 确认）
      耗时：1 个 RTT（TLS 1.2 需 2 个 RTT）

      ─── 至此，连接建立完成 ───

      HTTP 请求
      ├── 客户端 → 服务器：GET /index.html HTTP/1.1
      └── 服务器 → 客户端：HTTP/1.1 200 OK + 数据
      耗时：1 个 RTT（至少）

      浏览器渲染
      ├── 解析 HTML，构建 DOM 树
      ├── 解析 CSS，构建 CSSOM 树
      ├── 遇到 <img> / <script> / <link> 等，发起新的请求
      └── 渲染页面

总计（首次访问，无缓存）：约 3-5 个 RTT + 传输时间
总计（再次访问，缓存命中）：约 50ms（大部分阶段可跳过或并行）
```

> **注意**：实际场景中，浏览器会对同一个域名复用 TCP 连接（HTTP/1.1 的 Keep-Alive），后续请求不需要重新握手。HTTP/2 更是可以全程复用同一个连接。

### 六、性能优化：dns-prefetch 和 preconnect

理解了上述流程后，你就能理解这两个 HTML 标签的真正价值了。

#### 6.1 dns-prefetch（DNS 预解析）

```html
<link rel="dns-prefetch" href="//api.example.com">
```

**作用**：在当前页面空闲时，提前解析将来可能用到的域名。当用户真的触发请求时，DNS 解析这一步已经完成了。

**节省的时间**：DNS 解析的 RTT（通常 10-100ms），成本极低，几乎无副作用。

**适用场景**：页面中有第三方资源、跳转目标域名、即将访问的 API 域名。

#### 6.2 preconnect（预连接）

```html
<link rel="preconnect" href="//api.example.com">
```

**作用**：提前完成 DNS + TCP + TLS 全套连接建立。等真正需要发请求时，连接已就绪，可以直接发数据。

**节省的时间**：DNS + TCP + TLS，约 2-3 个 RTT（50-200ms）。

**适用场景**：确定会用且即将使用的关键资源（如关键 API、关键 CDN）。

**注意**：preconnect 会维持连接（占用服务器资源），每个页面建议控制在 4-6 个以内，且只预连接真正关键且很快会用到的域名。

#### 6.3 两者对比

```html
<!-- 轻度优化：只提前翻译，便宜但只省 DNS 时间 -->
<link rel="dns-prefetch" href="//analytics.example.com">

<!-- 重度优化：提前建好全链路，贵但效果最好 -->
<link rel="preconnect" href="//api.example.com">

<!-- 最佳实践：preconnect 本身就包含了 DNS 预解析 -->
<link rel="preconnect" href="//cdn.example.com">
```

#### 6.4 综合示例：现代 Web 应用的资源提示

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8">

  <!-- 关键 CDN：提前建好完整连接 -->
  <link rel="preconnect" href="//cdn.example.com">

  <!-- 第三方分析服务：只做 DNS 预解析即可（不确定何时用到） -->
  <link rel="dns-prefetch" href="//analytics.example.com">

  <!-- 可能的跳转目标 -->
  <link rel="dns-prefetch" href="//login.example.com">

  <title>我的应用</title>
</head>
```

### 七、实战：用 Network Timing 分析请求耗时

Chrome Network 面板的 **Timing** 标签可以让你直观看到每个请求在各阶段花了多少时间。

#### 解读 Timing 面板

点开任意一个请求，切换到 Timing 标签，你会看到类似这样的分布：

```
┌─────────────────────────────────────────────────────────┐
│ Queueing              │███│  1.5 ms — 浏览器队列等待     │
│ Stalled               │█  │  0.8 ms — 连接可用前的等待   │
│ DNS Lookup            │███│  3.2 ms — DNS 解析          │
│ Initial connection    │███│  4.1 ms — TCP 握手           │
│ SSL                   │████│  6.5 ms — TLS 握手           │
│ Request sent          │█  │  0.3 ms — 发送请求           │
│ Waiting (TTFB)        │████████│  45.2 ms — 等待服务器响应│
│ Content Download      │████│  12.8 ms — 下载响应内容      │
└─────────────────────────────────────────────────────────┘
```

#### 各阶段含义

| 阶段 | 含义 | 优化方向 |
|---|---|---|
| **Queueing** | 浏览器排队（HTTP/1.1 域名并发限制 6-8 个） | 升级 HTTP/2 或做域名分散 |
| **Stalled** | 等待可用 TCP 连接 | 减少连接数或使用 preconnect |
| **DNS Lookup** | DNS 解析耗时 | 使用 dns-prefetch |
| **Initial connection** | TCP 三次握手 | 使用 preconnect |
| **SSL** | TLS 握手 | 使用 TLS 1.3、preconnect |
| **Request sent** | 发送请求体 | 减少请求体大小 |
| **Waiting (TTFB)** | 从发出请求到收到第一个字节 | 后端优化（查询、缓存、CDN） |
| **Content Download** | 下载响应体 | 压缩、CDN、减少响应体 |

> **TTFB（Time To First Byte）**：衡量从发起请求到收到服务器第一个响应字节的时间，是后端性能的核心指标。前端能做的就是减少请求并发、使用 CDN 缩短物理距离。

#### 实战练习步骤

1. 打开一个你常用的网站，记录首页 HTML 文档的 Timing 分布
2. 找一个静态资源（CSS/JS），观察它的 DNS Lookup 和 Initial connection 是否为 0（为什么？因为它复用了主页面的 TCP 连接）
3. 找一个第三方域名的资源，观察它从 DNS 开始建立新连接的完整流程
4. 对比 HTTP/2 和 HTTP/1.1 请求的 Queueing 时间差异

## 常见问题

**Q1：为什么 TCP 是三次握手而不是两次？**

如果只有两次握手，服务器无法区分"客户端真心想连"和"旧的迷路请求"。三次握手的最后一次 ACK 让客户端确认自己真正需要这个连接，防止服务器为"幽灵请求"浪费资源。

**Q2：TCP 四次挥手时，为什么有 TIME_WAIT 状态？**

TIME_WAIT 等 2MSL 有两个目的：① 确保最后的 ACK 到达（如果丢了，服务器会重发 FIN，你还能回应）；② 让旧连接的残余数据包在网络中超时消亡，不会干扰新连接。

**Q3：TLS 1.3 比 TLS 1.2 快多少？**

TLS 1.2 需要 2-RTT 完成握手，TLS 1.3 只需要 1-RTT。假设往返时间 50ms，每次新连接就省了 50ms。如果使用 PSK（之前连接过），TLS 1.3 甚至可以做到 0-RTT。

**Q4：DNS 查询为什么有时快有时慢？**

看缓存命中情况。浏览器/系统缓存命中 → 接近 0ms；路由器/ISP 缓存命中 → 5-20ms；需要递归查询到权威 DNS → 50-200ms。`dns-prefetch` 就是利用空闲时间提前预热缓存。

**Q5：preconnect 用多了有什么坏处？**

每个 preconnect 会建立一个连接并维持它，占用浏览器和服务器资源（每个连接消耗内存和文件描述符）。如果预连接了 10 个域名却只用到 2 个，那 8 个连接就浪费了。建议每个页面控制在 4-6 个关键域名以内。

**Q6：为什么 Chrome Network 面板中有些请求的 DNS Lookup 和 Initial connection 都是 0？**

因为浏览器对同一个域名（Origin）复用连接。比如主页面 `www.example.com` 已经完成了 DNS + TCP + TLS，后续对同域名的 CSS/JS/图片请求直接走已有连接，不需要重新握手。这就是 HTTP Keep-Alive 的作用。

**Q7：HTTP/3 还需要 TCP 三次握手和 TLS 握手吗？**

HTTP/3 基于 QUIC（UDP），不需要 TCP 三次握手。但 QUIC 内置了 TLS 1.3，所以加密握手仍然需要。不过 QUIC 的设计可以把连接建立和 TLS 握手合并，实现 0-RTT 或 1-RTT。

## 本节小结

- DNS 解析是"域名 → IP"的翻译过程，每一层都有缓存加速
- TCP 三次握手确保双方收发能力正常，防止旧连接干扰
- TCP 四次挥手因为全双工需要分两个方向分别关闭
- TLS 1.3 将加密握手从 2-RTT 降到 1-RTT（0-RTT 恢复更快）
- 一次 HTTPS 请求 = DNS → TCP → TLS → HTTP → 渲染
- `dns-prefetch` 提前解析域名，`preconnect` 提前建好全链路
- Chrome Timing 面板是分析请求性能的第一手工具
