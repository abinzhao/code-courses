## 内容讲解

### 一、什么是 HTTP

HTTP 全称 **HyperText Transfer Protocol（超文本传输协议）**，是浏览器和服务器之间沟通的语言。

举个例子：你在浏览器地址栏输入 `https://www.example.com` 并回车，浏览器做的第一件事就是向服务器发送一段"HTTP 请求报文"，服务器收到后回复一段"HTTP 响应报文"，浏览器再把响应内容渲染成你看到的页面。

```
┌──────────┐    HTTP 请求（"我要首页 HTML"）    ┌──────────┐
│  浏览器   │ ──────────────────────────────→ │  服务器   │
│          │ ←────────────────────────────── │          │
└──────────┘    HTTP 响应（"给你，这是 HTML"）   └──────────┘
```

> **类比**：HTTP 就像快递行业的"面单格式"——你寄快递时，面单上必须有发件人、收件人、物品描述。HTTP 规定了"请求"和"响应"的格式，浏览器和服务器都按这个格式说话，才能互相理解。

HTTP 是一个**无状态**协议，意思是服务器不会"记住"上一次请求是谁发的。这也是为什么需要 Cookie、Token 等机制来维持登录状态——后面课程会讲到。

### 二、URL 结构拆解

URL（统一资源定位符）就是你在浏览器地址栏里看到的那一串地址。一个完整的 URL 长这样：

```
https://www.example.com:443/api/users?id=10&page=2#profile
```

我们把它拆开来看：

| 部分 | 示例值 | 说明 |
|---|---|---|
| **协议（Scheme）** | `https` | 告诉浏览器用什么方式通信，常见的有 `http`、`https`、`ws`、`ftp` |
| **域名（Host）** | `www.example.com` | 服务器的地址，最终会通过 DNS 解析成 IP 地址 |
| **端口（Port）** | `443` | 服务器上的"门牌号"。HTTP 默认 80，HTTPS 默认 443，默认时可省略 |
| **路径（Path）** | `/api/users` | 服务器上的"文件路径"，告诉服务器你要访问哪个资源 |
| **查询参数（Query）** | `?id=10&page=2` | 以 `?` 开头，`key=value` 格式，多个参数用 `&` 连接。用于传递筛选、分页等附加信息 |
| **片段（Fragment / Hash）** | `#profile` | 以 `#` 开头，指向页面内的某个锚点（id）。**注意：片段不会发送到服务器**，只在浏览器端使用 |

> **注意**：日常开发中，`?` 后面的部分不会影响路由匹配——`/users` 和 `/users?id=10` 在服务端看来是同一个路径，只是带了不同的查询条件。

### 三、HTTP 请求报文结构

一个 HTTP 请求报文由三部分组成：**请求行 → 请求头 → 请求体**。

下面是一个完整的 HTTP 请求示例（当你用 POST 提交登录表单时，浏览器发出的内容大致如此）：

```http
POST /api/login HTTP/1.1                   ← 请求行
Host: www.example.com                       ← 请求头（从这里开始）
Content-Type: application/json
Content-Length: 56
Authorization: Bearer eyJhbGciOi...
User-Agent: Mozilla/5.0 (Macintosh; ...)
Accept: application/json
                                            ← 空行（请求头和请求体之间的分隔线）
{                                           ← 请求体
  "username": "zhangsan",
  "password": "123456"
}
```

#### 3.1 请求行

```
POST /api/login HTTP/1.1
```

- **请求方法**（`POST`）：告诉服务器你想做什么（获取数据？提交数据？删除数据？）
- **请求路径**（`/api/login`）：你要访问的资源路径
- **协议版本**（`HTTP/1.1`）：使用的 HTTP 版本

#### 3.2 请求头（Request Headers）

请求头是 `Key: Value` 格式的键值对，用来传递附加信息。最常见的几个：

| 请求头 | 含义 | 示例 |
|---|---|---|
| `Host` | 目标主机（域名） | `www.example.com` |
| `Content-Type` | 请求体的数据类型 | `application/json`、`application/x-www-form-urlencoded` |
| `Content-Length` | 请求体的字节数 | `56` |
| `Authorization` | 身份认证信息 | `Bearer eyJhbGci...` |
| `User-Agent` | 客户端标识（浏览器类型、操作系统） | `Mozilla/5.0 ...` |
| `Accept` | 客户端能接收的响应格式 | `application/json` |
| `Cookie` | 携带的 Cookie 信息 | `sessionId=abc123` |

#### 3.3 请求体（Request Body）

不是所有请求都有请求体。**GET 请求通常没有请求体**，数据通过 URL 的查询参数传递；**POST、PUT、PATCH 请求通常携带请求体**，数据放在 body 里。

```json
{
  "username": "zhangsan",
  "password": "123456"
}
```

### 四、HTTP 响应报文结构

响应报文也是三部分：**状态行 → 响应头 → 响应体**。

```http
HTTP/1.1 200 OK                             ← 状态行
Date: Mon, 12 Oct 2026 08:00:00 GMT         ← 响应头
Content-Type: application/json
Content-Length: 85
Cache-Control: no-cache
Set-Cookie: sessionId=abc123; HttpOnly
                                            ← 空行（分隔线）
{                                           ← 响应体
  "code": 0,
  "message": "登录成功",
  "data": {
    "token": "eyJhbGciOi..."
  }
}
```

#### 4.1 状态行

```
HTTP/1.1 200 OK
```

- **协议版本**：`HTTP/1.1`
- **状态码**：`200`（三位的数字）
- **状态描述**：`OK`（人类可读的描述，不同服务器措辞可能略有不同）

#### 4.2 响应头（Response Headers）

| 响应头 | 含义 |
|---|---|
| `Content-Type` | 响应体的数据类型，告诉浏览器该用什么方式解析 |
| `Content-Length` | 响应体的字节数 |
| `Set-Cookie` | 让浏览器保存 Cookie |
| `Cache-Control` | 缓存策略（下一节详细讲） |
| `Access-Control-Allow-Origin` | 跨域允许的源（CORS 相关） |

#### 4.3 响应体（Response Body）

这是服务器返回的实际内容。可能是 HTML、JSON、图片的二进制数据等等。浏览器根据 `Content-Type` 来决定如何处理它。

### 五、常见 HTTP 方法

| 方法 | 语义 | 幂等性 | 有无请求体 | 典型场景 |
|---|---|---|---|---|
| **GET** | 获取资源 | 是（多次请求结果一样） | 无 | 查文章列表、看用户详情 |
| **POST** | 创建资源 | 否（多次请求会创建多个） | 有 | 注册账号、发表评论 |
| **PUT** | 完整更新资源 | 是（多次更新结果一样） | 有 | 替换整篇文章内容 |
| **PATCH** | 部分更新资源 | 否（通常） | 有 | 只改文章标题 |
| **DELETE** | 删除资源 | 是（删一次和删多次结果一样） | 通常无 | 删除某条评论 |

> **幂等性**：同一个操作执行一次和执行多次，对服务器产生的**副作用**是一样的。GET 查十次不会改变数据（幂等），POST 提交十次会创建十条记录（不幂等）。

**PUT vs PATCH 的区别**——面试高频考点：
- PUT：你给我一个完整的对象，我把旧的全部替换掉。
- PATCH：你只给我需要修改的字段，我只更新这些字段。

```javascript
// PUT：你需要把整个对象发过去
fetch('/api/users/1', {
  method: 'PUT',
  body: JSON.stringify({ name: '张三', age: 25, email: 'zhang@test.com' })
})

// PATCH：只需发要修改的字段
fetch('/api/users/1', {
  method: 'PATCH',
  body: JSON.stringify({ age: 26 })
})
```

### 六、核心状态码速记表

#### 2xx — 成功

| 状态码 | 含义 | 什么时候出现 |
|---|---|---|
| **200 OK** | 请求成功 | 正常 GET/POST 请求成功的响应 |
| **201 Created** | 资源创建成功 | POST 创建新用户、新文章后返回 |
| **204 No Content** | 成功但没有响应体 | DELETE 删除成功后，不需要返回内容 |

#### 3xx — 重定向

| 状态码 | 含义 | 什么时候出现 |
|---|---|---|
| **301 Moved Permanently** | 永久重定向 | 旧网址永久迁移到新网址，浏览器会记住并自动跳转 |
| **302 Found** | 临时重定向 | 临时跳转，比如未登录时跳转到登录页 |
| **304 Not Modified** | 资源未修改 | 配合缓存使用，告诉浏览器"用你本地的缓存就行" |

> **301 vs 302**：301 告诉搜索引擎"旧地址已经永久搬家了，以后只收录新地址"；302 表示"只是暂时借用，下次还回来"。

#### 4xx — 客户端错误

| 状态码 | 含义 | 什么时候出现 |
|---|---|---|
| **400 Bad Request** | 请求参数错误 | 前端传了服务器不认识的参数格式 |
| **401 Unauthorized** | 未认证 | 没登录或 token 过期 |
| **403 Forbidden** | 无权限 | 已登录但没有操作权限（比如普通用户试图删除别人的文章） |
| **404 Not Found** | 资源不存在 | 访问了一个不存在的页面或接口 |

> **401 vs 403**：401 是"你是谁？我不知道"（需要登录）；403 是"我知道你是谁，但你不配"（已登录但没权限）。

#### 5xx — 服务端错误

| 状态码 | 含义 | 什么时候出现 |
|---|---|---|
| **500 Internal Server Error** | 服务器内部错误 | 代码抛异常了，服务挂了 |
| **502 Bad Gateway** | 网关错误 | 上游服务器返回了无效响应（常见于 Nginx 反代场景） |
| **503 Service Unavailable** | 服务不可用 | 服务器在维护中，或请求量过载 |
| **504 Gateway Timeout** | 网关超时 | 上游服务器响应太慢，超时了 |

### 七、HTTP 版本演进：从 1.1 到 3

这是面试中的经典话题。你不需要记住所有细节，但要清楚每一代解决了什么问题。

#### 7.1 HTTP/1.1（1997，至今仍广泛使用）

HTTP/1.1 最大的痛点是**队头阻塞（Head-of-Line Blocking）**。

HTTP/1.1 在一个 TCP 连接上，请求必须排队——前一个请求的响应没回来，后面的请求就不能发送。

```
时间线 →
请求1 │████████████████████│ → 响应1
请求2                      │██████████│ → 响应2
请求3                                   │██████│ → 响应3
```

> **类比**：就像只有一个收银台的超市，不管后面的人买多买少，都得等前面的人结完账。

浏览器通常同时开 6-8 个 TCP 连接来缓解这个问题，但这治标不治本。

#### 7.2 HTTP/2（2015，现在主流）

HTTP/2 的三大杀器：

**① 多路复用（Multiplexing）**

在**一个 TCP 连接**上同时发送多个请求，不用排队了。

```
时间线 →
请求1 │██████████│ → 响应1
请求2 │████████│ → 响应2
请求3 │████│ → 响应3
         ↑ 三个请求在同一连接中交错传输
```

**② 头部压缩（HPACK）**

HTTP/1.1 每次请求都带着又长又重复的头部（`User-Agent`、`Cookie` 等）。HTTP/2 用 HPACK 算法压缩头部，大幅减少传输量。

**③ 服务器推送（Server Push）**

服务器可以"主动"把资源推给浏览器，不再等浏览器来请求。比如你请求 `index.html`，服务器知道你一定还需要 `style.css`，就直接一起推给你。

> **局限**：HTTP/2 的多路复用仍然受限于底层的 TCP——如果 TCP 层发生丢包，所有在这个 TCP 连接上的 HTTP 请求都得等重传。这就是 TCP 层的队头阻塞。

#### 7.3 HTTP/3（2022 标准化，越来越普及）

HTTP/3 最大的变革是：**不用 TCP 了，改用 QUIC（基于 UDP）**。

| 对比维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 传输层协议 | TCP | TCP | QUIC（UDP） |
| 多路复用 | 不支持 | 支持（但 TCP 层仍可能队头阻塞） | 支持（彻底消除队头阻塞） |
| 头部压缩 | 无 | HPACK | QPACK |
| 连接建立 | TCP 三次握手 + TLS 握手 | TCP 三次握手 + TLS 握手 | 0-RTT / 1-RTT 握手 |
| 连接迁移 | 不支持（切换网络需要重建连接） | 不支持 | 支持（由连接 ID 标识，WiFi 切 4G 不断连） |

**QUIC 的核心优势**：
1. **彻底消除队头阻塞**：QUIC 在 UDP 之上实现了独立的流，一个流丢包不影响其他流
2. **0-RTT 握手**：如果之前连过同一个服务器，可以直接发送数据，不需要等待握手完成
3. **连接迁移**：从 WiFi 切换到 4G 时连接不会中断

> **现实情况**：截至 2026 年，Google、YouTube、Facebook 等大型网站已广泛使用 HTTP/3，但企业内网和部分 CDN 仍在 HTTP/2。浏览器通常会自动协商使用最高版本。

### 八、实战：用 Chrome Network 面板分析请求

#### 步骤

1. 打开 Chrome，按 `F12` 或 `Cmd+Option+I`（Mac）打开开发者工具
2. 切换到 **Network（网络）** 标签页
3. 勾选 **Preserve log**（保留日志，页面跳转时不清空）
4. 访问 `https://www.example.com`（或任何一个你喜欢的网站）
5. 观察面板中出现的请求列表

#### 你要关注的信息

- **Name**：请求的文件名或路径
- **Status**：状态码（重点关注有没有 4xx/5xx）
- **Type**：资源类型（document、script、stylesheet、xhr/fetch、image）
- **Size**：传输大小
- **Time**：总耗时
- **Waterfall**：时间瀑布图（直观看到每个请求的排队、等待、下载时间）

#### 点开一个请求，查看详情

- **Headers 标签**：看 General（请求 URL、方法、状态码）、Request Headers、Response Headers
- **Preview / Response 标签**：看返回的具体内容
- **Timing 标签**：看请求在各个阶段花了多少时间（DNS 解析 → 连接 → SSL → 发送 → 等待 → 下载）

> **练习建议**：分别找一个 document 类型、xhr/fetch 类型、image 类型的请求打开看看，对比它们有什么不同。

## 常见问题

**Q1：HTTP 和 HTTPS 的区别是什么？**

HTTPS = HTTP + TLS/SSL 加密层。HTTP 是明文传输，任何中间人都能看到内容；HTTPS 对传输内容加密，中间人看不到。浏览器地址栏左侧的"小锁"图标表示当前连接使用了 HTTPS。

**Q2：GET 请求能传请求体吗？**

技术上可以（HTTP 协议本身没有禁止），但几乎所有浏览器和服务器实现都不支持或不推荐。数据应当通过 URL 查询参数传递，或者改用 POST。

**Q3：为什么 POST 不是幂等的而 PUT 是？**

因为 POST 的语义是"创建一个新资源"，每次请求都会产生新的资源（新的 ID）。而 PUT 的语义是"把指定 ID 的资源替换成这个内容"，替换一百次，该资源最终还是那样。

**Q4：304 状态码是谁返回的？**

304 是服务器返回的。浏览器带着缓存验证信息（如 `If-None-Match`）去问服务器"我这个缓存还有效吗？"，服务器检查后如果资源没变，就返回 304 告诉浏览器"用你本地的就行"。整个过程请求确实发出去了，但响应体是空的，节省了带宽。

**Q5：HTTP/2 的服务器推送为什么在实际生产中用得不多？**

因为推送是"盲目的"——服务器不知道浏览器是否已经有缓存。Chrome 在 2022 年甚至移除了对 HTTP/2 Server Push 的支持，转而推荐使用 `<link rel="preload">` 让浏览器主动控制预加载。

**Q6：怎么知道一个网站用的是 HTTP/1.1 还是 HTTP/2？**

在 Chrome Network 面板中，右键点击列头，勾选 **Protocol** 列，就能看到每个请求使用的协议版本（`h2` 表示 HTTP/2，`h3` 表示 HTTP/3，`http/1.1` 就是 HTTP/1.1）。

**Q7：状态码 499 是什么意思？**

499 不是标准 HTTP 状态码，而是 **Nginx 自定义的**。它表示客户端在服务器返回响应之前主动关闭了连接（比如用户关了浏览器标签页）。

## 本节小结

- HTTP 是浏览器和服务器之间的通信协议，请求和响应各有固定格式
- URL 由协议 + 域名 + 端口 + 路径 + 查询参数 + 片段组成
- GET（查）、POST（增）、PUT（完整改）、PATCH（部分改）、DELETE（删）各司其职
- 2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务端错误——各记住核心 3-4 个
- HTTP/1.1 队头阻塞 → HTTP/2 多路复用 + 头部压缩 → HTTP/3（QUIC）彻底解决队头阻塞
