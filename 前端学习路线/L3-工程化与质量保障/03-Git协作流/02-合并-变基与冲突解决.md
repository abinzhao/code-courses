## 学习目标

- 理解 `git merge` 三种模式（fast-forward, --no-ff, --squash）的区别和适用场景
- 掌握 `git rebase` 的底层原理：「变基 = 重放 commit」
- 能根据场景判断该用 merge 还是 rebase
- 牢记黄金法则：禁止 rebase 已推送的公共分支
- 熟练使用 `git rebase -i` 整理 commit 历史（squash / fixup / reword / reorder）
- 能冷静、有序地解决任意冲突
- 掌握 `git reflog`、`git cherry-pick`、`git stash` 三个"救命"命令

## 内容讲解

### 1. `git merge` 的三种模式

merge 本质上就是把一个分支的变更"合入"另一个分支。Git 根据两个分支的 commit 关系，自动选择策略。

#### 场景设定

假设初始状态：

```
  A ← B ← C    ← main
```

你从 main 创建 `feature` 分支，并在 feature 上提交了 D 和 E：

```
  A ← B ← C             ← main
              \
               D ← E     ← feature
```

#### 1.1 Fast-Forward Merge（快进合并）

当 main 在 feature 分叉之后没有任何新 commit，Git 直接**把 main 指针滑过去**：

```bash
git switch main
git merge feature          # Git 检测到可以 fast-forward
# 输出：Fast-forward
#        src/file.js | 2 ++
#        1 file changed, 2 insertions(+)
```

结果：

```
  A ← B ← C ← D ← E    ← main, feature（两者指向同一个 commit）
```

**不产生任何 merge commit**，历史是完美线性的。

**适用**：feature 分支上只有你一个人开发，main 没变。前端日常小功能合并最常用。

#### 1.2 `--no-ff`（强制非快进）

有时你**希望保留"这个功能是一个独立分支"的记录**：

```bash
git merge --no-ff feature    # 强制创建一个 merge commit
```

结果：

```
  A ← B ← C ←───────────M   ← main
              \         /
               D ← E ←      ← feature
```

**M 是一个 merge commit，有两个 parent：C 和 E**。即使可以 fast-forward，也生成一个合并节点。

**适用**：你想一眼看出哪些 commit 是一个 feature 一起进来的。某些团队规范要求所有合并都用 `--no-ff`。

#### 1.3 Squash Merge

把整个 feature 分支的 commit 压缩成一个，然后放在 main 上：

```bash
git merge --squash feature   # 把所有变更压缩到暂存区，不产生 commit
git commit -m "feat: 完整功能描述"   # 手动 commit
```

结果：

```
  A ← B ← C ← S   ← main（S 包含 D+E 的所有变更，但只是一个 commit）
              \
               D ← E    ← feature（还在，但孤立了）
```

**注意**：S 的 parent 只有 C（不像 merge commit 有两个 parent）。feature 分支和 main 之间的"亲缘关系"丢失了。

**适用**：前端项目最推荐的合并方式——参见上一篇关于 Squash Merge 的讨论。

### 2. `git rebase` 的原理

如果说 merge 是"缝合"，rebase 就是"搬家"。

#### 核心机制

```
  rebase 之前：
  A ← B ← C               ← main
            \
             D ← E         ← feature

  git switch feature
  git rebase main

  rebase 过程中：
  A ← B ← C               ← main
            \
             D ← E         ← feature（原始位置）
            \
             D' ← E'       ← feature（搬到 C 之后，逐个"重放"）
```

**rebase 做了什么**：
1. 找到 `feature` 和 `main` 的共同祖先 C
2. 把 feature 上从 C 之后的所有 commit（D, E）暂存起来
3. 把 feature 指针移到 main 的顶端 C
4. 逐个应用 D, E 的 diff，生成新的 commit D', E'
5. feature 指向 E'

**结果是**：新的 D', E' 和旧的 D, E **内容相同但 hash 不同**（因为 parent 变了）。

```bash
git switch feature
git rebase main
# 输出：
# Successfully rebased and updated refs/heads/feature.
```

结果：

```
  A ← B ← C ← D' ← E'    ← feature
              ↑
              main
```

**历史变成了一条直线**，就像你一开始就从最新的 main 开始开发一样。

#### 底层：rebase 是逐 commit "重放"

你能理解下面这句话，就彻底懂了 rebase：

> Rebase 不是"移动 commit"，而是**扔掉旧 commit，生成内容相同但 parent 不同的新 commit**。

因此，已经推送到远程的 commit 一旦 rebase，本地和远程 hash 对不上，push 时只能用 `--force`。这就是黄金法则的由来。

### 3. Merge vs Rebase：何时用哪个

```
         merge                          rebase
    ┌──────────────┐              ┌──────────────┐
    │  保留真实历史  │              │  创造线性历史  │
    │  有 merge commit│             │  无 merge commit│
    │  适合公共分支  │              │  适合私有分支  │
    └──────────────┘              └──────────────┘
```

| 场景 | 用 merge | 用 rebase |
|---|---|---|
| 把 main 更新同步到 feature 分支 | ❌ 会产生无意义的 merge commit | ✅ `git rebase main` |
| 把 feature 合并到 main | ✅（通过 PR 的 Squash Merge） | 可选（Rebase Merge） |
| 整理本地尚未 push 的 commit | ❌ | ✅ `git rebase -i` |
| 合并两个公共分支 | ✅ 通常用 `git merge` | ⚠️ 仅在团队明确协调历史重写时使用 |
| 从开源项目上游同步更新 | 看情况 | ✅ `git rebase upstream/main` |

#### 决策口诀

> **优先只 rebase 你自己的、未推送分支。** 已推送但只有你使用的功能分支可以在确认后 rebase，并用 `--force-with-lease` 推送；多人共享分支不要擅自改写历史。
>
> 同步公共分支用 merge，整理私有历史用 rebase。

### 4. 黄金法则：不要 rebase 已推送的公共分支

为什么？看一个血泪案例：

```
 远程 feature:  A ← B ← C ← D
 你 fetch 下来:  A ← B ← C ← D

 你 rebase main 之后:
 本地 feature:   A ← B ← M ← N ← D'  （D 变成了 D'，hash 不同了）
 远程 feature:   A ← B ← C ← D       （D 还在）

 你 git push:
 ❌ rejected! 本地和远程历史分叉了。
 你 git push --force:
 ✅ 推送成功，但把 D 覆盖成了 D'
 💀 同事本地还有 D，他们 git pull 时会把 D 和 D' 合并，
    然后历史中 A ← B ← C ← D ← D' ← (merge)
    D 和 D' 内容一模一样，但作为两个独立 commit 出现，
    混乱无比。
```

**唯一的例外**：你一个人在自己的 feature 分支上，且你确认没有人在你的分支上协作。此时 `git push --force-with-lease`（比 `--force` 安全，会检查远程有没有别人推的新 commit）可以接受。

### 5. `git rebase -i`：交互式变基

这是整理 commit 历史的神器。你可以在 rebase 过程中做四件事：

```
pick   = 保留这个 commit（默认）
squash = 合并到上一个 commit，保留 commit message
fixup  = 合并到上一个 commit，丢弃 commit message
reword = 保留，但修改 commit message
drop   = 删除这个 commit
```

#### 实战：整理一团乱的 commit 历史

假设你本地有 5 个 commit：

```
9a3f2b1 fix typo                            ← 最旧
7c1d4e8 feat: 添加购物车页面
2e8f5a0 fix: 修复按钮颜色
a1b6c3d chore: 格式化代码
f4d9e1b feat: 添加购物车接口调用            ← 最新
```

显然不合理——"fix typo"应该在"添加购物车页面"之后合并，"格式化代码"应该属于"添加购物车页面"。我们需要整理：

```bash
git rebase -i HEAD~5   # 对最近 5 个 commit 进行交互式 rebase
```

打开的编辑器：

```
pick 9a3f2b1 fix typo
pick 7c1d4e8 feat: 添加购物车页面
pick 2e8f5a0 fix: 修复按钮颜色
pick a1b6c3d chore: 格式化代码
pick f4d9e1b feat: 添加购物车接口调用
```

修改为：

```
pick 7c1d4e8 feat: 添加购物车页面           # 调到了第一位
fixup a1b6c3d chore: 格式化代码             # 合并进去，丢弃 message
fixup 9a3f2b1 fix typo                     # 合并进去，丢弃 message
pick 2e8f5a0 fix: 修复按钮颜色              # 独立保留
pick f4d9e1b feat: 添加购物车接口调用        # 独立保留
```

保存退出后，最终 history：

```
7c1d4e8' feat: 添加购物车页面              ← 包含格式化代码 + typo 修复
2e8f5a0' fix: 修复按钮颜色
f4d9e1b' feat: 添加购物车接口调用
```

5 个混乱的 commit → 3 个清晰的 commit。这就是你在 push 之前应该做的事。

**注意**：`fixup` 和 `squash` 的区别仅在于是否保留 message。大多数时候你用 `fixup`（"修个小错，不值一提"），偶尔用 `squash`（"这个 commit 的描述也有保留价值"）。

### 6. 冲突的本质和解决策略

#### 冲突是怎么产生的

Git 合并不是靠"AI 理解代码"，而是规则很简单：**逐行 diff，如果两个分支改了同一文件的同一行，就产生冲突**。

```
 main:       const title = "Hello World";        ← 第 12 行
 feature:    const title = "你好，世界";          ← 第 12 行（同一行！）
```

Git 无法知道你要保留哪个，于是把决定权交给你。

#### 冲突标记解读

```
<<<<<<< HEAD              ← 你当前所在分支的内容（通常是 main 或 rebase 的目标）
const title = "Hello World";
=======                   ← 分界线
const title = "你好，世界";
>>>>>>> feature           ← 合并进来的分支的内容
```

**解决原则**：
1. 读懂两边各自做了什么
2. 决定保留哪边、或组合两边
3. 删除冲突标记（`<<<<<<<` `=======` `>>>>>>>`）
4. 确保最终代码是正确的

#### 常见冲突场景

| 场景 | 示例 | 解决思路 |
|---|---|---|
| 两个人改了同一行 | 一个人改了文案，一个人改了组件名 | 沟通确认最终值 |
| 一个人删了，另一个人改了 | A 删除了 `utils/format.js`，B 修改了它 | 确认：是迁移了位置，还是确实要删？ |
| 一个人重构了函数签名，另一个人加了新调用 | A 把 `fetchUser(id)` 改成 `fetchUser({ id })`，B 在另一个文件调用了旧签名 | 全局搜索所有调用点，逐一处更新 |
| 配置文件冲突 | 两人都在 `package.json` 加了不同依赖 | 都保留，但要检查版本兼容 |
| 锁文件冲突 | `pnpm-lock.yaml` 冲突 | 解决 `package.json` 冲突后，直接重新 `pnpm install` 生成锁文件 |

### 7. 冲突解决流程

以 rebase 中遇到冲突为例（merge 冲突流程类似，只是用 `git merge --continue` 或 `git commit`）：

```bash
# ===== 第 1 步：rebase 被中断 =====
git rebase main
# 输出：
# Auto-merging src/cart/CartFooter.jsx
# CONFLICT (content): Merge conflict in src/cart/CartFooter.jsx
# error: could not apply 3a7b2c1... feat: 更新购物车底部计算逻辑
# Resolve all conflicts manually, mark them as resolved with "git add/rm <conflicted_files>",
# then run "git rebase --continue".

# ===== 第 2 步：查看冲突清单 =====
git status
# 输出：
# interactive rebase in progress; onto xxxxx
#   both modified:   src/cart/CartFooter.jsx
#   both modified:   src/cart/CartItem.jsx
#
# no changes added to commit (use "git add" and/or "git commit -a")

# ===== 第 3 步：逐个解决冲突文件 =====
# 打开 src/cart/CartFooter.jsx，看到：
# <<<<<<< HEAD
# const DISCOUNT_RATE = 0.85;            ← main 上最新的代码
# =======
# const DISCOUNT_RATE = 0.9;             ← 你这个 commit 要应用的变更
# >>>>>>> 3a7b2c1 (feat: 更新购物车底部计算逻辑)
#
# 你决定：用 main 上的 0.85（因为另一个 PR 已经更新了折扣策略）
# 删除冲突标记，保留 const DISCOUNT_RATE = 0.85;

# ===== 第 4 步：标记已解决 =====
git add src/cart/CartFooter.jsx          # git add = 告诉 Git："我已经搞定了"
git add src/cart/CartItem.jsx            # 同样处理

git status
# 输出：
# interactive rebase in progress; onto xxxxx
#   all conflicts fixed: you might want to run "git rebase --continue"

# ===== 第 5 步：继续 rebase =====
git rebase --continue
# 会弹出编辑器让你确认 commit message，保存退出
# 输出：Successfully rebased and updated refs/heads/feature/cart.

# ===== 备选：如果搞砸了 =====
git rebase --abort                        # 放弃整个 rebase，回到 rebase 之前的状态
git rebase --skip                         # 跳过当前冲突的 commit，丢弃它的变更（慎用）

# ===== 验证 =====
git log --oneline --graph                 # 检查最终历史是否符合预期
```

**关键心态**：冲突不是事故，是 Git 在保护你。遇到冲突 → `git status` → 看清局面 → 逐个解决 → 继续。不要慌，不要 `git rebase --abort` 逃跑。

### 8. 三个"救命"命令

#### 8.1 `git reflog`：后悔药

Git 会记录你**所有本地操作**的历史（包括已删除的 commit / 分支），保存 90 天：

```bash
git reflog
# 输出：
# a1b2c3d HEAD@{0}: commit: feat: 添加购物车接口
# e4f5g6h HEAD@{1}: rebase (finish): returning to refs/heads/feature/cart
# i7j8k9l HEAD@{2}: rebase (start): checkout main
# m0n1o2p HEAD@{3}: commit: feat: 重构购物车
# ...

# 场景：你 rebase 搞砸了，想回到 rebase 之前的状态
git reset --hard HEAD@{3}     # 回到"feat: 重构购物车"那个时间点

# 场景：你本地曾经获取过被覆盖的远程提交
git reflog --all             # 查找本地记录过的远程分支旧位置
git branch recovery <那个hash> # 先建立恢复分支，避免再次丢失引用
```

**边界**：`reflog` 只记录当前仓库中引用的移动，而且记录会过期并可能被 `git gc` 清理。提交如果曾在本地出现且尚未被清理，通常可以找回；从未拉到本地的同事提交要去同事的克隆、远程平台或备份中恢复。

#### 8.2 `git cherry-pick`：挑选特定 commit

从别的分支**复制**一个 commit 到当前分支：

```bash
# 场景：你在 feature/a 分支，想用 feature/b 上的一个工具函数 commit
git log feature/b --oneline
# b1c2d3e feat: 添加日期格式化工具函数
# f4a5b6c feat: 另一些功能

git cherry-pick b1c2d3e       # 把那个工具函数 commit 复制到当前分支
# 输出：[feature/a xxxxxxx] feat: 添加日期格式化工具函数

# 如果有冲突：
# 解决冲突 → git add → git cherry-pick --continue
# 或者放弃：git cherry-pick --abort
```

**cherry-pick 不是灵丹妙药**：频繁 cherry-pick 说明你的分支拆分或代码复用出了问题。只在紧急场景使用。

#### 8.3 `git stash`：临时保存工作区

开发到一半，突然要切去修 emergency bug，但你不想 commit 半成品：

```bash
# 保存当前工作区 + 暂存区
git stash
# 或者带描述：git stash push -m "购物车重构进行中，差 40%"

# 工作区恢复干净，可以切分支了
git switch main
git switch -c hotfix/critical-bug
# ... 修 bug ...

# 回到原分支
git switch feature/cart-rebuild
git stash pop                  # 恢复之前的工作区
# 输出：Dropped refs/stash@{0} ← stash 已弹出

# 其他常用命令
git stash list                 # 查看所有 stash
git stash apply stash@{1}      # 应用指定 stash 但不删除它
git stash drop stash@{1}       # 删除指定 stash
git stash pop --index          # 恢复时也恢复暂存区状态
```

**注意**：`git stash` 不会保存新文件（untracked files）。如果需要，加 `-u`：`git stash -u`。

### 9. 实战：模拟完整的 rebase 冲突解决流程

假设你和同事都在改购物车相关代码，他的代码已经合并到了 main。

#### 场景设定

```
 你的 feature/cart 分支:
   commit 1: "重构 CartItem 组件"
   commit 2: "添加购物车价格计算"

 远程 main 分支（同事已合并）:
   commit X: "优化价格计算公式"
   commit Y: "添加折扣标记"
```

main 上 commit X 和你 commit 2 修改了**同一个文件的同一行**（价格计算逻辑的 `DISCOUNT_RATE`）。

```bash
# ===== 第 1 步：同步 main =====
git switch feature/cart                     # 确保在 feature 分支上
git fetch origin                            # 拉取远程更新

# ===== 第 2 步：rebase 到最新 main =====
git rebase origin/main                      # 等价于先 fetch 再 rebase
# 输出：
# Auto-merging src/cart/calcPrice.js
# CONFLICT (content): Merge conflict in src/cart/calcPrice.js
# error: could not apply d4e5f6a... 添加购物车价格计算
# Resolve all conflicts manually...

# ===== 第 3 步：查看状态 =====
git status
# 输出：
# interactive rebase in progress; onto xxxxxx
# Last command done (1 command done):
#    pick 1a2b3c4 重构 CartItem 组件             ← 这个已经成功 rebase 了
# Next command to do (1 remaining command):
#    pick d4e5f6a 添加购物车价格计算               ← 这个卡住了
#   both modified:   src/cart/calcPrice.js

# ===== 第 4 步：分析冲突 =====
# 打开 src/cart/calcPrice.js，看到：

# <<<<<<< HEAD                                    ← origin/main 的内容
# const DISCOUNT_RATE = 0.88;  // 2024 年折扣
# const TAX_RATE = 0.06;
# function calcFinalPrice(price) {
#   return price * (1 - DISCOUNT_RATE) * (1 + TAX_RATE);
# }
# =======
# const DISCOUNT_RATE = 0.85;  // 促销折扣
# function calcFinalPrice(price, discount = DISCOUNT_RATE) {
#   return price * (1 - discount);
# }
# >>>>>>> d4e5f6a (添加购物车价格计算)

# 分析：
# - main 上：折扣 0.88 + 税率 0.06，函数只收 price
# - 你的代码：折扣 0.85（可传参覆盖），函数可收 discount，没有税率

# 沟通后决定：用 main 的折扣率 0.88（最新的业务要求），
# 但你添加的 discount 参数灵活性保留，税率也保留。

# ===== 第 5 步：手动解决 =====
# 修改为：
# const DISCOUNT_RATE = 0.88;  // 2024 年促销折扣（对齐运营最新要求）
# const TAX_RATE = 0.06;
# function calcFinalPrice(price, discount = DISCOUNT_RATE) {
#   return price * (1 - discount) * (1 + TAX_RATE);
# }

# 删除所有 <<<<<<< ======= >>>>>>> 标记

# ===== 第 6 步：标记已解决并继续 =====
git add src/cart/calcPrice.js

git rebase --continue
# 弹出编辑器，确认 commit message：「添加购物车价格计算」
# 保存退出

# 输出：
# Successfully rebased and updated refs/heads/feature/cart.

# ===== 第 7 步：验证 =====
git log --oneline --graph -5
# 输出：
# * d4e5f6a' 添加购物车价格计算           ← 新 hash，包含了冲突解决
# * 1a2b3c4' 重构 CartItem 组件           ← 新 hash（parent 变了）
# * xxxxxx 添加折扣标记                    ← origin/main
# * xxxxxx 优化价格计算公式                ← origin/main
# * xxxxxx 上一个发布版本                  ← origin/main

# 历史完美线性，你的 commit 都在最顶端！

# ===== 第 8 步：推送（因为 rebase 改变了 hash） =====
git push --force-with-lease origin feature/cart
# --force-with-lease: 如果你的远程分支在 rebase 期间被其他人推送了，
# 它会拒绝覆盖，比 --force 安全。
```

#### 如果中途搞砸了怎么办

```bash
# 方案 A：放弃整个 rebase
git rebase --abort
# 回到 rebase 之前的状态，你的 2 个原始 commit 完好无损

# 方案 B：用 reflog 回到某个时间点
git reflog                                    # 找到 rebase 之前的 HEAD
git reset --hard HEAD@{5}                     # 回到那个时间点

# 方案 C：跳过当前有问题的 commit
git rebase --skip                             # 丢弃「添加购物车价格计算」这个 commit
# ⚠️ 会丢失这个 commit 的所有代码变更，慎用
```

## 常见问题

**Q1：`git pull` 是 `git fetch` + `git merge` 还是 `git fetch` + `git rebase`？**
A：默认是 `fetch + merge`。但强烈推荐设置 `git config --global pull.rebase true`，让它变成 `fetch + rebase`，避免产生无意义的 merge commit。如果你某次确实想 merge，可以 `git pull --no-rebase`。

**Q2：rebase 后 push 被拒绝，必须 `--force` 吗？**
A：是的，因为 rebase 改变了 commit hash。但用 `--force-with-lease` 而不是 `--force`。`--force-with-lease` 会在远程分支有新 commit（说明有别人也在推）时拒绝覆盖，保护你的同事。

**Q3：Squash Merge 和 `git merge --squash` 有什么区别？**
A：一样的效果。Squash Merge 是 GitHub/GitLab 的 UI 操作，底层就是 `git merge --squash` + `git commit`。

**Q4：rebase 到一半，终端关了 / 断电了怎么办？**
A：重新打开终端，`git status` 会显示 `interactive rebase in progress`。你可以 `git rebase --continue`（如果冲突还在）、`git rebase --skip` 或 `git rebase --abort`。

**Q5：`git cherry-pick` 和 `git merge` 有什么区别？**
A：`merge` 把分支上**所有** commit 合进来，`cherry-pick` 只挑**某一个** commit。cherry-pick 不记录两个分支的亲缘关系，是一个纯粹的"复制"操作。

**Q6：什么时候该用 `git stash` 而不是直接 commit？**
A：你的代码还没到能 commit 的程度（编译不过、功能不完整、只是想暂存一下切分支）。如果代码已经是一个逻辑完整的单元，直接 commit 更安全——至少进了 reflog。

**Q7：merge 和 rebase 冲突有什么不同？**
A：解决冲突的操作完全一样。区别在于：merge 只产生一次冲突解决（在 merge commit 中），rebase 可能每个 commit 都产生冲突（因为每个 commit 需要逐个"重放"）。如果 feature 分支有 10 个 commit 且每个都和 main 冲突，rebase 就是地狱——这种场景 merge 更适合。

**Q8：`git revert` 和 `git reset` 有什么区别？**
A：`revert` 创建一个新的 commit 来"撤销"某个 commit，**不修改既有历史**，适合撤销已经共享的提交。`reset` 直接移动当前分支指针，适合整理尚未共享的本地历史；若用它改写已推送分支，通常还要强制推送并影响协作者。公共分支需要保留可追溯历史时优先用 `revert`。

## 实操作业

### 基础练习：交互式 rebase 整理 commit

新建一个 Git 仓库，模拟以下操作：
1. 创建 5 个 commit，模拟混乱的提交历史（fix typo、格式化、WIP 等）
2. 用 `git rebase -i HEAD~5` 整理成 3 个有意义的 commit
3. 过程中练习 `pick`、`fixup`、`squash`、`reword` 四种操作
4. 用 `git log --oneline --graph` 对比整理前后的历史

### 进阶练习：rebase 冲突解决

用两个目录模拟两个开发者（或直接用两个本地仓库）：
1. 仓库 A：在 main 上修改 `utils/format.js` 的 `formatDate` 函数签名
2. 仓库 B：从 main 创建 feature 分支，也修改 `formatDate` 的同一行，同时新增一个新的 `formatCurrency` 函数
3. 仓库 A 先合并到 main
4. 仓库 B `git rebase main`，遇到冲突
5. 解决冲突，保留两个函数的变更，确保代码正确
6. 记录完整的冲突内容和你的解决策略

### 挑战练习：灾难恢复

模拟以下灾难场景并逐一恢复：
1. 你在 feature 分支上开发，rebase main 时产生大量冲突，搞砸了。用 `git reflog` 找回 rebase 之前的状态
2. 你用 `git reset --hard` 误删了最近的 2 个 commit。用 `git reflog` 恢复
3. 你不小心在 main 上 commit 了，还没 push。用 `git reset --soft HEAD~1` 撤销 commit 但保留改动，然后 `git stash` 暂存，切到 feature 分支 `git stash pop`
4. 写一份 200 字的总结：描述每个灾难是因为什么操作发生的，以及恢复的关键命令

## 本节小结

| 要点 | 一句话 |
|---|---|
| merge 三模式 | fast-forward（线性）、--no-ff（保留分支痕迹）、--squash（压缩成一个） |
| rebase 原理 | 不是移动 commit，是逐 commit "重放"，生成新 hash |
| 黄金法则 | 只 rebase 未推送的私有分支，已推送的用 merge |
| rebase -i | squash / fixup / reword / drop，push 前整理历史的利器 |
| 冲突本质 | 两个分支改了同一行，Git 无法自动决定，交给你决策 |
| 冲突流程 | status 查看 → 手动编辑 → add 标记 → continue |
| reflog | 记录本地引用移动；在记录过期或对象被清理前可用于恢复 |
| cherry-pick | 复制特定 commit，紧急场景使用，不要滥用 |
| stash | 临时保存工作区，切分支前的好习惯 |
