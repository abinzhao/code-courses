# 01 — 分支策略与工作流

## 学习目标

- 真正理解 Git 的分布式本质：工作区、暂存区、本地仓库、远程仓库四层模型
- 掌握分支的底层本质：分支只是一个指向 commit 的可移动指针
- 能说清 GitFlow、GitHub Flow、Trunk-Based Development 三种策略的运作方式和适用场景
- 建立规范的分支命名习惯
- 能独立走完 feature 分支 → PR → Code Review → 合并的完整流程
- 会编写有效的 .gitignore

---

## 内容讲解

### 1. Git 的四层模型

很多 Git 教程一开始就让你 `git add`、`git commit`、`git push`，但不解释数据流向。等你理解了这四层，所有命令就穿成了一条线：

```
 ┌──────────┐    git add     ┌──────────┐    git commit    ┌──────────┐    git push     ┌──────────┐
 │  工作区   │ ───────────→  │  暂存区   │ ──────────────→ │ 本地仓库  │ ──────────────→ │ 远程仓库  │
 │ Working  │               │ Staging  │                 │  Local   │                │ Remote   │
 │ Directory│ ←───────────  │  Area    │ ←────────────── │  Repo    │ ←────────────── │  Repo    │
 └──────────┘   git restore  └──────────┘  git reset HEAD  └──────────┘    git pull     └──────────┘
                  git checkout --                                                git fetch
```

| 层 | 存储位置 | 内容 | 对应命令 |
|---|---|---|---|
| 工作区 | 你的磁盘文件 | 当前正在编辑的文件 | `git status` 看到的 modified/untracked |
| 暂存区 | `.git/index` | 下一次 commit 的快照 | `git add` 写入；`git restore --staged` 撤回 |
| 本地仓库 | `.git/objects/` | 完整的版本历史 | `git commit` 写入；`git log` 查看 |
| 远程仓库 | GitHub/GitLab 服务器 | 协作共享的版本历史 | `git push` / `git fetch` / `git pull` |

关键认知：**Git 是分布式的**。你的本地仓库包含完整历史，断网时你可以自由 commit、建分支、看 log，等联网后再 push。这和 SVN 那种「离线就废了」的集中式模型有本质区别。

### 2. 分支的底层本质

很多人觉得分支"很玄"，其实一句话就能说清楚：

> **分支只是一个指向某个 commit 的可移动指针。**

Git 内部的 commit 通过 `parent` 指针形成有向无环图（DAG）：

```
  A ← B ← C    ← main（指向 C）
       ↑
       └── feature（也指向 C，然后你在这个基础上继续 commit）
```

当你 `git commit` 时，Git 做了三件事：
1. 把当前暂存区的内容打包成一个新 commit 对象（包含 tree、parent、author、message）
2. 新 commit 的 parent 指向你当前所在的 commit
3. 把你当前分支的指针从旧 commit 移到新 commit

```bash
# 分支操作的核心就是移动指针
git branch feature/login        # 创建一个指向当前 commit 的新指针（不切换过去）
git switch feature/login        # 把 HEAD 指向 feature/login 分支
git switch -c feature/login     # 创建 + 切换，一步到位

# HEAD 是一个特殊的指针，指向你"当前在哪"
# 可以用 cat .git/HEAD 看它指向谁
```

**为什么分支如此轻量？** 因为创建分支只是写一个 40 字节的文件（里面存的是 commit hash），不复制任何代码。所以你完全可以为每个小任务建分支，用完就删。

### 3. 三种主流分支策略

#### 3.1 GitFlow

由 Vincent Driessen 在 2010 年提出，是"重型"分支策略的标杆。

```
 main     ──●────────────●──────────────●──────────────●──  ← 生产版本
              \          / \            /              /
 develop ─────●──●──●──●───●──●──●───●──────────────────  ← 开发主线
                   \    /     \    /
feature/xxx ────────●──●       ●──●                      ← 功能分支
                              \
release/x.x ───────────────────●──●──────────────────    ← 发布准备
                                       \
hotfix/xxx ─────────────────────────────●──●────────     ← 紧急修复
```

**分支角色**：
- `main`：生产环境代码，每个 commit 对应一个发布版本（打 tag）
- `develop`：开发主线，feature 分支合并到这里
- `feature/*`：从 develop 分出，开发完后合并回 develop
- `release/*`：从 develop 分出，做发布前的最后打磨（修 bug、改版本号），完成后合并到 main 和 develop
- `hotfix/*`：从 main 分出，紧急修复生产问题，完成后合并到 main 和 develop

**适用场景**：发布周期固定（如每月一次）、需要多版本并行维护、团队 10 人以上的传统软件项目。

**缺点**：太重了。大部分前端项目根本用不到 release 分支和 hotfixes 的复杂合并。

#### 3.2 GitHub Flow

GitHub 内部使用的策略，极其简单：

```
 main ──●────────●────────●──  ← 始终可部署
          \      / \      /
feature     ●────●   ●────●   ← 功能分支（寿命短，合并完就删）
```

**规则只有 6 条**：
1. `main` 上的任何东西都是可部署的
2. 从 `main` 创建描述性命名的分支
3. 在分支上频繁 commit 并定期推送到远程
4. 需要反馈 / 讨论 / 准备合并时，开 Pull Request
5. PR 经过 Review 通过后，合并到 `main`
6. 合并后**立即部署**

GitHub Flow 的哲学是"持续部署"。你的 `main` 分支从来不应该处于半成品状态。

**适用场景**：持续部署项目、前端/后端 SaaS、大部分中小团队。这是目前前端团队最常用的策略。

#### 3.3 Trunk-Based Development（主干开发）

极简：**所有人直接往 `main` commit**，不过 feature 藏在 feature flag 后面：

```
 main ──●──●──●──●──●──●──●──●──●──  ← 所有人都在这里
                     ↑
               short-lived
               feature branch（几小时到一天）
```

核心理念：
- 分支存活不超过一天（很多团队甚至不用分支，直接在 main 上小步提交）
- 未完成的功能用 feature flag / toggle 隐藏
- 极其频繁地集成，冲突极小
- 要求扎实的测试覆盖和 CI 自动校验

**适用场景**：Google、Facebook 级别的工程团队（有成熟的 CI/CD 和 feature flag 基础设施）、高迭代速度的 SaaS。

---

### 4. 策略对比

| 维度 | GitFlow | GitHub Flow | Trunk-Based |
|---|---|---|---|
| 团队规模 | 10+ 人 | 2-50 人 | 20+ 人（需要基建） |
| 发布频率 | 数周一次 | 持续部署 / 每日 | 每日多次 |
| 分支寿命 | feature 数天到数周 | feature 数小时到数天 | 数小时（甚至无分支） |
| 长期分支 | main + develop | main | main |
| 学习成本 | 高 | 低 | 中（需要理解 feature flag） |
| 合并冲突概率 | 高（分支活太久） | 低（分支短） | 极低 |
| 版本回滚 | 简单（有 release tag） | 回滚 = 重新部署旧 commit | 关闭 feature flag |

**推荐**：前端团队默认选 **GitHub Flow**。当你的项目复杂到需要 GitFlow 的那一天，你一定已经遇到了足够多的痛，切换时你会清楚为什么需要它。

### 5. 分支命名规范

统一命名是团队协作的基本素养。推荐约定：

```
feature/<模块>-<简短描述>     # 新功能开发
bugfix/<问题编号>-<简短描述>  # Bug 修复
hotfix/<版本>-<简短描述>      # 紧急线上修复
release/<版本号>              # 发布准备
chore/<描述>                  # 杂项：依赖更新、配置修改、重构
```

示例：

```bash
feature/user-auth-login          # ✅ 清晰
feature/login                    # ✅ 也行
feature/fix                       # ❌ 太模糊
bugfix/issue-342-crash-on-null   # ✅ 关联 issue
bugfix/crash                     # ❌ 不知道修什么
chore/upgrade-react-19           # ✅
chore/eslint-config              # ✅
```

**建议**：用 `-` 连接单词，全小写。某些团队用 `/` 分隔模块和描述（如 `feat/user-login`），都可以——**关键是团队统一**。

### 6. PR/MR 协作流程

PR（Pull Request，GitHub）或 MR（Merge Request，GitLab）是协作的核心机制。它不是"通知别人你写完了"，而是**发起一次代码讨论**。

#### 完整流程

```
1. 从 main 创建分支
   git switch -c feature/cart-rebuild

2. 开发 + 频繁提交
   git add src/cart/Cart.jsx
   git commit -m "feat: 重构购物车状态为 Zustand"   ← 规范 commit message
   git push -u origin feature/cart-rebuild

3. 在 GitHub/GitLab 上创建 PR
   - 标题：[类型] 简要描述
   - 描述：做了什么、为什么做、怎么验证
   - 关联 Issue：Closes #123
   - 指定 Reviewer

4. Code Review 迭代
   - Reviewer 提 comment → 你修改 → git push（PR 会自动更新）
   - 如果 main 有新 commit，git rebase main 或 git merge main

5. 合并
   - CI 全部通过 + Reviewer Approved → 点击 Merge
```

#### Code Review 礼仪

**作为提交者**：
- PR 保持小而专注（200 行以内最佳，超过 500 行拆成多个 PR）
- commit message 写清楚「做了什么」和「为什么」
- PR 描述里附上截图 / 录屏 / 测试结果

**作为 Reviewer**：
- 先看整体设计，再看细节实现
- comment 区分「必须改」和「建议改」（用 `nit:` 标记小建议）
- 24 小时内完成 Review（团队约定）

#### 三种合并方式

```
Squash Merge：        Merge Commit：         Rebase Merge：
 main ──●───●──S      main ──●───●──M        main ──●───●──A──B──C
                     \         \ /          （历史是线性的）
 feature ──A──B──C    feature ──A──B──C
```

| 方式 | 效果 | 推荐场景 |
|---|---|---|
| Squash Merge | 所有 commit 压缩成 1 个 | PR 内部有很多混乱的小 commit，合并时整理干净 |
| Merge Commit | 保留完整分支历史，生成一个 merge commit | 大功能开发，希望保留每一步 commit |
| Rebase Merge | feature 分支的 commit 逐个"搬家"到 main 顶端 | 追求线性历史，没有无用 merge commit |

**推荐**：前端项目默认用 **Squash Merge**。你的 PR 是交付的一个功能单元，1 个清晰的 commit message 远好过 15 个 `fix typo`、`update`、`wip`。

### 7. .gitignore 配置策略

原则：**只版本控制源文件，不版本控制生成物和本地环境**。

```gitignore
# 依赖
node_modules/

# 构建产物
dist/
build/
.next/

# 环境变量（含密钥的）
.env
.env.local
.env.*.local

# 编辑器配置（团队是否共享 editorconfig 由你们决定）
.vscode/
.idea/

# 操作系统
.DS_Store
Thumbs.db

# 日志
*.log
npm-debug.log*

# 测试覆盖率
coverage/

# TypeScript 编译缓存
*.tsbuildinfo
```

**关键习惯**：
- `.env` 默认加入 `.gitignore`，但提供一个 `.env.example`（不含真实密钥）作为模板
- 新增依赖时确认 `package-lock.json` / `yarn.lock` / `pnpm-lock.yaml` **一定要提交**

### 8. 实战：模拟完整协作流程

假设你要给一个前端项目添加购物车功能。下面给出完整命令和每步解释：

```bash
# ===== 第 1 步：确保本地 main 是最新的 =====
git switch main                              # 切换到 main 分支
git pull origin main                         # 拉取远程最新代码
# 输出：Already up to date.                  # 确认本地和远程同步

# ===== 第 2 步：创建功能分支 =====
git switch -c feature/cart-rebuild           # 创建并切换到新分支
# 等价于：git branch feature/cart-rebuild && git switch feature/cart-rebuild

# ===== 第 3 步：开发 + 提交 =====
# ... 编辑 src/cart/Cart.jsx ...
git status                                   # 查看改了哪些文件
# 输出：modified: src/cart/Cart.jsx

git add src/cart/Cart.jsx                    # 将改动加入暂存区
git commit -m "feat(cart): 用 Zustand 重构购物车状态管理"  # 提交到本地仓库

# 可以多次 commit，不必一次写完
# ... 继续开发 ...
git add src/cart/CartItem.jsx
git commit -m "feat(cart): 抽离 CartItem 组件"

# ===== 第 4 步：推送到远程 =====
git push -u origin feature/cart-rebuild      # -u 设置上游跟踪，以后只用 git push
# 输出：
# remote: Create a pull request for 'feature/cart-rebuild' on GitHub by visiting:
# remote:   https://github.com/xxx/pull/new/feature/cart-rebuild

# ===== 第 5 步：在 GitHub 创建 PR =====
# 标题：feat(cart): 重构购物车为 Zustand + 优化组件拆分
# 描述：
#   - 移除 useState 局部状态，改用 Zustand create
#   - 拆分 CartItem 和 CartFooter 组件
#   - 持久化到 localStorage（使用 persist 中间件）
#   - 待 Review：折扣计算逻辑放在了 store 还是组件？见 CartFooter.jsx:12
# Closes #88
# 指定 Reviewer：@同事A

# ===== 第 6 步：Code Review 迭代 =====
# 同事 A 提了 3 个 comment：
# 1. Cart.jsx:23 —— 建议用 shallow 防重渲染
# 2. CartItem.jsx:15 —— 缺少加载态处理
# 3. CartFooter.jsx:12 —— 折扣逻辑建议放 store 的 getter

# 你在本地修改代码：
git add src/cart/CartItem.jsx src/cart/CartFooter.jsx
git commit -m "fix(cart): 添加 loading 状态，折扣逻辑移至 store"
git push                                      # 因为已设置上游，直接 push
# PR 页面自动更新，评论对应的 diff 会标记为 "Outdated"

# ===== 第 7 步：同步 main 的更新（如果有） =====
git switch main
git pull origin main
git switch feature/cart-rebuild
git rebase main                              # 把你的 commit 搬到最新 main 之上
# 如果有冲突，参考下一篇教程解决
git push --force-with-lease                  # rebase 后需要 force push
# ⚠️ 注意：--force-with-lease 比 --force 安全，如果远程有新 commit 会拒绝

# ===== 第 8 步：合并 =====
# 在 PR 页面点击 "Squash and merge"
# 输入合并 commit 信息：feat(cart): 重构购物车状态管理（#88）
# 勾选 "Delete branch" → 确认
# ✅ 功能上线！

# ===== 第 9 步：清理本地 =====
git switch main
git pull origin main                         # 拉取合并后的 main
git branch -d feature/cart-rebuild           # 删除本地分支
# 如果提示未合并：git branch -D feature/cart-rebuild
```

**这个流程是你每天都要走的**。熟练了之后，从建分支到开 PR 不会超过 30 秒。

## 常见问题

**Q1：为什么我 `git push` 被拒绝，提示 `Updates were rejected`？**
A：远程分支有你本地没有的 commit（通常是同事推了新代码，或者你在另一台机器上改了）。先 `git pull`（或 `git pull --rebase`）把远程变更同步下来，再 push。如果用了 rebase 解决冲突，需要用 `git push --force-with-lease`。

**Q2：GitFlow 的 release 分支到底有没有必要？**
A：对大部分前端项目来说——没有必要。如果你有独立的上线窗口（如 iOS App Store 审核期间需要冻结代码），release 分支才有意义。前端持续部署项目用 GitHub Flow 就够了。

**Q3：什么时候该用 Merge Commit 而不是 Squash Merge？**
A：当一个 PR 中的多个 commit 之间存在有意义的步骤区分，丢掉它们会损失信息时。比如一个 API 迁移 PR 包含「添加新接口 → 双写 → 切换读取 → 清理旧代码」四个独立可回滚的步骤，保留每个 commit 有助于未来排查问题。

**Q4：`.gitignore` 不生效怎么办？**
A：`.gitignore` 只对**未跟踪**的文件生效。如果你之前已经 `git add` 了某个文件，它已经在 Git 的索引中，`.gitignore` 拦不住它。需要用 `git rm --cached <file>` 从索引中移除，然后重新 `.gitignore`。

**Q5：commit message 到底怎么写？**
A：推荐 [Conventional Commits](https://www.conventionalcommits.org/) 格式：`type(scope): description`。示例：`feat(auth): 添加短信验证码登录`、`fix(cart): 修复空购物车崩溃`、`chore(deps): 升级 React 到 19.1`。type 常用：feat / fix / refactor / chore / docs / test / style。

**Q6：同事直接 push 到 main 了怎么办？**
A：第一，在 GitHub 上给 main 分支开启 Branch Protection Rules（要求 PR + Review 才能合并）。第二，和同事沟通流程——这不是技术问题，是协作习惯问题。

**Q7：PR 太大会不会被同事吐槽？**
A：会。经验法则：超过 400 行的 PR，Reviewer 找到问题的概率会下降。把大功能拆成多个小 PR：先重构不改变行为的代码（一个 PR），再加新功能（一个 PR），最后加测试（一个 PR）。

**Q8：我怎么知道本地分支是否和远程同步？**
A：`git status` 会告诉你 `Your branch is ahead of 'origin/main' by 2 commits`。或者用 `git log main..origin/main` 看远程有哪些你还没有的 commit。

## 实操作业

### 基础练习：走通一次完整流程

用你自己的一个项目（或新建一个 demo），完成如下流程：
1. 从 main 创建 `feature/add-footer` 分支
2. 添加一个 footer 组件，分 2 次 commit（一次 HTML 结构，一次样式）
3. 推送到远程，创建 PR（没有远程仓库就用 GitHub/GitLab 建一个）
4. 自己模拟 Review：在 PR 页面留一条 comment，然后修改代码、push
5. 用 Squash Merge 合并到 main
6. 删除本地和远程分支

截图记录最后 `git log --oneline --graph` 的输出。

### 进阶练习：多人协作模拟

找一个同事（或用两个终端模拟两个开发者）：
1. 开发者 A 创建 `feature/modify-header`，修改 header 组件，推送到远程
2. 开发者 B 创建 `feature/modify-footer`，修改 footer 的同一个文件的同一行，推送到远程
3. 开发者 A 先合并到 main
4. 开发者 B 尝试合并时遇到冲突，通过 `git rebase main` 解决冲突
5. 记录你遇到的冲突内容和解决过程

### 挑战练习：为团队制定分支规范

假设你是新团队的技术负责人，团队 5 人，前端项目，每周发布 2 次。请完成：
1. 写出你选择的策略（GitFlow / GitHub Flow / Trunk-Based），附 100 字理由
2. 画出分支流转图（ASCII 风格）
3. 写出 5 条团队必须遵守的规则（如「所有合并必须通过 PR + 至少 1 人 Review」）
4. 配置 main 分支的 Branch Protection Rules（列出具体配置项）
5. 预测团队运行 1 个月后可能出现的 3 个协作问题，并给出预防方案
