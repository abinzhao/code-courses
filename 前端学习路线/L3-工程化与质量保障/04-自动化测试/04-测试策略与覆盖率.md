## 内容讲解

### 一、测试金字塔：经典模型

Mike Cohn 在 2009 年提出的测试金字塔至今仍是入门的基准模型：

```
         ┌──────────┐
         │  E2E 测试  │  少：只测核心用户流程
         │  (UI 层)   │  ~10%
        ┌┴──────────┴┐
        │  集成测试   │  中：测模块间的协作
        │  (API/组件)  │  ~20%
       ┌┴────────────┴┐
       │   单元测试    │  多：测独立逻辑
       │  (函数/模块)  │  ~70%
       └─────────────┘
```

**金字塔的核心思想：下层测试多、上层测试少。** 原因很直观：

| 维度 | 单元测试 | 集成测试 | E2E |
|------|---------|---------|-----|
| 运行速度 | 毫秒 | 秒 | 分钟 |
| 定位问题 | 精确到行 | 缩小到模块 | 只知道"某个流程挂了" |
| 维护成本 | 低 | 中 | 高（UI 一改就红） |
| 运行环境 | Node.js | Node.js（jsdom） | 真实浏览器 + 真实后端 |
| flaky 概率 | ~0% | ~5% | ~15% |

**代码示例——从底层到顶层的三层测试覆盖：**

```typescript
// ===== 第 1 层：单元测试（测纯函数逻辑） =====
// utils/order.test.ts
describe('calculateTotal', () => {
  it('折扣 + 运费正确计算', () => {
    const items = [{ price: 100, qty: 2 }, { price: 50, qty: 1 }]
    const result = calculateTotal(items, { discount: 0.1, shipping: 15 })
    // 100*2 + 50*1 = 250 → 折扣 10% = 225 → + 运费 15 = 240
    expect(result).toBe(240)
  })

  it('空购物车总价为 0', () => {
    expect(calculateTotal([], { discount: 0, shipping: 0 })).toBe(0)
  })
})

// ===== 第 2 层：集成测试（测组件 + API 交互） =====
// Cart.test.tsx
describe('Cart 组件', () => {
  it('添加商品后总价正确显示', async () => {
    render(<Cart />)
    const user = userEvent.setup()

    // 模拟添加商品
    await user.click(screen.getByRole('button', { name: '添加商品 A' }))
    await user.click(screen.getByRole('button', { name: '添加商品 B' }))

    // 验证总价显示
    expect(screen.getByTestId('total-price')).toHaveTextContent('¥350.00')
  })
})

// ===== 第 3 层：E2E 测试（测完整下单流程） =====
// checkout.spec.ts
test('用户完成完整下单流程', async ({ page }) => {
  await page.goto('/products')
  await page.getByRole('button', { name: '加入购物车' }).first().click()
  await page.goto('/cart')
  await page.getByRole('button', { name: '去结算' }).click()
  await page.getByLabel('收货地址').fill('北京市朝阳区')
  await page.getByRole('button', { name: '提交订单' }).click()
  await expect(page.getByText('下单成功')).toBeVisible()
})
```

### 二、测试奖杯模型：更现代的视角

Kent C. Dodds 提出的测试奖杯（Testing Trophy）重新分配了各层权重：

```
       ┌──────────┐
       │  E2E      │  很少：核心 Sanity Check
       │           │
      ┌┴──────────┴┐
      │  集成测试   │  主力：组件 + API 交互测试
      │  (最多份量) │
      │           │
     ┌┴───────────┴┐
     │  静态分析    │  TypeScript + ESLint
     │             │
     └────────────┘
     │  单元测试    │  少：只测纯逻辑函数
     └────────────┘
```

**奖杯模型为什么把集成测试放在最大一层？**

因为你写的大部分前端代码不是纯函数，而是"组件 + 状态 + API 调用"的组合。单独测一个纯函数意义不大——真正的 Bug 往往出现在这些模块的**边界**上：你传了 `undefined` 给一个期待 `string` 的组件、API 返回了意料之外的数据结构、两个组件之间共享的 state 不同步。

**一句话总结两种模型的取舍：** 如果你的代码是工具库（lodash、日期处理等），遵循金字塔。如果你是业务前端应用，遵循奖杯模型——把大部分测试投资在组件集成测试上。

### 三、各层测试的投入产出比

| 测试类型 | 写一条的时间 | 对信心的贡献 | 维护成本 | 适用场景 |
|---------|-----------|-----------|---------|---------|
| 纯函数单测 | 2 分钟 | ★★★ 对逻辑极有信心 | 低 | 工具函数、算法、数据转换 |
| 组件集成测试 | 10 分钟 | ★★★★★ 对 UI 行为极有信心 | 中 | 表单、列表、交互组件 |
| API mock 测试 | 5 分钟 | ★★★★ 对前后端契约有信心 | 中 | 数据获取层 |
| E2E | 30 分钟 | ★★★★ 对整体流程有信心 | 高 | 核心业务流（登录、下单） |
| 快照测试 | 1 分钟 | ★ 低 | 极高 | 几乎不推荐，除非配置对象 |

**判断测试优先级的简化模型：**

```
测试优先级 ∝ 失败概率 × 失败影响 × 变更频率 ÷ 编写与维护成本
```

- 核心支付逻辑：出错影响巨大 → 用决策表覆盖金额、幂等、权限和失败补偿，不能只看行覆盖率
- 年度归档页面：一年改一次，出错了影响小 → 不需要 E2E，基础渲染测试即可
- 营销落地页：频繁改，但影响小 → 写冒烟测试（能渲染就行）

### 四、覆盖率的真相

**覆盖率是一个工程指标，不是一个质量指标。**

```
覆盖率 = 被测试执行的代码行 / 总代码行
```

它只回答一个问题："这行代码有没有被执行过？" 不回答"这行代码的逻辑被正确验证了吗？"

看一个经典的覆盖率陷阱：

```typescript
// 这个函数有 100% 的覆盖率，但测试完全没用
export function divide(a: number, b: number): number {
  if (b === 0) {
    throw new Error('除数不能为零')
  }
  return a / b
}

// 测试：达到 100% 覆盖率
it('正常除法', () => {
  expect(divide(10, 2)).toBe(5)
  // 一行测试就覆盖了除数为零的分支……但你没有验证它抛出异常的行为！
})

// 这行测试确实"执行"了 throw 语句——但如果你看覆盖率报告，这行也被标记为绿色。
// 实际上你的测试根本没有走到 throw 分支，覆盖率却显示 100%。
// 为什么？因为你没验证 throw 行为，等于没测。
```

**确实有意义的断言覆盖 vs 无效的行覆盖：**

```typescript
// ✅ 好的测试：验证了行为
it('除数为零时抛出异常', () => {
  expect(() => divide(10, 0)).toThrow('除数不能为零')
})

it('正常返回商', () => {
  expect(divide(10, 2)).toBe(5)
  expect(divide(0, 5)).toBe(0)
  expect(divide(-6, 2)).toBe(-3)
})

// ❌ 只有一个断言，覆盖率一样 100%，但信心完全不同
```

**覆盖率配置建议：**

```typescript
// vite.config.ts 中的覆盖率阈值
coverage: {
  thresholds: {
    lines: 80,        // 全局行覆盖率 80%
    branches: 75,     // 分支覆盖率可以稍低
    functions: 80,
    // 按文件目录设定更细粒度的阈值
    'src/utils/**': {
      lines: 95,      // 工具函数要求更高
      branches: 90,
    },
    'src/components/**': {
      lines: 70,      // 组件可以稍低
    },
  },
}
```

**不要追求 100% 数字的四个理由：**
1. 有些代码不值得测（简单的 getter/setter）
2. 覆盖率 100% 会给你虚假的安全感
3. 为达标而写的无意义测试反而是技术债
4. 把时间花在更有价值的测试上，而不是凑覆盖率

### 五、写多少测试算够？

没有一个固定的数字。但有一套判断框架：

| 代码类型 | 测试策略 | 目标 |
|---------|---------|------|
| 核心业务逻辑（支付、权限） | 按业务规则建立决策表，覆盖边界、拒绝和补偿路径 | 需求与风险覆盖，可辅以高分支阈值 |
| 数据处理函数 | 正常 + 边界 + 异常，必要时加入属性测试 | 关键分支和不变量被验证 |
| 表单组件 | 正常提交、每个校验规则、错误提示、loading 态 | 行为覆盖 |
| 列表/展示组件 | 空数据、有数据、加载中、错误重试 | 状态覆盖 |
| 路由配置 | 测试权限、重定向、参数和 404 等业务行为 | 路由契约覆盖 |
| 第三方 UI 库 | 不重复测内部实现，测试应用的适配与关键集成 | 集成契约覆盖 |
| E2E | 只测核心流程（登录、注册、下单） | 流程覆盖 |

**更实用的问法：**

不要问"覆盖率多少？"，问下面四个问题：
1. 如果这里出错，用户能不能完成核心任务？
2. 如果这里出错，我们能在 CI 中发现吗？
3. 这个测试如果失败，我能不能快速定位问题？
4. 这个测试的维护成本，团队能接受吗？

### 六、TDD：测试驱动开发

TDD 的三步循环：

```
  RED          GREEN         REFACTOR
（写失败测试）→（写最少代码让测试通过）→（重构代码）
    ↑                                        │
    └──────────────────────────────────────┘
```

**一个真实的 TDD 过程：**

```typescript
// ===== RED：先写测试，测试是红的 =====
describe('validatePassword', () => {
  it('密码少于 8 个字符返回 false', () => {
    // 这个函数还不存在！测试必然失败 ✓
    expect(validatePassword('abc123')).toBe(false)
  })
})
// 运行测试 → ❌ FAIL（函数 undefined）

// ===== GREEN：写最少代码让测试通过 =====
function validatePassword(password: string): boolean {
  // 最少代码：直接 return false 就能让测试通过
  // 但我们是人，不是 CI，所以写合理的最少代码
  return password.length >= 8
}
// 运行测试 → ✅ PASS

// ===== REFACTOR：强化边界，补充测试 =====
it('至少包含一个数字', () => {
  expect(validatePassword('abcdefgh')).toBe(false)
})
// → RED（现在测试失败）

// → GREEN：补充逻辑
function validatePassword(password: string): boolean {
  return password.length >= 8 && /\d/.test(password)
}

it('至少包含一个大写字母', () => {
  expect(validatePassword('abc12345')).toBe(false)
  expect(validatePassword('Abc12345')).toBe(true)
})
// → RED → GREEN，继续循环
```

**TDD 的适用场景：**
- ✅ 纯函数、算法、数据转换逻辑
- ✅ API 端点、后端服务层
- ✅ 有明确输入输出的工具函数
- ❌ UI 布局和样式（你很难"先写测试"）
- ❌ 探索性开发（你还没想清楚 API 长什么样）
- ❌ 快速原型（TDD 会拖慢试错节奏）

**TDD 的核心价值不在测试本身，而在于它迫使你先思考 API 的设计。** 如果你先写实现再补测试，你很容易写出测试不了的代码。如果你先写测试，你天然就会设计出可测试的 API。

### 七、测试代码也是一种代码

很多人写业务代码用 SOLID，写测试代码就放飞自我。测试代码和业务代码一样需要维护——甚至更多，因为它是"代码的代码"。

**测试代码的坏味道：**

```typescript
// ❌ 坏味道 1：重复的 setup
describe('UserList', () => {
  it('测试 A', () => {
    render(<UserList />)
    const user = userEvent.setup()
    // 50 行 setup...
  })
  it('测试 B', () => {
    render(<UserList />)
    const user = userEvent.setup()
    // 50 行相同的 setup...
  })
})

// ✅ 重构：把重复逻辑抽到 beforeEach
describe('UserList', () => {
  beforeEach(() => {
    render(<UserList />)
  })
  it('测试 A', async () => {
    // 直接测试核心逻辑，setup 已在 beforeEach 中
  })
})

// ❌ 坏味道 2：测试不知道测什么
it('test submit', async () => {
  // 20 行操作，5 个不相关的断言，一个失败全红
  // 失败了不知道到底哪个行为出了问题
})

// ✅ 重构：一个用例只测一件事
it('提交后成功提示出现', async () => { /* ... */ })
it('提交后表单被清空', async () => { /* ... */ })
it('提交后按钮被禁用', async () => { /* ... */ })

// ❌ 坏味道 3：魔法数字
expect(getDiscount(150)).toBe(135) // 135 怎么来的？
// ✅ 用推导
const original = 150
const expected = original * 0.9
expect(getDiscount(original)).toBe(expected)
```

### 八、CI 中集成测试的最佳实践

测试真正的价值在 CI（持续集成）中体现——每次提交自动跑测试，阻止坏的代码进入主分支。

```yaml
# .github/workflows/test.yml
name: 测试

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  # Job 1：单元测试 + 类型检查（快，并行跑）
  unit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
      - run: npm ci
      - run: npx vitest --coverage --reporter=junit
      - name: 上传覆盖率
        uses: actions/upload-artifact@v4
        with:
          name: coverage
          path: coverage/

  # Job 2：E2E 测试（慢，只跑关键 spec）
  e2e:
    runs-on: ubuntu-latest
    needs: unit  # 单元测试过了才跑 E2E——节省 CI 资源
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - run: npx playwright test --project=chromium
      - name: 上传失败截图
        if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: e2e-screenshots
          path: test-results/
```

**CI 测试配置黄金法则：**

1. **快速失败：** 单元测试先跑，不过就不跑 E2E（`needs: unit`）
2. **并行执行：** 单元测试和 lint 并行，E2E 的多个 project 并行
3. **只跑变化的：** 大型项目用 Vitest 的 `--changed` 标志和 Playwright 的分片
4. **测试失败 = 不能合并：** 在 GitHub 上设置 Branch Protection，必须所有 CI 通过
5. **保存产物：** 失败时上传截图、trace、JUnit 报告，方便事后排查
6. **定期全量跑：** 增量测试可能漏掉边缘影响，每天凌晨跑一次全量

### 九、实战：为一个中等复杂度项目制定测试策略

假设你正在做一个「团队任务管理」的单页应用，功能包括：

- 注册 / 登录 / 退出
- 创建项目、查看项目列表
- 在项目中创建任务、分配执行人、修改状态（待处理/进行中/已完成）
- 任务列表支持搜索和筛选
- 个人仪表盘（我创建的任务、指派给我的任务、即将到期的任务）

**这个项目的测试策略应该怎么定？**

```
【项目结构】
└── src/
    ├── utils/          ← 工具函数（格式化日期、状态映射、权限判断）
    ├── api/            ← API 层（axios 封装、请求拦截、错误处理）
    ├── components/     ← 共享组件（TaskCard、StatusBadge、SearchBar）
    ├── pages/          ← 页面组件（Login、Dashboard、ProjectDetail）
    └── hooks/          ← 自定义 Hooks（useAuth、useTasks、useDebounce）
```

**分层测试策略：**

**第一层：单元测试（约 30% 的测试投入）**

```typescript
// ✅ 测 utils/ —— 纯逻辑，单元测试最合适
// formatDate、getStatusLabel、canEditTask 等
// 目标：100% 函数覆盖 + 100% 分支覆盖

// ✅ 测 hooks/ —— 使用 renderHook 测试
// useDebounce 的防抖逻辑
// useTasks 的状态管理（增删改查）
describe('useTasks', () => {
  it('addTask 增加一条任务到列表中', () => { /* ... */ })
  it('toggleTask 切换任务的完成状态', () => { /* ... */ })
  it('deleteTask 从列表中移除指定任务', () => { /* ... */ })
})
```

**第二层：组件集成测试（约 50% 的测试投入）**

```typescript
// ✅ 测 components/TaskCard —— 各种状态展示
describe('TaskCard', () => {
  it('待处理任务显示灰色标签', () => { /* ... */ })
  it('逾期任务显示红色边框', () => { /* ... */ })
  it('点击完成按钮切换状态', () => { /* ... */ })
  it('分配执行人显示头像', () => { /* ... */ })
})

// ✅ 测 pages/Login —— 表单完整交互
describe('LoginPage', () => {
  it('正确账号密码登录成功并跳转', () => { /* ... */ })
  it('错误密码显示错误提示', () => { /* ... */ })
  it('空用户名校验', () => { /* ... */ })
})

// ❌ 不测：TaskCard 的 CSS 类名（除非类名是功能的载体）
// ❌ 不测：第三方日期选择器的行为
```

**第三层：E2E（约 20% 的测试投入）**

```typescript
// ✅ 测核心流程，每个一条 happy path

// 注册 + 登录 + 创建项目流程
test('新用户注册并创建第一个项目', async ({ page }) => {
  // 注册 → 登录 → 创建项目 → 验证项目出现在列表中
})

// 任务状态流转
test('任务从待处理流转到已完成', async ({ page }) => {
  // 登录 → 进入项目 → 创建任务 → 开始任务 → 完成任务 → 验证状态变化
})

// 搜索 + 筛选
test('按关键词和状态筛选任务', async ({ page }) => {
  // 登录 → 进入项目 → 搜索关键词 → 筛选状态 → 验证结果
})

// ❌ 不测：每一个表单验证规则的边界（单元测试已经覆盖了）
// ❌ 不测：空状态下的样式（用视觉回归测试，不要用 E2E）
```

**一个中型项目的示例投入分配（不是统一配额）：**

| 层 | 用例数 | 预期时间 | 覆盖范围 |
|----|-------|---------|---------|
| 单测（utils + hooks） | ~40 | 开发同期完成 | 纯逻辑 90%+ |
| 组件集成测试 | ~50 | 开发同期完成 | 组件行为 80%+ |
| E2E | ~8 | 关键流程形成时同步补充 | 每条 P0 用户旅程至少一条稳定主路径 |
| **合计** | **~100** | **初期投入 3-5 天，后续每个功能 1-2 小时** | |

## 常见问题

**Q1：新项目什么时候开始写测试？**
从第一条有业务风险的行为开始。纯展示原型可以先快速验证方向，但一旦形成需要长期维护的契约，就应在同一个改动中补测试，不把测试长期留作“以后再补”。

**Q2：老项目没测试，怎么补？**
不要试图一次补全。用"侦察兵策略"：每次改一个模块时，给这个模块加测试。六个月后，改动频繁的模块自然就有测试了，不变的模块没测试也无所谓。

**Q3：TDD 真的能提升代码质量吗？**
能——但不是因为多测了几个分支。而是因为 TDD 迫使你在写代码之前先想清楚 API 的输入输出。难测试的 API 往往是坏设计。但 TDD 不是所有场景都适用（见第六节），合理使用即可。

**Q4：覆盖率设多少合适？**
没有跨项目通用数字。先记录现有基线，再按模块风险设置分支/行阈值并逐步提高；公共库、权限和金额逻辑通常比展示页面要求更高。阈值用于发现退化，不能替代断言质量、变异测试或关键路径 E2E。

**Q5：测试应该谁写？**
实现者应对改动的单元和组件测试负责；QA、开发和产品可共同定义验收风险，E2E 由最了解流程且能维护它的人编写。所有权可以因团队而异，但不应把质量责任完全转交给某一个角色。

**Q6：测试失败但代码没错怎么办？**
先判断是代码问题还是测试问题。如果是测试过度耦合到实现细节，修复测试。如果是时序问题（flaky），加固测试的等待逻辑。如果是后端数据变了，更新 mock。**永远不要注释掉测试或 skip 掉让它"通过"。**

**Q7：AI 生成的测试可信吗？**
可以当作起点，但不能盲信。AI 倾向于生成 happy path 测试，缺少边界和异常场景。用它生成框架，你来补充真正有意义的断言和边界用例。

**Q8：如何在团队中推广测试文化？**
不要在 Code Review 时强制要求测试覆盖率——那只会催生凑数的测试。更好的方式是：在复杂模块的 Code Review 中，reviewer 问"这个场景你手动验证过吗？能写成测试吗？"——让测试成为帮助开发者自己放心的工具，而不是卡流程的门槛。

## 实操作业

### 🟢 基础：为一个工具库设计测试策略

一个日期处理工具库包含：`format`、`addDays`、`diffDays`、`isWeekend`、`getStartOfWeek`。请写出：

1. 哪些函数需要单元测试？（答案：全部）
2. 每个函数需要覆盖哪些场景？（正常 / 边界 / 异常）
3. 合理的覆盖率目标是多少？（建议 95%+）
4. 需要 E2E 吗？（不需要——纯函数没有 UI 流程）

### 🟡 进阶：为团队任务管理应用写测试策略文档

参考第九节的示例，为一个"图书馆借阅系统"（搜索图书 → 借阅 → 归还 → 逾期提醒）写一份测试策略。要求包含：
- 项目结构划分和各层测试类型
- 每层至少列出 3 个具体测试场景
- 工具函数、组件、E2E 的投入比例
- 一个 `playwright.config.ts` 的多项目配置

### 🔴 挑战：用 TDD 实现一个数据校验库

从零开始，严格按照 **Red → Green → Refactor** 循环，实现一个表单校验库，至少包含：
- `required(value)`：非空校验
- `minLength(value, len)`：最小长度
- `pattern(value, regex)`：正则匹配
- `compose(...validators)`：组合多个校验器

要求：
- 每次只写一个测试，红 → 绿 → 重构 → 下一个测试
- 用 git 记录每一步的代码快照（commit message 用 RED/GREEN/REFACTOR 前缀）
- 对这个小型练习达到 100% 分支覆盖率，并说明为什么这仍不能证明逻辑正确
- 至少手工制造一个错误实现，确认测试会失败
- 写一份简短反思：TDD 过程中哪些地方让你感觉有价值，哪些地方让你感觉繁琐

### 作业参考与验收

- **基础**：日期函数覆盖闰年、时区、夏令时、周起始与非法输入；纯函数无需 UI E2E。覆盖率帮助找未执行分支，加入错误实现或变异验证测试是否真能发现问题。
- **进阶**：借阅系统按规则/组件/API/旅程分层；库存并发与权限在集成层，关键借还链在 E2E。比例按风险与成本决定，多项目浏览器配置以真实目标为准。
- **挑战**：required/minLength/pattern/compose 每轮先红再绿；正则 global 的 lastIndex 不能让重复校验不一致。100% 分支仍可能漏输入组合，注入错误并确认失败。

## 本节小结

- 测试金字塔：单元多、集成中、E2E 少；奖杯模型：集成多、单元和 E2E 少
- 前端业务项目优先遵循奖杯模型——组件集成测试是主力
- 覆盖率是工程指标不是质量指标：测到了 ≠ 测对了
- 判断是否值得测：该逻辑出错的影响 × 该逻辑变化的频率（指数为负）
- TDD 三步循环：RED（写失败测试）→ GREEN（最少代码通过）→ REFACTOR（优化）
- TDD 适用纯函数和 API 层，不适用 UI 布局和探索性开发
- 测试代码同样需要维护：避免重复 setup、一个用例只测一件事、用推导代替魔法数字
- CI 中：单元先跑（快失败） → E2E 后跑、并行执行、失败不合并、保存产物、定期全量
- 老项目用"侦察兵策略"补测试：改哪个模块就给哪个模块加
