## 内容讲解

### 一、环境变量的概念和用途

前端代码在开发机上、测试服务器上、正式线上运行时，依赖的外部资源不同（API 地址、CDN 域名、调试工具等）。如果每次切换环境都手动改代码，不但低效而且容易出错。

**环境变量的本质：** 在构建时或运行时，将不同的配置注入到代码中，让同一份源码适配不同的运行环境。

#### 典型用途

| 变量 | 开发环境 | 测试环境 | 生产环境 |
|------|---------|---------|---------|
| `API_BASE_URL` | `http://localhost:8080` | `https://test-api.example.com` | `https://api.example.com` |
| `CDN_URL` | `/`（本地） | `https://test-cdn.example.com` | `https://cdn.example.com` |
| `DEBUG_MODE` | `true` | `true` | `false` |
| `APP_VERSION` | `1.0.0-dev` | `1.0.0-rc.1` | `1.0.0` |
| `SENTRY_DSN` | `''`（不上报） | `'https://xxx@sentry.io/2'` | `'https://xxx@sentry.io/1'` |
| `ENABLE_MOCK` | `true` | `false` | `false` |

### 二、Vite 的环境变量机制

#### .env 文件体系

Vite 使用 **dotenv** 从以下文件中加载环境变量，加载优先级从低到高：

```
.env                  # 所有环境都加载（兜底值）
.env.local            # 所有环境都加载，但被 git 忽略（放敏感信息）
.env.development      # 仅 vite dev 时加载
.env.production       # 仅 vite build 时加载
.env.staging          # 自定义模式，通过 --mode staging 指定
```

**高优先级的文件覆盖低优先级的同名变量。**

#### 文件示例

```bash
# .env —— 所有环境的兜底值
VITE_APP_TITLE=My Application
VITE_API_TIMEOUT=10000
```

```bash
# .env.development —— 开发环境覆盖
VITE_API_BASE_URL=http://localhost:8080/api
VITE_ENABLE_MOCK=true
VITE_DEBUG_PANEL=true
```

```bash
# .env.production —— 生产环境覆盖
VITE_API_BASE_URL=https://api.example.com
VITE_ENABLE_MOCK=false
VITE_DEBUG_PANEL=false
```

```bash
# .env.staging —— 预发环境（通过 vite build --mode staging 使用）
VITE_API_BASE_URL=https://staging-api.example.com
VITE_ENABLE_MOCK=false
VITE_DEBUG_PANEL=true   # 预发环境保留调试面板方便验收
```

#### 在代码中使用

```typescript
// 在任何 .ts / .tsx / .js 文件中
console.log(import.meta.env.VITE_API_BASE_URL)
console.log(import.meta.env.MODE)        // 当前模式：development / production / staging
console.log(import.meta.env.DEV)         // boolean，是否为开发模式
console.log(import.meta.env.PROD)        // boolean，是否为生产模式
```

**关键规则：只有 `VITE_` 前缀的变量才会暴露给客户端代码。** 这是安全机制——防止意外的敏感变量泄漏到浏览器。

#### 类型安全的环境变量

```typescript
// src/vite-env.d.ts —— 扩展环境变量类型
/// <reference types="vite/client" />

interface ImportMetaEnv {
  /** API 基础地址 */
  readonly VITE_API_BASE_URL: string
  /** 是否启用 Mock */
  readonly VITE_ENABLE_MOCK: string  // 注意：.env 中的值总是 string！
  /** 是否显示调试面板 */
  readonly VITE_DEBUG_PANEL: string
  /** 应用标题 */
  readonly VITE_APP_TITLE: string
}

interface ImportMeta {
  readonly env: ImportMetaEnv
}
```

#### 自定义模式

```bash
# package.json —— 定义不同模式的构建脚本
{
  "scripts": {
    "dev": "vite",                          # 默认 mode=development
    "build:test": "vite build --mode test",          # 自定义测试环境构建
    "build:staging": "vite build --mode staging",    # 自定义预发环境构建
    "build:prod": "vite build --mode production",    # 生产环境构建
    "preview:staging": "vite preview --mode staging" # 本地预览预发包
  }
}
```

```bash
# .env.test —— 对应 mode=test 的环境变量
VITE_API_BASE_URL=https://test-api.example.com
VITE_ENABLE_MOCK=false
```

### 三、Webpack 的环境变量

#### DefinePlugin：编译时替换

```javascript
// webpack.config.js
const webpack = require('webpack')

module.exports = {
  plugins: [
    new webpack.DefinePlugin({
      // 注意：值必须是 JSON 字符串或带引号的字符串
      'process.env.API_BASE_URL': JSON.stringify('https://api.example.com'),
      'process.env.APP_VERSION': JSON.stringify('1.0.0'),
      'process.env.DEBUG': JSON.stringify(false),
      // 如果直接写字符串不加 JSON.stringify，会被当作变量名
    }),
  ],
}
```

**`DefinePlugin` 的本质是「宏替换」**：在编译阶段，直接把代码中的 `process.env.API_BASE_URL` 替换为 `"https://api.example.com"`。这意味着它不是运行时读取，而是编译时固化。

#### 使用 --env 参数

```javascript
// webpack.config.js —— 导出函数接收 env 参数
module.exports = (env, argv) => {
  const isProd = argv.mode === 'production'

  return {
    mode: argv.mode,
    plugins: [
      new webpack.DefinePlugin({
        'process.env.API_BASE_URL': JSON.stringify(
          isProd
            ? 'https://api.example.com'
            : 'http://localhost:8080'
        ),
      }),
    ],
  }
}
```

```bash
# 命令行传入
npx webpack --env API_URL=https://staging-api.example.com --mode production

# 在 webpack.config.js 中接收
module.exports = (env) => {
  console.log(env.API_URL) // 'https://staging-api.example.com'
}
```

#### dotenv-webpack：使用 .env 文件

```bash
npm install dotenv-webpack -D
```

```javascript
// webpack.config.js
const Dotenv = require('dotenv-webpack')

module.exports = (env, argv) => ({
  plugins: [
    new Dotenv({
      path: `.env.${argv.mode}`,  // 按 mode 加载不同的 .env 文件
      safe: false,                // 是否要求所有变量都在 .env.example 中声明
      systemvars: true,           // 是否加载系统环境变量
    }),
  ],
})
```

### 四、环境变量命名规范

| 工具/框架 | 前缀 | 原因 |
|-----------|------|------|
| Vite | `VITE_` | 只有此前缀的变量暴露给客户端，防止误泄漏 |
| Create React App | `REACT_APP_` | 同上的安全机制 |
| Vue CLI | `VUE_APP_` | 同上的安全机制 |
| Next.js | `NEXT_PUBLIC_` | `NEXT_PUBLIC_` 前缀暴露客户端，不带前缀仅服务端可见 |
| 自定义（Webpack） | 任意（建议统一前缀） | DefinePlugin 无限制，但建议用 `APP_` 或 `PUBLIC_` |

**原则：给暴露到浏览器的变量统一前缀，不暴露任何密钥、私密 Token。**

### 五、mode 的概念

`mode` 是一个特殊的「元变量」，不仅改变你的代码行为，还改变打包工具的内置优化策略：

| 特性 | `development` | `production` |
|------|---------------|--------------|
| 代码压缩 | 不压缩 | 压缩（Terser/esbuild） |
| Tree Shaking | 不启用 | 启用 |
| Source Map | `eval-cheap-module-source-map` | 不生成（Vite 默认） |
| `process.env.NODE_ENV` | `'development'` | `'production'` |
| CSS 提取 | 一般不提取 | 提取为独立文件 |
| 错误提示 | 详细 | 精简 |

**staging 模式的设计：** staging 是一种「类 production 但有调试能力」的模式。通常在 production 基础上保留 sourcemap 和调试面板，用于上线前的最后验证。

```bash
# 创建 staging 模式
vite build --mode staging

# .env.staging
VITE_DEBUG_PANEL=true
VITE_ENABLE_SOURCE_MAP=true
```

### 六、多环境构建策略

#### 四环境体系

```
开发环境 (dev)  →  测试环境 (test)  →  预发环境 (staging)  →  生产环境 (production)
   │                    │                      │                      │
   │                    │                      │                      │
 本地开发              QA 测试              上线前验证            最终用户
 Mock 数据             真实接口             真实接口              真实接口
 热更新                CDN 测试域名         CDN 预发域名          CDN 生产域名
 完整调试工具          部分调试工具          调试面板可选          无调试工具
```

#### 统一的环境变量访问层

```typescript
// src/config/env.ts —— 统一的环境变量访问，提供类型安全和默认值
export const env = {
  /** 当前构建模式 */
  mode: import.meta.env.MODE as 'development' | 'test' | 'staging' | 'production',

  /** API 基础地址 */
  apiBaseUrl: import.meta.env.VITE_API_BASE_URL || '/api',

  /** 是否启用 Mock */
  enableMock: import.meta.env.VITE_ENABLE_MOCK === 'true',

  /** 日志级别 */
  logLevel: (import.meta.env.VITE_LOG_LEVEL || 'info') as 'debug' | 'info' | 'warn' | 'error',

  /** 应用标题 */
  appTitle: import.meta.env.VITE_APP_TITLE || 'My App',

  /** Sentry DSN（空字符串表示不上报） */
  sentryDsn: import.meta.env.VITE_SENTRY_DSN || '',

  /** 是否显示开发者工具面板 */
  enableDevtools: import.meta.env.VITE_ENABLE_DEVTOOLS === 'true',

  /** 便捷判断方法 */
  isDev: import.meta.env.DEV,
  isProd: import.meta.env.PROD,
  isTest: import.meta.env.MODE === 'test',
  isStaging: import.meta.env.MODE === 'staging',
} as const
```

```typescript
// 在业务代码中使用
import { env } from '@/config/env'

// 初始化 SDK
if (env.sentryDsn) {
  Sentry.init({ dsn: env.sentryDsn, environment: env.mode })
}

// 条件性渲染
{env.enableDevtools && <DevToolsPanel />}

// API 请求
const response = await fetch(`${env.apiBaseUrl}/users`)
```

#### CI/CD 中的环境变量注入

```yaml
# .github/workflows/deploy.yml —— GitHub Actions 示例
jobs:
  deploy-staging:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run build:staging
        env:
          VITE_SENTRY_DSN: ${{ secrets.STAGING_SENTRY_DSN }}
          # .env.staging 中的非敏感变量可直接写在文件中
          # 敏感变量通过 CI Secret 注入
      - run: npm run deploy:staging
```

**原则：** 非敏感的默认值写入 `.env` 文件并提交 Git；敏感的密钥/Token 通过 CI 环境变量注入，不写入文件。

## 常见问题

### Q1：为什么 `.env` 中的布尔值要写成字符串 `"true"` 而不是 `true`？

`.env` 文件是纯文本，所有值都是字符串。`VITE_ENABLE_MOCK=false` 读取后 `import.meta.env.VITE_ENABLE_MOCK` 的值是 `"false"`（字符串），不是 `false`（布尔值）。这就是为什么在 `env.ts` 中要做 `=== 'true'` 的判断。

### Q2：敏感信息（API Key）怎么处理？

**绝不能放在 `.env` 文件中提交到 Git。** 正确做法：
1. 本地开发：放在 `.env.local`（已在 `.gitignore` 中）
2. CI/CD：通过 CI 平台的环境变量/Secret 注入
3. 服务端密钥：绝对不暴露到前端代码中，放在后端

### Q3：Vite 中 `MODE` 和 `NODE_ENV` 有什么区别？

- `import.meta.env.MODE`：来自 `--mode` 参数，可以是 `development` / `production` / 自定义（如 `staging`）
- `process.env.NODE_ENV`：由 Vite 根据 `mode` 自动设置。mode 为 `production` 时 `NODE_ENV=production`，其他都是 `development`

这意味着自定义 mode（如 `staging`）时，`NODE_ENV` 是 `development`，可能导致某些库（如 React）以开发模式运行。如果 staging 需要 production 级别的优化，在 `vite.config.ts` 中手动设置 `NODE_ENV`。

### Q4：Webpack DefinePlugin 和 dotenv-webpack 选哪个？

`DefinePlugin` 是内置的，零依赖，适合变量少、不复杂的场景。`dotenv-webpack` 支持 `.env` 文件体系，适合多环境、变量多的项目。两者不冲突，可以同时使用。

### Q5：如何在运行时（而不仅是构建时）切换环境变量？

前端的构建时环境变量是固化的。如果需要在同一份构建产物中切换多个环境（如一个 Docker 镜像部署到不同环境），有两种方案：
1. 把配置放在 `public/config.js` 中，HTML 中通过 `<script>` 加载，运行时读取 `window.__CONFIG__`
2. 使用 Nginx 的 `sub_filter` 在部署时替换占位符

### Q6：`.env.local` 和 `.env.development` 的区别？

`.env.development` 提交到 Git，团队共享。`.env.local` 不提交到 Git，用于个人本地覆盖（如个人的 API Key、代理端口等）。

### Q7：TypeScript 报 `import.meta.env` 不存在怎么办？

在 `tsconfig.json` 中添加：
```json
{
  "compilerOptions": {
    "types": ["vite/client"]
  }
}
```
或者在 `src/vite-env.d.ts` 中添加 `/// <reference types="vite/client" />`。

### Q8：staging 环境需要 sourcemap 但不想公开，怎么办？

Vite 中设置 `build.sourcemap: 'hidden'`：生成 sourcemap 但不给 JS 文件加 `sourceMappingURL` 注释。这样只有知道 sourcemap 文件名和路径的人（团队内部）才能用，普通用户看不到。

## 实操作业

### 基础练习：双环境配置

在一个 Vite + React + TypeScript 项目中配置开发和生产两套环境：
- 开发环境使用 `http://localhost:8080/api`，显示调试面板
- 生产环境使用 `https://api.example.com`，关闭调试面板
- 创建 `src/config/env.ts` 统一访问
- 用 `import.meta.env.DEV` 和 `import.meta.env.PROD` 做条件渲染

### 进阶练习：四环境构建流水线

扩展为四套环境（dev / test / staging / production），要求：
- 每套环境的 API 地址、日志级别、Sentry DSN 不同
- staging 环境保留调试面板，production 关闭
- production 构建前做类型检查（`tsc --noEmit`）
- 写一个简单的构建脚本（shell），一键构建所有非开发环境的包并放到不同目录
- 验证每个产物的环境变量是否正确注入

### 挑战练习：容器化 + 运行时注入

创建一个 Docker 镜像，让同一份镜像可以通过环境变量在不同环境运行：
1. 用 Nginx 作为 Web 服务器
2. 在 Dockerfile 的 ENTRYPOINT 脚本中，根据 `$APP_ENV` 环境变量替换 JS 文件中的占位符
3. 测试在本地 Docker 中分别以 dev / staging / prod 模式启动，验证界面连接的是正确的后端

### 作业参考与验收

- **基础**：env.ts 统一解析公开配置，DEV/PROD 表示构建模式相关标志。故意缺 URL 时构建或启动给明确错误；浏览器 bundle 中不能出现私密 API Key。
- **进阶**：mode 与 NODE_ENV 分开，staging 也可能是生产优化构建；遍历实际 mode 输出不同目录。类型检查失败中止脚本，逐个 preview 验证地址与面板开关。
- **挑战**：同镜像在启动时生成白名单 public config JSON/JS，并正确 JSON 编码值；避免任意 sed 改 minified bundle。两个容器地址不同，注入值含引号仍合法且不执行代码。

## 本节小结

环境变量是前端工程化的「配置层」，让同一份代码适配不同环境。核心要点：

1. **Vite 的 `VITE_` 前缀是安全机制**，只暴露带此前缀的变量
2. **`.env` 文件加载有优先级**：`.env.[mode].local` > `.env.[mode]` > `.env.local` > `.env`
3. **mode 决定打包行为**：development 不压缩、production 全量优化、staging 是类 production + 调试
4. **敏感信息走 CI 注入 + `.env.local`**，绝不提交到仓库
5. **统一访问层 `env.ts`** 是工程化习惯，能避免散落的 `import.meta.env.XXX`，提供类型安全和默认值
