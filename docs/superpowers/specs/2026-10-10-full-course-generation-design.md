# NoteFlow 全量 48 周课程生成设计规格

## 1. 目标与当前状态

本次工作把 NoteFlow 全栈工程师课程从“课程蓝图 + W1 样例”推进为完整的 48 周、96 单元课程。

全量完成标准：

- 96 个知识单元全部有可阅读的完整正文。
- 每个单元包含统一的 13 个固定章节。
- 每个单元都有实验入口、可运行案例或可观察的工程练习。
- 每个单元都说明 NoteFlow 集成成果、失败排查和阶段验收。
- 9 个阶段都有周次地图、阶段目标、成果和导航。
- 课程入口、单元前后关系和实验链接全部可达。
- 自动脚本能够检查单元数量、标题、链接、实验入口、重复 ID 和阶段覆盖。
- 需要 Node.js 的实验统一使用 Node.js 24 运行基线；执行前通过 `nvm use 24` 切换。

当前已完成：

- 课程骨架和 9 个阶段 README。
- 课程地图、NoteFlow 演进地图、考核标准和版本基线。
- W1/U01：Web 应用、浏览器和服务器是什么。
- W1/U02：终端、文件系统、Git 与开发环境。
- W1 的 U01/U02 实验。
- 单元模板和基础链接/章节校验脚本。

本次不回退或覆盖已经存在的 W1 正文、课程地图、模板和用户已调整的格式。

## 2. 内容架构

课程内容分成五层，每层有独立职责。

```text
根目录设计资料
  -> 课程入口与阶段地图
  -> 单元正文
  -> 单元实验和 NoteFlow 项目切片
  -> 自动检查与阶段验收
```

### 2.1 根目录设计资料

根目录的蓝图、路线图、NoteFlow 项目规格、版本清单和评分标准是课程设计真相源。课程正文引用它们，但不复制全部内容，避免后续规则变化时出现多份冲突。

### 2.2 课程阅读入口

`web-fullstack-course/` 面向学习者，包含：

- 课程入口；
- 9 个阶段 README；
- 学习路径；
- NoteFlow 演进地图；
- 考核和版本说明；
- 每周、每单元的前后导航。

### 2.3 单元正文

单元按阶段、周次和主题放置：

```text
web-fullstack-course/<stage>/WXX/
  <unit-id>-<slug>.md
```

为了兼容已经交付的 W1 文件，W1 保持现有目录：

```text
web-fullstack-course/00-common/W01-web-foundations/
  01-web-app-browser-server.md
  02-terminal-filesystem-git.md
```

W2 以后统一使用周次目录，便于一次定位一周的两个单元。

### 2.4 实验目录

每个单元都拥有一个实验入口：

```text
web-fullstack-course/labs/WXX/UXX-<slug>/
├── README.md
├── source files or runnable scripts
└── test or verification files when the topic requires them
```

实验入口至少说明：

- 环境和版本；
- 从仓库根目录执行的命令；
- 预期输出或页面；
- 失败时首先查看的证据；
- 与 NoteFlow 主线的关系。

纯理论单元也必须有可观察练习，例如 DevTools 观察、命令行实验、DOM 输出、类型检查、SQL `EXPLAIN` 或测试断言，不创建只有说明文字的空实验目录。

## 4. 单元内容契约

每个单元必须按以下顺序包含 13 个章节：

1. 任务背景
2. 学习目标
3. 预备知识
4. 核心理论
5. 标签、属性、API 或配置清单
6. 最小可运行案例
7. NoteFlow 集成案例
8. 常见错误与排查路径
9. 课后题
10. 实践练习
11. 阶段验收
12. 常见问题
13. 扩展阅读

每篇正文还必须提供：

- 任务卡；
- 可观察的本单元成果；
- “先看结果”和“拆开看”；
- 文件路径、运行命令、预期结果和失败诊断；
- 单元前后导航；
- “我现在能做到什么”。

## 5. NoteFlow 连续项目规则

单元成果必须沿着同一条产品主线累积：

```text
公共内容页
  -> 响应式视觉
  -> 原生交互
  -> React/Vue 管理后台
  -> Monorepo 与质量门禁
  -> API 与数据库
  -> 认证、组织隔离和 RBAC
  -> 缓存、队列、文件、测试和部署
```

每个单元正文必须明确：

- 当前 NoteFlow 的产品问题；
- 本单元改动的页面、模块或数据边界；
- 学习者能够演示的结果；
- 下一单元会依赖的接口、状态或文件；
- 当前阶段还没有实现的能力边界。

公共内容侧和团队后台的核心概念必须保持一致。React 与 Vue 阶段实现相同的登录、列表、搜索筛选、编辑表单、权限状态和路由能力。

## 7. 自动校验设计

在现有 `check-course-links.js` 基础上扩展或新增 `check-course-completeness.js`，检查：

1. 课程清单中 96 个单元 ID 不重复且连续。
2. 每个单元正文存在且标题包含单元 ID。
3. 每个正文包含 13 个固定章节。
4. 每个正文包含任务卡、最小案例、NoteFlow 集成、阶段验收和扩展阅读。
5. 每个单元在 `labs/` 下有对应实验入口。
6. Markdown 相对链接目标存在。
7. 每个阶段、每个周次都能从课程入口或学习路径到达。
8. 实验 README 包含环境、运行命令、预期结果和失败诊断。
9. 单元 ID、周次、阶段目录和实验目录互相一致。
10. 正文没有未完成占位表达、调试输出或秘密样例。

Node.js 代码使用：

```bash
. "$HOME/.nvm/nvm.sh"
nvm use 24
node web-fullstack-course/scripts/check-course-completeness.js
```

代码实验按阶段补充最小验证命令。需要包管理器的批次在 `nvm use 24` 后使用锁定的 pnpm 版本，不在正文中使用浮动安装命令。

## 8. 内容质量与可读性

为了避免 96 篇文章变成机械复制，每个单元必须有自己的：

- 真实产品情境；
- 具体失败案例；
- 可观察运行结果；
- NoteFlow 交付变化；
- 练习输入和验收证据。

理论写作遵循：

```text
先遇到问题 -> 先看到结果 -> 拆解机制 -> 故意出错 -> 修复并验收
```

类比只负责建立直觉，随后必须回到准确术语、代码、命令和运行证据。不同阶段的难度按前置知识递增，不把 React、Vue、数据库和部署概念提前塞入 HTML 或 CSS 单元。

## 9. 环境和版本策略

- Node.js 实验使用 `nvm use 24`。
- 课程主线技术版本以现有版本基线为准。
- 当前 Node.js 24 补丁版本与文档快照不一致时，正文使用主版本契约，实验记录实际版本。
- 依赖型实验必须提供安装、启动、检查和失败诊断命令。
- 不执行自动部署、远端推送、数据库迁移或真实外部服务写入。
- 不在实验中使用真实 Token、密码、生产数据或私有 API。

## 11. 风险与取舍

### 11.1 全量内容规模

96 篇完整教程无法安全地一次性塞进单个文件或单次变更。按批次写作和提交，能让每个阶段独立可校验，也能在发现术语或项目边界问题时及时修正。

### 11.2 实验复杂度不同

HTML 单元的实验可能是浏览器观察和静态页面，数据库单元的实验可能是迁移、查询和测试。实验形式可以不同，但每个单元必须有可运行或可观察证据，不用同一种代码模板强行套所有主题。

### 11.3 课程代码与教程代码的边界

教程实验先追求可理解、可验证和边界清楚；生产级系统能力通过后续单元逐步增加。正文会明确“当前实验不负责什么”，防止学习者把最小示例误认为生产实现。
