# 小程序开发课程蓝图

> 状态：仅供方向评审，不创建小程序教程、项目或平台发布任务。
> 技术快照：2026-10-11；基础库、审核规则和开发者工具必须在实施启动时复核。

## 培养目标

面向已完成 Web 全栈主线的 React/TypeScript 学习者。完成后应能以一个主代码库交付至少两个小程序
平台，同时识别平台生命周期、组件、网络、登录、存储、隐私、包体、审核和发布差异。目标不是
“一份代码无条件跑全部平台”，而是共享领域与页面意图、显式隔离平台适配。

## 前置知识

- JavaScript/TypeScript、React、表单、网络、存储、测试和构建；
- 邻里集市 API 契约、对象授权、会话/Token、幂等和冲突；
- 能使用 Git、锁文件、环境配置、CI 与脱敏证据；
- 具备目标平台测试账号、开发者工具与真机；不在教材中保存 AppSecret、私钥或真实用户数据。

## 目标生态

主线顺序：

1. 微信小程序作为首个实现与验收平台；
2. 抖音小程序作为第二平台，验证生命周期、能力与审核差异；官方文档明确区分开发工具、能力、
   发布和备案流程。[cite:3]
3. 支付宝小程序作为第三平台适配练习；
4. H5 只做降级对照，不把浏览器结果当小程序真机证据。

## 技术选型

| 方案 | 优势 | 主要成本 | 结论 |
|---|---|---|---|
| 各平台原生 | 能力、调试与审核边界最直接 | 多套模板、API 和发布链 | 平台深度参考 |
| Taro + React + TypeScript | Taro 官方支持 React/Vue 及多个小程序平台；平台配置可显式拆分。[cite:1][cite:2] | 仍需平台条件编译、插件和真机验证 | **默认主线** |
| uni-app | 生态与可视化工具丰富 | 新运行时与 Vue 心智，和现有 React 主线衔接较弱 | 对照评估 |
| 自建编译适配层 | 可精确控制 | 长期维护成本最高 | 不作为课程主线 |

### 推荐默认

采用 **Taro + React + TypeScript**，先完成微信单平台闭环，再添加抖音、支付宝 adapter。Taro
共享页面和领域逻辑，但组件、API、配置文件、登录、支付、隐私弹窗、审核和包体必须按平台核对。
Taro 文档列出不同平台配置文件，证明“可编译”不等于“配置相同”。[cite:2]

持续集成只负责静态、测试和授权环境中的预览/上传。平台私钥属于外部系统凭据，不能进入源码或
通用制品；Taro CI 文档也要求独立的工具标识和私钥路径。[cite:4]

## 模块结构

1. 小程序运行时、App/Page/Component 生命周期；
2. 模板、样式、事件、数据更新和渲染性能；
3. 路由、分包、预加载、返回栈与页面恢复；
4. 网络域名、请求 parser、取消、错误与幂等；
5. 登录 code、服务端换取会话、Token 生命周期与退出；
6. Storage、文件、缓存、配额、清理与用户隔离；
7. 平台组件、权限、隐私授权和能力降级；
8. 图片、相机、位置、订阅消息与最小数据；
9. Taro 平台 adapter、条件配置和差异登记；
10. 单测、组件测试、开发者工具、真机和弱网；
11. 包体、分包、构建、预览、提审、灰度与回退；
12. Capstone 与第二平台独立适配。

## 连续项目

“邻里集市小程序”阶段交付：

- 商品列表、搜索、详情与分享卡片；
- 登录、收藏、发布草稿和预约；
- 图片选择与上传前校验；
- 预约响应丢失后同幂等键查询/重试；
- 离线只保存本地草稿，不宣布预约成功；
- 平台订阅消息只作通知，打开后读取权威状态；
- 微信首发，随后在抖音或支付宝完成第二平台适配。

不接入真实支付。支付能力只在扩展评审中讨论签名、回调、退款和对账，不能用前端成功页代替。

## 平台边界

| 边界 | 必须证明 |
|---|---|
| 生命周期 | 页面隐藏、销毁、返回和冷启动不会重复提交 |
| 网络 | 合法域名、TLS、超时、错误 code 与 requestId |
| 登录 | code 只交服务端；客户端不保存平台密钥 |
| 存储 | 用户隔离、配额失败、退出清理和升级迁移 |
| 权限 | 使用时请求，拒绝和永久拒绝都有恢复说明 |
| 订阅消息 | 用户授权、模板用途和最终状态回读 |
| 分包 | 首包、异步包、公共依赖和独立分包有预算 |
| 审核 | 隐私、类目、内容、账号和功能说明真实一致 |

## 测试与发布证据

- Node 环境单测与 parser/状态机测试；
- 每个平台开发者工具的构建、网络、存储和性能记录；
- 至少两台真机或两个真实平台客户端；
- 冷启动、热启动、切后台、返回栈、弱网、无网和升级；
- 登录过期、权限拒绝、图片超限、预约冲突和重复提交；
- 平台配置 diff、包体/分包清单、构建摘要；
- 预览二维码、体验版、提审、驳回修复和回退记录；
- 只有真实平台结果才能标记该平台通过。

## 验收标准

- 微信主线完整，第二平台完成同一核心业务；
- 共享代码不包含平台密钥，不绕过平台审核或隐私规则；
- 网络响应从 `unknown` 解析，金额/UTC/状态与 Web 主线一致；
- 登录和对象授权由服务端保证；
- 本地草稿、上传中、已提交和服务端成功状态不混写；
- 平台差异集中在 adapter/config，不散落无说明条件分支；
- 真机覆盖权限拒绝、后台恢复、网络失败和版本升级；
- 预览/提审/发布证据记录 commit、工具版本、平台和时间；
- 未验证平台、机型、基础库和审核结果明确列为缺口。

## 复用关系

| Web 能力 | 小程序复用 | 新增内容 |
|---|---|---|
| React/TypeScript | 页面状态、领域契约、parser | 小程序组件与生命周期 |
| 浏览器网络/存储 | 失败、取消、缓存思维 | 合法域名、平台 Storage |
| 后端 | API、授权、幂等、冲突 | 平台登录 code 交换 |
| 工程化 | pnpm、测试、构建、CI | 多平台配置、开发者工具 |
| 全栈交付 | 证据、发布、回退 | 预览、提审、平台审核 |

## 建议周数

建议 **12 周，每周 18–22 小时**：

- 1–2：运行时、组件、生命周期；
- 3–4：路由、网络、登录；
- 5–6：存储、图片、权限；
- 7：分包、性能和平台配置；
- 8–9：微信业务闭环与真机验收；
- 10：第二平台 adapter；
- 11：预览、提审和回退；
- 12：Capstone 与独立平台修复。

第三平台完整验收另增加 2–3 周。

## 实施顺序

1. 冻结平台顺序、类目、账号、隐私和 API 契约；
2. 建立 Taro React/TS 基线、锁文件和平台配置；
3. 只在微信完成列表/详情与运行时 parser；
4. 接入服务端登录、写操作、幂等和冲突；
5. 加入存储、图片、权限和订阅消息；
6. 建立工具/真机/弱网/升级测试矩阵；
7. 抽出 platform adapter，再适配第二平台；
8. 完成预览、提审、驳回与回退演练；
9. 独立评审通过后再生成逐周教程计划。

## 风险与决策门

- 平台 API 或组件差异超过 adapter 可控范围时，允许平台专用页面；
- 第三方 Taro 插件必须审计权限、维护状态和包体；
- CI 上传是外部写操作，需用户明确授权且不得回显凭据；
- 平台规则变化快，蓝图不固定长期基础库补丁号。
