# Web 全栈工程师课程骨架与第一周设计规格

## 1. 目标与范围

本次工作把已有课程蓝图、48 周路线图和 NoteFlow 项目规格落地为可持续扩展的课程目录，并完成第一周两个可直接学习的知识单元。

首批范围：

- 建立 9 个课程阶段的稳定目录边界。
- 建立课程入口、课程地图、NoteFlow 演进地图、考核标准和版本基线的导航。
- 建立可复用的单元写作模板。
- 完成 W1/U01“Web 应用、浏览器和服务器是什么”。
- 完成 W1/U02“终端、文件系统、Git 与开发环境”。
- 为两个单元分别提供可运行实验目录。
- 提供链接、章节和占位表达检查脚本。

本次不完成 W2 及之后的正文，不提前实现完整 NoteFlow 产品，不引入前端框架或后端框架依赖。

## 2. 设计原则

### 2.1 连续项目主线

学习者以刚加入 NoteFlow 产品团队的工程师身份学习。每个单元都回答三个问题：

1. 当前产品任务是什么？
2. 哪个浏览器、操作系统或工程机制决定了任务结果？
3. 学习者能提交什么可验证的成果？

W1 的叙事从“页面为什么能出现”进入“我如何掌控这套系统”：

```text
URL -> 浏览器 -> 网络请求 -> 服务器响应 -> 页面显示
终端 -> 文件系统 -> 进程 -> Node.js -> Git -> 可复现项目
```

### 2.2 先验证再解释

每个单元先给出任务成果、运行结果或 DevTools/终端证据，再拆解理论。代码示例必须能在指定目录中运行，正文不得依赖未提供的隐含文件。

### 2.3 小单元、强边界

课程正文按阶段、周次和单元拆分。实验代码与教程正文物理分离，避免 Markdown 变成无法维护的代码仓库。新增单元只需遵循模板、补充导航并通过校验。

### 2.4 证据驱动的验收

验收不只检查“页面看起来正常”，还要求提交命令输出、浏览器网络观察、Git 历史或解释记录。失败场景必须包含复现方式和诊断路径。

## 4. 单元内容契约

每个知识单元固定包含：

1. 任务背景
2. 学习目标
3. 预备知识
4. 核心理论
5. 标签、属性、API 或配置清单
6. 最小可运行案例
7. NoteFlow 集成案例
8. 常见错误与排查路径
9. 课后题
10. 实践练习
11. 阶段验收
12. 常见问题
13. 扩展阅读

为了增强学习节奏，每个单元在正文开头增加任务卡，在理论部分增加“先看结果”和“拆开看”，在结尾增加“我现在能做到什么”。这些内容服务于学习目标，不替代正式章节。

所有代码示例必须标注：

- 文件位置
- 运行命令
- 预期结果
- 失败时的诊断路径

正文和脚本中不得出现“自行补充”“略”“待完善”“TODO”“TBD”等未完成表达。

## 5. 第一周设计

### 5.1 U01：Web 应用、浏览器和服务器是什么

学习者完成一个最小静态页面，并使用浏览器开发者工具观察：

- URL 的组成
- 浏览器发起的请求
- 请求方法、状态码和响应头
- HTML 文档如何进入页面
- 浏览器、服务器和文件系统的职责边界

实验不依赖框架，使用静态 HTML 和一个稳定的本地静态服务器命令。实验结果需要能在浏览器中打开，并能在 Network 面板中找到文档请求。

NoteFlow 集成成果是“公共文章首页的第一张草图”：只保留产品名称、页面标题、简单文章入口和请求观察记录，不提前引入 W2 的 HTML 语义体系。

### 5.2 U02：终端、文件系统、Git 与开发环境

学习者从空目录建立 NoteFlow 学习仓库，完成：

- 使用终端导航、创建、复制、移动和检查文件
- 区分文件、目录、进程和端口
- 检查 Node.js、pnpm 和 Git 版本
- 创建最小项目说明和实验文件
- 初始化 Git、提交第一次变更并查看历史
- 根据常见命令错误完成一次排查

实验以 Node.js LTS 和 pnpm 版本基线为准。命令必须兼容 macOS/Linux；涉及 Windows 差异时单独标注，不把平台差异隐藏在命令中。

NoteFlow 集成成果是一个可复现的学习仓库入口，包含项目说明、运行命令、目录说明和首个 Git 提交。

### 5.3 W1 阶段验收

学习者必须提交：

- 两个实验目录
- U01 的浏览器 Network 观察记录
- U02 的版本检查结果
- Git 首次提交记录
- 一份“浏览器、服务器、终端和 Git 各自负责什么”的解释
- 一条故障排查记录，包含现象、证据、原因和修复

## 6. 视觉与内容风格

教程使用“任务卡 + 证据卡 + 原理拆解 + 练习闯关”的版式：

- 使用短段落、表格、代码块和流程图降低阅读密度。
- 重要警告、检查点和验收标准使用统一 Markdown 引用块。
- 每个单元开头明确可交付成果，结尾明确能力变化。
- 类比只用于建立直觉，随后必须回到真实术语、命令和运行证据。
- 不使用夸张营销文案，不用大量装饰性符号替代理论。

## 7. 导航与扩展规则

- 根 README 指向课程入口和所有设计资料。
- 课程 README 指向阶段地图和已完成单元。
- 每个阶段 README 说明阶段目标、单元列表和阶段成果。
- 每个单元提供上一单元、下一单元和所属阶段链接。
- 链接校验脚本扫描 Markdown 相对链接，并验证目标文件存在。
- 章节校验脚本验证已完成单元包含 13 个必需章节。
- 新增阶段或单元时，先更新课程地图，再新增正文和实验，最后运行校验。

## 8. 验证标准

实现后至少运行：

```bash
node scripts/check-course-links.js
node --check labs/W01/U01-web-runtime/server.mjs
node --check labs/W01/U02-dev-environment/check-env.mjs
```

并人工验证：

- 从课程 README 能进入两个 W1 单元。
- U01 实验页面能打开，Network 面板能观察到文档请求。
- U02 环境检查脚本能运行，并输出版本检查结果。
- Git 实验命令不依赖全局隐含配置。
- 两个单元的命令、目录和预期结果互相一致。

## 9. 风险与取舍

### 9.1 暂不自动生成 96 个正文文件

提前创建空正文会制造断链和“课程已完成”的错觉，也会增加后续结构调整成本。阶段目录和地图足以支持后续扩展。

### 9.2 暂不绑定复杂本地服务

W1 的目标是建立运行模型和工程习惯，不让数据库、容器或框架安装噪声掩盖基础概念。复杂依赖从对应阶段开始引入。

### 9.3 版本变化

正文依赖技术版本基线中的稳定 API 契约。具体补丁版本以实验仓库锁文件为准，版本变化时更新版本基线和诊断说明，不在每个单元中重复维护浮动版本。
