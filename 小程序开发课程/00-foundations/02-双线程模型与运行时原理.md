# 02-双线程模型与运行时原理

## 目标

完成本知识单元后，学员应能从架构层面理解小程序代码的运行位置与通信机制，而不是把 `setData` 当成普通赋值。

学员应能够：

1. 画出小程序双线程（逻辑层、渲染层）加 Native 系统层的整体架构图，说清各自职责。
2. 解释为什么小程序采用双线程模型，它同时解决了 WebView 单线程下的哪些问题，又带来什么代价。
3. 说清逻辑层的运行环境（iOS/安卓/工具各自由什么 JS 引擎执行），以及逻辑层为什么没有 `window`、`document` 和 DOM。
4. 区分 WebView 渲染层与 Skyline 渲染引擎的基本差异，知道 Skyline 把渲染任务放到独立线程。
5. 完整描述一次用户点击从渲染层到逻辑层、再经 `setData` 回到渲染层的通信链路。
6. 说清 `setData` 的执行过程：数据序列化、跨线程传输、渲染层 diff 与重绘，理解其异步语义与第二个参数 callback。
7. 区分 `this.data.x =` 直接改值与 `this.setData({ x })` 的本质差别，并解释为什么前者不会更新界面。
8. 使用路径更新、字段级更新等方式减小 `setData` 传输量，并识别高频、全量 setData 等性能反模式。
9. 通过日志与调试器，自己动手验证双线程通信的时序与 setData 的生效时机。
10. 理解基础库在双线程模型中扮演的角色，以及逻辑层与渲染层数据并非共享内存这一核心约束。

本单元是后续生命周期、组件、性能优化（U27）与 Skyline（U28）的理论地基。

## 详细的理论知识讲解和示例伪代码

### 1. 从 WebView 单线程谈起

#### 1.1 普通网页的问题

在传统移动端 H5 页面中，一个 WebView 大致在同一条主线程上完成：

- 解析 HTML、构建 DOM；
- 解析 CSS、计算样式；
- 执行 JavaScript；
- 布局（Layout）与绘制（Paint）。

这意味着当 JavaScript 执行时间过长时，页面渲染会被阻塞，出现点击无响应、动画掉帧；同时页面脚本可以直接操作 DOM、读取页面上下文，在“把不可信第三方页面也放进微信”的场景下存在安全与稳定性风险。

#### 1.2 小程序的目标

微信希望小程序同时具备：

- **流畅性**：业务 JS 不应轻易阻塞界面；
- **安全性**：第三方小程序代码与微信内部环境隔离，不能随意访问宿主；
- **管控性**：能力通过受控 API 开放，网络、授权、支付都可被平台监管。

为此，小程序把“跑 JS 的逻辑”与“画界面的渲染”拆到不同线程，两者不共享内存，只能通过 Native 层中转——这就是**双线程模型**。

### 2. 双线程架构总览

```text
┌─────────────────────────────┐
│            微信客户端           │
│                             │
│  ┌──────────────┐           │
│  │   逻辑层       │  运行 JS：业务、数据、生命周期、wx API
│  │ App Service  │  （无 DOM / BOM）
│  └──────┬───────┘           │
│         │  Native 桥接（序列化消息）│
│  ┌──────┴───────┐           │
│  │   渲染层       │  运行 WXML / WXSS
│  │   View       │  WebView 或 Skyline
│  └──────────────┘           │
│         │                    │
│  ┌──────┴───────┐           │
│  │  Native 系统层 │  能力桥接：网络、支付、定位、存储、权限
│  └──────────────┘           │
└─────────────────────────────┘
```

三条关键数据流：

1. **渲染层 → 逻辑层**：用户操作以“事件消息”形式通知逻辑层（bindtap 等）。
2. **逻辑层 → 渲染层**：通过 `setData` 把数据变化发给渲染层。
3. **逻辑层 ↔ Native**：调用 `wx.*` 能力（网络、支付、存储等）由 Native 实现并回调。

核心约束：

> 逻辑层与渲染层不共享内存，所有跨线程交换的数据都会被序列化成消息，经 Native 转发。

这决定了小程序性能优化的中心往往不是“JS 算得快不快”，而是“跨线程传了多少数据、传得多频繁”。

### 3. 逻辑层详解

#### 3.1 逻辑层运行环境

逻辑层负责执行小程序的 JavaScript。不同端使用的 JS 引擎实现不同（以官方说明为准）：

- iOS：通常基于 JavaScriptCore；
- Android：通常基于 V8 或微信自研内核相关实现；
- 开发者工具：通常基于桌面端 Chromium/NW.js 同类环境；
- Skyline 模式下逻辑层上下文组织方式也会调整（见后文）。

对开发者而言，重点不是引擎名称，而是：**逻辑层是一个独立的 JS 运行环境，与界面隔离**。

#### 3.2 没有 window、document、DOM

逻辑层不是浏览器，因此：

- 不存在 `window`、`document`；
- 不能 `document.querySelector`、不能 `element.appendChild`；
- 不能直接读取某个节点的实时位置（要用专门的 `wx.createSelectorQuery`）；
- 浏览器上的第三方库只要依赖 DOM，就不能直接在逻辑层使用。

概念对比：

```text
浏览器:  JS ──直接操作──> DOM ──> 浏览器渲染
小程序:  JS ──setData──> Native ──> 渲染层更新
```

#### 3.3 逻辑层有什么

逻辑层提供：

- App/Page/Component 构造器与生命周期；
- 模块化（CommonJS 风格的 `require/module.exports`，工具也支持 ES Module 语法转换）；
- 小程序专属 API：`wx.*`；
- 定时器、部分 ES 内置对象；
- 当前页面的 `data` 与 `setData`。

示例：一个最小页面的逻辑层

```javascript
// pages/thread/thread.js
Page({
  data: {
    count: 0
  },
  onLoad() {
    console.log('[逻辑层] onLoad, count =', this.data.count)
  },
  onAdd() {
    const next = this.data.count + 1
    this.setData({ count: next })
  }
})
```

### 4. 渲染层详解

#### 4.1 WebView 渲染层

传统模式下，渲染层由 WebView 承担：

- WXML 经过编译生成渲染函数，WXSS 提供样式；
- 通常**每个页面一个 WebView**（因此页面间天然隔离，也便于页面栈管理）；
- 用户在界面上的交互在此捕获，再以事件形式发给逻辑层。

渲染层结构示例：

```xml
<!-- pages/thread/thread.wxml -->
<view class="card">
  <text>当前计数：{{ count }}</text>
  <button bindtap="onAdd">加 1</button>
</view>
```

渲染层本身不执行业务 JS 来修改 `count`；它只负责显示逻辑层给的数据，并把“按钮被点了”这一事件上报。

#### 4.2 Skyline：把渲染独立出来

传统 WebView 模式下，一个 WebView 内部的 JS 解析、DOM 树创建、布局、绘制仍较多挤在一起。Skyline 是微信新一代渲染引擎，核心变化：

- 创建独立的**渲染线程**承担布局（Layout）、合成（Composite）、绘制（Paint）；
- 在逻辑层划出独立上下文承担原本由 WebView 承担的部分 JS/组件树构建；
- 支持 Worklet，把动画/手势处理放到渲染线程，减少跨线程往返；
- 界面更不易被业务逻辑阻塞，交互更接近原生。

注意 Skyline 仍有平台与特性覆盖限制（部分端、部分 CSS/组件能力在完善中），因此课程以 WebView 为兼容性主线，Skyline 在 U28 作为进阶专题并要求保留回退。

### 5. Native 系统层

Native 层是小程序与设备能力之间的桥梁，负责：

- 转发逻辑层与渲染层之间的消息；
- 实现网络、存储、支付、定位、蓝牙、扫码等系统能力；
- 调度应用与页面生命周期；
- 权限、安全与分包资源管理。

当你调用 `wx.request`、`wx.getLocation` 时，真正的能力由微信 Native（及对应系统 API）完成，逻辑层只是发起调用并接收结果。这也解释了为什么敏感能力需要授权、网络要配置合法域名。

### 6. 通信一：渲染层事件到逻辑层

#### 6.1 事件消息

用户点击按钮时，渲染层并不会直接调用逻辑层函数，而是把一条事件消息发给逻辑层，消息包含：

- 事件类型与绑定的处理函数名；
- 触发节点的 `data-*` 数据集（dataset）；
- 事件附加信息（如触摸点坐标、表单组件值等）。

逻辑层收到后，根据函数名找到对应方法执行。

```xml
<button bindtap="onAdd" data-step="2">加 2</button>
```

```javascript
Page({
  onAdd(event) {
    const step = Number(event.currentTarget.dataset.step) // 2
    this.setData({ count: this.data.count + step })
  }
})
```

#### 6.2 bind 与 catch

- `bindtap`：绑定事件且事件会继续向上冒泡；
- `catchtap`：绑定事件并阻止冒泡；
- 还有 capture-bind / capture-catch 用于捕获阶段（事件系统在 U08 深入）。

理解“事件是跨线程消息”有助于解释：为什么不能在 WXML 里直接写复杂 JS 表达式——渲染层只负责采集与上报，业务运算要在逻辑层进行（渲染层简单逻辑可使用 WXS）。

### 7. 通信二：setData 到渲染层

#### 7.1 setData 做了什么

调用 `this.setData(obj)` 时，大致经历：

```text
逻辑层:
  1. 把本次更新与 data 合并，更新 this.data（逻辑层数据）
  2. 把 obj 序列化成消息
  3. 通过 Native 发送给渲染层
渲染层:
  4. 反序列化，根据数据重新执行渲染
  5. 计算差异（diff），更新对应节点
  6. 布局与绘制
```

因此 `setData` 的成本由三部分构成：

- 序列化与跨线程传输（数据越大越贵）；
- 渲染层 diff（节点越多、结构越复杂越贵）；
- 布局绘制（触发布局变化更贵）。

#### 7.2 setData 是异步的

`setData` 发起的跨线程更新是异步过程，这带来两个典型时序问题。

问题一：调用后立即读 `this.data`

```javascript
this.setData({ count: 1 })
console.log(this.data.count)
```

在当前实现中，逻辑层 `this.data` 的合并通常可较早反映新值，但**渲染层界面更新完成**是稍后的事；不同基础库/端的细微时序不应被业务依赖。要在“界面确实更新后”执行逻辑，使用第二个参数 callback：

```javascript
this.setData({ count: 1 }, () => {
  console.log('渲染层已完成本次更新')
})
```

问题二：高频连续 setData

连续多次调用会产生多次跨线程通信。应合并为一次：

```javascript
// 不推荐：三次通信
this.setData({ a: 1 })
this.setData({ b: 2 })
this.setData({ c: 3 })

// 推荐：一次通信
this.setData({ a: 1, b: 2, c: 3 })
```

#### 7.3 直接赋值为什么不更新界面

```javascript
// 只改了逻辑层这份数据，没有发消息给渲染层，界面不会变
this.data.count = 10
```

`this.data` 只是逻辑层持有的普通数据对象。界面更新必须走 `setData` 触发跨线程同步。这也是初学者最常见的“数据变了但页面没反应”的根因。

### 8. 减小 setData 成本

#### 8.1 只传变化的字段

```javascript
// 不推荐：整个大对象全量传
this.setData({ list: this.data.list })

// 推荐：只传变化的字段
this.setData({ [`list[${index}].liked`]: true })
```

#### 8.2 路径更新

支持用字符串路径精确更新数组某项或对象某字段，显著减少序列化体积：

```javascript
this.setData({
  'user.profile.nickname': '小新',
  ['list[' + i + '].score']: 95
})
```

#### 8.3 与界面无关的数据不要放进 data

只在逻辑层使用、不需要渲染的数据，可挂在普通属性上或使用纯数据字段（组件中可用 `pureDataPattern`/options），避免无意义地跨线程传输。

```javascript
Page({
  // timer 仅逻辑层使用，不放进 data
  timer: null,
  onLoad() {
    this.timer = setInterval(() => {}, 1000)
  },
  onUnload() {
    clearInterval(this.timer)
  }
})
```

#### 8.4 高频场景使用 WXS 响应事件

滚动、手势等高频交互若每次都跨线程到逻辑层再回来，开销很大。这类“渲染层可闭环”的简单逻辑可由 WXS 响应事件直接在渲染层处理，U06 与 U27 会专门训练。

### 9. 一次点击的完整旅程

把前面串起来，一次“点赞”的完整时序：

```text
1. 用户在渲染层点击点赞按钮
2. 渲染层生成事件消息（函数名 onLike、dataset、触点信息）
3. 消息经 Native 转发到逻辑层
4. 逻辑层执行 onLike：
   - 修改业务数据（可能调用 wx.request 或云函数）
5. 逻辑层调用 setData，序列化变更
6. 变更消息经 Native 到渲染层
7. 渲染层 diff，更新心形图标与点赞数
8. 浏览器/WebView 完成布局绘制，用户看到反馈
```

伪代码：

```text
onLike(event):
    id = event.currentTarget.dataset.id
    调用接口更新点赞状态
    成功后:
        setData({ [`list[${index}].liked`]: true })  // 仅更新该项字段
```

这个旅程是小程序一切交互的通用骨架，务必能不看资料完整复述。

### 10. 双线程约束下的编程规则

| 规则 | 原因 |
|---|---|
| 不依赖 DOM，节点信息用 createSelectorQuery | 逻辑层没有实时 DOM |
| 更新界面必须 setData | 只有它触发跨线程同步 |
| setData 尽量小而少 | 跨线程序列化与 diff 有成本 |
| 敏感逻辑放服务端/云函数 | 前端代码与数据可被客户端获取，不能放密钥 |
| 高频渲染逻辑考虑 WXS | 减少往返通信 |
| 不假设跨线程操作是即时同步完成 | 需要完成后逻辑时用 callback |
| 页面卸载时清理定时器/监听 | 逻辑层对象可能残留导致泄漏 |

### 11. 常见性能反模式

1. **全量 setData**：每次把整个列表/对象都传过去。
2. **高频 setData**：在 input、scroll、touchmove 中每次都发大对象。
3. **data 里塞无关数据**：定时器句柄、大段缓存、仅逻辑层用的中间结果。
4. **列表无 key 或 key 不稳定**：导致渲染层 diff 成本升高、状态错乱。
5. **setData 传不可序列化或过大的数据**：增加通信与解析负担。
6. **依赖“setData 后立刻读界面状态”**：跨线程更新尚未完成。

这些反模式会在 U27「运行时性能优化」中用真实数据量化并修复。

### 12. 基础库在双线程中的角色

基础库同时存在于逻辑层与渲染层：

- 逻辑层：提供 App/Page/Component、`wx.*` API、运行时；
- 渲染层：提供内置组件、渲染与事件能力；
- 两端协议由基础库约定，因此新能力、协议优化随基础库版本发布。

当出现“同一份代码在不同手机表现不同”时，先确认两端基础库版本，再判断是版本差异还是逻辑缺陷，不要直接归因于“玄学”。

#### 任务

```text
WXML 按钮 bindtap="onTap"
onTap:
```

### 练习 3：setData 数据量与合并更新实验

#### 任务

构造一个较长列表，分别用“全量更新”“路径更新”“多次/单次合并”三种方式更新，用 `console.time` 对比耗时并观察通信次数。

实验伪代码：

```text
初始化 list（例如 200 项）
方式 A: setData({ list: newList })               全量
方式 B: setData({ [`list[${i}].name`]: name })   路径
方式 C: 连续三次 setData vs 合并为一次 setData      合并对比
分别 console.time/timeEnd 记录
```

参考代码片段：

```javascript
function buildList(n) {
  return Array.from({ length: n }, (_, i) => ({ id: i, name: '店铺' + i }))
}

Page({
  data: { list: buildList(200) },
  onFull() {
    const list = buildList(200)
    list[100].name = '已更新'
    console.time('全量更新')
    this.setData({ list }, () => console.timeEnd('全量更新'))
  },
  onPath() {
    console.time('路径更新')
    this.setData({ 'list[100].name': '已更新' }, () =>
      console.timeEnd('路径更新')
    )
  }
})
```

#### 步骤约束

1. 数据规模以可观察差异、又不卡死工具为准（如 200、500 两档）。

3. 在 Network/日志之外，重点记录 callback 完成耗时差异。
4. 只做对比分析，不要为了实验把工具搞到无响应。

#### 提交物

- 实验代码；
- 三种方式耗时记录表；
- 不同数据规模对比；
- 200 字以内结论（哪种通信量最小）。

#### 验收标准

- 路径更新与全量更新的耗时差异有数据支撑；
- 能把差异对应到“序列化/传输数据量”；
- 理解合并更新减少了跨线程往返次数。
