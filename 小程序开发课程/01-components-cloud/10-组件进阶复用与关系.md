# 10-组件进阶复用与关系

## 目标

完成本知识单元后，学员应能在基础组件之上，系统运用**混入、插槽、监听、关联、样式开放、抽象节点**六类进阶手段，把组件做成「一处定义、多处复用、按需定制」的可复用资产，而不是每遇到一个略有差异的场景就 fork 一份组件代码。

学员应能够：

1. 建立组件复用的分层认知：逻辑复用用 behaviors，内容分发用 slot，派生计算用 observers，强关联通信用 relations，样式定制用 externalClasses 与 styleIsolation，类型/实现替换用 componentGenerics。
2. 使用 `Behavior({})` 抽取跨组件共享的数据、方法与生命周期，并说清同名字段的合并规则。
3. 描述多个 behaviors 与组件自身生命周期的**执行顺序**，能在正确的层级安排初始化逻辑。
4. 使用内置 behavior：`wx://form-field` 让组件对接表单提交与重置，`wx://component-export` 对外导出受控接口。
5. 使用默认插槽与 `options.multipleSlots: true` 的具名插槽，让使用方向组件的不同区域分发内容。
6. 使用 `observers` 监听一个或多个数据字段（含嵌套路径、通配符），响应变化并派生数据，并与 property 的 `observer` 区分。
7. 使用 `relations` 声明组件间的 parent/child/ancestor/descendant 关联，通过 `linked/unlinked` 与 `getRelationNodes` 实现强关联组件协作。
8. 使用 `externalClasses` 暴露样式入口，并理解 `options.styleIsolation` 的 `isolated / apply-shared / shared` 三种隔离级别及其影响面。
9. 使用 `componentGenerics` 抽象节点，让列表类组件的「渲染哪一种条目」由使用方注入。
10. 从 API 设计角度评估组件封装的取舍：受控与非受控、粒度、配置与组合、稳定性与扩展性，并据此改造「逛吃指南」的评分器与笔记卡片。

本单元是 U09 的直接延伸；U11 将在新一代组件框架 glass-easel 中看到这些能力的新写法。

## 技术栈

本单元仍不引入后端与第三方组件库，在 U09 已建立的 TypeScript 组件工程上继续扩展。

| 工具或 API | 用途 | 学习要求 |
|---|---|---|
| `Behavior({})` | 定义可混入逻辑单元 | 会抽 data/methods/生命周期并合并 |
| `behaviors: []` | 组件引用 behavior | 理解多混入与字段合并规则 |
| `wx://form-field` | 内置表单 behavior | 组件可被 form 提交与重置 |
| `wx://component-export` | 内置导出 behavior | selectComponent 返回导出对象 |
| `<slot>` / `multipleSlots` | 内容分发 | 会写默认插槽与具名插槽 |
| `observers` | 字段变化监听 | 会监听多字段、嵌套路径、通配符 |
| `relations` | 关联组件通信 | 会定义 type 与 linked/unlinked |
| `getRelationNodes` | 获取关联节点 | 能批量操作关联组件 |
| `externalClasses` | 外部样式类 | 会暴露并使用样式入口 |
| `styleIsolation` | 样式隔离级别 | 理解 isolated/apply-shared/shared |
| `componentGenerics` | 抽象节点 | 会声明默认实现与 generic 注入 |
| 微信开发者工具 | 验证进阶特性 | 借助日志、组件树与样式调试 |

实验约定：

- 共享逻辑统一放入 `behaviors/` 目录；改造 U09 组件时先保证原有用法不破坏，再叠加新能力。
- 每一种通信/开放机制都在演示页单独跑通后再组合，避免多个特性同时出问题难以定位。
- 选项支持的基础库版本以官方文档为准，低版本不可用时提供降级写法。

## 详细的理论知识讲解和示例伪代码

### 1. 组件复用的层次全景

#### 1.1 是什么

U09 解决了「把一块界面做成组件」，本单元解决「组件之间如何共享与定制」。六类机制各管一件事：

| 需求 | 机制 | 通信/开放方向 |
|---|---|---|
| 多个组件共享一段数据、方法、生命周期 | behaviors | 横向复用 |
| 使用方向组件内部填充内容 | slot | 外部 → 组件内容区 |
| 字段变化后做派生计算或联动 | observers | 组件内数据 → 组件内行为 |
| 列表与条目等强关联组件互相调用 | relations | 关联节点之间 |
| 使用方修改组件局部样式 | externalClasses | 外部样式 → 指定节点 |
| 调整组件与页面的样式影响范围 | styleIsolation | 样式边界 |
| 使用方决定组件渲染哪一种子组件 | componentGenerics | 实现注入 |

#### 1.2 与小程序开发的关系

真实业务里，笔记卡片在首页是「封面在上」、在收藏页需要「显示取消收藏按钮」、在活动页要换成门店卡。若每种差异都复制组件，组件数量会爆炸。进阶复用的目标是：**用一个稳定的组件内核，吸收有限的、可控的变化**。

#### 1.3 常见误区

- 学到新机制后什么场景都套：纯静态展示组件硬塞 relations、单插槽也要开 multipleSlots。机制服务于差异，没有差异就不用。
- 六类机制在一个组件里全部用上，组件变成无人能懂的「魔法盒」。组合要克制，优先选择最简单的方案。

### 2. behaviors：混入的定义与合并

#### 2.1 是什么

behavior 是一段用 `Behavior({})` 定义的、可被多个组件引用的逻辑片段，可以包含 `data`、`properties`、`methods`、`lifetimes` 等组件字段。组件在 `behaviors: [xxx]` 中引用后，字段会被合并进组件。

#### 2.2 与小程序开发的关系

「点赞」能力同时出现在笔记卡片和评论项上；「埋点曝光」几乎所有卡片都需要。这些横切逻辑用 behavior 实现一次，各组件引用即可，避免重复代码并保证行为一致。

#### 2.3 可运行示例：点赞 behavior

```typescript
// behaviors/like-behavior.ts
export default Behavior({
  data: {
    liked: false,
    likeCount: 0
  },
  methods: {
    onLikeTap(this: WechatMiniprogram.Component.TrivialInstance) {
      const next = !this.data.liked
      this.setData({
        liked: next,
        likeCount: this.data.likeCount + (next ? 1 : -1)
      })
      this.triggerEvent('likechange', { liked: next })
    }
  }
})
```

组件引用：

```typescript
// components/comment-item/comment-item.ts
import likeBehavior from '../../behaviors/like-behavior'

Component({
  behaviors: [likeBehavior],
  properties: {
    comment: { type: Object, value: {} as { id: string; text: string } }
  }
})
```

comment-item.wxml 中直接使用混入的 data 与方法：

```xml
<view class="comment">
  <text>{{comment.text}}</text>
  <view class="like" bindtap="onLikeTap">
    {{liked ? '已赞' : '赞'}} · {{likeCount}}
  </view>
</view>
```

#### 2.4 字段合并规则

| 字段类型 | 合并规则 |
|---|---|
| `data` | 按 key 合并，组件自身字段覆盖 behavior；多个 behavior 间，数组中靠后的覆盖靠前的 |
| `properties` | 同名属性以组件自身为准；属性本身仍受类型约束 |
| `methods` | 同名方法组件自身覆盖 behavior，靠后的 behavior 覆盖靠前的 |
| 生命周期 | **不覆盖**：各 behavior 与组件自身的同名生命周期都会执行 |
| `created` 等回调 | behavior 的先执行（按引用顺序），组件自身最后执行 |

behavior 也可以引用其他 behavior，规则同样适用。

#### 2.5 常见误区

- 以为生命周期会被覆盖只执行一个——混入的生命周期是「叠加执行」，在多个 behavior 里写初始化代码时要意识到它们都会跑。
- 在 behavior 中使用与组件强耦合的字段名（如随意占用 `list`、`index`），合并时静默覆盖且难排查。behavior 暴露的字段应带语义前缀或写进注释文档。

### 3. 多 behaviors 与生命周期顺序

#### 3.1 是什么

当组件同时引用多个 behavior 时，任一个生命周期回调的执行顺序是：**被引用的 behaviors 按数组顺序先执行 → 组件自身的回调最后执行**。嵌套引用的 behavior 按深度优先、引用顺序展开。

#### 3.2 与小程序开发的关系

理解顺序能安排依赖：若 behavior B 的初始化依赖 behavior A 先写入的数据，就要保证 A 在数组中排在 B 前；需要在所有混入逻辑完成后再做的收尾，放在组件自身的同名回调里。

#### 3.3 可运行示例：观察执行顺序

```typescript
// behaviors/track-behavior.ts
export default Behavior({
  lifetimes: {
    created() { console.log('track: created') },
    attached() { console.log('track: attached') }
  }
})
```

```typescript
// behaviors/like-behavior.ts
export default Behavior({
  lifetimes: {
    created() { console.log('like: created') },
    attached() { console.log('like: attached') }
  }
})
```

```typescript
Component({
  behaviors: [trackBehavior, likeBehavior],
  lifetimes: {
    created() { console.log('component: created') },
    attached() { console.log('component: attached') }
  }
})
```

输出：

```text
track: created
like: created
component: created
track: attached
like: attached
component: attached
```

#### 3.4 常见误区

- 依赖「组件自身 attached 先于 behavior attached」来抢占初始化——顺序恰好相反。
- 在不同 behavior 的同名回调里对同一字段做覆盖式 setData，结果由顺序决定，脆弱且隐晦；混入之间应尽量操作各自字段，或在文档中显式约定。

### 4. 内置 behaviors

#### 4.1 wx://form-field：让组件成为表单控件

引用后，组件内部维护的 `this.data.value` 会被外层 `form` 组件识别：`bindsubmit` 的 `detail.value` 中会以标签上的 `name` 为键收集该值；`form` 的 reset 会把 value 恢复到页面加载时的值。

```typescript
// components/shop-input/shop-input.ts
Component({
  behaviors: ['wx://form-field'],
  data: {
    value: ''
  },
  methods: {
    onInput(e: WechatMiniprogram.Input) {
      // 更新内部 value，即同步给 form
      this.setData({ value: e.detail.value })
      this.triggerEvent('input', { value: e.detail.value })
    }
  }
})
```

页面中：

```xml
<form bindsubmit="onSubmit" bindreset="onReset">
  <shop-input name="shopName"></shop-input>
  <button form-type="submit">提交</button>
  <button form-type="reset">重置</button>
</form>
```

```typescript
Page({
  onSubmit(e: WechatMiniprogram.FormSubmit) {
    console.log(e.detail.value.shopName)
  },
  onReset() {
    console.log('shop-input 已由 form 自动复位')
  }
})
```

#### 4.2 wx://component-export：导出受控接口

默认情况下父级 `selectComponent` 拿到的是组件完整实例。引用该 behavior 并实现 `export()` 后，父级拿到的是你显式导出的对象，只暴露必要能力、隐藏内部结构：

```typescript
Component({
  behaviors: ['wx://component-export'],
  data: { value: '', touched: false },
  methods: {
    onInput(e: WechatMiniprogram.Input) {
      this.setData({ value: e.detail.value, touched: true })
    },
    reset() {
      this.setData({ value: '', touched: false })
    }
  },
  export() {
    const self = this
    return {
      value: self.data.value,
      reset: () => self.reset()
    }
  }
})
```

父级：

```typescript
const input = this.selectComponent('#shop-input') as unknown as {
  value: string
  reset: () => void
}
console.log(input.value)
input.reset()
```

#### 4.3 常见误区

- 引用了 `wx://form-field` 却不更新 `this.data.value`，form 提交拿不到值——表单对接的唯一约定字段是 `value`。
- 以为 `export()` 返回值会随 setData 自动更新；导出对象是在调用 `selectComponent` 时按当时数据生成的快照式接口，方法内部仍应实时读取 `this.data`。

### 5. slot 与 multipleSlots

#### 5.1 是什么

插槽是组件在 WXML 中预留的内容位置。使用方把内容写在组件标签内部，框架将其分发到插槽处：

- 默认插槽：`<slot></slot>`，接收不带 slot 名的内容；
- 具名插槽：组件在 json/options 中开启 `multipleSlots: true`，用 `<slot name="x">` 定义多个位置，使用方用 `slot="x"` 指定去向。

#### 5.2 与小程序开发的关系

插槽解决「组件骨架一致，但局部内容使用方各不相同」的问题：同一个卡片组件，首页在头部插评分标签，商家页在底部插预约按钮。组件不需要为此增加大量开关属性，组合优于配置。

#### 5.3 可运行示例：开启多插槽

```typescript
// components/note-card/note-card.ts
Component({
  options: {
    multipleSlots: true
  },
  properties: {
    title: { type: String, value: '' }
  }
})
```

note-card.wxml：

```xml
<view class="note-card">
  <view class="header">
    <text class="title">{{title}}</text>
    <slot name="header-extra"></slot>
  </view>
  <view class="content">
    <slot></slot>
  </view>
  <view class="footer">
    <slot name="footer"></slot>
  </view>
</view>
```

页面使用：

```xml
<note-card title="巷子里的老火锅">
  <view slot="header-extra" class="badge">必吃榜</view>
  <image src="/images/hotpot.jpg" mode="widthFix" />
  <button size="mini" slot="footer" bindtap="onBook">立即预约</button>
</note-card>
```

没有使用方内容时插槽为空，也可在组件内为插槽位置准备兜底结构。

#### 5.4 常见误区

- 未开启 `multipleSlots` 却使用具名 slot，内容不会按预期分发。
- 试图用插槽传递数据——插槽是「使用方向组件内塞结构」，方向与 properties 相反；需要插槽内容访问组件数据的场景在 glass-easel（U11）中有更强的 slot 能力。
- slot 内容的样式写在组件 wxss 中却期望生效——插槽内容属于使用方，主要受使用方样式与隔离规则影响。

### 6. observers：数据字段监听

#### 6.1 是什么

`observers` 用于监听组件内任意数据字段（properties 与 data 皆可）的变化并执行回调，支持：

- 单字段：`'note.rating'(rating)`；
- 多字段联合：`'keyword, loading'(keyword, loading)`；
- 子树通配：`'tags.**'(tags)`；
- 全量监听：`'**'()`。

#### 6.2 与小程序开发的关系

observers 适合**派生状态**：评分变化时更新展示文案；多个筛选条件任一变化时重算结果列表。它把「联动」集中声明，避免在每个可能改字段的方法里手动补调用。

#### 6.3 可运行示例：评分文案与筛选派生

```typescript
Component({
  properties: {
    rating: { type: Number, value: 0 },
    keyword: { type: String, value: '' },
    onlyOpen: { type: Boolean, value: false },
    list: {
      type: Array,
      value: [] as Array<{ name: string; rating: number; open: boolean }>
    }
  },
  data: {
    ratingText: '',
    result: [] as Array<{ name: string; rating: number; open: boolean }>
  },
  observers: {
    rating(rating) {
      const text = rating >= 4.5 ? '超赞' : rating >= 4 ? '值得去' : rating > 0 ? '一般' : '暂无'
      this.setData({ ratingText: text })
    },
    'keyword, onlyOpen, list': function (keyword, onlyOpen, list) {
      const result = list.filter((item) => {
        const hitKeyword = !keyword || item.name.includes(keyword)
        const hitOpen = !onlyOpen || item.open
        return hitKeyword && hitOpen
      })
      this.setData({ result })
    }
  }
})
```

注意：observers 在字段**被更新时**触发，初始化赋值不会触发；回调中可以 setData，但不要形成「A 改 B、B 又改 A」的循环。

#### 6.4 observer（properties）与 observers 的区别

| 对比项 | property 的 observer | observers 字段 |
|---|---|---|
| 监听对象 | 单个 property | properties 与 data，支持多字段/路径/通配 |
| 参数 | newVal, oldVal | 各字段当前值，无 oldVal |
| 定义位置 | 写在属性定义内部 | 构造器顶层的 observers |
| 适用 | 单个对外属性的变化响应 | 派生计算、多字段联动 |

#### 6.5 常见误区

- 在 observers 回调里对被监听字段再次 setData 相同值，引发重复触发甚至死循环。
- 用 `'**'` 监听一切并在其中 setData，任何更新都触发回调，性能与可维护性双输。
- 误以为嵌套对象「内部修改」会被监听——深层路径监听仍以实际字段更新为前提，修改应通过 setData 路径更新。

### 7. relations：关联组件机制

#### 7.1 是什么

relations 用于声明两个组件之间**确定的层级关联**，常见于「容器—条目」结构（如 note-list 与 note-card、tabs 与 tab-item）。关联类型：

- `parent` / `child`：直接父子；
- `ancestor` / `descendant`：允许跨层的祖孙关系。

关联生命周期：

- `linked(target)`：关系建立时触发（子被插入父）；
- `linkChanged(target)`：自定义组件被移动导致关系变化；
- `unlinked(target)`：关系解除（子被移除）。

关联路径写**对方组件的相对路径**。

#### 7.2 与小程序开发的关系

properties/triggerEvent 适用于松耦合的父子通信；而「列表要统一控制所有条目（单选互斥、批量曝光、统一高亮）」时，逐个传属性很笨拙。relations 让容器直接管理条目集合，条目也能反向访问容器，这是组件库中 Tabs、Form、Collapse 一类组件的标准实现方式。

#### 7.3 可运行示例：容器与条目互相注册

components/note-list/note-list.ts：

```typescript
Component({
  relations: {
    '../note-card/note-card': {
      type: 'child',
      linked(target) {
        console.log('[note-list] 条目挂载:', target.data.note?.id)
      },
      unlinked(target) {
        console.log('[note-list] 条目移除:', target.data.note?.id)
      }
    }
  },
  methods: {
    highlightAll(active: boolean) {
      const cards = this.getRelationNodes('../note-card/note-card')
      cards.forEach((card) => card.setData({ active }))
    }
  }
})
```

components/note-card/note-card.ts：

```typescript
Component({
  relations: {
    '../note-list/note-list': {
      type: 'parent',
      linked(target) {
        // 保存容器实例，条目事件可通知容器统一处理
        this.list = target as WechatMiniprogram.Component.TrivialInstance
      },
      unlinked() {
        this.list = null
      }
    }
  },
  data: { active: false },
  methods: {
    onSelect() {
      this.list?.triggerEvent?.('itemselect', { id: this.data.note.id })
    }
  }
})
```

注意：关联的组件必须在 WXML 中真实构成嵌套关系，关系才会建立；通过 wx:if 动态增删条目时 linked/unlinked 会成对触发。

#### 7.4 常见误区

- 路径写成标签名字符串（如 `'note-card'`）——relations 的键必须是组件文件的相对路径。
- 只在一侧声明 relations：单向声明可以拿到一部分回调，但双向协作需要两侧互相声明对应类型。
- 在 `linked` 中假设对方已完成全部渲染：linked 表示关系建立，节点布局未必完成；依赖布局用 ready 之后的时机。

### 8. relations 实战：单选互斥的条目组

以「筛选条件组」为例：任意时刻只能选中一个条件，由容器统一仲裁。

condition-group.ts：

```typescript
Component({
  relations: {
    '../condition-item/condition-item': {
      type: 'child'
    }
  },
  methods: {
    choose(id: string) {
      const items = this.getRelationNodes('../condition-item/condition-item')
      items.forEach((item) => {
        item.setData({ checked: item.data.id === id })
      })
      this.triggerEvent('change', { id })
    }
  }
})
```

condition-item.ts：

```typescript
Component({
  relations: {
    '../condition-group/condition-group': {
      type: 'parent'
    }
  },
  data: {
    id: '',
    label: '',
    checked: false
  },
  methods: {
    onTap() {
      const group = this.getRelationNodes('../condition-group/condition-group')[0]
      group && (group as any).choose(this.data.id)
    }
  }
})
```

页面使用时只与容器对话：

```xml
<condition-group options="{{conditions}}" bind:change="onConditionChange" />
```

这样条目互斥规则完全内聚在组件族内部，页面无需知道有多少个条目。

### 9. externalClasses：外部样式类

#### 9.1 是什么

`externalClasses` 是组件显式暴露给外部的样式类名。使用方在标签上传入一个（页面侧定义的）class，组件把它挂到指定节点上，实现「不改组件源码的局部换肤」。

#### 9.2 与小程序开发的关系

当多个页面共享卡片但品牌色、圆角、间距不同时，比起为每种视觉差异增加属性，外部样式类让使用方直接写 WXSS，灵活且不污染组件逻辑。

#### 9.3 可运行示例

组件 ts：

```typescript
Component({
  externalClasses: ['custom-class', 'title-class'],
  properties: {
    title: { type: String, value: '' }
  }
})
```

组件 wxml：

```xml
<view class="note-card custom-class">
  <text class="title title-class">{{title}}</text>
</view>
```

页面 wxml：

```xml
<note-card title="深夜食堂" custom-class="promo-card" title-class="promo-title" />
```

页面 wxss：

```css
.promo-card {
  border-radius: 16rpx;
  border: 2rpx solid #ff6a00;
}
.promo-title {
  color: #ff6a00;
  font-weight: 600;
}
```

#### 9.4 常见误区

- 外部类与组件自身类写在同一节点且设置同一属性（如都定义 `color`），优先级冲突、表现不稳定；建议外部类作用于组件预留的节点，或用它控制布局类属性。
- 期望外部样式类可以凭空选择组件内部任意节点——它只能影响组件明确挂载该 class 的节点，因此组件要设计好可定制点。
- 类名使用驼峰或动态拼接导致匹配失败，外部类名保持 kebab-case 字符串一致。

### 10. styleIsolation：样式隔离

#### 10.1 三种级别

在组件 `options.styleIsolation`（或组件 json）中配置：

| 级别 | 页面/外部 → 组件 | 组件 → 页面/外部 | 典型用途 |
|---|---|---|---|
| `isolated`（默认） | 不影响 | 不影响 | 通用可复用组件 |
| `apply-shared` | 页面 wxss 影响组件 | 组件不影响页面 | 组件想跟随页面主题 |
| `shared` | 页面影响组件 | 组件也影响页面与其他 shared/apply-shared 组件 | 组件与页面强绑定的业务组件 |

旧式 `addGlobalClass: true` 语义接近 apply-shared，新代码统一用 styleIsolation。

#### 10.2 与小程序开发的关系

默认隔离保证组件拿到任何页面都不会「被污染」或「污染别人」，这是组件可安全复用的底座。但在活动页等场景，你可能希望页面写一套主题类就能改组件内部样式，这时才考虑放开隔离——放开的方向和范围要与使用范围匹配。

#### 10.3 可运行示例

跟随页面主题（apply-shared）：

```typescript
Component({
  options: {
    styleIsolation: 'apply-shared'
  }
})
```

页面 wxss：

```css
.theme-dark .note-inner {
  background: #1f1f1f;
  color: #f2f2f2;
}
```

组件内节点使用同名 class 时即可接收页面样式；组件样式仍然不会泄漏回页面。

双向共享（shared，慎用）：

```typescript
Component({
  options: {
    styleIsolation: 'shared'
  }
})
```

此时组件 wxss 中的类可能影响页面和其他组件，通用组件库组件不应使用，否则样式冲突将不可控。

另需注意：全局/页面 wxss 中的**标签名选择器**（如 `view { ... }`）可能不受隔离边界约束、仍影响组件，因此全局样式应坚持使用 class 选择器。

#### 10.4 常见误区

- 把通用组件设为 shared 贪图方便，结果一个页面的 `.title` 改动污染全站卡片。
- 以为 isolated 下 app.wxss 的标签选择器也失效，在 app.wxss 大写 `image {}` 导致组件图片被意外缩放。
- externalClasses 与 styleIsolation 混淆：前者是「定向开口」，后者是「整体边界」，需要精确开放几个点时优先 externalClasses。

### 11. componentGenerics：抽象节点

#### 11.1 是什么

抽象节点是组件 WXML 中的「占位组件」：组件只规定这里要放某类条目，但具体由哪个组件实现，由使用方通过 `generic:xxx` 注入。在组件 json 的 `componentGenerics` 中声明，可提供默认实现。

#### 11.2 与小程序开发的关系

列表组件常常想复用「加载、空态、触底」逻辑，但条目类型不同：笔记条目、门店条目、活动条目。抽象节点让一个 note-list 承载所有列表逻辑，条目渲染由外部注入，避免为每种条目写一套列表组件。

#### 11.3 可运行示例

components/note-list/note-list.json：

```json
{
  "component": true,
  "componentGenerics": {
    "item": {
      "default": "/components/default-note-item/default-note-item"
    }
  }
}
```

components/note-list/note-list.wxml：

```xml
<view class="note-list">
  <block wx:for="{{items}}" wx:key="id">
    <item data="{{item}}" index="{{index}}" />
  </block>
</view>
```

页面注入具体实现：

```xml
<note-list
  items="{{notes}}"
  generic:item="note-card"
  bind:itemtap="onNoteTap"
/>

<note-list
  items="{{shops}}"
  generic:item="shop-card"
/>
```

若声明为 `"item": true`（不给默认值），使用方必须显式注入，否则该节点没有实现。

#### 11.4 常见误区

- 把抽象节点当动态组件随意切换状态——它在单次使用中由 `generic:item` 确定实现，注入的组件应与列表数据结构约定好属性接口。
- 忘记提供默认实现又不在使用方注入，节点静默不渲染。
- 抽象节点与 relations 混用却不共享路径约定，导致关联建立失败；二者配合时路径与嵌套关系要同时满足。

### 12. 组件封装的设计取舍

#### 12.1 受控与非受控

- **受控**：组件显示值完全来自 property，变化先 triggerEvent，由外部更新后再传回（如搜索栏 keyword 由页面持有）。状态唯一、可外部控制，代价是样板代码多。
- **非受控**：组件内部 data 自管初始值与变化，外部只给默认值（如展开/收起）。用法简单，但外部难同步状态。
- 经验：需要被页面联动、提交、回显的值用受控；纯局部 UI 状态用非受控。

#### 12.2 配置与组合

当差异可以用「往某区域放内容」表达时，优先 slot 组合；当差异是稳定的少量开关时，用 properties；差异是成体系的另一套实现时，用 generics。不要把十几个布尔属性堆在一个组件上模拟插槽和抽象节点。

#### 12.3 粒度与 API 稳定性

- 粒度过粗：一个组件包办列表+卡片+操作，难以复用；过细：层层 props 透传，样板代码膨胀。以「一个可独立命名的业务/交互概念」为粒度。
- 组件一旦被多处使用，properties 名与事件名就是公开 API，改名要评估所有使用方；新增能力优先「增量加可选属性」，不轻易破坏旧契约。

#### 12.4 常见误区

- 组件内部自行发请求、读密钥、写死业务规则，导致无法复用且有安全隐患——任何 SecretKey、访问令牌都不得放在前端代码中，需要鉴权的请求由后端/云函数中转。
- 追求「万能组件」，为假想中的未来需求预埋大量属性，真实使用率极低却让组件难以维护；按当下需求设计，保留扩展余地即可。

### 13. 综合实战：评分器 rater

需求：显示 0–5 分、支持半星（可选）、可只读可交互、可被表单收集、样式可换、交互时通知页面。综合运用前述能力：

```typescript
// components/rater/rater.ts
Component({
  behaviors: ['wx://form-field'],
  externalClasses: ['custom-class', 'icon-class'],
  options: { styleIsolation: 'isolated' },
  properties: {
    name: { type: String, value: '' },
    max: { type: Number, value: 5 },
    allowHalf: { type: Boolean, value: false },
    readonly: { type: Boolean, value: false },
    score: { type: Number, value: 0, observer(v: number) {
      // 对外属性变化时同步内部 value（表单值）
      this.setData({ value: v })
    } }
  },
  data: {
    value: 0,
    stars: [] as boolean[]
  },
  observers: {
    value(value) {
      const stars = Array.from({ length: this.data.max }, (_, i) => value >= i + 1)
      this.setData({ stars })
    }
  },
  lifetimes: {
    attached() {
      this.setData({ value: this.data.score, stars: [] })
    }
  },
  methods: {
    onTap(e: WechatMiniprogram.TouchEvent) {
      if (this.data.readonly) return
      const index = Number(e.currentTarget.dataset.index) + 1
      const next = this.data.value === index ? 0 : index
      this.setData({ value: next })
      this.triggerEvent('change', { value: next })
    }
  },
  export() {
    return { value: this.data.value }
  }
})
```

rater.wxml：

```xml
<view class="rater custom-class">
  <text
    wx:for="{{stars}}"
    wx:key="index"
    data-index="{{index}}"
    class="star icon-class {{item ? 'on' : ''}}"
    bindtap="onTap"
  >★</text>
</view>
```

使用方：

```xml
<rater
  name="taste"
  score="{{form.taste}}"
  bind:change="onTasteChange"
  custom-class="big-rater"
/>
```

这个评分器同时具备：表单可收集（form-field）、外部可读接口（export）、派生展示（observers）、样式可换（externalClasses）、默认隔离安全（isolated）。新增「半星」只需扩展 onTap 计算，不影响使用方。

### 14. 复用手段选型速查

| 你遇到的问题 | 首选方案 | 备选/升级 |
|---|---|---|
| 两个组件逻辑几乎一样 | 抽 behavior | 进一步抽象成 generics |
| 卡片某区域内容每页不同 | slot | 差异稳定后可改属性 |
| 一个值变了要更新另一个值 | observers | 单属性用 observer |
| 容器要批量控制条目 | relations | 简单场景用 triggerEvent |
| 页面想换组件颜色圆角 | externalClasses | 整页主题再考虑 apply-shared |
| 同一列表要渲染不同条目 | componentGenerics | — |
| 组件只想跟页面主题走 | apply-shared | 通用组件不要用 shared |

### 15. 进阶误区总清单

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| behavior 字段名随意 | 合并静默覆盖 | 语义化命名并写文档 |
| 误以为生命周期被覆盖 | 初始化行为异常 | 理解叠加执行与顺序 |
| 具名插槽忘开 multipleSlots | 内容不分发 | options 开启 |
| observers 中循环 setData | 死循环/性能差 | 派生单向、避免回写 |
| relations 路径写标签名 | 关联不建立 | 用组件相对路径 |
| 通用组件用 shared | 样式全局污染 | isolated + externalClasses |
| 全局 wxss 用标签选择器 | 穿透隔离 | 统一 class 选择器 |
| generics 不注入也无默认 | 空白节点 | 提供 default 或强制注入 |
| 前端存放密钥/令牌 | 安全事故 | 后端/云函数持有密钥 |
| 堆砌开关属性做万能组件 | 难维护 | 组合优先、按需设计 |

学完本单元，学员应能面对一个新差异时，先判断它属于「逻辑、内容、数据联动、关联、样式、实现」哪一类，再选用最小够用的机制，并始终守住组件的输入/输出边界。

| relations 关联 | 20 | 路径与类型正确、互斥逻辑内聚、增删正常 |
| 插槽与抽象节点 | 20 | multipleSlots 与 generics 使用正确、默认实现完备 |

| 设计与安全 | 10 | 受控/非受控合理、无前端密钥、文档齐全 |

### 强制不通过条件

- 为绕过差异直接复制/fork 组件代码，未真正使用复用机制；
- relations 路径、类型声明错误导致关联链路不可用，或互斥等核心规则失效；
- observers 出现循环 setData，或通用组件使用 shared 造成样式污染；
- 前端代码中出现密钥、访问令牌等敏感凭据；
- 使用进阶能力后默认用法发生回归而未修复；
- 无法说清任一进阶机制的适用场景与通信/影响方向。
