# 21-位置服务与地图

## 目标

完成本知识单元后，学员应能把「拿到一次可信定位 → 在地图上正确表达 → 借助位置服务完成业务」的链路工程化，而不是只会调一个 `wx.getLocation`、把一个 `map` 标签摆到页面上就交付。学员要为「逛吃指南」交付发布绑定门店、门店详情地图、到店导航等完整位置能力，并对用户拒绝授权有明确兜底。

学员应能够：

1. 说清位置能力的四个层次：操作系统定位能力、微信宿主与授权体系、小程序定位/选点/查看 API、map 组件与第三方位置服务（LBS），以及各层之间的依赖关系。
2. 区分 WGS-84、GCJ-02、BD-09 三种坐标系，知道微信 `getLocation` 的 `type` 参数、map 组件、腾讯位置服务分别使用什么坐标，理解坐标系混用为什么会造成几十到几百米偏移。
3. 正确完成定位的合规声明：`app.json` 中 `permission.scope.userLocation.desc` 与 `requiredPrivateInfos` 的声明，知道未声明时隐私接口会直接失败，以及后台还需配置用户隐私保护指引。
4. 熟练使用 `wx.getLocation`，掌握 `type`、`altitude`、`isHighAccuracy`、`highAccuracyExpireTime` 等参数与返回字段，并设计定位缓存与精度/耗电的平衡策略。
5. 实现完整定位授权状态机：未请求、已同意、已拒绝三种状态的判定与流转，拒绝后不再弹原生框、用 `wx.openSetting` 引导，并保证拒绝授权时业务仍可走手动选店等兜底路径。
6. 区分并使用 `wx.chooseLocation`（让用户选点）与 `wx.openLocation`（在内置地图查看位置并导航），说清它们与 `getLocation` 的职责差异。
7. 熟练使用 map 组件：中心点、`scale`、`markers`、`polyline`、`circles`、`controls`、`callout`/`label`、`include-points` 及各类图层开关，并通过事件与 `MapContext` 实现交互。
8. 接入腾讯位置服务完成逆地址解析、POI 搜索/关键词提示、距离矩阵与路线规划，理解密钥安全边界：SK 签名只在服务端/云函数完成，前端不存放机密密钥。
9. 说清前台持续定位与后台定位的能力边界、声明要求与审核门槛，能根据业务判断「逛吃指南」是否真的需要后台定位，不滥用敏感权限。
10. 完整落地「逛吃指南」：发布动态时绑定门店位置，门店详情页展示地图、气泡与距离，用户点击导航，且在拒绝定位、弱网、定位漂移等异常下行为均正确。

本单元承接 U20 的表单工程（发布表单里新增位置字段），也为 U22 的「到店扫码领券/核销」提供位置上下文与到店能力基础。

## 技术栈

本单元使用微信原生位置与地图能力 + TypeScript，位置服务对接腾讯位置服务 WebService API（经自建服务端或云函数代理），数据落库沿用 U13/U14 的数据层。

| 工具或环境 | 用途 | 学习要求 |
|---|---|---|
| app.json permission | 定位授权文案 | 配置 `scope.userLocation.desc` |
| app.json requiredPrivateInfos | 隐私接口声明 | getLocation/chooseLocation/startLocationUpdate 等逐项声明 |
| wx.getLocation | 获取当前位置 | type、isHighAccuracy、返回字段与缓存策略 |
| wx.authorize / getSetting / openSetting | 授权流程 | 三态判定与拒绝后引导 |
| wx.chooseLocation | 地图选点 | 返回 name/address/经纬度 |
| wx.openLocation | 查看位置与导航 | 内置地图页，scale/name/address |
| map 组件 | 页面内地图 | markers/polyline/circles/controls/callout/include-points |
| MapContext | 地图命令式 API | getCenterLocation/moveToLocation/includePoints/translateMarker |
| 腾讯位置服务 WebService | POI/逆地址/距离/路线 | geocoder、place、distance、direction 系列接口 |
| qqmap-wx-jssdk（可选） | 小程序端 SDK | 知道它是对 WebService 的封装及密钥风险 |
| Haversine 公式 | 本地直线距离 | 能手写并知道与路网距离的差异 |
| wx.startLocationUpdate 系列 | 持续/后台定位 | 前台与后台边界、requiredBackgroundModes |
| 云函数/自建服务端 | 密钥保管与代理 | SK 签名不出服务端 |
| TypeScript | 位置模型类型化 | LatLng/Marker/POI 等接口定义，不用 any |

约定：

- 一切定位均以真机为准，开发者工具的定位是模拟点，无法还原 GPS 漂移、室内弱信号与系统级权限弹窗。
- 位置属于个人敏感信息，只收集业务必需的精度：判断“到店”一般不需要持续高精度定位；隐私政策与实际采集必须一致。
- 第三方位置服务的密钥安全遵循 U17 的原则：可公开的 key 也要做授权 APP ID/域名限制，带签名能力的 SK 绝不进前端包。

## 详细的理论知识讲解和示例伪代码

### 1. 位置能力全景：四个层次与它们的依赖关系

小程序里的“位置”不是一个 API，而是一条自上而下的能力链：

1. **系统定位层**：手机芯片与操作系统通过 GPS、基站、Wi-Fi、蓝牙信标、辅助 AGPS 融合出位置。定位是否准确、是否允许定位，最终由系统开关和用户授权决定。
2. **微信宿主与授权层**：微信 App 持有系统定位权限，并把能力通过授权 scope 暴露给小程序；小程序拿到的任何位置数据都经过微信这一层。
3. **小程序 API 层**：`wx.getLocation`（取当前位置）、`wx.chooseLocation`（打开地图让用户选点）、`wx.openLocation`（打开内置地图页查看/导航）、持续定位系列 API。
4. **地图表达与 LBS 层**：map 组件负责把经纬度画成地图；POI 搜索、地址解析、距离与路线等“地理智能”由腾讯位置服务这类 LBS 提供。

依赖方向是单向的：没有系统定位权限，`getLocation` 失败；没有在 `app.json` 声明隐私接口，调用直接报错；没有 LBS 服务，你只有一对经纬度数字，不知道它对应哪家店、距离多远、怎么走。

「逛吃指南」的三个典型需求正好落在不同层：

| 业务需求 | 用到的层 | 核心 API |
|---|---|---|
| 发布动态时绑定门店 | 3 + 4 | chooseLocation 或 POI 搜索 |
| 详情页展示门店在哪 | 4 | map + markers |
| 用户导航到店 | 3 | openLocation（或路线规划） |
| “离我最近”排序 | 3 + 4 | getLocation + 距离计算 |

误区提醒：

- 把“经纬度”当成业务全部：经纬度只有配合坐标系声明、POI 数据与地图表达才有业务意义，单独入库一对裸数字是典型的半成品设计。

### 2. 坐标系：WGS-84、GCJ-02、BD-09 与偏移问题

同一物理地点在不同坐标系下的数值不同，这是国内地图开发最容易踩的坑：

- **WGS-84**：GPS 原始坐标系，国际通用，也是设备芯片直接产出的坐标。
- **GCJ-02（火星坐标系）**：国家要求的加密坐标系，由 WGS-84 经非线性偏移得到。中国大陆境内合规地图服务（腾讯地图、高德等）均使用 GCJ-02。
- **BD-09**：百度在 GCJ-02 上再次加密的坐标系，仅用于百度地图。

微信的约定非常关键：

- `wx.getLocation` 的 `type` 可选 `'wgs84'`（默认）或 `'gcj02'`；
- map 组件、`wx.openLocation`、`wx.chooseLocation` 使用的都是 GCJ-02；
- 腾讯位置服务 WebService API 在大陆地区也使用 GCJ-02。

因此一条经验法则：**只要结果要喂给 map 组件或腾讯位置服务，就用 `type: 'gcj02'` 取坐标。**

```typescript
// services/location.ts
export interface LatLng {
  latitude: number
  longitude: number
}

/** 用于 map / chooseLocation / openLocation / 腾讯位置服务的定位，一律 gcj02 */
export function getGcj02Location(): Promise<WechatMiniprogram.GetLocationSuccessCallbackResult> {
  return new Promise((resolve, reject) => {
    wx.getLocation({
      type: 'gcj02',
      isHighAccuracy: true,
      highAccuracyExpireTime: 3500,
      success: resolve,
      fail: reject,
    })
  })
}
```

误区提醒：

- 用默认的 WGS-84 坐标直接在 map 上打点，在中国大陆会出现几十到几百米甚至更大的偏移；这类问题在开发者工具里不明显，真机上才暴露。
- 不要试图在前端实现 WGS-84 与 GCJ-02 的互转算法，偏移算法的使用本身受测绘法规约束；直接通过 `type: 'gcj02'` 让平台返回正确坐标才是合规做法。
- 坐标出海：境外地区不涉及 GCJ 偏移，与境外地图服务集成时要按对方文档确认坐标系。

### 3. 合规声明：permission.desc 与 requiredPrivateInfos

定位是隐私接口，必须“先声明、再使用”。需要两处配置加一处后台设置：

```json
{
  "pages": ["pages/publish/publish", "pages/shop-detail/shop-detail"],
  "permission": {
    "scope.userLocation": {
      "desc": "用于在发布逛吃动态时绑定门店，并为你推荐附近的美食店铺"
    }
  },
  "requiredPrivateInfos": [
    "getLocation",
    "chooseLocation",
    "onLocationChange",
    "startLocationUpdate"
  ]
}
```

要点逐个说清：

1. `permission.scope.userLocation.desc` 是**首次向用户申请定位授权时，系统弹窗里展示的说明文案**。文案必须具体说明用途，写“用于功能展示”这类空话在审核中会被质疑。
2. `requiredPrivateInfos` 是 2022 年起对隐私接口的强制声明。用到哪个就声明哪个：
   - `getLocation`：主动定位；
   - `chooseLocation`：地图选点（chooseLocation 同样需要声明）；
   - `onLocationChange` / `startLocationUpdate`：前台持续定位；
   - `startLocationUpdateBackground`：后台定位；
   - `getFuzzyInfo`：模糊定位（若只用粗略位置可申请它，精度低、敏感度低）。
3. 还要在小程序管理后台的「用户隐私保护指引」中勾选“位置信息”，填写收集场景并审核通过。真机上，未完成指引配置时隐私接口可能被拦截。

未声明的后果是调用直接走 `fail`，常见错误信息形如 `getLocation:fail the api need to be declared in the requiredPrivateInfos field`。

误区提醒：

- 只写了 `permission.desc` 没写 `requiredPrivateInfos`，或者反过来——两者解决的不是一件事：前者是授权弹窗文案，后者是隐私接口使用声明，缺一不可。
- 把可能用到的接口全部声明进 `requiredPrivateInfos` 以求省事：声明范围应与实际使用一致，过度声明在审核时会被要求解释。

### 4. wx.getLocation：参数、返回值与定位缓存

`wx.getLocation` 的完整参数与返回结构：

```typescript
wx.getLocation({
  type: 'gcj02', // wgs84 | gcj02
  altitude: false, // 是否返回高度
  isHighAccuracy: true, // 开启高精度
  highAccuracyExpireTime: 4000, // 高精度超时，超时后返回低精度结果而非失败
  success: (res) => {
    res.latitude // 纬度，范围 -90 ~ 90
    res.longitude // 经度，范围 -180 ~ 18
    res.speed // 速度，m/s
    res.accuracy // 位置精度，米，越小越可信
    res.horizontalAccuracy // 水平精度
    res.verticalAccuracy // 垂直精度
  },
})
```

工程上要考虑两点：

- **精度与耗电的平衡**：高精度模式会更多调用 GPS，发布页这种“一次定位”场景可以开启；列表页“附近排序”用普通定位即可。
- **不要重复定位**：一次进入小程序内多次需要位置时，做带时间戳的缓存，而不是每个页面 `onShow` 都调一次。

```typescript
// services/location-cache.ts
import type { LatLng } from './location'

interface CachedLocation extends LatLng {
  accuracy: number
  cachedAt: number
}

let cache: CachedLocation | null = null
const CACHE_TTL = 30_000 // 30 秒内复用

export function getLocationCached(force = false): Promise<CachedLocation> {
  if (!force && cache && Date.now() - cache.cachedAt < CACHE_TTL) {
    return Promise.resolve(cache)
  }
  return new Promise((resolve, reject) => {
    wx.getLocation({
      type: 'gcj02',
      success: (res) => {
        cache = {
          latitude: res.latitude,
          longitude: res.longitude,
          accuracy: res.accuracy,
          cachedAt: Date.now(),
        }
        resolve(cache)
      },
      fail: reject,
    })
  })
}
```

`accuracy` 还要参与业务判断：门店打卡这类场景，如果 `accuracy > 200`（米），应提示“定位信号弱，请到门口重试”，而不是拿一个漂移坐标做判定。

误区提醒：

- 把定位失败一律提示“请开启定位”：失败原因可能是用户拒绝授权、系统定位关闭、信号弱、接口未声明，处理方式各不相同（见第 5 节）。

### 5. 定位授权流程：三态状态机与拒绝兜底

`scope.userLocation` 在任何时刻处于三种状态之一：

| 状态 | getSetting 表现 | 用户看到过什么 | 接下来怎么处理 |
|---|---|---|---|
| 未请求 | `undefined` | 什么都没看到 | 调用定位/authorize，系统弹窗征求同意 |
| 已同意 | `true` | 点过“允许” | 直接定位 |
| 已拒绝 | `false` | 点过“拒绝” | 系统不会再弹窗，只能引导去 openSetting |

关键机制：**用户拒绝过一次之后，再次 `wx.authorize` 不会再弹原生框，会直接 fail。** 此时必须用自定义弹窗解释“为什么需要定位”，用户确认后调 `wx.openSetting` 跳到设置页。

```typescript
// services/location-auth.ts
export type LocationAuthState = 'granted' | 'denied' | 'not-determined'

export function checkLocationAuth(): Promise<LocationAuthState> {
  return new Promise((resolve) => {
    wx.getSetting({
      success: (res) => {
        const v = res.authSetting['scope.userLocation']
        if (v === true) resolve('granted')
        else if (v === false) resolve('denied')
        else resolve('not-determined')
      },
      fail: () => resolve('not-determined'),
    })
  })
}

/** 业务侧统一入口：保证拿到定位，拒绝时走引导 */
export async function ensureLocation() {
  const state = await checkLocationAuth()
  if (state === 'granted') return getLocationCached()
  if (state === 'not-determined') {
    // 第一次：直接触发定位，微信会在此时弹出授权框
    return getLocationCached()
  }
  // denied：弹自定义说明框 -> openSetting
  const modal = await new Promise<boolean>((resolve) => {
    wx.showModal({
      title: '需要位置权限',
      content: '用于为你推荐附近门店并在发布时绑定位置，可在设置中重新开启',
      confirmText: '去设置',
      success: (r) => resolve(r.confirm),
    })
  })
  if (!modal) throw new Error('LOCATION_AUTH_DENIED')
  const setting = await new Promise<WechatMiniprogram.OpenSettingSuccessCallbackResult>(
    (resolve, reject) => wx.openSetting({ success: resolve, fail: reject }),
  )
  if (setting.authSetting['scope.userLocation'] !== true) {
    throw new Error('LOCATION_AUTH_DENIED')
  }
  return getLocationCached(true)
}
```

拒绝授权时的**业务兜底**必须提前设计，而不是让页面卡死：

- 列表页：定位被拒，默认展示全城热门门店，并提供“手动选择城区”入口；
- 发布页：定位被拒，允许通过搜索 POI 或 `chooseLocation`（chooseLocation 本身不依赖 getLocation 授权，用户在地图里自行选点）绑定门店；
- 详情页：展示门店位置完全不需要用户定位，地图照打 marker，只是无法计算“距你多远”。

误区提醒：

- 一进页面 `onLoad` 就弹定位授权：用户还没理解用途，拒绝率极高。应在用户触发“附近/绑定位置/导航”等具体动作时按需申请。
- 拒绝后反复调用 `wx.authorize` 试图“再弹一次”——不会再弹，只会让交互死循环。

### 6. chooseLocation 与 openLocation：选点与查看位置

两个 API 名字接近，职责完全不同：

```typescript
// 让用户在微信内置地图页搜索/拖动选一个点
wx.chooseLocation({
  latitude: 39.908, // 可选，指定地图打开时的中心
  longitude: 116.397,
  success: (res) => {
    res.name // 地点名称，如“老王涮肉（五道口店）”
    res.address // 地址
    res.latitude
    res.longitude
  },
})

// 在微信内置地图页展示一个已知地点，页面带“导航”按钮
wx.openLocation({
  latitude: shop.latitude,
  longitude: shop.longitude,
  name: shop.name,
  address: shop.address,
  scale: 18,
})
```

在「逛吃指南」里：

- **发布绑定门店**优先用 `chooseLocation`：用户搜“老王涮肉”，选完拿到标准 POI 名称、地址、经纬度，比让用户手填地址再定位可靠得多。它需要 `requiredPrivateInfos` 声明 `chooseLocation`。
- **详情页“到这去”**用 `openLocation`：无需自己实现导航 UI，用户在内置地图里可以选微信/第三方地图 App 发起实时导航。

```typescript
// pages/shop-detail/shop-detail.ts
function openNavigation(shop: Shop): void {
  wx.openLocation({
    latitude: shop.latitude,
    longitude: shop.longitude,
    name: shop.name,
    address: shop.address,
    scale: 18,
    fail: () => wx.showToast({ title: '地图打开失败', icon: 'none' }),
  })
}
```

误区提醒：

- `chooseLocation` 返回的名称是用户当时选的 POI，可能重复（多家分店同名），入库时要保留地址与经纬度做区分，不能只存名字。
- `openLocation` 不返回用户是否真的开始导航，它只负责“打开位置页”，不要基于它做“已到店”判定。

### 7. map 组件基础：中心点、scale 与 markers

map 是原生组件，属性即声明式配置：

```xml
<map
  id="shopMap"
  class="shop-map"
  longitude="{{shop.longitude}}"
  latitude="{{shop.latitude}}"
  scale="16"
  markers="{{markers}}"
  show-location
  enable-3D
  bindmarkertap="onMarkerTap"
  bindcallouttap="onCalloutTap"
></map>
```

- `longitude`/`latitude`：地图中心点坐标；
- `scale`：缩放级别 3（大洲）到 20（楼栋），门店详情常用 16-18；
- `show-location`：显示用户当前位置蓝点（需要定位授权，没授权时不显示但不报错）。

markers 是覆盖物数组，完整字段比想象中多：

```typescript
// pages/shop-detail/shop-detail.ts
interface ShopMarker {
  id: number
  latitude: number
  longitude: number
  title?: string
  iconPath: string // 本地包路径 / 临时文件 / 网络图片
  width?: number
  height?: number
  callout?: {
    content: string
    color?: string
    fontSize?: number
    borderRadius?: number
    bgColor?: string
    padding?: number
    display: 'BYCLICK' | 'ALWAYS' // 点按显示 / 常显
    textAlign?: 'left' | 'center' | 'right'
  }
  label?: {
    content: string
    color?: string
    bgColor?: string
    anchorX?: number
    anchorY?: number
  }
  anchor?: { x: number; y: number }
}

function buildMarker(shop: Shop): ShopMarker[] {
  return [
    {
      id: 1,
      latitude: shop.latitude,
      longitude: shop.longitude,
      iconPath: '/images/map-pin.png',
      width: 32,
      height: 32,
      anchor: { x: 0.5, y: 1 }, // 图标底部尖端对准坐标点
      callout: {
        content: shop.name,
        color: '#1f2937',
        fontSize: 12,
        borderRadius: 8,
        bgColor: '#ffffff',
        padding: 8,
        display: 'ALWAYS',
      },
    },
  ]
}
```

`anchor` 很关键：默认图标左上角对齐坐标点，图钉会“飘”在目标上方；设 `{x: 0.5, y: 1}` 让尖端对准门店。

误区提醒：

- marker 的 `id` 必须在当前 markers 数组内唯一，`bindmarkertap` 只靠 `e.detail.markerId` 告诉你点了哪个，id 重复会无法区分。
- 原生组件的层级最高，普通 `view` 盖不住它；需要在地图上叠加按钮时用 `cover-view`/`cover-image`，或用 controls。

### 9. 地图事件与 MapContext：让地图“可交互”

常用事件：

```typescript
// pages/map-search/map-search.ts
Page({
  onRegionChange(e: WechatMiniprogram.MapOnRegionChange) {
    // type: 'begin' | 'end'；causedBy: 'drag' | 'scale' | 'update'
    if (e.type === 'end' && e.causedBy === 'drag') {
      const mapCtx = wx.createMapContext('shopMap', this)
      mapCtx.getCenterLocation({
        success: (center) => {
          // 用户拖动结束后，以新中心点搜周边 POI
          this.searchNearby(center)
        },
      })
    }
  },

  onMarkerTap(e: { detail: { markerId: number } }) {
    const shop = this.data.shops.find((s) => s.id === e.detail.markerId)
    if (shop) this.setData({ activeShopId: shop.id })
  },

  recenter() {
    const mapCtx = wx.createMapContext('shopMap', this)
    // moveToLocation 需要定位授权；未授权时 fail，走兜底
    mapCtx.moveToLocation({
      fail: () => wx.showToast({ title: '未获得定位权限', icon: 'none' }),
    })
  },

  fitAll() {
    wx.createMapContext('shopMap', this).includePoints({
      points: this.data.includePoints,
      padding: [60, 40, 60, 40],
    })
  },
})
```

其他高频 MapContext 方法：

- `getScale()` / `getRegion()`：读当前缩放级别与视野四角经纬度；
- `translateMarker({ destination, animationEnd })`：让 marker 平滑移动（车辆轨迹场景）；
- `toScreenLocation` / `fromScreenLocation`：经纬度与屏幕像素坐标互算。

性能要点（结合 U02 的双线程模型）：marker/路线数据更新要通过 `setData` 从逻辑层跨线程传到渲染层。地图数据通常体积大，应：

1. 只更新变化字段，如 `setData({ [`markers[${idx}].callout.content`]: newText })`；
2. 拖动地图的过程中不要高频 `setData`，在 `regionchange end` 时统一处理；
3. 上百个 marker 考虑聚合（marker 的 `cluster` 能力或服务端网格聚合），不要一次性渲染上千点。

误区提醒：

- 在 `bindregionchange` 回调里无条件 `setData` 中心点：`setData` 改中心又触发 regionchange，形成“抖动”循环；用 `causedBy` 区分用户手势与程序更新。

### 10. 接入腾讯位置服务：申请、域名与密钥边界

接入步骤：

1. 在腾讯位置服务官网（lbs.qq.com）注册并创建应用，添加 **WebServiceAPI** 类型的 key；
2. 在 key 设置里绑定小程序的 APP ID，并开启每日配额/限流；
3. 在小程序管理后台把 `https://apis.map.qq.com` 加入 request 合法域名（U17）；
4. 决定调用方式：
   - **安全做法（推荐）**：小程序请求自己的云函数/服务端，由服务端用 SK 对请求签名后转发给腾讯，key（尤其 SK）永不下发；
   - 受限做法：小程序端直接调 WebService，只使用 key 本身（部分接口无需签名），但 key 会暴露在包里，必须靠 APP ID 绑定与配额限制降低风险。

```typescript
// services/lbs-client.ts —— 走自己的后端代理，前端不接触 SK
import { http } from './http' // U17 的请求层

interface ReverseGeocodeResult {
  address: string
  province: string
  city: string
  district: string
}

export function reverseGeocode(point: LatLng): Promise<ReverseGeocodeResult> {
  return http.get<ReverseGeocodeResult>('/lbs/geocoder', {
    location: `${point.latitude},${point.longitude}`,
  })
}
```

服务端（云函数示例，签名逻辑只存在于这里）：

```typescript
// cloudfunctions/lbs-proxy/index.ts
import crypto from 'crypto'

const KEY = process.env.TENCENT_MAP_KEY! // 环境变量注入
const SK = process.env.TENCENT_MAP_SK! // 机密，只在服务端

function sign(pathWithQuery: string): string {
  // 腾讯 WebService SK 签名：md5(pathWithQuery + SK)
  return crypto.createHash('md5').update(pathWithQuery + SK).digest('hex')
}

export async function main(event: { action: string; params: Record<string, string> }) {
  const query = new URLSearchParams({ ...event.params, key: KEY }).toString()
  const path = `/ws/${event.action}?${query}`
  const sig = sign(path)
  const url = `https://apis.map.qq.com${path}&sig=${sig}`
  const resp = await fetch(url)
  return resp.json()
}
```

误区提醒：

- 把带全部权限的 key 连同 SK 一起写进小程序源码：小程序包可被解包，密钥泄露会被刷爆配额甚至用于其他应用；SK 从设计上就只能存在服务端。
- 忘了配 request 合法域名，真机上请求被拦，只在开发者工具开了“不校验域名”时能用——这是“工具好好的、真机挂了”的经典来源。

### 12. 距离计算：Haversine 与距离矩阵的取舍

两种“距离”，用途不同：

- **直线距离（球面距离）**：本地就能算，零配额成本，适合“附近列表”粗排；
- **路网距离/时间**：LBS 的 distance matrix 接口给出真实驾车/步行距离和耗时，适合“步行 8 分钟到店”这种承诺式文案。

Haversine 手写实现：

```typescript
// utils/geo.ts
const EARTH_RADIUS_M = 6_371_000

const toRad = (deg: number): number => (deg * Math.PI) / 180

export function haversineMeters(a: LatLng, b: LatLng): number {
  const dLat = toRad(b.latitude - a.latitude)
  const dLng = toRad(b.longitude - a.longitude)
  const lat1 = toRad(a.latitude)
  const lat2 = toRad(b.latitude)
  const h =
    Math.sin(dLat / 2) ** 2 +
    Math.cos(lat1) * Math.cos(lat2) * Math.sin(dLng / 2) ** 2
  return 2 * EARTH_RADIUS_M * Math.asin(Math.sqrt(h))
}

/** 列表本地粗排 + 展示 */
export function sortByDistance<T extends LatLng>(shops: T[], origin: LatLng): (T & { distance: number })[] {
  return shops
    .map((s) => ({ ...s, distance: haversineMeters(origin, s) }))
    .sort((a, b) => a.distance - b.distance)
}

export function formatDistance(meters: number): string {
  return meters < 1000 ? `${Math.round(meters)}m` : `${(meters / 1000).toFixed(1)}km`
}
```

路网距离走服务端：

```typescript
// 腾讯距离矩阵：/ws/distance/v1/matrix
// mode=walking，一次性算“一个起点 × 多个门店”
export function fetchWalkingDistances(origin: LatLng, shops: LatLng[]) {
  return http.get('/lbs/distance-matrix', {
    mode: 'walking',
    from: `${origin.latitude},${origin.longitude}`,
    to: shops.map((s) => `${s.latitude},${s.longitude}`).join(';'),
  })
}
```

误区提醒：

- 用直线距离给出“步行 X 分钟”的承诺：隔一条江、绕一个立交，直线 300 米可能要走 15 分钟；涉及时间承诺一律路网距离。
- 对几十个门店逐个调距离接口：matrix 接口支持一次传入多个终点，批量计算，注意别在循环里发 N 个请求。

### 13. 路线规划：direction 接口与 polyline 解码

当详情页要画“从我的位置到门店的步行路线”时，调路线规划接口。返回的 `polyline` 字段是**压缩编码**的坐标串，按腾讯文档的规则解码：

```typescript
// utils/polyline-decoder.ts
/**
 * 腾讯路线规划 polyline 压缩规则：
 * 1) 经纬度做差分后乘 1e6，以 36 进制表示；
 * 2) 特殊字符替换：^->空格，$->=，?->;，]->,
 */
const RESTORE_MAP: Record<string, string> = {
  '^': ' ',
  '$': '=',
  '?': ';',
  ']': ',',
}

export function decodeTencentPolyline(encoded: string): LatLng[] {
  const restored = encoded.replace(/[\^$?\]]/g, (ch) => RESTORE_MAP[ch])
  const points: LatLng[] = []
  let prevLat = 0
  let prevLng = 0
  for (const coordinate of restored.split(';')) {
    const [latPart, lngPart] = coordinate.split(',')
    prevLat += parseInt(latPart, 36)
    prevLng += parseInt(lngPart, 36)
    points.push({ latitude: prevLat / 1e6, longitude: prevLng / 1e6 })
  }
  return points
}
```

完整路线加载：

```typescript
async function loadWalkingRoute(origin: LatLng, shop: Shop) {
  const route = await http.get<{
    distance: number
    duration: number
    polyline: string
  }>('/lbs/direction-walking', {
    from: `${origin.latitude},${origin.longitude}`,
    to: `${shop.latitude},${shop.longitude}`,
  })
  const points = decodeTencentPolyline(route.polyline)
  this.setData({
    polyline: [{ points, color: '#FF6B35', width: 6, arrowLine: true }],

```

注意路线坐标同样是 GCJ-02，可以直接喂给 map。接口支持 driving/walking/bicycling/transit 四种模式，门店到店场景默认 walking，远距离再提供 driving。

误区提醒：

- 不做解码直接把 polyline 字符串塞进 `points`，地图不画线或报错；压缩串必须先解码。
- 把 LBS 路线规划当作唯一导航入口：更稳的产品设计是详情页同时保留 `openLocation` 按钮，让用户可直接跳系统级实时导航（含实时路况与语音）。

### 14. 后台定位边界：什么时候用、怎么声明、为什么别滥用

持续定位分前台与后台两套：

```typescript
// 前台持续定位：小程序在前台运行时持续收到位置
wx.startLocationUpdate({
  success: () => {
    wx.onLocationChange((res) => {
      // res.latitude / longitude / accuracy ...
    })
  },
})

// 后台定位：小程序切到后台后仍持续定位
wx.startLocationUpdateBackground({
  success: () => wx.onLocationChange(handleLocation),
})
```

后台定位的门槛显著更高，需要同时满足：

1. `requiredPrivateInfos` 声明 `startLocationUpdateBackground`（以及 `onLocationChange`）；
2. `app.json` 配置 `"requiredBackgroundModes": ["location"]`；
3. 小程序类目属于支持后台定位的类型（运动轨迹、出行导航、外卖配送等），并在审核时说明具体使用场景；
4. 有明确的用户开启动作与持续提示（如前台常驻提示“正在后台记录轨迹”）。

判断原则：**没有“记录完整运动轨迹/配送轨迹”这类刚需，就不要申请后台定位。** 「逛吃指南」的场景是“用户在某个时刻看附近门店、到店导航”，全部用一次性定位即可；为了“精准推送”而后台追踪用户，既过不了审核，也违背最小收集原则。

停止与清理同样不能漏：

```typescript
wx.stopLocationUpdate({
  success: () => wx.offLocationChange(handleLocation),
})
```

误区提醒：

- 申请了后台定位却没有可见的功能对应，审核会被驳回；
- 页面 `onUnload` 不停止监听，定位持续耗电，用户会在系统电量报告里看到微信被点名。

### 练习 1：定位授权状态机与拒绝兜底

参考代码：

```typescript
// ensureLocation 见正文第 5 节
try {
  const origin = await ensureLocation()
  const list = sortByDistance(shops, origin)
  this.setData({ shops: list, located: true })

}
```
