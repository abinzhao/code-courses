# 20-表单录入与校验工程

## 目标

完成本知识单元后，学员应能把「一个报名表单从用户输入到安全入库」的完整链路工程化，而不是堆一堆 `input`、在提交按钮里写几个 `if` 就交付。学员要为「逛吃指南」的活动报名交付多字段、可联动、可恢复、防重复提交的表单。

学员应能够：

1. 熟练使用 `input`、`textarea`、`radio`、`checkbox`、`switch`、`slider`、`picker`（含 `picker-view`）等表单组件，并说清各组件的事件与返回值结构。
2. 理解受控数据绑定原理：输入事件在渲染层产生、经逻辑层回写 `data`、再由 `setData` 跨线程把值送回渲染层，数据的唯一真值在逻辑层。
3. 使用 `model:value` 简易双向绑定简化文本输入，并清楚它的限制（只能绑定数据路径、不能在绑定时做变换、自定义组件需满足约定）。
4. 设计声明式校验规则：必填、长度区间、正则、数字范围，并支持“满足条件时才校验”的条件规则。
5. 实现字段联动：一个字段变化时重置依赖字段、刷新选项、动态增删校验规则。
6. 建立统一错误提示：字段级错误就近展示、提交前整体校验、自动聚焦第一个错误字段，而不是只弹一个 toast。
7. 实现多步表单：分步收集、单步校验通过才放行、跨步骤状态保存与进度回显。
8. 实现草稿本地恢复：输入防抖自动保存到 Storage，再次进入时按活动识别并提示恢复，提交成功后清理。
9. 实现提交态与防重复提交：提交中按钮禁用加 loading、幂等键保证重试不产生重复单据，并能把服务端返回的字段级校验错误回填到表单。
10. 完整落地「逛吃指南」活动报名表单：基本信息、同行人数、场次选择、发票与饮食偏好等多字段，非法输入、提交失败、重复提交下行为均正确。

本单元承接 U19 媒体能力（报名页可能要上传凭证图），也为后续支付（报名后下单）提供干净的订单数据入口。

## 技术栈

本单元使用微信原生表单能力 + TypeScript，草稿使用 U12 的本地存储工具，提交对接自建服务端或云函数。

| 工具或环境 | 用途 | 学习要求 |
|---|---|---|
| input | 单行文本输入 | 掌握 type、maxlength、confirm-type 与 input 事件 |
| textarea | 多行文本 | auto-height、fixed、字数统计 |
| radio-group / radio | 单选 | 监听 group change，取 value |
| checkbox-group / checkbox | 多选 | 返回 value 数组 |
| switch | 开关 | checked、bindchange 布尔值 |
| slider | 数值滑杆 | min/max/step、changing/change |
| picker | 底部弹起选择器 | selector/multiSelector/time/date/region 五种 mode |
| picker-view | 内嵌滚动选择 | 多列联动选择 |
| form 容器 | name 提交模式 | bindsubmit、button form-type |
| model:value | 简易双向绑定 | 会用并知道限制 |
| 自定义校验器 | 规则执行 | 声明式规则、单字段/整表校验 |
| wx.setStorage 系列 | 草稿持久化 | 防抖保存、恢复与清理 |
| wx.request / 云函数 | 提交报名 | 字段错误结构解析 |
| 幂等键 | 防重复提交 | 重试复用同一键 |
| TypeScript | 类型化表单模型 | 不用 any 掩盖字段结构 |

约定：

- 前端校验的定位是**体验与引导**，不是安全边界；服务端必须独立做同等甚至更严格的校验，前端校验可被绕过。
- 表单数据含个人信息，本地草稿要最小化、可过期、可被用户清除；身份证号等敏感字段不进本地草稿。
- 本节所有交互以真机键盘表现为准，开发者工具不能完全模拟键盘遮挡与聚焦行为。

## 详细的理论知识讲解和示例伪代码

### 1. 表单工程是什么：从“能输入”到“输入正确、可提交、可恢复”

一个生产级表单要回答四个问题：

1. **怎么采**：用什么组件、数据以什么结构进逻辑层；
2. **怎么验**：什么时机校验、错误怎么展示、字段之间怎么联动；
3. **怎么存**：填一半退出能不能恢复、提交时怎么保证不重复；
4. **怎么交**：服务端说某个字段不对，能不能把错误精确回填。

「逛吃指南」活动报名的数据模型先定下来，后面的所有讨论围绕它：

```typescript
interface SignupForm {
  name: string
  phone: string
  gender: 'male' | 'female' | ''
  companions: number // 同行人数，0-5
  sessions: string[] // 想参加的场次 id
  sessionDate: string // 场次日期
  needInvoice: boolean
  invoiceTitle: string
  foodPref: string // 饮食偏好
  foodPrefOther: string
  region: string[] // 所在城区
  remark: string
}

const createEmptyForm = (): SignupForm => ({
  name: '',
  phone: '',
  gender: '',
  companions: 0,
  sessions: [],
  sessionDate: '',
  needInvoice: false,
  invoiceTitle: '',
  foodPref: '',
  foodPrefOther: '',
  region: [],
  remark: '',
})
```

先定数据结构再写 UI，是表单工程与“随手摆控件”的分水岭：字段名、类型、空值形态（`''`、`0`、`[]`）一旦统一，校验与回填逻辑才能收敛。

误区提醒：

- 空值形态混用（有时 `null`、有时 `''`）会让校验器到处判空；建表时就固定每类字段的空值。

### 2. input 与 textarea：文本输入的主力组件

```xml
<view class="field">
  <text class="label">联系人</text>
  <input
    value="{{form.name}}"
    data-field="name"
    bindinput="onInput"
    placeholder="请输入真实姓名"
    maxlength="20"
    confirm-type="next"
    cursor-spacing="20"
  />
  <text wx:if="{{errors.name}}" class="error">{{errors.name}}</text>
</view>

<view class="field">
  <text class="label">手机号</text>
  <input
    value="{{form.phone}}"
    data-field="phone"
    bindinput="onInput"
    type="number"
    maxlength="11"
    placeholder="用于活动通知"
  />
  <text wx:if="{{errors.phone}}" class="error">{{errors.phone}}</text>
</view>

<view class="field">
  <text class="label">备注（{{remarkLen}}/200）</text>
  <textarea
    value="{{form.remark}}"
    data-field="remark"
    bindinput="onInput"
    maxlength="200"
    auto-height
    placeholder="忌口、到达时间等"
  />
</view>
```

常用属性与行为：

1. `type`：`text` / `number` / `idcard` / `digit`（带小数点）/ `safe-password` / `nickname`。`type="number"` 只是键盘与输入约束，逻辑层拿到的仍是字符串，参与数值计算前要转换。
2. `maxlength`：硬截断；配合字数统计展示，比提交时报“超长”体验好。`-1` 表示不限。
3. `confirm-type`：键盘完成键文案（`done`/`next`/`search` 等），多字段长表单用 `next` 引导连续填写。
4. `cursor-spacing` / `adjust-position`：控制键盘弹起时输入框与键盘的距离，避免被遮挡；复杂吸底布局还要关注 `adjust-position="{{false}}"` 自行处理。
5. 事件：`bindinput`（每次输入）、`bindblur`（失焦）、`bindconfirm`（点完成键）。实时校验放 blur 或输入停顿后，避免用户刚敲一个字符就报红字。

textarea 额外注意：`fixed` 定位的弹层中要用 `fixed` 属性避免渲染错位；大文本避免频繁全量 setData。

误区提醒：

- 不要在 `bindinput` 里做 `toUpperCase` 之类变换再回写——光标容易跳位；需要规范化的值应在 blur 或提交时处理。

### 3. radio、checkbox、switch、slider：选择类组件

```xml
<!-- 单选：radio-group 监听变化 -->
<radio-group data-field="gender" bindchange="onPickChange">
  <label><radio value="male" color="#ff6a00" />男</label>
  <label><radio value="female" color="#ff6a00" />女</label>
</radio-group>

<!-- 多选：checkbox-group 的 e.detail.value 是数组 -->
<checkbox-group data-field="sessions" bindchange="onPickChange">
  <label wx:for="{{sessionOptions}}" wx:key="id">
    <checkbox value="{{item.id}}" color="#ff6a00" />{{item.label}}
  </label>
</checkbox-group>

<!-- 开关 -->
<switch checked="{{form.needInvoice}}" data-field="needInvoice" bindchange="onSwitch" color="#ff6a00" />

<!-- 滑杆：同行人数 0-5 -->
<slider
  min="0"
  max="5"
  step="1"
  value="{{form.companions}}"
  data-field="companions"
  show-value
  activeColor="#ff6a00"
  bindchange="onSliderChange"
/>
```

```typescript
Page({
  onPickChange(e: WechatMiniprogram.CustomEvent<string | string[]>) {
    const field = e.currentTarget.dataset.field as keyof SignupForm
    this.setData({ [`form.${field}`]: e.detail.value, [`errors.${field}`]: '' })
  },

  onSwitch(e: WechatMiniprogram.CustomEvent<boolean>) {
    const field = e.currentTarget.dataset.field as 'needInvoice'
    const patch: Record<string, unknown> = {
      [`form.${field}`]: e.detail.value,
      [`errors.${field}`]: '',
    }
    // 关闭发票时连带清空发票抬头及其错误
    if (!e.detail.value) {
      patch['form.invoiceTitle'] = ''
      patch['errors.invoiceTitle'] = ''
    }
    this.setData(patch)
  },

  onSliderChange(e: WechatMiniprogram.CustomEvent<number>) {
    this.setData({ 'form.companions': e.detail.value, 'errors.companions': '' })
  },
})
```

要点：

1. `radio-group` 的值是选中 radio 的 `value`（字符串）；`checkbox-group` 的值是勾选值数组，顺序按选项顺序而非点击顺序。
2. `label` 包住控件可扩大点击区域，比只点小圆圈友好。
3. `slider` 同时有 `bindchanging`（拖动过程中高频触发）和 `bindchange`（松手）；联动重计算若较重应只监听 change。

误区提醒：

- 不要试图给每个 radio 单独绑事件取值，值永远从 group 的 change 事件拿，单一真值入口。

### 4. picker：五种 mode 的选择器

`picker` 是点击后从底部弹起的选择器，覆盖五类常见选择。

```xml
<!-- 1. selector：单选一列 -->
<picker
  mode="selector"
  range="{{foodOptions}}"
  range-key="label"
  value="{{foodIndex}}"
  data-field="foodPref"
  bindchange="onFoodPick"
>
  <view class="picker-value">{{form.foodPref ? foodOptions[foodIndex].label : '请选择饮食偏好'}}</view>
</picker>

<!-- 2. multiSelector：多列，如数量+规格 -->
<picker mode="multiSelector" range="{{multiColumns}}" bindchange="onMultiPick" bindcolumnchange="onColumnChange">
  <view class="picker-value">多列选择</view>
</picker>

<!-- 3. time / 4. date -->
<picker mode="time" value="{{formTime}}" bindchange="onTimePick">
  <view class="picker-value">{{formTime || '选择集合时间'}}</view>
</picker>
<picker mode="date" value="{{form.sessionDate}}" start="{{today}}" fields="day" data-field="sessionDate" bindchange="onDatePick">
  <view class="picker-value">{{form.sessionDate || '选择场次日期'}}</view>
</picker>

<!-- 5. region：省市区 -->
<picker mode="region" value="{{form.region}}" data-field="region" bindchange="onRegionPick">
  <view class="picker-value">{{form.region.length ? form.region.join(' ') : '选择所在城区'}}</view>
</picker>
```

各 mode 返回的 `e.detail.value`：

| mode | value 形态 | 额外字段 |
|---|---|---|
| selector | 下标 number | - |
| multiSelector | 每列下标 number[] | bindcolumnchange 提供列变化 |
| time | `"HH:mm"` | - |
| date | `"YYYY-MM-DD"`（随 fields 变化） | - |
| region | `[省, 市, 区]` | `code` 行政区划代码、`postcode` |

要点：

1. selector 拿到的是**下标**不是值，展示与入库要经 `range[index]` 转换；不要把下标当业务值存。
2. date 的 `start`/`end` 限定可选区间，报名截止后日期应禁选，比选完再报错好。
3. region 的值是中文名称数组，做统计分析更建议同时保存 `code`。
4. 需要选择器常驻页面（不是弹起）时用 `picker-view`，常用于多步表单底部内嵌选择。

误区提醒：

- multiSelector 的列联动（如第一列变了第二列选项要换）必须在 `bindcolumnchange` 里重建对应列数据并保留已选合法下标，否则出现越界空选。

### 5. 受控绑定原理：事件回写与 setData 跨线程

小程序双线程模型下，输入控件与数据的关系和 Web React 受控组件几乎同构，但要牢记**跨线程**成本：

```text
渲染层：用户敲字 -> input 事件 detail.value
        -> native 桥（逻辑层/渲染层通信，序列化）
逻辑层：onInput -> setData({ [path]: value })
        -> native 桥（把新 data diff 送回渲染层）
渲染层：input value 被刷新
```

统一的受控输入处理器：

```typescript
function onInput(this: SignupPage, e: WechatMiniprogram.Input) {
  const field = e.currentTarget.dataset.field as keyof SignupForm
  const value = e.detail.value

  this.setData({
    [`form.${field}`]: value,
    [`errors.${field}`]: '', // 用户开始修改即清除该字段错误
  })
  this.scheduleDraft()
}
```

路径 setData 的好处是只传变化字段：

```typescript
this.setData({ 'form.phone': '13800000000' }) // 只跨线程传一个字符串
```

成本意识：

1. 大表单里每敲一个字都有一次“渲染层 → 逻辑层 → 渲染层”的往返，因此 `setData` 只带必要字段，别顺手把整个 `form` 重发。
2. 不要在 input 里做重计算（遍历大数组、复杂正则回溯）后再 setData，打字会卡顿。
3. 错误清除应精准到字段，而不是清掉整个 `errors`。

误区提醒：

- “改了 `this.data.form.phone` 界面会更新”——错误。直接改对象不经过 setData 不会跨线程同步，渲染层看不到。

### 6. model:value：简易双向绑定

基础库 2.9.3 起支持简易双向绑定，文本类组件可省去手写 input 处理器：

```xml
<input model:value="{{form.name}}" placeholder="姓名" />
<textarea model:value="{{form.remark}}" placeholder="备注" />
```

编译器会把它展开为“value 绑定 + input 事件自动回写同一路径”。

它也支持支持约定的自定义组件（组件声明 `value` 属性并通过 `input` 事件回传）：

```xml
<my-field model:value="{{form.name}}" />
```

使用限制（必须记住）：

1. 绑定表达式必须是**单一数据路径**，如 `form.name`；不能是字面量、运算表达式、函数调用。
2. 一个组件只能有一个双向绑定属性（如开关类对应 `model:checked` 的场景按组件约定）。
3. 它只负责“值回去”，**不会**帮你清错误、做格式化、触发联动；这些仍需显式监听事件。
4. 深层路径（`form.a.b`）要求中间对象已存在，否则写入失败。

选型建议：

- 纯收集、无即时变换的字段用 `model:value` 最省代码；
- 需要“输入即联动/清错/存草稿”的字段仍用受控处理器显式控制。

误区提醒：

- 不要写 `model:value="{{form.phone.trim()}}"` 这类表达式，双向绑定不接受运算。

### 7. 声明式校验规则：必填、长度、正则、数字范围

把规则从 `if` 堆砌升级为**声明式规则表**，规则可复用、可序列化、可按条件启用。

```typescript
type Rule =
  | { kind: 'required'; message: string }
  | { kind: 'length'; min?: number; max?: number; message: string }
  | { kind: 'pattern'; regex: RegExp; message: string }
  | { kind: 'range'; min?: number; max?: number; message: string }

interface FieldSchema {
  label: string
  /** 返回 false 时该字段本次不参与校验（条件字段） */
  when?: (form: SignupForm) => boolean
  rules: Rule[]
}

type SignupSchema = Record<keyof SignupForm, FieldSchema>
```

报名表单规则表：

```typescript
const schema: SignupSchema = {
  name: {
    label: '联系人',
    rules: [
      { kind: 'required', message: '请输入联系人姓名' },
      { kind: 'length', min: 2, max: 20, message: '姓名长度需为 2-20 个字' },
    ],
  },
  phone: {
    label: '手机号',
    rules: [
      { kind: 'required', message: '请输入手机号' },
      { kind: 'pattern', regex: /^1[3-9]\d{9}$/, message: '手机号格式不正确' },
    ],
  },
  gender: {
    label: '性别',
    rules: [{ kind: 'required', message: '请选择性别' }],
  },
  companions: {
    label: '同行人数',
    rules: [{ kind: 'range', min: 0, max: 5, message: '同行人数需在 0-5 之间' }],
  },
  sessions: {
    label: '参加场次',
    rules: [{ kind: 'required', message: '请至少选择一个场次' }],
  },
  sessionDate: {
    label: '场次日期',
    rules: [{ kind: 'required', message: '请选择场次日期' }],
  },
  needInvoice: { label: '发票', rules: [] },
  invoiceTitle: {
    label: '发票抬头',
    when: (form) => form.needInvoice,
    rules: [
      { kind: 'required', message: '请输入发票抬头' },
      { kind: 'length', min: 4, max: 60, message: '发票抬头长度需为 4-60 个字' },
    ],
  },
  foodPref: {
    label: '饮食偏好',
    rules: [{ kind: 'required', message: '请选择饮食偏好' }],
  },
  foodPrefOther: {
    label: '其他偏好',
    when: (form) => form.foodPref === 'other',
    rules: [
      { kind: 'required', message: '请填写其他饮食偏好' },
      { kind: 'length', max: 30, message: '不超过 30 个字' },
    ],
  },
  region: {
    label: '所在城区',
    rules: [{ kind: 'required', message: '请选择所在城区' }],
  },
  remark: {
    label: '备注',
    rules: [{ kind: 'length', max: 200, message: '备注不超过 200 个字' }],
  },
}
```

规则执行器（返回第一条错误；非必填字段为空时跳过其他规则）：

```typescript
function validateField(form: SignupForm, field: keyof SignupForm): string {
  const conf = schema[field]
  if (conf.when && !conf.when(form)) return ''

  const raw = form[field]
  const isEmpty =
    raw === '' || raw === undefined || raw === null ||
    (Array.isArray(raw) && raw.length === 0)

  for (const rule of conf.rules) {
    if (rule.kind === 'required') {
      if (isEmpty) return rule.message
      continue
    }

    // 非必填项为空时，后续规则一律跳过
    if (isEmpty) return ''

    switch (rule.kind) {
      case 'length': {
        const len = String(raw).trim().length
        if ((rule.min !== undefined && len < rule.min) || (rule.max !== undefined && len > rule.max)) {
          return rule.message
        }
        break
      }
      case 'pattern':
        if (!rule.regex.test(String(raw).trim())) return rule.message
        break
      case 'range': {
        const n = Number(raw)
        if (Number.isNaN(n) || (rule.min !== undefined && n < rule.min) || (rule.max !== undefined && n > rule.max)) {
          return rule.message
        }
        break
      }
    }
  }

  return ''
}
```

要点：

1. 规则与 UI 解耦：新增字段只加一条 schema，校验器代码不动。
2. 字符串校验前 `trim`，避免一堆空格骗过必填；但要保留用户原始值，trim 只用于判断。
3. 正则要克制，避免灾难性回溯；手机号这类通用格式用成熟稳定的写法。

误区提醒：

- 只在前端写正则就认为数据安全——前端校验随时可被绕过，服务端必须重验。

### 8. 字段联动：依赖、重算与联动清空

联动的三类常见动作：

1. **清空依赖字段**：开关关掉发票，发票抬头与其错误一起清（见第 3 节 onSwitch）。
2. **刷新可选项**：选定场次日期后，当天可选的场次列表才有效，换日期要重拉/过滤并剔除已选的失效场次。
3. **切换条件字段**：饮食偏好从“其他”切走时，清空 `foodPrefOther`。

```typescript
async function onDatePick(this: SignupPage, e: WechatMiniprogram.CustomEvent<string>) {
  const date = e.detail.value
  const options = await fetchSessions(date) // U17 的网络层

  const validIds = new Set(options.map((o) => o.id))
  const kept = this.data.form.sessions.filter((id) => validIds.has(id))

  this.setData({
    'form.sessionDate': date,
    'form.sessions': kept, // 剔除跨日期不可用的旧选择
    sessionOptions: options,
    'errors.sessionDate': '',
  })
}

function onFoodPick(this: SignupPage, e: WechatMiniprogram.CustomEvent<number>) {
  const index = e.detail.value
  const value = this.data.foodOptions[index].value
  const patch: Record<string, unknown> = {
    'form.foodPref': value,
    'errors.foodPref': '',
  }
  if (value !== 'other') {
    patch['form.foodPrefOther'] = ''
    patch['errors.foodPrefOther'] = ''
  }
  this.setData(patch)
}
```

联动设计原则：

- 联动规则集中在字段的 change 处理器里，不要散落在多个页面；
- 每次联动后顺带清理可能失效的错误，否则界面会残留“其实已合法”的红字；
- 异步联动（换日期拉场次）要有加载态与失败兜底，避免选项停留在旧数据。

误区提醒：

- 不要在被联动字段上保留旧值却不提示——用户以为选了 A 日期的场次，实际值已非法。要么显式剔除，要么弹窗告知。

### 9. 统一错误提示与提交前整体校验

错误展示分两层：字段下方就近红字（持续可见）+ 提交时整体校验并滚动/聚焦到第一个错误。

```typescript
type ErrorsMap = Partial<Record<keyof SignupForm, string>>

function validateAll(form: SignupForm): ErrorsMap {
  const errors: ErrorsMap = {}
  ;(Object.keys(schema) as (keyof SignupForm)[]).forEach((field) => {
    const message = validateField(form, field)
    if (message) errors[field] = message
  })
  return errors
}

function validateSome(form: SignupForm, fields: (keyof SignupForm)[]): ErrorsMap {
  const errors: ErrorsMap = {}
  fields.forEach((field) => {
    const message = validateField(form, field)
    if (message) errors[field] = message
  })
  return errors
}
```

页面上锚点定位第一个错误字段（给每个 field 容器加 id）：

```typescript
function focusFirstError(errors: ErrorsMap): void {
  const first = Object.keys(errors)[0] as keyof SignupForm | undefined
  if (!first) return

  wx.pageScrollTo({ selector: `#field-${first}`, duration: 200 })
  wx.showToast({ title: errors[first]!, icon: 'none' })
}
```

校验时机策略：

| 时机 | 行为 |
|---|---|
| 输入中 | 仅清错，不报错（避免打断） |
| 失焦 blur | 校验当前字段，给出红字 |
| 提交 | 整表校验，定位第一个错误 |
| 服务端返回 | 字段级错误回填（第 13 节） |

误区提醒：

- 只弹一个 toast“表单有误”是最差体验：用户不知道错在哪、错了几个；必须字段级可见。

### 10. form 容器：name 提交模式与受控模式对比

小程序还提供 `<form>` 容器的原生提交：控件加 `name`，按钮用 `form-type="submit"`，提交事件一次性收集所有命名字段。

```xml
<form bindsubmit="onNativeSubmit" bindreset="onReset">
  <input name="title" placeholder="标题" />
  <switch name="agree" />
  <button form-type="submit">提交</button>
  <button form-type="reset">重置</button>
</form>
```

```typescript
onNativeSubmit(e: WechatMiniprogram.FormSubmit) {
  const values = e.detail.value as { title: string; agree: boolean }
}
```

两种模式对比：

| 对比项 | 受控模式（data 真值） | form/name 模式 |
|---|---|---|
| 实时联动 | 强，字段变化即可响应 | 弱，只在提交时拿值 |
| 错误就近展示 | 方便 | 需自行补受控逻辑 |
| 多步/草稿 | 天然支持 | 不直接支持 |
| 适合场景 | 复杂业务表单 | 简单一次性表单、筛选条 |

本单元主线一律采用**受控模式**；form/name 模式了解即可，适合设置页那种字段少、无联动的表单。

误区提醒：

- form/name 模式下没加 `name` 的控件不会出现在 `detail.value`，排查“字段怎么是 undefined”先看 name。

### 11. 多步表单：分步、单步校验与状态保存

报名信息较长时拆成三步：基本信息 → 同行与场次 → 确认提交。

```typescript
const STEPS: { key: string; title: string; fields: (keyof SignupForm)[] }[] = [
  { key: 'base', title: '基本信息', fields: ['name', 'phone', 'gender', 'region'] },
  { key: 'plan', title: '同行与场次', fields: ['companions', 'sessionDate', 'sessions', 'foodPref', 'foodPrefOther'] },
  { key: 'confirm', title: '确认提交', fields: ['needInvoice', 'invoiceTitle', 'remark'] },
]
```

```xml
<view class="steps">
  <view wx:for="{{stepTitles}}" wx:key="*this" class="dot {{index <= step ? 'active' : ''}}">
    {{index + 1}} {{item}}
  </view>
</view>

<!-- 仅渲染当前步骤的字段，数据始终保存在 form 中 -->

<button bindtap="prev" wx:if="{{step > 0}}">上一步</button>
<button bindtap="next" wx:if="{{step < 2}}">下一步</button>
<button type="primary" bindtap="submit" wx:if="{{step === 2}}">确认报名</button>
```

```typescript
function next(this: SignupPage) {
  const current = STEPS[this.data.step]
  const errors = validateSome(this.data.form, current.fields)

  if (Object.keys(errors).length > 0) {
    this.setData({ errors: { ...this.data.errors, ...errors } })
    focusFirstError(errors)
    return
  }

  this.setData({ step: this.data.step + 1 })
}

function prev(this: SignupPage) {
  this.setData({ step: Math.max(0, this.data.step - 1) })
}
```

要点：

1. 只有当前步骤校验通过才放行，不能“先跳过去回头再补”，否则最后一步集中爆错。
2. 所有步骤共享同一个 `form` 对象，上一步数据不会因切走而丢；确认页只读展示汇总。
3. 允许点进度条回退到已完成步骤修改，前进时重新校验该步。

误区提醒：

- 不要用三个独立页面做步骤然后靠全局变量传数据——状态保存、返回键、草稿恢复都会变复杂；同页分步是首选。

### 12. 草稿本地恢复：防抖保存、按活动识别

用户填一半被电话打断是常态。用 U12 的 Storage 工具做草稿：

```typescript
import { get, set, remove } from '../../utils/storage'

const DRAFT_KEY_PREFIX = 'signup_draft'
const DRAFT_TTL = 24 * 60 * 60 * 1000 // 草稿保留一天

interface SignupDraft {
  activityId: string
  form: SignupForm
  step: number
  savedAt: number
}

let draftTimer: ReturnType<typeof setTimeout> | null = null

function draftKey(activityId: string): string {
  return `${DRAFT_KEY_PREFIX}_${activityId}`
}

function scheduleDraft(this: SignupPage) {
  if (draftTimer) clearTimeout(draftTimer)
  draftTimer = setTimeout(() => {
    set(
      draftKey(this.data.activityId),
      {
        activityId: this.data.activityId,
        form: this.data.form,
        step: this.data.step,
        savedAt: Date.now(),
      } satisfies SignupDraft,
      DRAFT_TTL,
    )
  }, 600)
}
```

进入页面时识别并提示恢复：

```typescript
function onLoad(this: SignupPage, query: { id?: string }) {
  const activityId = query.id ?? ''
  this.setData({ activityId })

  const draft = get<SignupDraft | null>(draftKey(activityId), null)

  if (draft && hasMeaningfulData(draft.form) && Date.now() - draft.savedAt < DRAFT_TTL) {
    wx.showModal({
      title: '恢复报名',
      content: `检测到 ${formatTime(draft.savedAt)} 未提交的报名信息，是否继续填写？`,
      confirmText: '恢复',
      cancelText: '不恢复',
      success: (res) => {
        if (res.confirm) {
          this.setData({ form: draft.form, step: draft.step })
        } else {
          remove(draftKey(activityId))
        }
      },
    })
  }
}
```

要点：

1. 草稿必须绑定 `activityId`，换活动不能串草稿；恢复时再校验 TTL。
2. 只有“存在有意义输入”才提示，空白表单不弹窗。
3. 提交成功立即删除草稿，避免下次进来恢复已报名数据。
4. 身份证等敏感字段不进草稿（本主线报名不采集；若业务需要，应单独评估加密与合规）。

误区提醒：

- 不要在 `onUnload` 无条件覆盖草稿——用户主动“不恢复”后又被写回，应区分用户意图。

### 13. 提交态、防重复提交与服务端错误回填

提交是整个表单风险最高的一环：网络抖动时用户连点会产生两条报名。

统一提交逻辑：

```typescript
interface FieldApiError {
  fieldErrors?: Partial<Record<keyof SignupForm, string>>
  message?: string
}

async function submit(this: SignupPage) {
  // 1. 提交中直接吞掉后续点击
  if (this.data.submitting) return

  // 2. 整体校验
  const errors = validateAll(this.data.form)
  if (Object.keys(errors).length > 0) {
    this.setData({ errors, step: earliestErrorStep(errors) })
    focusFirstError(errors)
    return
  }

  // 3. 进入提交态：按钮 loading + 遮罩，幂等键只生成一次
  const idempotencyKey = this.data.idempotencyKey || makeIdempotencyKey()
  this.setData({ submitting: true, idempotencyKey })
  wx.showLoading({ title: '提交中', mask: true })

  try {
    await submitSignup({
      activityId: this.data.activityId,
      form: normalize(this.data.form),
      idempotencyKey, // 服务端按此键去重：同键只落一单
    })

    remove(draftKey(this.data.activityId))
    wx.showToast({ title: '报名成功', icon: 'success' })
    setTimeout(() => wx.redirectTo({ url: '/pages/signup/result/result' }), 800)
  } catch (err) {
    handleSubmitError(this, err as FieldApiError)
  } finally {
    wx.hideLoading()
    this.setData({ submitting: false })
  }
}
```

防重提交的四道闸：

1. `submitting` 布尔位 + 按钮 `disabled`/`loading`，函数入口再判一次（事件可能排队）；
2. `mask: true` 的 loading 挡住界面其它点击；
3. 幂等键随请求带给服务端，**重试复用同一个键**，服务端落单前去重，这是根治“超时后重试产生两单”的关键；
4. 成功后跳转用 `redirectTo`，避免返回键回到提交页再触发。

服务端字段错误回填：

```typescript
function handleSubmitError(page: SignupPage, err: FieldApiError): void {
  if (err.fieldErrors && Object.keys(err.fieldErrors).length > 0) {
    // 服务端字段名可能是 snake_case，必要时先做映射
    const mapped = mapServerFields(err.fieldErrors)
    page.setData({ errors: mapped })
    focusFirstError(mapped)
  } else {
    wx.showToast({ title: err.message || '提交失败，请重试', icon: 'none' })
  }
}
```

要点：

- 服务端常见返回：名额已满（业务错误，toast/弹窗）、手机号已报名（可定位到 phone 字段）、422 字段校验错误（批量回填）。前端要区分这三类，不能一律“网络错误”。
- 幂等键在一次报名会话内保持不变，只有报名成功或用户明确重置表单后才换新键。

误区提醒：

- 防重点击只做前端禁用是不够的——弱网下请求超时、用户杀小程序重进都可能重复，真正的去重必须由服务端按幂等键完成。

### 15. 常见误区、可访问性与上线自查清单

**功能误区：**

1. 空值形态不统一，校验器到处判空；
2. 在 input 里做格式变换导致光标跳位；
3. selector 把下标当业务值入库；
4. 联动后不清错误、不剔失效值，残留非法状态；
5. 提交只弹“表单有误”，没有字段级提示与定位；
6. 多步表单不做单步校验，最后一步集中爆错；
7. 草稿不绑活动、不设过期，串活动恢复；
8. 只做按钮禁用，没有幂等键，弱网重试产生重复单据；
9. 服务端字段错误没有回填，用户只能靠 toast 猜；
10. 以为前端正则就是安全边界，服务端不重验。

**可访问性与体验：**

- 用 `label` 扩大点击区域；点击区域不小于常见触控尺寸；
- 键盘类型与字段匹配（数字键盘、完成键引导下一步）；
- 长表单注意键盘遮挡，真机验证 `cursor-spacing`；
- 错误文案说清“要什么”，如“请输入 11 位手机号”，不要只写“格式错误”。

**安全底线：**

- 服务端必须重验全部规则，并对名额、重复报名做业务校验；
- 最小化收集个人信息，敏感字段不进本地草稿、不打日志；
- 用户输入在他人页面展示（如报名留言上墙）要做服务端转义/清洗，防 XSS。

**上线前自查清单：**

1. 必填、长度、正则、范围四类规则是否都在真机上走通过；
2. 名额已满、重复报名、服务端 422 三类错误表现是否正确；
3. 弱网/超时下连点提交是否只产生一单（查服务端记录）；
4. 杀进程重进草稿恢复、提交成功后草稿清理是否生效；
5. 键盘遮挡、聚焦滚动、多步往返是否在 iOS 与 Android 真机验证。

### 练习 2：三步报名表单 + 草稿恢复

#### 任务

把报名表单拆成“基本信息 / 同行与场次 / 确认提交”三步，单步校验通过才能前进；输入防抖 600 ms 自动保存草稿，杀进程重进按 activityId 提示恢复，成功提交后清理草稿。

参考伪代码：

```text
下一步 -> validateSome(当前步字段) -> 有错定位，无错 step+1
输入 -> scheduleDraft -> set(signup_draft_{activityId}, {form, step, savedAt}, TTL 一天)
```

## 阶段验收作业

本作业是阶段三“平台能力”的表单综合证据点，重点证明**你能为「逛吃指南」交付一个多字段、可联动、可恢复、防重复、能消化服务端错误的活动报名表单，并清楚校验与安全边界**。

### 任务描述

实现「逛吃指南」活动报名页（建议同页三步），包含：

1. 字段采集：姓名、手机号、性别、同行人数（0-5）、多场次勾选、场次日期、发票开关与抬头、饮食偏好（含“其他”条件输入）、所在城区、备注。
2. 校验工程：声明式规则覆盖必填、长度、正则、数字范围；条件字段（发票抬头、其他偏好）按 when 启用；输入清错、blur 单字段校验、提交整表校验并定位第一个错误。
3. 字段联动：换日期过滤并剔除不可用场次；关发票清抬头；偏好离开“其他”清自定义输入。
4. 多步与草稿：三步分步 + 单步校验；草稿防抖保存、按 activityId 恢复、TTL 一天、成功即清。
5. 提交闭环：提交态 + 遮罩 + 幂等键防重；服务端字段错误回填，业务错误（名额已满/重复报名）正确提示。
6. 提交不超过 300 字说明：前端校验与服务端校验的分工、幂等去重原理、个人信息保护做法。

### 完成标准

- 真机上完整走通“填写 → 分步校验 → 草稿中断恢复 → 提交 → 结果页”，数据正确入库；
- 非法输入在字段级可见，提交时定位准确；条件字段启用/停用与 UI 一致；
- 弱网连点、超时重试只产生一单（以服务端记录为准）；
- 服务端返回 422 字段错误可精确回填，名额已满等业务错误有明确提示；
- 草稿按活动隔离、过期失效、成功清理；
