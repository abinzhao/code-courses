# 24-订阅消息与服务通知

## 目标

完成本知识单元后，学员应能把「用户为什么会收到、又为什么收不到小程序发来的服务通知」从授权、额度到服务端下发完整讲清楚，并在「逛吃指南」中实现「支付成功后请求订阅 → 服务端记录授权 → 在支付成功/核销/活动开始节点准时下发通知」的完整服务通知链路。

学员应能够：

1. 说清订阅消息的定位：它是小程序在用户**主动订阅授权**后才能下发的服务通知，分为**一次性订阅**与**长期订阅**，区别于已下线的旧模板消息和受严格时间窗限制的客服消息。
2. 掌握 `wx.requestSubscribeMessage` 的调用方式、`tmplIds` 参数规则与返回结果，能识别用户对每个模板的三种选择：同意（accept）、拒绝（reject）、后台被禁用（ban）。
3. 理解一次性订阅「一次授权只能下发一条」的额度模型，以及用户勾选「总是保持以上选择」后的授权行为，能在服务端正确记录每个用户对每个模板的可用额度。
4. 在微信公众平台为小程序配置订阅消息模板（类目、模板标题、字段、关键词），理解模板字段类型与顺序对下发 `data` 的约束。
5. 在 Node 服务端/云函数中获取并缓存 `access_token`（全局共享、提前刷新、中控原则），牢记 **access_token 只能在服务端获取与使用，绝不下放前端**。
6. 使用服务端接口 `subscribeMessage.send` 正确下发：指定 `touser`(openid)、`template_id`、`page`、`data`、`miniprogram_state` 等参数，并用 TypeScript 约束模板字段。
7. 掌握支付成功回调、扫码核销、活动开始前（定时触发器）三类典型触发时机，把通知挂到 U23 交易闭环的正确节点上。
8. 理解下发额度的获取与扣减：未授权、额度用尽、用户关闭都会导致下发失败，能根据返回 errcode（如 43101）做重试、降级与重新引导授权。
9. 划清客服消息边界（仅在用户主动交互后的有限时间窗内可下发），避免把订阅消息当营销群发，规避投诉与能力封禁。
10. 交付「完成支付 → 引导订阅 → 支付结果通知」的可演示闭环，并说明订阅消息的合规要求与常见误区。

本单元承接 U23 微信支付，是商业化交易闭环的「最后一公里」：让支付结果、核销确认、活动提醒可靠触达用户。

## 技术栈

本单元前端使用微信原生 + TypeScript 完成订阅授权，模板在公众平台配置，消息下发与 `access_token` 管理全部在 Node 服务端或微信云开发云函数中完成。

| 工具或环境 | 用途 | 学习要求 |
|---|---|---|
| wx.requestSubscribeMessage | 请求一次性/长期订阅授权 | 参数、返回值、三种用户选择 |
| 微信公众平台 · 订阅消息 | 配置模板、类目、关键词 | 模板 id、字段顺序与类型 |
| access_token | 服务端接口调用凭证 | 获取、缓存、提前刷新、中控，仅服务端 |
| cgi-bin/token 接口 | 用 AppID+AppSecret 换 access_token | AppSecret 仅服务端 |
| subscribeMessage.send | 下发订阅消息 | touser/template_id/page/data/state |
| Node.js（https/axios） | 服务端获取 token 与下发 | errcode 处理、重试 |
| 云函数 wx-server-sdk | openapi.subscribeMessage.send | 云开发免维护 token 的用法 |
| 云数据库 | 记录用户授权与发送结果 | 额度计数、发送日志 |
| 定时触发器 | 活动开始前提醒 | cron 配置、批量扫描下发 |
| 客服消息接口（边界认知） | 用户交互窗口内消息 | 时间窗限制、不可滥发 |

工程约定：

- **AppSecret、access_token 只存在于服务端/云函数**，前端通过业务接口间接触发下发，绝不接触凭证。
- 是否允许给某用户下发某条模板，以「服务端记录的授权额度」与下发接口实时返回为准，不能只信前端的授权成功回调。
- 服务通知内容必须与模板、用户订阅的服务场景一致，不得用于与服务无关的营销群发。
- 接口地址、额度规则、errcode、模板字段限制以微信官方文档与公众平台实际配置为准。

## 详细的理论知识讲解和示例伪代码

### 1. 订阅消息是什么：先建立正确心智

小程序里的「消息能力」经常被混淆。订阅消息的核心定义是：

> 小程序在用户**主动订阅**了某个服务场景（对应一个模板）后，才能在该服务发生时给用户下发一条一次性或长期的服务通知。通知出现在微信「服务通知」/订阅消息入口里，点击可跳回小程序指定页面。

两种订阅类型：

| 类型 | 授权与额度 | 典型场景 |
|---|---|---|
| 一次性订阅消息 | 用户每授权一次，获得**一次**下发额度；下发一条后额度清零 | 支付结果、预约结果、订单状态变更 |
| 长期订阅消息 | 用户授权后可在较长周期内多次下发（受类目/模板资质限制） | 长期服务、签到提醒、连续课程/到店提醒 |

对「逛吃指南」而言：

- 活动票支付成功通知、券核销成功通知，属于典型的**一次性订阅**；
- 若做「连续 7 天美食打卡提醒」这类长期服务，才需要长期订阅模板，且通常类目要求更严。

关键点：**先有用户授权，后有消息下发**，下发次数严格受授权额度约束，不能想发就发。

误区提醒：

- 「用户用了小程序就能给他推消息」——错误，必须逐条模板获得订阅授权。
- 「订阅消息就是老的模板消息换个名」——错误，旧模板消息能力已下线/受限，订阅消息以用户主动订阅为前提。

### 2. 订阅消息、客服消息与营销群发的边界

三类能力必须分清，发错就可能违规：

| 能力 | 触发前提 | 时间窗/额度 | 用途边界 |
|---|---|---|---|
| 订阅消息 | 用户对具体模板点了「允许」 | 一次性：一次一条；长期：按模板规则 | 仅与所订阅服务相关的通知 |
| 客服消息 | 用户在小程序内有主动交互（如点击、发送） | 交互后的有限时间窗内（如 48 小时内，以文档为准） | 客服沟通、回复用户，不是无限推送通道 |
| 营销/群发 | 受平台严格限制，不能借订阅消息随意群发 | —— | 不得用服务通知做无关广告 |

「逛吃指南」的设计选择：

- 支付结果、核销结果、活动开场提醒 → 用**订阅消息**；
- 用户主动咨询「券能不能退」→ 在交互窗口内用**客服消息**回复；
- 绝不用支付通知的模板塞「快来买别的券」这类营销内容。

误区提醒：

- 把客服消息当长期推送通道——超出时间窗就发不出。
- 用订阅消息下发与订阅场景无关的广告——易被投诉、导致消息能力受限。

### 3. wx.requestSubscribeMessage 全参数与返回结果

前端通过 `wx.requestSubscribeMessage` 弹出系统授权框，一次可请求一个或多个模板（数量有上限，以文档为准）。

最基础调用：

```typescript
// services/subscribe.ts

/** 支付结果模板 id（在公众平台配置后获得） */
export const TPL_PAY_RESULT = 'xhqpayResultTemplate001'
export const TPL_VERIFY_RESULT = 'xhqverifyTemplate002'

export function requestSubscribe(tmplIds: string[]): Promise<Record<string, string>> {
  return new Promise((resolve, reject) => {
    wx.requestSubscribeMessage({
      tmplIds,
      success(res) {
        // res 中对每个模板 id 给出一个选择
        resolve(res as unknown as Record<string, string>)
      },
      fail(err) {
        reject(err)
      },
    })
  })
}
```

返回结果里每个 `tmplId` 对应一个值：

| 返回值 | 含义 | 服务端含义 |
|---|---|---|
| `accept` | 用户本次同意订阅 | 一次性模板 +1 条下发额度 |
| `reject` | 用户本次拒绝 | 无额度，不应下发 |
| `ban` | 用户后台已禁用该模板（或被系统判定为拒绝） | 无额度，需引导用户到设置页开启 |

调用示例与结果判读：

```typescript
const res = await requestSubscribe([TPL_PAY_RESULT, TPL_VERIFY_RESULT])
// 例如：
// {
//   xhqpayResultTemplate001: 'accept',
//   xhqverifyTemplate002: 'reject',
//   errMsg: 'requestSubscribeMessage:ok'
// }

if (res[TPL_PAY_RESULT] === 'accept') {
  // 把「该用户对支付结果模板 +1 额度」上报服务端
  await reportGrant(TPL_PAY_RESULT)
}
```

要特别注意：**前端拿到 accept 只是“授权动作成功”，真正能不能下发还要看服务端记录额度并调用接口**。弱网下前端授权成功但上报服务端失败，就会出现“用户同意了却没收到”的情况，因此授权结果必须可靠落库（见第 4 节）。

误区提醒：

- 不判读每个模板的返回值，把弹窗成功等同于所有模板都同意。
- 在用户没有任何相关操作时一进页面就狂弹授权框，体验差且易被拒。

### 4. 授权结果上报与额度记录

授权结果要落到服务端，建议用一张「订阅授权表」记录每个用户、每个模板的可用额度与版本状态。

```typescript
// types/subscription.ts
export interface UserSubscription {
  _id: string
  openid: string
  templateId: string
  /** 一次性订阅：当前剩余可下发条数 */
  quota: number
  /** 授权类型 */
  type: 'once' | 'long_term'
  /** 最近一次用户选择 */
  lastChoice: 'accept' | 'reject' | 'ban'
  updatedAt: Date
}

export interface SendLog {
  _id: string
  openid: string
  templateId: string
  bizId: string // 关联订单号/活动 id，便于对账
  errcode: number
  errmsg: string
  sentAt: Date
}
```

前端授权后上报（注意幂等，防止重复点击导致额度虚高）：

```typescript
// services/subscribe.ts
import { http } from '../utils/request'

export async function reportGrant(templateId: string): Promise<void> {
  await http.post('/v1/subscribe/grant', { templateId }, { silent: true })
}
```

服务端接收授权（云函数中可直接从登录态拿 openid）：

```javascript
// cloud-functions/subGrant/index.js
const cloud = require('wx-server-sdk')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const db = cloud.database()
const _ = db.command

exports.main = async (event) => {
  const { OPENID } = cloud.getWXContext()
  const { templateId } = event

  // 原子自增：同一用户+模板维度累加一次性额度
  const existing = await db
    .collection('user_subscriptions')
    .where({ openid: OPENID, templateId })
    .limit(1)
    .get()

  if (existing.data.length === 0) {
    await db.collection('user_subscriptions').add({
      data: {
        openid: OPENID,
        templateId,
        quota: 1,
        type: 'once',
        lastChoice: 'accept',
        updatedAt: new Date(),
      },
    })
  } else {
    await db
      .collection('user_subscriptions')
      .doc(existing.data[0]._id)
      .update({
        data: {
          quota: _.inc(1),
          lastChoice: 'accept',
          updatedAt: new Date(),
        },
      })
  }
  return { code: 0 }
}
```

要点：额度自增要在服务端做，且与「一次用户授权」一一对应；前端重复上报不应让额度凭空增加（可用授权请求的 nonce/幂等键约束）。

### 5. 订阅时机与交互设计：支付成功后再订阅

授权弹窗的时机直接决定接受率。最佳实践是在**用户能明确感知“我需要这条通知”的场景**请求，例如：

- 用户点「立即支付」前/支付成功页：「是否接收支付成功通知？」；
- 报名活动成功后：「是否接收活动开始提醒？」；
- 券核销操作后：「是否接收核销凭证？」。

「逛吃指南」推荐的支付闭环交互：在用户完成支付后的结果页（或支付前与用户约定）请求订阅，此时用户最清楚通知的价值。

```typescript
// pages/pay-result/index.ts
import { requestSubscribe, reportGrant, TPL_PAY_RESULT } from '../../services/subscribe'
import { getOrderDetail } from '../../services/order'

Page({
  data: { orderNo: '' },

  onLoad(query: Record<string, string>) {
    this.setData({ orderNo: query.orderNo })
    // 支付结果已产生，此时订阅用于接收后续核销/活动提醒；
    // 支付成功结果本身的通知，应在「支付前」就已获得授权（见练习）
  },

  async onSubscribeNotify() {
    try {
      const res = await requestSubscribe([TPL_PAY_RESULT])
      if (res[TPL_PAY_RESULT] === 'accept') {
        await reportGrant(TPL_PAY_RESULT)
        wx.showToast({ title: '已开启通知', icon: 'success' })
      } else if (res[TPL_PAY_RESULT] === 'ban') {
        this.guideOpenSetting()
      } else {
        wx.showToast({ title: '已取消订阅', icon: 'none' })
      }
    } catch {
      wx.showToast({ title: '订阅失败，请稍后再试', icon: 'none' })
    }
  },

  guideOpenSetting() {
    wx.showModal({
      title: '通知已被关闭',
      content: '可在设置中打开订阅消息开关',
      confirmText: '去设置',
      success: (r) => {
        if (r.confirm) wx.openSetting()
      },
    })
  },
})
```

设计原则：**不强弹、不欺骗、说明用途**。对 `ban` 状态不要反复弹框，应引导去设置页；对 `reject` 用户可在下次相关场景再温和询问一次，不连续骚扰。

误区提醒：

- 首页一加载就 `requestSubscribeMessage`，与服务场景无关联，拒绝率极高。
- 对 ban 用户反复弹窗——系统不会允许，只会恶化体验。

### 6. 在公众平台配置订阅消息模板

模板不是自己随便写 JSON 就能用，需要在微信公众平台（mp.weixin.qq.com）「订阅消息」中：

1. 选择/申请符合业务的**类目**（如电商交易、餐饮美食服务等）；
2. 在公共模板库中挑选合适模板，或在允许范围内申请自定义模板；
3. 确认模板的**标题、关键词字段（name）与顺序**，发布后得到 `template_id`。

一个「支付成功通知」模板的字段示意（真实以平台模板为准）：

```text
模板标题：支付成功通知
模板 id：xhqpayResultTemplate001
关键词：
  thing1   商品名称
  amount2  支付金额
  date3    支付时间
  character_string4 订单编号
  phrase5   支付状态
```

服务端下发的 `data`，键名必须与模板字段一一对应，且值要符合字段类型约束（如 `thing` 一般为短文本、`amount` 带金额、`date` 为时间）。

```json
{
  "thing1": { "value": "阿婆牛杂代金券" },
  "amount2": { "value": "￥30.00" },
  "date3": { "value": "2026-10-09 12:35" },
  "character_string4": { "value": "GC17284464001234" },
  "phrase5": { "value": "支付成功" }
}
```

要点：

1. 模板字段顺序/键名一旦确定，服务端 `data` 必须严格匹配，漏字段或键名错误会报参数错误。
2. 不同环境（开发/线上）模板可能不同，建议把 `template_id` 放进配置而不是写死。
3. 内容要落在模板语义范围内，避免用“其他”字段硬塞营销话术。

误区提醒：

- 以为 `data` 里随便加 key 都行——必须是模板里已有的关键词。
- 用线上不存在的模板 id 去发，报模板不存在。

### 7. access_token：获取、缓存与中控原则

调用 `subscribeMessage.send` 需要 `access_token`。它由 AppID + AppSecret 调用 `cgi-bin/token` 接口获得，**有效期通常为 7200 秒，需要缓存并提前刷新**。

获取接口（服务端发起，AppSecret 仅服务端）：

```text
GET https://api.weixin.qq.com/cgi-bin/token?grant_type=client_credential&appid=APPID&secret=APPSECRET
```

返回：

```json
{ "access_token": "ACCESS_TOKEN", "expires_in": 7200 }
```

服务端 token 管理器（中控：全系统统一一份，避免互相刷新导致旧 token 失效）：

```javascript
// server/utils/access-token.js
const https = require('https')

let cached = { value: '', expireAt: 0 }
let inflight = null // 合并并发刷新

function fetchTokenFromWx() {
  const appid = process.env.WX_APPID
  const secret = process.env.WX_APPSECRET
  const path = `/cgi-bin/token?grant_type=client_credential&appid=${appid}&secret=${secret}`

  return new Promise((resolve, reject) => {
    https.get(`https://api.weixin.qq.com${path}`, (res) => {
      let chunks = ''
      res.on('data', (d) => (chunks += d))
      res.on('end', () => {
        const json = JSON.parse(chunks)
        if (json.access_token) resolve(json.access_token)
        else reject(new Error('获取 access_token 失败: ' + chunks))
      })
    }).on('error', reject)
  })
}

async function getAccessToken() {
  const now = Date.now()
  // 提前 5 分钟刷新，避免临界点过期
  if (cached.value && cached.expireAt - now > 5 * 60 * 1000) {
    return cached.value
  }

  // 多个调用同时需要 token 时，只发一次刷新请求
  if (inflight) return inflight

  inflight = fetchTokenFromWx()
    .then((token) => {
      cached = { value: token, expireAt: now + 7200 * 1000 }
      return token
    })
    .finally(() => {
      inflight = null
    })

  return inflight
}

module.exports = { getAccessToken }
```

为什么必须中控：微信每天获取 token 的次数有上限，且**每次刷新会使上一个 token 失效**。多个服务实例各自刷新会互相“踢掉”对方的 token，导致随机报错。生产中可用 Redis 等共享存储让多实例共用同一份 token 与过期时间。

安全边界：**AppSecret、access_token 绝不下发前端**。前端无法也不应直接调微信服务端接口，只能调我们自己的后端。

误区提醒：

- 每次发消息都重新获取 token——触发频率限制并使旧 token 失效。
- 多实例各自缓存 token、各自刷新——互相冲突破报 40001/42001。

### 8. subscribeMessage.send：服务端下发

拿到 token 后，服务端调用下发接口：

```text
POST https://api.weixin.qq.com/cgi-bin/message/subscribe/send?access_token=ACCESS_TOKEN
```

请求体关键字段：

| 字段 | 含义 | 约束 |
|---|---|---|
| `touser` | 接收人 openid | 必须是本小程序用户 |
| `template_id` | 模板 id | 公众平台配置 |
| `page` | 点击通知跳转的小程序页面 | 可带 query，如 `pages/order-detail/index?orderNo=xx` |
| `data` | 模板字段内容 | 与模板关键词一一对应 |
| `miniprogram_state` | 跳转小程序版本 | developer/trial/formal |
| `lang` | 语言 | zh_CN / zh_TW / en |

Node 下发封装：

```javascript

const https = require('https')
const { getAccessToken } = require('../utils/access-token')

function sendSubscribe(payload) {
  return new Promise(async (resolve, reject) => {
    const token = await getAccessToken()
    const body = JSON.stringify(payload)
    const path = `/cgi-bin/message/subscribe/send?access_token=${token}`

    const req = https.request(
      {
        hostname: 'api.weixin.qq.com',
        path,
        method: 'POST',
        headers: {
          'Content-Type': 'application/json',
          'Content-Length': Buffer.byteLength(body),
        },
      },
      (res) => {
        let chunks = ''
        res.on('data', (d) => (chunks += d))
        res.on('end', () => resolve(JSON.parse(chunks)))
      },
    )
    req.on('error', reject)
    req.write(body)
    req.end()
  })
}

module.exports = { sendSubscribe }
```

### 9. 触发时机一：支付成功回调中下发

订阅消息应挂在「服务真正发生」的节点。最自然的位置是 U23 支付回调幂等入账成功**之后**——只有确认钱到账、订单转为 PAID，才下发「支付成功通知」。

```javascript
// 在 payNotify 的 settleOrder 成功分支中调用
const { notifyPaySuccess } = require('../services/notify-pay')

// 订单已由 PENDING 条件更新为 PAID 后：
try {
  const r = await consumeQuotaAndSend(order.openid, process.env.TPL_PAY_RESULT, async () =>
    notifyPaySuccess(order),
  )
  await logSend(order.openid, process.env.TPL_PAY_RESULT, order.orderNo, r)
} catch (e) {
  // 通知失败不应影响支付主流程，记录日志后走降级
  console.error('支付成功通知下发失败', e)
}
```

关键设计：

1. **先记账成功，再发通知**——通知是支付成功的结果，不能反过来“先发通知后发现扣款失败”。
2. **通知失败不阻断交易**——支付主流程已成功，通知走异步重试/降级，不回滚订单。
3. 下发与扣额度要原子化（见第 10 节），避免额度没扣却发了，或扣了额度却没发出去。

### 10. 额度扣减与下发的原子化

一次性订阅「一条授权对应一条下发」。下发前要检查并扣减额度，下发失败时要判断是否退还额度（取决于失败原因），保证不超发、不浪费用户授权。

```javascript
// server/services/quota.js
const db = require('../db')

async function consumeQuotaAndSend(openid, templateId, sendFn) {
  // 1. 条件扣减：只有 quota>0 才减 1
  const res = await db
    .collection('user_subscriptions')
    .where({ openid, templateId, quota: db.gt(0) })
    .update({ data: { quota: db.inc(-1) } })

  if (res.stats.updated === 0) {
    const err = new Error('NO_QUOTA')
    err.errcode = 43101
    throw err
  }

  // 2. 真正下发
  try {
    const r = await sendFn()
    if (r.errcode !== 0) {
      // 非用户侧原因（如系统繁忙）可退还额度稍后重试；
      // 43101 未授权说明额度记录有误，不重复退
      if (r.errcode !== 43101 && isRefundable(r.errcode)) {
        await refundQuota(openid, templateId)
      }
    }
    return r
  } catch (e) {
    await refundQuota(openid, templateId) // 网络异常，额度返还
    throw e
  }
}

async function refundQuota(openid, templateId) {
  await db
    .collection('user_subscriptions')
    .where({ openid, templateId })
    .update({ data: { quota: db.inc(1) } })
}

function isRefundable(errcode) {
  // 系统繁忙类错误可重试；参数/模板错误不应重试
  return [-1, 45009, 40001 /* 视具体语义 */].includes(errcode)
}
```

额度心智模型：

- 用户点一次「允许」→ 服务端 +1；
- 成功发出一条 → 服务端 -1；
- 因平台/网络原因没发出去 → 额度返还，稍后重试；
- 因未授权/额度用尽发不出 → 不返还，等用户下次授权。

误区提醒：

- 不扣额度直接发——可能超发被微信拒绝。
- 任何失败都不返还额度——用户明明授权了却因系统抖动白白损失一条，体验差。

### 12. 下发失败：errcode、重试与降级

下发不总是成功，常见返回码（以官方错误码文档为准）：

| errcode | 含义 | 处理策略 |
|---|---|---|
| 0 | 成功 | 扣减额度，记成功日志 |
| 43101 | 用户未订阅/拒绝接收 | 不重试，等下次重新授权；可在相关页面引导订阅 |
| 47003 | 模板参数不准确（字段名/类型不符） | 修代码，不盲目重试 |
| 40037 | 模板 id 错误 | 检查环境与模板配置 |
| 40001 / 42001 | access_token 无效/过期 | 强制刷新 token 后重试一次 |
| 45009 | 接口调用频率超限 | 退避限流，稍后重试 |
| -1 | 系统繁忙 | 有限次退避重试，返还额度 |

统一错误处理与降级：

```javascript
// server/services/subscribe-retry.js
const sleep = (ms) => new Promise((r) => setTimeout(r, ms))

async function sendWithFallback(openid, templateId, payload, bizId) {
  for (let attempt = 0; attempt < 3; attempt += 1) {
    const r = await sendSubscribe(payload)

    await logSend(openid, templateId, bizId, r.errcode, r.errmsg)

    if (r.errcode === 0) return r

    if (r.errcode === 40001 || r.errcode === 42001) {
      await forceRefreshToken() // token 问题：强制刷新后重试
      continue
    }
    if (r.errcode === -1 || r.errcode === 45009) {
      await sleep(500 * 2 ** attempt) // 退避
      continue
    }
    // 43101/47003/40037 等不可重试错误：结束，等待重新授权/修配置
    return r
  }
}
```

降级体验：即便通知没发出去，订单、券本身依然有效，用户可在小程序「我的订单」里随时查看状态——**通知是增强，不是唯一凭证**。对关键支付结果，可在用户下次进入小程序时，根据订单状态在站内补一个明显提示条。

误区提醒：

- 对 43101 无限重试——用户没授权，永远失败，还浪费调用量。
- 把 47003 当系统繁忙重试——字段错了，重试 100 次还是错。

### 14. 完整闭环：支付成功 → 订阅 → 通知

把 U23 与 U24 串起来的完整时间线（注意授权要在下发之前完成）：

```text
1. 用户进入券详情，点「立即支付」
2. 前端先 requestSubscribeMessage([支付结果模板])
   ├─ accept → reportGrant 服务端额度 +1
   └─ reject/ban → 仍允许支付，只是不保证有通知
3. createOrder → fetchPayParams → wx.requestPayment 完成扣款
4. 微信回调服务端 → 验签解密幂等入账 PENDING→PAID
5. 入账成功后 consumeQuotaAndSend：
   ├─ 额度>0：扣 1 → subscribeMessage.send 支付成功通知
   └─ 无额度：跳过，用户在订单页仍可查看
6. 用户到店扫码核销 PAID→VERIFIED → 下发核销凭证（需核销模板授权）
7. 活动开始前 1 小时，定时任务批量下发活动提醒（幂等）
```

前端“支付前订阅”的整合示例：

```typescript
async function onBuy() {
  // 先就「支付结果通知」请求授权（不阻断支付）
  try {
    const grant = await requestSubscribe([TPL_PAY_RESULT])
    if (grant[TPL_PAY_RESULT] === 'accept') await reportGrant(TPL_PAY_RESULT)
  } catch {
    // 授权失败不影响下单支付
  }

  // 正常走支付
  const order = await createOrder(this.data.itemId)
  const params = await fetchPayParams(order.orderNo)
  await requestPayment(params)
  const status = await confirmOrderStatus(order.orderNo)
  wx.redirectTo({ url: `/pages/pay-result/index?orderNo=${order.orderNo}&status=${status}` })
}
```

这个顺序保证了「授权在支付前、通知在支付后」，用户完成支付时服务端已有可用额度，回调一入账即可成功触达。

### 15. 合规、风控与常见排错

合规红线：

1. 下发内容必须与用户订阅的服务场景一致，不做无关营销与诱导分享。
2. 不诱导、不欺骗用户授权；不通过技术手段绕过订阅限制。
3. 用户拒绝/关闭后应尊重选择，不反复骚扰；重视投诉率，过高可能被限制消息能力。
4. 通知中不泄露他人隐私，金额、订单信息准确。

排错清单：

| 现象 | 常见原因 | 排查方向 |
|---|---|---|
| 用户点了允许仍收不到 | 授权结果未上报/额度未入库 | 查 user_subscriptions 额度与上报日志 |
| 返回 43101 | 未授权或额度用尽 | 确认授权时机在下发前，额度是否已被其他消息用掉 |
| 返回 47003 | data 字段名/类型不符 | 对照公众平台模板关键词逐项核对 |
| 偶发 40001/42001 | token 过期/多实例互相刷新 | token 中控、提前刷新、共享缓存 |
| 重复收到提醒 | 定时任务无幂等标记 | 加 remindSent 条件与更新 |
| 正式版收不到、开发版能收到 | miniprogram_state 配错 | 生产用 formal，确认模板线上已发布 |
| iOS/安卓表现不一 | 通知入口/系统设置差异 | 以微信内服务通知记录与接口返回为准 |

排错时优先确认三件事：**服务端是否有该用户该模板的额度、接口实际返回的 errcode/errmsg、模板在当前环境是否存在且字段匹配**。

```text
支付回调 PENDING→PAID 成功
  └─ consumeQuotaAndSend（扣额度→下发→失败按错误码处理）
核销 PAID→VERIFIED
  └─ 下发核销凭证（幂等）
定时任务（每 10 分钟）
  └─ 扫描未来 1 小时内开始且 remindSent!=true 的报名 → 下发 → 置 remindSent=true
```

#### 步骤约束

1. 通知必须在对应业务状态确认成功后触发，通知失败不回滚业务、不阻断主流程。
2. 额度扣减与下发按第 10 节逻辑处理，可重试错误返还额度，43101 不重试。
3. 定时提醒必须有 remindSent 幂等标记，重跑/并发不重复下发。
4. 对下发失败要记录 SendLog，并在用户进入小程序时提供站内状态提示作为降级。

#### 提交物

- 支付/核销触发代码、eventRemind 定时云函数及触发器配置；
- 支付成功通知、核销凭证、活动开始提醒三类消息的触达录屏；
- 额度扣减日志、发送日志，以及一次“无额度用户被正确跳过”的证据。

#### 验收标准

- 三类通知均在正确节点准确触达、点击可跳转对应页面；
- 额度不超发、不浪费，重复执行不产生重复通知；
- 未授权/无额度用户被安全跳过且业务不受影响；
- 失败有日志、有降级，凭证在订单页始终可查。

## 阶段验收作业

本作业是商业化交易闭环的「最后一公里」证据点，重点证明**你能在支付成功、核销、活动开始等关键节点，合规、准确、幂等地把服务通知触达用户，并清楚授权额度与 access_token 的服务端边界**。

### 任务描述

在「逛吃指南」中交付完整订阅消息能力，并与 U23 支付链路打通：

1. 在公众平台配置至少两个订阅消息模板（如支付成功通知、核销凭证/活动提醒），记录模板 id 与字段。
2. 前端在支付前/结果页合理请求订阅授权，判读 accept/reject/ban 并上报；拒绝授权不影响正常支付。
3. 服务端实现用户授权额度表与上报接口，保证额度与授权一一对应、幂等记录。
4. 实现 access_token 中控（获取、缓存、提前刷新、并发合并）或使用云开发 openapi；调用 `subscribeMessage.send` 在支付回调入账成功后下发支付成功通知。
5. 实现扫码核销后下发凭证，以及定时触发器在活动开始前批量下发提醒（带幂等标记）。
6. 实现失败处理（43101 等）、SendLog 记录与站内降级；提供不超过 400 字的服务通知说明。

### 完成标准

- 用户授权后能在微信「服务通知」收到对应通知，点击跳回正确页面；
- 一次性订阅严格「一次授权一条下发」，额度扣减/返还逻辑正确、不超发；
- access_token 仅服务端获取与缓存，前端与仓库无 AppSecret、token；
- 通知在业务状态确认成功后触发，失败不影响支付/核销主流程；
- 定时提醒幂等，重跑/并发不重复下发；未授权用户被安全跳过；
- TypeScript 类型检查通过，关键节点有发送日志与可演示证据。

### 强制不通过条件

- AppSecret、access_token 出现在小程序前端、Storage、仓库或截图中，或由前端直接调用微信下发接口；
- 未经用户订阅授权就下发，或用订阅消息发送与服务无关的营销内容；
- 一次性订阅超发、额度记录错误，或重复执行（回调/定时任务）导致用户重复收到通知；
- 通知在业务未确认成功时提前下发（如未扣款先报支付成功），或通知失败错误回滚已成功的支付；
- 对 43101 等不可重试错误盲目无限重试，且无任何日志与降级，用户无法在订单页查到凭证；
- 模板字段与公众平台配置不一致导致下发失败且未修复，或类型检查不通过用 any 掩盖消息结构。
