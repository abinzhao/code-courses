# 23-微信支付与交易闭环

## 目标

完成本知识单元后，学员应能把「用户在小程序里点了一下支付，钱到底是怎么安全地从微信账户进到商户账上、订单又是怎么从待支付变成已支付的」完整讲清楚，并在「逛吃指南」中交付活动票/代金券从下单、支付、回调、核销到退款的完整交易闭环。

学员应能够：

1. 说清微信支付的几个核心身份及其关系：小程序（AppID）、商户号（mchid）、商户 API 密钥（APIv3 Key）、商户 API 证书（私钥/证书序列号）、微信支付平台证书，以及 openid 在 JSAPI 支付中的作用。
2. 完成商户号开通、与小程序 AppID 的关联绑定，理解「商户号与 AppID 必须绑定，且下单的 openid 必须来自该 AppID」这一硬约束。
3. 画出 JSAPI 支付全链路时序：前端创建本地订单 → 服务端创建业务订单并调用「统一下单」拿 `prepay_id` → 服务端按规则生成 `paySign` → 前端 `wx.requestPayment` 拉起收银台 → 微信支付回调通知服务端。
4. 在 Node 服务端/云函数中构造统一下单请求，正确设置金额（单位分）、`out_trade_no`、`notify_url`，并用商户私钥完成 APIv3 请求签名。
5. 严格按官方规则生成小程序调起支付所需的 `timeStamp`、`nonceStr`、`package`、`signType` 与 `paySign`，理解签名串拼接顺序与 SHA256-RSA 的关系。
6. 在前端用 TypeScript 封装「下单 → 发起支付 → 支付结果确认 → 跳转结果页」流程，牢记**前端只负责发起支付与展示结果，绝不持有证书密钥、绝不以前端回调作为到账依据**。
7. 实现支付结果通知回调：正确接收 APIv3 回调、验证微信支付平台证书签名、用 APIv3 密钥做 AEAD_AES_256_GCM 解密，并按要求应答。
8. 设计订单状态机（待支付 / 已支付 / 已核销 / 已退款 / 已取消），用状态机约束每一次合法流转，杜绝非法跳变。
9. 处理回调的幂等性：理解微信会重复推送通知，用「状态前置判断 + 唯一约束/事务」保证同一笔订单被通知多次也只入账一次。
10. 实现主动查单对账、超时关单、退款与退款回调，掌握云开发支付（`cloud.cloudPay.unifiedOrder`）的简化方式与边界。

本单元是阶段三商业化能力的核心，承接 U21 地图、U22 扫码核销，与 U24 订阅消息配合形成「支付成功 → 服务通知」的完整商业闭环。

## 技术栈

本单元以微信原生 + TypeScript 为前端，支付下单、签名、回调全部落在 Node 服务端或微信云开发云函数中。

| 工具或环境 | 用途 | 学习要求 |
|---|---|---|
| 微信商户号（mchid） | 商户收款主体 | 开通流程、与小程序 AppID 绑定 |
| 商户 API 证书（apiclient_key.pem / cert.pem） | 请求签名与身份认证 | 私钥仅存服务端，区分证书序列号 |
| APIv3 密钥 | 回调报文 AES 解密 | 32 位，仅存服务端环境变量 |
| 微信支付平台证书 | 验证回调通知签名 | 会下载/自动轮换平台证书 |
| 统一下单接口（JSAPI） | 获取 prepay_id | 请求构造、Authorization 签名头 |
| Node.js（https/axios + crypto） | 服务端下单与验签 | SHA256-RSA、AEAD_AES_256_GCM |
| wx.requestPayment | 前端拉起收银台 | 全参数、success/fail 语义 |
| 微信支付回调 notify_url | 接收支付/退款结果 | 必须 HTTPS、验签、幂等、正确应答 |
| 查询订单 / 申请退款 / 对账单接口 | 主动对账与退款 | 定时查单、退款状态机 |
| 云开发 wx-server-sdk `cloud.cloudPay` | 云开发支付简化下单/回调 | 理解其免签名特性与适用边界 |
| 云数据库 | 订单持久化 | 唯一索引、事务、状态字段 |

工程约定：

- 商户私钥、APIv3 密钥、证书文件、平台证书等**全部只存在于服务端/云函数环境变量或受控密钥管理中，绝不下发、不打包进小程序**。
- 订单金额一律以「分」为单位用整数表示并在服务端二次核算，前端展示的金额仅用于呈现。
- 是否支付成功，以**微信支付回调（验签后）或服务端主动查单**为准，前端支付成功回调只用于引导交互，不作为发货/发券依据。
- 所有接口域名、证书下载地址、字段长度限制以微信支付官方文档与商户平台实际规则为准。

## 详细的理论知识讲解和示例伪代码

### 1. 微信支付是什么：先认清五个身份

很多支付 Bug 都源于「身份没理清」。在小程序里做一笔 JSAPI 支付，涉及五个关键身份：

| 身份 | 标识 | 作用 | 存放位置 |
|---|---|---|---|
| 小程序 | AppID | 用户在哪个小程序里发起支付，决定 openid 归属 | 前端配置 + 服务端使用 |
| 商户号 | mchid | 钱最终进谁的收款账户 | 商户平台，服务端使用 |
| 商户 API 私钥 | apiclient_key.pem | 对「统一下单」等主动请求签名 | **仅服务端** |
| APIv3 密钥 | 32 位字符串 | 解密微信回调里的加密资源 | **仅服务端** |
| 微信支付平台证书 | 微信公钥证书 | 验证「回调真的来自微信支付」 | 服务端下载缓存 |

它们的关系可以这样理解：

- **AppID 和 mchid 必须绑定**。商户在商户平台把小程序 AppID 关联到商户号，否则统一下单会报错；一个商户号可以关联多个 AppID。
- **JSAPI 支付必须带 openid**，且这个 openid 必须是用户在「被绑定的那个小程序 AppID」下的 openid。openid 通过 `wx.login` 的 code 在服务端用 AppID + AppSecret 调 `code2Session` 换得（见 U16），**AppSecret 在服务端**。
- 商户私钥用来「证明这个请求确实是商户发的」；平台证书（公钥）用来「证明这个回调确实是微信发的」。这是一对方向相反的信任关系。

误区提醒：

- 「拿到商户号就能收款」——还要完成签约、绑定 AppID、配置 API 密钥与证书。
- 「openid 随便哪个小程序的都行」——必须是下单 AppID 对应的 openid，否则报 `invalid openid`。

### 2. 商户号开通与小程序关联

实操流程（具体入口以商户平台为准）：

1. 在微信支付商户平台（pay.weixin.qq.com）提交营业执照、经营信息、结算账户完成商户号申请，或使用已有商户号。
2. 在商户平台「产品中心」开通 **JSAPI 支付** 产品（小程序场景）。
3. 在「AppID 账号管理 / 商户号与 AppID 关联」中发起关联，填入小程序 AppID，并到小程序对应的公众平台确认，双方授权后绑定生效。
4. 在「账户中心 → API 安全」中：
   - 设置 **APIv3 密钥**（一个 32 位字符串，设置后平台不可见，只能重置）；
   - 申请并下载 **商户 API 证书**，得到 `apiclient_cert.pem`（证书）和 `apiclient_key.pem`（私钥），记录**证书序列号**；
   - 获取/下载 **微信支付平台证书**（推荐使用官方平台证书下载工具或 SDK 自动管理，平台证书会轮换）。
5. 配置支付回调地址 `notify_url`（必须是公网可访问的 HTTPS 地址）。

服务端环境变量示意（真实值绝不写进代码仓库，用 `.env` + 密钥管理且 `.env` 加入 `.gitignore`）：

```bash
# .env（示例结构，禁止提交真实值）
WX_APPID=wx1234567890abcdef
WX_APPSECRET=仅服务端可见_用于code2Session
WX_MCHID=1600000001
WX_MCH_SERIAL=商户证书序列号
WX_MCH_PRIVATE_KEY_PATH=/secrets/apiclient_key.pem
WX_APIV3_KEY=32位APIv3密钥
WX_NOTIFY_URL=https://api.guangchi.example.com/pay/notify
```

误区提醒：

- 把 `.env` 或 `.pem` 提交进 Git——等于把金库钥匙公开，历史记录里也删不干净，必须立即重置密钥。
- 混淆「商户证书序列号」和「平台证书序列号」：请求头用的是商户证书序列号。

### 3. 交易全链路总览

一次完整的 JSAPI 支付时序如下（注意钱的流转由微信完成，我们的服务端只在两边记账）：

```text
小程序前端                     我们的服务端                  微信支付
   │                              │                           │
   │ 1. 选择券/活动，点「立即支付」  │                           │
   │ ───────────────────────────▶ │                           │
   │                              │ 2. 校验商品/价格，创建订单     │
   │                              │    状态=待支付              │
   │                              │ 3. 调统一下单(带签名)        │
   │                              │ ────────────────────────▶ │
   │                              │ 4. 返回 prepay_id          │
   │                              │ ◀──────────────────────── │
   │ 5. 返回 timeStamp/nonceStr/   │                           │
   │    package/paySign           │                           │
   │ ◀─────────────────────────── │                           │
   │ 6. wx.requestPayment 拉起收银台│                           │
   │ ────────────────────────────────────────────────────────▶ │
   │ 7. 用户输密码/指纹，完成扣款     │                           │
   │ ◀──────────────────────────────────────────────────────── │
   │                              │ 8. 支付结果通知(POST notify) │
   │                              │ ◀──────────────────────── │
   │                              │ 9. 验签+解密+幂等更新订单    │
   │                              │    状态=已支付              │
   │                              │ 10. 应答 200/成功          │
   │                              │ ────────────────────────▶ │
   │ 11. 前端查单确认，展示结果页     │                           │
```

两个必须刻进脑子里的结论：

1. **第 7 步前端拿到的支付成功，不等于我们服务端已经记账**——弱网下回调可能还没到，因此前端要「主动查我们服务端的订单状态」，而不是直接写死成功。
2. **第 8～10 步是交易闭环的关键**——微信会在支付成功后调用 `notify_url`，我们必须验签、幂等处理并正确应答，否则微信会按策略重复通知。

### 4. 服务端创建订单与订单状态机

在调用微信之前，先在自己库里建一条业务订单。订单状态机建议包含五个核心状态：

```text
        超时未支付 / 主动取消
   ┌──────────────────────────┐
   ▼                           │
[待支付] ──支付回调(验签)──▶ [已支付] ──到店扫码核销──▶ [已核销]
   │                           │
   │ 支付前退款(一般不适用)       ├──申请退款──▶ [已退款]
   ▼                           │
[已取消]                        └──────────────▶ 终态
```

状态流转约束：

| 当前状态 | 允许流转到 | 触发事件 |
|---|---|---|
| 待支付 | 已支付 | 支付回调验签通过 / 查单确认支付成功 |
| 待支付 | 已取消 | 超时关单（且查单确认未支付）/ 用户主动取消 |
| 已支付 | 已核销 | 到店扫码核销（U22） |
| 已支付 | 已退款 | 商户/用户申请退款且退款回调成功 |
| 已核销 | 已退款 | 特殊情况下退款（需业务允许） |
| 已退款 / 已取消 / 已核销 | — | 终态，原则上不再流转 |

订单表结构（云数据库/关系库同理，字段名以项目为准）：

```typescript
// types/order.ts
export type OrderStatus =
  | 'PENDING' // 待支付
  | 'PAID' // 已支付
  | 'VERIFIED' // 已核销
  | 'REFUNDED' // 已退款
  | 'CANCELED' // 已取消

export interface Order {
  _id: string
  orderNo: string // 商户订单号 out_trade_no，需唯一
  openid: string // 支付人 openid
  appId: string
  mchId: string
  itemId: string // 活动/券 id
  itemName: string
  totalFee: number // 应付金额，单位：分（整数）
  status: OrderStatus
  prepayId?: string
  transactionId?: string // 微信支付订单号，支付成功后回填
  paidAt?: Date
  verifiedAt?: Date
  refundedAt?: Date
  createdAt: Date
  expireAt: Date // 订单超时时间
}
```

创建订单的 Node/云函数逻辑骨架：

```javascript
// cloud-functions/payCreate/index.js（Node 运行时）
const cloud = require('wx-server-sdk')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const db = cloud.database()

const ORDER_TTL_MS = 15 * 60 * 1000 // 订单 15 分钟有效

exports.main = async (event, context) => {
  const { OPENID } = cloud.getWXContext()
  const { itemId } = event

  // 1. 查商品，价格以服务端数据为准，绝不信任前端传来的金额
  const itemRes = await db.collection('items').doc(itemId).get()
  const item = itemRes.data
  if (!item || item.status !== 'on_sale') {
    return { code: 40001, message: '商品不存在或已下架' }
  }

  // 2. 生成唯一商户订单号
  const orderNo = genOrderNo()
  const now = Date.now()

  const order = {
    orderNo,
    openid: OPENID,
    itemId,
    itemName: item.name,
    totalFee: item.priceInFen, // 分
    status: 'PENDING',
    createdAt: new Date(now),
    expireAt: new Date(now + ORDER_TTL_MS),
  }
  await db.collection('orders').add({ data: order })

  return { code: 0, data: { orderNo, totalFee: order.totalFee } }
}

function genOrderNo() {
  return 'GC' + Date.now() + Math.floor(1000 + Math.random() * 9000)
}
```

要点：**价格永远来自服务端商品库**。前端哪怕传了金额，也只当作“它以为的价格”，下单时必须用服务端实时价格覆盖。

### 5. 调用统一下单接口（APIv3）

创建好待支付订单后，服务端调用微信支付「统一下单（JSAPI）」接口换取 `prepay_id`。APIv3 的请求需要构造 `Authorization` 头，其核心是用商户私钥对签名串做 SHA256-RSA。

签名串格式（严格按行拼接，`\n` 换行）：

```text
HTTP请求方法\n
请求URL（含查询串，不含域名）\n
请求时间戳\n
请求随机串\n
请求报文主体（GET 时为空串）\n
```

Node 示例（使用内置 crypto，实际项目也可用官方/社区 SDK 简化）：

```javascript
// server/utils/wxpay/sign.js
const crypto = require('crypto')
const fs = require('fs')

function loadPrivateKey() {
  // 从受控路径/环境变量读取，禁止硬编码进源码
  return fs.readFileSync(process.env.WX_MCH_PRIVATE_KEY_PATH)
}

/** SHA256-RSA 签名，返回 base64 */
function rsaSign(message) {
  const sign = crypto.createSign('RSA-SHA256')
  sign.update(Message)
  return sign.sign(loadPrivateKey(), 'base64')
}

/** 构造 APIv3 Authorization 头 */
function buildAuthHeader({ method, url, body, mchid, serial }) {
  const timestamp = Math.floor(Date.now() / 1000).toString()
  const nonce = crypto.randomBytes(16).toString('hex')
  const signStr = [method, url, timestamp, nonce, body, ''].join('\n')
  const signature = rsaSign(signStr)
  return [
    'WECHATPAY2-SHA256-RSA2048',
    `mchid="${mchid}"`,
    `nonce_str="${nonce}"`,
    `signature="${signature}"`,
    `timestamp="${timestamp}"`,
    `serial_no="${serial}"`,
  ].join(',')
}

module.exports = { buildAuthHeader }
```

发起统一下单：

```javascript
// server/services/pay.js
const https = require('https')
const { buildAuthHeader } = require('../utils/wxpay/sign')

const UNIFIED_ORDER_PATH = '/v3/pay/transactions/jsapi'

function unifiedOrder({ order, appid, mchid, serial, notifyUrl, openid }) {
  const bodyObj = {
    appid,
    mchid,
    description: order.itemName,
    out_trade_no: order.orderNo,
    time_expire: order.expireAt.toISOString(),
    notify_url: notifyUrl,
    amount: { total: order.totalFee, currency: 'CNY' },
    payer: { openid },
  }
  const body = JSON.stringify(bodyObj)

  const authorization = buildAuthHeader({
    method: 'POST',
    url: UNIFIED_ORDER_PATH,
    body,
    mchid,
    serial,
  })

  return new Promise((resolve, reject) => {
    const req = https.request(
      {
        hostname: 'api.mch.weixin.qq.com',
        path: UNIFIED_ORDER_PATH,
        method: 'POST',
        headers: {
          'Content-Type': 'application/json',
          'Content-Length': Buffer.byteLength(body),
          Authorization: authorization,
        },
      },
      (res) => {
        let chunks = ''
        res.on('data', (d) => (chunks += d))
        res.on('end', () => {
          const json = JSON.parse(chunks || '{}')
          if (json.prepay_id) resolve(json.prepay_id)
          else reject(new Error('统一下单失败: ' + chunks))
        })
      },
    )
    req.on('error', reject)
    req.write(body)
    req.end()
  })
}

module.exports = { unifiedOrder }
```

返回成功时微信响应形如 `{ "prepay_id": "wx202610091234..." }`。`prepay_id` 有效期有限，需要尽快返回给前端调起支付。

误区提醒：

- 金额用了「元」或用了小数——微信以「分」为单位，且必须整数。
- `notify_url` 用了 http 或带了不可被公网访问的地址——回调将失败。

### 6. 生成小程序调起支付参数 paySign

拿到 `prepay_id` 后，并不能直接给前端。小程序 `wx.requestPayment` 需要的支付参数里有一个 `paySign`，它是对**固定四个字段按固定顺序拼接**后再用商户私钥做 SHA256-RSA 的结果。

签名串（注意末尾也有换行，严格按官方规则）：

```text
appId\n
timeStamp\n
nonceStr\n
package\n
```

其中：

- `appId`：小程序 AppID；
- `timeStamp`：当前秒级时间戳（字符串）；
- `nonceStr`：随机串；
- `package`：格式为 `prepay_id=xxx`。

服务端生成示例：

```javascript
// server/services/pay.js（续）
const crypto = require('crypto')

function buildPayParams(appid, prepayId) {
  const timeStamp = Math.floor(Date.now() / 1000).toString()
  const nonceStr = crypto.randomBytes(16).toString('hex')
  const packageStr = `prepay_id=${prepayId}`

  const signStr = [appid, timeStamp, nonceStr, packageStr, ''].join('\n')
  const paySign = crypto
    .createSign('RSA-SHA256')
    .update(signStr)
    .sign(fs.readFileSync(process.env.WX_MCH_PRIVATE_KEY_PATH), 'base64')

  return {
    timeStamp,
    nonceStr,
    package: packageStr,
    signType: 'RSA',
    paySign,
  }
}
```

下单云函数/接口最终返回给前端的数据：

```json
{
  "timeStamp": "1728446400",
  "nonceStr": "a1b2c3d4e5f60718",
  "package": "prepay_id=wx202610091234",
  "signType": "RSA",
  "paySign": "base64签名串"
}
```

注意区分两个签名：第 5 节是「调微信服务端 API 的请求签名」，第 6 节是「给小程序调起支付用的 paySign」，二者**签名串内容不同、用途不同，不能混用**。

误区提醒：

- 把字段顺序按字母排序（JSAPI 调起签名不是字典序，是固定四行顺序）。
- 漏了最后一个换行，或把 `package` 直接写成 `prepay_id` 的值而没有 `prepay_id=` 前缀。

### 7. wx.requestPayment：前端只负责发起与展示

前端拿到支付参数后调用 `wx.requestPayment`。用 TypeScript 封装一个支付服务：

```typescript
// services/pay.ts
import { http } from '../utils/request'

interface CreateOrderResult {
  orderNo: string
  totalFee: number
}

interface WxPayParams {
  timeStamp: string
  nonceStr: string
  package: string
  signType: 'RSA' | 'MD5'
  paySign: string
}

/** 第一步：在服务端创建业务订单 */
export async function createOrder(itemId: string): Promise<CreateOrderResult> {
  return http.post<CreateOrderResult>('/v1/pay/create', { itemId })
}

/** 第二步：用订单号换取微信支付参数 */
export async function fetchPayParams(orderNo: string): Promise<WxPayParams> {
  return http.post<WxPayParams>('/v1/pay/params', { orderNo })
}

/** 第三步：拉起微信收银台 */
export function requestPayment(params: WxPayParams): Promise<void> {
  return new Promise((resolve, reject) => {
    wx.requestPayment({
      timeStamp: params.timeStamp,
      nonceStr: params.nonceStr,
      package: params.package,
      signType: params.signType,
      paySign: params.paySign,
      success: () => resolve(),
      fail: (err) => reject(err),
    })
  })
}
```

页面中的完整支付交互：

```typescript
// pages/item-detail/index.ts
import { createOrder, fetchPayParams, requestPayment } from '../../services/pay'
import { getOrderStatus } from '../../services/order'

Page({
  data: { itemId: '', paying: false },

  async onPay() {
    if (this.data.paying) return // 防重复点击
    this.setData({ paying: true })
    let orderNo = ''
    try {
      const order = await createOrder(this.data.itemId)
      orderNo = order.orderNo
      const params = await fetchPayParams(orderNo)
      await requestPayment(params)

      // 关键：不直接当成功，轮询/查询我们服务端的订单状态
      const finalStatus = await this.confirmOrderStatus(orderNo)
      if (finalStatus === 'PAID' || finalStatus === 'VERIFIED') {
        wx.redirectTo({ url: `/pages/pay-result/index?orderNo=${orderNo}` })
      } else {
        wx.showToast({ title: '支付确认中，请稍后查看订单', icon: 'none' })
      }
    } catch (err) {
      const msg = (err as WechatMiniprogram.Err).errMsg || ''
      if (msg.includes('cancel')) {
        wx.showToast({ title: '已取消支付', icon: 'none' })
      } else {
        wx.showToast({ title: '支付失败，请重试', icon: 'none' })
      }
    } finally {
      this.setData({ paying: false })
    }
  },

  async confirmOrderStatus(orderNo: string) {
    for (let i = 0; i < 5; i += 1) {
      const res = await getOrderStatus(orderNo)
      if (res.status === 'PAID' || res.status === 'VERIFIED') return res.status
      await new Promise((r) => setTimeout(r, 800))
    }
    return 'PENDING'
  },
})
```

前端三条铁律：

1. **不出现私钥、证书、APIv3 密钥、AppSecret**，支付参数全部来自服务端；
2. **不以前端 success 作为到账依据**，要回查服务端订单状态；
3. 用户取消支付走 `fail`（errMsg 含 cancel），应区别对待，不要提示“支付失败”。

### 8. 支付结果回调通知：机制与正确应答

微信支付成功（或失败）后，会向 `notify_url` 发送 POST 请求。APIv3 的回调结构大致为：

```json
{
  "id": "EV-202610091234",
  "create_time": "2026-10-09T12:35:00+08:00",
  "event_type": "TRANSACTION.SUCCESS",
  "resource_type": "encrypt-resource",
  "resource": {
    "algorithm": "AEAD_AES_256_GCM",
    "ciphertext": "加密后的支付结果(base64)",
    "nonce": "随机串",
    "associated_data": "transaction"
  }
}
```

处理回调的标准步骤：

1. 取 HTTP 头 `Wechatpay-Timestamp`、`Wechatpay-Nonce`、`Wechatpay-Signature`、`Wechatpay-Serial`；
2. 用 `Wechatpay-Serial` 找到对应的微信支付平台证书，对通知验签；
3. 验签通过后，用 APIv3 密钥对 `resource.ciphertext` 做 AEAD_AES_256_GCM 解密，拿到明文支付结果；
4. 校验金额、订单号，幂等更新订单状态；
5. **必须应答**：成功处理返回 HTTP 200 且 body 为 `{ "code": "SUCCESS", "message": "成功" }`；处理失败返回非 200 或 `code: FAIL`，微信会重试。

验签与解密的 Node 实现：

```javascript
// server/utils/wxpay/notify.js
const crypto = require('crypto')

/** 用微信支付平台证书(公钥)验证通知签名 */
function verifyNotify({ timestamp, nonce, body, signature, platformCertPem }) {
  const message = `${timestamp}\n${nonce}\n${body}\n`
  const verify = crypto.createVerify('RSA-SHA256')
  verify.update(message)
  return verify.verify(platformCertPem, signature, 'base64')
}

/** AEAD_AES_256_GCM 解密 resource.ciphertext */
function decryptResource(resource, apiv3Key) {
  const key = Buffer.from(apiv3Key, 'utf8')
  const nonce = Buffer.from(resource.nonce, 'utf8')
  const ciphertext = Buffer.from(resource.ciphertext, 'base64')
  const aad = resource.associated_data
    ? Buffer.from(resource.associated_data, 'utf8')
    : Buffer.alloc(0)

  // ciphertext 末尾 16 字节为 authTag
  const authTag = ciphertext.slice(ciphertext.length - 16)
  const data = ciphertext.slice(0, ciphertext.length - 16)

  const decipher = crypto.createDecipheriv('aes-256-gcm', key, nonce)
  decipher.setAuthTag(authTag)
  decipher.setAAD(aad)

  const decoded = Buffer.concat([decipher.update(data), decipher.final()])
  return JSON.parse(decoded.toString('utf8'))
}

module.exports = { verifyNotify, decryptResource }
```

误区提醒：

- 不验签直接信任回调 body——攻击者可以构造请求让你“被支付”。
- 业务处理抛错却仍返回 SUCCESS——微信以为你收到了，就不再重试，导致掉单。
- 解密成功就万事大吉——还要核对 `out_trade_no` 与 `amount.total` 是否与库里订单一致，防伪造/串单。

### 9. 回调里的业务处理：状态机 + 幂等

微信可能因网络抖动、超时等原因**重复推送同一笔支付通知**。幂等的核心：**同样的通知处理 1 次和处理 N 次，结果完全一样。**

幂等入账实现（以云数据库为例，关系库可用唯一约束 + 事务）：

```javascript
// cloud-functions/payNotify/index.js
const cloud = require('wx-server-sdk')
const { verifyNotify, decryptResource } = require('./wxpay')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const db = cloud.database()
const _ = db.command

exports.main = async (event) => {
  // 云函数中由 API 网关透传原始 headers 与 body；自建服务则从 req 取
  const { headers, rawBody } = event

  const ok = verifyNotify({
    timestamp: headers['wechatpay-timestamp'],
    nonce: headers['wechatpay-nonce'],
    body: rawBody,
    signature: headers['wechatpay-signature'],
    platformCertPem: getPlatformCert(headers['wechatpay-serial']),
  })
  if (!ok) {
    return { statusCode: 401, body: { code: 'FAIL', message: '验签失败' } }
  }

  const payload = JSON.parse(rawBody)
  if (payload.event_type !== 'TRANSACTION.SUCCESS') {
    return { statusCode: 200, body: { code: 'SUCCESS', message: '成功' } }
  }

  const result = decryptResource(payload.resource, process.env.WX_APIV3_KEY)
  const orderNo = result.out_trade_no
  const payAmount = result.amount.total
  const transactionId = result.transaction_id

  return await settleOrder(orderNo, payAmount, transactionId)
}

async function settleOrder(orderNo, payAmount, transactionId) {
  const q = await db
    .collection('orders')
    .where({ orderNo })
    .limit(1)
    .get()
  const order = q.data[0]

  if (!order) {
    // 单不存在：返回 FAIL 让微信重试，同时触发告警排查
    return { statusCode: 500, body: { code: 'FAIL', message: '订单不存在' } }
  }

  // 幂等关键 1：金额必须一致，防伪造/串单
  if (order.totalFee !== payAmount) {
    return { statusCode: 500, body: { code: 'FAIL', message: '金额不一致' } }
  }

  // 幂等关键 2：只有待支付订单才入账，已支付的重复通知直接当成功应答
  if (order.status !== 'PENDING') {
    return { statusCode: 200, body: { code: 'SUCCESS', message: '成功' } }
  }

  // 幂等关键 3：条件更新，只有 status=PENDING 才改，防并发双花
  const updateRes = await db
    .collection('orders')
    .where({ orderNo, status: 'PENDING' })
    .update({
      data: {
        status: 'PAID',
        transactionId,
        paidAt: new Date(),
      },
    })

  if (updateRes.stats.updated === 0) {
    // 已被另一个并发通知/查单处理过，视为成功
    return { statusCode: 200, body: { code: 'SUCCESS', message: '成功' } }
  }

  // 至此完成一次性入账：发券/记库存/触发订阅消息（U24）……
  return { statusCode: 200, body: { code: 'SUCCESS', message: '成功' } }
}
```

三层幂等防线要同时具备：**状态前置判断 + 条件更新（CAS）+ 唯一约束/事务**。只靠「先查再改」在高并发下仍可能双花，因为两次查询可能都看到 PENDING。

误区提醒：

- 回调里给用户加积分/发券却没有幂等，重复通知导致重复发券。
- 用 `out_trade_no` 之外的字段（如时间戳）做对账主键，无法保证唯一。

### 10. 主动查单与定时对账兜底

回调不是 100% 可靠（服务宕机、证书过期、网络分区都可能丢通知）。因此要**主动查单**作为兜底，这叫主动对账。

调用「查询订单」接口（同样需要请求签名），按 `out_trade_no` 查：

```javascript

    mchid,

  })
  // ... https.request GET api.mch.weixin.qq.com/path，带 Authorization
  // 返回 trade_state：SUCCESS / NOTPAY / CLOSED / REFUND / ...
}
```

定时对账任务（云函数定时触发器或 cron）：

```javascript
// cloud-functions/payReconcile/index.js
exports.main = async () => {
  const now = Date.now()

  // 1. 找出「创建超过 2 分钟仍待支付」的订单
  const pending = await db
    .collection('orders')
    .where({ status: 'PENDING' })
    .get()

  for (const order of pending.data) {
    const remote = await queryOrderByOrderNo(order.orderNo, process.env.WX_MCHID)

    if (remote.trade_state === 'SUCCESS') {
      // 微信侧已扣款但本地未入账：补入账（幂等）
      await settleOrder(
        order.orderNo,
        remote.amount.total,
        remote.transaction_id,
      )
    } else if (
      remote.trade_state === 'NOTPAY' &&
      new Date(order.expireAt).getTime() < now
    ) {
      // 超时且确认未支付：关单
      await closeOrderIfPending(order.orderNo)
    }
  }
}
```

配置定时触发器（云函数 `config.json`，表达式以平台文档为准）：

```json
{
  "triggers": [
    { "type": "timer", "config": "0 */2 * * * * *" }
  ]
}
```

要点：**回调是主通道，查单是兜底**，二者都必须走同一套幂等入账函数 `settileOrder`，保证殊途同归、绝不重复入账。

### 11. 超时关单与订单取消

待支付订单不能永久挂着。正确关单姿势是「**先确认微信侧确实没支付，再关单**」，避免把「钱已扣但回调晚到」的订单误关。

```javascript
async function closeOrderIfPending(orderNo) {
  const res = await db
    .collection('orders')
    .where({ orderNo, status: 'PENDING' })
    .update({ data: { status: 'CANCELED' } })
  return res.stats.updated === 1
}
```

也可以调用微信「关闭订单」接口让 `prepay_id` 失效，防止用户在本地关单后还能支付成功。用户在有效期内主动取消，应先查单确认 NOTPAY，再流转到 CANCELED。

状态机保护：**只有 PENDING 能到 CANCELED**；若查单返回 SUCCESS，则必须走支付成功逻辑而不是关单。

### 12. 退款与退款回调

已支付订单可发起退款。退款同样在服务端调用「申请退款」接口，需要商户请求签名，并指定退款单号（需唯一）：

```javascript
// server/services/refund.js
async function refund({ order, refundFee, reason }) {
  const path = '/v3/refund/domestic/refunds'
  const bodyObj = {
    out_trade_no: order.orderNo,
    out_refund_no: 'RFD' + Date.now() + Math.floor(Math.random() * 1000),
    reason,
    amount: {
      refund: refundFee, // 退款金额，分
      total: order.totalFee, // 原订单总额，分
      currency: 'CNY',
    },
  }
  // body 签名后 POST，回调地址可单独配置或复用 notify
}
```

退款结果通过退款回调（`REFUND.*` 事件）通知，处理方式与支付回调一致：**验签 → 解密 → 幂等更新**。退款单也应有状态（退款中 / 退款成功 / 退款异常），收到成功回调后再把订单从 PAID/VERIFIED 流转到 REFUNDED。

对账方面，微信支付提供**对账单/交易账单下载接口**，运营与财务应定期拉取账单，与本地订单逐笔比对，找出「微信有、本地无」「本地已支付、微信无」等差异单。

误区提醒：

- 申请退款后立刻把订单置为 REFUNDED——退款可能失败，应以退款回调为准。
- 退款金额超过原订单金额或重复退款——退款单号唯一 + 状态机约束。

### 13. 云开发支付：简化方式与边界

使用微信云开发时，`wx-server-sdk` 提供了 `cloud.cloudPay.unifiedOrder`，它帮你省去了构造商户请求签名、管理部分证书的工作（云环境已与商户号绑定）。

云函数中调用：

```javascript
// cloud-functions/payCreate/index.js（云开发支付版本）
const cloud = require('wx-server-sdk')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })

exports.main = async (event) => {
  const { OPENID } = cloud.getWXContext()
  const order = await loadPendingOrder(event.orderNo)

  const res = await cloud.cloudPay.unifiedOrder({
    body: order.itemName,
    outTradeNo: order.orderNo,
    spbillCreateIp: '127.0.0.1',
    subMchId: undefined, // 普通商户不需要；服务商模式才用
    totalFee: order.totalFee,
    envId: cloud.DYNAMIC_CURRENT_ENV,
    functionName: 'payNotify', // 支付结果回调直接触发指定云函数

```

前端拿到 `res.payment` 后直接透传给 `wx.requestPayment`：

```typescript
const payment = await createCloudOrder(itemId)
await new Promise<void>((resolve, reject) =>
  wx.requestPayment({ ...payment, success: resolve, fail: reject }),

```

云开发支付回调由平台直接触发指定云函数，`event` 中携带支付结果信息（字段以 SDK 文档为准），**业务上仍然要做幂等入账**。

边界要清楚：

1. 云开发支付把「商户请求签名」托管给平台，但「订单状态机、幂等、金额校验」依然是你自己的责任；
2. 需要复杂分账、多商户号、服务商模式或强财务定制时，自建服务端直接对接 APIv3 更灵活；
3. 无论哪种方式，**密钥治理红线不变**——前端永远没有私钥与 APIv3 密钥。

### 14. 安全红线汇总

支付安全没有“差不多”，以下为强制红线：

1. **商户私钥、APIv3 密钥、AppSecret、证书文件绝不放前端**，不写进小程序源码、Storage、globalData，也不放进可公开仓库；使用环境变量/密钥管理服务。
2. **回调必须验签 + 解密**，未验签的请求一律拒绝处理。
3. **金额以服务端商品数据为准并二次核对回调金额**，前端金额只用于展示。
4. **订单必须幂等入账**，状态机 + 条件更新 + 唯一约束缺一不可。
5. 校验 `out_trade_no`、`mchid`、`appid` 归属，防止串单；敏感操作（退款）加权限与审批。
6. `notify_url` 使用 HTTPS，防止中间人伪造；保护好接口不被重放攻击（结合 nonce/时间戳校验）。

### 15. 常见错误与排错清单

| 现象/报错 | 常见原因 | 排查方向 |
|---|---|---|
| 统一下单返回签名错误 | 签名串换行/路径/body 与实际不一致 | 确认参与签名的 body 与发送 body 完全一致 |
| invalid openid | openid 与 AppID 不匹配 | 用下单 AppID 的 code 重新 code2Session |
| 调起支付 paySign 报错 | 四字段顺序/换行/前缀错误 | 严格按 appId/timeStamp/nonceStr/package 拼接 |
| 回调一直收不到 | notify_url 非 HTTPS/不可公网访问 | 用公网工具自测该地址 |
| 微信重复通知 | 未在超时内正确应答 SUCCESS | 确认返回 200 且 code=SUCCESS |
| 用户扣款但订单仍待支付 | 回调丢失或验签失败 | 主动查单补单；检查平台证书是否轮换 |
| 金额对不上 | 单位用了元/小数 | 统一用「分」整数 |
| 平台证书过期 | 未做证书轮换 | 接入平台证书自动下载/轮换机制 |

排错时优先看三处日志：服务端下单日志、回调接收日志、微信商户平台的「接口/回调」相关记录与查单结果。

10. 场景题：「逛吃指南」上线后，财务反馈有两张异常订单：A 订单微信侧显示已扣款但本地仍是待支付；B 订单因回调被处理了两次，用户被重复发了两张券。请分别分析这两张单的根因，说明应如何修复存量数据，以及在下单、回调、对账三个环节如何改造以避免再次发生。

```javascript
// 服务端
```


- 200 字以内的下单链路说明。

#### 验收标准

- 能稳定换取 prepay_id 并生成合法支付参数；
- 订单号唯一、金额单位正确；

- 前端不出现任何签名/证书逻辑。

### 练习 2：支付回调验签、解密与幂等入账

#### 任务

实现支付结果通知接口：对微信回调做平台证书验签、AEAD_AES_256_GCM 解密，校验订单号与金额后，用状态机 + 条件更新幂等入账，并按要求正确应答。

参考伪代码：

```text
收到回调
 ├─ 验签失败 → 返回 401/FAIL
 ├─ event_type != TRANSACTION.SUCCESS → 直接应答 SUCCESS
 ├─ 解密 → 取 out_trade_no / amount.total / transaction_id
 ├─ 订单不存在或金额不符 → 返回 FAIL（触发重试/告警）
 ├─ 订单已非 PENDING → 直接应答 SUCCESS（幂等）
 └─ 条件更新 PENDING→PAID 成功 → 应答 SUCCESS
```

#### 步骤约束

1. 必须真实实现验签与解密逻辑，不允许写“假验签直接通过”。
2. 入账更新必须带 `status='PENDING'` 条件，保证并发重复通知只入账一次。
3. 处理失败不得应答 SUCCESS；成功必须返回 200 且 code=SUCCESS。
4. 入账成功后预留发券/触发通知的扩展点，但发券逻辑本身也要幂等。

#### 提交物

- 回调接口代码、验签/解密工具；
- 用同一通知连续推送两次，订单状态只变化一次、券只发一张的录屏或日志；
- 验签失败请求被拒绝的证据。

#### 验收标准

- 验签、解密、金额/订单号校验完整；
- 重复通知下订单与权益均幂等，无双花、无重复发券；
- 应答符合微信要求，不触发无意义重试；
- 回调处理全过程无密钥泄漏。

### 练习 3：主动查单对账 + 超时关单 + 退款

#### 任务

新增定时对账任务与退款能力：扫描超时待支付订单，主动查询微信侧状态，已支付的幂等补单、未支付的关单；对已支付订单发起退款并依据退款回调更新为已退款。

参考代码：

```javascript
const remote = await queryOrderByOrderNo(order.orderNo, mchid)
if (remote.trade_state === 'SUCCESS') await settleOrder(/*...*/)
else if (remote.trade_state === 'NOTPAY' && expired(order)) {
  await closeOrderIfPending(order.orderNo)
}
```

#### 步骤约束

1. 查单补单必须复用与回调相同的幂等入账函数，禁止另写一套会重复入账的逻辑。
2. 关单前必须确认微信侧为 NOTPAY，避免误关已扣款订单。
3. 退款单号唯一，订单仅在收到退款成功回调后才置为 REFUNDED。
4. 定时任务触发频率合理并记录每次对账处理明细。

#### 提交物

- 对账云函数/定时任务、退款服务与退款回调代码；
- 模拟“回调丢失 → 定时查单补单成功”和“超时未支付 → 自动关单”两条链路的日志；
- 一笔退款从申请到 REFUNDED 的完整记录。

#### 验收标准

- 掉单能被定时任务正确补齐且不重复入账；
- 超时订单在确认未支付后才关闭；
- 退款以回调为准、状态流转合法、退款单号唯一；
- 对账过程可追溯，无异常静默失败。
