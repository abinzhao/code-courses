# 18-列表搜索与状态工程

## 目标

完成本知识单元后，学员应能把「一个列表页在各种输入与网络条件下应该处于什么状态」讲清楚，并把「逛吃指南」的首页与探索页从“一次性拉取 + wxs 过滤”的云开发版本，改造为“分页加载、下拉刷新、搜索防抖、筛选排序联动、多状态可恢复”的工程化列表，而不是出现重复数据、页码错乱、旧结果覆盖新结果、弱网下永久转圈等典型问题。

学员应能够：

1. 说清列表页的输入（关键词、筛选、排序、页码）与状态（首次加载、刷新、加载更多、成功、空、错误），用状态机视角而不是“多个布尔变量互相打架”的方式设计页面。
2. 掌握页码分页模型：`page` / `pageSize` / `total` / `hasMore` 的计算与约定，知道首页从 1 还是从 0 开始必须与后端统一。
3. 理解游标分页：`cursor` / `nextCursor` 的语义、适用场景（高频写入、深分页），以及它不能跳页的限制，能在两种模型间做选型。
4. 使用页面生命周期 `onReachBottom`（配合 `onReachBottomDistance`）实现加载更多，并用 loading/hasMore 标志防止重复触发；知道 scroll-view 的 `bindscrolltolower` 备选方案。
5. 使用 `onPullDownRefresh` + `wx.stopPullDownRefresh` 实现下拉刷新，正确重置分页与状态，错误时也要收起动效。
6. 实现列表数据的追加、按 id 去重与合并；下拉刷新用新列表替换，加载更多做拼接，杜绝重复卡片。
7. 实现搜索防抖（延迟触发、立即确认、清空处理），并理解防抖为什么要与请求取消/请求序号配合才能真正防止竞态。
8. 实现关键词、筛选条件、排序方式的联动：任一条件变化都统一“取消旧请求 → 重置分页 → 回到顶部 → 重新请求”。
9. 设计加载/空/错误三态与骨架屏：区分首次加载与加载更多的错误展示，空态区分“无数据”与“筛选无结果”，骨架屏只在首屏使用并避免布局跳动。
10. 掌握长列表性能治理：稳定 `wx:key`、减少 `setData` 频率与数据量、路径更新受影响项、recycle-view 虚拟列表概念与选型，并能在弱网与竞态下保证只接受最新一次响应。

本单元直接建立在 U17 的接口层之上，是 W12 商业化里程碑之前最重要的“数据—状态—渲染”工程训练。

## 技术栈

本单元基于微信原生页面能力、U17 封装的 request 模块与 TypeScript 实现。

| 工具或环境 | 用途 | 学习要求 |
|---|---|---|
| Page.onReachBottom | 页面触底加载更多 | 配合 onReachBottomDistance，防重复触发 |
| Page.onPullDownRefresh | 页面下拉刷新 | 配 enablePullDownRefresh，必须 stopPullDownRefresh |
| scroll-view bindscrolltolower / refresher-enabled | 页内滚动列表的触底与刷新 | 页面非整页滚动时使用 |
| Page.data + setData | 列表与视图状态驱动 | 理解跨线程成本，做路径更新与减量 |
| wx:key | 列表节点身份 | 必须用稳定唯一 id，不用 index |
| 防抖函数（自实现） | 搜索输入延迟触发 | 会处理 confirm、清空与 timer 释放 |
| RequestTask.abort / 请求序号 | 取消旧请求、防竞态 | 只接受最新一次响应 |
| U17 的 http 模块与 PageResult&lt;T&gt; | 分页接口通道 | 复用 listShops 等服务，不裸写 wx.request |
| 骨架屏（WXML + WXSS shimmer） | 首屏加载占位 | 卡片尺寸稳定，避免布局跳动 |
| recycle-view（概念/选型） | 超长列表虚拟渲染 | 知道原理、成本与适用阈值 |
| wx.pageScrollTo | 搜索/筛选后回顶 | scrollTop 归零 |
| wx.onNetworkStatusChange / getNetworkType | 弱网感知与恢复 | 会在网络恢复时重试 |

工程约定：

- 列表页所有数据来自 U17 的 `services`，页面只维护“查询条件 + 分页游标 + 视图状态”。
- 任何改变结果集合的操作（搜索、筛选、排序、刷新）都必须经过统一的重置入口，禁止各处自行改页码。
- 视图状态对渲染层可见的放 `data`；仅逻辑层使用的标志（如当前请求序号）直接挂页面实例，减少跨线程数据。

## 详细的理论知识讲解和示例伪代码

### 1. 列表页工程全景：把页面看成状态机

一个“简单”的列表页，实际同时承受三类输入：

```text
用户输入：
  关键词 keyword（频繁变化）
  筛选 district / category（离散变化）
  排序 sort（离散变化）
  翻页动作（触底 / 下拉）

系统输入：
  网络可用/不可用
  请求成功/失败/超时
  页面显示/隐藏/卸载

输出状态：
  firstLoading  首次加载
  refreshing    下拉刷新
  loadingMore   加载更多
  success       成功（可能有数据，也可能空）
  error         错误（首次错误 / 加载更多错误）
```

反面教材是用一堆互相关联的布尔值：

```typescript
// 混乱写法：loading、isEnd、isError 可能同时为 true，界面无法预测
data: { loading: false, isEnd: false, isError: false, list: [] }
```

推荐用一个显式的视图状态字段：

```typescript
type ViewState =
  | 'first_loading'
  | 'success'
  | 'empty'
  | 'first_error'
  | 'refreshing'
  | 'loading_more'
  | 'load_more_error'

interface ListData<T> {
  viewState: ViewState
  list: T[]
  hasMore: boolean
}
```

状态之间的迁移是可枚举的：进入页面 → `first_loading`；成功且有数据 → `success`；成功但无数据 → `empty`；失败 → `first_error`（可重试）；触底且 hasMore → `loading_more` → 成功则合并、失败则 `load_more_error`（已有数据保留）。

关系要点：

- **刷新与加载更多不改变“已有列表是否存在”的底色**：刷新时旧列表可以继续显示；加载更多失败时已有数据也不能丢。
- 关键词/筛选/排序变化属于“换一个问题”，必须回退到 `first_loading` 语义，而不是在旧结果后追加。

误区提醒：

- 多个布尔标志缺乏约束，组合出不可能的状态（既 loading 又 error），WXML 里只能堆条件补丁。
- 把“空”和“错误”都显示成一张空白页，用户无法区分是没数据还是出故障。

### 2. 页码分页模型：page、pageSize、total 与 hasMore

最常见的分页协议：客户端传“要第几页、每页多少条”，服务端返回“当前页数据、总数”。

```typescript
// 请求
interface PageQuery {
  page: number // 页码，约定从 1 开始
  pageSize: number // 每页条数，前端固定 20
}

// 响应（与 U17 的 PageResult 对应）
interface PageResult<T> {
  list: T[]
  page: number
  pageSize: number
  total: number
  hasMore: boolean
}
```

`hasMore` 的计算口径要统一，二选一，不要前后端各算各的：

```typescript
// 口径 A：服务端直接给 hasMore（推荐，客户端少猜）
const hasMore = page * pageSize < total

// 口径 B：客户端依据已加载条数判断
const hasMore = loadedCount < total
```

首屏查询示例：

```typescript
const res = await listShops({ page: 1, pageSize: 20 })
// res.total = 56 → 共 3 页（20 + 20 + 16）
// res.hasMore = true
```

工程注意：

1. **页码起点必须与后端书面约定**：有的后端从 0 开始（offset 思维），混用时第一页和第二页会重复或丢数据。
2. `pageSize` 由前端固定、不要让用户随意传大值，防止被拉全表。
3. `total` 可能在翻页期间变化（新笔记发布），因此 `hasMore` 以“服务端每次返回”为准，不要客户端缓存 total 后一直自己算。
4. 最后一页可能返回少于 pageSize 的条数，这是正常现象，不能据此判错误。

误区提醒：

- 用“返回条数等于 pageSize”来判断还有更多——最后一页恰好满页时会多请求一次空页。
- 前端写死 total，数据变化后 hasMore 永远算错。

### 3. 游标分页：cursor、nextCursor 与选型

页码分页有两个固有问题：一是**深分页性能差**（数据库要跳过前 N 条），二是**结果漂移**（用户翻第 2 页前，第 1 页之前插入了新数据，第 2 页就会漏掉/重复一条）。游标分页为此而生：

```typescript
// 请求：带上一页返回的游标
interface CursorQuery {
  cursor?: string // 首次不传
  pageSize: number
}

// 响应
interface CursorResult<T> {
  list: T[]
  nextCursor: string | null // null 表示没有更多
}
```

游标通常由服务端生成，内容可能是“最后一条记录的排序键 + id”的编码（如 Base64），对客户端是**不透明字符串**：不要解析、不要构造、不要比较。

```typescript
// 第一次
let r = await listFeed({ pageSize: 20 })
// r.nextCursor = 'eyJ0c1wiOjE3MDAwMDAsXCJpZFwiOlwic2hvcF8yMFwifQ=='

// 第二次：原样回传
r = await listFeed({ cursor: r.nextCursor, pageSize: 20 })
// 直到 nextCursor === null
```

两种模型选型：

| 维度 | 页码分页 | 游标分页 |
|---|---|---|
| 能否跳页（第 N 页） | 能 | 不能，只能顺序前进 |
| 插入新数据时 | 易漏/重复 | 稳定 |
| 深分页性能 | 差 | 好 |
| 实现/调试成本 | 低 | 中 |
| 典型场景 | 后台管理、强筛选列表 | 时间流 feed、无限滚动 |

「逛吃指南」首页推荐流适合游标；带强筛选、需要展示“共多少条”的探索页更适合页码分页（可用 `hasMore` + 不展示 total 的折中）。

误区提醒：

- 把游标当数字自增，或跨筛选条件复用旧游标——条件一变游标立即失效，必须重置。
- 游标分页还想保留“跳到第 5 页”的产品交互，二者天然冲突。

### 4. onReachBottom：触底加载更多

整页滚动时，页面触底会触发 `onReachBottom`。先在页面 json 中配置触底距离：

```json
{
  "onReachBottomDistance": 100,
  "enablePullDownRefresh": true,
  "backgroundTextStyle": "dark"
}
```

页面逻辑：

```typescript
// pages/index/index.ts
import { listShops, type ShopCard, type ShopQuery } from '../../services/shop'

Page({
  data: {
    viewState: 'first_loading' as ViewState,
    list: [] as ShopCard[],
    hasMore: true,
  },

  // 非渲染数据直接挂实例（不会经 setData 跨线程）
  page: 1,
  loading: false,

  async onReachBottom() {
    // 三道闸门：正在请求 / 没有更多 / 当前是首屏错误态
    if (this.loading || !this.data.hasMore) return
    if (this.data.viewState === 'first_error') return

    this.loading = true
    this.setData({ viewState: 'loading_more' })

    try {
      const nextPage = this.page + 1
      const query: ShopQuery = {
        ...this.buildQuery(),
        page: nextPage,
        pageSize: 20,
      }
      const res = await listShops(query)
      this.page = nextPage

      const merged = mergeList(this.data.list, res.list)
      this.setData({
        list: merged,
        hasMore: res.hasMore,
        viewState: 'success',
      })
    } catch (err) {
      // 加载更多失败：保留已有数据，只在列表底部提示
      this.setData({ viewState: 'load_more_error' })
    } finally {
      this.loading = false
    }
  },

  buildQuery(): Omit<ShopQuery, 'page' | 'pageSize'> {
    return { keyword: this.keyword, district: this.district, sort: this.sort }
  },
})
```

底部 footer 随状态变化（WXML 片段）：

```xml
<view class="list-footer">
  <block wx:if="{{viewState === 'loading_more'}}">
    <view class="footer-loading">正在加载…</view>
  </block>
  <block wx:elif="{{viewState === 'load_more_error'}}">
    <view class="footer-retry" bindtap="onRetryLoadMore">加载失败，点击重试</view>
  </block>
  <block wx:elif="{{!hasMore && list.length > 0}}">
    <view class="footer-end">没有更多了</view>
  </block>
</view>
```

如果列表位于页内 `scroll-view` 中（页面本身不整页滚动），用 `scroll-view` 的 `bindscrolltolower` 事件与 `lower-threshold` 属性，逻辑完全相同；两套机制不要混用。

误区提醒：

- 不加 loading 闸门，触底事件在弱网下连续触发，同一页被请求多次，出现重复卡片。
- 加载更多失败就把整页切到错误态，丢掉已加载的几十条数据。

### 5. onPullDownRefresh：下拉刷新

下拉刷新用于“以当前条件重新从第一页拉取”。页面 json 开启 `enablePullDownRefresh` 后实现：

```typescript
async onPullDownRefresh() {
  try {
    await this.resetAndLoad({ showFirstLoading: false })
  } finally {
    // 无论成功失败都必须收起动效，否则下拉动画卡住
    wx.stopPullDownRefresh()
  }
},
```

刷新时的体验取舍：

1. 旧列表继续显示，请求成功后整体替换；失败则保留旧数据并 toast，不清空列表；
2. 若产品要求“刷新表示有新内容”，可在成功后用轻提示告知（如“已更新 3 条”），数量来自服务端或时间戳对比；
3. 刷新与加载更多互斥：刷新进行中忽略触底，刷新完成后 `hasMore` 与页码以新响应为准。

`wx.stopPullDownRefresh` 必须放在 finally——弱网超时若不收起动效，用户会看到下拉条一直挂着，且后续手势异常。

误区提醒：

- 只在 success 里 stop，失败时动效不收回。
- 刷新时先 `setData({ list: [] })` 造成列表闪空；应保留旧数据直到新数据到达。

### 6. 列表合并与去重

重复卡片有三个来源：翻页期间有新数据插入、触底事件重复触发、游标/页码用错。无论哪种，最后一道防线是**按稳定 id 合并**：

```typescript
// utils/list.ts

/** 追加合并：保留原有顺序，新数据去重后拼到尾部 */
export function mergeList<T extends { id: string }>(
  prev: T[],
  incoming: T[],
): T[] {
  const seen = new Set(prev.map((item) => item.id))
  const appended: T[] = []
  for (const item of incoming) {
    if (!seen.has(item.id)) {
      seen.add(item.id)
      appended.push(item)
    }
  }
  return [...prev, ...appended]
}

/** 刷新替换：新数据整体替换，并顺手去掉新数据内部的重复项 */
export function replaceList<T extends { id: string }>(incoming: T[]): T[] {
  const seen = new Set<string>()
  const result: T[] = []
  for (const item of incoming) {
    if (!seen.has(item.id)) {
      seen.add(item.id)
      result.push(item)
    }
  }
  return result
}
```

合并后还要校正分页认知：

- 若服务端返回空页但 `hasMore=true`（极端时序），页码不应前进，下一次触底再试同一页；
- 若去重后一条都没加上但 hasMore 仍为 true，可允许自动再拉下一页（设上限，一般 1～2 次），避免底部一直“没有更多”之外的怪状态；
- 收藏态等局部变化用路径 setData 更新（见第 12 节），绝不为改一个心形重新请求整页。

误区提醒：

- 用 `indexOf` / `includes` 按对象引用去重，接口返回的新对象引用必然不同。
- 去重 key 用数组 index——index 随顺序变化，不表示身份。

### 7. 搜索防抖：让输入“安静下来”再发请求

每敲一个字就发一次请求，既浪费请求名额（U17 的并发上限），又必然制造竞态。防抖的含义：**事件被触发后等待一小段时间，若期间又被触发则重新计时，直到停顿才真正执行。**

```typescript
// utils/debounce.ts

export function debounce<A extends unknown[]>(
  fn: (...args: A) => void,
  wait: number,
): ((...args: A) => void) & { cancel: () => void } {
  let timer: ReturnType<typeof setTimeout> | null = null

  const debounced = (...args: A) => {
    if (timer) clearTimeout(timer)
    timer = setTimeout(() => {
      timer = null
      fn(...args)
    }, wait)
  }

  debounced.cancel = () => {
    if (timer) clearTimeout(timer)
    timer = null
  }

  return debounced
}
```

页面接入搜索：

```typescript
let searchRunner: ((keyword: string) => void) & { cancel: () => void }

Page({
  data: { keyword: '', viewState: 'first_loading', list: [], hasMore: true },

  onLoad() {
    searchRunner = debounce((keyword: string) => {
      this.keyword = keyword
      this.resetAndLoad()
    }, 350)
  },

  onKeywordInput(e: WechatMiniprogram.Input) {
    const keyword = e.detail.value
    this.setData({ keyword }) // 输入框内容必须立即响应，不能防抖
    searchRunner(keyword.trim())
  },

  // 键盘“搜索”键：不再等待，立即执行
  onKeywordConfirm(e: WechatMiniprogram.InputConfirm) {
    searchRunner.cancel()
    this.keyword = e.detail.value.trim()
    this.resetAndLoad()
  },

  onClearKeyword() {
    searchRunner.cancel()
    this.setData({ keyword: '' })
    this.keyword = ''
    this.resetAndLoad()
  },

  onUnload() {
    searchRunner.cancel()
  },
})
```

关键区分：**输入框显示要即时，发请求要防抖。** 对 `setData({ keyword })` 防抖会让输入体验卡顿，是常见错误。空关键词要视为“取消搜索、恢复默认列表”，而不是发一个空串条件。防抖时间一般 300～500ms；过短失去意义，过长让人觉得反应迟钝。

误区提醒：

- 只做防抖、不处理竞态：停顿前最后一次请求与更早的请求仍可能“后发先至”，必须配合第 14 节的请求序号/abort。
- 不在 `onUnload` 取消 timer，页面销毁后回调仍执行 setData。

### 8. 关键词 × 筛选 × 排序：统一联动入口

关键词、行政区、菜系、人均区间、排序方式，本质都是“查询条件”。它们任意一个变化，动作完全相同，应收敛到唯一入口 `resetAndLoad`：

```typescript
Page({
  keyword: '',
  district: '',
  category: '',
  sort: 'default',
  page: 1,
  requestSeq: 0, // 请求序号：只接受最新一次响应
  loading: false,

  /** 条件变化的统一入口：换问题 = 重置一切 */
  async resetAndLoad() {
    // 1. 废弃在飞的旧请求（搜索/筛选快速切换时关键）
    this.currentTask?.abort()
    const seq = ++this.requestSeq

    // 2. 重置分页
    this.page = 1
    this.loading = true

    // 3. 进入首屏加载态（若已有数据且希望“换条件不闪空”，可保留旧列表，
    //    由产品决定；探索页通常切到 first_loading + 骨架屏）
    this.setData({ viewState: 'first_loading', hasMore: true })

    // 4. 回顶（见第 11 节）
    wx.pageScrollTo({ scrollTop: 0, duration: 0 })

    try {
      const { task, promise } = createShopsRequest({
        keyword: this.keyword,
        district: this.district,
        category: this.category,
        sort: this.sort,
        page: 1,
        pageSize: 20,
      })
      this.currentTask = task
      const res = await promise

      // 5. 序号校验：过期响应直接丢弃
      if (seq !== this.requestSeq) return

      const list = replaceList(res.list)
      this.setData({
        list,
        hasMore: res.hasMore,
        viewState: list.length === 0 ? 'empty' : 'success',
      })
    } catch (err) {
      if (seq !== this.requestSeq) return
      if (isAbortError(err)) return // 主动取消，静默
      this.setData({ viewState: 'first_error' })
    } finally {
      if (seq === this.requestSeq) this.loading = false
    }
  },

  onFilterTap(e: WechatMiniprogram.Tap) {
    const { type, value } = e.currentTarget.dataset as {
      type: 'district' | 'category' | 'sort'
      value: string
    }
    this[type] = value
    // 同步筛选按钮高亮（只更新 UI 状态字段）
    this.setData({ [`filterState.${type}`]: value })
    this.resetAndLoad()
  },
})
```

筛选条 UI 的选中态要与真实条件双向一致：点击高亮 → 发请求；点击已选中项可以是“取消筛选”。查询参数序列化（空值不传）应放在 services 层统一处理，避免 URL 上出现 `district=&`。

误区提醒：

- 筛选变化后只改条件不重置页码，带着“第 3 页”请求新条件，结果为空或错乱。
- 每个筛选按钮各自写一套请求逻辑，条件组合时很快失控。

### 9. 加载 / 空 / 错误三态

三态是用户能否“自助恢复”的关键。完整 WXML 结构：

```xml
<!-- pages/explore/explore.wxml -->
<view class="page">
  <!-- 搜索栏与筛选条始终常驻，保证任何状态都能换条件 -->
  <search-bar value="{{keyword}}" bind:input="onKeywordInput" bind:confirm="onKeywordConfirm" />
  <filter-bar state="{{filterState}}" bind:change="onFilterTap" />

  <!-- 首次加载：骨架屏 -->
  <block wx:if="{{viewState === 'first_loading'}}">
    <shop-skeleton wx:for="{{[1,2,3,4]}}" wx:key="*this" />
  </block>

  <!-- 首次错误：整页错误 + 重试 -->
  <block wx:elif="{{viewState === 'first_error'}}">
    <view class="state-block">
      <image class="state-img" src="/images/state-error.png" />
      <view class="state-title">加载失败</view>
      <view class="state-desc">网络好像开小差了</view>
      <button class="state-btn" bindtap="resetAndLoad">重新加载</button>
    </view>
  </block>

  <!-- 空态：区分无筛选 / 有筛选 -->
  <block wx:elif="{{viewState === 'empty'}}">
    <view class="state-block">
      <image class="state-img" src="/images/state-empty.png" />
      <view class="state-title">{{hasActiveFilter ? '没有符合条件的店铺' : '还没有店铺收录'}}</view>
      <view class="state-desc">{{hasActiveFilter ? '换个关键词或筛选条件试试' : '换个区域逛逛吧'}}</view>
      <button wx:if="{{hasActiveFilter}}" class="state-btn" bindtap="onResetFilter">清空筛选条件</button>
    </view>
  </block>

  <!-- 成功：列表 + 底部 footer -->
  <block wx:else>
    <shop-card
      wx:for="{{list}}"
      wx:key="id"
      card="{{item}}"
      data-id="{{item.id}}"
      bind:tap="onShopTap"
    />
    <view class="list-footer">
      <view wx:if="{{viewState === 'loading_more'}}" class="footer-loading">正在加载…</view>
      <view wx:elif="{{viewState === 'load_more_error'}}" class="footer-retry" bindtap="onRetryLoadMore">
        加载失败，点击重试
      </view>
      <view wx:elif="{{!hasMore}}" class="footer-end">没有更多了</view>
    </view>
  </block>
</view>
```

要点：

1. **搜索栏与筛选条任何状态下都保留**，错误/空态时用户仍能直接换条件自救；
2. 空态文案按“是否存在生效条件”分叉，筛选无结果时提供“一键清空筛选”；
3. 错误分两级：首次错误占整页（列表不存在），加载更多错误只占 footer（列表保留）；
4. 重试按钮直接调用对应入口：整页错误 → `resetAndLoad`，底部错误 → `loadMore`。

误区提醒：

- 错误态把搜索栏一起隐藏，用户只能退出页面。
- 空态就一张灰图一句话，不说明原因也不给下一步动作。

### 10. 骨架屏：原理、实现与布局稳定

### 11. 回顶与滚动位置保持

两个相反的诉求要分清：

**场景 A：换了问题（搜索/筛选/排序）→ 应回到顶部。**

```typescript
// resetAndLoad 内
wx.pageScrollTo({ scrollTop: 0, duration: 0 })
```

`duration: 0` 瞬时回顶，避免用户看着旧列表滚一段再变新内容。scroll-view 场景则设置 `scroll-top="{{scrollTop}}"`（配合下次先置非零再置零的写法触发变化）。

**场景 B：从详情页返回列表 → 必须保持原位置。**

这要求列表页在详情期间不被销毁（`navigateTo` 打开详情，页面栈保留，天然保持）；同时返回时**不要在 onShow 无脑重置列表**。正确做法：

1. 列表数据不重载，只通过 U12 的事件总线接收收藏态等局部变化，做路径 setData；
2. 确需刷新时用“差异合并”而不是 `resetAndLoad`；
3. 如果因内存紧张页面被回收（再次进入走 onLoad），接受重建并用合理首屏策略，这是极端情况。

误区提醒：

- 在 `onShow` 里 `resetAndLoad`，每次从详情返回都回到第一页、丢掉浏览位置，是最影响体验的错误之一。
- 换筛选后不回顶，新列表从第 3 屏的位置开始显示，用户以为没变化。

### 12. 长列表性能（一）：wx:key 与 setData 治理

列表越长，渲染层节点越多、每次 `setData` 跨线程传输与 diff 成本越高。治理手段：

**（1）wx:key 必须稳定唯一。**

```xml
<!-- 正确：业务 id 稳定，顺序变化时节点可复用 -->
<shop-card wx:for="{{list}}" wx:key="id" />

<!-- 错误：index 随数据变化，插入/刷新后节点身份全乱，状态（如图片懒加载）错乱 -->
<shop-card wx:for="{{list}}" wx:key="index" />
```

框架借助 key 判断节点增删与复用；key 不稳定会导致整列表被重建，动画、内部状态丢失。

**（2）减少 setData 的数据量与频率。**

```typescript
// 反例：只改一个收藏态，却把整列表重新跨线程传输
this.setData({ list: this.data.list.map((s) => (s.id === id ? { ...s, liked } : s)) })

// 正例：路径更新，传输量只有一个布尔值
const i = this.data.list.findIndex((s) => s.id === id)
if (i >= 0) this.setData({ [`list[${i}].liked`]: true })
```

**（3）非渲染数据不进 data。**

页码、loading 标志、请求序号、timer 直接挂页面实例（`this.page`），它们不需要显示，放 data 只会增加跨线程数据。组件中可用**纯数据字段**（`options: { pureDataPattern }`）声明只在逻辑层存在的字段。

**（4）卡片本身要轻。**

图片懒加载（`lazy-load`）、固定尺寸减少重排、卡片内不写复杂表达式与过多 WXS；合并连续状态变化为一次 setData（如数据到齐后一次性 setData，而不是循环里逐次调用）。

**（5）衡量而非凭感觉。**

用开发者工具的 setData 统计、Trace 面板与真机 Performance 观察：单次 setData 传输大小、回调耗时、列表总节点数与帧率。

误区提醒：

- 认为“setData 很快”——它跨线程序列化，列表几百条时单次全量 setData 可明显掉帧。
- 一个事件回调里连续多次 setData，应合并成一次。

### 13. 长列表性能（二）：recycle-view 与虚拟列表概念

分页把“总量无限”变成“每次 20 条”，但用户连续触底滚到几百条后，DOM 中仍累积了几百个卡片节点，内存与渲染压力上升。**虚拟列表**的思路是：只渲染可视区附近的少量节点，滚动时回收复用、替换数据，节点总数保持恒定。

```text
可视区 + 缓冲区内：渲染真实节点（约 10～15 个卡片）
更远的数据：只有数据，没有节点
滚动时：离开的节点被回收，进入的节点复用同一批组件、换绑数据
```

微信官方提供过 `recycle-view` / `recycle-item` 组件（miniprogram-recycle-view），核心约束：

1. 列表项高度需要可确定（等高卡片最适合；不等高支持复杂、成本高）；
2. 数据更新、滚动位置控制有专门 API，不能完全当普通列表操作；
3. 接入 npm 构建与调试成本都高于普通 wx:for。

选型建议（由轻到重）：

| 方案 | 适用量级 | 成本 |
|---|---|---|
| 分页 + 卡片轻量化 + setData 治理 | 几百条以内 | 低，默认选择 |
| scroll-view + 手动控制渲染窗口（进阶） | 数百到上千条 | 中 |
| recycle-view 虚拟列表 | 上千条且单卡结构稳定 | 高 |
| Skyline 渲染引擎下的 scroll-view | 追求高帧率长列表 | 中高，专题单元展开 |

「逛吃指南」的探店卡片有封面有标题、高度基本一致，属于分页足够、recycle-view 可选的形态；不要为炫技提前引入虚拟列表，先用数据证据证明有必要。

误区提醒：

- 以为“上了 recycle-view 就一定更快”——不等高、频繁数据变更时反而更难维护。
- 节点已达上千、帧率明显下降仍不做任何治理。

### 14. 弱网与竞态：旧结果绝不能覆盖新结果

竞态（race）指多个请求在飞时，**返回顺序不等于发起顺序**，旧响应晚到后覆盖了新响应。列表页的高发场景：

1. 快速输入“火锅 → 火锅 店”，两个请求几乎同时在飞，“火锅”的结果晚回来 → 界面显示与“火锅店”不符的结果；
2. 快速切换行政区筛选，旧区域结果晚到覆盖新区域；
3. 弱网下触底加载更多，用户等不及又下拉刷新，两路数据互相拼接出重复/错位。

两道防线（第 8 节已落地，这里总结原理）：

**防线 A：请求序号（推荐为主）。**

```typescript
// 每次“换问题”递增序号，响应回来时比对
const seq = ++this.requestSeq
const res = await listShops(query)
if (seq !== this.requestSeq) return // 我已过期，丢弃一切结果
```

序号方案覆盖所有竞态，包括“请求无法 abort”的情况，且不会让 promise reject 出额外错误。

**防线 B：abort 取消旧请求。**

条件变化时 `this.currentTask.abort()`，省流量、省并发名额；abort 错误静默。实战中**两者并用**：abort 主动释放资源，序号兜底乱序回调。

**弱网专项：**

```typescript
// 感知网络变化，恢复后允许用户/自动重试
wx.onNetworkStatusChange((res) => {
  if (res.isConnected && this.data.viewState === 'first_error') {
    this.resetAndLoad()
  }
})

// 进入页面也可查询一次
wx.getNetworkType({
  success(res) {
    if (res.networkType === 'none') {
      // 直接给离线态，不必等超时
    }
  },
})
```

加载更多防重复的另一道保险：进入 `loading_more` 期间忽略所有触底；失败后 footer 提供“点击重试”，页码不动。超时时间按“分页接口应较快返回”设置（如 10s），避免 footer 长时间假死。

误区提醒：

- 只靠 abort 防竞态：abort 有时机窗口（响应已在回调队列），序号不能省。
- 弱网下用 loading mask 锁死整个页面，用户连“返回/改关键词”都做不了；分页加载应只锁 footer。

### 15. 综合实战：首页与探索页完整改造

把前面所有能力合到一个完整页面。数据与类型：

```typescript
// pages/explore/explore.ts
import { debounce } from '../../utils/debounce'
import { listShops, type ShopCard, type ShopQuery } from '../../services/shop'
import { isAbortError } from '../../utils/request/cancel'
import { bus, EVENTS } from '../../utils/event-bus'

type ViewState =
  | 'first_loading'
  | 'success'
  | 'empty'
  | 'first_error'
  | 'loading_more'
  | 'load_more_error'

interface ExploreData {
  viewState: ViewState
  list: ShopCard[]
  hasMore: boolean
  keyword: string
  filterState: { district: string; category: string; sort: string }
  hasActiveFilter: boolean
}

let unsubscribe: (() => void) | null = null

Page<ExploreData, WechatMiniprogram.IAnyObject>({
  data: {
    viewState: 'first_loading',
    list: [],
    hasMore: true,
    keyword: '',
    filterState: { district: '', category: '', sort: 'default' },
    hasActiveFilter: false,
  },

  // —— 非渲染运行期变量 ——
  keywordRaw: '',
  district: '',
  category: '',
  sort: 'default',
  page: 1,
  loading: false,
  requestSeq: 0,
  currentTask: null as wx.RequestTask | null,
  searchRunner: null as
    | ((keyword: string) => void) & { cancel: () => void }
    | null,
  unsubscribe: null as (() => void) | null,

  onLoad() {
    this.searchRunner = debounce((keyword: string) => {
      this.keywordRaw = keyword
      this.resetAndLoad()
    }, 350)

    // 收藏变更：路径更新单卡，不整页刷新
    this.unsubscribe = bus.on<{ shopId: string; liked: boolean }>(
      EVENTS.FAVORITE_CHANGED,
      ({ shopId, liked }) => {
        const i = this.data.list.findIndex((s) => s.id === shopId)
        if (i >= 0) this.setData({ [`list[${i}].liked`]: liked })
      },
    )

    this.resetAndLoad()
  },

  // 返回本页不重置列表：保持位置，局部变化由事件处理
  onShow() {},

  // —— 查询条件处理 ——
  onKeywordInput(e: WechatMiniprogram.Input) {
    this.setData({ keyword: e.detail.value })
    this.searchRunner?.(e.detail.value.trim())
  },

  onKeywordConfirm(e: WechatMiniprogram.InputConfirm) {
    this.searchRunner?.cancel()
    this.keywordRaw = e.detail.value.trim()
    this.resetAndLoad()
  },

  onClearKeyword() {
    this.searchRunner?.cancel()
    this.keywordRaw = ''
    this.setData({ keyword: '' })
    this.resetAndLoad()
  },

  onFilterTap(e: WechatMiniprogram.Tap) {
    const { type, value } = e.currentTarget.dataset as {
      type: 'district' | 'category' | 'sort'
      value: string
    }
    this[type] = value
    this.setData({
      [`filterState.${type}`]: value,
      hasActiveFilter:
        this.district !== '' || this.category !== '' || this.sort !== 'default',
    })
    this.resetAndLoad()
  },

  onResetFilter() {
    this.district = ''
    this.category = ''
    this.sort = 'default'
    this.setData({
      filterState: { district: '', category: '', sort: 'default' },
      hasActiveFilter: false,
    })
    this.resetAndLoad()
  },

  // —— 核心：统一重置入口 ——
  async resetAndLoad() {
    this.currentTask?.abort()
    const seq = ++this.requestSeq
    this.page = 1
    this.loading = true
    this.setData({ viewState: 'first_loading', hasMore: true })
    wx.pageScrollTo({ scrollTop: 0, duration: 0 })

    try {
      const { task, promise } = this.createRequest(1)
      this.currentTask = task
      const res = await promise
      if (seq !== this.requestSeq) return

      const list = replaceList(res.list)
      this.setData({
        list,
        hasMore: res.hasMore,
        viewState: list.length === 0 ? 'empty' : 'success',
      })
    } catch (err) {
      if (seq !== this.requestSeq || isAbortError(err)) return
      this.setData({ viewState: 'first_error' })
    } finally {
      if (seq === this.requestSeq) this.loading = false
    }
  },

  // —— 加载更多 ——
  async onReachBottom() {
    if (this.loading || !this.data.hasMore) return
    if (this.data.viewState === 'first_error') return

    const seq = this.requestSeq // 翻页不递增“问题序号”，但要校验中途没换条件
    this.loading = true
    this.setData({ viewState: 'loading_more' })

    try {
      const nextPage = this.page + 1
      const { task, promise } = this.createRequest(nextPage)
      this.currentTask = task
      const res = await promise
      if (seq !== this.requestSeq) return

      this.page = nextPage
      this.setData({
        list: mergeList(this.data.list, res.list),
        hasMore: res.hasMore,
        viewState: 'success',
      })
    } catch (err) {
      if (seq !== this.requestSeq || isAbortError(err)) return
      this.setData({ viewState: 'load_more_error' })
    } finally {
      if (seq === this.requestSeq) this.loading = false
    }
  },

  onRetryLoadMore() {
    if (!this.loading) this.onReachBottom()
  },

  // —— 下拉刷新 ——
  async onPullDownRefresh() {
    try {
      // 复用重置逻辑，但保留旧列表展示：临时把 viewState 视作 success
      await this.refreshSilently()
    } finally {
      wx.stopPullDownRefresh()
    }
  },

  async refreshSilently() {
    this.currentTask?.abort()
    const seq = ++this.requestSeq
    this.page = 1

    const { task, promise } = this.createRequest(1)
    this.currentTask = task
    const res = await promise
    if (seq !== this.requestSeq) return

    const list = replaceList(res.list)
    this.setData({
      list,
      hasMore: res.hasMore,
      viewState: list.length === 0 ? 'empty' : 'success',
    })
  },

  // —— 工具 ——
  createRequest(page: number) {
    const query: ShopQuery = {
      keyword: this.keywordRaw || undefined,
      district: this.district || undefined,
      category: this.category || undefined,
      sort: this.sort,
      page,
      pageSize: 20,
    }
    return createShopsTask(query)
  },

  onShopTap(e: WechatMiniprogram.Tap) {
    const { id } = e.currentTarget.dataset as { id: string }
    wx.navigateTo({ url: `/pages/detail/detail?id=${id}` })
  },

  onUnload() {
    this.searchRunner?.cancel()
```
