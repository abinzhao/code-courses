# 25-分享裂变与社交增长

## 目标

完成本知识单元后，学员应能为「逛吃指南」设计并落地一条完整的社交增长链路：用户把笔记或活动分享给好友/群/朋友圈，被邀请人通过卡片、小程序码或短链进入落地页，服务端完成可归因、可风控、可发奖的邀请关系绑定。重点不是“让页面能转发”，而是让**每一次分享带来的流量都可追踪、每一份激励都经得起薅羊毛攻击**。

学员应能够：

1. 在页面中实现 `onShareAppMessage` 与 `onShareTimeline`，准确配置标题、路径、配图，并理解返回值各字段的限制与默认行为。
2. 设计**分享参数透传**方案：通过 `path` 的 query 或朋友圈的 `query` 把渠道、活动、邀请人短码安全带到落地页，并正确编码、解析。
3. 区分菜单转发（右上角胶囊菜单）与按钮转发（`open-type="share"`）两种触发方式，理解 `wx.showShareMenu` / `wx.hideShareMenu` 与 `withShareTicket` 的用途。
4. 在落地页正确处理冷启动与热启动参数，理解 `onLoad` options、`App.onShow` options、`wx.getLaunchOptionsSync`、`wx.getEnterOptionsSync` 的分工，看懂常见场景值。
5. 在服务端（云函数）完成邀请关系绑定：基于可信的登录态（openid/unionid）记录 inviter 与 invitee 的归因关系，支持归因窗口、首次绑定、幂等。
6. 设计邀请防刷风控：识别自邀、小号、设备农场、高频刷量，把风控与奖励发放放在服务端，理解“密钥不放前端”是不可协商的底线。
7. 用云函数调用 `wxacode` 系列接口生成小程序码，理解 `getwxacode`、`getwxacodeunlimit`、`createQRCode` 的差异，掌握 `scene` 的 32 字符限制与短码映射技巧。
8. 区分小程序码、普通链接二维码、URL Link、URL Scheme 四种“码与链”的适用场景（线下物料、短信、H5、App、直播间），并说明有效期与配置要求。
9. 实现跳转公众号关注组件、视频号、其他小程序（含半屏小程序）的联动，并配置 `navigateToMiniProgramAppIdList` 白名单。
10. 建立分享回流数据追踪体系：落地页曝光、注册/登录、有效行为、发奖等关键事件的埋点与归因，计算邀请转化率，并清楚“分享成功”不可作为发奖依据的平台规则。

本单元承接 U16 登录鉴权与用户体系、U14 云函数，是阶段四「性能与增长」的第一课，也为 U26 把营销落地页拆入独立/普通分包提供需求来源。

本单元使用微信原生分享与开放能力 + TypeScript，关系绑定与发奖逻辑放在云函数（或等价的自建服务端），数据落云数据库。

约定：

- 邀请关系、风控、奖励发放**只在服务端判定**；前端上报的任何身份字段（inviterId、deviceId）都只能作为参考线索，不能作为信任依据。
- `access_token`、API 密钥、发奖密钥绝不写入小程序代码；云函数使用 `cloud.openapi` 时由平台托管鉴权，自建后端自行换取并缓存 `access_token`。
- 卡片标题、配图、活动规则必须真实，诱导分享、诱导关注、虚假奖励属于平台红线。

## 详细的理论知识讲解和示例伪代码

### 1. 社交增长的基本盘：转发、分享与“回流”到底在说什么

先统一术语，这一节的概念后面会反复出现：

- **分享/转发**：用户把当前页面以消息卡片形式发到好友会话、群会话（`onShareAppMessage`），或发布到朋友圈（`onShareTimeline`）。对开发者而言，这只是“把卡片发出去”。
- **进入（落地）**：另一个用户点开卡片，微信冷启动或热启动小程序，并把卡片携带的参数交给目标页面。
- **回流**：被邀请人不仅进入了小程序，还完成了被定义的关键行为——新用户登录、发布第一篇笔记、报名活动、下单。**没有行为的进入只是一次访问，不是增长。**
- **邀请关系（归因）**：服务端记录“这次有效行为是谁带来的”，即 inviter（邀请人）与 invitee（被邀请人）之间的一条事实记录。
- **激励**：在归因成立且通过风控后，给邀请人（有时也给被邀请人）发奖励。

用增长漏斗看「逛吃指南」的邀请有礼：

```text
分享用户数 A
  └─ 卡片被点击进入数 B      （点击率 = B/A）
       └─ 新用户登录数 C     （激活率 = C/B）
            └─ 完成有效行为 D（有效率 = D/C，如发布第一篇笔记）
                 └─ 通过风控并发放奖励 E
```

K 因子（每个用户平均带来多少新用户）= A 人均分享数 × 点击进入率 × 有效转化率。工程团队的抓手在每一层：卡片标题与配图影响点击，落地页首屏影响激活，参数透传与服务端归因影响“这一切能不能被算清楚”。

误区提醒：

- 把“分享成功”当成转化终点。平台从 2020 年起不再保证把用户是否真的发送了卡片告知开发者，而且以“分享成功”为发奖条件本身就是诱导分享红线。
- 只做转发 UI、不做服务端归因，最后无法回答“这批新用户是谁带来的”，增长成了玄学。

### 2. onShareAppMessage：页面转发的总开关

在 Page（或 Component 构造的页面）中定义 `onShareAppMessage` 后，该页面才支持“转发给朋友”。用户从两个入口触发：右上角胶囊菜单的“转发”（`from: 'menu'`），以及页面内 `<button open-type="share">`（`from: 'button'`，此时 `target.dataset` 可拿到按钮上绑定的数据）。

返回对象三个核心字段：

| 字段 | 说明 | 缺省行为 |
|---|---|---|
| title | 卡片标题 | 取小程序名称 |
| path | 落地页路径，必须以 `/` 开头，可带 query | 当前页面路径，不带参数 |
| imageUrl | 自定义配图，PNG/JPG，显示比例 5:4 | 自动截取当前页面 |

「逛吃指南」笔记详情页的完整示例：

```typescript
// miniprogram/pages/note-detail/note-detail.ts
import { buildSharePath } from '../../utils/share'

interface ShareData {
  title: string
  path: string
  imageUrl?: string
}

Page({
  data: {
    noteId: '',
    noteTitle: '',
    cover: '',
    inviterCode: '',
  },

  onLoad(options: Record<string, string>) {
    // options 可能来自他人分享：id、inviterCode、source
    this.setData({
      noteId: options.id ?? '',
      inviterCode: options.inviterCode ?? '',
    })
  },

  onShareAppMessage(from: {
    from: 'button' | 'menu'
    target?: { dataset: Record<string, string> }
  }): ShareData {
    const { noteId, noteTitle, cover, inviterCode } = this.data

    // 按钮上可以绑定 campaign（如 note_detail_footer）
    const campaign = from.target?.dataset.campaign ?? 'note_detail_menu'

    return {
      title: noteTitle || '我在逛吃指南发现一家宝藏小店',
      path: buildSharePath('/pages/note-detail/note-detail', {
        id: noteId,
        inviterCode: inviterCode || getMyShareCode(), // 自己的短码，服务端可换 openid
        source: 'appmessage',
        campaign,
      }),
      imageUrl: cover || undefined, // 无封面时不传，走页面截图
    }
  },
})
```

配图是网络图片时直接给 https URL 即可；也可以先 `wx.downloadFile` 拿到临时路径。若需要异步生成卡片（例如现画一张带价格的图），可以返回 Promise：

```typescript
onShareAppMessage() {
  return new Promise<ShareData>((resolve) => {
    drawSharePoster(this.data.note).then((tempFilePath) => {
      resolve({
        title: this.data.note.title,
        path: buildSharePath('/pages/note-detail/note-detail', { id: this.data.noteId }),
        imageUrl: tempFilePath,
      })
    })
  })
}
```

误区提醒：

- `path` 不以 `/` 开头，或在 query 里直接拼接未编码的中文、URL（比如笔记里的店铺链接），会出现参数解析错乱。
- 不设 `imageUrl` 时截图对“长页面”不友好，可能截到一半的文字；关键分享场景应显式准备 5:4 卡片图。
- `onShareAppMessage` 只在定义它的页面生效，它不是全局能力，不能写在 `App()` 里。

### 3. 分享参数透传：把“谁分享的”安全带到落地页

参数透传要回答：被邀请人进入后，落地页如何知道**这是哪一场活动、从哪个渠道、由谁分享的**。原则有三条：

1. **只传短码，不传身份**。卡片在聊天里是半公开的，query 对接收方可见、可被复制和篡改。所以传 `inviterCode`（服务端可反查邀请人的短随机码），绝不能直接放 openid、手机号。
2. **统一编码与解析**。中文、特殊字符一律 `encodeURIComponent`，并在落地页做类型收敛。
3. **参数最小化**。query 越长卡片越丑（调试时），也更容易触发长度限制；大参数（如完整活动配置）放服务端，用短码去取。

工具函数：

```typescript
// miniprogram/utils/share.ts
interface ShareQuery {
  [key: string]: string | number | undefined
}

/** 拼接带 query 的分享路径，自动跳过空值并编码 */
export function buildSharePath(path: string, query: ShareQuery): string {
  const entries = Object.entries(query).filter(([, v]) => v !== undefined && v !== '')
  if (entries.length === 0) return path
  const search = entries
    .map(([k, v]) => `${encodeURIComponent(k)}=${encodeURIComponent(String(v))}`)
    .join('&')
  return `${path}?${search}`
}

/** 从 onLoad options 中安全取分享参数 */
export function parseShareOptions(options: Record<string, string | undefined>) {
  return {
    noteId: options.id ? decodeURIComponent(options.id) : '',
    inviterCode: options.inviterCode ? decodeURIComponent(options.inviterCode) : '',
    source: options.source ? decodeURIComponent(options.source) : '',
    campaign: options.campaign ? decodeURIComponent(options.campaign) : '',
  }
}

/** 读取本人的分享短码（登录后由服务端下发并缓存） */
export function getMyShareCode(): string {
  return wx.getStorageSync('my_share_code') || ''
}
```

分享路径最终形如：

```text
/pages/note-detail/note-detail?id=n_1024&inviterCode=8K2xQp&source=appmessage&campaign=note_detail_footer
```

误区提醒：

- 把 openid 放进 query 当作 inviterId。openid 本身虽然不是秘密，但客户端可把它改成任何人的 openid，服务端若直接信任，就能“给任意账号刷邀请奖励”。
- 参数里嵌套 JSON（`?data=[{"a":1}]`），不做二次编码时 `&`、`{` 会把 query 结构打穿。
- 同一条卡片在群里被二次转发后，透传的仍是最初邀请人的短码——这通常是期望行为（归因给最初分享者），但要在活动规则里想清楚“二次转发算不算新渠道”。

### 4. onShareTimeline：分享到朋友圈的单页模式

`onShareTimeline` 让页面支持“分享到朋友圈”，基础库 2.11.3 起支持。它的返回值与 `onShareAppMessage` 有一个关键差异：**没有 `path` 字段**。朋友圈卡片固定指向当前页面，能自定义的是 `title`、`query`、`imageUrl`。

```typescript
// 同一个笔记详情页
onShareTimeline(): { title: string; query: string; imageUrl?: string } {
  const { noteId, noteTitle, cover } = this.data
  return {
    title: noteTitle || '这家店值得专门跑一趟',
    // query 是字符串，不是对象；同样只放短码
    query: `id=${encodeURIComponent(noteId)}&inviterCode=${encodeURIComponent(getMyShareCode())}&source=timeline`,
    imageUrl: cover,
  }
}
```

用户从朋友圈点开时，页面以**单页模式**运行：不加载 tabBar、页面栈中只有这一个页面、`wx.switchTab` 等依赖完整应用结构的能力不可用，部分 JS API 受限制；页面 `onLoad` 会收到上面定义的 `query`。因此落地页必须“自包含”——首屏就能看懂内容、能登录、能完成关键转化，不能假设用户还能沿 tabBar 逛到别处。

适配示例：

```typescript
onLoad(options: Record<string, string>) {
  const isSinglePage = wx.getEnterOptionsSync().scene === 1014? // 不写死，见第 6 节
  // 无论从哪里来，先保证笔记内容可独立浏览
  this.loadNote(options.id)
  // 单页模式下把“发布我的笔记”“报名活动”做成页内按钮，而非 tabBar 引导
}
```

误区提醒：

- 以为朋友圈可以像好友分享一样指定任意落地 `path`，结果把活动页路径写进返回值——该字段会被忽略。
- 在单页模式里强依赖 tabBar 与多级返回栈，导致从朋友圈进来的用户卡在空白页。
- `query` 直接拼中文不编码，部分机型进入后 onLoad 拿不到完整参数。

### 5. 菜单分享与按钮分享：showShareMenu 与 open-type="share"

微信**不提供**“JS 直接调起分享面板”的 API，这是防诱导分享的设计。分享只能由两个用户主动行为触发：

1. 右上角胶囊菜单 → “转发”/“分享到朋友圈”；
2. 页面内 `<button open-type="share">`，点击后等价于菜单转发，且走同一个 `onShareAppMessage`。

菜单可以通过 `wx.showShareMenu` / `wx.hideShareMenu` 控制：

```typescript
onLoad() {
  wx.showShareMenu({
    withShareTicket: true, // 群分享卡片带回 shareTicket，可用于获取 openGId
    menus: ['shareAppMessage', 'shareTimeline'],
  })
}
```

按钮分享的 WXML，注意通过 `data-*` 传递分享上下文：

```xml
<!-- miniprogram/pages/note-detail/note-detail.wxml -->
<view class="footer-bar">
  <button
    class="share-btn"
    open-type="share"
    data-campaign="note_detail_footer"
    data-id="{{noteId}}"
  >分享给饭搭子</button>
</view>
```

点击后 `onShareAppMessage` 收到：

```typescript
{
  from: 'button',
  target: { dataset: { campaign: 'note_detail_footer', id: 'n_1024' } }
}
```

`withShareTicket: true` 用于群场景：用户把卡片分享到某个群、且卡片是带票据版本时，小程序在 `App.onShow` / `getEnterOptionsSync` 里能拿到 `shareTicket`，再调 `wx.getShareInfo` 换取群标识 `openGId`，可做“群专属活动、同群去重”。

误区提醒：

- 页面没有定义 `onShareAppMessage`，却放了 `open-type="share"` 按钮，点击没有任何反应。
- 试图用“点击普通按钮 → JS 里调起转发”，这条路不存在；运营弹层里的“立即分享”必须最终落到 `open-type="share"` 按钮上。
- 对不需要朋友圈的页面（如含敏感表单的页面）忘记用 `hideShareMenu` 收敛入口。

### 6. 分享进入与启动参数：冷启动、热启动与场景值

参数在三个层级拿到，分工不同：

| 层级 | API/回调 | 能拿到什么 | 典型用途 |
|---|---|---|---|
| 应用 | `App.onLaunch(options)` | 冷启动时的 path/query/scene/shareTicket | 全局归因、启动来源 |
| 应用 | `App.onShow(options)` | 冷启动 + 每次切回前台 | 热启动重新归因 |
| 页面 | `Page.onLoad(options)` | 目标页面的 query | 落地页渲染、邀请绑定 |
| 同步 | `wx.getLaunchOptionsSync()` | 冷启动参数（全程不变） | 任何模块读取启动来源 |
| 同步 | `wx.getEnterOptionsSync()` | 最近一次进入小程序的参数 | 回到前台时的最新来源 |

`options.scene` 是**数字场景值**，回答“从什么入口进来”，教学中常见的几个：

| 场景值 | 含义 |
|---|---|
| 1001 | 发现栏小程序主入口 |
| 1007 | 单人聊天会话中的小程序消息卡片 |
| 1008 | 群聊会话中的小程序消息卡片 |
| 1011 | 扫描二维码 |
| 1044 | 带 shareTicket 的小程序消息卡片 |
| 1047 | 扫描小程序码 |
| 1048 | 长按图片识别小程序码 |
| 1049 | 手机相册选取小程序码 |

场景值随微信版本会增删，以官方“场景值”文档为准。

**命名陷阱**（高频面试与实战 bug）：应用级 `options.scene` 是数字场景值；而 `getwxacodeunlimit` 的 `scene` 参数会作为**字符串**出现在页面 `onLoad(options)` 的 `options.scene` 里。两者同名、类型不同、语义不同：

```typescript
App({
  onLaunch(appOptions) {
    console.log(appOptions.scene) // 数字，如 1047（扫码进入）
  },
})

Page({
  onLoad(pageOptions) {
    // 小程序码 getUnlimited 携带的 scene 字符串在这里
    if (pageOptions.scene) {
      const params = parseCodeScene(decodeURIComponent(pageOptions.scene))
      // 如 { inviterCode: '8K2xQp', activityId: 'a9' }
    }
  },
})
```

热启动场景：用户已经开着小程序，又从聊天里点开一张新卡片，页面不一定重新 `onLoad`（若页面栈已有实例）。需要在 `App.onShow` 里拿到最新 path/query 后通过事件或全局状态通知落地页重新归因，不能只在 `onLoad` 处理一次。

误区提醒：

- 只在 `onLoad` 解析邀请参数，热启动点开新卡片时归因丢失。
- 把数字场景值和码 scene 字符串混用，写出 `if (scene === '1007')` 永远不成立的判断。
- 用场景值做安全判断（场景值可被技术手段构造），它只能用于统计，不能用于鉴权。

### 7. 落地页参数解析与邀请关系绑定：核心在服务端

正确的邀请绑定链路（以「逛吃指南」邀请有礼为例）：

```text
1. 邀请人打开小程序，登录后云函数下发并缓存个人分享短码 inviterCode
2. 分享卡片 path 携带 inviterCode（query），卡片发出
3. 被邀请人点开卡片，落地页 onLoad 读到 inviterCode
4. 被邀请人完成登录（wx.login → 云函数拿到可信 openid）
5. 前端调 bindInvite 云函数，只传 inviterCode；openid 由服务端从上下文取
6. 服务端：短码反查邀请人 → 校验 → 幂等写 invites → 返回绑定结果
7. 被邀请人完成有效行为（如发布首篇笔记）→ 服务端更新状态 → 风控通过 → 发奖
```

云函数示例：

```javascript
// cloudfunctions/bindInvite/index.js
const cloud = require('wx-server-sdk')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const db = cloud.database()
const _ = db.command

exports.main = async (event) => {
  const { OPENID } = cloud.getWXContext() // 被邀请人可信身份
  const { inviterCode, source, campaign } = event

  if (!inviterCode || typeof inviterCode !== 'string') {
    return { ok: false, reason: 'BAD_CODE' }
  }

  // 1. 短码反查邀请人（短码与 openid 的映射表由服务端维护）
  const codeRes = await db.collection('share_codes')
    .where({ code: inviterCode.slice(0, 32) }).limit(1).get()
  if (codeRes.data.length === 0) return { ok: false, reason: 'CODE_NOT_FOUND' }

  const inviterOpenid = codeRes.data[0].openid
  if (inviterOpenid === OPENID) return { ok: false, reason: 'SELF_INVITE' }

  // 2. 幂等：该被邀请人已有有效邀请关系则直接返回既有结果
  const existed = await db.collection('invites')
    .where({ invitee: OPENID, status: _.neq('invalid') }).limit(1).get()
  if (existed.data.length > 0) {
    return { ok: true, duplicated: true, inviteId: existed.data[0]._id }
  }

  // 3. 写入归因关系（状态机：bound → activated → rewarded / invalid）
  const add = await db.collection('invites').add({
    data: {
      inviter: inviterOpenid,
      invitee: OPENID,
      source: String(source || '').slice(0, 16),
      campaign: String(campaign || '').slice(0, 32),
      status: 'bound',
      createdAt: db.serverDate(),
      activatedAt: null,
      rewardedAt: null,
    },
  })
  return { ok: true, duplicated: false, inviteId: add._id }
}
```

关键设计点：

- **被邀请人身份不从前端拿**。`OPENID` 来自 `getWXContext()`，客户端无法伪造；前端只负责提交“我点了谁的码”。
- **首次绑定原则**：一个新用户通常只归因给第一个有效邀请人（防抢归因），用查询 + 唯一约束保证。
- **归因窗口**：从 `bound` 到 `activated`（完成有效行为）设有效期（如 7 天），超期关系置 `invalid`。
- 跨公众号/App 识别同一用户时用 unionid（需同开放平台主体），但要在隐私政策中说明。

误区提醒：

- 前端直接把 inviterOpenid 传给云函数并信任之——攻击者改参数就能把奖励送给任何账号。
- 不做幂等，被邀请人重复进入、重复登录产生多条 invites，奖励被重复发放。
- 绑定即发奖：正确顺序是“绑定 → 有效行为激活 → 风控 → 发奖”。

### 8. 邀请防刷与风控：把恶意邀请挡在发奖之前

黑产攻击邀请活动的常见手法：

| 手法 | 表现 | 服务端对策 |
|---|---|---|
| 自邀 | 自己邀请自己的小号 | openid 自比；unionid 同主体下多 openid 关联识别 |
| 小号海 | 批量注册新账号刷新人奖 | 新用户有效行为门槛（发真实笔记、下单、留存 N 天） |
| 设备农场 | 同设备/同 IP 批量登录 | 设备与网络特征聚类（仅作风控特征，不做强判定） |
| 改参数 | 篡改 inviterCode/渠道 | 服务端短码反查，不接受任何客户端身份字段 |
| 高频刷 | 短时间大量“激活” | 邀请人/被邀请人双侧频率限制与异常阈值 |
| 行为造假 | 机器人生成垃圾笔记骗激活 | 内容安全检测 + 行为序列模型 + 人工抽审 |

风控要落在状态机里，而不是一个 if：

```javascript
// cloudfunctions/evaluateReward/index.js
exports.main = async (event) => {
  const { inviteId } = event
  const invite = (await db.collection('invites').doc(inviteId).get()).data

  // 规则 1：必须已激活（被邀请人完成有效行为）
  if (invite.status !== 'activated') return { ok: false, reason: 'NOT_ACTIVATED' }

  // 规则 2：归因窗口内
  const hours = (Date.now() - invite.createdAt.getTime()) / 3600000
  if (hours > 24 * 7) {
    await db.collection('invites').doc(inviteId).update({ data: { status: 'invalid' } })
    return { ok: false, reason: 'EXPIRED' }
  }

  // 规则 3：邀请人当日发奖次数上限
  const todayCount = await db.collection('invites').where({
    inviter: invite.inviter,
    rewardedAt: _.gt(new Date(Date.now() - 24 * 3600000)),
  }).count()
  if (todayCount.total >= 20) return { ok: false, reason: 'DAILY_LIMIT' }

  // 规则 4：被邀请人质量分（由离线/实时风控服务写入，如登录后是否有真实浏览）
  if ((invite.inviteeRiskScore ?? 0) > 60) {
    return { ok: false, reason: 'RISK_REVIEW' } // 进入人工复核队列
  }

  // 规则 5：幂等发奖（唯一约束 inviteId，防止重试重复发）
  await grantRewardOnce(invite) // 内部用事务/唯一键保证只发一次
  await db.collection('invites').doc(inviteId).update({
    data: { status: 'rewarded', rewardedAt: db.serverDate() },
  })
  return { ok: true }
}
```

关于密钥：

- 自建后端调用 `https://api.weixin.qq.com/...` 需要 `access_token`，它由 `appid + appsecret` 换取。**appsecret 只能保存在服务器**，前端代码、前端仓库、云函数环境变量之外的任何位置都不允许出现。
- 使用云开发时优先用 `cloud.openapi`，免 token 管理；即便如此，发奖用的业务密钥（如有）也应放在服务端配置中。

误区提醒：

- 只在前端做“同一设备只能被邀请一次”，清缓存即绕过。
- 风控规则写死成硬编码阈值且没有复核出口，误伤真实用户无法申诉。
- 用“分享成功回调”触发发奖（见第 13 节），既不合规也不安全。

### 9. 小程序码：三种 wxacode 接口怎么选

小程序码（菊花码）是微信生态内识别度最高的入口。服务端有三个生成接口：

| 接口（云开发 openapi） | 参数携带 | 限制要点 | 适用场景 |
|---|---|---|---|
| wxacode.get（getwxacode） | path + query | path 总长度 128 字节以内 | 少量、路径直接可读 |
| wxacode.getUnlimited（getwxacodeunlimit） | scene（≤32 个可见字符）+ page | 数量“不限”，参数极简 | 量大、笔记/活动每物一码 |
| wxacode.createQRCode（createQRCode） | path + query | 较早的方形二维码，path 128 字节 | 兼容旧物料 |

「逛吃指南」为每篇笔记生成永久小程序码，用 `getUnlimited` + 云存储：

```javascript
// cloudfunctions/genNoteCode/index.js
const cloud = require('wx-server-sdk')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })

exports.main = async (event) => {
  const { noteId, inviterCode } = event

  // scene 总长 ≤32，采用“短字段 + 短码”，如 n.noteId:i.inviterCode
  let scene = `n=${noteId}`
  if (inviterCode) scene += `&i=${inviterCode}`
  if (scene.length > 32) throw new Error('SCENE_TOO_LONG')

  const res = await cloud.openapi.wxacode.getUnlimited({
    scene,
    page: 'pages/note-detail/note-detail', // 必须是已发布/对应版本存在的页面
    checkPath: false,                       // 配合 envVersion 时可关掉严格校验
    envVersion: 'release',                 // release / trial / develop
    width: 280,
  })

  // res.buffer 是 PNG 二进制，上传云存储后返回 fileID
  const upload = await cloud.uploadFile({
    cloudPath: `qrcodes/note/${noteId}_${Date.now()}.png`,
    fileContent: res.buffer,
  })
  return { fileID: upload.fileID, scene }
}
```

落地页解析：

```typescript
onLoad(options: Record<string, string>) {
  if (options.scene) {
    // scene 形如 n=n_1024&i=8K2xQp
    const parsed = new URLSearchParams(decodeURIComponent(options.scene))
    this.setData({
      noteId: parsed.get('n') ?? '',
      inviterCode: parsed.get('i') ?? '',
      source: 'wxacode',
    })
  }
}
```

当业务参数超过 32 字符（典型：多活动、多标签），不要硬塞——用服务端**短码映射**：生成码时把完整参数存表，换一个 6~8 位码放进 scene（如 `c=Ab3kQ9`），落地时回调云函数取全量参数。

误区提醒：

- scene 里直接放长标题、URL，超长报错或被截断后归因失败。
- `envVersion: 'release'` 指向正式版，新页面还没发布时 `checkPath` 会报 path 不存在；联调期用 `develop/trial`。
- 在前端调 `wx.request` 直连 `api.weixin.qq.com` 并用写死的 access_token 生成码——token 会过期且泄露密钥。

### 10. 普通链接二维码：把线下与 H5 流量接进小程序

普通链接二维码就是一个标准 URL 二维码（形如 `https://m.guangchi.example.com/note/1024`），用户用微信扫码后，微信根据**小程序后台配置的“二维码规则”**决定是否打开小程序以及打开哪个页面。

配置路径：小程序管理后台 → 开发管理 → 开发设置 → 扫普通链接二维码打开小程序：

1. 添加二维码规则：填写 URL 前缀（协议、域名、路径前缀），域名需通过 ICP 等合规校验并放置校验文件；
2. 配置小程序功能页面（URL 与小程序页面的占用关系）；
3. 填写测试链接（先加白名单测试，再申请发布；未发布前仅管理员/体验成员可测）。

落地页收到的参数是原始 URL，放在 `options.q`（已编码）：

```typescript
onLoad(options: Record<string, string>) {
  if (options.q) {
    const url = decodeURIComponent(options.q)
    // https://m.guangchi.example.com/note/n_1024?i=8K2xQp
    const parsed = new URL(url)
    const noteId = parsed.pathname.split('/').pop() ?? ''
    const inviterCode = parsed.searchParams.get('i') ?? ''
    this.tryBindInvite(inviterCode, 'qrcode')
    this.loadNote(noteId)
  }
}
```

适用判断：物料已经印了普通码、二维码还要兼容微信外浏览器扫码、或者与已有 H5 站点共用链接时，用普通链接二维码；纯粹为微信内传播设计的码，用小程序码（识别度与打开体验更好）。

误区提醒：

- 规则只在测试状态、没申请发布，真实用户扫码只打开 H5 不进小程序。
- 忘记 `decodeURIComponent(options.q)`，拿到一串 `%2F%2F...` 无法解析。
- URL 前缀配得过宽，把站点下无关路径也抢进了小程序。

### 11. URL Link 与 URL Scheme：短信、App、H5 场景的短链

不是所有流量都能“扫码”。短信触达、Push、App 内嵌 H5、直播间评论，需要的是一条可点击的链接。两种形态：

| 能力 | 形态 | 主要使用环境 | 生成接口（云开发） |
|---|---|---|---|
| URL Link | `https://wxaurl.cn/xxxx` | 短信、微信外浏览器，点开拉起微信再进小程序 | urllink.generate |
| URL Scheme | `weixin://dl/business/?t=xxxx` | App 内、微信内 H5（location.href 跳转） | urlscheme.generate |

两者都支持指定落地 path/query，都**不能永久有效**（有效期最长 30 天量级，具体以官方文档为准），需要过期重新生成。

云函数示例：

```javascript
// cloudfunctions/genInviteLinks/index.js
const cloud = require('wx-server-sdk')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })

exports.main = async (event) => {
  const { noteId, inviterCode } = event
  const query = `id=${noteId}&inviterCode=${inviterCode}&source=link`

  // URL Link：用于短信投放
  const link = await cloud.openapi.urllink.generate({
    path: '/pages/note-detail/note-detail',
    query,
    expireType: 1,          // 1 = 按间隔天数过期
    expireInterval: 7,      // 7 天有效
  })

  // URL Scheme：用于 App / 微信内 H5 跳转
  const scheme = await cloud.openapi.urlscheme.generate({
    jumpWxa: {
      path: '/pages/note-detail/note-detail',
      query,
    },
    isExpire: true,
    expireType: 1,
    expireInterval: 7,
  })

  return { urlLink: link.urlLink, scheme: scheme.openlink }
}
```

微信内 H5 用 Scheme 时：

```html
<!-- 仅在微信内置浏览器中有效 -->
<a href="weixin://dl/business/?t=xxxx">打开逛吃指南看完整攻略</a>
```

误区提醒：

- 把 Link/Scheme 当永久链接埋进长期物料，过期后入口全废；应按批次生成、到期前重投。
- 类目或主体不满足开放条件时接口报错，需先查接口开通范围。
- 在微信外浏览器使用 Scheme、或在微信内页面用 Link，环境用反了都可能拉不起来。

### 12. 公众号、视频号与其他小程序：跳转矩阵与回流入口

社交增长不是小程序单兵作战。常见联动：

**跳转其他小程序**——需要在 `app.json` 声明目标 AppId 白名单（最多 10 个）：

```json
{
  "navigateToMiniProgramAppIdList": ["wxabcdef1234567890"]
}
```

```typescript
wx.navigateToMiniProgram({
  appId: 'wxabcdef1234567890',
  path: 'pages/partner/index?from=guangchi',
  extraData: { campaign: 'food_joint' },
  envVersion: 'release',
})
// 半屏形态（满足版本与场景要求时）：wx.openEmbeddedMiniProgram(...)
```

**公众号关注组件**——页面中放置 `<official-account>`，用户可在此一键关注关联的同主体公众号，用于把小程序流量沉淀为可多次触达的粉丝：

```xml
<official-account id="official" bindload="onOfficialLoad" binderror="onOfficialError"></official-account>
```

注意该组件**只在特定场景值下可见**（例如从公众号相关入口进入时），普通发现栏进入时不展示，要做兼容布局。

**视频号联动**——小程序与视频号绑定后，可通过 `wx.openChannelsUserProfile`、`wx.openChannelsLive` 等跳转到视频号主页/直播间，视频号主页也可挂载小程序；页面中还可用 `channel-video` 组件播放视频号内容，形成“短视频种草 → 小程序转化”。

**H5 反向拉起小程序**——在已关联的公众号 H5 页面中，使用开放标签 `<wx-open-launch-weapp>`（需 JSSDK 签名，签名逻辑在服务端），让 H5 直接打开小程序指定页面。

误区提醒：

- 未配 `navigateToMiniProgramAppIdList`，真机调用直接 fail。
- 把 `<official-account>` 当常驻按钮，结果在多数场景下是一块空白。
- H5 的 JSSDK 签名参数（jsapi_ticket 等）在前端生成——签名密钥必须留在服务端。

### 13. 分享回流数据追踪：从“有人点”到“可归因”

埋点要围绕“可计算转化”设计，而不是记录所有点击。「逛吃指南」的最小事件集：

| 事件 | 触发时机 | 关键参数 |
|---|---|---|
| share_enter | 落地页首屏曝光 | inviterCode、source、campaign、noteId |
| signup_login | 新用户完成登录 | invitee 由服务端识别 |
| invite_bind | 服务端绑定关系成功 | inviteId、是否重复 |
| invite_activate | 完成有效行为 | 行为类型、noteId |
| reward_grant | 奖励发放成功 | inviteId、奖励类型 |

客户端自定义分析用 `wx.reportAnalytics`（事件需先在小程序后台“自定义分析”中注册）：

```typescript
wx.reportAnalytics('share_enter', {
  source: 'appmessage',
  campaign: 'note_detail_footer',
  note_id: this.data.noteId,
})
```

但要记住：前端埋点会丢、会重复、可被构造。**奖励与归因的最终真值在服务端事件**（invites 状态流转），前端埋点用于漏斗分析与看板，两者通过 inviteId 串联，对账时以服务端为准。

特别强调平台规则：**开发者无法可靠获知用户是否真的把卡片发送成功**。`onShareAppMessage` 没有可用的“发送成功”回执作为奖励依据；以“分享后立得红包”为条件属于诱导分享。合规做法是：分享动作本身不给奖励，奖励条件挂在“被邀请人通过你的卡片进入并完成有效行为”上。

可计算的核心指标：

```text
分享进入→激活率 = invite_activate 去重人数 / share_enter 去重人数
邀请人转化率   = 带来 ≥1 有效新用户的邀请人数 / 参与分享人数
人均邀请有效数 = 有效激活总人数 / 参与分享人数（近似 K 因子的有效部分）
被邀请人次日留存 = 被邀请人中次日仍活跃的比例（衡量流量质量）
```

误区提醒：

- 用“点击分享按钮次数”当分享量，用户点开菜单取消也会计数，数据虚高。
- 事件不去重，一次落地因热启动/重进上报多次，漏斗各层对不上。
- 只看邀请数不看被邀请人留存，黑产流量把看板做得很漂亮但没有业务价值。

### 14. 激励发放、合规红线与完整链路验收

激励模型建议（合规且可持续）：

- **奖励对象**：以被邀请人“新用户 + 有效行为 + 留存”为发奖条件；可对被邀请人同时给新人礼（促进激活）。
- **奖励形式**：优先非现金或受限权益（店铺优惠券、活动优先报名、积分），现金类奖励受更严格的类目与规则约束。
- **防超发**：奖励预算池 + 单人封顶 + 单日封顶；发奖云函数对 inviteId 做唯一约束，支持重试不重复发。
- **阶梯奖励**：累计有效邀请 1/3/5 人解锁不同奖励，激励多次分享；阶梯判定同样在服务端重算，不信任客户端上报的累计数。

合规检查清单：

1. 卡片标题、配图真实，不出现“未分享不能使用”等胁迫式门槛（能力不能因分享才解锁）。
2. 活动规则页明示：奖励条件、有效期、上限、申诉方式。
3. 用户生成内容与自定义昵称过 `security.msgSecCheck`，避免违规文本随分享扩散。
4. 昵称、头像通过开放数据/头像昵称能力按需获取，隐私政策覆盖邀请与归因数据用途。
5. 不采集与活动无关的通讯录、精确位置等信息。

完整链路自测（以笔记分享为例）：

```text
□ A 账号登录拿到 inviterCode，笔记页分享卡片到文件传输助手
□ B 账号（新用户）点开卡片，落地页 onLoad 取参正确
□ B 登录后 bindInvite 成功，服务端 invites 生成 bound 记录
□ 同卡片重复进入，返回 duplicated，不产生新记录
□ B 发布首篇笔记，状态变 activated，过风控后 rewarded，奖励到账
□ 重试飞奖只发一次；A 自邀被 SELF_INVITE 拒绝
□ 分享进入/激活/发奖事件在后台看板可按 campaign 拆分
□ 小程序码（getUnlimited）扫码进入同样完成上述归因
```

这条自测清单就是阶段验收作业的雏形：**能解释每个环节“信任从哪里来、攻击从哪里进、奖励为什么只发一次”。**

### 练习 2：服务端邀请绑定云函数与防刷规则

#### 任务

实现 `bindInvite` 与 `evaluateReward` 两个云函数：短码反查邀请人、自邀拒绝、首次绑定幂等、激活后按频率上限与质量分判定发奖；用两个测试账号验证正常链路、重复绑定、自邀、超日限四种结果。

参考伪代码：

```text
bindInvite(inviterCode):
  invitee = context.OPENID
  inviter = share_codes.lookup(inviterCode)
  reject when !inviter or inviter == invitee
  return existed invite when invitee already bound
  insert invites(status=bound)

evaluateReward(inviteId):
  require status=activated and within 7-day window
  reject when inviter rewarded 20 in last 24h or riskScore > 60
  grantRewardOnce(inviteId) → status=rewarded
```

#### 步骤约束

1. 被邀请人 openid 只能来自 `getWXContext()`，函数入参中出现 openid 字段必须忽略。

3. 发奖必须幂等（同一 inviteId 重试两次只发一次），奖励变更与状态更新要在同一事务或等效原子操作中完成。
4. 风控不通过要返回明确 reason，并保留复核出口，不允许静默吞掉。

## 阶段验收作业

本作业是阶段四「性能与增长」的增长侧综合证据点，重点证明**你能为「逛吃指南」交付一条从分享到发奖、可归因、可风控、合规的社交裂变完整链路，而不只是几个能转发的页面**。

### 任务描述

实现「逛吃指南」邀请增长闭环：

1. 分享配置：笔记详情页（或活动详情页）同时支持好友/群分享与朋友圈分享，卡片标题、配图（5:4）、参数经过设计；页面内有按钮分享入口并能区分触发来源。
2. 参数透传：统一的 path/query 构建与解析工具，携带内容 id、邀请人短码、source、campaign；覆盖冷启动、热启动（App.onShow 二次归因）两种进入方式。
3. 服务端归因：`bindInvite` 云函数完成短码反查、自邀拒绝、首次绑定、幂等；invites 关系具备 bound→activated→rewarded/invalid 状态机与归因窗口。
4. 风控与发奖：有效行为（新用户发布首篇笔记或完成活动报名）后才激活；含频率限制、质量判定、幂等发奖、预算/封顶设计；可疑流量进入复核队列。
5. 码与链：用 `getwxacodeunlimit` 生成内容小程序码（scene 超 32 字符时使用短码映射），并说明该活动在短信/线下物料场景下应改用 URL Link 或普通链接二维码的理由与生成方式。
6. 数据追踪：落地曝光、绑定、激活、发奖事件埋点，输出该活动的转化漏斗（进入→激活→发奖）与被邀请人次留数据。
7. 提交不超过 400 字说明：信任边界（哪些字段可信、为什么）、防刷设计、合规依据（为何不以分享成功发奖）。

- 自邀、超频、可疑小号被准确拦截或进入复核，拦截理由可在服务端查到；

- 漏斗看板可按 source/campaign 拆分，前端埋点与服务端记录可对账；

### 强制不通过条件

- 邀请人身份（openid/手机号等）由前端入参提供并被服务端直接信任，或邀请关系可被参数篡改为任意账号；
- 绑定或发奖不幂等，重复进入、重试导致重复关系或重复发奖（以服务端记录为准）；

- 漏斗数据完全无法与服务端记录对账，或被邀请人质量（留存/有效行为）完全未纳入活动评估。
