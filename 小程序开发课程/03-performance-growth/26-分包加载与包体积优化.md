# 26-分包加载与包体积优化

## 目标

完成本知识单元后，学员应能把「逛吃指南」从“所有页面都塞在主包、上传逼近 2MB 红线、启动越来越慢”的状态，改造为“主包精干、业务模块按需加载、首屏秒开、体积可持续守护”的工程形态。重点不是记住几个配置项，而是建立**体积预算意识**：知道每个 KB 进了哪个包、为什么用户要为它等待，以及如何用工具量化每次改动的收益。

学员应能够：

1. 说清小程序包体积限制（主包、单个分包、全量包的上限）及其与启动链路（下载、注入、渲染）的关系。
2. 理解主包、普通分包、独立分包的区别与依赖关系，并能根据「逛吃指南」的访问路径决定模块归属。
3. 在 `app.json` 中正确配置 `subpackages`（root/name/pages/independent），并按分包约束组织目录与公共资源。
4. 掌握分包加载时机：首次进入分包页面时才下载，理解跳转等待、失败处理，以及为什么不能在主包引用分包内容。
5. 配置 `preloadRule` 分包预下载，在合适的页面、合适的网络下提前拉取分包，并理解 `__APP__` 与独立分包预下载主包的用法。
6. 使用独立分包承载营销活动、小程序码落地页等“直达入口”，并处理其不能依赖主包的限制（`getApp({ allowDefault: true })` 等）。
7. 使用 `lazyCodeLoading: requiredComponents` 按需注入，理解代码注入与包体积、启动耗时的区别与联系。
8. 使用分包异步化（`require.async`）与组件占位（`componentPlaceholder`）处理跨分包引用与加载体验。
9. 系统优化资源：图片压缩与格式选择、云存储/CDN 承载大图、字体与图标的加载策略，避免资源占满主包。
10. 清理代码与 npm 依赖（按需引入、废弃代码删除、上传压缩），并用开发者工具的代码依赖分析量化主包下降、输出前后对比报告。

本单元是阶段四「性能与增长」的第二课，承接 U25 的分享落地页（这些页面正是独立分包的典型用户），也为后续 Skyline 渲染与性能量化单元提供干净的工程基线。

## 技术栈

本单元使用微信原生工程配置 + TypeScript，资源走云存储/CDN，包体积分析使用微信开发者工具内置面板。

| 工具或配置 | 用途 | 学习要求 |
|---|---|---|
| app.json → pages | 主包页面声明 | tabBar 页必须在主包 |
| app.json → subpackages | 分包声明 | root/name/pages/independent |
| app.json → preloadRule | 分包预下载 | network、packages、__APP__ |
| independent 字段 | 独立分包 | 直达入口、不依赖主包 |
| lazyCodeLoading | 按需注入 | requiredComponents |

| require.async | 分包异步化 JS | 跨分包异步引用 |
| wx.navigateTo | 跨分包跳转 | 首次触发下载 |
| getApp({allowDefault}) | 独立分包取全局 | 默认对象占位 |
| wx.loadFontFace | 网络字体 | iconfont 不进包 |
| 云存储/CDN | 图片与资源外置 | downloadFile 合法域名 |
| 开发者工具 → 代码依赖分析 | 体积构成分析 | 文件级定位大文件 |
| 开发者工具 → 详情/基本信息 | 主包分包体积 | 建立基线与对比 |

约定：

- 一切体积结论以**真机 + 开发者工具面板的量化数字**为准，不凭感觉判断“应该小了”。
- 分包改造后必须回归所有入口：tabBar、分享卡片、小程序码、扫码、跳转其他小程序的回流，避免“瘦了主包、断了路径”。
- 主包只保留启动与首屏必需内容；判断标准是“新用户首次打开未连任何分包时，产品是否仍可用”。

## 详细的理论知识讲解和示例伪代码

### 1. 包体积为什么是增长的敌人：限制与启动链路

微信对小程序代码包有明确的体积上限（2026 年常规小程序）：

| 项目 | 上限 |
|---|---|
| 主包大小 | 2 MB |
| 单个分包大小 | 2 MB |
| 整个小程序所有包合计 | 20 MB |

不同主体、类目可能有差异化政策（如特定行业的总量放宽），以官方文档与后台提示为准。但**主包 2MB 是所有小程序共同的硬约束**，超过无法上传。

用户点开小程序到看到首页，运行时大致经历：

```text
1. 下载：微信拉取主包（冷启动；已缓存且无更新时跳过）
2. 注入：执行主包 JS、注册 App 与首页 Page/组件
3. 渲染：首页 WXML/WXSS 上屏、首屏数据请求
```

主包越大，弱网下第 1 步越慢（2MB 在移动网络里不是一个可以忽略的数字），第 2 步注入的代码越多，启动 JS 耗时越长。这就是为什么“分包”的核心收益首先是**主包变小、冷启动变快**，其次才是工程上的模块隔离。

分包的本质是：把代码切成多个包，主包必下，其余包**在用户即将用到时才下载**。用户的首次启动只为首屏付费，而不是为整个 App 的全部功能付费。

误区提醒：

- “用户都在 Wi-Fi 下，包大点没事”——Wi-Fi 解决下载，不解决注入耗时；且低端机上几百 KB 多余 JS 的执行代价依然明显。
- 把分包理解成“单纯的目录整理”，没有体积与加载行为的改变就不算分包。

### 2. 主包、普通分包、独立分包：三种包的关系

| 类型 | 是否启动必下 | 能否依赖主包 | 典型内容 |
|---|---|---|---|
| 主包 | 是 | —— | tabBar 页面、登录、全局 store、首屏公共组件 |
| 普通分包 | 否，进入时下载 | 能（JS、组件、资源） | 活动模块、发布编辑器、个人中心、设置 |
| 独立分包 | 否，可作为直达入口单独运行 | 否（运行时不保证主包存在） | 大促页、邀请落地页、广告投放页 |

依赖方向的规则：

- 普通分包**可以**引用主包的 JS、自定义组件、样式资源（主包保证已在本地）。
- 主包**不能**引用任何分包内容（构建期就会报错，因为启动时分包不在本地）。
- 分包 A 不应直接 require 分包 B 的文件（B 未必已下载）；确有需要时用分包异步化（第 7 节），或把公共部分收回主包。
- tabBar 配置的页面**必须在主包**，这是最常见的改造红线。

「逛吃指南」的模块归属决策：

```text
主包：首页信息流、笔记详情（分享主入口）、登录引导、全局组件
普通分包 packageActivities：活动列表、活动详情、报名结果
普通分包 packagePublish：发布编辑器、拍照滤镜、地点选择
普通分包 packageProfile：个人主页、设置、我的收藏、消息中心
独立分包 packageLanding：邀请有礼落地页（小程序码/广告直达）
```

误区提醒：

- 按“文件大小”拆包（把最大的几个页面扔走），正确依据是**访问路径与首屏必要性**。
- 把公共组件放进某个分包，又被多个分包引用，造成跨分包依赖与重复打包。

### 3. app.json 分包配置与目录组织

分包在 `app.json` 中声明，每个分包由 `root`（目录前缀）、`pages`（相对 root 的页面列表）、可选 `name`（预下载时可用名）、`independent` 组成。

```json
{
  "pages": [
    "pages/home/home",
    "pages/note-detail/note-detail",
    "pages/login/login"
  ],
  "subpackages": [
    {
      "root": "packageActivities",
      "name": "activities",
      "pages": [
        "pages/list/list",
        "pages/detail/detail",
        "pages/result/result"
      ]
    },
    {
      "root": "packagePublish",
      "name": "publish",
      "pages": [
        "pages/editor/editor",
        "pages/location/location"
      ]
    },
    {
      "root": "packageProfile",
      "name": "profile",
      "pages": [
        "pages/me/me",
        "pages/settings/settings",
        "pages/messages/messages"
      ]
    },
    {
      "root": "packageLanding",
      "name": "landing",
      "pages": ["pages/invite/invite"],
      "independent": true
    }
  ],
  "window": {
    "navigationBarTitleText": "逛吃指南"
  }
}
```

对应的物理目录（root 是一个真实目录）：

```text
miniprogram/
├── app.json
├── app.ts
├── app.wxss
├── pages/                    # 主包页面
│   ├── home/
│   ├── note-detail/
│   └── login/
├── components/               # 主包公共组件
├── packageActivities/        # 分包：root 即目录
│   └── pages/...
├── packagePublish/
├── packageProfile/
└── packageLanding/
```

目录组织三条经验：

1. 分包内资源（图片、分包专用组件）放在各自 root 下，保证“这个页面的一切都在这个包里”，不要散落在主包目录再跨包引用。
2. 被多个分包共用的组件/工具放主包 `components/`、`utils/`；若体积大且只在分包用，用分包异步化而不是复制两份。
3. 迁移页面时连带改路径引用：相对路径、自定义组件的 `usingComponents`、TS 的路径别名、跳转 URL 都要同步。

误区提醒：

- 配置了 `subpackages` 但文件还在主包目录，实际没有任何体积移动。
- root 目录下混入被主包页面引用的文件，构建期报主包依赖分包错误。
- 页面路径在跳转处仍写旧路径，分包后 404。

### 4. 分包加载时机与跨分包跳转

普通分包对用户透明：代码里照常 `wx.navigateTo` 到分包页面，微信发现该包不在本地时，**先下载并注入分包，再打开页面**。

```typescript
// 首页点击“周末活动”
wx.navigateTo({
  url: '/packageActivities/pages/list/list',
  success() {
    // 分包已就绪且页面入栈
  },
  fail(err) {
    // 下载失败、取消、路径错误都会走到这里
    wx.showToast({ title: '加载失败，请重试', icon: 'none' })
  },
})
```

首次点击分包入口时，下载期间微信会展示系统级加载提示。若分包较大且网络差，用户会明显感觉“点了没反应”。工程对策有三类：

1. **入口前置预下载**（第 6 节 preloadRule），让用户点击前包已就位；
2. **控制分包体积**，单包尽量远小于 2MB，目标建议 500KB 以内；
3. **入口处给即时反馈**，点击立刻出现本地 loading 态，不要让用户怀疑没点上。

分包一旦下载即缓存，之后进入同一分包不再重复下载；版本更新时随小程序版本管理机制整体更新。

误区提醒：

- 在首页 `onLoad` 就连续跳分包大页做“预热”，反而拖慢首屏并浪费流量。
- 假设分包一定下载成功，不处理 `fail`——弱网下用户可能永远卡在入口。
- 分包页面里再 `navigateTo` 主包页面是允许的（普通分包场景主包本就在），但独立分包场景会触发主包下载（见第 5 节）。

### 5. 独立分包：不依赖主包的直达入口

`independent: true` 的分包是独立分包，用户可以**不经主包直接进入**（典型：扫小程序码打开邀请落地页、广告点击直达）。此时主包可能尚未下载，因此独立分包受到一系列约束：

- 不能 `require` 主包的 JS 文件，不能依赖主包资源；
- `app.wxss`（全局样式）不会作用到独立分包页面，样式需自包含；
- 主包 `App()` 未注册时，`getApp()` 可能返回 `undefined`；需要全局对象时使用 `getApp({ allowDefault: true })`，平台会返回一个默认占位对象，待主包加载后自动并入真实 App；
- 插件等能力在独立分包中的支持有专门限制，以文档为准。

U25 的邀请落地页就是独立分包的标准场景：流量大、链路短、要求秒开，且它本身就是入口，不该先拖一个 1MB 主包。

```typescript
// packageLanding/pages/invite/invite.ts
const app = getApp<{ globalData: { theme: string } }>({ allowDefault: true })

Page({
  data: { inviterCode: '', theme: 'light' },

  onLoad(options: Record<string, string>) {
    const inviterCode = options.i ?? ''
    this.setData({ inviterCode })
    // 样式、文案、逻辑全部自包含，不引用主包 store
    wx.reportEvent?.('landing_view')
  },

  onGoHome() {
    // 用户想进首页时，跳转主包页面会触发主包下载，之后成为完整小程序
    wx.switchTab({ url: '/pages/home/home' })
  },
})
```

独立分包适合放：营销大促页、邀请/助力页、活动报名单页、客服引导页。不适合放需要完整用户体系与多层导航的复杂模块。

误区提醒：

- 把独立分包当普通分包用，代码里大量引用主包组件/工具，直达时白屏报错。
- 依赖全局样式却不引入，进入后样式全丢。
- 在独立分包中强拿 `getApp()` 不做空值处理，`undefined.globalData` 直接崩溃。

### 6. preloadRule：在空闲时把分包提前下好

`preloadRule` 按“进入某个页面”为触发条件，在指定网络下预下载指定分包，把用户点击分包入口时的等待消灭在前置浏览过程中。

```json
{
  "preloadRule": {
    "pages/home/home": {
      "network": "all",
      "packages": ["activities"]
    },
    "pages/note-detail/note-detail": {
      "network": "wifi",
      "packages": ["publish", "profile"]
    },
    "packageLanding/pages/invite/invite": {
      "network": "all",
      "packages": ["__APP__"]
    }
  }
}
```

字段含义：

- key：触发页面路径（用户进入该页面即评估规则）；
- `network`：`all` 不限网络，`wifi` 仅 Wi-Fi；
- `packages`：要预下载的分包，可写分包的 `name` 或 `root`；`__APP__` 表示主包。

配置策略（「逛吃指南」）：

1. 首页曝光时预下载活动分包——首页浏览与活动点击是连贯路径，用户点“活动”时包已在本地，且 `network: all` 保证移动网络也生效（包小才敢这么配）。
2. 笔记详情页在 Wi-Fi 下预下载发布与个人中心——这两个分包不是下一跳的确定路径，只在 Wi-Fi 空闲时下载。
3. 独立落地页预下载 `__APP__` 主包：用户从邀请页点“去首页”之前，主包已在后台备好，独立分包回流主包不再卡顿。

同一个分包被多次规则命中时系统只下载一次；预下载的总体积、并发数受平台约束，以官方文档为准。

误区提醒：

- 在首页把所有分包都 `all` 预下载——主包瘦身省下的流量一次还回去，冷启动后立刻抢带宽，首屏数据请求都被拖累。
- 预下载规则的页面 key 写错（与 app.json 页面路径不完全一致），规则静默不生效。
- 不管分包大小一律移动网络预下，用户感知到“这个小程序偷跑流量”。

### 7. 分包异步化与组件占位

跨分包引用默认不允许（被引用包可能没下载）。分包异步化提供两种受控方式。

JS 异步引用：

```typescript
// packageActivities/pages/detail/detail.ts
async function openSharePoster() {
  // publish 分包可能未下载，require.async 会在需要时触发下载并返回模块
  const posterMod = await require.async(
    '../../packagePublish/utils/poster'
  )
  const tempPath = await posterMod.drawActivityPoster(this.data.activity)
  wx.previewImage({ urls: [tempPath] })
}
```

组件占位：某分包组件被当前页面使用时，先显示主包中的轻量占位组件，分包下载完成后替换。页面 json：

```json
{
  "usingComponents": {
    "heavy-editor": "/packagePublish/components/editor/editor",
    "editor-placeholder": "/components/editor-placeholder/editor-placeholder"
  },
  "componentPlaceholder": {
    "heavy-editor": "editor-placeholder"
  }
}
```

```xml
<!-- 分包未就绪期间渲染 editor-placeholder，就绪后自动替换为 heavy-editor -->
<heavy-editor activity-id="{{id}}" />
```

分包插件也支持异步声明，让使用分包插件的页面不被插件下载阻塞。

误区提醒：

- 滥用异步化：若两个分包几乎总是同时使用（如活动详情必然用发布工具），应考虑合并分包或直接预下载，而不是引入大量 loading 态。
- 占位组件与真实组件的 props/事件差异过大，替换后行为突变；占位组件应对齐真实组件的最小接口。

### 8. lazyCodeLoading：按需注入

分包解决“下载什么”，`lazyCodeLoading` 解决“注入执行什么”。在 `app.json` 开启：

```json
{
  "lazyCodeLoading": "requiredComponents"
}
```

开启后，基础库按页面/组件实际声明和使用情况**按需注入**未被引用的组件与代码，而不是在启动时把主包内所有组件代码全部执行。对组件多、自定义组件体系重的项目，启动注入耗时会明显下降。

它和分包的关系要分清：

| 手段 | 作用阶段 | 直接收益 |
|---|---|---|
| 分包 | 下载阶段 | 主包体积变小，下载变快 |
| lazyCodeLoading | 注入阶段 | 启动时执行的代码变少，注入变快 |
| preloadRule | 下载阶段（提前） | 点击分包入口无等待 |

三者通常同时使用、互不替代。

注意事项：

- 按需注入要求代码符合规范（避免在全局顶层执行有副作用的注册逻辑、避免动态拼路径使用组件让静态分析找不到）。
- 开启后要全量回归自定义组件渲染，少数依赖“所有组件均已注册”这一隐式假设的写法会暴露问题。

误区提醒：

- 以为开了按需注入就能缩小包体积——包内文件还在，体积数字不变，变的是启动执行量。
- 开启后不做回归，动态使用组件的页面出现组件未注入。

### 9. 主包瘦身方法论：拆什么、留什么

面对一个膨胀的主包，按下面的顺序决策，而不是上来就挪文件：

1. **画访问路径**：新用户冷启动后，第一屏是什么？前三次典型点击去哪里？这些路径上的页面与组件留主包。
2. **识别 tabBar 硬约束**：tabBar 页面必须留，围绕它们的首屏依赖也留。
3. **按“功能域”而非“单页面”划包**：同一功能域的页面、专用组件、资源放进同一分包，避免跨包网状依赖。
4. **处理公共依赖**：被 3 个以上分包共用的内容回主包；只被 1~2 个分包共用的重组件，考虑分包异步化或下沉到其中一个分包。
5. **识别直达流量**：来自小程序码、广告、短信的落地页优先评估独立分包。

「逛吃指南」的一次典型拆分结果（示意数字）：

| 模块 | 拆分前位置 | 拆分后 | 主要理由 |
|---|---|---|---|
| 首页信息流、笔记详情 | 主包 | 主包 | 首屏与分享主入口 |
| 活动列表/详情/结果 | 主包 | packageActivities | 非首屏确定路径，可预下载 |
| 发布编辑器/地点 | 主包 | packagePublish | 重逻辑、低频、按需使用 |
| 个人主页/设置/消息 | 主包 | packageProfile | tabBar“我的”若存在则相关页需评估，注意 tabBar 约束 |
| 邀请落地页 | 主包 | packageLanding（独立） | 小程序码直达，要求秒开 |

误区提醒：

- “我的”是 tabBar 时把它整体扔进分包——违规。做法是 tabBar 页面留主包，其二级页面（设置、消息、收藏）进分包。
- 为了主包数字好看，把首屏必需组件挪走，冷启动首页反而要等分包，本末倒置。

### 10. 图片与媒体资源优化

图片往往是主包里最大的体积来源。优化按“能不进包就不进包、必须进包就压到最小”执行。

**外置到云存储/CDN**：运营图、活动 banner、默认大图、引导插画全部走网络（云存储或 CDN），不占代码包：

```xml
<image src="{{coverUrl}}" mode="aspectFill" lazy-load />
```

使用网络图片注意：`wx.downloadFile`/`<image>` 涉及的域名要配置在 downloadFile 合法域名中（云存储域名一般已内置支持）；图片 URL 建议带版本号，更新时换 URL 避开缓存。

**必须进包的图（如首屏骨架、分享默认图）压缩处理**：

- 先用工具（TinyPNG 类）无损/有损压缩，再按实际显示尺寸导出，不要把 750px 的位置放 2000px 的图；
- 选择合适格式：色彩简单的图标用 PNG，照片类考虑 WebP（体积更小，现代基础库与设备支持良好），避免在包里放大 GIF；
- 小图标用 iconfont 字体或合图，字体通过网络加载：

```typescript
wx.loadFontFace({
  family: 'GC-Icons',
  source: 'url("https://cdn.guangchi.example.com/fonts/gc-icons.woff2")',
  global: true,
})
```

网络字体同样不占包；避免把字体 base64 进 WXSS（会直接撑大样式文件）。

**数据类资源外置**：城市列表、POI 词典等大 JSON 不应进包，改为接口或云函数按城市返回。

误区提醒：

- 为“省事”把切图原图全部丢进 `images/`，一个 banner 顶半个分包。
- 网络图片不做尺寸约束，`mode` 用错导致拉伸或下载超大图。
- 同一图标在不同分包各放一份 PNG，总体积叠加。

### 11. 组件、npm 依赖与代码清理

包体积是“留在包里的每个文件”之和，代码清理同样有实打实的收益。

npm 依赖：

- 使用“小程序 npm 构建”后，检查构建产物里是否打进了整个大型库。例如 `import _ from 'lodash'` 会带入全部方法，应改为按需引入（lodash 的 per-method 包或支持 tree-shaking 的等价方案）；
- 时间库、UI 工具库优先选支持 ESM/tree-shaking 的版本，避免 moment 这类会把全部语言包打进来的依赖；
- 卸载 `package.json` 中已经不用的依赖并重新构建，构建产物目录（`miniprogram_npm`）会同步变小。

代码与文件清理：

- 删除已下线页面、废弃组件、注释掉的大段代码、调试用的 mock JSON；
- 合并重复实现（多个分包各写一份日期格式化工具），公共工具收敛到主包 `utils/`；
- 保持上传/预览时的压缩开关开启（JS 混淆压缩、WXSS、WXML 压缩），本地调试代码与上线产物体积可能差很多，体积评估应以压缩后产物为准。

普通小程序 JS 多为 CommonJS，构建期 tree-shaking 能力有限，这决定了“按需引入”主要靠开发者手动保证，而不是指望构建器自动删干净。

误区提醒：

- 只删源码不重新构建 npm，`miniprogram_npm` 里旧产物仍被打包。
- 以为“代码没几行不占体积”，source map（若误入产物）、内嵌 base64、重复模板都可能成为大头。
- 为了几处工具方法引入一个数百 KB 的通用库。

### 12. 用开发者工具量化包体积

“优化”必须闭环到数字。微信开发者工具提供几处关键面板：

1. **详情 → 基本信息**：显示本地代码主包/各分包大小（上传后还会显示服务端构建产物大小），这是建立基线的地方。
2. **代码依赖分析**（工具菜单）：以树形结构列出每个包内文件的体积占比，能直接定位“哪个组件、哪张图、哪个 npm 包最大”，并展示文件间依赖关系，帮助判断某文件能否挪出主包。
3. **上传时的依赖分析与压缩提示**：上传弹窗会展示包体积与超限/预警，确认压缩选项。
4. **体验评分/Audits**：给出启动与加载维度的评估，辅助验证优化对性能的实际影响。

建立量化表（数字仅为格式示例，以实测为准）：

| 指标 | 优化前 | 优化后 | 变化 |
|---|---:|---:|---:|
| 主包体积 | 1980 KB | 860 KB | -56.6% |
| activities 分包 | —— | 320 KB | 新增 |
| publish 分包 | —— | 410 KB | 新增 |
| profile 分包 | —— | 260 KB | 新增 |
| landing 独立分包 | —— | 90 KB | 新增 |
| 首屏可交互（弱网实测） | 3.8 s | 1.9 s | -50% |

量化时的纪律：

- 优化前先截图/记录基线，否则无法证明收益；
- 主包体积看“压缩上传后”的产物口径，前后口径要一致；
- 文件级分析要落实到具体动作（“components/editor 目录 180KB → 移入 publish 分包”），而不是一句“做了优化”。

误区提醒：

- 只看总包大小下降，主包却没变化——冷启动收益为零。
- 优化后只在开发者工具看一眼，不做真机弱网实测。

### 13. 分包实战：逛吃指南模块拆分全流程

把前面的方法串成一次可执行的改造，推荐在独立分支进行：

```text
步骤 1 建基线
  - 记录主包/各页面体积，截图代码依赖分析；列出全部跳转路径与入口

步骤 2 建目录
  - 创建 packageActivities/packagePublish/packageProfile/packageLanding
  - 移动页面、分包专用组件与图片到对应 root

步骤 3 改配置
  - app.json 删除主包旧页面路径，写入 subpackages
  - 迁移 tabBar 相关页面时逐页核对（tabBar 页留主包）

步骤 4 修引用
  - 页面内相对路径、usingComponents、TS 路径别名
  - 全局 wx.navigateTo/switchTab/redirectTo 的 URL
  - 分包内不再 require 主包以外的分包（改 require.async）

步骤 5 配预下载与注入
  - preloadRule：首页 → activities(all)；详情页 → publish/profile(wifi)；落地页 → __APP__
  - 开启 lazyCodeLoading；需要的异步组件配 componentPlaceholder

步骤 6 真机回归
  - 冷启动首页、四个分包首次进入、分享卡片进入、小程序码进入
  - 独立落地页直达与回流主包、分包下载失败（切弱网/断网点）重试

步骤 7 出报告
  - 优化前后体积对比、首屏耗时对比、遗留风险
```

常见报错与处理：

| 现象 | 原因 | 处理 |
|---|---|---|
| 主包依赖分包文件，构建失败 | 主包页面引用了已移走的文件 | 公共文件收回主包，或该页面随文件一起进分包 |
| 跳转报页面不存在 | 旧 URL 未更新 | 全局替换为 `/root/pages/...` 新路径 |
| 独立分包样式丢失 | 依赖了 app.wxss | 样式复制/引入到分包内 |
| 预下载不生效 | key 路径与实际不完全一致 | 严格对齐 app.json 页面路径 |
| 分包组件首次打开闪一下占位 | 占位与真实组件差异 | 对齐接口、必要时改为预下载 |

误区提醒：

- 一口气移动全部模块再调试，出错时无法定位；应一个分包一个分包地迁、每迁一个就回归。
- 改完只测主流程，分享/扫码/通知跳转等“深链接入口”全部漏掉——这些恰恰是小程序最高频的入口。

### 14. 持续守护：体积预算与迭代防反弹

体积优化不是一次性项目：每个迭代都有新图片、新组件、新依赖，主包会悄悄反弹。需要建立轻量的守护机制。

**体积预算**：

```text
主包预算：1.5 MB 预警，1.8 MB 阻断评审（硬上限 2 MB）
单分包预算：500 KB 预警
新增网络外资源（进包图片）：需说明首屏必要性
新增 npm 依赖：评估体积（构建后增量），优先按需方案
```

**迭代检查动作**：

- 提测前跑一次代码依赖分析，与上次发布对比主包增量，超过约定阈值（如 +50KB）要说明原因；
- Code Review 关注三类问题：图片是否可外置、依赖是否按需引入、是否在主包引用分包；
- 大版本发布后复查真实下载/启动数据，确认面板结论与线上一致。

**自动化思路**（进阶）：可用脚本扫描仓库内图片体积与资源目录、解析 app.json 校验规则完整性（如 preloadRule key 是否合法、tabBar 页面是否误进分包），把检查挂到提交或流水线中；平台也提供 CI 相关能力用于命令行预览/上传后读取产物信息。

误区提醒：

- 验收当周数据漂亮，一个季度后主包又贴着 2MB——没有预算与回归机制，反弹是必然。
- 把预算定得太粗（“不超 2MB 就行”），失去提前预警的意义。
- 只守主包不守分包，单个分包超限同样无法上传。

### 完成标准

- 主包从接近上限降至 1.5MB 以下（以工具面板/上传产物为准），各分包功能完整；
- 首页冷启动与弱网首屏耗时量化下降，普通分包首次进入有反馈、预下载路径无等待；
- 独立分包可脱离主包直达并正常回流，样式与全局对象处理正确；
- 所有历史入口（分享卡片、朋友圈、小程序码、扫码、通知跳转）回归通过；

### 强制不通过条件

- 主包体积未实质下降（降幅 <35% 或仍高于 1.5MB），或只移动目录而产物中主包仍包含这些文件；
- tabBar 页面被放入分包，或构建出现主包依赖分包文件的错误且未解决；
- 分包改造后任一历史入口（分享、朋友圈、小程序码、扫码、通知）打不开或页面异常；
- 独立分包仍 require 主包代码/依赖 app.wxss，脱离主包直达时崩溃；
- 优化结论没有工具面板与真机数据支撑，前后口径不一致、无法复核；
- npm 改动后未重新构建，或压缩/按需引入仅停留在口头，产物无变化；
- 只做一次性清理，没有任何体积预算或迭代守护措施。
