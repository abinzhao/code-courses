# 27-运行时性能优化

## 目标

完成本知识单元后，学员应能以“可测量、可复现、可对比”的工程方式治理小程序运行时性能，而不是把性能优化理解为背诵几条 setData 军规。

学员应能够：

1. 建立“先量化、后优化、再对比”的性能工程闭环，所有结论都有数据证据，拒绝“我觉得变快了”。
2. 再探 `setData` 的三段成本：数据序列化与跨线程传输、渲染层 diff、布局与绘制，并能根据数据规模与更新频率估算单次交互代价。
3. 熟练使用路径更新（字符串路径与计算键）精确更新嵌套对象字段与数组项，把一次点赞的通信量从“整份列表”压缩到“两个叶子字段”。
4. 设计合并更新调度器，把同一时间片内的高频小更新收敛为一次 `setData` 通信，并正确处理回调聚合与异步竞态。
5. 掌握自定义组件纯数据字段 `options.pureDataPattern`，说清纯数据只存在于逻辑层、不进入渲染层，并能在 `observers` 中使用。
6. 在页面 `data`、组件纯数据字段、组件/页面实例属性三类状态位置之间做出正确决策，杜绝句柄与缓存污染 `data`。
7. 使用 WXS 响应事件把滚动、拖拽类高频交互闭环在渲染层，并量化其减少的跨线程通信次数。
8. 使用 `wx.createSelectorQuery` 与 `IntersectionObserver` 完成节点测量、滚动位置查询、曝光统计与懒加载触发，牢记逻辑层没有 DOM、节点信息只能异步查询。
9. 手写节流（throttle）与防抖（debounce）并按场景选型；掌握图片懒加载、分页加载与 WebView 模式下的长列表渲染策略。
10. 识别定时器、事件监听、全局引用与页面栈导致的内存泄漏；使用性能面板、真机调试与 `wx.getPerformance` 采集启动耗时、setData 通信量与帧率，产出优化前后量化报告。

本单元不引入新的云服务或第三方框架，全部能力来自微信原生框架与开发者工具；业务代码继续使用 TypeScript。

## 详细的理论知识讲解和示例伪代码

### 1. 性能优化的第一原则：用证据说话

性能优化最常见的失败模式不是“不会优化”，而是：改了一堆代码，没人说得清到底快了多少、瓶颈原来在哪、有没有改出新问题。因此本单元把方法论放在第一条。

小程序运行时性能关注四类指标：

| 指标类别 | 典型度量 | 回答的问题 |
|---|---|---|
| 启动性能 | 冷启动到首帧、到首屏可交互的耗时 | 用户多久能看到并操作内容 |
| 通信性能 | `setData` 次数、单次/累计数据字节数 | 跨线程传了多少、传了多频繁 |
| 渲染性能 | 滚动/动画平均帧率（FPS）、P95 帧时长 | 交互是否流畅、掉帧多严重 |
| 内存性能 | 页面驻留内存、重复进出的内存曲线、内存告警 | 有没有泄漏、会不会被杀后台 |

标准流程是一个闭环：

```text
1. 建立基线：录制当前页面的启动、通信、帧率、内存数据
2. 定位瓶颈：从 Trace 中找出占比最高的那段（而不是猜）
3. 提出假设：例如“点赞卡顿主要来自整份列表序列化”
4. 单点改动：一次只改一处，保证归因清晰
5. 同路径复测：用完全相同的操作再录一次
6. 沉淀台账：记录指标、机型、基础库版本、结论
```

性能台账模板：

| 指标 | 优化前 | 优化后 | 变化幅度 | 采集方式 |
|---|---|---|---|---|
| 冷启动到首屏可交互 | 2180ms | 1320ms | -39% | 真机 Trace，3 次中位数 |
| 单次点赞通信量 | 12.4KB | 0.3KB | -97% | 序列化字节估算 |
| 首屏 setData 次数 | 14 次 | 5 次 | -64% | 计数埋点 |
| 快速滑动平均帧率 | 42fps | 58fps | +38% | 真机帧率浮窗 |
| 进出 10 次后内存 | 268MB | 171MB | -36% | 开发者工具内存曲线 |

常见误区：

- 只在模拟器测量：电脑 CPU 与真机芯片、屏幕刷新率完全不同，模拟器数据不能验收。
- 只测一次：单次结果受后台活动、网络抖动影响，至少 3 次并看中位数。
- 没有基线就先改：改完无法回答“提升了多少”，等于白做。

### 2. 再探 setData：把成本拆成三段

U02 讲过 `setData` 会触发跨线程同步。这里进一步把成本拆开，因为“减小数据量”和“降低频率”优化的并不是同一段。

```text
逻辑层：
  ① 合并数据到 this.data
  ② 将更新对象序列化为消息（与数据量成正比）
  ③ 经 Native 桥跨线程发送（消息要排队）
渲染层：
  ④ 反序列化消息
  ⑤ 在组件树上做 diff（与受影响节点数正相关）
  ⑥ 重新布局 Layout 与绘制 Paint（结构/几何变化更贵）
```

可以用一个近似关系帮助直觉：

```text
单次 setData 成本 ≈ A × 传输数据量 + B × 受影响节点数 + C × 是否触发重排
一段时间的总成本 ≈ 单次成本 × 调用次数
```

这解释了两类反模式为什么都危险：

- 数据量大但低频：一次全量同步一个 50KB 的列表，②③⑤都贵。
- 数据量小但高频：touchmove 每帧一次，即使每次只有 1KB，每秒也有 60~120 次跨线程消息，桥的排队开销会主导体验。

用 TypeScript 直观估算一次更新的字节量：

```typescript
// pages/perf/perf.ts
interface NoteItem {
  id: number
  title: string
  liked: boolean
  likeCount: number
}

function payloadBytes(data: unknown): number {
  // 近似估算：序列化后的 UTF-16 代码单元数，真实字节以 UTF-8 为准
  return JSON.stringify(data).length
}

Page({
  data: {
    list: [
      { id: 1, title: '巷子里的小面馆', liked: false, likeCount: 12 },
      { id: 2, title: '江边落日咖啡馆', liked: false, likeCount: 8 }
    ] as NoteItem[]
  },

  comparePayload() {
    const list = this.data.list.map((item) =>
      item.id === 1 ? { ...item, liked: true, likeCount: 13 } : item
    )

    // 反模式：整份列表重发
    const full = { list }
    console.log('全量更新约', payloadBytes(full), '字符')

    // 正确：只发两个叶子字段
    const patch = {
      'list[0].liked': true,
      'list[0].likeCount': 13
    }
    console.log('路径更新约', payloadBytes(patch), '字符')
  }
})
```

常见误区：

- 以为“数据小就没成本”：高频调用下，消息排队与线程切换才是大头。
- 把 callback 的完成时间等同于“用户看到了新画面”：callback 表示渲染层已完成本次数据处理与更新调度，复杂合成仍可能在随后的时间片完成。
- 传函数、Symbol 等不可序列化内容：它们无法跨线程，可能被丢弃或报错。

### 3. 路径更新：只传变化的叶子节点

路径更新允许用“数据路径字符串”精确定位到对象嵌套字段或数组下标，框架只把路径末端的值序列化发送。

三种典型写法：

```typescript
Page({
  data: {
    list: [
      { id: 1, liked: false, likeCount: 10, tags: ['面馆'] },
      { id: 2, liked: false, likeCount: 5, tags: ['咖啡'] }
    ],
    shop: { name: '巷子里的小面馆', coupon: { received: false } }
  },

  // ① 更新数组某项的多个字段：计算键（ES2015）
  onLike(index: number) {
    const next = this.data.list[index].likeCount + 1
    this.setData({
      [`list[${index}].liked`]: true,
      [`list[${index}].likeCount`]: next
    })
  },

  // ② 更新深层嵌套对象字段：字符串字面量路径
  onReceiveCoupon() {
    this.setData({ 'shop.coupon.received': true })
  },

  // ③ 在数组尾部追加一项：下标即当前长度
  onAppend(item: NoteItem) {
    this.setData({
      [`list[${this.data.list.length}]`]: item
    })
  }
})
```

路径语法规则：

- 对象字段用点号：`shop.coupon.received`；
- 数组下标用方括号：`list[0].likeCount`；
- 路径可以作为对象 key，用计算键语法 `[`list[${i}].liked`]` 动态拼接；
- 一次 `setData` 可以带多条路径，它们仍只产生一次通信。

常见误区：

- 路径指向不存在的位置：框架会尝试沿路径创建结构；给数组设置越界下标（如长度为 2 时写 `list[5]`）会产生稀疏数组（空洞项），`wx:for` 与后续路径更新都可能异常。追加请用“当前长度”作为下标。
- 把变量直接拼进字符串却忘记类型转换：模板字符串会自动转，但手写 `'list[' + i + '].liked'` 时要确保 `i` 是有限数字。
- 路径更新与全量更新混用但仍期待通信量小：通信量由本次所有 key 的并集决定。

### 4. 合并更新：把高频小更新收敛成一次通信

同一同步执行流中连续多次调用 `setData`，会产生多条跨线程消息。可以用一个“脏检查 + 时间片刷新”的调度器，把一批小更新合并。

```typescript
// utils/batch-updater.ts
type Patch = Record<string, unknown>

interface SetDataTarget {
  setData: (patch: Patch, callback?: () => void) => void
}

class BatchUpdater {
  private pending: Patch = {}
  private scheduled = false

  constructor(private target: SetDataTarget) {}

  // 业务侧调用它，而不是直接 setData
  set(path: string, value: unknown): void {
    this.pending[path] = value
    if (!this.scheduled) {
      this.scheduled = true
      // 放到下一个时间片：本时间片内的所有 set 都会被收集
      wx.nextTick(() => this.flush())
    }
  }

  private flush(): void {
    const patch = this.pending
    this.pending = {}
    this.scheduled = false
    this.target.setData(patch)
  }
}
```

在页面中使用：

```typescript
import { BatchUpdater } from '../../utils/batch-updater'

Page({
  data: {
    list: [
      { id: 1, progress: 0 },
      { id: 2, progress: 0 }
    ]
  },

  onLoad() {
    this.batcher = new BatchUpdater(this)
  },

  // 哪怕一个循环里更新 100 个字段，最终只发一次
  onBatchProgress(updates: Array<{ index: number; progress: number }>) {
    updates.forEach(({ index, progress }) => {
      this.batcher.set(`list[${index}].progress`, progress)
    })
  }
})
```

轻量场景也可以不写类，直接在页面内收集：

```typescript
Page({
  pending: {} as Record<string, unknown>,
  scheduled: false,

  scheduleSet(path: string, value: unknown) {
    this.pending[path] = value
    if (!this.scheduled) {
      this.scheduled = true
      wx.nextTick(() => {
        const patch = this.pending
        this.pending = {}
        this.scheduled = false
        this.setData(patch)
      })
    }
  }
})
```

异步竞态注意：多个请求的返回合并更新时，旧请求可能晚于新请求返回。需要给请求加序号，过期结果不得再写入：

```typescript
private requestSeq = 0

fetchList(keyword: string) {
  const seq = ++this.requestSeq
  wx.request({
    url: 'https://api.example.com/notes',
    data: { keyword },
    success: (res) => {
      if (seq !== this.requestSeq) return // 过期响应，丢弃
      this.scheduleSet('list', res.data)
    }
  })
}
```

常见误区：

- 依赖“每次 setData 的独立 callback”做计时：合并后只有一次 callback，计时口径要一起改。
- 误以为所有时间点的调用都能合并：`wx.nextTick` 之后到达的更新自然进入下一批，这是正常现象。
- 合并了请求结果却没做竞态保护：旧数据覆盖新数据。

### 5. 纯数据字段：options.pureDataPattern

有些数据逻辑层确实需要（要参与计算、要被监听变化），但它们永远不会出现在界面上。把它们放进普通 `data`，每次相关更新仍会被序列化发往渲染层，纯属浪费。自定义组件提供了**纯数据字段**机制解决这个问题。

```typescript
// components/note-filter/note-filter.ts
interface Filters {
  city: string
  category: string
  maxPriceCents: number
}

Component({
  options: {
    // 所有字段名匹配该正则的 data 字段都是纯数据字段
    pureDataPattern: /^_/
  },

  data: {
    _filters: { city: 'shanghai', category: 'noodle', maxPriceCents: 20000 } as Filters,
    resultCount: 0 // 普通字段：参与渲染
  },

  observers: {
    // 纯数据字段同样可以被 observers 精确监听
    _filters(filters: Filters) {
      const count = this.countByFilters(filters)
      this.setData({ resultCount: count })
    }
  },

  methods: {
    onCityChange(city: string) {
      const next = { ...this.data._filters, city }
      // 只更新纯数据字段：不向渲染层发送它
      this.setData({ _filters: next })
    },
    countByFilters(filters: Filters): number {
      return 42 // 示例：真实项目按全量数据计算
    }
  }
})
```

纯数据字段的关键事实：

- 它仍然是 `this.data` 的成员，逻辑层可正常读写；
- 它的变化可以触发 `observers`，因此适合“需要响应式管理但不渲染”的数据；
- 它不会被发送到渲染层，模板无法获得它的真实值；
- 适合承载：复杂筛选条件、列表原始备份、定时器计数、编辑草稿等。

常见误区：

- 在 WXML 中引用纯数据字段：渲染层拿不到，引用不会按预期更新。
- 正则匹配过宽：例如 `/^[a-z]/` 会把所有小写字段都变成纯数据，渲染字段集体失效。建议统一用固定前缀（如 `_`）。
- 在 `Page` 构造器上找 `pureDataPattern`：该选项属于 `Component`。页面确有需要时，可把页面实现为组件，或直接使用实例属性（见下一节）。

### 6. data 之外：逻辑层状态的正确存放位置

小程序里“状态”有三个合法位置，选择依据是“谁需要它”。

| 数据性质 | 存放位置 | 例子 |
|---|---|---|
| 需要渲染到界面 | 页面/组件 `data` | 标题、列表、点赞态 |
| 逻辑层需要、希望被 observers 管理 | 纯数据字段 | 筛选条件、原始数据备份 |
| 只在逻辑层使用、与渲染无关 | 实例属性 | 定时器句柄、请求序号、缓存、调度器实例 |

TypeScript 示例：

```typescript
Page({
  // 实例属性：声明在 Page 配置对象上，不进 data、不跨线程
  timer: null as ReturnType<typeof setInterval> | null,
  requestSeq: 0,
  batcher: null as BatchUpdater | null,

  data: {
    keyword: '',
    now: Date.now()
  },

  onLoad() {
    this.batcher = new BatchUpdater(this)
    this.timer = setInterval(() => {
      // 仅当界面确实需要显示时间时才 setData
      this.batcher?.set('now', Date.now())
    }, 30000)
  },

  onUnload() {
    if (this.timer) {
      clearInterval(this.timer)
      this.timer = null
    }
  }
})
```

判断口诀：**“界面看得见的进 data；要被观察的进纯数据；其余挂实例。”**

常见误区：把定时器 id、大段字典缓存、请求回调对象塞进 `data` 图省事——它们每次随渲染数据一起维护，增加无意义的序列化与 diff 负担。

### 7. WXS 响应事件：高频交互的渲染层闭环

U06 已学习 WXS 响应事件，这里从“通信量”角度再算一次账。触摸移动在真机上每秒可触发 60~120 次；如果每次都“渲染层 → 逻辑层（事件）→ 渲染层（setData）”，一帧要完成两个跨线程往返，手指必然追不上画面。

需求：笔记卡片左滑露出“不感兴趣”操作按钮。

```javascript
// wxs/swipe.wxs
var ACTION_WIDTH = 160
var SNAP = 80

function onTouchStart(event, ownerInstance) {
  var touch = event.touches[0]
  this.startX = touch.clientX
  var state = ownerInstance.getState()
  this.baseX = state && typeof state.x === 'number' ? state.x : 0
}

function onTouchMove(event, ownerInstance) {
  var dx = event.touches[0].clientX - this.startX
  var x = this.baseX + dx
  if (x > 0) {
    x = 0
  }
  if (x < -ACTION_WIDTH) {
    x = -ACTION_WIDTH
  }
  // 渲染层直接改样式：零跨线程通信
  ownerInstance.setStyle({ transform: 'translateX(' + x + 'px)' })
  ownerInstance.setState({ x: x })
}

function onTouchEnd(event, ownerInstance) {
  var state = ownerInstance.getState()
  var x = state ? state.x : 0
  var opened
  if (x < -SNAP) {
    x = -ACTION_WIDTH
    opened = true
  } else {
    x = 0
    opened = false
  }
  ownerInstance.setStyle({ transform: 'translateX(' + x + 'px)' })
  ownerInstance.setState({ x: x })
  // 仅在“确实打开操作区”时回逻辑层一次
  if (opened) {
    ownerInstance.callMethod('onSwipeOpen')
  }
}

module.exports = {
  onTouchStart: onTouchStart,
  onTouchMove: onTouchMove,
  onTouchEnd: onTouchEnd
}
```

```xml

</view>
```

逻辑层只接收低频结果：

```typescript
Page({
  onSwipeOpen() {
    // 记录“不感兴趣”入口曝光，或准备操作菜单
    console.log('操作区已打开')
  }
})
```

量化口径：一次完整 1 秒的滑动，跨线程消息从约 120 条（move 事件）+ 120 条（setData）降为 0~1 条（结束时 callMethod）。

常见误区：在 `onTouchMove` 里 `callMethod` 让逻辑层 setData 跟手——等于退回双程老路；WXS 里使用 ES6 语法（箭头函数、模板字符串、`let`）导致编译失败。

### 8. wx.createSelectorQuery：逻辑层如何“看”节点

逻辑层没有 DOM，不能 `document.querySelector`。需要节点位置、尺寸、滚动位置时，使用专门的选择器查询 API，它把请求发给渲染层、把结果异步带回逻辑层。

常用链式方法：

| 方法 | 作用 |
|---|---|
| `wx.createSelectorQuery()` | 创建一次查询（页面上可直接用） |
| `.in(this)` | 限定在自定义组件内部查找（组件内必写） |
| `.select(selector)` / `.selectAll(selector)` | 选单个 / 全部匹配节点 |
| `.selectViewport()` | 选择视口（用于查视口滚动位置） |
| `.boundingClientRect()` | 查询节点位置与尺寸 |
| `.scrollOffset()` | 查询节点/视口滚动位置 |
| `.fields(fields)` | 按需查询：id、dataset、rect、size、scrollOffset、properties、computedStyle、context、node |
| `.exec(callback)` | 执行全部链式请求，结果按顺序组成数组返回 |

一次查询多个目标：

```typescript
Page({
  scrollInfo: null as WechatMiniprogram.ScrollOffsetCallbackResult | null,
  cardRects: [] as WechatMiniprogram.BoundingClientRectCallbackResult[],

  onReady() {
    // 节点在 onReady 时才保证已完成首次渲染
    wx.createSelectorQuery()
      .in(this)
      .select('.note-scroll')
      .scrollOffset()
      .selectAll('.note-card')
      .boundingClientRect()
      .exec((res) => {
        this.scrollInfo = res[0] as WechatMiniprogram.ScrollOffsetCallbackResult
        this.cardRects = (res[1] as WechatMiniprogram.BoundingClientRectCallbackResult[]) || []
        console.log('滚动位置', this.scrollInfo.scrollTop)
        console.log('卡片数量', this.cardRects.length)
      })
  }
})
```

按需取字段（例如 Canvas 2D 需要拿原生 node）：

```typescript
wx.createSelectorQuery()
  .select('#share-canvas')
  .fields({ node: true, size: true })
  .exec((res) => {
    const canvas = res[0].node as WechatMiniprogram.Canvas
    const width = res[0].width
    console.log(canvas, width)
  })
```

常见误区：

- 在 `onLoad` 里查询：此时节点尚未完成首次渲染，结果为 null；应在 `onReady` 或 `setData` callback 之后。
- 组件内忘记 `.in(this)`：默认查的是页面范围，找不到组件内节点。
- 对滚动容器内未渲染的离屏节点做 `selectAll`：按需渲染模式下它们可能根本不存在（U28 详解）。

### 9. IntersectionObserver：曝光统计与懒加载触发

`IntersectionObserver` 用于异步监听“目标节点与某个参照区域是否相交、相交比例多少”。它比手工监听滚动 + 逐个算坐标更高效，判定发生在渲染侧，只有状态变化才通知逻辑层。

API 要点：

- 页面：`this.createIntersectionObserver(options)`；
- 自定义组件：`this.createIntersectionObserver(this, options)`，第一个参数是组件实例；
- `options.thresholds`：数值数组（默认 `[0]`），相交比例跨过这些阈值时触发回调；
- `options.initialRatio`：初始相交比例，用于避免初始化阶段的误触发；
- `options.observeAll`：是否同时监听选择器命中的多个节点；
- `.relativeTo(selector, margins?)`：指定参照节点及四边缩放边距；
- `.relativeToViewport(margins?)`：以视口为参照；
- `.observe(selector, callback)`：开始监听，可多次调用监听不同节点；
- `.disconnect()`：停止监听；
- 回调结果含：`intersectionRatio`（0~1）、`intersectionRect`、`boundingClientRect`、`relativeRect`、`time`。

场景一：笔记曝光去重统计（每张卡片只报一次）。

```typescript
Page({
  exposed: new Set<number>(),
  observer: null as WechatMiniprogram.IntersectionObserver | null,

  onReady() {
    const observer = this.createIntersectionObserver({ thresholds: [0.5] })
    observer.relativeToViewport()
    this.data.list.forEach((item) => {
      observer.observe(`#note-${item.id}`, (res) => {
        if (res.intersectionRatio >= 0.5 && !this.exposed.has(item.id)) {
          this.exposed.add(item.id)
          wx.reportAnalytics('note_expose', { note_id: item.id })
        }
      })
    })
    this.observer = observer
  },

  onUnload() {
    this.observer?.disconnect()
  }
})
```

场景二：图片进入视口前提前 200px 开始加载，并只触发一次。

```typescript
onLoad() {
  const lazyObserver = this.createIntersectionObserver({ thresholds: [0] })
  lazyObserver
    .relativeToViewport({ bottom: 200 }) // 参照区域下边界向外扩 200px
    .observe('#cover-image', (res) => {
      if (res.intersectionRatio > 0) {
        this.setData({ imgVisible: true })
        lazyObserver.disconnect()
      }
    })
}
```

常见误区：

- 不调用 `disconnect()`：Observer 本身持有节点与回调引用，页面退出后仍可能存活，属于监听泄漏。
- 把 `thresholds` 当“触发频率”：它是相交比例的判定阈值点，比例不变就不会重复回调。
- 曝光不做去重：同一张卡片上下滑会反复满足条件，埋点数据虚高。

### 10. 节流与防抖：给高频事件装阀门

节流和防抖都用于限制函数执行频率，但语义不同，选错会直接伤害体验。

- 节流（throttle）：在连续触发过程中，按固定时间间隔执行（如每 100ms 最多一次），保证“有节奏地持续执行”。
- 防抖（debounce）：触发后等待一段时间，期间若再次触发则重新计时，保证“停下来之后才执行一次”。

TypeScript 实现：

```typescript
// utils/flow-control.ts

// 节流：leading + trailing 混合版，保证间隔内最多执行一次，尾调用补齐
function throttle<T extends (...args: any[]) => void>(fn: T, wait = 100): T {
  let last = 0
  let timer: ReturnType<typeof setTimeout> | null = null

  return function (this: unknown, ...args: any[]) {
    const now = Date.now()
    const remaining = wait - (now - last)

    if (remaining <= 0) {
      if (timer) {
        clearTimeout(timer)
        timer = null
      }
      last = now
      fn.apply(this, args)
    } else if (!timer) {
      timer = setTimeout(() => {
        last = Date.now()
        timer = null
        fn.apply(this, args)
      }, remaining)
    }
  } as T
}

// 防抖：默认 trailing；immediate 为 true 时改为首次触发立即执行
function debounce<T extends (...args: any[]) => void>(
  fn: T,
  wait = 300,
  immediate = false
): T {
  let timer: ReturnType<typeof setTimeout> | null = null

  return function (this: unknown, ...args: any[]) {
    if (timer) {
      clearTimeout(timer)
    }
    if (immediate && !timer) {
      fn.apply(this, args)
    }
    timer = setTimeout(() => {
      timer = null
      if (!immediate) {
        fn.apply(this, args)
      }
    }, wait)
  } as T
}

export { throttle, debounce }
```

场景选型：

| 场景 | 选择 | 理由 |
|---|---|---|
| 页面/滚动容器滚动同步状态 | 节流（约 100ms） | 过程中要持续更新，又不能每帧都算 |
| 搜索框输入联想 | 防抖（200~300ms） | 用户停止输入后请求一次，省请求、免抖动 |
| 支付/提交按钮防连点 | 节流（1~2s）或提交中禁用按钮 | 防止重复下单 |
| 拖拽跟手改样式 | 两者都不要用，走 WXS/Worklet | 节流也会让画面断续 |
| 窗口尺寸变化重排 | 防抖 | 尺寸稳定后再重排一次 |

页面中的写法（注意用普通函数表达式保持 `this` 指向页面实例）：

```typescript
import { throttle, debounce } from '../../utils/flow-control'

Page({
  data: { keyword: '' },

  onLoad() {
    this.onScrollSync = throttle((e: WechatMiniprogram.Page.IPageScrollOption) => {
      console.log('滚动位置', e.scrollTop)
    }, 100)

    this.onSearch = debounce((keyword: string) => {
      this.fetchSuggestions(keyword)
    }, 300)
  },

  onPageScroll(e: WechatMiniprogram.Page.IPageScrollOption) {
    this.onScrollSync(e)
  },

  onKeywordInput(e: WechatMiniprogram.Input) {
    this.onSearch(e.detail.value)
  },

  fetchSuggestions(keyword: string) {
    console.log('请求联想', keyword)
  }
})
```

常见误区：对拖拽跟手用防抖（永远慢一拍且中间无反馈）；对搜索用节流（输入第一个字也要等一个间隔，且中途发多余请求）；不区分首尾调用导致一次操作执行两遍。

### 11. 图片懒加载与长列表策略（WebView 模式）

长列表卡顿往往不是单一原因：节点总数过多、图片加载引发重排、全量数据重渲染会叠加。

图片层面：

- 使用 `image` 组件的 `lazy-load` 属性，图片进入可视区域前后才加载（在页面与 scroll-view 内有效）；
- 给图片容器固定尺寸或固定宽高比，避免图片下载完成后撑开布局引发整页重排；
- 用 `mode="aspectFill"` 配合 CDN 裁剪参数，只下载需要的分辨率；
- 加载前显示骨架/底色，减少视觉跳动。

```xml
<image
  class="note-card__cover"
  src="{{ item.coverUrl }}{{ item._loaded ? '' : '' }}"
  lazy-load
  mode="aspectFill"
/>
```

数据层面：分页加载，始终只持有“已加载页”的数据，触底再追加。

```typescript
const PAGE_SIZE = 20

Page({
  data: {
    list: [] as NoteItem[],
    page: 1,
    hasMore: true,
    loading: false
  },

  onLoad() {
    this.loadPage(1)
  },

  // scroll-view 用 bindscrolltolower 触发；页面可用 onReachBottom
  onReachBottom() {
    if (this.data.hasMore && !this.data.loading) {
      this.loadPage(this.data.page + 1)
    }
  },

  loadPage(page: number) {
    this.setData({ loading: true })
    wx.request({
      url: 'https://api.example.com/notes',
      data: { page, pageSize: PAGE_SIZE },
      success: (res) => {
        const rows = (res.data as { list: NoteItem[]; hasMore: boolean }) || { list: [], hasMore: false }
        this.setData({
          list: this.data.list.concat(rows.list),
          page,
          hasMore: rows.hasMore
        })
      },
      complete: () => {
        this.setData({ loading: false })
      }
    })
  }
})
```

节点层面：

- WebView 模式下节点没有平台级回收，数据总量要有上限；常见做法是分页 + 适度缓存（如最多保留若干屏）。
- 对超长（数百上千项）且结构统一的列表，可使用官方 `recycle-view` 组件做节点回收，但它要求按其数据接口组织，简单分页能满足时优先简单方案。
- `wx:for` 必须配 `wx:key`，且 key 应是业务稳定 id。

常见误区：`wx:key="index"`——列表头部插入或删除一项时，后续全部项的 key 错位，diff 认为“节点还在、内容全变”，状态错乱且更耗时；不约束图片尺寸导致每加载一张整页跳一次。

### 12. 内存泄漏识别（一）：定时器与闭包

泄漏的本质是：页面本应在 `onUnload` 后被回收，但有“外部持有者”仍引用着它。定时器闭包是最典型的一种。

```typescript
// 反模式
Page({
  onLoad() {
    // 箭头函数捕获 this（页面实例）；定时器不清除，页面永远无法回收
    setInterval(() => {
      this.setData({ now: Date.now() })
    }, 1000)
  }
})
```

后果叠加：页面退出后定时器仍在跑；回调对已销毁页面 `setData`，控制台出现“setData of undefined”一类告警；反复进出页面会并存多个定时器，刷新频率翻倍、内存只涨不跌。

修复模板：

```typescript
Page({
  timer: null as ReturnType<typeof setInterval> | null,

  onLoad() {
    this.timer = setInterval(() => {
      this.setData({ now: Date.now() })
    }, 1000)
  },

  onHide() {
    // 可选：页面不可见时暂停，进一步省电
    if (this.timer) {
      clearInterval(this.timer)
      this.timer = null
    }
  },

  onUnload() {
    if (this.timer) {
      clearInterval(this.timer)
      this.timer = null
    }
  }
})
```

递归 `setTimeout` 同理：链式定时器也要在卸载时清除当前这一个。

识别方法：进入页面 → 退出，重复 10 次；观察控制台是否持续出现该页面的日志或 setData 告警、内存曲线是否回不到首次进入前的水平。

### 13. 内存泄漏识别（二）：事件监听与全局事件总线

第二类持有者是“注册到页面外部、却没注销”的监听。

微信能力监听必须成对出现：`wx.onLocationChange` 对应 `wx.offLocationChange`，以此类推。

```typescript
Page({
  locationHandler: null as ((res: WechatMiniprogram.OnLocationChangeCallbackResult) => void) | null,

  onLoad() {
    this.locationHandler = (res) => {
      console.log('位置变化', res.latitude, res.longitude)
    }
    // 必须传入具名引用，匿名函数之后无法精确注销
    wx.onLocationChange(this.locationHandler)
  },

  onUnload() {
    if (this.locationHandler) {
      wx.offLocationChange(this.locationHandler)
    }
  }
})
```

全局事件总线同理（U12 的全局状态方案常见）：

```typescript
const app = getApp<{
  bus: { on: (e: string, h: (...args: unknown[]) => void) => void; off: (e: string, h: (...args: unknown[]) => void) => void }
}>()

Page({
  onLoad() {
    this.onNoteChanged = () => this.refresh()
    app.bus.on('note:changed', this.onNoteChanged)
  },
  onUnload() {
    app.bus.off('note:changed', this.onNoteChanged)
  },
  refresh() {
    console.log('刷新列表')
  }
})
```

常见误区：注册时传匿名函数，注销时拿不到同一引用；以为页面卸载会自动注销 `wx.on*` 监听——不会，监听注册在全局，生命周期比页面长。

### 14. 内存泄漏识别（三）：页面栈、全局引用与组件内部

页面栈本身也会持有页面实例。`wx.navigateTo` 的页面栈最多 10 层，深层链路应适时用 `redirectTo`（替换当前页）或 `reLaunch`（清栈重启）收敛，避免栈里堆积重页面。

更隐蔽的是主动把页面/回调挂到全局：

```typescript
// 反模式：把页面实例或回调缓存进 globalData，旧页面被全局数组长期持有
getApp().globalData.pendingPages.push(this)
```

异步回调持有 `this` 也很常见：请求未返回就退页，回调里继续 `setData`。应加“已销毁”标记：

```typescript
Page({
  disposed: false,

  onLoad() {
    wx.request({
      url: 'https://api.example.com/notes',
      success: (res) => {
        if (this.disposed) return // 页面已卸载，不再处理
        this.setData({ list: res.data as NoteItem[] })
      }
    })
  },

  onUnload() {
    this.disposed = true
  }
})
```

自定义组件还要警惕：

- 组件内部启动的定时器、注册的监听同样要在 `detached` 生命周期清理；
- `observers` 中无条件连锁 `setData`，可能形成循环触发，既耗性能又让组件树长期处于忙碌状态。

系统级内存压力可监听并主动降级：

```typescript
wx.onMemoryWarning(() => {
  // 释放非必要缓存，降低被杀后台概率
  getApp<{ cache?: Map<string, unknown> }>().cache?.clear()
  console.warn('收到内存告警，已清理缓存')
})
```

### 15. 用工具采集性能：性能面板、真机调试与 wx.getPerformance

采集工具分三层，互为补充。

第一层：开发者工具的性能/Trace 面板。开始录制后操作页面，结束后可看到函数耗时火焰图、`setData` 记录（调用栈、数据量、渲染耗时）、FPS 曲线与内存曲线，适合先在开发阶段定位热点。

第二层：真机调试与真机帧率。通过 USB 或局域网真机调试，配合帧率浮窗观察滚动与动画；中低端 Android 必须单独采集，它通常先暴露问题。

第三层：程序化采集 `wx.getPerformance`，把性能数据当作普通 entry 读取：

```typescript
const performance = wx.getPerformance()

const observer = performance.createObserver((entryList) => {
  entryList.getEntries().forEach((entry) => {
    // entry 常见字段：entryType、name、startTime、duration
    console.log(entry.entryType, entry.name, Math.round(entry.duration) + 'ms')
  })
})

// entryType 集合以官方文档为准，常见包括路由、首屏渲染、脚本注入等类别
observer.observe({
  entryTypes: ['navigation', 'renderScript', 'evaluateScript']
})
```

setData 通信量除了看 Trace，也可在实验期用计数器统计：

```typescript
let count = 0
const rawSetData = this.setData.bind(this)
this.setData = (patch: Record<string, unknown>, cb?: () => void) => {
  count += 1
  const bytes = JSON.stringify(patch).length
  console.log(`第 ${count} 次 setData，约 ${bytes} 字符`)
  rawSetData(patch, cb)
}
```

采集操作清单：

1. 冷启动：杀掉微信进程，进入小程序到首屏可交互，重复 3 次，记录中位数。
2. 首屏通信：统计首屏内 setData 次数与总字符数。
3. 快速滑动：以稳定手势快速滑动列表 10 秒，记录平均帧率与 P95 帧时长。
4. 高频交互：完整执行一次滑动卡片/连续点赞，记录通信条数。
5. 内存：连续进出页面 10 次，记录内存曲线与告警。

报告中至少写清：机型与系统、微信版本、基础库版本、每次指标值、采集方式、结论。

常见误区：只在工具里测完就验收；只报平均帧率、不报长尾帧时长（卡顿正来自少数超长帧）；把热启动数据当冷启动。

### 练习 2：IntersectionObserver 曝光去重与图片懒加载

#### 任务

在分页笔记列表中实现：每张卡片露出面积达到 50% 时上报一次曝光（同一 id 不重复）；封面图在进入视口前 200px 触发加载；并用 `SelectorQuery` 测量首屏卡片高度，输出报告。

参考代码：

```typescript
Page({
  exposed: new Set<number>(),
  io: null as WechatMiniprogram.IntersectionObserver | null,

  onReady() {
    const io = this.createIntersectionObserver({ thresholds: [0.5] })
    io.relativeToViewport()
    this.data.list.forEach((item) => {
      io.observe(`#note-${item.id}`, (res) => {
        if (res.intersectionRatio >= 0.5 && !this.exposed.has(item.id)) {
          this.exposed.add(item.id)
          wx.reportAnalytics('note_expose', { note_id: item.id })
        }
      })
    })
    this.io = io

    wx.createSelectorQuery()
      .selectAll('.note-card')
      .boundingClientRect()
      .exec((res) => {
        const rects = (res[0] as WechatMiniprogram.BoundingClientRectCallbackResult[]) || []
        console.log('首屏卡片高度', rects.map((r) => Math.round(r.height)))
      })
  },

  onUnload() {
    this.io?.disconnect()
  }
})
```

#### 步骤约束

1. WXML 中每个卡片节点必须带 `id="note-{{item.id}}"`，封面图使用 `lazy-load`。

3. 页面卸载后不得再有 observer 回调；在 `onUnload` 中 `disconnect`。
4. 至少准备两页数据，验证新页追加后曝光监听对新节点同样生效（追加后需重新 observe）。


```typescript
Page({
  timer: null as ReturnType<typeof setInterval> | null,
  handler: null as ((res: WechatMiniprogram.OnLocationChangeCallbackResult) => void) | null,

  onLoad() {
    this.timer = setInterval(() => {
      console.log('定时器仍在运行', this.data.pageId)
    }, 1000)

    this.handler = () => {
      console.log('位置回调', this.data.pageId)
    }
    wx.onLocationChange(this.handler)
  },

  onUnload() {
    if (this.timer) {
      clearInterval(this.timer)
      this.timer = null
    }
    if (this.handler) {
      wx.offLocationChange(this.handler)
    }
  },

  data: { pageId: 'leak-demo' }
})
```
