# 31-自动化测试与质量保障

## 目标

收官阶段的第一个单元，要解决一个真实的工程焦虑：「逛吃指南」已经有交易闭环、有性能治理、准备上线，那么以后每一次修改，凭什么相信它没有改坏？本单元的目标是给项目补上自动化测试体系、质量门禁与发布后监控，让“修改后还敢不敢发”有客观答案。完成本单元后，学员应能够：

1. 说清小程序测试金字塔的三层划分：纯函数与云函数单元测试、miniprogram-simulate 组件测试、miniprogram-automator 端到端测试各自验证什么、成本如何、边界在哪，并能为一个具体需求选择正确的测试层。
2. 独立搭建 Jest + TypeScript 测试环境：编写多项目（projects）配置，处理小程序专有文件与路径别名，区分单元、组件、E2E 三类测试的匹配规则与 npm 脚本。
3. 使用 miniprogram-simulate 在 Node 环境加载并渲染自定义组件：传入 properties、挂载到容器、查询内置节点与子组件，断言渲染文本与 data 的行为变化。
4. 在组件测试中模拟真实交互：派发 tap/input 等事件，接收并断言组件 `triggerEvent` 抛出的自定义事件（含 detail 载荷），覆盖 observers、生命周期与条件渲染分支。
5. 为云函数编写可重复的单元测试：用 stub/mock 替换 `wx-server-sdk` 的 `init`、`database`、`getWXContext`，注入 OPENID，用内存数据或 `jest.fn` 验证数据库调用参数与返回契约。
6. 区分 stub（提供预设答案）与 mock（验证调用行为）的职责，正确使用 `jest.mock` 工厂、`jest.spyOn`、假时钟来控制网络、时间、随机数等外部依赖。
7. 使用 miniprogram-automator 连接开发者工具自动化端口（及真机调试通道），编写“启动 → 进入页面 → 输入点击 → 支付结果”的端到端关键路径测试，并用 `mockWxMethod` 隔离 `wx.login`、`requestPayment` 等强环境依赖。
8. 落实测试隔离与数据清理：用例之间无共享状态、测试数据带前缀可重建可回收、测试环境与生产环境的数据库和 AppID 物理隔离。
9. 读懂 Istanbul 覆盖率四类指标并设置合理阈值，理解“高覆盖率不等于高质量”；系统治理 flaky test：以条件等待替代固定睡眠、固定夹具数据、限定重试与隔离的边界。
10. 把测试分层接入 CI 门禁：单元/组件测试作为每次合并的必过条件，E2E 按条件或定时运行；结合真机远程调试与灰度期监控，形成“测试拦截 — 灰度验证 — 线上观测”的质量闭环。

实验约定：

- 测试代码全部进入 Git 仓库，与被测代码同仓管理；测试文件统一放在 `__tests__/` 目录或以 `.test.ts`、`.e2e.ts` 结尾。
- 单元测试与组件测试必须离线可跑：不允许依赖真实网络、真实数据库、真实支付；所有外部依赖显式 mock。
- E2E 只覆盖关键路径（登录、下单、支付、退款申请等），不追求用 E2E 覆盖所有分支，分支逻辑由下层测试负责。
- 测试环境与生产环境物理隔离：独立云环境、独立 AppID（或独立测试租户）、测试数据统一带 `e2e`/`test` 前缀。
- 密钥与凭证（AppSecret、CI 上传私钥、测试账号信息）只存在于 CI secrets 或服务端，禁止硬编码进仓库或测试代码。

## 详细的理论知识讲解和示例伪代码

### 1. 小程序的测试金字塔：三层各自验证什么

在 Web 前端语境里，测试通常分为单元测试、组件测试与端到端测试。小程序因为双线程模型与宿主环境的存在，这套分层需要重新落到具体工具上：

```text
          ┌─────────────────────────────┐
  少量    │  E2E（miniprogram-automator）│ 真实页面、真实路由、真实渲染
          ├─────────────────────────────┤ 验证“整条业务链路走得通”
  适量    │  组件测试（miniprogram-       │ Node 内模拟组件树
          │  simulate）                  │ 验证输入→渲染/事件/数据
          ├─────────────────────────────┤
  大量    │  单元测试（Jest）             │ 纯函数、状态机、云函数
          └─────────────────────────────┘ 验证“一个单元的行为契约”
```

三层的判断标准：

- **单元测试**：被测对象是一个函数或一个模块，所有外部依赖（数据库、网络、时间、宿主 API）都被替换。毫秒级、可以有几百个。价格计算、订单状态流转、参数校验器是典型对象。
- **组件测试**：被测对象是一个自定义组件。simulate 会在 Node 里建立一套模拟的组件树与 DOM（jsdom），组件逻辑、WXML 渲染、`setData`、事件冒泡都真实执行，但不运行在微信客户端里。
- **端到端测试（E2E）**：被测对象是完整小程序，automator 通过 WebSocket 操控真实的开发者工具（或真机），页面、路由、网络、存储全部真实，只有 `wx.login`、支付等强环境依赖按需 mock。

一个常见误区是“全用 E2E 不就最真实吗”。真实，但贵：E2E 启动一次要数十秒，失败时定位困难，且强依赖环境。正确的结构是：分支逻辑靠大量单测兜底，组件交互靠适量组件测试，E2E 只钉死几条不能断的关键路径。

两个关键设计：

1. E2E 默认不进 `npm test`，也不进覆盖率统计——它需要启动开发者工具，属于另一类资源消耗，通常在 CI 的独立 job 或定时任务里运行。
2. E2E 使用 `--runInBand` 串行执行：多个用例同时操控同一个小程序实例会互相干扰。

误区：把所有测试都放进默认 `testMatch: **/*.test.js`。短期省事，后期无法按层选择环境、无法让 E2E 脱离门禁、无法统计分层结果。

### 3. 纯函数单元测试：先把最好测的部分测起来

不是所有逻辑都绑在组件里。U18 的搜索过滤、U23 的金额计算、订单状态机这类纯逻辑应抽到 `utils/`，它们是测试性价比最高的部分：

```ts
// miniprogram/utils/order.ts
export type OrderStatus =
  | 'pending_pay'
  | 'paid'
  | 'preparing'
  | 'completed'
  | 'cancelled'
  | 'refunding'
  | 'refunded'

const ALLOWED_TRANSITIONS: Record<OrderStatus, OrderStatus[]> = {
  pending_pay: ['paid', 'cancelled'],
  paid: ['preparing', 'refunding'],
  preparing: ['completed', 'refunding'],
  completed: ['refunding'],
  cancelled: [],
  refunding: ['refunded', 'preparing'],
  refunded: []
}

export function canTransit(from: OrderStatus, to: OrderStatus): boolean {
  return ALLOWED_TRANSITIONS[from]?.includes(to) ?? false
}

export function calcAmount(
  items: Array<{ count: number; price: number }>
): number {
  // 以分为单位内部计算，避免浮点误差；这里返回元，保留两位小数
  const cents = items.reduce((sum, item) => {
    if (item.count < 0 || item.price < 0) {
      throw new Error('INVALID_ITEM')
    }
    return sum + Math.round(item.count * item.price * 100)
  }, 0)
  return Math.round(cents) / 100
}
```

```ts
// miniprogram/utils/__tests__/order.test.ts
import { calcAmount, canTransit, type OrderStatus } from '../order'

describe('calcAmount', () => {
  test('多件商品求和且不产生浮点尾差', () => {
    expect(
      calcAmount([
        { count: 2, price: 30 },
        { count: 1, price: 15.5 }
      ])
    ).toBe(75.5)
  })

  test('空数组金额为 0', () => {
    expect(calcAmount([])).toBe(0)
  })

  test('负数数量或单价抛错', () => {
    expect(() => calcAmount([{ count: -1, price: 10 }])).toThrow('INVALID_ITEM')
  })
})

describe('canTransit 订单状态机', () => {
  test.each<[OrderStatus, OrderStatus]>([
    ['pending_pay', 'paid'],
    ['paid', 'refunding'],
    ['refunding', 'refunded']
  ])('合法流转 %s -> %s', (from, to) => {
    expect(canTransit(from, to)).toBe(true)
  })

  test.each<[OrderStatus, OrderStatus]>([
    ['pending_pay', 'completed'],
    ['completed', 'paid'],
    ['cancelled', 'paid'],
    ['refunded', 'paid']
  ])('非法流转 %s -> %s 被拒绝', (from, to) => {
    expect(canTransit(from, to)).toBe(false)
  })
})
```

注意断言基于**行为**：状态机测“给定状态，能不能流转”，而不是测内部表长什么样；金额函数测“给定输入，输出多少/抛什么错”。即使将来把实现换成 Map 或类，用例不需要改。

### 4. miniprogram-simulate：在 Node 里渲染一个组件

simulate 的工作方式是：加载组件四件套 → 在 jsdom 中建立组件实例 → 像真实宿主一样执行生命周期、渲染 WXML、响应 `setData`。核心 API 只有四步：`load` → `render` → `attach` → 查询/交互。

被测组件（店铺卡片，承接 U09/U10 的组件化功底）：

```ts
// miniprogram/components/shop-card/index.ts
interface Shop {
  id: number
  name: string
  score: number
  tags: string[]
}

Component({
  properties: {
    shop: {
      type: Object,
      value: { id: 0, name: '', score: 0, tags: [] as string[] }
    },
    favorite: { type: Boolean, value: false }
  },

  data: {
    expanded: false
  },

  observers: {
    'shop.score'(score: number) {
      this.setData({ scoreText: Number(score).toFixed(1) })
    }
  },

  methods: {
    onTapCard() {
      this.triggerEvent('select', { id: this.properties.shop.id })
    },

    onToggleFav() {
      const next = !this.data.favorite
      this.setData({ favorite: next })
      this.triggerEvent('favoritechange', {
        id: this.properties.shop.id,
        favorite: next
      })
    },

    onToggleTags() {
      this.setData({ expanded: !this.data.expanded })
    }
  }
})
```

```xml
<!-- miniprogram/components/shop-card/index.wxml -->
<view class="shop-card" bindtap="onTapCard">
  <text class="name">{{shop.name}}</text>
  <text class="score">{{scoreText}} 分</text>
  <view class="fav {{favorite ? 'on' : ''}}" catchtap="onToggleFav">
    {{favorite ? '已收藏' : '收藏'}}
  </view>
  <button size="mini" bindtap="onToggleTags">标签</button>
  <view class="tags" wx:if="{{expanded}}">
    <text wx:for="{{shop.tags}}" wx:key="*this" class="tag">{{item}}</text>
  </view>
</view>
```

### 5. 组件测试：传 properties、查渲染、断 data

```ts
// miniprogram/components/shop-card/__tests__/index.test.ts
import path from 'node:path'
import simulate from 'miniprogram-simulate'

describe('shop-card 组件', () => {
  let id: string

  beforeAll(() => {
    // load 返回组件 id；路径建议用绝对路径，避免随执行目录变化
    id = simulate.load(path.resolve(__dirname, '../index'), 'shop-card')
  })

  function renderCard(favorite = false) {
    const comp = simulate.render(id, {
      shop: {
        id: 7,
        name: '老巷口火锅',
        score: 4.8,
        tags: ['麻辣', '夜宵', '包间']
      },
      favorite
    })
    // 必须挂载到一个容器元素，触发生命周期与布局相关行为
    comp.attach(document.createElement('parent-wrapper'))
    return comp
  }

  test('渲染店名与评分，未展开时标签区不存在', async () => {
    const comp = renderCard()
    await simulate.sleep(0)

    expect(comp.querySelector('.name').dom.textContent).toBe('老巷口火锅')
    expect(comp.querySelector('.score').dom.textContent).toContain('4.8')
    // wx:if 为 false 时节点根本不存在
    expect(comp.querySelector('.tags')).toBeNull()
  })

  test('点击卡片抛出 select 事件，detail 携带店铺 id', async () => {
    const comp = renderCard()
    const onSelect = jest.fn()
    comp.addEventListener('select', onSelect)

    comp.querySelector('.shop-card').dispatchEvent('tap')
    await simulate.sleep(0)

    expect(onSelect).toHaveBeenCalledTimes(1)
    expect(onSelect.mock.calls[0][0].detail).toEqual({ id: 7 })
  })

  test('收藏按钮：切换 data.favorite、抛出 favoritechange，且不触发卡片 select', async () => {
    const comp = renderCard(false)
    const onSelect = jest.fn()
    const onFav = jest.fn()
    comp.addEventListener('select', onSelect)
    comp.addEventListener('favoritechange', onFav)

    comp.querySelector('.fav').dispatchEvent('tap')
    await simulate.sleep(0)

    // 行为一：组件内部状态翻转，并反映到样式类
    expect(comp.data.favorite).toBe(true)
    expect(comp.querySelector('.fav').dom.className).toContain('on')

    // 行为二：对外抛出带载荷的事件
    expect(onFav).toHaveBeenCalledTimes(1)
    expect(onFav.mock.calls[0][0].detail).toEqual({ id: 7, favorite: true })

    // 行为三：catchtap 阻止冒泡，卡片的 select 不应被触发
    expect(onSelect).not.toHaveBeenCalled()
  })

  test('点标签按钮切换展开态，展开后渲染全部标签', async () => {
    const comp = renderCard()

    comp.querySelector('button').dispatchEvent('tap')
    await simulate.sleep(0)
    expect(comp.data.expanded).toBe(true)
    expect(comp.querySelectorAll('.tag')).toHaveLength(3)

    comp.querySelector('button').dispatchEvent('tap')
    await simulate.sleep(0)
    expect(comp.data.expanded).toBe(false)
    expect(comp.querySelector('.tags')).toBeNull()
  })
})
```

这里体现了测试断言的正确对象：

- 断言**渲染结果**（文本、节点是否存在、class）——用户看得见的行为；
- 断言**对外事件契约**（事件名、detail）——父组件依赖的行为；
- 断言**data 的可观察变化**——会影响后续渲染的行为。

误区：断言“`onTapCard` 被调了几次”“`setData` 被传了什么对象”。这是实现细节，重构方法名或合并一次 `setData` 都会让测试误报，而用户行为根本没变。

### 6. 组件中的 observers、生命周期与父子组件通信

observers 与生命周期分支同样按行为断言。例如上例中评分观察者产出 `scoreText`，只需断言 `.score` 的渲染文本，不必直接调用观察者。

当组件包含子自定义组件时，用 `>>>` 跨越组件边界查询内部节点，`querySelector` 命中自定义组件标签时返回的是子组件实例：

```ts
test('子组件 dish-row 的加入菜品事件被父组件接收', async () => {
  const parentId = simulate.load(
    path.resolve(__dirname, '../cart-panel'),
    'cart-panel'
  )
  const comp = simulate.render(parentId, { shopId: 'shop-1' })
  comp.attach(document.createElement('parent-wrapper'))

  const firstRow = comp.querySelector('dish-row') // 子组件实例
  expect(firstRow).not.toBeNull()

  const onAddDish = jest.fn()
  comp.addEventListener('adddish', onAddDish)

  // 在子组件上派发其内部 triggerEvent 抛出的事件
  firstRow.dispatchEvent('adddish')
  await simulate.sleep(0)

  expect(onAddDish.mock.calls[0][0].detail).toMatchObject({
    dishId: expect.any(String)
  })
})
```

两个易错点：

- 忘记 `attach`：组件未挂载，依赖布局或生命周期的查询会拿到意外结果。
- 在 jsdom 中用 `innerText` 断言：jsdom 不做布局，`innerText` 不可靠；断言文本用 `textContent`。

### 7. 云函数单测：mock wx-server-sdk 并注入身份

云函数是小程序里最“正经”的后端代码：可测性强、出问题代价大，应优先覆盖。以 U23 的下单云函数为例：

```ts
// cloud/functions/createOrder/index.ts
import cloud from 'wx-server-sdk'

cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })

interface CreateOrderEvent {
  shopId: string
  items: Array<{ dishId: string; count: number; price: number }>
  remark?: string
}

export const main = async (event: CreateOrderEvent) => {
  const { OPENID } = cloud.getWXContext()
  if (!OPENID) {
    throw new Error('NO_OPENID')
  }
  if (!event.items || event.items.length === 0) {
    throw new Error('EMPTY_ITEMS')
  }

  const amount =
    Math.round(
      event.items.reduce(
        (sum, item) => sum + item.count * item.price * 100,
        0
      )
    ) / 100

  const db = cloud.database()
  const res = await db.collection('orders').add({
    data: {
      _openid: OPENID,
      shopId: event.shopId,
      items: event.items,
      amount,
      status: 'pending_pay',
      createdAt: db.serverDate()
    }
  })

  return { orderId: res._id, amount }
}
```

测试通过 `jest.mock` 替换整个 SDK：

三个关键机制要讲清：

1. **身份注入**：真实环境里 OPENID 由微信运行时注入，测试中由 mock 的 `getWXContext` 返回固定身份，从而可重复地验证“订单挂在正确用户名下”。
2. **jest.mock 提升**：`jest.mock` 会被提升到文件顶部、先于 `import` 执行，所以 `import { main }` 拿到的已经是 mock 后的 SDK。工厂中引用的外部变量必须以 `mock` 开头（如 `addMock`），否则提升后未初始化。
3. **stub 与 mock 的分工**：`addMock.mockResolvedValue(...)` 是 stub，给函数一个答案；`expect(addMock).toHaveBeenCalledWith(...)` 是 mock，验证云函数与数据库之间的契约。两者服务于不同断言。

对于更复杂的查询（`where`、`get`、`update`、事务），可以写一个内存集合模拟：

```ts
// cloud/functions/createOrder/__tests__/memory-db.ts
export interface MemoryDoc {
  _id: string
  [key: string]: unknown
}

export function createMemoryCollection(seed: MemoryDoc[] = []) {
  const docs = [...seed]
  return {
    add: jest.fn(async ({ data }: { data: Omit<MemoryDoc, '_id'> }) => {
      const _id = 'mem-' + (docs.length + 1)
      docs.push({ _id, ...data })
      return { _id }
    }),
    where: jest.fn(() => ({
      get: jest.fn(async () => ({ data: docs }))
    })),
    _docs: docs
  }
}
```

误区：让云函数单测连真实云环境。网络抖动、数据残留、身份不稳定都会让测试不可重复；单测必须在毫秒级、离线、零副作用地运行。

### 10. E2E 关键路径：下单到支付，强依赖一律 mock

支付链路是 U23 的成果，也是整条业务最不能断的路径。E2E 让页面、路由、云函数、数据库全部真实运行，只把两件无法自动化的事 mock 掉：微信登录换码与收银台支付：

```ts
// tests/e2e/order-flow.e2e.ts
import path from 'node:path'
import automator, { type MiniProgram } from 'miniprogram-automator'

const PROJECT_PATH = path.resolve(__dirname, '../..')
const TEST_SHOP_ID = 'shop_e2e_demo'
const TEST_LOGIN_CODE = process.env.E2E_LOGIN_CODE as string

describe('下单支付关键路径（E2E）', () => {
  let miniProgram: MiniProgram

  beforeAll(async () => {
    miniProgram = await automator.launch({
      cliPath: process.env.WEAPP_CLI_PATH as string,
      projectPath: PROJECT_PATH,
      timeout: 60_000
    })

    // 固定测试身份：测试环境后端约定该 code 对应固定测试租户 openid
    await miniProgram.mockWxMethod('login', { code: TEST_LOGIN_CODE })
  }, 120_000)

  afterAll(async () => {
    await miniProgram?.close()
  })

  test('进入店铺 → 加菜 → 提交订单 → 支付成功', async () => {
    const page = await miniProgram.reLaunch(
      `/pages/shop-detail/shop-detail?id=${TEST_SHOP_ID}`
    )

    // 等真实数据渲染出菜品，而不是 sleep 固定时长
    await page.waitFor('.dish-item', { timeout: 15_000 })
    const dishes = await page.$$('.dish-item')
    expect(dishes.length).toBeGreaterThan(0)

    const addBtn = await dishes[0].$('.add-btn')
    await addBtn?.tap()

    await (await page.$('.cart-bar'))?.tap()
    await page.waitFor('.order-confirm')

    // 关键：mock 收银台，支付成功分支可在自动化中走通
    await miniProgram.mockWxMethod('requestPayment', {
      errMsg: 'requestPayment:ok'
    })
    await (await page.$('.pay-btn'))?.tap()

    await page.waitFor('.pay-success', { timeout: 10_000 })
    expect(await page.data('orderStatus')).toBe('paid')
  }, 90_000)
})
```

为什么登录与支付必须 mock：

- `wx.login` 的 code 只能由真实微信客户端向微信服务器换取，自动化环境无法完成真实换码；测试环境后端预置“测试 code → 测试 openid”的映射，用 `mockWxMethod('login')` 固定 code，就固定了整条链路的身份。
- `requestPayment` 会拉起真实收银台并涉及真实资金，任何自动化都不应触发真实扣款；mock 返回 `requestPayment:ok`，验证的是“支付成功后订单状态、跳转、消息触达是否正确”，这正是小程序侧代码的职责；支付渠道本身由微信保证。

失败路径（用户取消支付、扣款失败）同理：在测试构建中通过 mock 的不同返回或测试专用开关构造，不要依赖手工操作收银台。

### 11. 真机 E2E 与真机/远程调试

开发者工具中的 E2E 验证的是工具运行时；发布前还应在真机走关键路径：

- 真机自动化：通过真机调试通道（USB，开发者工具的真机调试/自动化能力）进行连接，操控能力弱于工具端，适合验证启动、页面渲染、原生能力调用，支付仍需 mock。
- 远程调试：开发版/体验版可在开发者工具发起远程调试，断点、查看 storage 与网络，适合复现特定机型问题。
- 真机调试 2.0：真机与工具间建立直连，可在真机环境下看 Console、Network、Storage，并对逻辑层断点。

调试期工具：vConsole 类能力仅用于开发/体验排查，正式版必须关闭；正式版的诊断依赖日志上报而不是调试面板。

### 12. 测试隔离与数据清理

“可重复”是测试可信度的底线。隔离设计分三层：

1. **环境隔离**：E2E 连接独立的测试云环境与测试 AppID，测试后端与生产后端部署分开，域名/环境通过构建配置切换（沿用 U30 的多环境方案）。
2. **用例隔离**：每个用例自己造数、自己清理，不依赖执行顺序，不假设其他用例的残留数据。数据带唯一前缀（如 `e2e_${用例名}`）。
3. **状态隔离**：组件测试每个用例重新 `render`；云函数测试在 `beforeEach` 里 `clearAllMocks` 并重置返回值；E2E 每条用例 `reLaunch` 冷启动页面。

E2E 的数据清理用管理端凭证在服务端完成（凭证同样只放 CI secrets），例如：

```ts
// tests/e2e/helpers/cleanup.ts
export async function cleanupTestOrders(openid: string): Promise<void> {
  const admin = createTestAdminSdk() // 使用测试环境管理凭证，从环境变量读取
  const db = admin.database()
  const snapshot = await db
    .collection('orders')
    .where({ _openid: openid, tag: 'e2e' })
    .get()

  await Promise.all(
    snapshot.data.map((doc) =>
      db.collection('orders').doc(doc._id).delete()
    )
  )
}
```

```ts
afterEach(async () => {
  await cleanupTestOrders('test-openid-e2e')
})
```

误区：在用例之间复用订单、复用购物车状态来“省时间”。一旦前一个用例失败提前退出，后续用例集体红灯，且难以判断失败归因——隔离的目的就是让每个红灯只指向一个问题。

### 13. 覆盖率：读得懂，也别迷信

运行 `npm run test:coverage` 后，Jest 用 Istanbul 产出四类指标：

| 指标 | 含义 |
|---|---|
| Statements | 语句执行比例 |
| Branches | 分支（if、三元、`??`、`??` 兜底等）走全的比例 |
| Functions | 函数被调用的比例 |
| Lines | 行执行比例（与 statements 接近，统计粒度不同） |

用法建议：

- 用 `coverageThreshold` 设全局下限防止趋势恶化，但不要一开始就追 100%；错误处理分支、防御性代码的成本要权衡。
- 优先盯 **branches**：U23/U16 的大量 bug 藏在失败分支（支付失败、登录失效、权限拒绝），语句覆盖高但分支覆盖低是危险信号。
- 对确实无需测试的文件用配置排除，而不是写空测试凑数。

覆盖率的两个陷阱必须记住：

1. 覆盖率只证明“代码执行过”，不证明“断言过”。一个没有任何 `expect` 的用例照样把代码标绿。
2. E2E 默认不纳入这份报告（运行环境不同），所以覆盖率数字描述的是单元/组件层；关键路径的完整性由 E2E 用例清单保证。两者互补，不能互相冒充。

### 14. Flaky test 治理：同一份代码，偶尔失败怎么办

flaky test（不稳定测试）比没有测试更危险：它教会团队忽略红灯。常见成因与对策：

```text
成因一：固定 sleep 等渲染/网络  → 改为 waitFor 条件等待（选择器出现、data 符合预期）
成因二：依赖真实时间            → 假时钟固定系统时间
成因三：依赖真实网络/第三方      → mock，或使用录制好的固定夹具（fixture）
成因四：用例共享数据/顺序依赖    → 隔离 + 独立造数清理
成因五：动画/过渡未结束就断言    → 关闭测试环境动画，或等待动画结束信号
```

治理纪律：

- 先修再谈重试。`jest.retryTimes` 只能作为**调查期**的临时手段（附带记录重试次数），不能把 flaky 永久“重试到绿”。
- 短期无法修复的用例可以显式隔离（skip 并挂工单、写明责任人与期限），让红灯集合保持可信。
- CI 上连续多跑若干次（如同一分支重复 3 轮）用于暴露 flaky，而不是在正式门禁里偷偷重试。

### 15. 接入 CI 门禁与灰度监控

把质量保障从“开发者自觉”变成“合并的客观条件”。示例 GitHub Actions：

```yaml
# .github/workflows/quality.yml
name: quality-gate

on:
  pull_request:
  push:
    branches: [main]

jobs:
  lint-and-unit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm run test:coverage
      - name: 归档覆盖率报告
        uses: actions/upload-artifact@v4
        with:
          name: coverage-report
          path: coverage/
          retention-days: 14

  e2e:
    runs-on: ubuntu-latest
    timeout-minutes: 25
    env:
      WEAPP_CLI_PATH: /opt/wechat-devtools/cli
      E2E_LOGIN_CODE: ${{ secrets.E2E_LOGIN_CODE }}
      TEST_ADMIN_SECRET: ${{ secrets.TEST_ADMIN_SECRET }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run test:e2e
```

门禁规则：

- PR 必须通过 lint、单元/组件测试（含覆盖率阈值）才允许合并；E2E 作为合并前必跑或合并后定时跑，按团队资源选择，但关键路径失败必须阻断发布。
- 凭证全部来自 `secrets`：日志自动脱敏；fork 来的 PR 拿不到 secrets，避免凭证泄露。AppSecret 永远不出现在前端与仓库中；上传私钥、测试管理密钥等同理。

发布后的观测闭环：

```ts
// miniprogram/app.ts
App({
  onError(error) {
    // 上报到自建监控或云函数；只传错误信息与上下文，不传用户敏感数据
    wx.getRealtimeLogManager().error('app.onError', error)
  },
  onUnhandledRejection(res) {
    wx.getRealtimeLogManager().error('unhandledrejection', res.reason)
  }
})
```

灰度期间（U32 会讲分阶段发布）重点盯三类信号：崩溃/异常率、关键接口错误率与耗时、支付漏斗每一步的转化。任一指标越过预设阈值即暂停放量或回退——自动化测试保证“已知行为没改坏”，监控负责发现“测试没想到的事”，两者合起来才是完整的质量保障。

### 练习 1：组件测试套件——shop-card 全行为覆盖

#### 任务

为「逛吃指南」的 `shop-card` 组件建立组件测试，覆盖：初始渲染、点击选店事件、收藏切换（含不冒泡）、标签展开/收起、评分 observer 文本，共不少于 5 个测试用例，全部离线可跑。

参考代码：

```ts
// miniprogram/components/shop-card/__tests__/index.test.ts
import path from 'node:path'
import simulate from 'miniprogram-simulate'

describe('shop-card', () => {
  const id = simulate.load(
    path.resolve(__dirname, '../index'),
    'shop-card'
  )

  function renderCard(favorite = false) {
    const comp = simulate.render(id, {
      shop: { id: 7, name: '老巷口火锅', score: 4.8, tags: ['麻辣', '夜宵'] },
      favorite
    })
    comp.attach(document.createElement('parent-wrapper'))
    return comp
  }

  test('点击卡片抛出 select 且 detail 正确', async () => {
    const comp = renderCard()
    const onSelect = jest.fn()
    comp.addEventListener('select', onSelect)

    comp.querySelector('.shop-card').dispatchEvent('tap')
    await simulate.sleep(0)

    expect(onSelect).toHaveBeenCalledTimes(1)
    expect(onSelect.mock.calls[0][0].detail).toEqual({ id: 7 })
  })
})
```

#### 步骤约束

1. 每个用例独立 `render`，不允许在用例之间复用组件实例。
2. 事件断言必须校验 `detail` 载荷；收藏用例必须额外验证 select 未被触发。
3. 所有等待使用 `simulate.sleep(0)` 或查询节点，不允许真实延时。
4. 用 `npm test -- shop-card` 可独立跑通，重复执行 5 轮结果一致。

#### 提交物

- 组件四件套（如组件尚不存在则一并补齐）；
- `__tests__/index.test.ts`；
- 本地连续 5 轮执行结果截图或终端输出。

#### 验收标准

- 用例数不少于 5，全部通过且断言基于渲染文本、节点存在性与事件 detail；
- 无任何对实现细节（方法名、setData 调用次数）的断言；
- 重复运行结果稳定。

### 练习 2：云函数单测——createOrder 的成功与失败分支

#### 任务

为下单云函数编写测试，用 `jest.mock` 替换 wx-server-sdk，覆盖：正常下单（金额与写库参数）、空购物车拒绝、无 OPENID 拒绝三个分支，并保证测试完全离线。

参考代码：

```ts
const addMock = jest.fn()

jest.mock('wx-server-sdk', () => ({
  init: jest.fn(),
  DYNAMIC_CURRENT_ENV: 'dynamic-env',
  getWXContext: jest.fn(),
  database: jest.fn(() => ({
    collection: jest.fn(() => ({ add: addMock })),
    serverDate: jest.fn(() => new Date('2026-10-09'))
  }))
}))

import cloud from 'wx-server-sdk'
import { main } from '../index'

beforeEach(() => {
  jest.clearAllMocks()
  ;(cloud.getWXContext as jest.Mock).mockReturnValue({
    OPENID: 'test-openid-001'
  })
  addMock.mockResolvedValue({ _id: 'order-1001' })
})
```

#### 步骤约束

1. 成功分支必须同时断言返回值与 `add` 的写库参数（用 `expect.objectContaining`）。
2. 两个失败分支都必须验证 `add` 未被调用。
3. 金额用例必须包含一个易产生浮点尾差的组合（如 15.5 元）。
4. OPENID 通过 mock 注入固定值，禁止读真实环境。

#### 提交物

- 云函数 `index.ts` 与 `__tests__/index.test.ts`；
- 测试通过的终端输出。

#### 验收标准

- 三个分支全部通过，断言同时覆盖返回契约与数据库调用契约；
- 断网状态下测试仍可通过；
- 能口头解释工厂提升与 `mock` 前缀限制。

### 练习 3：automator E2E——登录到支付成功关键路径

#### 任务

编写一条 automator 端到端用例：以固定测试 code 启动小程序，进入指定测试店铺，加菜并提交订单，mock 支付为成功后断言支付成功页与订单状态；测试数据带 `e2e` 前缀并在结束时清理。

伪代码：

```text
launch(cliPath, projectPath)
mockWxMethod('login', { code: E2E_LOGIN_CODE })
reLaunch('/pages/shop-detail/shop-detail?id=shop_e2e_demo')
waitFor('.dish-item') → 点击首个 .add-btn → 点击 .cart-bar
waitFor('.order-confirm')
mockWxMethod('requestPayment', { errMsg: 'requestPayment:ok' })
点击 .pay-btn → waitFor('.pay-success')
断言 page.data('orderStatus') === 'paid'
cleanup：删除该测试 openid 下 tag=e2e 的订单
close()
```

#### 步骤约束

1. 连接信息（cliPath、code、管理凭证）全部来自环境变量，代码中不得出现任何密钥。
2. 所有等待必须是 `waitFor` 条件等待，不允许固定 sleep（等待工具启动除外）。
3. 必须连接测试环境，严禁指向生产云环境与真实 AppID。
4. 无论用例成功或失败都要执行数据清理与 `close`。

#### 提交物

- E2E 测试文件与清理脚本；
- 一次成功运行的完整日志；
- 关键步骤录屏（可选但建议）。

#### 验收标准

- 用例在开发者工具自动化下稳定通过，连续 3 轮结果一致；
- 支付未拉起真实收银台，测试后无残留订单；
- 全程无硬编码凭证。

## 阶段验收作业

本作业是 W16 结业里程碑的质量证据点：为「逛吃指南」建立分层自动化测试体系并接入 CI 门禁，使“交易关键路径不被改坏”从口头承诺变为可重复验证的客观事实。

### 任务描述

1. 盘点测试清单：列出交易主链路（进入店铺 → 加菜 → 下单 → 支付成功 → 订单状态；以及取消支付/退款申请的失败路径）的测试点，并标注每个测试点落在哪一层（单测/组件/E2E）。
2. 单元与组件层：为金额计算与订单状态机（或等价纯逻辑）、至少 2 个关键组件（建议 shop-card、购物车/订单卡片）补齐测试，组件测试须覆盖 properties 传入、事件 detail、条件渲染与 data 的行为变化。
3. 云函数层：为下单云函数（及一个核心写操作云函数，如退款申请）补齐成功与失败分支测试，wx-server-sdk 全部 mock，OPENID 固定注入。
4. E2E 层：用 automator 覆盖“登录（mock code）→ 下单 → 支付（mock 成功）”整条关键路径，失败路径（支付取消）至少一条；完成测试数据隔离与清理。
5. CI 接入：配置门禁 workflow，单元/组件测试在 PR 必过，E2E 在独立 job 或定时任务执行；凭证仅使用 CI secrets。产出质量报告：用例数、通过率、覆盖率、连续 3 轮稳定性结果。

### 完成标准

- `npm test` 与 `npm run test:coverage` 在干净环境一键通过，覆盖率达到自设阈值且关键模块分支覆盖无明显缺口。
- 组件与云函数测试全部离线可重复，无真实网络、真实数据库、真实支付依赖。
- E2E 关键路径在开发者工具自动化下连续 3 轮通过，测试后无数据残留。
- CI 实际运行并留下记录（workflow 链接或日志），仓库内无任何硬编码密钥。
- 关键路径有发布后监控手段（错误捕获、日志或看板），并写明灰度期关注的指标与回退触发条件。

### 强制不通过条件

- E2E 触发了真实支付或真实资金变动，或测试连接生产环境、生产 AppID；
- 仓库（含测试代码、配置、日志截图）中出现硬编码 AppSecret、上传私钥、管理凭证等敏感信息；
- 断言基于实现细节（断言 `setData` 调用、私有方法调用）而非可观察行为，且拒不修改；
- 测试不可重复：依赖执行顺序、真实网络/时间，或同一代码连续运行结果不一致且未治理；
- 只有测试文件但 CI 从未实际运行，或门禁可被随意跳过且无说明；
- 关键路径（下单/支付成功）没有任何一层测试覆盖，或用例无有效断言（绿但不验证行为）；
- 无法解释测试金字塔分层、mock/stub 区别或支付 mock 的边界。
